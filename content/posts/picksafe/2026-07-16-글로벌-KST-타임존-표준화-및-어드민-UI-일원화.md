"사용자가 오늘 오후 2시에 제품을 스캔했는데, 마이페이지에는 '어제 스캔함'으로 나옵니다."
"배치 스크립트가 왜 한창 유저가 몰리는 목요일 오전 9시에 돌아서 DB CPU 부하를 주나요?"

서비스 규모가 커지고 클라우드 기반 인프라를 도입하면서 한 번쯤 마주치게 되는 단골 문제가 있습니다. 바로 **타임존(Timezone) 불일치**입니다. 

PickSafe 개발팀은 최근 클라우드 호스팅 서버(Render)와 매니지드 DB(Neon DB)를 도입하는 과정에서, 인프라의 기본 타임존인 **UTC(협정 세계시, +00:00)**와 실제 사용자의 타임존인 **KST(한국 표준시, +09:00)**의 괴리로 인해 비즈니스 로직과 데이터 정합성, 그리고 어드민 UI 전반에 걸쳐 예상치 못한 이슈들을 마주했습니다. 

단순히 "시간에 9시간을 더하면 끝나는 것 아닌가?"라고 생각하기 쉽지만, 엔지니어링 관점에서는 그렇게 단순하지 않습니다. 시스템의 확장성(Scalability)을 해치지 않으면서, 데이터의 정합성을 보장하고, 개발자 생산성까지 유지할 수 있는 아키텍처적 해결책을 치열하게 고민했습니다. 

우리가 직면했던 문제와 대안, 그리고 최종 해결 과정을 공유합니다.

---

## 1. 문제 정의 (Problem)

클라우드 네이티브 환경으로 이관한 후, 시스템 전반에서 세 가지 주요 문제가 발생했습니다.

### ① 시간대 왜곡으로 인한 사용자 경험(UX) 저하
유저가 한국 시간(KST) 오후 2시(14:00)에 식품 성분을 스캔하면, DB에는 UTC 기준 오전 5시(05:00)로 저장되었습니다. 이 값이 가공 없이 클라이언트에게 노출되면서, 유저는 방금 완료한 활동을 "어제 완료한 행동"으로 인지하거나 몇 시간 전 기록으로 보게 되는 혼란을 겪었습니다.

### ② 배치 스케줄러 실행 시점의 불일치와 DB 부하
식약처 성분 데이터를 매일 동기화하는 중요 배치 스케줄러가 존재합니다. 서비스 영향도가 가장 적은 **KST 자정(00:00)**에 실행되도록 의도했으나, 서버의 시스템 타임존이 UTC인 탓에 **UTC 자정(KST 오전 9시)**에 배치가 실행되었습니다. 결과적으로 출근 시간 트래픽 피크 타임에 대규모 배치 작업이 겹쳐 시스템 자원(DB CPU)에 병목이 발생했습니다.

### ③ 일관성 없는 어드민 UI/UX
어드민 관리 도구 내에서 날짜가 ISO 8601 포맷, `YYYY-MM-DD HH:MM:SS`, 상대 시간(예: 3시간 전) 등으로 제각각 표현되고 있었습니다. 이로 인해 운영팀이 CS 문의에 대응하거나 데이터를 모니터링할 때 시간 계산 오류가 빈번히 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 세 가지 아키텍처적 방향성을 두고 비교 검토했습니다.

| 비교 항목 | Option A: 인프라 자체를 KST로 변경 | Option B: DB는 UTC 유지, App/UI 레이어에서 변환 (채택) | Option C: 클라이언트 측에서 모든 타임존 변환 처리 |
| :--- | :--- | :--- | :--- |
| **작업 공수** | 매우 낮음 (설정 한 줄 변경) | 보통 (통합 헬퍼 및 데코레이터 개발 필요) | 높음 (모든 프론트엔드 코드 수정 필요) |
| **글로벌 확장성** | 나쁨 (추후 글로벌 진출 시 전체 재수정 필요) | 매우 우수 (국가별 로컬 타임존 유연 대처 가능) | 우수 |
| **데이터 정합성** | 보통 (DB 인스턴스 이관 시 이슈 발생 가능) | 높음 (ISO 표준 준수 및 일관된 UTC 저장) | 낮음 (사용자 기기 설정에 따라 왜곡 가능) |

### 왜 Option B를 선택했는가?
* **글로벌 스탠다드 준수**: 인프라(OS, DB) 자체의 시간대를 강제로 KST로 맞추는 것(Option A)은 당장은 편하지만, 멀티 리전이나 글로벌 서비스를 지향할 때 기술 부채가 됩니다. 데이터베이스에는 항상 절대 표준시인 **UTC로 저장하고 읽는 것을 원칙**으로 삼았습니다.
* **사용자 기기 의존도 배제**: 클라이언트 브라우저 설정에만 시간 변환을 의존(Option C)할 경우, 기기 시간이 잘못 설정된 유저에게는 데이터가 왜곡되어 노출될 위험이 있었습니다.
* **결론**: 백엔드 API 레이어를 **'단일 진실 공급원(Single Source of Truth)'**으로 정의하고, 입출력(Input/Output) 경계에서 KST 변환을 보장하는 파이프라인을 구축하기로 결정했습니다.

## 3. 최종 해결 및 구현 (Implementation)

문제를 해결하기 위해 백엔드, 데이터베이스, 프론트엔드 전반에 걸쳐 표준화된 타임존 변환 전략을 적용했습니다.

### ① 백엔드 KST 타임존 변환 표준화 (FastAPI)
백엔드 전역에서 오차 없이 작동할 수 있도록 `timezone(timedelta(hours=9))` 상수를 정의하고, 날짜/시간 데이터를 직렬화(Serialization)할 때 KST 변환을 강제 처리하는 유틸리티 기능을 도입했습니다.

```python
# [보안 필터링 및 단순화된 예시 코드]
from datetime import datetime, timezone, timedelta

# KST 타임존 상수 정의
_KST = timezone(timedelta(hours=9))

def convert_to_kst(dt: datetime) -> datetime:
    """모든 나이브/어웨어 datetime 객체를 정확한 KST 시간대로 변환합니다."""
    if not dt:
        return dt
    if dt.tzinfo is None:
        # 정보가 없는 경우 UTC로 가정 후 KST로 변환
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(_KST)

# API Response 예시: 클라이언트가 즉시 읽을 수 있는 포맷으로 제공
def format_datetime_response(dt: datetime) -> str:
    return convert_to_kst(dt).strftime('%Y-%m-%d %H:%M:%S')
```

### ② 데이터베이스(Neon DB) 저장 표준 수립
SQLAlchemy 및 DB 드라이버 레벨에서 시스템 시간(`now()`)을 호출할 때 서버 기준이 아닌, 표준 UTC로 명시하여 적재하도록 일관성을 부여했습니다. 조회 시에는 저장된 UTC 시간을 위 헬퍼 함수를 통해 KST로 변환하여 응답합니다.

```python
# DB 적재 시에는 언제나 표준 시간대를 유지하도록 보장
created_at = Column(DateTime(timezone=True), server_default=func.now())
```

### ③ 프론트엔드 및 어드민 디자인 시스템 포맷터 일원화
사용자와 운영진이 직관적으로 시간을 인지할 수 있도록 시간 포맷을 일원화하고 디자인 컴포넌트를 표준화했습니다.

* **상대 시간 표준화**: 당일 기록은 `"오늘 14:30"`, 이전 기록은 `"08.28 14:30"`과 같이 직관적인 KST 기준 상대 시간 포맷으로 UI를 통일했습니다.
* **어드민 컴포넌트 표준화**: 대시보드, 성분 수집 현황, 에러 로그 모니터링 등 개별 어드민 페이지에서 들쭉날쭉하던 아이콘 세트와 카드 컴포넌트를 정렬하여 일관된 뷰를 구축했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 타임존 표준화 및 어드민 리팩토링 작업을 통해 팀이 얻은 교훈은 명확합니다.

1. **타임존은 시스템 설계 초기단계부터 정의되어야 한다**:
   인프라가 로컬 환경에서 클라우드로 넘어가는 과정에서 타임존은 가장 먼저 깨지기 쉬운 고리입니다. 시스템의 "시간 원칙(Time Principle)"을 초기에 명확히 세워두어야 추후 비즈니스 로직 수정에 따른 막대한 리팩토링 비용을 막을 수 있습니다.

2. **서버-클라이언트 간 계약(Contract)의 중요성**:
   "서버는 무조건 UTC 데이터셋을 보장하고, 클라이언트에게 응답을 주기 바로 직전(API Presentation 레이어)에 로컬 시간대로 최종 변환한다"는 단 하나의 규칙을 세움으로써 커뮤니케이션 비용과 버그 추적 비용을 대폭 줄일 수 있었습니다.

3. **일관된 도구(UI)가 비즈니스 효율을 극대화한다**:
   어드민 UI 리팩토링을 통해 단순히 이쁘고 깔끔한 화면을 만든 것에 그치지 않고, 운영진의 휴먼 에러(날짜 오독으로 인한 잘못된 데이터 적재 등)율을 0%에 가깝게 낮추는 정량적 성과를 만들어 냈습니다.

인프라의 확장성을 지키면서도 사용자의 친숙함을 잃지 않는 것, 이것이 PickSafe가 기술적 타협점(Trade-off)을 찾고 최선의 결과를 만들어가는 방식입니다.
