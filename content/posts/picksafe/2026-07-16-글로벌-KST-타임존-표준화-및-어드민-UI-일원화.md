안녕하세요. PickSafe 백엔드/프론트엔드 엔지니어링 팀입니다. 

서비스를 글로벌 클라우드 인프라(Render, Neon DB 등)에 배포하고 운영하다 보면, 한 번쯤 마주치게 되는 고질적인 문제가 있습니다. 바로 **'타임존(TimeZone) 불일치'** 문제입니다. 

이번 포스팅에서는 서버 기본 설정인 UTC와 비즈니스 요구사항인 KST(한국 표준시) 사이의 간극을 메우기 위해 어떤 기술적 고민을 했고, 어떻게 시스템 전체의 시간 표준화와 어드민 UI를 일원화했는지 그 과정을 공유해 드립니다.

---

## 1. Problem: 클라우드 시대의 은밀한 적, UTC와 KST의 충돌

최신 클라우드 플랫폼과 매니지드 DB 서비스는 기본적으로 전 세계 표준인 **UTC(협정 세계시, +00:00)**를 기준으로 동작합니다. 우리 서비스 역시 별도의 타임존 설정 없이 기본값을 그대로 사용하고 있었습니다. 그러다 보니 다음과 같은 치명적인 문제들이 연쇄적으로 발생했습니다.

1. **사용자 경험(UX) 저해**: 사용자가 한국 시간(KST) 기준 오후 2시에 주요 액션을 완료했음에도, 마이페이지나 어드민 로그에는 9시간이 지난 오전 5시(UTC)로 기록되었습니다. 직관적으로 "방금 전"이어야 할 데이터가 "어제"로 표기되거나 혼란을 주는 상황이 빈번했습니다.
2. **배치 스케줄러 오작동**: 식약처 성분 데이터 등 일일 수집을 담당하는 배치 스케줄러가 KST 자정이 아닌, UTC 자정(한국 시간 기준 오전 9시)에 구동되었습니다. 이는 트래픽이 몰리는 피크 타임과 겹쳐 시스템 부하를 가중시키는 원인이 되었습니다.
3. **어드민 파편화**: 어드민 페이지마다 개발 시점에 따라 시간 포맷(ISO 8601, `YYYY-MM-DD HH:MM`, 혹은 제각각의 상대 시간)과 아이콘 세트가 달라, 운영 관리자의 피로도가 누적되고 있었습니다.

---

## 2. Trade-off & Architecture: 어떻게 시간을 정렬할 것인가?

문제를 해결하기 위해 두 가지 대안을 놓고 고민했습니다.

* **대안 A: DB 자체의 타임존을 KST(+09:00)로 변경**
  * *장점*: 애플리케이션 단에서 별도의 변환 로직을 거치지 않고 바로 조회 가능.
  * *단점*: 글로벌 확장성을 고려할 때 DB 서버의 타임존을 특정 지역(KST)에 종속시키는 것은 향후 서비스 지역 확장 시 마이그레이션 지옥을 유발할 수 있음. 또한 많은 클라우드 DB 매니지드 서비스가 UTC 기준 운영을 권장함.
* **대안 B: 영속성(Storage)은 UTC를 유지하되, 애플리케이션 계층에서 KST 변환 레이어 표준화 (선택)**
  * *장점*: DB 표준(UTC)을 준수하여 글로벌 확장성 확보, 데이터 무결성 유지.
  * *단점*: API 응답 및 직렬화 과정에서 휴먼 에러가 발생하지 않도록 철저한 헬퍼 함수 표준화 필요.

우리는 **대안 B**를 선택했습니다. 데이터는 안전하게 UTC로 적재하되, 비즈니스 로직과 사용자 접점에서는 일관된 KST 규격을 강제하기로 했습니다.

---

## 3. Solution: 백엔드 타임존 헬퍼 표준화와 어드민 리팩토링

### 3.1. 백엔드 타임존 변환 헬퍼 표준화 (FastAPI / Python)
애플리케이션 전역에서 사용할 수 있는 KST 타임존 상수를 정의하고, 날짜/시간 직렬화 시 이를 강제하는 패턴을 도입했습니다.

```python
from datetime import datetime, timezone, timedelta

# KST 타임존 상수 정의 (+09:00)
_KST = timezone(timedelta(hours=9))

# DB 적재 시: UTC 기준 함수 사용 (예: server_default=func.now())
# API 응답 및 UI 직렬화 시: KST 변환 적용 예시
def format_kst(dt: datetime) -> str:
    if not dt:
        return ""
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(_KST).strftime('%Y-%m-%d %H:%M:%S')
```

모든 API 응답 스키마와 로그 포맷터가 위 컨벤션을 따르도록 코드를 정비하여, 개발자가 의도치 않게 UTC 시간을 노출하는 실수를 원천 차단했습니다. 또한 수집 스케줄러 역시 KST 기준 자정에 정확히 동작하도록 트리거 타임을 재조정했습니다.

### 3.2. 어드민 UI 및 컴포넌트 일원화
타임존 정비와 더불어, 백오피스(어드민)의 파편화된 사용자 경험을 개선했습니다.
* 대시보드, 성분 수집 현황, 번역 관리, 방문자 통계, 1:1 문의 등 분산되어 있던 관리 모듈의 아이콘 세트와 카드 컴포넌트를 디자인 시스템 기준으로 일원화했습니다.
* CAS 번호 자동 보강 작업 내역 및 오류 관리 목록 테이블의 시간 포맷을 `"오늘 14:30"` 혹은 `"MM.DD HH:MM"`과 같은 직관적인 KST 상대 시간 포맷으로 리팩토링하여 운영 효율성을 극대화했습니다.

---

## 4. Takeaway: 엔지니어링 교훈

1. **타임존은 초기에 잡아야 한다**: 서비스가 성장한 뒤에 타임존 정책을 바꾸는 것은 데이터 마이그레이션과 API 규격 수정이라는 큰 비용을 치르게 합니다. 글로벌 인프라를 활용할 때 DB는 UTC, 서비스 레이어는 로컬 타임(KST)으로 분리하는 원칙을 초기부터 세우는 것이 중요합니다.
2. **개발자 경험(DX)이 곧 운영 효율성이다**: 백엔드의 타임존 헬퍼 표준화와 프론트엔드의 디자인 시스템 일원은 단순한 시각적 개선을 넘어, 장애 요소를 줄이고 비즈니스 로직에만 집중할 수 있는 튼튼한 토대를 만들어 주었습니다.

PickSafe 팀은 앞으로도 안정적이고 직관적인 기술 인프라를 바탕으로 고품질의 서비스를 제공해 나가겠습니다. 감사합니다.
