안녕하세요, PickSafe 백엔드/프론트엔드 엔지니어링 팀입니다. 

서비스를 글로벌 클라우드 인프라(PaaS 및 매니지드 DB)에 배포하고 운영하다 보면, 인프라의 기본 설정과 비즈니스 요구사항 간의 미묘한 차이로 인해 예상치 못한 레벨의 기술적 부채를 마주하곤 합니다.

이번 포스팅에서는 **클라우드 서버의 기본 UTC 타임존과 한국 사용자/관리자 중심의 KST(한국 표준시) 간의 괴리**로 인해 발생했던 문제들을 정의하고, 이를 전사적으로 해결하기 위해 적용한 아키텍처적 접근과 UI 일원화 과정을 공유하고자 합니다.

---

## 1. 문제 정의 (Context): "왜 시간이 다르게 보일까?"

프로덕션을 클라우드 환경에 배포한 직후, 사용자 피드백과 내부 모니터링을 통해 다음과 같은 크리티컬한 문제점들이 수면 위로 떠올랐습니다.

1. **시간 불일치로 인한 UX 저하**
   * 서버 및 DB의 시스템 타임존이 `UTC (+00:00)`로 설정되어 있어, 사용자가 오후 2시(14:00 KST)에 수행한 액션이 마이페이지와 어드민 로그에 오전 5시(05:00 UTC)로 기록되었습니다. 이로 인해 "방금 완료한 작업이 어제 일로 표기"되거나 "시간순 정렬이 어그러지는" 심각한 혼선이 발생했습니다.
2. **배치 스케줄러의 실행 시점 왜곡**
   * 식약처 성분 데이터 등 핵심 일일 수집 배치 스케줄러가 비즈니스 로직상 반드시 수행되어야 하는 KST 자정이 아닌, UTC 자정(즉, 한국 시간 오전 9시)에 구동되었습니다. 이는 트래픽이 집중되는 피크 타임과 겹쳐 시스템 부하를 가중시키는 원인이 되었습니다.
3. **어드민 프론트엔드의 파편화된 시간 포맷 및 UI**
   * 초기 속도 중심의 개발로 인해 각 어드민 페이지(대시보드, 성분 수집, 번역 관리, 방문자 통계, 1:1 문의 등)마다 시간 표기 방식(ISO 8601, YYYY-MM-DD HH:MM, 상대 시간 등)과 아이콘 세트가 제각각이었습니다. 이는 관리자의 인지 부하를 높이고 운영 효율성을 떨어뜨렸습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

타임존 문제를 해결하기 위해 엔지니어링 팀 내부에서 크게 두 가지 대안을 놓고 논의를 진행했습니다.

### 대안 A: DB 서버 및 백엔드 운영체제 전체의 시스템 타임존을 KST로 변경
* **장점**: 코드 레벨의 변환 로직 없이 데이터베이스에 저장되는 시점부터 KST가 적용되어 직관적임.
* **단점**: 
  * 매니지드 클라우드 DB 서비스의 특성상 시스템 타임존 변경이 불가능하거나 제한적인 경우가 많음.
  * 추후 글로벌 확장(예: 동남아, 미주 등 다중 타임존 서비스)을 고려할 때, DB 레벨의 타임존 고정은 확장성을 심각하게 저해하는 안티패턴임.

### 대안 B: DB는 표준인 UTC(또는 인프라 기본값)를 유지하고, 애플리케이션 계층에서 KST 변환 레이어 표준화 (선택)
* **장점**: 
  * 인프라 변경에 독립적이며, 향후 다중 타임존 확장성 확보 가능.
  * 글로벌 스탠다드인 UTC 기반 데이터 적재 원칙을 준수하면서, 클라이언트 인터페이스에서만 정확한 비즈니스 시간(KST) 보장.
* **단점**: 개발자가 API 응답 및 직렬화 과정에서 의도적으로 변환 로직을 거치도록 강제하는 컨벤션 관리가 필요함.

팀은 **확장성과 데이터 정합성의 원칙**을 지키기 위해 **[대안 B]**를 최종 채택했습니다.

## 3. 최종 해결 및 엔지니어링 구현

### 3.1. 백엔드 KST 타임존 변환 헬퍼 및 직렬화 표준화
FastAPI 백엔드 전역에서 날짜와 시간을 다룰 때 일관된 변환을 보장하기 위해, 공통 타임존 상수(`_KST`)를 정의하고 API 응답 직렬화 직전에 KST 변환을 거치도록 파이프라인을 구축했습니다.

```python
from datetime import datetime, timedelta, timezone

# 1. 백엔드 전역 KST 타임존 상수 정의 (UTC +9)
_KST = timezone(timedelta(hours=9))

# 2. API 응답 포맷팅 헬퍼 예시
def format_to_kst(dt: datetime | None) -> str | None:
    if not dt:
        return None
    # DB에 저장된 무중력(Naive) 또는 UTC 타임스탬프를 KST로 변환 후 문자열 포맷팅
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(_KST).strftime('%Y-%m-%d %H:%M:%S')
```

* **DB 저장 표준**: 데이터 적재 시에는 ORM의 서버 기본값(`server_default=func.now()`)을 활용해 UTC 기준 시각을 안전하게 적재합니다.
* **API 및 UI 응답 표준**: 클라이언트로 향하는 모든 데이터는 `astimezone(_KST)`를 경유하여 일관된 KST 문자열 혹은 타임스탬프로 변환되도록 강제했습니다.

### 3.2. 어드민 디자인 시스템 및 UI/UX 일원화
백엔드의 시간 정합성 확보와 동시에, 분산되어 있던 어드민 프론트엔드의 컴포넌트를 리팩토링했습니다.
* **상대 시간 포맷 통일**: 관리자가 직관적으로 로그를 파악할 수 있도록 `"오늘 14:30"`, `"08.28 14:30"` 형태의 직관적인 KST 상대 시간 포맷터 컴포넌트를 공통화했습니다.
* **디자인 컴포넌트 표준화**: 대시보드, 성분 수집, 번역 관리, 방문자 통계 등 각 모듈에 산재해 있던 아이콘 세트와 카드 컴포넌트를 단일 디자인 시스템으로 통합하여 관리자 경험(Admin UX)을 극적으로 개선했습니다.

---

## 4. Takeaway (배운 점)

1. **인프라 타임존에 의존하지 않는 설계의 중요성**
   * 클라우드 환경에서 서버의 기본 타임존(UTC)을 무작정 바꾸려 하기보다, **"저장은 표준(UTC), 표현은 로컬(KST)"**이라는 아키텍처 원칙을 지키는 것이 장기적인 확장성 면에서 훨씬 안전하다는 것을 다시 한번 확인했습니다.
2. **컨벤션의 코드화**
   * 타임존 변환 같은 전역적인 규칙은 문서로만 공유하기보다, 공통 헬퍼 함수나 미들웨어/시리얼라이저 레벨에서 강제할 수 있도록 코드로 녹여내야 휴먼 에러를 방지할 수 있습니다.

이번 개선을 통해 PickSafe는 사용자 화면 및 어드민 전반에서 **정확한 한국 표준시(KST) 표기 100% 일치**를 달성했으며, 배치 스케줄러의 정합성까지 확보하여 더욱 안정적인 서비스를 제공할 수 있게 되었습니다. 

앞으로도 견고한 엔지니어링을 바탕으로 신뢰할 수 있는 서비스를 만들어 나가겠습니다. 감사합니다.
