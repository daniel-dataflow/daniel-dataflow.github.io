외부 공공 API 데이터를 주기적으로 동기화하는 시스템을 구축해 본 개발자라면 한 번쯤 고민해 보았을 주제가 있습니다. **"수시로 업데이트되거나 원천 데이터 변경이 발생하는 외부 데이터셋을, 실운영 서비스의 RDB 참조 관계를 깨뜨리지 않고 어떻게 안전하게 반영할 것인가?"**

PickSafe 팀은 최근 식약처 성분 데이터 수집 파이프라인을 재설계하면서, 기존 데이터베이스의 외래키(FK) 무결성을 100% 보장하는 동시에 데이터 검증 및 보강 프로세스를 비동기화하는 **Staging & Merge 아키텍처**를 도입했습니다.

이번 포스팅에서는 우리가 마주했던 기술적 위협과 이를 해결하기 위한 대안 비교, 그리고 최종 아키텍처 수립을 통해 얻은 엔지니어링 교훈을 공유합니다.

---

## 1. 문제 정의: 레거시 동기화 방식과 FK Corruption 위험

기존 성분 데이터 수집 파이프라인은 외부 API로부터 데이터를 수집할 때 실운영 테이블(`ingredients_master`)을 **직접 덮어쓰거나(Bulk Overwrite), 전체 삭제 후 재적재(Drop & Re-create)** 하는 방식으로 작동했습니다.

초기 단독 테이블 형태일 때는 문제가 없었으나, 서비스가 성장함에 따라 `ingredients_master`는 주요 도메인 모델들과 복잡한 참조 관계(Foreign Key)를 맺게 되었습니다.

```
[user_allergens] ------------+
                             | (FK: ingredient_id)
[product_ingredients] -------+---> [ingredients_master]
                             |
[scan_result_ingredients] ---+
```

이 구조에서 외부 데이터 동기화 시 행(Row)을 통째로 재생성하거나 UUID(`id`)를 교체(Swap)할 경우, 다음과 같은 치명적인 문제가 발생합니다.

1. **사용자 도메인 오염**: 유저가 설정한 알레르기 기피 성분의 UUID가 엉뚱한 성분을 가리키거나 `NULL` 처리됨.
2. **히스토리 유실**: 과거 사용자가 스캔했던 제품의 성분 매칭 분석 결과 기록이 상실됨.
3. **참조 무결성 붕괴(FK Corruption)**: RDB 차원의 참조 제약 조건 위반 에러로 인해 전체 동기화 트랜잭션이 중단됨.

핵심 과제는 **"운영 중인 DB의 식별자(UUID)를 고정 보존하면서, 외부 API 데이터의 신규 추가(INSERT) 및 변경 사항(UPDATE)만 정교하게 추출하여 반영하는 시스템"**을 구축하는 것이었습니다.

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 크게 세 가지 접근 방식을 검토했습니다.

### 대안 A: 데이터베이스 테이블 스왑 (Blue/Green Table Swap)
- **방식**: 임시 테이블에 새 데이터를 적재한 후, RDB의 `RENAME TABLE` 구문으로 실운영 테이블과 원샷 교체.
- **장점**: 구현이 비교적 간단하고 동기화 순간의 읽기 락(Read Lock) 시간을 최소화함.
- **단점**: 기존 테이블의 UUID를 참조하던 타 테이블의 FK 제약 조건을 모두 해제했다가 재연결해야함. **FK Corruption 위험이 그대로 잔존**하며 실시간 서비스 환경에서는 채택 불가능.

### 대안 B: 인-플레이스 실시간 Upsert (Direct In-Place Upsert)
- **방식**: API 데이터를 수집하는 즉시 실운영 테이블에 `ON CONFLICT DO UPDATE` 구문으로 반영.
- **장점**: 별도의 중간 저장소가 필요 없어 구조가 단순함.
- **단점**: API 응답 데이터에 이상(필드 누락, 포맷 변경 등)이 있을 경우 **실운영 데이터가 즉시 오염됨**. 수집과 검증이 강하게 결합하여 데이터 품질을 사전 검수하기 어려움.

### 대안 C: Staging 테이블 도입 + 자연 키(Natural Key) 기반 트랜잭션 Merge (최종 선택)
- **방식**: 외부 데이터를 1차로 격리된 Staging 테이블에 적재 후, 상태 값(State) 관리를 통해 안전 검증을 거친 건만 자연 키 기준으로 실운영 테이블에 병합(Merge).
- **장점**:
  - 실운영 데이터와 외부 수집 영역의 완전한 격리.
  - 기존 PK(UUID)를 100% 보존하여 FK 참조 무결성 유지.
  - 데이터 품질 검수 및 사후 비동기 데이터 보강 패턴 적용 가능.
- **단점**: Staging 테이블 관리에 따른 추가 저장 공간 및 상태 변화(State Machine) 로직 작성 비용 발생.

저희는 **데이터의 안정성과 무결성이 오버헤드보다 훨씬 중요하다**고 판단하여 **대안 C**를 선택했습니다.

## 3. 최종 해결 방안 및 시스템 아키텍처

### 3.1 파이프라인 개요

전체 데이터 흐름은 **[수집/격리] -> [상태 평가] -> [트랜잭션 병합] -> [비동기 보강]**의 4단계로 연동됩니다.

```
[외부 API] ──(1. 수집)──> [Staging Table] ──(2. 검증/상태 부여)
                                 │
                        (3. 어드민 승인 & Merge)
                                 ▼
                     [Master DB (UUID 유지)]
                                 │
                   (4. 비동기 CAS 보강 배치)
                                 ▼
                     [공인 사전 딜레이 크롤링]
```

### 3.2 핵심 메커니즘

#### ① 상태 기반 Staging 격리 (State Machine)
수집된 데이터는 실운영 테이블 대신 `ingredients_master_staging`에 먼저 저장되며, 각 행은 다음과 같은 라이프사이클 상태를 가집니다.

- `pending`: 필수 명칭(국문명, INCI명)이 정상 입력되어 운영 DB로 병합 가능한 상태.
- `error`: 필수 데이터가 누락되어 어드민의 수동 검토가 필요한 상태.
- `suggested`: 백그라운드 배치가 추측/보완한 유효 데이터 상태.
- `merged`: 실운영 DB로 성공적으로 병합 완료되어 이력이 보존된 상태.

#### ② 자연 키(`inci_name`) 기반의 UUID 보존 Upsert
실운영 테이블과의 병합 시, 변하지 않는 국제 표준 명칭인 **`inci_name`을 자연 키(Natural Key) 매칭 기준**으로 활용합니다.

- **기존 데이터 존재 시**: **기존 UUID(id)를 절대 변경하지 않고**, 가변적인 메타데이터(국문명, 규제 정보 등)만 `UPDATE`합니다.
- **신규 데이터 시**: 새로운 UUID를 생성하여 `INSERT`합니다.
- **원자성 보장**: 병합 작업은 단일 DB 트랜잭션으로 실행되어 단 하나의 에러라도 발생할 경우 전체 롤백됩니다. 성공 시에는 조회 성능 향상을 위한 캐시 인벌리데이션(Cache Invalidation) 및 재빌드가 트리거됩니다.

#### ③ 비동기 사후 데이터 Enrichment (CAS 번호 보강)
화학물질 고유 번호인 CAS 번호가 누락되어도 성분 명칭이 명확하다면 먼저 서비스를 가동할 수 있도록 **데이터 결합도를 낮췄습니다.**

- 수집 시점에는 CAS 번호 유무와 상관없이 정상 명칭이면 `pending` 처리하여 실운영에 즉시 반영합니다.
- 이후 백그라운드 스케줄러가 운영 DB 내 `cas_no IS NULL`인 항목을 탐색하여, 외부 공인 성분 사전과 연동해 사후 보강합니다.
- 외부 요청 시 **Rate Limiting(1초 딜레이)**을 적용하여 타 서비스에 피해를 주지 않도록 설계했으며, 보강 결과는 어드민 승인을 거치도록 `suggested` 상태로 안전하게 큐잉됩니다.

#### ④ 휴먼 에러 방지를 위한 안전한 Admin UX & API 설계
고위험 작업(데이터 초기화/비우기) 실행 시 인적 실수를 방지하도록 API와 UI 차원의 안전장치를 마련했습니다.

- 데이터 삭제 API의 파라미터(`target_table`) 기본값을 항상 **`Staging`**으로 국한했습니다.
- 어드민 대시보드에 **[실운영 성분 수]**와 **[Staging 대기 수]**를 이중 메트릭 카드로 동시에 노출하여, 현재 파이프라인의 동기화 상태를 한눈에 파악할 수 있는 관찰 가능성(Observability)을 확보했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

이번 Staging & Merge 아키텍처 재설계를 통해 팀이 얻은 핵심 레슨은 다음과 같습니다.

1. **RDB의 PK/UUID는 도메인 고유의 정체성(Identity)이다**  
   외부 시스템 데이터 동기화의 편의성을 위해 DB 내부의 Primary Key를 손대는 것은 시한폭탄을 안고 가는 것과 같습니다. 자연 키(Natural Key)를 활용한 Upsert 패턴을 통해 식별자 불변성을 지키는 것이 데이터 무결성의 핵심입니다.

2. **수집(Ingestion)과 검증(Validation)의 분리**  
   데이터를 가져오는 행위와 운영 DB에 적용하는 행위를 분리(Staging)하면, 외부 파이프라인 장애나 원천 데이터의 이상 유무가 실운영 서비스로 전파되는 것을 완벽히 차단할 수 있습니다.

3. **안전한 시스템은 UI/UX 디자인에서 완성된다**  
   기술적 안전장치만큼이나 어드민 사용자의 파괴적인 동작(Purge/Reset)에 대한 Defaults-Safe 디자인(기본값을 안전한 임시 영역으로 설정)이 시스템 안정성 유지에 결정적인 역할을 합니다.
