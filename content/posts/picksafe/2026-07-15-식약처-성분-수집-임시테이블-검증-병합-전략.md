안녕하세요. PickSafe 팀의 백엔드 엔지니어입니다.

저희 PickSafe 서비스의 핵심 가치는 **"사용자에게 안전한 성분 정보를 제공하는 것"**입니다. 이를 위해 공공기관(식약처 등)에서 제공하는 대용량 성분 API 데이터를 주기적으로 동기화하여 최신 상태를 유지하고 있습니다. 

하지만 서비스 규모가 커지고 데이터 간의 관계가 복잡해지면서, 단순히 "데이터를 긁어와서 덮어쓰는 것"만으로는 해결할 수 없는 심각한 데이터 아키텍처적 도전에 직면하게 되었습니다. 

오늘은 실운영 환경에서 **단 1%의 데이터 무결성 붕괴도 허용하지 않으면서, 대용량 외부 데이터를 안전하게 수집하고 정제하여 병합(Merge)하는 시스템을 구축한 여정**을 공유하고자 합니다.

---

## 1. 문제 정의: "데이터 동기화가 사용자 데이터를 파괴한다?"

기존 시스템은 식약처 API 데이터를 수집할 때, 실운영 테이블(`ingredients_master`)을 완전히 비우고 새로 적재(Truncate & Insert)하거나 단순 덮어쓰기(Overwrite) 방식을 취했습니다. 초기 개발 단계에서는 문제가 없었지만, 서비스가 고도화되면서 이 방식은 시한폭탄과 같았습니다.

이유는 **외래 키(Foreign Key) 참조 관계**에 있었습니다.

```
[ingredients_master (성분 마스터)] <--- (ID 참조) --- [user_allergens (사용자 기피 성분)]
                                 <--- (ID 참조) --- [product_ingredients (제품 성분)]
                                 <--- (ID 참조) --- [scan_results (스캔 매칭 히스토리)]
```

운영 테이블의 레코드가 삭제되거나, 새로 동기화되는 과정에서 행의 UUID(`id`)가 변경되면 다음과 같은 치명적인 문제가 발생합니다.

1. **외래 키 제약 조건(FK Constraint) 충돌**: 참조 중인 자식 데이터가 있어 테이블 비우기(Truncate) 자체가 실패합니다.
2. **참조 무결성 붕괴**: 만약 제약 조건을 임시 해제하고 데이터를 임의로 갈아끼운다면, 사용자가 등록해 둔 '기피 성분'이 엉뚱한 성분을 가리키거나, 과거 스캔 기록의 UUID 매칭이 깨져 오작동을 일으킵니다.

즉, **실운영 테이블의 기존 UUID를 고정 보존하면서 신규 데이터만 안전하게 Upsert(Update + Insert)할 수 있는 새로운 아키텍처**가 절실했습니다.

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 저희 팀은 세 가지 방향성을 두고 치열하게 논의했습니다.

### 대안 A: API 호출 시마다 운영 DB 직접 조회 및 업데이트 (In-place Sync)
* **방식**: API 데이터를 한 행씩 읽으며 운영 DB에 존재하는지 확인하고, 있으면 UPDATE, 없으면 INSERT를 수행합니다.
* **장점**: 별도의 임시 테이블이 필요 없어 단순합니다.
* **단점**: 네트워크 I/O 및 커넥션 점유 시간이 길어져 DB 성능에 부하를 줍니다. 수집 중 에러가 발생했을 때 중간 지점부터 복구(Rollback)하기가 매우 까다롭습니다.

### 대안 B: 데이터베이스 수준의 테이블 스왑 (Table Swapping)
* **방식**: 임시 테이블에 데이터를 다 받고, 운영 테이블과 이름을 바꿉니다 (`RENAME TABLE`).
* **장점**: 전환 속도가 매우 빠릅니다.
* **단점**: UUID가 완전히 새로 생성되므로 기존 자식 테이블들의 외래 키 참조 관계가 모두 깨집니다. 우리 상황에서는 채택 불가능했습니다.

### 대안 C: 임시 스테이징 테이블 도입 및 자연 키 기반 병합 (선택)
* **방식**: 완충 지대 역할을 하는 임시 테이블(`Staging`)에 데이터를 1차 적재한 뒤, 검증을 거쳐 **자연 키(Natural Key)**를 기준으로 운영 테이블에 트랜잭션 병합을 수행합니다.
* **장점**: 운영 테이블의 UUID를 완벽히 보존할 수 있으며, 데이터 검증 단계(Validation Sandbox)를 둘 수 있어 운영 안정성이 극대화됩니다.
* **단점**: 병합 로직의 설계 공수가 다소 늘어납니다.

저희는 데이터 무결성과 서비스 안정성을 최우선 가치로 삼고, **대안 C(Staging & Merge 전략)**를 선택했습니다.

## 3. 최종 해결책: 안전한 병합을 위한 4단계 파이프라인

새롭게 설계한 아키텍처는 데이터 수집부터 검증, 병합, 사후 보강까지 이어지는 구조적인 파이프라인을 가집니다.

```
[식약처 API] 
     │ (1단계: 수집)
     ▼
[Staging Table] ── (2단계: 상태 기계 검증) ──► [pending / error / suggested]
     │ 
     │ (3단계: 자연 키 기반 Upsert 트랜잭션)
     ▼
[Master Table] ◄── (4단계: 백그라운드 Worker) ──► [외부 사전 크롤러]
```

### 1단계: 임시 스테이징 테이블 (`ingredients_master_staging`) 도입
API를 통해 수집된 데이터는 운영 테이블에 곧바로 영향을 주지 않고, 완충 지대인 스테이징 테이블에 우선 저장됩니다. 이때 레코드는 정교한 **유한 상태 기계(FSM)** 구조에 따라 아래 중 하나의 `status` 필드 값을 부여받습니다.

* `pending`: 필수 정보(국문명, INCI 영문명)가 모두 정상 기입되어 병합 대기 중인 상태.
* `error`: 필수 명칭이 누락되어 관리자의 검토가 필요한 상태.
* `suggested`: 수집 후 백그라운드 배치를 통해 보완 데이터가 확보된 상태.
* `merged`: 성공적으로 운영 테이블에 반영되어 보존 중인 상태.

### 2단계: 자연 키(`inci_name`) 기반의 트랜잭션 병합 (Upsert)
어드민이 **[병합 실행]**을 승인하면, `status == 'pending'` 상태인 데이터들만 실운영 테이블로 병합을 시도합니다.

* **자연 키(Natural Key) 매칭**: 화장품 성분의 국제 표준 명칭인 `inci_name`을 매칭 키로 활용합니다.
* **Upsert 메커니즘**:
  * 운영 테이블에 동일한 `inci_name`이 이미 존재한다면, **기존 UUID(PK)를 그대로 고정**하고 성분명, CAS 번호 등 변경된 필드만 `UPDATE`합니다. 이로써 사용자 기피 성분 등의 FK가 절대 깨지지 않습니다.
  * 존재하지 않는 신규 성분일 경우에만 새 UUID를 채번하여 `INSERT`합니다.
* **원자성 보장**: 이 모든 과정은 단일 데이터베이스 트랜잭션 범위 내에서 수행되며, 단 하나의 오류라도 발생 시 전체 롤백됩니다. 병합에 성공하면 정적 JSON 캐시를 강제로 재빌드하여 조회 성능을 유지합니다.

### 3단계: 가용성 극대화를 위한 사후 CAS 백그라운드 보강 배치
식약처 API 데이터 중에는 CAS 번호(화학물질 고유 번호)가 누락된 경우가 빈번히 발생합니다. 이로 인해 전체 데이터 수집이 블로킹되는 것을 막기 위해, 저희는 **"느슨한 동기화와 비동기 보강"** 전략을 취했습니다.

1. 명칭만 정상이라면 우선 `pending`으로 분류하여 실운영 테이블에 즉시 병합합니다.
2. 병합 완료 후, 백그라운드 스케줄러가 운영 테이블 내 `cas_no`가 `NULL`인 대상들을 추출합니다.
3. 대한화장품협회 사전을 자동 조회하는 크롤러를 **1초 간격의 딜레이(Rate Limiter)**를 두고 실행하여 대상 정보의 신뢰성을 확보하고 서버 부하를 최소화합니다.
4. 확보된 CAS 정보는 어드민 화면에 `suggested` 상태로 추천 처리되어, 관리자가 클릭 한 번으로 손쉽게 데이터를 보강할 수 있도록 유도합니다.

### 4단계: 휴먼 에러를 방지하는 방어적 UX 설계
시스템이 아무리 훌륭해도 운영자의 실수 한 번으로 운영 데이터가 유실될 수 있습니다. 이를 방지하기 위해 어드민 가드레일을 대폭 강화했습니다.

* **초기화 대상 토글 강제화**: 데이터 비우기(Reset) 요청 시, 대상 테이블(`Staging` vs `Master`)을 명확히 토글 선택하도록 구현했으며, 기본값을 상대적으로 안전한 `Staging` 테이블로 지정했습니다.
* **이중 적재 모니터링**: 대시보드에 실운영 성분 수와 스테이징 활성 성분 수를 실시간 이중 노출하여, 현재 동기화 흐름을 한눈에 인지할 수 있도록 직관성을 높였습니다.

## 4. 결과 및 엔지니어링 교훈 (Takeaways)

### 성과
* **참조 무결성 100% 보장**: 대용량 동기화를 수없이 진행해도 기존 가입자의 설정 및 스캔 히스토리가 손상되는 이슈가 단 한 건도 발생하지 않았습니다.
* **운영 안정성 확보**: API 데이터 오염이 발생하더라도 스테이징 단계에서 필터링되므로, 서비스 중단 없이 어드민에서 검수 후 롤백할 수 있게 되었습니다.
* **비즈니스 연속성 달성**: 미완성 데이터(CAS 누락) 수집을 무조건 중단하기보다, '선 병합 후 비동기 보강' 구조로 개선하여 서비스 출시 속도와 데이터 품질이라는 두 마리 토끼를 모두 잡았습니다.

### 시니어 개발자로서 얻은 교훈
1. **가장 훌륭한 시스템은 실수를 예방하는 시스템이다**
   아무리 엄격한 API 명세가 있더라도 외부 데이터는 언제든 깨질 수 있습니다. 스테이징 영역과 상태 기계(FSM)를 활용한 완충 지대 설계는 대외 협력 시스템 개발 시 필수적인 방어벽이 됩니다.
2. **UX와 백엔드 보안은 연결되어 있다**
   어드민 페이지의 단순한 토글 기본값 설정, 데이터 카운트 이중 노출 같은 디테일이 대형 데이터 유실 사고를 미연에 방지하는 훌륭한 보안 장치 역할을 합니다.
3. **트레이드 오프(Trade-off)의 예술**
   모든 데이터를 동기식으로 완벽히 맞추려 고집했다면 시스템 성능 저하나 파싱 병목에 시달렸을 것입니다. 중요 명칭은 동기식(Transactional)으로 맞추고, 부가 정보(CAS)는 비동기(Asynchronous)로 수집하는 이원화 설계가 대규모 시스템 운영에서 얼마나 유연한지 다시금 깨달았습니다.
