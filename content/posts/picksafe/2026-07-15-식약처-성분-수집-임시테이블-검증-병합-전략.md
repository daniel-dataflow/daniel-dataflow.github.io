외부 공공 API나 제3자 데이터를 수집하여 서비스의 코어 데이터 베이스에 동기화하는 작업은 단순해 보이지만, **실서비스 운용 환경에서는 매우 치명적인 리스크**를 내포하고 있습니다. 

특히 수집 대상 데이터가 기존 유저 데이터(알레르기 정보, 스캔 이력 등)와 **외래 키(FK)로 복잡하게 얽혀 있는 핵심 엔티티**라면, 단 한 번의 잘못된 덮어쓰기나 PK(UUID) 재발급으로 인해 시스템 전체의 데이터 참조 무결성이 파괴될 수 있습니다.

이번 포스팅에서는 **PickSafe 팀이 식약처 공공 데이터를 수집·병합하는 과정에서 직면한 데이터 참조 무결성 붕괴 문제를 Staging 테이블 도입과 Natural Key 기반 Upsert 전략으로 어떻게 해결했는지** 그 엔지니어링 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): "수집 스케줄러가 돌아갈 때마다 유저 데이터가 깨진다?"

기존 성분 수집 파이프라인은 외부 API를 호출한 뒤, 실운영 테이블(`ingredients_master`)을 **전체 삭제 후 재적재(Truncate & Insert)**하거나 **기존 행을 덮어쓰는(Overwrite)** 방식으로 동작했습니다.

하지만 서비스가 성장함에 따라 `ingredients_master` 테이블은 다음과 같이 다양한 핵심 domain 테이블들과 외래 키(FK) 참조 관계를 맺게 되었습니다.

- **유저 알레르기 설정**: `user_allergens` $\rightarrow$ `ingredients_master.id`
- **제품 성분 매핑**: `product_ingredients` $\rightarrow$ `ingredients_master.id`
- **성분 스캔 분석 이력**: `scan_result_ingredients` $\rightarrow$ `ingredients_master.id`

### 💥 발생했던 핵심 문제점
1. **FK 참조 붕괴 (FK Corruption)**: 전체 삭제 후 재적재 시 식별자(UUID)가 재발급되면서 유저가 설정한 기피 성분이 엉뚱한 성분을 가리키거나 과거 스캔 매칭 기록의 FK 연결이 끊어지는 심각한 장애 발생.
2. **오염된 외부 데이터의 즉시 노출**: 외부 API에서 이름이 누락되거나 규격에 맞지 않는 에러 데이터가 들어왔을 때, 검증 단계 없이 실운영 DB로 직접 흘러 들어가 서비스 장애 유발.
3. **휴먼 에러 위험성**: 어드민 데이터 관리 시 실운영 테이블과 임시 수집 테이블의 경계가 모호하여 운영자가 실수로 운영 데이터 전체를 비워버릴 수 있는 불안정한 UX Structure.

---

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이 문제를 해결하기 위해 크게 3가지 데이터 수집 및 반영 아키텍처를 비교 검토했습니다.

| 검토 항목 | Option A: 운영 DB 직접 덮어쓰기 | Option B: Blue/Green 테이블 Swap | Option C: Staging 테이블 + Natural Key Upsert (최종 선택) |
| :--- | :--- | :--- | :--- |
| **FK 무결성 보존** | ❌ 붕괴 위험 매우 높음 | ❌ FK 재연결 및 Lock 비용 과다 | **✅ 100% 보존 (기존 UUID 고정 유지)** |
| **데이터 검수 단계** | ❌ 없음 (실시간 오염 risk) | 🔺 교체 전 검수는 가능하나 복잡함 | **✅ Staging 상태값 기반 안전 검수** |
| **데이터 불완전성 대응**| ❌ 불완전 데이터 유입 시 파이프라인 중단 | ❌ 동일 | **✅ 비동기 백그라운드 보강 배치 연동** |
| **시스템 복잡도** | Low | High | **Medium (적절한 도메인 격리)** |

- **Option A**는 운영 데이터 오염과 FK 파괴 위험성으로 즉시 제외되었습니다.
- **Option B**는 RDBMS 환경에서 FK 참조 관계가 복잡하게 얽혀 있어, 테이블 자체를 Swap 할 때 발생하는 DDL Lock과 FK 재설정 비용이 가용성 타격을 준다고 판단했습니다.
- 최종적으로 **Option C(Staging 패턴 + Natural Key 기반 Upsert)**를 선택하여, **기존 UUID 식별자를 철저히 보존하면서 수집과 반영 단계를 아키텍처적으로 완벽히 분리**하기로 결정했습니다.

## 3. 해결책 및 상세 설계 (Solution)

### 3.1 Staging 테이블 도입 및 State Machine 기반 분리

운영 테이블 직접 접근을 차단하기 위해 중간 격리 구역인 `ingredients_master_staging` 테이블을 배치했습니다. 외부 API 수집 데이터는 1차적으로 무조건 Staging 테이블로만 들어갑니다.

```
[ 외부 API 수집 ] ──> [ Staging DB (상태 검증) ] ──(어드민 승인/자동 병합)──> [ Master DB (실운영) ]
```

각 Staging 레코드는 명확한 **상태(Status) 생명주기**를 갖습니다:
- `pending`: 국문명과 국제 화장품 성분명(INCI)이 정상이어서 운영 병합이 가능한 대기 상태.
- `error`: 필수 명칭 누락 등 규격에 맞지 않아 어드민 검토가 필요한 상태.
- `suggested`: 백그라운드 배치가 추가 식별 정보(CAS 번호 등)를 찾아내 승인 대기 중인 상태.
- `merged`: 이미 실운영 DB에 안전하게 병합되어 이력이 보존된 상태.

### 3.2 자연 키(`inci_name`) 기반 트랜잭션 Upsert

병합 실행 시, 시스템은 `inci_name`(국제 표준 성분명)을 **자연 키(Natural Key)**로 활용하여 대조 작업을 수행합니다.

1. **동일 `inci_name`이 실운영 DB에 이미 존재하는 경우**:
   - **기존 UUID(`id`)를 절대 변경하지 않고 그대로 고정 유지**합니다.
   - 성분명, 규제 사유 등 변경 가능한 메타데이터 필드만 `UPDATE`합니다. (FK 무결성 100% 보존)
2. **실운영 DB에 존재하지 않는 경우**:
   - 새로 `UUID`를 채번하여 `INSERT`합니다.
3. **원자성(Atomicity) 보장**:
   - 전체 병합 과정은 단일 DB 트랜잭션으로 묶이며, 오류 발생 시 완전 롤백됩니다.
   - 병합 성공 시에만 읽기 성능 최적화를 위한 정적 캐시 파일(JSON)을 재빌드합니다.

### 3.3 비동기 데이터 보강 (Eventual Completeness)

수집된 성분 중 필수 명칭은 존재하지만 식별 번호(CAS No)가 누락된 경우, 전체 파이프라인을 차단(Block)하는 대신 **일단 병합을 진행하여 비즈니스 유연성을 확보**하도록 설계했습니다.

이후 **백그라운드 스케줄러**가 가동되어 `cas_no`가 `NULL`인 성분들을 대상으로 외부 규정 사전을 자동 탐색(1초 rate limit 적용)합니다. 발견된 정보는 Staging 테이블에 `status = 'suggested'` 상태로 자동 등록되어, 어드민이 클릭 한 번으로 승인 및 보강할 수 있는 **Human-in-the-loop** 구조를 완성했습니다.

### 3.4 방어적 UX/UI 및 어드민 안전장치

인적 실수로 인한 운영 장애를 원천 차단하기 위해 어드민 제어부 및 API 레이어에 방어적 설계를 적용했습니다.

- **비우기(Truncate) 동작의 토글화**: 어드민 데이터 초기화 API 호출 시 `target_table`을 명시적 파라미터로 요구하며, **기본 선택값(Default)을 항상 'Staging'으로 강제**합니다.
- **실시간 데이터 모니터링 노출**: 대시보드 카드에 `실운영 데이터 건수`와 `Staging 활성 건수`를 동시 노출하여 현재 수집 및 병합 대기 상태를 한눈에 파악할 수 있도록 모니터링 환경을 개선했습니다.

## 4. 엔지니어링 레슨 및 인사이트 (Takeaway)

이번 Staging & Merge 파이프라인 개편을 통해 거둔 주요 성과와 배운 점은 다음과 같습니다.

### 1. "대체 키(Surrogate Key)와 자연 키(Natural Key)의 명확한 역할 분리"
내부 RDBMS 참조용으로는 UUID(Surrogate Key)를 사용하더라도, 외부 데이터와의 동기화 및 병합 시에는 데이터 도메인 고유의 Natural Key를 기점(Anchor)으로 삼아야만 참조 관계를 깨뜨리지 않고 안전하게 시스템을 확장할 수 있음을 확인했습니다.

### 2. Zero-Trust Ingestion (외부 데이터는 절대 믿지 않는다)
외부 API 데이터를 실운영 DB에 곧바로 적재하는 것은 시한폭탄을 안고 달리는 것과 같습니다. **Staging 격리 구역**과 **상태 머신(State Machine)**을 중간에 둠으로써, 파이프라인의 안정성과 데이터 품질 검수 능력이 비약적으로 상승했습니다.

### 3. 완벽성과 속도의 트레이드오프 (Eventual Completeness)
데이터의 모든 필드가 채워질 때까지 동기화를 미루는 것보다, 핵심 필드만으로 우선 서비스를 가동하고 비동기 배치로 품질을 점진적으로 높여나가는(Eventual Completeness) 아키텍처 전략이 사업적 시간 단축(Time-to-Market) 측면에서 훨씬 유리함을 체득했습니다.
