안녕하세요. `PickSafe` 백엔드 엔지니어링팀입니다. 

서비스를 운영하며 외부 공공 데이터를 주기적으로 수집·반영하는 작업은 필수적이지만, 동시에 데이터베이스 무결성을 위협하는 고위험 작업이기도 합니다. 특히 수집 대상 데이터가 유저의 민감한 데이터(알레르기, 기피 성분 등)와 외래 키(FK)로 강하게 엮여 있는 경우, 단순한 덮어쓰기나 전체 삭제 후 적재 방식은 서비스 장애로 직결될 수 있습니다.

이번 글에서는 식약처 성분 데이터를 안전하게 수집하고, 기존 유저 데이터의 FK 무결성을 100% 보장하기 위해 도입한 **Staging 테이블 및 자연 키(Natural Key) 기반 Upsert 아키텍처**의 설계 고민과 트레이드오프 과정을 공유합니다.

---

## 1. Problem: 무작정 덮어쓰기가 가져온 데이터 무결성 붕괴 위험

기존 성분 수집 시스템은 외부 API 데이터를 가져와 실운영 테이블(`ingredients_master`)에 직접 덮어쓰거나, 전체 테이블을 truncate한 뒤 새로 적재하는 구조였습니다.

하지만 서비스가 고도화되면서 `ingredients_master`는 다수의 도메인 테이블과 외래 키 참조 관계를 맺게 되었습니다.
- 유저별 알레르기/기피 성분 설정 테이블 (`user_allergens`)
- 제품별 포함 성분 매핑 테이블 (`product_ingredients`)
- 과거 바코드 스캔 매칭 히스토리 (`scan_result_ingredients`)

만약 수집 단계에서 기존 데이터를 무작정 삭제하거나 행의 고유 식별자(UUID)를 통째로 교체(Swap)할 경우, **과거 사용자가 등록한 기피 성분이 엉뚱한 성분을 가리키거나 과거 스캔 기록이 깨지는 치명적인 데이터 무결성 붕괴(FK Corruption)**가 발생할 위험이 있었습니다.

> **핵심 과제:** "기존 유저 데이터의 UUID 참조 관계는 완벽히 고정 보존하면서, 외부 API의 최신 변경 사항은 안전하게 반영할 수 있는 구조는 무엇인가?"

---

## 2. Solution & Trade-off: 스테이징(Staging) 도입과 자연 키 기반 Upsert

이 문제를 해결하기 위해 데이터베이스 레이어와 어드민 워크플로우를 아우르는 새로운 아키텍처를 설계했습니다.

### ① 임시 스테이징 테이블 (`ingredients_master_staging`) 분리
모든 외부 API 수집(Seeding) 동작은 운영 테이블에 즉시 반영되지 않고, 1차적으로 **스테이징 테이블**에 적재되도록 격리했습니다. 각 레코드는 `status` 필드를 통해 상태를 관리합니다.
- `pending`: 국문명과 INCI명이 정상 기입되어 병합 가능한 상태
- `error`: 필수 데이터 누락으로 검토가 필요한 상태
- `suggested`: 백그라운드 배치가 보강한 추천 CAS 정보 상태
- `merged`: 운영 테이블로 병합이 완료되어 보존 중인 상태

### ② 자연 키(`inci_name`) 기반 트랜잭션 Upsert 전략
어드민에서 **[병합 실행]**을 누르면, `pending` 상태의 데이터만 골라 실운영 테이블로 반영합니다.
- **매칭 기준:** 고정된 UUID 대신 자연 키인 `inci_name`을 기준으로 삼습니다.
- **UPDATE:** 이미 동일한 INCI명이 존재한다면, **기존 UUID(id)를 그대로 유지**한 채 성분명, CAS 번호 등 변경된 속성 페이로드만 갱신합니다.
- **INSERT:** 존재하지 않는 신규 성분인 경우에만 새로운 UUID를 발급하여 추가합니다.
- 이 모든 과정은 **단일 DB 트랜잭션**으로 묶여 실패 시 전체 롤백되며, 성공 시 정적 JSON 캐시를 강제 재빌드하여 성능과 일관성을 동시에 잡았습니다.

### ③ 비동기 사후 보강 배치 (Asynchronous Enrichment)
데이터 수집 속도와 품질 사이의 트레이드오프를 해결하기 위한 고민도 있었습니다. CAS 번호가 누락되었다고 해서 수집 자체를 막아버리면 서비스의 신속한 대응력이 떨어집니다.
- CAS 번호가 없더라도 명칭이 정상적이라면 스테이징에서 즉시 병합을 허용했습니다.
- 이후, 백그라운드 스케줄러가 운영 테이블의 `cas_no IS NULL`인 레코드들을 대상으로 외부 사전을 비동기 조회하여(`suggested`) 어드민에서 원클릭으로 보완할 수 있도록 설계했습니다.

### ④ 고위험 작업의 휴먼 에러 방지 (UI/UX Safety Net)
어드민에서 데이터를 초기화(비우기)하는 고위험 액션 역시 사고를 방지하기 위한 안전장치를 두었습니다.
- 삭제 대상을 `임시 테이블(Staging)`과 `실운영 테이블(Master)` 중 토글로 명시적으로 선택하도록 강제했습니다.
- 기본값을 안전한 `임시 테이블`로 지정하고, 대시보드에 두 테이블의 적재 건수를 동시에 노출하여 운영자가 현재 데이터의 파이프라인 단계를 직관적으로 인지할 수 있게 했습니다.

## 3. Takeaway: 엔지니어링 교훈

이번 아키텍처 개선을 통해 얻은 가장 큰 교훈은 **"외부 시스템과의 연동부와 핵심 도메인(SSOT) 영역은 반드시 물리적/논리적으로 분리해야 한다"**는 점입니다.

1. **데이터 무결성 사수:** 외래 키 참조가 걸린 핵심 마스터 데이터를 외부 수집 로직으로부터 완벽히 보호하여, 대규모 데이터 갱신 시에도 유저 경험과 히스토리가 안전하게 유지되도록 했습니다.
2. **운영의 안정성(Safety First):** 자동화된 파이프라인 속에서도 사람이 개입하여 검수하고 병합할 수 있는 '휴먼 인 더 루프(Human-in-the-loop)' 포인트를 마련함으로써, 서비스 장애 확률을 극적으로 낮추었습니다.

앞으로도 `PickSafe`는 빠르고 편리한 기능 제공만큼이나, 단단하고 신뢰할 수 있는 데이터 아키텍처를 구축하는 데 집중하겠습니다.
