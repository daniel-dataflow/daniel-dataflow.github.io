대규모 공공데이터나 외부 API를 주기적으로 수집하여 서비스 마스터 데이터로 동기화하는 작업은 백엔드 엔지니어링에서 흔히 마주하는 과제입니다. 

하지만 수집 대상 데이터가 **서비스 내 수많은 핵심 도메인(사용자 설정, 분석 이력, 연관 상품 등)과 외래 키(FK)로 얽혀 있다면** 이야기는 완전히 달라집니다. 단순히 "새 데이터로 테이블을 교체(Drop & Replace)"하거나 "단순 덮어쓰기"를 진행하는 순간, 서비스 전체의 데이터 무결성이 산산조각 날 수 있기 때문입니다.

이번 글에서는 외부 공공 규제 데이터를 안전하게 수집·검증하고, 서비스 중단 및 FK 붕괴 없이 실운영 마스터에 점진적으로 반영하기 위해 설계한 **Staging 기반 Upsert 파이프라인과 비동기 데이터 보강 아키텍처**를 소개합니다.

---

### 1. 문제 정의: "데이터를 갱신했을 뿐인데, 사용자 히스토리가 깨졌다?"

기존 시스템의 초기 설계에서는 공공 API로부터 규제/성분 데이터를 일괄 수집(Seeding)할 때 실운영 마스터 테이블에 직접 덮어쓰거나 전체를 삭제 후 재적재하는 방식을 취하고 있었습니다.

그러나 서비스가 고도화되면서 마스터 테이블의 PK(UUID)는 다음과 같은 주요 엔티티들과 강한 FK 관계를 맺게 되었습니다:

- **사용자 기피 성분 설정 데이터** (특정 성분 UUID 참조)
- **제품별 매칭 성분 데이터** (제품-성분 M:N 매핑)
- **과거 이미지/텍스트 스캔 및 판독 이력** (판독 시점의 성분 UUID 스냅샷/매핑)

```
[Master Table (UUID)] <--- FK --- [User Preferences]
                      <--- FK --- [Product Ingredients]
                      <--- FK --- [Scan History]
```

이 상태에서 단순 전체 동기화를 위해 레코드를 재생성하거나 UUID를 교체(Swap)할 경우, **기존 사용자가 등록한 알레르기 유발 물질이 엉뚱한 성분을 가리키거나 과거 스캔 분석 리포트의 관계가 끊어지는 치명적인 데이터 오염(FK Corruption)**이 발생할 위험이 있었습니다.

또한 공공 API 데이터 특성상 간헐적으로 필수 식별자나 규제 코드가 누락되는 불완전한 레코드가 섞여 들어왔는데, 이를 사전 검증 없이 운영 DB에 즉시 반영하는 것은 매우 위험했습니다.

---

### 2. 기술적 고민과 아키텍처 결정 (Trade-offs)

우리는 데이터 정합성을 100% 보장하면서도 수집 효율을 극대화하기 위해 다음과 같은 3가지 아키텍처 결정을 내렸습니다.

#### ① Staging(임시 적재) 테이블을 통한 격리 수집
운영 테이블에 직접 쓰기 작업을 수행하지 않고, `Staging Table`을 완충 지대로 두었습니다.
- 외부 API 수집 배치는 오직 Staging 테이블로만 원시 데이터를 적재합니다.
- 레코드별 유효성 검증(필수 명칭 누락 여부 등)을 거쳐 `pending`, `error`, `suggested`, `merged` 상태 머신(State Machine)을 부여합니다.
- 어드민은 검증을 통과한 `pending` 데이터만 선별하여 안전하게 운영계로 반영할 수 있습니다.

#### ② 자연 키(Natural Key) 기반의 트랜잭션 Upsert
PK인 내부 UUID를 보존하면서 최신 메타데이터를 갱신하기 위해 **국제 표준 명칭(Natural Key)**을 매칭 키로 채택했습니다.

- **기존 레코드 존재 시**: 내부 `id(UUID)`를 엄격히 보존하고, 세부 속성(규제 정보, 식별 코드 등)만 `UPDATE`.
- **신규 레코드일 시**: 새로운 `UUID`를 발급하여 `INSERT`.
- 전체 반영 과정은 **단일 Database Transaction**으로 격리하여, 단 하나의 오류라도 발생 시 전체 롤백되도록 원자성(Atomicity)을 보장했습니다.
- 병합 완료 후 캐시 레이어의 일관성을 위해 마스터 정적 캐시를 즉시 재생성(Rebuild)하도록 트리거했습니다.

#### ③ 비동기 보강(Enrichment) 파이프라인을 통한 수집 지연 해소
일부 성분은 공공 식별 코드(CAS No 등)가 누락된 채 인입됩니다. 이를 완전한 데이터가 될 때까지 수집 중단(Block)시키면 규제 정보 업데이트 속도가 지나치게 늦어집니다.

- **해결책**: 기본 명칭이 유효하다면 우선 1차 병합을 허용하되, 식별 코드가 비어 있는 레코드만 백그라운드 워커가 전문 협회 사전을 크롤링/조회하여 보강하도록 분리했습니다.
- 조회된 보강 데이터는 즉시 운영에 덮어쓰지 않고 Staging 테이블에 `suggested` 상태로 적재하여, 관리자가 변경 사항을 리뷰 후 원클릭 승인할 수 있도록 휴먼-인-더-루프(Human-in-the-loop) 검증 절차를 마련했습니다.

```
[외부 API] ──(수집)──> [Staging DB] ──(검증/Pending)──> [Admin 검수] 
                             │                                │ (단일 트랜잭션 Upsert)
                             │ (식별자 누락 건)                ▼
                             ▼                          [Master DB (UUID 보존)]
                     [Background Enrichment Worker]           ▲
                             │                                │ (보강 승인)
                             └───(추천값/Suggested)───────────┘
```

#### ④ 실수 방지(Poka-Yoke)를 고려한 안전한 운영 인터페이스
데이터 리셋이나 초기화는 매우 파괴적인 작업입니다. 운영자의 인적 실수(Human Error)를 방지하기 위해:
- 데이터 비우기 API 호출 시 대상 테이블(`Staging` vs `Master`)을 명시적으로 선택하도록 강제했습니다.
- 인터페이스의 기본값을 안전한 `Staging` 테이블로 지정하여 무의식적인 실행으로 인한 운영 데이터 삭제를 원천 차단했습니다.
- 어드민 대시보드에 실시간으로 운영 성분 수와 Staging 대기 성분 수를 이중 지표로 노출하여 파이프라인 동기화 현황을 한눈에 파악할 수 있도록 관측성(Observability)을 높였습니다.

### 3. 성과 및 엔지니어링 교훈 (Takeaways)

#### 1. 데이터 참조 무결성 100% 달성
기존 가입자의 기피 설정 및 수천 건의 판독 히스토리 매핑 데이터가 유실되거나 어긋나는 위험을 완전히 제거했습니다. 자연 키 기반 Upsert 전략 덕분에 스키마 진화와 외부 데이터 변경 속에서도 내부 식별자의 영속성을 완벽히 방어할 수 있었습니다.

#### 2. 안정성과 출시 속도의 균형 (Eventual Consistency)
누락된 데이터가 채워질 때까지 전체 파이프라인을 블로킹하는 대신, Staging 격리와 백그라운드 보강 배치를 통해 **'우선 배포 후 점진적 보강'** 구조를 구축했습니다. 이를 통해 서비스 오픈 일정은 앞당기면서도 최종적인 데이터 품질은 점진적으로 수렴시키는 설계를 완성했습니다.

#### 3. 운영자 경험(DX/UX)과 장애 방지 설계
아무리 정교한 백엔드 아키텍처라도 운영 인터페이스가 취약하면 인적 재난으로 이어질 수 있습니다. 고위험 액션의 격리, 안전한 기본값(Safe Defaults), 실시간 메트릭 가시화가 시스템 안정성에 얼마나 중요한지 다시 한번 확인했습니다.

### 마치며

외부 데이터 의존도가 높은 서비스일수록 "외부 데이터는 언제든 불완전할 수 있고, 내부 도메인은 항상 보호되어야 한다"는 원칙이 중요합니다. Staging 레이어와 상태 머신 기반 Upsert 전략은 복잡한 데이터 파이프라인에서 데이터 무결성과 운영 안정성을 동시에 챙길 수 있는 강력한 무기가 될 수 있습니다.
