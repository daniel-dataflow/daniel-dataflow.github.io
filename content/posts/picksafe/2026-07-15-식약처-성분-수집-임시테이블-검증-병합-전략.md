안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스를 운영하면서 외부 오픈 API나 공공데이터 포털의 대량 데이터를 주기적으로 동기화해야 하는 요구사항은 흔히 발생합니다. 

이번 글에서는 식약처 성분 데이터를 수집·갱신하는 과정에서 마주한 **데이터 무결성 붕괴 위험을 해결하기 위해 도입한 스테이징(Staging) 테이블과 자연 키(Natural Key) 기반 Upsert 아키텍처**에 대한 기술적 고민과 의사결정 과정을 공유합니다.

---

## 1. Problem: 싹 밀고 새로 넣기(Drop & Insert)가 불러온 치명적인 위험

기존 성분 수집 시스템은 API 데이터를 가져와 실운영 테이블(`ingredients_master`)에 직접 덮어쓰거나, 전체 데이터를 삭제하고 새로 적재하는 방식을 사용했습니다. 데이터가 단순 참고용이라면 이 방법도 나쁘지 않습니다.

하지만 `ingredients_master`는 서비스 내 핵심 도메인들과 깊은 외래 키(FK) 참조 관계를 맺고 있습니다.
- 사용자별 알레르기/기피 성분 설정 (`user_allergens`)
- 제품별 함유 성분 매핑 (`product_ingredients`)
- 사용자의 스캔 히스토리 및 매칭 결과 (`scan_result_ingredients`)

만약 수집 단계에서 테이블을 임의로 비우거나, 행의 고유 식별자(UUID)를 통째로 교체(Swap)해버리면 어떻게 될까요? **사용자가 등록해 둔 기피 성분 정보가 엉뚱한 성분을 가리키거나, 과거 스캔 매칭 기록이 깨지는 치명적인 데이터 무결성 붕괴(FK Corruption)**로 이어지게 됩니다.

우리가 해결해야 할 문제는 명확했습니다.
> **"기존 사용자의 참조 무결성과 UUID를 완벽히 보존하면서, 외부 API의 변경된 최신 데이터를 안전하게 반영하는 방법은 무엇인가?"**

---

## 2. Trade-off & Architecture: 스테이징 테이블과 자연 키 Upsert 도입

이 문제를 해결하기 위해 도입한 핵심 아키텍처는 **1차 스테이징(Staging) 적재 후, 자연 키(`inci_name`) 기반의 조건부 병합(Upsert)** 구조입니다.

### ① 임시 스테이징 테이블 (`ingredients_master_staging`) 분리
모든 수집(Seeding) 동작은 운영 테이블에 곧바로 손을 대지 않고, 임시 스테이징 테이블에 먼저 적재합니다. 
각 레코드는 상태 값(`status`)을 가져 데이터의 라이프사이클을 명확히 추적합니다.
- `pending`: 병합 대기 상태 (필수 명칭 보유)
- `error`: 필수 명칭 누락 등 검토 필요 상태
- `suggested`: 백그라운드 배치가 보강한 추천 CAS 정보 상태
- `merged`: 운영 테이블로 병합 완료된 상태

### ② 자연 키(`inci_name`) 기반의 스마트 Upsert
어드민에서 **[병합 실행]**을 누르면, `status == 'pending'`인 데이터들만 실운영 테이블로 반영됩니다. 이때 무작정 INSERT하는 것이 아니라 `inci_name`을 자연 키로 활용합니다.
- **이미 존재하는 경우**: 기존 레코드의 **UUID를 고정 유지**하고, 성분명과 규제 사유 필드만 `UPDATE`합니다.
- **존재하지 않는 경우**: 새로운 UUID를 부여하여 `INSERT`합니다.
- **트랜잭션 보장**: 이 모든 과정은 단일 DB 트랜잭션으로 묶여 실패 시 전체 롤백되며, 성공 시 정적 JSON 캐시를 강제 재빌드하여 성능과 일관성을 동시에 잡았습니다.

### ③ 백그라운드 CAS 보강 배치
외부 데이터를 수집하다 보면 CAS 번호가 누락된 경우를 빈번하게 마주합니다. 이를 강제로 차단하면 수집 파이프라인이 멈추기 때문에, CAS 번호가 없어도 명칭이 정상적이라면 일단 스테이징 단에서 병합을 허용했습니다. 

이후, 백그라운드 스케줄러가 운영 테이블의 `cas_no`가 `NULL`인 성분들을 대상으로 외부 사전을 자동 조회(`1초 간격 딜레이`)하여 어드민에서 원클릭으로 승인할 수 있도록 `suggested` 상태로 갱신해 줍니다. 이를 통해 **서비스 출시 속도와 데이터 품질** 두 마리 토글을 모두 잡았습니다.

### ④ 휴먼 에러(Human Error) 방지 UI/UX 설계
고위험 작업인 '데이터 초기화(비우기)' 기능은 실수로 실운영 데이터를 날려버리는 사고를 방지하기 위해, 대상 테이블을 토글(`Staging` vs `Master`)로 명시적으로 선택하도록 강제했습니다. 기본값은 언제나 안전한 `임시 테이블`로 지정하고, 어드민 대시보드에 두 테이블의 적재 건수를 동시에 노출해 데이터 흐름을 직관적으로 모니터링할 수 있게 개선했습니다.

## 3. Takeaway: 무엇을 얻었는가?

1. **데이터 신뢰성 확보**: FK 참조 무결성을 100% 보존함으로써, 대규모 데이터 갱신 작업 중에도 사용자 데이터가 유실되거나 오염되는 사고를 원천 차단했습니다.
2. **운영의 안전장치(Safety Net)**: 개발자가 아닌 운영자(어드민)도 수집된 데이터를 눈으로 검수하고 안전하게 병합/롤백할 수 있는 프로세스를 구축했습니다.
3. **확장 가능한 파이프라인**: 실시간 처리와 비동기 백그라운드 배치를 적절히 조합하여, 외부 시스템의 제약(크롤링 제한 등) 속에서도 유연하게 동작하는 데이터 파이프라인 설계를 경험했습니다.

기술은 단순히 코드를 작성하는 것을 넘어, **"비즈니스 도메인의 핵심 자산을 어떻게 안전하게 지킬 것인가"**에 대한 깊은 고민의 결과물이어야 합니다. PickSafe는 앞으로도 데이터의 안정성과 개발 생산성 사이의 최적의 균형점을 찾아 나갈 것입니다.
