안녕하세요, **PickSafe** 백엔드 엔지니어링 팀입니다.

우리가 매일 사용하는 서비스들의 이면에는 외부 기관이나 파트너사의 API로부터 데이터를 주기적으로 동기화하는 파이프라인이 존재합니다. 식약처와 같은 공공데이터 포털에서 성분 정보를 가져와 사용자에게 유용한 정보를 제공하는 PickSafe 역시 마찬가지입니다.

하지만 대용량 외부 데이터를 가져와 우리 시스템에 들이는 과정은 생각보다 단순하지 않습니다. 초기 설계에서 간과하기 쉬운 **"데이터 무결성 붕괴(FK Corruption)"**와 **"인적 실수로 인한 데이터 유실"** 문제를 우리가 어떻게 아키텍처적으로 우아하게 해결했는지, 그 여정을 공유하고자 합니다.

---

## 1. 문제 정의: "어느 날 갑자기 사용자의 알레르기 설정이 사라졌다?"

기존 PickSafe의 성분 수집 파이프라인은 정기적으로 식약처 API를 호출하여 최신 성분 정보를 받아왔습니다. 이때 기존 방식은 매우 단순하고 과격했습니다. 

> **"기존 테이블을 통째로 비우고(Truncate) 새로 적재하거나, 동일한 성분명에 대해 기존 행을 지우고 덮어쓴다."**

이 방식은 수집 대상 테이블이 독립적일 때는 문제가 없습니다. 하지만 서비스가 성장하면서 성분 테이블(`ingredients_master`)을 참조하는 핵심 기능들이 늘어났습니다.

*   사용자가 등록한 기피 성분 (`user_allergens.ingredient_id` 참조)
*   등록된 상품별 매칭 성분 (`product_ingredients.ingredient_id` 참조)
*   사용자의 과거 스캔 기록 (`scan_result_ingredients.ingredient_id` 참조)

모두 `ingredients_master` 테이블의 기본 키(UUID)를 **외래 키(FK)**로 바라보고 있는 구조였습니다. 

이 상태에서 동기화 배치가 돌며 기존 레코드를 삭제하고 새 UUID로 재생성하자, **기존에 맺어져 있던 외래 키 관계가 모두 끊어지거나 엉뚱한 성분을 가리키는 대참사(FK Corruption)**가 발생할 위험에 노출되었습니다. 데이터의 참조 무결성이 완전히 붕괴되는 순간이었습니다.

우리는 이 문제를 해결하기 위해 **"절대 기존 레코드의 UUID를 변경하거나 유실시키지 않으면서, 신규 데이터만 안전하게 병합하는 전략"**이 필요했습니다.

## 2. 기술적 고민과 대안 비교

이를 해결하기 위해 엔지니어링 팀은 세 가지 방향성을 두고 토론을 거쳤습니다.

### 대안 A: 데이터 임시 교체(Table Swap) 방식
신규 데이터를 임시 테이블에 완전히 새로 적재한 뒤, DB 수준에서 테이블의 이름을 바꾸어(Rename/Swap) 치환하는 방식입니다.
*   **장점:** 교체 속도가 매우 빠르고 무중단 처리가 단순함.
*   **단점:** 외래 키 관계가 걸려 있는 경우 데이터베이스 레벨에서 이름 변경(Rename)이 불가능하거나, 관계를 끊었다가 다시 맺는 과정에서 데이터 유실 위험이 매우 높음. (기각)

### 대안 B: 실시간 API 호출 및 직접 Upsert 방식
API를 한 행씩 읽으며 실운영 테이블에 직접 `INSERT ... ON CONFLICT (id) DO UPDATE`를 수행하는 방식입니다.
*   **장점:** 별도의 임시 테이블 공간이 필요 없음.
*   **단점:** 외부 API 응답 중에 불완전한 데이터(예: 성분명이 누락되었거나 깨진 데이터)가 섞여 들어올 경우, 실운영 테이블이 즉시 오염됨. 롤백이 어려움. (기각)

### 대안 C: 임시 스테이징(Staging) 테이블 도입 및 트랜잭션 병합 (선택)
수집 데이터를 1차적으로 임시 테이블(`ingredients_master_staging`)에 안전하게 격리 적재한 뒤, 데이터 검증이 완료되면 **자연 키(Natural Key)를 기준으로 실운영 테이블에 병합(Upsert)**하는 방식입니다.
*   **장점:** 
    *   잘못된 데이터가 실운영에 미치는 영향을 완벽히 격리(Sandboxing).
    *   기존에 존재하는 성분은 UUID를 고정 유지한 채 필요한 필드만 업데이트하여 **외래 키 무결성 100% 보존**.
    *   어드민 검수 단계를 추가하여 안전 장치 마련 가능.
*   **단점:** 저장 공간이 일시적으로 더 필요하고 병합 로직 구현 공수가 듦.

우리는 서비스 안정성과 데이터 무결성을 최우선 가치로 삼아, **대안 C(스테이징 테이블 도입 및 자연 키 기반 병합 전략)**를 채택했습니다.

## 3. 최종 해결 아키텍처 및 구현

우리가 설계하고 구축한 새로운 데이터 수집 체계는 다음과 같습니다.

```
[외부 식약처 API] 
       │
       ▼ (1차 수집)
┌─────────────────────────────────┐
│ ingredients_master_staging      │ ◀─── [백그라운드 CAS 보강 배치] (정기 실행)
│  - status: pending / error /    │
│            suggested / merged   │
└─────────────────────────────────┘
       │
       ▼ (어드민 검수 및 병합 실행 - Single Transaction)
┌─────────────────────────────────┐
│ ingredients_master (실운영)     │ ───▶ [정적 JSON 캐시 재빌드]
│  - INCI Name (자연 키 매칭)      │
└─────────────────────────────────┘
```

### ① 격리된 스테이징 레이어 구축
모든 외부 API 수집 데이터는 실운영 테이블이 아닌 `ingredients_master_staging`으로 우선 적재됩니다. 데이터의 상태를 관리하기 위해 상태 머신(`status` 필드)을 도입했습니다.

*   `pending`: 필수 명칭(국문명, INCI명)이 모두 확보되어 병합 대기 중인 정상 상태.
*   `error`: 필수 명칭이 누락되어 검토가 필요한 상태.
*   `suggested`: 백그라운드 배치를 통해 유실되었던 CAS(Chemical Abstracts Service) 번호가 자동으로 보완된 상태.
*   `merged`: 이미 실운영 데이터로 이관이 완료되어 기록 보존 중인 상태.

### ② 자연 키(`inci_name`) 기반의 멱등성(Idempotent) 병합
어드민이 **[병합 실행]**을 트리거하면, `status == 'pending'`인 데이터만을 대상으로 단일 DB 트랜잭션 내에서 병합이 수행됩니다.

이때 가장 중요한 열쇠는 국제 화장품 성분 사전 명칭인 **`inci_name`을 자연 키(Natural Key)로 활용**한 점입니다.

```python
# 내부 병합 로직의 개념적 수도코드 (Pseudo-code)
def merge_staging_to_master(db_session):
    pending_items = get_staging_items_by_status(db_session, status="pending")
    
    for item in pending_items:
        # 1. 자연 키(inci_name)를 기준으로 기존 실운영 데이터 조회
        existing_ingredient = find_master_by_inci_name(db_session, item.inci_name)
        
        if existing_ingredient:
            # 2. 존재한다면 기존 UUID(id)는 고정 유지하고 내용만 업데이트
            existing_ingredient.korean_name = item.korean_name
            existing_ingredient.cas_no = item.cas_no or existing_ingredient.cas_no
            existing_ingredient.regulatory_reason = item.regulatory_reason
        else:
            # 3. 존재하지 않는 완전히 새로운 성분인 경우에만 새 UUID 발급 및 삽입
            new_ingredient = IngredientMaster(
                id=generate_uuid(),
                inci_name=item.inci_name,
                korean_name=item.korean_name,
                cas_no=item.cas_no
            )
            db_session.add(new_ingredient)
            
        item.status = "merged"
    
    # 단일 트랜잭션 커밋으로 원자성(Atomicity) 보장
    db_session.commit()
    
    # 캐시 일관성을 위한 정적 파일(JSON) 재빌드 트리거
    rebuild_static_cache()
```

이 방식을 통해 기존 사용자가 맺어둔 FK(`ingredient_id`)는 전혀 흔들리지 않으면서도, 신규 성분 반영 및 기존 성분 정보 업데이트를 안전하게 완수할 수 있게 되었습니다.

### ③ 휴먼 에러를 방지하는 어드민 안전장치 (Safety Toggle)
개발자가 어드민 툴에서 테스트 데이터를 지우거나 초기화할 때, 실수로 실운영 데이터를 삭제하는 대참사를 예방하기 위한 UX적/API 레벨의 안전장치를 심었습니다.

*   **초기화 대상 토글 강제화:** 데이터 비우기 요청 시, `Staging`과 `Master` 중 대상을 명확히 토글 선택해야만 API 요청 파라미터(`target_table`)가 전송되도록 설계했습니다.
*   **보수적 기본값 설정:** 실수로 버튼을 누르더라도 실운영 데이터가 상하지 않도록 기본 타겟을 `Staging` 테이블로 강제 고정했습니다.
*   **이중 카운팅 대시보드:** 대시보드 상에 실운영 성분 개수와 임시 성분 개수를 실시간으로 동시에 시각화하여, 현재 동기화 흐름을 직관적으로 모니터링할 수 있게 했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 개편을 통해 우리 팀이 얻은 핵심 교훈은 다음과 같습니다.

1.  **데이터 무결성은 타협 대상이 아니다:** 속도가 빠르다고 무작정 데이터를 비우고 새로 쓰는 방식은 서비스가 성장할 때 반드시 부메랑이 되어 돌아옵니다. 데이터 구조 설계 시 외래 키 관계와 데이터 라이프사이클을 고려한 병합 전략 수립이 필수적입니다.
2.  **스테이징 레이어는 훌륭한 완충 지대다:** 외부 API는 언제나 불완전한 상태로 올 수 있습니다. 이를 격리할 수 있는 가상 샌드박스(Staging)를 두는 것만으로도 서비스 안정성이 몇 배는 올라갑니다.
3.  **시스템은 사용자의 실수까지도 예측하고 설계해야 한다:** 어드민을 사용하는 운영자나 개발자도 실수를 합니다. 파괴적인 작업을 수행하는 API는 토글 선택 유도, 안전한 기본값 설정 등 시스템 아키텍처 차원에서 안전핀을 꽂아두어야 합니다.

PickSafe 팀은 앞으로도 "안전하고 신뢰할 수 있는 서비스"를 만들기 위해 보이지 않는 백엔드의 아주 작은 무결성 고리 하나까지도 집요하게 검증하고 고도화해 나갈 것입니다.
