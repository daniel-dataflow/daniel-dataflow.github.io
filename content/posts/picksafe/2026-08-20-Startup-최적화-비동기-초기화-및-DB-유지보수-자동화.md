최근 우리 팀은 서비스 배포 과정에서 고질적으로 발생하던 **서버 기동 지연(Startup Latency)** 문제를 해결했습니다. 배포 시마다 평균 3분 이상 소요되던 지연 시간을 **10초 이내**로 단축한 아키텍처 개선 과정을 공유하고자 합니다.

---

## 1. 배경 (Context): "No open ports detected"의 악몽

PaaS 환경(예: Render)을 활용해 서비스를 배포하던 중, 배포 로그에 "No open ports detected" 메시지가 2~3분간 반복되다가 간신히 서버가 뜨는 현상이 관찰되었습니다. 

원인을 분석해 보니, **FastAPI 애플리케이션의 진입점(`main.py`) 모듈 레벨에서 서버 포트를 열기 전, 무거운 동기 작업들을 순서대로 블로킹 방식으로 실행**하고 있었기 때문이었습니다.

### 발견된 병목 작업 리스트
1. **대용량 데이터 동기화 (`ingredients_master`)**: DW Failover 발생 시 매 배포마다 전체 데이터 재복제 (소요 시간: 1~3분)
2. **DB 간 데이터 이관**: 완료 여부와 상관없이 매번 테이블 조회 및 이관 시도 (소요 시간: 수십 초)
3. **스키마 변경 감지 (`ALTER TABLE`)**: 이미 존재하는 컬럼도 매 배포마다 중복 확인 (소요 시간: 수 초 $\times$ 횟수)
4. **번역 캐시 적재 및 타임존 설정**: 동기 블로킹 방식으로 인한 추가 지연

서버가 외부 트래픽을 받을 준비(포트 바인딩)를 하기도 전에 애플리케이션이 무거운 내부 유지보수 작업에 묶여 있었던 것입니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

문제를 해결하기 위해 크게 **동기 실행 제거**, **상태 관리(플래그) 도입**, **운영 도구(어드민) 연계**라는 세 가지 축으로 아키텍처를 재설계했습니다.

### Track A: 완료 플래그(`system_meta`) 도입
매 배포마다 무조건 실행되던 초기화 작업을 제어하기 위해, DB에 Key-Value 형태의 `system_meta` 메타데이터 테이블을 도입했습니다.
* **이관/동기화 작업**: 최초 1회 완료 시 `completed` 플래그를 기록하고, 이후 기동 시 플래그가 존재하면 즉시 스킵하도록 변경했습니다.
* **Trade-off**: DB 조회 쿼리가 추가되지만, 수 분에 달하는 배포 지연 시간에 비하면 얻는 이점이 압도적으로 큽니다. 비상 시 어드민을 통해 플래그를 리셋하여 강제 재실행할 수 있는 유연성도 확보했습니다.

### Track B: 무거운 작업을 백그라운드(`startup_event`)로 격리
FastAPI의 수명주기(Lifespan) 이벤트인 `@app.on_event("startup")`을 활용했습니다.
* 모듈 레벨에서 실행되던 블로킹 코드를 비동기 백그라운드 태스크(`_background_init`)로 이전했습니다.
* 필수적인 최소 DDL 확인만 거친 뒤 **서버 포트를 즉시 오픈(~10초)**하고, 무거운 데이터 이관 및 캐시 적재는 백그라운드에서 비동기로 순차 실행되도록 구조를 전환했습니다.

```
[기존 Startup 흐름]
임포트 → DDL → DB 이관 → Hydration → 번역캐시 → 포트 오픈 (3분+)

[개선 후 Startup 흐름]
임포트 → DDL → 포트 즉시 오픈 (~10초) → [백그라운드] 번역캐시 → 이관 스킵 → 성분 사전 스킵
```

### Track C: 어드민 인프라 모니터링 & 수동 제어 UI 구축
자동화된 플래그 도입으로 인해 "데이터를 강제로 다시 동기화하고 싶을 때"의 문제가 생겼습니다. 이를 해결하기 위해 어드민 인프라 화면(`/admin/infra`)에 수동 유지보수 UI를 구축했습니다.
* **성분 사전 동기화**: 실시간 건수 및 최종 동기화 시각 표기, `🔄 성분 사전 재동기화` 버튼 및 `in_progress` 상태 자동 감지(Smart Polling) 구현.
* **번역 캐시 갱신**: 서버 재시작 없이 인메모리 캐시를 실시간으로 리로드할 수 있는 API 연동.

## 3. 최종 구현 및 결과 (Implementation & Results)

단계별(Phase 1~3) 개선 작업을 성공적으로 적용한 결과, 다음과 같은 극적인 변화를 이뤄냈습니다.

* **배포 기동 시간 단축**: 3분 이상 소요되던 Startup 시간이 **10초 내외**로 대폭 단축되어, 배포 시 타임아웃 이슈가 완전히 해결되었습니다.
* **운영 효율성 증대**: 어드민 화면을 통해 서버 재시작 없이 성분 사전 재동기화 및 번역 캐시 갱신이 가능해져 운영 편의성이 크게 향상되었습니다.
* **환경별 인프라 가시성 확보**: 로컬 개발 환경과 PaaS(Render) 환경의 메모리 사용량 측정 로직을 분기하여, 프로세스의 정확한 RSS(Resident Set Size) 점유량을 직관적으로 모니터링할 수 있게 되었습니다.

## 4. Takeaway (엔지니어링 교훈)

> **"서버의 생명주기(Lifecycle)와 비즈니스 초기화 로직은 철저히 분리해야 한다."**

애플리케이션 기동 단계(Startup)에서 외부 I/O나 무거운 데이터 동기화 작업을 동기적으로 처리하는 것은 배포 안정성을 해치는 주범입니다. 
1. **빠른 포트 바인딩**을 통해 인프라 레벨의 헬스체크와 배포 안정성을 먼저 확보하고, 
2. 무거운 작업은 **백그라운드 비동기 처리 및 메타데이터 기반 스킵 로직**으로 제어하며, 
3. 예외 상황을 대비한 **어드민 수동 제어 수단**을 함께 마련하는 것이 프로덕션 레벨의 백엔드 시스템을 구축하는 핵심이라는 점을 다시 한번 깊이 깨달은 작업이었습니다.

앞으로도 PickSafe 팀은 안정적이고 확장 가능한 아키텍처를 위해 치 고민하고 개선해 나가겠습니다. 읽어주셔서 감사합니다.
