안녕하세요, PickSafe 백엔드 팀입니다. 

최근 서비스를 지속해서 고도화하고 배포 파이프라인을 점검하는 과정에서, 사소해 보이지만 서비스 안정성에 큰 영향을 미치는 병목 현상을 마주했습니다. 바로 **애플리케이션 Startup 단계에서 발생하는 3분 이상의 배포 지연 현상**이었습니다.

이번 글에서는 어떤 원인으로 지연이 발생했는지 분석하고, **FastAPI의 이벤트 루프와 메타데이터 플래그 패턴**을 활용해 이를 어떻게 극복했는지, 그리고 운영 편의성을 위해 어드민 아키텍처를 어떻게 개선했는지 공유해 드립니다.

---

## 1. Problem: 왜 배포마다 3분이 걸렸을까?

클라우드 플랫폼(예: Render)에 배포를 진행할 때, 로그 창에 반복적으로 다음과 같은 메시지가 찍히는 것을 발견했습니다.

> *"No open ports detected"*

서버가 올라가야 하는데, 포트를 열지 못하고 2~3분 동안 멈춰 있는 현상이었습니다. 원인을 추적해 보니, 문제는 `main.py`의 **모듈 레벨(Module-level)**에서 실행되는 무거운 동기(Synchronous) 작업들에 있었습니다.

FastAPI 앱이 라우터를 로드하고 포트를 바인딩하기도 전에, 아래와 같은 작업들이 순차적으로 블로킹 방식으로 실행되고 있었습니다.

1. **대용량 데이터 동기화 (`ingredients_master` Hydration):** DW Failover 등의 상황에서 매 배포마다 전체 데이터를 다시 복제 (소요 시간: 1~3분)
2. **DB 간 데이터 이관:** 완료 여부와 무관하게 매번 테이블을 조회하고 마이그레이션 시도 (소요 시간: 수십 초)
3. **스키마 변경 쿼리 (`ALTER TABLE`):** 이미 존재하는 컬럼임에도 매 배포마다 확인 및 실행 (소요 시간: 수 초 $\times$ 10회 이상)
4. **번역 캐시 적재 및 타임존 설정:** 동기 블로킹 방식으로 메모리에 적재

결과적으로 **"서버가 준비될 때까지 아무것도 하지 못하는 구조"**가 배포 지연과 타임아웃을 유발하고 있었습니다.

---

## 2. Decision: 아키텍처 개선 및 대안 비교

이 문제를 해결하기 위해 4가지 핵심 트랙(Track)을 설정하고 아키텍처를 전면 개편했습니다.

### Track A. 완료 플래그(`system_meta`) 도입으로 중복 작업 차단
매번 반복되던 무거운 데이터 이관과 성분 사전 동기화 작업을 스킵하기 위해, DB에 `system_meta` (Key-Value 구조) 테이블을 도입했습니다.
* **DB 이관 작업:** 최초 1회 성공 시 `dw_migration_v1 = completed` 플래그를 기록하고, 이후 기동 시 플래그를 확인하여 즉시 스킵합니다.
* **성분 사전 동기화:** `dw_hydration_v1 = completed` 플래그를 두어 불필요한 네트워크 I/O를 원천 차단했습니다. (단, 운영상 필요할 때는 어드민을 통해 강제 재동기화 가능)

### Track B. 무거운 초기화 작업을 백그라운드(`startup_event`)로 이관
FastAPI의 `@app.on_event("startup")` 라이프사이클 훅을 활용했습니다. 
모듈 레벨에서 실행되던 무거운 작업들을 비동기 백그라운드 태스크(`_background_init`)로 분리하여, 서버는 기본적인 DDL 확인 후 **포트를 즉시 열어 10초 이내에 정상 기동**하도록 변경했습니다.

```
[기존 Startup 흐름]
임포트 → DDL → DB 이관 → Hydration → 번역캐시 → 포트 오픈 (3분+)

[개선 후 Startup 흐름]
임포트 → DDL → 포트 즉시 오픈 (~10초) → [백그라운드 비동기 실행] 번역캐시 → 이관 스킵 → 성분 사전 스킵
```

### Track C. 운영 편의성을 위한 어드민 인프라 UI 구축
서버가 백그라운드에서 초기화되더라도, 운영자가 상태를 모니터링하고 제어할 수 있는 수단이 필요했습니다. 어드민 인프라 화면(`/admin/infra`)에 다음 기능을 추가했습니다.
1. **성분 사전 동기화 관리:** Main/DW DB 건수 및 최종 동기화 시각 실시간 표기, `🔄 성분 사전 재동기화` 버튼 및 Smart Polling을 통한 진행 상태(`in_progress`) 자동 감지.
2. **번역 문구 캐시 관리:** 8개 국어 지원 현황 및 총 캐시 수 표기, `🔄 번역 캐시 즉시 갱신` 버튼을 통해 **서버 재시작 없이 인메모리 캐시를 실시간 리로드**.

### Track D. 환경별 스마트 메모리 모니터링
로컬 개발 환경과 클라우드 컨테이너 환경의 메모리 측정 기준이 달라 발생하는 혼선을 줄였습니다.
* **로컬 환경:** 내 PC 전체 메모리 사용량(`19.9%`, `7.74 GB / 38.88 GB`)을 메인으로 보여주며, 하단 서브 텍스트로 `FastAPI 프로세스 메모리`를 함께 표기합니다.
* **클라우드 컨테이너 환경:** 512MB 제한에 맞춘 실사용량(`77.3 MB / 512 MB`)을 직관적으로 노출하여 리소스 누수를 빠르게 감지할 수 있게 개선했습니다.

## 3. Result & Takeaway: 무엇을 얻었는가?

이러한 개선 작업을 거친 후 서비스는 다음과 같은 극적인 변화를 맞이했습니다.

* **배포 시간 94% 이상 단축:** Startup 시간이 **3분 이상에서 10초 내외**로 대폭 단축되어, Render 배포 시 발생하던 포트 바인딩 타임아웃 이슈가 완전히 해결되었습니다.
* **제로 다운타임 핫픽스:** 서버 기동이 빨라짐에 따라 긴급 핫픽스 배포 시 서비스 다운타임이 최소화되고, 전체적인 배포 주기가 빨라졌습니다.
* **운영 생산성 향상:** 서버를 재시작하지 않고도 어드민 화면에서 성분 사전 재동기화나 번역 캐시 갱신을 수동으로 제어할 수 있게 되었습니다.

### 💡 엔지니어링 교훈
> **"I/O 작업과 서버 부팅 프로세스는 반드시 분리하라."**

웹 프레임워크가 포트를 열고 트래픽을 받을 준비를 하는 과정(Lifecycle)과, 외부 데이터베이스나 거대한 데이터셋을 동기화하는 비즈니스 로직은 철저히 분리되어야 합니다. 특히 클라우드 환경에 배포하는 애플리케이션이라면, '서버의 빠른 기동(Fast Startup)'이 인프라 안정성과 직결된다는 점을 다시 한번 깊이 깨달은 작업이었습니다.

앞으로도 PickSafe 팀은 안정적이고 확장 가능한 아키텍처를 바탕으로 더 나은 서비스 경험을 만들어 가겠습니다. 읽어주셔서 감사합니다!
