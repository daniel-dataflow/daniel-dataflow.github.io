새로운 기능을 배포할 때마다 슬랙 채널에 경고 메시지가 울립니다. 
클라우드 호스팅 플랫폼(Render)의 로그에는 **"No open ports detected"**라는 메시지가 2~3분간 반복되고, 헬스 체크(Health Check) 실패로 인해 배포가 취소되거나 지연되는 현상이 발생하곤 했습니다.

서비스가 커지고 다루는 데이터의 양이 늘어남에 따라, 애플리케이션 기동(Startup) 단계에서 수행되는 초기화 작업들이 서버의 발목을 잡기 시작한 것입니다. 

이번 글에서는 **초기 기동 시간 3분 이상에서 10초 미만으로 대폭 단축**시킨 과정과 함께, 서비스 안정성을 확보하기 위해 도입한 **DB 유지보수 자동화 및 옵저버빌리티(Observability) 개선 여정**을 공유합니다.

## 1. 문제 정의: 무엇이 우리 애플리케이션의 숨통을 막고 있었는가?

원인은 명확했습니다. 애플리케이션 구동을 담당하는 `main.py` 내부의 **모듈 레벨(Module Level)**에서, 서버가 포트를 열고 클라이언트의 요청을 받을 준비를 하기도 전에 무겁고 동기적인 작업들을 순차적으로 실행하고 있었기 때문입니다.

당시 스타트업 단계에서 발생하던 병목 작업들을 분석해 보니 다음과 같았습니다.

| 작업 내용 | 위치 | 소요 시간 | 근본적인 문제점 |
| :--- | :--- | :--- | :--- |
| **마스터 데이터 동기화 (Hydration)** | `main.py` | 1~3분 | 배포 시마다 외부 데이터웨어하우스(DW)로부터 전체 데이터를 매번 재복제함. |
| **데이터 이관 (Migration)** | `main.py` | 수십 초 | 완료 여부와 관계없이 매 구동마다 중복해서 데이터 조회를 수행함. |
| **스키마 수정 (`ALTER TABLE`)** | `main.py` | 수 초 $\times$ N회 | 이미 존재하는 컬럼임에도 매번 배포 때마다 구문을 중복 실행하여 검사함. |
| **번역 캐시 인메모리 적재** | `main.py` | 수 초 | 동기 블로킹(Blocking) 방식으로 실행되어 다음 프로세스를 막음. |

FastAPI와 같은 ASGI 프레임워크는 이벤트 루프가 싱글 스레드로 동작하기 때문에, 기동 시점에 동기식 블로킹 작업이 길어지면 **서버는 포트조차 바인딩하지 못한 채 멈춰 서게 됩니다.** 클라우드 플랫폼 입장에서는 서버가 죽어 있는 것으로 판단해 컨테이너를 강제 종료하는 악순환이 반복되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 엔지니어링 팀은 세 가지 방향성을 두고 고민했습니다.

### 대안 1: 플랫폼의 헬스 체크 임계값(Timeout) 늘리기
* **장점:** 코드 수정 없이 즉각적으로 배포 실패를 막을 수 있음.
* **단점:** 임시방편에 불과함. 오토스케일링(Auto-scaling)이나 긴급 핫픽스 배포 시, 인스턴스 하나가 뜨는 데 여전히 3분 이상 걸려 장애 대응 속도가 치명적으로 느려짐.

### 대안 2: 별도의 초기화 스크립트(Pre-start Script) 활용
* **장점:** 컨테이너 실행 전 별도 프로세스로 가동하므로 서버 메인 루프에 영향을 주지 않음.
* **단점:** 초기화 스크립트가 실행되는 동안에도 결국 헬스 체크 타임아웃이 발생할 수 있어, 완전한 비동기 처리가 어려움.

### 대안 3: 비동기 백그라운드 전환 및 상태 플래그 데이터베이스 도입 (선택)
* **장점:** 서버는 즉시 포트를 열어 10초 이내에 정상 기동 상태로 전환됨. 무거운 작업들은 백그라운드 스레드에서 순차 처리하며, 이미 완료된 무거운 이관 작업은 메타 테이블의 플래그를 통해 즉시 스킵(Skip)함.
* **단점:** 비동기 작업 중 들어오는 초기 요청에 대해 데이터 정합성을 보장할 장치가 필요함. (이는 어드민 페이지에서의 복구 기능 및 상태 모니터링으로 보완하기로 결정)

## 3. 해결책: 3대 개선 트랙(Track)

우리는 시스템 안정성과 운영 효율성을 모두 잡기 위해 구조적 개선을 단행했습니다.

### Track A. 완료 플래그(`system_meta`) 도입을 통한 중복 작업 제거
매번 무식하게 전체 데이터를 긁어오던 방식을 개선하기 위해, 일종의 '상태 기록부'인 `system_meta` 테이블을 설계했습니다. key-value 구조의 단순한 테이블로, 특정 마이그레이션이나 동기화 작업이 완료되면 기록을 남깁니다.

```sql
-- 개념 구조 (보안을 위해 단순화된 스키마입니다)
CREATE TABLE system_meta (
    meta_key VARCHAR(255) PRIMARY KEY,
    meta_value VARCHAR(255),
    updated_at TIMESTAMP
);
```

이 플래그를 통해 **데이터 이관 작업**이나 **마스터 데이터 동기화**는 최초 1회만 실행된 후, 이후 기동 시점에는 단 `0.01초`만에 스킵됩니다.

### Track B. 무거운 작업을 `startup_event` 비동기 백그라운드로 격리
서버 기동을 방해하던 모든 무거운 작업을 FastAPI의 `@app.on_event("startup")` (혹은 `lifespan`) 이벤트 핸들러 하위의 비동기 백그라운드 태스크로 이관했습니다.

```python
# 개선된 흐름의 예시 코드 (컨셉)
@app.on_event("startup")
async def startup_event():
    # 1. 최소한의 연결성 및 필수 DDL만 검증 (포트 오픈 방해 금지)
    # 2. 무거운 작업은 백그라운드 태스크로 예약 후 즉시 리턴
    asyncio.create_task(run_background_initialization())
```

이로 인해 전체적인 스타트업 흐름이 아래와 같이 드라마틱하게 개선되었습니다.

```
[기존 Startup 흐름]
임포트 ➔ DDL ➔ DB 이관 ➔ Hydration ➔ 번역 캐시 ➔ 포트 오픈 (3분 이상 소요)

[개선 후 Startup 흐름]
임포트 ➔ 필수 DDL ➔ 포트 즉시 오픈 (10초 미만) ➔ [백그라운드] 번역 캐시 ➔ 이관 확인(스킵) ➔ Hydration(스킵)
```

### Track C. 운영자를 위한 인프라 모니터링 및 온디맨드(On-Demand) UI 구축
비동기로 작업을 넘기면서 생기는 불안 요소(예: 백그라운드 작업 실패 시 복구 대책)는 **어드민 내부 인프라 대시보드**를 개발하여 극복했습니다.

* **동적 마스터 데이터 동기화 섹션:** Main DB와 외부 DB의 데이터 건수 불일치율을 모니터링하고, 필요할 때 운영자가 버튼 클릭 한 번으로 `🔄 재동기화`를 수행할 수 있게 했습니다. (Smart Polling을 통해 실시간 진행률 표시)
* **번역 문구 캐시 리로드:** 수천 개의 다국어 캐시 문구를 서버 재시작 없이 실시간으로 리로드할 수 있는 버튼을 배치하여 배포 없는 운영이 가능케 했습니다.
* **반응형 대시보드:** 데스크톱에서는 정보 밀도를 높이기 위해 2열 레이아웃으로, 모바일에서는 1열 스택으로 전환되는 UI를 적용하여 모바일 장애 대응력도 높였습니다.

```
+--------------------------------------------------+
|               어드민 인프라 대시보드               |
+------------------------+-------------------------+
| [마스터 데이터 동기화]   | [인메모리 번역 캐시]     |
| - 상태: 정상 (대기 중)  | - 캐시 문구 수: 2,400개  |
| - 데이터 불일치: 0건    | - 최종 동기화: 5분 전   |
| [🔄 즉시 동기화 실행]   | [🔄 캐시 즉시 갱신]     |
+------------------------+-------------------------+
```

## 4. 환경별 스마트 메모리 모니터링 적용

서버의 안정성을 모니터링하기 위해서는 자원 사용량을 정확히 측정하는 것이 중요합니다. 특히 컨테이너 환경인 **Render**와 개발용 **로컬 환경(PC)**은 메모리 제한 스펙이 완전히 다릅니다. 

이를 구분하지 않고 모니터링 지표를 보여주면, 컨테이너의 실제 여유 메모리를 잘못 판단하여 **OOM(Out Of Memory)** 장애를 유발할 수 있습니다. 이를 해결하기 위해 환경별 맞춤 지표를 수집하도록 로직을 세분화했습니다.

* **로컬 환경:** 전체 호스트 PC의 메모리를 기준으로 오버뷰를 제공합니다. (`19.9% 사용 중, 7.74 GB / 38.88 GB`)
* **클라우드 컨테이너 환경:** 샌드박스 한계점인 `512MB`를 타깃으로 삼아, 실제 해당 FastAPI 프로세스가 점유하고 있는 정확한 **RSS(Resident Set Size)** 점유율을 모니터링 화면에 뿌려줍니다. (`15.1% 사용 중, 77.3 MB / 512 MB`)

이를 통해 컨테이너가 가용 자원 한계에 도달하기 전 선제적으로 인프라 스케일업 의사결정을 내릴 수 있게 되었습니다.

## 5. 엔지니어링 교훈 (Takeaways)

이번 개선 작업을 통해 우리 팀은 다음과 같은 값진 교훈을 얻었습니다.

1. **"스타트업 단계의 모든 작업은 비용이다"**
   애플리케이션 기동 시 무심코 추가하는 초기화 코드들은 기술 부채가 되어 배포 파이프라인의 발목을 잡습니다. 기동 시점에는 오직 **'포트를 열기 위한 최소한의 작업'**만 수행하고, 나머지는 영리하게 비동기 처리하거나 수동 트리거로 넘겨야 합니다.
2. **"클라우드 네이티브 환경에 맞는 아키텍처 설계"**
   현대의 컨테이너 오케스트레이션 환경은 빠른 기동과 빠른 정상 상태 확인(Liveness/Readiness Probe)을 전제로 합니다. 로컬에서 잘 돌던 모놀리식 코드가 클라우드 배포 환경에서는 실패작이 될 수 있음을 늘 염두에 두어야 합니다.
3. **"운영 생산성과 인프라 옵저버빌리티의 시너지"**
   인프라의 내부 상태를 시각화하고 제어할 수 있는 어드민 도구는 개발자의 심리적 안정감을 극대화합니다. 모니터링 대시보드는 사후 대처용이 아닌, 실시간 자원 관리와 선제적 조치를 위한 필수 요소입니다.

현재 저희 팀은 임시방편으로 남아있던 `ALTER TABLE` 검사 구문들을 완전히 걷어내고, 데이터베이스 형상 관리 도구인 **Alembic 마이그레이션**으로 통합하는 다음 단계를 준비하고 있습니다. 

단순히 "서버가 잘 뜬다"를 넘어, "배포가 안전하고 빨라진다"는 신뢰감을 팀 전체에 선물한 뜻깊은 아키텍처 개선 여정이었습니다.
