안녕하세요, PickSafe 백엔드 팀입니다. 

최근 서비스를 클라우드 플랫폼(Render)에 배포하는 과정에서 배포 직후 **"No open ports detected"** 로그와 함께 헬스체크 타임아웃이 발생하고, 서버가 실제로 뜨는 데까지 **3분 이상 소요**되는 병목 현상을 마주했습니다.

이번 포스팅에서는 모듈 레벨에서 동기적으로 실행되던 무거운 초기화 작업들을 분석하고, **비동기 백그라운드 이벤트**와 **완료 플래그(Idempotent Flag)** 패턴을 도입해 서버 기동 시간을 **10초 이내**로 획기적으로 단축한 아키텍처 개선 경험을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 왜 서버가 3분 동안 응답이 없었을까?

원인은 `main.py` 모듈 레벨(서버가 포트를 열기 전)에서 실행되던 순차적이고 무거운 동기 작업들에 있었습니다. 

서버가 외부로 포트를 열고 트래픽을 받을 준비를 하기도 전에, 아래와 같은 작업들이 메인 스레드를 블로킹하고 있었습니다.

| 작업 | 위치 | 추정 소요 시간 | 문제점 |
|---|---|---|---|
| 대용량 데이터 사전 Hydration | `main.py` | 1 ~ 3분 | 데이터웨어하우스(DW) Failover 시 매 배포마다 전체 재복제 발생 |
| DB 간 데이터 이관 | `main.py` | 수십 초 | 이미 완료된 작업임에도 매번 테이블 전체 조회 및 검증 |
| 스키마 변경 (`ALTER TABLE`) | `main.py` | 수 초 × N회 | 이미 존재하는 컬럼도 매 배포마다 존재 여부 확인 |
| 번역 캐시 적재 및 타임존 설정 | `main.py` | 수 초 | 동기 블로킹 방식으로 전체 흐름 지연 |

이로 인해 클라우드 배포 환경에서 헬스체크 타임아웃이 빈번하게 발생했고, 핫픽스 배포 시에도 긴 다운타임이 강제되는 운영상 리스크가 컸습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 **"서버가 빨리 뜨게 만들고, 무거운 작업은 뒤로 미루자"**는 원칙을 세우고 몇 가지 아키텍처 대안을 검토했습니다.

### 대안 1: 외부 작업 디스패처 (Celery / Redis Queue) 도입
* **장점:** 완벽한 비동기 분산 처리 가능.
* **단점:** 초기 인프라 구성 비용(Redis/Broker 관리)이 크고, 현재 단일 서버 배포 구조 대비 오버엔지니어링 우려.
* **결론:** 기각. FastAPI 내장 이벤트 루프만으로도 충분히 해결 가능하다고 판단.

### 대안 2: FastAPI `startup_event` + 완료 플래그 패턴 (채택)
* **장점:** 추가 인프라 없이 FastAPI 생명주기(`@app.on_event("startup")`)를 활용해 가볍게 구현 가능. 멱등성(Idempotency)을 보장하는 메타 테이블을 두어 중복 실행 방지.
* **단점:** 백그라운드에서 실행되는 동안 초기 데이터 조회가 필요한 요청에 대한 예외 처리 필요.
* **결론:** 채택.

## 3. 최종 해결 및 아키텍처 개선 (Solution)

### Track A: 완료 플래그(`system_meta`) 도입을 통한 멱등성 확보
DB에 Key-Value 구조의 `system_meta` 테이블을 신규 생성했습니다. 
* **데이터 이관 작업:** 최초 1회 완료 시 `dw_migration_v1 = completed` 플래그를 기록하고, 이후 기동 시 플래그를 확인하여 즉시 스킵합니다.
* **사전 동기화:** 플래그를 기반으로 중복 실행을 막되, 운영자가 필요할 때 어드민을 통해 강제로 재동기화할 수 있는 안전장치를 마련했습니다.

### Track B: FastAPI 생명주기를 활용한 포트 선바인딩
`main.py` 모듈 레벨의 블로킹 코드를 제거하고, 모든 무거운 작업을 비동기 백그라운드 태스크(`_background_init`)로 격리했습니다.

```python
@app.on_event("startup")
async def startup_event():
    # 서버 포트는 이미 열린 상태, 백그라운드에서 안전하게 무거운 작업 수행
    asyncio.create_task(_background_init())
```

* **개선 전 흐름:** 임포트 → DDL → DB 이관 → Hydration → 번역캐시 → 포트 오픈 **(3분 이상 소요)**
* **개선 후 흐름:** 임포트 → DDL → **포트 즉시 오픈 (~10초)** → [백그라운드] 이관/동기화 스킵 및 비동기 적재

### Track C: 어드민 인프라 모니터링 & 수동 제어 UI
서버가 백그라운드에서 초기화를 수행하는 동안, 운영자가 시스템 상태를 파악하고 수동으로 제어할 수 있도록 어드민 인프라 화면(`/admin/infra`)을 고도화했습니다.
* 성분 사전 건수 및 최종 동기화 시각 실시간 표기 (`🔄 성분 사전 재동기화` 버튼 제공)
* 8개 국어 번역 캐시 문구 수(약 2,400여 개) 인메모리 실시간 리로드 기능
* 로컬 개발 환경과 클라우드 컨테이너 환경의 메모리 사용량(RSS)을 환경별로 분기하여 정확하게 모니터링할 수 있도록 지표 개선

## 4. 엔지니어링 교훈 (Takeaways)

1. **포트 바인딩은 최우선 과제입니다:** 클라우드 배포 환경에서 애플리케이션의 헬스체크는 생존과 직결됩니다. 무거운 초기화 작업은 반드시 포트 오픈 이후의 라이프사이클(Background Task)로 밀어내야 합니다.
2. **멱등성(Idempotency)은 배포 안정성의 핵심입니다:** 매번 서버가 뜰 때마다 전체 데이터를 검증하거나 마이그레이션하는 구조는 확장성에 치명적입니다. 메타 플래그(`system_meta`)를 활용해 "이미 완료된 작업은 스킵한다"는 원칙을 적용하는 것만으로도 시스템 부하를 극적으로 줄일 수 있습니다.
3. **운영 편의성을 고려한 아키텍처:** 백그라운드 처리를 도입하더라도, 운영자가 시스템 상태를 눈으로 확인하고 필요시 수동 트리거할 수 있는 어드민 인터페이스가 함께 뒷받침되어야 진정한 의미의 프로덕션 레디(Production-Ready) 아키텍처가 완성됩니다.

이번 최적화를 통해 서버 기동 시간을 **3분 이상에서 10초 내외**로 단축함과 동시에, 배포 안정성과 운영 가시성이라는 두 마리 토끼를 모두 잡을 수 있었습니다. 유사한 병목을 겪고 계신 엔지니어분들께 작은 참고가 되었기를 바랍니다.
