안녕하세요, PickSafe 백엔드 엔지니어입니다. 

최근 서비스를 클라우드 플랫폼(Render)에 배포하는 과정에서, 배포 로그에 **"No open ports detected"** 에러가 반복되며 서버가 실제로 뜨기까지 **3분 이상 소요되는 치명적인 병목 현상**을 마주했습니다. 

이번 포스팅에서는 모듈 레벨의 무거운 동기 작업들이 왜 서버 기동을 지연시켰는지 분석하고, **완료 플래그(System Meta) 도입**, **FastAPI `startup_event`를 통한 비동기 백그라운드 전환**, 그리고 **어드민을 통한 수동 제어 구조**로 이를 어떻게 해결했는지 공유해 드립니다.

---

## 1. Problem: 왜 서버 기동에 3분이나 걸렸을까?

기존 구조에서는 `main.py` 모듈 레벨에서 서버 포트를 열기 전, 다음과 같은 무거운 동기 작업들을 순서대로(블로킹 방식으로) 실행하고 있었습니다.

| 작업 | 위치 | 추정 소요 시간 | 문제점 |
|---|---|---|---|
| **성분 사전 Hydration** | `main.py` | 1~3분 | DW(Data Warehouse) Failover 발생 시, 매 배포마다 전체 데이터를 재복제함 |
| **DB 간 데이터 이관** | `main.py` | 수십 초 | 이미 이관이 완료되었음에도 매번 테이블을 조회함 |
| **스키마 변경 (`ALTER TABLE`)** | `main.py` | 수 초 × 10회 | 이미 존재하는 컬럼도 매번 확인 및 수정 시도 |
| **번역 캐시 적재** | `main.py` | 수 초 | 동기 블로킹 방식으로 인메모리 적재 |

이로 인해 클라우드 플랫폼은 포트가 열리지 않는 것으로 판단하여 타임아웃을 유발했고, 핫픽스 배포 시에도 긴 다운타임을 감수해야 하는 비효율적인 상황이었습니다.

---

## 2. Trade-off & Architecture: 어떻게 개선할 것인가?

문제를 해결하기 위해 **"서버가 빠르게 포트를 열고, 무거운 작업은 뒤로 미룬다(Lazy/Asynchronous)"**는 원칙을 세우고 4가지 트랙으로 나누어 아키텍처를 개편했습니다.

### Track A: `system_meta` 플래그 테이블 도입 (멱등성 확보)
매 배포마다 반복되던 이관 및 동기화 작업을 막기 위해 메인 DB와 DW DB에 키-값 형태의 `system_meta` 테이블을 신규 생성했습니다.
* **데이터 이관**: 최초 1회 완료 시 `dw_migration_v1 = completed` 플래그를 기록하고, 이후 기동 시 플래그를 확인하여 즉시 스킵합니다.
* **성분 사전 동기화**: `dw_hydration_v1 = completed` 플래그를 두어 불필요한 네트워크 I/O를 원천 차단했습니다. (운영자 필요 시 어드민에서 강제 재동기화 가능)

### Track B: FastAPI `startup_event`를 활용한 논블로킹 기동
기존에 모듈 임포트 시점에 실행되던 무거운 작업들을 `@app.on_event("startup")` 이벤트의 백그라운드 태스크(`_background_init`)로 격리했습니다.
* 스키마 기본 검증만 마친 뒤 **서버 포트를 즉시 오픈(10초 이내)** 합니다.
* 포트가 열린 이후 백그라운드에서 번역 캐시 적재, 이관 여부 확인, 성분 사전 동기화가 순차적으로 안전하게 실행됩니다.

```text
[기존 구조 (Blocking)]
임포트 → DDL → DB 이관 → Hydration → 번역 캐시 → 포트 오픈 (3분 이상 소요 ❌)

[개선된 구조 (Non-Blocking)]
임포트 → DDL → 포트 즉시 오픈 (~10초) ⭕
              └── [Background Task] 번역 캐시 적재 / 이관 스킵 / 사전 동기화 실행
```

### Track C: 어드민 인프라 모니터링 & 수동 제어 UI
백그라운드로 전환됨에 따라, 운영자가 현재 시스템 상태를 직관적으로 파악하고 제어할 수 있는 관리자 화면(`/admin/infra`)을 구축했습니다.
1. **성분 사전 동기화 상태 확인 및 수동 제어**: Main/DW 건수 및 최종 동기화 시각 표기, `🔄 성분 사전 재동기화` 버튼 제공 (`in_progress` 상태 시 Smart Polling 적용)
2. **번역 캐시 실시간 리로드**: 8개 국어, 약 2,400여 개의 캐시 현황을 모니터링하고, 서버 재시작 없이 `🔄 번역 캐시 즉시 갱신` 수행 가능
3. **반응형 2열 레이아웃**: 데스크톱 환경에서는 넓은 화면을 활용해 1:1 좌우 균형 배치, 모바일에서는 1열 스택 구조로 자동 전환되도록 UX 개선

### Track D: 환경별 스마트 메모리 모니터링
로컬 환경과 클라우드(Render 컨테이너, 512MB 제한) 환경의 인프라 스펙 차이를 고려했습니다.
* **로컬**: PC 전체 메모리 사용량(`19.9%`, `7.74 GB / 38.88 GB`)을 메인으로 보여주되, 하단에 프로세스 실제 점유량(`FastAPI: XX MB`)을 서브 텍스트로 표기
* **Render**: 컨테이너 한도 대비 실사용량(`77.3 MB / 512 MB`, `15.1%`)을 직관적으로 모니터링 가능하도록 분기 처리

---

## 3. Takeaway: 무엇을 얻었는가?

1. **배포 안정성 및 속도 극대화**: Startup 시간이 **3분+에서 10초 내외**로 대폭 단축되어, Render 배포 시 포트 바인딩 타임아웃 이슈가 완전히 해결되었습니다.
2. **운영 편의성 확보**: 서버를 재시작하지 않고도 어드민 화면에서 성분 사전 동기화와 번역 캐시 갱신을 제어할 수 있게 되었습니다.
3. **아키텍처의 탄력성**: 초기화 로직에 멱등성(Idempotency) 개념과 비동기 백그라운드 패턴을 적용함으로써, 향후 대규모 데이터 마이그레이션 작업이 추가되더라도 메인 배포 파이프라인에 영향을 주지 않는 구조를 마련했습니다.

앞으로도 PickSafe 팀은 안정적이고 확장 가능한 인프라 아키텍처를 구축하기 위해 지속적인 개선을 이어 나가겠습니다. 감사합니다!
