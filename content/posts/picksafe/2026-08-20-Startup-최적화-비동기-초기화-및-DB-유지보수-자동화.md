안녕하세요, PickSafe 백엔드 팀입니다. 

최근 서비스를 지속적으로 고도화하면서 마주한 흥미로운 인프라 병목 현상과, 이를 해결하기 위해 적용한 아키텍처 개선 과정을 공유해 드립니다. 

배포할 때마다 서비스가 3분 이상 지연되고, 클라우드 플랫폼(Render 등)에서 "No open ports detected" 에러와 함께 헬스체크 타임아웃이 발생하던 문제를 어떻게 해결했는지, 그 기술적 의사결정 과정을 소개합니다.

---

## 1. Problem: 왜 서버 기동에 3분이 걸렸을까?

초기 서비스 아키텍처에서는 `main.py` 모듈 레벨(서버가 포트를 열기 전)에서 데이터베이스 마이그레이션, 대용량 데이터 이관, 외부 성분 사전 동기화, 번역 캐시 적재 등의 무거운 작업들을 **동기식 블로킹(Blocking) 방식**으로 순차 실행하고 있었습니다.

분석해 본 주요 병목 작업들은 다음과 같습니다:

1. **성분 사전 동기화 (`ingredients_master`)**: 데이터웨어하우스(DW) Failover 시 매 배포마다 전체 데이터를 다시 복제 (1~3분 소요)
2. **DB 데이터 이관**: 완료 여부와 상관없이 매번 테이블 전체를 조회하고 비교
3. **스키마 변경 (`ALTER TABLE`)**: 이미 존재하는 컬럼도 매 배포마다 체크
4. **번역 캐시 적재 및 타임존 설정**: 서버 기동을 가로막는 무거운 동기 연산들

이로 인해 서버가 실제 HTTP 요청을 받을 수 있는 포트를 열기까지 무려 3분 이상의 시간이 소요되었고, 이는 빠른 배포와 핫픽스가 생명인 스타트업 환경에서 큰 발목을 잡았습니다.

---

## 2. Decision: 아키텍처 트레이드오프와 해결 전략

이 문제를 해결하기 위해 **"서버 기동 속도(Time-to-Port)"**를 최우선 지표로 삼고, 아래 3가지 핵심 트랙으로 아키텍처를 재설계했습니다.

### Track A: 완료 플래그(`system_meta`) 도입으로 중복 작업 제거
모든 초기화 작업이 매 배포마다 실행될 필요는 없습니다. Main DB와 DW DB에 key-value 구조의 `system_meta` 테이블을 신규 생성했습니다.
* **데이터 이관 및 성분 사전 동기화**: 1회 완료 시점에 `completed` 플래그를 기록하고, 이후 기동 시 플래그가 존재하면 즉시 스킵합니다. 
* 필요시 어드민 UI를 통해 수동으로 플래그를 초기화하고 재동기화할 수 있도록 설계했습니다.

### Track B: 동기 블로킹 코드를 비동기 백그라운드(`startup_event`)로 전환
서버의 포트 오픈을 지연시키는 주범인 무거운 작업들을 `main.py` 모듈 레벨에서 걷어냈습니다.
* FastAPI의 `@app.on_event("startup")`을 활용해, 서버는 DDL 확인 후 **10초 이내에 즉시 포트를 열고 정상 기동**하도록 변경했습니다.
* 무거운 초기화 작업들은 백그라운드 태스크(`_background_init`)로 이관하여 서버 기동 직후 비동기로 안전하게 실행되도록 구조를 변경했습니다.

> **[아키텍처 변경 요약]**
> * **기존:** 임포트 → DDL → DB 이관 → Hydration → 번역캐시 → 포트 오픈 (`3분+ 소요`)
> * **개선:** 임포트 → DDL → **포트 즉시 오픈 (`~10초`)** → [백그라운드] 번역캐시 / 이관 / 성분 동기화 처리

### Track C: 어드민 인프라 모니터링 & 수동 유지보수 UI 구축
자동화된 백그라운드 작업이 실패하거나, 데이터 수동 갱신이 필요한 운영상의 요구사항을 해결하기 위해 어드민 인프라 화면(`/admin/infra`)을 고도화했습니다.
* **성분 사전 및 번역 캐시 제어**: 현재 동기화 상태와 캐시 적재량을 실시간으로 확인하고, 서버 재시작 없이 `🔄 즉시 갱신/재동기화`를 수행할 수 있는 UI를 구축했습니다. (스마트 폴링 적용)
* **환경별 메모리 모니터링**: 로컬 개발 환경과 클라우드 컨테이너 환경의 메모리 측정 기준을 분리하여, 실제 프로세스의 점유량(RSS)을 정확히 모니터링할 수 있도록 개선했습니다.

## 3. Implementation & Results: 무엇이 달라졌는가?

이러한 개선 작업을 단계별로 적용한 결과는 매우 성공적이었다.

| Phase | 주요 작업 내용 | 적용 효과 |
|---|---|---|
| **Phase 1** | `system_meta` 플래그 도입 및 `startup_event` 비동기화 | 기동 시간 **3분+ → 10초 내외로 단축** |
| **Phase 2** | 번역 캐시 비동기 적재 및 타임존 최적화 | 포트 즉시 바인딩 보장 |
| **Phase 3** | 어드민 인프라 DB 유지보수 UI 및 실시간 폴링 | 운영자 수동 복구 및 상태 모니터링 완비 |
| **인프라** | 로컬/클라우드 환경별 스마트 메모리 측정 분기 | 정확한 컨테이너 리소스 파악 |

### 💡 엔지니어링 교훈 (Takeaways)
1. **Critical Path 분리**: 서버가 외부와 통신(포트 오픈)하기 전 단계의 Critical Path에는 네트워크 I/O나 대용량 데이터 처리 로직을 절대 두지 않아야 합니다. 초기화 작업은 철저히 백그라운드로 밀어내야 합니다.
2. **상태 관리(Stateful)의 중요성**: 클라우드 환경에서 배포는 빈번하게 일어납니다. "매번 실행되는 코드"가 아니라 "상태를 체크하고 필요한 경우에만 실행되는(Idempotent한) 코드"로 작성하는 것이 인프라 안정성을 높이는 핵심입니다.
3. **운영 편의성과의 조화**: 완전 자동화도 중요하지만, 분산 환경이나 예외 상황을 대비해 관리자가 UI를 통해 수동으로 상태를 제어할 수 있는 백도어(어드민 기능)를 마련해 두는 것이 프로덕션 안정성에 큰 도움이 됩니다.

앞으로도 PickSafe 팀은 탄탄하고 확장 가능한 아키텍처를 바탕으로 안정적인 서비스를 제공해 나가겠습니다. 감사합니다!
