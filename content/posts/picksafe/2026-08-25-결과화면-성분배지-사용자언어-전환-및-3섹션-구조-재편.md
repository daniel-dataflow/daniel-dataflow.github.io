안녕하세요, PickSafe 백엔드/풀스택 에디터입니다. 

서비스를 고도화하다 보면 기능 구현에 매몰되어 **'개발자의 언어'**로 UI를 채우고 있는 자신을 발견하게 됩니다. 이번 글에서는 성분 분석 서비스인 PickSafe에서 결과 화면의 배지와 정보 구조를 사용자 중심(User-Centric)으로 전면 개편했던 아키텍처 및 프론트엔드/백엔드 리팩토링 경험을 공유하고자 합니다.

---

## 1. Problem: 개발자 중심의 데이터, 혼란스러운 사용자

초기 버전의 PickSafe 결과 화면은 기능 구현에 집중한 나머지, 데이터베이스의 상태를 그대로 화면에 노출하고 있었습니다.

* **맥락 없는 `일치함`**: 사용자는 이 배지가 "DB에서 식별되었다"는 뜻인지, "안전하다"는 뜻인지 직관적으로 알기 어려웠습니다.
* **모호한 `? 미확인 성분`**: 텍스트가 다소 길고, 데이터 부족에 의한 것인지 위험 성분인지 모호했습니다.
* **단일 리스트 구조**: 사용자가 가장 먼저 확인해야 할 '알레르기 유발 성분'을 찾기 위해 불필요한 스크롤을 해야 했습니다.

특히 **"안전함"**이라는 단어를 무심코 쓸 경우, 의료적 진단이나 법적 책임 문제(Medical Liability)로 이어질 수 있는 치명적인 리스크가 있었습니다. 기술적 정확성뿐만 아니라 **비즈니스 도메인의 제약 사항**을 UI/UX와 데이터 구조에 어떻게 녹여낼 것인가가 이번 개선의 핵심 과제였습니다.

---

## 2. Approach & Trade-off: 기술적 고민과 대안 비교

### 2.1 배지 명칭 표준화와 법적 리스크 회피
가장 먼저 배지 텍스트를 표준화했습니다. 

* **기각된 대안 (`안전함` / `좋음`)**: 의료적 판단을 내리는 듯한 인상을 주어 기각했습니다. 사용자가 개인 기피 성분을 등록하지 않았음에도 '안전함' 판정을 받아 오인할 위험이 컸습니다.
* **최종 선택 (`✅ 이상없음`)**: '안전하다'는 단정적 표현 대신, **"우려 성분이 검출되지 않았음"**을 뜻하는 중립적 표현을 채택하여 법적 리스크를 방어했습니다.
* **공인 기준 vs 개인 기준 분리**: 공인 알레르기(EU 82종, 식약처 25종)와 사용자가 직접 온보딩에서 등록한 개인 기피 성분을 각각 `⚠️ 알레르기`와 `⚠️ 기피성분`으로 분리하여 경고의 근거를 명확히 했습니다.

### 2.2 3섹션 Accordion 구조 재편
기존의 단일 리스트 구조를 중요도 순 3섹션(주의 성분 / 이상없는 성분 / 확인 불가 성분)으로 분리했습니다.

* **백엔드 변경**: 파이썬 기반의 결과 처리 레이어에서 성분 분류 결과에 `badge_type` 필드(`"ok"` / `"allergen"` / `"personal"` / `"unknown"`)를 명시적으로 내려주도록 모델을 확장했습니다.
* **프론트엔드 변경**: 상단에 즉시 판정 배너(3상태 색코딩)를 신설하고, 중요도가 높은 `주의 성분` 섹션은 항상 펼쳐두되, `이상없는 성분`과 `확인 불가 성분`은 기본 닫힘(Accordion) 처리하여 정보 밀도를 조절했습니다.

## 3. Implementation: 영향 범위 및 단계별 적용

이번 리팩토링은 백엔드 응답 포맷부터 프론트엔드 템플릿, 다국어 번역 테이블까지 풀스택에 걸쳐 진행되었습니다.

1. **백엔드 (Python)**: 성분 대조 엔진의 출력값에 `badge_type` 메타데이터 추가
2. **템플릿 & JS (HTML/Jinja2)**: 3섹션 아코디언 컴포넌트 렌더링 로직 및 배너 상태 계산기 구현
3. **i18n**: 글로벌 사용자를 위한 4개 국어(EN/KO/JA/ZH) 번역 테이블 신규 등록

안정적인 배포를 위해 **1단계(배지 텍스트 교체) ➔ 2단계(상단 즉시 판정 배너 신설) ➔ 3단계(3섹션 아코디언 구조 재편) ➔ 4단계(다국어 반영)** 순으로 점진적(Iterative) 적용을 진행하여 프로덕션 리스크를 최소화했습니다.

## 4. Takeaway: 엔지니어링 교훈

> **"좋은 소프트웨어는 컴퓨터가 이해하기 쉬운 코드를 넘어, 사용자가 이해하기 쉬운 도메인을 만든다."**

이번 작업을 통해 얻은 교훈은 명확합니다.
1. **도메인 특화 언어(DSL)의 UI 확장**: 백엔드의 DB 매칭 상태(`matched`, `unidentified`)를 그대로 사용자에게 보여주는 것은 안티패턴입니다. 백엔드의 데이터 구조와 프론트엔드의 UX 언어 사이에 명확한 매핑 레이어가 필요합니다.
2. **비즈니스 리스크를 고려한 설계**: `안전함` 같은 단순한 단어도 법적/윤리적 리스크가 될 수 있습니다. 에디터블한 상태 값 설계를 통해 비즈니스 요구사항 변화에 유연하게 대응할 수 있는 구조를 짜야 합니다.

PickSafe는 앞으로도 사용자가 가장 빠르고 정확하게 위험 요소를 파악할 수 있도록, 기술과 도메인 관점 모두에서 단단한 아키텍처를 구축해 나갈 것입니다.
