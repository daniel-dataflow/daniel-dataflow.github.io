시스템을 구축하다 보면 DB의 쿼리 결과나 백엔드 비즈니스 로직의 상태값이 프론트엔드를 거쳐 사용자 화면(UI)까지 그대로 노출되는 실수를 범하곤 합니다. 대표적인 예가 DB 튜플 매칭 성공을 뜻하는 `Matched` 데이터가 사용자 화면에 그대로 **"일치함"**이라는 어색한 배지로 표시되는 현상입니다.

성분 분석 플랫폼 PickSafe 팀은 최근 이러한 **'개발자 관점의 언어'를 '사용자 중심의 언어'로 재설계**하고, 정보의 시각적 우선순위를 재구조화하는 아키텍처 리팩토링을 진행했습니다. 

이번 포스팅에서는 데이터베이스의 매칭 로직이 어떻게 안전한 사용자 경험(UX)으로 승화되었는지, 그 과정에서 발생한 기술적 고민과 법적 리스크 회피 전략, 그리고 백엔드 API 계약(Contract)의 변경 과정을 공유합니다.

---

## 1. 문제 정의: 개발자 용어의 유출과 높은 인지 부하 (Cognitive Load)

기존 시스템의 성분 결과 화면은 두 가지 결정적인 문제를 안고 있었습니다.

### ① 맥락을 알 수 없는 배지 텍스트
DB 데이터 대조 결과가 `MATCHED`일 때 화면에는 단순히 **"일치함"**이라는 배지가 노출되었습니다.
- **사용자의 혼란**: *"이 성분이 무엇과 일치했다는 뜻인가? 내 알레르기 성분과 일치해서 위험하다는 뜻인가, 아니면 안전하다고 확인되었다는 뜻인가?"*
- **데이터 모호성**: DB 인덱스 매칭이라는 백엔드 내부 구현 상세가 사용자 UI 도메인으로 유출(Leakage)된 전형적인 사례였습니다.

### ② 단일 리스트 구조로 인한 탐색 비용 $O(N)$
모든 성분이 단일 수평 리스트로 나열되어 있었습니다. 사용자는 자신에게 치명적일 수 있는 **알레르기 유발 성분을 확인하기 위해 스크롤을 내리며 전체 성분을 하나하나 눈으로 주사(Scan)해야만 했습니다.**

```
[기존 구조]
- 성분 A [일치함]
- 성분 B [⚠️ 알레르기]  <-- 사용자가 직접 찾기 전까지 위험 인지 불가
- 성분 C [? 미확인 성분]
- 성분 D [일치함]
```

## 2. 기술적 고민과 대안 비교 (Trade-offs)

### 고민 1: "안전함"이라는 직관적인 단어를 사용할 수 있는가?
가장 먼저 떠오른 직관적인 텍스트는 `안전함`이었습니다. 하지만 기획 및 기술 검토 과정에서 **법적 리스크(Legal Risk)** 및 **도메인 한계**가 식별되었습니다.

- **문제점**: 플랫폼이 의사의 진단이나 의료적 판단을 대체할 수 없습니다. 사용자가 기피 성분을 프로필에 등록하지 않았을 뿐인데 서비스가 `안전함`이라고 단정 지을 경우, 오인으로 인한 사고 발생 시 법적 책임 및 오탐(False Negative) 리스크가 발생합니다.
- **대안 검토**:

| 대안 | 평가 | 채택 여부 및 이유 |
| :--- | :--- | :--- |
| `일치함` | 개발자 관점 | ❌ **기각**: 의미 불명확 |
| `안전함` | 과도한 보장 | ❌ **기각**: 의료적 진단 오인 및 법적 리스크 |
| `좋음` / `확인됨` | 애매한 맥락 | ❌ **기각**: 사용자 입장에서의 정보 가치 부족 |
| **`이상없음`** | **중립적·명확함** | ✅ **채택**: "우려 성분이 검출되지 않음"을 나타내는 완벽한 도메인 용어 |

또한 공인 기준(EU/식약처)과 개인 설정 기준을 명확히 분리하기 위해 **`⚠️ 알레르기`**(공인)와 **`⚠️ 기피성분`**(개인)으로 배지 분류를 세분화했습니다.

### 고민 2: 프론트엔드 추론 연산 vs 백엔드 Enum 명시
성분의 상태를 분류하는 로직을 프론트엔드 JS에서 계산할지, 백엔드 API의 Response Schema 단계에서 명시할지에 대한 아키텍처적 선택이 필요했습니다.

- **프론트엔드 처리**: API 수정 없이 기존 플래그들을 조합하여 JS에서 배지 타입을 분기. -> *문제: 비즈니스 로직이 프론트엔드로 파편화되고 파급력이 커짐.*
- **백엔드 처리 (채택)**: API 응답 객체에 표준화된 `badge_type` Enum 필드를 신설하여 도메인 응답을 캡슐화.

## 3. 아키텍처 및 구현 스키마 재설계

### 백엔드 API 계약(Contract) 리팩토링
백엔드 도메인 모델에 `badge_type`을 명시적으로 정의하여 프론트엔드가 렌더링에만 집중할 수 있도록 레이어를 separation했습니다.

```json
// 백엔드 API Response Payload 예시 (마스킹 처리됨)
{
  "product_id": "PRD-9921",
  "summary_status": "WARNING", // CRITICAL, WARNING, CLEAN
  "ingredients": [
    {
      "name": "성분명_A",
      "badge_type": "allergen", // allergen | personal | ok | unknown
      "badge_label": "⚠️ 알레르기"
    },
    {
      "name": "성분명_B",
      "badge_type": "ok",
      "badge_label": "✅ 이상없음"
    }
  ]
}
```

### 결과 화면 3섹션 아코디언(Accordion) UX 재편
사용자의 인지 부하를 줄이기 위해 성분 리스트를 **우선순위 기반 3섹션 아코디언 구조**로 재설계했습니다.

1. **상단 즉시 판정 배너**: 페이지 진입 즉시 최상단 배너의 색상(Red/Yellow/Green)과 문구로 전체 결과 요약 전달 ($O(1)$ 인지 가능).
2. **[섹션 1] ⚠️ 주의 성분 (우선순위 최상)**: 공인 알레르기 및 개인 기피 성분을 상단에 강제 배치하며 **기본 펼침(Expanded)** 상태 유지.
3. **[섹션 2] ✅ 이상없는 성분**: 검출되지 않은 안전 성분 그룹 (기본 접힘/Collapsed).
4. **[섹션 3] ❓ 확인 불가 성분**: DB 미등재 성분 그룹 (기본 접힘/Collapsed).

```
┌────────────────────────────────────────────────────────┐
│ [상단 배너] ⚠️ N개의 성분이 알레르기 유발 기준과 일치합니다   │
└────────────────────────────────────────────────────────┘
  ▼ [섹션 1] ⚠️ 주의 필요 성분 (2개)           [ 항상 펼쳐짐 ]
    - 성분 X  [⚠️ 알레르기]
    - 성분 Y  [⚠️ 기피성분]

  ▶ [섹션 2] ✅ 이상없는 성분 (15개)          [ 기본 접힘 ]

  ▶ [섹션 3] ❓ 확인 불가 성분 (1개)          [ 기본 접힘 ]
```

## 4. 단계별 배포 전략 (Zero-Downtime / Risk Mitigation)

기존 동작 중인 UI 시스템의 통째 전환으로 인한 부작용을 최소화하기 위해 4단계 순차 적용 전략을 수립하여 실행했습니다.

1. **1단계 (Data Layer)**: 백엔드 API 신규 Enum `badge_type` 파이프라인 배포 및 배지 텍스트 1차 교체 (`일치함` → `이상없음`).
2. **2단계 (View Layer - Summary)**: 결과 화면 상단에 3상태 색코딩 요약 배너 컴포넌트 신설.
3. **3단계 (View Layer - List)**: 단일 리스트를 3섹션 Accordion 레이아웃으로 데이터 Grouping 및 JS 렌더링 엔진 교체.
4. **4단계 (i18n)**: 글로벌 확장을 위한 다국어 번역 테이블(EN/KO/JA/ZH) 매핑 연동.

## 5. 엔지니어링 교훈 (Takeaways)

1. **유비쿼터스 언어(Ubiquitous Language)는 API 계약에도 적용되어야 한다**
   DB의 상태값(`MATCHED`)이 도메인 지식 없이 클라이언트로 흐르면 UI 품질이 저하됩니다. 백엔드 개발자도 엔드유저 도메인 언어를 이해하고 API 스키마를 설계해야 합니다.

2. **기술적 제약과 법적 리스크를 고려한 UX 문구 설계**
   엔지니어링 시스템이 '100% 안전'을 보장할 수 없다면, 소프트웨어가 제공하는 데이터의 한계를 정확히 반영하는 중립적 언어(`이상없음`)를 선택하는 것이 서비스의 안전성을 높이는 길입니다.

3. **정보의 시각적 계층화(Information Hierarchy)를 통한 인지 부하 감소**
   동일한 데이터를 보여주더라도 백엔드에서 의미 단위로 이벨류에이션(Evaluation)하여 전달하고 프론트엔드에서 우선순위별로 분리 렌더링함으로써, 사용자의 미션 달성 시간(Time-to-Value)을 획기적으로 단축할 수 있었습니다.
