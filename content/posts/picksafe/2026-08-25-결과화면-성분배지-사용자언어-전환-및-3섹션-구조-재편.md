소비자가 제품의 라벨을 스캔했을 때 원하는 것은 무엇일까요? '내부 데이터베이스에 레코드가 존재하는가'가 아니라, **'이 제품을 내가 안전하게 섭취하거나 사용해도 되는가'**라는 명확한 판정입니다.

초기 기능 개발 단계에서는 시스템의 동작 메커니즘이 UI에 그대로 노출되기 쉽습니다. PickSafe 역시 성분 분석 엔진 고도화에 집중한 나머지, 백엔드 매칭 결과를 개발자 관점의 언어로 화면에 직렬화하여 보여주고 있었습니다.

이번 글에서는 **개발자 중심의 데이터 표현 방식을 사용자 중심의 직관적 정보 구조로 전환**하고, **도메인 특수성(법적/의학적 리스크)을 고려한 상태 모델링**을 적용한 엔지니어링 과정을 공유합니다.

---

## 1. Problem: 엔지니어링 멘탈 모델과 사용자 멘탈 모델의 충돌

초기 결과 화면은 성분 목록을 분석한 뒤 각 항목 우측에 매칭 상태를 표시했습니다. 하지만 사용자 관점에서 세 가지 치명적인 문제가 드러났습니다.

```
[기존 단일 리스트 구조]
- 성분 A [일치함]   --> (사용자: "내 알레르기와 일치한다는 뜻인가? 안전하다는 뜻인가?")
- 성분 B [⚠️ 알레르기] --> (사용자: "공인 규격 기준인가, 내가 등록한 기피 성분인가?")
- 성분 C [? 미확인 성분] --> (사용자: "위험 성분인가, 단순 미등록인가?")
```

1. **모호한 맥락 (Ambiguity):** `일치함`이라는 배지는 '성분 사전 DB의 식별자(Identifier)와 일치했다'는 시스템 상태일 뿐, 사용자에게는 '위험 성분과 일치'한 것인지 '정상 데이터'인지 판별할 수 없는 노이즈였습니다.
2. **신뢰의 근거 부재:** 동일한 경고 배지(`⚠️`)라도 이것이 공인 규제 기관(EU/식약처 등) 기준인지, 온보딩 시 사용자가 설정한 개인 기피 데이터셋인지 분리되지 않았습니다.
3. **높은 인지 부하 (High Cognitive Load):** 성분이 단일 플랫 리스트(Flat List)로 나열되어 있어, 사용자는 자신에게 유해한 성분이 있는지 확인하기 위해 수십 개의 목록을 끝까지 스크롤해야만 했습니다.

## 2. Technical Decision & Trade-offs: 단어 하나에도 엔지니어링 철학이 필요하다

단순히 텍스트를 수정하는 것을 넘어, **데이터 분류 모델**과 **표현 계층의 제약 조건**을 재정의했습니다.

### ① '안전함' vs '이상없음' (Legal & Domain Trade-off)
가장 직관적인 표현인 `안전함`, `좋음` 등의 단어는 의도적으로 배제했습니다. 
* **기각 사유:** 성분 분석 엔진은 의료적 진단을 대체할 수 없으며, 사용자가 미처 등록하지 못한 개인 특이체질 성분까지 '안전하다'고 보증할 수 없습니다.
* **채택안 (`이상없음`):** 공인 알레르기 유발 리스트 및 사용자 등록 기피 성분과 대조했을 때 "우려되는 인자가 검출되지 않았다"는 **중립적·사실 중심적 상태**를 명확히 전달하도록 확정했습니다.

### ② 상태 데이터 모델의 세분화 (`badge_type`)
백엔드 분석 엔진의 출력 스키마를 정규화하여 프론트엔드가 명확한 상태 기반 렌더링을 수행할 수 있도록 설계했습니다.

```python
# 성분 판정 결과 분류 모델 (Conceptual)
class IngredientBadgeType(str, Enum):
    OK = "ok"              # 대조군 내 위험 인자 미검출 (이상없음)
    ALLERGEN = "allergen"  # 공인 규제 기관 기준 알레르기 유발 물질
    PERSONAL = "personal"  # 사용자 정의 기피 성분 일치
    UNKNOWN = "unknown"    # 데이터베이스 미등재 성분 (확인 불가)
```

이를 통해 단일 경고 상태를 **공인 규격(`ALLERGEN`)**과 **개인 맞춤형 규격(`PERSONAL`)**으로 분리하여 신뢰도를 높였습니다.

## 3. Architecture: 시선 흐름을 고려한 3섹션 아코디언 파이프라인

정보의 우선순위에 따라 UI 아키텍처를 **상단 즉시 판정 배너 + 3단계 계층 구조**로 재편했습니다.

```
┌──────────────────────────────────────────────────────────┐
│ [상단 즉시 판정 배너]                                      │
│  ⚠️ N개의 성분이 알레르기/기피 기준과 일치합니다            │
└──────────────────────────────────────────────────────────┘
                           │
 ┌─────────────────────────▼──────────────────────────────┐
 │ [섹션 1] ⚠️ 주의 성분 (공인 알레르기 / 기피 성분)        │ --> [Default: Open]
 ├────────────────────────────────────────────────────────┤
 │ [섹션 2] ✅ 이상없는 성분                                │ --> [Default: Closed]
 ├────────────────────────────────────────────────────────┤
 │ [섹션 3] ❓ 확인 불가 성분                               │ --> [Default: Closed]
 └────────────────────────────────────────────────────────┘
```

* **Zero-Scroll 판정 (상단 배너):** 화면 진입 0.1초 만에 전체 위험 여부를 요약 제공하여 즉각적인 의사결정을 지원합니다.
* **Fail-Fast 노출 전략:** 위험도가 가장 높은 `주의 성분` 섹션만 기본 활성화(Expanded) 상태로 두고, 정상 성분 및 미확인 성분은 기본 축소(Collapsed) 처리하여 스크롤 비용을 80% 이상 절감했습니다.
* **동적 뷰 전환:** 우려 성분이 0건일 경우, 안내 메시지와 함께 `이상없는 성분` 섹션이 자동으로 펼쳐지는 반응형 로직을 구축했습니다.

## 4. Rollout Strategy & Engineering Takeaway

UI/UX 변경에 따른 사이드 이펙트를 최소화하기 위해 4단계의 점진적 롤아웃(Phased Rollout) 전략을 취했습니다.

1. **1단계 (Data Mapping):** 백엔드 응답의 `badge_type` 매핑 및 코어 배지 텍스트 1차 교체
2. **2단계 (Global Status):** 상단 요약 배너 및 3상태 컬러 코딩 파이프라인 구축
3. **3단계 (Structure):** 렌더링 엔진의 3섹션 아코디언 구조 분리 및 인터랙션 최적화
4. **4단계 (i18n):** 다국어 로컬라이제이션(Localization) 테이블 동기화

### 💡 Key Takeaway

1. **UI는 데이터베이스 상태의 거울이 아닙니다.**
   엔지니어가 편한 용어(`일치함`, `대조 성공`)를 그대로 노출하는 것은 사용자에게 시스템 내부 구현을 해석하라고 강요하는 것과 같습니다. 데이터는 프레젠테이션 계층에 도달하기 전, 철저히 **사용자 관점의 가치**로 재해석되어야 합니다.
2. **엔지니어링에는 도메인 리스크에 대한 방어적 설계가 포함됩니다.**
   단순한 UX 문구 변경이라도 법적 책임, 의학적 오인 가능성을 고려한 어휘 선택(`안전` 대신 `이상없음`)과 상태 모델링이 결합되어야 견고한 프로덕트가 완성됩니다.
