소프트웨어를 설계할 때 개발자는 자연스럽게 데이터베이스(DB)의 관점에서 생각하게 됩니다. "데이터가 매칭되었는가?" 혹은 "쿼리 결과가 Null인가?"와 같은 질문들이 그것이죠. 하지만 이러한 **'개발자 편의적 언어'가 추상화 계층을 뚫고 최종 사용자 화면(UI)까지 흘러들어 간다면 어떻게 될까요?**

최근 PickSafe 팀은 서비스의 핵심 기능인 '성분 분석 결과 화면'에서 이와 같은 전형적인 **추상화 누수(Leaky Abstraction)** 문제를 발견했습니다. 단순한 단어 선택의 문제를 넘어, 데이터 모델의 설계와 아키텍처적 관점에서 이 문제를 어떻게 정의하고 해결했는지 그 과정을 공유합니다.

---

## 1. 문제 정의: 개발자의 언어가 만든 불완전한 UX

기존 PickSafe의 성분 분석 결과 화면은 분석된 성분 데이터와 사용자의 프로필 데이터를 대조한 뒤, 매칭 결과를 배지(Badge) 형태로 나열해 보여주었습니다. 하지만 이 과정에서 심각한 UX 인지 불일치 문제가 발생했습니다.

| 기존 배지 | 데이터베이스(DB) 관점의 의미 | 사용자가 느끼는 문제점 |
| :--- | :--- | :--- |
| **`일치함`** | 사용자 기피 성분 DB와 제품 성분명이 `Match` 됨 | "무엇과 일치했다는 거지? 안전하다는 뜻인가, 위험하다는 뜻인가?" |
| **`⚠️ 알레르기`** | 공인 알레르기 유발 물질 목록에 포함됨 | 경고의 근거가 모호함 (국가 공인 기준인지, 내 개인 설정 기준인지 구분 불가) |
| **`? 미확인 성분`** | 성분 사전 DB에 존재하지 않아 `Null` 반환 | "미확인되었으니 먹으면 위험하다는 뜻인가? 아니면 단순히 데이터가 없다는 뜻인가?" |

### 구조적 문제: 정보 과부하 (Information Overload)
더 큰 문제는 **화면 구조**에 있었습니다. 모든 성분이 단일 플랫 리스트(Flat List)로 무작위 나열되어 있다 보니, 사용자는 자신에게 치명적일 수 있는 '알레르기 유발 성분'을 찾기 위해 수십 개의 성분 목록을 끝없이 스크롤해야만 했습니다. 

개발하기에는 가장 단순한 구조였지만, 사용자에게는 가장 가독성이 떨어지는 구조였습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 백엔드 데이터 모델부터 프론트엔드 렌더링 영역까지 전체 레이어를 재검토했습니다. 이 과정에서 마주한 핵심 의사결정 포인트를 소개합니다.

### 고민 1: "안전함"이라는 매력적인 단어를 포기한 이유 (법적 리스크와 방어적 설계)
기존의 `일치함` 배지를 가장 직관적인 단어인 `안전함` 혹은 `좋음`으로 바꾸자는 의견이 있었습니다. 하지만 엔지니어링팀은 기획팀과 함께 이 대안을 과감히 기각했습니다.

*   **이유**: PickSafe는 의료 진단 서비스가 아닙니다. 사용자가 자신의 알레르기 정보를 누락했거나, 서비스 DB에 아직 업데이트되지 않은 신종 성분이 있을 경우, `안전함`이라는 단정적 표현은 사용자에게 잘못된 안도감을 주어 심각한 건강/법적 리스크를 초래할 수 있습니다.
*   **해결책**: 우려 성분이 검출되지 않았음을 뜻하는 중립적이고 방어적인 표현인 **`✅ 이상없음`**을 채택했습니다. 기술이 제공할 수 있는 보장 범위(SLA)를 명확히 정의하는 디자인 패턴을 적용한 것입니다.

### 고민 2: 클라이언트 사이드 필터링 vs 백엔드 기반 뱃지 데이터 모델링
분석 결과를 3개의 섹션(주의 성분 / 이상없는 성분 / 확인 불가 성분)으로 분리하여 보여주기 위해, 데이터를 어디서 어떻게 가공할 것인가에 대한 아키텍처적 고민이 있었습니다.

*   **대안 A: 프론트엔드(Client)에서 로직 처리**
    *   백엔드는 기존처럼 플랫한 성분 리스트만 내려주고, 프론트엔드가 자바스크립트로 필터링 및 그룹핑을 수행합니다.
    *   *장점*: 백엔드 API 스키마를 변경할 필요가 없습니다.
    *   *단점*: 웹, iOS, Android 등 멀티 플랫폼 환경에서 동일한 그룹핑 로직을 중복 구현해야 하며, 로직의 정합성이 깨질 위험이 큽니다.
*   **대안 B: 백엔드(Server) 중심의 데이터 모델링 (채택)**
    *   백엔드 API 응답 데이터에 각 성분의 상태를 명확히 규정하는 `badge_type` 필드(`"ok"`, `"allergen"`, `"personal"`, `"unknown"`)를 추가합니다.
    *   *장점*: 비즈니스 로직이 백엔드에 캡슐화되어 프론트엔드는 단순 렌더링에만 집중할 수 있습니다. 다국어 지원(Translations) 및 유지보수가 압도적으로 유리합니다.

## 3. 최종 해결책: 사용자 중심의 3섹션 아키텍처 도입

우리는 백엔드 API 설계를 개편하고, 프론트엔드 렌더링 구조를 **중요도 기반의 3섹션 구조**로 재편성했습니다.

### 데이터 모델링의 변화 (API Response 예시)
보안을 위해 실제 비즈니스 로직을 마스킹한 간소화된 구조는 다음과 같습니다.

```json
{
  "summary_banner": {
    "status": "warning",
    "message": "2개의 성분이 주의 성분으로 감지되었습니다."
  },
  "ingredients": [
    {
      "name": "정제수",
      "badge_type": "ok",
      "badge_text_key": "BADGE_OK"
    },
    {
      "name": "밀가루",
      "badge_type": "allergen",
      "badge_text_key": "BADGE_ALLERGEN"
    },
    {
      "name": "특정감미료",
      "badge_type": "personal",
      "badge_text_key": "BADGE_PERSONAL"
    }
  ]
}
```

### UI 레이아웃의 구조적 변화
이제 화면은 사용자가 즉시 행동을 취할 수 있도록 정보의 우선순위에 따라 3가지 섹션으로 나뉘어 렌더링됩니다.

```
[상단 즉시 판정 배너] (우려 성분 유무에 따라 3가지 상태로 분기)
  └ 예: "⚠️ N개의 성분이 알레르기 유발 기준과 일치합니다"

──────────────────────────────────────────────────────
[섹션 1] ⚠️ 주의 성분 (알레르기 또는 개인 기피성분 해당)  ← [항상 펼쳐짐]
──────────────────────────────────────────────────────
[섹션 2] ✅ 이상없는 성분                             ← [기본 닫힘 / 아코디언]
──────────────────────────────────────────────────────
[섹션 3] ❓ 확인 불가 성분                            ← [기본 닫힘 / 아코디언]
```

만약 주의 성분이 전혀 검출되지 않았다면, 섹션 1은 비워두는 대신 "우려 성분이 없습니다"라는 안심 메시지를 보여주고, 섹션 2(이상없는 성분)를 자동으로 펼쳐주어 불필요한 터치 횟수(TAP)를 줄였습니다.

## 4. 점진적 배포 전략 (Rollout Plan)

아무리 좋은 개편안이라도 한 번에 모든 것을 바꾸는 빅뱅(Big Bang) 식 배포는 장애 위험을 높입니다. 우리는 리스크를 최소화하기 위해 4단계의 마일스톤을 수립하여 순차적으로 배포를 진행하고 있습니다.

1.  **1단계 (즉시)**: 레거시 백엔드 데이터 포맷을 유지한 채 UI 배지 텍스트만 1차 교체 (`일치함` → `이상없음`, `미확인 성분` → `미확인`)
2.  **2단계**: 백엔드 API에 `badge_type` 필드를 추가하고, 상단 즉시 판정 배너 신설
3.  **3단계**: 프론트엔드 UI를 3섹션 아코디언(Accordion) 구조로 전면 개편
4.  **4단계 (안정화)**: 다국어 번역 테이블(KO/EN/JA/ZH)에 새로운 키값을 바인딩하여 글로벌 유저 대응 완료

## 5. 이번 리팩토링으로 얻은 엔지니어링 교훈 (Takeaways)

1.  **UI는 DB의 거울이 아니다**: 개발자가 설계한 테이블 스키마와 데이터 상태를 그대로 화면에 노출시키는 것은 최악의 UX를 만듭니다. 시스템의 언어를 사용자의 언어로 번역하는 레이어가 반드시 필요합니다.
2.  **비즈니스 제약 조건을 코드에 투영하라**: `안전함` 대신 `이상없음`을 선택한 의사결정처럼, 기술은 비즈니스의 법적/운영적 제약 조건(Medical Disclaimer)을 방어적으로 보호할 수 있도록 설계되어야 합니다.
3.  **백엔드 중심 UI(Backend-Driven UI)의 가치**: 데이터의 분류 체계와 핵심 로직을 백엔드 API 스펙으로 명확히 규정해 둠으로써, 클라이언트 사이드의 복잡도를 획기적으로 낮추고 멀티 플랫폼 대응 속도를 극대화할 수 있었습니다.
