제품이 성장하고 성분 분석 엔진의 데이터베이스(DB)가 고도화될수록, 개발팀 내부에서는 '당연하게' 통용되던 데이터 구조가 사용자 관점에서는 커다란 인지적 허들(Friction)로 작용하는 순간이 찾아옵니다.

식품/화장품 성분 안전성 분석 서비스 **PickSafe** 역시 최근 이러한 문제에 직면했습니다. 백엔드 매ched 상태값인 `일치함(Matched)`이라는 개발자 관점의 용어가 UI에 그대로 노출되고 있었고, 플랫(Flat)한 성분 목록 구조 때문에 사용자는 자신에게 치명적인 알레르기 성분을 찾기 위해 긴 스크롤을 감수해야 했습니다.

이번 포스팅에서는 **1) 개발자 중심 어휘를 사용자 도메인 어휘로 정제하는 과정**, **2) 법적/의료적 리스크를 피하면서도 명확한 전달력을 확보한 고민**, 그리고 **3) 이를 지원하기 위해 백엔드 모델과 UI 구조를 어떻게 도메인 중심(Domain-driven)으로 재설계했는지**를 공유합니다.

---

## 1. 문제 정의: "일치함"이 주는 불확실성과 인지 부하

기존 결과 화면은 DB 조회 결과를 프론트엔드에 직렬화하여 그대로 보여주는 구조였습니다. 이로 인해 세 가지 큰 문제점이 존재했습니다.

### ① 개발자 관점 언어의 UI 노출 (Data Leakage in UX)
* **기존 배지 `일치함`**: 백엔드 알고리즘이 "DB 내 기준 테이블과 인덱스가 매칭됨"을 의미하던 내부 용어입니다. 그러나 사용자에게는 *"무엇과 일치했는지"*, *"안전하다는 것인지 위험하다는 것인지"* 명확한 맥락을 제공하지 못했습니다.
* **기존 배지 `? 미확인 성분`**: 단순히 성분 데이터베이스에 등재되지 않았음을 의미하지만, 사용자 관점에서는 "먹으면 위험한 성분인가?"라는 오해를 불어일으켰습니다.

### ② 정보 계층 구조(Information Hierarchy)의 부재
단일 리스트 형태로 평균 30~50개에 달하는 전체 성분을 단순 나열했습니다. 이로 인해 사용자는 **가장 우려되는 알레르기 유발 성분의 존재 여부**를 파악하기 위해 화면 전체를 스크롤하며 일일이 배지를 확인해야 했습니다.

### ③ 공인 기준과 사용자 개인 설정의 혼재
국가 공인 기관(EU 82종, 한국 식약처 25종)이 지정한 알레르기 성분과 사용자가 개인 온보딩 과정에서 직접 등록한 기피 성분이 구별되지 않고 똑같은 `⚠️ 알레르기` 배지로 표기되었습니다. 경고의 근거가 모호해지면서 경고 피로감(Alert Fatigue)이 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

UX 개선 및 데이터 라벨링 단계를 진행하며, 제품 및 엔지니어링 팀은 어휘 선정과 데이터 분류 모델 구축 시 다양한 대안을 검토했습니다.

### [고민 1] "이상없음" vs "안전함" — 법적 리스크와 중립성 간의 Trade-off

| 대안 | 장점 | 단점/기각 이유 |
| :--- | :--- | :--- |
| **`안전함`** | 사용자가 즉시 직관적인 안도감을 느낌. | **[기각]** 사용자가 온보딩 시 미처 등록하지 못한 개인 기피 성분이 있을 수 있으며, 앱이 의료적/진단적 안전성을 100% 보증하는 것으로 오인될 시 **법적 리스크** 발생. |
| **`좋음`** | 긍정적인 UX 제공. | **[기각]** 성분의 독성 여부를 다루는 서비스 맥락상 '좋음'은 의미가 애매함. |
| **`✅ 이상없음` (선택)** | 법적 보증 표현을 피하면서도 우려 성분이 검출되지 않았음을 정확히 전달. | 표현이 조금 건조할 수 있으나, 중립성과 정확성을 확보. |

> **의사결정 원칙:** PickSafe 서비스는 의료 진단을 대체할 수 없습니다. 따라서 '안전'이라는 단정적 단어 대신 **"우려 성분이 검출되지 않음"**을 명확히 하는 중립적 표현 `이상없음`을 최종 선택했습니다.

### [고민 2] 경고 기준 분리: 공인 데이터 vs 개인화 데이터

경고 배지를 단순히 "위험" 하나로 통일하지 않고, 공인 알레르기 목록과 개인 기피 성분을 분리하기로 했습니다.

* **`⚠️ 알레르기`**: EU/식약처 등 보건 당국 지정 공인 알레르기 성분 매칭 시
* **`⚠️ 기피성분`**: 사용자가 온보딩 프로필에 직접 등록한 성분 매칭 시

이러한 분리는 사용자가 "내가 등록해서 뜬 경고인가?" 혹은 "식약처 기준 위험 성분인가?"를 구분하게 해주어 **서비스에 대한 데이터 신뢰도**를 크게 높여줍니다.

## 3. 백엔드 및 프론트엔드 아키텍처 재설계

이러한 UX 변경을 시스템에 적용하기 위해 백엔드 API 계약(Contract) 및 프론트엔드 렌더링 계층을 개편했습니다.

### 3.1 백엔드 데이터 모델: `BadgeType` Enum 도입 (Python / FastAPI)

기존에는 문자열 라벨을 비즈니스 로직 중간에서 조합하여 리턴했다면, 개편 후에는 성분 분류 엔진이 명확한 `BadgeType` Enum 값을 산출하도록 분리했습니다.

```python
# [백엔드 모델 추상화 예시]
from enum import Enum
from pydantic import BaseModel

class BadgeType(str, Enum):
    OK = "ok"             # 이상없음 (공인/개인 기피 기준 모두 통과)
    ALLERGEN = "allergen" # 공인 알레르기 유발 성분 해당
    PERSONAL = "personal" # 사용자 개인 기피 성분 해당
    UNKNOWN = "unknown"   # DB 미등재 성분 (대조 불가)

class IngredientResult(BaseModel):
    raw_name: str
    display_name: str
    badge_type: BadgeType  # UI 상태를 완전히 제어하는 이넘 데이터
    # ... 기타 내부 메타데이터
```

이 구조 변경을 통해 UI 레이어는 백엔드의 내부 매칭 알고리즘을 알 필요 없이 `badge_type` 하나만으로 시각적 렌더링과 아코디언 배치 로직을 독립적으로 처리할 수 있게(Decoupling) 되었습니다.

### 3.2 3섹션 아코디언(Accordion) 및 상단 배너 구조화

단일 리스트였던 UI 구조를 정보의 중요도에 따라 3개의 독립된 섹션 및 상단 집계 배너로 재편했습니다.

```text
[상단 즉시 판정 배너]
  ├─ 🔴 N개의 성분이 공인 알레르기 목록에 해당합니다
  ├─ ⚠️ N개의 성분이 개인 기피 성분과 일치합니다
  └─ ✅ 우려 성분이 검출되지 않았습니다

[섹션 1] ⚠️ 주의 성분 (알레르기 or 기피성분)  --> [기본값: 펼침]
[섹션 2] ✅ 이상없는 성분                      --> [기본값: 닫힘]
[섹션 3] ❓ 확인 불가 성분                     --> [기본값: 닫힘]
```

* **우선순위 기반 렌더링**: 사용자가 결과 화면에 진입하자마자 스크롤 없이 **"주의할 성분이 있는가?"**를 0.1초 만에 인지할 수 있도록 하였습니다.
* **상태 기반 자동 개폐**: 주의 성분이 0개일 경우, [섹션 1]은 "주의 성분 없음" 메시지를 보여주고 [섹션 2]가 자동으로 펼쳐져 사용자 경험을 매끄럽게 보장합니다.

## 4. 단계적 배포 전략 및 다국어(i18n) 확장성

영향 범위를 최소화하고 안정적인 프로덕션 반영을 위해 4단계 롤아웃 계획을 수립하여 진행했습니다.

1. **1단계 (Data Mapping)**: 백엔드 `BadgeType` 신설 및 배지 텍스트 표준화 (`일치함` → `이상없음`, `미확인 성분` → `미확인`)
2. **2단계 (Summary Banner)**: 상단 즉시 판정 배너 계산 로직 및 컴포넌트 신설
3. **3단계 (UI Restructuring)**: 결과 리스트의 3섹션 아코디언 구조 재편
4. **4단계 (i18n)**: 한국어(KO), 영어(EN), 일본어(JA), 중국어(ZH) 번역 키 맵핑 완료

## 5. 엔지니어링 교훈 (Takeaways)

이번 결과 화면 재설계 작업을 진행하며 얻은 엔지니어링 관점의 핵심 레슨은 다음과 같습니다.

1. **DB의 언어와 사용자의 언어를 철저히 분리할 것**  
   개발 데이터베이스 테이블의 상태값(`matched`, `unidentified`)이 UI 라벨에 직접 노출되는 순간 사용자 경험은 해쳐집니다. 백엔드 도메인 모델은 사용자의 사용 맥락(Context)을 반영하는 표현 형식으로 추상화되어 제공되어야 합니다.

2. **도메인 특성에 따른 컴플라이언스/법적 리스크 고려**  
   IT 엔지니어링은 기술 구현뿐만 아니라 제품이 속한 도메인 규제(헬스케어/성분 분석 서비스의 진단 대체 금지 원칙)를 기술 사양에 녹여내야 합니다. '안전함' 대신 중립적인 '이상없음'을 정의한 것은 기술과 비즈니스 및 법적 리스크 완화가 결합된 좋은 사례였습니다.

3. **명확한 Enum 설계가 Frontend와 Backend 간의 커플링을 줄인다**  
   백엔드에서 단순히 텍스트 리터럴을 내려주는 대신 명확한 `BadgeType` 규격을 제공함으로써 프론트엔드의 다국어 처리(i18n), 상단 배너 상태 계산, 아코디언 분류 로직이 획기적으로 간결해졌습니다.

PickSafe 팀은 앞으로도 정교한 성분 분석 데이터 파이프라인을 구축함과 동시에, 이를 사용자 친화적이고 안전한 언어로 전달할 수 있도록 엔지니어링과 UX 구조를 지속해서 개선해 나갈 것입니다.
