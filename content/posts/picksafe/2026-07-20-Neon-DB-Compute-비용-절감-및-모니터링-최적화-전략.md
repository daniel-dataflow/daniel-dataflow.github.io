안녕하세요, **PickSafe** 백엔드 개발팀입니다. 

MSA나 서버리스 인프라를 도입할 때 개발자들이 가장 마주하기 쉬운 함정 중 하나는 바로 **'비용 통제'**입니다. 저희 서비스는 서버리스 PostgreSQL인 **Neon DB**를 메인 데이터베이스로 사용하고 있습니다. Neon은 데이터베이스가 연결되거나 쿼리가 실행되는 시간(Compute Active Time, CU-Hours)을 기준으로 과금되는 합리적인 구조를 가졌지만, 거꾸로 말하면 **"불필요한 쿼리나 백그라운드 작업이 DB를 깨워두면 요금 폭탄으로 이어진다"**는 뜻이기도 합니다.

이번 글에서는 대규모 성분 수집(Seeding) 배치와 실시간 어드민 모니터링 환경에서 마주한 비용 과다 청구 문제를 해결하기 위해, **Multi-DB 아키텍처 도입과 폴링 최적화를 적용한 아키텍처 의사결정(ADR) 과정**을 공유하고자 합니다.

---

## 1. 🚨 Problem: 서버리스 DB를 위협하는 3가지 요인

서비스가 성장하면서 다음과 같은 구조적 한계와 비용 리스크를 마주했습니다.

1. **배치 부하로 인한 서비스 지연**: 2만 건에 달하는 식약처 API 성분 수집 및 매쉬업 배치가 돌 때 대량의 CPU와 IOPS를 소모하여, 동시 접속 중인 일반 사용자의 웹 응답 속도에 악영향을 미침.
2. **지속적인 깨어남(Keep-Alive) 문제**: 어드민 대시보드의 실시간 모니터링과 로그 자동 조회 기능이 DB 커넥션을 주기적으로 갱신하여, DB가 Auto-suspend(자동 일시정지) 상태로 진입하지 못함.
3. **인프라 제약**: 저비용/무료 호스팅 환경(예: Render)의 특성상 별도의 외부 Redis 인메모리 캐시 서버를 두기 까다로워 DB로 직접 향하는 트래픽이 많음.

---

## 2. 🛠️ Trade-off & Architecture: 어떻게 해결할 것인가?

문제를 해결하기 위해 인프라와 애플리케이션 레벨에서 세 가지 핵심 전략을 세웠습니다.

### ① 데이터베이스 물리적 분리 (Multi-DB Architecture)
일반 사용자의 안정적인 서비스 경험을 최우선으로 두고, 무거운 연산과 모니터링 쿼리를 격리하기 위해 데이터베이스를 **A(실운영)**와 **B(배치/수집/로그/모니터링)**로 쪼갰습니다.

*   **실운영 DB A (Master DB)**: 사용자용 성분 조회, 인기 제품 검색 등을 담당. 무거운 연산을 배제하여 Neon 최저 리소스(0.25 CU)만으로도 쾌적한 응답 속도 보장.
*   **수집/배치/로그 DB B (Staging & Log DB)**: 대규모 수집 임시 데이터, 어드민 통계, 서버 메트릭스 저장. **Auto-suspend(5분)를 타이트하게 적용하여 배치 미구동 시 물리적 요금이 0원이 되도록 격리.**

```mermaid
flowchart TD
    UserApp[일반 사용자 App] -->|성분/제품 조회| DB_A[(실운영 DB A: Master)]
    AdminDash[어드민 대시보드] -->|수집 명령 / 모니터링 및 로그 쿼리| DB_B[(수집/배치 DB B: Staging)]
    
    subgraph Neon Project A (실운영 전용)
        DB_A
    end
    
    subgraph Neon Project B (수집/로그/모니터링 전용)
        DB_B
    end
    
    DB_B -->|🚀 최종 병합 Merge| DB_A
```

### ② 수집기 커넥션 완전 격리 (Double-Buffering)
초기에는 수집 배치가 돌 때마다 DB A(Master)의 마스터 테이블을 직접 조회하며 중복을 체크했습니다. 이는 "비용 절감"이라는 아키텍처 취지에 반하는 행동이었습니다.
*   **개선**: 수집 프로세스 중에는 DB A로의 모든 커넥션을 원천 차단했습니다. 오직 DB B(DW)의 Staging 테이블에서 상태를 체크하고, 최종적으로 어드민에서 **[병합(Merge)]** 액션을 단행하는 시점에만 DB B에서 DB A로 벌크 트랜잭션을 실행합니다.

### ③ 모니터링 폴링 최적화 및 1시간 자동 타임아웃
관리자가 대시보드를 켜둔 채 자리를 비우거나 퇴근하여 DB가 밤새 깨어있는 상황을 원천 방지하기 위해 가드레일을 설치했습니다.
*   **Off-by-Default**: 인프라/로그 실시간 갱신 스위치의 기본값을 `False(꺼짐)`로 설정.
*   **1시간 자동 타임아웃**: 사용자가 스위치를 켜더라도 1시간이 지나면 클라이언트에서 강제로 스위치를 끄도록 설계.
*   **Page Visibility API 연동**: 어드민 탭이 브라우저 백그라운드로 내려가면 즉시 폴링을 중단.

### ④ 인메모리 로컬 캐싱 (`cachetools`) 도입
외부 Redis를 두기 어려운 환경에서, Python 내장 LRU(Least Recently Used) 캐시를 API 서버 메모리에 적용했습니다. 자주 조회되는 성분 매칭 사전 정보를 메모리에 캐싱하여, DB A로 도달하는 단순 조회 트래픽을 약 70% 감쇄시켰습니다.

## 3. 💡 Takeaway: 엔지니어링 교훈

이번 최적화 작업을 통해 얻은 교훈은 명확합니다.

1. **비용은 아키텍처 설계 단계부터 고려해야 한다**: 서버리스 환경에서는 "동작한다"에서 끝나는 것이 아니라, "리소스가 언제 내려가는가(Auto-suspend)"까지 설계해야 프로덕션 비용 폭탄을 막을 수 있습니다.
2. **읽기와 쓰기, 그리고 백그라운드 작업의 분리**: 핵심 비즈니스(Master)와 부가 작업(Staging/Log)의 데이터베이스를 분리하는 것만으로도 시스템 안정성과 비용 효율성을 동시에 잡을 수 있음을 증명했습니다.
3. **사용자의 휴먼 에러를 방어하는 안전장치**: 모니터링 폴링의 자동 타임아웃이나 Page Visibility API 활용처럼, 개발자의 코드가 아닌 사용자의 실수(방치)로부터 인프라를 보호하는 장치의 중요성을 깨달았습니다.

서버리스 DB 도입을 고민하고 계시거나, 예산 제약 속에서 아키텍처를 고민하는 엔지니어분들에게 작은 도움이 되었기를 바랍니다. 감사합니다!
