서버리스(Serverless) 인프라는 초기 구축 비용이 저렴하고 확장성이 뛰어나다는 강력한 장점이 있습니다. 하지만 트래픽 패턴을 고려하지 않은 채 아키텍처를 설계하면, 어느 날 갑자기 날아온 '요금 폭탄'이라는 뼈아픈 현실을 마주하게 됩니다.

이번 프로젝트인 **PickSafe**를 운영하며, 서버리스 PostgreSQL인 **Neon DB**의 핵심 과금 요소인 **Compute Active Time(CU-Hours)** 비용을 극적으로 절감하기 위해 진행했던 아키텍처 개편과 모니터링 최적화 과정을 공유합니다.

---

## 1. 마주한 문제 (Problem)

프로젝트를 고도화하는 과정에서 Neon DB와 Serverless 환경의 특성으로 인해 다음과 같은 구조적 한계와 비용 리스크를 마주했습니다.

1. **과금 구조의 함정 (CU-Hours)**: 
   Neon은 데이터베이스가 연결되어 있거나 쿼리가 실행되는 시간(Compute Active Time)을 기준으로 과금합니다. 개발 환경이나 어드민의 상시 모니터링 쿼리로 인해 DB가 잠들지 못하면(Auto-suspend 지연) 불필요한 비용이 발생합니다.
2. **배치 부하가 실서비스에 미치는 영향**: 
   수만 건의 오픈 API 성분 데이터를 수집(Seeding)하고 매쉬업하는 무거운 배치 프로세스가 실서비스 DB에 직접 쿼리를 날리면서, 일반 사용자의 웹 서비스 응답 속도까지 저하시키는 간섭 현상이 발생했습니다.
3. **인프라 제약 (Resource Constraint)**: 
   비용 절감을 위해 저비용 호스팅 환경(Render 등)을 사용 중이었으나, 제한된 RAM 용량 때문에 외부 Redis 같은 인메모리 캐시 서버를 별도로 구축하기가 까다로운 상황이었습니다.

---

## 2. 기술적 고민과 아키텍처 대안 (Trade-offs)

비용과 성능 두 마리 토끼를 잡기 위해 세 가지 핵심 아키텍처 전략을 수립하고 트레이드오프를 검토했습니다.

### ① 데이터베이스 물리적 분리 (Multi-DB Architecture)
* **대안 A (단일 DB 유지)**: 관리 포인트가 적지만, 배치 작업과 사용자 조회 쿼리가 섞여 DB가 쉴 틈 없이 깨어있고 리소스 경쟁이 발생함.
* **대안 B (Multi-DB 격리)**: 실운영 DB(Master)와 수집/배치/로그용 DB(Staging/DW)를 완전히 분리. 
* **선택**: **대안 B**. 일반 사용자의 응답 속도 보장을 최우선으로 두고, 무거운 연산과 모니터링 쿼리를 DB B로 몰아넣은 뒤 타이트한 `Auto-suspend`(5분)를 적용해 평상시 배치 미구동 시 DB B의 물리적 요금이 '0원'이 되도록 설계했습니다.

### ② 어드민 모니터링 폴링 최적화 (Off-by-Default & Page Visibility)
* **문제**: 관리자가 대시보드를 켜두고 자리를 비우거나 백그라운드 탭에 방치할 경우, 실시간 메트릭/로그 조회가 백그라운드에서 계속 돌며 DB를 강제로 깨워두는 현상 발생.
* **해결**: 
  * 인프라/로그 실시간 갱신 스위치를 **기본 꺼짐(`Off-by-Default`)**으로 설정.
  * 1시간 경과 시 자동으로 스위치를 내리는 **타임아웃 안전장치** 도입.
  * 브라우저 `Page Visibility API`를 연동하여 탭이 비활성화되면 폴링을 즉시 중단하도록 처리.

### ③ 외부 Redis 대신 내부 메모리 캐시(Local LRU Cache) 활용
* **문제**: 반복되는 성분 매칭 사전 정보 조회로 인해 DB I/O가 낭비됨.
* **해결**: 외부 인프라 추가에 따른 비용/관리 부담을 피하고자, Python 내장 라이브러리(`cachetools`)를 활용해 API 서버 메모리 내에 **초경량 LRU 캐시**를 구현. 이를 통해 DB로 향하는 단순 조회 쿼리량을 최대 70%까지 감쇄시켰습니다.

## 3. 최종 해결 및 엔지니어링 교훈 (Takeaway)

### 🚀 핵심 개선 사항 요약
1. **Double-Buffering 수집 파이프라인**: 수집기 구동 시 실운영 DB(A)로의 직접 접근을 원천 차단하고, 수집/배치 DB(B)에서 일괄 처리한 뒤 최종 병합(Merge) 시점에만 벌크 트랜잭션을 수행하도록 구조를 변경했습니다.
2. **안전한 로그 로테이션**: 단일 텍스트 파일에 무제한 쌓이던 로그를 `/log/` 디렉토리로 격리하고, `RotatingFileHandler`를 장착해 최대 5MB, 백업 1개로 제한하여 디스크 잠식과 메모리 크래시 위험을 원천 차단했습니다.

### 💡 오늘의 Takeaway
> **"서버리스 환경에서의 비용 최적화는 코드 레벨의 최적화뿐만 아니라, 인프라의 라이프사이클(Auto-suspend 등)을 이해하고 제어하는 데서 시작됩니다."**

이번 아키텍처 개선을 통해 실서비스의 안정성을 확보함과 동시에, 불필요하게 낭비되던 서버리스 컴퓨팅 비용을 극적으로 절감할 수 있었습니다. 제한된 환경 속에서도 아키텍처의 분리와 명확한 트레이드오프 분석을 거친다면 비용과 성능이라는 두 마리 토끼를 모두 잡을 수 있다는 것을 배운 소중한 경험이었습니다.
