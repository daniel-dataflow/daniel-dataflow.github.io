안녕하세요, PickSafe 팀 시니어 백엔드 에디터입니다. 

MSA와 서버리스(Serverless) 인프라가 대중화되면서 개발 생산성은 폭발적으로 증가했지만, 반대로 **비용 통제(Cost Optimization)**는 엔지니어의 중요한 핵심 역량 중 하나가 되었습니다. 특히 사용량 기반으로 과금되는 클라우드 DB를 사용할 때, 작은 설계 실수 하나가 '요금 폭탄'으로 이어질 수 있습니다.

이번 포스팅에서는 최근 **Neon Serverless PostgreSQL**을 도입하면서 겪었던 **Compute Active Time 과금 이슈**를 해결하고, 대규모 배치 작업과 실서비스의 안정성을 동시에 확보한 아키텍처 개선 여정을 공유하려 합니다.

---

## 1. Problem: 서버리스 DB 환경에서 마주한 '비용과 부하'의 딜레마

우리는 식약처 API를 통해 수만 건의 성분 데이터를 수집(Seeding)하고 이를 가공하는 배치 프로세스를 운영하고 있습니다. 초기 인프라를 구성하며 다음과 같은 치명적인 한계와 마주했습니다.

1. **Neon DB의 과금 구조 (CU-Hours)**: Neon은 데이터베이스가 연결되어 있거나 쿼리가 실행되는 시간(Compute Active Time)을 기준으로 CU(Compute Unit)를 과금합니다.
2. **배치 부하가 실서비스로 전파**: 수만 건의 데이터 수집 및 매쉬업 배치가 단일 DB에 집중되면서, 대량의 CPU와 IOPS 소모로 인해 **일반 사용자의 웹 서비스 응답 속도가 저하**되는 현상이 발생했습니다.
3. **좀비 커넥션으로 인한 Auto-suspend 방해**: 어드민 대시보드에서 실시간 모니터링을 위해 DB 커넥션을 주기적으로 갱신하자, DB가 리소스 절감을 위해 진입해야 할 **Auto-suspend(자동 일시정지) 상태를 영구히 차단**하는 문제가 생겼습니다.
4. **인프라 제약**: 클라우드 무료/저비용 호스팅 환경(예: Render)을 사용 중이라, 별도의 외부 Redis 인메모리 캐시 서버를 구축하기에 메모리 제약이 컸습니다.

---

## 2. Trade-off & Architecture: 어떻게 해결할 것인가?

이 문제를 해결하기 위해 **"비용 절감"**과 **"실서비스 안정성"** 두 마리 토끼를 잡는 3대 아키텍처 전략을 수립했습니다.

### ① Multi-DB Architecture (데이터베이스 물리적 격리)
비용을 아끼기 위해 성능을 희생할 수는 없습니다. 데이터베이스를 목적에 따라 두 개로 완전히 분리했습니다.

*   **실운영 DB A (Master DB)**: 일반 사용자용 조회 전용. 무거운 연산이나 모니터링 쿼리를 원천 차단하여 최저 리소스(0.25 CU)만으로도 쾌적한 응답 속도를 보장합니다.
*   **수집/배치/로그 DB B (Staging & Log DB)**: 대규모 성분 수집, 어드민 통계, 서버 로그 저장 전용. 평상시에는 쿼리가 없을 때 **Auto-suspend(5분)를 타이트하게 적용하여 평소 물리적 요금이 '0원'이 되도록 설계**했습니다.

```mermaid
flowchart TD
    UserApp[일반 사용자 App] -->|성분/제품 조회| DB_A[(실운영 DB A: Master)]
    AdminDash[어드민 대시보드] -->|수집 명령 / 모니터링 및 로그 쿼리| DB_B[(수집/배치 DB B: Staging)]
    
    subgraph Neon Project A (실운영 전용)
        DB_A
    end
    
    subgraph Neon Project B (수집/로그/모니터링 전용)
        DB_B
    end
    
    DB_B -->|🚀 최종 병합 Merge| DB_A
```

### ② 수집기 커넥션 완전 격리 (Double-Buffering)
초기 설계에서는 수집기가 실운영 DB A의 테이블을 매번 SELECT하며 중복 여부를 체크했습니다. 이러면 데이터 분리의 의미가 퇴색됩니다. 
이를 개선하여, **수집 중에는 실운영 DB A로의 모든 커넥션을 원천 차단**하고, 오직 DB B(DW)의 Staging 테이블(`is_merged=True` 플래그 및 CAS 번호)만 대조하도록 변경했습니다. 최종적으로 관리자가 어드민에서 **[병합(Merge)]** 버튼을 누르는 시점에만 DB B에서 DB A로 벌크 트랜잭션을 실행합니다.

### ③ 모니터링 'Off-by-Default' 및 로컬 LRU 캐시
*   **어드민 자동 조회 기본 비활성화**: 관리자가 자리를 비우거나 퇴근할 때 자동 갱신으로 인해 DB B가 잠들지 못하는 리스크를 방지하고자, 대시보드 진입 시 모니터링 스위치를 기본적으로 `Off`로 설정하고 **1시간 경과 시 강제 타임아웃** 및 **Page Visibility API 연동(브라우저 탭 이탈 시 폴링 즉시 중단)**을 적용했습니다.
*   **Render 환경 맞춤형 Local LRU Cache**: 외부 Redis 도입 대신 Python 내장 메모리 캐시 라이브러리(`cachetools`)를 활용하여 반복적인 성분 매칭 사전 조회 트래픽을 API 레벨에서 캐싱, **DB A로 향하는 단순 조회 쿼리를 70% 이상 감쇄**시켰습니다.

## 3. Takeaway: 무엇을 배웠는가?

1. **서버리스 과금 구조에 대한 깊은 이해**: 서버리스 DB(Neon 등)를 도입할 때는 단순히 코드를 최적화하는 것을 넘어, **"커넥션이 유지되는 시간"과 "자동 일시정지(Auto-suspend)를 방해하는 요인"을 아키텍처 레벨에서 통제**해야 진정한 비용 절감이 가능함을 깨달았습니다.
2. **트래픽 성격에 따른 데이터베이스 분리의 위력**: 읽기/쓰기 비율이 극단적으로 다른 시스템에서 DB를 Master/Staging으로 분리하는 것은 안정성과 비용 두 측면 모두에서 가장 강력한 무기입니다.
3. **외부 인프라 의존성 최소화**: 저비용 호스팅 환경에서도 언어 수준의 내장 캐시(`cachetools`)와 일자별 로그 로테이션(`RotatingFileHandler`를 활용한 `/log` 폴더 격리 및 5윤 제한)을 적절히 조합하면, 고비용 인프라 없이도 프로덕션 급의 안정성을 충분히 확보할 수 있습니다.

이번 아키텍처 개선을 통해 PickSafe 팀은 **실서비스 응답 속도의 안정성을 유지하면서도 Neon DB Compute 비용을 드라마틱하게 절감**할 수 있었습니다. 제한된 예산과 리소스 속에서 인프라 효율화를 고민하시는 개발자분들께 작은 영감이 되었기를 바랍니다.
