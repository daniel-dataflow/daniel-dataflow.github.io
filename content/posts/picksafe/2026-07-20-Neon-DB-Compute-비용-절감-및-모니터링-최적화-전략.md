사이드 프로젝트나 초기 스타트업 단계에서 서버리스 데이터베이스(Serverless DB)는 초기 구축 비용을 아끼고 인프라 관리 부담을 줄여주는 훌륭한 선택입니다. 저희가 서비스 중인 **PickSafe** 역시 개발 생산성을 높이기 위해 Serverless PostgreSQL 환경을 채택해 운영해 왔습니다.

하지만 서버리스의 편리함 뒤에는 고질적인 비용 함정이 존재합니다. 바로 **'Compute Active Time(실행 시간)'에 따른 과금 체계**입니다. 

이번 글에서는 대규모 데이터 수집 배치(Seeding)와 실시간 어드민 모니터링 환경이 맞물리면서 발생했던 DB 비용 낭비 문제를 해결하고, **물리적 DB 이중화와 메모리 캐싱을 통해 Compute 비용을 극적으로 절감한 아키텍처 의사결정 과정**을 공유하고자 합니다.

---

## 1. 마주한 문제 (Problem): 편리함 뒤에 숨겨진 서버리스 과금 폭탄

서비스를 고도화하는 과정에서 다음과 같은 구조적 한계와 비용 리스크를 마주했습니다.

1. **상시 활성화(Keep-Alive)로 인한 Auto-suspend 방해**
   어드민 페이지에서 실시간 인프라 및 로그 모니터링을 위해 주기적으로 DB를 조회하고 있었습니다. 이로 인해 DB가 사용되지 않을 때 자동으로 일시정지(Auto-suspend)되는 서버리스의 핵심 장점을 누리지 못하고, 24시간 내내 Compute 비용이 청구되고 있었습니다.
2. **배치 부하가 실서비스(Master)에 미치는 영향**
   수만 건의 오픈 API 데이터를 수집하고 매쉬업하는 배치 프로세스가 실서비스 DB에 직접 쿼리를 날리면서, 대량의 CPU와 IOPS 리소스를 소모했습니다. 이는 동시 접속 중인 일반 사용자의 웹 서비스 응답 속도 저하로 직결되었습니다.
3. **인프라 제약 상황**
   비용 절감을 위해 저비용 호스팅 환경(Render 등)을 사용하고 있어, 외부 Redis 같은 별도의 인메모리 캐시 서버를 구성하기 곤란한 제약이 있었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 **1) DB 스케일 업(Scale-up)**, **2) 외부 캐시 서버 도입**, **3) 아키텍처 레벨의 비용 절감 전략**을 저울질했습니다. 

외부 인프라를 추가하는 방식은 호스팅 환경의 제약과 고정 비용 증가로 인해 제외하였고, **"데이터베이스의 역할 분리"**와 **"애플리케이션 레벨의 폴링 제어"**라는 아키텍처적 접근을 선택했습니다.

### 전략 1: 데이터베이스 물리적 분리 (Multi-DB Architecture)
실서비스 사용자를 위한 **Master DB(A)**와 수집/로그/모니터링을 담당하는 **Staging DB(B)**로 프로젝트를 이중화했습니다.
* **실서비스 DB A**: 무거운 연산이나 모니터링 쿼리를 원천 차단하여 최저 리소스 설정만으로도 안정적인 응답 속도를 보장합니다.
* **수집/로그 DB B**: 대량의 쓰기 작업과 모니터링 쿼리를 몰아넣은 뒤, **Auto-suspend 타임아웃(5분)을 타이트하게 적용**하여 평소 배치 미구동 시에는 물리적 요금이 '0원'이 되도록 설계했습니다.

### 전략 2: 수집기 커넥션 완전 격리 (Double-Buffering)
배치 수집 시 매번 Master DB를 조회하여 중복을 검사하던 기존 방식을 버렸습니다. 수집 프로세스 중에는 Master DB로의 커넥션을 완전히 차단하고, DB B(DW)의 임시 테이블 플래그(`is_merged=True`)만을 활용해 중복을 스킵합니다. 이후 관리자가 **[병합(Merge)]**을 승인하는 시점에만 단 한 번 벌크 트랜잭션을 실행합니다.

### 전략 3: 어드민 모니터링 'Off-by-Default' 및 로컬 캐시 도입
* **Off-by-Default 정책**: 대시보드 진입 시 실시간 갱신 스위치를 기본적으로 "꺼짐(False)"으로 두고, 관리자가 켜더라도 **1시간 경과 시 자동으로 스위치를 Off**시키도록 강제했습니다. 또한 브라우저 백그라운드 탭 진입 시(Page Visibility API) 폴링을 즉시 중단합니다.
* **로컬 LRU 캐시**: 외부 Redis 대신 Python 내장 `cachetools` 라이브러리를 활용해 API 서버 메모리 단에 초경량 LRU 캐시를 구현, Master DB로 향하는 단순 조회 트래픽을 70% 이상 감쇄시켰습니다.

## 3. 최종 아키텍처 및 구현 결과

이러한 전략을 단계적으로 적용한 결과, 시스템의 안정성과 비용 효율성을 동시에 잡을 수 있었습니다.

* **비용 절감**: 모니터링 자동 조회 차단과 DB B의 엄격한 Auto-suspend 적용으로 유휴 시간대 Compute 비용을 대폭 절감했습니다.
* **서비스 안정성**: 배치 수집이 일어나는 동안에도 실서비스 DB A는 일정한 응답 속도를 유지하여 사용자 경험(UX) 저하를 방어했습니다.
* **리소스 위생 관리**: 일자별 로컬 로그 분할(`RotatingFileHandler`, 최대 5MB 제한)을 도입하여 장기 구동 시 발생할 수 있는 디스크 용량 잠식 및 메모리 크래시 리스크를 사전 차단했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

> **"서버리스 환경에서의 비용 최적화는 인프라 스펙 조절이 아니라, 트래픽의 생명주기를 이해하는 아키텍처 설계에서 시작됩니다."**

서버리스 DB는 사용하지 않을 때 '꺼질 수 있는 환경'을 만들어주는 것이 핵심입니다. 아무리 좋은 클라우드 기능이라도 어드민의 사소한 자동 폴링 하나, 무심코 열어둔 DB 커넥션 하나가 그 장점을 무력화할 수 있습니다. 

이번 PickSafe의 아키텍처 개선을 통해, **비즈니스 로직의 특성에 맞게 데이터베이스의 역할을 물리적으로 분리하고, 클라이언트의 상태(State)까지 고려한 방어적 프로그래밍**이 대규모 인프라 비용 절감으로 이어진다는 값진 경험을 얻었습니다.
