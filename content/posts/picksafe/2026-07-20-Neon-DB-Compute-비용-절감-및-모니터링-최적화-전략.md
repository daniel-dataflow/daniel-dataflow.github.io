서버리스(Serverless) 데이터베이스는 초기 비용이 저렴하고 확장성이 뛰어나다는 장점이 있지만, 트래픽 패턴을 고려하지 않고 설계하면 예상치 못한 '요금 폭탄'을 맞기 쉽습니다. 

프로젝트 **PickSafe**를 운영하며 도입한 **Neon Serverless PostgreSQL** 역시 코어 과금 요소인 **COMPUTE 사용량(CU-Hours)** 관리가 핵심 과제였습니다. 특히 대량의 외부 API 데이터를 수집하는 배치 작업과 실시간 어드민 모니터링이 맞물리면서, 데이터베이스가 슬립(Sleep) 모드에 진입하지 못하는 문제가 발생했습니다.

이번 글에서는 무중단 서비스 안정성을 지키면서 **Neon DB Compute 비용을 극적으로 절감하기 위해 적용한 아키텍처 분리 전략과 모니터링 최적화 과정**을 공유합니다.

---

## 1. 마주한 문제 (Problem)

PickSafe 개발 과정에서 서버리스 DB 환경을 운영하며 다음과 같은 구조적 한계와 비용 리스크를 마주했습니다.

1. **배치 부하로 인한 서비스 지연**: 2만 건에 달하는 대규모 데이터 수집(Seeding) 및 매쉬업 배치가 실행될 때 대량의 CPU/IOPS가 소모되어, 동시 접속 중인 일반 사용자의 웹 서비스 응답 속도에 악영향을 미쳤습니다.
2. **Auto-suspend 방해 (Keep-Alive 문제)**: 어드민 페이지의 실시간 인프라 및 로그 모니터링이 자동 조회를 통해 DB 커넥션을 지속적으로 갱신하면서, DB가 자동으로 일시정지(Auto-suspend) 상태로 진입하지 못해 지속적인 비용이 발생했습니다.
3. **인프라 제약**: 저비용 호스팅 환경(Render 등)의 제약으로 인해 별도의 외부 Redis 인메모리 캐시를 구성하기 어려운 상황이었습니다.

---

## 2. 기술적 고민과 대안 선택 (Trade-off)

비용을 절감하면서도 운영 안정성을 확보하기 위해 세 가지 핵심 아키텍처 전략을 수립했습니다.

### ① 데이터베이스 물리적 분리 (Multi-DB Architecture)
일반 사용자의 조회가 일어나는 영역과 무거운 배치/로깅 영역을 하나의 DB에 두면 리소스 경합을 피할 수 없습니다. 이에 따라 **실운영 DB(Master)**와 **수집/배치/로그 DB(Staging)**로 프로젝트를 물리적으로 분리했습니다.

*   **실운영 DB A (Master)**: 일반 사용자 성분 조회 및 검색 전용. 무거운 연산이 없어 최저 리소스(0.25 CU)만으로도 쾌적한 응답 속도 유지.
*   **수집/배치/로그 DB B (Staging)**: 임시 적재, 어드민 통계, 서버 메트릭 및 실시간 로그 저장. **배치가 돌지 않을 때는 Auto-suspend(5분)를 타이트하게 적용하여 물리적 요금을 0원으로 유도.**

```mermaid
flowchart TD
    UserApp[일반 사용자 App] -->|성분/제품 조회| DB_A[(실운영 DB A: Master)]
    AdminDash[어드민 대시보드] -->|수집 명령 / 모니터링 쿼리| DB_B[(수집/배치 DB B: Staging)]
    
    subgraph Neon Project A (실운영 전용)
        DB_A
    end
    
    subgraph Neon Project B (수집/로그/모니터링 전용)
        DB_B
    end
    
    DB_B -->|🚀 최종 병합 Merge| DB_A
```

### ② 어드민 폴링 최적화 및 'Off-by-Default' 정책
관리자가 자리를 비우거나 브라우저 탭을 켜둔 채 퇴근하는 경우 발생하는 리소스 낭비를 막기 위해 프론트엔드와 백엔드 연동 방식을 전면 개편했습니다.
*   대시보드 진입 시 인프라/로그 실시간 갱신 스위치를 기본적으로 **"꺼짐(False)"** 상태로 설정.
*   **1시간 자동 타임아웃 오프**: 사용자가 수동으로 켜두었더라도 1시간이 지나면 클라이언트에서 강제로 스위치를 Off하여 불필요한 백엔드 쿼리 유발 원천 차단.
*   `PageVisibility API`를 연동하여 브라우저 백그라운드 진입 시 폴링 즉시 중단.

### ③ 외부 Redis 대체: FastAPI 로컬 LRU 캐시
외부 인메모리 DB를 두기 어려운 환경적 제약을 극복하기 위해, Python 내장 라이브러리(`cachetools`)를 활용한 **초경량 로컬 LRU(Least Recently Used) 캐시**를 API 레이어에 도입했습니다. 반고정 성분 매칭 사전 데이터를 메모리에 캐싱함으로써, Master DB로 향하는 단순 조회 트래픽을 최대 70% 감쇄시켰습니다.

## 3. 고도화: 수집기 격리와 로그 로테이션

설계 검증 과정에서 추가로 발견된 엣지 케이스들을 다음과 같이 보완했습니다.

*   **수집기 더블 버퍼링 (Double-Buffering)**: 수집 배치 구동 시 실운영 DB(Master)를 매번 조회하던 방식을 개선, 수집 중에는 DB A 접근을 완전히 차단하고 DB B(Staging)에만 적재한 뒤, 어드민에서 **[병합(Merge)]** 액션을 수행할 때만 벌크 트랜잭션을 실행하도록 격리했습니다.
*   **일자별 로컬 로그 분할 및 제한**: 단일 텍스트 파일에 로그가 무제한 쌓여 디스크를 잠식하던 문제를 해결하기 위해, 프로젝트 루트의 독립된 `/log/` 폴더(`seeding_run_YYYY-MM-DD.log`)로 격리하고 `RotatingFileHandler`를 장착해 최대 5MB, 백업 1개로 제한하여 디스크 안정성을 확보했습니다.

---

## 4. Takeaway (엔지니어링 교훈)

1. **서버리스의 핵심은 '재우기(Idle State Management)'다**: 서버리스 인프라 비용 절감의 핵심은 쿼리를 최적화하는 것뿐만 아니라, **"언제 확실하게 DB를 재울 수 있는가"**를 설계하는 데 있습니다. 물리적 분리와 타이트한 Auto-suspend 설정은 이를 달성하는 가장 확실한 방법입니다.
2. **트래픽 성격에 따른 데이터베이스 격리**: OLTP(실서비스 조회)와 OLAP/Batch(수집 및 로그)는 성격이 완전히 다릅니다. 초기 설계 단계부터 물리적/논리적 분리를 고려하는 것이 장기적인 인프라 비용과 장애 범위를 줄이는 길입니다.
3. **인프라 제약은 소프트웨어 레이어의 지혜로 극복할 수 있다**: 비싼 외부 인프라(Redis 등)를 구축할 수 없는 환경이라도, `cachetools`나 `PageVisibility API` 같은 경량 기술을 적절히 조합하면 충분히 프로덕션 레벨의 효율을 낼 수 있음을 확인했습니다.
