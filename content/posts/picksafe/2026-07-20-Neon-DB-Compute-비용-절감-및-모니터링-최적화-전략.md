안녕하세요, PickSafe 팀의 시니어 백엔드 에디터입니다. 

클라우드 기반의 서버리스 데이터베이스는 초기 구축 비용이 저렴하고 확장성이 뛰어나다는 장점이 있지만, 과금 체계를 정확히 이해하고 아키텍처를 설계하지 않으면 예상치 못한 '요금 폭탄'을 맞기 쉽습니다.

이번 포스팅에서는 **Neon Serverless PostgreSQL**을 도입하면서 마주한 Compute 비용 급증 문제를 해결하기 위해 적용한 **Multi-DB 물리적 분리 전략**, **어드민 모니터링 폴링 최적화**, 그리고 **로컬 인메모리 캐싱** 도입 과정을 공유합니다.

---

## 1. Problem: 서버리스 DB 환경의 함정과 비용 폭탄의 위협

우리가 도입한 Neon DB는 데이터베이스가 연결되거나 쿼리가 실행되는 시간(**Compute Active Time, CU-Hours**)을 기준으로 과금되는 구조입니다. 하지만 실운영 환경에서 다음과 같은 구조적 한계로 인해 비용 효율성에 적신호가 켜졌습니다.

1. **배치 부하 간섭**: 수만 건의 외부 API 데이터를 수집(Seeding)하고 매쉬업하는 대형 배치 프로세스가 일반 사용자용 웹 서비스와 동일한 DB를 바라보면서 CPU와 IOPS를 소모, 응답 속도 저하를 유발했습니다.
2. **상시 활성화(Keep-Alive) 리스크**: 어드민 페이지의 실시간 인프라 및 로그 모니터링이 자동 조회를 통해 끊임없이 DB 커넥션을 갱신하면서, DB가 비용이 절감되는 **Auto-suspend(자동 일시정지)** 상태로 진입하지 못했습니다.
3. **인프라 제약**: 저비용 호스팅 환경(예: Render 무료/저비용 티어)의 제한된 RAM 용량 때문에 외부 Redis 같은 인메모리 캐시를 별도로 구축하기가 까다로웠습니다.

---

## 2. Trade-off & Architecture: 어떻게 해결할 것인가?

이 문제를 해결하기 위해 단순한 쿼리 튜닝을 넘어, **인프라 레벨의 아키텍처 재설계**를 단행했습니다.

### ① 데이터베이스 물리적 분리 (Multi-DB Architecture)
실서비스의 안정성과 비용 절감을 위해 데이터베이스를 성격에 따라 완전히 이중화(A/B 분리)했습니다.

*   **실운영 DB A (Master DB)**: 일반 사용자용 조회 서비스만 담당합니다. 무거운 쓰기 작업이나 모니터링 쿼리를 원천 차단하여, 최저 리소스 설정(0.25 CU)만으로도 쾌적한 응답 속도를 보장합니다.
*   **수집/배치/로그 DB B (Staging & Log DB)**: 대량의 수집 데이터(`_staging`), 어드민 통계, 서버 로그 등을 전담합니다. 평소에는 타이트한 **Auto-suspend(5분)**를 적용해 배치 미구동 시 **물리적 요금 청구가 0원**이 되도록 설계했습니다.

```mermaid
flowchart TD
    UserApp[일반 사용자 App] -->|성분/제품 조회| DB_A[(실운영 DB A: Master)]
    AdminDash[어드민 대시보드] -->|수집 명령 / 모니터링 및 로그 쿼리| DB_B[(수집/배치 DB B: Staging)]
    
    subgraph Neon Project A (실운영 전용)
        DB_A
    end
    
    subgraph Neon Project B (수집/로그/모니터링 전용)
        DB_B
    end
    
    DB_B -->|🚀 최종 병합 Merge| DB_A
```

### ② 수집기 커넥션 완전 격리 (Double-Buffering)
배치 수집 시 매번 실운영 DB(A)를 조회하던 방식을 개선했습니다. 
수집 과정에서는 DB A와의 통신을 완전히 끊고, 오직 **DB B(Staging)**에서 중복 여부를 판단한 뒤, 최종 관리자가 **[병합(Merge)]** 액션을 수행할 때만 DB A로 벌크 트랜잭션을 실행하도록 구조를 변경했습니다.

### ③ 어드민 모니터링 'Off-by-Default' 및 1시간 타임아웃
관리자가 자리를 비우거나 백그라운드 탭에 방치했을 때 DB가 깨어있는 현상을 방지하기 위해:
*   인프라/로그 모니터링 갱신 스위치의 기본값을 **`False`(꺼짐)**로 설정했습니다.
*   클라이언트단에서 **1시간이 경과하면 강제로 스위치를 끄는 타임아웃**을 구현하고, `PageVisibility API`를 연동하여 브라우저 탭이 비활성화되면 폴링을 즉각 중단하도록 했습니다.

### ④ 초경량 로컬 LRU 캐시 도입
외부 Redis 대신 FastAPI 애플리케이션 메모리 내에 Python의 내장 LRU 캐시(`cachetools`)를 적용하여, 반고정 성분 매칭 사전 정보 조회 쿼리를 메모리 수준에서 처리함으로써 **DB A로 향하는 단순 조회 트래픽을 70% 이상 감쇄**시켰습니다.

## 3. Takeaway: 엔지니어링 교훈

1. **서버리스의 핵심은 '재울 수 있는 용기'다**: 서버리스 아키텍처에서 비용을 아끼는 가장 확실한 방법은 쿼리 최적화뿐만 아니라, **"사용하지 않을 때 시스템이 확실히 잠들 수 있는 환경(Auto-suspend)"**을 만들어주는 것입니다. 폴링과 백그라운드 커넥션 관리가 그 열쇠입니다.
2. **비즈니스 목적에 따른 데이터 격리(Multi-DB)**: 모든 데이터를 하나의 DB에 우겨넣는 것은 단기적으로는 편해 보이지만, 대형 배치 작업 하나가 핵심 서비스의 생사를 좌우하는 리스크를 낳습니다. 비용과 안정성 두 마리 토끼를 잡기 위해 과감히 DB를 분리하는 결단이 필요합니다.
3. **제약 속의 아키텍처링**: 고가의 외부 인프라(Redis 등)를 쓸 수 없는 환경이라도, 애플리케이션 레벨의 로컬 캐싱과 일자별 로그 로테이션(`RotatingFileHandler`를 활용한 5MB 제한 등) 같은 섬세한 설계로 충분히 프로덕션 수준의 안정성을 확보할 수 있습니다.

이번 최적화를 통해 PickSafe는 인프라 안정성을 높이면서도 Neon DB Compute 비용을 극적으로 절감할 수 있었습니다. 서버리스 환경에서 비용과 성능으로 고민하시는 엔지니어분들에게 작은 영감이 되었기를 바랍니다.
