안녕하세요, PickSafe Dev Team입니다. 

서비스가 성장함에 따라 엔지니어는 필연적으로 트레이드오프(Trade-off)의 순간을 마주하게 됩니다. 최근 저희 팀은 **"서비스 보안 및 어뷰징 방지"**라는 운영적 요구사항과 **"사용자 개인정보 보호(GDPR/PIPA)"**라는 가치 사이에서 깊은 고민을 거쳤습니다. 

기존 PickSafe는 개인정보 최소화 원칙에 따라 방문자의 원본 IP를 저장하지 않고 도시(`city`)와 국가(`country`) 정보만 식별해 왔습니다. 하지만 서비스 스케일이 커지면서 비정상적인 스크래핑, DDoS성 반복 요청, 관리자 테스트 데이터 분리 등의 이슈를 해결하기 위해 **방문자 원본 IP 수집이 불가피한 시점**에 도달했습니다.

이번 포스팅에서는 PickSafe가 어떻게 기술적 타협 없이 **원본 IP를 수집하면서도 강력한 4대 안전장치(Security Controls)를 통해 규제 준수와 보안을 모두 잡았는지** 그 아키텍처와 엔지니어링 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): 현실적인 보안 위협과 규제의 충돌

기존의 "도시/국가 단위 수집" 방식은 프라이버시 관점에서는 훌륭했으나, 실제 프로덕션 환경에서는 다음과 같은 한계에 봉착했습니다.

1. **분산 어뷰징 및 DDoS 식별 불가**: 동일한 도시 내에서 짧은 시간 동안 수만 번의 요청이 들어올 때, 개별 IP 단위의 식별자가 없다면 정상 사용자들의 트래픽과 어뷰징 트래픽을 구분하여 차단하기 어렵습니다.
2. **동적 어드민 트레픽 필터링 한계**: 서비스 개선을 위해 관리자(Admin)가 직접 프로덕션 환경을 테스트할 때, 이 통계가 실제 사용자 데이터에 섞여 분석가들에게 왜곡된 지표를 제공했습니다. 이를 실시간으로 제외하기 위해서는 기기별 고유 식별(IP)이 필수적이었습니다.

하지만 원본 IP는 개인 식별 가능성이 있는 **민감한 개인정보**로 분류됩니다. 컴플라이언스(PIPA/GDPR)를 준수하면서 시스템의 안전을 확보하기 위한 정교한 아키텍처 설계가 요구되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

원본 IP 수집이라는 결정을 내리기 전, 저희 팀은 여러 대안을 검토했습니다.

| 대안 | 장점 | 단점 | 채택 여부 |
| :--- | :--- | :--- | :--- |
| **A. 단방향 해시화 (SHA-256 + Salt)** | 개인정보 유출 우려가 전혀 없음. | IP 대역대 기반의 차단(WAF 연동)이나 어뷰징 패턴 분석(예: Class C 대역 차단)이 원천적으로 불가능함. | **기각** |
| **B. 원본 IP 무기한 수집** | 보안 분석 및 영구 트래킹에 매우 용이함. | GDPR/PIPA 위반 소지가 매우 높으며, DB 유출 시 치명적인 보안 사고로 이어짐. | **기각** |
| **C. 원본 IP 수집 + 4대 안전장치 구축** | 실시간 어뷰징 방지 및 관리자 필터링 가능, 법적 컴플라이언스 완벽 준수. | 추가적인 파이프라인(TTL 배치 등)과 감사 시스템 구축 공수 발생. | **최종 채택** |

결국 보안 운영 효율성을 극대화하되, 기술적인 안전장치를 겹겹이 쌓아 리스크를 제로(0)에 가깝게 수렴시키는 **'C안'**을 선택했습니다.

## 3. 해결책: 신뢰를 구축하는 '4대 안전장치' 아키텍처

저희가 설계하고 적용한 4대 안전장치는 다음과 같습니다.

```
[방문자 트래픽] ──> [FastAPI Backend] 
                          │
                          ├─► ① RBAC: 오직 super_admin 권한만 raw_ip 조회 가능
                          ├─► ② TTL: 30일 경과 시 raw_ip 영구 파기 (Daily Summary로 익명 집계)
                          ├─► ③ Transparency: 어드민 화면 내 수집 정책 명시
                          └─► ④ Audit Trail: super_admin의 조회 이력을 시스템 로그에 영구 기록
```

### ① 역할 기반 권한 제어 (RBAC: Role-Based Access Control)
* **설계**: 시스템 내부에서 모든 관리자가 원본 IP를 볼 수 있는 것은 아닙니다. 마케팅, CS, 번역 등 통계 정보만 필요한 일반 관리자는 비식별화된 요약본(`daily_summaries`)만 볼 수 있도록 권한을 철저히 격리했습니다.
* **구현**: 오직 `super_admin` 권한을 가진 계정만 원본 로그 API 엔드포인트에 접근할 수 있도록 FastAPI의 Dependency Injection 구조를 활용해 인가(Authorization) 계층을 강화했습니다.

### ② 데이터 수명 주기 관리 (Data TTL - 30일 후 영구 파기)
* **설계**: 어뷰징 방지와 테스트 트래픽 제외 목적의 데이터는 오랜 기간 보관할 필요가 없습니다. 분석용 원본 로그는 딱 **30일**만 보관합니다.
* **구현**: 매일 자정 실행되는 배치 작업(`aggregate_daily_summary`)을 통해 통계 요약본을 안전하게 가공/저장한 뒤, 30일이 지난 원본 이벤트 데이터는 데이터베이스 레벨에서 `DELETE` 쿼리로 영구 삭제(Purge)하도록 스케줄러를 구성했습니다.

```sql
-- 30일 경과 데이터 영구 파기 쿼리 (개념 예시)
DELETE FROM visitors_events 
WHERE created_at < NOW() - INTERVAL '30 days';
```

### ③ 목적의 명시 및 투명성 (Transparency)
* **설계**: 투명성은 컴플라이언스의 기본입니다. 사내 기술 의사결정 문서(ADR)로 본 목적을 명문화하는 것에 그치지 않고, 시스템을 다루는 내부 작업자들에게 경각심을 주기 위해 어드민 대시보드 하단에 수집 목적, 보관 기간(30일), 그리고 감사 추적이 진행 중임을 상시 안내하는 UI 영역을 추가했습니다.

### ④ 원본 IP 열람 감사 로그 (Audit Trail - "감시자를 감시하는 체계")
* 아무리 최고 관리자(`super_admin`)라 할지라도 개인정보가 포함된 원본 IP 목록을 조회할 때는 합당한 이유가 있어야 합니다. 
* 이를 통제하기 위해, 최고 관리자가 원본 IP가 포함된 API를 호출할 때마다 시스템은 이를 자동으로 감지하여 `logs_system` 테이블에 **`[AUDIT] super_admin (email) viewed raw visitor IP logs`** 형태의 포맷으로 감사 로그를 즉시 기록합니다. 이 감사 로그는 수정 및 삭제가 불가능하며 영구 보존됩니다.

## 4. 엔지니어링 교훈 (Takeaway)

이번 작업을 통해 저희 팀이 얻은 핵심 교훈은 다음과 같습니다.

1. **보안과 개인정보 보호는 제로섬(Zero-Sum) 게임이 아니다**: 
   안전장치를 정교하게 설계한다면, 비즈니스 목적(보안/어뷰징 방지)을 달성하면서도 사용자 프라이버시 권리를 완벽히 존중할 수 있습니다.
2. **데이터 수명 주기(Lifecycle)를 처음부터 고려하라**: 
   쌓아두기만 하고 지우지 않는 데이터는 언젠가 반드시 기술 부채나 법적 리스크로 돌아옵니다. 데이터 저장소 설계 시점부터 TTL 정책과 자동 삭제 메커니즘을 고민하는 습관이 중요합니다.
3. **신뢰는 검증 가능성에서 온다 (Audit Trail)**: 
   내부 직원의 권한 남용을 방지하는 시스템적인 감사 장치가 마련되어 있을 때, 비로소 외부 투자자나 고객들에게 "우리 시스템은 안전하다"고 떳떳하게 증명할 수 있습니다.

앞으로도 PickSafe는 고도의 기술적 안정성과 윤리적 데이터 관리를 동시에 실현하는 아키텍처를 지향하겠습니다. 긴 글 읽어주셔서 감사합니다!
