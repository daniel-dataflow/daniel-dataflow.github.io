안녕하세요, PickSafe 개발팀의 Daniel입니다.

스타트업이 서비스를 성장시키다 보면 필연적으로 **'개인정보 최소화 원칙'**과 **'보안 및 어뷰징 방지'**라는 두 가치의 충돌을 마주하게 됩니다. 

기존 PickSafe의 분석 엔진은 개인정보를 보호하기 위해 방문자의 원본 IP를 저장하지 않고, 국가와 도시 단위의 통계 데이터만 수집해 왔습니다. 하지만 서비스 스케일이 커짐에 따라 악의적인 스크래핑, DDoS 공격, 시크릿 모드를 우회한 중복 어뷰징 등 **실제 IP 기반의 실시간 방어 체계**가 절실히 요구되는 시점에 도달했습니다.

오늘 포스팅에서는 우리가 어떻게 **개인정보보호법(PIPA) 및 GDPR 가이드라인을 철저히 준수**하면서도, 보안 요구사항을 만족하는 **'4대 안전장치 기반 원본 IP 수집 아키텍처'**를 구축했는지 공유하고자 합니다.

---

## 1. 문제 정의 (Context)

통계 중심의 비식별 텔레메트리만으로는 서비스가 직면한 아래 두 가지 실무적인 문제를 해결하기 어려웠습니다.

1. **지능형 어뷰징 및 봇 트래픽 식별 불가**
   * 쿠키나 로컬 스토리지를 초기화하는 시크릿 모드 환경에서는 동일 기기의 악의적 반복 요청을 단시간 내에 탐지하기 어려웠습니다.
2. **개발/관리자 테스트 데이터 오염**
   * 운영 환경에서 동적으로 관리자 테스트 트래픽을 필터링해야 했으나, 고유 식별값(IP)의 부재로 과거 및 당일의 테스트 접속 이력을 통계에서 실시간으로 완벽히 제외하기 불가능했습니다.

결국 **원본 IP 수집은 불가피한 선택**이 되었습니다. 하지만 "수집한다"에서 그치지 않고, 이를 **"어떻게 안전하고 법규에 어긋나지 않게 관리할 것인가"**가 엔지니어링팀의 핵심 과제였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

IP 수집 방식을 결정하기 위해 저희 팀은 세 가지 아키텍처 대안을 두고 치열하게 토론했습니다.

| 비교 항목 | 대안 A: 단순 단방향 해싱 (SHA-256) | 대안 B: IP 수집 배제 및 행동 패턴 분석 | 대안 C: 원본 IP 수집 + 4대 안전장치 (선택) |
| :--- | :--- | :--- | :--- |
| **장점** | 원본을 저장하지 않아 상대적으로 보안 유출 위험 낮음. | 개인정보 규제로부터 완벽히 자유로움. | **정확한 어뷰징 차단 가능, 동적 관리자 트래픽 필터링 완벽 지원.** |
| **단점** | 레인보우 테이블 공격에 취약(IP 대역폭이 좁아 염역 추적 가능), 실시간 IP 대역 차단 등 방어 동작 연계 불가. | 탐지 정확도가 떨어지며 오탐(False Positive) 가능성 매우 높음. | 보안 관리 체계 및 무결성 감사 시스템을 추가 개발해야 하는 오버헤드. |
| **선택 여부** | 미채택 | 미채택 | **최종 채택** |

**결론**: 단순히 책임을 회피하기 위해 데이터 품질을 타협하기보다, **가장 정확한 원본 데이터를 수집하되 기술적/제도적 안전장치를 엄격하게 설계하여 리스크를 제로에 수렴하게 만드는 방향(대안 C)**을 선택했습니다.

## 3. 4대 안전장치 아키텍처 설계 (The 4 Security Controls)

우리가 설계한 안전장치는 **"필요한 사람만 보고, 필요한 기간만 보관하며, 모든 행위는 기록되고, 프로세스는 투명하게 공개된다"**는 대원칙을 따릅니다.

```
[ Visitor Access ] ──> [ FastAPI Router ]
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
     [ 1. RBAC 검증 ]                [ 4. 감사 로그 기록 ]
    (super_admin 전용)          (logs_system 내 무결성 보존)
               │                             │
               └──────────────┬──────────────┘
                              ▼
                     [ PostgreSQL DB ] ──> [ 2. 30일 경과 데이터 ] ──> [ Daily TTL Purge ]
```

### ① RBAC (Role-Based Access Control) 기반 접근 통제
원본 IP 정보가 유출되는 가장 큰 경로는 내부 관리자 권한 남용입니다. 
이를 방지하기 위해 마케팅, CS, 번역 담당 등 일반 관리자 계정은 일자별 통계 요약 데이터만 조회할 수 있도록 제한하고, 원본 IP 조회 API 엔드포인트는 오직 **최고 관리자(`super_admin`)** 권한을 가진 계정만 접근할 수 있도록 의존성 주입(Dependency Injection) 체계를 구축했습니다.

### ② 데이터 생명주기 관리 (30일 TTL 영구 파기)
로그 데이터는 쌓일수록 보안 리스크가 커집니다. 
수집된 원본 로그(`visitors_events`)는 **정확히 30일 동안만 보관**됩니다. 매일 자정 실행되는 배치 작업(`aggregate_daily_summary`)이 당일 통계 요약을 생성함과 동시에, 30일이 지난 원본 IP 레코드를 데이터베이스에서 완전히 삭제(`DELETE`)합니다. 통계용 익명화 데이터는 보존되므로 비즈니스 지표 흐름에는 영향을 주지 않습니다.

### ③ 감시자를 감시하는 '원본 IP 열람 감사 로그(Audit Trail)'
"아무리 최고 관리자라 할지라도 무단으로 사용자의 IP 정보를 열람해서는 안 된다." 
이 원칙을 실현하기 위해, 최고 관리자가 원본 IP가 포함된 웹 콘솔 화면에 접근할 때마다 시스템 내부 테이블(`logs_system`)에 자동으로 감사 로그가 기록되도록 설계했습니다.
* 로그 포맷 예시: `[AUDIT] super_admin (admin@picksafe.io) viewed raw visitor IP logs`
* 이 로그는 삭제나 수정이 불가능한 격리된 DB에 보존되어 추후 보안 감사(Audit) 시 증적 자료로 활용됩니다.

### ④ 보관 목적의 문서화 및 UI 투명성 공개
우리는 투명성을 신뢰의 핵심 가치로 삼고 있습니다. 본 기술 결정 문서(ADR)를 아카이빙하는 것은 물론, 어드민 페이지 하단에 개인정보 처리 방침과 30일 TTL 작동 방식을 안내 문구로 상시 노출하여 시스템 운영 정책을 투명하게 밝혔습니다.

## 4. FastAPI & DB 구현 들여다보기

아래 코드는 이번 아키텍처를 구현하기 위해 적용된 핵심 로직의 개념적 예시입니다. (보안을 위해 내부 비즈니스 로직 및 스키마는 마스킹 처리되었습니다.)

### 1) RBAC 및 감사 로그가 적용된 API 엔드포인트 (`visitors.py`)

FastAPI의 의존성 주입을 활용하여 권한을 검증하고, 조회가 발생할 때마다 감사 로그를 영구 기록합니다.

```python
from fastapi import APIRouter, Depends, HTTPException, status
from app.services.auth import get_current_super_admin
from app.services.analytics import AnalyticsService
from app.services.audit import AuditLogger

router = APIRouter(prefix="/admin/visitors", tags=["Admin Visitors"])

@router.get("/recent-events")
async def get_recent_visitor_events(
    current_user: User = Depends(get_current_super_admin), # 1. RBAC 제한
    analytics_service: AnalyticsService = Depends()
):
    # 2. 감사 로그 기록 (Audit Trail)
    await AuditLogger.log_action(
        actor_email=current_user.email,
        action=f"viewed raw visitor IP logs"
    )
    
    events = await analytics_service.get_recent_events_with_raw_ip()
    return events
```

### 2) 30일 경과 데이터 영구 퍼지 및 통계 요약 (`analytics_service.py`)

통계를 집계한 후, 30일이 지난 원본 데이터를 안전하게 삭제하여 데이터의 생명 주기를 엄격히 제어합니다.

```python
from datetime import datetime, timedelta
from sqlalchemy.orm import Session

class AnalyticsService:
    def __init__(self, db: Session):
        self.db = db

    async def aggregate_daily_summary(self):
        """매일 자정 통계 데이터를 집계하고 30일 지난 원본 로그를 영구 파기합니다."""
        # 1. 일자별 통계 요약본 생성 로직 수행
        # ... (생략) ...

        # 2. 30일 경과 데이터 파기 (TTL)
        expiration_date = datetime.utcnow() - timedelta(days=30)
        
        self.db.execute(
            "DELETE FROM visitors_events WHERE created_at < :expiration_date",
            {"expiration_date": expiration_date}
        )
        self.db.commit()
```

## 5. 엔지니어링 교훈 (Takeaway)

이번 아키텍처 개편 과정을 통해 우리 팀은 크게 세 가지 교훈을 얻었습니다.

1. **보안과 사용성/기능성은 제로섬 게임이 아니다.**
   * 원본 IP를 안전장치 없이 무방비하게 수집하는 것은 위험하지만, 규제 준수 체계(Compliance as Code)를 파이프라인 내부 구조로 자동화해 놓는다면 보안과 비즈니스 요구사항을 모두 만족할 수 있습니다.
2. **"감시하는 자도 감시받는 체계"의 중요성**
   * 최고 권한 관리자의 행동 양식을 감사 로그(Audit Trail)로 남기는 것은 내부 직원에 대한 상호 신뢰를 높이고, 휴먼 에러나 악의적 탈취 시도를 차단하는 가장 강력한 방어선입니다.
3. **데이터 TTL은 DB 비용 최적화의 기본이다.**
   * 필요한 기간이 지난 비정형 로그 데이터를 과감히 정리함으로써 디스크 용량을 최적화하고, 쿼리 인덱스 성능 향상이라는 부가적인 아키텍처 이점까지 얻을 수 있었습니다.

기술적 도전 과제 속에서 항상 최선의 타협점을 찾고 이를 구조적으로 해결해 나가는 것, 이것이 PickSafe 개발팀이 일하는 방식입니다.
