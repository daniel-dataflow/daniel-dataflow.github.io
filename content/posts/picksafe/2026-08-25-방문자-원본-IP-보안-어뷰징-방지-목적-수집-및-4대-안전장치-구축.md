안녕하세요, PickSafe 개발 팀의 Daniel입니다. 

서비스가 성장함에 따라 플랫폼의 안정성을 위협하는 요인들도 진화합니다. 시크릿 모드나 쿠키를 우회하는 정교한 웹 스크래핑, 단시간 내 몰리는 비정상 트래픽(DDoS/어뷰징), 그리고 개발 및 운영 과정에서 관리자의 테스트 트래픽이 실무 데이터 오염으로 이어지는 문제 등은 서비스 초기 아키텍처에서 쉽게 마주하는 난제입니다.

기존 PickSafe는 개인정보 최소화 원칙에 입각해 원본 IP를 저장하지 않고 대략적인 위치(`city`, `country`)만 수집해 왔습니다. 하지만 **보안 관측 가능성(Observability) 확보와 어뷰징 방어**라는 비즈니스적 요구가 거세지면서, 원본 IP 수집이라는 기술적 결정을 내릴 기로에 섰습니다.

이번 포스팅에서는 **개인정보보호법(PIPA) 및 GDPR 컴플라이언스를 완벽히 준수하면서도, 보안과 어뷰징 방어 목적을 달성하기 위해 설계한 '4대 안전장치(Security Controls)' 아키텍처**를 공유해 드립니다.

---

## 1. 문제 정의 (Context): 왜 원본 IP 수집이 필요해졌는가?

초기 시스템은 개인정보 유출 리스크를 원천 차단하기 위해 IP 주소를 해싱하거나 파기하고 지리적 메타데이터만 활용했습니다. 그러나 서비스 운영 과정에서 다음 두 가지 한계에 부딪혔습니다.

1. **정교한 어뷰징 및 스크래핑 식별 불가**: 쿠키와 세션 스토리지를 초기화하며 반복 접근하는 악성 트래픽을 단일 사용자로 오인하거나 추적할 수 없음.
2. **관리자 기기 데이터의 노이지(Noise) 발생**: 관리자가 운영 검증을 위해 접속한 이력이 실시간 트래픽 집계에 섞여 들어와 정확한 지표 분석을 방해함.

**"보안과 어뷰징 방어를 위해 원본 IP를 수집해야 한다. 하지만, 개인정보 보호 컴플라이언스 기준을 절대 위반해서는 안 된다."** 
이 상반된 요구사항을 해결하기 위해, 우리는 원본 IP를 다루되 **강력한 가드레일(Guardrail)을 동반한 아키텍처**를 설계하기로 결정했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

원본 IP(`ip_address`)를 데이터베이스에 적재하는 순간, 해당 데이터는 **개인정보(PII, Personally Identifiable Information)**로 분류됩니다. 따라서 다음과 같은 아키텍처적 대안을 두고 고민했습니다.

* **Alternative A: 단방향 해싱(Hashing) 및 솔트(Salt) 저장**
  * *Pros*: 원본 유출 리스크 없음.
  * *Cons*: 동적 IP 변동이나 복잡한 패턴의 DDoS 분석 시 추적력이 떨어지고, 특정 IP 대역 차단(CIDR Block) 같은 실질적인 보안 조치에 적용하기 까다로움.
* **Alternative B: 원본 IP 저장 + 강력한 컴플라이언스 및 자동 파기 가드레일 (Selected)**
  * *Pros*: 정밀한 어뷰징 패턴 분석, 실시간 관리자 트래픽 필터링, 그리고 정확한 감사 추적(Audit Trail) 가능.
  * *Cons*: 구현 및 운영 상에서 엄격한 접근 통제와 자동 파기(TTL) 로직을 강제해야 함.

우리는 보안 위협에 민첩하게 대응하고 정확한 트래픽 필터링을 수행하기 위해 **Alternative B**를 선택했습니다. 단, 오직 '보안 및 어뷰징 방지'라는 명확한 목적 하에만 수집하고, 데이터 생명주기를 시스템적으로 강제하는 **4대 안전장치**를 백엔드 코어에 녹여냈습니다.

## 3. 핵심 아키텍처: 4대 안전장치 (4 Security Controls)

FastAPI 기반의 백엔드(`analytics_service.py`, `visitors.py`)와 PostgreSQL 인프라 레벨에서 구현한 4대 안전장치는 다음과 같습니다.

### ① 접근 권한 최고 관리자(`super_admin`) 전용 제한 (RBAC)
원본 IP 및 상세 이벤트 로그에 접근할 수 있는 엔드포인트는 일반 관리자(마케팅, CS 등)에게는 완전히 차단됩니다. 
* 오직 최상위 권한인 `super_admin`만 해당 데이터에 접근할 수 있도록 Role-Based Access Control(RBAC)을 엄격히 적용했습니다.
* 일반 관리자는 비식별화된 일자별 통계 요약(`visitors_daily_summaries`)만 조회할 수 있습니다.

### ② 데이터 자동 만료 (TTL 30일 영구 파기)
원본 텔레메트리 데이터(`visitors_events`)는 무기한 보관하지 않습니다.
* 수집 시점으로부터 **30일이 경과한 원본 IP 데이터는 매일 자정 실행되는 통계 배치 작업(`aggregate_daily_summary`)을 통해 영구 자동 삭제(DELETE)**됩니다.
* 단, 분석을 위한 익명화된 일자별 통계 요약본은 영구 보존하여 비즈니스 인사이트 손실을 방지합니다.

```python
# analytics_service.py 내부 배치 파기 로직 예시 (개념 코드)
def aggregate_daily_summary(db: Session):
    # 1. 일자별 통계 요약 집계 수행
    # ...
    
    # 2. 30일 경과 원본 IP 텔레메트리 영구 파기 (TTL 30 Days)
    db.execute(
        text("DELETE FROM visitors_events WHERE created_at < NOW() - INTERVAL '30 days'")
    )
    db.commit()
```

### ③ 보관 목적 문서화 및 UI 정책 안내
엔지니어링 문서(ADR)를 통해 수집 목적을 영구 보존함과 동시에, 어드민 대시보드 UI 하단에 **"개인정보 및 보안 운영 정책 안내(수집 목적, 30일 TTL, 감사 추적)"** 문구를 상시 노출하여 투명성을 확보했습니다.

### ④ 원본 IP 열람 감사 로그 (`Audit Trail`)
"감시하는 자도 감시받아야 한다"는 보안 원칙에 입각했습니다.
* 최고 관리자가 원본 IP 목록을 조회하는 순간, 백엔드 라우터에서 시스템 감사 로그 테이블(`logs_system`)에 **`[AUDIT] super_admin (email) viewed raw visitor IP logs`** 형태의 로그를 자동으로 적재합니다. 
* 내부 정보 유출 및 비정상적 열람 시도를 사후 추적할 수 있는 체계를 완성했습니다.

## 4. 엔지니어링 교훈 및 Takeaways

이번 아키텍처 고도화를 통해 얻은 교훈은 명확합니다.

1. **보안과 컴플라이언스는 제로섬(Zero-sum)이 아니다**: 비즈니스 운영상 민감한 데이터(원본 IP)가 반드시 필요하다면, 저장을 회피하는 것보다 **"어떻게 안전하게 다루고 언제 파기할 것인가"**에 대한 기술적 가드레일을 시스템화하는 것이 더 완성도 높은 엔지니어링입니다.
2. **자동화된 생명주기 관리(TTL)**: 사람이 직접 지우는 데이터는 휴먼 에러를 유발합니다. 백엔드 배치 파이프라인에 데이터 만료 로직을 강제하여 규정 준수 리스크를 시스템적으로 제거했습니다.
3. **책임 소재의 명확화 (Auditability)**: 강력한 권한을 부여하는 만큼, 그 권한을 행사하는 행위 자체를 투명하게 로깅(`Audit Trail`)하는 추적 체계가 반드시 동반되어야 안전한 시스템 운영이 가능합니다.

PickSafe는 앞으로도 데이터 보안과 사용자 프라이버시 보호를 최우선 가치로 두고, 견고한 백엔드 아키텍처를 지속적으로 만들어 나갈 것입니다.
