안녕하세요. PickSafe 기술 블로그입니다. 

글로벌 서비스를 구축하면서 가장 마주하기 까다로운 문제 중 하나는 **'서로 다른 언어와 표현으로 작성된 데이터를 어떻게 정확하고 확장성 있게 처리할 것인가'**입니다. 특히 화장품이나 식품 등의 성분 데이터는 국가별 명칭(INCI), 현지 언어, 그리고 소비자가 입력하는 다양한 오타와 통용어까지 고려해야 하므로 단순한 문자열 매칭으로는 해결하기 어려운 복잡성을 가집니다.

이번 글에서는 전 세계 100개 언어 확장과 지능형 오타 매칭을 동시에 달성하기 위해 우리가 어떤 아키텍처적 고민을 했고, 어떤 트레이드오프를 거쳐 문제를 해결했는지 공유해 드립니다.

---

## 1. Problem: 100개 언어 확장과 '사용자의 오타'라는 두 마리 토끼

글로벌 서비스 론칭을 앞두고 우리 팀은 다음과 같은 기술적 도전에 직면했습니다.

1. **폭발적인 데이터 확장성 문제 ($O(N^2)$의 함정)**:
   만약 모든 국가별 언어로 성분 데이터를 개별 관리한다면, 새로운 언어가 추가될 때마다 매핑 관계가 기하급수적으로 늘어나는 $O(N^2)$ 모델에 빠지게 됩니다. 유지보수가 불가능한 구조였습니다.
2. **이질적인 입력 데이터 (OCR 에러 및 오타)**:
   사용자가 제품 라벨을 찍어 올리거나(OCR) 직접 검색할 때, 법정 성분명과 정확히 일치하는 경우는 드뭅니다. 미세한 오타, 음차 표기 차이, 국가별 통용어로 인해 기존의 Exact Match 방식은 높은 실패율을 보였습니다.
3. **인프라 및 리소스 비용**:
   번역 엔진 도입과 관리용 테이블을 무분별하게 늘리면 인프라 파편화와 API 쿼터 관리 비용이 급증합니다.

---

## 2. Technical Choices & Trade-offs: 아키텍처 설계와 대안 비교

이 문제를 해결하기 위해 우리 팀은 몇 가지 핵심적인 아키텍처 의사결정을 내렸습니다.

### ① Hub & Spoke 아키텍처 채택 ($O(N)$ 선형 모델)
* **대안 검토**: 국가별 성분 테이블 파편화 vs 단일 축 중심 확장
* **선택**: 국제 화장품 표준 명명법인 **INCI 영문명을 중심축(Hub)**으로 두고, 그 주변으로 100개 언어(Spoke)를 연결하는 구조를 채택했습니다.
* **Trade-off**: 새로운 언어 추가 시 Hub와의 매핑만 추가하면 되므로 복잡도를 $O(N)$으로 극적으로 낮췄습니다. 단, Hub 데이터의 정합성이 전체 시스템의 품질을 좌우하므로 초기 표준화 작업에 집중했습니다.

### ② 기존 SSOT(Single Source of Truth) 인프라 100% 재사용
* **대안 검토**: 성분 번역 전용 신규 테이블 및 별도 인프라 구축 vs 기존 공용 번역 저장소 통합
* **선택**: 별도의 테이블을 신설하는 대신, 기존에 운영 중인 `translations_dictionary`에 `entity_type='ingredient'` 조건을 부여하여 통합했습니다.
* **Trade-off**: Gemini AI 자동 번역 엔진 파이프라인과 API 키 쿼터 관리 인프라를 수정 없이 그대로 재사용할 수 있었습니다. 덕분에 개발 공수를 대폭 줄이면서도 시스템 응집도를 높였습니다.

### ③ 4단계 다중 방어선 매칭 엔진 구축
사용자의 다양한 입력 패턴을 포착하기 위해 단일 알고리즘이 아닌 **4단계 다중 방어선(Multi-layered Defense)** 매칭 파이프라인을 설계했습니다.

1. **1단계 (Exact Match)**: 시스템 등록명과 완벽히 일치하는 경우 (가장 빠름)
2. **2단계 (Synonym / Hub Match)**: 동의어 사전 및 Hub 명칭을 통한 교차 검증
3. **3단계 (15개 한국어 음차 룰 적용)**: 글로벌 성분이 한국어로 음차될 때 발생하는 고유의 발음 변형 패턴 대응
4. **4단계 (Fuzzy Levenshtein 85%+)**: OCR 오인식이나 미세한 오타를 보정하기 위한 편집 거리(Levenshtein Distance) 알고리즘 적용

## 3. Takeaways: 엔지니어링 교훈

이번 설계를 통해 얻은 가장 큰 배움은 **"복잡한 도메인일수록 표준(Standard)에 의존하고, 예외 처리는 단계별 파이프라인으로 격리해야 한다"**는 점입니다.

* **표준의 힘**: INCI라는 명확한 Hub를 설정함으로써 100개라는 방대한 언어 확장성 문제를 우아하게 해결할 수 있었습니다.
* **재사용성의 가치**: 새로운 인프라를 무조건 구축하기보다, 기존 SSOT 구조를 확장 가능하게 설계하는 것이 운영 리스크를 줄이는 지름길임을 다시 한번 확인했습니다.
* **방어적 설계**: 오타와 OCR 에러는 완벽히 막을 수 없으므로, 시스템이 단계별(Exact ➔ Rule ➔ Fuzzy)로 유연하게 fallback 할 수 있는 다중 방어선을 구축하는 것이 사용자 경험(UX) 측면에서 결정적인 차이를 만듭니다.

PickSafe 기술팀은 앞으로도 대규모 데이터와 글로벌 환경에서 마주하는 기술적 난제들을 견고하고 확장 가능한 아키텍처로 풀어나가겠습니다.
