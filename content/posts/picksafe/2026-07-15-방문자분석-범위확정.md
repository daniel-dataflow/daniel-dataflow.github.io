안녕하세요, PickSafe 개발팀입니다. 
서비스를 운영하면서 "데이터는 많을수록 좋다"는 함정에 빠지기 쉽습니다. 사용자 행동을 실시간으로 추적하고, 화려한 대시보드를 구축하는 것은 개발자로서 매력적인 작업이지만, 때로는 과도한 데이터 수집이 인프라 비용을 폭발시키고 시스템 성능을 저하시키는 부메랑이 되어 돌아오기도 합니다.

이번 포스팅에서는 무료 티어 인프라 환경에서 **어드민 방문자 분석 및 텔레메트리 기능을 설계하며 마주한 기술적 고민(Problem), 이를 해결하기 위한 아키텍처 선택(Trade-off), 그리고 배운 점(Takeaway)**을 공유하고자 합니다.

---

## 1. Problem: Vanity 지표의 함정과 GeoIP의 한계

초기 어드민 분석 기능을 기획할 때, 화려하고 상세한 실시간 지표들을 수집하려는 요구사항이 있었습니다. 접속 지도 시각화, 실시간 상세 세션 목록, ISP/통신망 조회 등이 대표적이었습니다. 

하지만 인프라 제약(무료 티어 DB)을 고려했을 때, 이러한 'Vanity 지표(보여주기식 지표)'는 심각한 문제를 야기할 수 있었습니다.
1. **리소스 낭비 및 커넥션 고갈**: 불필요하게 많은 쿼리와 대역폭을 소모하여 제한된 DB 자원을 고갈시킵니다.
2. **GeoIP의 오조회 문제 (핵심 비즈니스 특성)**: PickSafe의 주 사용자는 **방한 외국인 관광객**입니다. 이들이 한국 현지에서 USIM을 교체하거나 로밍을 이용할 때 IP를 기반으로 국가를 판별(GeoIP)하면, 대부분 한국(`KR`)으로 오조회되어 실제 국적 분석 데이터로서의 변별력이 완전히 상실됩니다.

실질적인 비즈니스 의사결정(다국어 확장, 온보딩 UX 개선 등)에 도움도 되지 않으면서 시스템에 과부하만 주는 구조를 과감히 들어내야 했습니다.

## 2. Trade-off & Architecture: 무엇을 버리고 무엇을 취할 것인가

우리는 분석의 범위를 철저히 '실질적인 운영 지표'로 한정하고, 가볍고 정확한 데이터 수집 파이프라인을 설계했습니다.

### ① 3대 핵심 운영 지표로 범위 축소
무의미한 실시간 로그를 버리고, 서비스 개선과 직결되는 다음 3가지 지표에만 집중하기로 했습니다.
* **언어 분포**: 다국어 지원 우선순위 검증용
* **온보딩 완료율 vs 건너뛰기율**: 기피 성분 설정 온보딩 장벽 난이도 검증용
* **게스트 ➔ 회원 전환율**: 비회원 장벽 완화 배너 효과 검증용

### ② IP 기반 GeoIP 탈피: HTTP 헤더 신뢰 전략
IP 기반 위치 추적 대신, 브라우저가 전송하는 표준 HTTP 헤더를 활용했습니다.
* **언어권 식별**: 맥스민드(MaxMind) 같은 무거운 GeoIP 라이브러리 대신, `Accept-Language` 헤더의 최우선 로케일 값을 파싱하여 실제 기기 언어권을 정확히 타겟팅했습니다. (관광객이 한국 유심을 써도 기기 언어 설정은 외국어로 유지되므로 정확한 분석이 가능합니다.)
* **기기/OS 스펙 분석**: `User-Agent` 헤더를 자체 RegEx 파서로 가볍게 파싱하여 기기 유형(`Mobile`/`Tablet`/`Desktop`)과 OS 정보를 추출합니다.
* **개인정보 보호**: IP 주소 등 민감한 개인 식별 정보를 원천적으로 저장하지 않아 데이터 보안 리스크를 최소화했습니다.

### ③ 이벤트 분할 기록(Append-only)과 배치 집계 구조 (`analytics_events` ➔ `daily_analytics_summary`)
대시보드를 열 때마다 `COUNT`나 `GROUP BY` 같은 무거운 집계 연산이 실시간으로 돌게 두면 DB가 버티지 못합니다. 이를 해결하기 위해 **CQRS 패턴의 사상**을 일부 차용했습니다.

```[Client Request] 
       │
       ▼ (가벼운 단건 인서트)
[analytics_events 테이블 (Raw Log)]
       │
       │ (하루 1회 Cron /admin/analytics/aggregate)
       ▼
[daily_analytics_summary 테이블 (Aggregated)]
       │
       ▼ (부하 0에 가까운 조회)
[Admin Dashboard]
```

1. **Write 최적화 (`analytics_events`)**: 사용자 요청 시점에는 이벤트를 가볍게 단건 인서트(`INSERT`)만 수행합니다.
2. **Batch 요약**: 외부 스케줄러(cron-job.org 등)를 통해 하루 1회 `/admin/analytics/aggregate` 엔드포인트를 호출, 전날의 원본 로그를 일괄 집계하여 `daily_analytics_summary` 테이블에 요약본으로 적재합니다.
3. **Read 최적화**: 어드민 대시보드는 이 요약 테이블만을 조회하므로, 실시간 집계로 인한 DB 과부하를 원천 차단했습니다.

## 3. Takeaway: 제약은 최고의 아키텍트다

이번 기능을 구현하며 얻은 엔지니어링 교훈은 명확합니다.

* **비즈니스 도메인 이해가 곧 최고의 기술적 선택이다**: "외국인이 한국 유심을 쓴다"는 도메인 특성을 간과하고 일반적인 GeoIP 방식을 고집했다면, 쓸모없는 오답 데이터를 수집하느라 비용을 낭비했을 것입니다. 기술 도입 전에 도메인의 본질을 먼저 파악해야 합니다.
* **실시간성이 항상 답은 아니다**: 어드민 대시보드 특성상 1초 단위의 실시간성장애 지표가 아니라면, 배치 기반의 요약 테이블(Summary Table) 구조가 인프라 비용과 확장성 면에서 압도적으로 유리합니다. 
* **무료 티어 인프라에서의 최적화 습관**: 리소스가 제한된 환경일수록 쿼리 대역폭과 커넥션을 아끼는 아키텍처적 고민(Write와 Read의 분리, 불필요한 데이터 수집 지양)을 깊게 하게 되며, 이는 서비스가 성장했을 때도 튼튼한 뼈대가 됩니다.

앞으로도 PickSafe는 화려한 기술보다 '실질적으로 비즈니스에 기여하고 지속 가능한 아키텍처'를 만들어 나가는 과정을 공유하겠습니다. 읽어주셔서 감사합니다!
