안녕하세요, PickSafe 팀의 시니어 개발자입니다. 

서비스가 성장함에 따라 비즈니스 지표를 모니터링하기 위한 어드민 대시보드 구축은 필수적인 단계입니다. 하지만 "있으면 다 좋아 보이는" 화려한 지표들을 무작정 수집하다 보면, 리소스 낭비는 물론 인프라 비용 증가와 성능 저하라는 부메랑을 맞기 쉽습니다.

이번 글에서는 **무료 티어 인프라 환경에서 한정된 리소스를 극대화**하고, **방한 외국인이라는 서비스 타겟 특성에 맞게 어드민 방문자 분석 및 기기 사양 트래킹 시스템을 설계한 과정**을 공유하고자 합니다.

---

## 1. Problem: 화려한 지표의 함정과 "한국("KR")"으로 도배되는 GeoIP

초기 어드민 분석 기능 요구사항을 정의할 때, 일반적인 웹 서비스들이 도입하는 기능들이 대거 물망에 올랐습니다. 
* 상세 접속 지도 실시간 시각화
* 실시간 상세 세션 목록 추적
* ISP 및 접속 통신망 조회
* IP 기반 국가 판별(GeoIP)

하지만 우리 서비스에는 치명적인 **두 가지 문제점**이 있었습니다.

1. **무료 티어 인프라 리소스 낭비**: 상세 세션 추적이나 실시간 집계 쿼리는 DB 커넥션과 쿼리 대역폭을 과도하게 소모합니다. 트래픽이 많지 않은 초기 단계에서 과도한 텔레메트리(Telemetry) 구축은 오버엔지니어링입니다.
2. **GeoIP의 실효성 상실**: 우리 서비스의 주 사용자는 **"방한 외국인 관광객"**입니다. 이들은 한국 현지에서 USIM을 교체하거나 로밍을 사용하기 때문에, IP 기반으로 국가를 판별하면 **대부분 "KR"로 오조회**되었습니다. 실질적인 국적 및 언어권 분석 데이터로서의 변별력이 완전히 상실되는 셈입니다.

> **"무엇을 수집할 것인가"보다 "무엇을 버릴 것인가"가 더 중요한 순간이었습니다."**

## 2. Trade-off & Architecture: 비용은 낮추고 정확도는 높이는 설계

우리는 시스템 부하를 최소화하면서도, 다국어 확장과 UX 최적화에 직결되는 핵심 지표만 남기기로 결정했습니다.

### ① 3대 핵심 운영 지표로 범위 축소
무의미한 실시간 분석을 배제하고, 서비스 성장에 직접적인 피드백을 주는 지표만 엄선했습니다.
* **언어 분포**: 다국어 번역 우선순위 검증용
* **온보딩 완료율 vs 건너뛰기율**: 기능 진입 장벽(콜드스타트) 난이도 검증용
* **게스트 ➔ 회원 전환율**: 비회원 장벽 완화 배너의 효과 검증용

### ② IP GeoIP 대신 Header 파싱 전략 선택
* **언어권 식별**: MaxMind 같은 무거운 GeoIP 라이브러리 도입을 포기했습니다. 대신, 브라우저가 전송하는 표준 HTTP 헤더인 `Accept-Language`의 최우선 로케일 값을 신뢰하여 실제 기기의 언어 설정을 파악합니다. (로밍망 환경에서도 사용자의 원본 언어 설정을 정확히 잡아낼 수 있습니다.)
* **기기/OS 통계**: `User-Agent` 헤더를 가벼운 정규식(RegEx)으로 파싱하여 기기 유형(`Mobile` / `Tablet` / `Desktop` / `Unknown`)과 OS(`iOS` / `Android` / `Windows` 등)를 추출합니다.
* **개인정보 보호**: IP 주소 등 개인 식별 위험이 있는 민감 정보는 애초에 저장하지 않아 보안 리스크를 원천 차단했습니다.

### ③ 이벤트 로그 ➔ 배치 집계 요약 파이프라인 구축 (`analytics_events` ➔ `daily_analytics_summary`)
사용자가 요청을 보낼 때마다 DB에서 `COUNT`, `GROUP BY` 등 무거운 집계 연산이 돌면 대시보드가 느려지는 것은 자명합니다. 이를 해결하기 위해 두 단계의 저장 구조를 설계했습니다.

1. **Raw Log 적재 (`analytics_events`)**: 사용자 요청 시 이벤트를 가볍게 단순 인서트(Insert)만 수행하는 로그 테이블을 둡니다. (동기/비동기 처리로 응답 지연 방지)
2. **배치 집계 (`daily_analytics_summary`)**: `cron-job.org`와 연동된 일 1회 트리거 엔드포인트(`.admin/analytics/aggregate`)를 통해 전날의 원본 로그를 일괄 집계하여 요약 테이블에 적재합니다.
3. **어드민 조회 최적화**: 어드민 대시보드는 무거운 원본 테이블이 아니라, 이미 계산된 요약 테이블만 조회하므로 DB 과부하를 0에 가깝게 통제했습니다.

## 3. Takeaway: 엔지니어링 교훈

이번 아키텍처 결정을 통해 다음과 같은 엔지니어적 성과와 깨달음을 얻었습니다.

* **비즈니스 도메인 특성에 대한 깊은 이해의 중요성**: 기술적으로 화려한 GeoIP가 비즈니스 특성(방한 외국인)과 만나면 무용지물이 될 수 있음을 확인했습니다. 기술 도입 전 도메인 환경을 먼저 분석하는 것이 최우선입니다.
* **CQRS 패턴의 가벼운 적용**: 복잡한 대규모 프레임워크 없이도, '쓰기 전용 로그 테이블'과 '읽기 전용 요약 테이블'을 분리하고 일일 배치(Batch)를 태우는 것만으로도 소규모 서비스에서 대시보드 성능을 극적으로 끌어올릴 수 있음을 증명했습니다.
* **오버엔지니어링 경계**: 무료 티어 인프라 환경에서도 합리적인 아키텍처 트레이드오프를 거치면 충분히 확장 가능하고 안정적인 시스템을 구축할 수 있습니다.

데이터는 많을수록 좋다는 미신에서 벗어나, **"우리에게 꼭 필요한 데이터가 무엇인가"**를 정의하는 것부터가 진짜 엔지니어링의 시작입니다.
