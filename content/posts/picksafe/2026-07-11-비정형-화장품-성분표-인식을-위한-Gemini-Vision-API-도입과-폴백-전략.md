화장품 성분 분석 서비스인 PickSafe를 개발하며 가장 먼저 해결해야 했던 과제는 '사용자가 촬영한 성분표 이미지를 얼마나 정확하고 안정적으로 텍스트화할 것인가'였습니다. 

제품 용기나 상자 뒷면에 인쇄된 성분표는 촬영 각도, 빛 반사, 굴곡진 표면, 그리고 한국어와 영어가 섞인 복잡한 레이아웃 등으로 인해 일반적인 텍스트 추출 방식으로는 정교한 결과를 얻기 어렵습니다. 초기 설계 과정에서 마주했던 기술적 병목과 이를 극복하기 위해 Gemini Vision API 및 디버그 폴백 시스템을 구축한 과정을 기록으로 남깁니다.

## 🎯 마주한 고민과 문제 배경

화장품 성분표 데이터는 일반적인 서적이나 문서의 텍스트와 다른 몇 가지 독특한 특징을 가집니다.

1. **비정형 다국어 믹스**: 표기 원칙에 따라 국문 성분명과 영문 표기(INCI), 식물학적 명칭(라틴어)이 줄바꿈과 쉼표(,), 슬래시(/), 괄호 등과 뒤섞여 있습니다.
2. **복잡한 폰트 및 용기 굴곡**: 화장품 용기 특성상 텍스트가 곡면에 인쇄되어 있거나, 작은 폰트 크기로 인해 픽셀 대비 명암비가 낮을 때가 많습니다.
3. **단어 경계 및 문맥 파악의 한계**: 오픈소스 전통 OCR 엔진(Tesseract 등)을 테스트해보았으나, 성분 간 구분자(쉼표 등)를 오인하거나 글자가 일부 뭉개졌을 때 해당 화학물질명을 올바르게 추론하지 못하는 한계가 명확했습니다.

초기 서비스 검증 단계(MVP)에서는 고비용의 상용 OCR 서비스를 무턱대고 도입하기보다, **무료 사용량이 제공되면서도 인프라 비용 부담이 적고 비정형 문맥 복원 능력이 뛰어난 엔진**을 찾는 것이 급선무였습니다. 또한, API 키가 없거나 외부 요청 한도(Rate Limit)에 도달했을 때 전체 애플리케이션 서비스가 멈추지 않는 구조적 안전장치도 함께 고민해야 했습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

성분표 디지털화를 위해 아래 세 가지 접근 방식을 검토했습니다.

| 비교 항목 | 오픈소스 OCR (Tesseract 등) | 클라우드 전용 OCR (GCP/AWS) | LLM 기반 Vision API (Gemini) |
| :--- | :--- | :--- | :--- |
| **문맥 복원력** | 낮음 (단순 이미지-텍스트 맵핑) | 보통 (영역 인식 위주) | **매우 높음** (불완전 텍스트 추론 가능) |
| **비정형 데이터 구조화**| 별도의 복잡한 후처리 로직 필수 | 별도의 텍스트 파싱 로직 필수 | **프롬프트 기반 단일 처리 가능** |
| **초기 도입 비용** | 무료 (자체 서버 연산 비용) | 호출당 과금 (초기 비용 발생) | **무료 티어 활용 가능** |
| **처리 속도 및 지연시간**| 매우 빠름 (로컬 연산) | 빠름 | 보통 (대형 모델 인퍼런스 지연) |

### 최종 선택 이유

비정형 성분표 처리의 핵심은 단순히 글자를 읽는 것(OCR)을 넘어 **'읽어낸 문자가 화장품 성분 단어인가'를 문맥적으로 파악하는 것**이었습니다. 

Gemini Vision API는 거대 언어 모델 기반으로 동작하기 때문에, 오탈자나 일부 훼손된 문자열이 들어오더라도 성분표라는 문맥 안에서 올바른 단어로 복원해내는 능력이 기존 OCR 대비 월등히 우수했습니다. 또한 초기 개발 단계에서 제공되는 무료 티어 범위를 활용하면 인프라 비용을 대폭 절감할 수 있다는 현실적인 이점도 크게 작용했습니다.

## 🏗️ 시스템 아키텍처 및 흐름

외부 Vision API 의존성을 줄이고, API 키 부재 및 요청 실패 상황에서도 전체 시스템이 안정적으로 동작할 수 있도록 OCR 서비스 레이어를 추상화했습니다.

```mermaid
graph TD
    subgraph Client ["클라이언트 영역"]
        A["성분표 이미지 업로드"]
    End

    subgraph Backend ["백엔드 라우터 레이어"]
        B["이미지 스캔 엔드포인트"]
    End

    subgraph OCR_Layer ["OCR 서비스 추상화 레이어 (ocr_service.py)"]
        C{"API Key 설정 및<br/>상태 검증"}
        D["Gemini Vision API 호출"]
        E["Mock 디버그 데이터<br/>폴백 로직"]
        F{"외부 API 요청 성공?"}
    End

    subgraph Response ["응답 수집"]
        G["성분 텍스트 구조화 반환"]
    End

    A --> B
    B --> C
    C -- "유효한 API Key 존재" --> D
    C -- "API Key 미설정 / 한도 초과" --> E
    D --> F
    F -- "성공" --> G
    F -- "오류 / Rate Limit" --> E
    E --> G
```

이 구조에서는 핵심 서비스 로직이 특정 외부 API 구현체에 직접 의존하지 않습니다. API 키가 없거나 외부 서비스 연결에 실패하더라도 Mock 데이터 폴백 경로로 전환되어 전체 앱 런타임이 중단되는 상황을 방지합니다.

### 1. 외부 서비스 추상화 및 런타임 폴백 설계

### 2. 트러블슈팅: Vision 모델의 높은 지연시간(Latency)과 응답 유연성

LLM 기반 Vision API는 일반 OCR 엔진에 비해 응답 지연시간이 길다는 단점이 있었습니다. 

* **문제**: 이미지 전송 후 텍스트 파싱까지 걸리는 시간이 길어져 사용자 경험이 저하됨.
* **해결 방안**:
  1. **이미지 리사이징 최적화**: 성분표의 텍스트 식별이 불가능해지지 않는 선에서 이미지 가로/세로 해상도를 제한하여 업로드 페이로드 크기를 줄였습니다.
  2. **프롬프트 응답 구조 단축**: 비전 모델이 긴 부연설명을 붙이지 않고 오직 구분자로 분리된 성분 단어 목록만 즉시 출력하도록 프롬프트를 최소화하여 토큰 생성 지연시간을 단축시켰습니다.

## 💡 돌아보며 배운 점 (회고)

### 얻은 성과

1. **인식 정확도 개선**: 복잡하고 굴곡진 화장품 성분표 이미지에서도 오탈자를 문맥적으로 교정하며 성분명을 높은 수준으로 추출해낼 수 있었습니다.
2. **개발 환경의 안정성 확보**: API 키가 없는 로컬 개발 환경에서도 Mock 폴백 로직 덕분에 백엔드 및 프론트엔드 연동 테스팅을 멈춤 없이 진행할 수 있었습니다.
3. **비용 효율성**: 무료 티어 제한 범위 내에서 백엔드 파이프라인의 핵심 검증을 안정적으로 진행할 수 있었습니다.

### 추후 보완이 필요한 점

* **성분 데이터 정규화 DB와의 매칭**: Vision API가 텍스트를 정밀하게 추출하더라도 식약처 및 표준 성분 DB에 등록된 명칭과 일치하지 않는 예외 표기들이 존재합니다. 추후 추출된 텍스트와 표준 성분 데이터베이스 간의 퍼지 문자열 매칭(Fuzzy Matching) 알고리즘을 강화할 예정입니다.
* **하이브리드 OCR 검토**: 향후 트래픽이 증가하거나 외부 API의 Rate Limit 제한이 엄격해질 경우, 1차적으로 가벼운 로컬 OCR을 거치고 인식률이 낮은 이미지에 한해서만 Vision API를 호출하는 2단계(Two-Tier) Fallback 아키텍처로 개선해볼 수 있을 것입니다.

단순히 화려한 최신 AI 기술을 도입하는 것보다, **상황에 맞는 기술적 장단점을 비교하고 서비스가 멈추지 않는 안전장치를 만드는 것**이 백엔드 설계에서 얼마나 중요한지 다시금 배울 수 있는 작업이었습니다.
