복잡한 화장품 성분표 앞에서 망설여본 적이 있으신가요? 민감성 피부나 특정 알레르기를 가진 사람들에게 성분 확인은 단순한 선택이 아닌 **안전의 문제**입니다. 

**PickSafe(픽세이프)** 프로젝트는 "모바일 카메라로 성분표를 찍는 즉시, 식약처 지정 26대 알레르기 유발 성분과 개인 기피 성분을 1초 만에 감지한다"는 명확한 제품 비전에서 시작되었습니다. 

제품의 핵심 가치가 **'모바일 환경에서의 초고속 응답'**에 있는 만큼, 초기 기술 스택과 아키텍처 선정은 전체 프로젝트의 성패를 가르는 중요한 의사결정이었습니다. 이번 포스팅에서는 PickSafe 백엔드 및 프론트엔드 초기 아키텍처를 설계하며 고민했던 **기술적 문제, 대안과의 Trade-off, 그리고 얻은 엔지니어링 교훈**을 공유합니다.

---

## 1. 문제 정의 (Problem Definition)

초기 아키텍처 설계 시 우리가 해결해야 했던 핵심 도전 과제는 다음 두 가지였습니다.

1. **I/O 병목 및 빠른 데이터 처리**
   * 성분 스캔 서비스 특성상 향후 OCR 이미지 분석, 외부 API 연동, 데이터베이스 조회 등 **I/O 바운드 작업**이 중점적으로 발생합니다.
   * 모바일 현장에서 사용자에게 **1초 이내의 빠른 판별 결과**를 전달할 수 있는 비동기 처리 기반이 필요했습니다.

2. **모바일 웹 진입 속도(FCP) 극대화 및 MVP 빠른 구현**
   * 사용자들은 오프라인 매장에서 빠르게 앱/웹을 열어 성분을 확인하고자 합니다.
   * 무거운 SPA(Single Page Application) 프레임워크의 대용량 자바스크립트 번들 다운로드로 인한 **첫 화면 도달 시간(FCP, First Contentful Paint) 지연을 최소화**해야 했습니다.

## 2. 핵심 기술적 고민과 Trade-off 분석

### ① 백엔드 프레임워크: Django vs Flask vs FastAPI

백엔드 파이썬 프레임워크 선정 과정에서 3가지 대안을 두고 비교했습니다.

| 항목 | Django | Flask | **FastAPI (선택)** |
| :--- | :--- | :--- | :--- |
| **비동기(Async) 지원** | 부분 지원 (ASGI 도입 중) | 동기 중심 (WSGI) | **완벽 지원 (ASGI 내장)** |
| **데이터 유효성 검증** | DRF 별도 설치 필요 | 추가 라이브러리 필요 | **Pydantic 내장 (타입 안정성)** |
| **API 문서화** | Swagger 연동 작업 필요 | 플러그인 필요 | **Auto OpenAPI (Swagger) 제공** |
| **오버헤드** | 거대함 (Monolithic) | 경량이나 확장 시 번거로움 | **경량 + high performance** |

* **선택: FastAPI + Python 3.11**
  FastAPI는 Python의 `async/await` 구문을 완벽히 활용하여 I/O 바운드 작업에서 최상의 응답 속도를 보장합니다. 또한 **Pydantic을 통한 데이터 유효성 검증**이 프레임워크 수준에서 강제되므로, 런타임 시 잘못된 타입으로 인한 버그를 원천 차단할 수 있었습니다. Auto OpenAPI 기능은 프론트엔드와의 협업 효율성을 극대화해 주었습니다.

---

### ② 프론트엔드 아키텍처: React/Vue SPA vs Jinja2 + Vanilla JS

서비스 초기에 흔히 채택하는 React/Vue 기반 SPA 구조와 전통적인 템플릿 렌더링 방식을 비교 검토했습니다.

* **React/Vue (SPA) 방식**:
  * *장점*: 풍부한 라이브러리 생태계, 컴포넌트 재사용성.
  * *단점*: Webpack/Vite 등 빌드 환경 구성 복잡도 증가, 초기에 거대한 JS 번들을 로딩해야 하므로 **모바일 FCP 단축에 불리**.

* **Jinja2 SSR + Vanilla JS 방식 (선택)**:
  * *장점*: 별도의 프론트엔드 빌드 오버헤드가 없음. 서버 측에서 핵심 뼈대를 렌더링하여 **첫 로딩 속도를 0.5초 이내로 극대화**.
  * *단점*: 복잡한 UI 상태 관리의 어려움.
  * *의사결정 이유*: PickSafe의 초기 MVP는 성분 스캔 및 결과 표시라는 **직관적이고 단순한 UI 흐름**을 가집니다. 따라서 과도한 프론트엔드 엔지니어링 낭비를 줄이고, 모바일 사용자 경험(초고속 로딩)에 직결되는 **경량 Jinja2 SSR + Vanilla JS** 조합을 최종 결정했습니다.

## 3. 최종 시스템 아키텍처

기술 스택 결정 후 확정된 PickSafe의 계층 구조는 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 계층 (Mobile-First Web / PWA)                     │
│ - HTML5 + Vanilla JS + CSS (경량 모바일 최적화 UI)          │
│ - Jinja2 서버사이드 템플릿 렌더링 (FCP < 0.5s 목표)          │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - Async (ASGI) 라우팅 기반 초고속 I/O 처리                  │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM (Async)
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL / SQLite)                      │
│ - 사용자, 스캔 이력, 성분 마스터, 찜 상품 관리              │
└─────────────────────────────────────────────────────────────┘
```

백엔드 코드베이스의 유지보수성을 위해 디렉토리 구조를 역할별로 명확히 분리했습니다:
* `web/backend/app/`: 라우터, DB 모델, 비즈니스 서비스 로직의 철저한 분리 (Clean Architecture 지향)
* `web/frontend/`: static 자산과 Jinja2 템플릿의 일관된 관리
* `bin/`: 데이터 마이그레이션 및 데이터 시딩(Seeding) 자동화 스크립트 전용 영역

## 4. 엔지니어링 교훈 (Takeaways)

1. **기술 선택의 기준은 언제나 '비즈니스 목표'여야 한다.**
   트렌디한 React/Vue SPA를 무조건 도입하기보다, "모바일에서 1초 만에 안전성을 보여준다"는 제품 목표에 맞춰 Jinja2 SSR과 Vanilla JS를 선택함으로써 **초기 개발 속도 향상과 FCP 최적화**라는 두 마리 토끼를 잡을 수 있었습니다.

2. **초기 스캐폴딩 시 데이터 검증 체계를 잡는 것이 중요하다.**
   FastAPI와 Pydantic을 전면에 내세워 API 입출력 데이터 규격을 엄격하게 정의한 덕분에, 이후 기능 확장 시 발생할 수 있는 데이터 타입 관련 예외를 사전에 방지할 수 있는 탄탄한 기반을 마련했습니다.

3. **확장성을 고려한 레이어 분리**
   서비스 계층(`services`)과 라우터 계층(`routers`)을 명확히 분리해 둠으로써, 향후 OCR 파이프라인 고도화나 대용량 성분 DB 검색 엔진(Elasticsearch 등) 도입 시에도 기존 코드를 크게 수정하지 않고 유연하게 확장할 수 있는 구조를 구축했습니다.
