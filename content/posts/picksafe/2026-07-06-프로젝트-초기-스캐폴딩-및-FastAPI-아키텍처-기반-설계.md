안녕하세요, 시니어 에디터입니다. 오늘은 화장품 성분 분석 및 알레르기 판별 서비스인 **PickSafe(픽세이프)**의 초기 프로젝트 스캐폴딩 과정에서 내린 핵심 아키텍처 의사결정 과정을 공유하려 합니다.

PickSafe는 사용자가 스마트폰 카메라로 화장품 전성분표를 촬영(OCR)하면, 1초 안에 26대 공인 알레르기 유발 성분 및 개인 기피 성분을 감지해 안전성을 판별해 주는 모바일 중심 서비스입니다. 

초기 설계 단계에서 **"어떤 기술 스택을 선택해야 모바일 환경에서 가장 빠르고 확장성 있는 서비스를 만들 수 있을까?"**라는 고민을 해결하기 위해 마주한 기술적 문제와 트레이드오프, 그리고 최종 아키텍처를 소개합니다.

---

## 1. Problem: 모바일 환경과 I/O 바운드 작업의 한계

PickSafe 서비스의 핵심 유저 시나리오는 다음과 같습니다.
1. 사용자가 모바일 웹으로 접속해 성분표를 촬영하거나 업로드합니다.
2. 서버는 이미지를 받아 OCR 처리 및 외부 데이터 연동을 수행합니다.
3. 결과를 즉시(1초 이내) 유저에게 보여주어야 합니다.

이 시나리오에서 마주한 기술적 제약은 명확했습니다.
* **I/O 바운드 작업의 비중**: OCR 이미지 분석, 외부 API 호출, DB 조회 등 네트워크 및 디스크 I/O가 빈번하게 발생합니다.
* **모바일 네트워크 환경**: 사용자는 언제나 완벽한 Wi-Fi 환경에 있지 않습니다. 첫 로딩 속도(FCP, First Contentful Paint)가 느리면 이탈률이 급격히 증가합니다.
* **빠른 개발 및 안정성**: 스타트업 초기 단계이므로 비즈니스 로직 검증이 빠르되, 타입 안정성과 런타임 오류 방지가 필수적이었습니다.

---

## 2. Trade-off & Architecture: 왜 FastAPI와 Jinja2인가?

현대 웹 개발에서 React, Vue 등 SPA(Single Page Application)를 채택하는 것은 흔한 선택입니다. 하지만 PickSafe의 초기 스캐폴딩에서는 **과감히 무거운 SPA 프레임워크를 배제**하고, **FastAPI + Jinja2 + Vanilla JavaScript** 조합을 선택했습니다. 그 이유는 다음과 같습니다.

### ① 백엔드: Django나 Flask 대신 `FastAPI`를 선택한 이유
* **비동기(ASGI) 네이티브 지원**: OCR 분석 및 외부 연동 같은 I/O 바운드 작업에서 동기식 프레임워크보다 훨씬 효율적인 자원 사용과 응답 속도를 제공합니다.
* **Pydantic을 통한 선언적 스키마 검증**: 런타임에 발생할 수 있는 데이터 타입 에러를 사전에 차단하고, API 문서(Swagger)가 자동 생성되어 개발 생산성을 극대화합니다.

### ② 프론트엔드: React/Vue 대신 `Jinja2 + Vanilla JS`를 선택한 이유 (Trade-off)
* **장점 (Performance)**: Node.js 기반의 복잡한 빌드 체인(Webpack, Vite 등)과 대규모 자바스크립트 번들 파일을 완전히 제거했습니다. 모바일 브라우저가 파싱하고 실행해야 할 JS 풋프린트가 줄어들어, **첫 로딩 속도(FCP)를 0.5초 이내**로 단축할 수 있었습니다.
* **트레이드오프 (UX)**: 클라이언트 사이드 루팅이 없기 때문에 페이지 전환 시 전통적인 새로고침 방식이 발생합니다. 하지만 PickSafe의 핵심은 '초고속 성분 판별'이라는 단일 목적의 직관적인 유저 플로우이므로, 모바일 웹/PWA 환경에서는 오히려 가벼운 서버사이드 렌더링이 더 큰 이점을 가져다준다고 판단했습니다.

## 3. Architecture Overview

최종 확정된 PickSafe의 백엔드 및 데이터 구조는 다음과 같이 계층화되었습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS + CSS (모바일 최적화 UI)               │
│ - Jinja2 서버사이드 템플릿 렌더링                           │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - 비동기(ASGI) 라우팅 및 고성능 JSON 직렬화                 │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL / SQLite 로컬)                 │
│ - 사용자 계정, 스캔 이력, 성분 마스터, 찜 상품 스키마      │
└─────────────────────────────────────────────────────────────┘
```

디렉토리 구조 역시 비즈니스 로직(`routers`, `services`, `models`)과 프론트엔드 자산(`templates`, `static`), 그리고 데이터 시딩 스크립트(`bin`)를 명확히 분리하여 향후 OCR 엔진 고도화나 대용량 성분 DB 적재 시에도 확장성을 잃지 않도록 설계했습니다.

---

## 4. Takeaway: 엔지니어링 교훈

1. **"모든 곳에 SPA가 정답은 아니다"**: 서비스의 타겟 환경(모바일 중심)과 핵심 가치(1초 만에 결과 도달)를 고려했을 때, 불필요한 추상화 레이어를 걷어내는 것이 성능과 개발 속도 모두를 잡는 키가 되었습니다.
2. **견고한 기반(Scaffolding)의 중요성**: 프로젝트 초기 단계에서 FastAPI의 Pydantic과 SQLAlchemy 2.0을 조합해 타입 안전성을 확보한 덕분에, 이후 비즈니스 로직이 복잡해지더라도 레거시 부채 없이 빠른 기능 개발이 가능해졌습니다.

PickSafe는 이번 아키텍처 설계를 바탕으로 안전하고 빠른 화장품 성분 분석 플랫폼으로 도약할 준비를 마쳤습니다. 앞으로 이어질 OCR 최적화 및 성능 개선 이야기도 기대해 주세요!
