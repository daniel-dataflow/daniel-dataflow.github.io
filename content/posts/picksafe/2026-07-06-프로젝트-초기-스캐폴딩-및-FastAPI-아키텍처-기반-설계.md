안녕하세요, **PickSafe(픽세이프)** 백엔드 개발을 맡고 있는 Daniel & Antigravity입니다. 

화장품 성분 정보의 복잡함 속에서 소비자가 1초 만에 안전성을 판별할 수 있도록 돕는 서비스, **PickSafe**의 첫 스캐폴딩(Scaffolding) 과정을 기술 블로그를 통해 공유하려 합니다. 

이번 포스팅에서는 프로젝트 초기 단계에서 마주한 **"모바일 환경에서 어떻게 하면 극한의 반응 속도와 가벼운 아키텍처를 가져갈 것인가?"**에 대한 고민과 기술적 의사결정(Trade-off) 과정을 다룹니다.

---

## 1. Problem: 무엇을 해결하고자 했는가?

PickSafe의 핵심 유저는 **스마트폰 카메라로 화장품 성분표를 촬영하고, 즉시(1초 이내) 알레르기 유발 성분이나 기피 성분을 검출**해야 합니다. 

이 유스케이스는 다음과 같은 기술적 제약을 동반합니다.
1. **I/O Bound 작업의 비중 높음**: OCR 이미지 분석, 외부 API 통신, 데이터베이스 조회가 빈번하게 발생합니다.
2. **모바일 네트워크 환경**: 사용자는 이동 중이거나 네트워크가 불안정한 환경에서 접속할 확률이 높습니다. 따라서 초기 로딩 속도(FCP, First Contentful Paint)가 서비스 이탈률을 결정합니다.
3. **엄격한 데이터 무결성**: 성분 정보는 사용자 건강(알레르기)과 직결되므로, 잘못된 데이터 입력이나 타입 에러가 런타임에 발생하면 치명적입니다.

---

## 2. Trade-off & Architecture: 기술 스택 선정의 고민

초기 스캐폴딩 단계에서 프레임워크와 렌더링 방식을 결정하기 위해 몇 가지 대안을 비교했습니다.

### 2.1. 백엔드: 왜 FastAPI를 선택했는가?
* **대안 A: Django / Django REST Framework (DRF)**
  * *장점*: 강력한 오르엠(ORM), 인증, 어드민 등 풀스택 배터리가 제공되어 빠른 초기 구축 가능.
  * *단점*: 무거움. 비동기 처리(ASGI) 지원이 추가되었으나, 구조적 한계로 인해 순수 비동기 I/O 성능 측면에서 FastAPI에 비해 오버헤드가 큼.
* **대안 B: Node.js (Express / NestJS)**
  * *장점*: 자바스크립트 단일 언어 사용, 뛰어난 비동기 처리 성능.
  * *단점*: 머신러닝/OCR 파이프라인이나 파이썬 기반 데이터 가공 스크립트와의 통합 측면에서 향후 확장성이 떨어짐.
* **최종 선택: FastAPI (Python 3.11)**
  * **초고속 비동기(ASGI) 성능**: OCR 및 외부 연동 등 I/O 바운드 작업에서 우수한 성능 발휘.
  * **Pydantic 기반 엄격한 스키마 검증**: 런타임 에러를 사전에 차단하고 문서화(Swagger) 자동화 이점 확보.

### 2.2. 프론트엔드: SPA(React/Vue) 대신 Jinja2를 택한 이유
현대 웹 개발에서 SPA는 표준처럼 여겨지지만, PickSafe 초기 버전에는 과도한 엔지니어링(Over-engineering)이 될 수 있다고 판단했습니다.

* **문제점**: React/Vue 등 대형 프레임워크를 도입할 경우, 빌드 번들 크기로 인한 모바일 초기 로딩 지연, Webpack/Vite 등 복잡한 프론트엔드 빌드 파이프라인 유지보수 비용 발생.
* **해결책 (Jinja2 + Vanilla JS)**:
  * 서버사이드 렌더링(SSR)을 통해 브라우저가 무거운 JS 런타임을 다운로드하고 실행하는 시간을 제거.
  * **첫 로딩 속도(FCP) 0.5초 이내 단축**을 목표로, Tailwind 없는 경량 모바일 뷰와 Jinja2 템플릿 엔진을 결합하여 가볍고 빠른 모바일 웹 경험 설계.

## 3. System Design: 전체 아키텍처 구조

최종 확정된 PickSafe의 백엔드 및 데이터 구조 스케치는 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS (경량 모바일 뷰)                       │
│ - Jinja2 서버사이드 템플릿 렌더링                           │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - 비동기(ASGI) 라우팅 및 빠른 JSON 직렬화                   │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL / SQLite 로컬)                 │
│ - 사용자 계정, 스캔 이력, 성분 마스터, 찜 상품 스키마      │
└─────────────────────────────────────────────────────────────┘
```

디렉토리 구조 역시 비즈니스 로직과 프론트엔드 에셋, 배치 스크립트를 명확히 분리하여 향후 확장성에 대비했습니다.
* `web/backend/app/`: 라우터, 모델, 서비스 레이어, 데이터베이스 연결 관리
* `web/frontend/`: 템플릿 및 정적 자산(JS/CSS/Images)
* `bin/`: 마스터 데이터 시딩 및 CLI 배치 스크립트

---

## 4. Takeaway: 엔지니어링 교훈

1. **목적에 맞는 기술 선택 (Right Tool for the Job)**:
   모바일 환경에서 유저가 느끼는 '즉각적인 반응'이 최우선 과제였기에, 복잡한 SPA 번들링 구조를 과감히 배제하고 FastAPI + Jinja2 조합으로 **속도와 단순함** 모두를 잡았습니다.
2. **레이어드 아키텍처 기반 확장성 확보**:
   초기 스캐폴딩 단계에서 라우터(Router)와 서비스(Service) 계층을 명확히 분리해 둔 덕분에, 향후 OCR 엔진 고도화나 대용량 성분 DB 적재 같은 복잡한 비즈니스 로직이 추가되더라도 코드베이스의 응집도를 유지할 수 있는 기반이 마련되었습니다.
