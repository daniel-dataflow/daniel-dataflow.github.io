안녕하세요, 시니어 백엔드 에디터입니다. 
오늘은 화장품 성분 알레르기 및 유해 성분 판별 서비스인 **PickSafe(픽세이프)** 프로젝트의 초기 스캐폴딩과 백엔드 아키텍처 설계 과정을 공유하려 합니다. 

새로운 프로덕트를 제로베이스에서 기획할 때, 개발자로서 가장 먼저 마주하는 고민은 **"어떤 기술 스택을 선택할 것인가"**입니다. 특히 모바일 환경에서 사용자의 카메라 촬영(OCR)을 통해 즉각적인 결과를 보여주어야 하는 서비스 특성상, **응답 속도(Latency)**와 **개발 생산성** 사이의 균형이 무엇보다 중요했습니다.

이번 포스팅에서는 PickSafe가 마주한 기술적 과제와, 이를 해결하기 위해 검토한 아키텍처 선택의 기로(Trade-off), 그리고 최종적으로 내린 기술적 의사결정을 공유합니다.

---

## 1. Problem: 무엇을 해결해야 하는가?

PickSafe의 핵심 유저 시나리오는 명확합니다. 
> *"마트에서 화장품 뒷면의 복잡한 성분표를 스마트폰 카메라로 찍으면, 1초 안에 내 피부에 위험한 성분이 있는지 판별해 준다."*

이 시나리오를 기술적으로 분석했을 때 백엔드가 마주한 핵심 제약 사항은 다음과 같습니다.
1. **I/O 바운드 작업의 빈번함**: 이미지 업로드, OCR 엔진 연동, 외부 API 호출 등 네트워크 및 디스크 I/O가 빈번하게 발생합니다.
2. **모바일 웹/앱 환경의 한계**: 사용자는 대기 시간에 매우 민감합니다. SPA 프레임워크(React, Vue 등)를 무겁게 올리기보다, 첫 페이지 로딩 속도(First Contentful Paint)를 극단적으로 줄여야 했습니다.
3. **엄격한 데이터 무결성**: 화장품 성분 정보는 사용자 건강과 직결되므로, 데이터 유효성 검증에서 사소한 런타임 에러도 허용될 수 없습니다.

---

## 2. Trade-off & Architecture: 기술적 고민과 대안 비교

이러한 문제를 해결하기 위해 초기 스캐폴딩 단계에서 다음과 같은 기술 스택을 검토하고 최적의 대안을 선택했습니다.

### ① 백엔드 프레임워크: FastAPI vs Django / Spring Boot
* **Django**: 강력한 올인원 프레임워크지만, 초기 페이로드와 오버헤드가 크고 비동기 처리(ASGI) 생태계가 상대적으로 무겁습니다.
* **Spring Boot**: 엔터프라이즈 환경에 적합하나, 소규모 팀에서 신속하게 프로토타입을 만들고 피벗하기에는 개발 속도 측면에서 아쉬움이 있습니다.
* **FastAPI (선택)**: 
  * Python 기반으로 AI/OCR 라이브러리 연동이 매우 자연스럽습니다.
  * 기본적으로 **비동기(ASGI)를 지원**하여 OCR 이미지 분석 및 외부 통신과 같은 I/O 바운드 작업에서 뛰어난 성능을 발휘합니다.
  * **Pydantic**을 통한 런타임 데이터 유효성 검증으로 휴먼 에러를 원천 차단할 수 있습니다.

### ② 프론트엔드 렌더링: SPA(React/Vue) vs SSR(Jinja2 + Vanilla JS)
* **SPA 구조**: 향후 고도화된 인터랙션에는 유리하지만, 모바일 브라우저에서 초기 JS 번들을 다운로드하고 파싱하는 시간(Bundle Overhead)이 발생합니다.
* **Jinja2 서버사이드 렌더링 + Vanilla JavaScript (선택)**:
  * 별도의 빌드 체인(Webpack, Vite 등) 없이 즉시 렌더링이 가능하여 **모바일 환경에서의 초기 로딩 속도를 0.5초 이내**로 단축할 수 있습니다.
  * 모바일 중심의 가벼운 PWA(Progressive Web App) 형태로 빠르게 피드백을 수렴하기에 가장 합리적인 선택이었습니다.

---

## 3. 최종 아키텍처 설계

위와 같은 고민을 거쳐 확립된 PickSafe의 백엔드 아키텍처 골격은 다음과 같습니다.

```
[Mobile-First Web / PWA (Jinja2 + Vanilla JS)]
                 │
                 ▼ (HTTP / JSON API)
[FastAPI Backend (Python 3.11 + Pydantic + ASGI)]
                 │
                 ▼ (SQLAlchemy 2.0 ORM)
[PostgreSQL Database (Neon DB)]
```

* **레이어드 아키텍처**: 라우터(Router), 비즈니스 로직(Service), 데이터 모델(Model)을 엄격히 분리하여, 향후 OCR 엔진이 고도화되거나 새로운 외부 API가 연동되더라도 비즈니스 로직의 변경을 최소화했습니다.
* **디렉토리 구조 표준화**: 핵심 백엔드 로직과 프론트엔드 자산을 명확히 격리하고, 배치 작업 및 마스터 데이터 시딩을 위한 `bin/` 디렉토리를 분리하여 운영 편의성을 높였습니다.

---

## 4. Takeaway: 엔지니어링 교훈

1. **"상황에 맞는 도구(Right tool for the job)"의 중요성**: 무조건 트렌디한 프론트엔드 SPA를 도입하기보다, '1초 만의 판별'이라는 서비스 목표와 모바일 환경을 최우선으로 고려해 서버사이드 렌더링(Jinja2)으로 선회한 것은 초기 속도 확보에 결정적인 신의 한수였습니다.
2. **타입 안정성과 생산성의 조화**: FastAPI와 Pydantic 조합은 별도의 복잡한 설정 없이도 견고한 API 스키마를 보장해주어, 개발 초기 단계에서 디버깅 시간을 획기적으로 줄여주었습니다.

PickSafe는 이제 이 단단한 아키텍처 기반 위에서 본격적인 성분 분석 엔진 고도화와 사용자 경험 개선을 향해 나아갑니다. 초기 스캐폴딩 단계에서 고민하고 계신 많은 엔지니어분들에게 이 글이 작은 인사이트가 되었기를 바랍니다.
