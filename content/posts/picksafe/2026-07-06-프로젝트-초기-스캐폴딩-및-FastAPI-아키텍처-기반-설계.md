안녕하세요, **PickSafe(픽세이프)** 프로젝트의 초기 스캐폴딩과 백엔드 아키텍처 설계를 맡은 시니어 백엔드 엔지니어입니다. 

화장품 성분 정보의 비대칭성을 해결하고, 사용자가 카메라 촬영(OCR)을 통해 1초 만에 알레르기 유발 성분을 감지할 수 있는 서비스를 세상에 내놓기 위해서는 **‘압도적인 속도’**와 **‘경량화된 아키텍처’**가 필수적이었습니다.

이번 글에서는 프로젝트의 첫 발을 떼며 마주한 요구사항을 정의하고, 이를 해결하기 위해 어떤 기술적 고민과 트레이드오프(Trade-off)를 거쳐 현재의 아키텍처를 확정하게 되었는지 공유해 드립니다.

---

## 1. 문제 정의 (Problem Context)

PickSafe의 핵심 유저 시나리오는 명확합니다. 
> *"마트나 올리브영 매장에서 화장품 전성분표를 카메라로 찍었을 때, 대기 시간 없이 즉시(1초 이내) 내 피부에 유해한 성분이 있는지 판별해 주어야 한다."*

이 요구사항은 시스템에 다음과 같은 기술적 제약과 도전 과제를 던졌습니다.

1. **I/O 바운드 작업의 빈번함**: OCR 이미지 처리 및 외부 API 통신이 잦기 때문에, 동기(Sync) 방식의 서버는 금방 병목에 부딪힐 위험이 컸습니다.
2. **초기 로딩 속도 극대화**: 모바일 환경에서 사용자가 웹 브라우저를 열었을 때, 무거운 SPA(Single Page Application) 프레임워크의 번들 파일을 다운로드하고 파싱하는 시간조차 아껴야 했습니다.
3. **엄격한 데이터 무결성**: 화장품 성분 및 사용자 기피 성분 매칭 로직에서 데이터 타입 오류나 누락은 치명적인 사용자 경험 저하로 이어집니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Architecture Decisions)

### 2.1. 왜 Node.js나 Spring 대신 `FastAPI (Python 3.11)`를 선택했는가?
* **대안 A: Spring Boot (Java)**
  * *장점*: 강력한 엔터프라이즈 생태계, 정적 타이핑의 안정성.
  * *단점*: 초기 스캐폴딩이 무겁고, 빠른 MVP(Minimum Viable Product) 빌드 관점에서 오버엔지니어링 우려.
* **대안 B: Express.js (Node.js)**
  * *장점*: 뛰어난 비동기 I/O 성능, 프론트엔드와의 언어 통일성.
  * *단점*: 복잡한 성분 유효성 검증 및 추후 도입할 머신러닝/OCR 라이브러리 연동 시 Python 생태계가 훨씬 유리함.
* **최종 선택: FastAPI**
  * **비동기(ASGI) 기본 지원**: OCR 및 외부 I/O 대기 시간에 효율적으로 대응 가능.
  * **Pydantic을 통한 선언적 스키마 검증**: 런타임 에러를 사전에 방지하고 API 문서(Swagger)를 자동 생성하여 개발 생산성 극대화.

### 2.2. 무거운 SPA를 버리고 `Jinja2 + Vanilla JS`를 택한 이유
최근 프론트엔드 트렌드는 React나 Vue 기반의 SPA이지만, PickSafe는 모바일 퍼스트(Mobile-First) 웹/PWA 환경을 지향합니다.

* **고민**: React를 도입하면 클라이언트 사이드 렌더링(CSR)으로 인해 초기 First Contentful Paint(FCP) 지연이 발생할 수 있습니다.
* **결정**: 빌드 번들 오버헤드를 완전히 배제하고, 서버 사이드에서 렌더링되는 **Jinja2 템플릿과 가벼운 Vanilla JavaScript**를 조합하기로 했습니다. 이를 통해 모바일 환경에서 첫 로딩 속도를 0.5초 이내로 단축하고, 불필요한 프론트엔드 빌드 파이프라인의 복잡성을 낮췄습니다.

## 3. 최종 아키텍처 및 디렉토리 구조

위의 고민들을 녹여내어 확정한 아키텍처의 기본 골격은 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS + CSS (Jinja2 서버사이드 렌더링)       │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - ASGI 비동기 라우팅 & Pydantic 스키마 유효성 검증          │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL on Neon DB / SQLite 로컬)     │
└─────────────────────────────────────────────────────────────┘
```

백엔드와 프론트엔드의 관심사를 명확히 분리하면서도, 확장성을 고려하여 디렉토리 구조를 표준화했습니다.

* `web/backend/app/`: 라우터, 비즈니스 로직(Services), 데이터베이스 모델(Models) 분리
* `web/frontend/`: 템플릿 및 모바일 최적화 정적 자산(CSS/JS) 관리
* `bin/`: 마스터 데이터 시딩 및 배치 작업을 위한 CLI 스크립트 격리

## 4. 엔지니어링 교훈 및 Takeaway

1. **목적에 맞는 기술 스택의 역설계**: "무조건 최신 프론트엔드 프레임워크를 써야 한다"는 고정관념을 깨고, 모바일 웹 환경의 속도라는 본질에 집중하여 Jinja2를 선택한 것은 초기 개발 속도와 성능 모두를 잡은 훌륭한 결정이었습니다.
2. **타입 안정성과 생산성의 조화**: FastAPI + Pydantic 조합은 별도의 복잡한 설정 없이도 견고한 API 계약(Contract)을 만들어주어, 팀원 간 협업 시 인터페이스 오류를 극적으로 줄여주었습니다.

PickSafe는 이제 탄탄한 초기 스캐폴딩을 바탕으로 본격적인 성분 분석 엔진 고도화와 사용자 경험 개선에 박차를 가할 준비를 마쳤습니다. 앞으로 이어질 트러블슈팅과 기능 확장기도 많은 기대 바랍니다!
