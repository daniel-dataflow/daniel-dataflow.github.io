새로운 서비스를 세상에 선보일 때, 개발자가 마주하는 가장 큰 유혹은 **"가장 핫한 기술을 모두 쏟아붓고 싶은 욕심"**입니다. React, Next.js, MSA, Kubernetes... 모두 훌륭한 기술이지만, 과연 극초기 MVP(Minimum Viable Product) 단계에서도 최선의 선택일까요?

우리가 준비하는 **PickSafe(픽세이프)**는 스마트폰 카메라로 화장품 성분표를 촬영(OCR)하여 26대 식약처 지정 알레르기 성분과 개인별 기피 성분을 1초 만에 판별해 주는 모바일 웹 서비스입니다. 

마트나 드럭스토어 매장 한복판에서 제품을 들고 있는 사용자가 우리 서비스를 켭니다. 이때 로딩 속도가 3초를 넘어간다면 사용자는 바로 이탈할 것입니다. 모바일 네트워크 환경에서도 **첫 로딩 속도(First Contentful Paint, FCP)를 0.5초 이내로 단축**하면서, 동시에 향후 OCR 및 대용량 성분 분석 DB 확장성을 확보해야 하는 과제가 주어졌습니다.

팀 PickSafe의 시니어 개발자로서, 오버 엔지니어링을 경계하고 오직 **'극단적 성능과 실용성'**에 집중해 설계한 초기 아키텍처 설계 여정과 그 비하인드 스토리를 공유합니다.

---

## 1. 문제 정의: 찰나의 순간, 사용자를 잡기 위한 성능적 제약 사항

모바일 환경에서의 OCR 서비스는 성능적으로 매우 가혹한 환경에 놓여 있습니다.

1. **지연 시간(Latency) 최소화**: 사용자는 매장에서 제품을 들고 서 있습니다. OCR 분석과 외부 API 매핑, 안전성 판별까지 전체 프로세스가 **1초 내외**에 끝나야 매끄러운 사용자 경험(UX)을 제공할 수 있습니다.
2. **첫 로딩 속도(FCP) 극대화**: 네트워크 상태가 불안정한 오프라인 매장에서도 웹 앱이 즉각적으로 화면을 띄워야 합니다. 무거운 자바스크립트 번들 파일을 다운로드하고 CSR(Client-Side Rendering)로 화면을 그릴 시간적 여유가 없습니다.
3. **빠른 가치 검증(Time-to-Market)**: 검증되지 않은 가설을 위해 거대한 인프라를 구축하는 것은 낭비입니다. 빌드와 배포 프로세스를 최소화하고 즉각적인 피드백을 반영할 수 있는 경량 구조가 필요했습니다.

## 2. 기술적 고민과 대안 비교: Pragmatic Trade-off

이 세 가지 문제를 해결하기 위해 백엔드와 프론트엔드 레이어에서 치열한 기술 비교 평가를 진행했습니다.

### 백엔드: Django vs FastAPI
파이썬 생태계에서 웹 백엔드를 구축할 때 가장 먼저 고민하는 두 후보입니다.

| 비교 항목 | Django (DRF) | FastAPI |
| :--- | :--- | :--- |
| **비동기 지원 (Async I/O)** | 동기 위주 (비동기 지원이 추가되었으나 서드파티 호환성 제한) | **네이티브 ASGI 지원** (초고속 비동기 루프 기반) |
| **성능 (Throughput)** | 보통 (오버헤드 큼) | **매우 높음** (Uvicorn + Starlette 기반 최상급 성능) |
| **데이터 검증** | Django Serializer | **Pydantic 2.0** (Rust 기반 핵심 엔진으로 압도적 속도) |
| **생산성** | Admin 페이지 등 내장 기능 풍부 | 코드 자동 문서화(Swagger)로 빠른 API 피드백 루프 |

*   **선택 (FastAPI)**: OCR 이미지 분석 요청이나 외부 API 호출 등 **I/O 바운드 작업이 핵심인 PickSafe의 특성상 네이티브 비동기 처리가 필수적**이었습니다. 또한 Pydantic을 활용한 엄격한 스키마 유효성 검증은 데이터 일관성을 보장하고 런타임 오류를 원천 차단해주기 때문에 FastAPI를 최종 선택했습니다.

### 프론트엔드: React(SPA) vs Jinja2(SSR) + Vanilla JS
현대 웹 개발에서 SPA(Single Page Application)는 표준처럼 여겨지지만, 우리는 과감하게 역발상을 시도했습니다.

*   **SPA 방식의 한계**: React/Vue 기반 프레임워크는 모바일 웹 초기 구동 시 거대한 JS 번들(Bundle)을 다운로드하고 브라우저에서 'Hydration' 과정을 거쳐야 합니다. 저사양 모바일 기기나 매장 내 약한 LTE 환경에서는 이 과정이 치명적인 병목이 됩니다.
*   **선택 (Jinja2 + Vanilla JS)**: 복잡한 상태 관리가 필요 없는 심플한 단일 목적형 뷰(View) 구조이므로, **백엔드에서 완성된 HTML을 즉시 렌더링하여 내려주는 Jinja2 서버사이드 템플릿 방식**을 채택했습니다. 여기에 화면 제어는 빌드가 필요 없는 순수 Vanilla JS와 경량 CSS(Tailwind조차 걷어낸 핵심 모바일 스타일링)로만 구성했습니다. 
*   **결과**: 이를 통해 첫 로딩 속도(FCP)를 **0.5초 이내**로 확보하는 초경량 클라이언트 레이어를 완성했습니다.

## 3. 최종 아키텍처 및 폴더 구조 설계

팀이 합의한 최종 개념 아키텍처는 아래와 같이 직관적이고 레이어가 명확히 분리된 구조입니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS + CSS (최적화 모바일 전용 뷰)           │
│ - Jinja2 서버사이드 템플릿 렌더링                           │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - 비동기(ASGI) 라우팅 및 빠른 JSON 직렬화                   │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL / SQLite 로컬)                  │
│ - 사용자 계정, 스캔 이력, 성분 마스터 DB                    │
└─────────────────────────────────────────────────────────────┘
```

생산성과 확장성을 모두 챙기기 위해 디렉토리 구조도 단순하지만 엄격하게 규격화했습니다. 백엔드와 프론트엔드 자산을 명확히 격리하되, 개발 초기 단계에서 모노레포처럼 빠르게 통합 테스트를 수행할 수 있도록 배치했습니다.

```bash
├── bin/                       # CLI 배치 및 마스터 데이터 시딩 스크립트
├── web/
│   ├── backend/               # 백엔드 핵심 애플리케이션
│   │   └── app/
│   │       ├── database/      # DB 커넥션 및 세션 관리
│   │       ├── models/        # SQLAlchemy ORM 모델
│   │       ├── routers/       # 비동기 API 엔드포인트 라우터
│   │       ├── schemas/       # Pydantic 데이터 검증 스키마
│   │       └── services/      # 비즈니스 로직 (OCR 연동, 성분 판별 알고리즘)
│   └── frontend/              # 클라이언트 사이드 리소스
│       ├── static/            # 경량 CSS, JS, 이미지 자산
│       └── templates/         # Jinja2 HTML 템플릿
```

## 4. 엔지니어링 교훈 (Takeaways)

프로젝트 초기 스캐폴딩 단계를 마무리지으며 우리 팀이 얻은 가장 큰 엔지니어링 교훈은 다음과 같습니다.

1. **"트렌디한 기술"이 항상 "올바른 기술"은 아니다.**
   모두가 React나 Next.js를 논할 때, 비즈니스 핵심 지표인 'FCP 0.5초'를 만족하기 위해 서버사이드 렌더링(Jinja2)과 Vanilla JS라는 전통적이고 가벼운 무기를 선택했습니다. 이 타협은 모바일 사용자 환경에서 엄청난 성능 이점으로 돌아왔습니다.
2. **성능을 담보하는 비동기(Async) 설계의 중요성**
   사용자의 이미지를 분석하고 성분 DB와 매핑하는 과정은 수많은 네트워크 I/O를 동반합니다. FastAPI의 비동기(ASGI) 아키텍처는 동시 요청이 몰리는 상황에서도 최소한의 리소스로 높은 처리량(Throughput)을 보장할 수 있는 튼튼한 뼈대가 되었습니다.
3. **지속 가능한 도메인 격리**
   비록 시작은 하나의 프로젝트 폴더 내에 백엔드와 프론트엔드가 모여 있는 단순한 형태이지만, `services` 레이어와 `routers`를 완벽히 격리함으로써 향후 OCR 판별 엔진이 고도화되거나 MSA로 서비스가 쪼개지더라도 큰 리팩토링 비용 없이 유연하게 대처할 수 있는 확장성을 확보했습니다.

우리는 가장 단순한 형태로 가장 빠른 가치를 제공할 수 있는 기반을 마련했습니다. 이제 남은 것은 이 단단한 스캐폴딩 위에 강력한 성분 분석 알고리즘을 얹어, 고객들의 쇼핑 경험을 안전하게 혁신하는 일뿐입니다.
