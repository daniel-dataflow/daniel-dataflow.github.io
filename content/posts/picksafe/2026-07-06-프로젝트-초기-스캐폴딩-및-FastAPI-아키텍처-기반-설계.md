안녕하세요, PickSafe(픽세이프) 개발 팀입니다. 

마트나 화장품 매장에서 전성분 표를 마주했을 때, 알레르기 유발 성분을 일일이 스마트폰으로 검색해 본 경험이 있으신가요? 글씨는 너무 작고, 화학 용어는 낯설기만 합니다. 

**PickSafe**는 이러한 정보의 비대칭성을 해결하기 위해 시작된 프로젝트입니다. 스마트폰 카메라로 성분표를 촬영(OCR)하면, **식약처 지정 26대 알레르기 유발 성분과 개인 맞춤형 기피 성분을 단 1초 만에 판별**하여 직관적인 안전 점수를 제공합니다.

이번 포스팅에서는 "1초 이내 판별"이라는 사용자 경험(UX)을 달성하기 위해, 프로젝트 초기 단계에서 백엔드 프레임워크를 선정하고 모바일 환경에 최적화된 초경량 아키텍처를 설계하며 고민했던 트레이드오프(Trade-off) 과정을 공유합니다.

---

## 1. 문제 정의: 킬러 UX의 핵심은 '속도'와 '경량화'

PickSafe가 타깃으로 하는 주요 사용 시나리오는 **"오프라인 매장 매대 앞"**입니다. 이동통신망(LTE/5G) 환경이 불안정할 수 있는 오프라인 매장에서 사용자가 카메라를 켜고 제품을 스캔했을 때, 앱 로딩과 분석 결과가 나오기까지 수 초 이상 지연된다면 사용자는 즉시 서비스를 이탈할 것입니다.

우리가 정의한 핵심 기술적 요구사항은 다음과 같았습니다.

1. **초경량 프론트엔드**: 네트워크 상태가 좋지 않아도 첫 화면이 0.5초 이내에 렌더링(FCP, First Contentful Paint)되어야 함.
2. **고성능 비동기 백엔드**: 이미지 업로드, OCR 분석 호출, 성분 데이터베이스(DB) 매칭 등 동시다발적인 I/O 바운드 작업을 지연 없이 처리해야 함.
3. **엄격한 데이터 스키마 유효성 검증**: OCR로 파싱된 불안정한 텍스트 데이터를 정제하고, 백엔드-프론트엔드 간 안전한 데이터 계약(Data Contract)을 보장해야 함.

## 2. 기술적 고민과 대안 비교: React+Node.js vs FastAPI+Jinja2

초기 설계 단계에서 가장 치열하게 논의되었던 부분은 **"트렌디한 SPA(Single Page Application) 기술 스택을 쓸 것인가, 클래식하지만 확실한 SSR(Server-Side Rendering)을 쓸 것인가"**였습니다.

### 대안 1: React + Node.js (Express)
가장 대중적이고 생태계가 넓은 조합입니다. 
* **장점**: 컴포넌트 재사용성이 높고, 풍부한 UI 라이브러리를 활용할 수 있음.
* **단점**: React 라이브러리 및 번들(Bundle) 크기로 인해 모바일 환경에서 첫 로딩 속도(FCP)가 느려짐. 클라이언트 사이드 하이드레이션(Hydration) 비용 발생.

### 대안 2: FastAPI + Jinja2 (서버사이드 템플릿) + Vanilla JS (최종 채택)
전통적인 서버사이드 렌더링에 현대적인 고성능 Python 비동기 프레임워크를 결합한 구조입니다.
* **장점**: 
  * 백엔드에서 HTML을 즉시 렌더링하여 전송하므로 **FCP를 0.5초 이내로 극단적으로 단축** 가능.
  * 불필요한 빌드 도구(Webpack, Vite 등) 의존성을 제거하여 초기 프로젝트 복잡도 최소화.
  * Python 기반의 데이터 분석 및 OCR 파이프라인과의 강력한 호환성.
* **단점**: 복잡한 상태 관리(State Management)를 프론트엔드에서 구현하기 까다로움. (단, PickSafe는 스캔 -> 결과 화면으로 이어지는 단방향 흐름이 지배적이므로 이 단점이 크게 작용하지 않음)

### 의사결정의 이유 (Trade-off)
우리는 **"복잡한 클라이언트 상태 관리보다 모바일 첫 로딩 속도가 비즈니스 성공에 더 결정적이다"**라고 판단했습니다. 이에 따라 화면이 무거운 React 대신, 경량 **Jinja2 템플릿과 Tailwind CSS조차 배제한 순수 CSS/Vanilla JS** 구성을 선택했습니다.

백엔드의 경우, 멀티스레딩 및 비동기 처리에 강점이 있는 **FastAPI(ASGI)**를 채택하여 OCR 호출 및 DB 조회의 병목을 원천 해결하고자 했습니다.

## 3. PickSafe 아키텍처 및 디렉토리 구조

이를 바탕으로 설계한 PickSafe의 초기 아키텍처 골격은 다음과 같습니다.

### 시스템 아키텍처 다이어그램

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS + CSS (최소화된 경량 모바일 뷰)         │
│ - Jinja2 서버사이드 템플릿 렌더링                           │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - 비동기(ASGI) 라우팅 및 빠른 JSON 직렬화                   │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL on Serverless / SQLite 로컬)   │
│ - 사용자 계정, 스캔 이력, 성분 마스터, 찜 상품 스키마      │
└─────────────────────────────────────────────────────────────┘
```

### 아키텍처를 뒷받침하는 클린 디렉토리 구조
프로젝트가 커지더라도 비즈니스 로직과 프론트엔드 에셋이 엉키지 않도록 구조적 책임을 명확히 분리했습니다.

```text
picksafe-project/
├── bin/                       # CLI 배치 및 마스터 데이터 시딩 스크립트
├── web/
│   ├── backend/               # 백엔드 코어 (FastAPI)
│   │   └── app/
│   │       ├── database/      # DB 연결 및 SQLAlchemy 설정
│   │       ├── models/        # DB ORM 엔티티 정의
│   │       ├── routers/       # API 엔드포인트 제어
│   │       └── services/      # 핵심 비즈니스 로직 (OCR, 성분 분석)
│   └── frontend/              # 프론트엔드 에셋
│       ├── templates/         # Jinja2 템플릿 파일 (.html)
│       └── static/            # 정적 파일 (CSS, JS, Images)
```

## 4. 엔지니어링 교훈 (Takeaways)

이번 프로젝트 초기 스캐폴딩 작업을 진행하며 얻은 시니어 엔지니어로서의 교훈은 다음과 같습니다.

1. **기술 트렌드보다 비즈니스 도메인의 제약이 우선한다**: React, Next.js 같은 최신 기술이 항상 정답은 아닙니다. 오프라인 모바일 네트워크라는 환경적 제약 속에서는 오히려 '서버사이드 렌더링 + 바닐라 JS'라는 클래식한 접근이 최상의 성능을 냅니다.
2. **FastAPI와 Pydantic의 강력한 시너지**: Pydantic을 활용한 스키마 검증은 단순한 유효성 검사를 넘어 프론트엔드와의 명확한 API 계약서 역할을 해줍니다. Swagger UI가 자동 생성되어 협업 효율이 극대화되었습니다.
3. **확장성을 고려한 레이어 분리**: 당장은 모놀리식 구조로 시작하지만, 비즈니스 로직(`services`)과 전송 계층(`routers`), DB 계층(`models`)을 엄격히 격리함으로써, 향후 무거운 OCR 엔진을 마이크로서비스(MSA)로 분리하더라도 코드 수정 범위를 최소화할 수 있는 기반을 마련했습니다.

PickSafe는 이제 첫걸음을 뗐습니다. 단단하게 다져진 기초 아키텍처 위에 더 빠르고 정확한 OCR 인식 기술과 대용량 성분 매칭 알고리즘을 얹어가는 여정을 앞으로도 기술 블로그를 통해 공유해 드리겠습니다. 

많은 기대 부탁드립니다!
