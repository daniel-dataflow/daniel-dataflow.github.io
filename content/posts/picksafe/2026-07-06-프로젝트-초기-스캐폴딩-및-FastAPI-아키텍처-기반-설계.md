안녕하세요, **PickSafe(픽세이프)** 프로젝트의 초기 아키텍처 설계 및 스캐폴딩 과정을 기록합니다. 

PickSafe는 사용자가 스마트폰 카메라로 화장품 전성분 표를 촬영(OCR)하면, 1초 만에 식약처 공인 알레르기 유발 성분과 사용자 기피 성분을 감지해 안전성을 판별해 주는 모바일 웹/앱 서비스입니다. 

서비스의 특성상 **'즉각적인 응답 속도'**와 **'모바일 환경에서의 가벼운 첫 로딩'**이 핵심 성공 요인입니다. 이번 포스팅에서는 프로젝트의 첫 발을 떼며 왜 **FastAPI**와 **Jinja2 기반의 경량 SSR(Server-Side Rendering)** 조합을 선택하게 되었는지, 그 기술적 고민과 트레이드오프(Trade-off) 과정을 공유합니다.

---

## 1. Problem: 우리가 마주한 기술적 과제

서비스를 기획하며 마주한 가장 큰 제약 사항은 다음과 같습니다.

1. **I/O 바운드 작업의 빈번함**: 이미지를 받아 OCR 엔진을 거치고, 데이터베이스에서 방대한 성분 마스터 데이터를 대조하는 과정은 네트워크 및 디스크 I/O가 빈번하게 발생합니다. 동기식 프레임워크를 사용한다면 대규모 트래픽 유입 시 병목이 명확했습니다.
2. **모바일 웹 환경의 속도 제약**: 민감성 피부나 알레르기가 있는 소비자가 매장에서 급하게 제품을 검색할 때, 무거운 SPA(React/Vue 등) 프레임워크의 번들 파일을 다운로드하고 구동하는 지연 시간(FCP, First Contentful Paint)조차 사용자 경험을 해칠 수 있었습니다.

---

## 2. Trade-off & Decision: 기술 스택 선정 과정

### ① 백엔드: FastAPI vs Django / Spring
* **고민**: 엔터프라이즈 환경에서 검증된 Django나 Spring을 사용할 수도 있었습니다. 특히 Django는 오랫동안 사랑받아 온 모놀리식 웹 프레임워크입니다.
* **선택**: **FastAPI (Python 3.11)**
* **이유**: 
  * **비동기(ASGI) 성능**: Starlette 기반의 비동기 처리를 지원하므로, 외부 API 통신이나 이미지 처리 등 I/O 바운드 작업에서 높은 동시성 처리 성능을 기대할 수 있습니다.
  * **Pydantic을 통한 엄격한 타입 및 스키마 검증**: 화장품 성분 데이터는 안전성과 직결되므로 데이터 무결성이 중요합니다. 런타임 에러를 사전에 방지하는 Pydantic의 강력한 스키마 검증 기능은 큰 메리트였습니다.

### ② 프론트엔드: React/Vue SPA vs Jinja2 + Vanilla JS SSR
* **고민**: 현대적인 컴포넌트 기반 개발을 위해 React나 Vue를 도입하는 것이 생산성 면에서는 유리할 수 있습니다.
* **선택**: **Jinja2 서버사이드 렌더링 + 모바일 최적화 바닐라 JavaScript**
* **이유**: 
  * 불필요한 빌드 도구 의존성(Webpack, Vite 등)과 거대한 자바스크립트 런타임 번들을 완전히 배제했습니다.
  * 모바일 네트워크 환경에서 첫 로딩 속도(FCP)를 **0.5초 이내**로 단축하여, 사용자가 매장 등에서 대기 시간 없이 즉시 서비스를 이용할 수 있도록 했습니다.

## 3. Architecture Overview

위와 같은 고민을 바탕으로 구축한 전체적인 아키텍처의 기본 골격은 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 프론트엔드 (Mobile-First Web / PWA)                         │
│ - HTML5 + Vanilla JS + CSS (Tailwind 없는 경량 모바일 뷰)   │
│ - Jinja2 서버사이드 템플릿 렌더링 + 모바일 최적화 UI        │
└─────────────────────────────────────────────────────────────┘
                              │ HTTP / JSON API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 백엔드 계층 (FastAPI + Python 3.11)                          │
│ - 비동기(ASGI) 라우팅 및 빠른 JSON 직렬화                   │
│ - Pydantic 기반 Request/Response 스키마 유효성 검증         │
└─────────────────────────────────────────────────────────────┘
                              │ SQLAlchemy 2.0 ORM
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 데이터 저장 계층 (PostgreSQL / SQLite 로컬)                │
│ - 사용자 계정, 스캔 이력, 성분 마스터, 찜 상품 스키마      │
└─────────────────────────────────────────────────────────────┘
```

디렉토리 구조 역시 비즈니스 로직(`routers`, `services`, `models`)과 프레임워크 리소스(`templates`, `static`)를 명확히 분리하여, 향후 OCR 엔진 고도화나 대용량 성분 DB 적재 등 기능이 확장되더라도 유지보수성이 높도록 설계했습니다.

---

## 4. Takeaway: 엔지니어링 교훈

1. **목적에 맞는 기술 선택 (Right Tool for the Job)**: 화려하고 최신 트렌드의 프레임워크를 무조건 도입하기보다, '1초 만의 안전성 판별'이라는 서비스 핵심 가치와 '모바일 환경의 빠른 로딩'이라는 제약 조건에 가장 부합하는 기술(FastAPI + SSR)을 선택하는 것이 최우선임을 다시 한번 확인했습니다.
2. **초기 스캐폴딩의 중요성**: 프로젝트 초기 단계에서 명확한 아키텍처 기준과 디렉토리 구조 표준을 확립함으로써, 개발 팀원 간의 컨벤션 비용을 줄이고 확장성 있는 기반을 다질 수 있었습니다.
