안녕하세요, PickSafe 백엔드 개발팀입니다. 

서비스가 성장하고 기능이 확장됨에 따라, 초기 개발 속도에 초점을 맞춰 작성되었던 소스 코드와 디렉토리 구조의 한계에 부딪히게 되었습니다. 특히 OCR 스캔, 알레르기 성분 매칭, 사용자 인증 등 핵심 비즈니스 로직이 늘어나면서 코드의 응집도를 높이고 유지보수성을 확보할 필요성이 커졌습니다.

이번 포스팅에서는 **PickSafe 프로젝트의 루트 폴더 구조를 전면 개편하고, 향후 확장성(Scalability)을 고려해 백엔드와 프론트엔드의 책임을 명확히 분리한 아키텍처 의사결정 과정(Trade-off)**을 공유하고자 합니다.

---

## 1. Problem: 무엇을 마주했는가?

프로젝트 초기에는 빠른 프로토타이핑을 위해 루트 디렉토리 주변에 설정 파일, 라우터, 템플릿들이 혼재되어 있었습니다. 하지만 이로 인해 다음과 같은 기술적 부채가 발생했습니다.

1. **관심사의 혼재 (Separation of Concerns 부족):** 백엔드 API 로직, Jinja2 템플릿 기반의 프론트엔드 리소스, 그리고 다양한 문서(Docs)가 한 공간에 얽혀 있어 파일 탐색과 코드 파악에 불필요한 인지 부하가 발생했습니다.
2. **미래의 확장성 제약:** 현재는 서버 사이드 렌더링(SSR) 방식을 혼용하고 있으나, 향후 프론트엔드를 독립된 SPA(React, Next.js 등)로 전환하거나 모바일 앱과 연동할 때, 현재 구조 그대로는 프론트엔드와 백엔드를 독립적으로 격리하기 어렵다는 문제가 있었습니다.
3. **테스트 및 유지보수의 어려움:** 비즈니스 로직(Services), 데이터 정의(Models), 그리고 HTTP 요청 처리(Routers)가 명확히 분리되지 않으면 유닛 테스트 작성 시 의존성 주입과 모킹(Mocking)이 까다로워집니다.

---

## 2. Trade-off: 왜 이러한 아키텍처를 선택했는가?

이러한 문제를 해결하기 위해, 우리는 **FastAPI의 모듈성과 표준적인 계층형 아키텍처(Layered Architecture)**를 적용하기로 결정했습니다.

```
/picksafe
  /web
    /backend
      /app
        /models       # 데이터베이스 ORM 모델 (SQLAlchemy)
        /routers      # HTTP 엔드포인트 및 뷰 렌더링
        /services     # 핵심 비즈니스 로직 (OCR, 매칭 등)
        config.py     # 환경 설정 (Pydantic Settings)
        database.py   # DB 연결 엔진 및 세션 관리
        main.py       # FastAPI 진입점
    /frontend
      /static         # 정적 리소스 (CSS, JS, Images)
      /templates      # Jinja2 HTML 템플릿
  /docs               # 아키텍처 및 의사결정 문서 관리
```

### 주요 디자인 결정과 대안 비교

* **디렉토리 계층 격리 (`/web/backend` vs `/web/frontend`)**
  * *고민:* 단일 디렉토리에 모든 코드를 두는 것이 당장의 파일 이동이나 경로 설정에는 편할 수 있습니다.
  * *선택:* 빌드 시스템과 배포 파이프라인, 그리고 추후 프론트엔드 단독 독립 배포 가능성을 열어두기 위해 명확히 물리적 폴더 수준에서 백엔드와 프론트엔드를 격리(`web/`)했습니다.

* **엄격한 백엔드 레이어 분리 (`Routers` -> `Services` -> `Models`)**
  * *라우터(Routers):* HTTP 요청을 받고 응답을 반환하는 역할에만 집중합니다.
  * *서비스(Services):* OCR 스캔, 알레르기 표준 성분 매칭 등 핵심 비즈니스 로직을 캡슐화하여, HTTP 프레임워크에 종속되지 않도록 분리했습니다.
  * *모델(Models):* ERD 설계서를 기반으로 한 SQLAlchemy ORM 모델을 독립된 패키지로 관리하여 데이터 무결성과 스키마 가독성을 높였습니다.

---

## 3. Takeaway: 무엇을 배웠고 어떻게 적용되는가?

이번 구조 개편을 통해 얻은 엔지니어링 교훈과 실무적인 변화는 다음과 같습니다.

1. **응집도 향상과 결합도 저하:** 
   개발자는 특정 기능(예: 알레르기 성분 매칭 로직 변경)을 수정할 때 `services/ingredient_matcher.py`만 집중적으로 수정하면 되므로, 다른 계층에 미치는 부수 효과(Side-effect)를 최소화할 수 있게 되었습니다.
2. **실행 경로 및 환경 설정의 변화:**
   구조가 변경됨에 따라 Uvicorn 서버 구동 경로 역시 `web/backend` 디렉토리 내부를 기준으로 하거나 올바른 패키지 경로를 지정해야 합니다 (`uvicorn app.main:app`). 다만, 내부 임포트 경로는 `app` 패키지 기준으로 유지(`from app.models.user import User`)하여 대규모 코드 리팩토링 없이 임포트 안정성을 확보했습니다.
3. **확장 가능한 기반 마련:**
   이제 PickSafe는 견고한 백엔드 구조를 바탕으로, 향후 대용량 트래픽이나 복잡한 도메인 로직 추가, 프론트엔드 분리 작업에도 유연하게 대처할 수 있는 탄탄한 토대를 갖추게 되었습니다.

> "좋은 아키텍처는 변경을 쉽게 만든다." 이번 폴더 구조 마이그레이션은 단순한 파일 정리가 아니라, PickSafe 서비스의 지속 가능한 성장을 위한 중요한 기술적 도약이었습니다. 

앞으로도 PickSafe 팀은 더 안정적이고 확장 가능한 시스템을 만들기 위해 고민하고 개선해 나가겠습니다. 감사합니다.
