안녕하세요, PickSafe 개발 팀입니다. 
이번 포스팅에서는 프로젝트 초기 루트 디렉토리에 혼재되어 있던 리소스들을 정리하고, 장기적인 확장성과 유지보수성을 고려하여 백엔드와 프론트엔드 계층을 격리한 아키텍처 의사결정 과정을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 르네상스 시기의 대혼란, "뒤엉킨 디렉토리"

초기 프로젝트 셋업 단계에서는 속도(Time-to-Market)를 최우선으로 고려하다 보니, 백엔드와 프론트엔드, 그리고 각종 문서와 설정 파일들이 루트 디렉토리에 플랫(Flat)하게 쌓였습니다. 

이로 인해 다음과 같은 기술적 부채가 누적되기 시작했습니다.
* **관심사의 혼재:** 비즈니스 로직, API 라우터, DB 모델, 정적 파일(CSS/JS), HTML 템플릿의 경계가 모호해져 코드 내비게이션(Code Navigation) 효율이 급격히 저하되었습니다.
* **확장성 제약:** 현재는 FastAPI와 Jinja2 템플릿 기반의 SSR(Server-Side Rendering) 방식을 취하고 있으나, 향후 서비스 성장에 따라 프론트엔드를 React나 Next.js 같은 독립된 SPA/SSR 프레임워크로 분리할 때 디렉토리 구조 변경에 엄청난 비용이 소모될 구조였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 **"어떻게 폴더 구조를 가져갈 것인가?"**에 대한 논의를 진행했습니다.

### 대안 A: 도메인 주조 설계(DDD) 형태의 패키지 분할
* **장점:** 각 도메인(`user`, `scan`, `product` 등)별로 응집도가 극대화됨.
* **단점:** 프로젝트 초기 단계에서는 도메인 간의 경계가 유동적이고 오버엔지니어링(Over-engineering)이 될 확률이 높음.

### 대안 B: 계층형 구조(Layered Architecture) + 클라이언트/서버 디렉토리 격리 (채택)
* **장점:** 
  1. `web/backend`와 `web/frontend`를 물리적으로 격리하여, 향후 프론트엔드 단독 독립 배포나 기술 스택 교체(예: React 전환) 시 백엔드 코드의 수정 없이 프론트엔드 디렉토리만 들어내기 용이합니다.
  2. FastAPI 생태계에서 가장 널리 쓰이는 표준적인 레이어 분리(Router - Service - Model)를 적용하여 개발자 온보딩 비용을 줄입니다.
* **단점:** 모놀리식 구조이므로 장기적으로는 마이크로서비스(MSA) 전환 시 도메인 단위로 코드를 다시 잘라내야 하는 비용이 발생함. (단, 현재 단계에서는 `web/backend` 내부를 명확한 서비스 레이어로 격리해 두어 향후 MSA 전환 시 브릿지 역할을 하도록 설계함.)

---

## 3. 최종 해결: 클린 아키텍처 지향의 폴더 구조 수립

위의 트레이드오프 분석을 바탕으로, 다음과 같이 `web` 하위에 백엔드와 프론트엔드를 명확히 분리하고, 백엔드 내부에서는 관심사에 따른 레이어드 아키텍처를 적용했습니다.

```
/picksafe
  /web
    /backend
      /app
        /models       (SQLAlchemy ORM 모델 - 데이터 레이어)
        /routers      (FastAPI 라우터 및 뷰 렌더링 - 인터페이스 레이어)
        /services     (OCR, 매칭 등 핵심 비즈니스 로직 - 서비스 레이어)
        config.py     (Pydantic Settings 환경 설정)
        database.py   (DB 연결 및 세션 관리)
        main.py       (FastAPI 앱 진입점)
      requirements.txt
    /frontend
      /static         (정적 리소스: CSS, JS, 이미지)
      /templates      (Jinja2 HTML 템플릿)
  /docs               (아키텍처 및 기획 문서)
  .env
  .gitignore
  README.md
```

### 💡 주요 설계 포인트
1. **비즈니스 로직과 라우터의 분리 (`/routers` vs `/services`):** 
   HTTP 요청을 받고 응답을 내려주는 라우터 영역과, 실제 OCR 처리나 성분 매칭 등 핵심 비즈니스 연산이 일어나는 서비스 영역을 완전히 분리했습니다. 이를 통해 단위 테스트(Unit Test) 작성 시 HTTP mocking 없이 순수 비즈니스 로직을 검증할 수 있게 되었습니다.
2. **환경 변수 및 설정 중앙화 (`config.py`):** 
   Pydantic의 `BaseSettings`를 활용하여 타입 안정성을 확보하고 설정 관리를 일원화했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

* **확장성을 위한 사전 격리:** "언젠가 바뀔 것"을 위해 과도한 추상화를 하는 것은 독이지만, **"프론트엔드와 백엔드의 물리적 분리"**는 초기 단계에서부터 해두어야 나중에 리팩토링 지옥에 빠지지 않는다는 교훈을 얻었습니다.
* **일관된 컨벤션의 중요성:** 임포트 경로는 `app` 패키지 기준으로 통일(`from app.models.user import User`)하여, 디렉토리 구조가 바뀌더라도 코드 내부의 import 구문 대대적인 수정 없이 원활한 마이그레이션이 가능했습니다.

이번 폴더 구조 개편을 통해 PickSafe 팀은 더 안정적이고 확장 가능한 기반 위에서 기능을 개발해 나갈 수 있게 되었습니다. 앞으로도 기술적 고민과 성장의 과정을 블로그를 통해 공유하겠습니다. 감사합니다!
