## 문제 정의: 복잡도가 증가하는 프로젝트를 어떻게 구조화할 것인가?

프로젝트 초기에는 속도가 우선입니다. 루트 디렉토리에 모든 파일을 나열하고 빠르게 기능을 구현하는 방식은 MVP 개발에 효율적입니다. 하지만 서비스 규모가 커지고 기능 단위의 로직이 복잡해지면서, 소위 '스파게티 코드'의 징후가 나타나기 시작했습니다. 

특히, 프론트엔드 정적 리소스와 백엔드 API 로직이 혼재된 구조는 다음과 같은 병목을 발생시켰습니다.
1. **관심사 분리의 모호성**: 비즈니스 로직과 뷰 렌더링 코드가 섞여 있어 코드 수정 시 영향 범위를 파악하기 어려움.
2. **기술 스택 변경의 어려움**: 향후 프론트엔드를 React나 Next.js와 같은 SPA(Single Page Application)로 전환하려 할 때, 현재 구조로는 리소스 분리가 물리적으로 어려움.
3. **가독성 저하**: 엔드포인트(Router), 비즈니스 로직(Service), 데이터 모델(Model)이 구분되지 않아 신규 온보딩된 팀원이 코드 흐름을 파악하는 데 시간이 걸림.

## 기술적 고민과 대안 비교

이러한 문제점을 해결하기 위해 고민한 핵심은 **"어떻게 하면 현 상태를 유지하면서도, 미래의 기술적 전환을 유연하게 받아낼 것인가?"**였습니다.

### 1. 계층형 아키텍처(Layered Architecture) 도입
비즈니스 로직을 API 엔드포인트와 분리하여 `Service Layer`를 도입했습니다. 이를 통해 API 라우터는 요청을 검증하고 서비스 로직을 호출하는 역할만 수행하고, 실제 비즈니스 로직은 독립적으로 테스트 가능한 상태로 유지할 수 있게 되었습니다.

### 2. 폴더 구조의 물리적 격리
`web/` 디렉토리를 루트로 설정하고, 그 아래 `backend/`와 `frontend/`를 명확히 분리했습니다.
* **Backend**: `app/` 패키지 구조 내에 `models`, `routers`, `services`를 배치하여 역할 기반 분리.
* **Frontend**: `static`과 `templates`를 분리하여 차후 SPA 프레임워크로 교체 시, 백엔드 로직 수정 없이 `frontend` 폴더만 교체할 수 있는 구조를 마련했습니다.

### 3. Trade-off 분석
* **이점**: 명확한 역할 분담, 향후 기술 스택 변경 시의 이식성 확보, 단위 테스트의 용이성 증가.
* **비용**: 실행 경로 변경에 따른 로컬 개발 환경 재설정 필요, import 경로 관리에 대한 엄격한 규칙 준수 필요.

## 최종 해결: 구조적 정교화

결과적으로 우리는 프로젝트를 다음과 같은 레이어로 구조화하였습니다.

* **Models Layer**: SQLAlchemy를 통한 데이터 정의
* **Routers Layer**: FastAPI의 엔드포인트 정의 및 요청/응답 관리
* **Services Layer**: 비즈니스 핵심 로직(OCR 처리, 매칭 알고리즘 등)
* **Frontend Layer**: 독립된 정적 리소스 및 템플릿 영역

특히, 실행 환경에서의 혼선을 줄이기 위해 `uvicorn` 실행 경로를 명확히 고정하고, `app` 패키지 내부에서의 import 방식은 유지함으로써 기존 코드의 유지보수성을 극대화했습니다.

## 엔지니어링 교훈 (Takeaway)

이번 리팩토링을 통해 **"구조는 곧 문서다"**라는 점을 다시 한번 깨달았습니다. 잘 설계된 폴더 구조는 신규 개발자가 프로젝트에 진입하는 시간을 대폭 줄여주며, 코드 리뷰 과정에서 각 레이어의 책임 소재를 명확히 하여 논쟁을 줄여줍니다.

또한, 당장 필요한 기술 스택(현시점의 Jinja2 템플릿)에 매몰되지 않고, **'언젠가 기술 스택이 바뀔 것'을 가정하고 구조를 설계하는 것**이 기술 부채를 최소화하는 길임을 배웠습니다. 기술 블로그를 읽는 분들도 프로젝트 초기 단계라면, 너무 일찍 최적화할 필요는 없지만, 디렉토리 구조만큼은 최소한의 관심사 분리가 반영된 형태로 시작하시길 권장합니다.
