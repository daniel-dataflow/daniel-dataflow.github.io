스타트업의 초기 제품 개발 단계에서는 빠른 기능 구현이 최우선 과제가 되곤 합니다. 저희의 세이프 푸드 솔루션인 **PickSafe** 역시 유저들에게 핵심 가치를 빠르게 전달하기 위해 속도전에 집중해 왔습니다. 

하지만 서비스가 성장하고 기능이 고도화됨에 따라, 루트 디렉토리에 백엔드 비즈니스 로직과 프론트엔드(Jinja2) 템플릿, 정적 리소스, 각종 설정 파일이 혼재되는 현상이 발생했습니다. 이는 개발자의 인지 과부하(Cognitive Load)를 유발하고 코드 간의 결합도를 높여, 사소한 변경이 예기치 못한 사이드 이펙트를 낳는 원인이 되었습니다.

최근 저희 PickSafe 개발 팀은 이러한 기술 부채를 해결하고, **향후 프론트엔드 아키텍처 전환(React/Next.js)까지 고려한 대대적인 폴더 구조 리팩토링**을 단행했습니다. 이 과정에서 겪었던 기술적 고민과 의사결정의 이유, 그리고 얻은 교훈을 공유합니다.

## 1. 문제 정의: 무엇이 개발 생산성을 가로막고 있었는가?

기존 구조는 백엔드와 프론트엔드의 경계가 모호한 전형적인 초기 모놀리식(Monolithic) 형태였습니다. 이로 인해 다음과 같은 세 가지 실질적인 페인 포인트(Pain Point)가 존재했습니다.

1. **높은 결합도와 확장성의 한계**
   현재는 서버 사이드 렌더링(SSR)을 위해 Jinja2 템플릿 엔진을 사용하고 있습니다. 하지만 향후 모바일 앱 대응 및 고도화된 UI/UX 제공을 위해 React나 Next.js 기반의 싱글 페이지 애플리케이션(SPA)으로 전환할 로드맵을 가지고 있었습니다. 기존 구조에서는 백엔드 API와 템플릿 뷰가 얽혀 있어 프론트엔드 계층만 따로 분리해 내기가 매우 까다로웠습니다.
2. **비즈니스 로직의 파편화**
   OCR 스캔 기능, 알레르기 성분 매칭 로직 등 핵심 도메인 비즈니스 로직이 API 엔드포인트(Router) 레이어와 혼재되어 있었습니다. 이로 인해 동일한 비즈니스 로직을 재사용하기 어렵고, 유닛 테스트(Unit Test)를 작성하기가 매우 난해했습니다.
3. **신규 팀원 온보딩 병목**
   특정 기능(예: 어드민 페이지, 마이페이지)을 수정하기 위해 백엔드 코드와 HTML/CSS/JS 파일이 어디에 위치해 있는지 한눈에 파악하기 어려워, 온보딩 프로세스에서 불필요한 커뮤니케이션 비용이 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

구조 개선을 위해 저희 팀은 두 가지 아키텍처 패턴을 두고 치열하게 토론했습니다.

### 대안 A: 도메인 중심의 모듈형 구조 (Domain-driven Modular Pattern)
사용자(User), 상품(Product), 스캔(Scan) 등 각 도메인별로 폴더를 만들고, 그 내부에 `models.py`, `router.py`, `templates/`를 모두 집어넣는 Django 스타일의 구조입니다.

* **장점:** 특정 도메인을 수정할 때 하나의 폴더 안에서 모든 작업(DB 모델부터 프론트엔드 뷰까지)을 끝낼 수 있어 응집도가 높습니다.
* **단점:** FastAPI는 프레임워크 수준에서 이러한 구조를 강제하지 않기 때문에, 순환 참조(Circular Import) 이슈가 발생하기 쉽습니다. 무엇보다 향후 백엔드 API 서버와 프론트엔드 프로젝트를 완전히 물리적으로 분리(Repository 분리)하고자 할 때 이중 작업이 발생합니다.

### 대안 B: 레이어드 아키텍처 기반의 물리적 격리 구조 (Layered Architecture & Strict Separation)
백엔드(`web/backend`)와 프론트엔드(`web/frontend`)의 최상위 계층을 완전히 격리하고, 백엔드 내부는 역할에 따라 **Models(데이터) - Routers(프레젠테이션) - Services(비즈니스 로직)** 레이어로 명확히 구분하는 구조입니다.

* **장점:** 
  * 백엔드와 프론트엔드의 결합도가 완전히 제거됩니다. 향후 프론트엔드를 React로 전환할 때 `frontend` 디렉토리만 통째로 대체하면 됩니다.
  * 레이어별 역할이 명확하여 코드 가독성과 테스트 용이성이 극대화됩니다.
* **단점:** 폴더 깊이(Depth)가 깊어져 초기 실행 경로 설정 및 임포트 경로 처리에 추가적인 공수가 듭니다.

### 최종 선택: 대안 B
우리는 **"미래의 확장성"**과 **"역할의 명확한 분리(Separation of Concerns)"** 가치를 최우선으로 판단하여 **대안 B**를 선택했습니다.

## 3. 최종 해결: 정립된 PickSafe의 새로운 아키텍처

리팩토링을 통해 완성된 PickSafe의 디렉토리 구조는 다음과 같습니다. 보안과 관련된 민감한 정보 및 원본 스키마는 마스킹 처리하거나 제거하고, 논리적 구조 위주로 재구성했습니다.

```
/picksafe
  /web
    /backend
      /app
        /models       (SQLAlchemy ORM 모델 레이어 - DB 테이블 정의)
          __init__.py
          user.py
          product.py
          scan.py
        /routers      (FastAPI 라우터 및 Jinja2 뷰 렌더링 엔드포인트)
          __init__.py
          auth.py
          scan.py
          products.py
        /services     (도메인 비즈니스 로직 레이어 - OCR, 매칭 엔진 등)
          __init__.py
          ocr_service.py
          ingredient_matcher.py
        config.py     (Pydantic Settings 기반 환경 설정 관리)
        database.py   (SQLAlchemy 연결 및 세션 라이프사이클 관리)
        main.py       (FastAPI 애플리케이션 엔트리포인트)
      requirements.txt
    /frontend
      /static         (Pure 정적 리소스 - CSS, JS, Images)
        /css
        /js
      /templates      (Jinja2 HTML 템플릿 레이어)
        base.html
        scan.html
        result.html
  /docs               (아키텍처 정의서 및 ADR 문서 관리)
  .env
```

### 핵심 레이어별 역할 정의

1. **`models` 레이어**: 데이터베이스 엔티티 정의에만 집중합니다. 비즈니스 규칙이나 프레젠테이션 로직은 이곳에 침범하지 못합니다.
2. **`services` 레이어**: OCR 결과 파싱, 알레르기 유발 성분 매칭 알고리즘 등 핵심 비즈니스 로직을 담당합니다. 웹 프레임워크(FastAPI)나 HTTP 요청/응답 객체에 의존하지 않는 **순수 파이썬 코드**로 작성되어 있어, 독립적인 유닛 테스트가 매우 쉬워졌습니다.
3. **`routers` 레이어**: 클라이언트의 요청을 받아 적절한 `services`를 호출하고, 그 결과를 JSON이나 Jinja2 템플릿(프론트엔드 레이어)에 바인딩하여 응답하는 역할만 수행합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 폴더 구조 마이그레이션 작업을 통해 저희 팀은 값진 엔지니어링 경험을 얻었습니다.

* **코드 배치의 직관성이 곧 생산성이다**
  새 구조 도입 이후, 버그 리포트가 들어왔을 때 어느 레이어의 코드를 수정해야 하는지 토론하는 시간이 거의 사라졌습니다. "OCR 인식 오류는 `services/ocr_service.py`를, 매칭 화면 UI 수정은 `frontend/templates/result.html`을 보면 된다"는 직관성이 확보되었습니다.
* **아키텍처는 비즈니스 로드맵과 발맞추어 진화해야 한다**
  처음부터 완벽한 아키텍처를 설계하느라 시간을 허비하는 것보다, 서비스의 성장 속도에 맞춰 적절한 시점(Pivot Point)에 리팩토링을 결단하는 것이 중요합니다. 이번 리팩토링 덕분에 저희는 향후 웹 Front-end 리빌딩과 모바일 앱 출시라는 비즈니스 로드맵을 기술적 걸림돌 없이 안정적으로 수용할 수 있게 되었습니다.
* **인프라 및 구동 환경의 변화 관리**
  구조를 변경하면서 Uvicorn 구동 경로가 `web/backend` 내부로 변경되는 등의 환경적 변화가 있었습니다. 이를 문서화(`ADR`)하고 실행 스크립트를 표준화하여 팀원들의 로컬 개발 환경 혼선을 최소화하는 과정 역시 아키텍처 변경만큼 중요하다는 것을 배웠습니다.

PickSafe 팀은 앞으로도 변화에 유연하게 대응할 수 있는 단단한 소프트웨어를 만들기 위해, 지속적으로 기술 부채를 상환하고 아키텍처를 개선해 나갈 것입니다. 다음 포스팅에서는 개선된 구조를 바탕으로 구축한 **'도메인 서비스 레이어의 격리된 유닛 테스트 환경 구축기'**로 찾아오겠습니다.
