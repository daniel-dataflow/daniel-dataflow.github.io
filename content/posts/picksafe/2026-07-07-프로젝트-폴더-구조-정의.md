안녕하세요, PickSafe 백엔드 팀입니다. 

서비스가 성장하고 기능이 확장됨에 따라, 초기 개발 속도에 초점을 맞춰 구성했던 모놀리식 단일 루트 디렉토리 구조는 점차 기술 부채로 다가왔습니다. 특히 프론트엔드와 백엔드의 경계가 모호해지고, 비즈니스 로직이 라우터에 섞이는 현상이 발생하기 시작했습니다.

이번 포스팅에서는 **"어떻게 하면 향후 확장성(예: 프론트엔드 분리)을 확보하고, 유지보수하기 좋은 구조를 만들 것인가?"**에 대한 고민과 그 해결책으로 선택한 계층형 아키텍처(Layered Architecture) 기반의 디렉토리 구조 마이그레이션 과정을 공유합니다.

---

## 1. Problem: 마주한 기술적 문제

초기 프로젝트는 빠른 프로토타이핑을 위해 단일 루트 아래 스크립트와 설정 파일, 템플릿들이 혼재되어 있었습니다. 이로 인해 다음과 같은 문제가 발생했습니다.

1. **관심사의 혼재 (Separation of Concerns 부족)**
   - API 엔드포인트를 처리하는 라우터 내부에 데이터베이스 쿼리와 외부 OCR 연동 같은 비즈니스 로직이 함께 얽히면서 코드의 가독성이 떨어지고 단위 테스트 작성(Testability)이 어려워졌습니다.
2. **프론트엔드/백엔드 결합도 문제**
   - 현재는 FastAPI의 Jinja2 템플릿을 활용해 SSR(Server-Side Rendering) 방식으로 동작하고 있지만, 향후 서비스 고도화를 위해 React나 Next.js 같은 모던 프론트엔드 프레임워크로 전환할 가능성이 열려 있었습니다. 하지만 기존 구조에서는 프론트엔드 리소스(HTML/CSS/JS)가 백엔드 코드와 강하게 결합되어 있어 리팩토링 비용이 매우 클 것으로 예상되었습니다.

---

## 2. Trade-off & Decision: 왜 이 구조를 선택했는가?

이 문제를 해결하기 위해 두 가지 대안을 두고 고민했습니다.

* **대안 A: 기능별(Feature-based) 패키지 구조**
  * 도메인별로 폴더를 묶는 방식 (예: `users/`, `scan/`, `products/` 등 각 폴더에 모델, 라우터, 서비스가 공존).
  * *장점:* 특정 도메인 관련 코드를 한곳에서 응집력 있게 관리할 수 있음.
  * *단점:* 초기 소규모 팀에게는 오버엔지니어링일 수 있으며, 전역 설정이나 공통 서비스(OCR, 보안 등)의 의존성 관리가 복잡해질 수 있음.

* **대안 B: 명확한 계층형(Layered) 구조 + 웹 리소스 격리 (선택한 방식)**
  * `web/` 하위에 프론트엔드와 백엔드를 물리적으로 분리하고, 백엔드 내부를 다시 `models`(데이터), `routers`(인터페이스), `services`(비즈니스 로직)로 엄격히 분리하는 방식.

### 최종 의사결정: 대안 B
우리는 현재 팀 규모와 추후 **프론트엔드 독립(API 서버화)** 가능성을 높게 평가하여 대안 B를 선택했습니다.

```
/picksafe
  /web
    /backend
      /app
        /models       # SQLAlchemy ORM 모델 (ERD 설계서 기준)
        /routers      # 엔드포인트 및 뷰 렌더링
        /services     # 핵심 비즈니스 로직 (OCR, 매칭, 보안 등)
        config.py     # Pydantic Settings 환경 설정
        database.py   # DB 연결 및 세션 관리
        main.py       # FastAPI 진입점
    /frontend
      /static         # CSS, JS, 이미지
      /templates      # Jinja2 HTML 템플릿
```

이 구조를 통해 얻고자 한 목표는 명확합니다.
- **백엔드 레이어의 책임 분리:** `Router`는 요청/응답만 다루고, `Service`는 순수 비즈니스 로직을, `Model`은 데이터 정의만 담당하도록 격리합니다.
- **클라이언트 교체 용이성:** 추후 프론트엔드를 SPA/SSR 독립 프레임워크로 전환할 때 `/web/frontend` 디레토리만 들어내어 교체하거나 별도 레포지토리로 분리하기 쉽도록 설계했습니다.

---

## 3. Takeaway: 무엇을 배웠고 어떻게 적용했는가?

1. **실행 경로(Execution Path)의 변화 관리**
   - 디렉토리가 `web/backend` 계층 아래로 이동함에 따라, Uvicorn 서버 구동 명령어 역시 변경이 필요했습니다 (`uvicorn web.backend.app.main:app --reload` 또는 해당 디렉토리 내부에서 구동). 배포 파이프라인(CI/CD)이나 작업 지침서 문서도 함께 업데이트하여 팀원들의 혼선을 최소화했습니다.
2. **임포트(Import) 안정성 유지**
   - 패키지 내부의 모듈 구조(`from app.models.user import User`)는 유지하여, 대규모 디렉토리 이동임에도 불구하고 비즈니스 로직 코드의 대대적인 수정 없이 원활한 마이그레이션을 마칠 수 있었습니다.

---

### 마무리하며

좋은 아키텍처는 "처부터 완벽한 구조"를 만드는 것이 아니라, **"비즈니스 변화와 기술적 전환(Migration)에 유연하게 대응할 수 있는 구조"**를 갖추는 것임을 이번 리팩토링을 통해 다시 한번 체감했습니다. 

PickSafe는 앞으로도 확장 가능하고 견고한 엔지니어링 기반 위에서 안전하고 유용한 서비스를 만들어 나갈 것입니다. 다음 포스팅에서는 이 아키텍처 위에서 구현한 OCR 기반 성분 매칭 로직에 대해 다뤄보겠습니다. 감사합니다!
