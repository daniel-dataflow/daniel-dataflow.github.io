안녕하세요, PickSafe 백엔드 개발 팀입니다. 

서비스가 성장하고 기능이 확장됨에 따라, 초기 빠르게 프로토타이핑을 진행하며 잡았던 프로젝트 구조의 한계를 마주하게 되었습니다. 이번 글에서는 모놀리식 환경에서 향후 프론트엔드 분리 및 유지보수성을 극대화하기 위해 **어떤 고민을 거쳐 폴더 구조를 재정의(Migration)** 했는지, 그리고 그 과정에서 고려한 기술적 트레이드오프를 공유하고자 합니다.

---

## 1. Problem: 무엇을 마주했는가?

프로젝트 초기에는 개발 속도를 높이기 위해 루트 디렉토리에 백엔드와 프론트엔드 관련 리소스가 혼재되어 있었습니다. 하지만 다음과 같은 문제가 점차 가시화되었습니다.

* **관심사의 혼재:** API 엔드포인트, 비즈니스 로직, 데이터베이스 모델, 그리고 Jinja2 템플릿과 정적 파일들이 모호하게 얽히면서 코드 내비게이션 비용이 증가했습니다.
* **확장성의 제약:** 현재는 서버 사이드 렌더링(Jinja2) 기반으로 빠르게 서비스를 구축하고 있지만, 향후 모던 프론트엔드(React, Next.js 등)로 전환하거나 모바일 앱 클라이언트를 확장할 때 현재 구조로는 프론트엔드 레이어의 완전한 독립이 어려웠습니다.
* **테스트 용이성 저하:** 라우터와 비즈니스 로직(OCR 스캔, 성분 매칭 등)이 강하게 결합될 경우, 단위 테스트(Unit Test) 작성 시 의존성을 Mocking하기 까다로워지는 문제가 있었습니다.

---

## 2. Trade-off & Architecture: 왜 이 방식을 선택했는가?

이 문제를 해결하기 위해 **"관심사 분리(Separation of Concerns)"**와 **"미래 확장성(Future-proofing)"**을 최우선 원칙으로 삼고 디렉토리 구조를 전면 재설계했습니다.

### ① `web/backend`와 `web/frontend`의 물리적 격리
* **대안 A:** 기존처럼 단일 루트에 모든 파일을 두고 패키지만 나누기
  * *장점:* 설정이 단순하고 초기 실행 경로가 직관적임.
  * *단점:* 추후 프론트엔드 스택이 변경되거나 별도 팀으로 협업할 때 리소스 충돌 발생 우려.
* **대안 B (선택):** `web/` 하위에 `backend`와 `frontend`를 완전히 격리
  * *장점:* 향후 프론트엔드 영역을 별도의 독립된 리포지토리나 프레임워크(React 등)로 교체하기 매우 용이함. 배포 파이프라인 역시 프론트엔드/백엔드로 분리하기 수월해짐.

### ② FastAPI 전형적인 3계층 아키텍처 (Layered Architecture) 적용
백엔드 내부(`web/backend/app`)는 다음과 같이 책임을 명확히 분리했습니다.

* **`routers/` (Interface Layer):** HTTP 요청을 받고 응답을 반환하는 진입점. Jinja2 뷰 렌더링 및 API 엔드포인트 담당.
* **`services/` (Business Logic Layer):** OCR 스캔, 성분 매칭 알고리즘, 보안 및 이메일 전송 등 핵심 비즈니스 로직 집약. 라우터는 비즈니스 로직을 직접 알지 못하고 서비스 레이어를 호출하기만 함.
* **`models/` & `database.py` (Data Access Layer):** SQLAlchemy ORM 모델과 DB 세션 관리 분리.

## 3. 최종 해결 및 폴더 구조

위와 같은 고민을 반영하여 정돈된 최종 디렉토리 구조는 다음과 같습니다.

```text
/picksafe
  /web
    /backend
      /app
        /models       (ERD 설계서 테이블 단위 SQLAlchemy ORM 모델)
        /routers      (기능 단위 라우터 및 뷰 렌더링 엔드포인트)
        /services     (스캔 OCR, 매칭 등 핵심 비즈니스 로직)
        config.py     (Pydantic Settings 환경 설정)
        database.py   (SQLAlchemy DB 연결 엔진 및 세션 관리)
        main.py       (FastAPI 진입점)
      requirements.txt
    /frontend
      /static         (CSS, JS, 이미지 등 정적 리소스)
      /templates      (Jinja2 HTML 템플릿)
  /docs               (기획, 설계 및 의사결정 문서)
  .env
  .gitignore
  README.md
```

### 💡 주의할 점 (Migration Impact)
구조가 변경됨에 따라 Uvicorn 실행 경로가 조정되었습니다. 이제 백엔드 구동 시 `web/backend` 디렉토리 내부에서 실행하거나 적절한 모듈 경로를 지정해야 합니다.
```bash
# 예시
uvicorn app.main:app --reload (web/backend 디렉토리 내부에서 실행 시)
```
다만, 내부 패키지 임포트 경로는 `app` 패키지 기준으로 유지(`from app.models.user import User`)하여 기존 코드의 대규모 수정 소요를 최소화했습니다.

## 4. Takeaway: 무엇을 배웠는가?

1. **초기 구조 설계의 중요성:** 프로젝트가 커진 뒤의 리팩토링은 비용이 큽니다. 비록 프로토타이핑 단계라 하더라도 **서비스 레이어와 라우터 레이어의 분리**는 처음부터 가져가는 것이 기술 부채를 줄이는 지름길입니다.
2. **확장성을 고려한 디렉토리 배치:** 프론트엔드와 백엔드를 `web` 하위로 묶어 격리함으로써, 향후 아키텍처 진화(예: SPA 분리)에 유연하게 대응할 수 있는 기반을 다졌습니다.

PickSafe 팀은 앞으로도 견고하고 확장 가능한 아키텍처를 바탕으로 사용자에게 안전하고 빠른 서비스를 제공하기 위해 고민하겠습니다. 감사합니다!
