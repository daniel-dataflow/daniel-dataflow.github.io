안녕하세요, PickSafe 백엔드 팀입니다. 

서비스가 성장함에 따라 코드베이스의 규모도 점차 커지기 마련입니다. 초기 개발 속도를 높이기 위해 단일 디렉토리 구조로 시작했던 PickSafe 역시, 기능이 확장되면서 코드의 응집도는 떨어지고 결합도는 높아지는 기술 부채를 마주하게 되었습니다. 

이번 글에서는 **외부 프론트엔드 교체 가능성(Extensibility)**과 **비즈니스 로직의 명확한 관심사 분리(Separation of Concerns)**를 목표로 단행한 폴더 구조 리팩토링 과정과 그 아키텍처적 의사결정(Trade-off)을 공유하고자 합니다.

---

## 1. Problem: 무엇을 마주했는가?

초기 프로젝트는 빠른 프로토타이핑을 위해 루트 디렉토리에 백엔드와 프론트엔드 관련 파일들이 혼재되어 있었습니다. 

이로 인해 발생한 문제점은 명확했습니다.
- **관심사의 혼재:** API 엔드포인트를 처리하는 코드와 템플릿 렌더링, 정적 파일(CSS/JS)의 경계가 모호해져 프로젝트 루트가 비대해졌습니다.
- **확장성의 한계:** 현재는 서버 사이드 렌더링(Jinja2) 기반으로 빠르게 서비스를 전개하고 있으나, 향후 프론트엔드를 React나 Next.js 같은 SPA/SSR 프레임워크로 전환할 때 디렉토리 구조 변경에 막대한 리스크가 발생할 구조였습니다.
- **유지보수성 저하:** 비즈니스 로직(OCR 스캔, 성분 매칭 등)과 데이터 접근 레이어, 라우터가 유기적으로 분리되지 않아 새로운 기능을 추가할 때마다 사이드 이펙트 파악이 어려워졌습니다.

---

## 2. Trade-off & Architecture: 왜 이 방식을 선택했는가?

이 문제를 해결하기 위해, 우리는 **"현재의 개발 생산성"**과 **"미래의 확장성"** 사이의 균형을 맞추는 아키텍처를 설계해야 했습니다. 

대안 검토 끝에, 우리는 **FastAPI의 모듈러 단일체(Modular Monolith) 패턴**을 채택하고, 프론트엔드와 백엔드의 물리적 디렉토리를 완전히 격리하는 방식을 선택했습니다.

### 최종 폴더 구조 설계
```text
/picksafe
  /web
    /backend
      /app
        /models       # SQLAlchemy ORM 모델 (테이블 단위)
        /routers      # FastAPI 라우터 및 뷰 렌더링 엔드포인트
        /services     # 핵심 비즈니스 로직 (OCR, 매칭, 보안 등)
        config.py     # Pydantic Settings 환경 설정
        database.py   # DB 연결 엔진 및 세션 관리
        main.py       # FastAPI 애플리케이션 진입점
      requirements.txt
    /frontend
      /static         # CSS, JS, 이미지 등 정적 리소스
      /templates      # Jinja2 HTML 템플릿
  /docs               # 아키텍처 및 의사결정 문서 관리
  .env
  README.md
```

### 왜 레이어를 이렇게 나누었을까? (핵심 설계 원칙)

1. **`web/backend`와 `web/frontend`의 물리적 분리**
   - 현재는 Jinja2 템플릿을 활용해 빠른 렌더링을 수행하지만, 프론트엔드 코드를 `web/frontend`로 격리함으로써 향후 API 서버(Backend)와 클라이언트(Frontend)를 완전히 독립된 리포지토리나 서비스로 분리할 때 드는 비용을 최소화했습니다.

2. **철저한 계층화 (Routers vs Services vs Models)**
   - **Routers:** HTTP 요청을 받고 응답을 반환하는 역할에만 집중합니다.
   - **Services:** OCR 스캔, 알러지 성분 매칭 등 핵심 비즈니스 로직을 캡슐화합니다. 비즈니스 로직이 라우터나 모델에 종속되지 않아 단위 테스트(Unit Test) 작성 용이성이 극대화되었습니다.
   - **Models:** ERD 설계를 반영한 SQLAlchemy ORM 모델을 독립적으로 관리합니다.

## 3. Implementation & Troubleshooting: 마이그레이션 과정의 도전

구조를 개편하면서 직면한 가장 큰 기술적 도전은 **실행 경로(Execution Path)의 변경**이었습니다.

- **기존:** 루트 디렉토리 기준 `uvicorn app.main:app --reload`
- **변경 후:** 백엔드 소스 코드가 `web/backend` 하위로 이동함에 따라, Uvicorn 실행 시 작업 디렉토리(Working Directory)를 고려해야 하거나 실행 경로를 조정해야 하는 상황이 발생했습니다.

우리는 임포트 안정성을 유지하기 위해 `app` 패키지 내부의 절대/상대 임포트 규칙(`from app.models.user import User` 등)은 그대로 유지하되, 진입점(`main.py`)의 위치와 애플리케이션 구동 가이드를 `docs/decisions`에 문서화하여 팀원 간의 혼선을 방지했습니다.

## 4. Takeaway: 무엇을 배웠고 얻었는가?

1. **초기 구조 설계의 중요성:** 프로젝트가 커진 뒤의 리팩토링은 비용이 큽니다. 비록 규모가 작은 초기 단계라 할지라도, **"언젠가 분리될 것"을 가정하고 경계를 그어두는 것**이 기술 부채를 줄이는 가장 빠른 길임을 다시 한번 확인했습니다.
2. **관심사의 분리가 주는 가독성:** 라우터, 서비스, 모델의 역할이 코드로 명확히 드러나다 보니, 새로운 팀원이 합류하거나 새로운 기능(예: 새로운 OCR 알고리즘 도입)을 추가할 때 코드를 파악하는 시간이 대폭 단축되었습니다.

PickSafe는 이번 아키텍처 정비를 바탕으로, 더욱 견고하고 확장 가능한 헬스케어 비즈니스 로직을 안정적으로 쌓아갈 준비를 마쳤습니다. 앞으로도 서비스의 성장과 함께 진화하는 PickSafe의 기술 여정을 기대해 주세요!
