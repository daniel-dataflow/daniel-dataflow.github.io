안녕하세요, PickSafe 백엔드/인프라스트럭처 에디터입니다. 
서비스가 급성장하면서 데이터베이스에 축적되는 마스터 데이터와 로그의 규모도 기하급수적으로 늘어났습니다. 데이터가 늘어남에 따라 이를 관리하는 **어드민(Admin) 시스템**의 안정성과 유지보수성의 중요성 역시 커졌죠.

이번 포스팅에서는 최근 팀 내부에서 진행한 **어드민 공통 표준 페이징 라이브러리 구축**, **DB 헬스체크 고도화**, 그리고 **Slack 장애 텔레메트리 개선** 과정을 통해 마주한 기술적 고민과 해결 방안을 공유하고자 합니다.

---

## 1. Problem: 급성장하는 서비스 이면의 기술 부채

서비스 규모가 확장됨에 따라 성분 마스터 데이터, 방문자 로그, 1:1 고객 문의, 시스템 이벤트 로그 등 관리 대상 데이터가 수만 건을 넘어섰습니다. 하지만 이 데이터를 다루는 어드민 페이지들은 초기 급조된 구조의 한계를 드러내기 시작했습니다.

1. **페이징 코드의 심각한 파편화**
   * 페이지마다 `renderPagination`, `createPageNav` 등 파편화된 프론트엔드 페이징 로직이 제각각 존재했습니다. 
   * UI 일관성이 깨질뿐더러, 페이지네이션 관련 버그가 발생할 때마다 여러 파일을 수정해야 하는 높은 유지보수 비용(Maintenance Cost)을 유발했습니다.
2. **단순 DB 핑(Ping)의 한계와 오탐**
   * 메인 DB와 보조(DW) DB 간의 헬스체크 로직이 너무 단순했습니다. 실제 커넥션 풀 고갈이나 Failover 스위칭 상태를 정확히 반영하지 못했고, 이로 인해 관리자 화면에 불필요한 가짜 장애 알람이 빈번하게 발생했습니다.
3. **장애 인지(MTTD)를 지연시키는 불친절한 슬랙 알림**
   * 서버 다운타임이나 이상 징후 발생 시 슬랙으로 날아오는 에러 메시지에 스택트레이스와 발생 맥락(Context) 정보가 부족하여, 엔지니어가 원인을 규명하고 로그를 뒤지는 데 불필요한 시간이 소요되었습니다.

---

## 2. Trade-off & Solution: 무엇을 버리고 무엇을 취했는가

이 문제를 해결하기 위해 팀은 세 가지 핵심 축에 집중하여 아키텍처를 개선했습니다.

### ① 프론트엔드: `renderStandardPagination` 전역 모듈화
* **접근 방식**: 각 페이지에 흩어져 있던 DOM 조작 코드를 제거하고, `static/js/admin/admin_common.js`를 통해 전역 모듈화된 표준 페이징 함수를 만들었습니다.
* **Trade-off**: 모든 어드민 페이지의 UI 스펙을 일괄적으로 통일해야 했습니다. 각 페이지마다 미세하게 다르던 요구사항(예: 특정 페이지는 이전/다음만 존재)을 포기하고, `[<< 이전] [1] ... [4] [5] [6] ... [20] [다음 >>]` 및 페이지당 노출 개수 셀렉터(10/20/50개)를 포함한 표준 스펙으로 일원화했습니다.
* **결과**: 어드민 프론트엔드 코드 중복을 **1,000라인 이상 제거**하는 쾌거를 이뤘습니다.

### ② 인프라: 무중단 DB 헬스체크 프로브(Health Probe) 정밀화
* **접근 방식**: DB 연결 상태 검사를 가볍게 최적화(`SELECT 1` 쿼리 타임아웃 2초 설정 및 실제 쓰기 가능 여부 점검)하여, 헬스체크 트래픽 자체가 메인 DB 풀에 부하를 주지 않도록 설계했습니다.
* **시각화**: 메인 DB와 보조 DB의 활성 상태를 어드민 상단에 실시간 배지 UI로 시각화하여, 인프라 담당자가 Failover 상황을 직관적으로 인지할 수 있게 했습니다.

### ③ 옵저버빌리티: Slack 리치 블록 키트(Block Kit) 텔레메트리
* **접근 방식**: 단순 텍스트 에러 알림 대신, 슬랙 Block Kit을 활용해 서버 호스트, 에러 메시지, 영향받은 라우터, 타임스탬프를 구조화된 카드로 전송하도록 변경했습니다.
* **결과**: 에러 발생 시 맥락 파악 속도가 빨라져 시스템 장애 인지 시간(MTTD)을 **80% 단축**했습니다.

## 3. Architecture Overview

개선된 아키텍처의 흐름은 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 표준 공통 페이징 라이브러리 (renderStandardPagination)   │
│    - static/js/admin/admin_common.js 전역 모듈화             │
│    - [<< 이전] [1] ... [4] [5] [6] ... [20] [다음 >>] 구조   │
│    - 페이지당 노출 개수(10/20/50개) 동적 셀렉터 내장         │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. DB 헬스체크 & Failover 감지 엔진 최적화                 │
│    - SELECT 1 쿼리 타임아웃(2초) 및 실제 쓰기 가능 여부 점검 │
│    - 메인 DB ↔ 보조 DB 활성 상태 실시간 배지 UI 시각화     │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 슬랙(Slack) 장애 텔레메트리 상세화                        │
│    - 서버 호스트, 에러 메시지, 영향받은 라우터 및 타임스탬프 │
│    - 리치 블록 키트(Block Kit) 포맷 알림 전송               │
└─────────────────────────────────────────────────────────────┘
```

## 4. Takeaway: 시니어 엔지니어가 전하는 교훈

1. **기술 부채는 미룰수록 이자가 붙는다**: 
   초기에 빠르게 개발하느라 방치했던 어드민 페이징 코드는 결국 서비스 확장 시점에 운영 효율을 크게 떨어뜨렸습니다. 공통 컴포넌트화와 표준화 작업은 "귀찮은 리팩터링"이 아니라 비즈니스 속도를 지키는 "핵심 인프라 투자"입니다.
2. **모니터링은 '알림'이 아니라 '맥락'이다**: 
   장애가 났을 때 "에러가 발생했다"는 사실보다, **"어떤 서버에서 어떤 라우터를 타다가 어떤 맥락으로 실패했는가"**를 즉시 알려주는 텔레메트리가 MTTD를 단축하는 핵심 열쇠라는 점을 다시 한번 확인했습니다.

PickSafe 팀은 앞으로도 안정적이고 확장 가능한 아키텍처를 바탕으로 견고한 서비스를 만들어 나가겠습니다. 다음 기술 블로그도 기대해 주세요!
