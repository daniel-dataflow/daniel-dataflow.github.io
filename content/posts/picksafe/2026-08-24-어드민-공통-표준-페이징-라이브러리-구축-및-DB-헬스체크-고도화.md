서비스가 성장함에 따라 비즈니스 데이터는 기하급수적으로 늘어납니다. 성분 마스터 데이터, 사용자 로그, 1:1 문의 등 관리해야 할 데이터가 수만 건을 돌파하면서, 이를 다루는 **백오피스(어드민) 시스템의 안정성과 유지보수성**은 서비스 본체만큼이나 중요해집니다.

이번 글에서는 PickSafe 개발팀이 어드민 시스템의 레거시 부채를 청산하고, 대규모 데이터를 효율적으로 다루기 위해 **공통 페이징 라이브러리를 구축**하며, **DB 헬스체크 및 장애 알림(Telemetry)을 고도화**한 기술적 의사결정과 문제 해결 과정을 공유합니다.

---

## 1. 문제 정의 (Context & Problem)

초기 어드민 페이지들은 빠른 기능 개발에 집중한 나머지, 다음과 같은 기술적 부채가 누적되었습니다.

1. **페이징 코드의 심각한 파편화**
   * 페이지마다 개발자가 각자의 입맛에 맞게 페이징 UI 함수(`renderPagination`, `createPageNav` 등)를 구현했습니다. 이로 인해 미세한 UI 버그가 반복 발생했고, 리스트 조회 조건이 바뀔 때마다 프론트엔드 코드를 수정해야 하는 높은 유지보수 비용이 발생했습니다.
2. **단순 DB 핑(Ping) 방식의 한계**
   * 메인 DB와 보조(DW) DB 간의 헬스체크가 단순 연결 확인에 그쳤습니다. 실제 커넥션 풀 고갈이나 페일오버(Failover) 스위칭 상태를 정확히 반영하지 못해, 관리자 화면에 불필요한 오탐(False Positive) 알람이 빈번했습니다.
3. **슬랙 장애 알림의 맥락(Context) 부족**
   * 서버 장애나 이상 징후 발생 시 슬랙으로 전송되는 에러 메시지가 단순 텍스트 수준이었습니다. 에러 스택트레이스와 발생 맥락이 부족하여 원인 파악(MTTD, 평균 탐지 시간)에 불필요한 시간이 소요되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs & Solution)

우리는 이 문제를 해결하기 위해 **프론트엔드 코드 중복 제거**, **안전한 헬스 프로브**, 그리고 **가독성 높은 텔레메트리**라는 세 가지 축을 세웠습니다.

```
[아키텍처 개요]
┌─────────────────────────────────────────────────────────────┐
│ 1. 표준 공통 페이징 라이브러리 (renderStandardPagination)   │
│    - 전역 모듈화 및 동적 셀렉터(10/20/50개) 내장               │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. 무중단 DB 헬스체크 & Failover 감지 엔진                   │
│    - 타임아웃 제어 및 실시간 Active DB 시각화               │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 슬랙(Slack) Block Kit 기반 텔레메트리                    │
│    - 호스트, 에러, 라우터 정보 포함 리치 포맷 알림 전송       │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. 프론트엔드 페이징의 전역 모듈화 (`admin_common.js`)
* **대안 검토**: 각 페이지별 프레임워크 도입 vs 순수 바닐라 JS 기반 공통 모듈화
* **선택**: 어드민 전용 공통 정적 자산인 `admin_common.js`에 `renderStandardPagination` 함수를 전역 모듈화했습니다.
* **이유**: 무거운 프론트엔드 프레임워크를 도입하는 것보다, 기존 템플릿 엔진 환경에서 단 1줄의 함수 호출(`renderStandardPagination(...)`)만으로 직관적인 반응형 네비게이션과 페이지 당 노출 개수(10/20/50개) 동적 셀렉터를 제공하는 것이 마이그레이션 비용과 학습 곡선 측면에서 가장 합리적이었습니다.

### 2.2. 부하를 주지 않는 경량 DB 헬스 프로브
* **문제점**: 빈번한 DB 헬스체크가 오히려 DB 커넥션 풀을 고갈시키거나 불필요한 락(Lock)을 유발할 위험이 있었습니다.
* **해결**: 타임아웃(2초 이내)을 엄격하게 건 가벼운 상태 점검 쿼리를 수행하고, 메인 DB와 보조 DB의 활성 상태를 판별하여 어드민 상단에 실시간 배지 UI로 시각화했습니다. 이를 통해 운영자가 인프라의 상태를 직관적으로 인지할 수 있게 되었습니다.

### 2.3. Slack Block Kit을 활용한 텔레메트리 강화
* 텍스트 기반의 단조로운 알림 대신, Slack Block Kit을 도입하여 **서버 호스트, 발생 시각, 영향받은 라우터, 상세 에러 메시지**를 구조화된 카드로 전송하도록 개선했습니다.

## 3. 결과 및 엔지니어링 교훈 (Results & Takeaways)

이번 표준화 작업과 모니터링 고도화를 통해 다음과 같은 정량적/정성적 성과를 거두었습니다.

* **코드 베이스 경량화**: 어드민 프론트엔드 전반에 걸쳐 중복되던 레거시 코드 **1,000라인 이상을 제거**하여 유지보수성을 대폭 향상시켰습니다.
* **장애 대응력 강화**: 표준화된 페이징으로 대용량 성분 데이터(30,000+건) 탐색 편의성이 극대화되었으며, 개선된 텔레메트리와 헬스체크 덕분에 **시스템 장애 인지 시간(MTTD)을 80% 단축**했습니다.

> **💡 에디터의 Takeaway**
> "백오피스(Admin) 시스템은 비즈니스의 속도에 밀려 기술적 부채가 쌓기 쉬운 영역입니다. 하지만 서비스가 성장할수록 백오피스의 안정성은 곧 운영 효율성과 직결됩니다. 
> 이번 작업은 거대한 아키텍처 개편이 아니라, **'반복되는 파편화를 하나로 모으고(표준화), 시스템의 맥락을 투명하게 드러내는 것(관측 가능성)'**만으로도 얼마나 큰 엔지니어링 임팩트를 낼 수 있는지 증명한 좋은 사례입니다."
