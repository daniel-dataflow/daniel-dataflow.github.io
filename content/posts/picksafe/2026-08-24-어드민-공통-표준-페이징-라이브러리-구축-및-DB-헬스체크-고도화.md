안녕하세요, PickSafe 백엔드/플랫폼 팀입니다. 

서비스가 성장함에 따라 성분 마스터 데이터(3만 건 이상), 방대한 방문자 로그, 1:1 고객 문의 내역 등 관리해야 할 데이터가 급증했습니다. 이에 비례하여 어드민 시스템의 부하도 커졌고, 백오피스 환경 전반의 레거시 코드로 인한 기술 부채가 수면 위로 떠올랐습니다.

이번 글에서는 **어드민 공통 표준 페이징 라이브러리 구축**, **DB 헬스체크 및 Failover 감지 고도화**, 그리고 **Slack 텔레메트리 상세화**를 통해 시스템 안정성과 운영 효율성을 극대화한 아키텍처 의사결정 과정을 공유합니다.

---

## 1. 배경 및 문제 상황 (Context & Problem)

초기 어드민 시스템은 빠른 기능 구현에 집중한 나머지 다음과 같은 구조적 한계를 마주했습니다.

1. **페이징 코드의 심각한 파편화**
   * 성분 관리, 번역 관리, 방문자 로그 등 각 페이지마다 `renderPagination`, `createPageNav` 등 서로 다른 페이징 UI 함수를 각자 구현하고 있었습니다. 
   * 이로 인해 디자인 일관성이 깨지고, 페이징 관련 버그가 발생할 때마다 모든 페이지를 수정해야 하는 높은 유지보수 비용이 발생했습니다.
2. **단순 DB 핑(Ping)의 한계와 모니터링 공백**
   * 메인 DB와 보조(DW) DB 간의 헬스체크 로직이 단순 연결 여부만 확인하는 단편적인 수준이었습니다.
   * 실제 커넥션 풀 고갈이나 Failover 스위칭 상태를 정확히 반영하지 못해, 관리자 화면에 불필요한 가짜 장애 알람이 빈번하게 발생했습니다.
3. **슬랙(Slack) 장애 알림의 정보 부족**
   * 서버 다운타임이나 이상 징후 발생 시 단순 에러 메시지만 전송되어, 어떤 호스트에서 어떤 라우터 처리 중 발생한 문제인지 파악하기 어려워 원인 규명(MTTR)에 오랜 시간이 소요되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 2.1. 프론트엔드 페이징: 전면 SPA 전환 vs 바닐라 JS 공통 모듈화
* **대안 A (SPA 프레임워크 전면 도입)**: React/Vue 등으로 어드민을 재구축하는 방안. 
  * *Trade-off*: 근본적인 해결책이지만, 현재 백엔드 중심의 템플릿 렌더링 구조를 전면 들어내야 하므로 전환 비용과 리소스가 너무 큼.
* **대안 B (바닐라 JS 기반 전역 공통 모듈화)**: `admin_common.js`를 신설하여 표준화된 페이징 함수(`renderStandardPagination`)를 배포하는 방안.
  * *Trade-off*: 최신 프레임워크의 이점을 다 가져올 순 없지만, 최소한의 공수(Low Cost)로 프론트엔드 코드 중복을 획기적으로 제거하고 일관된 UX를 제공할 수 있음.
* **선택**: **대안 B**. 1,000라인 이상의 중복 코드를 제거하고, 페이지당 노출 개수(10/20/50개)를 동적으로 제어할 수 있는 표준 UI 컴포넌트를 완성했습니다.

### 2.2. DB 헬스체크: 무거운 트랜잭션 검사 vs 경량화 쿼리 프로브(Probe)
* **대안 A (전체 테이블 조회 검증)**: 실제 비즈니스 테이블을 `SELECT`하여 데이터 정합성까지 확인.
  * *Trade-off*: 헬스체크 주기마다 DB에 과도한 부하를 주어 오히려 장애를 유발할 위험이 큼.
* **대안 B (최적화된 타임아웃 기반 핑 쿼리)**: `SELECT 1`과 같은 초경량 쿼리에 2초 타임아웃을 걸고, 실제 쓰기 가능 여부를 안전하게 점검하는 방식.
  * *Trade-off*: 복잡한 락(Lock) 상황까지는 완벽히 잡아내지 못하나, DB 커넥션 및 Failover 상태 감지에는 충분함.
* **선택**: **대안 B**. DB 풀에 부담을 주지 않으면서도, 메인 DB와 보조 DB의 활성 상태를 실시간 배지 UI로 어드민 상단에 시각화하여 운영자의 가시성을 높였습니다.

### 2.3. 장애 텔레메트리: 텍스트 로그 vs 리치 블록 킷(Block Kit) 알림
* 단순 텍스트 형태의 Slack 알림에서 벗어나, **서버 호스트, 에러 메시지, 영향받은 라우터, 타임스탬프**를 구조화된 Slack Block Kit 포맷으로 전송하도록 개선했습니다.

## 3. 최종 아키텍처 및 구현 요약

```
[어드민 UI] ──(1줄 호출)──> [admin_common.js] (표준 페이징 & 동적 셀렉터)
                                    │
[DB 헬스 프로브] ──(2초 타임아웃)──> [메인/보조 DB 실시간 스위칭 감지] ──> [어드민 UI 상태 배지]
                                    │
[장애 발생] ──────(상세 텔레메트리)──> [Slack Block Kit (호스트/라우터/스택트레이스)]
```

* **표준화**: 어드민 전체 하위 페이지에서 단 1줄의 함수 호출로 반응형 페이지 네비게이션을 렌더링하도록 일원화.
* **관측 가능성(Observability)**: DB Failover 상태를 실시간 시각화하고, 장애 발생 시 슬랙을 통해 즉각적이고 맥락 있는 원인 파악이 가능해짐.

---

## 4. 엔지니어링 교훈 및 성과 (Takeaway)

1. **레거시 환경에서의 '현실적인' 최적화**: 모든 것을 최신 기술로 갈아엎는 것보다, 현재 시스템의 제약 안에서 공통화를 이루어내는 것이 비즈니스 임팩트(비용 대비 효과)가 훨씬 클 수 있음을 배웠습니다.
2. **운영자 중심의 관측 가능성(Observability)**: 단순한 시스템 생존 여부(UP/DOWN)를 넘어, *현재 어떤 DB를 바라보고 있는지*, *장애의 정확한 맥락이 무엇인지*를 빠르게 인지시키는 것이 **MTTD(Mean Time To Detect)를 80% 이상 단축**하는 핵심임을 증명했습니다.

앞으로도 PickSafe 팀은 견고하고 확장 가능한 아키텍처를 바탕으로 안정적인 서비스를 제공하기 위해 치열하게 고민하겠습니다. 읽어주셔서 감사합니다.
