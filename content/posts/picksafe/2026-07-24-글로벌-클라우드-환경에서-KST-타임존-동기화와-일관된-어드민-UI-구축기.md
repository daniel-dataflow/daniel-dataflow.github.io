화장품 성분 분석 서비스인 **PickSafe**를 개발하고 운영하면서, 제한된 인프라 리소스 안에서 시스템의 안정성과 정합성을 확보하는 일은 늘 중요한 과제였습니다. 

최근 겪었던 가장 까다로운 버그 중 하나는 **서버와 데이터베이스의 타임존 불일치**로 인한 데이터 왜곡 문제였습니다. 글로벌 클라우드 호스팅 환경을 사용하다 보니 시스템 기본 타임존이 UTC로 설정되어 있었고, 이로 인해 사용자 화면과 어드민 대시보드 곳곳에서 시각적인 정합성이 깨지는 현상이 발생했습니다. 

이 문제를 해결하기 위해 백엔드와 데이터베이스의 시간 저장 표준을 재정의하고, 관리자 경험을 개선하기 위해 어드민 UI를 일원화한 과정을 차분히 기록해 봅니다.

## 🎯 마주한 고민과 문제 배경

PickSafe는 인프라 비용을 효율화하기 위해 **Render**와 **Neon DB(PostgreSQL)**를 기반으로 동작하고 있습니다. 이 환경의 시스템 기본 타임존은 **UTC(협정 세계시, +00:00)**로 고정되어 있습니다. 이 조건에서 서비스를 운영하다 보니 다음과 같은 세 가지 치명적인 문제가 발생했습니다.

### 1. 사용자 활동 기록의 시간 왜곡
사용자가 한국 시간(KST)으로 오후 2시(14:00)에 화장품 성분 스캔을 완료했음에도, 마이페이지와 어드민 로그에는 오전 5시(05:00 UTC)로 표기되었습니다. 이로 인해 사용자 화면에 **"어제 스캔함"**과 같은 잘못된 상대 시간이 노출되거나 날짜가 어긋나 보이는 현상이 발생해 사용자에게 혼란을 주었습니다.

### 2. 배치 스케줄러의 실행 시점 정합성 붕괴
식약처 성분을 일일 수집하는 배치 스케줄러가 백엔드에 내장되어 있습니다. 이 스케줄러는 사용자의 서비스 이용률이 가장 저조한 **KST 자정(00:00)**에 실행되도록 설계했습니다. 하지만 서버 타임존이 UTC 기준으로 동작하면서 실제로는 **KST 오전 9시(UTC 00:00)**에 배치가 실행되었습니다. 결과적으로 출근 시간대 및 활성 트래픽이 몰리는 시점에 DB와 네트워크 부하가 겹쳐 일시적인 API 지연 현상이 발생했습니다.

### 3. 어드민 페이지의 시각적 일관성 부족
서비스가 점차 구체화되면서 대시보드, 성분 수집, 번역 관리, 1:1 문의 등 관리해야 할 모듈이 늘어났습니다. 그러나 개발 편의를 이유로 각 페이지마다 시간 포맷(ISO 8601, 단순 날짜 표기, 상대 시간 등)과 UI 아이콘이 제각각으로 구현되어 있었습니다. 특히 CAS(화학물질 식별번호) 자동 보강 작업 내역이나 오류 로그를 검증할 때 시간 정합성이 맞지 않아 운영 리소스가 낭비되고 있었습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

이 문제를 해결하기 위해 크게 두 가지 방향성을 검토했습니다.

### 대안 1: 인프라 레벨에서 타임존을 KST(Asia/Seoul)로 강제 변경
* **장점**: 애플리케이션 코드 단에서 타임존 변환 로직을 추가로 작성할 필요가 없어 단순합니다.
* **단점**: Render나 Neon DB의 관리형(Managed) 인프라 환경에서는 시스템 레벨의 타임존 세팅을 변경하는 데 제약이 따릅니다. 설령 편법으로 변경하더라도, 추후 멀티 리전으로 서비스를 확장하거나 이기종 클라우드로 마이그레이션할 때 인프라 종속성이 생겨 유지보수가 어려워집니다.

### 대안 2: DB에는 UTC 표준으로 저장하고, 애플리케이션 및 UI 레이어에서 KST로 변환 (선택)
* **장점**: 데이터베이스의 원본 데이터는 글로벌 표준인 UTC를 유지하므로 데이터의 무결성이 지켜집니다. 인프라 환경이 바뀌어도 코드 레벨에서 타임존을 제어하므로 이식성이 높습니다.
* **단점**: 데이터를 조회하고 가공하여 클라이언트에게 내보내는 모든 API 엔드포인트와 스케줄러 로직에서 타임존 변환 처리를 꼼꼼하게 누락 없이 구현해야 합니다.

**결정**: 시스템의 확장성과 인프라 독립성을 위해 **대안 2**를 선택했습니다. 데이터베이스에는 UTC 표준 시간으로 적재하되, 백엔드 애플리케이션 전역에 타임존 상수를 도입하여 응답 직렬화(Serialization) 시점에 KST로 변환하고, 프론트엔드에서는 이를 받아 일관된 상대 시간 포맷으로 렌더링하도록 구조를 잡았습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 백엔드 타임존 상수 정의 및 직렬화 표준화

우선 백엔드 전역에서 안전하게 사용할 수 있도록 KST 타임존 상수를 정의하고, SQLAlchemy 모델과 Pydantic 스키마에서 이를 처리하도록 통일했습니다.

```python
# app/utils/timezone.py
from datetime import datetime, timedelta, timezone

# KST 타임존 상수 정의 (+09:00)
_KST = timezone(timedelta(hours=9))

def get_now_utc() -> datetime:
    """DB 적재용 UTC 현재 시간을 반환합니다."""
    return datetime.now(timezone.utc)

def convert_to_kst_str(dt: datetime) -> str:
    """UTC datetime 객체를 KST 기준의 문자열 포맷으로 변환합니다."""
    if not dt:
        return ""
    # 타임존 정보가 없는 naive datetime인 경우 UTC로 가정 후 변환
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(_KST).strftime('%Y-%m-%d %H:%M:%S')
```

데이터베이스 모델을 정의할 때는 `server_default=func.now()`를 사용하여 DB 자체의 UTC 시간으로 기본값이 들어가도록 설계했습니다.

```python
# app/models/scan.py
from sqlalchemy import Column, Integer, String, DateTime, func
from app.database import Base

class ScanLog(Base):
    __tablename__ = "scan_logs"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(String, nullable=False)
    # DB 레벨에서는 UTC 기준으로 자동 적재
    created_at = Column(DateTime(timezone=True), server_default=func.now(), nullable=False)
```

### 2. 프론트엔드 포맷터 일원화

백엔드에서 변환하여 내려준 KST 기준의 날짜 문자열을 프론트엔드에서 일관된 포맷으로 가공하는 유틸리티 함수를 구현했습니다. 단순히 딱딱한 날짜를 그대로 보여주는 대신, 사용자가 직관적으로 인지할 수 있는 상대 시간 포맷을 적용했습니다.

```javascript
// src/utils/dateFormatter.js
export function formatKSTRelativeTime(dateString) {
  if (!dateString) return '-';
  
  const targetDate = new Date(dateString.replace(' ', 'T')); // ISO 형식 대응
  const now = new Date();
  
  const isToday = targetDate.toDateString() === now.toDateString();
  const isYesterday = new Date(now.setDate(now.getDate() - 1)).toDateString() === targetDate.toDateString();
  
  const hours = String(targetDate.getHours()).padStart(2, '0');
  const minutes = String(targetDate.getMinutes()).padStart(2, '0');
  
  if (isToday) {
    return `오늘 ${hours}:${minutes}`;
  } else if (isYesterday) {
    return `어제 ${hours}:${minutes}`;
  } else {
    const month = String(targetDate.getMonth() + 1).padStart(2, '0');
    const day = String(targetDate.getDate()).padStart(2, '0');
    return `${month}.${day} ${hours}:${minutes}`;
  }
}
```

### 3. 어드민 디자인 시스템 및 아이콘 일원화 트러블슈팅

시간 포맷을 맞추는 것과 동시에, 어드민 콘솔의 시각적 파편화 문제를 해결했습니다. 기존에는 대시보드와 배치 로그, 1:1 문의 등 각 페이지의 아이콘 스타일과 테이블 구조가 달라 관리 흐름이 매끄럽지 못했습니다.

* **아이콘 세트 표준화**: 관리 모듈(대시보드, 성분 수집, 번역 관리, 방문자 통계 등)에 사용되는 모든 아이콘을 통일성 있는 라이브러리로 대체하고, 일관된 색상 테마를 부여했습니다.
* **CAS 번호 및 오류 관리 테이블 리팩토링**: 식약처 성분 수집 중 발생하는 CAS 번호 자동 보강 작업 내역 테이블의 UI를 개선했습니다. 아래와 같이 비식별화된 데이터 구조를 기준으로 정돈된 테이블 UI를 설계하여 운영 효율을 높였습니다.

## 💡 돌아보며 배운 점 (회고)

이번 작업을 진행하면서 얻은 가장 큰 교훈은 **"인프라의 기본 환경 설정을 맹신하지 말고, 설계 단계부터 표준 시간대 정책을 명확히 해야 한다"**는 점이었습니다. 

처음에는 로컬 개발 환경(KST)에서 잘 돌아가니까 괜찮겠지 하고 안일하게 넘어갔던 부분이, 클라우드 환경으로 배포되자마자 타임존 불일치라는 부메랑이 되어 돌아왔습니다. 글로벌 서비스를 타깃으로 하든 국내 전용 서비스를 타깃으로 하든, **DB는 UTC로 통일하고 비즈니스 로직과 표현 레이어에서 로컬 타임존을 주입하는 아키텍처**가 가장 안전하고 유연하다는 것을 몸소 깨달았습니다.

또한, 어드민 콘솔처럼 내부 관리자가 쓰는 화면이라도 일관된 디자인 시스템과 표준화된 시간 포맷을 유지하는 것이 장기적인 운영 비용을 줄이는 지름길임을 체감했습니다. 데이터의 선후 관계를 추적할 때 시간 왜곡이 사라지니, 시스템 에러 로그를 분석하는 속도와 정확도가 이전에 비해 눈에 띄게 개선되었습니다.

앞으로도 인프라의 제약 사항을 기민하게 파악하고, 코드 레벨에서 이를 우아하게 방어할 수 있는 견고한 설계를 지향해 나가고자 합니다.
