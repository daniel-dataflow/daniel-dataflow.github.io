제품 개발 초기 단계, 특히 시장 검증을 위한 **MVP(Minimum Viable Product)** 개발 시기에는 매일이 선택과 집중의 연속입니다. 흔히 '있으면 좋은 기능(Nice-to-Have)'과 '반드시 있어야 하는 기능(Must-Have)'을 구분하라고 하지만, 실제 개발에 들어가면 이 경계가 모호해지곤 합니다.

최근 우리 팀은 **PickSafe**의 초기 인프라 구축 과정에서 이메일 인증 및 이메일 기반 고객 문의 아키텍처를 전면 검토했습니다. 결과적으로 우리는 **이메일 관련 기능과 코드를 100% 제거**하고, 데이터베이스 중심의 **인앱(In-App) 1:1 대화식 티켓 시스템**으로 피벗(Pivot)했습니다. 

이 과정에서 우리가 마주한 기술적 페인 포인트와 의사결정의 트레이드오프, 그리고 이를 통해 얻은 엔지니어링 교훈을 공유합니다.

---

## 1. 문제 정의: 초기 인프라에서의 이메일 연동 잔혹사

초기 설계 단계에서 우리는 관성적으로 다음과 같은 기능을 포함했습니다.
*   자체 이메일/비밀번호 회원가입 및 이메일 인증 메일 발송
*   비회원 문의 접수 및 이메일을 통한 답변 피드백

하지만 MVP 배포 환경(Render, Neon DB 프리티어)에 이 시스템을 얹으려 하자마자 즉각적인 운영 및 기술적 병목에 부딪혔습니다.

### 페인 포인트 1: 서드파티 이메일 API(Resend 등)의 샌드박스 제약
초기 비용 절감을 위해 이메일 발송 서비스(Resend API 등)의 프리티어를 검토했으나, 도메인 소유권 인증(DKIM/SPF 설정) 프로세스의 번거로움과 샌드박스 환경에서의 일일 발송 제한으로 인해 로컬 개발 및 QA 단계에서 잦은 병목이 발생했습니다.

### 페인 포인트 2: 이메일 가입 유저 관리에 따른 보안 및 운영 오버헤드
자체 비밀번호 저장에 따른 보안 위협(해싱, 솔팅 등), 비밀번호 분실 시 재설정 흐름 구현, 스팸 가입 계정 필터링 등 '이메일 가입' 하나를 위해 백엔드와 프론트엔드에서 부담해야 할 공수가 너무나 컸습니다.

### 페인 포인트 3: 비회원 문의의 낮은 신뢰성과 비용 낭비
비회원 유저가 가짜 이메일 주소로 문의를 남길 경우, 시스템은 쓸데없이 이메일을 발송하려 시도할 것이고 이는 고스란히 서비스 평판(Bounce Rate) 하락과 리소스 낭비로 이어집니다.

## 2. 기술적 고민과 트레이드오프

우리는 이 문제를 해결하기 위해 두 가지 대안을 비교했습니다.

| 비교 항목 | 대안 A: 유료 이메일 인프라 도입 및 자체 가입 유지 | 대안 B (선택): 소셜 로그인 단일화 + DB 기반 인앱 문의 |
| :--- | :--- | :--- |
| **인프라 비용** | 매월 고정 비용 발생 (이메일 SaaS API 등) | **$0 (완전 무료)** |
| **개발 공수 (Time-to-Market)** | 높음 (SMTP 연동, 회원가입/비밀번호 찾기 페이지 구현 등) | **낮음 (OAuth 연동 및 CRUD 쿼리 구현)** |
| **운영 오버헤드** | 메일 미수신 문의 대응, 스팸 메일 처리 필요 | 데이터베이스 트랜잭션 내에서 완결되어 관리 용이 |
| **유저 경험(UX)** | 가입 절차가 번거로움 (이메일 인증 링크 클릭 필요) | 간편한 원클릭 로그인, 마이페이지에서 문의 내역 실시간 확인 |

### 우리의 선택: 대안 B (과감한 삭제와 단순화)
우리는 이메일 관련 복잡성을 유지하는 것이 초기 가설 검증 속도를 늦추는 주범이라고 판단했습니다. 

따라서 이메일 발송 서비스(`email_service.py`)와 관련 HTML 템플릿들을 **완전히 삭제**하고, 대신 데이터베이스를 활용한 **인앱 1:1 대화식 티켓 시스템**을 구축하기로 결정했습니다.

## 3. 아키텍처 개편 및 구현 전략

### ① 인증의 단순화: 소셜 로그인(OAuth) 단일화
기존의 자체 회원가입 엔드포인트(`auth/signup`, `auth/verify-email`)를 완전히 제거했습니다. 회원가입 및 로그인은 오직 **Google 및 Facebook 소셜 로그인**으로만 수행되도록 개편했습니다. 

이를 통해 가입 인증 메일 발송 필요성 자체를 원천적으로 제거했고, 사용자의 이메일 소유권 증명 책임을 신뢰할 수 있는 대기업 서드파티(IdP)에 위임했습니다.

```
[기존 방식]
유저 -> 자체 회원가입 요청 -> DB 저장(미인증 상태) -> 인증 메일 발송 -> 유저 메일함 확인 및 링크 클릭 -> 가입 완료 (엄청난 이탈률 및 구현 복잡도)

[개선 방식]
유저 -> Google OAuth 인증 -> ID 토큰 검증 -> 세션 생성 및 가입 완료 (단 1초)
```

### ② 소통의 단순화: DB 기반 1:1 인앱 문의 시스템
외부 이메일 인프라에 의존하지 않고, 서비스 내부 데이터베이스 구조 내에서 문의와 답변이 완결되도록 구조를 개편했습니다.

*   **비회원 접근 제안:** 비회원의 문의 작성 기능을 제거하고, 마이페이지의 문의 작성 폼은 로그인된 회원만 접근할 수 있도록 미들웨어를 적용했습니다.
*   **티켓형 데이터 모델 설계:** 문의(`inquiries`) 테이블을 기반으로 유저의 추가 질문과 어드민의 답변이 스레드(Thread) 형태로 누적되도록 아키텍처를 잡았습니다.
*   **어드민 대시보드 연동:** 어드민이 메일 발송 API를 호출하는 대신, 어드민 페이지에서 특정 티켓에 답변 레코드를 추가하면 유저 마이페이지에 실시간으로 반영되도록 구현했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 단순화 작업을 통해 우리 팀은 크게 세 가지 교훈을 얻었습니다.

### 1. YAGNI (You Aren't Gonna Need It) 원칙의 재발견
우리는 초기 기획 단계에서 "고객 문의 시스템에는 당연히 이메일 알림이 있어야지"라고 생각했습니다. 하지만 냉정하게 바라보았을 때, MVP 단계에서 중요한 것은 **'사용자의 피드백을 수집하고 소통할 수 있는 창구의 존재'**이지, '이메일 알림 기술' 그 자체가 아니었습니다. 없어도 되는 기술적 요소를 걷어내자 코드베이스는 훨씬 가벼워졌고 배포 속도는 빨라졌습니다.

### 2. 관리 포인트 최소화가 최고의 최적화다
이메일 연동은 외부 네트워크 호출, 전송 실패 시의 재시도 큐(Queue) 관리, 스팸 처리 등 잠재적인 장애 포인트를 동반합니다. 이를 데이터베이스 트랜잭션 범위 안으로 가져옴으로써 시스템 전체의 안정성을 비약적으로 높일 수 있었습니다.

### 3. 비즈니스 요구사항과 비용의 일치
무료 클라우드 티어를 적극 활용해야 하는 초기 단계에서 인프라 비용을 추가로 지출하지 않으면서도, 1:1 대화식 게시판이라는 신뢰성 높은 피드백 루프를 완벽히 구축해냈습니다.

## 마치며

가장 좋은 코드는 **'작성하지 않은 코드'**이며, 가장 안정적인 아키텍처는 **'제거할 수 있는 외부 의존성을 모두 제거한 아키텍처'**입니다. 

PickSafe는 앞으로도 한정된 리소스 속에서 기술적 허영심을 버리고, 비즈니스 가치를 극대화할 수 있는 가장 단순하고 단단한 엔지니어링을 지향해 나갈 것입니다. 우리의 이러한 실용주의적 접근이 초기 프로덕트를 설계하는 많은 개발자분들께 영감이 되었기를 바랍니다.
