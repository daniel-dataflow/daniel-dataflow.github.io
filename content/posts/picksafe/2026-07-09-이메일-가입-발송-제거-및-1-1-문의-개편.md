프로젝트 초기 검증(MVP) 단계에서 가장 경계해야 할 것은 **"불필요한 외부 의존성으로 인한 엔지니어링 리소스 낭비"**입니다. 서비스 검증에 집중해야 할 시기에 이메일 발송 인프라 설정, 도메인 소유권 인증, 샌드박스 제약 극복에 너무 많은 시간을 빼앗기고 있지는 않으신가요?

최근 **PickSafe** 백엔드 팀은 인프라 복잡성을 획기적으로 낮추고 서비스 안정성을 높이기 위해 **이메일 인증 및 발송 시스템을 완전히 제거하고, DB 기반의 1:1 대화식(티켓형) 문의 시스템으로 개편**했습니다. 

이번 포스팅에서는 우리가 마주했던 기술적 병목, 대안 비교 과정에서의 엔지니어링 트레이드오프, 그리고 이를 통해 얻은 교훈을 공유합니다.

---

## 1. 문제 상황 (Problem): 외부 인프라가 일으키는 마찰과 비용

초기 PickSafe 서비스는 전통적인 이메일/비밀번호 가입 방식과 문의사항 접수 시 이메일로 답변을 전송하는 구조를 가지고 있었습니다. 그러나 레포지토리와 무료/클라우드 인프라(Render, Neon DB) 환경에서 서비스를 운영하며 다음과 같은 기술적 문제에 직면했습니다.

1. **외부 이메일 API(Resend 등) 연동의 제약**
   * 발신 전용 도메인 인증, SPF/DKIM 설정 등 오버헤드가 발생했습니다.
   * 개발/테스트 환경에서의 Sandbox 제약으로 인해 이메일 도달율을 보장하기 어려웠고, 이는 곧 회원가입 및 문의 피드백 루프의 단절로 이어졌습니다.
2. **비회원 문의 관리의 품질 저하**
   * 비회원(게스트) 문의는 식별 가능한 신뢰성 있는 채널이 없어, 잘못된 이메일 입력 시 답변 도달이 불가능했습니다.
3. **불필요한 장애 포인트(Point of Failure) 증가**
   * 이메일 발송 로직(`email_service`)의 비동기 처리 실패 시 유저 경험이 심각하게 훼손되었으며, 이를 위한 재시도 로직 구축은 MVP 범위를 넘어서는 오버헤드였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 두 가지 대안을 놓고 트레이드오프를 분석했습니다.

| 비교 항목 | 대안 A: 유료 도메인 및 이메일 SaaS 도입 | 대안 B: OAuth 단일화 + DB 기반 티켓 시스템 (최종 선택) |
| :--- | :--- | :--- |
| **인프라 비용** | 도메인 구매 및 이메일 API 유료 플랜 비용 발생 | **$0 (기존 RDBMS 활용)** |
| **운영 복잡도** | 도메인 DNS, SPF/DKIM, 이메일 바운스 관리 필요 | **외부 의존성 Zero (무중단 운영 용이)** |
| **유저 인증 신뢰성** | 가입 인증 메일 유실 가능성 존재 | **OAuth 제공자(Google, Facebook)에 인증 위임** |
| **CS 피드백 보존** | 이메일 유실 시 답변 확인 불가 | **마이페이지 내 문의/답변 이력 영구 보존 및 확인** |
| **단점/포기한 점** | 초기 인프라 공수 증가 | 게스트 문의 불가 (로그인 사용자 대상 제한) |

### **결정 (Decision)**
우리는 **대안 B**를 선택했습니다. 

비회원 문의를 임시 보류하는 대신, **로그인된 회원만을 대상으로 OAuth 인증을 단일화**하고, 외부 이메일 API 호출 대신 **내부 데이터베이스(`inquiries`) 내에서 상태(Pending/Answered)를 관리하는 1:1 대화식 티켓 아키텍처**로 개편하기로 결정했습니다.

---

## 3. 엔지니어링 해결 방안 (Implementation)

### ① 인증 체계 단일화 (Social OAuth Only)
복잡한 회원가입 validation 및 이메일 인증 핸들러(`auth/signup`, `auth/verify-email`)를 완전히 제거했습니다. Google 및 Facebook OAuth 2.0 흐름으로 통합하여, 사용자 식별 체계를 단순화하고 보안성과 데이터 신뢰도를 높였습니다.

```python
# 백엔드 라우터 구조의 단순화 (Pseudo-code)
# 기존: 이메일 가입, 인증, 로그인, OAuth 등 다수 엔드포인트 존재
# 변경: OAuth Callback 기반의 단일화된 인증 흐름만 유지

@router.get("/auth/callback/{provider}")
async def oauth_callback(provider: str, code: str, db: Session = Depends(get_db)):
    # OAuth 프로바이더를 통한 신뢰할 수 있는 사용자 정보 획득 및 세션 생성
    user = await process_oauth_login(provider, code, db)
    return create_user_session(user)
```

### ② 이메일 인프라 절단 및 DB 중심 티켓팅 전환
기존의 `email_service.py`를 비활성화/삭제하고, 모든 문의와 어드민 답변은 RDBMS의 ACID 특성을 활용해 직접 관리하도록 개편했습니다.

* **사용자 흐름:** 로그인 상태에서 문의 작성 폼 제출 -> DB 레코드 생성 -> 마이페이지에서 본인의 문의 상태(`Pending`, `Answered`) 실시간 조회 및 추가 질의(대화식) 가능.
* **어드민 흐름:** 어드민 대시보드에서 문의 티켓 확인 -> 답변 입력 시 DB 업데이트 및 유저 마이페이지 즉시 반영 (메일 발송 과정 없음).

## 4. 성과 및 엔지니어링 교훈 (Takeaways)

이번 아키텍처 단순화 작업을 통해 얻은 핵심 성과는 다음과 같습니다.

1. **운영 리스크 및 외부 의존성 제거**
   * 외부 이메일 API 실패로 인한 비동기 트랜잭션 오류 가능성을 100% 제거했습니다.
2. **Zero 추가 인프라 비용 달성**
   * Render와 Neon DB의 Free Tier 제약 안에서 추가 비용 발생 없이 무중단 운영이 가능한 구조를 완성했습니다.
3. **더 나은 서비스 피드백 루프 구축**
   * 이메일 수신함에 묻히기 쉬운 CS 답변을 서비스 내부 마이페이지로 일원화함으로써, 유저의 재방문율(Retention)을 유도하고 답변 전달 성공률을 100%로 끌어올렸습니다.

> **💡 Senior Developer's Lesson**
> 
> "시스템의 우수성은 얼마나 많은 기술과 외부 서비스를 연결했는가가 아니라, **목적 달성을 위해 얼마나 불필요한 복잡성을 덜어냈는가(KISS - Keep It Simple, Stupid)**에 의해 결정됩니다. MVP 단계에서는 가설 검증을 방해하는 외부 요소를 과감히 절단하고, 가용한 리소스(DB)를 극대화하는 아키텍처가 가장 강력한 무기입니다."
