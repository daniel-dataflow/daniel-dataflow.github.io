안녕하세요, PickSafe 개발 팀입니다. 
우리는 종종 제품의 완성도를 높인다는 명목으로 불필요한 기능과 인프라를 초기 단계부터 끌어안는 실수를 범하곤 합니다. 

이번 포스팅에서는 초기 MVP(Minimum Viable Product) 단계에서 **이메일 가입 및 발송 관련 인프라를 전면 제거**하고, 데이터베이스 기반의 **1:1 대화식(티켓형) 문의 시스템으로 아키텍처를 과감하게 피벗(Pivot)한 의사결정 과정과 그 기술적 트레이드오프**를 공유하려 합니다.

---

## 1. Problem: MVP 단계에서 마주한 '이메일 인프라'라는 오버엔지니어링

프로젝트 초기, 사용자 인증을 위해 이메일 회원가입 및 인증 절차(`auth/signup`, `auth/verify-email`)를 구현하고, 고객 지원을 위한 외부 이메일 전송 서비스(`email_service.py`)를 연동했습니다. 

하지만 무료 클라우드 인프라(Render, Neon)를 기반으로 서비스를 배포하고 검증하는 과정에서 몇 가지 치명적인 마찰(Friction)을 마주했습니다.

1. **외부 서드파티 API(Resend 등)의 샌드박스 제약 및 도메인 인증 비용:** 초기 검증 단계에서 외부 이메일 API의 발송량 제한과 엄격한 도메인 소유권 인증 절차는 빠른 배포와 테스트를 방해하는 병목이 되었습니다.
2. **비회원 문의의 신뢰성 부재:** 비회원이 이메일 없이 남긴 문의는 답변을 전달할 방법이 없어, 결국 운영 단계에서 스팸이나 유령 티켓으로 전락할 위험이 컸습니다.
3. **인프라 파편화:** 단순히 문의 대응을 위해 이메일 발송 서버 설정, SMTP/API 키 관리, 템플릿 관리를 유지하는 것은 초기 프로젝트의 복잡도를 불필요하게 높였습니다.

---

## 2. Trade-off & Architecture Decision: 무엇을 버리고 무엇을 취할 것인가

우리는 "초기 MVP의 핵심 가치(Core Value)에만 집중한다"는 원칙 하에 대수술을 감행했습니다.

### 대안 1: 외부 이메일 인프라 유지 및 고도화 (Rejected)
* **장점:** 전통적인 웹 서비스와 동일한 가입/문의 플로우 제공 가능.
* **단점:** 비용 발생, 외부 서비스 장애 시 인증 및 고객 지원 기능 동시 마비, 초기 개발 리소스 낭비.

### 대안 2: 소셜 로그인 단일화 + DB 기반 1:1 티켓 시스템 구축 (Selected)
* **장점:** 
  * 외부 이메일 서비스 의존성 **완전 제거** (비용 Zero, 인프라 복잡도 대폭 감소)
  * Google, Facebook OAuth를 통한 간편하고 안전한 인증 단일화
  * 인앱(In-App) 1:1 티켓 시스템을 통해 데이터베이스 내에서 문의와 답변을 영구적이고 체계적으로 추적 가능
* **단점:** 
  * 이메일 가입을 선호하는 일부 사용자 진입장벽 소폭 상승 (단, 초기 타겟층 분석 시 영향 미미함으로 판단)
  * 비회원 문의 수집 기능 일시 중지

## 3. Implementation: 어떻게 변경되었는가

아키텍처 개편에 따라 백엔드와 프론트엔드의 구조를 다음과 같이 정비했습니다.

* **인증 플로우 단일화:** 
  * 이메일 가입 관련 라우터(`auth/signup`) 및 관련 HTML 템플릿을 제거하고, OAuth 인증 경로로만 로그인이 가능하도록 백엔드 로직을 단순화했습니다.
* **이메일 서비스 격리:** 
  * `email_service.py`와 관련 인프라 코드를 완전히 삭제하여 코드베이스의 응집도를 높였습니다.
* **인앱 1:1 티켓 시스템 도입:** 
  * 마이페이지(`mypage.py`) 내에 로그인된 사용자만 접근할 수 있는 문의 폼을 배치했습니다.
  * 어드민 대시보드(`admin.py`)를 연동하여, 관리자가 별도의 메일러를 통하지 않고 대시보드 내에서 직접 티켓에 답변을 달면 데이터베이스에 즉시 반영되어 사용자가 마이페이지에서 대화 형태로 확인할 수 있게 구현했습니다.

```
[Before]
사용자 문의 -> 외부 이메일 발송 API -> 메일함 확인 -> 외부 메일로 답장 (추적 어려움, 외부 의존성 높음)

[After]
로그인한 사용자 -> DB (Inquiries 테이블) -> 어드민 대시보드에서 직접 답변 -> 마이페이지에서 실시간 확인 (비용 Zero, 무중단 운영)
```

## 4. Takeaway: 시니어 에디터의 엔지니어링 교훈

1. **"모든 기능을 구현할 필요는 없다." (Kill the Unnecessary Features):**
   초기 스타트업이나 개인 프로젝트의 최대 적은 '시간'과 '자원'입니다. 당장 핵심 검증에 필요 없는 이메일 인프라를 과감히 걷어냄으로써, 개발 리소스를 핵심 비즈니스 로직에 집중시킬 수 있었습니다.
2. **"인프라의 단순함은 곧 시스템의 안정성이다."**
   외부 API에 대한 의존성을 줄이고 데이터베이스 내부로 로직을 가져오는 것만으로도 장애 포인트를 획기적으로 줄였습니다. 무중단 운영이 가능한 가장 안정적인 아키텍처는 때로는 가장 단순한 형태입니다.
3. **"제약(Constraint)은 최고의 설계 도구다."**
   무료 인프라 환경이라는 제약 덕분에, 오히려 불필요한 오버엔지니어링을 피하고 더 직관적이고 확장 가능한 인앱 티켓 시스템이라는 아키텍처 결정을 내릴 수 있었습니다.
