안녕하세요, PickSafe 개발 팀입니다. 

서비스가 빠르게 성장하고 다루는 데이터의 규모가 커질수록, 초기 설계 단계에서 간과했던 작은 균열들이 시스템의 안정성을 위협하는 거대한 부채로 돌아오곤 합니다. PickSafe 팀 역시 최근 서비스 고도화 과정에서 **'유지보수 효율 저하'**, **'인프라 비용 제약과 데이터 유실 위험'**, 그리고 **'단일 장애점(SPOF)'**이라는 세 가지 커다란 벽에 부딪혔습니다.

오늘 포스팅에서는 스타트업으로서 직면한 인프라 예산의 한계를 소프트웨어 아키텍처의 혁신으로 극복하고, 서비스 지속 가능성을 극대화하기 위해 감행했던 **도메인 중심 1:1 버티컬 매핑**과 **3중 핫스왑(Hot-Swap) 고가용성 아키텍처 구축기**를 공유하고자 합니다.

---

## 1. 우리가 마주한 세 가지 기술적 당면 과제

### 과제 1: 파편화된 네이밍으로 인한 인지 비용의 폭발
기능이 우후죽순 추가되면서 테이블명, 라우터, 모델, 템플릿, 정적 자산(CSS/JS)의 이름이 서로 다르게 흩어져 있었습니다. 예를 들어, 동일한 방문자 분석 기능을 개발하는데 어떤 곳은 `users_analytics`, 어떤 곳은 `visitor_log`라는 명칭을 혼용하고 있었습니다. 이로 인해 코드 한 줄을 수정할 때마다 연관 파일을 찾기 위해 전체 검색을 해야 하는 불필요한 인지 비용(Cognitive Load)이 발생하고 있었습니다.

### 과제 2: 서버리스 DB(Neon)의 자원 한계와 데이터 단절 리스크
우리는 데이터웨어하우스(DW) 용도로 서버리스 PostgreSQL 서비스인 Neon을 활용하고 있었습니다. 하지만 무료 티어가 제공하는 월 100 Compute Hours 제한은 트래픽이 몰릴 때 언제든 DB가 잠길 수 있는(Lock) 시한폭탄과 같았습니다. 

게다가 자원 고갈을 피해 다른 DW 인스턴스로 전환(DW1 ➔ DW2)할 때, **과거의 텔레메트리 및 통계 데이터가 단절되어 시계열 분석이 불가능해지는 치명적인 문제**가 존재했습니다.

### 과제 3: 모니터링 부재와 단일 장애점(SPOF)
Main DB나 DW DB에 장애가 발생하더라도 이를 자동으로 복구하거나 우회할 수 있는 고가용성(HA) 레이어가 없었습니다. 더욱이 시스템 장애가 발생했을 때 개발진이 즉각 인지할 수 있는 알림 체계가 부재하여, 사용자 제보가 들어온 후에야 사후 약방문 격으로 대응하는 구조였습니다.

## 2. 해결을 위한 아키텍처적 고민과 Trade-off

이 문제를 해결하기 위해 우리 팀은 단순히 '더 비싼 인프라 요금제를 결제하는 것'을 넘어, **코드와 시스템 수준에서 근본적인 회복 탄력성(Resilience)을 확보하는 방향**을 선택했습니다.

### 고민 1: 전면적 리팩토링 vs 부분적 타협
기존의 모든 소스코드를 바꾸는 것은 리스크가 큽니다. 하지만 장기적인 유지보수성을 위해 지금 정리하지 않으면 앞으로 신규 기능을 붙일 때마다 부채가 눈덩이처럼 불어날 것이 자명했습니다. 
* **결정:** **1:1 Vertical Mapping 규칙**을 도입하여 화면 도메인 단위로 DB 테이블부터 프론트엔드 자산 파일명까지 접두사를 전면 통일하기로 했습니다.

### 고민 2: 상용 유료 DB 전환 vs 소프트웨어 레벨의 다중화(Hot-Swap)
상용 클라우드 DB의 고가용성 옵션은 매월 상당한 고정 비용을 발생시킵니다. 
* **결정:** 비용 효율성을 위해 여러 개의 무료/저비용 DB 인스턴스를 논리 풀(Pool)로 묶고, **애플리케이션 단에서 실시간 모니터링을 통해 엔드포인트를 전환하는 핫스왑 라우터**를 직접 구현하기로 했습니다.

## 3. 최종 아키텍처 설계 및 구현 내용

### 3.1 화면 중심의 1:1 Vertical Mapping 표준화

우리는 관리자 메뉴 9개와 사용자 핵심 도메인을 기준으로 모든 레이어의 명칭을 통일했습니다. 이렇게 함으로써 개발자는 특정 기능의 접두사(Prefix)만 알면 DB, 백엔드 라우터, UI 템플릿, 스타일시트까지 직관적으로 추적할 수 있게 되었습니다.

```
[Before] 중구난방의 네이밍
analytics_events (Table) ➔ user_logger.py (API) ➔ stat.html (View)

[After] 1:1 Vertical Mapping 표준화
visitors_events (Table) ➔ visitors.py (API) ➔ visitors.html (View)
```

| 화면 도메인 | 접두사 (Prefix) | 표준 DB 테이블명 (예시) | 소속 DB 구분 | 관련 소스코드 파일군 |
| :--- | :--- | :--- | :--- | :--- |
| **방문자 관리** | `visitors_` | `visitors_events`, `visitors_daily_summaries` | DW / Main | `visitors.py`, `visitors.html`, `visitors.js` |
| **인프라 모니터링**| `infra_` | `infra_settings`, `infra_db_status` | Main | `infra.py`, `infra.html`, `infra.css` |
| **로그 모니터링** | `logs_` | `logs_system` | DW | `logs.py`, `logs.html`, `logs.js` |
| **사용자 관리** | `users_` | `users_accounts`, `users_admins` | Main | `users.py`, `users.html`, `users.css` |

이 표준화 작업을 통해 신규 온보딩 엔지니어의 **코드 파악 시간이 기존 대비 70% 이상 단축**되는 극적인 효과를 얻었습니다.

### 3.2 3중 핫스왑(Hot-Swap) 및 중앙 앵커링(Anchoring) 아키텍처

가장 심혈을 기울인 부분은 제한된 인프라 리소스 하에서 서비스 정지 시간을 제로(0)에 가깝게 유지하는 **고가용성 고도화**였습니다.

```
                  ┌─────────────────┐
                  │   Client Req    │
                  └────────┬────────┘
                           │
                           ▼
               ┌───────────────────────┐
               │  FastAPI Application  │
               │  (Active DB Router)   │
               └───────────┬───────────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
       [Primary DW]   [Backup DW 2]  [Backup DW 3]
         (Neon 1)       (Neon 2)       (Neon 3)
           │              ▲
           │ (90% Threshold Exceeded)
           └──────────────┘ (In-Memory Hot Swap)
```

#### ① Main DB 2중화 (Active-Passive)
메인 비즈니스 로직을 담당하는 데이터베이스는 `DATABASE_URL`(Primary)과 `DATABASE_BK_URL`(Backup)로 이중화했습니다. 헬스 체크 미들웨어가 상시 작동하며 Primary 장애 감지 시, 대기 중인 Backup DB로 즉각적인 failover를 수행합니다.

#### ② Multi-DW 3중 핫스왑 (Active-Active-Active Pool)
무료 티어 서버리스 DW의 자원 소진 문제를 해결하기 위해 3개의 DW 엔스포인트를 라우터 풀로 구성했습니다. 
* **90% 사전 임계치 감지 스위칭**: 인스턴스의 누적 컴퓨팅 사용량이 100%에 도달해 완전히 Lock이 걸리기 전, **90% 수준에서 임계치를 감지하여 차기 가용 인스턴스(DW2)로 인메모리 핫스왑**을 실행합니다. 
* 이전 DB(DW1)는 '읽기 전용'으로 보존하여 무중단 서비스와 데이터 안전성을 동시에 획득했습니다.

#### ③ 중앙 앵커링(Central Anchoring)을 통한 시계열 데이터 단절 해결
DW가 물리적으로 변경(DW1 ➔ DW2)되면 과거의 누적 통계 데이터가 유실되는 데이터 단절 문제가 있었습니다. 이를 해결하기 위해 **중앙 앵커링 기법**을 고안했습니다.

* 매일 자정, 현재 DW에 쌓인 로우 데이터를 집계하여 **핵심 통계 요약본(`visitors_daily_summaries`)을 Main DB에 상시 복제(Sync)**합니다.
* 새로운 DW 인스턴스로 전환되더라도, 애플리케이션은 Main DB의 요약본 테이블을 기준으로 과거 데이터를 즉시 조회하므로 **단 0.1초 만에 과거의 모든 시계열 대시보드를 완벽하게 복원**해 냅니다.

### 3.3 실시간 장애 조치와 인프라 대시보드 시각화

아무리 훌륭한 자동화 아키텍처를 설계했더라도, 운영 조직이 모르는 자동 복구는 잠재적 시한폭탄입니다. 가시성과 모니터링을 강화하기 위해 두 가지 장치를 더했습니다.

```
[Alarm Target & Threshold]
- [DW Resource 90%] ➔ "Warning: DW_1 capacity at 90%. Switching to DW_2 initiated."
- [Main DB Failure] ➔ "Critical: Primary DB connection failed. Failover to Backup active."
- [Server Memory > 80%] ➔ "Alert: Server memory spike detected."
```

1. **Slack Webhook 실시간 경보**: 핵심 위기 지표가 감지되는 즉시, 장애 유발 쿼리나 리소스 분석 로그를 슬랙 채널로 포워딩하여 실시간으로 인프라 팀이 개입할 수 있도록 조치했습니다.
2. **4단계 상태 정렬 UI**: 어드민 대시보드 내 인프라 현황판을 가독성 높게 개편했습니다. 
   * `🟢 Active (연결됨)` ➔ `⚪ Standby (대기)` ➔ `🔴 Exceeded (자원 한계 초과)` ➔ `⚫ Disconnected (연결 불가)` 순으로 정렬 배치하여, 어떤 DB 인스턴스가 현재 열일을 하고 있고 어떤 녀석이 바톤 터치를 준비 중인지 한눈에 파악할 수 있게 설계했습니다.

## 4. 엔지니어링 교훈과 얻은 것들 (Takeaway)

이번 아키텍처 고도화 작업을 마치며, 팀원 모두가 한 단계 더 성장할 수 있었습니다. 저희가 얻은 교훈은 크게 세 가지입니다.

1. **깨끗한 코드는 견고한 인프라의 토대이다**
   도메인 중심의 1:1 Vertical Mapping은 단순한 네이밍 규칙 제정이 아니었습니다. 코드베이스 전체의 구조를 투명하게 만들어, 장애가 났을 때 어느 곳의 소스코드를 즉시 점검해야 하는지 직관적으로 알려주는 강력한 나침반이 되었습니다.
2. **비용 한계는 아키텍처적 창의성의 트리거다**
   비싼 상용 솔루션을 구매하는 것만이 정답은 아닙니다. 오픈소스와 무료 티어의 제약을 명확히 인지하고, 소프트웨어 레벨에서 3중 핫스왑 라우터와 중앙 앵커링 기법을 구현함으로써 **비용을 거의 들이지 않고 대기업 수준의 무중단 고가용성(HA) 환경을 구성**해 낼 수 있었습니다.
3. **가시성(Visibility) 없는 복구는 반쪽짜리다**
   아무리 자동 Failover가 잘 설계되어 있어도 개발자가 모르는 시스템 상태 변화는 위험합니다. 슬랙 알림과 계층형 모니터링 UI를 결합함으로써 비로소 "살아 숨 쉬고 통제 가능한 아키텍처"가 완성되었습니다.

---

PickSafe 팀은 주어진 환경의 한계를 극복하며, 가장 효율적이고 회복 탄력성 높은 아키텍처를 구현하기 위해 지금 이 순간도 끊임없이 고민하고 있습니다. 저희의 도전기에 관심이 있거나 함께 더 단단한 서비스를 만들어 가고 싶으시다면 언제든 문을 두드려 주세요!
