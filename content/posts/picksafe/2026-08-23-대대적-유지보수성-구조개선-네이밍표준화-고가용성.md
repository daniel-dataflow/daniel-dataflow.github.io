안녕하세요. PickSafe 백엔드/아키텍처 팀입니다.

서비스가 급격히 성장하고 관리해야 할 도메인과 데이터가 늘어남에 따라, 코드베이스와 인프라 전반에 걸쳐 대대적인 유지보수성 구조 개선 작업을 진행했습니다. 이번 포스팅에서는 **기능 확장 과정에서 직면한 3대 구조적 문제**, 이를 해결하기 위해 고민한 **아키텍처적 Trade-off**, 그리고 무중단 운영을 위해 도입한 **Multi-DW 3중 핫스왑(HA) 시스템**의 설계 과정을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 서비스 성장에 발목을 잡는 3가지 기술적 부채

PickSafe 고도화 과정에서 다음과 같은 한계점에 직면했습니다.

1. **파편화된 네이밍으로 인한 인지 부하**: 
   - 초기 개발 속도에 집중한 나머지, 테이블명(`users`, `admin_ips`, `analytics_events` 등), 파일명, 템플릿, 프론트엔드 리소스 간의 명명 규칙이 어긋났습니다. 특정 기능을 수정할 때 관련된 파일을 찾는 데만 불필요한 시간이 소모되었습니다.
2. **무료 티어 DB(Neon)의 용량/Compute 한계와 DW 전환 시 데이터 단절 리스크**:
   - 텔레메트리 및 통계 데이터를 처리하는 무료 데이터웨어하우스(DW)의 Compute Hours 소진 시 DB가 잠기는 리스크가 있었습니다. 또한, DW 인프라를 마이그레이션할 때 과거 시계열 데이터가 유실되거나 단절될 위험이 존재했습니다.
3. **SPOF(단일 장애점)와 실시간 모니터링/알림 체계 부재**:
   - Main DB나 DW에 장애가 발생했을 때 즉각적으로 트래픽을 우회할 수 있는 페일오버(Failover) 수단이 없고, 운영자가 실시간으로 장애를 인지할 수 있는 자동화된 알림 채널이 부족했습니다.

## 2. 기술적 고민과 아키텍처 대안 비교 (Trade-off)

### 2.1 네이밍 규칙: 1:1 Vertical Mapping 도입
* **고민**: 기존의 도메인별 분산된 구조를 어떻게 하면 직관적으로 바꿀 수 있을까?
* **대안**: 
  - **대안 A (기존 유지)**: 디렉토리 구조를 기능별로 묶기. (단, 파일명이 제각각이라 여전히 검색 필요)
  - **대안 B (1:1 Vertical Mapping 표준화)**: 어드민 9개 핵심 메뉴 및 사용자 도메인에 맞춰 접두사(`visitors_`, `infra_`, `logs_`, `scans_` 등)를 정의하고, DB 테이블부터 라우터, 모델, HTML/CSS/JS 파일명까지 1:1로 강제 매핑.
* **선택**: **대안 B**. 신규 팀원이 합류하더라도 특정 화면의 코드를 단 3초 만에 찾을 수 있는 직관성을 확보했습니다.

### 2.2 DB 고가용성(HA) 및 핫스왑 전략
* **고민**: 무료 DB 환경에서 리소스 소진으로 인한 서비스 중단을 어떻게 막을 것인가?
* **대안**:
  - **대안 A (단일 DW + 스냅샷 백업)**: 비용은 절감되지만, 다운타임 발생 시 복구에 수 분~수 시간이 소요됨.
  - **대안 B (Multi-DW 3중 핫스왑 + Main DB 앵커링)**: DW 3개를 구성(`DATABASE_DW_1_URL` ~ `DATABASE_DW_3_URL`)하고, 리소스가 100% 잠기기 전 **90% 임계점에 도달하면 인메모리로 스위칭**하여 기존 DW를 읽기 전용으로 보존.
* **선택**: **대안 B**. 특히, 실시간 이벤트 데이터는 DW에 분산하되, 매일 자정 확정되는 핵심 요약 데이터(`visitors_daily_summaries`)는 **Main DB에 중앙 앵커링(복제)**하여 DW 인프라가 교체되더라도 과거 통계를 0.1초 만에 100% 복원할 수 있도록 설계했습니다.

## 3. 최종 해결 및 구현 (Solution)

### 3.1 화면 중심 네이밍 표준화 적용 결과
전체 시스템을 아래 표준에 맞춰 리팩토링을 단행했습니다.

| 화면 도메인 | 접두사 | 표준 DB 테이블명 | 소속 DB | 연결 파일 (Router / Model / View) |
|---|---|---|---|---|
| **방문자 관리** | `visitors_` | `visitors_events`<br>`visitors_daily_summaries`<br>`visitors_admin_ips` | events: **DW**<br>summaries: **DW+Main**<br>ips: **Main** | `visitors.py` / `visitors.html` / `visitors.js` |
| **인프라 모니터링** | `infra_` | `infra_settings`, `infra_db_status` | **Main DB** | `infra.py` / `infra.html` / `infra.js` |
| **로그 모니터링** | `logs_` | `logs_system` | **DW DB** | `logs.py` / `logs.html` / `logs.js` |
| **[사용자] 성분 스캔** | `scans_` | `scans_user_history` | **Main DB** | `scan.py` / `scan.html` |

### 3.2 3중 고가용성(HA) 및 90% 사전 위기 감지 스위칭
- **Main DB 2중화**: `DATABASE_URL`(Primary)과 `DATABASE_BK_URL`(Backup)을 구성하여 Primary 장애 시 즉각적인 전환 경로 확보.
- **Multi-DW 3중 핫스왑**: 
  - DW1의 컴퓨팅 자원 사용량이 **90%에 도달하는 시점**에 애플리케이션 레벨에서 이를 감지.
  - 슬랙(Slack) 웹훅을 통해 즉시 운영자에게 경고 알림을 발송함과 동시에, 트래픽을 DW2로 무중단 인메모리 핫스왑 처리.

### 3.3 운영 효율을 높이는 인프라 모니터링 UI 정렬
운영자가 한눈에 시스템 상태를 파악할 수 있도록 인프라 상태를 4단계로 시각화했습니다.
1. `🟢 연결됨 (Active)` — 최상단 고정
2. `⚪ 대기 (Standby)`
3. `🔴 초과 (Exceeded)`
4. `⚫ 미연결 (Disconnected)` — 기본 접힘 아코디언 처리

## 4. 엔지니어링 교훈 (Takeaway)

이번 구조 개선을 통해 다음의 소중한 교훈을 얻었습니다.

1. **규칙은 문서가 아니라 구조여야 한다**: 네이밍 컨벤션을 사내 위키에만 적어두는 것은 의미가 없습니다. 파일, 테이블, 라우터 명명 규칙을 1:1로 일치시키는 아키텍처 디자인 자체가 강력한 가이드가 됩니다.
2. **장애는 '막는 것'이 아니라 '우회하는 것'이다**: 완벽한 인프라는 없기에, 단일 장애점(SPOF)을 제거하고 임계점 도달 전 사전 핫스왑(Proactive Failover)하는 구조가 서비스 신뢰도를 극적으로 높여준다는 점을 확인했습니다.

PickSafe는 앞으로도 안정적이고 확장 가능한 아키텍처를 바탕으로 사용자에게 더 안전하고 빠른 서비스를 제공해 나가겠습니다. 읽어주셔서 감사합니다!
