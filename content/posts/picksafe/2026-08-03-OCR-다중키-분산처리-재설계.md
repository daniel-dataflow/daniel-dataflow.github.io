안녕하세요. `PickSafe` 서비스 백엔드 개발 에디터입니다. 
최근 저희 서비스는 AI 기반 OCR 및 번역 기능을 고도화하는 과정에서 **Google Gemini API의 엄격한 Rate Limit(RPM/RPD)**이라는 기술적 벽에 부딪혔습니다. 

특히 관광객이 몰리는 피크 타임에는 단일 API 키가 가진 분당 요청 수(RPM) 한도를 쉽게 초과하여 서비스 장애로 이어질 위험이 있었습니다. 이를 해결하기 위해 여러 개의 API 키를 안전하게 분산 처리하고, 동시성 환경에서도 무결성을 보장하는 **다중 키 분산 쿼터 관리 시스템**을 설계하게 되었습니다. 

이번 글에서는 이 시스템을 구축하며 마주한 문제들과, 이를 해결하기 위해 선택한 아키텍처적 트레이드오프, 그리고 엔지니어링 교훈을 공유합니다.

---

## 1. Problem: 무엇이 문제였는가?

초기 설계에서는 단순히 **RPD(일일 총량)**만을 추적하며 여러 개의 API 키를 라운드 로빈 방식으로 번갈아 사용하는 방식을 구상했습니다. 하지만 실제 운영 환경을 가정했을 때 두 가지 치명적인 문제가 발견되었습니다.

1. **RPM(분당 요청 수) 통제의 부재**: RPD만 관리하다 보니, 트래픽이 순간적으로 몰릴 때 RPM 한도(예: Flash-Lite 기준 키당 15 RPM)를 순식간에 초과하여 외부 API로부터 `429 Too Many Requests` 응답을 받게 되었습니다.
2. **Race Condition(경쟁 상태)**: 백엔드 서버가 다중 인스턴스 또는 비동기 환경으로 동작할 때, "현재 남은 쿼터 조회 ➔ 사용 가능 여부 판단 ➔ 쿼터 차감" 단계가 분리되어 있으면, 동시에 들어온 여러 요청이 똑같이 '여유가 있다'고 판단하여 **동일한 키로 요청이 몰리는 쏠림 현상**이 발생했습니다.

---

## 2. Technical Decisions & Trade-offs: 아키텍처 설계와 대안 비교

이 문제를 해결하기 위해 다음과 같은 핵심 원칙들을 세우고 아키텍처를 재설계했습니다.

### ① RPM과 RPD의 독립적 2중 추적
* **고민**: 슬라이딩 윈도우 방식으로 정교하게 RPM을 추적할 것인가?
* **선택**: **고정 1분 버킷(Fixed 1-minute bucket)** 방식 채택.
* **Trade-off**: 슬라이딩 윈도우가 이론적으로는 더 정확하지만, 구현 복잡도와 연산 비용이 급증합니다. 타이트한 API 쿼터 환경에서는 매 분 정각에 카운터가 리셋되는 단순한 구조가 유지보수성과 성능 면에서 훨씬 유리하다고 판단했습니다.

### ② 순수 랜덤 배제 및 "여유 우선(Least-Loaded)" 선택 전략
* **고민**: 단순 랜덤 혹은 순차 라운드 로빈으로 키를 고를 것인가?
* **선택**: 현재 분(minute) 기준 **사용량이 더 적은 키를 우선적으로 선택**하는 알고리즘 적용.
* **Trade-off**: 키가 단 2개뿐인 상황에서 순수 랜덤은 우연에 의해 한쪽 키로 트래픽이 편중될 위험이 큽니다. 약간의 메타데이터 비교 연산을 추가하더라도 잔여 쿼터가 더 많은 키를 우선 배정하는 것이 안정성을 크게 높여주었습니다.

### ③ SQLAlchemy `with_for_update()`를 통한 원자적(Atomic) 쿼터 차감
* **고민**: 인메모리 락과 DB 락 중 어디서 동시성을 제어할 것인가?
* **선택**: **SQLAlchemy의 Row-level Lock (`with_for_update()`)** 활용.
* **Trade-off**: DB 접근으로 인한 미세한 지연(Latency)이 발생하지만, 분산 환경이나 서버 스케일아웃 상황에서도 쿼터 초과 인출(Over-allocation) 원천 차단하기 위해 데이터베이스 트랜잭션 레벨의 원자성을 선택했습니다. 또한, 외부 API 통신 중 에러(429, 500 등)가 발생할 경우 **차감된 쿼터를 즉시 롤백(Rollback)**하는 보상 로직을 함께 구현하여 싱크 불일치를 방지했습니다.

### ④ Fail-Safe 전략과 사용자 경험(UX) 분세화
* **고민**: 모든 키가 소진되었을 때 어떻게 대응할 것인가?
* **선택**: 에러 유형(RPM 초과, TPM 초과, RPD 초과)에 따라 **서로 다른 커스텀 안내 메시지**를 제공하고, 외부 API 호출 전 로컬 체크와 별개로 429 발생 시 **다른 키로 1회 자동 재시도(Retry)** 메커니즘을 도입했습니다.
* **Trade-off**: 단순히 "에러 발생" 처리하는 것보다 예외 처리가 복잡해지지만, 사용자에게 명확한 가이드(예: "현재 요청이 많아 1분 후 다시 시도해주세요")를 제공하여 서비스 신뢰도를 높였습니다.

## 3. Takeaways: 엔지니어링 교훈

1. **"분산"은 마법이 아니다**: 다중 키 분산 처리는 가용성을 높여주지만, 제한된 총량을 무제한으로 늘려주지는 않습니다. 한계치를 명확히 인지하고 그에 맞는 방어적 프로그래밍(Fall-back, Retry)이 동반되어야 합니다.
2. **동시성 제어는 설계 초기 단계에서 잡아야 한다**: "조회 후 수정" 패턴은 멀티스레드/비동기 환경에서 반드시 Race Condition을 유발합니다. ORM 레벨의 락 기능을 적극 활용해 데이터 무결성을 지키는 것이 디버깅 비용을 아끼는 지름길입니다.
3. **모니터링 데이터 소스의 단일화(Single Source of Truth)**: 여러 어드민 화면에서 동일한 API 상태를 보여줘야 할 때, 각각 다른 엔드포인트를 바라보게 하면 반드시 데이터 불일치 버그가 발생합니다. 하나의 데이터 소스를 공유하고 뷰(View)에서 필터링만 다르게 가져가는 구조가 정답입니다.

이번 설계를 통해 제3자 API의 제약을 극복하는 백엔드 아키텍처의 뼈대를 단단하게 다질 수 있었습니다. 앞으로도 PickSafe는 안정적인 인프라를 바탕으로 사용자에게 끊김 없는 서비스를 제공하겠습니다.
