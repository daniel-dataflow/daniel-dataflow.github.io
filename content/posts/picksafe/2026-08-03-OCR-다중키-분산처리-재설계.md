안녕하세요. PickSafe 팀의 백엔드 아키텍트입니다. 

최근 LLM(대규모 언어 모델)을 서비스 핵심 로직에 도입하는 서비스가 늘어나고 있습니다. 저희 팀 역시 서비스 내 OCR 및 번역 품질을 고도화하기 위해 Google의 **Gemini API(주력 모델: Gemini 3.1 Flash-Lite)**를 적극적으로 도입했습니다. 

하지만 고성능을 자랑하는 LLM API 뒤에는 늘 **'엄격한 호출 제한(Rate Limit)'**이라는 현실적인 벽이 존재합니다. 특히 무료/저가형 티어의 경우 분당 호출 수(RPM)와 일일 호출 수(RPD) 제한이 매우 타이트합니다. 

오늘 포스팅에서는 단 2개의 독립된 API 키(합산 한도: 30 RPM, 1,000 RPD)라는 극한의 제약 조건 속에서, **동시성 경쟁 상태(Race Condition)를 해결하고 무중단에 가까운 안정적인 서비스를 구축한 아키텍처 설계 여정**을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 트래픽 스파이크와 '조회 후 차감'의 맹점

초기 설계 단계에서 단순하게 "여러 개의 API 키를 등록해 두고 분산 처리하면 되겠지"라고 생각했습니다. 하지만 실제 운영 환경을 고려해 보니 두 가지 치명적인 문제가 발견되었습니다.

### 문제 A: RPM(분당 제한) 누락과 트래픽 스파이크
기존 시스템은 일일 총량(RPD)만 추적하고 있었습니다. 하지만 실제 사용자 트래픽은 하루 동안 고르게 인입되지 않습니다. 특정 시간대에 관광객 등 사용자가 몰리는 트래픽 스파이크가 발생하면, RPD가 아무리 많이 남아있어도 **분당 제한(RPM)을 초과하여 서비스가 마비(HTTP 429 Too Many Requests)**되는 현상이 예측되었습니다.

### 문제 B: 동시성 상황에서의 경쟁 상태 (Race Condition)
가장 보편적인 설계 오류인 **"확인 후 선택 후 차감(Check-Then-Act)"** 구조가 문제였습니다.
```
[요청 1] ---> 쿼터 확인 (Key A 여유 있음) ------------> Key A 사용 및 차감
[요청 2] ---> 쿼터 확인 (Key A 여유 있음) ---> Key A 사용 및 차감 (초과 발생!)
```
동시 다발적으로 요청이 들어올 경우, 데이터베이스나 메모리에 반영되기 전에 여러 요청이 동일한 키를 '사용 가능한 상태'로 판단하여 동시에 호출을 시도합니다. 결국 로컬 카운트와 실제 외부 API 서버의 쿼터 상태가 어긋나 429 에러를 뿜어내게 됩니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 아키텍처 리팩토링 과정에서 크게 세 가지 엔지니어링 의사결정을 거쳤습니다.

### 고민 1. 쿼터 카운팅 데이터를 어디에 저장하고 동기화할 것인가?
*   **대안 1: 인메모리(서버 메모리) 관리**
    *   *장점:* 초고속 조회 및 갱신 가능.
    *   *단점:* 다중 인스턴스(컨테이너) 환경에서 인스턴스 간 쿼터 상태 동기화가 불가능하며, 서버 재시작 시 데이터가 유실됨.
*   **대안 2: RDBMS (PostgreSQL/MySQL 등) 기반 관리**
    *   *장점:* 강력한 ACID 트랜잭션 지원 및 영속성 보장. 다중 인스턴스 환경에서도 일관성 유지 가능.
    *   *단점:* 인메모리 방식 대비 DB 커넥션 및 I/O 비용 발생.
*   **선택:** 저희 서비스는 여러 대의 API 서버가 로드밸런싱되는 환경이므로 일관성이 무엇보다 중요했습니다. 초당 수천 건의 트래픽이 몰리는 대규모 시스템이 아닌, 제한된 API 쿼터 내에서 정밀하게 분산 처리하는 구조였기에 **RDBMS를 선택하여 데이터 무결성을 보장**하기로 했습니다.

### 고민 2. 동시성 제어(Concurrency Control)를 어떻게 구현할 것인가?
여러 요청이 동시에 하나의 API 키에 접근할 때 원자성(Atomicity)을 보장해야 했습니다.
*   **대안 1: 애플리케이션 레벨의 Async Lock**
    *   *단점:* 단일 서버 내부에서만 유효하며, 분산 서버 환경에서는 경쟁 상태를 막을 수 없음.
*   **대안 2: DB Row-level Lock (`SELECT ... FOR UPDATE`)**
    *   *장점:* DBMS 차원에서 특정 API 키 레코드에 락을 걸어 트랜잭션이 완료될 때까지 다른 세션의 접근을 제어함.
*   **선택:** SQLAlchemy ORM의 `with_for_update()` 기능을 채택했습니다. 이를 통해 **"조회 → 판단 → 차감" 단계를 하나의 트랜잭션 안에서 원자적(Atomic) 연산으로 처리**하여 경쟁 상태를 원천 차단했습니다.

### 고민 3. API 키 선택 알고리즘 (Routing)
*   **대안 1: 순수 랜덤 / 라운드 로빈**
    *   *단점:* 두 키의 현재 사용량 상태를 고려하지 않으므로, 우연히 하나의 키로 요청이 몰려 429 에러가 발생할 확률이 존재함.
*   **대안 2: 사용량 최소 우선순위 방식 (Least-Used-First)**
    *   *장점:* "이번 분(minute)"에 사용량이 더 적은 키를 우선적으로 선택하여 부하를 동적으로 균등하게 분산함.
*   **선택: 대안 2.** 제한된 쿼터를 극대화하기 위해 동적 우선순위 라우팅 알고리즘을 설계했습니다.

## 3. 최종 아키텍처 설계 및 구현 전략

리팩토링 지시서를 기반으로 확립한 구체적인 시스템 동작 원칙은 다음과 같습니다.

### 1) Dual-Window Quota Tracking (RPM & RPD 독립 추적)
키마다 분당 요청 수(RPM)와 일일 요청 수(RPD)를 독립적으로 기록합니다. 
*   **RPM:** "고정 1분 버킷" 방식(예: 매 분 0초에 리셋)을 채택하여 구현 복잡도를 낮추면서 효율적으로 분당 스파이크를 방지합니다.
*   키 선택 알고리즘은 **RPM과 RPD의 잔여 한도를 모두 체크**하여, 둘 중 하나라도 한도에 도달한 키는 후보군에서 제외합니다.

### 2) 데이터 정합성을 위한 '롤백(Rollback)' 메커니즘
로컬 DB에서 API 키의 쿼터를 정상적으로 차감했더라도, 실제 외부 API(Google Gemini) 호출 단계에서 네트워크 지연, 500 에러, 혹은 예기치 못한 429 에러가 발생할 수 있습니다. 

이 경우 **이미 차감했던 로컬 DB의 사용량 카운트를 트랜잭션 외부에서 다시 되돌리는(+1 Rollback) 예외 처리 로직**을 추가했습니다. 이를 누락하면 실제 사용하지 않았음에도 쿼터가 소진된 것으로 판정되어 멀쩡한 키가 시스템에서 배제되는 "가짜 소진(False Exhaustion)" 문제가 발생하기 때문입니다.

### 3) 429 에러 발생 시 자동 재시도 (Graceful Failover)
로컬 데이터와 실제 외부 API 서버 간의 미세한 동기화 오차로 인해 간헐적으로 429 에러가 반환될 수 있습니다. 시스템은 이를 즉시 에러로 처리하지 않고, **남은 다른 키를 찾아 즉시 1회 재시도(Failover)** 하도록 설계하여 사용자 경험의 연속성을 확보했습니다.

```
[API 호출 요청] 
      │
      ▼
[Key A 선택 및 차감 (with_for_update)] ──► [외부 Gemini API 호출]
                                                    │
                      ┌─────────────────────────────┴────────────┐
                      ▼ (성공)                                    ▼ (429 에러 발생)
                  [결과 반환]                              [Key A 카운트 복구(+1)]
                                                                 │
                                                                 ▼
                                                    [Key B로 자동 재시도 (1회)]
```

### 4) 사용자 에러 메시지 세분화 (UX 고도화)
모든 키가 완전히 소진되었을 때, 단순히 `500 Internal Server Error`를 던지는 대신 원인을 명확히 규명하여 프론트엔드에 전달합니다.
*   **RPM 초과:** "현재 요청이 많아 잠시 지연되고 있습니다. 1분 후 다시 시도해 주세요."
*   **TPM(토큰량) 초과:** "처리할 이미지가 너무 큽니다. 잘라서 다시 시도해 주세요."
*   **RPD 초과:** "오늘의 무료 제공량이 소진되었습니다. 내일 다시 이용해 주세요."

### 5) Single Source of Truth (SSOT) 어드민 모니터링
기존에는 API 상태를 인프라 모니터링, 번역 관리, OCR 성능 비교 등 여러 화면에서 각기 다른 API 엔드포인트로 조회하고 있었습니다. 이는 데이터 불일치(Desync) 문제를 유발하기 쉬운 구조였습니다. 

리팩토링을 통해 **모든 모니터링 화면이 단일한 쿼터 조회 데이터 소스(Single Source of Truth)를 공유**하도록 변경했습니다. 또한, 특정 키의 소진율이 80%를 초과할 시 대시보드에 시각적 경고(Warning)를 띄우고, 모든 키가 소진되어 요청이 최종 거부된 횟수를 별도 카운터로 누적하여 향후 인프라 확장 규모를 산정하는 지표로 활용하도록 했습니다.

### 6) 보안 강화를 위한 마스킹 (Masking)
`.env` 파일에 등록된 실제 API 키의 일부라도 화면에 노출되는 것을 원천 차단하기 위해, 시스템 내부적으로 실제 키와 연동되지 않는 임의의 라벨(예: `"Key A"`, `"Key B"`)을 부여하여 식별하고 관리합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 설계 및 구현을 통해 저희 팀이 얻은 핵심 교훈은 다음과 같습니다.

1.  **외부 API는 신뢰할 수 없는 블랙박스다:** 외부 서비스의 Rate Limit 정책과 로컬 데이터의 싱크는 언제나 어긋날 수 있습니다. 따라서 로컬에서의 정밀한 제어(Row-level Lock)뿐만 아니라, 실패했을 때 다시 원복하는 **'롤백 전략'과 '재시도 폴백 아키텍처'**가 동반되어야 시스템의 복원력(Resiliency)이 완성됩니다.
2.  **데이터 소스는 언제나 하나여야 한다 (SSOT):** 시스템 상태를 표현하는 대시보드가 다변화될수록 백엔드 데이터의 일관성 유지가 어렵습니다. 데이터를 가공하는 레이어와 표시하는 레이어를 철저히 분리해야 운영 중 혼선을 막을 수 있습니다.
3.  **에러 핸들링은 훌륭한 UX의 연장선이다:** 서버의 한계 상황을 사용자에게 투명하면서도 친절하게 설명하는 백엔드 에러 세분화 설계는 이탈률을 막는 중요한 방어벽이 됩니다.

단순한 키 로테이션 구현을 넘어, 동시성 제어와 장애 복구 시나리오까지 꼼꼼히 고려한 덕분에 저희 서비스는 트래픽 스파이크 상황에서도 단 한 건의 유실 없이 매끄럽게 인공지능 기능을 제공할 수 있게 되었습니다. 앞으로도 안정적이고 확장 가능한 서비스를 만들기 위한 고도화 고민을 계속해 나가겠습니다.
