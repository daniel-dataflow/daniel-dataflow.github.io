안녕하세요, PickSafe 팀의 시니어 백엔드 에디터입니다. 

최근 서비스 내에서 OCR 및 번역 기능을 위해 외부 LLM API(Gemini)를 도입하는 과정에서 마주한 **API 쿼터 제한(Rate Limit) 문제와 이를 해결하기 위한 분산 처리 아키텍처 설계 과정**을 공유하려 합니다.

타이트한 API 호출 제한 속에서 다중 계정의 키를 효율적으로 분산하고, 동시성 이슈(Race Condition)를 방어하며, 예외 상황에서 사용자 경험(UX)을 지켜낸 엔지니어링 의사결정 과정을 소개합니다.

---

## 1. Problem: 마주한 기술적 한계

서비스 초기, 우리는 단순히 일일 총 호출량인 **RPD(Requests Per Day)** 만을 추적하며 키를 관리하고 있었습니다. 그러나 실 서비스 환경을 시뮬레이션한 결과, 다음과 같은 치명적인 문제가 발견되었습니다.

1. **RPM(Requests Per Minute) 초과 위험**: 
   주력 모델(Flash-Lite 계열) 기준, 단일 API 키의 RPM은 15로 매우 타이트합니다. 관광객 등 트래픽이 몰리는 피크 타임에는 일일 총량(RPD)이 남아 있더라도 분당 요청 수 제한으로 인해 `429 Too Many Requests` 에러가 빈번하게 발생했습니다.
2. **동시성 환경에서의 Race Condition**: 
   기존의 `조회 -> 판단 -> 차감` 로직은 비동기/멀티스레드 환경에서 여러 요청이 동시에 동일한 키의 남은 쿼터를 읽어가게 만들었고, 이로 인해 특정 키로 트래픽이 쏠리는 병목이 발생했습니다.
3. **분산의 한계 인식**: 
   서로 다른 프로젝트의 API 키 2개를 확보하여 분산 처리를 구성하더라도, 합산된 RPM은 30에 불과합니다. 즉, **"분산처리는 여유를 늘려줄 뿐, 무제한으로 만들어주지 않는다"**는 전제 하에 견고한 예외 처리와 폴백(Fallback) 전략이 필수적이었습니다.

---

## 2. Trade-off & Architecture: 기술적 고민과 대안 비교

이 문제를 해결하기 위해 시스템을 재설계하며 내린 핵심 아키텍처 의사결정은 다음과 같습니다.

### ① 키 선택 전략: 순수 랜덤(Random) vs 여유 우선(Least-Loaded)
* **고민**: 키 2개 환경에서 순수 랜덤으로 키를 할당하면 우연히 한쪽으로 요청이 몰려 쉽게 429 에러를 마주하게 됩니다.
* **선택**: **"이번 분(Minute)에 사용량이 더 적은 키를 우선 선택"**하는 방식을 채택했습니다. 분 단위 카운터를 독립적으로 추적하여 부하를 기계적으로 분산시켰습니다.

### ② 동시성 제어: Redis 분산 락 vs DB Row-level Lock (`with_for_update`)
* **고민**: 쿼터 차감의 원자성(Atomicity)을 보장하기 위해 Redis 분산 락 도입을 검토했으나, 인프라 복잡도를 불필요하게 높인다고 판단했습니다.
* **선택**: 현재 백엔드 스택(SQLAlchemy)에서 제공하는 **`with_for_update()` (Row-level Lock)**를 활용하기로 했습니다. 트랜잭션 내에서 조회부터 차감까지의 락을 보장하여, DBMS 레벨에서 경쟁 상태를 완벽히 차단했습니다.

### ③ 장애 대응: 실패 시 즉시 에러 반환 vs 자동 재시도 및 롤백 (Rollback)
* **고민**: 로컬에서 계산한 쿼터와 실제 구글 서버의 상태가 네트워크 지연 등으로 어긋나 429가 발생할 수 있습니다.
* **선택**: 
  - 429 발생 시 **남은 다른 키로 즉시 1회 자동 재시도**하는 폴백 메커니즘을 구현했습니다.
  - 만약 로컬 DB에서 쿼터를 차감했으나 외부 API 통신 중 에러가 발생한 경우, **차감된 쿼터를 즉시 롤백(+1 복구)**하여 로컬 상태와 실제 사용량의 싱크 불일치(Ghost Quota)를 방지했습니다.

## 3. Key Takeaways: 엔지니어링 교훈

이번 아키텍처 리팩토링을 통해 얻은 가장 큰 교훈은 **"제한된 자원을 다룰 때는 클라이언트 측의 철저한 방어적 설계가 사용자 경험(UX)을 좌우한다"**는 점입니다.

* **세분화된 에러 핸들링과 UX**: 
  모든 키가 소진되었을 때 무뚝뚝한 "에러 발생" 화면을 보여주는 대신, 쿼터 초과 원인(RPM 초과, TPM 토큰 초과, RPD 일일 한도 초과)에 따라 **사용자에게 명확한 가이드 메시지**를 제공하도록 개선했습니다.
* **모니터링 데이터 소스 단일화**: 
  인프라 모니터링, 번역 관리, OCR 성능 비교 등 여러 어드민 화면에서 제각각 쿼터를 조회하던 구조를 **하나의 통합 쿼터 조회 파이프라인**으로 묶어 데이터 정합성을 확보했습니다. 또한 80% 이상 소진 시 시각적 경고를 추가하여 운영 안정성을 높였습니다.
* **보안 원칙 준수**: 
  실제 API 키의 노출을 원천 차단하기 위해 화면상에는 실제 문자열 대신 독립적인 라벨("키 A", "키 B")을 매핑하여 보안성을 강화했습니다.

외부 API의 제약이라는 물리적 한계를 완벽히 우회할 수는 없지만, **정교한 분산 제어와 실패 복구 로직**을 통해 서비스의 탄력성(Resilience)을 한 단계 끌어올릴 수 있었습니다. 앞으로도 PickSafe는 안정적인 인프라 아키텍처를 바탕으로 신뢰도 높은 서비스를 만들어 가겠습니다.
