최근 LLM(대형 언어 모델)을 서비스에 도입하는 기업이 늘고 있습니다. 하지만 프로덕션 환경에서 글로벌 테크 기업의 API(예: Google Gemini)를 사용할 때 가장 먼저 마주치는 현실적인 장벽은 바로 **'쿼터(Quota) 제한'**입니다. 

특히 무료 티어나 낮은 등급의 엔터프라이즈 계정의 경우, 주력 모델의 RPM(분당 요청 수)과 RPD(일일 요청 수)가 매우 타이트하게 제한되어 있습니다. 

우리 팀 역시 Gemini Flash-Lite 계열을 활용해 OCR 및 번역 서비스를 구축하는 과정에서 **"2개 API 키 합산 최대 30 RPM, 1,000 RPD"**라는 극단적인 제약 조건과 마주했습니다. 이 문제를 해결하기 위해 단순한 라운드 로빈 방식을 넘어, **동시성(Concurrency)을 보장하고 실시간 모니터링이 가능한 다중 API 키 분산 처리 아키텍처**를 재설계한 과정을 공유합니다.

---

## 1. 문제 정의: 단순한 쿼터 추적이 실패한 이유

처음 설계했던 프로토타입 분산 처리 방식에는 두 가지 치명적인 맹점이 있었습니다.

### ① RPD(일일 총량)만 관리하고 RPM(분당 요청)은 방치함
사용자가 몰리는 특정 시간대에 갑작스러운 동시 요청이 발생하면, 하루 한도(RPD)는 넉넉하더라도 분당 한도(RPM)가 초과되어 `429 Too Many Requests` 에러가 쏟아졌습니다.

### ② 'Check-Then-Act' 구조로 인한 경쟁 상태(Race Condition)
기존의 키 선택 로직은 다음과 같았습니다.
1. DB에서 키들의 현재 사용량을 조회한다.
2. 여유가 있는 키를 하나 선택한다.
3. 해당 키의 사용량을 DB에 1 증가(차감)시키고 API를 호출한다.

이 구조는 단일 요청만 들어올 때는 잘 작동합니다. 하지만 **수십 개의 요청이 동시에 들어오는 멀티스레드/비동기 환경**에서는 여러 요청이 동일한 시점에 "키 A가 비어있음"을 확인하고 동시에 키 A를 선택해 버립니다. 결국 특정 키에 요청이 몰리며 실시간 한도를 초과하는 경쟁 상태가 발생했습니다.

## 2. 기술적 고민과 대안 비교

이를 해결하기 위해 크게 세 가지 아키텍처적 의사결정이 필요했습니다.

### Q1. 실시간 쿼터 관리를 어디서 할 것인가? (Redis vs DB)
* **대안 A: Redis (In-Memory)**
  * **장점**: 분당 리셋되는 고정 버킷(Fixed Window)을 `INCR`와 `EXPIRE` 명령어로 매우 빠르고 원자적(Atomic)으로 처리할 수 있습니다.
  * **단점**: 인프라 복잡도가 늘어나고, 일일 총량(RPD) 및 어드민 모니터링을 위한 영속성 데이터를 결국 RDB와 동기화해야 하는 이중 관리 비용이 발생합니다.
* **대안 B: RDB + Row-Level Locking (선택)**
  * **이유**: 현재 인프라 구조에서 추가적인 Redis 도입 없이 기존 관계형 데이터베이스를 활용하기로 결정했습니다. 다중 API 키가 2~4개 수준으로 소규모이므로, RDB의 **비관적 락(Pessimistic Lock)**을 활용해도 충분히 성능을 보장할 수 있다고 판단했습니다.

### Q2. 어떤 키를 먼저 선택할 것인가? (Random vs Least-Utilized)
* **대안 A: 순수 랜덤 / 라운드 로빈**
  * **단점**: 한도가 타이트한 상황(키당 RPM 5~15)에서 우연히 한 키에 요청이 연속으로 몰리면 바로 429 에러가 발생합니다.
* **대안 B: 사용량이 가장 적은 키 우선 선택 (선택)**
  * **이유**: "이번 분(minute)에 가장 적게 사용된 키"를 우선적으로 매칭함으로써 쿼터를 균등하게 소모하고 버스트(Burst) 요청에 유연하게 대응할 수 있도록 했습니다.

## 3. 최종 해결 및 엔지니어링 구현

우리는 안정성, 일관성, 그리고 우아한 예외 처리를 목표로 삼고 다섯 가지 핵심 원칙을 세워 아키텍처를 재구현했습니다.

### ① SQLAlchemy `with_for_update()`를 통한 원자성 보장
경쟁 상태를 원천 차단하기 위해, "조회 및 차감"을 하나의 데이터베이스 트랜잭션 내에서 **비관적 락(Row-Level Lock)**으로 묶었습니다.

```python
# 개념적 구현 예시 (SQLAlchemy)
async def acquire_available_key(session: AsyncSession):
    async with session.begin():
        # 1. 쿼터가 남아있고 현재 분(Minute)에 사용량이 가장 적은 키를 Row-Lock과 함께 조회
        stmt = (
            select(APIKeyQuota)
            .where(
                APIKeyQuota.current_rpm < APIKeyQuota.max_rpm,
                APIKeyQuota.current_rpd < APIKeyQuota.max_rpd
            )
            .order_by(APIKeyQuota.current_rpm.asc()) # 사용량 적은 순
            .with_for_update() # SELECT ... FOR UPDATE (Row-level Lock)
        )
        result = await session.execute(stmt)
        api_key_record = result.scalars().first()

        if not api_key_record:
            raise QuotaExceededException("모든 API 키의 쿼터가 소진되었습니다.")

        # 2. 조회와 동시에 즉시 사용량 차감 (원자적 연산)
        api_key_record.current_rpm += 1
        api_key_record.current_rpd += 1
        await session.commit()
        
        return api_key_record.key_label
```

### ② API 실패 시 원상복구(Rollback) 메커니즘 구축
로컬 DB에서 성공적으로 쿼터를 차감했더라도, 실제 외부 API 호출 과정에서 네트워크 순단이나 500 에러 등으로 요청이 실패할 수 있습니다. 이 경우 차감했던 로컬 카운트를 반드시 다시 복구(`+1 -> -1`)해 주어야 실시간 싱크 불일치(Drift)를 막을 수 있습니다.

```python
try:
    response = await call_gemini_api(key_label)
except GeminiAPIException as e:
    # API 호출 실패 시 로컬 DB 카운트 복구(Rollback)
    await rollback_key_quota(key_label)
    raise e
```

### ③ 429 대응을 위한 즉시 1회 자동 재시도 (Fallback Chain)
네트워크 지연이나 외부 플랫폼 이슈로 실시간 동기화가 어긋나 429 에러가 발생하면, 즉시 다른 후보 키로 **1회 자동 재시도(Failover)**를 수행하여 클라이언트가 느끼는 에러율을 제로에 가깝게 유지했습니다.

### ④ 에러 메시지 세분화를 통한 사용자 경험(UX) 개선
모든 쿼터 초과 상황을 동일한 오류로 처리하지 않고, 원인에 따라 세분화된 가이드를 클라이언트에 제공합니다.
* **RPM 초과**: "현재 요청이 많아 지연되고 있습니다. 1분 후 다시 시도해 주세요."
* **TPM (토큰) 초과**: "입력 데이터의 양이 너무 많습니다. 이미지를 분할하여 시도해 주세요."
* **RPD 초과**: "오늘의 무료 제공량이 소진되었습니다. 내일 다시 이용해 주세요."

### ⑤ 어드민 대시보드의 '단일 데이터 소스(Single Source of Truth)' 확립
기존에는 인프라 모니터링, 번역 관리, OCR 성능 비교 화면이 각자 다른 데이터 모델이나 엔드포인트를 통해 데이터를 조회하고 있어 수치 불일치가 발생할 우려가 있었습니다. 

이를 해결하기 위해 **모든 화면이 동일한 쿼터 조회 API 엔드포인트를 공유**하도록 단일화하고, 어드민 화면 단에서 필터링해서 보여주도록 변경했습니다. 또한, 특정 키의 소진율이 **80% 이상**이 되면 시각적 경고(색상 변화)를 주어 관리자가 선제적으로 대응할 수 있도록 했습니다.

## 4. 보안 강화를 위한 Key 마스킹 전략

보안 취약점을 방어하기 위해 화면이나 로그 어디에도 실제 API 키의 일부(`AQ.A***6V9w`)조차 노출하지 않도록 설계했습니다. 대신 서버 기동 시 내부적으로 `.env` 환경 변수를 로드할 때 각 키에 **"KEY_A", "KEY_B"**와 같은 추상적인 논리적 라벨을 매핑하여 데이터베이스 및 모니터링 시스템에서 사용하도록 처리했습니다.

## 5. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 재설계 작업을 통해 얻은 핵심 레슨런은 다음과 같습니다.

1. **인프라 제약 조건은 아키텍처의 기본 전제이다**: 외부 API 요금과 물리적 한도는 개발자가 컨트롤할 수 없는 영역입니다. 시스템은 "한도가 절대 초과되지 않는다"가 아니라 **"언젠간 초과될 것이며, 그때 어떻게 우아하게 대처할 것인가(Graceful Degradation)"**를 전제로 설계되어야 합니다.
2. **동시성 제어는 처음부터 고려해야 한다**: 로컬 환경(단일 요청)에서 잘 돌던 코드가 프로덕션(멀티스레드/비동기)에서 깨지는 가장 흔한 원인은 `Check-Then-Act` 패턴입니다. 데이터의 일관성이 중요한 비즈니스 로직에는 항상 트랜잭션 격리 수준과 락(Lock) 전략을 명확히 해야 합니다.
3. **모니터링의 일관성이 신뢰를 만든다**: 운영 중 대시보드마다 수치가 다르게 표현되면 개발자와 운영팀 모두 시스템 상태를 불신하게 됩니다. 데이터의 읽기 경로(Query Path)를 단일화하는 것이 유지보수 관점에서 얼마나 중요한지 다시금 깨달았습니다.
