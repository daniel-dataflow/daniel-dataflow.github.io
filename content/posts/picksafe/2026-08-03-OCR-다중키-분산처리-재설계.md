최근 LLM 기반 서비스를 운용하면서 가장 흔히 직면하는 걸림돌 중 하나는 **외부 API의 타이트한 Rate Limit(초당/분당 요청 한도)**입니다. 특히 무료/스타터 쿼터 환경에서는 분당 요청 수(RPM)가 5~15회 수준으로 대단히 제한적입니다.

PickSafe 팀은 OCR 및 번역 파이프라인에서 Gemini API를 활용하던 중, 트래픽 분산을 위해 복수의 API 키를 도입했음에도 **동시 접속 시 429 Too Many Requests 에러가 빈번하게 발생하는 문제**를 겪었습니다. 

본 포스팅에서는 이 문제를 원인부터 분석하고, **동시성 환경에서의 경쟁 상태(Race Condition) 해결**, **원자적(Atomic) 쿼터 차감**, 그리고 **재시도/롤백 메커니즘**을 엔지니어링적으로 어떻게 설계했는지 공유합니다.

---

## 1. 문제 정의: "일일 한도는 충분한데, 왜 429 에러가 터질까?"

기존 시스템은 단순한 구조였습니다. 일일 허용량(RPD, Requests Per Day)만을 추적하고, 여러 API 키 중 하나를 무작위(Random)로 선택해 요청을 보내는 방식이었습니다.

하지만 실제 사용자가 몰리는 peak-time 분석 결과, 다음과 같은 심각한 허점이 드러났습니다.

### 1) RPD와 RPM의 미스매치
주력 모델인 `Gemini Flash-Lite` 계열의 한도는 키 1개당 **RPM 15, RPD 500**이었습니다. 키 2개를 합쳐도 **분당 최대 30회**만 처리가 가능했습니다. 하루 전체 쿼터(RPD)가 넉넉히 남아있더라도, 특정 1분 동안 요청이 15회를 넘어서는 순간 외부 API 서버는 즉시 429 에러를 반환했습니다.

### 2) "조회 후 차감"이 만든 경쟁 상태 (Race Condition)
기존 로직은 다음과 같은 순서로 작동했습니다:
1. DB에서 키 A의 사용량을 조회한다. (`SELECT`)
2. 한도가 남았는지 판단한다. (`IF usage < limit`)
3. 키 A로 API를 호출하고 사용량을 +1 한다. (`UPDATE`)

동시 요청 10개가 0.1초 사이에 몰릴 경우, **모든 요청이 1번 단계를 동시에 통과**하여 동일한 키로 몰리는 현상이 발생했습니다. 로컬 DB가 차감 상태를 기록하기도 전에 구글 서버의 RPM 한도를 초과해 버리는 것이었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 3가지 핵심 영역에서 기술적 대안을 검토했습니다.

### 고민 A: 분당 사용량(RPM) 추적 알고리즘
- **대안 1: 슬라이딩 윈도우 (Sliding Window)**
  - *장점*: 정확한 초 단위 윈도우 기반 한도 관리 가능.
  - *단점*: Redis 등의 In-Memory 저장소 필요성 증가 및 구현 복잡도 상승.
- **대안 2: 고정 1분 버킷 (Fixed 1-Minute Bucket)**
  - *장점*: 매 분 0초마다 카운터를 리셋하는 단순한 구조로, DB overhead가 적음.
  - *단점*: 윈도우 경계 시점(예: 59초와 01초)에 순간적으로 2배의 트래픽이 몰릴 가능성 존재.
- **선택**: **대안 2 (고정 버킷)**. 
  현재 서비스 규모 및 RPM 한도(15~30)를 감안할 때, 고정 버킷 방식만으로도 충분한 안정성을 확보할 수 있으며 시스템 복잡도를 낮추는 trade-off가 타당하다고 판단했습니다.

### 고민 B: 동시성 제어 및 원자성(Atomicity) 보장 방식
- **대안 1: Application-level Lock (e.g. Asyncio Lock)**
  - *장점*: DB 입출력 없이 메모리 단에서 빠르게 처리.
  - *단점*: 분산 서버 환경(Multi-worker)으로 확장 시 프로세스 간 동기화 불가.
- **대안 2: DB Row-Level Lock (`SELECT FOR UPDATE`)**
  - *장점*: 트랜잭션 범위 내에서 완전한 원자성 보장. 멀티 워커 환경에서도 안전함.
  - *단점*: DB Lock 대기로 인한 미세한 Latency 증가.
- **선택**: **대안 2 (`with_for_update()`)**.
  LLM API 호출 자체의 Latency(약 1~3초)에 비해 DB Lock 대기 시간(수 ms)은 무시할 수 있는 수준입니다. 확실한 데이터 일관성을 위해 SQL-ORM 레벨의 비관적 락(Pessimistic Lock)을 채택했습니다.

### 고민 C: 키 선택 전략
- **대안 1: 순수 무작위 (Random) / 라운드로빈 (Round-Robin)**
  - 키별 실시간 사용량 편차를 반영하지 못해 특정 키의 RPM만 초과될 위험.
- **대안 2: 사용량 최소 키 우선 (Least-Used First)**
  - 현재 분(Minute) 기준으로 **가장 여유가 있는 키를 우선 선택**.
- **선택**: **대안 2 (Least-Used First)**. RPM 한도가 매우 타이트하므로 균등한 부하 분산이 최우선 과제였습니다.

## 3. 최종 아키텍처 및 핵심 구현

전체적인 API 호출 파이프라인은 아래와 같은 흐름으로 재설계되었습니다.

```
[클라이언트 요청]
       │
       ▼
[트랜잭션 시작 (with_for_update)]
       │ ── 1. 현재 분(Minute)의 사용량이 가장 적은 키 조회 & 차감 (+1)
       ▼
[Gemini API 호출]
       ├── (성공) ──► [트랜잭션 커밋 & 결과 반환]
       │
       └── (429 에러 발생)
              │
              ├── 2. 차감했던 사용량 즉시 롤백 (-1)
              ├── 3. 보조 키(Key B)로 자동 1회 재시도
              └── (모든 키 소진 시) ──► [원인별 상세 에러 반환 (RPM/TPM/RPD)]
```

### 1) 원자적 쿼터 조회 및 차감 (Pessimistic Locking)
SQLAlchemy ORM을 활용하여 조회와 검증, 차감을 **단일 트랜잭션 내에서 원자적으로 처리**합니다.

```python
# 비즈니스 로직의 개념적 구조 (보안을 위해 단순화됨)
async def acquire_available_key(session: AsyncSession, current_minute: datetime) -> KeyModel:
    # 1. Row-level Lock을 사용해 분당/일당 한도가 남은 키 중 가장 적게 사용된 키 조회
    stmt = (
        select(APIKeyQuota)
        .where(
            APIKeyQuota.rpm_usage < APIKeyQuota.rpm_limit,
            APIKeyQuota.rpd_usage < APIKeyQuota.rpd_limit
        )
        .order_by(APIKeyQuota.rpm_usage.asc()) # 여유 있는 키 우선
        .with_for_update()                      # 원자성 보장을 위한 비관적 락
    )
    
    result = await session.execute(stmt)
    selected_key = result.scalars().first()
    
    if not selected_key:
        raise QuotaExhaustedException("ALL_KEYS_EXHAUSTED")
        
    # 2. 조회와 동시에 사용량 차감 (원자적 연산)
    selected_key.rpm_usage += 1
    selected_key.rpd_usage += 1
    await session.commit()
    
    return selected_key
```

### 2) 롤백(Rollback) 및 장애 전이(Failover) 보장
외부 API 호출 중 429(Rate Limit) 혹은 5xx 에러가 발생한 경우, **로컬 DB에서 차감했던 카운트를 반드시 보상 트랜잭션(Rollback)으로 복구**해야 로컬 카운트와 실제 외부 서비스의 상태 불일치를 막을 수 있습니다.

또한, 1번 키에서 429가 발생하면 사용자에게 즉시 에러를 던지지 않고 **2번 키로 자동 1회 재시도(Failover)** 하도록 구현했습니다.

### 3) 사용자 경험(UX) 세분화
모든 키가 소진되었을 때, 단순 `500 Internal Server Error`가 아닌 발생 원인에 따른 명확한 가이드를 제공하도록 처리했습니다.

- **RPM 초과**: *"현재 요청이 몰리고 있습니다. 1분 후 다시 시도해 주세요."*
- **TPM 초과**: *"처리할 이미지/텍스트 양이 많습니다. 분량 조절 후 시도해 주세요."*
- **RPD 초과**: *"오늘의 무상 제공량이 소진되었습니다. 내일 다시 이용해 주세요."*

### 4) 단일 진실 공급원 (SSOT) 대시보드
어드민 모니터링 화면(인프라 모니터링, 번역 관리, OCR 성능 비교)이 서로 다른 엔드포인트를 호출하여 수치가 파편화되는 문제를 방지하기 위해, **통합 쿼터 조회 메트릭 API** 하나만을 바라보도록 통일했습니다. 

보안을 위해 실제 API Key 문자열(`AIzaSy...`)은 절대 프론트엔드에 노출하지 않고, 시스템 내부 매핑 라벨(`Key A`, `Key B`)로만 시각화했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

1. **외부 API 분산 처리는 "무제한"이 아니라 "시간을 버는 것"이다.**
   - 아무리 로드 밸런싱을 완벽하게 구현하더라도, 업스트림 API의 한도 절대치가 낮다면 과도한 트래픽을 모두 감당할 수는 없습니다. 따라서 아키텍처의 목표는 **"한도 내에서 최대한 쥐어짜되, 초과 시 사용자에게 친절하게 우아한 실패(Graceful Degradation)를 제공하는 것"**이어야 합니다.

2. **상태를 갖는(Stateful) 외부 연동 시에는 보상 트랜잭션이 필수적이다.**
   - 로컬 DB 차감 후 외부 통신이 실패했을 때 롤백 처리를 하지 않으면, 멀쩡한 키가 "사용 불가능" 상태로 마킹되어 서비스 전체의 가용성이 급격히 떨어집니다.

3. **동시성 문제는 테스트 단계에서 부하 시뮬레이션으로 검증해야 한다.**
   - 단발성 테스트에서는 드러나지 않던 경쟁 상태가 동시 요청 시뮬레이션을 통해서만 포착되었습니다. `with_for_update()`와 같은 원자성 보장 장치가 제대로 동작하는지 단위/통합 테스트 체크리스트를 정립하는 계기가 되었습니다.
