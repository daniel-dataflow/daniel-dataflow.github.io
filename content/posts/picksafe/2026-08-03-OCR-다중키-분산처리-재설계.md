외부 LLM API를 활용해 실시간 서비스를 구축할 때 가장 자주 마주치는 병목은 무엇일까요? 바로 **'API Rate Limit(호출 제한)'**입니다. 

PickSafe팀은 Gemini API를 활용한 OCR 및 번역 서비스를 운영하던 중, 사용자 트래픽 급증 시 429(Too Many Requests) 에러가 빈번하게 발생하는 문제를 겪었습니다. 단순히 여러 개의 API 키를 돌려쓰는 얇은 상면의 분산 처리로는 해결되지 않았던 동시성 한계와, 이를 해결하기 위해 백엔드 아키텍처를 전면 재설계한 과정을 공유합니다.

---

## 1. 문제 정의: "왜 키를 여러 개 쓰는데도 429 에러가 나는가?"

초기 시스템은 일단 RPD(일일 총 요청량)만을 메모리에서 추적하며 여러 개의 키를 순수 랜덤(Random) 방식으로 선택해 호출했습니다. 하지만 서비스가 확장되면서 두 가지 주요 결함이 표면화되었습니다.

### ① RPD(일일 제한) 관리만으로는 RPM(분당 제한) 폭주를 막을 수 없다
Gemini의 Flash-Lite 모델 기준, 키당 한도는 **RPM 15, RPD 500** 수준으로 분당 처리할 수 있는 양이 상당히 타이트합니다. 일일 쿼터(RPD)가 넉넉히 남아있더라도, 점심시간이나 특정 이벤트 시점에 사용자가 몰리면 1초 안에 15회 이상의 요청이 몰려 즉시 `HTTP 429`가 터졌습니다.

### ② '조회-판단-차감' 사이의 경쟁 상태(Race Condition)
동시 요청이 몰릴 때 기존 로직은 다음과 같이 동작했습니다.

```
[요청 A] ──(1. 키1 남은 쿼터 조회: 5개 남음) ──(2. 키1 선택) ─────────────────> (3. 키1 차감)
[요청 B] ────(1. 키1 남은 쿼터 조회: 5개 남음) ────(2. 키1 선택) ───────────────> (3. 키1 차감)
```

요청 A와 B가 동시에 들어오면, 두 요청 모두 아직 차감되지 않은 키 1의 쿼터를 확인하고 동일한 키 1을 선택합니다. 결과적으로 **초과 할당(Over-subscription)**이 발생하여 실제 API 서버에서는 요청이 거부되었습니다.

### ③ 고스트 쿼터 차감(Phantom Exhaustion) 현상
로컬 DB/메모리에서 쿼터를 성공적으로 차감했으나, 정작 구글 API 서버 통신 단계에서 네트워크 타임아웃이나 5xx 에러가 발생했을 때 **차감한 쿼터를 복구(Rollback)하지 않는 문제**가 있었습니다. 이로 인해 실제로는 쓰지도 않은 API 쿼터가 마모되어 멀쩡한 키가 차단되는 현상이 발생했습니다.

## 2. 기술적 고민과 트레이드오프 (Trade-off)

이 문제를 해결하기 위해 시스템 아키텍처 설계 시 세 가지 핵심 트레이드오프를 고려했습니다.

### Trade-off 1: 분 단위 슬라이딩 윈도우 vs 고정 버킷(Fixed Bucket)
* **슬라이딩 윈도우(Sliding Window):** 정교하게 최근 60초간의 요청 수를 계산할 수 있으나 Redis 등 별도의 인메모리 시계열 데이터 구조가 필요하고 구현 복잡도가 높음.
* **고정 버킷(Fixed 1-Minute Bucket):** 매 분 00초마다 RPM 카운터를 리셋하는 방식. 미세한 경계 시점(59초->00초)의 트래픽 스파이크 위험은 있으나, 데이터베이스 구조가 단순해지고 락 트랜잭션 수용량이 뛰어남.
* **결정:** 현재 처리해야 하는 시스템 규모상 고정 버킷 방식으로도 충분히 안정성을 확보할 수 있다고 판단하여 **고정 버킷 방식**을 채택했습니다.

### Trade-off 2: 인메모리(Redis) Atomic Incr vs RDBMS 비관적 락(Pessimistic Lock)
* **Redis:** 성능이 압도적으로 빠르지만, 분산 환경에서 RPD/RPM의 영속성 보장 및 어드민 모니터링 데이터와의 실시간 동기화 레이어가 추가로 필요함.
* **RDBMS (`with_for_update`):** 디스크 IO 부담이 있지만, 정확히 단일 트랜잭션 내에서 **"여유 키 검색 -> Row Lock -> 쿼터 검증 -> 차감"**을 완벽한 원자성(Atomicity)으로 처리 가능.
* **결정:** 초당 수만 건 이상의 초고성능 트래픽보다는 **"단 1건의 동시성 오류도 없는 엄격한 쿼터 제어"**가 우선이었기에, SQLAlchemy의 `with_for_update()`를 통한 **비관적 락(Row-level Lock)** 방식을 선택했습니다.

## 3. 엔지니어링 해결책

### (1) 비관적 락 기반의 원자적(Atomic) 쿼터 차감 & 알고리즘 개선
키 선택 알고리즘을 '순수 랜덤'에서 **'현재 분(Minute)의 잔여 RPM이 가장 많이 남은 키 우선(Greedy)'** 구조로 변경했습니다.

```python
# [개념적 구현 코드 예시 - 보안 마스킹 처리됨]
def get_and_decrement_capacity(session, current_minute, current_date):
    """
    현재 분/일자 기준으로 가장 여유 있는 키를 원자적으로 조회하고 차감합니다.
    """
    # 1. Row-level Lock을 걸어 동시 접근 제어 (SQLAlchemy with_for_update)
    stmt = (
        select(APIKeyQuota)
        .where(APIKeyQuota.is_active == True)
        .where(APIKeyQuota.current_rpm < APIKeyQuota.max_rpm)
        .where(APIKeyQuota.current_rpd < APIKeyQuota.max_rpd)
        .order_by((APIKeyQuota.max_rpm - APIKeyQuota.current_rpm).desc()) # 여유 쿼터가 가장 많은 순
        .with_for_update()
    )
    
    selected_key = session.execute(stmt).scalars().first()
    
    if not selected_key:
        raise QuotaExhaustedException("모든 API 키의 쿼터가 소진되었습니다.")

    # 2. 원자적 차감 진행
    selected_key.current_rpm += 1
    selected_key.current_rpd += 1
    session.commit()
    
    return selected_key
```

### (2) 보상 트랜잭션(Rollback)과 자동 Failover (1회 재시도)
외부 API 호출이 실패할 경우 쿼터를 복구하는 보상 트랜잭션 로직과, 429 발생 시 다른 키로 즉시 우회하는 복구 회로를 구축했습니다.

```
[사용자 요청]
   │
   ▼
[원자적 키 차감 (Key A)] ──(실패 시 롤백)──┐
   │                                   │
   ▼                                   │
[Gemini API 호출 (Key A)]               │
   │                                   │
   ├───(HTTP 429 획득) ───> [Key A 롤백] ──> [다른 키(Key B)로 1회 재시도]
   │                                           │
   └───(네트워크/5xx 에러) ─> [Key A 롤백] ──> [에러 응답]
```

### (3) 사용자 경험(UX) 관점의 에러 세분화
쿼터가 전량 소진되었을 때 단순 "서버 에러"를 던지는 대신, 초과한 쿼터 종류에 따라 세분화된 에러 응답을 전달하도록 개선했습니다.

* **RPM (분당 요청 초과):** `"현재 요청이 몰려 잠시 지연되고 있습니다. 1분 후 다시 시도해 주세요."`
* **TPM (분당 토큰 초과):** `"처리할 이미지/텍스트 용량이 큽니다. 분량을 줄여 다시 시도해 주세요."`
* **RPD (일일 제한 초과):** `"오늘의 제공량이 모두 소진되었습니다. 내일 다시 이용해 주세요."`

### (4) observability & 보안: Single Source of Truth와 Key 식별자 캡슐화
어드민 대시보드 내 여러 화면(인프라 모니터링, 번역 관리, OCR 성능 비교)이 서로 다른 API를 호출하여 상태 수치가 불일치하던 문제를 해결하기 위해 **통합 쿼터 데이터 프로바이더(Unified Quota Provider)**를 구축했습니다.

또한, 어드민 화면상에 실제 API Key 시크릿 문자열이나 마스킹된 하위 값(`AQ.A***6V9w`)이 노출되는 보안 위험을 방지하기 위해, 내부 환경 변수 매핑 기반의 **추상화 라벨("키 A", "키 B")**만을 클라이언트에 응답하도록 전면 캡슐화했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

이번 아키텍처 재설계를 진행하며 얻은 시니어 관점의 엔지니어링 레슨은 다음과 같습니다.

1. **"다중 키/인스턴스는 여유 공간을 늘려줄 뿐, 무제한을 의미하지 않는다"**  
   키를 2개, 4개로 늘려도 분산 라우터의 '원자성'이 보장되지 않는다면 동시성 병목 시점에는 다 같이 무너집니다. 아키텍처의 핵심은 수평 확장(Scale-out) 그 자체보다 **제어 흐름의 동기화(Synchronization)**에 있습니다.
2. **외연 실패(Upstream Failure)에 대한 보상 트랜잭션은 필수다**  
   내부 DB 상태를 업데이트했더라도 외부 벤더 API 호출 단계에서 오류가 날 수 있음을 항상 전제해야 합니다. 실패 시 로컬 상태를 원복하는 롤백 메커니즘이 없으면 '유령 사용량'으로 인해 서비스 가용성이 갉아먹히게 됩니다.
3. **모니터링 데이터는 단 하나의 진실 원천(Single Source of Truth)을 가리켜야 한다**  
   동일한 상태 데이터가 뷰(View) 단위로 파편화되면 운영 중 상황 판단을 그르치기 쉽습니다. 모니터링 파이프라인은 초기 단계부터 통합 엔드포인트/서비스 레이어로 묶어 관리하는 것이 유지보수성을 극대화합니다.
