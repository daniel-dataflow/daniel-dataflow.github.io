글로벌 서비스를 지향하는 **PickSafe** 제품군에서는 이미지 기반 OCR과 실시간 번역 처리 유즈케이스를 해결하기 위해 Google Gemini API를 적극적으로 활용하고 있습니다. 

그러나 LLM 인프라를 운용하다 보면 필수적으로 마주치는 제약이 있습니다. 바로 **API Provider의 엄격한 쿼터(Quota) 제한**입니다. 특히 서비스 초기 단계나 비용 효율화를 위한 무료/최저 프라이싱 티어에서는 **Flash-Lite 계열 기준 RPM 15(분당 요청 수), RPD 500(일일 요청 수)**이라는 극도로 제한된 환경에서 안정적인 서비스를 제공해야 합니다.

사용자가 일시적으로 몰리는 피크 타임(Peak Time)에 단순 호출 구조는 즉시 `429 Too Many Requests` 에러 폭탄으로 이어집니다. 이번 포스팅에서는 다중 API 키 환경에서 발생하는 **경쟁 상태(Race Condition)를 해결하고, 분산 처리 및 실시간 모니터링 체계를 구축한 프로덕션 재설계 과정**을 소개합니다.

## 1. 문제 정의: "키를 여러 개 쓰는데 왜 429가 발생할까?"

기존 아키텍처는 일일 누적 사용량(RPD)만 추적하고, 동시 요청 시 무작위(Random)로 키를 할당하는 방식이었습니다. 이 구조는 두 가지 치명적인 맹점을 안고 있었습니다.

### ① RPM과 RPD의 디커플링 문제
* **일일 총량(RPD)**만 체크하고 **분당 요청 수(RPM)**를 추적하지 않았습니다.
* 하루 쿼터(RPD 500)가 넉넉히 남아있어도, 사용자 5명이 동시 1초에 접속하면 RPM(15 limit) 한도를 즉시 초과하여 서비스가 마비되었습니다.

### ② "조회 후 차감" 패턴이 초래한 경쟁 상태(Race Condition)
전형적인 **Check-Then-Act** 패턴의 문제였습니다.

```
[Request 1] ──(쿼터 남아있나? Yes) ───────────────> (키 A 선택 & 차감)
[Request 2] ──(쿼터 남아있나? Yes) ──> (키 A 선택 & 차감)
```

두 개 이상의 비동기 worker 요청이 거의 동시에 들어올 경우, 동일한 API 키의 남은 쿼터를 읽어 들여 **모두 같은 키로 몰리는 쏠림 현상**이 발생했습니다. 결과적으로 로컬 모니터링 수치와 실제 Google API 서버의 쿼터 상태가 어긋나며 429 에러가 터졌습니다.

## 2. 아키텍처 개선과 엔지니어링 Trade-off

저희 팀은 시스템 안정성을 확보하기 위해 다음 4가지 핵심 원칙을 세우고 아키텍처 재설계를 진행했습니다.

### ① 고정 창(Fixed Window) 버킷 기반의 RPM / RPD 독립 추적
RPM과 RPD는 완전히 독립된 수치로 관리되어야 합니다. 키 선정을 위한 알고리즘 도입 전, 분 단위 카운터 리셋 구조가 필요했습니다.

* **Trade-off 고민:** *슬라이딩 윈도우(Sliding Window)* 알고리즘 vs *고정 창(Fixed Window)* 알고리즘
  * **Sliding Window:** 경계 조건에서의 쿼터 초과를 완벽하게 막지만, Redis 등 메모리 기반 구조와 ZSET 자료구조 운용 비용/구현 복잡도가 높음.
  * **Fixed Window (채택):** 매 분 0초마다 카운터를 리셋하는 방식. 트래픽 분산 알고리즘(가장 여유 있는 키 우선 선택)과 조합하면 프로덕션 요구사항을 충분히 충족하면서도 오버헤드가 적음.

### ② pessimistic Locking(비관적 락)을 통한 원자적(Atomic) 쿼터 차감
동시성 문제를 해결하기 위해 애플리케이션 레벨의 락이 아닌, **DB 트랜잭션 레벨의 비관적 락(Pessimistic Locking)**을 채택했습니다.

SQLAlchemy ORM 환경에서 `with_for_update()` 구문을 활용하여 **"조회 + 판단 + 차감" 과정을 단일 원자적 연산(Atomic Operation)**으로 묶었습니다.

```python
# [개념 코드 예시 - 보안상 도메인 로직 마스킹]
async def allocate_least_used_api_key(db: AsyncSession, current_minute: datetime):
    """
    현재 분(Minute) 기준 RPM 여유가 가장 많은 키를 비관적 락(Row-level Lock)으로 조회 및 즉시 차감
    """
    stmt = (
        select(KeyQuotaModel)
        .where(KeyQuotaModel.is_active == True)
        .where(KeyQuotaModel.rpd_used < KeyQuotaModel.rpd_limit)
        .where(KeyQuotaModel.rpm_used < KeyQuotaModel.rpm_limit)
        .order_by(KeyQuotaModel.rpm_used.asc())  # 여유 있는 키 우선 (Least-Used First)
        .with_for_update()  # SELECT ... FOR UPDATE (Row-level Lock)
    )
    
    result = await db.execute(stmt)
    selected_key = result.scalars().first()
    
    if not selected_key:
        raise QuotaExhaustedException("ALL_KEYS_EXHAUSTED")
        
    # 조회와 동시에 차감 수행 (원자성 보장)
    selected_key.rpm_used += 1
    selected_key.rpd_used += 1
    await db.commit()
    
    return selected_key
```

### ③ 429 장애 전이 방지: 자동 재시도 및 보상 트랜잭션(Rollback)
로컬에서 원자적으로 쿼터를 차감했더라도, 네트워크 지연이나 외부 서버의 판단 오차로 `429 Too Many Requests` 또는 `500 Server Error`가 발생할 수 있습니다.

1. **자동 서킷 릴레이(Failover):** A 키에서 429가 발생하는 즉시 B 키로 1회 자동 재시도합니다.
2. **보상 트랜잭션 (Rollback):** 외부 API 호출이 최종 실패하면, 앞서 DB에서 차감했던 `rpm_used` 및 `rpd_used` 카운트를 **즉시 +1 복원(Rollback)**합니다. 이 보상 트랜잭션이 누락되면 실 사용량과 DB 카운트 간의 싱크가 깨져 정상적인 키가 배제되는 부작용이 생깁니다.

## 3. 사용자 경험(UX) 세분화 & Observability(단일 진실 공급원)

아키텍처 개선은 백엔드 엔진에만 국한되지 않고, 사용자 경험과 모니터링 환경 개선으로 이어졌습니다.

### ① 원인별 세분화된 에러 핸들링
모든 쿼터 소진 시 무의미한 "알 수 없는 에러" 대신, 차단 원인에 따른 정밀한 커스텀 에러를 전향적으로 도입했습니다.

* **RPM 초과:** *"현재 요청이 많아 잠시 지연되고 있습니다. 1분 후 다시 시도해 주세요."* (429 Retry-After 제공)
* **TPM (Token) 초과:** *"처리할 이미지/텍스트 용량이 큽니다. 분량 단위를 줄여주세요."*
* **RPD 초과:** *"오늘의 무료 제공량이 소진되었습니다."*

### ② Single Source of Truth (SSOT) 기반 모니터링
기존에는 어드민 모니터링, 번역 관리, OCR 비교 분석 등 **각기 다른 화면이 각자의 API를 호출해 동일한 쿼터 데이터를 다르게 보여주는 파편화 현상**이 있었습니다.

 이를 **단일 쿼터 조회 서비스 API 엔드포인트**로 통합(SSOT)하고, 클라이언트는 해당 표준 데이터 세트를 받아 각 뷰에 맞게 필터링 노출하도록 변경했습니다.

* 모든 어드민 UI에서 **RPM / RPD 실시간 사용률(%)** 동시 시각화
* 쿼터 사용량이 **80% 초과 시 시각적 경고(Visual Warning)** 노출
* 보안을 위해 실제 API Key 시크릿 값은 완전히 감추고 `키 A`, `키 B` 형태의 **격리된 라벨(Alias)**만 노출

## 4. 엔지니어링 교훈 (Takeaways)

1. **외부 API 파이프라인에는 반드시 "원자적 차감"과 "보상 트랜잭션"이 필요하다:**
   외부 서비스 쿼터를 앱 내부 DB에 캐싱/추적할 때, Race Condition 방지를 위한 DB Row Lock과 API 실패 시 DB 카운터를 돌려놓는 보상 트랜잭션(Rollback)은 대규모 동시성 환경의 필수 조건입니다.
2. **Trade-off에 기반한 적정 기술 선택:**
   모든 곳에 Redis Sliding Window와 같은 복잡한 시스템이 필요한 것은 아닙니다. 서비스 초기 프레임워크와 DB가 제공하는 ACID 트랜잭션/비관적 락 및 Fixed Window 카운팅만으로도 동시성 이슈를 극적으로 해결할 수 있었습니다.
3. **제한된 리소스에서의 UX 디자인:**
   무료/저비용 API 쿼터 한계는 엔지니어링만으로 무제한으로 늘릴 수 없습니다. 한계를 인정하고 시스템 소진 시 사용자에게 명확하고 친절한 액션 가이드를 제공하는 것이 제품의 전체 완결성을 높여줍니다.
