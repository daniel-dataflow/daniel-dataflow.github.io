안녕하세요, **PickSafe** 백엔드 팀입니다. 

서비스를 초기 구축하고 회원가입 기능을 구현할 때, 가장 먼저 마주하는 작지만 까다로운 문제 중 하나는 **'인증 메일 발송'**입니다. 초기 MVP 단계에서는 비용을 아끼고 빠르게 기능을 구현하기 위해 흔히 개인용 SMTP 서버(예: Gmail SMTP)를 연동하곤 합니다. 

하지만 PickSafe는 초기 설계 단계부터 프로덕션 수준의 안정성과 확장성을 고려하고자 하였고, 결과적으로 **Resend API**를 도입하기로 결정했습니다. 이번 포스팅에서는 기존의 Gmail SMTP 방식 대신 왜 Resend API를 선택했는지, 그리고 개발자 경험(DX)을 해치지 않기 위해 어떤 아키텍처적 고민을 했는지 공유해 드립니다.

---

### 1. 문제 정의 (Problem)

초기 회원가입 기능에서 인증 메일 발송 시스템을 구축할 때 우리가 직면한 요구사항과 한계는 다음과 같았습니다.

* **발신자 신뢰도 문제**: 일반 Gmail SMTP를 사용할 경우 발신 주소가 `xxx@gmail.com` 형태로 고정됩니다. 이는 사용자 입장에서 스팸 메일로 오인하기 쉽고, 브랜드 신뢰도를 크게 떨어뜨립니다.
* **보안 리스크**: Gmail SMTP 연동을 위해 개인 구글 계정의 '앱 비밀번호'를 서버 환경 변수에 주입해야 합니다. 이는 계정 탈취나 권한 남용 측면에서 보안 감사 시 취약점으로 지적될 수 있는 요소입니다.
* **낮은 전달력**: 트랜잭션 메일에 최적화되지 않은 일반 SMTP는 메일 서버(SPF, DKIM 등) 설정 미비로 인해 주요 메일함이 아닌 스팸함으로 빠지는 경우가 빈번합니다.

---

### 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 크게 두 가지 대안을 비교했습니다.

#### 대안 A: 자체 SMTP 서버 구축 또는 상용 이메일 솔루션 (AWS SES 등)
* **장점**: 대규모 트래픽 처리 가능, 강력한 커스텀 기능.
* **단점**: 초기 설정(도메인 인증, DNS 레코드 설정 등)에 소요되는 러닝 커브가 높고, MVP 단계에서는 과도한 오버엔지니어링(Over-engineering)이 될 수 있음.

#### 대안 B: 개발자 친화적인 트랜잭션 메일 API (Resend)
* **장점**: 
  * 개발자 경험(DX)이 매우 뛰어남 (RESTful API 및 SDK 제공).
  * 도메인 인증을 통해 `noreply@yourdomain.com`과 같은 전문적인 발신 주소 사용 가능.
  * MVP 운영에 충분한 무료 티어(Free Tier) 제공.
  * 전용 API Key 방식으로 언제든지 권한을 회수하거나 재발급할 수 있어 보안 관리가 용이.
* **단점**: 무료 티어 제한량을 초과할 경우 비용 발생 (단, 초기 MVP 단계에서는 충분함).

**결정:** 우리는 빠른 개발 속도를 유지하면서도 프로덕션 급의 신뢰성을 확보할 수 있는 **대안 B(Resend API)**를 최종 채택했습니다.

---

### 3. 최종 해결 및 아키텍처 설계

Resend API를 도입하면서, 실제 운영 환경과 로컬 개발 환경에서 모두 유연하게 동작할 수 있도록 몇 가지 설계 원칙을 적용했습니다.

1. **설정값의 외부 주소화 (Environment Configuration)**
   * 하드코딩을 방지하고 환경 변수를 통해 API 키(`RESEND_API_KEY`)와 발신자 주소(`EMAIL_FROM_ADDRESS`)를 분리했습니다.
   * 이를 통해 추후 도메인 변경 시 코드 수정 없이 환경 변수 변경만으로 대응할 수 있습니다.

2. **개발 편의성을 위한 디버깅 폴백 모드 (Fallback Mode)**
   * 외부 API를 사용하는 서비스 개발 시, 네트워크 환경이 불안정하거나 API 키가 없는 로컬 환경에서 회원가입 플로우 테스트가 막히는 불편함이 있습니다.
   * 이를 해결하기 위해 **API 키가 설정되지 않은 경우**, 메일을 실제로 발송하는 대신 **메일 내용을 터미널 콘솔 로그에 출력하고 인증을 곧바로 성공시키는 폴백 로직**을 구현했습니다. 

```python
# 예시 개념 코드 (FastAPI 기반 백엔드 환경)
if not settings.RESEND_API_KEY:
    logger.warning("Resend API Key가 설정되지 않았습니다. 디버깅 모드로 동작합니다.")
    print(f"[DEBUG] 메일 내용: {email_body}")
    return True # 개발 편의를 위한 폴백
else:
    # Resend API를 통한 실제 메일 발송 로직
    pass
```

### 4. 맺음말 및 Takeaway

이번 Resend API 도입을 통해 다음과 같은 엔지니어링 교훈을 얻었습니다.

* **초기 단계라도 사용자 경험(UX)과 보안은 타협하지 말 것**: 사소한 발신자 주소(`@gmail.com` vs `@domain.com`) 하나가 서비스의 첫인상을 결정합니다. API 기반 서비스를 활용하면 적은 공수(Low Effort)로 높은 프로덕션 퀄리티(High Quality)를 낼 수 있습니다.
* **개발자 경험(DX)을 고려한 예외 처리**: 외부 서드파티 의존성을 추가할 때는 항상 네트워크 단절이나 로컬 환경을 고려한 '폴백(Fallback) 메커니즘'을 함께 설계해야 개발 생산성이 떨어지지 않습니다.

PickSafe는 앞으로도 빠르고 안전한 아키텍처를 바탕으로 완성도 높은 서비스를 만들어 나가겠습니다. 감사합니다.
