안녕하세요. PickSafe 백엔드 엔지니어입니다.

서비스를 처음 구축하고 사용자 회원가입 기능을 구현할 때, 가장 먼저 마주하는 인프라 고민 중 하나는 바로 **"인증 메일을 어떻게 안정적으로 발송할 것인가?"**입니다. 

초기 개발 단계에서는 가장 익숙한 Gmail SMTP를 연동해 빠르게 프로토타입을 완성하고 싶어지죠. 하지만 우리 팀은 MVP(Minimum Viable Product) 단계임에도 불구하고 **Gmail SMTP 대신 서드파티 트랜잭션 메일 API인 'Resend API'를 전격 채택**했습니다. 

이번 글에서는 우리가 왜 이러한 결정을 내렸는지, 그리고 개발 편의성과 보안을 동시에 챙기기 위해 어떤 아키텍처적 고민(Trade-off)을 거쳤는지 공유해 드립니다.

---

## 1. Problem: Gmail SMTP의 치명적인 한계들

초기 기능 정의 단계에서 Gmail SMTP를 검토했으나, 다음과 같은 명확한 기술적 한계에 부딪혔습니다.

* **발신자 신뢰도(Spam Filtering) 문제:** 일반 Gmail 계정(`xxx@gmail.com`)을 통해 메일을 발송할 경우, 스팸 필터에 걸려 사용자함에 도달하지 못할 확률이 매우 높습니다. 프로덕션 서비스로서 `noreply@picksafe.com`과 같은 전문적인 브랜딩 발신 주소가 필수적이었습니다.
* **보안 및 인증 정보 노출 리스크:** SMTP를 사용하려면 개인 구글 계정의 '앱 비밀번호'를 서버 환경 변수에 하드코딩해야 합니다. 이는 계정 탈취나 키 유출 시 전체 인프라 보안에 구멍이 뚫릴 수 있는 위험한 구조입니다.
* **운영 가시성 부족:** SMTP는 메일이 실제로 성공적으로 전달되었는지, 스팸으로 처리되었는지에 대한 상세한 트래픽 로그나 웹훅(Webhook) 기반의 모니터링을 구축하기 까다롭습니다.

---

## 2. Trade-off & Decision: 왜 Resend API인가?

우리는 이러한 문제를 해결하기 위해 트랜잭션 메일에 특화된 **Resend API**를 도입하기로 결정했습니다. 대안 비교를 통해 도출한 핵심 도입 이유는 다음과 같습니다.

### ① 격리된 API Key 기반의 보안
개인 계정 정보를 공유할 필요 없이, 서비스 전용 `RESEND_API_KEY`를 발급받아 사용합니다. 키가 노출되더라도 해당 API 키만 즉시 폐기(Revoke) 및 재발급하면 되므로 blast radius(영향 범위)를 최소화할 수 있습니다.

### ② 유연한 도메인 전환 설계 (Configuration Isolation)
당장 커스텀 도메인 DNS 설정이 완료되지 않았더라도 서비스 개발을 멈출 수는 없습니다. 이에 우리는 도메인 종속성을 제거하기 위해 환경 변수(`EMAIL_FROM_ADDRESS`)로 발신자를 분리했습니다. 
* 초기 테스트 단계: `onboarding@resend.dev` 기본 도메인 활용
* 프로덕션 단계: DNS 인증 완료 후 `noreply@picksafe.com`으로 환경 변수만 변경하여 즉시 전환 가능

### ③ 비용 효율성과 무료 티어(Free Tier)
MVP 초기 단계의 트래픽을 충분히 소화할 수 있는 관대한 무료 티어를 제공하며, SMTP 대비 압도적인 인박스(Inbox) 도달율을 보여줍니다.

## 3. Engineering Consideration: 로컬 개발 환경과 디버깅 폴백 모드

외부 API를 의존성으로 가지게 되면, 로컬 개발 환경(오프라인 상태이거나 API 키가 없는 팀원)에서 회원가입 테스트를 할 때 문제가 발생할 수 있습니다. 

이를 해결하기 위해 애플리케이션 레벨에서 **디버깅 폴백 모드(Debugging Fallback Mode)**를 구현했습니다.

```python
# 의도된 예시 로직 (개념 코드)
if not settings.RESEND_API_KEY:
    logger.warning("RESEND_API_KEY가 설정되지 않았습니다. 메일 발송을 콘솔로 대체합니다.")
    print(f"[DEBUG] 인증 링크: {verification_link}")
    return # 메일 발송 성공으로 처리
```

* **API 키가 있는 경우:** 정상적으로 Resend API를 호출하여 원격 메일 발송
* **API 키가 없는 경우:** 터미널 콘솔 로그에 인증 링크를 출력하고 메일 전송을 우회(Fallback)

이 작은 예외 처리를 통해, 팀원들은 복잡한 서드파티 설정 없이도 로컬에서 원활하게 회원가입 및 인증 플로우를 테스트할 수 있는 개발자 경험(DX)을 확보했습니다.

## 4. Takeaway: 무엇을 배웠는가?

1. **MVP라도 보안과 브랜딩은 타협하지 마라:** 초기 구축 비용이 조금 들더라도, 처음부터 올바른 도메인 기반 메일링 서비스를 붙이는 것이 장기적으로 기술 부채를 줄이는 길입니다.
2. **외부 서비스 의존성에 대비한 Fallback 설계:** 서드파티 API(메일, 결제 등)를 도입할 때는 항상 네트워크 장애나 로컬 개발 환경을 고려한 폴백(Fallback) 전략을 코드로 녹여내야 합니다.

PickSafe 팀은 앞으로도 작은 기능 하나를 만들더라도 확장성과 보안, 그리고 개발자 경험을 모두 고려하는 견고한 아키텍처를 만들어 나가겠습니다. 읽어주셔서 감사합니다.
