서비스를 개발하며 마주하는 수많은 기술적 의사결정 중, '인증 메일 발송'과 같이 사소해 보이는 기능도 서비스의 신뢰도와 보안에 큰 영향을 미칩니다. 이번 포스팅에서는 초기 MVP 단계에서 범용적인 Gmail SMTP 대신 **Resend API**를 도입하게 된 기술적 배경과, 개발 생산성을 놓치지 않기 위해 적용한 폴백(Fallback) 아키텍처에 대해유의미한 인사이트를 공유하고자 합니다.

## 1. Problem: MVP 초기, 인증 메일 발송의 딜레마

회원가입 기능 구현 시 사용자 본인 인증을 위한 메일 발송은 필수적입니다. 초기 개발 단계에서는 가장 접근하기 쉬운 **Gmail SMTP**를 연동하여 테스트를 진행했습니다. 

하지만 곧 다음과 같은 명확한 한계(Problem)에 부딪혔습니다.

1. **스팸 폴더 직행 및 낮은 브랜드 신뢰도**: 
   개인 Gmail 계정이나 범용 SMTP 서버를 통해 메일을 발송할 경우, 수신자의 메일함에서 스팸으로 오인될 확률이 매우 높았습니다. 특히 서비스 도메인과 일치하지 않는 발신자 주소(`@gmail.com`)는 사용자에게 서비스의 신뢰도를 떨어뜨리는 주요 원인이었습니다.
2. **보안 및 자격 증명(Credential) 관리 리스크**:
   Gmail SMTP를 연동하려면 개발자 개인의 구글 계정 정보나 '앱 비밀번호'를 서버 환경 변수에 주입해야 합니다. 이는 퇴사나 권한 이전 시 보안 사고로 이어질 위험이 컸으며, 세밀한 권한 제어와 API Key 단위의 생명주기 관리(발급/폐기)가 불가능했습니다.

---

## 2. Trade-off & Architecture: 왜 Resend API인가?

기존 SMTP 방식의 리스크를 해결하기 위해 트랜잭션 메일(Transactional Email) 전용aaS(Software as a Service) 도입을 검토했고, 최종적으로 **Resend API**를 채택했습니다. 

우리가 고려한 대안들과 트레이드오프(Trade-off)는 다음과 같습니다.

### 대안 비교
* **기존 Gmail SMTP**: 
  * *장점*: 추가 비용 없음, 설정이 간단함.
  * *단점*: 스팸 처리율 높음, 개인 계정 정보 노출 리스크, 발신자 주소 커스텀의 한계.
* **AWS SES (Simple Email Service)**: 
  * *장점*: 엔터프라이즈 급 안정성, 극도로 저렴한 비용.
  * *단점*: 초기 샌드박스 해제 프로세스의 번거로움, MVP 단계에 비해 러닝 커 curva와 설정 오버헤드가 큼.
* **Resend API (선택)**: 
  * *장점*: 뛰어난 개발자 경험(DX), RESTful API 기반의 깔끔한 통합, 무료 티어 제공, 도메인 인증(SPF/DKIM) 연동 용이.
  * *단점*: 무료 티어 소진 시 비용 발생 (단, MVP 단계에서는 충분함).

### 핵심 도입 이유
1. **도메인 신뢰도 확보**: 추후 서비스 도메인을 연동하여 전문적인 발신자 주소(`noreply@picksafe.com`)를 사용할 수 있으며, 현재는 기본 테스트 도메인(`onboarding@resend.dev`)으로 빠르게 시작한 뒤 환경 변수(`EMAIL_FROM_ADDRESS`) 수정만으로 전환할 수 있도록 유연하게 설계했습니다.
2. **보안 분리**: 개인 계정이 아닌 전용 API Key(`RESEND_API_KEY`)를 통해 인증을 처리하므로, 키가 노출되더라도 언제든지 대시보드에서 즉시 폐기 및 재발급이 가능합니다.

## 3. Implementation & Dev Experience: 디버깅 폴백(Fallback) 모드

외부 API를 도입할 때 항상 고려해야 하는 점은 **"네트워크가 차단된 로컬 환경이나 CI/CD 파이프라인에서 테스트할 때 메일 서비스 장애가 전체 시스템에 영향을 주면 안 된다"**는 점입니다.

이를 해결하기 위해 애플리케이션 레벨에서 **디버깅 폴백 모드**를 구현했습니다.

* 서버 기동 시 `RESEND_API_KEY` 환경 변수의 존재 여부를 체크합니다.
* 만약 키가 설정되어 있지 않다면(예: 로컬 개발 환경), 외부 API를 호출하는 대신 **메일 내용을 터미널 콘솔 로그에 출력**하고, 인증 프로세스는 곧바로 성공(Success) 처리하도록 설계했습니다.

이를 통해 개발자는 외부 서비스 가입이나 API Key 발급 없이도 로컬에서 회원가입 및 인증 플로우를 끊김 없이 테스트할 수 있는 높은 생산성을 확보했습니다.

## 4. Takeaway: 시니어 에디터의 요약

이번 Resend API 도입을 통해 다음과 같은 엔지니어링 교훈을 얻었습니다.

* **초기 단계일수록 전문화된 SaaS를 활용하라**: 인프라 구축에 쏟는 리소스를 아끼고, 개발자 경험(DX)이 뛰어난 도구를 선택하는 것이 MVP의 출시 속도를 높이는 핵심입니다.
* **보안은 아키텍처 단계부터 분리해야 한다**: 개인 인증 정보를 애플리케이션 설정에 포함시키는 안티 패턴을 제거하고, 언제든 격리 및 교체 가능한 API Key 체계를 구축해야 합니다.
* **로컬 개발 환경을 위한 폴백(Fallback)은 필수다**: 외부 의존성(Third-party API)이 생기더라도 로컬 개발과 테스트가 오프라인 또는 최소한의 설정으로 가능하도록 방어 코드를 작성하는 것이 장기적인 안정성을 담보합니다.

PickSafe는 앞으로도 작지만 단단한 아키텍처 의사결정을 통해 안정적인 서비스를 만들어 나가겠습니다.
