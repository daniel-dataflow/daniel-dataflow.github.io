제품 초기 단계에서 회원가입 및 본인 인증을 위한 **트랜잭션 이메일(Transactional Email)** 발송 시스템은 서비스의 '첫인상'을 결정짓는 핵심 요소입니다. 이메일이 스팸함으로 들어가거나 발송이 지연되면, 유저는 서비스에 진입하기도 전에 이탈하게 됩니다.

PickSafe 팀은 초기 프로토타이핑 단계에서 구현이 쉬운 **Gmail SMTP**를 사용했으나, 서비스 정식 론칭 및 확장성을 고려하여 **Resend API** 기반의 이메일 인프라로 전환하는 아키텍처 결정을 내렸습니다. 

이번 포스팅에서는 왜 기존 방식을 이탈해야 했는지, 어떤 기술적 Trade-off를 고려했는지, 그리고 이를 통해 **시스템 신뢰성과 개발자 경험(DX)**을 어떻게 극대화했는지 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

초기 프로토타입 개발 시에는 가성비와 속도를 위해 개인 혹은 팀의 Gmail SMTP를 연동하여 인증 메일을 발송했습니다. 그러나 프로덕션 환경을 준비하면서 다음과 같은 크리티컬한 문제점들이 도출되었습니다.

1. **낮은 전달률과 스팸 분류 (Deliverability Issue)**
   * `xxx@gmail.com`과 같은 일반 수신용 주소로 대량의 인증 메일을 발송할 경우, 주요 메일 서비스(Gmail, Outlook 등)의 스팸 필터링 알고리즘에 걸려 스팸함으로 직행하는 문제가 발생했습니다.
2. **보안 및 계정 관리 리스크**
   * Gmail SMTP 연동을 위해서는 구글 계정의 '앱 비밀번호(App Password)'를 발급받아야 합니다. 이는 개인 계정에 종속적이며, 권한 분리가 불가능하여 API 키 단위의 섬세한 접근 제어(Least Privilege)나 빠른 보안 회전(Key Rotation)이 불가능했습니다.
3. **환경 격리의 어려움**
   * 개발(Dev), 테스트(Staging), 운영(Production) 환경에 따라 도메인과 발신자 주소를 유연하게 분리하기 어려웠습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off Analysis)

인프라 전환을 위해 대표적인 3가지 대안을 비교 검토했습니다.

| 항목 | Gmail SMTP | AWS SES | Resend API (선택) |
| :--- | :--- | :--- | :--- |
| **발신자 신뢰도** | 낮음 (스팸율 높음) | 높음 (DKIM/SPF 설정 시) | 높음 (도메인 검증 제공) |
| **보안/권한 관리** | 개인 계정 종속 (위험) | IAM 정책 기반 (우수) | 전용 API Key 단위 관리 (우수) |
| **개발자 경험 (DX)** | 단순함 | 샌드박스 해제 등 초기 설정 복잡 | 모던 API, 직관적 대시보드 |
| **비용 구조** | 무료 (제한적) | 매우 저렴 (초대량에 유리) | MVP 적합 무료 티어 제공 |

### 왜 Resend API인가?

* **AWS SES vs Resend**: AWS SES는 단가가 매우 저렴하지만, MVP 단계에서 샌드박스 해제 요청, DKIM/SPF 레코드 설정, 복잡한 SDK 적용 등의 초기 오버헤드가 컸습니다. 반면 **Resend**는 최신 트랜잭션 메일 API 서비스로서 높은 전달률을 보장하며, 뛰어난 Developer Experience(DX)와 대시보드 모니터링을 제공합니다.
* **무료 티어 활용**: 초기 MVP 서비스 운영량을 충분히 커버하는 무료 티어를 제공하므로, 초기 비용을 0원 가깝게 유지하면서도 전문적인 메일 인프라를 구축할 수 있었습니다.

---

## 3. 기술적 해결 및 구현 (Engineering Solutions)

우리는 단순히 API를 교체하는 것에 그치지 않고, 시스템의 **유연성**과 **개발 생산성**을 모두 챙길 수 있는 구조를 설계했습니다.

### (1) 환경 변수 기반의 도메인 유연화 (Decoupled Configuration)

운영 환경에서는 자사 커스텀 도메인(`noreply@picksafe.com`)을 사용해야 하지만, 초기 도메인 셋업 전이나 개발 환경에서는 테스트 도메인이 필요합니다.
이를 위해 애플리케이션 코드를 수정하지 않고 환경 변수 변경만으로 발신 도메인을 스위칭할 수 있도록 캡슐화했습니다.

* **초기/개발 단계**: Resend 기본 제공 테스트 도메인(`onboarding@resend.dev`) 활용
* **운영 단계**: 커스텀 도메인(`noreply@picksafe.com`)으로 `.env` 설정만 변경하여 즉시 적용

### (2) 개발 생산성을 위한 디버깅 폴백 모드 (Debug Fallback Mode)

로컬 개발 환경이나 CI/CD 파이프라인에서 매번 실제 이메일 API를 호출하는 것은 API 쿼터 소비, 네트워크 지연, 테스트 환경 복잡도 증가라는 문제를 야기합니다.

이를 해결하기 위해 **디버깅 폴백(Fallback) 메커니즘**을 구현했습니다.

```
[인증 메일 발송 요청]
       │
       ▼
 [RESEND_API_KEY 존재 여부 확인]
       ├── (YES) ──> Resend API 호출 (실제 메일 발송)
       └── (NO)  ──> [폴백 모드] 콘솔 로그 출력 + 인증 절차 자동 성공 처리
```

이 구조를 통해 새롭게 합류한 개발자는 로컬 환경에 별도의 외부 API 키를 설정하지 않고도 회원가입/인증 로직을 즉시 테스트하고 개발할 수 있게 되었습니다.

---

## 4. 엔지니어링 교훈 (Takeaways)

1. **기술 선택의 기준은 '현재 단계의 생산성'과 '미래의 확장성' 사이의 균형이다.**
   AWS SES가 장기적인 단가는 가장 저렴하지만, MVP 단계에서는 개발 속도와 높은 전달률을 빠르게 확보할 수 있는 Resend가 최적의 선택(Trade-off)이었습니다.
2. **개발자 경험(DX)은 시스템 아키텍처의 일부다.**
   API 키가 없는 로컬 환경을 고려하여 구축한 '디버깅 폴백 모드'는 개발팀의 병목을 줄이고 온보딩 속도를 크게 향상시켰습니다.
3. **외부 제3자 서비스(Third-party) 의존성은 환경 변수로 추상화해야 한다.**
   발신 주소와 API Key를 비즈니스 로직과 철저히 분리했기 때문에, 추후 다른 메일 파이프라인으로 전환하더라도 핵심 코드 변경 없이 설정 변경만으로 대응이 가능한 구조를 완성했습니다.

---

PickSafe 팀은 무조건적인 최신 기술 도입이 아닌, **서비스의 신뢰성, 보안, 그리고 생산성을 골고루 높일 수 있는 실용적인 엔지니어링**을 지향합니다.
