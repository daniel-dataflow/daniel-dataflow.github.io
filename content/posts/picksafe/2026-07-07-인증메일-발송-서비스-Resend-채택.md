초기 단계의 스타트업이나 신규 프로젝트(MVP)를 빌드할 때, 가장 먼저 마주하는 관문 중 하나는 **'사용자 인증(Authentication)'**입니다. 그리고 이 인증 과정에서 이메일 인증 링크나 인증 코드를 발송하는 것은 필수적인 흐름입니다.

저희 PickSafe 팀 역시 초기 가입 프로세스를 구축하며 빠르게 이메일 발송 기능을 구현해야 했습니다. 이 과정에서 겪은 기술적 페인 포인트와, 이를 해결하기 위해 기존 Gmail SMTP에서 **Resend API**로 전환하며 얻은 아키텍처적 이점, 그리고 개발자 경험(DX)을 극대화한 설계 방식을 공유합니다.

---

## 1. 문제 정의: "빠른 구현" 뒤에 숨은 부채들

초기 개발 단계에서는 가장 익숙하고 비용이 들지 않는 **Gmail SMTP**를 연동하여 인증 메일을 발송했습니다. 구현은 간단했지만, 실제 운영 관점으로 전환하려는 순간 다음과 같은 치명적인 한계점들이 드러났습니다.

### ① 발신자 주소의 신뢰도 저하 (스팸 분류 리스크)
Gmail SMTP를 사용하면 발신자 주소가 `xxx@gmail.com`으로 고정됩니다. 서비스의 공식 메일이 아닌 개인 메일 주소 혹은 임시 구글 계정으로 발송되는 인증 메일은 포털 사이트(Naver, Daum 등)나 기업 메일 시스템에서 **스팸 메일로 분류될 확률이 매우 높습니다.** 가입 단계에서 인증 메일이 스팸함으로 간다면, 이는 곧바로 유저 이탈(Churn)로 이어집니다.

### ② 보안 및 계정 관리의 위험성
Gmail SMTP 연동을 위해서는 구글 계정의 '앱 비밀번호(App Password)'를 생성하여 환경 변수로 관리해야 합니다. 이는 개인 혹은 공용 구글 계정의 권한 일부를 시스템에 직접 노출하는 형태입니다. API 키처럼 **세분화된 권한 제어(Fine-grained access control)가 불가능**하며, 유출 시 대응 및 주기적인 키 로테이션(Rotation)이 매우 까다롭습니다.

### ③ 유연하지 못한 인프라 확장성
추후 서비스 공식 도메인(`@picksafe.com`)을 확보했을 때, SMTP 설정 자체를 다시 뜯어고쳐야 하는 구조적 결합도가 존재했습니다. 코드의 변경 없이 환경 변수만으로 발송 도메인을 유연하게 스위칭할 수 있는 구조가 필요했습니다.

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 저희는 세 가지 선택지를 두고 Trade-off를 분석했습니다.

| 비교 요인 | 대안 1: 기존 Gmail SMTP 유지 | 대안 2: AWS SES (Simple Email Service) | 대안 3: Resend API (최종 채택) |
| :--- | :--- | :--- | :--- |
| **도메인 커스텀** | 불가능 (`@gmail.com` 고정) | 가능 (DKIM, SPF 설정 필요) | **가능 (간편한 DNS 연동)** |
| **보안성** | 낮음 (App Password 노출) | 높음 (IAM 및 전용 자격 증명) | **높음 (전용 API Key 발급/폐기)** |
| **초기 설정 공수**| 매우 낮음 | 높음 (Sandbox 해제 요청 필요) | **낮음 (모던한 UI, 즉시 연동)** |
| **비용 (MVP 규모)**| 무료 (일일 제한 존재) | 매우 저렴 (무료 티어 존재하나 까다로움) | **무료 (월 3,000건 무료 제공)** |
| **개발자 경험 (DX)**| 보통 | 낮음 (콘솔 UI가 복잡함) | **최상 (개발자 친화적 SDK 및 모니터링)** |

### 왜 Resend API인가?
**AWS SES**는 훌륭한 솔루션이지만, 초기 샌드박스(Sandbox) 해제 요청 절차가 까다롭고 설정 과정이 다소 무겁습니다. 반면, **Resend**는 모던한 개발자 경험(DX)을 제공하며, 이메일 스팸 처리율이 매우 낮고, 무엇보다 **초기 MVP 운영 규모를 충분히 감당할 수 있는 합리적인 무료 티어(하루 100건, 월 3,000건)**를 제공했습니다. 

이에 저희는 생산성과 보안, 그리고 비용 효율성을 모두 챙길 수 있는 **Resend API**를 채택하기로 결정했습니다.

## 3. 최종 아키텍처 및 구현 디테일

저희는 이번 전환을 단순히 '라이브러리 교체'에 그치지 않고, **환경 격리**와 **개발자 편의성**을 극대화하는 방향으로 설계했습니다.

### ① 환경 변수를 통한 도메인 및 API 키 격리
운영 환경과 개발 환경의 유연한 대처를 위해 아래와 같이 설정을 분리했습니다.

```bash
# .env 예시
RESEND_API_KEY=re_123456789... # 발급받은 API Key
EMAIL_FROM_ADDRESS=noreply@picksafe.com # 향후 커스텀 도메인 적용 시
```
우선은 Resend에서 제공하는 기본 테스트 도메인(`onboarding@resend.dev`)으로 빠른 기능을 검증하되, 추후 정식 도메인 연결 시 **코드 수정 없이 환경 변수 변경만으로 배포**할 수 있는 확장성을 확보했습니다.

### ② 개발 생산성을 극대화하는 '디버깅 폴백(Fallback) 모드'
매번 로컬에서 테스트 가입을 진행할 때마다 실제 메일이 발송되는 것은 API 쿼터(Quota) 낭비일 뿐만 아니라 테스트 속도를 저하시킵니다. 

이를 해결하기 위해, 로컬 환경에서 `RESEND_API_KEY`가 설정되어 있지 않은 경우, **메일 발송 흐름을 차단하지 않고 터미널 콘솔 로그에 인증 링크를 출력한 뒤 즉시 인증 성공으로 우회하는 폴백 모드**를 구현했습니다.

```python
# pseudo-code: 메일 발송 서비스 레이어
class EmailService:
    def __init__(self, api_key: str, from_address: str):
        self.api_key = api_key
        self.from_address = from_address

    async def send_verification_email(self, to_email: str, token: str):
        if not self.api_key:
            # [Fallback Mode] 로컬/스테이징 개발 편의성을 위한 처리
            logger.warning(f"⚠️ [MOCK EMAIL] To: {to_email} | Token: {token}")
            logger.warning("API Key가 없어 콘솔 로그로 대체하며, 가입 프로세스는 정상 진행됩니다.")
            return True
        
        # 실제 Resend API 호출 로직
        return await self._call_resend_api(to_email, token)
```
이 구조 덕분에 신규 입사한 팀원이나 외부 협업 개발자가 복잡한 메일 설정 없이도 로컬 환경을 3초 만에 셋업하고 인증 로직을 테스트할 수 있게 되었습니다.

## 4. Engineering Takeaway (배운 점)

이번 인증 메일 발송 서비스 고도화 작업을 통해 얻은 핵심 교훈은 다음과 같습니다.

1. **비즈니스 단계에 맞는 기술 선택 (Lean Startup)**
   처음부터 무겁고 복잡한 인프라(AWS SES 등)를 구축하기보다, 관리 공수가 제로에 가까우면서도 보안 요구사항을 충족하는 SaaS(Resend)를 활용하여 **Time-to-Market을 극대화**했습니다.
2. **보안의 기본은 자격 증명 분리**
   개인용/시스템용 계정 정보가 서비스 코드 및 환경 변수에 침투하는 것을 원천 차단했습니다. API 기반의 관리를 통해 필요시 즉각 키를 무효화할 수 있는 안전한 구조를 만들었습니다.
3. **디버깅 폴백 패턴의 가치**
   외부 API 의존성이 높은 기능일수록 개발 환경에서의 폴백 처리가 중요합니다. 이를 통해 API 호출 비용을 절감하고, 네트워크 장애 상황에서도 로컬 개발 환경이 중단 없이(Seamless) 유지되는 쾌적한 DX를 구축할 수 있었습니다.
