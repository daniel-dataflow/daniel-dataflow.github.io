서비스 극초기(MVP) 단계에서는 빠르게 기능을 구현하는 것이 최우선 과제입니다. PickSafe 역시 초기 회원가입 시 사용자 인증을 위한 이메일 발송 기능에 가장 구현하기 쉬운 **Gmail SMTP** 방식을 사용해 왔습니다. 

하지만 서비스를 정식 라이브하는 시점이 다가옴에 따라, 초기 구현 방식이 가진 **보안성 문제**, **메일 도달률(Deliverability) 문제**, 그리고 **개발자 경험(DX) 저하**가 명확한 기술 부채로 다가왔습니다.

본 아티클에서는 이러한 기술적 문제를 해결하기 위해 이메일 발송 인프라를 **Resend API** 기반으로 전환한 의사결정 과정과, 그 과정에서 적용한 아키텍처 및 백엔드 엔지니어링 패턴을 소개합니다.

---

## 1. 문제 정의: 기존 Gmail SMTP의 한계

초기 MVP 개발 시 사용한 Gmail SMTP 기반 메일 발송은 빠르게 프로토타입을 만드는 데는 유용했지만, 아래 3가지 치명적인 문제를 안고 있었습니다.

### 1) 발신자 신뢰도 낮음 (스팸함 직행 이슈)
`xxx@gmail.com` 형태로 발송되는 인증 메일은 주요 메일 서비스(Gmail, Outlook, Naver 등)의 스팸 필터링 알고리즘에 걸릴 확률이 높습니다. 트랜잭션 메일(인증, 비밀번호 재설정 등)의 도달 실패는 즉각적인 **유저 이탈**로 이어집니다.

### 2) 개인 계정 보안 리스크
Gmail SMTP 연동을 위해서는 Google 계정의 '앱 비밀번호(App Password)'를 사용해야 합니다. 이는 팀 내부에서 개인 계정 의존성을 만들고, 키 유출 시 계정 전체 권한이 위험해지는 보안적 취약점을 내포합니다.

### 3) 샌드박스 및 운영 확장성의 부재
개발 환경과 운영 환경의 분리가 명확하지 않고, 발송 성공/실패율이나 바운스(Bounce) 데이터를 추적할 수 있는 대시보드가 없어 문제 발생 시 원인 파악이 어려웠습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이메일 인프라 전환을 위해 대표적인 3가지 옵션을 비교 검토했습니다.

| 항목 | Option A: Gmail SMTP (기존) | Option B: AWS SES | Option C: Resend API (최종 선택) |
| :--- | :--- | :--- | :--- |
| **도달률 & 도메인 인증** | 낮음 (`@gmail.com` 사용) | 높음 (DKIM/SPF 설정 필요) | 높음 (쉽고 빠른 DKIM/SPF 설정) |
| **보안 관리** | 개인 앱 비밀번호 (위험) | IAM 정책 기반 관리 | 전용 API Key (세분화 및 즉시 폐기 가능) |
| **초기 도입 비용/시간**| 매우 낮음 | 보통 (Sandbox 해제 신청 절차 필요) | 매우 낮음 (몇 분 내 연동 가능) |
| **개발자 경험 (DX)** | 낮음 (로그 추적 불가) | 보통 (CloudWatch 연동 필요) | 매우 우수 (직관적인 Dashboard 제공) |
| **비용 효율성** | 무료 (일일 제한) | 매우 저렴 (종량제) | 스타트업에 최적화된 Free Tier 제공 |

### 왜 Resend API인가?
* **AWS SES**는 장기적인 비용 효율성과 확장성 면에서 뛰어납니다. 그러나 MVP 단계에서는 SES Sandbox 해제 절차, IAM 설정, 서드파티 모니터링 구축 등 **초기 공수(Overhead)**가 컸습니다.
* **Resend API**는 트랜잭션 메일에 특화되어 있어 개발자 친화적인 SDK를 제공하며, modern API-first 접근 방식을 취하고 있습니다. 도메인 연동(`noreply@picksafe.com`)이 매우 직관적이고 무료 티어 제공량이 초기 유저 유입을 감당하기에 충분했기에, **개발 속도와 운용 안정성 간의 최적의 균형점**이라 판단했습니다.

## 3. 해결 및 엔지니어링 설계

전환 과정에서는 단순 라이브러리 교체를 넘어, **환경 분리**와 **개발 편의성**을 고려한 아키텍처 개선을 진행했습니다.

```
                  ┌────────────────────────┐
                  │   Authentication API   │
                  └───────────┬────────────┘
                              │
               Is API Key set in Environment?
                              │
             ┌────────────────┴────────────────┐
          [ YES ]                           [ NO ]
             │                                 │
  ┌──────────▼──────────┐           ┌──────────▼──────────┐
  │  Resend External    │           │ Console Fallback    │
  │  Mail Service API   │           │ Debugging Mode      │
  └─────────────────────┘           └─────────────────────┘
 (Send Actual Verification Email)     (Log token to terminal &
                                       Auto-bypass Auth for Dev)
```

### 1) 설정 분리 (Decoupled Configuration)
발신 도메인이 확정되기 전 단계(`onboarding@resend.dev`)와 커스텀 도메인 확정 후(`noreply@picksafe.com`) 단계 간의 전환이 소스코드 수정 없이 이루어지도록 환경 변수를 완전 분리했습니다.

```bash
# .env (보안을 위해 깃허브 추적 제외)
RESEND_API_KEY=re_xxxxxxxxxxxxxx
EMAIL_FROM_ADDRESS=noreply@picksafe.com
```

### 2) 개발 생산성을 위한 '디버깅 폴백(Fallback) 패턴' 도입
로컬 개발 환경이나 CI/CD 테스트 환경마다 외부 API 키를 설정하는 것은 비효율적이며, 테스트 중 무분별한 API 호출로 쿼터가 소진될 수 있습니다. 

이를 해결하기 위해 **API 키 미설정 시 터미널 콘솔 로그에만 인증 정보를 출력하고 성공으로 처리하는 폴백 모드**를 구현했습니다.

* **로컬/테스트 환경:** API Key 없이도 콘솔 로그로 메일 인증 흐름을 완벽히 테스트 가능 (API 쿼터 절약 & 독립적인 테스트 환경)
* **운영 환경:** `RESEND_API_KEY` 발급/등록을 통해 실제 이메일 발송 실행

## 4. Takeaway: 무엇을 배웠는가?

1. **서비스 신뢰도는 작은 디테일(발신 주소)에서 시작한다.**
   기술적으로 메일이 발송되는 것보다 중요한 것은 **'사용자 수신함에 안전하게 도착하는가'**입니다. 제대로 된 도메인 서명(SPF/DKIM)과 트랜잭션 전용 인프라 구축이 유저 전환율에 직접적인 영향을 준다는 것을 체감했습니다.

2. **보안과 관리의 용이성은 반비례하지 않는다.**
   개인 계정 기반의 App 비밀번호 공유를 폐기하고, 언제든 권한을 철회/재발급할 수 있는 전용 API Key 체계로 전환함으로써 사내 보안 기준을 상향시켰습니다.

3. **최고의 개발자 경험(DX)은 촘촘한 폴백 설계에서 나온다.**
   외부 서비스에 의존하는 기능을 개발할 때, 외부 망 연결 없이도 로컬 환경에서 개발을 진행할 수 있도록 설계(Console Fallback)함으로써 팀 전체의 개발 연속성과 테스트 효율성을 대폭 개선했습니다.

---

PickSafe 팀은 서비스의 성장 단계에 맞춰 아키텍처를 유연하게 진화시키고 있습니다. 작은 인프라 전환 하나에도 **보안, 확장성, 개발 생산성**을 함께 고민하며 단단한 엔지니어링 기반을 만들어가고 있습니다.
