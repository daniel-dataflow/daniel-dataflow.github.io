초기 서비스(MVP)를 개발할 때 많은 엔지니어들이 "가장 빠르고 익숙한 방법"을 선택하곤 합니다. 회원가입 단계에서 필수적인 **이메일 인증 기능**을 구현할 때도 마찬가지입니다. 흔히 구현이 간단하고 익숙한 'Gmail SMTP'를 첫 번째 후보로 떠올립니다.

하지만 서비스의 첫인상을 결정하는 회원가입 흐름에서, 사소해 보이는 이메일 발송 인프라 선택은 **보안 사고, 메일 수신 실패(스팸 분류), 그리고 로컬 개발 생산성 저하**라는 거대한 스노우볼이 되어 돌아올 수 있습니다.

PickSafe 팀이 회원가입 인증 메일 발송 서비스를 구축하며 마주한 고민과, 기존 SMTP 방식을 버리고 **Resend API**를 채택하며 설계한 **디버깅 폴백(Fallback) 아키텍처**를 공유합니다.

---

## 1. 문제 정의: Gmail SMTP의 명확한 한계

초기 프로토타입 단계에서는 Gmail SMTP 설정이 가장 직관적인 해결책처럼 보였습니다. 하지만 운영 단계와 협업 환경을 고려했을 때 다음과 같은 치명적인 한계가 존재했습니다.

### ① 신뢰성 및 스팸 필터링 문제
Gmail SMTP를 통해 개인 계정(`xxx@gmail.com`)으로 인증 메일을 대량 발송하면 수신 측 메일 서버(Gmail, Naver 등)에서 스팸으로 분류할 확률이 매우 높습니다. 서비스의 첫 단추인 이메일 인증이 스팸함으로 가버린다면, 사용자 이탈률은 극대화됩니다. 비즈니스 신뢰도를 위해 `noreply@picksafe.com`과 같은 **도메인 기반의 전문 발신 주소**가 필수적이었습니다.

### ② 보안 및 계정 관리의 취약성
Gmail SMTP를 연동하려면 구글 계정의 '앱 비밀번호'를 발급받아 시스템 환경 변수에 등록해야 합니다. 이는 개인 혹은 공용 구글 계정의 권한 일부를 시스템에 직접 노출하는 리스크를 안고 있으며, 키 유출 시 권한 회수나 재발급 관리가 매우 까다롭습니다.

### ③ 유연하지 못한 인프라 전환
추후 전용 도메인을 확보하거나 대규모 발송 인프라(SES 등)로 마이그레이션해야 할 때, SMTP 기반 코드는 유연하게 대처하기 어렵습니다.

## 2. 기술적 고민과 대안 비교: SMTP vs SaaS API (Resend)

우리는 이 문제를 해결하기 위해 기존 SMTP 방식과 최신 개발자 친화적 이메일 서비스인 **Resend API**를 비교 분석했습니다.

| 비교 항목 | 기존 Gmail SMTP | Resend API (채택) |
| :--- | :--- | :--- |
| **인증 방식** | 구글 앱 비밀번호 (계정 종속적) | 전용 API Key (손쉬운 재발급/폐기) |
| **도메인 연동** | 불가능 (`@gmail.com` 고정) | 가능 (`@picksafe.com` 등 맞춤 도메인) |
| **스팸 처리율** | 높음 (공용 IP 평판의 한계) | 낮음 (트랜잭션 메일 전문 인프라 사용) |
| **비용 (MVP)** | 무료 | 무료 티어 제공 (초기 운영량 충분히 감당 가능) |
| **확장성** | 코드 수정 필요 | 환경 변수 설정값 분리로 손쉬운 도메인 전환 |

### 왜 Resend였는가?
Resend는 최신 개발 트렌드에 맞춘 DX(Developer Experience)를 제공합니다. 무엇보다 **SPF, DKIM, DMARC 등 복잡한 도메인 보안 설정**을 직관적으로 지원하여 스팸 분류율을 획기적으로 낮춰줍니다. 또한 API Key 기반으로 동작하기 때문에 권한 분리가 명확하여 사내 보안 규정을 준수하기에 최적의 선택이었습니다.

## 3. 엔지니어링 디테일: "개발 생산성을 해치지 않는 보안 설계"

보안을 위해 외부 API 서비스를 도입할 때 흔히 발생하는 부작용이 있습니다. 바로 **"로컬에서 개발하거나 CI/CD 테스트를 돌릴 때마다 외부 API를 호출해야 하는가?"**에 대한 문제입니다.

모든 개발자에게 운영 환경의 API Key를 공유하는 것은 보안상 불가하며, 그렇다고 테스트용 Key를 일일이 발급하는 것은 번거로운 일입니다. 이를 해결하기 위해 PickSafe 팀은 **'디버깅 폴백 모드(Debugging Fallback Mode)'**를 아키텍처에 녹여냈습니다.

### 디버깅 폴백(Fallback) 아키텍처
환경 변수에 `RESEND_API_KEY`가 존재하지 않는 개발/테스트 환경에서는, 실제 외부 API를 호출하는 대신 **터미널 콘솔 로그에 인증 메일 내용을 출력하고 즉시 인증 성공 처리를 수행**하도록 설계했습니다.

```python
# [보안 필터링 및 추상화된 예시 코드]

import logging

logger = logging.getLogger(__name__)

class EmailVerificationService:
    def __init__(self):
        self.api_key = os.getenv("RESEND_API_KEY")
        self.from_address = os.getenv("EMAIL_FROM_ADDRESS", "onboarding@resend.dev")

    async def send_verification_email(self, to_address: str, token: str) -> bool:
        # API Key가 없는 경우: 디버깅 폴백 모드 작동
        if not self.api_key:
            logger.warning("⚠️ RESEND_API_KEY가 감지되지 않았습니다. [디버깅 폴백 모드]를 활성화합니다.")
            logger.info(f"[LOCAL DEVONLY] To: {to_address} | Subject: 회원가입 인증 이메일")
            logger.info(f"[LOCAL DEVONLY] Verification Token: {token}")

            return True

        # API Key가 존재하는 경우: 실제 Resend API 호출
        return await self._execute_resend_api(to_address, token)

    async def _execute_resend_api(self, to_address: str, token: str) -> bool:
```

### 이 설계가 주는 유익함 (DX & Security)
1. **완벽한 환경 분리**: 개발자는 별도의 API Key 설정 없이 소스 코드를 클론 받아 바로 로컬 서버를 구동하고 회원가입 흐름을 테스트할 수 있습니다.
2. **비용 절감**: 불필요한 로컬 테스트/CI 테스트 과정에서 발생하는 외부 API 호출을 차단하여 무료 티어 쿼터를 온전히 운영 환경에만 집중할 수 있습니다.
3. **유연한 도메인 전환**: 초기에는 Resend가 제공하는 기본 테스트 도메인(`onboarding@resend.dev`)을 사용하다가, 도메인이 확정되면 `.env` 파일의 `EMAIL_FROM_ADDRESS` 수정만으로 실서비스 배포가 가능합니다.

## 4. 마치며: 기술 의사결정의 교훈 (Takeaways)

이번 작업을 통해 PickSafe 팀이 얻은 핵심 교훈은 다음과 같습니다.

* **"동작하는 기능"을 넘어 "지속 가능한 인프라"를 고민할 것**: 단순히 메일이 발송되는 것에 만족했다면 Gmail SMTP로 빠르게 끝냈겠지만, 스팸 처리율과 보안을 고려한 사전 투자가 추후 발생할 유저 컴플레인과 마이그레이션 비용을 크게 줄여주었습니다.
* **보안과 개발자 경험(DX)은 상충하는 것이 아니다**: 로컬 폴백 모드 설계를 통해, 외부 서비스 도입으로 발생할 수 있는 개발 프로세스의 병목을 우아하게 해결했습니다.

앞으로도 PickSafe는 견고한 보안 정책을 유지하면서도, 개발 생산성을 훼손하지 않는 똑똑한 아키텍처를 지향해 나갈 것입니다.
