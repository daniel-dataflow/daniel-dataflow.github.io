비즈니스가 빠르게 성장하다 보면, 초기 속도전을 위해 선택했던 단순한 구조가 시간이 지남에 따라 **기술 부채(Technical Debt)**로 돌아오곤 합니다. 특히 외부 기관 API 수집 파이프라인과 어드민 대시보드처럼 기능 확장이 빈번한 영역은 레이어 간 파일명 파편화, 문서 정합성 결여, 템플릿 비대화 현상이 발생하기 쉽습니다.

이번 포스팅에서는 PickSafe 팀이 마주한 **파편화된 코드베이스와 모놀리식 대시보드 템플릿의 구조적 문제**를 정리하고, **"단 한 번의 다운타임이나 기동 에러 없이" 단계적으로 리팩토링을 완수한 시스템 개선 사례**를 공유합니다.

---

## 1. 문제 정의: 엔트로피의 증가와 히스토리성 사이드 이펙트

프로젝트의 스케일이 커지며 아래 세 가지 핵심 문제가 수면 위로 올라왔습니다.

### ① 레이어 간 도메인 맥락 파편화 (Domain Context Loss)
식약처(KFDA) 데이터 수집 및 보강을 담당하는 파이프라인 모듈들이 계층(Model, Router, Service 등)마다 서로 다른 네이밍 규칙을 사용하고 있었습니다.
* Router: `seeding.py`
* Service: `seed_kfda_ingredients.py`, `kfda_service.py`
* Model: `staging.py`

동일한 도메인 맥락을 공유함에도 파일명만으로는 관계를 파악하기 어려웠고, 이는 신규 엔지니어 온보딩 시 높은 인지 부하(Cognitive Load)를 발생시켰습니다.

### ② 'God Template'과 파일 손상 리스크
어드민 영역의 `dashboard.html`은 인프라/로그 모니터링, 고객 문의, 데이터 보강, analytics 등 6개 이상의 서로 다른 관리 도메인을 단일 템플릿 안에서 JavaScript 탭 전환(SPA 형태) 방식으로 처리하고 있었습니다.
* **SSR + 최소 JS 원칙 위배:** 단일 화면에 과도한 인라인 JS 스크립트가 집중됨.
* **안정성 부재:** 잦은 병합 충돌과 대규모 변경으로 인해 과거 **해당 템플릿 파일이 손상(Corruption)되는 이력이 두 차례나 발생**.

### ③ 문서와 코드 간의 갭 (Documentation Drift)
기능 명세서(`docs/features/`) 내의 "관련 파일 경로" 섹션이 실제 코드 위치와 일치하지 않는 현상이 누적되었습니다. 잘못된 문서는 버그 수정 시 오탐을 유발하고 개발 속도를 저하시키는 원인이 됩니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이러한 문제를 해결하기 위해 팀 내에서 두 가지 접근 방식을 비교했습니다.

| 비교 항목 | 대안 A: 빅뱅(Big-Bang) 리팩토링 | 대안 B: 점진적(Incremental) 안전 리팩토링 (선택) |
| :--- | :--- | :--- |
| **작업 방식** | 모든 라우팅/템플릿/파일명 한 번에 일괄 수정 | 검증(Phase 0) -> 파일 단위 리네이밍 -> 템플릿 분리 순으로 진행 |
| **리스크** | Import 참조 누락으로 인한 서버 기동 불가, 사이드이펙트 추적 불가능 | 각 단계별 동작 확인으로 기동 불가/화면 깨짐 리스크 차단 |
| **소요 시간** | 단기 집중 작업 필요 | 리소스를 분산하여 안전하게 수행 |
| **복구 가능성** | 실패 시 커밋 전체 롤백 필요 | 문제가 발생한 단일 커밋 단위만 롤백 가능 |

PickSafe 팀은 과거 대시보드 손상 이력을 교훈 삼아 **대안 B(점진적 리팩토링)**를 채택했습니다. 리스크가 낮은 작업부터 높은 작업으로 단계를 구성하고, 각 단계 직후 자동화 검증을 통과해야만 다음 단계로 넘어가는 원칙을 세웠습니다.

## 3. 실행 전략 및 문제 해결 과정

### Step 1. 리스크 제로: 문서 정합성 감사 (Documentation Sync)
가장 먼저 코드 동작에 영향을 주지 않는 문서군 감사(Audit)를 수행했습니다. `docs/features/` 내의 전체 명세서를 전수 조사하여 어긋난 번호 체계와 실제 코드 경로를 100% 동기화했습니다. 시스템의 '지도'를 먼저 올바르게 다듬는 작업이었습니다.

### Step 2. 임포트 그래프 분석을 통한 도메인 접두사 통일 (`kfda_`)
식약처 도메인 관련 파일명을 통일하기 전, 단순 `Rename` 작업이 발생시킬 참조 파손을 방지하기 위해 0단계(Phase 0) 조사를 수행했습니다.

```bash
# 참조 관계 전수 조사를 위한 정적 분석 예시
grep -rn "import.*seed_kfda\|import.*kfda_service\|from.*staging" ./app
```

1. **규칙 정립:** 레이어와 무관하게 동일 도메인은 `kfda_` 접두사를 사용 (`models/kfda_staging.py`, `routers/kfda_seeding.py` 등).
2. **단원 단위(Atomic) 실행:** 파일 1개 리네이밍 ➔ Python AST/Import 검증 (`py_compile`) ➔ 서버 기동 테스트 ➔ 다음 파일 진행.
3. **독립 스케줄러 분리:** 전용 배치 작업 여부를 확인하여 도메인 접두사를 한정적으로 부여.

### Step 3. 'God Template' 해체 및 SSR 기반 모듈화
단일 대시보드(`dashboard.html`)를 **독립 라우트 + 독립 템플릿** 구조로 분리했습니다.

```
[기존 monolithic 구조]
/admin/dashboard (단일 URL)
 └── dashboard.html (인라인 JS 기반 탭 전환, 2000+ Lines)

[개선된 레이어드 SSR 구조]
/admin/base_admin.html (공통 Layout, Sidebar, Header)
 ├── /admin/analytics    --> admin/analytics.html + static/js/admin/analytics.js
 ├── /admin/inquiries    --> admin/inquiries.html + static/js/admin/inquiries.js
 ├── /admin/products     --> admin/products.html  + static/js/admin/products.js
 └── /admin/infrastructure--> admin/infra.html     + static/js/admin/infra.js
```

1. **Jinja2 Template Inheritance 도입:** 공통 사이드바와 헤더를 `base_admin.html`로 분리하고, 각 관리 화면은 이를 `{% extends %}` 하도록 재설계하여 코드 중복을 제거했습니다.
2. **독립 라우팅 맵핑:** 각 화면에 고유 URL을 부여하여 RESTful한 SSR 구조를 완성했습니다.
3. **점진적 섹션 분리:** 탭 섹션 하나를 분리할 때마다 기동 테스트와 기능 동작 확인을 수행하여 과거와 같은 통합 손상 사고를 원천 차단했습니다.

## 4. 엔지니어링 교훈 및 결실 (Takeaways)

이번 리팩토링 작업을 통해 다음과 같은 기술적/조직적 성과를 거두었습니다.

### 1. **Zero Downtime / Zero Boot Failure 리팩토링 실현**
"한 번에 여러 파일을 수정하지 않는다"는 원칙과 단계별 기동 검증 프로세스를 도입함으로써, 대규모 네이밍 변경 및 라우팅 분리 작업 과정에서 **단 한 번의 서버 기동 에러나 런타임 버그 없이 성공적으로 전환**을 완료했습니다.

### 2. **유지보수성 및 인지 부하 대폭 개선**
* **코드 가독성 증가:** `kfda_` 접두사 통일로 도메인 경계가 명확해졌습니다.
* **대시보드 신뢰성 확보:** 2,000라인에 달하던 인라인 스크립트 비대화 파일이 도메인별 200~300라인 규모의 모듈화된 HTML/JS 파일로 분리되어 내구성이 크게 향상되었습니다.

### 3. **프로세스로 기술 부채 관리하기**
가장 뛰어난 개발 정책은 개발자의 개인 역량에 의존하는 것이 아니라, **안전 장치가 마련된 프로세스(Phase 0 확인 ➔ 실행 ➔ 기동 검증 ➔ 수용 기준 대조)**에 의존하는 것임을 다시금 확인했습니다.
