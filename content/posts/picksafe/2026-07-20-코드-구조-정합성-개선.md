## 1. 들어가며: 빠르게 성장한 서비스가 마주한 기술 부채

초기 스타트업과 신규 프로젝트 환경에서는 '빠른 기능 구현'이 최우선 목표가 되기 쉽습니다. 하지만 비즈니스가 확장되고 도메인 로직이 복잡해질수록, 초기에 감수했던 트레이드오프는 점차 시스템의 안정성을 위협하는 기술 부채로 돌아옵니다.

최근 우리 팀은 외부 공공 데이터 파이프라인 확장 및 백오피스 관리 기능 고도화 과정에서 다음과 같은 구조적 문제들을 마주했습니다.

1. **도메인 네이밍 불일치로 인한 인지 부하**: 동일한 데이터 파이프라인을 다루는 파일들이 계층(Router, Service, Model)마다 서로 다른 네이밍 규칙을 사용하여 추적성이 저하됨.
2. **단일 템플릿 파일의 비대화(Big-Ball-of-Mud)**: 백오피스 대시보드가 단일 파일 내 인라인 자바스크립트 기반의 탭 전환(Single Page Tab View)으로 구현되어 코드 충돌 및 파일 손상 위험이 지속적으로 발생함.
3. **문서와 코드베이스의 싱크 불일치**: 잦은 리팩토링 과정에서 프로젝트 아키텍처 문서가 실제 코드 구조를 온전히 반영하지 못함.

안정적인 서비스 운영과 팀의 개발 생산성을 회복하기 위해 진행한 **구조 정합성 개선(Architecture Consistency Refactoring)** 과정을 공유합니다.

## 2. 문제 정의와 기술적 고민

### 문제 A. 계층 간 네이밍 불일치와 사이드 이펙트 리스크
데이터 수집 및 정제 파이프라인이 성장하면서, 특정 도메인(공공 데이터 연동)을 처리하는 파일들이 `staging.py`, `seeding.py`, `seed_service.py`, `scheduler.py` 등 레이어별로 제각각 명명되어 있었습니다. 
- **문제점**: 파일명만으로는 해당 컴포넌트가 어떤 도메인에 종속되는지 파악하기 어려웠고, 의존성 그래프가 불투명해졌습니다.
- **고민**: 파이썬 환경에서는 모듈명을 변경할 때 순환 참조나 누락된 임포트로 인해 런타임 에러(ImportError/ModuleNotFoundError)가 발생하기 쉽습니다.

### 문제 B. 대시보드 템플릿의 거대화와 결합도 문제
관리자 대시보드(`dashboard.html`)는 모니터링, 고객 응대, 데이터 파이프라인 제어, 통계 분석 등 서로 다른 비즈니스 콘텍스트를 하나의 파일 안에서 수많은 인라인 스크립트와 탭 UI로 처리하고 있었습니다.
- **문제점**: 한 화면의 UI/스크립트를 수정하다가 다른 기능의 스크립트 스코프를 오염시키거나 마크업이 깨지는 문제가 반복되었습니다.
- **고민**: 
  - **대안 1**: 완전한 클라이언트 사이드 렌더링(React/Vue SPA)으로 백오피스 전면 재구축
  - **대안 2**: 서버 사이드 렌더링(SSR) 템플릿 엔진 구조를 유지하되, 고유 라우트 기반의 독립 모듈형 템플릿으로 분리

## 3. 엔지니어링 의사결정 및 대안 비교 (Trade-off)

### 3.1. SPA 전면 도입 vs 모듈형 SSR 구조 유지
백오피스를 SPA 프레임워크로 전면 재작성하는 방식은 높은 사용자 인터랙션을 제공할 수 있지만, 현재 단계에서는 다음과 같은 단점이 있었습니다.
- 별도의 프론트엔드 빌드 파이프라인 구축 및 API 인증/인가 체계 재설계에 따른 높은 리소스 소모
- "서버 사이드 렌더링 + 최소한의 Vanilla JS"라는 팀의 경량화 아키텍처 원칙과의 괴리

**결정**: 템플릿 상속(`Base Template`) 패턴을 활용하여 **독립 엔드포인트-독립 템플릿 구조**의 SSR 아키텍처로 점진적 분리하기로 결정했습니다.

```
[AS-IS]
/admin/dashboard (Single URL) 
  └─ dashboard.html (All Tabs + Inline JS in One Massive File)

[TO-BE]
/admin/base.html (공통 레이아웃 / 네비게이션)
  ├── /admin/analytics    --> analytics.html + analytics.js
  ├── /admin/inquiries    --> inquiries.html + inquiries.js
  ├── /admin/pipeline     --> pipeline.html + pipeline.js
  └── /admin/monitoring   --> monitoring.html + monitoring.js
```

### 3.2. 점진적 마이그레이션 전략 (Safe Refactoring Strategy)
안전한 배포를 위해 **"위험도 기반 3단계 실행 전략"**을 수립했습니다.

1. **1단계 (Low Risk - 문서 동기화)**: 코드 수정 전, 실제 아키텍처와 문서 간의 불일치를 전수 조사하여 도메인 맵을 재정의.
2. **2단계 (Medium Risk - 도메인 네이밍 통일)**: 도메인 접두사(Prefix) 규칙을 정의하고, 한 번에 하나씩 모듈을 리네이밍하며 임포트 그래프 및 컴파일 무결성을 검증.
3. **3단계 (High Risk - 화면 및 스크립트 분리)**: 단일 대시보드에서 각 기능 섹션을 하나씩 독립 라우트와 독립 템플릿/JS 파일로 순차 추출.

## 4. 최종 구현 및 해결 과정

### 1) 도메인 중심의 일관된 네이밍 컨벤션 확립
외부 데이터 수집·정제 도메인에 명확한 도메인 식별자(`kfda_*`)를 부여하여 계층 전반의 응집도를 높였습니다.

- `models/staging.py` ➔ `models/kfda_staging.py`
- `routers/seeding.py` ➔ `routers/kfda_pipeline.py`
- `services/seed_kfda_ingredients.py` ➔ `services/kfda_seed_service.py`

*검증 자동화*: 리네이밍 작업 시 `py_compile` 및 정적 AST 분석 도구를 활용하여, 변경 즉시 의존성 그래프가 깨지지 않는지 점검하는 단계를 파이프라인에 추가했습니다.

### 2) 템플릿 상속 및 라우트별 관심사 분리(SoC)
공통 네비게이션과 권한 검증 레이아웃은 `base_admin.html`로 추상화하고, 개별 도메인 뷰는 고유 URL을 부여받아 독립적으로 렌더링되도록 리팩토링했습니다.

```html
<!-- templates/admin/base_admin.html (공통 뼈대) -->
<!DOCTYPE html>
<html>
<head>
    <title>{% block title %}Admin Portal{% endblock %}</title>
    <link rel="stylesheet" href="/static/css/admin.css">
</head>
<body>
    <nav class="admin-sidebar">
        <!-- 공통 네비게이션: 한 곳에서 중앙 관리 -->
        {% include "admin/components/nav.html" %}
    </nav>
    <main class="admin-content">
        {% block content %}{% endblock %}
    </main>
    {% block scripts %}{% endblock %}
</body>
</html>
```

```html
<!-- templates/admin/analytics.html (독립된 모듈 템플릿) -->
{% extends "admin/base_admin.html" %}

{% block title %}Analytics - Admin{% endblock %}

{% block content %}
<section class="analytics-container">
    <h2>방문자 및 트래픽 분석</h2>
    <div id="metric-chart"></div>
</section>
{% endblock %}

{% block scripts %}
<script src="/static/js/admin/analytics.js" defer></script>
{% endblock %}
```

각 화면의 비즈니스 로직에 종속된 스크립트는 인라인 형태에서 독립된 외부 정적 파일(`analytics.js`, `pipeline.js`)로 격리하여, 전역 스코프 충돌 문제를 원천 차단했습니다.

## 5. 성과 및 엔지니어링 교훈 (Takeaways)

### 💡 얻은 성과
1. **코드 유지보수성 및 추적성 향상**: 도메인 네이밍 통일로 신규 온보딩 개발자의 도메인 컴포넌트 탐색 시간이 대폭 단축되었습니다.
2. **배포 안정성 확보**: 대형 템플릿 파일 내 충돌이 사라졌으며, 특정 어드민 기능의 장애가 다른 관리 기능으로 전파되지 않는 격리 구조를 완성했습니다.
3. **UI 수정 비용 절감**: 공통 베이스 템플릿 도입으로 네비게이션 및 디자인 시스템 수정 시 단 한 곳의 템플릿만 수정하도록 개선되었습니다.

### 🧠 핵심 교훈
- **"한 번에 크게 바꾸지 않는다"**: 레거시 코드를 개선할 때 가장 경계해야 할 것은 '빅뱅식 리팩토링'입니다. 아무리 단순해 보이는 리네이밍과 템플릿 분리라도 **[단일 모듈 분리 → 단위 검증 → 점진적 배포]**의 사이클을 준수할 때 프로덕션 무중단과 코드 품질을 동시에 확보할 수 있습니다.
- **문서화는 아키텍처의 일부다**: 코드가 변경될 때 문서의 정합성을 함께 감사(Audit)하는 프로세스가 갖춰지지 않으면, 문서는 가장 빠르게 부패하는 레거시가 됩니다.

우리는 앞으로도 서비스의 성장에 발맞추어 무분별한 복잡성을 경계하고, 단단한 엔지니어링 표준을 세워나갈 것입니다.
