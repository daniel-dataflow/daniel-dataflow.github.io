안녕하세요, **PickSafe** 백엔드 팀입니다. 

PickSafe는 사용자가 업로드한 성분 라벨을 **Gemini Vision AI**로 분석하여 안전 정보를 제공하는 서비스를 운영하고 있습니다. 서비스가 고도화됨에 따라 자연스럽게 마주하게 된 가장 큰 고민 중 하나는 **"어떻게 AI API 비용 폭탄과 악의적인 DoS 공격으로부터 서버와 자원을 보호할 것인가?"**였습니다.

이번 글에서는 무분별한 요청으로부터 백엔드를 보호하기 위해 FastAPI 환경에서 구현한 **슬라이딩 윈도우 Rate Limiter**, **엄격한 파일 무결성 검증**, 그리고 **엔터프라이즈급 보안 헤더**를 아우르는 **2-Track 방어 아키텍처** 설계 과정을 공유합니다.

---

## 1. 배경 및 문제 정의 (Context & Problem Statement)

AI 기반 서비스를 운영할 때 아키텍트가 가장 경계해야 할 시나리오는 크게 세 가지입니다.

1. **AI API 비용 폭탄 및 리소스 고갈 (Cost Bombing / DoS)**
   - 악의적인 봇이 `/scan/upload` 같은 핵심 엔드포인트로 초당 수십 장의 고화질 이미지를 연속 전송한다면, Gemini API 쿼터가 순식간에 소진되고 서버 메모리가 고갈되어 정작 일반 사용자가 서비스를 이용하지 못하는 상황이 발생합니다.
2. **인증 무차별 대입 공격 (Brute Force Attack)**
   - 로그인 및 소셜 인증 엔드포인트(`/auth/login` 등)를 타깃으로 한 크리덴셜 스터핑(Credential Stuffing) 공격은 계정 탈취 위험뿐만 아니라 백엔드에 불필요한 부하를 줍니다.
3. **악성 파일 업로드 및 대용량 페이로드 공격**
   - 확장자만 `.jpg`로 위장한 실행 파일(.php, .sh 등)을 업로드하거나, 수십 MB에서 수 GB에 달하는 거대 페이로드를 전송하여 서버 I/O를 마비시키려는 시도가 존재합니다.

우리는 이러한 위협들을 코드 레벨에서 즉각 차단하고, 추후 글로벌 인프라 확장 시에도 유연하게 대응할 수 있는 구조를 설계해야 했습니다.

## 2. 2-Track 방어 아키텍처 (2-Track Defense Architecture)

PickSafe는 인프라 변경 없이 즉시 적용 가능한 **코드 레벨의 내장 방어**와 추후 도메인 연동 시 적용할 **Cloudflare 글로벌 엣지 쉴드**를 결합한 **2-Track 전략**을 채택했습니다.

```mermaid
flowchart TD
    subgraph Track1_현재_내장_방어 [Track 1: 코드 레벨 내장 보안 (현재 100% 가동)]
        A1[클라이언트 요청] --> A2[보안 HTTP 응답 헤더 미들웨어]
        A2 --> A3[슬라이딩 윈도우 Rate Limiter 미들웨어]
        A3 -->|스캔 API: 1분 5회 / 1시간 30회 초과 시| A4[429 Too Many Requests 즉시 차단]
        A3 -->|정상 범위 요청| A5[이미지 매직바이트 & 25MB 용량 엄격 검증]
        A5 --> A6[비즈니스 로직 & Gemini OCR 안전 실행]
    end

    subgraph Track2_도메인_도입_시_확장 [Track 2: Cloudflare 글로벌 엣지 쉴드 (추후 확장)]
        B1[사용자/공격자] --> B2[Cloudflare 글로벌 엣지 프록시 쉴드]
        B2 -->|실제 서버 IP 완벽 은닉 & L3/L4 DDoS 1차 흡수| B3[Bot Fight Mode 악성 크롤러 차단]
        B3 --> B4[글로벌 CDN 정적 자산 캐싱]
        B4 --> A1
    end
```

## 3. 세부 기술 설계 및 구현 (Technical Specifications)

### 1) 고성능 슬라이딩 윈도우 Rate Limiter
고정 윈도우(Fixed Window) 방식은 윈도우 경계 시점에 트래픽이 몰리는 한계(Thundering Herd)가 있습니다. 이를 극복하기 위해 **인메모리 기반 슬라이딩 타임 윈도우(Sliding Window Log)** 알고리즘을 구현하여 타임스탬프 기반으로 정밀한 제어를 수행했습니다.

- **엔드포인트별 차등 제한 규칙**:
  - **스캔 API (`/scan/*`)**: AI API 비용 보호를 위해 동일 IP당 **1분 5회**, **1시간 30회**로 엄격히 제한.
  - **인증 API (`/auth/*`)**: 무차별 대입 방지를 위해 동일 IP당 **1분 10회** 제한.
  - **예외 처리 (Whitelist)**: 헬스체크(`/health`) 및 시스템 관리자 권한(`super_admin`)은 처리율 제한에서 제외.
- **응답 규격**: 
  - 제한 초과 시 표준 규격인 `HTTP 429 Too Many Requests`를 반환하고, `Retry-After` 헤더를 통해 클라이언트가 재시도할 수 있는 남은 시간을 안내합니다.

### 2) 이미지 파일 무결성 및 용량 검증 (Magic Bytes)
OCR 정확도를 위해 최신 스마트폰의 고화질 원본 사진(7MB~15MB)은 수용해야 하지만, 수십 MB 이상의 비정상적인 DoS 파일 폭탄은 사전에 차단해야 합니다.

- **용량 제한**: 최대 `25MB`(`25 * 1024 * 1024 bytes`) 초과 시 즉시 `413 Payload Too Large` 응답.
- **매직 바이트(Magic Bytes) 검증**: 
  - 단순히 파일 확장자(`string manipulation`)에 의존하면 확장자를 위조한 악성 스크립트를 막을 수 없습니다. 
  - 업로드된 파일 스트림의 **첫 바이트(File Header)**를 직접 읽어 실제 파일 형식을 검증합니다.
    - **JPEG**: `\xFF\xD8\xFF`
    - **PNG**: `\x89\x50\x4E\x47` (`\x89PNG`)
    - **WebP**: `RIFF....WEBP`
  - 위조된 파일은 진입 단계에서 `400 Bad Request`로 즉시 차단합니다.

### 3) 엔터프라이즈 보안 HTTP 응답 헤더 강제 주입
OWASP Top 10에서 지적하는 클라이언트 사이드 취약점(XSS, Clickjacking 등)을 방어하기 위해 모든 응답에 5대 표준 보안 헤더를 강제화했습니다.
- `X-Content-Type-Options: nosniff` (MIME 타입 스니핑 방지)
- `X-Frame-Options: SAMEORIGIN` (클릭재킹 방지)
- `X-XSS-Protection: 1; mode=block` (브라우저 XSS 필터 활성화)
- `Referrer-Policy: strict-origin-when-cross-origin` (민감 정보 유출 방지)
- `Permissions-Policy` (카메라/마이크 등 불필요한 하드웨어 권한 제어)

## 4. 검증 결과 및 Takeaways (Conclusion)

이번 보안 아키텍처 도입을 통해 다음과 같은 엔지니어링적 성과를 달성했습니다.

1. **AI API 비용 리스크 원천 차단**: 봇이나 비정상적인 사용자에 의한 대량 스캔 요청이 1분 5회 시점에서 차단되므로, 예기치 못한 API 쿼터 고갈 및 과금 폭탄 위험을 제거했습니다.
2. **백엔드 리소스 보호**: 거대 페이로드와 위조된 파일 포맷이 비즈니스 로직이나 OCR 엔진까지 도달하기 전 미들웨어 계층에서 필터링되어 서버 안정성이 크게 향상되었습니다.

### 💡 에디터의 챙겨보기 (Takeaways)
> 외부 서비스(Gemini, AWS 등)를 핵심 비즈니스 로직으로 활용하는 시스템일수록, 비즈니스 코드 작성만큼나 **'진입점(Edge/Middleware)에서의 방어선 구축'**이 서비스의 생존을 결정합니다. 아키텍처를 설계할 때 인프라(Cloudflare 등) 의존성과 애플리케이션 코드 레벨의 방어를 분리(2-Track)하여 구현한다면, 환경 변화에 유연하고 단단한 백엔드를 구축할 수 있습니다.
