안녕하세요, **PickSafe** 백엔드 엔지니어링 팀입니다. 

PickSafe는 AI 기반 성분 라벨 OCR 분석(Gemini Vision API)을 핵심 기능으로 제공하고 있습니다. 하지만 서비스가 성장함에 따라 **AI API 비용 폭탄, 리소스 고갈형 DoS 공격, 무차별 대입(Brute Force) 로그인 시도** 등 다양한 보안 위협에 노출되기 시작했습니다.

이번 포스팅에서는 인프라 레이어와 애플리케이션 레이어를 아우르는 **2-Track 방어 아키텍처**를 설계하고, FastAPI 환경에서 슬라이딩 윈도우 기반 Rate Limiter와 파일 무결성 검증 로직을 구현하며 마주한 기술적 고민과 해결 과정을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

OCR 및 AI 기능을 제공하는 서비스라면 누구나 공감할 만한 세 가지 핵심 리스크가 존재합니다.

1. **AI API 비용 폭탄 및 리소스 고갈 (Cost Bombing / DoS)**
   - 악의적인 봇이 `/scan/upload` 엔드포인트로 초당 수십 장의 고화질 이미지를 전송할 경우, Gemini API 쿼터가 순식간에 고갈되고 서버 메모리가 포화 상태에 빠집니다.
2. **인증 무차별 대입 공격 (Brute Force)**
   - 로그인(`/auth/login`, `/auth/google`) 엔드포인트 대상의 자동화된 크리덴셜 스터핑 공격으로 인한 서버 부하 및 계정 탈취 위험.
3. **악성 파일 및 대용량 페이로드 공격**
   - 확장자만 `.jpg`로 위장한 쉘 스크립트(.php, .sh 등) 업로드 및 수십 MB~GB 단위의 거대 파일 전송으로 인한 서버 I/O 점유.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

### 고민 1. Rate Limiting 알고리즘 선택
* **고정 윈도우 (Fixed Window)**: 구현이 단순하지만, 윈도우 경계 시점에 트래픽이 몰릴 경우(예: 분당 5회 제한인데 0분 59초에 5번, 1분 0초에 5번 요청) 허용량의 2배에 달하는 트래픽이 순간적으로 유입되는 허점이 존재합니다.
* **슬라이딩 타임 윈도우 (Sliding Window Log)**: 구현 복잡도가 약간 높지만, 시간 축을 연속적으로 계산하여 버스트 트래픽을 정밀하게 제어할 수 있습니다. 
* **결정**: AI API와 인증 부하를 확실하게 방어하기 위해 **인메모리 기반의 슬라이딩 윈도우 Rate Limiter**를 직접 구현하기로 결정했습니다.

### 고민 2. 파일 업로드 검증 방식
* 단순히 파일 확장자나 Content-Type 헤더만 신뢰할 경우, 위조된 악성 파일을 걸러낼 수 없습니다.
* **결정**: 최신 스마트폰의 고화질 원본 사진(7MB~15MB)을 온전히 수용하면서도 DoS를 막기 위해 **25MB 용량 상한선**을 두 고, 파일 헤더의 고유 바이트 패턴인 **매직 바이트(Magic Bytes)**를 직접 검증하는 이중 방어선을 구축했습니다.

## 3. 핵심 아키텍처 및 구현 (Architecture & Implementation)

### 2-Track 방어 아키텍처
현재 배포 환경의 즉각적인 코드 레벨 방어(Track 1)와 향후 글로벌 도메인 확장 시의 Cloudflare 엣지 쉴드(Track 2)를 결합한 구조를 설계했습니다.

```mermaid
flowchart TD
    subgraph Track1_현재_내장_방어 [Track 1: 코드 레벨 내장 보안 (현재 100% 가동)]
        A1[클라이언트 요청] --> A2[보안 HTTP 응답 헤더 미들웨어]
        A2 --> A3[슬라이딩 윈도우 Rate Limiter 미들웨어]
        A3 -->|스캔/인증 제한 초과 시| A4[429 Too Many Requests 즉시 차단]
        A3 -->|정상 범위 요청| A5[매직 바이트 및 25MB 용량 엄격 검증]
        A5 --> A6[비즈니스 로직 및 Gemini OCR 안전 실행]
    end

    subgraph Track2_도메인_도입_시_확장 [Track 2: Cloudflare 글로벌 엣지 쉴드 (추후 확장)]
        B1[사용자/공격자] --> B2[Cloudflare 글로벌 엣지 프록시]
        B2 -->|실제 서버 IP 은닉 & L3/L4 DDoS 흡수| B3[Bot Fight Mode]
        B3 --> A1
    end
```

### 주요 구현 포인트

1. **엔드포인트별 차등 Rate Limiting**
   - **스캔 API (`/scan/*`)**: 동일 IP 기준 **1분 5회, 1시간 30회** 제한.
   - **인증 API (`/auth/*`)**: 동일 IP 기준 **1분 10회** 제한.
   - 한계 초과 시 `HTTP 429 Too Many Requests`와 함께 `Retry-After` 헤더를 반환하여 클라이언트 친화적인 예외 처리를 구현했습니다.

2. **엄격한 매직 바이트(Magic Bytes) 검증**
   - 업로드된 파일의 첫 바이트를 파싱하여 유효한 이미지 포맷인지 확인합니다.
     - **JPEG**: `\xFF\xD8\xFF`
     - **PNG**: `\x89\x50\x4E\x47`
     - **WebP**: `RIFF....WEBP`
   - 허용되지 않은 포맷이나 위조된 파일은 즉시 `400 Bad Request`로 차단합니다.

3. **엔터프라이즈 보안 HTTP 헤더 강제 주입**
   - 모든 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Permissions-Policy` 등 5대 보안 헤더를 미들웨어로 주입하여 OWASP Top 10 클라이언트 취약점을 원천 방어합니다.

## 4. 맺음말 및 교훈 (Takeaways)

이번 보안 아키텍처 설계를 통해 얻은 가장 큰 교훈은 **"보안은 미루는 것이 아니라 비즈니스 로직과 함께 처음부터 설계해야 한다"**는 점입니다. 

특히 외부 유료 AI API를 연동하는 서비스 환경에서 Rate Limiting과 페이로드 검증은 선택이 아닌 필수 생존 조건입니다. 코드 레벨의 견고한 미들웨어 설계 덕분에 불필요한 인프라 비용 지출을 사전에 차단하고, 안정적인 서비스 운영 기반을 다질 수 있었습니다.

앞으로도 PickSafe는 견고한 엔지니어링을 바탕으로 안전하고 신뢰할 수 있는 서비스를 만들어 나가겠습니다. 감사합니다.
