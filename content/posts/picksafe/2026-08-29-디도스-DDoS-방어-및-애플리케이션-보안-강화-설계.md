안녕하세요, **PickSafe** 백엔드 엔지니어링 팀입니다. 

PickSafe는 AI(Gemini Vision AI)를 활용해 성분 라벨 OCR 분석을 제공하는 서비스입니다. AI 기반 서비스는 사용자에게 혁신적인 경험을 선사하지만, 반대로 **'비용 폭탄'과 '리소스 고갈 공격(DoS)'**이라는 치명적인 기술적 부채를 동시에 안고 있습니다.

만약 악의적인 봇이 대용량 이미지나 무작위 요청을 초당 수십 건씩 밀어 넣는다면 어떻게 될까요? 서버 메모리는 고갈되고, API 무료/유료 쿼터는 순식간에 소진되어 선량한 일반 사용자들까지 서비스를 이용하지 못하는 상황이 발생할 것입니다.

이번 글에서는 PickSafe가 이러한 문제를 해결하기 위해 설계하고 도입한 **2-Track 방어 아키텍처**와 **고성능 슬라이딩 윈도우 Rate Limiter**, 그리고 **엄격한 파일 무결성 검증 시스템**에 대한 기술적 의사결정(ADR) 과정을 공유합니다.

---

## 1. 마주한 문제 (Problem Statement)

서비스 오픈을 앞두고 검토한 주요 보안 위협은 크게 4가지였습니다.

1. **AI API Cost Bombing & DoS**: `/scan/upload` 엔드포인트로 대용량 이미지를 연속 전송해 Gemini API 쿼터를 고갈시키는 공격.
2. **Brute Force Attack**: 인증 엔드포인트(`/auth/login` 등)로 무작위 자격 증명을 시도하여 계정을 탈취하려는 시도.
3. **Malicious Payload Upload**: 실행 파일(`.php`, `.sh` 등)을 `.jpg` 등으로 확장자만 위장하여 업로드하거나 수십 MB의 거대 파일로 서버 I/O를 마비시키는 공격.
4. **Client-side Vulnerabilities**: 적절한 보안 HTTP 응답 헤더 누락으로 인한 XSS, Clickjacking, MIME Sniffing 등의 위협.

우리는 인프라 수준과 애플리케이션 수준에서 이를 동시에 방어할 수 있는 구조가 필요했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off & Architecture)

이를 해결하기 위해 **2-Track 방어 아키텍처**를 채택했습니다.

* **Track 1 (코드 레벨 내장 방어)**: 프레임워크(FastAPI) 미들웨어와 서비스 계층에서 직접 요청을 검증하고 차단 (현재 100% 가동)
* **Track 2 (글로벌 엣지 쉴드)**: 추후 자체 도메인 확장 시 Cloudflare를 연동하여 L3/L4 DDoS 및 봇 트래픽을 엣지에서 1차 차단

```mermaid
flowchart TD
    subgraph Track1_현재_내장_방어 [Track 1: 코드 레벨 내장 보안 (현재 100% 가동)]
        A1[클라이언트 요청] --> A2[보안 HTTP 응답 헤더 미들웨어]
        A2 --> A3[슬라이딩 윈도우 Rate Limiter]
        A3 -->|스캔 API: 1분 5회 초과 시| A4[429 Too Many Requests 즉시 차단]
        A3 -->|정상 범위 요청| A5[이미지 매직바이트 & 25MB 용량 검증]
        A5 --> A6[Gemini OCR 안전 실행]
    end
```

### 핵심 구현 포인트

#### ① 고성능 슬라이딩 윈도우 Rate Limiter (`app/services/rate_limiter.py`)
단순한 고정 윈도우(Fixed Window) 방식은 윈도우 경계 시점에 트래픽이 몰리는 단점이 있습니다. 이를 보완하기 위해 인메모리 기반의 **슬라이딩 타임 윈도우(Sliding Window Log)** 알고리즘을 구현했습니다.
* **스캔 API**: 동일 IP당 **1분 5회**, **1시간 30회** 제한 (AI 비용 보호)
* **인증 API**: 동일 IP당 **1분 10회** 제한 (무차별 대입 방어)
* **예외 처리**: 초과 시 `HTTP 429 Too Many Requests` 및 `Retry-After` 헤더 반환

#### ② 매직 바이트(Magic Bytes) 기반 파일 무결성 검증
확장자만 `.jpg`로 바꾼 악성 파일 업로드를 원천 차단하기 위해, 파일 스트림의 첫 바이트(Magic Bytes)를 직접 읽어 검증하도록 구현했습니다.
* JPEG (`\xFF\xD8\xFF`), PNG (`\x89PNG`), WebP (`RIFF...WEBP`) 시그니처가 아닐 경우 즉시 `400 Bad Request`로 차단합니다.
* 용량은 최신 스마트폰의 고화질 원본 사진(7~15MB)을 온전히 수용하면서도 DoS 폭탄을 막기 위해 **최대 25MB**로 엄격히 제한했습니다.

#### ③ 엔터프라이즈 보안 HTTP 헤더 강제 주입
모든 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection` 등의 5대 표준 보안 헤더를 미들웨어를 통해 강제 주입하여 OWASP Top 10 취약점을 방어합니다.

## 3. 무엇을 배웠는가? (Takeaway & Conclusion)

1. **방어선은 다중화할수록 안전하다**: 외부 CDN이나 WAF(Cloudflare)에만 의존하지 않고, 애플리케이션 코드 레벨(Track 1)에서 자체적인 Rate Limiting과 페이로드 검증 로직을 구축해 둔 덕분에 인프라 변경이나 로컬 테스트 환경에서도 일관된 보안 수준을 유지할 수 있었습니다.
2. **사용자 경험(UX)과 보안의 균형**: AI OCR 서비스 특성상 고화질 이미지를 허용해야 하므로 무조건적인 저용량 제한은 UX를 해칩니다. Magic Bytes 검증과 25MB 상한선을 조합하여 **"정상 사용자의 고화질 사진은 완벽히 수용하면서, 악성 페이로드는 진입 즉시 쳐내는"** 최적의 트레이드오프를 찾아냈습니다.

보안은 서비스 성장의 발목을 잡는 거추장스러운 장치가 아니라, 서비스가 안정적으로 스케일아웃하기 위해 반드시 거쳐야 하는 펀더멘털임을 다시 한번 깨달은 계기였습니다. PickSafe는 앞으로도 견고한 아키텍처를 바탕으로 안전하고 신뢰할 수 있는 AI 서비스를 만들어 가겠습니다.
