안녕하세요, **PickSafe** 백엔드 팀입니다. 

PickSafe는 이미지 기반의 성분 라벨 OCR 분석을 위해 **Gemini Vision AI**를 핵심 엔진으로 사용하고 있습니다. AI API는 강력하지만, 동시에 **비용 폭탄**과 **리소스 고갈(DoS) 공격**이라는 치명적인 양날의 검을 품고 있습니다. 

만약 악의적인 봇이 대용량 이미지나 무작위 인증 요청을 초당 수십 건씩 밀어 넣는다면 어떻게 될까요? API 쿼터는 순식간에 바닥나고, 서버 메모리는 고갈되어 일반 사용자들이 서비스를 이용하지 못하는 상황이 벌어질 것입니다.

이번 글에서는 이러한 위협에 대응하기 위해 FastAPI 환경에서 구현한 **코드 레벨 내장 방어 시스템**과 **2-Track 보안 아키텍처 설계 과정**을 공유합니다.

---

## 1. 마주한 문제 (Problem Statement)

AI 기반 서비스를 운영하면서 마주한 주요 보안 및 인프라 리스크는 크게 4가지였습니다.

1. **AI API 비용 폭탄 및 리소스 고갈 (Cost Bombing / DoS)**
   - OCR 스캔 엔드포인트(`/scan/*`)로 대용량 이미지를 연속 전송하여 외부 AI API 쿼터를 고갈시키거나 서버 메모리를 마비시키는 공격.
2. **인증 무차별 대입 공격 (Brute Force)**
   - 로그인 엔드포인트(`/auth/*`)에 무작위 계정 정보를 대입하여 계정을 탈취하거나 서버에 부하를 주는 행위.
3. **악성 페이로드 및 대용량 파일 업로드**
   - 확장자만 이미지(.jpg)로 위장한 실행 파일이나, 수십 MB에 달하는 거대 파일을 전송해 I/O를 점유하는 위협.
4. **클라이언트 사이드 웹 취약점**
   - XSS, 클릭재킹, MIME Sniffing 등을 방어하기 위한 보안 응답 헤더 누락.

## 2. 기술적 고민과 대안 비교 (Trade-off)

인프라 레벨의 방어(예: AWS WAF, API Gateway)를 구축하는 것이 가장 이상적이지만, 초기 배포 환경과 비용 효율성을 고려할 때 **코드 레벨에서 즉시 동작하는 미들웨어 기반 방어**가 필요했습니다.

### 대안 1: 외부 인프라 방어에 전적으로 의존
- **장점**: 애플리케이션 코드가 깔끔해짐.
- **단점**: 클라우드 서비스 변경 시 종속성이 생기고, 초기 구성 비용과 세팅 공수가 큼.

### 대안 2: FastAPI 미들웨어 및 인메모리 기반 2-Track 방어 아키텍처 (채택)
- **장점**: 현재 배포 환경(Render/Vercel 등)에서 추가 인프라 구축 없이 **즉시 100% 가동** 가능하며, 추후 Cloudflare 도메인 연동 시 2중 엣지 쉴드로 자연스럽게 확장 가능.
- **단점**: 분산 환경(여러 인스턴스)으로 확장 시 Redis 등 외부 저장소 연동이 필요할 수 있음 (추후 확장 포인트로 남김).

## 3. 핵심 구현 내용 (Technical Specifications)

### ① 슬라이딩 윈도우(Sliding Window) Rate Limiter
동일 IP 기준으로 엔드포인트 성격에 따라 차등적인 제한 규칙을 적용했습니다.

* **스캔 API (`/scan/*`)**: 동일 IP당 **1분 5회**, **1시간 30회** 제한. (AI API 보호)
* **인증 API (`/auth/*`)**: 동일 IP당 **1분 10회** 제한. (브루트포스 방어)
* **결과**: 제한 초과 시 `HTTP 429 Too Many Requests`와 함께 `Retry-After` 헤더를 반환하여 클라이언트가 올바르게 재시도하도록 유도했습니다.

### ② 매직 바이트(Magic Bytes) 기반 이미지 무결성 검증
단순히 파일 확장자(`filename.jpg`)만 믿고 서버 내부로 파일을 들이는 것은 자살행위입니다. 업로드된 파일의 **실제 바이너리 헤더(Magic Bytes)**를 직접 검사하도록 구현했습니다.

* **JPEG**: `\xFF\xD8\xFF`
* **PNG**: `\x89\x50\x4E\x47`
* **WebP**: `RIFF....WEBP`
* 위조된 스크립트 파일이나 악성 코드는 진입 즉시 `400 Bad Request`로 차단합니다. 또한, 최신 스마트폰의 고화질 원본 사진(7~15MB)은 충분히 수용하되, 25MB를 초과하는 거대 파일은 `413 Payload Too Large`로 엄격히 제한했습니다.

### ③ 엔터프라이즈급 보안 HTTP 응답 헤더 강제 주입
모든 응답에 5대 핵심 보안 헤더를 미들웨어로 강제 주입하여 OWASP Top 10의 클라이언트 취약점을 원천 차단했습니다.
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`

## 5. 맺음말 (Takeaways)

이번 아키텍처 설계를 통해 얻은 가장 큰 교훈은 **"보안은 미루는 것이 아니라 레이어를 쌓는 것"**이라는 점입니다. 

외부 인프라(Cloudflare 등)에만 의존하면 인프라 설정이 바뀌거나 로컬 테스트 환경에서는 무방비 상태가 되기 쉽습니다. 비즈니스 로직과 가장 가까운 애플리케이션 레이어(FastAPI)에서 1차적인 방어선(Rate Limit, Magic Byte 검증, Security Headers)을 단단히 구축해 둔 덕분에, 외부 환경 변화와 무관하게 서비스의 안정성과 AI API 비용을 안전하게 보호할 수 있게 되었습니다.

PickSafe는 앞으로도 견고한 엔지니어링을 바탕으로 사용자에게 안전하고 빠른 서비스를 제공해 나가겠습니다.
