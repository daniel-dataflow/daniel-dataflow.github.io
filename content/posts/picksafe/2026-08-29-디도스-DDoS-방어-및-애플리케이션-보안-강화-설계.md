안녕하세요. **PickSafe** 백엔드 팀입니다.

PickSafe 서비스는 사용자가 업로드한 성분 라벨을 **Gemini Vision AI**로 분석하여 안전 여부를 판별하는 핵심 기능을 제공하고 있습니다. 하지만 서비스를 고도화하는 과정에서, 외부 사용자에게 AI 기반 서비스를 오픈할 때 반드시 마주하게 되는 현실적인 인프라 과제들을 마주했습니다.

이번 포스팅에서는 **악의적인 봇의 API 비용 폭탄(Cost Bombing) 공격, 대용량 파일 페이로드 DoS, 그리고 인증 무차별 대입(Brute Force) 공격**을 방어하기 위해 적용한 **FastAPI 기반 2-Track 보안 및 스마트 Rate Limiting 아키텍처** 설계 과정을 공유합니다.

---

## 1. 문제 정의 (Context & Problem Statement)

AI 기반 서비스를 운영할 때 가장 경계해야 할 시나리오는 크게 3가지였습니다.

1. **AI API 비용 폭탄 및 리소스 고갈 공격 (Cost Bombing / DoS)**
   - 악의적인 스크립트가 대용량 이미지를 초당 수십 건씩 연속 전송할 경우, Gemini API의 쿼터가 순식간에 고갈되고 서버 메모리가 포화되어 일반 사용자의 서비스가 마비될 위험이 있었습니다.
2. **인증 무차별 대입 공격 (Brute Force)**
   - 로그인 및 소셜 인증 엔드포인트로 무작위 요청을 보내 계정을 탈취하거나 백엔드 부하를 유발하는 시도를 차단해야 했습니다.
3. **악성 파일 업로드 및 대용량 페이로드 위협**
   - 실행 파일을 이미지로 위장하거나, 수십 MB에 달하는 거대 페이로드를 전송해 서버 I/O를 마비시키는 공격 패턴이 존재했습니다.

인프라가 완벽히 구축되지 않은 초기 단계에서도 **코드 레벨에서 100% 방어선을 구축**하고, 추후 글로벌 엣지 영역까지 확장 가능한 유연한 구조를 설계하는 것이 이번 아키텍처의 목표였습니다.

## 2. 기술적 고민과 대안 비교 (Architecture & Trade-offs)

### 고민 1. Rate Limiting 저장소 선택: Redis vs In-Memory Sliding Window
- **Redis 도입 검토**: 분산 환경 및 다중 인스턴스 스케일아웃에 유리하지만, 초기 가벼운 배포 환경에서는 인프라 복잡도와 네트워크 레이턴시 비용이 발생함.
- **슬라이딩 타임 윈도우(Sliding Window Log) 인메모리 방식 채택**: 
  - 단일 인스턴스 환경에서 별도의 외부 인프라 비용 없이 매우 빠른 속도로 정밀한 타임스탬프 기반 제한을 구현할 수 있습니다. 
  - 추후 트래픽 증가 및 다중화 시 외부 캐시(Redis)로 쉽게 전환할 수 있도록 인터페이스를 추상화하는 방향으로 타협점을 잡았습니다.

### 고민 2. 이미지 용량 제한 기준 설정
- 최신 스마트폰(아이폰, 갤럭시)의 고화질 성분표 사진은 보통 **7MB ~ 15MB** 수준을 형성합니다. OCR 인식률을 보장하기 위해서는 이를 완벽히 수용해야 합니다.
- 반면, 50MB 이상의 비정상적인 DoS 파일 폭탄은 백엔드 로직에 도달하기 전 진입 단계에서 차단해야 하므로, **상한선을 25MB**로 엄격하게 고정하고 초과 시 즉시 거부(`413 Payload Too Large`)하도록 설계했습니다.

## 3. 최종 해결 및 세부 구현 (Technical Implementation)

### 1) 엔드포인트별 차등 스마트 Rate Limiter
비즈니스 성격에 따라 허용 임계치를 다르게 가져가는 미들웨어를 구현했습니다.
- **스캔 API (`/scan`)**: 동일 IP당 **1분 5회**, **1시간 30회**로 제한하여 고비용 AI 연산을 철저히 보호합니다.
- **인증 API (`/auth/login` 등)**: 동일 IP당 **1분 10회**로 제한하여 무차별 대입 공격을 차단합니다.
- **예외 처리**: 관리자 계정 및 헬스체크(`/__health__`) 엔드포인트는 Whitelist 처리하여 모니터링에 지장이 없도록 했습니다.
- 제한 초과 시 표준 규격인 `HTTP 429 Too Many Requests`와 함께 `Retry-After` 헤더를 반환합니다.

### 2) 매직 바이트(Magic Bytes) 기반 파일 무결성 검증
확장자만 `.jpg`로 조작한 쉘 스크립트나 악성 파일을 원천 차단하기 위해, 파일 업로드 시 바이너리 헤더의 첫 바이트를 직접 검사합니다.
- **JPEG**: `\xFF\xD8\xFF`
- **PNG**: `\x89PNG`
- **WebP**: `RIFF....WEBP`
- 파일 헤더가 일치하지 않을 경우, 비즈니스 로직을 타기 전 `400 Bad Request`로 즉시 차단합니다.

### 3) 2-Track 방어 아키텍처
현재는 FastAPI 미들웨어 레벨에서 1차 방어선(보안 헤더, 슬라이딩 윈도우 림이터, 매직바이트 검증)을 100% 가동 중이며, 추후 도메인 확장 시 **Cloudflare 글로벌 엣지 쉴드**를 앞단에 두어 L3/L4 DDoS와 악성 크롤러를 원천 차단하는 2-Track 구조를 완성했습니다.

```mermaid
flowchart TD
    subgraph Track1_현재_내장_방어 [Track 1: 코드 레벨 내장 보안 (현재 100% 가동)]
        A1[클라이언트 요청] --> A2[보안 HTTP 응답 헤더 미들웨어]
        A2 --> A3[슬라이딩 윈도우 Rate Limiter]
        A3 -->|임계치 초과| A4[429 Too Many Requests 차단]
        A3 -->|정상 범위| A5[이미지 매직바이트 & 25MB 엄격 검증]
        A5 --> A6[Gemini OCR 안전 실행]
    end
```

## 4. 맺음말 및 Takeaways

이번 아키텍처 설계를 통해 얻은 가장 큰 교훈은 **"외부 API를 연동하는 서비스일수록 애플리케이션 단에서의 방어선이 비용 직결 문제와 직결된다"**는 점입니다. 

단순히 기능을 구현하는 것을 넘어, 비즈니스의 비용 구조와 인프라 안정성을 동시에 고려한 방어 레이어를 설계함으로써 무분별한 쿼터 소모를 방어하고 안정적인 서비스 운영 기반을 다질 수 있었습니다. 

앞으로도 PickSafe는 견고한 엔지니어링을 바탕으로 안전하고 신뢰할 수 있는 서비스를 만들어 나가겠습니다. 감사합니다.
