화장품 성분 분석 서비스 **PickSafe**를 구축하면서 마주한 가장 첫 번째 엔지니어링 허들은 **"실제 사용자가 찍은 불완전한 성분표 이미지에서 어떻게 정확한 텍스트 데이터를 추출할 것인가?"**였습니다.

화장품 용기의 곡면, 비치는 재질, 미세한 폰트 크기, 그리고 영문과 한글이 섞인 복잡한 원료명은 기존 OCR 기술에게 꽤나 까다로운 도전과제였습니다. 이번 글에서는 저희 팀이 비정형 이미지 데이터 처리 문제를 해결하기 위해 전통적 OCR 대신 **Multimodal LLM(Gemini Vision API)**을 채택한 기술적 배경과, 개발 생산성 및 시스템 회복 탄력성을 높이기 위해 적용한 **Mock 디버그 폴백(Fallback) 모드**의 설계 과정을 공유합니다.

---

## 1. 문제 정의: 비정형 데이터와 텍스트 인식의 한계

화장품 성분표 이미지는 다음과 같은 기술적 난제들을 가지고 있습니다.

* **복잡한 구획 및 특수문자:** 성분은 쉼표(,), 슬래시(/), 괄호 등 온갖 특수문자로 구분되며 줄바꿈이 불규칙하게 발생합니다.
* **오타 및 전문 용어 문맥 복원 필요:** 화학 성분명은 한 끗 차이로 완전히 다른 성분이 됩니다. 단순 이미지-텍스트 변환만으로는 훼손된 글자를 올바르게 복원하기 어렵습니다.
* **다국어 혼용:** 국문 성분명과 INCI(국제 화장품 성분 명명법) 영문명이 혼용되어 나타납니다.

초기 검토 단계에서 전통적인 오픈소스 OCR(예: Tesseract)을 고려했으나, 이미지 전처리(Binarization, Deskew 등)에 막대한 파이프라인 구축 비용이 발생함에도 불구하고 전문 화학 용어 인식률과 문맥 복원력에서 한계를 보였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

저희는 **인식 정확도, 초기 도입 비용, 파이프라인 복잡도**라는 3가지 축을 기준으로 대안을 비교 평가했습니다.

| 기술 스택 | 인식 정확도 및 문맥 복원 | 초기 비용 | 파이프라인 관리 공수 |
| :--- | :--- | :--- | :--- |
| **Tesseract OCR (Open-source)** | 낮음 (전처리 의존도 높음) | 무료 | 매우 높음 (규칙 기반 파서 필요) |
| **상용 Cloud OCR (Google/AWS)** | 높음 (단순 텍스트 추출) | 유료 (호출당 과금) | 중간 (텍스트 후처리 작업 필요) |
| **Gemini Vision API (Multimodal LLM)** | **매우 높음 (문맥 기반 복원)** | **무료 티어 활용 가능** | **낮음 (JSON 직접 추출 가능)** |

### 왜 Gemini Vision API인가?
1. **문맥을 이해하는 Vision Engine:** LLM 기반 Vision 모델은 단순 픽셀 추론에 그치지 않고, "화장품 성분표"라는 문맥(Context)을 이해하여 훼손되거나 뭉개진 글자(예: `Centella Asiatica` $\rightarrow$ `센텔라 아시아티카`)를 보다 정확하게 교정하여 추출합니다.
2. **비용 효율적인 MVP 검증:** 검증 단계에서 상용 Cloud OCR의 고정 비용을 지불하는 대신, 제공되는 Free Tier 범위 내에서 충분히 고성능의 백엔드 파이프라인을 운영할 수 있었습니다.

## 3. 최종 해결책: 아키텍처 및 Mock 디버그 폴백 모드

외부 API 서비스에 대한 의존도가 높아질수록 **디버깅의 난항**과 **API Limit으로 인한 로컬 개발 블로킹**이라는 새로운 문제가 생겨납니다. 팀원 각자의 로컬 개발 환경에서 API Key가 미설정되어 있거나, Rate Limit에 도달했을 때 백엔드 애플리케이션 전체가 멈추는 상황은 방지해야 했습니다.

이를 위해 **서비스 레이어 추상화**와 **Mock Debug Fallback** 구조를 설계했습니다.

```
[ Client Request ]
        │
        ▼
[ Backend App (FastAPI) ]
        │
        ▼
[ OCR Service Layer ] ── ( API Key 존재 & 유효? )
        │                                 │
        ├─── [ YES ] ────────────► [ Gemini Vision API ]
        │                                 │ (Rate Limit/오류 발생 시)
        └─── [ NO / Failure ] ───► [ Mock Debug Fallback ]
                                          │
                                          ▼
                                (콘솔 경고 로깅 & Mock Data 반환)
```

### 디버그 폴백 모드 설계의 핵심 포인트

1. **인터페이스 추상화 (`ocr_service.py`):**
   외부 API호출 로직을 모듈 내부로 캡슐화하여, 컨트롤러(API Endpoint) 영역에서는 실제 Gemini API가 호출되었는지 Mock 데이터가 반환되었는지 알 필요가 없도록 디커플링했습니다.

2. **안전한 장애 예방 (Defensive Programming):**
   `GEMINI_API_KEY` 환경 변수가 누락되었거나 API 호출에 실패하더라도, 시스템이 Exception을 뿜으며 다운되는 대신 명확한 경고(Warning) 로그를 남기고 미리 정의된 화장품 성분 Mock 데이터를 안전하게 반환합니다.

3. **개발 생산성(DX) 향상:**
   신규 개발자가 로컬 환경을 세팅할 때 외부 API 키를 즉시 발급받지 않아도 백엔드 및 프론트엔드 연동 테스트를 즉시 진행할 수 있는 환경을 만들었습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 OCR 파이프라인 구축 및 결정을 통해 얻은 핵심 레슨은 다음과 같습니다.

1. **LLM은 훌륭한 '문맥 인식형' 데이터 추출기다:**
   단순 OCR 솔루션과 비교했을 때, 비정형 텍스트 영역에서 LLM의 Vision 기능은 텍스트 추출과 데이터 정제(Structuring)를 한 번에 해결해 주어 파이프라인 개발 시간을 대폭 단축시켜 줍니다.

2. **외부 의존성은 반드시 캡슐화하고 격리해야 한다:**
   외부 서비스는 언제든 실패(Failure)하거나 제약(Rate Limit)이 생길 수 있습니다. Mock 폴백 패턴과 같은 방어적 설계를 초기 단계부터 도입하면 외부 악재 속에서도 팀의 개발 템포를 안정적으로 유지할 수 있습니다.

3. **MVP 개발에서는 비용 대 효과(Trade-off) 추구가 핵심이다:**
   무조건 무겁고 비싼 솔루션을 채택하기보다, 프레임워크와 API의 제약 사항을 파악하고 비용 효율적인 도구를 적재적소에 배치하는 것이 시니어 엔지니어가 가져야 할 중요한 관점임을 다시 한번 확인했습니다.
