화장품 성분 분석 서비스 **PickSafe**를 개발하며 맞닥뜨린 가장 큰 기술적 도전 중 하나는 **"사용자가 찍은 성분표 이미지에서 얼마나 정확하고 유연하게 텍스트를 추출할 것인가"**였습니다.

실제 사용자가 촬영하는 화장품 용기 표면은 곡면이거나 빛 반사가 심하고, 다국어(영어, 한국어, 전성분 표기명 등)와 특수문자가 복잡하게 얽혀 있습니다. 이번 포스팅에서는 기존 OCR 방식의 한계를 극복하기 위해 **LLM 기반 Vision API를 채택한 과정**, 그리고 **개발 생산성(DX)과 안정성을 위한 Fallback 시스템 설계 경험**을 공유합니다.

---

## 1. 문제 정의: "단순 OCR로는 성분표를 읽을 수 없다"

화장품 성분표 이미지 인식에는 다음과 같은 까다로운 비정형 데이터 처리 이슈가 존재합니다.

1. **복잡한 도메인 특성**: '글리세린, 나이아신아마이드, 1,2-헥산다이올'처럼 화학 성분명 특유의 숫자와 특수문자가 조합되어 있습니다.
2. **이미지 품질 노이즈**: 곡면 용기, 조명 반사, 폰트 크기 미세함 등으로 인해 오타가 자주 발생합니다.
3. **후처리 비용**: 전통적인 OCR 엔진은 글자 위치만 파악할 뿐, `콤마(,)`나 `줄바꿈`이 성분 간의 구분자인지 문맥상 파악하지 못해 거대한 후처리 로직(Regex, 파싱 알고리즘)을 필요로 했습니다.

저희는 초기 검증(MVP) 단계에서 **최소한의 후처리 로직으로 정교한 성분 파싱 능력을 확보**하면서도 **비용 효율적인 아키텍처**를 찾아야 했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

성분표 파이프라인 엔진 선정을 위해 크게 3가지 대안을 비교 평가했습니다.

| 항목 | ① 오픈소스 OCR (Tesseract 등) | ② 상용 클라우드 OCR (AWS, Google Cloud) | ③ LLM 기반 Vision API (Gemini Vision) |
| :--- | :--- | :--- | :--- |
| **인식 정확도** | 낮음 (곡면/노이즈에 취약) | 높음 (텍스트 영역 추출 우수) | **매우 높음** (문맥 기반 복원 가능) |
| **성분 파싱 능력**| 별도 NLP/파서 개발 필수 | 별도 NLP/파서 개발 필수 | **자체 문맥 이해 및 구조화 가능** |
| **초기 비용** | 무상 (자체 서버 자원 사용) | 유상 (호출당 과금) | **Free Tier 제공 (비용 절감)** |
| **응답 속도** | 매우 빠름 | 빠름 | 보통 (네트워크 Latency 존재) |

### 💡 주요 의사결정 포인트: "OCR + 문맥 이해"의 결합
상용 OCR 솔루션은 텍스트 자체는 잘 읽어내지만, 깨진 단어를 교정하거나 오타를 복원하는 '문맥 파악'은 불가능합니다. 반면 **Gemini Vision API**는 거대언어모델(LLM)의 시각-언어 통합 능력을 활용해 **일부 훼손된 글자도 성분명 맥락을 기반으로 정확하게 보정**해 내는 압도적인 성능을 보여주었습니다.

또한, 검증 단계에서 고비용의 SaaS 솔루션을 도입하는 대신 **Free Tier 한도 내에서 유연하게 검증**할 수 있다는 점이 강력한 트레이드오프 요소로 작용했습니다.

## 3. 아키텍처 설계 및 해결 방안

### (1) OCR 서비스 추상화 (`ocr_service.py`)
향후 다른 Vision 모델로 교체되거나 자체 OCR 모델을 도입하더라도 비즈니스 로직에 영향이 없도록 **OCR 서비스를 추상화 레이어로 격리**했습니다.

```python
# 서비스 레이어 추상화 예시 (pseudo code)
class OCRService:
    async def extract_ingredients_from_image(self, image_bytes: bytes) -> list[str]:
        # 1. API Key 존재 여부 및 설정 검증
        # 2. Vision API 호출 및 성분 추출
        # 3. 예외 발생 또는 Key 미설정 시 Fallback 동작
        ...
```

### (2) 개발 환경 보호를 위한 'Mock Debug Fallback Mode' 설계
외부 API에 의존하는 구조는 **로컬 개발 환경의 DX(개발자 경험)**를 해칠 수 있습니다.
- 로컬 개발자마다 API 키를 발급받아 관리해야 하는 번거로움
- API Rate Limit(호출 제한) 초과 시 개발 작업 중단
- CI/CD 빌드 파이프라인에서의 비동기 테스트 난항

이를 해결하기 위해 **Graceful Degradation(우아한 성능 저하)** 원칙을 적용한 **Mock Debug Fallback Mode**를 도입했습니다.

```
[클라이언트 요청] ──> [OCR Service]
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
   [GEMINI_API_KEY 유효?]     [API Key 없음 / Rate Limit]
             │                         │
             ├─ YES ──> Gemini Call    └─ NO ──> [Mock Fallback]
             │                                       │
             └─ 실패 시 ─────────────────────────────┘
                                                     ▼
                                      로그 출력 & 표준 Mock 성분 반환
```

환경 변수(`GEMINI_API_KEY`)가 설정되지 않았거나 호출에 실패한 경우, 시스템은 런타임 에러를 던져 애플리케이션을 중단시키는 대신 **경고 로그를 남기고 미리 정의된 고품질의 Mock 성분 데이터셋을 반환**합니다. 이를 통해 개발자는 API 호출 제약 없이 백엔드 및 프론트엔드 연동 개발을 원활하게 진행할 수 있었습니다.

## 4. 엔지니어링 교훈 및 성과 (Takeaway)

1. **LLM은 단순히 대화형 도구가 아니다**: LLM의 Vision 기능을 비정형 이미지 데이터의 '스마트 ETL(추출·변환·적재) 파이프라인'으로 재정의함으로써, 수십 줄의 까다로운 후처리 Regex 로직을 제거하고 개발 속도를 대폭 향상시켰습니다.
2. **DX(개발자 경험)를 고려한 아키텍처의 중요성**: 외부 API 의존도가 높은 파이프라인에 Fallback 전략을 사전 구축함으로써, API 키 누락이나 쿼터 초과 상황에서도 로컬 개발 환경이 블로킹(Blocking)되는 현상을 완전히 방지했습니다.
3. **비용 효율적인 MVP 검증**: 초기에 과도한 인프라 비용을 지출하지 않고도, LLM Free Tier와 모듈화된 설계를 결합해 프로덕션 수준의 정확도를 빠르게 검증해낼 수 있었습니다.
