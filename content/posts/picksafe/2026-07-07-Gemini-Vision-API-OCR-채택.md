제품 패키지에 인쇄된 성분표를 사진으로 찍어 안전성을 분석하는 기능은 우리 서비스의 핵심 가치 중 하나입니다. 하지만 실제 사용자가 촬영하는 이미지는 조도, 곡면 왜곡, 다국어 혼용(영어·한국어 등), 복잡한 특수문자 분리 기호 등 다양한 노이즈를 포함하고 있습니다.

이번 글에서는 비정형 성분표 텍스트 추출 정확도를 극대화하면서도, 초기 MVP 단계의 비용 효율성과 개발 생산성을 동시에 확보하기 위해 **Gemini Vision API 기반 파이프라인과 Mock 디버그 폴백(Fallback) 아키텍처**를 설계한 과정을 공유합니다.

---

## 1. 마주한 문제: 비정형 다국어 성분표의 인식 한계

화장품 전성분 표기는 일반적인 정형 문서와 다른 독특한 기술적 난제를 안고 있습니다.

1. **복잡한 문맥과 특수 기호 분리**: 성분명은 콤마(`,`), 슬래시(`/`), 괄호(`()`) 등으로 연결되어 있으며, 줄바꿈 위치에 따라 단어가 임의로 분절되기도 합니다.
2. **다국어 혼용 및 오탈자**: 수입 화장품의 영문 전성분과 한글 번역 성분이 섞여 있거나 인쇄 폰트의 가독성이 낮아 기존 전통적 OCR 엔진으로는 인식 오류율이 높았습니다.
3. **개발 환경의 외부 의존성 리스크**: 외부 Vision API에 직접 의존할 경우, 로컬 개발 환경에서의 키 관리 번거로움, 레이트 리밋(Rate Limit) 초과, CI/CD 테스트 실패 등의 부작용이 발생할 수 있었습니다.

---

## 2. 기술적 고민과 대안 비교

성분 추출 파이프라인 구축을 위해 대표적인 세 가지 접근 방식을 비교 검토했습니다.

| 비교 항목 | 전통적 오픈소스 OCR (Tesseract 등) | 전용 클라우드 OCR (Cloud Vision / Textract) | LLM 기반 Vision API (Gemini) |
| :--- | :--- | :--- | :--- |
| **비정형 문맥 복원력** | 낮음 (단순 픽셀 기반 텍스트 추출) | 보통 (레이아웃 파싱 우수하나 문맥 보정 한계) | **매우 높음 (불완전 단어의 문맥적 보정 가능)** |
| **다국어 성분 구획 분리**| 추가 후처리 정규식 파이프라인 필수 | 후처리 파이프라인 필요 | **프롬프트 기반 단어 구획 정제 동시 수행** |
| **비용 및 인프라 부담** | 인프라 운영 비용 및 모델 튜닝 리소스 발생 | 종량제 과금에 따른 MVP 검증 비용 부담 | **무료 티어 활용으로 초기 검증 비용 제로화** |

### 의사결정의 핵심 근거

전통적인 OCR은 단순히 이미지 내 글자를 인식할 뿐, "이 글자가 성분명인가?"라는 문맥적 의미를 이해하지 못합니다. 반면 거대언어모델(LLM) 기반의 Vision 엔진은 **이미지 텍스트 인식과 의미 기반 토큰 정제(Structuring)를 단일 단계에서 처리**할 수 있다는 결정적 강점이 있었습니다.

이에 따라 MVP 단계에서 인식률과 파이프라인 단순성을 모두 잡을 수 있는 **Gemini Vision API**를 핵심 엔진으로 채택했습니다.

---

## 3. 아키텍처 설계: 서비스 추상화와 Mock Fallback

외부 API 의존도가 높은 파이프라인일수록 **장애 격리(Fault Isolation)**와 **개발자 경험(DX)**이 중요합니다. 우리는 다음과 같은 구조로 OCR 모듈을 추상화했습니다.

```
[클라이언트 이미지 업로드]
          │
          ▼
┌──────────────────────────────────────────────┐
│            OCR Service Layer                 │
│  (API Key 유효성 및 런타임 상태 검증)         │
└──────┬────────────────────────────────┬──────┘
       │ [API Key 정상]                 │ [Key 부재 / 제한 초과]
       ▼                                ▼
┌─────────────────────────┐    ┌─────────────────────────┐
│ Gemini Vision Pipeline  │    │  Mock Fallback Engine   │
│ (실시간 성분 추출/정제)  │    │ (사전 정의 픽스처 반환) │
└─────────────────────────┘    └─────────────────────────┘
```

### 1) 느슨한 결합을 위한 인터페이스 추상화
비즈니스 로직이 특정 Vision 공급자에 종속되지 않도록 OCR 호출부를 독립 서비스 모듈로 격리했습니다. 향후 자체 경량 OCR 모델이나 타 클라우드 솔루션으로 교체하더라도 상위 서비스 계층의 코드 변경 없이 어댑터 교체만으로 대응 가능합니다.

### 2) Zero-Config Mock 디버그 폴백 모드
새로운 팀원이 프로젝트에 온보딩하거나 CI 환경에서 테스트를 실행할 때, 별도의 외부 API 키 발급 없이도 전체 스캔 파이프라인이 정상 작동하도록 설계했습니다. 유효하지 않은 키나 호출 제한 상황에서는 명확한 경고 로그를 남기며 정형화된 더미 성분 데이터를 안전하게 반환하여 런타임 크래시를 방지합니다.

---

## 4. 엔지니어링 교훈 (Takeaway)

1. **최신 LLM Vision은 비정형 파싱의 훌륭한 대안이다**  
   단순 OCR + 무거운 정규식 후처리 파이프라인 조합 대신, Vision LLM을 도입함으로써 파이프라인 복잡도를 대폭 줄이고 다국어 인식률을 획기적으로 개선할 수 있었습니다.
2. **초기 단계일수록 Fallback 전략이 개발 속도를 좌우한다**  
   외부 유료/제한적 API를 핵심 코어로 둘 때는 처음부터 '키가 없거나 실패할 때의 안전망(Mock Fallback)'을 아키텍처에 포함해야 팀 전체의 개발 및 테스트 병목을 제거할 수 있습니다.
3. **비용 효율성과 확장성의 균형**  
   MVP 검증 단계에서는 무료 티어를 극대화해 리소스를 절감하되, 서비스 인터페이스를 추상화해 둠으로써 트래픽 급증 시 엔터프라이즈 파이프라인으로 매끄럽게 전환할 수 있는 확장성을 확보했습니다.
