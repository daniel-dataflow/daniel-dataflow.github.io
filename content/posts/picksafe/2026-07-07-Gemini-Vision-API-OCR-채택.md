제품 개발 초기(MVP) 단계에서 화장품 성분표처럼 **비정형성이 강하고 다국어가 뒤섞인 텍스트 데이터**를 정밀하게 추출하는 것은 생각보다 까다로운 문제입니다. 

오늘은 PickSafe 팀이 화장품 성분표 OCR 파이프라인을 구축하면서 경험한 **기술적 페인 포인트(Pain Point), 오픈소스 대비 LLM Vision 모델 채택 이유, 그리고 시스템 안정성을 확보하기 위한 폴백(Fallback) 모드 설계 과정**을 공유합니다.

---

## 1. 문제 정의: "텍스트는 읽히는데, 맥락이 파괴된다"

화장품 굴곡면이나 비닐 포장지에 인쇄된 성분표 이미지는 일반적인 문서 스캔과 전혀 다른 특성을 가집니다.

* **복잡한 비정형 구조**: 줄바꿈, 쉼표(,), 특수문자가 무작위로 섞여 있으며 폰트 크기와 간격이 불규칙합니다.
* **다국어 혼용**: 한국어 성분명과 INCI(국제 화장품 성분 명명법) 영어 성분이 한 텍스트 블록 내에 혼재합니다.
* **오탈자 파손**: 조명 반사나 빛 번짐으로 인해 글자가 일부 훼손되는 현상이 빈번합니다.

초기 연구 단계에서 고려한 **전통적 오픈소스 OCR 엔진(Tesseract 등)**은 글자 단위의 인식은 가능했으나, 훼손된 문맥을 복원하거나 성분 단위의 구획(Delimiter)을 정확히 파악하지 못했습니다. 결과적으로 OCR 이후 후처리를 위해 작성해야 하는 정규표현식 파서(Parser) 로직이 기하급수적으로 복잡해지는 문제가 발생했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

저희는 **인식 정확도, 후처리 비용, 운영 비용, 개발 생산성**을 기준으로 3가지 선택지를 비교 분석했습니다.

| 항목 | 전통적 오픈소스 OCR (Tesseract 등) | 엔터프라이즈 Cloud OCR (Google/AWS) | LLM 기반 Vision API (Gemini Vision) |
| :--- | :--- | :--- | :--- |
| **성분표 인식률** | 낮음 (문맥 파악 불가) | 높음 (단어 단위 인식 우수) | **매우 높음 (문맥 복원 및 구획 파악)** |
| **후처리 복잡도** | 매우 높음 (수많은 정규식 필요) | 중간 (파싱 로직 작성 필요) | **낮음 (원하는 구조 형태로 즉시 추출 가능)** |
| **비용 구조** | 무료 (자체 서버 자원 사용) | 종량제 (API 호출당 비용 발생) | **Free Tier 제공 (MVP 비용 최적화)** |
| **외부 의존성** | 없음 (Local 실행) | 높음 (네트워크/API 연동) | 높음 (네트워크/API 연동) |

### **선택: Gemini Vision API**
결과적으로 거대언어모델(LLM) 기반의 **Gemini Vision API**를 핵심 엔진으로 채택했습니다. Gemini Vision은 단순히 이미지를 텍스트로 변환하는 것에 그치지 않고, **"화장품 성분표"라는 도메인 맥락을 이해하여 훼손된 오탈자를 스스로 복원하고 성분별 구획을 명확히 구분**해 주는 장점이 있었습니다. 또한, MVP 검증 단계에서 무료 한도(Free Tier)를 활용하여 상용 Cloud OCR 대비 초기 운영 비용을 크게 절감할 수 있었습니다.

## 3. 구조적 한계 극복: Graceful Degradation & Mock 폴백 설계

LLM Vision API 도입이 항상 완벽한 것은 아닙니다. 외부 API 서비스에는 다음과 같은 리스크가 존재합니다.

1. **로컬 개발 환경의 블로킹**: 개발자 개개인이 API 키를 설정하지 않았거나, 키 발급이 지연될 경우 전체 애플리케이션 실행이 차단됨.
2. **Rate Limit 초과 및 서비스 장애**: 무료 티어 특성상 순간적인 트래픽 몰림으로 429(Rate Limit Exceeded) 또는 외부 네트워크 에러 발생 가능성.

이 문제를 해결하기 위해 시스템이 완전히 멈추지 않고 우아하게 저하되는 **Graceful Degradation 패턴** 기반의 **Mock 디버그 폴백 모드**를 설계했습니다.

```
 [클라이언트 요청]
        │
        ▼
 ┌──────────────┐
 │ OCR Service  │
 └──────┬───────┘
        │
        ├─▶ [유효한 API Key 존재 & 정상 호출] ──▶ Gemini Vision API 처리 ──▶ 결과 반환
        │
        └─▶ [API Key 미설정 / Rate Limit / 에러]
                  │
                  ▼ (Graceful Degradation)
           [Mock Debug Fallback Mode]
                  │
                  ├─▶ 경고(Warning) 로그 남김
                  └─▶ 미리 정의된 표준 성분 데이터셋 반환 (런타임 Crash 방지)
```

### **구현 포인트 (개념화된 코드 예시)**

백엔드 레이어에서는 OCR 기능을 추상화하여, API 키 미지정 환경에서도 애플리케이션 실행이 멈추지 않고 디버그 데이터를 반환하도록 조치했습니다.

* **인터페이스 추상화**: `ocr_service` 모듈을 격리하여 향후 다른 Vision 모델로 교체하더라도 상위 비즈니스 로직에 영향이 없도록 설계했습니다.
* **안전한 환경 변수 처리**: API 키 부재 시 런타임 예외(Exception)를 throw하는 대신 경고 로그를 출력하고 Mock 데이터 로직으로 전환시켰습니다.

이를 통해 개발자는 API 키 없이도 로컬 환경에서 파이프라인 전체를 E2E로 테스트할 수 있게 되었고, external API 호출 실패가 전체 백엔드 붕괴로 이어지는 위험을 차단했습니다.

## 4. 엔지니어링 교훈 및 결론 (Takeaways)

이번 OCR 파이프라인 설계 및 의사결정을 통해 얻은 핵심 성과는 다음과 같습니다.

1. **도메인 특성을 고려한 기술 선택**: 단순 글자 인식이 아닌 '문맥 이해'가 필요한 텍스트 처리에는 규칙 기반 파서보다 **Vision LLM의 맥락 복원 능력**을 활용하는 것이 후처리 코드를 줄이고 생산성을 극대화하는 길임을 확인했습니다.
2. **외부 의존성 제어 (Fault Tolerance)**: 외부 API에 100% 의존하는 시스템은 언제든 무너질 수 있습니다. 개발 초기부터 **Mock 폴백 설계**를 내재화하여 개발 생산성(DX)과 시스템의 회복탄력성(Resilience)을 모두 챙길 수 있었습니다.
3. **확장성을 염두에 둔 레이어 분리**: OCR 엔진 로직을 서비스 레이어로 격리해두었기 때문에, 향후 서비스 스케일업 시 유료 플랜 전환이나 타 클라우드 OCR/자체 구축 VLM 모델로의 전환이 매우 용이해졌습니다.

PickSafe 팀은 앞으로도 비즈니스 밸류를 빠르게 검증하면서도, 아키텍처의 유연성과 안정성을 잃지 않는 엔지니어링을 지향합니다.
