화장품 성분 분석 서비스 `PickSafe`를 개발하며 가장 먼저 마주한 기술적 난제는 **"사용자가 찍은 굴곡지고 희미한 성분표 이미지에서 어떻게 정확한 성분 텍스트를 추출할 것인가?"**였습니다.

실제 사용자가 촬영하는 화장품 패키지 이미지는 조명 불균형, 곡면 반사, 미세한 폰트, 한국어/영어/특수문자가 섞인 복잡한 레이아웃을 가집니다. 단순한 OCR 기술만으로는 서비스 요구사항을 충족하기 어려웠습니다. 

이 글에서는 비정형 데이터 인식 문제를 해결하기 위해 전통적 OCR 솔루션 대신 **Gemini Vision API**를 도입한 배경과, 외부 API 의존성 속에서 개발 생산성과 시스템 안정성을 확보하기 위해 적용한 **Mock 디버그 폴백(Fallback) 아키텍처**를 소개합니다.

---

## 1. 문제 정의: "텍스트 추출"을 넘어선 "문맥 이해"의 필요성

화장품 성분표 이미지는 다음과 같은 독특한 비정형 특성을 지닙니다.

1. **단어 구획(Delimiter)의 모호함**: 쉼표(,), 슬래시(/), 줄바꿈(Enter) 등이 혼용되어 있어 성분과 성분 사이의 경계를 파악하기 어렵습니다.
2. **다국어 혼용 및 노이즈**: 성분명에 포함된 화학명, 영문 표기, 괄호 속 추가 설명, 노이즈 텍스트(예: "용량: 50ml", "업소명 및 소재지")가 한 번에 찍힙니다.
3. **이미지 품질 저하**: 카메라 흔들림, 빛 반사로 인해 일부 글자가 훼손되는 경우가 빈번합니다.

기존의 OCR 기술은 '글자 형태의 복원'에는 강점을 보이지만, 추출된 문자열을 의미 있는 데이터 단위로 파싱하는 것은 전적으로 후처리(Post-processing) 로직에 의존해야 했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

저희 팀은 문제 해결을 위해 크게 세 가지 기술 대안을 검토했습니다.

| 비교 항목 | 오픈소스 OCR (Tesseract 등) | 상용 클라우드 OCR (Google Cloud Vision 등) | 멀티모달 LLM (Gemini Vision API) |
| :--- | :--- | :--- | :--- |
| **인식 정확도** | 낮음 (배경 노이즈 및 곡면에 취약) | 높음 (텍스트 추출 성능 우수) | **매우 높음 (문맥 기반 복원 가능)** |
| **후처리 파싱 비용** | 매우 높음 (규칙 기반 파서 구현 필수) | 높음 (별도의 NLP 파이프라인 필요) | **없음 (자연어 지시로 구조화 가능)** |
| **도입 및 운영 비용** | 무료 (서버 리소스 소모) | 사용량 비례 (MVP 단계 비용 부담) | **무료 티어 활용 가능 (비용 효율적)** |
| **개발 속도** | 늦음 (파서 개발 시간 소요) | 보통 | **매우 빠름** |

### 선택: 왜 Gemini Vision API인가?
* **문맥 기반 훼손 문자 복원**: 단순 이미지 픽셀 매칭이 아닌, 거대 언어 모델의 언어적 맥락을 바탕으로 찌그러지거나 잘린 성분명을 높은 확률로 유추해냅니다.
* **Extraction과 Parsing의 통합**: "이미지 내 성분명만 추출해서 리스트 형태로 반환해줘"와 같은 꺾쇠 형태의 프롬프팅만으로 텍스트 추출과 데이터 구조화(Parsing)를 한 번에 처리할 수 있습니다.
* **MVP 단계의 비용 최적화**: 극초기 데이터 검증 단계에서 Gemini의 무료 티어(Free Tier)를 활용함으로써 정식 상용 OCR 서비스 도입 대비 트래픽 비용을 획기적으로 절감할 수 있었습니다.

## 3. 엔지니어링 세부 구현: 회복 탄력성(Resilience)과 DX를 위한 폴백 모드

외부 API를 핵심 파이프라인에 통합할 때 가장 경계해야 할 점은 **외부 서비스 장애나 환경 설정 문제로 인해 전체 개발/운영 흐름이 차단(Blocking)되는 현상**입니다.

특히 다음과 같은 리스크가 존재했습니다.
- 로컬 개발 환경에서 매번 외부 API를 호출할 경우 발생하는 API Rate Limit 초과 문제
- API Key 미설정 환경(예: 신규 개발자 온보딩, CI/CD 테스트 환경)에서의 런타임 크래시
- 네트워크 지연으로 인한 개발 생산성 저하

이 문제를 해결하기 위해, 저희는 백엔드 OCR 서비스 서비스 레이어에 **Mock 디버그 폴백 시스템**을 구현했습니다.

```
[Client Image Upload] 
         │
         ▼
[OCR Service Layer]
         │
  API Key 유효성 검사
         ├── (Key 미지정 / Rate Limit) ──> [Console Warning Logging] ──> [Pre-defined Mock Ingredient Data 반환]
         │
         └── (Key 유효함) ───────────────> [Gemini Vision API 호출] ───> [실제 텍스트 데이터 반환]
```

### 핵심 구현 포인트
1. **역할 분리와 추상화**: OCR 로직을 서비스 내부 모듈로 추상화하여, 외부 API 인터페이스 변경이나 내부 폴백 동작이 API Controller 영역에 영향(Side-effect)을 주지 않도록 설계했습니다.
2. **Graceful Degradation**: `GEMINI_API_KEY` 환경변수가 없더라도 런타임 에러(Unhandled Exception)를 발생시키는 대신, 명확한 경고 로그를 남기고 미리 정의된 덤미 성분 텍스트를 반환하여 로컬 디버깅 프로세스가 중단되지 않도록 조치했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **도구 선택 시 '기능'보다 '도메인 맥락'을 고려하라**
   단순 OCR 성능 지표보다 "비정형 데이터에서 원하는 결과물을 얼마나 적은 공수로 이끌어내는가"가 중요했습니다. LLM 기반 Vision API는 데이터 파싱 공수를 획기적으로 줄여주는 최고의 도구였습니다.

2. **외부 의존성은 반드시 샌드박싱(Sandboxing)하라**
   외부 API는 언제든 실패하거나, 비용이 발생하거나, 속도가 느려질 수 있습니다. 개발 단계에서의 Mock 폴백 처리는 개발자 경험(DX)을 끌어올릴 뿐만 아니라, 향후 시스템의 회복 탄력성을 높이는 훌륭한 안전장치가 됩니다.

3. **MVP 아키텍처는 유연성을 최우선으로 해야 한다**
   추상화된 OCR 서비스 레이어 덕분에, 향후 트래픽 증가로 인해 자체 OCR 모델로 전환하거나 타 클라우드 API로 교체하더라도 상위 비즈니스 로직의 변경 없이 최소한의 공수로 대응할 수 있는 아키텍처 기반을 마련했습니다.
