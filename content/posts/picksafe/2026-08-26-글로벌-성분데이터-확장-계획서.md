## 1. Problem: 국내 DB의 한계와 해외 직구 시장의 폭발

최근 해외 직구 화장품(라로슈포제, 세라비, 디오디너리 등)의 소비가 급증하면서, 서비스 내 다국어 성분표 스캔 요청이 크게 늘어났습니다.

기존 시스템은 국내 공공 데이터(식약처 성분 마스터 약 2만 건)를 기반으로 고도화되어 있었으나, 글로벌 유통 제품을 분석하는 과정에서 명확한 한계에 부딪혔습니다.

1. **미등재 해외 독자 성분**: 최신 바이오 추출물이나 특허 펩타이드 등 국내 미등록 성분의 경우 OCR 스캔 후 '미분류 성분'으로 누락되는 문제.
2. **실물 라벨 표기(시노님/Alias)의 다양성**: 해외 제조사마다 라벨에 기재하는 영문/다국어 표기 방식이 달라 동일 성분임에도 매칭에 실패하는 문제.
3. **규제 기준의 파편화**: 국가마다 알레르기 유발 물질이나 배합 한도 기준이 달라, 국내 기준만으로는 글로벌 제품의 안전성을 정밀하게 검증하기 어려운 문제.

스캔 매칭률을 **99.9%**까지 끌어올리고 글로벌 규제 기준을 포괄하기 위해, 글로벌 3대 데이터 소스를 단일 파이프라인으로 통합하는 대대적인 데이터 아키텍처 확장을 결정했습니다.

## 2. Solution Architecture: 글로벌 3대 데이터 소스 결합

우리는 각기 다른 강점을 지닌 세 가지 글로벌 공공/오픈 데이터를 결합하는 정규화 파이프라인을 구축했습니다.

```mermaid
flowchart TD
    subgraph Sources["글로벌 3대 데이터 소스"]
        A["🇪🇺 유럽 EU CosIng<br/>(35,000+ 표준 성분)"]
        B["🇺🇸 미국 NIH PubChem<br/>(1억+ 화학/CAS 빅데이터)"]
        C["🌐 OpenBeautyFacts<br/>(10만+ 실물 화장품 패키지)"]
    end

    subgraph Integration["통합 정규화 파이프라인"]
        A -->|1. 표준 INCI 성분명 & 82종 규제 기준| D["통합 마스터 데이터베이스"]
        B -->|2. CAS 번호 자동 결손 보강| D
        C -->|3. 다국어 라벨 시노님(별칭) 정규화| D
    end

    D --> E["📱 실시간 스캔 판정 엔진 (< 10ms)"]
```

### 각 소스의 전략적 역할
- **🇪🇺 EU CosIng (35,000+ 종)**: 글로벌 표준 INCI(국제 화장품 성분 명명법) 기준 데이터셋과 EU SCCS 공인 82종 향료 알레르기 및 배합 금지/한도(Annex II, III) 법적 기준 확보.
- **🇺🇸 NIH PubChem (1억+ 건)**: 식약처 및 CosIng에서 결손된 CAS(Chemical Abstracts Service) 번호를 보강하고, 화학 구조 기반의 엄밀한 물질 검증 수행.
- **🌐 OpenBeautyFacts (100,000+ 건)**: 실제 해외 시판 패키지에서 수집된 브랜드별 다국어 성분 이명(Alias)을 흡수하여 OCR 인식률 극대화.

## 3. Engineering Trade-offs & Deep Dive

### 1) 마스터 스키마 설계: 멀티 테이블 vs 단일 통합 마스터

데이터 소스가 다변화되면서 **"데이터 출처별로 테이블을 분리할 것인가, 단일 테이블로 통합할 것인가?"**에 대한 고민이 있었습니다.

- **대안 A (출처별 분리 테이블)**: 식약처 테이블, CosIng 테이블, OBF 테이블을 개별 관리하고 상위 뷰(View)나 다형성 관계로 조인.
  - *단점*: 실시간 스캔 시 다중 테이블 조인 및 유니온 쿼리로 인한 RTT 증가, 제품-성분 간 외래키 복잡도 증가.
- **대안 B (단일 통합 마스터 + 출처 메타데이터 태깅) [선택]**:
  - `data_source` 메타데이터 필드를 부여하여 단일 통합 테이블로 인덱싱.
  - **결과**:
    - **초저지연 응답**: 단일 인덱스 캐시 조회를 통해 **10ms 이내**로 스캔 판정 완료 (DB 부하 0%).
    - **단순한 데이터 관계**: `Product`와 `Ingredient` 간의 관계를 단순 N:M 외래키로 유지하여 스키마 복잡도 최소화.

### 2) 다국어 번역 및 오역 방지 3단계 세이프티 파이프라인

단순 기계 번역을 해외 성분에 적용할 경우, 화학 물질명의 직역 오류로 인해 사용자에게 잘못된 안전 정보가 전달될 위험이 큽니다. 이를 방지하기 위해 **3단계 방어 전략**을 구축했습니다.

```
[해외 INCI 유입]
       │
       ▼
 [1단계: 기존 국내 공인 데이터 1:1 매핑] ─── (일치 시) ───► [기존 공인 국문명 채택 (오역률 0%)]
       │ (미일치 시)
       ▼
 [2단계: 표준 명명 규칙 기반 정규화 엔진] ──► [규칙 기반 접미사/어간 자동 변환 (Extract ➔ 추출물 등)]
       │ (규칙 외 특수 화학물)
       ▼
 [3단계: 안전 폴백 & 검토 큐 격리] ────────► [영문 원본 안전 노출 + 어드민 검토 큐 이관]
```

1. **1단계 (기존 공인 데이터 1:1 승계)**: 기존 등록된 공인 INCI와 완전 일치하는 경우 기존 표준 국문명을 100% 우선 적용.
2. **2단계 (화장품 성분 표준 명명 룰셋 기반 정규화)**: 미등록 성분 중 정형화된 패턴(`Extract` ➔ `추출물`, `Oil` ➔ `오일`, `Acid` ➔ `애씨드` 등)을 규칙 기반 엔진으로 1차 정규화.
3. **3단계 (안전 폴백 및 검토 큐)**: 복잡한 합성 화합물은 오역을 생성하지 않고 영문 원문을 안전하게 기본 노출하며, 비동기 검토 큐(Review Queue)로 이관하여 전문가 검증 후 확정.

## 4. Takeaways & Next Step

이번 글로벌 데이터 파이프라인 구축을 통해 얻은 엔지니어링 인사이트는 다음과 같습니다.

1. **데이터 양보다 중요한 것은 '정규화 전략'**: 1억 건이 넘는 빅데이터를 단순히 수집하는 것보다, CAS 번호와 INCI 코드를 기준으로 어떻게 충돌 없이 단일 식별자로 묶어내느냐가 검색 엔진의 성능을 결정합니다.
2. **Fail-Safe 번역 아키텍처**: 도메인 특화(화학/의약) 데이터의 다국어화는 LLM이나 번역 API에 전적으로 의존하기보다, **[공인 데이터 우선 -> 룰셋 정규화 -> 원문 폴백]** 구조의 결정론적 파이프라인이 훨씬 높은 신뢰도를 보장합니다.

우리는 이제 국내외 어떤 화장품 라벨을 스캔하더라도 10ms 이내에 정확한 성분 안전성 리포트를 제공할 수 있는 탄탄한 데이터 백본을 갖추게 되었습니다.
