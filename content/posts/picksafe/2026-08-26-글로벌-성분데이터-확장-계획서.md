안녕하세요, **PickSafe** 팀의 백엔드 엔지니어링 파트를 리딩하고 있는 시니어 개발자입니다.

최근 국내 뷰티 시장을 넘어 해외 직구 화장품(라로슈포제, 세라비, 디오디너리 등)을 이용하는 사용자가 급격히 늘어남에 따라, PickSafe의 성분 분석 엔진 역시 글로벌 스탠다드에 맞춰 확장해야 하는 변곡점을 맞이했습니다.

기존 식약처 기준의 2만여 개 성분 데이터를 넘어, **🇪🇺 유럽 CosIng(35,000+ 종), 🇺🇸 미국 NIH PubChem(1억+ 화학 빅데이터), 🌐 글로벌 OpenBeautyFacts(10만+ 시판 제품)**라는 거대한 글로벌 3대 데이터 소스를 단 하나의 파이프라인으로 통합하는 여정을 시작했습니다. 

이 과정에서 우리 팀이 마주한 **아키텍처적 고민, 데이터 정밀도와 성능 사이의 트레이드오프, 그리고 이를 해결한 구체적인 엔지니어링 기법**을 공유합니다.

---

## 1. 우리가 해결해야 했던 문제 (Problem)

글로벌 데이터셋 통합 작업은 단순히 '성분 테이블에 로우(Row)를 추가하는 일'이 아니었습니다. 세 가지 핵심적인 엔지니어링 장벽이 존재했습니다.

### ① 극단적인 데이터 스케일 차이와 정규화 문제
* 유럽 CosIng의 성분 정보, 미국 PubChem의 1억 건이 넘는 화학 물질 CAS(Chemical Abstracts Service) 번호, 그리고 OpenBeautyFacts의 실물 제품 라벨명은 데이터의 포맷도, 관리 주체도 완전히 달랐습니다.
* 이 파편화된 데이터들을 하나로 묶어 **성분 매칭률 99.9%**를 달성해야 했습니다.

### ② 쿼리 성능의 한계 (Latency Target: <10ms)
* 사용자가 마트나 드럭스토어에서 화장품 라벨을 카메라로 스캔했을 때, 성분 분석 결과는 **실시간(<10ms)**으로 화면에 뿌려져야 합니다.
* 데이터셋이 1억 건 수준으로 늘어난 상황에서, 매번 관계형 데이터베이스(RDB)에 조인(Join) 쿼리를 날리는 방식은 DB 부하(Neon DB CPU 쓰로틀링)를 유발하고 응답 속도를 저해할 것이 자명했습니다.

### ③ 자동 번역으로 인한 오역/직역 리스크
* 글로벌 성분명을 한국어로 자동 번역할 때, 화학 물질명이나 천연 추출물명이 어색하게 직역되거나 법적 규제 명칭과 다르게 표현될 경우, 서비스 신뢰도에 치명적인 타격을 줄 수 있었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

가장 치열하게 토론했던 부분은 **"글로벌 성분 데이터를 어떻게 적재하고 조회할 것인가?"**였습니다.

### 대안 A: 다형성 테이블 분리 방식 (Polymorphic DB Architecture)
* **구조**: 국산 성분 테이블, 유럽 CosIng 테이블, 미국 PubChem 테이블을 각각 독립적으로 두고, 스캔 엔진이 각 테이블을 병렬 조회하거나 Polymorphic Association(다형성 관계)을 맺는 방식.
* **장점**: 각 데이터 소스의 고유 스키마를 그대로 유지할 수 있어 데이터 변경에 유연함.
* **단점**: 성분 매핑 시 다중 조인이 필수적이며, 데이터 규모가 커질수록 인덱스 최적화가 어려워지고 쿼리 레이턴시가 기하급수적으로 증가함.

### 대안 B: 단일 통합 마스터 테이블 + 소스 태깅 (Single Unified Master Table) — **최종 선택**
* **구조**: 기존의 `IngredientMaster` 테이블에 `data_source` ('kfda' | 'cosing' | 'openbeauty' | 'manual') 컬럼을 추가하여, 단 하나의 거대한 마스터 테이블로 통합 관리하는 방식.

```
[IngredientMaster Table]
┌──────────────────┬─────────────┬─────────────────┬──────────────────────┐
│  ingredient_id   │    name     │   data_source   │    cas_no (PubChem)  │
├──────────────────┼─────────────┼─────────────────┼──────────────────────┤
│       1001       │   Niacin    │      kfda       │       59-67-6        │
│       1002       │  Adenosine  │     cosing      │       58-61-7        │
└──────────────────┴─────────────┴─────────────────┴──────────────────────┘
```

* **선택 이유**:
  1. **조회 속도 극대화 (<10ms)**: 단 1회의 단일 테이블 쿼리 또는 메모리 상의 정적 JSON 캐시 인덱싱만으로 국내외 성분을 즉각 판정할 수 있습니다.
  2. **외래키(FK) 관계의 단순성**: 제품-성분 간의 매핑 테이블(`ProductIngredient`)이 오직 하나의 마스터 테이블만 바라보면 되므로 스키마가 매우 깔끔해집니다.
  3. **UI/어드민 격리의 용이성**: 데이터 소스가 컬럼으로 명시되어 있어, 어드민 화면에서 필터링 및 출처 뱃지 표시가 간편합니다.

## 3. 세부 설계 및 해결 방안 (Implementation)

### ① 데이터 파이프라인 정형화 (Data Pipeline)

3대 소스를 아래와 같은 파이프라인을 통해 정규화한 뒤 통합 DB에 적재했습니다.

```mermaid
flowchart TD
    subgraph Sources["글로벌 3대 데이터 소스"]
        A["🇪🇺 유럽 EU CosIng<br/>(35,000+ 규제 기준)"]
        B["🇺🇸 미국 NIH PubChem<br/>(1억+ 화학식/CAS 번호)"]
        C["🌐 OpenBeautyFacts<br/>(10만+ 다국어 시노님)"]
    end

    subgraph Integration["통합 정규화 파이프라인"]
        A -->|1. 표준 INCI 성분명 매핑| D["PickSafe 글로벌 통합 마스터 DB"]
        B -->|2. CAS 번호 자동 보강| D
        C -->|3. 다국어 별칭(Alias) 흡수| D
    end

    D --> E["📱 10ms 이내 실시간 스캔 판정 엔진"]
```

* **EU CosIng**을 통해 글로벌 표준 성분명(INCI) 및 배합 금지/한도(Annex) 법적 기준 데이터의 뼈대를 잡고,
* **NIH PubChem** 데이터를 연동하여 식약처나 CosIng에 누락되어 있던 공식 화학 번호(CAS Number)를 백그라운드에서 자동 보강했습니다.
* **OpenBeautyFacts**의 크라우드 소싱 데이터를 분석하여, 실제 해외 화장품 용기 라벨에 인쇄되는 다양한 브랜드별 별칭(Alias, 시노님) 데이터를 추출하여 OCR 인식 사전(Dictionary)을 빌드했습니다.

### ② 번역 오역 방지를 위한 3단계 안전장치 (Translation Safeguard)

외국어 성분을 한글로 번역할 때 발생할 수 있는 오역을 방지하기 위해, 기계 번역에만 의존하지 않고 **3단계 폴백(Fallback) 전략**을 구축했습니다.

```
[번역 파이프라인]
1단계: 식약처 기등록 성명 (공인 명칭 100% 매핑)
  ▼ (매칭 실패 시)
2단계: 대한화장품협회 표준 명명 규칙 정규화 엔진 (Rule-based: "Extract" -> "추출물")
  ▼ (매칭 실패 시)
3단계: 안전한 영문 원문(INCI) 기본 노출 및 Admin 검토 큐 적재
```

1. **1단계 (식약처 데이터 매핑)**: 수집된 글로벌 성분의 INCI(국제성분명)가 기존 식약처 공인 성분(20,518건)과 일치할 경우, 국가 공인 한글명을 우선 매핑하여 오역률을 0%로 통제합니다.
2. **2단계 (룰셋 정규화)**: 매칭되지 않은 신규 성분은 대한화장품협회 가이드를 반영한 자체 규칙 엔진을 거칩니다. (예: `Extract` $\rightarrow$ `추출물`, `Oil` $\rightarrow$ `오일`, `Acid` $\rightarrow$ `애씨드` 등 접미사/접두사 표준화)
3. **3단계 (영문 원문 노출 및 휴먼 리뷰)**: 합성 화학 물질 등 룰셋으로 해결되지 않는 복잡한 성분은 어설픈 번역 대신 **영문 INCI 원문을 화면에 그대로 노출**하여 오정보 제공을 막고, 동시에 **어드민 검토 큐(Review Queue)**에 적재하여 내부 전문가가 수동 검수 후 반영하도록 설계했습니다.

## 4. 엔지니어링 교훈 및 성과 (Takeaway)

이번 글로벌 데이터베이스 확장 작업을 통해 우리 팀은 다음과 같은 값진 경험과 성과를 얻을 수 있었습니다.

1. **단순함의 승리 (Simplicity Wins)**: 
   빅데이터를 다룰 때 무조건 복잡한 분산 DB나 다형성 아키텍처를 도입하는 것이 정답은 아닙니다. 데이터의 조회 특성(Read-Heavy)을 명확히 이해하고, 단일 통합 테이블 설계와 인메모리 캐싱을 적절히 결합함으로써 시스템 복잡도를 획기적으로 낮추면서도 목표 성능을 달성할 수 있었습니다.
   
2. **방어적 데이터 엔지니어링 (Defensive Data Engineering)**: 
   외부 API나 공공 데이터를 100% 신뢰하지 않고, 누락될 수 있는 CAS 번호를 교차 검증하고(PubChem 활용), 번역 프로세스에 3단계 안전장치를 두어 데이터 품질을 방어하는 설계가 실제 프로덕션 환경에서 얼마나 중요한지 재확인했습니다.

3. **글로벌 비즈니스의 초석 마련**: 
   이번 아키텍처 개선을 통해 해외 직구 화장품의 OCR 스캔 매칭률을 **99.9%**까지 끌어올릴 수 있는 기술적 기반을 완성했으며, 이는 PickSafe가 글로벌 시장으로 빠르게 침투할 수 있는 강력한 무기가 되었습니다.

앞으로도 PickSafe 기술 블로그를 통해 대규모 데이터를 다루며 겪은 트러블슈팅과 아키텍처 혁신 이야기를 지속적으로 공유하겠습니다. 피드백이나 질문은 언제나 환영합니다!
