안녕하세요. PickSafe 개발팀입니다. 

서비스를 기획하고 운영하다 보면 항상 마주하는 딜레마가 있습니다. 바로 **"사용자에게 빠르고 간편한 경험을 제공할 것인가, 아니면 가입을 유도해 확실한 유저 데이터를 확보할 것인가?"**에 대한 고민입니다.

PickSafe는 화장품 성분 분석 및 개인화 추천 서비스를 제공합니다. 사용자가 서비스를 처음 접했을 때, 진단 기능을 이용하기 위해 강제로 회원가입이나 소셜 로그인을 요구한다면 초기 이탈률은 급격히 상승할 것입니다. 

이번 글에서는 **회원가입의 진입 장벽을 낮추면서도, 비회원 상태에서 축적된 개인화 데이터를 손실 없이 서버로 이관**하기 위해 우리가 어떤 아키텍처적 고민을 했고 왜 `localStorage` 기반의 데이터 전이 파이프라인을 선택했는지 공유해 드립니다.

---

## 1. Problem: 가입 허들과 서버 자원 낭비 사이의 트레이드오프

서비스 초기, 다음과 같은 두 가지 기술적·비즈니스적 문제가 있었습니다.

1. **높은 온보딩 이탈률**: 외국인 관광객이나 모바일 유저가 앱/웹에 진입하자마자 로그인을 요구받을 때 발생하는 심리적 허들.
2. **불필요한 서버 부하**: 만약 불특정 다수의 일회성 방문객을 위해 서버 DB에 '익명 사용자(Anonymous User)' 레코드를 생성한다면? 의미 없는 쓰레기 데이터(Garbage Data)가 급증하고, DB 커넥션 및 스토리지 리소스가 낭비됨.

즉, **"서버에 부담을 주지 않으면서 비회원에게 개인화 경험을 제공하고, 추후 가입 시 이 데이터를 어떻게 자연스럽게 흡수할 것인가?"**가 핵심 과제였습니다.

---

## 2. Alternatives & Trade-off: 왜 `localStorage`와 `Guest-Convert` 파이프라인인가?

우리는 이 문제를 해결하기 위해 세 가지 대안을 검토했습니다.

### 대안 A. 서버 세션(Session) 기반 임시 사용자 관리
* **방식**: 서버가 비회원에게 임시 세션 ID를 발급하고, 메모리나 Redis에 기피 성분/찜 목록을 임시 저장.
* **장점**: 프론트엔드 구현이 단순함.
* **단점 (Trade-off)**: 세션 만료 시 데이터 유실 위험이 크고, 일회성 방문객이 급증할 경우 Redis 메모리 비용이 선형적으로 증가함. 스케일링 측면에서 비효율적.

### 대안 B. 쿠키(Cookie)를 통한 데이터 저장
* **방식**: HTTP 쿠키에 JSON 형태로 기피 성분 데이터 저장.
* **장점**: 서버 요청 시 자동으로 데이터가 전송되므로 백엔드 연동이 쉬움.
* **단점 (Trade-off)**: 저장 용량 제한(약 4KB)이 매우 엄격함. 화장품 찜 목록이나 복잡한 성분 필터 데이터를 담기에는 용량이 턱없이 부족하며, 매 요청마다 불필요한 네트워크 트래픽(Overhead)을 유발함.

### 대안 C. 브라우저 `localStorage` + 회원 전환 시점 일괄 동기화 (Selected)
* **방식**: 비회원의 개인화 데이터(기피 성분, 찜한 상품 등)를 클라이언트의 `localStorage`에 영속적으로 저장하고, 추후 회원가입/로그인 완료 시점에 백엔드로 페이로드를 일괄 전송(`/auth/guest-convert`)하여 DB와 병합.
* **장점**: 
  - 서버 리소스를 전혀 소모하지 않음 (Cost-effective).
  - 브라우저 용량 제한(보통 5MB 이상) 내에서 충분한 개인화 데이터 보관 가능.
  - 사용자가 앱을 닫았다가 다시 와도 데이터가 유지됨 (High UX).
* **단점 (Trade-off)**: 클라이언트 단의 데이터 조작 가능성 및 브라우저 캐시 삭제 시 유실 가능성 존재. (단, 민감한 금융 정보가 아닌 개인화 추천 데이터이므로 감수 가능한 트레이드오프라 판단함)

---

## 3. Architecture & Implementation: 어떻게 구현했는가?

최종적으로 **대안 C**를 채택하여 프론트엔드와 백엔드 간의 데이터 전이 파이프라인을 구축했습니다.

1. **클라이언트 사이드 (Frontend JS)**:
   - 사용자가 로그인 없이 온보딩 설정을 마치거나 상품을 찜하면, `static/js/auth.js` 및 관련 페이지 스크립트가 `localStorage` 내 정의된 키(`guest_allergens`, `guest_saved_products`)에 데이터를 업데이트합니다.
2. **데이터 전이 파이프라인 (Guest-Convert)**:
   - 비회원이 이메일 또는 소셜 로그인을 통해 정식 회원이 되는 시점, 프론트엔드는 로컬 스토리지에 담긴 데이터를 읽어들여 백엔드의 `/auth/guest-convert` API로 전송합니다.
3. **서버 사이드 (Backend)**:
   - 백엔드는 전달받은 페이로드를 검증한 뒤, 신규 생성된 유저의 DB 레코드에 안전하게 매핑 및 병합합니다. 동기화가 성공적으로 완료되면 클라이언트의 `localStorage`를 클린업(Cleanup)하여 상태 동기화를 마칩니다.

---

## 4. Takeaway: 엔지니어링 교훈

이번 결정을 통해 다음과 같은 비즈니스적, 기술적 성과를 얻을 수 있었습니다.

* **초기 전환율(Conversion Rate) 개선**: 사용자는 로그인 압박 없이 PickSafe의 핵심 가치(빠른 성분 진단 및 추천)를 즉시 경험할 수 있게 되었으며, 이는 온보딩 이탈률 감소로 직결되었습니다.
* **인프라 비용 최적화**: 불필요한 익명 데이터 레코드를 DB에 적재하지 않음으로써 데이터베이스 I/O와 스토리지 비용을 효율적으로 아낄 수 있었습니다.
* **Client-First Thinking**: 모든 데이터를 서버가 중앙집중식으로 관리해야 한다는 고정관념에서 벗어나, 비회원 영역의 데이터는 클라이언트 자원을 적극 활용하고 인증(Authentication) 시점에만 스마트하게 동기화하는 패턴의 유효성을 검증했습니다.

PickSafe는 앞으로도 사용자에게는 매끄러운 경험을, 시스템에는 건강한 아키텍처를 제공하기 위한 기술적 고민을 이어가겠습니다. 

감사합니다.
