서비스 설계 시 엔지니어가 마주하는 흔한 대립 중 하나는 **"사용자 데이터의 서버 중앙화"와 "신규 사용자 진입 장벽 낮추기" 사이의 균형**입니다. 

화장품 개인화 진단 및 추천 서비스 PickSafe 개발 과정에서 저희 팀은 "로그인 없이 서비스를 즉시 체험할 수 있는 게스트 모드"를 도입하기로 결정했습니다. 

이번 포스팅에서는 불특정 다수의 게스트 사용자 데이터를 효율적으로 다루기 위해 **왜 서버 DB 대신 브라우저의 `localStorage`를 선택했는지**, 그리고 **추후 정식 회원가입 시 데이터를 매끄럽게 승계(Migration)하는 아키텍처**를 어떻게 구축했는지 공유합니다.

---

## 1. 문제 정의: 서비스 진입 장벽과 서버 리소스의 트레이드오프

서비스 초기에 사용자가 앱/웹에 진입하자마자 소셜 로그인이나 회원가입을 요구하면 **이탈률(Bounce Rate)이 급증**합니다. 특히 관광객이나 일회성 검색 유저의 경우 가입 절차는 거대한 장벽이 됩니다.

그러나 이탈을 막기 위해 게스트 사용자에게 개인화 기능(기피 성분 설정, 관심 상품 찜하기 등)을 제공하려면 **데이터 영속성**이 필요합니다. 

이때 백엔드 관점에서는 다음과 같은 고민이 생깁니다.

1. **임시 회원(Anonymous User) DB 저장 방식의 문제점**
   - 비회원 사용자가 방문할 때마다 DB에 `guest_id` 레코드를 생성하고 세션을 유지하면, **쓰레기 데이터(Garbage Data)**가 무기한 적재됩니다.
   - 불필요한 DB I/O가 증가하고, 정기적으로 유효기간이 지난 게스트 데이터를 삭제하는배치(Batch) 작업 등 운용 공수가 발생합니다.
2. **단순 세션 메모리 저장 방식의 문제점**
   - 브라우저를 새로고침하거나 탭을 닫으면 사용자가 열심히 설정한 기피 성분 정보나 찜한 리스트가 날아갑니다. 이는 최악의 사용자 경험(UX)을 제공합니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off Analysis)

저희 팀은 게스트 사용자의 상태 관리를 위해 두 가지 아키텍처 대안을 비교·검토했습니다.

| 항목 | 대안 A: 백엔드 임시 회원 레코드 생성 (Server-side) | 대안 B: 클라이언트 스토리지 활용 (Client-side First) |
| :--- | :--- | :--- |
| **저장 위치** | 서버 DB (RDBMS/Redis) | 브라우저 `localStorage` |
| **서버 비용/부하** | 불특정 다수의 요청으로 인한 DB 커넥션 및 용량 증대 | **0 (서버 리소스 사용 안 함)** |
| **데이터 유지력** | 세션 만료 전까지 유지 (스케줄러로 주기적 삭제 필요) | 사용자가 브라우저 캐시를 지우지 않는 한 영구 유지 |
| **회원 전환 시 처리** | DB 내 `guest_id` $\rightarrow$ `user_id` 외래키 업데이트 | **가입 시 클라이언트가 쌓아둔 데이터를 Payload로 전송 및 병합** |
| **구현 복잡도** | 서버 측 캐시 및 세션 정산 로직 필요 | 클라이언트 상태 관리 및 가입 시 데이터 전이 파이프라인 필요 |

### 🎯 선택: Client-side First 전략 (`localStorage` 활용)

저희는 **대안 B**를 최종 선택했습니다. 

1. **가입 허들 최소화**: 사용자는 앱 접속 즉시 어떠한 인증 절차 없이 카메라 스캔 및 진단 기능을 즉시 사용할 수 있습니다.
2. **서버 리소스 대폭 절감**: 실사용자로 전환되지 않는 90% 이상의 일회성 방문객 데이터가 서버 DB에 유입되는 것을 완벽히 차단했습니다.

## 3. 핵심 아키텍처: 게스트 데이터 전이 파이프라인 (Guest-to-Member Sync)

클라이언트 스토리지 방식을 선택했을 때 가장 중요한 엔지니어링 과제는 **"게스트 상태에서 저장한 데이터를 가입 후에도 잃어버리지 않게 동기화하는 것"**이었습니다.

이를 위해 다음과 같은 3단계 전이 파이프라인을 설계했습니다.

```
[게스트 모드]
사용자 활동 (기피성분 설정/찜) ──> 브라우저 localStorage에 JSON 형태로 상태 저장
                                          │
                                          ▼ (가입 및 로그인 발생)
[회원가입/로그인]
클라이언트 인증 완료 ──────────────> localStorage 감지 후 백엔드 전이 API 호출
                                          │
                                          ▼
[백엔드 병합 로직]
서버 DB ──────────────────────> 게스트 데이터 + 기존 회원 데이터 중복 제거 및 DB 저장
```

### ① 데이터 저장 및 추적 (Client-side)
비회원 상태에서의 모든 개인화 데이터(기피 성분 ID 배열, 찜한 상품 ID 배열 등)는 보안 위협이 없는 식별자 형태로 클라이언트 스토리지 키(`guest_allergens`, `guest_saved_products`)에 관리됩니다.

### ② 회원 전환 시 자동 동기화 트리거
로그인 성공 및 회원가입 이벤트 발생 시, 인증 모듈은 클라이언트 스토리지 내에 게스트 데이터가 남아있는지 확인합니다. 데이터가 존재할 경우 즉시 서버의 **데이터 통합 엔드포인트**로 해당 페이로드를 전달합니다.

### ③ 데이터 병합 및 정산 (Server-side Logic)
백엔드에서는 전달받은 페이로드를 처리할 때 다음 원칙을 따릅니다.
* **멱등성(Idempotency) 보장**: 동일한 전이 요청이 중복으로 들어와도 DB에는 유니크 제약 조건 및 Set 집합 연산을 통해 중복 데이터가 쌓이지 않도록 처리합니다.
* **성공 후 클라이언트 정리**: 동기화 완료 응답(200 OK)을 받으면 클라이언트 모듈은 `localStorage`에 남아있던 게스트 키를 안전하게 파기(`removeItem`)하여 상태 충돌을 방지합니다.

## 4. 성과 및 엔지니어링 레슨 (Takeaway)

### 📈 Business & Technical Impact

1. **초기 진입 이탈률 감소 및 전환율 향상**
   사용자가 서비스를 충분히 경험한 뒤 자연스럽게 가입하도록 유도함으로써, 가입 유저의 데이터 보존율과 서비스 만족도를 끌어올렸습니다.
2. **백엔드 인프라 효율성 극대화**
   의미 없는 임시 게스트 레코드 생성을 100% 방지하여 DB 인덱스 블로팅(Bloating)을 막고, 정기적인 데이터 청소(Cleanup) 배치 작업 부담을 제거했습니다.

### 💡 Key Takeaways

* **모든 데이터를 서버에 저장할 필요는 없다.** 보안적으로 민감하지 않으면서 일회성 성격이 강한 사용자 선호도 데이터는 클라이언트 자원을 적극적으로 활용하는 것이 비용 최적화의 핵심입니다.
* **상태 전이(State Transition) 설계의 중요성.** Client-side First 전략을 사용할 때는 '비회원 $\rightarrow$ 회원'으로 넘어가는 순간의 **데이터 병합 시점 및 멱등성 보장**이 아키텍처의 완성도를 결정짓습니다.

---

PickSafe 팀은 무조건적인 백엔드 중심 개발을 지양하고, **사용자 경험(UX)과 서버 운영 비용 최적화 사이의 접점**을 찾는 아키텍처 연구를 계속해 나가고 있습니다.
