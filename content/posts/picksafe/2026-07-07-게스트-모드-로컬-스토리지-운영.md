안녕하세요, PickSafe 팀의 시니어 백엔드 에디터입니다. 

서비스를 기획하고 개발할 때 엔지니어와 프로덕트 매니저가 늘 대립하는 지점이 있습니다. 바로 **'가입 장벽(Sign-up Friction)'과 '개인화 서비스의 가치' 사이의 저울질**입니다. 사용자가 서비스를 탐색하기도 전에 회원가입을 강제하면 이탈률이 급증하고, 반대로 가입 없이 서비스만 보여주면 사용자가 맞춤 설정한 데이터를 유지하기 어렵습니다.

오늘 포스팅에서는 PickSafe 팀이 어떻게 **클라이언트 사이드 스토리지(LocalStorage)**를 활용하여 가입 허들을 극복하고, 동시에 이탈률 감소와 서버 비용 절감이라는 두 마리 토끼를 모두 잡았는지 그 아키텍처와 엔지니어링 의사결정 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): 무분별한 DB 생성 vs 최악의 사용자 경험

외국인 관광객이나 모바일 사용자가 PickSafe 서비스를 처음 접했을 때, 가장 먼저 마주하는 화면이 '소셜 로그인'이라면 어떨까요? 귀찮은 가입 절차로 인해 서비스의 핵심 가치(카메라 스캔 및 성분 진단)를 경험하기도 전에 뒤돌아설 확률이 높습니다. 

팀은 이 이탈률을 줄이기 위해 **'선 체험, 후 가입' 구조의 게스트 모드**를 도입하기로 했습니다. 하지만 게스트 모드를 구현하면서 다음과 같은 기술적 딜레마에 부딪혔습니다.

*   **서버 사이드 임시 회원(Anonymous User) 방식의 한계:** 
    게스트가 유입될 때마다 데이터베이스에 임시 사용자 레코드를 생성하고 세션을 유지하는 방식입니다. 하지만 일회성으로 유입되고 이탈하는 수많은 게스트 데이터가 DB에 쌓이게 되면, **쓰레기 데이터 누적, DB 커넥션 낭비, 인덱스 성능 저하 및 인프라 비용 상승**이라는 치명적인 결과를 낳습니다.
*   **휘발성 상태 관리의 문제:**
    사용자가 게스트 모드로 들어와 기피 성분을 설정하고 마음에 드는 화장품을 찜(저장)해 두었습니다. 그러나 브라우저를 닫거나 새로고침을 했을 때 이 데이터가 모두 날아가 버린다면, 사용자는 심각한 불쾌감(UX 저하)을 느끼고 다시는 서비스를 찾지 않을 것입니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 서버 자원을 최소화하면서도, 게스트 상태에서 저장한 개인화 데이터(기피 성분 설정, 찜 목록 등)를 영속화하고, 최종 회원 가입 시 이 데이터를 유실 없이 온전히 보존할 수 있는 최적의 아키텍처를 고민했습니다. 세 가지 대안을 비교했습니다.

| 비교 대조군 | 대안 1: 서버 임시 테이블 저장 | 대안 2: 브라우저 SessionStorage | 대안 3: 브라우저 LocalStorage (선택) |
| :--- | :--- | :--- | :--- |
| **데이터 영속성** | 매우 높음 (DB 관리) | 낮음 (탭/브라우저 닫으면 소멸) | 높음 (브라우저 캐시 삭제 전까지 유지) |
| **서버 자원 소모** | 높음 (쓰기 작업 및 배치 삭제 필요) | 없음 | **없음 (완전한 클라이언트 자원 활용)** |
| **구현 복잡도** | 높음 (스케줄러, 가비지 컬렉션 필요) | 낮음 | **보통 (추후 로그인 시 데이터 병합 처리 필요)** |
| **UX 일관성** | 우수함 | 미흡함 (이탈 시 데이터 유실) | **우수함 (재방문 시에도 설정 유지)** |

### 선택 이유: LocalStorage와 '데이터 전이 파이프라인'
우리는 **LocalStorage**를 선택했습니다. 민감한 개인 정보(비밀번호, 개인식별정보 등)가 아닌 '기피 성분 코드'나 '제품 식별 번호'와 같은 비민감 설정 데이터 위주였기 때문에 로컬 스토리지에 저장해도 보안상의 리스크가 매우 낮다고 판단했습니다. 

단, 사용자가 최종적으로 회원가입(이메일/소셜)을 결심하는 순간, **로컬 스토리지에 쌓여 있던 게스트 데이터를 온전히 서버 DB로 마이그레이션(Merge)해 주는 파이프라인 설계**가 필요했습니다.

## 3. 최종 해결 방안 (Implementation)

설계한 전체 아키텍처 흐름은 다음과 같습니다.

```
[ 게스트 유입 ] ──> 기피성분 설정 & 찜하기 ──> LocalStorage에 비동기 저장
                                                     │
                                           (가입/로그인 버튼 클릭)
                                                     │
[ 가입 완료 단계 ] <── 클라이언트에서 로컬 데이터 취합 ──┘
         │
         ├──> POST /auth/guest-convert (Payload 전송)
         │
         └──> [Backend API]
                  ├── 1. 신규 회원 가입 처리 완료
                  ├── 2. 전달받은 게스트 데이터(기피성분/찜)를 신규 회원 ID와 매핑 및 DB 적재
                  └── 3. API 응답 성공 -> 클라이언트 LocalStorage 초기화
```

### 프론트엔드 비즈니스 로직 설계 (`static/js/auth.js` 추상화 예시)
회원 가입 성공 시점에 브라우저 로컬 스토리지에 격리되어 있던 임시 키값들을 읽어 백엔드 마이그레이션 API로 쏘아 올려주는 파이프라인을 구축했습니다.

```javascript
// 회원가입 완료 혹은 로그인 성공 시 호출되는 데이터 전이 함수
async function transferGuestDatatoServer(memberId) {
  const guestAllergens = localStorage.getItem('guest_allergens');
  const guestSavedProducts = localStorage.getItem('guest_saved_products');

  // 게스트 데이터가 없다면 동기화 과정을 생략합니다.
  if (!guestAllergens && !guestSavedProducts) return;

  try {
    const response = await fetch('/auth/guest-convert', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({
        member_id: memberId,
        allergens: guestAllergens ? JSON.parse(guestAllergens) : [],
        saved_products: guestSavedProducts ? JSON.parse(guestSavedProducts) : []
      })
    });

    if (response.ok) {
      // 서버 동기화에 성공하면 로컬 스토리지를 깨끗이 비워 중복 전송을 방지합니다.
      localStorage.removeItem('guest_allergens');
      localStorage.removeItem('guest_saved_products');
      console.log('게스트 데이터가 성공적으로 동기화되었습니다.');
    }
  } catch (error) {
    console.error('게스트 데이터 동기화 실패:', error);
    // 실패 시 사용자 시나리오에 따른 재시도 및 에러 핸들링 로직 수행
  }
}
```

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 결정을 통해 우리 팀은 비즈니스 지표와 시스템 성능 측면에서 모두 의미 있는 성과를 거둘 수 있었습니다.

1. **인프라 비용 보존 및 데이터 클렌징 비용 Zero화**
   가입하지 않고 떠나는 수많은 일회성 유저들의 가짜 데이터(Ghost Record)를 서버에 아예 기록하지 않음으로써 데이터베이스 용량을 절약했습니다. 더불어 주기적으로 유령 회원을 정리해야 하는 '배치(Batch) 삭제 프로세스'의 필요성 자체를 원천 차단했습니다.
2. **비즈니스 전환율(Conversion Rate) 대폭 향상**
   사용자는 서비스 기능을 즉시 자유롭게 체험한 후, 서비스의 가치를 확실히 느낀 시점에 자연스럽게 가입 단계로 전환됩니다. 가입 직후 이전에 자신이 설정해 둔 데이터가 그대로 유지되는 심리스(Seamless)한 이관 경험을 제공함으로써 사용자 잔존율(Retention)을 크게 높였습니다.
3. **적정 기술(Appropriate Technology)의 가치**
   무조건 모든 데이터를 데이터베이스에 실시간 동기화하는 것이 정답은 아닙니다. 데이터의 민감도, 생명 주기(Life Cycle), 비즈니스 목표를 다각도로 분석하여 **클라이언트 자원(Client-side Compute/Storage)을 적절히 하이브리드로 섞어 쓰는 아키텍처가 최적의 효율을 낸다**는 점을 다시 한번 배웠습니다.

앞으로도 PickSafe 팀은 사용자에게는 물 흐르듯 유연한 UX를 제공하면서도, 백엔드 인프라 아키텍처는 단단하고 효율적으로 유지할 수 있는 최적의 트레이드오프를 끊임없이 발굴해 나가겠습니다. 귀중한 인사이트가 되셨기를 바라며, 의견이 있으시다면 언제든 댓글로 공유해 주세요!
