서비스의 첫인상을 결정짓는 온보딩 과정에서 **'가입 장벽(Sign-up Wall)'**은 유저 이탈을 유발하는 가장 큰 원인 중 하나입니다. 특히 사용자가 서비스를 경험하기도 전에 회원가입을 강제하는 구조는 초기 전환율에 매우 부정적인 영향을 미칩니다.

PickSafe 팀은 이러한 문제를 해결하고 사용자 경험을 극대화하기 위해 **'게스트 모드(Guest Mode)'**를 도입했습니다. 이 글에서는 게스트 모드에서 생성되는 유저 개인화 데이터를 관리하기 위해 백엔드 DB 비용을 최소화하고, 가입 시점의 데이터를 매끄럽게 이관(Migration)하기 위해 선택한 클라이언트 스토리지 중심의 데이터 파이프라인 설계 프로세스와 엔지니어링 교훈을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

게스트 모드 제공의 핵심은 **"로그인 없이 즉시 핵심 기능(화장품 기피 성분 설정 및 찜하기)을 사용하게 만드는 것"**입니다. 그러나 이 과정에서 백엔드 아키텍처 관점의 명확한 난제에 직면했습니다.

1. **유령 데이터(Ghost Data)로 인한 DB 오염 및 서버 비용 상승**
   - 불특정 다수의 일회성 방문자에게 익명 PK(`anonymous_user_id`)를 부여하여 서버 DB에 저장할 경우, 서비스에 재방문하지 않는 수많은 쓰레기 레코드가 accumulate 됩니다.
   - 이는 데이터베이스 인덱스 크기를 증가시키고, 쓸데없는 쓰기(Write) IOPS를 유발하며, 주기적인 배치 삭제(Cron Job) 시스템 구축이라는 추가적인 운영 공수를 발생시킵니다.
2. **데이터 유실 없는 매끄러운 가입 전환 UX(User Experience) 필요**
   - 유저가 게스트 상태에서 열심히 설정해 둔 '기피 성분 목록'이나 '찜한 상품'이 로그인/회원가입을 완료했다고 해서 사라진다면 심각한 UX 상실감을 줍니다.
   - 비회원 시점의 데이터와 새롭게 생성될 정식 계정 데이터 간의 완벽한 데이터 병합(Merge) 메커니즘이 필요했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off Analysis)

이 문제를 해결하기 위해 크게 세 가지 아키텍처 대안을 검토했습니다.

| 항목 | Option A: 서버 세션/임시 DB 저장 | Option B: 순수 인메모리(SessionState) 저장 | Option C: 클라이언트 로컬 스토리지 + 가입 시 동기화 (최종 선택) |
| :--- | :--- | :--- | :--- |
| **저장 위치** | 백엔드 RDBMS / Redis | 클라이언트 메모리 (JS Variable) | 브라우저 `localStorage` |
| **영속성** | 브라우저를 닫아도 유지됨 | 브라우저 새로고침/창 닫기 시 즉시 유실 | 브라우저를 닫거나 재방문해도 영구 유지됨 |
| **서버 부하** | 높음 (임시 유저 세션 및 쓰기 트래픽 다량 발생) | 없음 | **없음 (가입 전환 시점에만 1회 호출)** |
| **구현 복잡도** | 중간 (배치 청소 로직 필요) | 낮음 | **중간 (가입 시 데이터 병합 API 및 중복 제거 로직 필요)** |
| **UX 영향** | 매우 높음 | 매우 낮음 (새로고침 시 데이터 삭제) | **매우 높음 (재방문 시에도 설정 유지)** |

### 선택: Option C (Client-Side Storage & Lazily Synced Pipeline)

우리는 **Option C**를 최종 선택했습니다. 
정식 회원이 되기 전까지는 서버 자원을 단 `1byte`도 소모하지 않는 '지연 동기화(Lazy Sync)' 전략을 취하기로 했습니다.

- **Non-blocking Onboarding:** 사용자가 서비스를 탐색하는 동안 백엔드 네트워크 트래픽 및 DB 커넥션 비용이 `0`에 수렴합니다.
- **Persistence:** 브라우저를 닫고 다음 날 다시 방문해도 유저가 선택한 기피 성분 설정이 브라우저 로컬 스토리지(`localStorage`)에 보존됩니다.

## 3. Architecture & Implementation: 데이터 전환 파이프라인

게스트 모드에서 정식 회원으로 전환되는 데이터 흐름은 아래와 같이 단방향 비동기 이관 파이프라인으로 구현되었습니다.

```
[게스트 상태]
User Action -> Browser LocalStorage (e.g., guest_allergens, guest_saved_products)
                               │
[회원가입 / 로그인 시점]        │ 
Submit Payload ───────────────┴──> POST /auth/guest-convert (API)
                                              │
                                              ▼
                                 [Backend Data Processing]
                                 1. Validate Payload Sanitization
                                 2. Merge & Deduplicate with User DB
                                 3. Transaction Commit
                                              │
                                              ▼
                                 [Success Response: 200 OK]
                                 - Clear Client LocalStorage
```

### 핵심 구현 포인트

1. **클라이언트 엣지 저장소 활용**
   - 로그인하지 않은 사용자의 모든 개인화 데이터 액션(기피 성분 체크, 상품 찜하기)은 로컬 스토리지의 구조화된 JSON 형태로 관리됩니다.

2. **단일 원자적 전환 엔드포인트 (`POST /auth/guest-convert`)**
   - 사용자가 이메일 가입 또는 OAuth 소셜 로그인을 완료하는 성공적인 시점에, 로컬 스토리지에 쌓여 있던 JSON 페이로드를 가입 요청 트랜잭션과 함께 백엔드로 일괄 전송합니다.

3. **백엔드 데이터 병합 및 멱등성(Idempotency) 보장**
   - 이미 동일한 성분이나 상품이 사용자의 계정에 존재하는 경우를 대비해 집합(Set) 연산 기반의 중복 제거 및 `UPSERT` 로직을 수행합니다.
   - 데이터 이관 트랜잭션이 성공적으로 수행 완료(`200 OK`)된 경우에만 클라이언트의 로컬 스토리지 키를 안전하게 비워냅니다(`clear`).

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 설계를 통해 얻은 핵심적인 엔지니어링 교훈은 다음과 같습니다.

### ① 모든 상태를 서버가 가질 필요는 없다 (Edge-First Thinking)
초기 기획 단계에서는 '모든 데이터의 중앙화'를 습관적으로 고려하기 쉽습니다. 하지만 비즈니스 임팩트(회원 전환율)를 해치지 않으면서도 백엔드 부하를 획기적으로 줄이기 위해서는 **"데이터 저장의 주체와 시점을 클라이언트 엣지로 최대한 밀어내는 컴퓨팅 사고"**가 유효하다는 것을 증명했습니다.

### ② 데이터 무결성은 백엔드 검증에서 시작된다
클라이언트 스토리지(`localStorage`)는 사용자가 임의로 조작할 수 있는 엔드포인트입니다. 따라서 전환 API 파이프라인 수신 시, 페이로드 데이터 타입에 대한 엄격한 스키마 검증(Sanitization)과 인젝션 방지 로직을 추가하여 클라이언트 측 데이터 오염이 DB로 전파되는 것을 방지했습니다.

### ③ UX와 시스템 정합성의 트레이드오프 극복
유저에게 가입 허들 없는 쾌적한 UX를 제공하는 동시에, 데이터베이스 정합성을 유지하고 쓰레기 데이터 쌓임을 방지하는 고성능의 린(Lean)한 백엔드 시스템을 구축할 수 있었습니다.
