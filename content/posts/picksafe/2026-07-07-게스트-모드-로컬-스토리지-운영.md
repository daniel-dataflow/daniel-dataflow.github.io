서비스의 첫인상을 결정하는 온보딩 과정에서 **'필수 회원가입'**만큼 강력한 이탈 장벽은 없습니다. 특히 모바일 환경이나 가벼운 탐색을 원하는 유저들에게 가입 절차는 큰 귀찮음으로 다가옵니다.

우리 팀이 개발 중인 성분 분석 및 추천 서비스 **PickSafe** 역시 동일한 고민을 안고 있었습니다. 유저가 서비스를 즉시 경험할 수 있도록 '게스트 모드'를 제공하고 싶었지만, 이 과정에서 발생하는 개인화 데이터(기피 성분 설정, 찜한 화장품 등)를 어떻게 관리할 것인가에 대한 아키텍처적 고민이 시작되었습니다.

가입 허들은 최소화하면서, 서버 자원을 효율적으로 방어하고, 동시에 매끄러운 유저 경험(UX)을 제공하기 위해 우리 팀이 선택한 **클라이언트 사이드 데이터 전환 파이프라인 구축기**를 공유합니다.

---

## 1. 문제 정의: 게스트 데이터의 딜레마

게스트 모드를 도입하기로 결정했을 때, 기술적으로 해결해야 할 핵심 과제는 **"로그인하지 않은 사용자의 설정을 어떻게 유지하고, 가입 시 어떻게 안전하게 이관할 것인가?"**였습니다.

처음에는 다음과 같은 두 가지 비즈니스 요구사항과 기술적 제약이 충돌했습니다.

*   **비즈니스 요구사항:** 유저가 비회원 상태에서 기피 성분을 등록하고 화장품을 찜했다면, 가입 후에도 이 데이터가 그대로 유지되어야 한다. (심리스한 UX 제공)
*   **기술적 제약:** 로그인하지 않은 사용자의 식별자가 불분명한 상태에서 이 데이터를 무작정 서버 데이터베이스(DB)에 저장할 경우, 다음과 같은 부작용이 예상된다.
    *   일회성 방문객으로 인한 **쓰레기 데이터(Zombie Row)의 급격한 누적**
    *   임시 사용자 식별을 위한 **DB 커넥션 낭비 및 인덱스 성능 저하**
    *   주기적으로 임시 데이터를 삭제해야 하는 **배치 작업(Garbage Collection) 관리 비용 발생**

즉, **UX를 극대화하면서도 서버와 DB에 부담을 주지 않는 영속성 전략**이 필요했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 아키텍처 관점에서 세 가지 대안을 테이블 위에 올려두고 비교했습니다.

| 비교 항목 | 대안 1: 임시 유저(Anonymous) 서버 저장 | 대안 2: 세션 쿠키(Session Cookie) | 대안 3: 브라우저 로컬 스토리지 (선택) |
| :--- | :--- | :--- | :--- |
| **저장 위치** | 서버 DB | 클라이언트 (쿠키) | 클라이언트 (로컬 스토리지) |
| **서버 자원 소모** | 매우 높음 (임시 Row 생성 및 배치 삭제 필요) | 낮음 | **없음 (완전한 클라이언트 자원 활용)** |
| **네트워크 비용** | 보통 (API 호출 발생) | 높음 (매 요청마다 쿠키 헤더에 실려 전송됨) | **낮음 (필요한 시점에만 단발성 API 전송)** |
| **데이터 용량 제한** | 무제한 | 매우 제한적 (약 4KB) | **비교적 여유로움 (약 5MB)** |
| **구현 복잡도** | 높음 (임시-정식 유저 간 매핑 테이블 필요) | 낮음 | **보통 (가입 시점 전송 로직 필요)** |

### 선택의 이유: 왜 로컬 스토리지인가?
우리는 **대안 3(로컬 스토리지)**을 최종 선택했습니다. 

기피 성분 데이터와 찜한 상품 리스트는 보안이 극도로 요구되는 민감 정보(패스워드, 결제 정보 등)가 아닌 일종의 **'선호도 설정 데이터'**입니다. 따라서 상대적으로 보안 위협(XSS 등)으로부터 방어책만 마련해 둔다면 클라이언트에 저장하는 것이 가장 효율적이었습니다. 

무엇보다 **가입하지 않은 유저의 데이터는 서버가 1바이트도 책임지지 않는다**는 원칙을 세움으로써, 불필요한 인프라 비용을 원천 차단할 수 있었습니다.

## 3. 최종 해결책: 'Guest-to-Member' 데이터 전환 파이프라인

우리가 구축한 파이프라인의 핵심은 **"클라이언트가 임시 보관하고, 가입 시점에 일괄 이관(Batch Sync)한다"**입니다.

### 아키텍처 흐름도

```
[게스트 상태]
유저 작업 (기피 성분 설정 / 찜하기)
       │
       ▼
브라우저 로컬 스토리지에 즉시 반영 (Key: guest_allergens, guest_saved_products)

       │
[가입/로그인 발생 시]
       ▼
Frontend가 로컬 스토리지 데이터 적재 여부 확인
       │
       ▼ (적재되어 있다면)
가입 요청 시 페이로드에 로컬 데이터 포함하여 전송 (POST /auth/guest-convert)
       │
       ▼
Backend에서 신규 가입 유저 ID와 전달받은 게스트 데이터를 병합(Merge) 후 DB 저장
       │
       ▼ (성공 응답 수신)
클라이언트 로컬 스토리지 내 게스트 키값 삭제 (Cleanup)
```

### 구현 디테일 (Engineering Details)

보안 관점을 준수하며 개념적으로 정제한 핵심 흐름은 다음과 같습니다.

1. **클라이언트 사이드 영속성 관리:**
   유저가 온보딩 화면이나 상세 페이지에서 액션을 취할 때마다, 자바스크립트는 브라우저의 `localStorage`를 업데이트합니다.
   ```javascript
   // 클라이언트 임시 저장 예시 (개념 코드)
   function saveGuestAllergens(allergens) {
     localStorage.setItem('guest_allergens', JSON.stringify(allergens));
   }
   ```

2. **조건부 동기화 트리거:**
   유저가 소셜 가입 또는 이메일 가입 폼을 제출하는 시점에, 프론트엔드는 로컬 스토리지를 조회합니다. 데이터가 존재할 경우, 가입 API 호출 직후(또는 동시에) 전환 API(`POST /auth/guest-convert`)를 호출합니다.

3. **멱등성(Idempotency) 및 병합 비즈니스 로직:**
   백엔드에서는 단순히 덮어쓰는 것이 아니라, 혹시나 존재할지 모르는 기존 유저 데이터와 게스트 데이터를 **병합(Merge)**하고 중복을 제거(De-duplicate)하는 로직을 수행하여 데이터 정합성을 유지합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 결정을 통해 우리 팀은 단순한 기능 구현을 넘어, 비용 효율적이고 확장성 있는 시스템을 설계하는 귀중한 경험을 얻었습니다.

1. **서버의 책임 최소화 (Zero-SaaS Cost for Guests):**
   만약 가입하지 않고 이탈한 90%의 게스트 데이터를 모두 DB에 저장했다면, 매월 수천만 건의 무의미한 Writes와 백업 비용이 발생했을 것입니다. 이를 클라이언트에 위임함으로써 **인프라 비용을 획기적으로 절감**했습니다.
2. **트레이드오프의 명확한 인식:**
   로컬 스토리지는 유저가 브라우저 캐시를 모두 비우거나 시크릿 모드를 사용할 경우 데이터가 유실된다는 한계가 있습니다. 하지만 우리는 '가입하지 않은 게스트의 데이터 유실 위험'보다 '서버 리소스 방어 및 빠른 온보딩'의 가치가 훨씬 크다고 판단했고, 이 예측은 비즈니스 지표로 증명되었습니다.
3. **UX와 DX(개발자 경험)의 조화:**
   단순한 로컬 스토리지 헬퍼 함수(`auth.js`)와 동기화 API 하나만으로, 복잡한 임시 세션 관리나 DB Batch 삭제 스크립트 없이도 완벽히 매끄러운 유저 전환 플로우를 완성했습니다.

**마치며**

"모든 데이터를 서버에 저장해야 한다"는 고정관념에서 벗어나, 브라우저가 가진 스토리지 자원을 적극적으로 활용할 때 비로소 가볍고 빠른 아키텍처가 탄생할 수 있음을 배웠습니다. 앞으로도 PickSafe 팀은 유저에게는 막힘없는 경험을, 시스템에는 안정성과 효율성을 제공하는 엔지니어링을 지향하겠습니다.
