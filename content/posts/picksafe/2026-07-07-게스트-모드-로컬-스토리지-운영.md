서비스의 첫인상을 결정짓는 '온보딩(Onboarding)' 단계에서 사용자에게 가입을 강제하는 것만큼 강력한 이탈 요인은 없습니다. 특히 모바일 웹 환경이나 빠른 정보 탐색을 원하는 사용자들에게는 "일단 써보게 하는 것"이 서비스 전환율의 핵심 지표가 됩니다.

최근 저희 PickSafe 팀은 **"로그인 없이 서비스를 즉시 체험하되, 이때 생성된 개인화 데이터(기피 성분 설정, 찜한 상품 등)를 가입 시점에 어떻게 안전하고 매끄럽게 보존할 것인가?"**에 대한 아키텍처적 고민을 마주했습니다. 

이번 포스팅에서는 임시 세션 데이터의 데이터베이스(DB) 적재로 인한 비용 문제를 해결하고, 클라이언트 자원을 활용해 매끄러운 UX와 서버 비용 절감을 모두 챙긴 **'게스트 모드 로컬 스토리지 활용 및 데이터 전이(Convert) 파이프라인'** 설계 여정을 공유합니다.

---

## 1. 문제 정의: 가입 허들 최소화와 '유령 데이터'의 트레이드 오프

처음 기획 단계에서 마주한 요구사항은 명확했습니다.
> **"로그인을 하지 않은 게스트(Guest) 상태에서도 사용자가 기피 성분을 설정하고 상품을 찜할 수 있어야 하며, 회원 가입을 하면 이 데이터가 그대로 유지되어야 한다."**

이 요구사항을 기술적으로 해결하기 위해 처음 떠올린 방식은 전통적인 **'서버 메모리/임시 테이블 활용'**이었습니다. 비회원 사용자가 접속하면 서버에서 세션 ID나 가상 사용자(Anonymous User) ID를 발급하고, 이를 DB에 기록하는 방식이죠.

하지만 이 방식은 즉각적인 엔지니어링 우려를 낳았습니다.

* **서버 리소스 낭비 및 DB 비대화 (DB Bloat):** 불특정 다수의 일회성 방문객이나 봇(Bot)이 발생시키는 데이터까지 모두 데이터베이스에 적재한다면, 쓰기 트래픽(Write IOPS)이 불필요하게 증가합니다. 결국 가입하지 않고 이탈한 '유령 회원'들의 쓰레기 데이터를 주기적으로 정리(Batch Cleanup)해야 하는 추가 공수도 발생합니다.
* **불필요한 세션 관리 비용:** 게스트 유저의 상태를 서버 세션으로 동기화하기 위한 Redis 비용이나 세션 클러스터링 관리 오버헤드가 발생합니다.

**우리의 목표는 명확했습니다.**
1. 사용자에게 로그인 압박이 없는 **제로 허들 온보딩**을 제공할 것.
2. 미가입 이탈 유저로 인한 **서버 비용과 DB 쓰기 부담을 '0'**에 가깝게 수렴시킬 것.
3. 가입 결정을 내린 유저의 데이터는 **단 1건의 유실도 없이 완벽하게 서버 DB로 마이그레이션**할 것.

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 크게 두 가지 아키텍처 모델을 두고 비교 분석했습니다.

### Alternative A: 서버 사이드 임시 유저(Anonymous User) 스키마 관리
* **개념:** 접속 즉시 임시 UUID를 발급하여 DB의 `users` 테이블에 `is_anonymous=True` 형태로 레코드를 생성하고 관계형 테이블에 데이터를 적재합니다. 가입 시 정식 계정으로 플래그를 변경합니다.
* **장점:** 클라이언트 구현이 단순해지며, 사용자가 브라우저를 닫거나 쿠키를 지워도 임시 ID만 쿠키에 남아있다면 데이터가 보존됩니다.
* **단점:** 대규모 트래픽 유입 시 미가입 이탈자의 데이터가 DB 커넥션을 점유하고 저장 공간을 낭비합니다. 개인정보 보호 관점에서도 불필요하게 미식별 데이터를 서버에 장기간 보관해야 하는 찝찝함이 남습니다.

### Alternative B: 브라우저 로컬 스토리지(`localStorage`) 기반의 지연 동기화 (선택)
* **개념:** 게스트 상태에서는 모든 설정 및 저장 행위를 브라우저의 `localStorage`에만 기록합니다. 이후 사용자가 가입 폼을 제출하는 시점에, 로컬 스토리지의 데이터를 API 페이로드에 실어 서버로 전송하고 서버 DB에 일괄 적재(Ingest) 및 병합(Merge)합니다.
* **장점:** 
  * 비회원 유저가 아무리 많은 데이터를 생성해도 서버 측 인프라 비용과 DB 부하는 **'0'**입니다.
  * 서버 스키마를 깨끗하게 유지할 수 있습니다.
  * 오프라인 환경에서도 클라이언트 사이드에서 즉각적인 반응(Instant UX)을 제공할 수 있습니다.
* **단점:** 클라이언트 사이드에서 상태 관리 로직(State Management)과 마이그레이션 예외 처리를 정교하게 작성해야 합니다.

```
[비회원 상태] 
사용자 행동 -> 로컬 스토리지 즉시 기록 (서버 통신 무)

[회원가입/로그인 시점]
로컬 스토리지 데이터 적재 -> 회원가입 API와 함께 페이로드 전송 -> 서버에서 기존 회원 데이터와 병합 -> 로컬 스토리지 비우기
```

**결정:** 비용 효율성과 아키텍처의 깔끔함을 고려하여 **Alternative B**를 선택했습니다. 클라이언트 자원을 최대한 활용하여 서버 비용을 아끼고, 비즈니스 가치가 검증된(즉 가입을 결정한) 데이터만 DB에 진입시키는 장벽을 구축하기로 했습니다.

## 3. 구현 아키텍처 및 예외 처리 전략

구현 과정에서 가장 중요하게 다룬 부분은 **'클라이언트 데이터의 신뢰성 검증'**과 **'병합(Merge) 충돌 해결'**이었습니다.

### 1) 데이터 구조화 및 마스킹된 API 명세
로컬 스토리지에는 단순 문자열이 아닌, 구조화된 JSON 데이터(`guest_allergens`, `guest_saved_products`)를 적재했습니다. 이후 회원가입 성공 시 호출되는 데이터 이관 엔드포인트(`POST /api/v1/auth/guest-convert`)를 설계했습니다.

```json
// POST /api/v1/auth/guest-convert (Payload 예시)
{
  "guest_allergens": [102, 305, 401], // 사용자가 선택한 기피 성분 ID 배열
  "guest_saved_products": ["prod_abc123", "prod_xyz789"] // 찜한 상품 ID 목록
}
```

### 2) 서버 사이드 멱등성 및 병합(Merge) 전략
가입 시점에 발생할 수 있는 특이 케이스들을 촘촘하게 방어해야 했습니다. 예를 들어, **이미 기존에 가입된 계정으로 소셜 로그인을 수행했는데, 현재 브라우저 로컬 스토리지에도 게스트 데이터가 있는 경우**입니다.

서버는 단순히 데이터를 덮어쓰는(Overwrite) 것이 아니라, **합집합(Union)** 연산을 수행하도록 비즈니스 로직을 설계했습니다.

* **기피 성분:** `기존 회원 DB 데이터 ∪ 로컬 스토리지 데이터` (중복 제거된 ID 목록 생성)
* **찜한 상품:** 동일하게 중복을 제거한 유니크 배열로 업데이트 후 DB 적재.

### 3) 클라이언트 트랜잭션 흐름 보장
데이터 유실을 막기 위해 클라이언트에서의 상태 전환 순서를 엄격히 제어했습니다.

1. 사용자가 가입/로그인을 완료하면 즉시 마이그레이션 API(`/guest-convert`)를 트리거합니다.
2. 서버로부터 성공(`200 OK`) 응답을 받은 **이후에만** 로컬 스토리지의 `guest_` 관련 키를 삭제(`removeItem`)합니다.
3. 만약 API 요청이 실패하면 로컬 데이터를 유지하여, 다음 세션 진입 시 재시도하거나 사용자에게 정중히 재동기화를 안내할 수 있는 백업 장치를 마련했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 작업을 통해 저희 팀은 기술적으로나 서비스적으로 큰 교훈을 얻을 수 있었습니다.

1. **인프라 비용은 아키텍처 설계 단계에서 아낄 수 있다:** 
   모든 사용자 데이터를 서버에 저장해야 한다는 고정관념에서 벗어나, 클라이언트의 스토리지 자원을 똑똑하게 활용함으로써 DB의 I/O 비용과 스토리지 비용을 획기적으로 줄였습니다. 서비스 규모가 커질수록 이러한 '지연 쓰기(Lazy Write)' 및 클라이언트 분산 처리 방식은 진가를 발휘합니다.

2. **UX 향상이 곧 비즈니스 지표의 향상이다:**
   가입 절차를 뒤로 미루고 자유로운 탐색 기회를 제공한 결과, 초기 이탈률이 유의미하게 감소했습니다. 가입 전환 시 기존 데이터를 잃지 않고 매끄럽게 계정에 녹여내는 '심리스(Seamless)'한 유저 경험은 서비스의 잔존율(Retention)에도 긍정적인 영향을 주었습니다.

3. **경계면(Boundary)에서의 방어적 코딩의 중요성:**
   클라이언트 환경은 언제나 변조되거나 비정상적인 데이터가 들어올 수 있는 '신뢰할 수 없는 영역'입니다. 로컬 스토리지의 데이터를 서버 DB로 이관할 때, 유효성 검증(Schema Validation) 및 가공 작업을 철저히 수행함으로써 시스템의 안정성을 보장할 수 있었습니다.

---

앞으로도 PickSafe 팀은 제한된 자원 속에서 최적의 비용으로 최고의 사용자 경험을 이끌어낼 수 있는 실용적인 아키텍처를 고민해 나갈 것입니다. 비슷한 고민을 하고 계신 백엔드/프론트엔드 엔지니어 분들께 이번 포스팅이 작은 영감이 되었기를 바랍니다.
