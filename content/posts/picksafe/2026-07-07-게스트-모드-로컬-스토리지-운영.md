안녕하세요, **PickSafe** 백엔드/프론트엔드 엔지니어링 팀입니다. 

서비스를 개발하며 가장 마주하기 까다로운 딜레마 중 하나는 **"사용자가 서비스의 핵심 가치를 빠르게 경험하게 할 것인가, 아니면 이른 시점에 회원가입을 유도하여 데이터를 확보할 것인가?"**라는 질문입니다. 

이번 포스팅에서는 PickSafe가 사용자 이탈률을 최소화하기 위해 **게스트 모드(Guest Mode)**를 도입하고, 비회원의 개인화 데이터(기피 성분, 찜한 상품 등)를 서버 DB에 무리 없이 통합하기 위해 어떤 아키텍처적 고민과 트레이드오프를 거쳤는지 공유해 드립니다.

---

## 1. Problem: 가입 허들과 서버 리소스 낭비 사이의 딜레마

PickSafe는 화장품 성분 분석과 진단을 핵심 기능으로 제공합니다. 초기 기획 단계에서 우리는 다음과 같은 사용자 행동 패턴을 분석했습니다.
- 신규 방문자는 복잡한 회원가입 절차(소셜 로그인, 약관 동의 등)를 마주하면 높은 확률로 이탈합니다.
- 특히 즉각적인 진단이 필요한 상황에서 로그인을 강제하는 것은 서비스 진입 장벽을 높이는 주원인입니다.

그렇다고 해서 **불특정 다수의 일회성 방문객 데이터를 서버 세션이나 데이터베이스에 무작정 저장(Anonymous User 패턴)**하는 것도 문제였습니다.
- 서비스 특성상 방문 후 이탈하는 비율이 높은데, 이들의 임시 데이터를 서버 DB에 적재하면 **'쓰레기 데이터(Garbage Data)'가 급증**합니다.
- 이는 불필요한 스토리지 비용뿐만 아니라, DB 커넥션 자원을 낭비하게 만드는 요인이 됩니다.

> **핵심 과제:** 
> *서버 자원을 낭비하지 않으면서도, 비회원 상태에서 사용자가 입력한 소중한 개인화 데이터를 유실 없이 보존하고, 추후 회원 전환 시 매끄럽게 연동할 수 있는가?*

---

## 2. Trade-off & Architecture: 왜 `localStorage`와 데이터 전이 파이프라인인가?

이 문제를 해결하기 위해 우리는 클라이언트 사이드 스토리지와 서버 API를 연계하는 **'Client-First Data Migration 파이프라인'**을 설계했습니다.

### 대안 비교
1. **서버 세션(Session) 활용**
   * *장점:* 서버가 데이터를 온전히 통제함.
   * *단점:* Redis나 DB에 임시 세션이 폭증하여 인프라 비용 증가 및 확장성 저하.
2. **쿠키(Cookie) 활용**
   * *장점:* 서버로 자동 전송되어 구현이 비교적 단순함.
   * *단점:* 용량 제한(4KB)이 엄격하고, 성분 리스트와 찜 목록 등 대용량 구조화 데이터를 담기에는 부적절함.
3. **브라우저 로컬 스토리지(`localStorage`) 활용 (선택)**
   * *장점:* 서버 리소스를 전혀 소모하지 않음. 최대 5MB 이상의 넉넉한 용량으로 클라이언트 단에서 자유로운 구조화 데이터(JSON) 관리 가능.
   * *단점:* 클라이언트 유저가 브라우저 캐시를 임의로 삭제할 경우 데이터 유실 가능성 존재. (단, 게스트 모드의 성격상 이는 허용 가능한 트레이드오프로 판단)

### 최종 아키텍처 흐름
1. **비회원 탐색 및 상태 저장:** 
   로그인 없이 서비스를 이용하는 동안, 프론트엔드(`static/js/auth.js` 등)는 사용자의 기피 성분 및 찜한 화장품 리스트를 브라우저의 `localStorage`(`guest_allergens`, `guest_saved_products`)에 영속적으로 저장합니다.
2. **전환(Conversion) 시점 트리거:** 
   사용자가 서비스의 가치를 느끼고 이메일 또는 소셜 가입을 진행하거나 로그인에 성공하는 시점에 프론트엔드는 로컬 스토리지의 데이터를 읽어옵니다.
3. **데이터 이관 API 호출:** 
   백엔드의 전용 엔드포인트(예: `/auth/guest-convert`)로 로컬 스토리지의 페이로드를 일괄 전송합니다. 서버는 트랜잭션 내에서 해당 데이터를 정식 회원의 프로필 및 찜 목록 DB에 안전하게 병합(Merge)합니다.
4. **스토리지 클린업:** 
   데이터 동기화가 성공적으로 완료되면 브라우저의 게스트 관련 로컬 스토리지를 안전하게 비워(Clear) 상태를 동기화합니다.

## 3. Takeaway: 엔지니어링 교훈

이번 게스트 모드 데이터 파이프라인 구축을 통해 얻은 교훈은 명확합니다.

* **인프라 비용 최적화와 UX는 상충되지 않는다:** 서버에 불필요한 임시 데이터를 남기지 않으면서도 클라이언트 자원을 현명하게 활용함으로써, 서버 리소스를 아끼고 가입 전환율(Conversion Rate)을 동시에 끌어올릴 수 있었습니다.
* **상태 관리의 경계 설정:** 모든 데이터를 서버가 쥐고 있어야 한다는 강박관계를 버리고, "비회원 단계의 임시 데이터는 클라이언트에게 책임을 위임하고, 인증된 정식 데이터만 서버가 관리한다"는 명확한 경계(Boundary)를 세운 것이 아키텍처의 단순성과 확장성을 지켜주었습니다.

PickSafe는 앞으로도 사용자에게는 매끄러운 경험을, 엔지니어에게는 확장 가능한 구조를 제공하기 위한 기술적 고민을 지속해 나가겠습니다. 읽어주셔서 감사합니다!
