안전한 성분 분석 플랫폼 **PickSafe**는 사용자가 업로드한 이미지나 텍스트를 분석하여 유해 성분을 감지하고 맞춤형 정보를 제공합니다. 

글로벌 사용자 유입이 늘어나고 데이터양이 방대해짐에 따라, 저희 개발 팀은 두 가지 핵심 엔지니어링 과제에 직면했습니다. **첫째, 외부 API 의존성 및 OCR 노이즈로 인한 스캔 지연(최대 3분)과 오매칭 현상.** **둘째, 글로벌 컴플라이언스(다국어 약관 동의)와 2만 건이 넘는 원천 데이터의 안정적인 동기화.**

이 글에서는 비즈니스 로직의 복잡도를 제어하면서도, **스캔 속도를 3분에서 1초로 단축**시키고 글로벌 서비스로서의 확장성을 확보한 기술적 여정과 엔지니어링 의사결정 과정을 공유합니다.

## 1. [성능 및 정확도 개선] 실시간 외부 API Bottleneck 해결과 오발 매칭 차단

### 문제 정의 (Problem): 3분의 대기 시간과 '가공소금'의 저주
사용자가 성분표 이미지를 스캔할 때, 시스템은 로컬 DB 및 캐시에 없는 성분에 대해 외부 공공 API(식약처 성분 데이터베이스)를 실시간으로 조회하여 매칭을 시도했습니다. 

여기서 두 가지 치명적인 문제가 발생했습니다.
1. **API 호출 지연 및 커넥션 고갈**: OCR(광학 문자 인식) 과정에서 읽어 들인 노이즈 문자열(예: 깨진 텍스트, 특수문자 등)이 대량으로 외부 API 조회 요청으로 이어졌습니다. 이로 인해 단 한 번의 스캔 요청에 수십 번의 외부 API 호출이 발생하며, 사용자 응답 시간이 최대 3분까지 늘어나는 장애 수준의 지연이 발생했습니다.
2. **잘못된 매칭 (False Positive)**: 외부 API의 검색 알고리즘이 유사 검색 방식을 지원하다 보니, OCR 노이즈 문자열에 대해 엉뚱한 첫 번째 검색 결과(예: '가공소금' 등)를 반환했습니다. 이 결과가 그대로 DB에 캐싱되어, 향후 다른 사용자에게도 잘못된 성분 정보가 노출되는 정밀성 훼손 문제가 발생했습니다.

### 기술적 고민과 대안 비교 (Trade-off)
우리는 실시간 조회의 가치를 살리면서도 시스템을 보호하기 위해 두 가지 선택지를 고민했습니다.

*   **Option A: 모든 외부 API 조회를 비동기 큐(Celery 등)로 넘기고 사용자는 폴링(Polling)하게 한다.**
    *   *장점*: 웹 서버의 동기적 블로킹을 막을 수 있습니다.
    *   *단점*: 실시간성이 핵심인 스캔 화면에서 사용자 경험(UX)이 극도로 저하되며, 인프라 복잡도가 증가합니다.
*   **Option B (선택): 정확 일치 검증(Exact Match) 도입 및 단일 요청당 API 호출 상한선(Max Rate Limit) 제어**
    *   *장점*: 인프라를 늘리지 않고도 실시간성을 유지하며, 잘못된 데이터 적재를 원천 차단합니다.
    *   *단점*: 아주 드물게 존재할 수 있는 '유사한 이름의 성분'에 대한 자동 매칭 기회를 놓칠 수 있으나, 이는 데이터 정밀도와 시스템 안정성을 위해 타협할 수 있는 영역이었습니다.

### 해결책 (Solution)

저희는 **Option B**를 채택하고, 엔진 구조를 다음과 같이 재설계했습니다.

```
[스캔 요청] ──> [1. 메모리/로컬 DB 캐시 조회] ──(Hit)──> [즉시 반환]
                 │
               (Miss)
                 ▼
        [2. 외부 API 실시간 조회]
                 │  ※ 상한선 설정: 단일 스캔당 최대 5회 제한
                 ▼
        [3. 정확 일치 검증 (Exact Match Validation)]
                 │  ※ 공백 제거, 대소문자 통일 등 정규화 비교
                 ├─ (일치) ─> [로컬 DB 캐시 적재] ─> [정상 매칭 반환]
                 └─ (불일치) ─> [노이즈 처리 및 매칭 생략]
```

1.  **정확 일치 검증 (Exact Match Validation)**
    외부 API가 반환한 성분명(국문/영문)과 입력받은 스캔 문자열을 정규화(공백 제거, 특수문자 정제, 대소문자 통일)하여 **완벽히 일치하는 경우에만** 유효한 성분으로 판정하고 로컬 DB에 캐싱했습니다. 이로써 '가공소금'과 같은 오발 매칭을 원천 차단했습니다.
2.  **스캔당 호출 상한선 제어 (Max 5 Limit)**
    하나의 스캔 트랜잭션 내에서 발생하는 실시간 외부 API 호출 횟수를 **최대 5회**로 강제 제한했습니다. 노이즈가 아무리 많은 이미지가 들어와도 최대 5번만 외부 통신을 수행하므로 비정상적인 지연을 예방할 수 있습니다.
3.  **지능적 캐시 레이어 분리**
    검증을 통과한 유효 성분은 로컬 DB 저장과 동시에 메모리 캐시에 동적 합류시켜, 동일 성분에 대해서는 두 번째 요청부터 API 호출 없이 밀리초(ms) 단위로 즉각 응답하도록 설계했습니다.

### 엔지니어링 성과 (Takeaway)
*   **성능 혁신**: 평균 스캔 처리 속도가 **3분에서 1초 미만**으로 단축되었습니다. (**99.4% 성능 개선**)
*   **데이터 신뢰성 확보**: 잘못 매칭된 성분 정보 유출 가능성을 제로(0)로 만들었습니다.
*   **교훈**: 외부 종속성(External Dependency)이 있는 시스템을 설계할 때는 항상 **최악의 시나리오(Worst-case Scenario)**를 대비한 방어적 코드(Defensive Coding)와 레이트 리미팅(Rate Limiting)이 필수적임을 재확인했습니다.

## 2. [데이터 파이프라인] 2만 건의 식약처 데이터 동기화 및 관찰 가능성(Observability) 확보

### 문제 정의 (Problem): 백그라운드 데이터 수집의 불투명성과 정제 실패
실시간 호출을 제한한 만큼, 사전에 공공 성분 데이터(약 21,833개)를 로컬 DB에 안정적으로 동기화(Seeding)해두는 작업이 매우 중요해졌습니다. 그러나 대용량 데이터를 동기화하는 과정에서 다음과 같은 백오피스 한계에 부딪혔습니다.
1.  **동기화 실패 데이터의 유실**: CAS(Chemical Abstracts Service) 번호 포맷 오류나 일시적인 DB 네트워크 단절로 인해 누락되는 성분 데이터들을 추적하기 어려웠습니다.
2.  **스케줄러 관리의 부재**: 동기화 배치가 언제 실행되는지, 현재 정상적으로 진행 중인지 모니터링할 수 있는 대시보드가 없었습니다.

### 해결책 (Solution): 비동기 스케줄러와 Dead Letter Queue 패턴 도입

우리는 시스템 부하를 최소화하면서 데이터 신뢰성을 보장하기 위해 별도의 무거운 인프라(Airflow 등)를 도입하는 대신, **FastAPI 비동기 태스크**와 **RDBMS 기반의 간단하고 견고한 데이터 파이프라인**을 구축했습니다.

```python
# FastAPI startup 이벤트를 활용한 백그라운드 스케줄러 루프 예시
@app.on_event("startup")
async def start_scheduler():
    # 메인 이벤트를 방해하지 않도록 독립적인 백그라운드 Task로 구동
    asyncio.create_task(seeding_scheduler_loop())
```

1.  **실패 데이터 관리를 위한 전용 스키마 (`ingredient_seed_errors`)**
    동기화 과정에서 검증 오류나 예외가 발생한 성분은 버리지 않고 일종의 **Dead Letter Queue(DLQ)** 역할을 하는 에러 이력 테이블에 저장합니다.
2.  **어드민 식약처 수집 관리(Seeding) 대시보드 구축**
    *   **실시간 모니터링 터미널**: Web API를 통해 수집 로그 스트리밍을 어드민 대시보드에 5초 주기로 업데이트하여, 수집 진행 상태를 웹 터미널 스타일로 실시간 관찰할 수 있게 했습니다.
    *   **수동 교정 및 재적재 (Human-in-the-loop)**: 포맷 오류(예: 잘못된 CAS 번호)로 실패한 데이터를 관리자가 어드민 화면에서 직접 수정하여 즉시 재적재할 수 있는 UI를 제공했습니다.

### 엔지니어링 성과 (Takeaway)
*   **비용 효율적인 모니터링**: 추가 인프라 비용 없이 FastAPI 내장 기능과 간단한 RDBMS 설계만으로 엔터프라이즈급의 데이터 정제 및 모니터링 도구를 구현했습니다.
*   **데이터 무결성**: 2만 여 개의 공공 성분 사전을 한 건의 누락 없이 깨끗하게 정제하여 프로덕션에 반영할 수 있는 프로세스를 구축했습니다.

## 3. [글로벌 컴플라이언스] 다국어 약관 동의 체인 및 유저 상태 전환 고도화

### 문제 정의 (Problem): 국가별 규제 대응과 부드러운 UX의 공존
글로벌 시장 진출을 위해 다양한 국가의 사용자를 수용해야 했습니다. 이용약관(TOS), 개인정보처리방침, 민감 정보 동의 등 법적 컴플라이언스 영역은 서비스 대상 국가의 언어로 정확하게 제공되어야 하며, 누락 시 심각한 법적 리스크를 초래합니다. 

또한, 비회원(Guest) 상태에서 스캔 서비스를 이용하다가 소셜 로그인을 통해 회원으로 전환(Guest-to-Member)할 때, 이전의 동의 이력이 유실되지 않고 안전하게 연동되어야 하는 유저 상태 관리의 난제가 있었습니다.

### 해결책 (Solution): 다국어 폴백 체인(Fallback Chain)과 상태 보존 아키텍처

```
[클라이언트 요청 언어] ──(없음)──> [영어 (en)] ──(없음)──> [한국어 (ko)]
```

1.  **다국어 폴백 체인 구축**
    사용자가 요청한 로케일(Locale) 언어에 맞는 약관 문서가 서버에 존재하지 않을 경우, 시스템이 다운되거나 빈 화면을 보여주는 대신, `요청 언어 ─> 영어(en) ─> 한국어(ko)` 순으로 순차적으로 대체 문서를 탐색하는 **폴백 체인**을 구현했습니다. 이를 통해 어떤 글로벌 환경에서도 약관이 안정적으로 노출되도록 보장했습니다.
2.  **온보딩 규제 가드독(Guarddog) 패턴**
    앱의 핵심 기능(스캔 등)에 접근하기 전, 미들웨어 레이어에서 사용자의 필수 약관(`terms_of_service`, `privacy_policy`) 동의 여부를 세션 기반으로 검증하고, 누락된 경우 온보딩 페이지로 강제 리다이렉션(Redirection)하는 안전장치를 마련했습니다.
3.  **게스트-회원 전환 시 동의 이력 영속화**
    익명 세션(Guest) 단계에서 수집한 동의 데이터를 소셜 가입/로그인(`guest-convert`) API 호출 시 회원 테이블로 트랜잭션 안전하게(Transactional) 마이그레이션하도록 구현했습니다.

### 엔지니어링 성과 (Takeaway)
*   **글로벌 컴플라이언스 충족**: 다국어 지원의 안정성을 높여 법적 분쟁 소지를 사전에 차단했습니다.
*   **전환율 상승**: 비회원에게 스캔 경험을 먼저 제공한 뒤 자연스럽게 회원으로 전환시키는 흐름을 설계하여, 동의 이력 유실 없이 매끄러운(Seamless) 사용자 경험을 제공했습니다.

## 맺으며: 비즈니스 가치를 극대화하는 실용주의 엔지니어링

이번 PickSafe 아키텍처 고도화 작업을 통해 저희 팀이 얻은 가장 큰 배움은 **"무조건 화려하고 복잡한 기술 스택을 도입하는 것이 정답은 아니다"**라는 점입니다.

*   외부 API 병목을 해결하기 위해 메시지 큐를 무작정 도입하는 대신, **정확 매칭 검증과 호출 상한선 제한**이라는 비즈니스 룰 정의를 통해 인프라 추가 비용 없이 성능을 **180배(3분 -> 1초)** 개선했습니다.
*   데이터 유실과 파이프라인의 불투명성은 **실패 기록 테이블(DLQ 패턴)과 어드민 내 모니터링 도구**를 직접 구현함으로써 영리하게 해결했습니다.

기술은 결국 비즈니스 문제를 해결하고 사용자에게 가치를 전달하기 위한 도구입니다. PickSafe 개발 팀은 앞으로도 이처럼 견고하고 실용적인 엔지니어링을 바탕으로 글로벌 사용자들에게 가장 안전하고 빠른 성분 분석 경험을 제공할 것입니다.
