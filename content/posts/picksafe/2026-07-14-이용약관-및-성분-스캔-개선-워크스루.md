글로벌 성분 안전 스캔 서비스 **PickSafe**는 유저가 영수증이나 성분표 이미지를 촬영하면, OCR로 추출된 텍스트를 바탕으로 식약처 공공 데이터 및 자체 데이터베이스를 교차 검증하여 성분의 위험성과 다국어 정보를 실시간으로 제공합니다.

하지만 데이터베이스에 등록되지 않은 신규 성분이 대량으로 들어오거나 OCR 인식 과정에서 **노이즈(Noise) 문자열**이 발생할 때, 시스템이 실시간 외부 API 조회 늪에 빠져 **응답 지연시간(Latency)이 최대 3분까지 치솟는 문제**와 **유사 검색 결과로 인한 잘못된 성분 매칭(False Positive)** 현상이 발생했습니다.

본 포스팅에서는 이 문제를 해결하기 위해 적용한 **정확도 우선 매칭 전략, 실시간 API 쿼리 상한선 제한(Throttling), 그리고 비동기 백그라운드 데이터 수집 시스템 설계 과정**과 엔지니어링 레슨을 공유합니다.

## 1. Problem: 노이즈 문자열의 폭주와 3분의 기다림

### 이슈 현상
사용자가 업로드한 영수증 및 제품 표지 사진에는 유효한 성분명 외에도 특수문자, 상호명, 깨진 글자 등 다양한 **OCR 노이즈 문자열**이 포함됩니다. 기존 시스템은 로컬 DB/캐시에서 찾지 못한 문자열이 발생하면 식약처 공공 API로 실시간 동기(Synchronous) 요청을 보냈습니다.

이 구조는 두 가지 치명적인 문제가 있었습니다.

1. **지연시간 폭증 (Latency Spikes):** 노이즈 문자열이 30~50개 이상 포함된 이미지가 들어올 경우, 무수한 실시간 API 호출이 누적되며 **스캔 응답 시간이 3분(180초)**까지 지연되었습니다.
2. **잘못된 매칭 (Data Contamination):** 외부 API의 오타 보정 및 유사 검색 기능 때문에, meaningless한 노이즈 문자열에 대해 API 검색 결과 1순위 항목(예: '가공소금' 등)이 무조건 매칭되는 현상이 일어났습니다. 이로 인해 오염된 데이터가 로컬 DB에 캐싱되는 악순환이 발생했습니다.

```
[기존 파이프라인]
이미지 스캔 ➔ OCR 텍스트 추출 ➔ 미매칭 문자열 N개 발견 ➔ 식약처 API N회 실시간 호출 (동기)
                                                         ↳ 3분 소요 & 노이즈가 '가공소금'으로 엉뚱하게 캐싱됨
```

## 2. Technical Decision & Trade-offs

문제 해결을 위해 우리는 핵심 핫패스(Hot-path) 영역에서 **"완벽한 실시간 탐색" 대신 "속도와 정교함의 밸런스"**를 선택하는 아키텍처 재설계를 진행했습니다.

### Trade-off 1: 유사 매칭 vs 정확 일치 검증 (Exact Match Validation)
* **대안 A (유사도 기반 매칭 유지):** 외부 API의 유사 검색 알고리즘을 신뢰한다. 
  * *Pros:* 오탈자가 있는 성분도 어떻게든 찾아낼 확률이 있음.
  * *Cons:* 노이즈 문자열이 엉뚱한 성분으로 잘못 매칭되어 서비스의 데이터 신뢰성을 치명적으로 훼손함.
* **대안 B (정규화 후 정확 일치 검증 - 선택):** 공백 제거 및 대소문자를 통일(Normalization)한 후, 정확히 일치하는(Exact Match) 성분만 캐싱하고 유효 성분으로 판정한다.
  * *Pros:* 잘못된 성분이 매칭되는 False Positive를 100% 원천 차단.
  * *Cons:* API 결과와 미세하게 다른 오탈자는 놓칠 수 있음 (이는 추후 데이터 정제 파이프라인으로 이관).

### Trade-off 2: 무제한 실시간 조회 vs 조회 상한선 제어 (Throttling)
* **대안 A (무제한 조회):** 사용자가 요청한 모든 텍스트를 끝까지 외부 API에서 조회.
  * *Cons:* 3분에 달하는 지연시간 재발.
* **대안 B (스캔당 최대 5회 API 호출 제한 - 선택):** 1회 스캔 요청 시 캐시 미스가 난 항목에 대한 외부 API 조회를 **최대 5회**로 강제 제한.
  * *Pros:* 노이즈가 대량 포함되어 있어도 응답 시간을 1~2초 이내로 보장.
  * *Cons:* 한 번의 스캔에서 5개 초과의 신규 성분이 등장할 경우 일부 성분은 즉시 매칭되지 않을 수 있음.

## 3. Solution: 고성능 파이프라인 및 백그라운드 데이터 파이프라인 구축

### 1) Exact Match & Max-5 Throttling 구현
핵심 로직 내부에서 식약처 API 조회를 제어하고, 반환된 데이터를 정규화 비교하도록 개선했습니다.

```python
# ingredient_matcher.py (가상화 및 단순화된 예시 코드)

MAX_EXTERNAL_API_CALLS = 5

async def match_ingredients(scanned_tokens: list[str]) -> list[IngredientResult]:
    matched_results = []
    unmatched_tokens = []
    
    # 1. 로컬 캐시/DB 조회 (Fast-path)
    for token in scanned_tokens:
        ingredient = await local_cache.get(token)
        if ingredient:
            matched_results.append(ingredient)
        else:
            unmatched_tokens.append(token)
            
    # 2. 캐시 미스 항목에 대한 실시간 API 조회 제한 (Max 5 Limit)
    api_call_count = 0
    for token in unmatched_tokens:
        if api_call_count >= MAX_EXTERNAL_API_CALLS:
            break  # Latency 방어를 위한 즉시 이탈
            
        api_result = await external_api.fetch(token)
        api_call_count += 1
        
        if api_result:
            # 문자열 정규화 후 Exact Match 검증
            normalized_input = normalize_string(token)
            normalized_target = normalize_string(api_result.name)
            
            if normalized_input == normalized_target:
                # 검증된 성분만 DB 저장 및 메모리 캐시 동적 합류
                await db.save_and_cache(api_result)
                matched_results.append(api_result)

    return matched_results
```

### 2) 백그라운드 데이터 동기화 & Self-Healing 어드민 파이프라인
실시간 API 호출을 제한한 만큼, **로컬 DB의 사전 성분 데이터(21,000+ 건)**가 충실해야 합니다. 이를 위해 비동기 스케줄러와 어드민 모니터링 시스템을 구축했습니다.

* **FastAPI Background Scheduler:** 서비스 기동 시 비동기 루프(`seeding_scheduler_loop`)를 구동하여 주기적으로 공공 성분 데이터를 동기화합니다.
* **실시간 로그 모니터링 터미널:** 어드민 대시보드에서 5초 주기로 데이터 적재 로그를 실시간 모니터링할 수 있도록 구현했습니다.
* **Self-Healing (오류 수동 교정 파이프라인):** CAS 번호 포맷 불량이나 DB 예외로 수집에 실패한 데이터는 `seed_errors` 테이블에 격리(Quarantine)되며, 관리자가 어드민 UI에서 데이터(CAS 등)를 교정 후 **"재적재"** 클릭 시 즉시 정상 반영되고 오류 리스트에서 제거되는 안전장치를 설계했습니다.

```
[개선된 파이프라인]
이미지 스캔 ➔ OCR 텍스트 추출 ➔ 로컬 DB/캐시 고속 조회 (1~2초)
                                  ↓ (캐시 미스 시)
                           최대 5회 제한 API 조회 & Exact Match 검증
                                  ↓ 
                       [비동기 백그라운드 루프]
                       주기적 21,000+ 공공 데이터 자동 배치 동기화 
                       + 어드민 예외 격리/재적재 UI
```

### 3) 글로벌 서비스를 위한 약관(TOS) 동의 체인 & 다국어 폴백
성분 매칭 고도화와 더불어, 글로벌 스케일업을 위해 약관 동의 시스템 및 다국어 처리 구조도 함께 개편했습니다.

* **동의 순서의 엄격성:** 법적 리스크 최소화를 위해 `이용약관 -> 개인정보처리방침 -> 민감정보 동의` 순으로 유저 동의 흐름을 강제했습니다.
* **다국어 폴백 체인 (Fallback Chain):** 지원되지 않는 언어로 요청이 들어올 경우 `요청 언어` $\rightarrow$ `영어(en)` $\rightarrow$ `한국어(ko)` 순으로 복귀(Fallback)하여 어떠한 환경에서도 사용자에게 안전하게 기본 약관(영어)이 노출되도록 구성했습니다.

## 4. Key Takeaways & Results

### 엔지니어링 성과 (Metrics)
* **스캔 응답 시간 99.4% 단축:** 최대 **3분(180초)**에 달하던 스캔 지연 시간을 **1초 내외**로 대폭 단축했습니다.
* **데이터 신뢰성 확보:** 노이즈 텍스트가 '가공소금' 등으로 엉뚱하게 매칭되던 False Positive 오류를 **0건**으로 방지했습니다.
* **운영 효율성 극대화:** 21,000여 개의 전체 성분 데이터를 백그라운드로 안전하게 동기화하고, 에러 데이터의 수동 재적재 UI를 통해 데이터 파이프라인의 자가 치유(Self-Healing) 능력을 확보했습니다.

### 엔지니어링 레슨 (Takeaway)
1. **사용자 요청 처리 경로(Hot-path)에서 외부 API 동기 호출을 최소화하라:** 외부 시스템의 응답 속도와 데이터 품질은 제어 불가능한 변수입니다. 핫패스에서는 Caching과 Throttling을 극단적으로 적용하고, 데이터 수집은 백그라운드 파이프라인으로 분리해야 합니다.
2. **"Fail-Fast"가 "Slow-Success"보다 낫다:** 모든 OCR 텍스트를 끝까지 찾아내려다 3분을 대기하게 만드는 것보다, 정확히 매칭되는 것만 빠르게 보여주고 1초 만에 응답을 주는 것이 훨씬 뛰어난 사용자 경험(UX)을 제공합니다.
3. **데이터 파이프라인에는 반드시 격리(Quarantine) 및 재시도 메커니즘이 필요하다:** 비동기 배치 수집 시 발생하는 포맷 오류나 예외를 그냥 버리지 않고, 어드민 인터페이스를 통해 수정 및 재적재할 수 있는 구조를 만드는 것이 장기적인 시스템 운용 비용을 획기적으로 줄여줍니다.
