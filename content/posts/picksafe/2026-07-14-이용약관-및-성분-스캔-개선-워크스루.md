안전한 성분 분석 플랫폼 **PickSafe**는 이미지 OCR을 통해 성분을 스캔하고, 식약처 등 공공 데이터베이스와 실시간 매칭하여 유해 성분 및 민감 반응 성분을 필터링해 주는 서비스를 제공하고 있습니다. 

서비스의 핵심 가치인 '빠르고 정확한 성분 판별'을 달성하는 과정에서, 저희 팀은 **OCR 노이즈 데이터로 인한 실시간 API 지연(최대 3분)**과 **유사 검색 오류로 인한 데이터 오발 매칭**이라는 심각한 병목 현상에 직면했습니다.

본 포스팅에서는 이 문제를 어떤 엔지니어링 의사결정을 통해 극복했는지, 그리고 **2만여 건의 공공 데이터를 안정적으로 동기화하는 백그라운드 파이프라인과 글로벌 서비스 확장을 위한 약관 아키텍처**를 어떻게 구축했는지 공유합니다.

---

## 1. 3분간의 병목: 실시간 외부 API 호출 구조의 딜레마

### 🔴 문제 정의 (Problem)
초기 스캔 아키텍처는 로컬 DB 및 캐시에 성분 데이터가 없을 경우, **실시간으로 식약처 외부 API를 호출하여 조회**하는 구조였습니다. 

그러나 영수증이나 성분표 이미지의 OCR 특성상 **인식 오류로 인한 노이즈 문자열**이 대량 발생했습니다. 이로 인해 다음과 같은 심각한 문제가 드러났습니다.

1. **지연 시간 폭증 (Latency Waterfall)**: 1회 스캔 요청 시 포함된 수십 개의 노이즈 문자열에 대해 연속적인 외부 API 통신이 발생하여, **스캔 응답 시간이 최대 3분(180초)까지 지연**되었습니다.
2. **유사 매칭의 부작용 (False Positives)**: 식약처 API의 키워드 검색 특성상, 의미 없는 노이즈 문자열이 검색 결과 상위 항목인 '가공소금' 등 무관한 성분으로 잘못 맵핑되어 DB에 오염 데이터로 캐싱되었습니다.

```
[기존 흐름] 
OCR 스캔 -> 로컬 DB 미매칭 -> 노이즈 문자열 20개 각각 외부 API 호출 (Waterfall) -> 지연시간 3분 발생 & 오발 매칭 발생
```

---

### ⚖️ 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 엔지니어링 팀은 두 가지 대안을 놓고 고민했습니다.

*   **대안 A: 완전 비동기 처리 (Background Event-driven)**
    *   스캔 시점에는 오직 로컬 DB에 존재하는 성분만 매칭하고, 미매칭 데이터는 MQ(Message Queue)로 던져 백그라운드로 처리.
    *   *장점*: 스캔 응답 속도가 비약적으로 빠름 (수백 ms 내 반환).
    *   *단점*: 사용자가 '방금 스캔한 신규 유효 성분'의 결과를 실시간으로 확인하지 못해 UX 단절 발생.
*   **대안 B: 동기 제약 추가 + 엄격한 검증 및 호출 한도 제한 (Adopted)**
    *   실시간성을 보장하되, 1회 요청당 API 호출 횟수를 엄격히 제한하고 **정확 일치(Exact Match)** 검증을 도입.
    *   *장점*: 실시간 UX 유지, 서비스 예측 가능성 증대, 오발 매칭 원천 차단.
    *   *단점*: 호출 한도 초과 시 신규 미매칭 성분의 실시간 반영이 다음 주기로 이월됨.

저희는 **사용자 경험(실시간성)과 시스템 안정성 사이의 균형**을 맞추기 위해 **[대안 B]**를 선택하고 안전장치(Safety Guardrails)를 재설계했습니다.

---

### 🛠️ 엔지니어링 구현 (Implementation)

#### 1) 정확 일치 검증 (Exact Match Validation)
외부 API 조회가 성공하더라도 반환된 성분명과 스캔 문자열을 정규화(공백 제거, 대소문자 통일)한 후 **100% 일치하는 경우에만 유효 매치로 판정하고 로컬 DB 및 메모리 캐시에 동적으로 동기화**하도록 변경했습니다. 

```python
# [개선된 매칭 로직 예시 - 식약처 반환 데이터 정규화 검증]
def validate_exact_match(scanned_text: str, api_response: dict) -> bool:
    normalized_scan = normalize_string(scanned_text)
    candidate_kr = normalize_string(api_response.get("name_kr", ""))
    candidate_en = normalize_string(api_response.get("name_en", ""))
    
    # 유사 매칭을 배제하고 정확 일치 건만 캐싱 및 매치 인정
    return normalized_scan in (candidate_kr, candidate_en)
```

#### 2) 스캔당 호출 상한선 제어 (Max Limit Guardrail)
1회 스캔 Context 내에서 외부 API 호출 횟수를 **최대 5회로 강제 제한**했습니다. 5회를 초과하는 미매칭 노이즈 문자열은 즉시 패스하여 응답 시간을 보장합니다.

```
[개선된 흐름]
OCR 스캔 -> 로컬 DB/캐시 우선 매칭 -> 미매칭 항목 발생 -> [최대 5회 제한] 외부 API 조회 -> 정규화 Exact Match 검증 -> 통과 시 로컬 DB 캐싱 -> 1초 내 고속 응답
```

---

### 📊 성과 및 결과 (Impact)

*   **스캔 응답 시간**: **3분(180초) $\rightarrow$ 1~2초 내로 단축 (약 99% 성능 개선)**
*   **데이터 정확도**: 노이즈 문자열이 무관한 성분으로 오발 맵핑되는 현상 **0건 달성**
*   **서버 리소스 보호**: 외부 API 장애 또는 Rate Limit으로 인한 내부 서비스 Cascading Failure 방지

## 2. 21,833개 데이터의 안정적 동기화: 백그라운드 파이프라인 & Observability

외부 API 호출을 제한함에 따라, **공공 데이터베이스의 21,833개 전체 성분 데이터를 로컬 DB에 미리 동기화(Seeding)해 두는 백그라운드 파이프라인**의 중요성이 커졌습니다.

### 🏗️ 백그라운드 스케줄러 & 회복 탄력성(Resilience) 설계

Web 서비스의 API 요청-응답 루프를 방해하지 않도록 **FastAPI Lifespan 이벤트 기반의 비동기 백그라운드 루프 스케줄러**를 구축했습니다.

```python
# [FastAPI App Lifecycle 내 스케줄러 구동]
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 서비스 기동 시 백그라운드 루프 비동기 실행
    scheduler_task = asyncio.create_counts_task(run_background_seeding_scheduler())
    yield
    scheduler_task.cancel()
```

#### 1) 실패 이력 추적 및 Human-in-the-Loop 예외 처리
공공 데이터 수집 중 CAS 번호 포맷 불량이나 데이터 누락 등으로 발생하는 DB 예외를 서비스 셧다운 없이 처리하기 위해 **전용 에러 추적 테이블(`ingredient_seed_errors`)**을 신설했습니다.

수집 실패 데이터는 별도로 격리 저장되며, 관리자는 어드민 대시보드에서 정제되지 않은 데이터(예: 잘못된 CAS 번호)를 **수동 교정 후 클릭 한 번으로 재적재(Retry)**할 수 있는 파이프라인을 완성했습니다.

```
[데이터 파이프라인 구조]
공공 데이터 수집 -> 파싱/검증 -> [정상] 로컬 DB 적재 & 메모리 캐시 갱신
                                -> [에러] Error Tracking DB 적재 -> Admin UI 표출 -> 관리자 교정 후 재적재
```

#### 2) 실시간 로그 모니터링 터미널 UI
어드민 페이지에서 2만 여 건의 백그라운드 수집 상태를 한눈에 파악할 수 있도록 **5초 주기 Polling 기반의 실시간 텍스트 로그 스트리밍 터미널 및 수집 현황 Dashboard**를 구축하여 운영 가시성(Observability)을 확보했습니다.

## 3. 글로벌 서비스를 위한 다국어 약관 및 동의 상태 관리

서비스 확장에 발맞추어 **이용약관(TOS), 개인정보처리방침, 민감정보 동의 흐름**의 결합도를 낮추고 다국어 대응력을 높였습니다.

### 🔐 다국어 폴백 체인 (Fallback Chain)
다국어 데이터가 부재할 경우 서비스가 중단되지 않고 안전하게 기본 언어로 디그레이드(Degradation)되는 폴백 아키텍처를 설계했습니다.

*   **Fallback Chain Order**: `요청 언어 (Requested)` $\rightarrow$ `영어 (en)` $\rightarrow$ `한국어 (ko)`

```python
def get_translated_document(doc_type: str, target_lang: str) -> str:
    # 1. 요청 언어 조회 -> 2. 실패 시 영어(en) 조회 -> 3. 실패 시 한국어(ko) 조회
    return load_doc(doc_type, target_lang) \
        or load_doc(doc_type, "en") \
        or load_doc(doc_type, "ko")
```

### 👤 게스트-회원 전환 시 상태 원자성(Atomicity) 보장
비회원(Guest) 상태에서 수집된 약관 동의 이력이 소셜 로그인/회원가입(`/guest-convert`)으로 이어질 때, 동의 상태가 누락되지 않도록 **트랜잭션 내 이관 연동**을 구현했습니다. 이를 통해 온보딩(`/onboarding`) 시 법적 필수 동의 항목 누락을 방지하고 컴플라이언스 리스크를 해소했습니다.

## 💡 Engineering Takeaways (핵심 교훈)

1. **외부 의존성(Third-party API)은 절대 신뢰하지 않는다**: 외부 API를 실시간 요청 루프에 직접 결합하면 외부의 지연과 오류가 서비스 전체로 전파됩니다. **Exact Match 검증과 Limit 제어**라는 안전장치가 시스템의 비상사태를 막아줍니다.
2. **실패를 전제로 한 시스템 설계(Design for Failure)**: 2만 개가 넘는 대용량 배치 수집 시 에러를 단순히 로그로 남기고 버리는 것이 아니라, **실패 전용 스키마와 관리자 재시도(Retry) UI**를 제공함으로써 데이터의 완전성을 달성할 수 있었습니다.
3. **사용자 경험과 시스템 성능의 Trade-off**: 100% 완전한 비동기 전환만이 답은 아닙니다. 핵심 사용자 경험을 해치지 않는 선에서 **호출 상한선(Rate Limit)을 설정하는 타협점**이 엔지니어링의 묘미임을 재확인했습니다.
