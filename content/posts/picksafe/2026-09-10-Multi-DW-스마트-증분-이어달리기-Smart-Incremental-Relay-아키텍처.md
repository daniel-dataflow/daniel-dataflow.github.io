서버리스 데이터베이스 환경을 운용하다 보면 컴퓨팅 쿼터나 비용 제약으로 인해 여러 데이터웨어하우스(DW) 인스턴스를 능동적으로 전환(Failover & Failback)해야 하는 상황을 마주합니다. 

PickSafe 코어 아키텍처 팀은 최근 다중 DW 인스턴스 간 자동 전환 과정에서 **"작업 중이던 대규모 스테이징 데이터가 사라진 것처럼 보이는 불일치 현상"**을 해결했습니다. 단순한 데이터 복제를 넘어, 비용 제약이 엄격한 환경에서 양쪽 DB의 작업 상태를 온전히 보존하는 **'스마트 증분 릴레이(Smart Incremental Relay)'** 아키텍처를 구축한 과정을 공유합니다.

---

## 1. 문제 상황: 완벽했던 페일오버, 그러나 사라진 4만 건의 데이터?

글로벌 원료 및 제품 데이터를 수집·가공하는 파이프라인은 매일 수만 건의 비정형 데이터를 처리합니다. 

어느 날 메인 DB(DW1)의 월간 컴퓨팅 한도 도달로 인해 대기 DB(DW2)로의 **핫스왑 핫페일오버(Hot-Failover)**가 정상 트리거되었고, DW2 활성 상태에서 수만 건의 글로벌 공공 원료 데이터 수집이 성공적으로 진행되었습니다. 이후 월간 쿼터 리셋 주기에 맞춰 메인 DB(DW1)로의 **자동 복구(Auto-Failback)** 역시 매끄럽게 수행되었습니다.

그러나 복구 직후 어드민 대시보드에 접속한 운영진은 당혹스러운 상황을 마주했습니다.

> **"DW2에서 수집했던 4만여 건의 글로벌 데이터가 DW1으로 돌아오니 0건으로 보입니다. 데이터가 유실된 건가요?"**

실제 데이터가 삭제된 것은 아니었습니다. DW2의 스테이징 테이블에는 데이터가 고스란히 남아 있었지만, 활성 커넥션이 DW1으로 전환되면서 DW1의 과거 시점 데이터만 조회되었던 것입니다.

```
[DW1 활성 상태] ──── (한도 도달) ────► [DW2 활성 상태] ──── (월초 리셋) ────► [DW1 복귀]
- 식약처 데이터 수집                  - 글로벌 성분 4.1만 건 수집              - 글로벌 성분 0건 표시!
                                    - CAS 번호 검증 작업 진행               (작업 내역 단절)
```

## 2. 근본 원인 분석: "스테이징(Staging)은 휘발성 버퍼"라는 잘못된 가정

문제를 파고들자 초기 아키텍처 설계 당시의 **도메인 라이프사이클에 대한 잘못된 가정**이 드러났습니다.

1. **휘발성 큐라는 오판**:
   초기 설계에서는 스테이징 테이블을 *'수집 즉시 가공되어 마스터로 적재되고 비워지는 1회성 임시 버퍼'*로 정의했습니다. 따라서 DB 스위칭 시 일별 통계 요약 데이터만 동기화하고 스테이징 큐는 동기화 대상에서 제외했습니다.
2. **실제 업무 프로세스와의 괴리**:
   실제 화장품/화학 성분 가공 파이프라인은 1차 수집 후 즉시 완료되지 않습니다. 수집된 데이터는 스테이징 공간에 머무르며 **수일~수주에 걸쳐 식별자 정규화, 음차 매칭, 규제/알레르기 정보 보강 등 다단계 비동기 가공**을 거칩니다.
3. **단절된 바통 터치(Handover Gap)**:
   인스턴스가 `DW1 ➔ DW2 ➔ DW1`으로 전환될 때, 이전 인스턴스에서 진행 중이던 파이프라인의 진척 상태가 인계되지 않아 작업의 연속성이 깨졌습니다.

## 3. 기술적 대안 비교 및 트레이드오프

이 문제를 해결하기 위해 두 가지 접근 방식을 검토했습니다.

| 비교 항목 | 대안 A: 전체 삭제 후 덮어쓰기 (Full Wipe & Clone) | 대안 B: 스마트 증분 이어달리기 (Smart Incremental Relay) |
| :--- | :--- | :--- |
| **방식** | 타깃 DB 스테이징을 `TRUNCATE` 후 소스 DB 전체 적재 | 고유 키 기준으로 차분만 감지하여 Merge/Upsert |
| **자원 소모량** | 전환 시마다 수십 MB I/O 발생 ➔ **무료 티어 쿼터 급속 고갈** | 변경된 레코드/필드만 전송 (수백 KB 미만, 99% 절감) |
| **정합성 위험** | **Split-Brain 데이터 유실** (양쪽 작업분 중 한쪽 영구 삭제) | **무손실 합집합(SSOT)** 보장 (양쪽 성과 누적 병합) |
| **전환 소요 시간** | 대량 Write 트랜잭션으로 수십 초 지연 및 락 위험 | 백그라운드 1~2초 내 비동기 동기화 완료 |
| **최종 평가** | ❌ 탈락 | 🟢 **최종 채택** |

**대안 A**는 구현이 간단하지만, 서버리스 DB의 제한된 컴퓨팅 리소스(CU)와 네트워크 트래픽을 단시간에 소모시킵니다. 더 심각한 문제는 DW1에서 진행한 식약처 수집본과 DW2에서 진행한 글로벌 수집본이 공존할 때, 어느 한쪽을 덮어쓰면 반대쪽 작업이 영구 유실되는 **스플릿 브레인(Split-Brain) 데이터 손실**이 발생한다는 점이었습니다.

따라서 우리는 도메인 식별자를 기반으로 양쪽의 진척도를 지능적으로 병합하는 **대안 B(Smart Incremental Relay)**를 선택했습니다.

## 4. 해결책: 스마트 증분 릴레이(Smart Incremental Relay) 아키텍처

우리는 인메모리 DB 라우터와 동기화 엔진 사이에 **차등 동기화 및 우선순위 기반 병합 파이프라인**을 구축했습니다.

```
       [Failover / Failback 이벤트 발생]
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
 [이전 활성 DW (DW A)]           [신규 활성 DW (DW B)]
       │                               │
       └───────────────┬───────────────┘
                       ▼
       [Smart Relay Engine (차분 추출)]
       - 비즈니스 고유 키(INCI Name 등) 기준 매칭
       - CAS 검증 상태 및 규제 정보 진척도 평가
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
[미존재 신규 데이터]             [기존 레코드 충돌]
 ➔ INSERT (신규 등록)            ➔ MERGE (더 진척된 필드로 승격)
                       │
                       ▼
         ✨ [완전체 스테이징 상태 달성]
```

### 핵심 구현 원칙

#### 1) 테이블 성격별 차등 동기화
모든 데이터를 무차별 동기화하지 않고 성격에 따라 격리 수준을 분리했습니다.
* **스테이징 작업 큐**: 비즈니스 키 기준 무손실 스마트 병합 (무손실 보장)
* **일별 통계 요약**: 날짜 기준 Upsert 동기화
* **시계열 시스템/접속 원천 로그**: 동기화 대상에서 제외하고 각 인스턴스에 로컬 격리 (컴퓨팅 쿼터 보호)

#### 2) 진척도 기반 우선순위 병합 (Merge Precedence)
단순한 타임스탬프 덮어쓰기가 아닌, **도메인 가공 단계의 성숙도**를 기준으로 데이터를 병합합니다.
* **신규 데이터**: 신규 인스턴스에 없는 항목은 메타데이터와 함께 즉시 복제
* **기존 데이터 충돌 시**:
  * 이전 DB의 검증 상태(`verified`, `suggested`)가 타깃 DB의 미검증 상태(`needed`)보다 앞서 있다면 검증 상태 및 보강 필드를 승격 업데이트
  * 규제/제한 정보나 표준 명칭 필드가 한쪽에만 채워져 있다면 빈 값을 안전하게 보강 채움

## 5. 엔지니어링 교훈 (Takeaways)

1. **'임시 데이터'의 생명주기를 과소평가하지 말 것**:
   엔지니어링 관점에서 큐(Queue)나 스테이징(Staging)은 언제든 비워질 수 있는 공간으로 생각하기 쉽습니다. 그러나 실제 비즈니스 프로세스에서는 수일에 걸쳐 점진적으로 정제되는 '가장 활발한 상태 저장소'일 수 있음을 배웠습니다.
2. **제약 조건(Constraint)이 좋은 아키텍처를 만든다**:
   무제한 인프라였다면 단순히 인스턴스 전체를 덤프해 복제했을지도 모릅니다. 서버리스 무료 티어의 쿼터 한계라는 제약이 있었기에, 네트워크 I/O를 99% 절감하면서도 데이터 정합성을 완벽히 보장하는 도메인 기반 증분 병합 패턴을 도출할 수 있었습니다.
3. **투명한 장애 복구(Transparent Handover)의 중요성**:
   진정한 고가용성(HA)은 단순히 커넥션 에러를 내지 않는 것에 그치지 않습니다. 인프라 스위칭이 발생하더라도 백그라운드 파이프라인의 작업 맥락(Context)이 끊김 없이 인계되어, 최종 사용자와 관리자가 단일 시스템을 사용하는 것처럼 느끼게 해야 합니다.
