제품을 개발할 때 엔지니어가 접하는 가장 흔한 도전 중 하나는 **"제한된 인프라 자원 내에서 서비스의 높은 이용 가능성(High Availability)과 데이터 정확성을 동시에 확보하는 것"**입니다. 

PickSafe 팀은 최근 식약처 공공데이터를 활용해 성분의 안전성 및 규제 정보 분석 기능을 구축하는 과정에서, 외부 API 파편화 문제와 서술형 Serverless DB(Neon DB)의 네트워크/비용 제약이라는 두 가지 거대한 벽에 직면했습니다.

본 포스팅에서는 공공데이터 매쉬업 기술과 **로컬 퍼스트(Local-First) 정적 캐싱 아키텍처**를 통해 원격 DB 호출을 99% 이상 줄이고, 인프라 비용 제약을 극복한 엔지니어링 여정을 공유합니다.

---

## 1. 직면한 문제 (Problem)

### ① 공공데이터의 파편화 (Data Fragmentation)
단일 식약처 "원료성분정보" API만으로는 성분의 표준 명칭만 알 수 있을 뿐, **배합 제한 한도**, **규제 국가 정보**, **알레르기 유발 여부** 등 실질적인 안전성 정보를 제공할 수 없었습니다. 사용자에게 유의미한 가치를 제공하려면 최소 3개 이상의 이종 데이터셋을 결합(Mashup)해야만 했습니다.

### ② Serverless DB(Neon DB)의 자원 한계와 트래픽 리스크
초기 스타트업 및 서벌리스 환경에서 흔히 사용하는 Neon DB(Serverless Postgres)는 용량과 월간 네트워크 트래픽(Network Transfer)에 제한이 존재합니다.
* 사용자의 성분 분석 요청이 들어올 때마다 수천 건의 성분 마스터 테이블을 DB에서 실시간 조회하거나,
* 배치(Batch) 작업마다 대량의 데이터를 원격 DB에 Direct Bulk Seeding 할 경우,

급격한 네트워크 트래픽 소모로 인해 **인프라 비용이 급증하거나 서비스가 일시 정지(Downtime)될 위험**이 극도로 높았습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이 문제를 해결하기 위해 크게 3가지 아키텍처 대안을 검토했습니다.

| 구분 | 대안 1: 100% 원격 DB 실시간 조회 | 대안 2: Redis 인메모리 캐시 도입 | 대안 3: 로컬 퍼스트 정적 파일 캐싱 (선택) |
| :--- | :--- | :--- | :--- |
| **장점** | 데이터 최신성 유지가 용이함 | O(1) 수준의 빠른 읽기 속도 | **추가 인프라 비용 0원**, DB 의존성 완벽 분리 |
| **단점** | DB 트래픽 폭증, 비용 및 쿼리 병목 발생 | 관리 인프라 추가(Redis 비용 및 운영 공수) | 신규 데이터 업데이트 시 빌드/배치 공수 필요 |
| **결론** | **부적합** (인프라 한계 초과) | **보류** (초기 비용 및 복잡도 증가) | **최종 채택** (비용 극대화, 오프라인 내성) |

### 왜 Redis가 아닌 '로컬 퍼스트 정적 파일'인가?
마스터 성분 데이터는 **"자주 변경되지 않는 읽기 전용(Read-Heavy) 데이터"**라는 도메인 특성을 가지고 있습니다. 별도의 Redis 서버를 띄워 인프라 비용을 추가하는 대신, 빌드 타임에 마스터 데이터를 JSON 형태(`app/resources/ingredients_master.json`)로 정적 컴파일하여 애플리케이션 메모리에 직접 로딩하는 방식을 선택했습니다.

## 3. 핵심 해결책: 로컬 퍼스트 하이브리드 파이프라인 (Architecture)

우리가 구축한 해결책은 크게 **데이터 매쉬업**과 **3단계 룩업(Lookup) 파이프라인**으로 나뉩니다.

```
[클라이언트 요청] 
       │
       ▼
┌─────────────────────────────────────────┐
│ 1차: 백엔드 인메모리 캐시 조회 (Static JSON)│ ──(99% 매칭 성공)──► [응답 완료]
└─────────────────────────────────────────┘
       │ (조회 실패 / 희귀 신규 성분)
       ▼
┌─────────────────────────────────────────┐
│ 2차: 식약처 실시간 API 매쉬업 호출       │
└─────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────┐
│ 3차: Neon DB 캐싱 & 정적 컴파일 데이터 동기화│
└─────────────────────────────────────────┘
```

### ① 식약처 3대 오픈 API 매쉬업 및 글로벌 표준 결합
배치 시더(Seeder)를 통해 아래 3가지 API 데이터를 결합했습니다.
1. **성분 기본 정보 API**: 표준 성분명 및 식별자 추출
2. **사용제한 원료 정보 API**: 배합 한도 및 제한 조건 추출 (`restriction_info`)
3. **규제 정보 API**: 국가별 규제 세부 설명 추출 (`regulation_info`)

추가로, 독자 구축한 **EU CosIng 및 국내 식약처 고시 향료 알레르기 표준 사전(82종/25종)**을 하이브리드로 결합하여 알레르기 유발 플래그(`is_allergen_standard`)를 자동 맵핑했습니다.

### ② 데이터 무결성을 위한 Mock 데이터 완벽 배제
테스트나 매칭률을 눈속임하기 위한 **가짜(Mock) 데이터는 완전히 배제**했습니다. API 조회가 실패하거나 사전 데이터에 없는 성분은 억지로 데이터를 생성하지 않고 순수하게 `unmatched` 상태로 도메인 모델을 유지하여 데이터 신뢰성을 보장했습니다.

## 4. 성과 및 엔지니어링 효과 (Impact)

1. **원격 DB 트래픽 99% 이상 절감**
   * 성분 분석 요청 시 원격 Neon DB로 가는 RTT(Round Trip Time) 및 SQL 쿼리를 완전 제거했습니다.
   * 인메모리 Hash Map 기반 O(1) 매칭을 통해 응답 속도를 압도적으로 개선했습니다.
2. **장애 격리 및 고가용성(Fault Tolerance) 확보**
   * 순간적인 네트워크 장애나 Neon DB가 오프라인 상태에 빠지더라도, 로컬 정적 백업 캐시를 통해 성분 분석 핵심 기능이 100% 상시 가동됩니다.
3. **인프라 비용 제로화**
   * Serverless DB의 Free Tier 범주 내에서 영구적으로 서비스를 운영할 수 있는 환경을 마련했습니다.
4. **도메인 정보 가치 제고**
   * 단순 성분명 나열을 넘어 상세 배합 한도 및 규제 경고 툴팁을 제공하여 서비스의 UX/가치를 크게 향상시켰습니다.

---

## 5. 핵심 교훈 (Takeaway)

* **비용과 제약은 아키텍처의 좋은 촉매제다**: 인프라 리소스 한계를 무조건 고사양 DB로 해결하려 했다면 불필요한 운영 비용이 발생했을 것입니다. 데이터의 특성(Read-Heavy, Low-Update)을 정확히 파악하여 **로컬 퍼스트 캐싱** 전략을 적용한 것이 최선의 결과를 낳았습니다.
* **데이터 무결성의 중요성**: 인프라를 최적화하는 과정에서도 Mock 데이터를 섞지 않고 strict한 `unmatched` 정책을 유지함으로써, 최종 사용자에게 항상 검증된 정보만 제공할 수 있는 신뢰성을 확보했습니다.

PickSafe 팀은 앞으로도 자원 효율적인 엔지니어링 기법을 적용하여, 견고하고 확장성 있는 서비스를 만들어 나갈 것입니다.
