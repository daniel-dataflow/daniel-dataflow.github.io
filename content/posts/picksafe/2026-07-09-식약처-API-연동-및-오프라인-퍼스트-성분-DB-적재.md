초기 단계의 스타트업이나 인디 프로젝트에서 **서버리스 데이터베이스(예: Neon DB)**와 **외부 공공 API**를 조합해 서비스를 구축할 때 자주 마주치는 두 가지 큰 벽이 있습니다. 

1. **파편화된 공공데이터**: 단일 API 제공 정보의 한계로 인해 깊이 있는 유저 가치를 제공하기 어려움
2. **인프라 제약과 비용 쿼터**: 트래픽 증가나 대량 시딩(Bulk Seeding) 시 초과되는 서버리스 DB의 Compute Hours 및 Network Transfer 제한

이번 포스팅에서는 PickSafe 팀이 식약처 3대 오픈 API를 유기적으로 매쉬업(Mashup)하는 과정에서 발생한 **데이터 파편화 문제**를 해결하고, **로컬-퍼스트(Local-First) 정적 캐싱 아키텍처**를 도입하여 Neon DB 트래픽 및 쿼리 비용을 99% 이상 절감한 엔지니어링 경험을 공유합니다.

---

## 1. 문제 정의: 파편화된 데이터와 Cloud Infra의 한계

### (1) 데이터의 파편화 (Data Fragmentation)
PickSafe 서비스에서 성분의 안전성을 검증하기 위해서는 단순 성명(Name)뿐만 아니라 **배합제한 한도** 및 **국가별 규제 정보**, 그리고 **알레르기 유발 여부**가 필수적입니다. 하지만 식약처의 기존 "원료성분정보" 단일 데이터셋은 표준 이름만 제공할 뿐, 세부 규제나 제한 수치를 포함하지 않았습니다.

### (2) Neon DB의 네트워크/용량 한계 리스크
저희는 메인 데이터베이스로 서버리스 PostgreSQL인 Neon DB를 사용하고 있습니다. Neon DB의 Free Tier 혹은 효율적인 인프라 운영 정책상 **월 Network Transfer(5GB)** 및 **Compute Usage** 제약이 존재합니다. 

성분 분석 요청이 들어올 때마다 수천~수만 건의 성분 테이블을 원격 DB에서 매번 Query하거나, 외부 데이터를 원격 DB에 대량 Write(Bulk Seeding)하는 구조는 다음과 같은 문제를 야기했습니다.
* **DB 쿼터 고갈:** 반복적인 쿼리로 인한 무상 요금제 이탈 및 서비스 정지 리스크
* **지연 시간(Latency):** 원격 DB 네트워크 RTT(Round Trip Time)로 인한 응답 속도 지연

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 아키텍처 설계 단계에서 크게 3가지 선택지를 검토했습니다.

| 항목 | 대안 A: 요청 시마다 외부 API 조회 + DB 저장 | 대안 B: 인메모리 분산 캐시(Redis) 도입 | 대안 C: 정적 데이터 Compiling & 로컬-퍼스트 캐싱 (선택) |
| :--- | :--- | :--- | :--- |
| **장점** | 구현이 매우 단순함 | 데이터 갱신 및 처리 속도가 우수함 | **인프라 비용 0원**, 네트워크 RTT 제로, DB 부하 99% 방어 |
| **단점** | 레이턴시 매우 높음, 외부 API 장애 시 서비스 마비 | 별도 인프라 구축 및 유지보수 비용 발생 | 데이터 업데이트 시 빌드/배치 수집 프로세스 필요 |
| **적합성** | ❌ 부적합 | ⚠️ 과도한 엔지니어링 (Over-engineering) | ✅ **최리적의 대안** |

### 왜 Redis가 아닌 '정적 JSON 파일 기반 캐스케이딩 조회'인가?
성분 사전을 구성하는 데이터는 **'자주 변경되지 않는(Semi-Static) 읽기 중심 데이터'**라는 특성을 가집니다. 변경 주기가 길고 신규 성분이 추가되는 속도가 완만한 도메인 특성상, 굳이 추가 비용을 들여 Redis 관리형 인프라를 둘 필요가 없었습니다.

대신 배치 시더(Seeder) 프로세스를 통해 식약처 3대 API와 자체 사전(EU CosIng + 한국 식약처 고시 향료 알레르기 82종/25종)을 매쉬업한 결합체 데이터를 **애플리케이션 빌드 단계에서 정적 JSON(`ingredients_master.json`)으로 로컬 디스크에 컴파일**하기로 결정했습니다.

## 3. 핵심 아키텍처 및 구현 (Architecture)

### (1) 데이터 매쉬업 (Mashup) 및 파이프라인
독자적인 데이터 파이프라인을 구축하여 식약처의 3대 API를 동합하고 표준 알레르기 사전을 자동으로 매핑하도록 구성했습니다.

```
[식약처 성분 정보 API] ──┐
[식약처 사용제한 정보 API] ┼─> Data Mashup Engine ──> [EU CosIng / KFDA 알레르기 사전]
[식약처 규제 정보 API]  ──┘         │                          │
                                    └──────────────────────────┴─> [ingredients_master.json]
```

### (2) 3단계 캐스케이딩 (Cascading) Lookup 전략
백엔드 애플리케이션(FastAPI) 시작 시 `ingredients_master.json` 파일을 메인 메모리에 로드합니다. 성분 분석 요청이 들어왔을 때의 아키텍처 라우팅 흐름은 다음과 같습니다.

```
 Client Request
       │
       ▼
 [1차: In-Memory JSON Cache] ──(Hit: 99%+)──> Fast Return (0ms Latency)
       │ (Miss - 극소수 신규 성분)
       ▼
 [2차: Live External API] ────(Fetch Success)──> [3차: Neon DB & JSON Sync] ──> Return
       │ (Fetch Fail / Edge Case)
       ▼
 [Return: Strictly 'unmatched' State] (Mock 데이터 절대 금지)
```

1. **1차 조회 (In-Memory Cache):** 로컬 정적 JSON 캐시에서 최우선으로 성분을 식별합니다. (대부분의 쿼리가 여기서 처리됨)
2. **2차 조회 (Real-Time External API):** 정적 사전에 존재하지 않는 롱테일(Long-tail) 희귀 성분에 한해 식약처 API 실시간 조회를 수행합니다.
3. **3차 적재 (Neon DB Sync):** 실시간으로 조회된 신규 성분은 데이터베이스에 적재하여 다음 요청에 대비합니다.

### (3) Data Integrity 원칙: Mock 데이터의 철저한 배제
엔지니어링 공정에서 임의의 가짜(Mock) 데이터를 생성하여 매칭시키는 방식을 완전히 금지했습니다. API 응답이 없거나 매칭되지 않는 원료는 **명시적인 `unmatched` 상태**로 가시화하여, 데이터 신뢰도를 높이고 유저 및 분석 엔진 시스템에 혼선을 주지 않도록 설계했습니다.

## 4. 성과 및 엔지니어링 교훈 (Takeaways)

### 📊 정량적 성과
* **DB API 호출 및 네트워크 트래픽 99% 이상 절감:** Neon DB에 대한 실시간 READ 쿼리가 획기적으로 줄어들어, 무료 티어/최소 요금제 환경에서도 서비스 정지 리스크 없이 안정적으로 서빙이 가능해졌습니다.
* **레이턴시 혁신:** 인메모리 로컬 조회 전환을 통해 평균 성분 분석 응답 속도가 크게 향상되었습니다.
* **High Availability (고가용성) 확보:** 외부 데이터베이스 서비스(Neon DB)에 일시적인 네트워크 장애가 발생하더라도, 로컬 디스크/메모리에 탑재된 정적 JSON 덕분에 성분 분석 핵심 기능은 **100% 상시 가동(Zero Downtime)** 상태를 유지합니다.

### 💡 Engineering Takeaways

1. **도메인 데이터의 특성을 고려한 캐싱 전략 선택**
   모든 동적/캐시 데이터에 Redis나 DB 쿼리가 답은 아닙니다. 데이터의 '수명 주기(Lifecycle)'와 '변경 빈도(Write Frequency)'를 파악하여 static file 기반의 로컬-퍼스트 캐싱 전략을 취하는 것이 초기 시스템 인프라 비용과 복잡도를 줄이는 데 훨씬 강력할 수 있습니다.

2. **FinOps 관점의 아키텍처 설계**
   기술적 화려함보다 중요한 것은 **서비스의 지속 가능성**입니다. 클라우드 쿼터 한계를 명확히 인식하고, 시스템 아키텍처 수준에서 DB 트래픽을 방어하는 설계를 가져가는 것이 백엔드 엔지니어의 핵심 덕목임을 다시 한번 배웠습니다.
