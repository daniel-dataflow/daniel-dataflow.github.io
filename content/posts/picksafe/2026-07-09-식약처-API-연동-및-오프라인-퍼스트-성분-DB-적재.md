## 1. 들어가며: 토이 프로젝트와 프로덕션 그 사이의 고민

사내 혹은 개인 프로젝트를 진행하며 서버리스(Serverless) 데이터베이스인 **Neon DB(Free Tier)**를 도입해 본 적이 있는가? 초기 구축 비용이 들지 않고 확장성이 뛰어나다는 장점이 있지만, **Compute Hours**와 **월 5GB의 Network Transfer 제약**이라는 명확한 인프라적 한계가 존재한다.

'PickSafe' 서비스를 개발하던 중, 식약처의 대규모 공공 오픈 API 데이터를 연동해야 하는 요구사항을 마주했다. 성분 정보를 대량으로 다루는 서비스 특성상, 사용자 요청마다 원격 DB를 찌르거나 대규모 데이터를 Bulk Insert하는 순간 무료 티어의 자원 한계로 서비스가 중단될 위험이 컸다.

이번 포스팅에서는 **단일 API의 정보 한계**, **원격 DB 부하 방어**, 그리고 **신뢰할 수 있는 데이터 정합성**이라는 세 가지 문제를 해결하기 위해 도입한 **로컬-퍼스트(Local-First) 하이브리드 아키텍처** 설계 경험을유기적으로 공유하고자 한다.

---

## 2. 마주한 기술적 문제 (Problem)

### ① 단일 API 데이터의 파편화
기존에는 식약처의 "원료성분정보" 1개 데이터셋만 의존하고 있었다. 이 방식은 성분의 표준 이름만 식별할 뿐, 실무적으로 가장 중요한 **배합제한 한도**나 **규제 국가 정보** 같은 상세한 규제 안전 정보를 알 수 없다는 치명적인 한계가 있었다. 이를 해결하려면 식약처의 성분·사용제한·규제 관련 3대 API를 매쉬업(Mash-up)해야 했다.

### ② 원격 Neon DB 네트워크 및 리소스 한계 리스크
3대 API로부터 수집되는 수천 건의 방대한 성분 데이터를 실시간으로 원격 DB에 쿼리하거나 대량 시딩(Bulk Seeding)할 경우, Neon DB 무료 티어의 네트워크 대역폭과 커넥션 풀을 순식간에 소모하게 된다. 잘못하면 트래픽 상한선 초과로 서비스 전체가 다운될 수 있는 상황이었다.

### ③ 가짜 데이터(Mock)의 유혹과 신뢰성 저하
개발 속도를 높이기 위해 임의의 Mock 데이터를 채워넣고 싶은 유혹이 있었지만, 화장품 및 성분 안전성을 다루는 도메인 특성상 잘못된 정보는 사용자에게 치명적이다. Mock 데이터를 배제하고 실제 데이터만 정확히 다루어야 했다.

## 3. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 두 가지 아키텍처 대안을 저울질했다.

*   **Alternative A: 전면 원격 DB 캐싱 전략**
    *   *내용:* 모든 API 데이터를 최초 구동 시점에 원격 DB에 밀어 넣고, 이후 조회는 DB 인덱싱을 통해 처리.
    *   *Pros:* 데이터 중앙 관리 용이.
    *   *Cons:* 초기 시딩 시 네트워크 트래픽 폭발, Neon DB 무료 티어 용량 및 대역폭 초과 위험 100%.
*   **Alternative B: 로컬-퍼스트 정적 파일 캐싱 + 하이브리드 매처 (선택한 방식)**
    *   *내용:* 빌드 및 배치 시점에 3대 API 데이터를 병합하여 **로컬 정적 JSON 파일**로 컴파일하고, 서버 메모리에 캐싱하여 1차 대조. DB는 보조 수단으로만 활용.
    *   *Pros:* 원격 DB 네트워크 호출 99% 이상 감소, DB가 다운되어도 핵심 기능(성분 조회) 가동 가능, 네트워크 비용 제로.
    *   *Cons:* 성분 데이터 업데이트 시 서버 재배포 혹은 정적 파일 갱신 프로세스 필요.

서비스의 안정성과 인프라 비용 절감이 최우선이었기에 **Alternative B (로컬-퍼스트 아키텍처)**를 채택했다.

## 4. 최종 해결 및 아키텍처 구현

### 1) 식약처 3대 API 매쉬업 및 정적 파일 컴파일러
배치 및 빌드 시점에 동작하는 시더(`seed_kfda_ingredients.py`)를 구현하여, 3대 API(`원료성분`, `사용제한원료`, `규제정보`)를 병합한 뒤 디스크에 정적 JSON 파일(`ingredients_master.json`)로 빌드하도록 했다.

```text
[식약처 3대 API] ---> (병합 배치 스크립트) ---> local: app/resources/ingredients_master.json (정적 캐시)
                                       ---> remote: Neon DB (백업/확장 저장소)
```

### 2) 메모리 캐시 최우선 매칭 메커니즘 (`ingredient_matcher.py`)
백엔드(`FastAPI`)는 요청이 들어오면 원격 DB를 먼저 조회하는 것이 아니라, 메모리에 로드된 정적 JSON 사전을 최우선으로 대조한다.
*   정적 파일과 DB 어디에도 없는 극소수의 희귀 신규 성분만 예외적으로 식약처 API 실시간 조회를 타며, 그 결과는 Neon DB에 적재한다.
*   이 구조를 통해 **Neon DB와의 실시간 통신 및 쿼리 비용을 99% 이상 절감**했다.

### 3) 글로벌 알레르기 사전과의 하이브리드 결합
식약처 데이터뿐만 아니라, 독자적으로 구축한 **EU CosIng + 한국 식약처 고시 향료 알레르기 표준 사전(82종/25종)** 로직을 병합하여 `is_allergen_standard = True` 값을 자동으로 마스킹하고 적재하도록 설계했다. 아울러 Mock 데이터를 일체 배제하고, 매칭에 실패한 성분은 `unmatched` 상태로 엄격하게 리턴하여 데이터 정합성을 확보했다.

## 5. 맺음말 및 엔지니어링 교훈 (Takeaway)

이번 아키텍처 개선을 통해 얻은 교훈은 명확하다.

1. **Infrastructure-Aware Architecture (인프라를 고려한 설계):** 화려하고 복잡한 분산 캐시 시스템(Redis 등)을 무조건 도입하기보다, 프로젝트의 규모와 인프라 제약(Neon DB Free Tier)에 맞춰 **'로컬 정적 파일 + 메모리 캐시'**라는 단순하지만 강력한 방식을 선택한 것이 주효했다.
2. **Resilience (탄력성 확보):** 서버리스 DB가 네트워크 장애를 일으키거나 오프라인 상태가 되더라도, 로컬 정적 JSON 파일 덕분에 핵심 서비스인 성분 분석 기능이 멈추지 않는 높은 가용성(High Availability)을 확보할 수 있었다.
3. **Domain Integrity (도메인 신뢰성):** 편의를 위한 Mock 데이터를 과감히 배제하고 철저한 데이터 매칭 파이프라인을 구축함으로써 서비스 전반의 신뢰도를 한 차원 끌어올렸다.

제약은 종종 가장 창의적이고 단단한 아키텍처를 낳는다. 이번 로컬-퍼스트 전환은 토이 프로젝트 및 초기 프로덕션 레벨에서 서버리스 비용과 성능 두 마리 토기를 잡은 모범적인 사례가 되었다.
