안녕하세요, PickSafe 개발 팀입니다. 

스타트업이나 초기 서비스 단계에서는 **'한정된 자원 속에서 어떻게 가장 빠르고 안정적인 서비스를 구축할 것인가'**가 늘 중요한 화두입니다. 특히 클라우드 기반의 서버리스 데이터베이스(Serverless DB)는 유연한 확장성을 제공하지만, 무료/엔트리 티어에서 제공하는 네트워크 대역폭(Network Transfer)과 연산량(Compute Hours)의 제약이라는 명확한 트레이드오프가 존재합니다.

이번 포스팅에서는 식약처의 파편화된 3대 오픈 API 데이터를 하나로 엮는 **데이터 매쉬업(Mashup)** 과정과, 서버리스 DB인 **Neon DB의 요금 및 트래픽 한계를 극복하기 위해 '로컬-퍼스트(Local-First)' 캐싱 아키텍처를 도입하여 DB 트래픽을 99% 이상 절감한 엔지니어링 사례**를 공유하고자 합니다.

---

## 1. 마주한 문제 (The Problem)

PickSafe는 화장품 및 식품 성분을 분석하여 배합 제한 물질이나 규제 정보를 직관적으로 가시화해 주는 서비스입니다. 이 서비스를 개발하는 과정에서 크게 두 가지 기술적 병목에 부딪혔습니다.

### ① 공공 데이터의 파편화 (Data Fragmentation)
식약처에서 제공하는 공공 API는 매우 유용하지만, 성분의 정보를 종합적으로 판단하기에는 데이터가 너무 파편화되어 있었습니다.
* **원료성분정보 API**: 성분의 표준명만 식별 가능.
* **사용제한 원료 정보 API**: 이 성분이 얼마나 배합 제한되어 있는지 식별 가능.
* **규제 정보 API**: 국가별/기관별 규제 강도 식별 가능.

즉, 사용자에게 "이 성분은 안전한가요?"라는 질문에 명확히 답하려면 이 **3개의 오픈 API 데이터를 실시간으로 조인(Join)하거나 병합하여 제공**해야만 했습니다.

### ② 서버리스 DB(Neon DB)의 네트워크 및 연산 처리 한계
초기 인프라 비용을 최적화하기 위해 PostgreSQL 기반의 서버리스 DB인 **Neon DB**를 도입했습니다. 하지만 Neon DB의 무료 티어에는 **월 5GB의 Network Transfer 제약**과 Compute Hours 제한이 걸려 있었습니다.
성분 분석 요청이 들어올 때마다 원격 DB를 풀 스캔하거나, 수천 건의 성분 마스터 데이터를 원격 DB에 직접 벌크 시딩(Bulk Seeding)하고 조회하는 방식은 **서비스 론칭 후 단 며칠 만에 쿼터 초과로 서비스가 마비될 수 있는 시한폭탄**과 같았습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 저희 팀은 세 가지 아키텍처 대안을 두고 치열하게 고민했습니다.

| 비교 분석 | 안 1. 실시간 API 호출 & 원격 DB 매핑 | 안 2. 원격 DB 중심의 검색 (Indexing) | 안 3. 로컬-퍼스트 정적 파일 캐싱 (선택) |
| :--- | :--- | :--- | :--- |
| **작동 방식** | 요청마다 식약처 API를 실시간 호출 및 DB 저장 | 3대 API를 미리 DB에 시딩해두고 쿼리로 조회 | 빌드 시점에 정적 JSON 컴파일 후 서버 메모리 캐싱 우선 조회 |
| **장점** | 실시간성이 가장 높음. DB 용량 최적화 가능. | 아키텍처가 단순하고 SQL로 제어하기 쉬움. | **DB 호출 빈도 99% 감소, DB 장애 시에도 성분 분석 작동.** |
| **단점** | 외부 API 장애 시 서비스 전체 마비, 매우 느린 속도. | Neon DB 네트워크 전송량 과부하로 서비스 정지 리스크. | 신규 성분 업데이트 시 빌드/배포 프로세스 필요. |

### 선택: 안 3. 로컬-퍼스트 정적 파일 캐싱 (Local-First Static Caching)
성분 마스터 데이터는 법 개정이나 규제 업데이트가 없는 한 **자주 변하지 않는 정적 데이터(Static Data)**의 성격을 가집니다. 굳이 매 요청마다 비싼 네트워크 비용과 DB 커넥션을 소모하며 원격 DB를 찌를 이유가 전혀 없었습니다.

따라서 저희는 빌드 및 배치 시점에 3대 API 데이터를 병합하여 **단일 정적 JSON 백업 파일(`ingredients_master.json`)**로 컴파일해 두고, 이를 백엔드 메모리에 캐싱하여 1차 조회를 처리하는 **'로컬-퍼스트' 아키텍처**를 채택했습니다.

## 3. 최종 아키텍처 설계 및 구현 (Implementation)

전체적인 데이터 흐름과 매칭 파이프라인은 다음과 같이 구조화했습니다.

```
[배치/빌드 시점]
식약처 3대 API (성분, 제한, 규제) + EU CosIng (알레르기)
               │
               ▼ (Mashup & Normalization)
     ingredients_master.json (정적 파일 생성)

[사용자 요청 시점]
사용자 성분 분석 요청
               │
               ├───► [1차] Local-First Memory Cache (ingredients_master.json) -> 99% Hit!
               │
               └───► [2차] (미스 시에만) Neon DB 또는 식약처 API 실시간 조회 -> 신규 성분 등록
```

### ① 데이터 매쉬업 및 글로벌 표준 알레르기 사전 결합
우선 파편화된 데이터의 부가가치를 높이기 위해, 식약처 3대 데이터뿐만 아니라 독자적인 **EU CosIng 및 한국 식약처 고시 향료 알레르기 표준 사전(82종/25종)** 정보를 하이브리드로 결합했습니다. 

매핑 성공 시 `is_allergen_standard = True` 플래그를 자동으로 부여하여 적재하는 파이프라인을 구축함으로써 데이터의 신뢰도를 글로벌 스탠다드 수준으로 끌어올렸습니다.

### ② 로컬 정적 JSON 백업 파일 도입
가장 핵심이 되는 최적화 로직입니다. 빌드 시 동작하는 세부 시더 스크립트(`seed_kfda_ingredients.py`)를 통해 병합된 마스터 데이터를 로컬 파일(`app/resources/ingredients_master.json`)로 저장합니다. 

이후 성분 매처(`ingredient_matcher.py`)는 다음과 같은 우선순위로 매칭을 시도합니다.

1. **메모리에 적재된 정적 JSON 캐시 조회 (최우선)**
2. 캐시에 없는 신규/희귀 성분의 경우에 한해서만 **Neon DB 조회**
3. DB에도 없을 경우 **식약처 API 실시간 조회 후 DB에 캐싱**

이 방식을 통해 원격 DB와의 실시간 통신 비용을 최소화하고, Neon DB가 오프라인이거나 점검 중인 상황에서도 서비스의 핵심 기능인 성분 분석이 끊김 없이 상시 작동하는 **고가용성(High Availability)**을 확보했습니다.

### ③ 신뢰성을 위한 'Zero-Mock' 정책
데이터 분석 서비스의 생명은 **정확성**입니다. 데이터 혼선을 막기 위해 어설픈 가짜(Mock) 성분 데이터는 완전히 배제했습니다. API 조회가 실패하거나 매칭되지 않는 성분은 순수하게 `unmatched` 상태로 명확하게 사용자 화면에 리턴 및 가시화하도록 구현하여 데이터 투명성을 확보했습니다.

## 4. 엔지니어링 교훈 및 결과 (Takeaway)

이번 아키텍처 개편을 통해 저희 팀이 얻은 정량적/정성적 성과는 다음과 같습니다.

* **네트워크 전송량(Network Transfer) 99% 감소**: 사용자의 대량 성분 스캔 요청 시 발생하던 DB 쿼리가 로컬 캐시로 흡수되면서, Neon DB 트래픽 사용량이 미미한 수준으로 급감했습니다. 이를 통해 무상 요금제 범위 내에서 장기적이고 안정적인 서비스 운영이 가능해졌습니다.
* **응답 속도 향상**: 원격 DB 커넥션 및 쿼리 실행 시간이 사라지고 로컬 메모리 인덱스에서 매칭이 이루어짐에 따라, API 응답 속도(Latency)가 혁신적으로 개선되었습니다.
* **인프라 장애 내성 확보**: 외부 API 장애나 Neon DB 네트워크 지연 등 외부 환경 요인에 구애받지 않고 상시 고성능 성분 분석 기능을 제공할 수 있게 되었습니다.

### 💡 에디터의 한 줄 평 (Conclusion)
> "무조건 최신 기술, 무조건 분산 DB 조회만이 정답은 아닙니다. 데이터의 주기와 인프라의 한계를 명확히 이해하고, **'로컬-퍼스트'와 같은 실용적인 캐싱 기법**을 적재적소에 활용할 때 진정한 비용 효율적 엔지니어링이 실현됩니다."
