안녕하세요, PickSafe 팀의 백엔드 아키텍트입니다. 

스타트업이나 인디 개발 팀이 글로벌 서비스를 준비할 때 가장 먼저 맞닥뜨리는 현실적인 장벽 중 하나는 바로 **'인프라 비용과 자원의 한계'**입니다. 특히 서버리스 SQL 데이터베이스(예: Neon DB, Supabase 등)의 프리 티어나 가벼운 요금제는 콜드 스타트 문제나 네트워크 대역폭(Network Transfer), 컴퓨팅 아웃바운드 용량에 엄격한 제한을 둡니다.

PickSafe 팀은 최근 식약처의 공공 데이터를 매쉬업하여 성분 안전 정보를 제공하는 핵심 기능을 개발하며 이 한계에 직면했습니다. 수천, 수만 건의 복잡한 성분 데이터를 매번 실시간으로 원격 DB에서 조회하거나 싱크를 맞추다가는 순식간에 네트워크 전송량 한계(월 5GB)를 초과해 서비스가 마비될 상황이었습니다.

우리가 이 문제를 **"로컬-퍼스트(Local-First) 정적 캐싱 구조"**와 **"빌드 타임 데이터 매쉬업"**을 통해 어떻게 우아하게 해결했는지, 그 아키텍처 고민과 엔지니어링 여정을 공유합니다.

---

## 1. 문제 정의: 데이터 파편화와 인프라의 한계

우리가 해결해야 할 문제는 크게 두 가지였습니다.

### ① 공공 데이터의 파편화 (KFDA 3대 API 매쉬업 필요)
소비자에게 신뢰할 수 있는 화장품/식품 성분 안전 정보를 제공하려면 단순한 성분명 외에도 **'배합 제한 한도'**와 **정부의 '규제 정보'**가 유기적으로 연결되어야 합니다. 하지만 식약처에서 제공하는 API는 아래와 같이 철저히 파편화되어 있었습니다.
*   **A 데이터셋:** 성분 기본 정보 (`getIngredientInfoList`)
*   **B 데이터셋:** 사용 제한 원료 정보 (`getRegisterIngredientRestrictionInfoList`)
*   **C 데이터셋:** 규제 정보 (`getRegisterIngredientRegulationInfoList`)

사용자가 성분을 검색할 때마다 이 3가지 API를 실시간으로 호출하고 조인(Join)하는 것은 대기 시간(Latency) 관점에서 최악의 사용자 경험을 낳습니다.

### ② Neon DB의 네트워크 대역폭 및 컴퓨팅 리소스 한계
이 마스터 데이터를 클라우드 데이터베이스(Neon DB)에 모두 적재하고 매번 쿼리를 날리는 정석적인 구조를 검토했습니다. 그러나 Neon DB 프리 티어는 **월 5GB의 Network Transfer 제한**이 있습니다. 
*   성분 분석 요청이 발생할 때마다 수십~수백 개의 성분을 원격 DB에서 `SELECT`하고 매칭하는 구조는 트래픽이 조금만 몰려도 한계를 마주합니다.
*   주기적인 대량 시딩(Bulk Seeding) 작업 역시 DB 커넥션과 컴퓨팅 리소스를 극심하게 소모시켰습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 우리 팀은 세 가지 아키텍처 대안을 두고 치열하게 토론했습니다.

| 비교 요인 | 대안 A: 실시간 API + Write-Through DB 캐싱 | 대안 B: 완전 원격 DB 인덱싱 및 쿼리 | 대안 C (채택): 로컬-퍼스트 정적 컴파일 및 하이브리드 조회 |
| :--- | :--- | :--- | :--- |
| **작동 방식** | 요청 시마다 식약처 API 호출 후 결과를 DB에 캐싱 | 모든 데이터를 DB에 미리 시딩 후 매번 DB 쿼리 | **빌드/배치 시점에 3대 데이터를 JSON 파일로 빌드 후 메모리 캐싱, 미스(Miss) 시에만 DB 조회** |
| **네트워크 비용** | 높음 (외부 API 지연 + DB 쓰기 부하) | 매우 높음 (Neon DB 트래픽 임계치 초과 위험) | **극도로 낮음 (메모리 내 조회율 99% 이상)** |
| **조회 성능 (Latency)**| 매우 느림 (외부 네트워크 타임아웃 위험) | 보통 (DB 인덱싱 최적화 필요) | **극도로 빠름 (Sub-millisecond 대)** |
| **데이터 정합성** | 실시간성이 높으나 API 장애 시 동반 장애 | 안정적이나 대량 시딩 시 비용 발생 | **높음 (안정된 정적 데이터 세트 보장)** |

### 결정: 대안 C (로컬-퍼스트 하이브리드 아키텍처)
성분 데이터는 정부 고시가 바뀌지 않는 한 **변경 빈도가 매우 낮은 정적 데이터(Read-Heavy)**입니다. 이런 데이터 성격을 고려할 때, 매번 원격 자원을 소모하는 것은 낭비였습니다. 

우리는 빌드/배치 단계에서 데이터를 단일 파일로 엮어내고, 서버 메모리를 1차 캐시로 삼는 **로컬-퍼스트 전략**을 선택했습니다.

## 3. 최종 해결 방식 및 아키텍처 구현

저희가 설계하고 구현한 아키텍처는 다음과 같은 3단계 레이어로 작동합니다.

```
[사용자 요청: 성분 분석] 
       │
       ▼
┌────────────────────────────────────────┐
│ 1단계: 메모리 캐시 (JSON 백업 엔진)    │ ── (99% 매칭 성공, DB 통신 Zero)
└────────────────────────────────────────┘
       │ (극소수 신종 성분 등 캐시 미스 발생 시)
       ▼
┌────────────────────────────────────────┐
│ 2단계: Neon DB (원격 데이터베이스)      │
└────────────────────────────────────────┘
       │ (DB에도 없는 최초 등장 성분인 경우)
       ▼
┌────────────────────────────────────────┐
│ 3단계: 식약처 실시간 API 연동 & DB 저장│
└────────────────────────────────────────┘
```

### ① 빌드 시점 데이터 매쉬업 및 정적 파일 컴파일
배치 스크립트(`seed_kfda_ingredients.py`)를 통해 식약처의 3대 오픈 API를 미리 순회하며 데이터를 수집합니다. 이때, 국내 데이터에만 머무르지 않고 **유럽 화장품 성분 사전(EU CosIng)** 및 **식약처 고시 알레르기 유발 향료 표준 정보**를 하이브리드로 결합하여 알레르기 유발 여부(`is_allergen_standard`)까지 자동으로 플래그를 매핑합니다.

이렇게 매쉬업된 최종 완성형 마스터 데이터는 데이터베이스뿐만 아니라 프로젝트 내부의 정적 JSON 파일(`app/resources/ingredients_master.json`)로 컴파일되어 저장됩니다.

### ② 애플리케이션 가동 시 메모리 로드 및 매칭 엔진
FastAPI 서버가 구동될 때, 이 정적 JSON 파일을 즉시 메모리에 캐싱합니다. 데이터 조회 요청이 들어오면 DB 커넥션을 맺기 전에 메모리 사전(`dict`)을 우선 검색합니다.

```python
# app/services/ingredient_matcher.py (컨셉 코드)

class IngredientMatcher:
    def __init__(self, static_json_path: str):
        # 서버 기동 시 정적 JSON을 메모리에 단 한 번 로딩 (O(1) 조회를 위한 해시맵 구조)
        self.memory_cache = self._load_static_master(static_json_path)

    def match_ingredient(self, name: str) -> IngredientSchema:
        # 1차: 로컬 메모리 캐시 조회 (Neon DB 부하 0%)
        if name in self.memory_cache:
            return self.memory_cache[name]
        
        # 2차: 캐시 미스 시 원격 DB 및 실시간 API Fallback
        return self._fallback_to_remote_db_and_api(name)
```

### ③ 데이터 신뢰성을 위한 'Zero-Mock' 정책
기술적 한계로 조회가 실패하는 경우, 가짜(Mock) 데이터를 임의로 채워 넣으면 헬스케어/뷰티 서비스의 정보 신뢰도가 치명적으로 손상됩니다. 

우리는 어설픈 가짜 데이터 매칭을 배제하고, 매칭되지 않는 희귀 신규 성분은 순수하게 `unmatched` 상태로 프론트엔드에 리턴하도록 설계했습니다. 이를 통해 사용자와 검증 기관 모두에게 투명하고 정확한 정보를 제공할 수 있게 되었습니다.

## 4. 엔지니어링 교훈 (Takeaway)

이번 아키텍처 개편을 통해 우리 팀이 얻은 교훈은 명확합니다.

1. **인프라 제약은 창의적인 아키텍처의 기회다:** 
   무료/저비용 티어의 한계를 극복하기 위해 도입한 로컬-퍼스트 캐싱은 결과적으로 Neon DB 트래픽을 **99% 이상 절감**하는 성과를 냈습니다. 비용 아웃풋을 통제하면서도 대기업 플랫폼 수준의 속도를 얻었습니다.
2. **모든 데이터가 DB로 갈 필요는 없다:** 
   자주 변하지 않는 대규모 메타데이터는 '정적 파일 컴파일'과 '애플리케이션 메모리 캐싱'의 결합이 RDBMS 튜닝보다 훨씬 강력하고 단순한 해결책이 될 수 있습니다.
3. **오프라인 회복 탄력성(Resilience) 확보:** 
   이 구조 덕분에 설령 원격 데이터베이스에 일시적인 네트워크 장애가 발생하더라도, 서비스의 핵심인 성분 분석 기능은 로컬 정적 사전을 기반으로 **장애 없이 상시 가동(Zero-Downtime)**됩니다.

인프라의 한계 안에서 최대의 성능을 이끌어내는 설계, 그것이 바로 시니어 엔지니어가 비즈니스에 기여하는 방식입니다. 앞으로도 PickSafe 팀은 효율적이고 지속 가능한 기술 아키텍처를 치열하게 고민해 나가겠습니다.
