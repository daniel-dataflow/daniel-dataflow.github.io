초기 스타트업이나 신규 프로젝트를 설계할 때 엔지니어가 마주하는 가장 흔한 숙제는 **"한정된 인프라 리소스 내에서 최고 수준의 가용성과 데이터 신뢰성을 확보하는 것"**입니다. 

PickSafe팀 역시 성분 분석 엔진을 구축하며 두 가지 큰 걸림돌에 직면했습니다. 단일 공공 API가 제공하는 데이터의 파편화 문제, 그리고 무료 티어 서버리스 DB(Neon DB)의 엄격한 네트워크/컴퓨팅 리소스 제한이었습니다. 

본 포스팅에서는 **식약처 3대 오픈 API 매쉬업**을 통해 데이터 완성도를 높인 과정과, **로컬-퍼스트 정적 파일 캐싱 전략**을 도입해 DB 트래픽을 99% 이상 절감하고 서비스 가용성을 대폭 향상시킨 기술적 의사결정 과정을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

### 1) 데이터의 파편화 (Data Fragmentation)
사용자에게 정확한 성분 안전 정보를 제공하기 위해서는 단순히 성분의 표준명(Name)뿐만 아니라, **배합 제한 한도(Restriction)** 및 **국가별 규제 정보(Regulation)**가 종합적으로 매핑되어야 합니다. 그러나 식약처에서 제공하는 단일 `원료성분정보` API만으로는 배합 제한 수치나 세부 규제 사유를 파악할 수 없었습니다.

### 2) 인프라 비용 및 트래픽 한계 (Resource Bottleneck)
저희는 클라우드 네이티브 서버리스 Postgres인 **Neon DB**를 활용하고 있습니다. Neon DB의 Free Tier는 월간 Network Transfer(5GB) 및 Compute Hours 제한이 촘촘하게 설정되어 있습니다. 
* 제품 스캔 요청이 올 때마다 수천 개의 성분 데이터베이스를 원격 DB에서 반복 조회한다면?
* 혹은 대량 성분 데이터 시딩(Bulk Seeding)을 주기적으로 원격 DB에 직접 실행한다면?

결과는 명확했습니다. 서비스 오픈 직후 쿼리 비용과 네트워크 트래픽 폭증으로 인해 DB가 한계에 도달하고 서비스가 마비될 위험이 컸습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이 문제를 해결하기 위해 시스템 아키텍처를 설계하며 세 가지 대안을 비교 검토했습니다.

| 항목 | 대안 A: 원격 DB 중심 실시간 조회 | 대안 B: Redis 기반 중앙 캐시 인프라 | 대안 C: 로컬-퍼스트 정적 파일 컴파일 & 메모리 캐싱 (선택) |
| :--- | :--- | :--- | :--- |
| **구조** | 매 요청마다 Neon DB 쿼리 실행 | Redis 클러스터 구축 후 캐싱 | 빌드/시딩 시점에 정적 JSON 컴파일 후 애플리케이션 메모리 캐싱 |
| **네트워크 비용** | 매우 높음 (DB 대역폭 소모) | 중간 (Redis 네트워크 대역폭 소모) | **최저 (원격 네트워크 통신 0건)** |
| **인프라 비용** | DB 쿼리 소모량 증가로 비용 위험 | 별도 Redis 서버 운용 비용 발생 | **추가 인프라 비용 없음 ($0)** |
| **DB 장애 시 영향** | 서비스 전체 마비 | Redis 가동 시 버텨으나 DB 복구 전 제한 | **DB 다운 타임에도 로컬 성분 조회 100% 정상 작동** |
| **단점/트레이드오프**| 트래픽 폭증 위험 | 인프라 복잡도 및 관리 비용 증가 | 데이터 업데이트 시 애플리케이션 재배포 또는 캐시 갱신 필요 |

### 💡 선택의 이유
성분 마스터 데이터는 **"읽기 비중이 99% 이상이고, 실시간 변동성이 매우 낮은(Read-Heavy, Rarely Changed)"** 특성을 가집니다. 매번 외부 DB나 별도의 In-memory 인프라(Redis)를 거칠 필요 없이, **애플리케이션 컴파일 시점에 검증된 정적 마스터 데이터(JSON)를 내장하여 로컬 메모리에서 즉시 1차 대조**를 수행하는 것이 성능, 비용, 안정성 측면에서 압도적으로 유리하다고 판단했습니다.

## 3. 최종 해결책 및 핵심 아키텍처 (Architecture Solution)

PickSafe 팀은 데이터 매쉬업 및 3계층 fallback 매칭 아키텍처를 설계하여 문제를 완전히 해결했습니다.

```
[사용자 요청: 성분 분석] 
       │
       ▼
[1계층: Memory Cache / ingredients_master.json]  ──(Hit 99%)──► [즉시 결과 반환 (0ms)]
       │ (Miss - 미등록 롱테일 희귀 성분)
       ▼
[2계층: 식약처 3대 API 실시간 조회 및 매쉬업]
       │
       ▼
[3계층: Neon DB 동적 적재 & 메모리 캐시 갱신]
```

### 1) 식약처 3대 오픈 API 매쉬업 & 글로벌 표준 하이브리드 결합
단일 API의 한계를 극복하기 위해 아래 3개 API를 데이터 시딩 시점에 사전 매쉬업(Mashup)하도록 구축했습니다.
1. `성분 정보 API` (표준 성분명 추출)
2. `사용제한 원료 정보 API` (배합 한도 수치 추출)
3. `규제 정보 API` (규제 국가 및 세부 사유 추출)

여기에 독자적인 **EU CosIng 데이터 및 한국 식약처 고시 향료 알레르기 표준 사전(82종/25종)**을 하이브리드로 자동 매칭하여 `is_allergen_standard` 플래그를 사전에 계산(Pre-computation) 후 인덱싱했습니다.

```python
# (개념 예시 - 보안상 비즈니스 핵심 로직 마스킹 처리)
class IngredientMashupService:
    def mashup_ingredient_data(self, raw_ingredients, restriction_list, regulation_list):
        """
        3대 공공 API 데이터를 조인하여 단일 도메인 모델(IngredientMaster)로 합성
        """
        processed_master = []
        for item in raw_ingredients:
            # 배합 제한 수치 및 규제 정보 맵핑
            restriction = self._find_restriction(item, restriction_list)
            regulation = self._find_regulation(item, regulation_list)
            
            # EU CosIng 및 식약처 알레르기 규격 하이브리드 매칭
            is_allergen = self._check_allergen_standards(item.name)

            processed_master.append({
                "code": item.code,
                "name": item.name,
                "restriction_info": restriction,
                "regulation_info": regulation,
                "is_allergen_standard": is_allergen
            })
        return processed_master
```

### 2) 로컬-퍼스트(Local-First) 정적 백업 컴파일 (`ingredients_master.json`)
시딩 시점에 생성된 완성형 성분 데이터셋은 애플리케이션 리소스 영역(`resources/ingredients_master.json`)에 로컬 정적 파일로 컴파일됩니다. 백엔드 서비스(FastAPI)가 기동될 때 이 파일은 메모리에 온전히 래핑(In-memory Load)됩니다.

이로 인해 99% 이상의 일반적인 성분 분석 요청은 **원격 DB 커넥션을 전혀 생성하지 않고, 0ms에 가까운 속도로 메모리에서 즉시 처리**됩니다.

### 3) Strict Real-Data 원칙 (No Mock Policy)
데이터 분석의 신뢰성을 위해 임의의 가짜(Mock) 데이터는 완전히 배제했습니다. 로컬 정적 캐시와 3대 API 실시간 통신으로도 매칭되지 않는 희귀 성분은 억지로 더미 데이터를 씌우지 않고, 명확히 `unmatched` 상태로 규정하여 프론트엔드에 전달합니다. 이를 통해 사용자에게 왜곡 없는 투명한 정확도를 보장합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 개편을 통해 얻은 핵심적인 엔지니어링 레슨은 다음과 같습니다.

1. **"모든 데이터가 DB 테이블에 실시간으로 위치할 필요는 없다."**
   읽기 집중형(Read-Heavy)이자 도메인 변경 주기가 긴 기준 정보(Master Data)는 애플리케이션 빌드 타임에 컴파일하거나 로컬 캐시로 전진 배치(Edge/Local-First)하는 것이 DB 부담을 획기적으로 줄이는 열쇠입니다.

2. **제약 조건(Constraint)은 훌륭한 설계를 유도한다.**
   Neon DB의 무료 티어 제한이라는 인프라적 제약이 없었다면 습관적으로 모든 요청을 DB 쿼리로 처리했을 것입니다. 이 한계를 극복하는 과정에서 DB 장애 타임에도 100% 작동하는 높은 내구성을 가진(Resilient) 시스템을 완성할 수 있었습니다.

3. **도메인 복잡성을 다루는 기술: 매쉬업(Mashup)의 힘**
   파편화된 공공 데이터를 백엔드 파이프라인 상에서 단일 표준 모델로 정제 및 융합함으로써, 프론트엔드는 단순화된 API 데이터 구조만 소비할 수 있게 되었고 클라이언트 렌더링 성능도 함께 개선되었습니다.

PickSafe 팀은 인프라 리소스 한계를 뛰어넘는 효율적인 아키텍처를 지속적으로 탐구하고 있습니다. 데이터 신뢰성과 시스템 가용성을 모두 잡기 위한 기술적 여정은 계속됩니다.
