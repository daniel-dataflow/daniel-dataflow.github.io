제품의 성분 안전성을 실시간으로 분석하는 백엔드 엔진을 구축할 때 가장 중요한 두 가지 축은 **'데이터의 신뢰성(정확도)'**과 **'지속 가능한 인프라 비용 및 응답 지연 시간(Latency)'**입니다.

성분 분석 플랫폼을 개발하며 공공 공시 데이터의 파편화 문제와 서버리스 데이터베이스(Serverless PostgreSQL)의 리소스 한계라는 두 가지 엔지니어링 과제를 맞닥뜨렸습니다. 본 글에서는 **다중 규제 데이터 매쉬업 파이프라인**과 **정적 스냅샷 기반의 로컬-퍼스트(Local-First) 캐싱 전략**을 통해 원격 DB 트래픽을 99% 이상 절감하고 서비스 가용성을 극대화한 아키텍처 개선 과정을 공유합니다.

---

## 1. 마주한 기술적 과제 (Problem)

### ① 분산된 공공 데이터와 단일 API의 정보 한계
초기에는 공공 성분 표준 API 하나에 의존해 성분명을 파싱했습니다. 하지만 단일 데이터셋만으로는 **성분의 표준명**만 식별할 뿐, 사용자가 반드시 알아야 하는 **배합 한도(Restriction Limits)** 및 **국가별 규제 정보(Regulation Info)**, **글로벌 알레르기 유발 항원 기준(EU CosIng 등)**을 실시간으로 종합 제공하기 어려웠습니다.

### ② 서버리스 DB의 네트워크 전송량(Network Egress) 및 비용 리스크
클라우드 서버리스 DB(Neon DB) 환경은 유연한 확장이 장점이지만, 무료/기본 티어 기준 **월간 네트워크 전송량(Network Transfer) 및 Compute Hours 상한선**이 존재합니다. 
* 수만 건에 달하는 성분 마스터 데이터를 원격 DB에 직접 전수 시딩(Bulk Seeding)할 경우 인프라 소모량이 급증합니다.
* 사용자의 성분 스캔 요청마다 원격 DB를 반복 조회(I/O)하면 금세 트래픽 한계에 도달해 서비스가 다운될 위험이 있었습니다.

---

## 2. 대안 탐색 및 트레이드오프 (Trade-off)

우리는 세 가지 접근 방식을 두고 트레이드오프를 검토했습니다.

| 아키텍처 대안 | 장점 | 단점 / 채택하지 않은 이유 |
| :--- | :--- | :--- |
| **대안 A: 요청 시마다 외부 API 실시간 집계** | DB 저장 공간 불필요, 항상 최신 데이터 | 외부 API 장애 시 서비스 전체 마비, 높은 네트워크 지연(Latency) |
| **대안 B: 전수 원격 DB 적재 및 상시 쿼리** | 전통적이고 직관적인 RDBMS 구조 | 수만 건 성분의 반복 I/O로 인한 **서버리스 네트워크 할당량 고갈**, DB 장애 시 분석 기능 완전 중단 |
| **대안 C: 빌드 타임 정적 스냅샷 + In-Memory 캐시 (채택)** | **DB 부하 99% 제거**, 서브 밀리초(sub-ms) 매칭 속도, 무상 인프라 한도 내 장기 운용 가능 | 신규 성분 추가 시 캐시 갱신/동기화 전략 필요 |

우리는 **대안 C(Local-First In-Memory Tiering)**를 선택했습니다. 빈번한 조회 패턴을 가진 정적 성분 사전 데이터의 특성을 활용해, DB가 아닌 애플리케이션 메모리 계층에서 대부분의 트래픽을 흡수하도록 설계했습니다.

## 3. 핵심 아키텍처 및 구현 (Solution)

```
[클라이언트 스캔 요청]
        │
        ▼
┌──────────────────────────────────────────────┐
│ 백엔드 인메모리 매처 (L1 Cache)                │
│  - 사전 컴파일된 마스터 데이터셋 즉각 대조     │
└───────┬──────────────────────────────┬───────┘
  (99% Hit: < 1ms 응답)          (1% Miss: 미식별 성분)
        │                              │
        ▼                              ▼
  [결과 즉시 반환]             ┌────────────────────────┐
                               │ 실시간 공공 API 호출 (L2)│
                               └───────────┬────────────┘
                                           │
                                           ▼
                               ┌────────────────────────┐
                               │  원격 DB 비동기 적재 (L3)│
                               └────────────────────────┘
```

### 1) 다중 공공 데이터 매쉬업 및 알레르기 사전 표준화
배치 및 빌드 파이프라인에서 3대 공공 성분 API(성분 마스터, 배합 한도, 규제 정보)를 식별자 기준으로 정규화(Normalization)하여 병합했습니다. 여기에 **EU CosIng 및 국내 고시 알레르기 유발 표준 데이터(82종/25종)**를 하이브리드로 결합하여 단일 성분 객체에 배합 한도와 알레르기 플래그가 완결된 형태로 포함되도록 가공했습니다.

### 2) 로컬 스냅샷 기반의 계층형 조회 (Tiered Lookup Engine)
* **L1 (In-Memory Snapshot):** 병합된 데이터를 컴파일 시점에 최적화된 정적 스냅샷 파일로 빌드하고, 서버 구동 시 메모리에 적재합니다. 99% 이상의 성분 조회는 원격 DB 네트워크 통신 없이 애플리케이션 내부 메모리에서 Sub-millisecond 속도로 완결됩니다.
* **L2 / L3 (Fallback & Persistence):** 사전에 없는 극소수의 신규·희귀 성분에 한해서만 외부 API를 실시간 조회(L2)하고 원격 DB에 영속화(L3)합니다.

### 3) 데이터 정합성 보장 (No-Mock 원칙)
데이터의 엄밀성을 위해 불완전한 예측용 가짜(Mock) 데이터를 완전히 배제했습니다. 매칭에 실패한 성분은 임의 추정치 대신 명확한 `unmatched` 상태로 분류하고, 프론트엔드에 투명하게 가시화하여 사용자가 오판하지 않도록 안전성을 확보했습니다.

## 4. 엔지니어링 성과 및 배운 점 (Takeaways)

### 📊 정량적 성과
* **원격 DB I/O 및 네트워크 전송량 99% 이상 절감:** 고빈도 매칭 로직을 메모리 계층으로 격리하여 제한된 서버리스 DB 무료 할당량 내에서도 안정적인 무비용 운영 기반을 확보했습니다.
* **성분 분석 처리 속도 대폭 단축:** 네트워크 홉(Network Hop)을 제거하여 대량 성분 리스트도 1ms 내외로 고속 매칭을 수행합니다.
* **장애 격리(Fault Tolerance):** 원격 DB에 일시적인 장애나 슬립 모드가 발생하더라도, 핵심 분석 엔진은 로컬 인메모리 스냅샷을 통해 100% 가동되는 회복 탄력성을 달성했습니다.

### 💡 엔지니어링 인사이트
1. **"모든 데이터를 DB에 둘 필요는 없다"**: 읽기 빈도가 압도적으로 높고 변경 주기가 긴 기준 데이터(Reference Data)는 **'로컬-퍼스트(Local-First)'** 접근 방식을 취할 때 인프라 비용과 응답 속도 모두에서 압도적인 이점을 얻을 수 있음을 확인했습니다.
2. **도메인 데이터의 깊이가 제품의 경쟁력**: 단순 이름 매칭에 그치지 않고 규제 한도와 글로벌 알레르기 데이터를 하나의 파이프라인으로 엮어냄으로써, 엔지니어링 레벨에서 데이터의 비즈니스 가치를 한 단계 끌어올릴 수 있었습니다.
