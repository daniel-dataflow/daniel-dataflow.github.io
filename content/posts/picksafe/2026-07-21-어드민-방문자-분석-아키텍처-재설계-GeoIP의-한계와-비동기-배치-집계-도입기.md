화장품 성분 분석 서비스 PickSafe를 개발하면서, 어드민 기능 내에 서비스 운영 의사결정을 도울 방문자 분석 모듈을 구축해야 했습니다. 

초기 구상 단계에서는 실시간 세션 추적이나 접속 국가 지도 시각화 같은 화려한 지표들을 수집하는 방안을 고려했습니다. 하지만 제한된 인프라 리소스 환경에서 무턱대고 모든 이벤트를 수집하고 실시간으로 집계하는 방식은 데이터베이스 커넥션과 CPU 대역폭에 무리를 줄 것이 명확했습니다.

또한 서비스 특성상 한국에 방문한 외국인 관광객의 사용 비중이 높은 편인데, 단순히 접속 IP 기반으로 위치를 추적하면 현지 로망/유심망 접속으로 인해 대다수가 한국(`KR`)으로 분류되는 심각한 데이터 오염 문제가 존재했습니다.

이 글에서는 서비스의 제한된 리소스를 효율적으로 방어하면서도, 오염되지 않은 실질적인 유저 분석 데이터를 수집하기 위해 고민하고 적용했던 아키텍처 개선 과정을 기록합니다.

## 🎯 마주한 고민과 문제 배경

어드민 방문자 분석 기능을 기획하고 설계하는 과정에서 세 가지 핵심 문제에 직면했습니다.

### 1. 실시간 집계 쿼리로 인한 DB 성능 병목
유저가 어드민 대시보드에 접근할 때마다 원본 로그 테이블에 `COUNT`, `GROUP BY` 연산을 포함한 무거운 실시간 쿼리를 실행하는 구조는 위험했습니다. 트래픽이 몰리는 상황에서 운영 대시보드 조회가 메인 서비스의 트랜잭션 성능에 직접적인 악영향을 미칠 수 있었습니다.

### 2. GeoIP(IP 기반 위치 추적)의 정합성 한계
방한 외국인 유저의 다국어 지원 우선순위를 판단하기 위해 사용자의 언어/국가 정보가 필요했습니다. 그러나 IP 주소 기반의 GeoIP 라이브러리(MaxMind 등)를 활용할 경우, 한국 현지 통신사 망을 이용하는 관광객 유저의 접속지가 모두 한국(`KR`)으로 오판독되었습니다. 이는 실제 서비스 유저층의 특성을 전혀 반영하지 못하는 오염된 데이터였습니다.

### 3. 과도한 개인정보 수집 및 Vanity Metrics
실시간 접속 세션 목록이나 상세 IP 주소 수집은 개인정보 관리 부담을 늘릴 뿐만 아니라, 실제 제품 개선에 기여하지 못하는 '허영 지표(Vanity Metrics)'에 가까웠습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

문제를 해결하기 위해 수집 대상 지표를 과감히 축소하고, 데이터 수집 및 집계 방식을 변경하는 대안을 비교 검토했습니다.

### 대안 1: GeoIP 라이브러리 vs Accept-Language & User-Agent 분석

| 비교 항목 | GeoIP (IP 기반 위치 분석) | Accept-Language & User-Agent 직접 파싱 |
| :--- | :--- | :--- |
| **국가/언어 정합성** | 관광객 접속 시 한국(`KR`)으로 오분류 가능성 높음 | 기기 자체 설정 언어 및 OS 환경을 100% 정밀 추적 |
| **개인정보 리스크** | IP 주소 저장 필요 (개인정보 식별 위험) | IP 미저장 (헤더의 파싱된 정보만 가공하여 저장) |
| **시스템 리소스** | IP DB 업데이트 및 외부 조회 부하 발생 | HTTP 요청 헤더 문자열 파싱 (추가 I/O 없음) |
| **결정** | ❌ 탈락 | **✅ 최종 선택** |

네트워크 접속 위치가 아닌 유저 기기의 실제 언어 설정(`Accept-Language`)을 최우선 신뢰 데이터로 채택했습니다. 기기 사양 정보 또한 헤더의 `User-Agent`를 파싱하여 Mobile/Desktop 구분 및 OS 환경 통계만 추출하는 방식을 선택했습니다.

### 대안 2: 실시간 대시보드 쿼리 vs 이벤트 로그 + 비동기 배치 요약

| 비교 항목 | 실시간 쿼리 방식 | 배치 집계 요약 방식 (`daily_analytics_summary`) |
| :--- | :--- | :--- |
| **데이터 신선도** | 즉시 반영 (Real-time) | 일 단위 집계 (T-1 비동기 반영) |
| **DB 부하** | 대시보드 로딩 시마다 원본 테이블 전체 스캔 | 요약된 단일/소수 행만 조회하여 부하 0
