사이드 프로젝트나 초기 스타트업 단계에서 글로벌 서비스를 준비할 때, 가장 먼저 마주하는 고민 중 하나는 **"다국어(i18n)를 어떻게 처리할 것인가"**입니다. 

화장품 성분 및 안전성 분석 플랫폼 **PickSafe**를 개발하면서, 초기 단계의 제한된 리소스(1인 개발, 무료 티어 인프라) 속에서 유료 번역 API의 비용 압박과 오번역 리스크를 피하고, 확장성을 확보하기 위해 내린 아키텍처 의사결정 과정을 공유합니다.

---

## 1. Problem: 초기 서비스가 마주한 다국어 처리의 딜레마

초기 기획 단계에서 다국어 지원은 피할 수 없는 요구사항이었습니다. 하지만 상세 설계로 들어가자 구조적인 문제가 나타났습니다.

* **동적 콘텐츠의 폭발적인 증가:** 사용자가 스캔하는 성분명, 제품명, 분석 결과 등의 데이터는 끝없이 생성됩니다. 이 모든 동적 데이터를 실시간 번역 API로 처리한다면 **예상치 못한 비용 폭탄**과 **API 호출 지연(Latency)**을 초래할 수 있습니다.
* **안전성 리스크:** 성분 안전성이나 알레르기 유발 물질 안내 문구는 정확도가 생명입니다. 기계 번역(Machine Translation)의 오번역은 치명적인 안전 사고(법적/신뢰도 문제)로 이어질 수 있습니다.
* **운영의 불편함:** 개발자가 일일이 소스코드 내 JSON 파일을 수정하고 배포하는 방식은 1인 개발 환경에서 지속 가능하지 않습니다.

---

## 2. Trade-off & Architecture: 무엇을 버리고 무엇을 취할 것인가

모든 것을 번역하려던 기존의 욕심을 내려놓고, **콘텐츠의 성격에 따라 전략을 이분화**하는 트레이드오프를 단행했습니다.

### ① 동적 콘텐츠: "번역"을 포기하고 "표준"을 믿다
* **결정:** 1차 MVP에서는 동적 콘텐츠 자동 번역을 전면 배제했습니다.
* **근거:** 화장품 성분명(INCI, `ingredients_master.inci_name`)은 이미 라틴어/영어 기반의 국제 표준이며, 한국 식약처 고시도 이를 따릅니다. 즉, 성분명 자체는 언어 중립적이므로 별도의 번역이 필요 없습니다. 
* **처리:** 한국어(식약처 원문)와 영어(INCI 표준)를 그대로 노출하고, 그 외 언어권 사용자에게도 동일한 원문을 보여줍니다. (추후 언어별 유입 통계를 보고 자동 번역 도입 여부를 재논의합니다.)

### ② 정적 콘텐츠: DB 기반 통합 관리와 인메모리 캐싱
UI 텍스트(버튼, 라벨, 안내 문구 등)와 같이 유한한 집합을 가진 정적 콘텐츠는 별도의 `translations` 테이블로 통합 관리하기로 했습니다.

```sql
-- 설계된 translations 테이블 스키마 (개념 모델)
translations
- id                UUID, PK
- entity_type       VARCHAR(20)   -- 'ui_string' (현재) / 'ingredient', 'product' (향후 확장용)
- entity_key        VARCHAR(255)  -- 예: 'result.no_flagged'
- locale            VARCHAR(10)   -- 'ko', 'en', 'ja', 'zh-CN', 'zh-TW', 'pt'
- text              TEXT
- updated_at        TIMESTAMP
- UNIQUE(entity_type, entity_key, locale)
```

* **비용 절감 및 성능 최적화:** 매 요청마다 DB를 조회하는 것은 비효율적이므로, **서버 기동 시 전체 번역 데이터를 메모리에 캐싱**하고, 어드민에서 수정이 발생할 때만 캐시를 갱신하도록 설계했습니다. (Neon 무료 티어 환경에서도 충분히 소화 가능한 가벼운 규모입니다.)
* **안전한 폴백(Fallback) 체인:** 
  `요청 언어` ➔ `영어(en)` ➔ **`entity_key` 문자열 자체 노출**
  번역 누락 시 빈 화면이나 조용한 에러 대신 키 값을 그대로 노출하여, 운영자가 어드민 화면에서 누락된 번역을 즉시 인지하고 수정할 수 있게 했습니다.

### ③ 타겟 언어 선정의 전략적 접근
단순 방한객 통계뿐만 아니라 비즈니스적 확장성을 고려해 우선순위를 재조정했습니다.
1. **한국어, 영어** (기본)
2. **중국어(간체), 일본어, 중국어(번체)** (방한객 통계 기반 상위권 국가)
3. **포르투갈어** (방한객 통계와는 무관하나, 브라질 소재 협력 여행사와의 파일럿 테스트를 위한 **전략적 채택**)

## 3. Takeaway: 엔지니어링 교훈

1. **"모든 것을 자동화/동적화"하려는 유혹 경계하기**
   스타트업 초기 단계에서는 비즈니스적 가치와 기술적 구현 비용을 엄격히 저울질해야 합니다. 모든 텍스트를 자동 번역하려 하기보다, "꼭 번역이 필요한 영역(정적 UI)"과 "표준으로 커버 가능한 영역(성분명)"을 분리하는 것이 훨씬 현실적이고 강건한 아키텍처를 만듭니다.
2. **확장성을 고려한 유연한 스키마 설계**
   현재는 UI 텍스트(`ui_string`)만을 대상으로 하지만, `entity_type`과 `entity_key` 패턴을 도입함으로써 향후 동적 콘텐츠 번역이나 타 도메인으로 확장할 때도 스키마 변경 없이 대응할 수 있는 기반을 다졌습니다.
3. **운영자(Human) 친화적인 시스템이 곧 최고급 자동화**
   코드 배포 없이 어드민 화면에서 `ko` 원문과 타국어 번역을 나란히 대조하며 수정할 수 있게 만든 구조는, 1인 개발/소규모 팀에서 품질을 유지하는 가장 강력한 무기입니다.
