서비스를 글로벌로 확장하거나 다양한 국적의 사용자를 맞이할 때, 다국어(i18n) 지원은 피할 수 없는 과제입니다. 특히 뷰티·성분 분석 서비스를 운영하다 보면 UI에 들어가는 정적 문구뿐만 아니라, 끝없이 확장되는 화장품 성분명이나 제품 설명 같은 '동적 콘텐츠'까지 번역해야 하는가에 대한 고민에 부딪히게 됩니다.

이번 포스팅에서는 **1인 개발 및 초기 스타트업 환경**에서 유료 번역 API 비용과 운영 리소스를 최소화하면서도, 확장성을 잃지 않는 다국어 시스템을 설계한 의사결정 과정을유출된 보안 정보 없이 아키텍처 관점에서 공유하려 합니다.

---

## 1. Problem: 무엇을 마주했는가?

서비스 개발 초기, 다국어 처리 방식에 대해 다음과 같은 미결정 과제들이 산적해 있었습니다.
- **번역 범위의 모호성:** 모든 텍스트(UI 버튼, 안내 문구부터 동적으로 생성되는 성분명, 스캔 결과까지)를 일괄적으로 번역해야 하는가?
- **비용과 리스크:** 사용자 스캔 데이터에 따라 무한정 늘어나는 동적 콘텐츠를 자동 번역 API로 처리할 경우, **유료 API 비용 발생** 및 안전 관련 문구의 **오번역 리스크**(안전 지침 위배 소지)가 존재했습니다.
- **운영의 불편함:** 코드 배포 없이 기획자나 운영자가 실시간으로 문구를 수정할 수 있어야 하는 요구사항이 있었습니다.

---

## 2. Trade-off & Architecture: 기술적 고민과 대안 비교

이 문제를 해결하기 위해 **"번역 대상을 어디까지 한정할 것인가"**와 **"어떻게 저장하고 서빙할 것인가"** 두 가지 측면에서 아키텍처를 고민했습니다.

### ① 콘텐츠의 분리: 정적 vs 동적
* **정적 콘텐츠 (UI 텍스트, 라벨, 안내/면책 문구 등):** 
  * DB에 저장하고 어드민 화면에서 직접 관리하도록 결정했습니다. 
* **동적 콘텐츠 (성분명, 제품명, 스캔 결과 등):** 
  * **1차 MVP에서는 번역을 전면 보류**하기로 했습니다.
  * *근거:* 화장품 성분명(INCI 표준)은 EU 규정 및 식약처 고시에 따라 이미 라틴어/영어 기반의 국제 표준(언어 중립적)을 따릅니다. 즉, 성분명 자체는 별도의 번역이 불필요하며, 한국어(식약처 원문)와 영어(INCI 표준)만 그대로 노출해도 글로벌 사용자에게 충분히 전달됩니다. 
  * 자동 번역 API 도입은 향후 언어권별 실제 유입 비율 데이터를 확인한 뒤 재논의하기로 했습니다.

### ② 단일 테이블 통합 설계 (`translations` 테이블)
향후 동적 콘텐츠 확장 가능성을 열어두면서도 현재의 복잡도를 낮추기 위해, 하나의 테이블로 다국어를 관리하는 구조를 택했습니다.

```sql
-- 개념적 스키마 구조
translations
- id                UUID (PK)
- entity_type       VARCHAR  -- 'ui_string' (현재) / 'ingredient', 'product' (향후 확장용)
- entity_key        VARCHAR  -- 리소스 식별 키 (예: 'result.no_flagged')
- locale            VARCHAR  -- 'ko', 'en', 'ja', 'zh-CN', 'zh-TW', 'pt'
- text              TEXT     -- 번역된 텍스트
- updated_at        TIMESTAMP
-- UNIQUE (entity_type, entity_key, locale)
```

- **확장성:** `entity_type`과 `entity_key` 조합을 통해, 추후 성분이나 제품 설명 번역이 필요해지더라도 스키마 변경 없이 데이터만 늘려나갈 수 있도록 설계했습니다.
- **전략적 언어 선정:** 방한객 통계(중국어 간체/번체, 일본어)를 반영하되, 브라질 협력사와 파일럿 테스트를 위해 포르투갈어(`pt`)를 선제적으로 포함했습니다. 테이블 구조 덕분에 새로운 언어 추가 시 `locale`만 늘리면 되어 기술적 장벽이 전혀 없습니다.

### ③ 성능 최적화: 인메모리 캐싱과 폴백 체인
* **DB 부하 최소화:** 매 요청마다 번역 데이터를 조회하면 데이터베이스에 불필요한 부하가 갑니다. 이를 해결하기 위해 **서버 기동 시 `translations` 전체를 메모리에 캐싱**하고, 어드민에서 문구가 수정될 때만 캐시를 갱신하도록 구현했습니다. (현재 소규모~중견 규모의 DB 티어에서 비용 부담 없이 완벽히 동작합니다.)
* **안전한 폴백(Fallback) 체인:** 
  1. 요청한 언어가 없으면 기본 언어(`en`)로 폴백
  2. `en`조차 없다면 **`entity_key` 값 자체를 화면에 그대로 노출**
  * *Takeaway:* 빈 문자열이나 에러로 조용히 넘어가면 개발 단계에서 번역 누락을 인지하기 어렵습니다. 키 값을 그대로 노출함으로써 운영자가 어드민이나 화면에서 누락을 즉시 발견하고 수정할 수 있도록 유도했습니다.

## 3. Takeaway: 무엇을 배웠는가?

1. **"모든 것을 자동화할 필요는 없다" (범위의 미학):** 
   모든 텍스트를 AI나 번역 API로 자동 번역하려 했다면 비용 폭탄과 오번역이라는 두 마리 토끼를 다 놓칠 뻔했습니다. 도메인의 특성(INCI 표준의 언어 중립성)을 파악하고 번역 대상을 유한한 집합(정적 UI)으로 좁힌 것이 핵심 승리 요인이었습니다.
2. **미래를 대비하되 과도한 엔지니어링은 피하기:**
   당장 쓰지 않는 동적 콘텐츠 번역 기능을 위해 복잡한 파이프라인을 구축하는 대신, `entity_type` 컬럼 하나로 향후 확장을 수용할 수 있는 유연한 스키마만 미리 확보해 두었습니다. 
3. **개발자 중심의 에러 가시성:**
   번역 누락 시 빈 화면을 보여주는 대신 키 자체를 노출하는 폴백 정책은, 1인 개발 및 소규모 팀에서 운영 리소스를 극적으로 줄여주는 훌륭한 디버깅/운영 포인트가 되었습니다.

비용을 쓰지 않고도 견고하고 확장 가능한 i18n 아키텍처를 고민하고 계신다면, "정적/동적 콘텐츠의 분리"와 "인메모리 캐싱" 조합을 강력히 추천합니다.
