안녕하세요, **PickSafe** 프로젝트를 진행하며 백엔드와 아키텍처를 담당하고 있는 시니어 개발자입니다. 

서비스의 글로벌 확장성을 고민하다 보면 언젠가 반드시 마주하게 되는 산이 있습니다. 바로 **다국어(i18n) 지원**입니다. 

이번에 PickSafe의 초기 아키텍처를 다듬는 과정에서, "모든 텍스트를 실시간으로 자동 번역하자"는 매혹적인 유혹을 뿌수고, **지속 가능한 현실적인 i18n 전략**을 수립한 과정을 공유하고자 합니다. 1인 개발 환경이나 초기 스타트업에서 무분별한 외부 API 도입으로 겪을 수 있는 트랩을 어떻게 피했는지 집중해서 봐주세요.

---

## 1. Problem: 무엇을 해결해야 했는가?

서비스가 성장함에 따라 한국어 외에 영어, 중국어(간체/번체), 일본어, 그리고 비즈니스 파트너십을 위한 포르투갈어까지 다양한 언어권의 사용자를 맞이할 준비를 해야 했습니다.

초기 기획 단계에서는 다음과 같은 막연한 요구사항이 있었습니다.
* *"화면에 노출되는 모든 텍스트(UI 문구부터 성분 설명까지)를 다국어로 지원해야 한다."*
* *"새로운 성분이나 제품 데이터가 들어오면 자동으로 번역되어야 하지 않을까?"*

하지만 기술 리더의 관점에서 이는 몇 가지 심각한 **기술적/비즈니스적 리스크**를 내포하고 있었습니다.

1. **비용 폭탄과 오번역 리스크:** 
   사용자가 스캔하는 방대한 동적 콘텐츠(성분명, 제품 설명 등)를 매번 유료 번역 API로 처리하면 비용이 선형적으로 증가합니다. 무엇보다 화장품 성분이나 안전 관련 문구는 **오번역 시 치명적인 안전 문제**로 직결될 수 있습니다.
2. **배포의 병목:** 
   프론트엔드 코드에 JSON 파일 형태로 i18n 딕셔너리를 박아두면, 문구 하나를 고칠 때마다 코드를 수정하고 빌드/배포를 해야 합니다. 1인 개발 체제에서 이는 큰 운영 부하입니다.

---

## 2. Trade-off & Architecture: 어떻게 해결할 것인가?

이 문제를 해결하기 위해 아키텍처 레벨에서 **콘텐츠의 성격을 분리**하고, **번역의 범위를 극단적으로 좁히는 타협(Trade-off)**을 선택했습니다.

### ① 콘텐츠의 이원화 (정적 vs 동적)
* **정적 콘텐츠 (UI 텍스트, 버튼, 안내 문구 등):** 
  * DB에 저장하고 어드민 화면에서 직접 관리합니다.
  * 개발자 배포 없이 어드민에서 즉시 수정 가능하도록 설계했습니다.
* **동적 콘텐츠 (성분명, 제품명 등):** 
  * **1차 MVP에서는 자동 번역을 과감히 제외**했습니다.
  * 화장품 성분명(INCI, `ingredients_master.inci_name`)은 이미 EU 규정 및 식약처 고시에 따라 라틴어/영어가 표준화된 **언어 중립적 데이터**입니다. 따라서 한국어(식약처 원문)와 영어(INCI 표준)를 그대로 노출하고, 그 외 언어권 사용자에게도 동일한 원문을 보여주는 방식을 택했습니다. (번역 누락과 데이터 누락을 엄격히 구분)

### ② 확장성을 고려한 단일 테이블 스키마 (`translations`)
정적/동적 콘텐츠를 모두 포용할 수 있도록 유연하면서도 단순한 단일 테이블 구조를 설계했습니다.

```sql
CREATE TABLE translations (
    id UUID PRIMARY KEY,
    entity_type VARCHAR(20)   -- 'ui_string' (현재) / 'ingredient', 'product' (향후 확장용)
    entity_key VARCHAR(255),  -- 예: 'result.no_flagged'
    locale VARCHAR(10),       -- 'ko', 'en', 'ja', 'zh-CN', 'zh-TW', 'pt' 등
    text TEXT,
    updated_at TIMESTAMP,
    CONSTRAINT unique_translation UNIQUE (entity_type, entity_key, locale)
);
```

### ③ 운영 효율성을 위한 엔지니어링 디테일
* **메모리 캐싱:** 서버 기동 시 `translations` 전체를 메모리에 적재하여 매 요청마다 DB를 조회하는 I/O 비용을 없앴습니다. (현재 DB인 Neon 무료 티어 환경에서도 충분히 가볍고 빠르게 동작합니다.) 어드민에서 문구가 수정될 때만 캐시를 갱신합니다.
* **폴백(Fallback) 체인과 가시성 확보:** 
  요청한 언어의 번역이 없으면 `en`을 찾고, 그래도 없으면 **`entity_key` 값 자체를 화면에 그대로 노출**하도록 했습니다. 빈 문자열로 조용히 넘어가 사용자를 당황하게 만드는 대신, 어드민 관리자가 화면에서 누락된 키를 즉시 인지하고 수정할 수 있게 만든 안전장치입니다.

## 3. Takeaway: 무엇을 배웠는가?

1. **"모든 것을 자동화할 필요는 없다" (오버엔지니어링 경계):**
   인공지능과 자동 번역 API가 흔한 시대이지만, 비즈니스의 도메인 특성(화장품 성분 표준화 등)을 정확히 이해하면 번역 비용과 리스크를 원천 차단할 수 있습니다. 
2. **데이터와 운영의 분리:**
   1인 개발 및 소규모 팀일수록 "코드 배포 없는 콘텐츠 운영" 환경이 생산성에 엄청난 차이를 만듭니다. DB 기반의 어드민 번역 관리 기능은 향후 서비스가 성장했을 때도 훌륭한 자산이 될 것입니다.
3. **확장 가능한 제네릭 설계:**
   현재는 UI 텍스트(`ui_string`) 위주로 사용하지만, 추후 동적 콘텐츠 번역이 꼭 필요해지는 시점이 오더라도 스키마 변경 없이 `entity_type` 확장만으로 대응할 수 있는 구조를 마련했습니다.

완벽한 자동화보다 **"지금 우리 서비스 규모에 가장 알맞은 지속 가능한 아키텍처"**를 선택하는 것, 그것이 시니어 개발자가 가져야 할 기술적 결단력이 아닐까 생각합니다. 

PickSafe의 글로벌 도약기를 앞으로도 지켜봐 주세요!
