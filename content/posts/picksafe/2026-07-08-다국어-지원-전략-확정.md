안녕하세요. 뷰티/헬스케어 데이터 플랫폼 **PickSafe**를 개발하고 있는 시니어 에디터입니다.

서비스를 글로벌로 확장하거나, 국내 체류 외국인을 타겟으로 삼는 순간 피할 수 없는 과제가 바로 **다국어(i18n) 지원**입니다. 초기 스타트업이나 1인 개발 환경에서 이 요구사항을 마주하면 흔히 두 가지 함정에 빠지곤 합니다.
1. "모든 텍스트(유저 생성 콘텐츠 포함)를 실시간 번역 API로 붙이자!" (비용 폭탄 및 오번역 리스크)
2. "모든 언어별 JSON 파일을 형상 관리하고, 배포할 때마다 빌드하자!" (운영 지옥)

이번 포스팅에서는 PickSafe 프로젝트에서 한정된 리소스(비용, 인력)를 극복하고, 확장성과 유지보수성을 모두 챙기기 위해 내린 **현실적인 다국어(i18n) 아키텍처 의사결정 과정**을 공유합니다.

---

## 1. 문제 정의 (Problem): 무엇을 번역할 것인가?

서비스를 고도화하면서 마주한 가장 큰 고민은 **"데이터의 성격에 따라 번역의 가치와 비용이 다르다"**는 점이었습니다. 

* **정적 콘텐츠:** 버튼, 라벨, UI 안내 문구, 면책 조항 등 (유한한 집합)
* **동적 콘텐츠:** 사용자 스캔 결과, 화장품 성분명, 제품명 등 (무한히 확장되는 데이터)

초기 기획 단계에서는 이 둘을 명확히 구분하지 않고 일괄적으로 다국어 처리를 하려다 보니, API 비용 문제와 안전성(화장품 성분 오번역 시 법적/안전 리스크)이라는 거대한 장벽에 부딪혔습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 아키텍처 원칙을 세우고, 몇 가지 대안을 저울질했습니다.

### 원칙 1: 동적 콘텐츠는 "번역"이 아닌 "원문 그대로 노출"
화장품 성분명(INCI, `ingredients_master.inci_name`)은 이미 EU 규정 및 한국 식약처 고시에 따른 국제 표준(라틴어/영어)입니다. 즉, 성분명 자체는 언어 중립적이므로 별도의 번역이 필요 없습니다. 
* **결정:** 1차 MVP에서는 자동 번역 API나 유료 서비스 도입을 과감히 보류했습니다. 한국어(식약처 원문)와 영어(INCI 표준)만 그대로 노출하고, 그 외 언어권 사용자에게도 동일한 표준 표기를 제공합니다. 번역 누락과 데이터 누락을 엄격히 분리하여 안전성을 확보했습니다.

### 원칙 2: 정적 콘텐츠는 DB 통합 관리 + 메모리 캐싱
파일 기반(JSON) i18n은 1인 개발 환경에서 코드 배포 없이 문구를 수정할 수 없다는 치명적인 단점이 있습니다. 어드민 화면에서 실시간으로 문구를 제어할 수 있어야 했습니다.

그렇다고 모든 요청마다 DB를 조회하는 것은 무료 티어(예: Neon DB) 환경이나 성능 측면에서 비효율적입니다.

* **해결책:** 
  1. 단일 `translations` 테이블로 정적 콘텐츠를 통합 관리합니다. (추후 확장성 고려)
  2. **서버 기동 시 전체 번역 데이터를 메모리에 캐싱**하고, 어드민에서 수정이 발생할 때만 캐시를 갱신합니다.

```sql
-- 적용된 translations 테이블 구조 (요약)
CREATE TABLE translations (
    id UUID PRIMARY KEY,
    entity_type VARCHAR(20),   -- 'ui_string' (현재) / 'ingredient', 'product' (확장용)
    entity_key VARCHAR(255),   -- 예: 'result.no_flagged'
    locale VARCHAR(10),        -- 'ko', 'en', 'ja', 'zh-CN', 'pt' 등
    text TEXT,
    UPDATED_AT TIMESTAMP,
    CONSTRAINT unique_translation UNIQUE (entity_type, entity_key, locale)
);
```

### 폴백(Fallback) 체인 전략
번역 데이터가 누락되었을 때의 사용자 경험(UX)도 중요합니다. 빈 문자열로 조용히 넘어가면 디버깅이 어렵습니다.
* **요청 언어** → 없으면 **`en` (영어)** → 그래도 없으면 **`entity_key` 값 자체를 화면에 노출**

개발자나 운영자가 화면을 보다가 키 값이 그대로 노출되면 누락된 번역임을 즉시 인지하고 어드민에서 바로 수정할 수 있도록 설계했습니다.

## 3. 지원 언어 선정의 비즈니스 로직

방한객 통계와 비즈니스 전략을 결합하여 지원 언어 우선순위를 합리적으로 정의했습니다.

1. **한국어, 영어** (기본)
2. **중국어(간체)** (방한객 비중 1위, 약 35%)
3. **일본어** (방한객 비중 2위, 약 17%)
4. **중국어(번체)** (대만·홍콩 타겟)
5. **포르투갈어** (**전략적 채택**: 통계적 근거는 없으나, 브라질 소재 협력 여행사 파일럿 테스트를 위해 `translations` 테이블의 `locale` 확장성만 믿고 과감히 추가)

이 구조 덕분에 스페인어 등 향후 언어 추가 요구사항이 들어와도 스키마 변경 없이 `locale` 데이터만 늘리면 되는 확장성을 확보했습니다.

---

## 4. 엔지니어링 교훈 (Takeaways)

1. **오버엔지니어링 경계하기:** 모든 것을 자동 번역 API로 해결하려 하기보다, 데이터의 성격을 분석해 "반드시 번역해야 하는 것(정적 UI)"과 "표준을 그대로 써도 되는 것(동적 성분명)"을 분리하는 것이 비용과 안정성 측면에서 훨씬 유리합니다.
2. **운영 편의성이 곧 개발 생산성:** 1인 개발/소규모 팀일수록 JSON 파일 관리에서 벗어나 DB + 어드민 조합으로 문구를 실시간 제어할 수 있는 환경을 만드는 것이 장기적인 유지보수 비용을 획기적으로 낮춰줍니다.
3. **유연한 스키마 설계:** 당장은 쓰지 않더라도(`entity_type='ui_string'`), 향후 도메인 확장(성분, 제품 설명 등)을 염두에 둔 추상화된 테이블 구조를 설계해 두면 나중에 코드를 갈아엎는 재앙을 막을 수 있습니다.
