안녕하세요. 1인 개발로 서비스를 빌드하다 보면, "이 기능을 지금 꼭 만들어야 할까?" 혹은 "어떤 기술 스택을 써야 비용과 유지보수 측면에서 가장 유리할까?"라는 고민에 부딪히곤 합니다.

이번 포스팅에서는 **PickSafe** 프로젝트에서 다국어(i18n) 지원 기능을 설계하며 마주한 기술적 고민과, 오버엔지니어링을 피하기 위해 내린 아키텍처 의사결정 과정을 공유하려 합니다.

---

## 1. Problem: 무엇을 해결해야 했는가?

글로벌 서비스를 지향하는 프로덕트라면 다국어 지원은 피할 수 없는 과제입니다. 하지만 초기 MVP(Minimum Viable Product) 단계에서 모든 텍스트를 무작정 자동 번역(DeepL, Google Translate API 등)에 의존하려니 다음과 같은 명확한 리스크가 존재했습니다.

1. **비용 및 운영 리스크:** 사용자 생성 데이터나 동적 콘텐츠까지 모두 실시간 API로 번역하면 예상치 못한 유료 API 비용이 발생합니다.
2. **안전성 및 오번역 리스크:** 화장품 성분 및 안전성 관련 문구에서 오번역이 발생할 경우, 사용자에게 치명적인 정보 오류를 전달할 수 있습니다.
3. **배포의 병목:** 개발자가 직접 코드 내 JSON이나 로컬 파일로 다국어를 관리하면, 문구 수정 하나에도 코드 빌드 및 배포 과정이 필요해집니다.

---

## 2. Trade-off & Architecture: 왜 이런 방식을 선택했는가?

고민 끝에 우리는 **"콘텐츠의 성격을 분리하고, 번역 범위를 최소화한다"**는 원칙을 세웠습니다.

### ① 정적/동적 콘텐츠의 분리
* **동적 콘텐츠 (성분명, 제품명 등):** 1차 MVP에서는 **별도 번역을 하지 않고 원문을 그대로 노출**하기로 했습니다. 화장품 성분명은 이미 EU 규정에 따른 INCI 표준(라틴어/영어)과 국내 식약처 고시(한글)를 따르고 있어 언어 중립적이기 때문입니다. 자동 번역 도입은 향후 유입 데이터를 보고 결정합니다.
* **정적 콘텐츠 (UI 텍스트, 안내/면책 문구 등):** 사용자와 직접 소통하는 유한한 집합의 텍스트이므로, 철저하게 관리 가능한 구조를 설계했습니다.

### ② 확장성을 고려한 단일 `translations` 테이블 설계
정적/동적 콘텐츠를 모두 수용할 수 있도록 유연한 구조의 단일 테이블을 설계했습니다.

```sql
-- 보안상 핵심 비즈니스 로직 및 제약조건은 간소화된 형태로 표현합니다.
CREATE TABLE translations (
    id UUID PRIMARY KEY,
    entity_type VARCHAR(20),   -- 'ui_string' (현재) / 'ingredient', 'product' (향후 확장)
    entity_key VARCHAR(255),   -- 예: 'result.no_flagged'
    locale VARCHAR(10),        -- 'ko', 'en', 'ja', 'zh-CN', 'zh-TW', 'pt'
    text TEXT,
    updated_at TIMESTAMP
);
```
* **유연성:** 향후 동적 콘텐츠 번역이 필요해지더라도 스키마 변경 없이 `entity_type`과 `entity_key`를 확장하여 재사용할 수 있습니다.
* **전략적 언어 선정:** 방한객 통계(중국, 일본 등)를 기반으로 우선순위를 정하되, 브라질 협력사와 파일럿 테스트를 위해 포르투갈어(`pt`)를 전략적으로 조기 채택했습니다. 

### ③ 인메모리 캐싱과 Fallback 체인
* **캐싱 전략:** 서비스 기동 시 `translations` 전체를 메모리에 로드하고, 어드민 페이지에서 수정이 발생할 때만 캐시를 갱신하도록 했습니다. 데이터 규모가 작아 무료 DB 티어 환경에서도 매 요청마다 DB를 조회하는 부하를 완전히 차단했습니다.
* **Fallback 체인:** 요청한 언어가 없다면 영어(`en`)로, 영어도 없다면 화면에 빈 문자열 대신 **`entity_key` 자체를 노출**하도록 설계했습니다. 이를 통해 번역 누락을 개발 단계나 어드민에서 즉각적으로 인지할 수 있게 했습니다.

---

## 3. Takeaway: 무엇을 배웠는가?

1. **완벽한 자동화보다 '제어 가능성'이 우선이다:** 
   초기 단계에서 무리한 자동 번역 API 도입은 비용과 오번역 리스크만 가중시킵니다. "번역할 대상"과 "원문 그대로 노출할 대상"을 명확히 구분하는 것이 엔지니어링 리소스를 아끼는 지름길입니다.
2. **코드 없는(Code-less) 콘텐츠 운영:** 
   개발자가 아닌 운영자(또는 어드민 사용자)가 직접 UI 문구를 수정할 수 있어야 진정한 서비스 운영이 가능해집니다. DB 기반의 i18n과 어드민 관리 툴의 결합은 1인 개발 환경에서 생산성을 극대화해 줍니다.
3. **미래를 대비하되, 구현은 당장 필요한 만큼만:** 
   향후 동적 콘텐츠까지 확장할 수 있는 테이블 구조(`entity_type` 분리)를 미리 설계해 두었음에도, 1차 MVP 구현 범위에서는 과감히 제외함으로써 일정의 지연을 막을 수 있었습니다.
