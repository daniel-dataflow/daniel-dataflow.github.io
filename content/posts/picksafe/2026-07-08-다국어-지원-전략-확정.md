제품이 성장하며 글로벌 사용자를 맞이할 준비를 할 때, 가장 먼저 마주하는 고민 중 하나는 '다국어 지원(i18n)'입니다. 특히 1인 개발 환경이나 초기 스타트업이라면 무분별한 자동 번역 도입이 가져올 **비용 폭탄과 데이터 품질 저하**를 경계해야 합니다. 

이번 글에서는 저희 서비스 'PickSafe'가 어떻게 효율적인 다국어 관리 체계를 구축했는지, 그 의사결정 과정을 공유합니다.

---

### 1. 문제 정의: 번역은 '모두' 해야 할까?

초기 설계 단계에서 가장 큰 고민은 "성분명이나 제품 정보 같은 동적 콘텐츠까지 모두 자동 번역 API를 태워야 하는가?"였습니다. 하지만 다음 두 가지 이유로 이는 잘못된 접근임을 깨달았습니다.

*   **비용과 리스크:** 동적 콘텐츠는 사용자 데이터에 따라 무한히 늘어납니다. 이를 매번 유료 API로 번역하면 고정 비용이 크게 발생하고, 안전 관련 문구의 오번역이 발생할 경우 서비스 신뢰도에 치명적입니다.
*   **언어 중립성(Language Neutrality):** 화장품 성분명(INCI)은 그 자체로 국제 표준입니다. 한국 식약처와 글로벌 규정이 동일한 표준을 따르기 때문에, 굳이 번역할 필요 없이 원문을 그대로 노출하는 것이 정확도 측면에서 훨씬 유리했습니다.

**결론적으로, 우리는 '정적 UI 텍스트'와 '동적 데이터'를 분리하고, 정적 콘텐츠만 관리하기로 했습니다.**

---

### 2. 기술적 고민: 왜 DB 기반의 중앙 관리인가?

많은 프로젝트가 `JSON`이나 `YAML` 파일을 통한 번역 관리를 선택합니다. 하지만 1인 개발 환경에서는 **"코드 배포 없이 실시간 수정"**이 서비스 운영 효율의 핵심입니다.

#### 아키텍처 선택: `translations` 테이블 설계
모든 UI 텍스트를 단일 DB 테이블로 관리하여 다음과 같은 이점을 확보했습니다.

```sql
-- 테이블 구조 예시 (추상화)
- entity_type: 'ui_string' (향후 제품/성분 확장 가능)
- entity_key: UI 내 참조 키 (예: 'result.no_flagged')
- locale: 'ko', 'en', 'ja', 'pt' 등
- text: 실제 번역 값
```

*   **효율적 캐싱:** 서버 기동 시 전체 번역 데이터를 메모리에 로드(In-memory caching)합니다. DB 부하를 원천 차단하면서도, 어드민 페이지에서 수정 시 즉시 캐시를 갱신하여 별도의 배포 과정 없이 문구를 실시간으로 변경합니다.
*   **폴백(Fallback) 전략:** 요청한 언어 데이터가 없을 경우 `en`을 우선 보여주고, 그마저도 없다면 **`entity_key` 자체를 노출**하도록 설계했습니다. 이는 개발자가 번역 누락을 화면에서 즉시 발견할 수 있게 하는 '디버깅 편의성'을 제공합니다.

---

### 3. 엔지니어링 교훈 및 Takeaway

이번 설계 과정을 통해 얻은 핵심 배움은 **"지금 당장 필요한 것에 집중하고, 미래의 확장을 위한 구조만 닦아두는 것"**입니다.

1.  **데이터 분류의 미학:** 모든 데이터를 번역 대상(UI 텍스트)과 원문 노출 대상(성분 데이터)으로 명확히 구분함으로써, API 비용은 아끼면서 서비스 품질은 높였습니다.
2.  **확장성을 고려한 설계:** 현재는 `ui_string`만 관리하지만, 테이블 구조를 `entity_type`으로 일반화하여 추후 제품/성분 데이터 번역이 필요해지더라도 스키마 변경 없이 로직 확장만으로 대응 가능하도록 설계했습니다.
3.  **운영 최우선 원칙:** 코드 레벨에서의 관리가 아닌 어드민 페이지를 통한 관리를 선택함으로써, 기술적 부채를 최소화하고 운영 공수를 획기적으로 줄였습니다.

**글로벌 진출을 고민하는 동료 개발자분들께:**
번역은 단순히 언어를 바꾸는 문제가 아니라, 우리 서비스의 정보를 어떤 철학으로 전달할지 결정하는 아키텍처 설계입니다. 무조건적인 자동화보다는 **'비즈니스 맥락에 맞는 번역 범위 획정'**부터 시작해 보시는 건 어떨까요?
