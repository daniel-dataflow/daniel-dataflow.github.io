제품의 글로벌 진출을 고려할 때, 다국어(i18n) 지원은 피할 수 없는 과제입니다. 하지만 초기 스타트업이나 1인 개발 환경에서 무턱대고 상용 번역 API를 도입하거나 복잡한 로케일 관리 시스템을 구축하는 것은 과도한 엔지니어링(Over-engineering)이 되기 쉽습니다.

이번 포스팅에서는 **PickSafe** 프로젝트를 진행하며 마주한 다국어 처리 미결정 과제를 어떻게 현실적이고 확장성 있게 해결했는지, 그 아키텍처 의사결정 과정(Trade-off)과 엔지니어링 교훈을유기적으로 공유합니다.

---

## 1. 문제 정의 (Problem)

초기 기능 정의 단계에서 다국어 처리는 다음과 같은 난제들을 안고 있었습니다.

1. **비용과 안전성 리스크:** 무한히 생성되는 동적 콘텐츠(사용자 스캔으로 발생하는 성분/제품 텍스트)를 모두 자동 번역하려 하면 막대한 API 비용이 발생합니다. 특히 화장품 성분 및 안전성 문구의 오번역은 치명적인 사용자 경험 저하와 신뢰도 하락으로 이어집니다.
2. **운영의 번거로움:** 텍스트 수정이 필요할 때마다 코드를 수정하고 재배포하는 방식은 1인 개발/운영 체제에서 엄청난 병목이 됩니다.
3. **확장성 부재:** 단순히 한국어/영어에 그치지 않고, 방한객 통계에 기반한 중국어(간체/번체), 일본어, 그리고 전략적 파트너십을 위한 포르투갈어까지 유연하게 수용할 수 있는 구조가 필요했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 아키텍처 레벨에서 두 가지 큰 결정을 내렸습니다.

### ① 콘텐츠의 성격에 따른 분리 (정적 vs 동적)
* **동적 콘텐츠 (성분명, 제품명 등):** 
  * 결론: **1차 MVP에서는 번역하지 않음 (원문 노출 원칙)**
  * 이유: 화장품 성분명(INCI 표준)은 이미 라틴어/영어 기반의 국제 표준이며 식약처 고시도 이를 따릅니다. 즉, 성분명 자체는 언어 중립적이므로 별도의 번역 비용을 들일 이유가 없습니다. 번역 누락과 데이터 누락을 엄격히 구분하여, 매칭 실패 성분은 "확인 불가"로 처리합니다.
* **정적 콘텐츠 (UI 텍스트, 안내/면책 문구 등):**
  * 결론: **DB 테이블 통합 관리 + 인메모리 캐싱**
  * 이유: 유한한 집합인 UI 텍스트는 완벽한 커버리지가 필요합니다. 코드 배포 없는 문구 수정을 위해 JSON 파일 대신 DB와 어드민 UI를 결합했습니다.

### ② 확장 가능한 `translations` 스키마 디자인
향후 동적 콘텐츠로 번역 범위를 확장하더라도 스키마 변경 없이 대응할 수 있도록 `entity_type` 패턴을 도입했습니다.

```sql
-- 민감 정보 및 비즈니스 로직을 제외한 범용 i18n 스키마 예시
CREATE TABLE translations (
    id UUID PRIMARY KEY,
    entity_type VARCHAR(20),   -- 'ui_string' (현재) / 'ingredient', 'product' (향후 확장)
    entity_key VARCHAR(255),   -- 식별용 키 (예: 'result.no_flagged')
    locale VARCHAR(10),        -- 'ko', 'en', 'ja', 'zh-CN', 'zh-TW', 'pt'
    text TEXT,
    updated_at TIMESTAMP,
    CONSTRAINT unique_translation UNIQUE (entity_type, entity_key, locale)
);
```

## 3. 최종 해결 및 구현 방식 (Solution)

* **어드민 중심의 번역 관리:** `ko` 원문 컬럼을 고정하고 나머지 언어 컬럼을 나란히 배치하여, 누락된 번역(빈 셀)을 한눈에 대조하고 수정할 수 있는 어드민 메뉴를 설계했습니다.
* **인메모리 캐싱으로 DB 부하 최소화:** 서버 기동 시 `translations` 전체를 메모리에 로드하고, 어드민에서 수정이 발생할 때만 갱신하도록 구현하여 매 요청마다 발생하는 DB I/O를 원천 차단했습니다 (무료 티어 DB 환경에서도 성능 최적화 달성).
* **안전한 폴백(Fallback) 체인:** 
  `요청 언어` ➔ `없으면 'en'` ➔ `그래도 없으면 entity_key 자체를 화면에 노출`
  * 빈 문자열이나 에러로 조용히 넘어가기보다, 개발자나 운영자가 화면에서 누락된 키를 즉시 인지할 수 있도록 방어적으로 설계했습니다.

---

## 4. 엔지니어링 교훈 (Takeaways)

1. **"모든 것을 자동화할 필요는 없다" (비즈니스적 타협):** 
   모든 텍스트를 AI나 번역 API로 해결하려 하기보다, 도메인 특성(INCI 표준 성분명 등)을 깊이 이해하면 번역 대상 범위를 극단적으로 줄여 비용과 리스크를 동시에 제어할 수 있습니다.
2. **미래를 대비하는 유연한 스키마:** 
   현재는 UI 텍스트(`ui_string`)만 다루지만, 설계 단계에서 `entity_type`과 `entity_key`를 분리해둠으로써 향후 데이터 모델의 대수술 없이 기능을 확장할 수 있는 발판을 마련했습니다.
3. **운영 편의성이 곧 시스템 안정성이다:** 
   1인 개발 환경에서 코드가 아닌 어드민 화면을 통해 실시간으로 문구를 제어하고 누락을 시각적으로 검증할 수 있는 환경은 운영 공수를 획기적으로 줄여줍니다.

작은 규모의 프로젝트라 하더라도, 아키텍처의 원칙과 확장 가능성을 치밀하게 고민한 경험은 앞으로 더 큰 트래픽과 복잡도를 다룰 때 강력한 자산이 될 것입니다.
