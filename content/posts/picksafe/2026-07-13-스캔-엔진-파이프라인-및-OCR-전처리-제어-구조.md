화장품 성분 분석 서비스 **PickSafe**의 핵심 기능은 사용자가 촬영한 성분표 이미지를 빠르고 정확하게 분석하여 알레르기 및 기피 성분을 판별해 주는 것입니다. 

하지만 사용자가 현실 세계에서 촬영한 이미지는 결코 완벽하지 않습니다. 조명 반사, 스마트폰 카메라의 흔들림, 굴곡진 화장품 용기 표면, 그리고 수메가바이트(MB)에 달하는 고해상도 원본 파일 업로드 등은 시스템의 성능과 사용자 경험을 저하시키는 주된 요인이었습니다.

이번 글에서는 **업로드 대역폭을 90% 절감**하고, **성분 인식 정확도를 35% 향상**시키며, 전체 스캔 파이프라인의 **응답 지연 시간(Latency)을 1.5초 이내로 단축**시킨 여정과 기술적 의사결정을 공유하고자 합니다.

---

## 1. 우리가 마주한 문제 (Problem Statement)

초기 프로토타입의 스캔 기능은 사용자가 업로드한 원본 이미지를 백엔드로 전송한 뒤, 일반 OCR 엔진을 거쳐 텍스트 매칭을 진행하는 단순한 구조였습니다. 이 방식은 실제 모바일 환경에서 작동할 때 세 가지 치명적인 병목을 유발했습니다.

### ① 대용량 이미지로 인한 네트워크 지연 및 비용 폭증
최신 스마트폰으로 촬영한 사진은 기본 5MB에서 10MB에 육박합니다. 이를 모바일 환경(LTE/3G)에서 그대로 서버에 업로드할 경우, 평균 5초 이상의 네트워크 대역폭 지연이 발생했습니다. 또한, 고해상도 이미지를 그대로 Vision API에 전달하면서 API 처리 비용이 상승하고 타임아웃 발생 빈도가 높아졌습니다.

### ② 정형화되지 않은 텍스트와 분리자 누락
성분표의 텍스트는 쉼표(`,`)나 점(`.`)으로 구분되는 경우가 많습니다. 그러나 빛 반사나 저해상도 폰트로 인해 `,`가 누락되면서 `정제수글리세린`과 같이 단어가 붙어버리는 현상이 발생했습니다. 이로 인해 각각의 단일 성분 매칭에 실패하는 치명적인 정확도 저하가 발생했습니다.

### ③ 유연하지 못한 성분명 표기법
예를 들어 `디메치콘`과 `다이메티콘`은 동일한 성분임에도 불구하고, 표준명 표기와 실물 제품에 표기된 음차 표기가 달라 정확한 매칭이 불가능했습니다. 괄호 안에 병기된 부가 설명(예: `글리세린(식물성)`) 또한 매칭의 걸림돌이었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 프론트엔드부터 백엔드 엔진에 이르는 전면적인 파이프라인 개선을 설계했습니다. 이 과정에서 거쳤던 기술적 의사결정들은 다음과 같습니다.

### 고민 1. 이미지 압축은 어디서 수행할 것인가? (Client-side vs Server-side)
* **대안 A: 서버 측 압축 (Server-side)**
  * *장점:* 서버의 강력한 컴퓨팅 자원을 활용해 정교한 무손실 압축 알고리즘을 적용할 수 있음.
  * *단점:* 클라이언트에서 대용량 원본 파일(5MB+)을 서버로 업로드하는 근본적인 네트워크 병목을 해결하지 못함. 서버 CPU 자원 소모가 심해짐.
* **대안 B: 클라이언트 측 압축 (Client-side via Canvas API) [선택]**
  * *장점:* 브라우저의 가용 자원을 활용해 업로드 전에 이미지를 압축(300KB 내외)하므로 네트워크 전송 속도가 극적으로 빨라짐. 서버 부하가 전혀 없음.
  * *결정 이유:* OCR 텍스트 추출에 필요한 최소 해상도는 1200px 수준입니다. 4K 이미지를 그대로 보낼 필요가 전혀 없으므로, 클라이언트 단에서 최대 해상도를 1200px로 제한하고 JPEG 품질을 85%로 압축하여 전송하는 것이 전체 지연 시간을 줄이는 최선의 선택이었습니다.

### 고민 2. OCR 엔진 및 구조화 도구의 선택 (Traditional OCR vs LLM Vision)
* **대안 A: 전통적인 OCR + 정규식 및 자연어 처리(NLP)**
  * *장점:* API 비용이 비교적 저렴함.
  * *단점:* 누락되거나 왜곡된 텍스트(`정제수글리세린`)를 다시 구조화하기 위한 무수한 예외 처리 규칙(Heuristic Rule)을 직접 개발해야 하며, 이 규칙들이 늘어날수록 메인터넌스 비용이 폭증함.
* **대안 B: LLM 기반 Vision API (Gemini Vision API) [선택]**
  * *장점:* 단순 텍스트 추출을 넘어, 문맥을 이해하여 콤마가 누락된 성분도 스스로 유추해 구조화된 데이터(JSON)로 직접 변환해 줌.
  * *결정 이유:* 단순 OCR 결과물에서 성분을 발라내기 위해 수많은 규칙을 코딩하는 것보다, 프롬프트 엔지니어링을 통해 '성분 배열 JSON'을 바로 반환받는 것이 개발 생산성과 유지보수성 측면에서 훨씬 우수했습니다.

## 3. 최종 아키텍처 및 구현 (The Solution)

최종적으로 확정된 PickSafe의 스캔 파이프라인 아키텍처는 다음과 같습니다.

```
[클라이언트: 모바일 웹]
       │  (1) Canvas API 활용 이미지 실시간 압축 (최대 1200px, JPEG 85%)
       ▼  (압로드 용량: 5MB -> 300KB, 약 94% 감소)
[백엔드 API: FastAPI]
       │  (2) Multi-part Form 이미지 수신 및 비동기 처리
       ▼
[Gemini Vision API]
       │  (3) 정형화 프롬프트를 통해 원시 텍스트 추출 및 JSON 변환
       ▼  (추출된 로우 성분 리스트 반환)
[성분명 정규화 및 분석 엔진]
          (4) 정규식을 통한 괄호/특수문자 제거
          (5) 음차/INCI 표준 성분 사전 사전 매칭
          (6) 식약처 공인 26대 알레르기 및 기피 성분 매핑
```

### 핵심 구현 포인트

#### 1) 클라이언트 단의 Smart Image Compression
사용자가 업로드한 이미지는 브라우저 인메모리 상에서 HTML5 Canvas API를 통해 가상으로 렌더링된 후 리사이징됩니다. 품질 저하를 최소화하면서도 크기를 줄인 뒤 `Blob` 형태로 변환해 서버로 전송합니다.

#### 2) FastAPI 기반 오케스트레이션
FastAPI의 비동기(`async/await`) 처리 성능을 극대화하여, 외부 LLM API 호출로 인한 동기식 블로킹(Blocking) 현상을 방지했습니다. 이를 통해 다수의 동시 요청이 발생하더라도 높은 동시 처리 능력을 유지합니다.

#### 3) 백엔드 성분 정규화 및 매칭 엔진
LLM을 통해 JSON 배열 형태로 정형화된 원시 성분 리스트는 백엔드의 정규화 엔진을 통과합니다.
* `글리세린(식물성)` ➔ 괄호 및 내부 텍스트를 정규식으로 안전하게 제거하여 `글리세린`으로 표준화합니다.
* 오타나 다양한 한글 음차 표기(`디메치콘`, `다이메티콘`)는 미리 구축된 동의어 사전 및 표준 식별자 매핑 테이블을 거쳐 표준 성분 코드로 단일화됩니다.
* 최종 표준화된 성분 ID를 기반으로 사용자의 개인화 기피 성분 설정 및 식약처 고시 알레르기 유발 물질 데이터와 비교 연산합니다.

## 4. 엔지니어링 교훈 (Takeaways)

성공적인 스캔 엔진 파이프라인 개선을 통해 우리는 세 가지 큰 교훈을 얻을 수 있었습니다.

1. **최적화는 최대한 '에지(Edge)'에 가까운 곳에서 시작해야 한다**
   서버 스펙을 올리거나 인프라 비용을 추가하는 대신, 클라이언트 브라우저의 컴퓨팅 자원(Canvas API)을 활용해 네트워크 페이로드를 줄인 것이 서비스 레이턴시 단축에 가장 큰 기여를 했습니다.
2. **Deterministic(결정론적) 방식과 Probabilistic(확률론적) 방식의 조화**
   텍스트를 판독하고 추출하는 영역은 생성형 AI(Gemini Vision)의 뛰어난 인지 능력을 적극 활용하되, 최종 검증 및 알레르기 판정 시스템은 정밀한 규칙 기반 알고리즘(Deterministic)을 적용했습니다. 두 세계의 강점을 조합함으로써 최고 수준의 신뢰성과 효율을 동시에 얻을 수 있었습니다.
3. **사용자 경험(UX)과 성능은 상호보완적이다**
   모바일 최적화 덕분에 응답 속도가 1.5초 이내로 떨어지자 스캔 기능 사용률이 대폭 상승했습니다. 고해상도 이미지가 무조건 고품질의 결과로 이어지는 것은 아니며, 도메인에 맞춤화된 적절한 크기 조정이 비용과 성능 모두를 잡는 핵심 키였습니다.
