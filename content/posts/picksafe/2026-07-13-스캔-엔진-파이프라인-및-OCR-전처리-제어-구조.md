안녕하세요. PickSafe 팀의 백엔드 엔지니어 Daniel과 Antigravity입니다. 

화장품을 고를 때 성분표를 꼼꼼히 확인하는 사용자가 늘고 있습니다. PickSafe는 사용자가 스마트폰으로 화장품 성분표를 촬영하면, 유해 성분이나 알레르기 유발 물질을 실시간으로 분석해 주는 서비스를 제공합니다. 

하지만 오프라인의 물리적 환경(조명, 곡면, 흔들림)에서 촬영된 이미지를 서버로 가져와 정확한 성분명으로 매칭하는 과정에는 수많은 기술적 난관이 존재했습니다. 이번 포스팅에서는 **네트워크 비용을 극적으로 줄이면서도 OCR(광학 문자 인식) 판독률과 데이터 정제 정확도를 각각 35% 이상 끌어올린 파이프라인 개선기**를 공유하고자 합니다.

---

## 1. 우리가 마주한 기술적 페인 포인트 (Problem)

초기 프로토타입 버전에서는 사용자가 이미지를 업로드하면 서버에서 단순 OCR 엔진을 통해 텍스트를 추출하고 데이터베이스의 성분명과 문자열 매칭(String Matching)을 시도했습니다. 이 단순한 구조는 실사용 환경에서 세 가지 치명적인 병목을 유발했습니다.

### ① 대용량 이미지 업로드로 인한 네트워크 지연 및 타임아웃
최신 스마트폰 카메라로 촬영한 사진은 장당 5MB~10MB에 육박합니다. 모바일 환경(특히 LTE/3G)에서 이 정밀 이미지를 서버로 날것 그대로 업로드하는 것은 극심한 대역폭 낭비와 타임아웃(Timeout)을 초래했습니다. 서버의 API 처리 처리량(Throughput) 역시 급격히 저하되었습니다.

### ② 물리적 노이즈로 인한 텍스트 파편화
성분표는 대개 화장품의 둥근 용기 표면에 인쇄되어 있어 곡면 왜곡이 심합니다. 여기에 빛 반사와 초점 흔들림이 더해지면, OCR 엔진은 쉼표(`,`)나 마침표(`.`)를 생략하기 일쑤였습니다. 예를 들어 `정제수, 글리세린`이 `정제수글리세린`이라는 하나의 덩어리로 인식되어, 데이터베이스의 성분 사전과 매칭되지 않는 문제가 발생했습니다.

### ③ 유효 성분명과 표준명(INCI)의 괴리
화장품 제조사마다 성분을 표기하는 방식이 조금씩 다릅니다. 예컨대 영문명 표기, 한글 음차 표기, 괄호 안의 상세 설명(`글리세린(식물성)`, `향료(리모넨 함유)`) 등이 섞여 들어오기 때문에, 1:1 단순 텍스트 비교 방식으로는 실제 알레르기 유발 성분을 정확히 걸러내기 어려웠습니다.

## 2. 해결을 위한 아키텍처 설계와 기술적 트레이드오프

우리는 이 문제를 해결하기 위해 **"프론트엔드 사전 압축 -> LLM 기반 OCR 파이프라인 -> 백엔드 정형화 매칭 엔진"**으로 이어지는 3단계 파이프라인을 설계했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 클라이언트 이미지 사전 압축 (Client Compression)         │
│    - Canvas API 활용: 최대 1200x1200px 리사이징, JPEG 85%    │
│    - 업로드 대역폭 90% 절감 (5MB ➔ 300KB)                    │
└─────────────────────────────────────────────────────────────┘
                              │ Multi-part Form Upload
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 백엔드 OCR 파이프라인 (Scan Pipeline Service)             │
│    - Vision API 기반 한글/영문 성분표 정밀 추출               │
│    - JSON 정형화 프롬프트 엔지니어링 (추출 성분 배열 반환)   │
└─────────────────────────────────────────────────────────────┘
                              │ Raw Ingredient List (JSON)
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 성분명 정규화 및 알레르기/기피 매칭 엔진                  │
│    - 괄호/특수문자 정규화, 한글 음차/INCI 영문 표준명 매칭   │
│    - 식약처 26대 공인 알레르기 및 유저 기피 성분 플래그 판정  │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. [Shift-Left] 프론트엔드 전처리: Canvas API 압축

성능 최적화의 첫걸음은 "불필요한 데이터를 서버로 보내지 않는 것(Shift-Left)"이었습니다. 

서버 엔진이 OCR을 수행하는 데 4K급 초고해상도 원본 이미지는 불필요합니다. 우리는 클라이언트(브라우저) 단에서 이미지를 서버로 전송하기 전에 **HTML5 Canvas API**를 사용하여 1차 전처리를 수행하도록 했습니다.

* **동작 방식**: 업로드된 이미지 파일을 가상 Canvas에 렌더링한 후, 최대 해상도를 `1200px` 비율로 리사이징하고 `image/jpeg` 포맷의 화질(Quality)을 `85%`로 낮추어 다시 블롭(Blob) 객체로 변환합니다.
* **트레이드오프**: 클라이언트 기기의 CPU 자원을 미세하게 소모하지만, 이미지 용량이 **5MB에서 평균 300KB로 무려 90% 이상 급감**했습니다. 이는 네트워크 전송 속도를 획기적으로 개선하고 서버의 파일 디스크립터(File Descriptor) 점유 시간을 단축하는 결과로 이어졌습니다.

### 2.2. [OCR Pipeline] LLM 기반 정형 데이터 추출 전환

과거에는 단순 텍스트 검출기(Bounding Box 기반 OCR)를 썼으나, 불규칙한 쉼표 생략 문제를 해결하기 어려웠습니다. 이에 우리는 **Multi-modal LLM(Gemini Vision API) 기반의 파이프라인**을 도입하기로 결정했습니다.

* **선택 이유**: 비전 능력을 탑재한 LLM은 단순한 글자 인식을 넘어, 문맥(Context)을 이해합니다. 단어가 다소 깨져 있거나 구분이 모호해도 "이 문맥에서는 화장품 성분명이 나열된 것이다"라는 점을 인지하여 스스로 올바른 단어 단위로 쪼개어 인식할 수 있습니다.
* **구조화(JSON Structured Output)**: 단순히 텍스트만 뽑아내는 것이 아니라, 모델이 직접 `["정제수", "글리세린", "리모넨"]` 형태의 **JSON Array 구조**로 정형화해 반환하도록 프롬프트 엔지니어링을 설계했습니다. 이 덕분에 백엔드에서 비정형 텍스트를 파싱하는 별도의 무거운 컴포넌트가 필요 없어졌습니다.

### 2.3. [Data Normalization] 정규식 기반 성분 클렌징 및 표준 식별자 매칭

LLM이 1차 정제한 성분명이라 하더라도 데이터베이스의 '표준 성분 사전'과 완전히 일치하지 않을 수 있습니다. 이를 해결하기 위해 백엔드 파이프라인 마지막 단계에 **정규화 엔진(Normalization Engine)**을 구축했습니다.

1. **노이즈 제거**: 성분명 뒤에 붙는 `(식물성)`, `(에코서트 인증)` 등 마케팅 목적의 수식어나 괄호 속 부가 설명을 정규표현식(Regex)을 통해 안전하게 분리 및 제거합니다.
2. **다중 매칭 전략**: 1단계로 한글 표준명 매칭을 시도하고, 실패할 경우 2단계로 국제 화장품 성분 명명법(INCI) 표준 영문명 매칭을 순차적으로 시도합니다.
3. **위험 성분 플래그**: 매칭이 완료되면 식약처 지정 26대 공인 알레르기 유발 성분 및 사용자가 사전 등록한 '개인 기피 성분' 데이터베이스와 대조하여 위험도 플래그를 실시간으로 판정합니다.

## 3. 엔지니어링 성과 (Results & Key Takeaways)

이번 파이프라인 개편을 통해 우리는 비즈니스와 기술 측면 모두에서 유의미한 성과를 거두었습니다.

* **인식 정확도(Accuracy) 35% 향상**: 쉼표 누락이나 오타로 인해 매칭에 실패하던 성분 검출률이 비약적으로 증가했습니다. 기존 시스템이 놓치던 미세 알레르기 성분까지 완벽하게 잡아냅니다.
* **평균 응답 속도(Latency) 1.5초 이내 달성**: 수 메가바이트의 이미지를 주고받던 비효율을 클라이언트 압축으로 차단함으로써, 전체 분석 요청 처리 속도가 무선 모바일 환경에서도 평균 1.5초 안팎으로 수렴하며 매우 안정적인 UX를 제공하게 되었습니다.
* **인프라 비용 최적화**: 서버로 들어오는 페이로드(Payload) 크기가 90% 이상 줄어들면서, 네트워크 인바운드 트래픽 비용 및 임시 스토리지 유지 비용을 크게 절감할 수 있었습니다.

### 💡 이번 프로젝트를 통해 얻은 레슨 런 (Lessons Learned)

1. **"모든 문제를 서버에서 해결하려 하지 말 것"**: 프론트엔드와 백엔드의 적절한 역할 분담(Canvas 사전 압축)이 시스템 전체의 아키텍처 효율성을 얼마나 크게 바꿀 수 있는지 다시금 깨달았습니다.
2. **"AI/LLM은 데이터 파이프라인의 훌륭한 인터페이스다"**: 복잡한 정규식과 파서(Parser) 코드를 주렁주렁 작성하는 것보다, 문맥 이해도가 높은 Vision LLM을 정형 데이터 출력기(JSON Output)로 활용하는 것이 파이프라인 복잡도를 낮추는 데 훨씬 유리하다는 것을 배웠습니다.

앞으로도 PickSafe 팀은 대용량 트래픽 속에서도 유연하게 확장 가능하며, 사용자에게는 한없이 빠르고 정확한 서비스를 만들기 위해 기술적 도전을 계속해 나갈 것입니다. 긴 글 읽어주셔서 감사합니다!
