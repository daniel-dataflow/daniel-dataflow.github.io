안녕하세요. PickSafe 팀의 백엔드 엔지니어 Daniel과 Antigravity입니다.

사용자가 화장품 성분표를 사진으로 찍으면, 유해 성분이나 알레르기 유발 물질을 즉시 분석해 주는 서비스는 편리하지만 기술적으로는 매우 까다로운 도전 과제입니다. 사용자가 완벽한 스튜디오 조명 아래에서 스캔하듯 사진을 찍지 않기 때문입니다. 

실제 유저들은 **둥근 화장품 용기(곡면 왜곡), 형광등 불빛(조명 반사), 흔들린 초점, 그리고 초고화질(4K) 이미지 업로드로 인한 네트워크 지연** 등 온갖 '실환경 노이즈'를 가지고 서비스를 찾아옵니다.

오늘 포스팅에서는 PickSafe 팀이 이러한 한계를 극복하고, **성분 인식 정확도를 35% 끌어올리는 동시에 분석 레이턴시를 1.5초 이내로 안정화**한 여정과 그 과정에서의 기술적 의사결정(Trade-off)을 공유하고자 합니다.

---

## 1. 우리가 마주한 세 가지 문제 (Problem)

초기 프로토타입 버전에서는 클라이언트가 찍은 원본 이미지를 그대로 서버로 전송한 뒤, 오픈소스 OCR 엔진을 통해 텍스트를 추출하고 단순 문자열 매칭을 시도했습니다. 하지만 실제 운영 환경에서는 다음과 같은 심각한 병목과 실패를 마주했습니다.

### ① 대용량 이미지 업로드로 인한 네트워크 지연 & 비용 상승
최신 스마트폰으로 촬영한 원본 사진은 장당 5MB에서 크게는 10MB에 육박합니다. 모바일 네트워크 환경에서 이 정도 크기의 이미지를 서버로 업로드하는 것은 평균 5초 이상의 지연(Latency)을 유발했고, 백엔드 서버 인프라 및 OCR API 호출 비용을 기하급수적으로 증가시켰습니다.

### ② 텍스트 분리 실패 (Delimiter Missing)
둥근 화장품 용기에 적힌 성분표는 줄바꿈이나 쉼표(`,`), 점(`.`)이 흐리게 인쇄되어 있거나 빛 반사로 날아가는 경우가 많습니다. 이로 인해 OCR 엔진이 `정제수, 글리세린`을 `정제수글리세린`이라는 하나의 텍스트로 인식하여 데이터베이스의 표준 성분명과 매칭되지 않는 현상이 발생했습니다.

### ③ 성분명 표기 오인식 및 유사어 처리 한계
제조사마다 `디메치콘`, `다이메티콘` 등 성분명을 다르게 표기하거나, OCR 판독 오류로 인해 오타가 발생했을 때 표준 INCI(국제화장품성분명) 데이터베이스와 매칭되지 않아 분석 결과가 누락되는 치명적인 문제가 있었습니다.

## 2. 해결을 위한 기술적 설계와 트레이드오프 (Trade-off)

우리는 이 문제를 해결하기 위해 **클라이언트(Edge) - 백엔드 파이프라인 - 데이터 매칭 엔진**으로 이어지는 3단계 아키텍처를 재설계했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 클라이언트 이미지 사전 압축 (Client Compression)         │
│    - Canvas API 활용: 최대 1200x1200px 리사이징, JPEG 85%    │
│    - 업로드 대역폭 90% 절감 (5MB ➔ 300KB)                    │
└─────────────────────────────────────────────────────────────┘
                              │ Multi-part Form Upload
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 백엔드 OCR 파이프라인 (Scan Pipeline Service)             │
│    - Gemini Vision API 기반 한글/영문 성분표 정밀 추출       │
│    - JSON 정형화 프롬프트 엔지니어링 (추출 성분 배열 반환)   │
└─────────────────────────────────────────────────────────────┘
                              │ Raw Ingredient List
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 성분명 정규화 및 알레르기/기피 매칭 엔진                  │
│    - 괄호/특수문자 정규화, 한글 음차/INCI 영문 표준명 매칭   │
│    - 식약처 26대 공인 알레르기 및 유저 기피 성분 플래그 판정  │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. [Trade-off 1] 이미지 압축: 서버에서 할 것인가, 클라이언트에서 할 것인가?
가장 먼저 해결해야 할 것은 업로드 대역폭이었습니다.

* **대안 A (서버 측 압축):** 클라이언트가 원본을 올리면 백엔드에서 OpenCV나 Pillow 라이브러리로 리사이징합니다. 이 방식은 클라이언트 연산 부담은 줄지만, **5MB가 넘는 원본 파일이 네트워크를 타야 하므로 대역폭 낭비와 네트워크 지연 문제를 전혀 해결하지 못합니다.**
* **대안 B (클라이언트 측 사전 압축 - 선택):** 브라우저 단에서 HTML5 `Canvas API`를 활용해 이미지를 인메모리 상에서 최대 1200x1200px 해상도로 리사이징하고, JPEG 품질 85%로 압축하여 업로드합니다.

**선택 이유:** 
실험 결과, 1200px 수준의 해상도는 OCR 텍스트 인식률에 영향을 주지 않으면서도 파일 크기를 **5MB에서 300KB 수준으로 90% 이상 절감**할 수 있었습니다. 사용자 기기의 가벼운 연산으로 서버 트래픽 비용과 레이턴시를 획기적으로 개선하는 방향을 선택했습니다.

### 2.2. [Trade-off 2] OCR 기술 스택: 전통적 OCR vs LLM 기반 Vision API
성분표 텍스트의 구조화(Structured Parsing) 문제를 해결하기 위한 도구를 비교했습니다.

* **대안 A (기존 OCR + 후처리 정규식 파서):** 일반적인 Cloud OCR을 사용해 텍스트 영역(Bounding Box)과 글자를 받아온 뒤, 백엔드에서 쉼표나 줄바꿈 기준으로 파싱합니다. 하지만 굴곡진 표면에서 단어가 누락되거나 합쳐지는 예외 케이스를 정규식만으로 대응하기엔 한계가 있었습니다.
* **대안 B (Gemini Vision API + 구조화 프롬프트 - 선택):** 구글의 Gemini Vision 모델을 활용합니다. 단순히 글자를 읽는 것을 넘어, "이미지 내 성분표 영역을 찾아 성분명들을 정형화된 JSON 배열 형태로 반환하라"는 지시를 프롬프트 엔지니어링을 통해 전달합니다.

**선택 이유:**
LLM 기반의 Vision API는 이미지의 맥락을 이해합니다. 즉, 글자가 약간 찌그러지거나 쉼표가 누락되어도, 전후 문맥(화장품 성분명 패턴)을 인지하여 스스로 올바른 단어 단위로 쪼개어 JSON 배열로 만들어 줍니다. 약간의 API 호출 비용 상승이 있었으나, **후처리 파이프라인의 복잡성을 대폭 낮추고 인식 정확도를 높이는 데 압도적으로 유리**하다고 판단했습니다.

### 2.3. 데이터 파이프라인: 정규화 및 안전 매칭 엔진
LLM이 1차로 정제해 준 성분 배열이라도 실서비스에 적용하려면 결정론적(Deterministic)인 매칭 엔진이 필요합니다. 성분명 뒤에 붙은 부가 설명(`글리세린(식물성)`, `향료(리모넨 함유)`)이나 영문 표기명 등을 깔끔하게 걸러내기 위해 다음과 같은 표준화 규칙을 적용했습니다.

1. **괄호 및 특수문자 제거:** 정규식을 통해 핵심 성분명 주위의 부가 정보를 표준화합니다.
2. **동의어 사전 매칭:** 식품의약품안전처 및 국제화장품성분(INCI) 사전을 기반으로, 한글 음차 차이(`디메치콘` vs `다이메티콘`)를 단일 표준 식별자로 맵핑합니다.
3. **안전성 판정 기법:** 매칭된 표준 식별자를 기준으로 식약처 고시 26대 알레르기 유발 물질 및 유저가 설정한 개인별 기피 성분을 O(1) 복잡도로 고속 판정합니다.

## 3. 결과 및 도입 성과 (Results)

이 아키텍처 개편을 통해 우리 서비스는 괄목할 만한 성능 개선을 이루어냈습니다.

* **인식 정확도(Accuracy) 35% 향상:** 조명 반사나 용기 굴곡으로 인해 기존에 매칭되지 않던 성분들이 Gemini Vision의 맥락 인지 능력 덕분에 대부분 완벽히 복원되었습니다.
* **레이턴시(Latency) 평균 1.5초 이내 안정화:** 클라이언트 단의 Canvas 사전 압축 덕분에 무거운 이미지 전송 시간이 사라졌고, 전체 API 처리 속도가 크게 단축되었습니다.
* **네트워크 비용 절감:** 이미지 평균 용량이 90% 이상 감소하면서 데이터 전송 비용과 스토리지 유지 비용을 크게 아낄 수 있었습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 프로젝트를 진행하며 배운 가장 큰 교훈은 **"문제를 시스템의 어느 레이어에서 해결할 것인가에 대한 전략적 선택이 중요하다"**는 점이었습니다.

1. **최적화는 가능한 한 사용자(Edge)와 가까운 곳에서 시작하라:** 5MB짜리 원본을 서버로 받아 최적화하려 했다면 불필요한 네트워크 리소스와 서버 컴퓨팅 파워를 낭비했을 것입니다. 클라이언트 브라우저 자원을 활용한 사전 압축은 시스템 전체의 효율을 바꾸는 훌륭한 레버리지가 되었습니다.
2. **LLM의 비결정론적 특성을 보완하는 안전장치 구축:** LLM(Gemini)은 훌륭한 파서 역할을 해주었지만, 100% 신뢰할 수 없는 비결정론적 결과를 낼 때가 있습니다. 이를 백엔드 단의 정형 정규식 및 마스터 DB 기반 정규화 파이프라인으로 2차 필터링해 줌으로써 실서비스에 걸맞은 안정성을 확보할 수 있었습니다.

앞으로도 PickSafe 팀은 사용자들에게 더 빠르고 안전한 성분 분석 경험을 제공하기 위해 파이프라인을 고도화해 나갈 예정입니다. 기술적 호기심과 도전을 즐기는 동료들이 늘 기다리고 있으니 많은 관심 부탁드립니다!
