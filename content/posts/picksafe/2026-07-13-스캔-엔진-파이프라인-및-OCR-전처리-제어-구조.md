스마트폰 카메라를 활용해 제품 정보를 실시간으로 분석하는 서비스에서 **"정확도 높은 데이터 추출"**과 **"낮은 응답 지연 시간(Latency)"**은 서비스의 성패를 가르는 핵심 사용자 경험(UX) 요소입니다.

화장품 성분표 분석 엔진을 고도화하며 겪었던 **모바일 환경의 실물 노이즈 극복 과정**, **네트워크 비용 최적화**, 그리고 **비정형 텍스트를 표준 데이터로 정규화한 엔지니어링 접근법**을 공유합니다.

---

## 1. 문제 정의: 실환경 노이즈와 네트워크 병목

화장품 패키징의 성분표를 분석할 때 마주한 기술적 문제는 크게 세 가지였습니다.

1. **물리적 환경 노이즈로 인한 파싱 실패**
   * 곡면 용기, 반사 재질, 초점 흔들림 등으로 인해 구분자(`,`, `.`)가 누락되어 `정제수글리세린`과 같이 복합 성분이 단일 단어로 결합되는 현상 발생.
2. **동의어 및 표기 변형의 한계**
   * 음차 표기 차이(예: `디메치콘` ➔ `다이메티콘`)나 부가 설명(예: `글리세린(식물성)`)으로 인해 표준 성분 데이터베이스(DB)와의 1:1 매칭률 저하.
3. **고해상도 이미지 업로드로 인한 Latency 및 비용 급증**
   * 최신 스마트폰의 4K 원본 이미지(5MB 이상) 업로드 시 네트워크 대역폭 낭비 및 Vision API 처리 시간/비용 급증.

---

## 2. 아키텍처 설계 및 기술적 의사결정 (Trade-offs)

우리는 문제 해결을 위해 전체 파이프라인을 **[클라이언트 전처리] ➔ [Vision AI 정형 추출] ➔ [결정론적 정규화 엔진]**의 3단계로 분리했습니다.

```
[클라이언트]                     [백엔드 API 서버]                   [데이터 엔진]
Canvas API 인메모리 압축  ──(300KB)──>  Vision AI 정형 프롬프트 파싱  ──(Raw Data)──>  정규화 및 표준 매칭
(5MB ➔ 300KB 경량화)                   (JSON Array 형태로 구조화)                (INCI 표준명 & 규제 성분 판정)
```

### 고민 1. 이미지 압축을 어디서 처리할 것인가? (Client vs. Server)
* **대안 A: 서버 사이드 압축 (Worker 처리)**
  * 장점: 클라이언트 디바이스 성능에 의존하지 않고 일관된 화질 제어 가능.
  * 단점: 수 MB의 원본 이미지가 업로드되는 네트워크 병목(Upload Latency)은 여전히 잔존.
* **선택: 브라우저 Canvas API를 활용한 인메모리 압축 (Client-side)**
  * 사용자 디바이스 단에서 원본 해상도를 최대 1200px(종횡비 유지), JPEG 압축률 85%로 실시간 전처리 후 업로드.
  * **결과**: 업로드 페이로드를 **90% 이상 절감 (5MB ➔ 약 300KB)**하여 업로드 지연시간을 5초 이상 단축.

### 고민 2. 비정형 성분 텍스트의 구조화 (Regex vs. Vision LLM)
* **대안 A: 전통적인 OCR + 정규표현식(Regex) 기반 분리**
  * 구분자(쉼표)가 누락되거나 줄바꿈(Wrap)이 일어난 텍스트를 규칙 기반으로만 복원하는 데 높은 오차율 발생.
* **선택: Vision Foundation Model 기반의 구조화 프롬프트 엔지니어링**
  * 이미지 내 성분 텍스트를 인지함과 동시에 의미론적 맥락을 파악하여 `string[]` 형태의 JSON 데이터로 즉시 반환하도록 유도.
  * 텍스트 추출과 토큰 분리 작업을 하나의 파이프라인으로 통합하여 OCR 오인식률을 대폭 감소.

### 고민 3. 부가 표기 정규화 및 표준명 식별 (Normalization Layer)
* Vision 모델이 반환한 원시 데이터(`Raw Array`)에 포함된 부가 설명(예: `향료(리모넨 함유)`) 및 구버전 성분명을 표준화하기 위해 **결정론적(Deterministic) 정규화 계층**을 구현.
* 특수문자 및 괄호 구조를 정규식으로 안전하게 분해하고, 표준 INCI(국제화장품성분명) 및 공인 알레르기 유발 성분 식별자로 매핑하는 룰 엔진 적용.

## 3. 구현 성과 및 측정 지표

이러한 파이프라인 설계를 통해 실환경에서 다음과 같은 성능 개선을 달성했습니다.

| 지표 | 개선 전 (Initial) | 개선 후 (Optimized) | 개선율 |
| :--- | :--- | :--- | :--- |
| **평균 업로드 페이로드** | ~ 5.2 MB | **~ 320 KB** | **93.8% 절감** |
| **전체 분석 응답 시간(E2E Latency)** | 6.5초 이상 | **평균 1.5초 이내** | **약 77% 단축** |
| **성분 DB 매칭 정확도(Accuracy)** | 62% | **97%** | **35%p 향상** |

## 4. 엔지니어링 교훈 (Takeaways)

1. **Edge(클라이언트) 리소스의 적극적 활용**
   * 모든 작업을 백엔드 인프라에서 처리하려 하기보다, 클라이언트 단에서 브라우저 API(Canvas)를 활용해 전처리(Pre-processing)함으로써 서버 비용 절감과 응답 속도 개선이라는 두 마리 토끼를 잡을 수 있었습니다.
2. **AI의 유연성과 규칙 기반(Rule-based) 엔진의 결합**
   * 생성형 AI/Vision 모델은 비정형 이미지에서 맥락을 파악해 구조화하는 데 탁월하지만, 표준 식별자 매칭과 같은 영역은 결정론적인 정규화 엔진이 보완해주어야 신뢰성 높은 시스템이 완성된다는 점을 재확인했습니다.
