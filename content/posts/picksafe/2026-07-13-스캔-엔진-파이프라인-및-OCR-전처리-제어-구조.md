스마트폰 카메라를 통해 실생활 제품의 텍스트를 인식하고 분석하는 서비스에서 가장 큰 걸림돌은 **‘현실 세계의 노이즈(Real-world Noise)’**입니다. 통제된 테스트 환경과 달리, 실제 사용자가 촬영한 화장품 성분표 이미지는 조명 반사, 용기의 곡면 왜곡, 초점 흔들림, 저해상도 폰트 등 정제되지 않은 데이터로 가득 차 있습니다.

이번 글에서는 이러한 실환경 모바일 OCR 처리의 한계를 극복하기 위해, **클라이언트 단의 데이터 슬림화부터 백엔드 파이프라인의 정규화 엔진 구축까지** 기술적 문제를 구조적으로 해결해 나간 과정과 Trade-off 고민을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

초기 단순 텍스트 추출 엔진을 프로덕션에 도입했을 때, 사용자 경험과 시스템 안정성 측면에서 크게 세 가지 병목이 발생했습니다.

1. **네트워크 대역폭 및 API 타임아웃**
   * 최신 스마트폰의 4K 고화질 원본 이미지(5MB 이상)가 그대로 전송되면서, 모바일 LTE/3G 환경에서 업로드 대역폭 병목이 발생했습니다. 이는 비전(Vision) API의 처리 지연으로 이어져 **초기 응답 시간이 5초 이상 소요**되거나 타임아웃으로 이어졌습니다.
2. **문장 부호 누락으로 인한 데이터 오염**
   * OCR 특성상 쉼표(`,`)나 점(`.`) 같은 미세한 문장 부호가 쉽게 누락되었습니다. 그 결과 `정제수, 글리세린`이 `정제수글리세린`이라는 하나의 문자열로 결합되어 DB 내 표준 성분 데이터베이스와 매칭되지 않는 현상이 빈번했습니다.
3. **노이즈 및 오인식에 따른 정밀도 저하**
   * 음차 표기 오타(예: `디메치콘` ➔ `다이메티콘`)나 원료의 부가 설명 표기(`글리세린(식물성)`)로 인해 식약처 공인 알레르기 유발 성분 및 유저 기피 성분을 정확히 추적해내지 못했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs & Architecture Decisions)

이 문제를 해결하기 위해 시스템 레이어를 **[클라이언트(Edge Layer)] - [비전 서버(Extraction Layer)] - [정규화 엔진(Processing Layer)]**으로 역할 분리하기로 결정했습니다.

### 고민 1: 이미지 압축의 주체는 어디여야 하는가? (Server-side vs Client-side)
* **대안 A: 서버 사이드 리사이징**
  * 장점: 백엔드에서 일관된 이미지 처리 라이브러리(e.g., OpenCV, Pillow)를 사용하여 리사이징 품질을 제어하기 쉬움.
  * 단점: 대용량 이미지(5MB+)가 네트워크를 타고 서버로 들어오는 것 자체를 막지 못하므로 대역폭 비용과 업로드 지연시간 문제 해결 불가능.
* **대안 B: 브라우저/클라이언트 인메모리 압축 (선택)**
  * 장점: Canvas API를 활용해 렌더링 전 인메모리에서 리사이징 및 JPEG 압축(1200px 이하, Quality 85%). **페이로드 크기를 5MB에서 300KB 수준으로 90% 이상 절감**.
  * 단점: 클라이언트 파편화 기기에 따른 압축 성능 영향 ➔ 테스트 결과, 1200px 수준의 리사이징은 모바일 브라우저에서도 CPU 연산 리소스 소비가 극히 미미함을 확인.

### 고민 2: 성분 추출 및 알레르기 매칭을 LLM 단일 모델에 의존할 것인가?
* **대안 A: 단일 비전 LLM 기반 End-to-End 추출**
  * 프롬프트만으로 "알레르기 성분까지 포함해서 분류해 줘"라고 요청하는 방식.
  * 문제점: LLM의 환각(Hallucination) 가능성과 non-deterministic(비결정론적) 특성 때문에 식약처 26대 공인 알레르기 성분 판정 같은 **법적/안전 기준 준수 시스템에 100% 신뢰성을 부여할 수 없음**.
* **대안 B: LLM 추출 + 결정론적 정규화 규칙 엔진의 하이브리드 파이프라인 (선택)**
  * 비전 모델은 오직 **"이미지 내 텍스트의 정형 JSON 배열 추출"**에만 집중시킵니다.
  * 이후 백엔드 내부의 **'정규화 및 알레르기 판정 엔진'**에서 정규식 파싱, 괄호 제거, INCI 표준 식별자 맵핑, 룰 기반 매칭을 수행합니다. 시스템의 안정성과 예측 가능성을 최대로 끌어올릴 수 있습니다.

## 3. 엔지니어링 구현: 3-Stage Scan Pipeline

최종 구축된 파이프라인 흐름은 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 클라이언트 이미지 사전 압축 (Edge Preprocessing)         │
│    - Canvas API: Max 1200x1200px, JPEG Quality 85%         │
│    - 페이로드 90% 절감 (5MB ➔ ~300KB)                       │
└─────────────────────────────────────────────────────────────┘
                              │ Multi-part Form Upload
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 백엔드 OCR 파이프라인 (Vision Extraction)                 │
│    - Vision API + Structured Output JSON 프롬프트            │
│    - 텍스트 오리엔테이션 교정 및 원시 성분 리스트 배열화    │
└─────────────────────────────────────────────────────────────┘
                              │ Raw Ingredient List
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 성분명 정규화 및 알레르기/기피 매칭 엔진 (Normalization)  │
│    - 괄호/특수문자 텍스트 파싱 및 표준 INCI 식별자 맵핑     │
│    - 식약처 26대 공인 알레르기 및 사용자 기피 성분 매칭     │
└─────────────────────────────────────────────────────────────┘
```

### 정규화 파이프라인 처리 핵심 예시 (Abstracted Logic)
LLM을 통해 수신된 텍스트 배열 중 부가 정보가 섞인 데이터(`"글리세린(식물성)"`, `"향료[리모넨 함유]"`)는 정규식(Regex) 트랜스포머를 거쳐 순수 핵심 화학 성분명과 부가 정보 속성을 분리합니다. 

이후 한국어 표준 성분명 테이블 및 INCI 영문 표준 식별자 맵과 교차 검증(Cross-validation)을 진행하여, 데이터 베이스 내 사전 정의된 ID와 1:1 바인딩을 수행합니다.

## 4. 성과 및 핵심지표 (Results & Impact)

이번 파이프라인 개선을 통해 기술적/비즈니스적으로 다음과 같은 성과를 얻었습니다.

1. **응답 지연 시간(Latency) 대폭 개선**
   * 클라이언트 압축을 통해 업로드 및 전체 분석 처리 응답 시간이 **평균 1.5초 이내**로 안정화되었습니다.
2. **성분 인식 및 매칭 정확도(Accuracy) 35% 향상**
   * 문장 부호 분실 이슈 해결 및 하이브리드 정규화 엔진 도입으로, 노이즈가 심한 모바일 환경에서도 **기존 대비 성분 매칭 성공률이 35% 크게 상승**했습니다.
3. **인프라 비용 효율화**
   * 비전 모델에 전달되는 데이터 양 축소 및 불필요한 토큰 소비를 방지하여 LLM API 호출 비용 및 네트워크 인프라 비용을 대폭 절감했습니다.

## 5. 엔지니어링 교훈 (Takeaways)

1. **"데이터 정제는 시스템의 가장 앞단(Edge)에서 시작해야 한다."**
   * 무조건 서버 성능을 올리거나 더 큰 AI 모델을 사용하는 것이 답이 아닙니다. 클라이언트에서 불필요한 페이로드를 미리 줄이는 것만으로도 전체 아키텍처의 안정성이 크게 개선됩니다.
2. **"AI의 유연함과 룰 엔진의 엄격함(Determinism)을 분리하라."**
   * AI 모델은 비정형 이미지를 정형화된 데이터 구조로 바꾸는 데 집중시키고, 도메인 지식이 필요한 엄격한 비즈니스 로직(알레르기 판정 등)은 프로그래밍 방식의 룰 엔진으로 다루는 것이 정답률과 트러블슈팅 가능성을 동시에 잡는 길입니다.
