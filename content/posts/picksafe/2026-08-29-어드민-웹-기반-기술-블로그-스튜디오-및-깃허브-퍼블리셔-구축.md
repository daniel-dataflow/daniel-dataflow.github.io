안녕하세요, PickSafe Core Architecture Team입니다. 

PickSafe는 그동안 프로덕트를 고도화하며 쌓아온 55개의 기술 의사결정 문서(ADR, Architecture Decision Record)를 대외 공개용 기술 블로그(`daniel-dataflow.github.io`)를 통해 세상과 공유하고자 하는 목표를 가지고 있었습니다. 

하지만 개발 조직이 블로그 운영에 들이는 공수를 최소화하면서도, 콘텐츠의 퀄리티를 담보하는 과정에서 몇 가지 현실적인 장벽에 부딪혔습니다. 이번 글에서는 사내 어드민 웹 내에 **'기술 블로그 스튜디오(Blog Studio)'**를 구축하고, 55개의 ADR을 원클릭으로 퍼블리싱할 수 있는 시스템을 설계하게 된 배경과 기술적 고민을 공유하려 합니다.

---

## 1. 문제 정의 (Context & Problem Statement)

초기에는 GitHub Actions를 활용해 사내 문서 레포지토리의 변경 사항을 블로그 레포지토리에 100% 자동 동기화하는 파이프라인을 구상했습니다. 하지만 몇 가지 치명적인 한계가 있었습니다.

1. **전면 자동화의 검수 불가 딜레마**
   - 개발 문서(ADR)를 마크다운 변환기만 거쳐 곧바로 발행할 경우, 외부 독자가 보기에 문맥이 매끄럽지 않거나 비즈니스 맥락이 누락될 위험이 있었습니다.
   - 그렇다고 블로그 레포지토리에서 직접 글을 수정하자니, 추후 사내 레포지토리와의 단방향 동기화 과정에서 덮어씌워져 수정본이 유실되는 **유지보수 지옥(Maintenance Hell)**이 예상되었습니다.
2. **시각적 검증의 부재**
   - 텍스트 기반의 마크다운 원문만으로는 실제 웹 브라우저에서 타이포그래피, 줄바꿈, 이미지 배치가 어떻게 렌더링될지 실시간으로 확인하기 어려웠습니다.
3. **개발 도구 의존성**
   - 글을 하나 발행하기 위해 매번 터미널을 열어 Git 명령어나 파이썬 스크립트를 수동 실행해야 하는 번거로움은 콘텐츠 발행 빈도를 낮추는 주원인이었습니다.

> **"브라우저 어드민 화면에서 '문서 선택 ➔ AI 초안 ➔ 직접 수정 및 이미지 드래그앤드롭 ➔ 원클릭 발행'이 가능한 내부 CMS가 필요하다."**

## 2. 시스템 아키텍처 및 작업 흐름

이러한 문제를 해결하기 위해, 기존에 구축되어 있던 FastAPI 기반의 어드민 백엔드와 연동되는 **경량 웹 기반 블로그 스튜디오**를 설계했습니다.

```mermaid
flowchart LR
    subgraph Admin_Frontend [어드민 기술 블로그 스튜디오 UI (/admin/blog)]
        A1[1. 55개 ADR 문서 목록 선택] --> A2[2. 🤖 AI 초안 1초 생성]
        A2 --> A3[3. 좌/우 스플릿 웹 에디터<br/>직접 수정 & 이미지 드래그앤드롭]
        A3 --> A4[4. 🚀 깃허브 블로그 즉시 발행]
    end

    subgraph Backend_Engine [FastAPI 백엔드 서비스]
        B1[docs/decisions/ 연대순 파서]
        B2[Gemini 2.5 Flash 보안 마스킹]
        B3[이미지 업로드 & 로컬 캐싱]
        B4[GitHub REST API / Git 배포기]
    end

    A1 --> B1
    A2 --> B2
    A3 --> B3
    A4 --> B4
    B4 --> C[🌐 daniel-dataflow.github.io 배포 완료]
```

### 핵심 컴포넌트 역할
* **FastAPI 백엔드(`app/routers/admin/blog.py`)**: 
  - 내부 문서 파싱, Gemini API를 활용한 보안 마스킹 및 초안 생성, 에디터 이미지 업로드 처리, 그리고 GitHub REST API를 통한 원격 저장소 커밋/푸시를 담당합니다.
* **프론트엔드 스튜디오 UI**: 
  - 좌측의 **문서 탐색기**, 중앙의 **스마트 마크다운 에디터**, 우측의 **실시간 라이브 렌더링 뷰포트**로 구성된 3단 반응형 구조를 통해 사용자 경험을 극대화했습니다.

## 3. 기술적 고민과 Trade-off

### ① 보안과 자동화의 균형: AI 초안 생성 시 보안 마스킹
사내 ADR 문서에는 내부 아키텍처 구조나 민감한 식별자가 포함되어 있을 수 있습니다. 이를 외부 블로그에 그대로 노출하는 것은 보안상 치명적입니다.
* **대안 A**: 사람이 일일이 읽고 민감 정보를 수동으로 마스킹하기
  - *Trade-off*: 가장 안전하지만, 블로그 발행 리소스가 너무 많이 들어 지속 가능성이 떨어짐.
* **대안 B**: Gemini API 호출 시 시스템 프롬프트 및 후처리를 통해 자동으로 내부 보안 정보를 마스킹하고 기술 블로그 톤으로 변환
  - *Trade-off*: AI 할루시네이션이나 마스킹 누락 가능성이 존재하나, 인간 에디터가 우측 화면에서 최종 검수(Human-in-the-loop)를 거치므로 리스크를 완벽하게 통제 가능함.
  - **결정**: 대안 B를 채택하여, **"AI 초안 80% + 개발자 디테일 20%"**의 효율적이면서도 안전한 워크플로우를 완성했습니다.

### ② 별도의 외부 CMS 도입 vs 내부 어드민 확장
* **대안 A**: Ghost, WordPress 등 외부 오픈소스 CMS 도입
  - *Trade-off*: 인프라 구성 비용 증가 및 사내 인증 시스템(Auth)과 별도로 분리되어 보안 관리 포인트가 늘어남.
* **대안 B**: 이미 인증과 세션 관리가 구현되어 있는 기존 FastAPI 어드민 백엔드 내에 라우터와 뷰 추가
  - *Trade-off*: 초기 개발 공수가 약간 발생하지만, 인프라 격리 없이 로컬 환경(`localhost:8100`)부터 프로덕션까지 동일한 환경에서 즉시 구동 가능하며 유지보수가 압도적으로 편함.
  - **결정**: 대안 B를 채택하여 시스템 복잡도를 낮추고 개발 생산성을 극대화했습니다.

---

## 4. 최종 구현 및 엔지니어링 교훈 (Takeaways)

이번 블로그 스튜디오 구축을 통해 얻은 가장 큰 교훈은 **"자동화는 사람의 검수 단계를 완전히 배제하는 것이 아니라, 사람이 가장 잘할 수 있는 일(크리에이티브 및 최종 검수)에 집중할 수 있도록 돕는 방향으로 설계되어야 한다"**는 점입니다.

- **무결점 배포 보장**: 에디터에서 최종 확인이 끝난 마크다운 파일과 에셋만 GitHub REST API를 통해 정확한 경로에 푸시되므로, 동기화 과정에서 글이 유실되거나 덮어씌워질 걱정이 사라졌습니다.
- **생산성 향상**: 개발 도구나 복잡한 Git 명령어 없이 브라우저 창 하나로 아이디어 도출부터 퍼블리싱까지 완결되는 경험을 제공함으로써, 기술 지식 공유 문화가 한층 더 가속화되었습니다.

PickSafe는 앞으로도 개발 과정에서 마주치는 크고 작은 병목 현상을 엔지니어링으로 우아하게 해결하고, 그 과정을 투명하게 나누겠습니다. 읽어주셔서 감사합니다!
