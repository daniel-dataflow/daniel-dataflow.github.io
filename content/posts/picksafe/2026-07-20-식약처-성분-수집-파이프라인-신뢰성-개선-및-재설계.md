안녕하세요, **PickSafe** 백엔드 팀입니다. 

저희 서비스의 핵심 가치는 사용자에게 '정확하고 안전한 성분 정보'를 제공하는 데 있습니다. 이를 위해 식약처 공공 API 및 외부 화장품 협회 데이터를 주기적으로 수집하고 정제하여 마스터 데이터를 구축하고 있습니다.

초기 MVP 단계에서는 빠른 기능 구현을 최우선으로 삼아 성분 수집 파이프라인을 구축했습니다. 하지만 사용자가 늘어나고 데이터가 누적되면서, 외부 API의 간헐적 장애, 복잡한 데이터 상태 관리의 한계 등 시스템적 균열이 발생하기 시작했습니다. 

이 글에서는 저희 팀이 **데이터 무결성을 지키고, 시스템의 회복 탄력성(Resilience)을 극대화하기 위해 데이터 파이프라인을 어떻게 재설계했는지** 그 과정을 공유합니다.

---

## 1. 문제 정의: 무엇이 우리 시스템의 신뢰성을 위협했는가?

기존 성분 수집 및 CAS(Chemical Abstracts Service) 등록번호 자동 보강 시스템은 크게 4가지 치명적인 구조적 문제를 가지고 있었습니다.

### ① 멱등성(Idempotency)의 결여와 데이터 유실
수집 스케줄러가 동작할 때마다 일시적 오류 데이터를 관리하는 임시 적재(Staging) 테이블의 데이터를 단순 삭제(`DELETE`)한 후 1페이지부터 다시 수집을 시작했습니다. 이로 인해 관리자가 수동으로 검토하고 조치해야 할 에러 상태의 데이터까지 함께 유실되는 현상이 발생했습니다.

### ② CAS 누락 데이터의 영구 소외
이미 마스터 데이터베이스에 등록된 성분 이름이 발견되면 수집 루프에서 단순히 스킵하는 최적화(?) 로직이 있었습니다. 이로 인해, 이름은 등록되어 있지만 정작 핵심 식별자인 CAS 번호가 비어 있는 성분들이 영구적으로 보강 및 재검토 대상에서 제외되는 악순환이 발생했습니다.

### ③ 외부 API 실패 감지 불가와 조기 종료
식약처 공공 API는 네트워크 타임아웃이나 호출 제한(Rate Limit)으로 인해 일시적으로 빈 데이터를 반환하는 경우가 잦습니다. 기존 시스템은 단 한 번이라도 빈 응답이 오면 이를 "모든 데이터 수집 완료"로 오인하고 전체 루프를 조기 종료해버렸습니다.

### ④ 모놀리식 파일 구조와 변경 취약성
성분 수집(Seeding), CAS 스크래핑 보강, 스케줄링, 마스터 데이터 병합(Merge) 로직이 모두 어드민 라우터 파일(`admin.py`) 하나에 조밀하게 얽혀 있었습니다. 이로 인해 작은 어드민 UI 수정 작업을 할 때도 핵심 수집 파이프라인 소스가 건드려져 구문 충돌이나 오동작을 유발했습니다.

## 2. 기술적 고민과 대안: 신뢰할 수 있는 상태 머신 설계하기

저희는 단순히 코드를 땜질식으로 수정하는 것을 넘어, **"완벽히 통제 가능하고 추적 가능한 상태"**를 정의하기로 했습니다.

### 단일 문자열 상태(`status`)의 한계 극복
기존에는 `status`라는 단일 필드에 `pending`, `error`, `suggested`, `merged` 상태를 모두 밀어 넣어 관리했습니다. 그러다 보니 "네트워크 실패로 수집이 안 된 상태"와 "수집은 완료되었으나 CAS 번호가 누락되어 검토가 필요한 상태"가 모호하게 섞여 시스템이 오동작했습니다.

이 대안으로 우리는 상태를 **5가지의 독립적인 차원(Multi-dimensional Status Properties)**으로 완전히 분리하여 정규화했습니다.

| 필드명 | 타입 | 기본값 | 역할 및 비즈니스 제약 |
| :--- | :--- | :--- | :--- |
| **`is_merged`** | Boolean | `False` | 운영 마스터 DB 이관 완료 여부. (가장 중요) |
| **`sync_status`** | String | `"success"` | API 동기화 자체의 상태 (`success` / `failed` / `critical_failed`) |
| **`cas_status`** | String | `"needed"` | CAS 번호 상태 (`needed` / `suggested` / `verified` / `not_found`) |
| **`cas_source`** | String | Nullable | CAS 번호 출처 (`kfda` (식약처), `kcia` (협회), `manual` (직접 입력)) |
| **`retry_count`** | Integer | `0` | 일시적 장애 대응을 위한 API 재시도 횟수 |

#### 🔒 Critical Gate (안전장치)
크롤링을 통해 자동으로 CAS 번호 보강 추천을 받은 상태(`cas_status = 'suggested'`)의 성분은 **운영 마스터 DB로 절대 자동 병합(`is_merged = True`)되지 못하게 차단**했습니다. 반드시 어드민 대시보드에서 담당자의 명시적 승인을 거쳐 `verified` 상태로 전환되어야만 최종 반영되도록 파이프라인 게이트를 설계하여 데이터 정합성을 보장했습니다.

## 3. 최종 해결 및 엔지니어링 구현

### ① 멱등성을 보장하는 Upsert 전략
재수집 시 기존 적재 데이터를 날려버리는 파괴적인 방식에서 탈출했습니다. 식약처 API에서 제공하지 않는 고유 식별값 대신 자연 키(Natural Key)인 `inci_name` (영문명)과 `korean_name` (국문명)의 조합을 복합 고유 키로 활용해, 데이터가 존재하면 업데이트(Upsert)하되 관리자가 조정한 보강 데이터나 오류 이력은 덮어쓰지 않고 보존하게 개선했습니다.

```python
# 내부 구현 로직의 개념적 예시 (Upsert 구조)
async def upsert_staging_ingredient(db, ingredient_data):
    # inci_name과 korean_name을 기준으로 중복 확인
    existing = db.query(IngredientMasterStaging).filter(
        IngredientMasterStaging.inci_name == ingredient_data.inci_name,
        IngredientMasterStaging.korean_name == ingredient_data.korean_name
    ).first()

    if existing:
        # 기존 데이터가 있고 관리자가 이미 검토한 이력이 있다면 핵심 필드 위주로 보정 업데이트
        if existing.cas_status != 'verified':
            existing.cas_no = ingredient_data.cas_no or existing.cas_no
            ...
        existing.sync_status = "success"
    else:
        # 신규 데이터 적재
        new_record = IngredientMasterStaging(**ingredient_data)
        db.add(new_record)
```

### ② Fault-Tolerant 네트워크 루프 및 자가 치유(Self-Healing)
외부 API 서버의 간헐적인 불안정성에 대응하기 위해 **자가 치유형 재시도 메커니즘**을 탑재했습니다.

1. **에러 페이지 우선 추적**: 신규 수집 가동 시, 이전 이력 중 `sync_status = 'failed'`이면서 `retry_count < 5`인 실패 페이지들을 큐에 먼저 적재하여 최우선 재수집합니다.
2. **에러 격리 (Circuit Breaker 및 Escalation)**: 재시도가 5회를 넘어가면 해당 페이지는 시스템의 자동 시도 대상에서 격리하여 `critical_failed` 상태로 변경하고, 시스템 운영자 알림 대시보드로 즉시 라우팅합니다.
3. **네트워크 조기 종료 방지**: 단 한 번의 빈 페이지 응답으로 루프를 끊지 않습니다. **연속 3회 빈 데이터가 감지될 때만** 진짜 수집의 끝으로 인식하게 함으로써, 간헐적 타임아웃 시에도 파이프라인이 끊기지 않고 끝까지 수행됩니다.

```python
# 조기 종료 방지를 위한 3-strike 아웃 메커니즘 개념 코드
consecutive_empty_count = 0

for page in range(start_page, max_pages):
    try:
        data = await fetch_kfda_api(page)
        if not data:
            consecutive_empty_count += 1
            if consecutive_empty_count >= 3:
                logger.info("연속 3회 빈 데이터 수신으로 안전하게 수집을 종료합니다.")
                break
            continue
        
        consecutive_empty_count = 0  # 성공 시 카운트 초기화
        await save_to_staging(data)
        
    except TemporaryNetworkError as e:
        # 실패 페이지 상태를 failed로 기록 및 retry_count 증가
        await record_failed_page(page, error_message=str(e))
```

### ③ 서비스 아키텍처의 물리적 분리
모놀리식 구조의 단순 어드민 파일에 얽혀 있던 비즈니스 로직들을 책임을 기준으로 완전히 구조화했습니다.
- **`app/models/staging.py`**: 데이터 수집 전용 가상 적재 스테이징 모델 정의
- **`app/services/seeding_service.py`**: 수집 루프, 재시도 제어 및 API 통신 샌드박스 비즈니스 로직 담당
- **`app/routers/seeding.py`**: 어드민 화면과 API 스케줄러 트리거용 엔드포인트 전용 분리

이를 통해 대시보드 UI 기획 요건이 변경되어 코드를 수정하더라도, 수십만 건의 성분 수집 파이프라인이 구동되는 백그라운드 엔진에는 단 한 줄의 영향도 주지 않도록 결합도를 대폭 낮췄습니다.

## 4. 엔지니어링 교훈 및 성과 (Takeaway)

이번 파이프라인 개편을 통해 시스템적으로 유의미한 성과들을 거두었습니다.

1. **데이터 무결성 100% 보장**: 수집을 몇 번이고 재시작하거나 도중에 인프라가 다운되더라도 데이터가 중복되거나 미승인 상태의 에러 로그가 소실되는 현상이 완전히 사라졌습니다. (멱등성 확보)
2. **CAS 수집 누수율 0% 달성**: 마스터 테이블에 이미 성분이 존재하더라도 CAS 정보가 없었던 '정보 사각지대'의 성분들이 재스크래핑 큐에 항상 포함되도록 설계하여, 성분 데이터의 완성도를 획기적으로 향상시켰습니다.
3. **인프라 공수 및 스트레스 감소**: 새벽 시간대 발생하는 외부 공공 API 서버의 에러 대응을 더 이상 개발자가 수동으로 개입해 모니터링할 필요가 없어졌습니다. 시스템 스스로 자가 치유를 수행하고, 진짜 치명적인 오류(`critical_failed`)만 골라내어 어드민 화면에서 보고받기 때문입니다.

### 💡 엔지니어로서의 깨달음
> 외부 파트너사나 공공 API 같은 **"우리가 통제할 수 없는 불안정한 시스템"**과 상호작용하는 아키텍처를 설계할 때는, 외부 시스템이 언제든 실패할 수 있음을 기본 전제로 삼아야 합니다. 
> 
> 실패를 에러 레이어로 격리하고, 상태를 다차원화하여 유연한 대응 전략을 수립하는 설계 능력이야말로 대규모 프로덕션을 안정적으로 이끄는 백엔드 엔지니어의 핵심 역량임을 다시 한번 체득할 수 있었던 소중한 경험이었습니다.
