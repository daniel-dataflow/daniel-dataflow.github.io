안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스가 성장함에 따라 외부 공공 데이터(식약처 성분 정보 등)를 주기적으로 수집·보강하는 파이프라인의 중요성은 날로 커지고 있습니다. 하지만 외부 API 연동 서비스들이 흔히 그렇듯, 우리 팀 역시 **데이터 유실, 네트워크 일시적 장애 대응 부재, 그리고 비대해진 모놀리식 라우터**라는 기술적 부채에 직면했습니다.

이번 포스팅에서는 기존 식약처 성분 수집 파이프라인의 구조적 한계를 분석하고, 이를 **멱등성(Idempotency)을 보장하는 견고한 아키텍처**로 재설계한 과정과 엔지니어링 교훈을 공유합니다.

---

## 1. 기존 파이프라인의 마주한 문제들 (Problem)

초기 구현된 수집 파이프라인은 빠른 기능 구현에 초점이 맞춰져 있어 운영 관점에서 다음과 같은 치명적인 결함이 있었습니다.

1. **멱등성(Idempotency) 결여로 인한 데이터 유실**:
   - 재수집을 트리거할 때마다 임시(Staging) 테이블의 미해결 에러 이력을 일괄 삭제(`delete()`)하도록 구현되어 있었습니다. 관리자가 에러를 확인하고 조치하기도 전에 데이터가 증발하는 현상이 발생했습니다.
2. **CAS 번호 누락 데이터의 영구 소외**:
   - 운영 DB에 성분 이름이 존재하면 수집 루프에서 스킵(Skip)하도록 처리되어 있어, 식별자는 있지만 핵심 속성(CAS 번호)이 비어 있는 성분들이 보강 후보군에서 영구적으로 차단되었습니다.
3. **취약한 네트워크 에러 감지 (False Termination)**:
   - 외부 공공 API 호출 중 일시적인 타임아웃이나 호출 제한으로 빈 데이터가 수신되면, 파이프라인은 이를 "데이터의 끝"으로 오인하여 전체 수집 루프를 조기 종료해 버렸습니다.
4. **모놀리식한 코드 구조 (`admin.py` 비대화)**:
   - Seeding, CAS 보강 스케줄링, 병합 로직 등 파이프라인의 핵심 도메인 코드가 어드민 라우터 파일에 혼재되어 있어, 작은 수정에도 구문 충돌과 소스 파일 손상 위험이 컸습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off & Architecture)

문제를 해결하기 위해 아키텍처를 원점부터 재검토하며 다음과 같은 설계 원칙을 세우고 적용했습니다.

### ① 단순 상태(Status) 문자열 제거 및 '다차원 상태 속성' 분리
기존의 모호한 단일 `status` 필드는 비즈니스 로직이 복잡해질수록 확장성이 떨어졌습니다. 이를 전면 제거하고, 5가지 독립된 필드로 분리했습니다.

* `is_merged` (Boolean): 운영 DB 이관 완료 여부
* `sync_status` (String): API 통신 자체의 성공/실패 여부 (`success`, `failed`, `critical_failed`)
* `cas_status` (String): CAS 번호 상태 (`needed`, `suggested`, `verified`, `not_found`)
* `cas_source` (String): 데이터 출처 (`kfda`, `kcia`, `manual`)
* `retry_count` (Integer): 실패 재시도 횟수 누적

> **[CRITICAL GATE 적용]** 
> 외부 스크래핑 등으로 자동 추천된 성분(`cas_status = 'suggested'`)은 **관리자의 명시적 승인(`verified`) 없이는 절대 운영 DB로 병합(`is_merged = True`)될 수 없도록 엄격한 가이트라인을 구축**했습니다.

### ② 네트워크 회복 탄력성(Fault-Tolerant) 및 스마트 재시도
일시적인 네트워크 장애로 인한 데이터 누락을 막기 위해 **실패 페이지 우선 재시도 메커니즘**을 도입했습니다.
- 파이프라인 구동 전, `sync_status = 'failed'` 이면서 `retry_count < 5`인 레코드의 페이지 번호를 역추적해 우선 수집합니다.
- 실패가 5회 누적될 경우 `critical_failed`로 전환하여 자동 큐에서 제외하고, 어드민 대시보드에서 수동 검토하도록 격리했습니다.
- 또한, 빈 데이터가 수신되더라도 1회 만에 종료하지 않고 **최대 3회 연속 빈 데이터 수신 시에만 진짜 끝으로 판단**하도록 Fault-Tolerant 루프를 적용했습니다.

### ③ 삭제 없는 Upsert 전환 (멱등성 확보)
데이터를 지우고 새로 넣는 방식(Delete-Insert)을 버리고, 자연 키(`inci_name`, `korean_name`)를 기반으로 한 **Upsert 패턴**으로 전환했습니다. 이로써 반복적인 수집 작업에도 기존 관리자의 검토 이력이나 에러 로그가 안전하게 보존됩니다.

### ④ 도메인 관심사 분리 (라우터 모듈화)
비즈니스 로직이 얽혀 있던 기존 구조를 개선하여, 식약처 수집 및 스케줄러 관련 엔드포인트를 전용 라우터 파일(`app/routers/seeding.py`)로 물리적으로 완전히 분리했습니다.

## 3. 무엇을 배웠는가 (Takeaway)

이번 파이프라인 재설계를 통해 얻은 엔지니어링 교훈은 명확합니다.

1. **외부 의존성이 높은 시스템일수록 '가정'을 의심하라**: 
   외부 공공 API가 항상 정상 작동할 것이라는 가정, 혹은 데이터가 순차적으로 완벽하게 들어올 것이라는 가정은 프로덕션 환경에서 반드시 실패합니다. 실패를 전제로 한 재시도(Retry)와 상태 분리 설계가 필수적입니다.
2. **멱등성은 데이터 파이프라인의 생명조차 같다**:
   몇 번을 반복해서 실행해도 시스템 상태가 안전하게 유지되는 멱등성이 보장될 때, 운영자는 비로소 불안감 없이 배치 스케줄러를 믿고 맡길 수 있습니다.
3. **관심사의 분리는 유지보수성의 기초**:
   어드민 UI를 다루는 라우터와 백그라운드 데이터 수집 파이프라인은 엄격히 분리되어야 합니다. 코드의 응집도를 높이고 결합도를 낮출 때 장애 반경(Blast Radius)을 최소화할 수 있습니다.

견고해진 파이프라인 덕분에 PickSafe는 더 높은 신뢰도로 안전한 성분 데이터를 사용자에게 제공할 수 있게 되었습니다. 앞으로도 데이터 무결성을 지키는 아키텍처 고민은 계속됩니다.
