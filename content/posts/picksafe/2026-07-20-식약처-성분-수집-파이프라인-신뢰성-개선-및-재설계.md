데이터 비즈니스를 영위하는 서비스에서 **외부 데이터 수집 파이프라인(Ingestion Pipeline)**의 안정성은 서비스 신뢰도의 근간입니다. 특히 정부 기관이나 공공 API로부터 데이터를 주기적으로 동기화하고 이를 서비스 내부 데이터와 안전하게 병합하는 과정은 생각보다 많은 예외 상황과 비즈니스 예외 케이스를 동반합니다.

성분 정보 분석 서비스인 **PickSafe** 개발 팀은 기존 식약처 성분 데이터 수집 및 CAS(Chemical Abstracts Service, 화학 물질 고유 번호) 자동 보강 시스템을 운영하며 심각한 데이터 무결성 위협과 마주했습니다. 

이번 글에서는 기존 파이프라인의 아키텍처적 결함을 진단하고, 이를 **멱등성(Idempotency)**과 **장애 복원력(Fault-Tolerance)**이 보장되는 견고한 데이터 파이프라인으로 재설계한 과정을 공유합니다.

---

## 1. 기존 시스템의 페인 포인트 (The Problem)

기존의 식약처 성분 수집 시스템은 단순 배치(Batch) 스크립트 기반으로 동작하고 있었습니다. 하지만 운영 데이터가 쌓이고 예외 케이스가 다양해짐에 따라 다음과 같은 4대 설계 결함이 수면 위로 드러났습니다.

### ① 멱등성(Idempotency) 결여로 인한 데이터 유실
수집 파이프라인을 1페이지부터 다시 실행할 때, 기존 Staging 테이블의 미해결 오류 이력(`status = 'error'`)을 일괄 삭제(`delete()`)한 후 새로 수집을 시작하도록 설계되어 있었습니다. 이로 인해 관리자가 에러 원인을 파악하고 조치하기 전에 기존 오류 데이터가 공중분해 되는 현상이 발생했습니다.

### ② '한 번 스킵되면 영원히 버려지는' 데이터 블랙홀
성분 마스터 테이블(`ingredients_master`)에 성분명이 존재하면 수집 루프에서 해당 성분을 완전히 스킵했습니다. 이 방식은 효율적으로 보였지만, **"이름은 등록되어 있으나 정작 중요한 식별자인 CAS 번호가 누락된 성분"**이 다시는 보강 및 재검토 후보군에 오르지 못하는 치명적인 병목을 만들었습니다.

### ③ 일시적 API 장애에 취약한 루프 구조 (Fragile Loop)
식약처 API 서버의 일시적인 네트워크 타임아웃이나 호출 제한으로 인해 빈(Empty) 응답 데이터가 수신되면, 파이프라인은 이를 '데이터의 끝(EOF)'으로 오판하여 동기화 루프를 조기 종료(`break`)했습니다. 이 때문에 배치 실행 시 데이터가 중간에 잘린 채 끝나는 현상이 잦았습니다.

### ④ 코드 밀집으로 인한 유지보수 비용 상승
배치 트리거, API 라우팅, CAS 스크래핑, 병합 로직이 모두 하나의 거대한 어드민 라우터 파일(`admin.py`)에 얽혀 있었습니다. 이로 인해 작은 수집 로직 하나를 고치려 해도 API 엔드포인트 전체가 위험에 노출되는 구조적 결함을 안고 있었습니다.

## 2. 해결을 위한 아키텍처적 의사결정 (Trade-offs & Decision)

이 문제를 해결하기 위해, 단순히 버그를 패치하는 수준을 넘어 **파이프라인의 상태 모델과 제어 흐름을 근본적으로 재정의**하기로 결정했습니다.

### 결정 1: 단일 상태 필드를 '다차원 독립 상태 속성'으로 분해
기존에는 `status`라는 단일 컬럼에 `pending`, `error`, `suggested`, `merged` 등의 값을 혼용하여 사용했습니다. 이 방식은 간편하지만 **"수집 성공 여부"**와 **"CAS 데이터 보강 단계"**라는 서로 다른 차원의 상태를 한 번에 표현하지 못했습니다.

우리는 이 단일 문자열 컬럼을 완전히 제거하고, 서로 직교(Orthogonal)하는 **5가지 독립 필드**로 분리했습니다.

| 새로운 상태 필드 | 타입 | 설명 |
| :--- | :--- | :--- |
| `is_merged` | Boolean | 운영 마스터 DB로 이관 및 반영이 완료되었는지 여부 |
| `sync_status` | String | API 수집 단계의 상태 (`success` / `failed` / `critical_failed`) |
| `cas_status` | String | CAS 번호 검증 상태 (`needed` / `suggested` / `verified` / `not_found`) |
| `cas_source` | String | CAS 번호의 출처 정보 (`kfda` (식약처), `kcia` (협회), `manual` (직접 입력)) |
| `retry_count` | Integer | API 호출 실패 시 재시도 횟수 |

#### 🛡️ [Critical Gate] 자동 병합 안전장치 마련
화장품협회(KCIA) 등 외부 소스에서 크롤링하여 자동으로 제안된 CAS 번호(`cas_status = 'suggested'`)가 검증 없이 프로덕션 DB에 바로 밀려 들어가는 사고를 방지하기 위해, **강력한 검증 게이트(Verification Gate)**를 두었습니다. 
자동 제안된 데이터는 무조건 `cas_status = 'suggested'` 상태로 묶여 관리자의 명시적 승인(`verified`로 변경)을 거쳐야만 `is_merged = True`로 승격될 수 있도록 상태 머신 제약을 구현했습니다.

---

### 결정 2: 데드 레터 큐(DLQ) 사상을 접목한 자가 치유(Self-Healing) 재시도 루프
일시적인 네트워크 순단으로 실패한 수집 건들을 구제하기 위해 **지능형 재시도 메커니즘**을 도입했습니다.

```
[수집 파이프라인 트리거]
        │
        ▼
1. 이전 실행 실패 건 검색 (sync_status = 'failed' & retry_count < 5)
        │
        ├─▶ 실패했던 특정 page_no 수집 재시도
        │      ├─ [성공] ──▶ sync_status = 'success', retry_count = 0 갱신
        │      └─ [실패] ──▶ retry_count += 1
        │                      │
        │                      ▼ retry_count == 5 도달 시
        │                    [critical_failed] 마킹 (Dead Letter 상태) -> 어드민 경고 발생
        ▼
2. 정상적인 신규 수집 순차 진행 (1페이지 혹은 체크포인트부터)
```

이 방식을 통해 전체 수집 프로세스를 무겁게 재실행하지 않고도, 특정 구멍 난 데이터(Failed Pages)만 핀포인트로 메우는 **회복 탄력성 높은 배치 아키텍처**를 완성했습니다.

---

### 결정 3: 삭제(Delete) 대신 자연 키 기반 Upsert와 상시 조회 개방
멱등성을 확보하기 위해 수집 시작 시 데이터를 삭제하는 행위를 일체 금지했습니다.

* **식약처 고유 ID가 없는 문제 해결**: 식약처 API 명세상 고유 식별 키가 마땅치 않았기 때문에, 성분의 자연 키(Natural Key)인 `inci_name` (영문명)과 `korean_name` (국문명)의 해시 조합을 고유 식별자로 정의했습니다.
* **Upsert 전략**: 수집 엔진은 무조건 이 자연 키 기준으로 DB를 조회하여, 이미 존재하는 레코드라면 기존의 관리자 보강 내역이나 에러 기록을 덮어쓰지 않고 변경된 항목만 업데이트(`Upsert`)합니다.
* **상시 개방 피드 구축**: 운영 DB(`IngredientMaster`)에 이미 등록된 성분이라 하더라도 `cas_no`가 비어 있거나 유효하지 않다면, 수집 루프에서 스킵하지 않고 "보강 필요 대상"으로 필터링하여 외부 CAS 스크래핑 엔진의 인풋으로 상시 제공되도록 파이프라인을 개방형(Closed Loop)으로 재조정했습니다.

---

### 결정 4: Fault-Tolerant 네트워크 루프 구현 (The Rule of 3)
단 한 번의 빈 응답으로 루프가 깨지는 취약성을 방어하기 위해 **슬라이딩 윈도우 방식의 종료 조건**을 도입했습니다.

네트워크 타임아웃이나 파싱 에러 등의 개별 예외는 Staging 테이블의 `error_message`에만 로깅하고 루프를 지속하되, **"3회 연속으로 실제 알맹이가 없는(Empty) 데이터가 올 때만"** 배치를 정상 종료 처리하도록 감지 모델을 강화했습니다.

## 3. 리팩토링 결과 및 엔지니어링 성과

### 깔끔하게 분리된 관심사 (Clean Architecture)
기존의 복잡한 `admin.py`에서 수집 및 스케줄러 관련 비즈니스 로직을 완벽히 분리해 내어 `app/routers/seeding.py`로 물리적 격리를 마쳤습니다. 

```python
# app/routers/seeding.py (개념 예시 코드)
@router.post("/sync/kfda", status_code=status.HTTP_202_ACCEPTED)
async def trigger_kfda_sync(
    background_tasks: BackgroundTasks,
    current_admin: User = Depends(get_current_admin)
):
    """
    관리자 검증 게이트를 제공하는 안전한 식약처 데이터 동기화 백그라운드 태스크
    """
    background_tasks.add_task(kfda_ingestion_service.run_pipeline)
    return {"message": "식약처 동기화 파이프라인이 백그라운드에서 안전하게 시작되었습니다."}
```

이 개선을 통해 변경 사항 발생 시 개발자가 안전하게 배포할 수 있게 되었고, 수집 파이프라인 오작동이 전체 관리자 화면 마비로 이어지던 결합도를 완전히 제거했습니다.

### 정량적 효과
* **데이터 무손실 달성**: 재수집 시 에러 이력 유실율 **0%** 달성.
* **CAS 보강률 향상**: 기존에 누락되어 방치되던 성분들의 상시 보강 피드가 열리면서 미보강 성분의 **완전 추적률 100%**에 도달.
* **네트워크 내결함성 확보**: 일시적인 API 서버 불안정으로 인한 데이터 조기 종료 건수가 개편 이후 단 한 건도 보고되지 않음.

## 💡 엔지니어링 교훈 (Takeaways)

이번 재설계 작업을 거치며 저희 팀이 얻은 가장 큰 배움은 다음과 같습니다.

1. **상태(State)는 분리될수록 안전하다**: 편의를 위해 하나의 문자열 필드에 여러 의미(수집 성공 여부 + 데이터 비즈니스 단계)를 욱여넣으면, 비즈니스가 고도화될 때 반드시 상태 전이의 모순이 발생합니다. 명확히 직교하는 상태는 컬럼 단위로 분리하는 것이 장기적으로 훨씬 유연합니다.
2. **멱등성은 인프라가 아닌 애플리케이션의 태도다**: "언제든, 몇 번이든 다시 돌려도 시스템이 안전해야 한다"는 원칙을 지키기 위해서는 인위적인 `Delete`를 지양하고 자연 키 설계와 `Upsert`를 기본 골자로 가져가야 합니다.
3. **외부 API는 언제든 실패할 수 있음을 가정하라**: 외부 파트너사나 공공 데이터는 우리의 SLA(Service Level Agreement)를 고려해주지 않습니다. 따라서 유연한 재시도 기법(Retry Window)과 수동 검토용 DLQ(Dead Letter Queue)를 구축하는 것은 선택이 아닌 필수입니다.

PickSafe 팀은 단순한 기능 구현을 넘어, 데이터 하나하나가 완벽한 신뢰를 지킬 수 있도록 아키텍처를 끊임없이 리팩토링하고 있습니다. 이러한 기술적 엄격함이야말로 저희 서비스가 고객에게 가장 안전한 성분 가이드를 제공할 수 있는 원동력입니다.
