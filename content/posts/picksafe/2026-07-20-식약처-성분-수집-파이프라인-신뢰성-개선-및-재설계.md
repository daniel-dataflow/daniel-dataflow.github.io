안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

우리가 매일 사용하는 화장품과 식품의 안전을 책임지기 위해, PickSafe는 식약처(MFDS) 공공 데이터 및 화장품협회(KCIA) 데이터를 주기적으로 수집하여 대용량 성분 사전 마스터 데이터를 구축하고 있습니다. 

공공 API 기반의 데이터 파이프라인을 운영하다 보면, 네트워크 일시 오류, 스펙 미비, 불완전한 상태 관리 등으로 인해 데이터 유실이나 정합성 오류를 마주하곤 합니다. 최근 저희 팀도 기존 파이프라인에서 발견된 구조적 결함을 해결하고, **어떠한 실패 환경에서도 데이터의 안정성과 멱등성(Idempotency)을 보장할 수 있는 고성능 파이프라인으로 재설계**하는 과정을 거쳤습니다.

이 과정에서 고민했던 기술적 문제와 아키텍처 관점에서의 해결책, 그리고 얻은 교훈을 공유합니다.

---

## 1. 기존 시스템의 문제 정의 (What went wrong?)

기존 파이프라인은 단순히 데이터를 '가져와서 적재하는 것'에만 집중하다 보니, 예외 상황에 대처하는 능력이 부족했습니다. 구체적으로는 다음과 같은 4가지의 치명적인 결함이 존재했습니다.

### ① 멱등성(Idempotency) 결여와 데이터 유실
수집 파이프라인을 처음(1페이지)부터 다시 구동할 때, 기존의 '임시 저장소(Staging)' 테이블에서 에러(`error`) 상태에 머물러 있는 데이터까지 일괄 삭제(Delete) 처리되는 로직이 있었습니다. 이로 인해 관리자가 오류 원인을 분석하고 대응하기 전에 데이터가 유실되는 심각한 상황이 발생했습니다.

### ② CAS(화학물질 식별번호) 누락 데이터의 영구 소외
성분 데이터는 국문명, 영문명 외에도 CAS 번호가 매핑되어야 가치가 극대화됩니다. 그러나 기존 로직은 마스터 테이블에 '이름'이 이미 존재하기만 하면 수집 루프에서 스킵(Skip)하도록 설계되어 있었습니다. 즉, 이름은 존재하지만 정작 중요한 CAS 번호가 비어 있는 성분들이 보강 및 재검토 후보군에서 영구적으로 격리되는 문제가 있었습니다.

### ③ API 일시 실패를 "데이터의 끝"으로 오인하는 조기 종료 (False EOF)
공공 API 호출 중 네트워크 일시 타임아웃이나 호출 제한(Rate Limit)으로 인해 일시적으로 빈(Empty) 데이터가 수신될 수 있습니다. 기존 시스템은 빈 응답을 받으면 이를 수집 완료(EOF) 단계로 착각하여 수집 루프를 조기 종료해 버렸습니다. 이로 인해 뒤쪽 페이지에 있는 데이터가 누수되는 현상이 빈번했습니다.

### ④ 모놀리식 라우터로 인한 유지보수 비용 상승
배치 주기 조절, CAS 수동 보강, 시딩(Seeding) 및 머지(Merge) 로직이 특정 단일 라우터 파일(`admin.py`)에 강하게 결합되어 있었습니다. 이로 인해 작은 코드 수정 시에도 잦은 병합 충돌(Git Conflict)이 발생했고, 서비스 안정성을 저해하는 리스크로 작용했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

저희 팀은 단순한 임시방편(Hot-fix)을 적용하기보다, 시스템의 본질적인 구조를 바꾸는 방향으로 결정을 내렸습니다.

### 고민 1. "단순 문자열 상태값(`status`)" vs "다차원 상태 속성 분리"

기존에는 Staging 테이블 내에 단일 String 형태의 `status`('pending', 'error', 'merged' 등) 컬럼을 두고 모든 흐름을 제어하려 했습니다. 그러다 보니 "네트워크 실패로 인한 에러"인지, "데이터 파싱은 성공했으나 CAS 번호가 누락된 에러"인지를 명확히 구분하기 어려웠습니다.

*   **대안 A (기존 유지 및 status 세분화):** `status_api_failed`, `status_no_cas` 등 문자열 값을 계속해서 추가하는 방식. 
    *   *단점:* 상태가 늘어날수록 비즈니스 흐름이 꼬이고 상호 배타적이지 않은 상태들이 뒤엉켜 스파게티 코드가 됩니다.
*   **대안 B (다차원 Boolean 및 독립 필드 분리 - 채택):** 의미론적으로 겹치지 않는 독립적인 도메인 필드들로 쪼갭니다.
    *   *장점:* 데이터 정합성 보장이 쉬워지고, 복잡한 상태 천이(State Transition)를 안전하게 관리할 수 있습니다.

### 고민 2. "전체 삭제 후 재적재(Clean and Insert)" vs "업서트(Upsert)"

*   **대안 A (삭제 후 재적재):** 수집 시점마다 데이터를 모두 밀고 새로 씁니다. 구현은 가장 단순합니다.
    *   *단점:* 수집 실행 중간에 장애가 날 경우 기존의 정상 데이터까지 모두 손실되어 서비스 불능에 빠질 수 있습니다. 멱등성이 전혀 보장되지 않습니다.
*   **대안 B (자연 키 기반의 Upsert - 채택):** 식약처 데이터 고유의 식별 정보인 `inci_name`(영문명)과 `korean_name`(국문명)의 조합을 복합 키처럼 활용하여, 기존 데이터가 존재하면 **업데이트**, 없으면 **삽입**하는 방식으로 개선합니다.
    *   *장점:* 실패 복구(Recovery)가 언제든 가능하며, 수집 도중 오류가 발생하더라도 이전에 수집된 데이터는 고스란히 보존됩니다.

## 3. 최종 해결책 및 아키텍처 설계 (The Solution)

위의 Trade-off 분석을 거쳐, 다음과 같은 견고한 자율형 복구 파이프라인(Self-healing Pipeline)을 설계하고 구현했습니다.

```
[식약처 API] ──(1) 3회 연속 빈 데이터 검증──> [Staging 데이터] (2) Upsert 처리 (inci_name, korean_name 기준)
                                                    │
                                                    ▼ (다차원 상태 분리)
                                            ┌───────────────┬───────────────┐
                                            ▼               ▼               ▼
                                      [sync_status]   [cas_status]     [is_merged]
                                       ('success' /    ('needed' /    (True / False)
                                        'failed')      'suggested' /        │
                                            │          'verified')          │
                                            │               │               ▼
                                   (3) 실패 시      (4) 보강 필요 시   [Master DB 이관]
                                   5회 재시도 루프   크롤러 스케줄러   (반드시 verified
                                   (DLQ로 이관)      상시 노출         상태만 병합)
```

### 1) 다차원 상태 속성의 완전 분리
복잡했던 단일 `status` 컬럼을 완전히 Drop하고, 역할이 격리된 5가지 속성으로 재정의했습니다.

*   `is_merged` (Boolean): 마스터 운영 테이블로 최종 이관되었는지 여부.
*   `sync_status` (String): API 수집 자체의 성공/실패 여부 (`success`, `failed`, `critical_failed`).
*   `cas_status` (String): CAS 번호 수집 상태 (`needed`, `suggested`, `verified`, `not_found`).
*   `cas_source` (String): CAS 출처 구분 (`kfda`, `kcia`, `manual`).
*   `retry_count` (Integer): 수집 재시도 횟수.

> 💡 **Critical Gate (승인 정책 강화):** 
> 크롤링 등을 통해 자동으로 분석된 CAS 제안 상태(`cas_status = 'suggested'`)의 성분은 **절대로 데이터베이스에 자동 병합되지 않도록 방어벽을 세웠습니다.** 반드시 관리자가 어드민 대시보드에서 최종 검토 및 승인을 거쳐 `verified`로 승격시켜야만 마스터 DB에 마이그레이션이 가능하게 통제권을 확보했습니다.

### 2) DLQ(Dead Letter Queue) 개념을 도입한 자동 재시도 루프
일시적인 네트워크 순단으로 수집에 실패한 이력들을 체계적으로 처리하기 위해 '재시도 큐(Queue)' 메커니즘을 적용했습니다.

*   신규 배치 구동 시, 먼저 `sync_status = 'failed'`이고 `retry_count < 5`인 페이지 목록을 최우선 수집 대상으로 추출하여 재시도를 수행합니다.
*   재시도가 성공하면 즉시 `success`로 정상화하고 데이터를 업데이트합니다.
*   만약 누적 재시도가 **5회를 초과**하면 시스템은 해당 요청을 **`critical_failed` 상태로 격리(Dead Letter Queue 역할)**합니다.
*   개발자나 시스템 관리자는 어드민 대시보드 오류 화면을 통해 `critical_failed` 데이터를 손쉽게 식별하고, 상세 API 에러 로그를 분석하여 원인을 즉각 수동 패치할 수 있습니다.

### 3) 멱등성을 보장하는 Upsert 파이프라인
더 이상 재수집 실행 시 기존 데이터를 비파괴적으로 다룹니다. 식약처 API에서 가져온 레코드를 임시 테이블에 저장할 때, 식약처 고유 자연 식별자인 `inci_name`을 기준으로 Upsert 처리를 적용하여 기존 데이터의 수집 히스토리와 오류 내역을 안전하게 보존합니다.

### 4) "연속 3회 빈 데이터" 수집 조기 종료 방지 설계
일시적인 API 지연으로 0건 응답이 왔을 때 즉시 중단되는 현상을 제거하기 위해, **연속 3회 빈 데이터 수신 시에만 루프를 공식 종료**하도록 허용 임계치(Tolerance Limit)를 두었습니다. 일시적인 1회성 무응답이나 네트워크 오류는 개별 `failed` 상태로 Staging 테이블에 고스란히 기록되며 전체 루프는 멈추지 않고 끝까지 진행됩니다.

### 5) 관심사 분리(SoC)를 통한 코드 구조 혁신
과도한 결합을 풀기 위해 라우터 구조 개편을 추진했습니다. 수집, 보강, 배치 스케줄과 관련된 모든 백엔드 엔드포인트를 무거운 `admin.py`에서 별도의 라우터 클래스(`seeding.py`)로 격리하였습니다. 비즈니스 단위로 파일과 책임을 쪼개면서 코드 병합 충돌 리스크를 90% 이상 대폭 줄였습니다.

## 4. 엔지니어링 교훈 (Takeaway)

이번 재설계 작업을 거치며 저희 백엔드 팀은 다음과 같은 중요한 엔지니어링 철학을 다시금 새길 수 있었습니다.

1.  **멱등성은 데이터 파이프라인의 핵심이다:**
    몇 번을 돌리든, 언제 실행하든 시스템이 안전하고 동일한 최종 상태(Consistent State)를 보장할 때 비로소 배치를 두려움 없이 자동화할 수 있습니다.
2.  **외부 API는 신뢰하지 마라 (Zero Trust for External API):**
    외부 통신은 언제든 끊어질 수 있고 비정상 데이터를 줄 수 있습니다. 에러 상태를 도메인 모델로 세분화하여 기록하는 다차원 상태 머신과 임계치를 둔 예외 처리는 대규모 데이터 통합에 필수적입니다.
3.  **수동 검토 영역을 명시적으로 격리하라:**
    아무리 훌륭한 자동화 파이프라인도 100% 완벽할 순 없습니다. `critical_failed` 상태를 지원해 시스템이 직접 해결하지 못하는 부분을 관리자용 도구를 통해 수동 검토하도록 유도하는 백업 전략이 훌륭한 사용자 경험(UX)과 시스템 데이터 정합성을 동시에 지키는 현실적인 방법입니다.

PickSafe 팀은 단순한 기능 개발에 그치지 않고, 대량의 이종 데이터가 맞물려 돌아가는 환경에서도 높은 안정성과 유연성을 주는 견고한 엔지니어링 아키텍처를 치열하게 고민하고 설계합니다. 

앞으로도 더 안전하고 안정적인 서비스를 만들기 위한 기술 여정은 계속됩니다. 읽어주셔서 감사합니다!
