안녕하세요. 백엔드 엔지니어링 과정에서 마주한 공공 데이터 수집 파이프라인의 구조적 한계와, 이를 극복하기 위해 적용한 아키텍처 개선 경험을 공유하고자 합니다.

서비스를 운영하며 외부 공공 API(식약처 성분 정보 등)를 연동해 데이터를 적재하는 파이프라인은 흔히 볼 수 있는 구조입니다. 하지만 **"외부 API는 언제나 실패할 수 있고, 데이터는 불완전할 수 있다"**는 전제를 놓치는 순간 데이터 유실과 유지보수 지옥이 시작됩니다. 

최근 PickSafe 프로젝트에서 운영 중이던 식약처 성분 수집 및 CAS 번호 보강 시스템을 전면 재설계하면서 고민했던 문제와 해결 과정을 기록합니다.

---

## 1. 기존 파이프라인의 치명적인 문제점 (Problem)

기존 시스템은 작동하는 것처럼 보였지만, 대규모 데이터와 반복적인 수집(Re-seeding) 상황에서 다음과 같은 구조적 결함(Architectural Debt)을 드러냈습니다.

1. **멱등성(Idempotency) 결여로 인한 데이터 유실**:
   수집 루프를 재시작할 때마다 임시(Staging) 테이블의 에러 이력(`error` 상태)을 일괄 삭제(`delete()`)하도록 구현되어 있었습니다. 관리자가 에러를 확인하고 조치하기도 전에 데이터가 증발하는 현상이 발생했습니다.
2. **CAS 번호 누락 데이터의 영구 소외**:
   실운영 테이블(`IngredientMaster`)에 성분 이름이 이미 존재하면 수집 루프에서 스킵(Skip)해 버렸습니다. 이로 인해 CAS 번호가 비어 있는 채로 등록된 성분들은 보강 기회를 영구히 박탈당했습니다.
3. **네트워크 장애에 취약한 조기 종료 (False Termination)**:
   외부 공공 API 호출 중 일시적인 타임아웃이나 제한으로 빈 데이터가 수신되면, 시스템은 이를 "데이터의 끝"으로 오인하여 수집 루프를 조기 종료해 버렸습니다.
4. **모놀리식한 라우터 구조 (`admin.py` 비대화)**:
   Seeding, CAS 보강, 스케줄링, 병합 로직이 모두 하나의 거대한 관리자 라우터 파일에 얽혀 있어, 작은 수정에도 구문 충돌과 소스 손상 위험이 컸습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off & Design Decisions)

이 문제를 해결하기 위해 **데이터 무결성(Data Integrity)**, **회복 탄력성(Resilience)**, **관심사 분리(Separation of Concerns)**를 핵심 원칙으로 삼고 설계를 전면 수정했습니다.

### ① 단일 Status 컬럼의 폐기 및 다차원 상태 속성 분리
* **고민**: 기존에는 `status`라는 하나의 문자열 컬럼(`pending`, `error`, `suggested` 등)으로 수집 상태와 검증 단계를 모두 표현하려다 보니 상태가 꼬였습니다.
* **대안 및 선택**: 단순 `status` 컬럼을 완전히 제거하고, 독립된 5개의 필드로 분리했습니다.
  * `is_merged` (Boolean): 운영 DB 반영 여부 (**[CRITICAL GATE]**: 외부 스크래핑으로 추천된 CAS 번호(`suggested`)는 관리자 승인(`verified`) 없이는 절대 자동 병합될 수 없도록 차단 장치 마련)
  * `sync_status` (String): 통신 성공 여부 (`success` / `failed` / `critical_failed`)
  * `cas_status` (String): CAS 번호 상태 (`needed` / `suggested` / `verified` / `not_found`)
  * `cas_source` (String): 데이터 출처 (`kfda`, `kcia`, `manual`)
  * `retry_count` (Integer): 실패 재시도 횟수
* **결과**: "API 통신 자체의 실패"와 "성분 데이터는 가져왔으나 CAS 번호가 빈 상태"를 명확히 격리하여 파이프라인의 가시성을 높였습니다.

### ② 멱등성 보장형 Upsert 및 실패 건 자동 재시도 (Fault-Tolerant Loop)
* **고민**: 데이터를 통째로 지우고 다시 넣는 방식(`Delete-Insert`)은 안전하지 않습니다. 또한 일시적인 네트워크 에러로 누락된 페이지를 어떻게 구제할 것인가?
* **대안 및 선택**: 
  1. 기존 Staging 데이터를 삭제하는 로직을 제거하고, 고유 자연 키인 `inci_name`(영문 성분명)과 `korean_name`(국문 성분명) 기반의 **Upsert(존재하면 갱신, 없으면 삽입)** 전략으로 전환했습니다.
  2. 파이프라인 구동 시 `sync_status = 'failed'`이면서 `retry_count < 5`인 레코드의 페이지 번호를 먼저 수집하여 **우선 재시도**하도록 구현했습니다. 5회 이상 실패 시 `critical_failed`로 전환하여 어드민 대시보드에 격리합니다.
  3. API 응답이 비어 있더라도 1회 만에 종료하지 않고, **최대 3회 연속 빈 데이터 수신 시에만 진짜 끝**으로 판단하도록 방어 로직을 추가했습니다.

### ③ 아키텍처 구조 개선 (라우터 분리)
* **대안 및 선택**: [admin.py](file:///home/daniel/dev/picksafe/web/backend/app/routers/admin.py)에 혼재되어 있던 모든 식약처 수집 및 스케줄러 관련 코드를 독립된 라우터인 `app/routers/seeding.py`로 물리적으로 완전히 분리했습니다.

## 3. 엔지니어링 교훈 (Takeaways)

1. **외부 의존성은 언제나 실패를 가정해야 한다**: 
   공공 API나 서드파티 연동 파이프라인을 구축할 때, "정상적인 응답"을 가정하고 코드를 짜면 장애 발생 시 데이터가 오염되거나 유실됩니다. 재시도 상한선(`retry_count`)과 장애 격리(`critical_failed`) 같은 회복 탄력성 메커니즘은 선택이 아닌 필수입니다.
2. **비즈니스 상태와 시스템 상태의 분리**:
   데이터베이스 설계 시 여러 의미를 하나의 상태(`status`) 컬럼에 우겨넣으면 기술 부채가 빠르게 쌓입니다. `is_merged`, `sync_status`, `cas_status`처럼 관심사를 독립된 컬럼으로 쪼개는 것이 장기적인 유지보수성에 훨씬 유리합니다.
3. **안전장치(Critical Gate)의 명시화**:
   자동화 파이프라인이 아무리 고도화되어도, 관리자의 검증이 반드시 필요한 영역(예: CAS 번호 자동 매칭 후 승인)에는 명확한 시스템적 게이트를 두어 휴먼 에러나 시스템 폭주를 방지해야 합니다.

이번 파이프라인 재설계를 통해 데이터 유실 없는 무결한 수집 체계를 구축하였으며, 향후 확장되는 다른 공공 데이터 연동 작업에도 견고한 베이스라인을 마련할 수 있었습니다.
