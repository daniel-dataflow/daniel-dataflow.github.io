외부 데이터 API를 연동하여 서비스를 구축해 본 엔지니어라면 누구나 공감하는 사실이 있습니다. **"외부 API는 결코 우리가 원하는 대로 동작해주지 않는다"**는 점입니다. 

네트워크 타임아웃, 예고 없는 응답 구조 변경, 비어 있는 결과값, 그리고 모호한 오류 응답까지… 데이터의 수집 및 보강 파이프라인(ETL)이 외부 시스템에 의존할수록, 시스템의 회복 탄력성(Resilience)과 데이터 무결성(Data Integrity)을 유지하는 것은 서비스의 핵심 경쟁력이 됩니다.

이번 글에서는 **PickSafe** 팀이 식약처(MFDS) 공공 성분 API 데이터를 수집·보강하는 파이프라인에서 마주친 4가지 치명적인 데이터 무결성 문제를 정의하고, 이를 **멱등성(Idempotency) 보장, 다차원 상태 데이터 모델 도입, 그리고 내결함성(Fault-tolerant) 구조 전환**을 통해 해결한 엔지니어링 여정을 공유합니다.

---

## 1. 문제 정의: "운영 환경에서 데이터가 사라지고 멈춘다"

초기 수집 시스템은 빠르게 MVP를 구축하기 위해 단편적인 루프 스크립트 형태로 작성되었습니다. 그러나 데이터 축적량이 늘어나고 외부 API의 일시적 장애가 빈번해지면서 다음과 같은 4가지 설계 결함이 드러났습니다.

```
[기존 파이프라인의 악순환]
API 수집 실패 발생 ➔ 'error' 상태 데이터 적재 ➔ 재수집 실행시 기존 데이터 일괄 삭제(Data Loss) 
  ↳ 빈 응답 수신 시 데이터 끝으로 오인해 전체 루프 조기 종료 (False Termination)
```

1. **멱등성 결여로 인한 데이터 유실**
   - 수집 파이프라인이 재실행될 때마다 이전 수집에서 발생한 미해결 에러 레코드(`error` 상태)를 일괄 삭제(`DELETE`)하는 로직이 존재했습니다. 이로 인해 관리자가 오류 원인을 분석하기도 전에 이력이 파기되었습니다.
2. **CAS(화학물질 고유번호) 누락 데이터의 영구 소외**
   - 실운영 DB에 성분명이 이미 존재하면 수집 대상에서 스킵(`SKIP`)하는 로직 탓에, 데이터는 존재하지만 핵심 정보인 CAS 번호가 비어 있는 성분들이 보강 대상에서 영구적으로 제외되었습니다.
3. **네트워크 지연/타임아웃 시 조기 종료(False Termination)**
   - 외부 API가 순간적인 과부하나 지연으로 인해 0건의 데이터를 반환하면, 파이프라인이 이를 "전체 데이터의 끝"으로 착각하여 수집 루프를 조기 탈출(`break`)했습니다.
4. **단일 모듈 밀집에 따른 아키텍처 리스크**
   - API 엔드포인트, 수집 스케줄러, 크롤링, DB 병합 로직이 단일 라우터(`admin.py`)에 뒤엉켜 있어 작은 코드 수정에도 구문 충돌 및 사이드 이펙트가 빈번했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 단순히 코드를 수정하는 임시방편(Monkey Patch)이 아닌, **파이프라인 아키텍처의 근본적인 재설계**를 결정했습니다. 이 과정에서 몇 가지 핵심적인 기술적 고민이 있었습니다.

### 고민 1: 단일 문자열 상태(Status Enum) vs 다차원 상태 분리 (Granular Flags)

* **기존 방식**: `status` 컬럼 하나로 `'pending'`, `'error'`, `'suggested'`, `'merged'`를 모두 표현.
* **문제점**: "API 수집의 성공/실패 여부"와 "성분 데이터(CAS 번호)의 보강 상태", 그리고 "운영 DB로의 이관 여부"라는 **서로 다른 맥락(Context)이 하나의 상태값에 뒤엉키는 현상**이 발생했습니다.
* **대안 선택**: 상태를 5개의 독립된 속성(Field)으로 분리하는 다차원 상태 모델 도입.
  * **[Trade-off]** DB 컬럼 수가 늘어나고 업데이트 쿼리가 다소 복잡해지지만, 시스템의 현재 상태를 명확히 추적할 수 있고 불확실한 상태 조합을 원천 차단할 수 있습니다.

### 고민 2: 삭제 후 재삽입(Delete & Insert) vs 멱등성 보장 Upsert

* **기존 방식**: 수집 시작 시 기존 Staging 데이터를 삭제하고 새로 Insert.
* **대안 선택**: 영문 성분명(`inci_name`)과 국문 성분명(`korean_name`)의 고유 유일성(Natural Key)을 기반으로 한 **Upsert(ON CONFLICT UPDATE)** 전략 적용.
* **[Trade-off]** 갱신 조건 판단을 위한 DB 조회 비용이 발생하지만, 데이터 덮어쓰기 방지 및 이력 보존을 통해 완전한 **멱등성(몇 번을 실행해도 결과가 동일함)**을 얻었습니다.

## 3. 핵심 해결 방안 및 구현 아키텍처

### 1) 다차원 상태 모델 설계 & 게이트키퍼(Gatekeeper) 메커니즘

수집 상태와 보강 상태를 철저히 분리하여 데이터 파이프라인의 제어권을 확보했습니다.

```
[Staging Record Status Model]

1. API Sync Status  :  [ success | failed | critical_failed ]
2. CAS Status       :  [ needed | suggested | verified | not_found ]
3. CAS Source       :  [ kfda | kcia | manual ]
4. Operation Flag   :  is_merged (Boolean)
```

특히 데이터 품질 보증을 위해 **CRITICAL GATE (승인 장벽)**를 구축했습니다:

* 자동 크롤링을 통해 CAS 번호가 추정 보강된 데이터(`cas_status = 'suggested'`)는 **시스템이 절대로 자동 이관(`is_merged = True`)할 수 없도록 차단**했습니다.
* 반드시 관리자의 개별/일괄 승인 프로세스를 거쳐 `cas_status = 'verified'`로 변경된 데이터만 운영 DB 이관 파이프라인에 편입되도록 도메인 제약조건을 강제했습니다.

### 2) Fault-Tolerant 재시도 큐 및 Windowing 알고리즘

외부 API의 불안정성에 대응하기 위해 **2단계 회복 메커니즘**을 도입했습니다.

```
                  [수집 파이프라인 가동]
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
 [1단계: 과거 실패 큐 재시도]      [2단계: 신규 페이지 수집]
   retry_count < 5 인 건 조회         3회 연속 빈 데이터 수신 시에만
   수집 재시도 ➔ 성공/실패 갱신         정상 완료로 간주 (Sliding Window)
            │
            ▼
   5회 이상 연속 실패 시 
  'critical_failed' 전환 
  (어드민 수동 검토 대기)
```

1. **실패 페이지 우선 재시도 (Retry Queue)**:
   - 파이프라인 시작 시 과거 `sync_status = 'failed'` 상태인 레코드의 페이지 번호를 우선 수집 큐에 할당합니다.
   - 실패 횟수(`retry_count`)를 추적하여 5회 이상 실패 시 `critical_failed` 상태로 전환, 개발자 알림 대시보드로 격리합니다.
2. **슬라이딩 윈도우 기반 조기 종료 방지**:
   - 단 1회의 빈 응답으로 루프를 종료하지 않고, **최대 3회 연속 빈 데이터 응답이 수신되었을 때만 파이프라인을 안전하게 종료**합니다. 

### 3) 단일 책임 원칙(SRP)에 따른 라우터 및 서비스 분리

거대했던 단일 라우터를 도메인 영역별로 물리적 분리했습니다.

* `app/routers/seeding.py`: 데이터 수집, 배치 트리거, 재시도 큐 관리 전용 API.
* `app/services/seeding_service.py`: 수집 알고리즘 및 State Machine 제어 로직 비즈니스 레이어.
* 기존 `admin.py`는 Pure UI/Dashboard 관리를 위한 역할만 수행하도록 경량화했습니다.

## 4. 엔지니어링 성과 및 레슨 런 (Takeaway)

### 📈 도입 성과

* **데이터 유실률 0% 달성**: 재수집 시 기존 에러 이력이 삭제되던 현상을 완벽히 차단하였으며, 멱등성 있는 Upsert 구조를 정착시켰습니다.
* **CAS 데이터 보강 완전성(Closed Loop) 확보**: 운영 DB에 성분이 존재하더라도 CAS가 누락된 항목을 지속적으로 추적·보강하는 피드백 루프를 구축했습니다.
* **네트워크 회복 탄력성 증대**: 일시적 API 장애 발생 시 자동 재시도 큐를 통해 다음 배치 시점 시 99% 이상 자동 복구가 이루어졌습니다.

### 💡 핵심 레슨 런 (Takeaways)

1. **상태(State)는 명확할수록 안전하다.**
   하나의 문자열 컬럼에 여러 의미의 상태를 몰아넣는 것은 시한폭탄과 같습니다. 의미가 다른 상태값은 명시적인 필드로 분리할 때 데이터 흐름을 안전하게 제어할 수 있습니다.
2. **외부 시스템의 응답을 신뢰하지 마라.**
   성공 응답 속의 빈 배열, 순간적인 타임아웃은 일상적인 이벤트입니다. 내결함성을 고려한 재시도 메커니즘과 임계값(Threshold) 설정을 통해 시스템의 자가 치유(Self-Healing) 능력을 키워야 합니다.
3. **멱등성은 백엔드 파이프라인의 기본 덕목이다.**
   동일한 작업을 1번 실행하든 100번 실행하든 시스템은 동일한 건전성을 유지해야 합니다. 데이터베이스 레벨의 Upsert 전략과 Natural Key 설계는 파이프라인의 신뢰성을 지탱하는 가장 강력한 무기입니다.
