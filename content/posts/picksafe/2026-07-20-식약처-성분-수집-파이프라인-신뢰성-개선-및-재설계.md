외부 공공 기관이나 3rd-party API를 연동하여 대량의 마스터 데이터를 수집해 본 개발자라면 누구나 한 번쯤 네트워크 불안정성, 예고 없는 빈 데이터 응답, 그리고 고유 식별자(Primary Key)의 부재로 고통받은 경험이 있을 것입니다. 

PickSafe팀 역시 식약처 성분 공공 API를 기반으로 화장품 성분 데이터를 수집하고, 한국화장품협회(KCIA) 데이터 및 CAS No.(화학물질 고유번호)를 자동 보강하는 파이프라인을 운영하던 중 대용량 처리 구조와 상태 관리에 존재하는 심각한 허점들을 발견했습니다.

이번 포스팅에서는 기존 파이프라인이 안고 있던 데이터 무결성 문제를 해결하기 위해 **데이터 상태의 차원 분리, 멱등성을 보장하는 Upsert 전략, 그리고 Fault-Tolerant 재시도 메커니즘**을 구현한 엔지니어링 여정을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

초기 데이터 파이프라인은 빠른 기능 구현에 집중한 나머지, 운영 기간이 길어짐에 따라 다음과 같은 기술 부채와 데이터 유실 위험을 노출했습니다.

### ① 단일 `status` 문자열 컬럼의 상태 오버로딩 (State Overloading)
기존 DB는 `pending`, `error`, `suggested`, `merged`와 같은 단일 문자열 상태값 하나에 수집 통신 결과, 메타 데이터 보강 상태, 운영 DB 병합 여부를 모두 담고 있었습니다. 이로 인해 **"API 수집 실패인가?"**와 **"수집은 성공했으나 CAS 번호가 없어 보강이 필요한 상태인가?"**를 명확히 구분할 수 없었습니다.

### ② 멱등성(Idempotency) 결여로 인한 데이터 유실
전체 수집을 다시 실행할 때마다 임시(Staging) 테이블의 미해결 이력(`error` 상태)을 일괄 삭제하는 방식을 채택하고 있었습니다. 이로 인해 관리자가 오류 원인을 분석하거나 조치하기도 전에 수집 스케줄러가 돌아가면 기존 오류 데이터가 영구 유실되는 문제가 있었습니다.

### ③ CAS 미보강 데이터의 영구 소외
운영 데이터베이스에 성분 이름이 존재하면 수집 루프에서 무조건 스킵하는 단순한 중복 체크 로직 때문에, 초기 수집 시 CAS 번호를 채우지 못한 성분들은 보강 재검토 대상에서 영구적으로 소외되었습니다.

### ④ 타임아웃을 "데이터의 끝"으로 오인
공공 API 호출 시 간헐적인 네트워크 타임아웃이나 호출 제한으로 인해 빈 배열(`[]`)이 반환될 경우, 파이프라인이 이를 "마지막 페이지 도달"로 착각하여 작업을 조기 종료(`break`)해 버리는 현상이 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off Analysis)

### 고민 1: 단일 상태 체계를 유지할 것인가, 상태 속성을 독립시킬 것인가?

*   **대안 A: 기존 `status` 필드 세분화 (`status='error_cas_needed'` 등 추가)**
    *   *장점:* DB 스키마 변경 최소화.
    *   *단점:* 상태의 가지수가 폭발적으로 증가하며, 조건문 조건이 복잡해져 비즈니스 로직 파악이 어려워짐.
*   **대안 B (선택): 직교(Orthogonal) 관계의 다차원 상태 필드로 분리**
    *   *장점:* 수집 성공 여부(`sync_status`), CAS 검증 상태(`cas_status`), 운영 반영 여부(`is_merged`)를 완전히 독립적인 필드로 분리. 상태 전이 모델이 명확해지고 쿼리 성능 및 가독성 대폭 향상.

### 고민 2: 수집 실패 건에 대한 재시도 알고리즘 설계

네트워크 불안정으로 인한 실패를 처리하기 위해 단순히 `retry` 횟수를 늘리는 것은 API 서버에 부담을 주고 수집 시간을 지연시킵니다.

*   **선택한 접근법: 배치 기반 재시도 큐 + Dead Letter Queue 메커니즘**
    1. 수집 파이프라인 시작 시, 신규 데이터를 가져오기 전 이전 실행에서 `sync_status = 'failed'` 및 `retry_count < 5` 인 실패 페이지 목록을 선별.
    2. 해당 실패 페이지들을 우선 재시도.
    3. 재시도 성공 시 정상 상태로 보정, 5회 이상 지속적으로 실패할 경우 `critical_failed` 상태로 전환하여 자동 큐에서 제외하고 **어드민 수동 검토 대상(Dead Letter)**으로 전환.

## 3. 최종 해결책 및 아키텍처 (Implementation)

```
[식약처 공공 API]
       │
       ▼ (1. 멱등성 보장 Upsert)
[Staging Table (임시 적재)]
 ├── sync_status: success / failed / critical_failed
 ├── cas_status:  needed / suggested / verified / not_found
 └── is_merged:   True / False
       │
       ├─ (2. CAS 보강 프로세스: KCIA 크롤링) ──► cas_status: 'suggested'
       │
       └─ (3. [CRITICAL GATE] 어드민 승인) ────► cas_status: 'verified'
                                                       │
                                                       ▼ (4. 운영 DB 이관)
                                             [IngredientMaster (운영 DB)]
```

### ① 다차원 상태 모델 설계
의미가 엉켜있던 `status` 문자열을 비우고, 상태 전이를 명확하게 추적할 수 있도록 모델을 재구축했습니다.

*   `sync_status`: 외부 API 통신 상태 (`success` | `failed` | `critical_failed`)
*   `cas_status`: CAS 번호의 생애주기 (`needed` | `suggested` | `verified` | `not_found`)
*   `cas_source`: 데이터 출처 (`kfda` | `kcia` | `manual`)
*   `is_merged`: 운영 테이블 반영 완료 여부 (`Boolean`)

> **💡 Critical Gate 원칙:**  
> 자동 보강(KCIA 스크래핑)으로 CAS 번호가 채워진 데이터(`cas_status = 'suggested'`)는 **절대 시스템이 자동으로 운영 DB에 병합(`is_merged = True`)하지 못하도록 제약**을 두었습니다. 데이터 신뢰성을 위해 반드시 관리자의 승인을 거쳐 `verified` 상태로 전환된 건만 운영 DB 이관 파이프라인을 통과하도록 설계했습니다.

### ② 자연 키(Natural Key) 기반의 멱등성(Upsert) 수집
공공 API에 고유 PK가 존재하지 않는 문제를 해결하기 위해, 데이터 유일성을 식별할 수 있는 자연 키 복합체인 **`inci_name`(영문 성분명) + `korean_name`(국문 성분명)**을 기준으로 삼았습니다.

재수집 실행 시 기존 데이터를 일괄 삭제하던 비효율을 없애고, 이미 존재하는 레코드는 기존의 검토 이력과 메시지를 보존하면서 필요한 데이터만 Update하는 **Upsert 방식**으로 전환하여 파이프라인의 멱등성을 완성했습니다.

### ③ Fault-Tolerant 네트워크 루프
일시적 오류로 빈 데이터가 반환되어 루프가 끊기는 현상을 방지하기 위해, **'연속 3회 빈 데이터 수신 시에만 정상 종료'**로 판단하는 윈도우 기반 안전장치를 적용했습니다. 단발성 네트워크 타임아웃은 실패 이력으로 기록 후 계속 다음 페이지 수집을 진행하도록 회복 탄력성을 높였습니다.

### ④ 관심사의 분리 (Separation of Concerns)
기존에 단일 라우터 파일(`admin.py`)에 스케줄러 설정, 수집 로직, 데이터 병합 API가 얽혀있던 구조를 도메인 단위로 완전히 분리했습니다. 파이프라인 전용 라우터(`seeding.py`)를 추출하여 코드 변경 시 일어날 수 있는 사이드 이펙트와 구문 충돌 위험을 원천 차단했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **상태(State)는 아끼지 않고 명확히 분리해야 한다**  
   단일 컬럼으로 여러 도메인의 상태를 표현하려는 시도는 향후 시스템이 복잡해질 때 커다란 기술 부채로 돌아옵니다. 속성이 완전히 독립적이라면 디비 컬럼 역시 독립적이어야 합니다.
2. **외부 데이터 파이프라인의 핵심은 '멱등성'과 '회복 탄력성'이다**  
   외부 API는 언제든 실패할 수 있습니다. N번을 실행해도 동일한 결과를 보장하는 멱등성(Idempotency) 구조를 갖추고, 실패를 시스템 내에서 격리 및 자동 재시도할 수 있는 회복 탄력성을 구축해야 비로소 사람의 개입이 최소화된 안정적인 파이프라인이 완성됩니다.
3. **자동화 프로세스 사이의 'Human-in-the-loop' 안전장치**  
   모든 것을 자동화하는 것이 완벽한 엔지니어링은 아닙니다. 데이터 무결성이 매우 중요한 영역에서는 `suggested` -> `verified` 단계처럼 시스템 자동화와 인간의 승인 절차(Human-in-the-loop)를 결합하는 것이 서비스 신뢰도를 지키는 확실한 보루가 됩니다.
