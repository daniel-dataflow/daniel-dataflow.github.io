프로덕트를 운영하다 보면 **"기술적으로 올바른 검증 로직"이 "실제 비즈니스 요구사항"과 충돌하는 순간**을 마주하게 됩니다. 

최근 뷰티/헬스케어 도메인 서비스를 재구축하면서 국내 식약처 성분 데이터를 마스터 DB에 편입하는 작업을 진행했습니다. 그 과정에서 약 1,000여 개의 성분이 수집 과정에서 지속적으로 탈락하는 현상을 발견했고, 이를 해결하기 위해 **서비스 가용성을 유지하면서 데이터 완성도를 비동기적으로 극대화하는 '이중 관리(Dual Management) 아키텍처'**를 설계했습니다.

이번 포스팅에서는 기술적 문제를 정의한 과정부터, 트레이드오프를 고려한 아키텍처 선택, 그리고 이를 구현하며 얻은 엔지니어링 교훈을 공유합니다.

---

## 1. 문제 정의: 엄격한 데이터 검증과 도메인 현실의 충돌

### 문제 상황
서비스 내 성분 스캔 기능의 매칭률을 높이기 위해 식약처 공인 화장품 성분 2만 여 건을 수집·편입하는 파이프라인을 가동했습니다. 그러나 수집 결과 약 1,000건의 성분이 오류 검토 큐로 분류되며 서비스 마스터 DB에 들어가지 못했습니다.

* **오류 대상**: "가공소금", "누룩추출물", "온천수" 등 주요 천연/식품/복합 원료 성분
* **영향**: 해당 성분이 포함된 바디스크럽, 발효 화장품 등을 스캔할 경우, 정상 식약처 등록 성분임에도 사용자에게 `❓ 미확인 성분`으로 표시됨.

```
[원인 분석]
기존 파이프라인의 파싱 엔진은 화학물질 고유 식별자인 'CAS 번호(Chemical Abstracts Service Registry Number)'의 유효성 검증(예: Standard Number Pattern)을 필수 조건(Strict Validation)으로 강제하고 있었습니다.

하지만 '천연 복합물'이나 '식품 원료'는 특성상 국제적으로 단일 CAS 번호가 존재하지 않거나(N/A), 복수 존재하는 도메인적 특성을 가집니다. 기술적 유효성 검증이 도메인 데이터의 특성을 반영하지 못해 정상 데이터를 '오류'로 낙인찍고 있었던 것입니다.
```

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 크게 3가지 대안을 검토했습니다.

| 구분 | 대안 A: CAS 유효성 검증 완전 제거 | 대안 B: 사전 수동 보강 후 일시 편입 | 대안 C: 이중 관리 파이프라인 구축 (선택) |
| :--- | :--- | :--- | :--- |
| **방식** | CAS 번호 유효성 검사를 완전히 끄고 모든 데이터 수집 | 관리자가 1,000여 건의 CAS를 모두 조사하여 채운 뒤 DB 반영 | **[읽기]** CAS 없이 즉시 마스터 DB 편입<br>**[쓰기/보강]** 별도 큐에서 비동기 보강 |
| **장점** | 개발 공수가 가장 적음 | 데이터 무결성 최상 유지 | **서비스 매칭률 즉시 100% 달성 + 데이터 무결성 비동기 확보** |
| **단점** | DB 내 데이터 오염 및 중복 레코드 제어 불가능 | 출시 일정이 수 주간 지연됨 (운영 병목) | 초기 상태 관리 및 비동기 파이프라인 구현 공수 발생 |

### 최종 선택: 대안 C (Dual Management Architecture)
사용자 경험(UX) 측면에서 `미확인 성분` 오분류를 제로화하는 것이 최우선 과제였습니다. 따라서 **사용자 서비스 영역(Read Path)에서는 데이터 가용성을 최우선**으로 두고, **관리자/데이터 영역(Write Path)에서는 데이터 무결성을 비동기적으로 맞춰가는(Eventual Consistency) 이중 관리 방식**을 선택했습니다.

## 3. 핵심 아키텍처 및 구현

전체 데이터 흐름은 **(1) 서비스 즉시 편입 파이프라인**과 **(2) CAS 비동기 보강 파이프라인**으로 완벽히 분리됩니다.

```
+-----------------------------------------------------------------------------------+
| 1. Ingestion Engine (즉시 서비스 편입)                                             |
|                                                                                   |
|  [식약처 데이터 수집] ---> (CAS 유무 확인) --+--[CAS 있음]---> [Master DB 반영]   |
|                                            |                                      |
|                                            +--[CAS 없음]---> [Master DB 반영]      |
|                                                              (cas_no = null)      |
|                                                                   |               |
|                                                                   v               |
|                                                      [📌 CAS 보강 전용 큐]         |
+-----------------------------------------------------------------------------------+
                                                                    |
+-------------------------------------------------------------------v---------------+
| 2. Async Enrichment Engine (비동기 데이터 보강)                                      |
|                                                                                   |
|  [CAS 보강 큐 (Pending)]                                                           |
|        |                                                                          |
|        +---> 🤖 [PubChem PUG-REST API 백그라운드 배치] ---> (자동 CAS 검색 및 저장) |
|        |                                                                          |
|        +---> ✍️ [어드민 UI 수동 에디터] ---------------> (공인 사전 조회 후 검증)  |
+-----------------------------------------------------------------------------------+
```

### 1) Master DB 모델 및 식별자 표준화
* **Graceful Degradation**: 한글 성분명이 존재하는 공인 성분은 `cas_no = null` 상태로 마스터 DB(`IngredientMaster`)에 즉시 등록합니다.
* **표준 식별자 보존**: 국제 성분명(INCI)이 비어있는 천연물의 경우, `N/A-[한글성분명]` 형태의 합성 키(Synthetic Key)를 생성하여 시스템 내 식별성을 확보했습니다.
* **상태 추적 메타데이터**: DB 레코드에 `cas_enrichment_status` (`none` | `pending` | `completed`) 필드와 인덱스를 추가하여 보강 대상을 빠르게 격리 조회할 수 있도록 했습니다.

### 2) 외부 API 연동 및 자동화 배치 (PubChem PUG-REST)
데이터 보강을 수작업에만 의존하지 않도록, **미국 국립보건원(NIH)의 PubChem PUG-REST API**를 연동한 자동 탐색 엔진을 구축했습니다.

* 백그라운드 비동기 작업(Async Batch)이 `pending` 상태인 성분들을 순차적으로 읽어 PubChem 레지스트리에 한글/영문 성분명을 질의합니다.
* 매칭되는 화학 식별자 및 CAS 번호를 수집하여 검증을 거친 후 자동 업데이트하고 상태를 `completed`로 전환합니다.

### 3) 3대 공인 사전 연동 및 운영 도구 제공
자동 탐색으로 해결되지 않는 모호한 천연물 복합체 데이터를 위해 어드민 전용 탭을 구축했습니다.
* 국내외 3대 공인 성분 사전(**KCIA**, **CosIng**, **K-REACH**)을 원클릭으로 열람할 수 있는 딥링크(Deep Link) 파라미터를 생성했습니다.
* 관리자가 외부 사전을 새 창에서 즉시 검증하고 인라인(Inline)으로 CAS를 정정/저장할 수 있는 에디터 UI를 제공하여 운영 효율을 대폭 향상시켰습니다.

### 4) 읽기 성능 최적화 (Read Path Isolation)
2만 여 건의 마스터 성분 데이터가 변경/보강되더라도 사용자 서비스 스캔 요청 시 메인 DB에 조회 부하를 주지 않도록 설계했습니다.
* 보강 작업 완료 시 백그라운드에서 **정적 In-Memory JSON 캐시(`ingredients_master.json`)**를 자동 리빌드하도록 구성했습니다.
* 이를 통해 스캔 서비스의 DB Read IOPS를 0%에 가깝게 유지하면서 고성능 성분 매칭을 보장했습니다.

## 4. 성과 및 엔지니어링 교훈 (Takeaways)

### 정량적 성과
* **성분 매칭률 100% 달성**: "가공소금", "누룩추출물" 등 1,000여 건의 천연/식품 성분이 정상 매칭되어, 앱 내 스캔 오분류(`미확인 성분`) 건수를 zero로 만들었습니다.
* **보강 자동화율 확보**: PubChem API 백그라운드 배치를 통해 미보유 CAS 성분 중 상당수를 자동 식별 및 보강했습니다.
* **DB 부하 차단**: 데이터 보강/수정 작업과 사용자 읽기 경로를 정적 캐싱으로 격리하여, 배치 가동 중에도 서비스 응답 속도 Latency를 안정적으로 유지했습니다.

### 엔지니어링 교훈

1. **데이터 모델은 현실 도메인을 반영해야 한다**
   엔지니어링 관점에서 "모든 성분은 고유한 CAS 번호를 가져야 한다"는 전제는 깔끔한 PK/FK 관계를 만듭니다.하지만 실제 도메인 데이터(천연물, 복합 원료)는 기술적 규칙을 벗어납니다. **엄격한 스키마 검증이 도메인의 현실성을 가로막지 않도록 유연하게 설계**해야 함을 배웠습니다.

2. **읽기(Read)와 쓰기(Write)의 목적 분리 (CQRS의 아이디어 활용)**
   사용자에게 필요한 것은 "이 성분이 안전한가"에 대한 빠른 응답(High Availability)이며, 관리자에게 필요한 것은 "이 성분의 화학적 식별자 완성도"(Data Completeness)입니다. 두 요구사항의 시점을 분리하여 **'선 제공, 후 보강(Eventual Consistency)'** 전략을 취함으로써 비즈니스 가치와 데이터 품질을 모두 잡을 수 있었습니다.

---

> **Editor's Note**: 데이터 파이프라인을 구축할 때 가장 경계해야 할 것은 '완벽한 데이터만 입력받겠다'는 기술적 욕심일지도 모릅니다. 때로는 불완전한 데이터를 시스템 내로 안전하게 받아들이고, 이를 점진적으로 정제해 나가는 비동기 아키텍처가 프로덕트와 사용자 모두에게 훨씬 더 큰 가치를 제공합니다.
