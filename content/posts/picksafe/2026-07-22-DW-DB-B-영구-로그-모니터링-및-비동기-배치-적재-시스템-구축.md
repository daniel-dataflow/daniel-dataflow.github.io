클라우드 기반 PaaS 환경에서 서비스를 운영하다 보면 마주치는 고질적인 문제가 있습니다. 바로 **가상 컨테이너의 휘발성(Ephemeral) 디스크 특성**입니다. 

서버가 재부팅되거나 핫리로드가 발생할 때마다 로컬에 쌓아둔 텍스트 로그(`/log/app/app.log`)가 초기화되어, 과거 장애의 원인을 추적하거나 장기적인 모니터링을 수행하기가 어려웠습니다.

이번 글에서는 외부 원격 데이터베이스(DW DB B)를 활용해 영구 시스템 로그 모니터링 시스템을 구축하면서 마주한 기술적 난관들과, 서버 비용(Compute 소비)을 0%에 가깝게 유지하면서도 에러 로그 손실률 0%를 달성하기까지의 아키텍처 고도화 과정을 공유합니다.

---

## 1. 문제 정의 (Problem Definition)

초기 시스템에는 다음과 같은 치명적인 한계가 있었습니다.
1. **로그 유실**: Render 등 PaaS 환경의 컨테이너 재부팅 시 로컬 로그 파일이 삭제되어 장애 추적 불가.
2. **비용 및 리소스 낭비 우려**: 원격 DB(Neon DB 등)에 로그를 실시간으로 스트리밍할 경우, 상시 커넥션 유지로 인해 **DB Autosupend(유휴 수면) 기능이 방해**받아 불필요한 컴퓨팅 비용이 발생.
3. **HTTP 요청 블로킹 위험**: 로그를 기록하는 I/O 작업이 메인 애플리케이션 스레드를 블로킹하여 전체 API 성능 저하 유발.

---

## 2. 기술적 고민과 대안 비교 (Trade-offs & V1 ~ V5 고도화)

서버리스/PaaS 환경의 특성을 살리면서 신뢰성을 확보하기 위해, 총 5단계에 걸쳐 아키텍처를 점진적으로 고도화했습니다.

### [V1 ~ V2] 인메모리 버퍼와 Neon Autosuspend 보장
* **초기 아이디어 (V1)**: 단순 20초 주기 버퍼링. 
  * *리스크*: 컨테이너가 비정상 종료(SIGKILL / OOM-kill)될 경우 직전의 결정적 에러 로그가 유실되며, 고정 커넥션 유지로 인해 Neon DB의 수면 모드가 방해받음.
* **개선 (V2)**: 에러 발생 시에만 즉시 처리하고, 큐가 비어있을 때는 DB 커넥션을 100% 스킵하여 **Neon Compute 유휴 수면을 보장**하도록 구조 변경.

### [V3 ~ V4] Non-blocking 워커와 스레드 안전 큐 도입
* **V3 (비동기 디스패치)**: HTTP 요청 스레드 블로킹을 막기 위해 백그라운드 워커를 도입하고, 멀티라인 에러 트레이스백(`Traceback...`)을 하나로 병합하는 파서 로직 구현.
* **V4 (생산자-소비자 패턴)**: 단순 이벤트 신호 방식의 에러 누락 위험을 해결하기 위해 파이썬 표준 `queue.Queue`를 도입하여 스레드 안전성을 확보 (`log_queue.put_nowait()`). 또한, 14일이 지난 오래된 로그는 멱등성을 보장하며 자동 삭제되도록 설계.

### [V5] 예외 트레이스백 100% 보존 및 안전한 종료(Graceful Shutdown)
* **`self.format(record)` 강제 호출**: `logger.exception()` 호출 시 발생하는 스택트레이스 전문을 DB 메시지 컬럼에 온전히 보존.
* **정상 종료 시 플러시**: `SIGTERM` 등 서버 종료 시그널 수신 시, 큐에 남아있는 잔여 로그(`batch`)를 드롭하지 않고 안전하게 DB에 플러시하여 로그 유실 차단.
* **오버플로우 대비**: 큐가 가득 찼을 경우(`dropped_count`), 에러를 발생시키는 대신 드롭 건수를 카운팅하여 운영 리포트에 반영.

## 3. 최종 해결 및 핵심 아키텍처

### 3.1 2단계 이중 조회 (Tiered Log Reader)
비용과 성능을 모두 잡기 위해 로그 조회 방식을 이원화했습니다.
* **1차 (Primary - 실시간 모니터링)**: 어드민 UI의 5초 주기 폴링 시 로컬 디스크(`app.log`)를 직접 읽어 처리 (**Neon Compute 사용량 0%**).
* **2차 (Fallback - 장애 분석)**: 컨테이너 재부팅으로 로컬 파일이 비었거나 과거 14일간의 영구 이력이 필요할 때만 **DW DB B (`system_logs`)** 쿼리 조회.

### 3.2 3대 엔지니어링 디테일
1. **복합 인덱스 적용**: `created_at`, `level`, `service` 컬럼에 복합 인덱스를 구성하여 대용량 로그 속에서 원하는 구간을 빠르게 조회.
2. **Self-Reference (무한 재귀) 차단**: DB 쓰기 작업 중 에러가 발생했을 때, 습관적으로 `logger.error`를 호출하면 **로깅 핸들러가 다시 에러를 내고 무한 루프에 빠지는 참사**가 발생합니다. 이를 방지하기 위해 DB 실패 시 `sys.stderr.write`로 안전하게 우회 처리.
3. **글로벌 핸들러 및 셧다운 연동**: FastAPI 앱의 `@app.on_event("shutdown")` 라이프사이클과 연동하여 서버가 내려갈 때 버퍼에 남은 로그를 완벽하게 밀어 넣도록 구현.

## 4. Takeaway (엔지니어링 교훈)

이번 시스템 구축을 통해 얻은 가장 큰 교훈은 **"클라우드의 제약(휘발성, 비용 구조)을 아키텍처의 제약으로만 받아들이지 않고, 오히려 효율적인 설계의 트리거로 활용할 수 있다"**는 점입니다.

* **비용과 신뢰성의 타협점**: 모든 데이터를 무조건 원격 DB에 실시간 동기화하는 것이 능사가 아닙니다. 로컬 캐시/파일 시스템과 원격 DB의 역할을 명확히 나누고(Tiered Reader), 이벤트 성격에 따라 커넥션을 제어함으로써 **비용은 Free Tier 수준(약 17.5MB 유지)으로 아끼면서도 에러 손실률 0%**라는 견고함을 달성할 수 있었습니다.
* **방어적 프로그래밍의 중요성**: 로깅 시스템 자체의 에러(무한 재귀)나 컨테이너의 비정상 종료(SIGKILL) 같은 엣지케이스를 사전에 정의하고 방어 코드를 작성하는 것이 시니어 레벨의 안정성을 만든다는 것을 다시 한번 체감했습니다.
