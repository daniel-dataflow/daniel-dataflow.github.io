이번 포스팅에서는 PaaS 클라우드 환경에서 마주한 **컨테이너 휘발성(Ephemeral) 디스크 문제**를 해결하고, 서버리스 DB의 비용 최적화(Autosuspend 보장)와 실시간 장애 추적의 두 마리 토끼를 잡기 위해 구축한 **Non-blocking 비동기 로그 배치 적재 시스템**의 아키텍처 의사결정 과정을 공유합니다.

## 1. Problem: PaaS 환경의 휘발성 디스크와 서버리스 DB의 딜레마

현대 많은 클라우드 PaaS 플랫폼은 가상 컨테이너 기반으로 동작합니다. 이 환경의 가장 큰 특징 중 하나는 **휘발성(Ephemeral) 디스크**라는 점입니다.

* 서버가 재부팅되거나 핫리로드(Hot-reload)가 발생하면, 로컬에 쌓이던 로그 파일(`/log/app/app.log`)은 흔적도 없이 초기화됩니다.
* 이로 인해 과거 발생했던 치명적인 에러의 원인 추적이 불가능해지는 치명적인 한계가 있었습니다.

이를 해결하기 위해 원격 데이터베이스(DW DB B)에 `system_logs` 테이블을 두고 영구 저장하는 방안을 고려했습니다. 하지만 여기서 새로운 기술적 난관에 부딪혔습니다.

1. **서버리스 DB (Neon DB)의 Compute 수면 방해 문제**: 로그가 발생할 때마다 매번 DB에 싱크로나이즈드(Synchronous) 쿼리를 날리면, DB가 유휴 상태로 진입하지 못해(Autosuspend 방해) 불필요한 비용과 리소스가 낭비됩니다.
2. **로그 유실 위험**: 에러를 인메모리 버퍼에 모아두었다가 주기적으로 배치 처리할 경우, 서버가 비정상 종료(SIGKILL / OOM-kill)되면 버퍼에 있던 결정적 에러 로그가 그대로 유실됩니다.

## 2. Trade-offs & Architecture: V1부터 V5까지의 점진적 고도화

이 문제를 해결하기 위해 시스템을 총 5단계에 걸쳐 정밀하게 고도화했습니다.

### [V1 ~ V2] 인메모리 버퍼 도입과 Neon Autosuspend 보장
* **초기 시도(V1)**: 20초 주기 고정 인메모리 버퍼링. 하지만 Render 비정상 사망 시 로그 유실 위험과 20초마다 발생하는 고정 커넥션이 서버리스 DB의 수면을 방해하는 리스크를 발견했습니다.
* **개선(V2)**: 에러 레벨에 따른 이원화 전략을 도입했습니다. 큐가 비어있을 경우 DB 커넥션을 100% 스킵하여 Neon Compute의 유휴 수면을 완벽히 보장하도록 설계했습니다.

### [V3 ~ V4] Non-blocking 비동기 큐와 안정성 확보
* **Non-blocking 디스패치(V3)**: HTTP 요청 스레드가 로깅 I/O로 인해 블로킹되는 현상을 막기 위해 비동기 디스패치 구조를 적용하고, 멀티라인 에러 트레이스백(`Traceback...`)을 하나로 병합하는 파서를 구현했습니다.
* **스레드 안전 큐 도입(V4)**: 단순 이벤트 신호 방식의 에러 누락 위험을 방지하고자 파이썬 표준 생산자-소비자 큐(`queue.Queue`)와 `put_nowait()`를 결합하여 안정적인 비동기 파이프라인을 구축했습니다.

### [V5] 예외 스택트레이스 100% 보존 및 Graceful Shutdown
* **`self.format(record)` 보장**: `logger.exception()` 호출 시 생성되는 예외 스택트레이스 전문을 DB 메시지 컬럼에 온전히 담아내도록 핸들러를 정제했습니다.
* **종료 시 유실 차단**: SIGTERM 등 정상 종료 시그널 수신 시, 루프 종료 직전 잔여 큐 데이터를 강제로 플러시(`_write_batch`)하여 마지막 로그까지 안전하게 적재합니다.
* **무한 재귀(Self-Reference) 방지**: DB 쓰기 작업 자체에서 에러가 발생했을 때 `logger.error`를 호출하면 무한 루프에 빠지게 됩니다. 이를 방지하기 위해 `sys.stderr.write`로 예외를 우회 처리하여 에러 증폭을 원천 차단했습니다.

## 3. 최종 아키텍처 스펙

### 3.1 2단계 이중 조회 (Tiered Log Reader)
비용 효율과 실시간성을 모두 잡기 위해 조회 방식을 이원화했습니다.
* **1차 (Primary - 실시간 모니터링)**: 어드민 UI 폴링 시 로컬 디스크(`app.log`)를 직접 읽어옵니다. (**Neon Compute 사용량 0%**)
* **2차 (Fallback - 영구 이력 분석)**: 컨테이너 재부팅으로 로컬 파일이 비었거나, 과거 14일간의 이력을 조회할 때만 DW DB B (`system_logs`)를 조회합니다.

### 3.2 14일 자동 정제 (Retention Policy)
* 일평균 5,000건 기준, 14일간 유지되는 데이터 총용량은 약 **17.5 MB**로 산출되었습니다.
* 이는 Neon DB Free Tier(500MB)의 **약 3.5%** 수준에 불과하며, 24시간 데몬 스레드를 통해 14일이 지난 로그는 자동으로 정제(`DELETE`)되도록 설계하여토탈 스토리지를 타이트하게 관리합니다.

## 4. Takeaways (엔지니어링 교훈)

1. **서버리스 환경에서의 I/O 전략**: 서버리스 아키텍처를 도입할 때는 비용 모델(Compute Time)을 반드시 고려해야 합니다. 무심코 던지는 주기적 쿼리 하나가 오토스케일링/수면 기능을 방해할 수 있음을 배웠습니다.
2. **Observability와 안정성의 양립**: 로깅 시스템 자체가 장애를 일으키는 아이러니한 상황(Self-Reference)을 막기 위한 안전장치(`sys.stderr` fallback)의 중요성을 다시 한번 깨달았습니다.
3. **PaaS 제약 극복**: 인프라가 제공하는 환경(휘발성 디스크)의 한계를 애플리케이션 레벨의 이중화 전략(Local + Remote Tiered Reader)으로 우아하게 해결할 수 있음을 입증했습니다.
