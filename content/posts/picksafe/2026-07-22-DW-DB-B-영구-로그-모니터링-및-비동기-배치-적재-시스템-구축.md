안녕하세요, PickSafe 팀의 백엔드 아키텍트입니다. 

스타트업이나 소규모 팀에서 인프라를 운영할 때 **Render**나 **Heroku** 같은 PaaS(Platform as a Service) 클라우드는 매우 매력적인 선택지입니다. 하지만 이들에게는 치명적인 약점이 하나 있습니다. 바로 **가상 컨테이너의 휘발성(Ephemeral) 디스크 특성**입니다. 서버가 재부팅되거나 코드가 핫 리로드(Hot Reload)될 때마다 로컬에 쌓아둔 텍스트 로그 파일이 완전히 초기화된다는 점이죠.

장애가 발생해 서버가 재시작되었는데, 정작 장애 원인이 담긴 로그 파일은 증발해 버리는 아이러니한 상황. 이를 해결하기 위해 많은 팀이 외부 로깅 솔루션을 도입하지만, 이는 곧바로 추가적인 인프라 비용과 직결됩니다.

오늘 포스팅에서는 무과금 실시간 모니터링을 지키면서도, **서버리스 DB(Neon DB)의 Compute 자원 소모를 극적으로 절감(0% 유휴 수면 보장)하고 에러 로그 손실률 0%를 달성한 비동기 배치 로깅 핸들러 설계 여정**을 공유합니다.

## 1. 문제 정의: 휘발성 디스크와 서버리스 DB의 '비용 갈등'

저희 팀은 영구적인 로그 보관을 위해 **DW DB(Neon DB)**에 `system_logs` 테이블을 구축하여 로그를 적재하기로 결정했습니다. 하지만 이 간단해 보이는 결정 뒤에는 세 가지 거대한 아키텍처적 제약 사항(Constraints)이 존재했습니다.

### ① 서버리스 DB의 Autosuspend(유휴 수면) 사수하기
Neon DB는 쿼리가 인입되지 않는 유휴 상태일 때 Compute 리소스를 자동으로 종료(Autosuspend)하여 비용을 0원으로 만듭니다. 만약 서버가 5초마다, 혹은 로그가 발생할 때마다 실시간으로 DB에 `INSERT`를 날린다면 DB는 절대 잠들지 못하고 계속해서 과금 요소를 발생시킬 것입니다. **"로그는 영구 저장하되, DB는 최대한 재워야 한다"**는 모순된 목표가 생겼습니다.

### ② HTTP 요청 스레드 블로킹(Blocking) 방지
로그를 DB에 직접 동기 방식으로 인서트하면, API 요청을 처리하는 메인 스레드가 DB 커넥션 및 네트워크 I/O 병목으로 인해 느려집니다. 로깅 때문에 메인 비즈니스 로직의 응답 속도(Latency)가 저하되는 것은 주객전도입니다.

### ③ 비정상 종료(SIGKILL/OOM) 시 최후의 에러 로그 보존
단순히 메모리 버퍼에 로그를 모았다가 배치로 보낼 경우, 서버가 갑작스럽게 사망할 때(OOM-kill 등) 가장 중요하게 확인해야 할 '사망 직전의 에러 로그'가 유실되는 치명적인 위험이 있었습니다.

## 2. 점진적 설계 고도화: V1에서 V5까지의 트레이드 오프

문제를 해결하기 위해 저희 팀은 점진적으로 설계를 진화시켰습니다. 이 과정에서 겪은 수많은 엣지 케이스와 해결책은 다음과 같습니다.

```
[V1: 단순 메모리 버퍼] ──(OOM 시 로그 유실 위험)──> [V2: 에러 레벨 이원화]
                                                            │
┌───────────────────────────────────────────────────────────┘
│
▼
[V3: Non-blocking 워커] ──(신호 누락 방지 필요)──> [V4: 스레드 안전 Queue & 멱등 삭제]
                                                            │
┌───────────────────────────────────────────────────────────┘
│
▼
[V5: 무한 루프 차단 & Graceful Shutdown 완벽 보장 (최종)]
```

### [V1] 단순 인메모리 버퍼 배치 아이디어 (실패)
* **방식**: 20초 주기로 메모리 버퍼를 비우며 DB에 배치 인서트.
* **리스크**: Render 플랫폼 특성상 OOM(메모리 초과)이나 비정상 사망 시 사망 직전의 결정적 에러 로그가 유실됨. 또한, 주기적인 타이머가 돌며 계속 커넥션을 맺어 DB의 유휴 수면(Autosuspend)을 방해함.

### [V2] 로그 레벨별 처리 이원화 (생각의 전환)
* **방식**: 일반 정보성 로그(`INFO`, `DEBUG`)는 버퍼링하되, 에러 로그(`ERROR`, `CRITICAL`)는 감지 즉시 DB로 즉시 발송하여 손실률 0%를 지향함.
* **개선**: 로그 큐가 비어있을 때는 DB 커넥션을 100% 스킵하여 DB가 평화롭게 수면 상태를 유지할 수 있도록 보장함.

### [V3] Non-blocking 비동기 디스패처 구현
* **방식**: 로그가 발생했을 때 메인 스레드가 대기하지 않도록, 별도의 백그라운드 워커 스레드가 큐를 컨슘하도록 설계.
* **해결**: 복잡한 멀티라인 파이썬 에러 트레이스백(`Traceback...`)을 정규식 기반으로 안전하게 병합하여 단일 로그 레벨 메타데이터로 파싱하는 알고리즘 구축.

### [V4] 스레드 안전(Thread-safe) 비동기 큐 전환
* **방식**: 기존의 단순 플래그 신호(`threading.Event()`) 방식은 짧은 순간에 에러가 연달아 터질 때 신호가 누락되는 레이스 컨디션(Race Condition)이 존재함.
* **해결**: 파이썬 표준 라이브러리의 생산자-소비자 패턴 전용 스레드 안전 큐인 `queue.Queue`를 도입하여 `log_queue.put_nowait()`로 안정적인 버퍼링 처리 구현. 
* **보너스**: 매일 데몬 스레드를 통해 14일이 지난 오래된 로그를 자동으로 멱등성 있게 `DELETE` 처리하는 가벼운 스케줄러 내장.

### [V5] 프로덕션 레벨의 엣지 케이스 디테일 보완 (최종형)
1. **`self.format(record)` 호출로 트레이스백 100% 보존**: `logger.exception()` 호출 시 발생하는 풍부한 예외 스택트레이스 전문을 유실 없이 DB의 `message` 컬럼에 완벽하게 바인딩하도록 로거 포맷터를 내장함.
2. **Graceful Shutdown 시 잔여 로그 플러시(Flush)**: 정상적인 서버 재배포(SIGTERM) 시, 현재 워커 루프가 종료되더라도 큐에 남아있던 최대 49건의 잔여 로그를 마지막 순간에 DB로 플러시하고 안전하게 종료되도록 셧다운 핸들러 연동.
3. **오버플로우 추적**: 최악의 상황(DB 장애 등)으로 인해 메모리 큐가 가득 찰 경우, 무한히 메모리를 먹어 서버가 죽는 것을 막고 `dropped_count`를 카운팅하여 운영자에게 비상 신호를 보내도록 설계.

## 3. 핵심 아키텍처 및 엔지니어링 포인트

최종 완성된 실시간 모니터링 아키텍처의 핵심 스펙과 기법들은 다음과 같습니다.

### 3.1 2단계 이중 조회 (Tiered Log Reader) 구조

우리가 고안한 가장 혁신적인 아이디어 중 하나는 **"이중 조회 패턴"**입니다.

```
어드민 모니터링 페이지 요청 (5초 주기 폴링)
      │
      ├─► 1차 조회 (Primary): 로컬 디스크의 `/log/app/app.log` 바로 읽기
      │                       (서버리스 DB 조회 0회 ──► 비용 $0 달성)
      │
      └─► 2차 조회 (Fallback & 고이력): 서버 재부팅으로 로컬 파일이 지워졌거나,
                                       14일 이내의 과거 히스토리가 필요할 때만
                                       DW DB B (`system_logs`) 쿼리 실행
```

이 방식을 통해 실시간 폴링 모니터링 환경에서도 DB 커넥션을 거의 사용하지 않으면서, 서버가 재부팅되는 비상 상황에서만 DB 백업 데이터를 활용하는 극도의 가성비를 챙길 수 있었습니다.

### 3.2 자가 참조 무한 루프(Self-Reference Loop) 차단 기술

커스텀 로깅 핸들러를 만들 때 주니어 개발자들이 가장 많이 하는 실수가 있습니다. **"로깅 핸들러 내부에서 에러가 발생하여 `logger.error()`를 호출하는 순간, 다시 커스텀 로깅 핸들러가 트리거되는 무한 재귀"**에 빠져 프로세스가 뻗어버리는 현상입니다.

우리는 DB 쓰기 실패나 커넥션 풀 고갈 등 핸들러 내부의 예외가 발생할 경우, 파이썬 기본 로거를 완전히 우회하고 **시스템 표준 에러 출력(`sys.stderr.write`)**을 사용하여 로깅 엔진 자체의 에러 증폭을 완전하게 차단했습니다.

```python
try:
    self._write_batch(batch)
except Exception as db_err:
    # 절대 logger.error를 쓰지 않고 표준 에러로 우회하여 무한 재귀 방지
    import sys
    sys.stderr.write(f"[LogHandler Critical Error] DB Writing Failed: {db_err}\n")
```

### 3.3 복합 인덱스(Composite Index) 및 보존 주기 최적화

`system_logs` 테이블은 조회가 빈번한 어드민 대시보드 성능 향상을 위해 아래와 같이 다차원 복합 인덱스를 적용했습니다.

* `Index('idx_syslogs_created_level', 'created_at', 'level')`: 특정 시점의 특정 레벨(예: 어제 발생한 에러 로그)을 빠르게 필터링하기 위함.
* `Index('idx_syslogs_service_created', 'service', 'created_at')`: 특정 마이크로서비스 컴포넌트별 타임라인 정렬용.

또한, **14일 자동 정제 정책**을 적용하여 데이터 용량을 최적화했습니다. 일평균 약 5,000건의 로그가 쌓인다고 가정하면 14일 총용량은 약 **17.5 MB**에 불과합니다. 이는 무료 티어 제한(500MB)의 **단 3.5%** 수준으로, 인프라 비용 부담 없이 영구적인 로그 이력을 안전하게 확보할 수 있게 되었습니다.

## 4. 마치며: 주니어에서 시니어로 가는 디테일의 차이

이번 태스크를 진행하며 얻은 가장 큰 배움은 **"아무리 훌륭한 아키텍처라도 리소스 제약과 예외 시나리오를 고려하지 못하면 프로덕션에서 무용지물"**이라는 점입니다. 

단순히 "로그를 DB에 저장한다"는 요구사항 하나에도 다음과 같은 수많은 엔지니어링 의사결정이 필요했습니다.

* 서비스가 호스팅되는 환경의 OS/하드웨어적 특성 파악 (**Ephemeral Disk**)
* 서드파티 서비스의 과금 모델 이해 (**Serverless DB Autosuspend**)
* 멀티스레드 환경에서의 동시성 이슈 대응 (**Thread-safe Queue**)
* 예기치 못한 애플리케이션 라이프사이클 관리 (**Graceful Shutdown**)
* 시스템 오류 상황에서의 방어적 설계 (**Self-Reference Recursion 차단**)

비용과 안정성이라는 두 마리 토끼를 모두 잡은 이번 로깅 시스템 구축 덕분에, 저희 팀은 이제 서버 재부팅 시에도 든든하게 과거의 이력을 추적하며 대시보드를 안정적으로 운영하고 있습니다. 시스템의 보이지 않는 곳에서 견고함을 유지하는 것, 이것이 바로 시니어 엔지니어가 추구해야 할 가치라고 믿습니다.
