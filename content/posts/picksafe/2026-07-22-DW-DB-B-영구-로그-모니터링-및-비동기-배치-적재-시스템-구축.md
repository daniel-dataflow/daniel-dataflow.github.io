안녕하세요, PickSafe 백엔드 에디터입니다. 
클라우드 PaaS 환경에서 서비스를 운영하다 보면 마주치는 고질적인 문제가 있습니다. 바로 **컨테이너의 휘발성(Ephemeral) 디스크 특성**으로 인해 서버 재부팅이나 핫리로드 시 로컬 로그 파일이 초기화된다는 점입니다. 이로 인해 과거의 장애 원인을 추적하거나 고이력 모니터링을 수행하는 데 큰 제약이 발생합니다.

이번 포스팅에서는 PaaS 환경에서 **에러 로그 손실률 0%**를 달성하고, 서버LESS/클라우드 DB의 **Compute 비용(유휴 수면)을 극적으로 절감**하기 위해 구축한 **비동기 배치 적재 및 이중 조회(Tiered Log Reader) 시스템**의 아키텍처 의사결정 과정을 공유합니다.

---

## 1. Problem: PaaS 환경과 로그 수집의 딜레마

Render와 같은 PaaS 플랫폼은 배포 가상 컨테이너가 휘발성 디스크를 사용합니다. 
* `/log/app/app.log`와 같은 로컬 텍스트 파일에 로그를 적재하면, 배포나 오토스케일링, 혹은 예기치 않은 인스턴스 재시작 시 **과거의 로그가 모두 소실**됩니다.
* 그렇다고 모든 로그를 실시간으로 원격 DB에 직접 싱크(Sync)하면, 네트워크 I/O 병목으로 인해 **메인 API 요청 스레드가 블로킹**되는 문제가 발생합니다.
* 특히 서버리스/클라우드 DB(예: Neon DB 등) 환경에서는 지속적인 커넥션 요청이 들어올 경우 **Autosuspend(유휴 수면 기능)가 방해받아 비용이 낭비**되는 치명적인 트레이드오프가 존재합니다.

---

## 2. Trade-off & Evolution: V1에서 V5까지의 점진적 고도화

이 문제를 해결하기 위해, 우리는 단순한 인메모리 버퍼링 방식에서 시작해 5단계의 정밀한 고도화를 거쳤습니다.

### [V1 ~ V2] 초기 구상과 DB 수면(Autosuspend) 보장
* **V1 (인메모리 버퍼 20초 주기 배치):** 단순 구현에는 좋았으나, 서버가 `SIGKILL`이나 `OOM-kill`로 비정상 사망할 경우 직전의 결정적 에러 로그가 유실되는 문제가 있었습니다. 또한 20초 고정 커넥션은 DB의 유휴 수면을 방해했습니다.
* **V2 (레벨별 이원화):** 에러(Error) 발생 시에는 즉시 처리하고, 큐가 비어있을 경우에는 DB 커넥션을 100% 스킵하여 **DB Compute 유휴 수면을 보장**하도록 구조를 변경했습니다.

### [V3 ~ V4] 안정성 확보: 비동기 큐와 트레이스백 파서
* **V3 (Non-blocking & 멀티라인 파서):** HTTP 요청 스레드의 블로킹을 막기 위해 비동기 디스패치를 도입하고, 파이썬 에러의 특성인 멀티라인 트레이스백(`Traceback...`)을 유실 없이 병합하는 로직을 정립했습니다.
* **V4 (`queue.Queue` 스레드 안전 큐 도입):** 단순 이벤트 신호 방식의 에러 누락 위험을 제거하기 위해 파이썬 표준 생산자-소비자 비동기 큐(`queue.Queue`)를 채택했습니다.

### [V5] 프로덕션 레벨의 엣지케이스 방어
최종 프로덕션 반영을 앞두고 다음과 같은 세부 리스크를 완벽히 통제했습니다.
1. **트레이스백 100% 보존:** `self.format(record)`를 강제 호출하여 `logger.exception()` 등 발생 시 전문(StackTrace)을 DB 메시지 컬럼에 온전히 보존했습니다.
2. **정상 종료(SIGTERM) 시 유실 차단:** 애플리케이션 셧다운 시점에 큐에 남아있는 잔여 로그를 플러시(`_write_batch`)하여 마지막 순간의 로그까지 안전하게 적재합니다.
3. **무한 재귀(Self-Reference) 차단:** **(매우 중요)** DB 쓰기 실패 시 로거(`logger.error`)를 호출하면 로깅 핸들러 내부에서 다시 에러가 발생해 무한 루프에 빠집니다. 이를 방지하기 위해 DB 에러 발생 시 `sys.stderr.write`를 사용하여 에러 증폭을 원천 차단했습니다.

## 3. Architecture: 이중 조회(Tiered Log Reader)와 비용 최적화

최종 구축된 아키텍처의 핵심은 **"평소에는 비용이 안 들고, 필요할 때는 확실하게 조회한다"**는 원칙에 기반합니다.

### 3.1 2단계 이중 조회 (Tiered Log Reader)
* **1차 (Primary - 실시간 폴링):** 어드민 UI의 5초 주기 폴링 시 로컬 디스크(`/log/app/app.log`)를 직접 읽어옵니다. 이 경우 **원격 DB Compute 사용량은 0%**를 유지합니다.
* **2차 (Fallback - 영구 이력 조회):** 컨테이너 재부팅으로 로컬 파일이 비었거나 과거 14일간의 장애 이력을 분석할 때만 원격 DB(`system_logs` 테이블)를 조회합니다.

### 3.2 14일 자동 정제 (Retention Policy)를 통한 용량 관리
* 일평균 약 5,000건의 로그 발생 시, 14일간 보관하는 총 데이터 용량은 약 **17.5 MB**에 불과합니다.
* 이는 무료 티어 DB 용량(예: 500MB)의 **약 3.5%** 수준으로, 비용 부담 없이 영구 모니터링 체계를 유지할 수 있습니다.
* 데몬 스레드를 통해 매일 14일이 지난 로그를 멱등적으로 자동 정제(`DELETE`)합니다.

## 4. Takeaway: 엔지니어링 교훈

1. **PaaS 환경의 제약을 인지하는 아키텍처:** 클라우드의 인프라 특성(휘발성 디스크, 서버리스 DB 수면 등)을 이해하고 이를 역이용하는 설계가 인프라 비용과 안정성을 동시에 잡는 열쇠입니다.
2. **방어적 프로그래밍의 중요성:** 특히 로깅 시스템이나 모니터링 도구 자체에서 발생한 에러가 메인 서비스에 영향을 주거나 무한 루프(`Self-Reference`)를 일으키지 않도록 `stderr` 등을 활용한 안전장치를 반드시 마련해야 합니다.
3. **트레이드오프의 균형:** 실시간성과 데이터 정합성, 그리고 DB 비용 사이에서 비동기 큐와 Tiered Read 전략을 통해 실용적인 타협점을 찾아냈습니다.

이번 시스템 도입을 통해 PickSafe는 **비용 증가 없이 과거 14일간의 에러 로그 손실률 0%**를 달성하며, 장애 대응 리드타임을 획기적으로 단축할 수 있었습니다. 유사한 환경에서 로그 인프라를 고민 중인 엔지니어분들께 좋은 참고가 되기를 바랍니다.
