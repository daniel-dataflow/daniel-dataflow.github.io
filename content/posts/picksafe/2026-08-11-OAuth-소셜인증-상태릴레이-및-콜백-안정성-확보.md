안녕하세요, PickSafe 개발팀의 Daniel과 Antigravity입니다. 

현대의 웹 서비스는 유연한 배포와 독립적인 확장을 위해 프론트엔드와 백엔드를 물리적으로 분리하는 아키텍처를 자주 채택합니다. 저희 팀 역시 프론트엔드는 **Vercel**, 백엔드 API는 **Render**를 활용해 서로 다른 서브도메인 환경에서 서비스를 운영하고 있습니다. 

이러한 **멀티 도메인(Multi-domain) 분리 배포 환경**은 많은 장점을 주지만, **OAuth 2.0 기반의 소셜 로그인**을 구현할 때는 까다로운 세션 관리 및 리다이렉트 유실 문제를 발생시킵니다. 

이번 포스팅에서는 저희 팀이 다른 서브도메인 간의 인증 흐름을 매끄럽게 연결하기 위해 **State Relay 패턴**을 도입하고, 다양한 소셜 플랫폼(구글, 페이스북, 카카오, 네이버 등)의 예외 케이스를 어떻게 안정적으로 극복했는지 그 엔지니어링 과정을 공유합니다.

## 1. 우리가 마주한 문제 (Problem)

소셜 로그인 과정은 단순히 '인증 완료 후 사용자를 돌려보내는 것' 이상으로 복잡합니다. 특히 멀티 도메인 환경에서는 다음과 같은 세 가지 치명적인 문제가 발생했습니다.

### ① 콜백 시점의 프론트엔드 Origin 유실
사용자가 `https://picksafe.app`에서 구글 로그인을 시도하면, 인증 완료 후 ID 공급자(Identity Provider, 이하 IdP)는 우리 백엔드 API 서버(`https://api.picksafe.app/auth/callback/...`)로 사용자 승인 코드(Authorization Code)를 보냅니다. 

이때, 백엔드 서버는 **"사용자가 원래 프론트엔드의 어떤 페이지(예: 메인화면, 특정 상품 상세 페이지, 혹은 개발 서버 환경)에서 로그인을 요청했는지"**에 대한 맥락(Context)을 잃어버리게 됩니다. 이로 인해 인증 후 엉뚱한 페이지로 튕기거나 404 에러를 마주하는 사용자 경험 저하가 발생했습니다.

### ② 소셜 플랫폼별 프로필 응답 스키마 불일치 (특히 페이스북/카카오)
IdP(Google, Facebook, Kakao, Naver 등)들은 저마다 고유한 사용자 프로필 스키마를 가지고 있습니다. 특히 페이스북이나 카카오의 경우, **사용자가 '이메일 제공 동의'를 해제**하고 가입을 진행하면 백엔드 필수 필드인 `email` 값이 빈 채로 콜백이 들어옵니다. 이는 DB 제약조건 위배로 인한 내부 서버 오류(500 Error)를 유발했습니다.

### ③ 어드민의 업무 연속성 단절 (Return-To 유실)
사내 관리자가 `/admin/translations`와 같은 번역/설정 깊은 페이지(Deep Link)에서 작업하던 중 세션이 만료되면, 다시 로그인을 거치게 됩니다. 하지만 로그인 성공 후 원래 작업하던 페이지가 아닌 어드민 메인 대시보드로 강제 이동되는 불편함이 있어 업무 효율이 크게 저하되었습니다.

## 2. 해결을 위한 아키텍처 설계: State Relay 패턴

우리는 이 문제를 해결하기 위해 OAuth 2.0 표준 규격에 존재하는 `state` 파라미터를 활용한 **상태 릴레이(State Relay) 아키텍처**를 설계했습니다.

### 2.1. 전체 데이터 흐름 (Sequence Diagram)

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드(picksafe.app)에서 [구글/페이스북 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(return_to)을 JSON으로 묶어 Base64 인코딩 후 state에 탑재
     state = base64_encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  IdP(Google/Facebook 등) 인증 후, 전달받았던 state 값을 그대로 유지하여 백엔드 콜백으로 전송

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 안전하게 302 Redirect
  - 올바른 화이트리스트 도메인 검증으로 Open Redirect 취약점 방어
```

### 2.2. 구현의 핵심: `state` 토큰의 직렬화와 보안 검증

서버는 클라이언트가 최초 로그인을 요청할 때 넘겨준 `origin`과 `next` 경로를 상태 객체로 만듭니다. 이 데이터를 안전하게 전달하기 위해 JSON으로 직렬화한 뒤 Base64 인코딩을 거쳐 OAuth `state` 값으로 전달합니다.

```python
# [보안 필터링 및 서명 프로세스 예시]
import base64
import json

def generate_oauth_state(origin_url: str, next_path: str) -> str:
    # 1. 화이트리스트 도메인 검증을 통해 Open Redirect 취약점 방어
    allowed_domains = ["picksafe.app", "picksafe.vercel.app", "localhost"]
    if not any(domain in origin_url for domain in allowed_domains):
        raise ValueError("Unauthorized Origin URL")

    state_payload = {
        "origin": origin_url,
        "next": next_path
    }
    
    # 2. JSON 직렬화 후 Base64 인코딩 수행
    serialized = json.dumps(state_payload).encode('utf-8')
    return base64.urlsafe_b64encode(serialized).decode('utf-8')
```

백엔드 콜백 엔드포인트에서는 이 `state`를 역직렬화(Deserialize)하여 사용자가 원래 머물렀던 도메인과 서브 경로를 파악하고, 사용자에게 `HttpOnly` 세션 쿠키를 안전하게 구워준 후 **정확한 원래 페이지로 리다이렉트(302 Redirect)** 시켜줍니다.

## 3. 플랫폼별 한계 극복: 사용자 프로필 정규화 (Normalization)

이메일 비공개 선택 등으로 인해 발생하던 가입 실패 및 500 에러를 방어하기 위해, 저희는 백엔드에 **데이터 정규화 레이어**를 두었습니다.

특정 소셜 IdP가 필수 식별자인 `email` 정보를 제공하지 않더라도, 고유 식별 값인 `id`는 항상 보장됩니다. 이를 활용해 가상 이메일을 결정론적(Deterministic)으로 생성하는 방어 코드를 작성했습니다.

```python
def normalize_social_profile(provider: str, raw_profile: dict) -> dict:
    """
    플랫폼별 고유 스키마를 공통 사용자 모델로 매핑 및 예외 방어
    """
    user_id = raw_profile.get("id")
    email = raw_profile.get("email")
    
    # 이메일 필수 동의 해제 대응을 위한 가상 고유 식별 이메일 생성
    if not email:
        email = f"{provider}_{user_id}@social.picksafe.app"
        
    return {
        "provider": provider,
        "provider_id": str(user_id),
        "email": email,
        "nickname": raw_profile.get("name") or raw_profile.get("properties", {}).get("nickname") or "Social User"
    }
```

이 기법을 도입한 덕분에 페이스북, 카카오 등에서 사용자가 까다로운 개인정보 동의를 거부하더라도 **100% 끊김 없는 회원가입 및 로그인 흐름을 제공**할 수 있게 되었습니다.

## 4. 어드민 복귀 경로 (Return-To) 유연성 확보

관리자 대시보드 역시 세션이 만료되면 로그인 화면으로 튕기게 되는데, 로그인 처리 핸들러에 `next` 쿼리스트링 매개변수를 전파하도록 개선했습니다. 

`/admin/login?next=/admin/translations`로 접근하면 로그인 폼 제출 완료 후 즉시 원래 수정하려던 `/admin/translations` 페이지로 백엔드가 리다이렉트 시켜줍니다. 덕분에 번역 작업을 하던 어드민 사용자가 흐름을 잃지 않고 업무 효율을 크게 높일 수 있었습니다.

## 5. 결과 및 엔지니어링 교훈 (Takeaways)

### 📈 정량적/정성적 성과
* **인증 성공률 100% 달성**: 분리 배포된 프론트/백엔드 아키텍처 환경에서도 도메인 분실로 인한 로그인 실패 건수가 **0건**으로 수렴했습니다.
* **이탈률 감소**: 이메일 권한 거부로 가입이 막히던 극단적 상황(Edge Case)을 가상 계정 바인딩 기법으로 완전히 차단했습니다.
* **보안성 확보**: 무분별한 리다이렉트를 막는 **화이트리스트 도메인 검증 로직**을 추가함으로써, 피싱이나 악성 사이트로 리다이렉트될 수 있는 Open Redirect 보안 취약점을 원천 차단했습니다.

### 💡 얻은 교훈
1. **표준 스펙의 깊은 이해**: OAuth 2.0의 `state` 파라미터는 단순히 CSRF 방어용 랜덤 토큰으로만 쓰이지 않고, **비동기 상태 전이의 컨텍스트 전달 매체**로 훌륭히 사용될 수 있다는 것을 체감했습니다.
2. **수비적 설계의 중요성**: 외부 플랫폼 API(Facebook, Kakao 등)에 의존하는 기능은 언제든 스키마가 깨지거나 필드가 누락될 수 있음을 가정하고, 항상 시스템 내부에 정규화 가드레일을 촘촘히 쳐두어야 견고한 프로덕션을 유지할 수 있음을 재확인했습니다.

앞으로도 PickSafe 개발팀은 사용자 경험과 보안이 타협 없이 공존하는 완성도 높은 서비스를 만들기 위해 끊임없이 개선을 거듭할 것입니다. 긴 글 읽어주셔서 감사합니다!
