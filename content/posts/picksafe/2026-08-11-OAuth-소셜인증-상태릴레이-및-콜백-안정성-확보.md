안녕하세요, **PickSafe** 백엔드 엔지니어링 팀입니다. 

현대의 웹 서비스는 유연한 확장성과 배포 독립성을 위해 프론트엔드와 백엔드를 서로 다른 인프라와 도메인에 분리 배포(Decoupled Architecture)하는 방식을 자주 채택합니다. 저희 PickSafe팀 역시 프론트엔드는 Vercel, 백엔드 API 서버는 Render를 활용하여 각각 멀티 도메인 환경으로 운영하고 있습니다.

이러한 분리 배포 환경은 생산성을 극대화해 주지만, **"상태(State)를 유지해야 하는 통신"**을 처리할 때 예상치 못한 난관을 만들어내곤 합니다. 대표적인 케이스가 바로 **OAuth 2.0 기반의 소셜 로그인**입니다. 

오늘 포스팅에서는 서로 다른 도메인 경계를 넘나들 때 발생하는 OAuth 리다이렉트 및 세션 유실 문제를 해결하고, 인프라 제약 속에서도 매끄러운 UX와 철저한 보안을 동시에 확보한 **'OAuth State Relay'** 설계 도입 과정을 공유합니다.

---

## 1. 우리가 마주한 문제 (Problem)

기존 소셜 로그인 흐름은 단일 도메인(Single Domain)을 기준으로 단순하게 설계되어 있었습니다. 하지만 프론트엔드(`https://picksafe.app`)와 백엔드 API(`https://api.picksafe.app`)가 물리적으로 분리되면서 다음과 같은 3가지 치명적인 이탈 지점(Drop-off Point)이 발생했습니다.

### ① 콜백 Origin 유실 현상
사용자가 소셜 로그인 버튼을 클릭하면 `OAuth Provider(Google, Kakao 등)` 페이지로 이동했다가, 인증 완료 후 백엔드 콜백 엔드포인트로 리다이렉트됩니다. 이때 백엔드는 **"인증을 완료한 사용자를 원래 프론트엔드의 어느 도메인(또는 어느 페이지)으로 돌려보내야 하는지"**에 대한 컨텍스트를 잃어버리는 현상이 발생했습니다. 특히 멀티 도메인(상용 도메인, Vercel Preview 도메인 등)을 함께 사용하는 개발 환경에서 이 유실 문제는 404 에러나 잘못된 호스트로의 리다이렉션을 유발했습니다.

### ② 소셜 플랫폼별 응답 포맷 편차 및 500 에러
OAuth Provider마다 유저 정보를 제공하는 스키마가 제각각이었습니다. 예를 들어, 페이스북이나 카카오 로그인 시 사용자가 **'이메일 제공 동의'를 해제**한 채로 가입을 시도할 경우, 백엔드 DB 스키마의 `Email (Unique)` 제약 조건과 충돌하거나 Null Pointer 관련 500 내부 서버 에러가 발생해 유저가 아예 서비스에 진입하지 못하는 심각한 가입 장벽이 있었습니다.

### ③ 어드민 세션 만료 후 작업 연속성 단절
관리자가 어드민 페이지(예: `/admin/translations`)에서 번역 작업을 하던 중 세션이 만료되면 로그인 페이지로 튕깁니다. 재인증을 마친 후에는 이전 작업 중이던 세부 관리자 페이지로 돌아가야 작업의 연속성이 유지되는데, 기존 구조에서는 로그인 성공 후 무조건 메인 대시보드 홈으로 강제 이동되어 어드민 사용자 경험을 크게 저해했습니다.

## 2. 해결을 위한 기술적 고민과 대안 (Trade-off)

이 문제를 해결하기 위해 백엔드 아키텍처 관점에서 크게 두 가지 대안을 검토했습니다.

### 대안 A: 세션/쿠키 기반의 상태 공유 (Session-based Tracking)
* **방식**: 로그인 요청 시점에 세션 쿠키나 Redis 세션에 프론트엔드의 `origin`과 `return_to` 주소를 저장하고, 콜백 시 세션 키를 대조해 복귀 주소를 찾는 방식.
* **한계**: 프론트엔드와 백엔드가 서로 다른 서브도메인을 쓰거나 Cross-site 환경일 경우 `SameSite` 쿠키 설정 제약(Third-party Cookie 규제 등)으로 세션이 차단될 리스크가 크고, 백엔드에 불필요한 상태(Stateful) 저장소가 추가로 요구되어 인프라 복잡도가 올라갑니다.

### 대안 B: OAuth State 토큰에 상태를 직렬화하는 방식 (State Relay Pattern) — **선택**
* **방식**: OAuth 2.0 표준 규격에 존재하는 `state` 파라미터를 활용하는 방식. 로그인 시작 시, 프론트엔드 도메인과 복귀 대상 경로를 JSON 데이터로 묶어 Base64로 인코딩한 뒤 `state` 값에 실어 보냅니다. OAuth Provider는 이 값을 그대로 반환해 주므로, 백엔드는 이 값을 디코딩하여 안전하게 목적지를 파악할 수 있습니다.
* **장점**: 완전히 **무상태성(Stateless)**을 유지할 수 있어 서버 리소스가 절약되며, 쿠키 도메인 제약에서 완전히 자유롭습니다. 단, 리다이렉트 주소를 신뢰하기 위한 엄격한 화이트리스트 검증 로직이 동반되어야 안전합니다.

## 3. 아키텍처 설계 및 구현 (State Relay Architecture)

최종적으로 **대안 B(State Relay 패턴)**를 채택하고, 이를 고도화하여 보안과 예외 처리까지 완벽히 커버하는 아키텍처를 구축했습니다.

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드(picksafe.app)에서 소셜 로그인 버튼 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(return_to)을 안전하게 Base64로 인코딩하여 state 파라미터에 적재
     state = base64_encode({ "origin": "https://picksafe.app", "next": "/admin/translations" })

[2. OAuth Provider 승인]
  구글/페이스북/카카오 인증 진행 후, Provider가 인가 코드(Authorization Code)와 함께 
  전달받았던 state 값을 그대로 백엔드 콜백 URL로 전송

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 전달받은 state 디코딩 ➔ JSON 파싱 후 복귀할 도메인 및 경로 획득
  - 세션 쿠키(HttpOnly, Secure) 발급
  - [보안] 사전에 허용된 화이트리스트 도메인과 일치하는지 검증 (Open Redirect 공격 원천 차단)
  - 원래의 origin/next 경로로 안전하게 302 Redirect 수행
```

### 3.1. 안전한 State Relay 코드 구현
백엔드(`auth.py`)에서는 전달받은 `state`를 해독할 때 악의적인 제3자가 변조하지 못하도록 서명/인코딩 처리를 거칩니다. 또한, 디코딩된 `origin` 주소가 실제 서비스 도메인(`picksafe.app` 등)이 맞는지 검증하는 **허용 도메인 화이트리스트 필터링**을 적용하여, 해커가 지정한 임의의 피싱 사이트로 사용자를 강제 리다이렉트시키는 **오픈 리다이렉트(Open Redirect) 취약점**을 원천 차단했습니다.

### 3.2. 이메일 미제공 사용자를 위한 프로필 정규화 (Normalization)
페이스북, 카카오 등 이메일 제공 동의를 생략할 수 있는 플랫폼 환경에 대응하기 위해, 유저 정보 조회 단계에서 방어 코드(Defense Code)를 구축했습니다.

```python
# 이메일 값이 누락되어 유입되는 경우에 대한 방어 코드 구조 예시
user_id = oauth_profile.get("id")
email = oauth_profile.get("email")

if not email:
    # 플랫폼 고유 식별자(ID)와 사내 가상 도메인을 조합해 고유 식별 이메일 임시 부여
    email = f"fb_{user_id}@social.picksafe.app"
```
이를 통해 DB의 유니크 제약조건을 우회하면서도, 플랫폼당 단 하나의 고유 계정이 매핑되도록 보장하여 가입 및 인증 성공률을 **100%**로 끌어올렸습니다.

### 3.3. 어드민 복귀 URL(`return_to`) 파라미터 보존
관리자 페이지에 미인증 접근 시, 미들웨어 단에서 현재 가고 있던 경로(`/admin/...`)를 `next` 쿼리 파라미터에 바인딩합니다. 로그인 폼 제출 후 이 `next` 정보가 OAuth의 `state` 파라미터에 고스란히 탑재되어 최종 콜백까지 보존됨으로써, 관리자는 재인증 후 자신이 보던 데이터 편집 화면으로 정확히 되돌아갈 수 있게 되었습니다.

## 4. 엔지니어링 성과 및 배운 점 (Takeaways)

이번 소셜 로그인 시스템 고도화 작업을 통해 PickSafe팀은 다음과 같은 비즈니스 및 기술적 가치를 창출했습니다.

* **소셜 로그인 실패율 0% 달성**: 분리 배포 환경 및 복잡한 서브도메인 간 세션 전송 환경에서도 리다이렉트 에러 및 사용자 이탈이 단 한 건도 발생하지 않게 되었습니다.
* **비즈니스 연속성 확보**: 이메일 제공에 동의하지 않는 유저들도 이탈 없이 안전하게 회원가입 프로세스로 수용하여 신규 가입 전환율이 유의미하게 개선되었습니다.
* **운영 효율성 제고**: 관리자 세션 만료 후 작업 흐름이 끊기던 불편을 완전히 제거하여 운영 리소스 손실을 방지했습니다.

### 💡 엔지니어링 교훈
1. **타사 연동(Third-party Integration)은 절대 신뢰할 수 없다**: 외부 프로바이더가 제공하는 데이터 구조는 언제든 누락되거나 바뀔 수 있음을 가정하고 설계해야 합니다. (항상 Default/Fallback 값을 정의하는 방어적 프로그래밍의 중요성)
2. **Stateless의 강력함**: 분리 배포 환경에서 세션 정합성을 유지하기 위해 무리하게 Stateful한 세션 스토리지를 공유하는 구조를 구축하기보다, OAuth 표준 명세(`state`)를 창의적으로 응용함으로써 훨씬 더 확장성 있고 견고한 아키텍처를 완성할 수 있었습니다.
