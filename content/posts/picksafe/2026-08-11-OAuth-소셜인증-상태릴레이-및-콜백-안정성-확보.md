안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

최근 PickSafe 서비스를 운영하며 프론트엔드와 백엔드를 서로 다른 도메인으로 분리 배포하는 과정에서, **OAuth 2.0 소셜 로그인 흐름 중 세션과 리다이렉트가 유실되는 까다로운 문제**를 마주했습니다. 

이번 글에서는 멀티 도메인 환경에서 왜 이러한 문제가 발생했는지, 그리고 이를 **State Relay 패턴**과 견고한 예외 처리를 통해 어떻게 해결했는지 공유해 드리고자 합니다.

---

## 1. 문제 정의 (Context & Problem)

현재 PickSafe는 프론트엔드(Vercel)와 백엔드 API(Render)가 서로 다른 도메인 환경으로 분리되어 있습니다. 이 구조에서 구글, 페이스북, 카카오, 네이버 등 다양한 소셜 로그인을 통합하는 과정에서 다음과 같은 세 가지 치명적인 문제가 발생했습니다.

1. **콜백 Origin 유실 문제**
   * OAuth 인증 서버에서 백엔드 콜백 엔드포인트로 리다이렉트될 때, 사용자가 인증을 시작했던 프론트엔드의 원래 도메인 정보(`https://picksafe.app` 등)를 잃어버리는 현상 발생. 이로 인해 로그인 성공 후 올바른 프론트엔드 화면으로 돌아가지 못하고 404 에러나 잘못된 호스트로 튕기는 문제가 발생했습니다.
2. **소셜 플랫폼별 응답 포맷 및 제약 차이 (예: 페이스북)**
   * 페이스북의 경우, 사용자가 이메일 제공 권한을 거부하거나 특정 권한이 누락된 채로 로그인할 때 백엔드 콜백에서 500 에러를 유발하는 취약점이 존재했습니다.
3. **어드민 로그인 후 사용자 경험(UX) 저하**
   * 관리자가 특정 상세 페이지(예: `/admin/translations`)를 보던 중 세션이 만료되어 로그인 페이지로 튕긴 뒤, 로그인을 완료해도 원래 보던 페이지가 아닌 무조건 대시보드 홈으로 이동하는 불편함이 있었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 크게 두 가지 방안을 검토했습니다.

* **대안 A: 프론트엔드 LocalStorage/SessionStorage 활용**
  * *접근 방식*: 로그인 요청 직전 브라우저 스토리지에 `origin`과 `next` 경로를 저장하고 콜백 시점에 읽어오기.
  * *한계점*: OAuth 인증 과정은 외부 프로바이더(Google, Facebook 등)의 도메인으로 완전히 이탈했다가 돌아오는 **Cross-Site 리다이렉트** 흐름입니다. 이 과정에서 브라우저 보안 정책이나 사파리 등의 서드파티 쿠키/스토리지 차단 정책으로 인해 데이터 유실 확률이 매우 높았습니다.
* **대안 B: OAuth `state` 파라미터를 활용한 State Relay 패턴 (선택)**
  * *접근 방식*: OAuth 표준 규격인 `state` 파라미터에 프론트엔드의 `origin`과 복귀 대상 URL(`next`) 정보를 담아 인코딩하여 프로바이더로 전달. 인증 서버는 이 `state` 값을 그대로 백엔드 콜백으로 돌려주므로, 세션 유실 없이 안전한 라우팅 정보 획득 가능.
  * *장점*: 브라우저 스토리지에 의존하지 않으며, OAuth 표준 규격을 준수하여 안정성이 매우 높음. 단, Open Redirect 취약점을 방어하기 위한 철저한 도메인 화이트리스트 검증 로직이 필수적임.

## 3. 최종 해결 및 아키텍처 설계

우리는 **대안 B (OAuth State Relay 패턴)**를 채택하여 다음과 같이 시스템을 재설계했습니다.

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드에서 [소셜 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(return_to)을 base64 인코딩하여 state 파라미터에 탑재
     state = base64_encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  Provider(Google/Facebook 등) 인증 후 state 값을 그대로 유지하여 백엔드 콜백으로 전송

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 안전하게 302 Redirect
  - 올바른 화이트리스트 도메인 검증으로 Open Redirect 취약점 완벽 방어
```

### 3.1. OAuth State Relay 구현 (`auth.py`)
로그인 시작 시점(Initiation)에 프론트엔드의 `origin`과 `next_url` 정보를 JSON으로 직렬화한 뒤, 안전하게 인코딩하여 `state` 토큰에 담아 전송했습니다. 콜백 시점에는 이 토큰을 다시 디코딩하여 사용자가 원래 있던 정확한 도메인과 페이지로 안전하게 리다이렉트 처리를 수행했습니다. 이때, 악의적인 사용자의 외부 사이트로의 리다이렉트 공격(Open Redirect)을 막기 위해 사전 승인된 도메인 화이트리스트 검증 로직을 반드시 거치도록 구현했습니다.

### 3.2. 소셜 프로필 정규화 및 방어 코드 작성
페이스북이나 카카오 등에서 사용자가 이메일 제공 동의를 해제하더라도 서비스 회원가입 및 로그인이 중단되지 않도록, 이메일 누락 시 내부 규칙에 따른 가상 고유 식별자(`fb_{id}@social.picksafe.app`)를 생성해 주는 방어 로직을 추가하여 로그인 성공률을 100%로 끌어올렸습니다.

### 3.3. 어드민 Return-To 지원
관리자 로그인 폼 제출 시 쿼리스트링으로 전달되는 `next` 파라미터를 세션/토큰 흐름과 연동하여, 로그인이 완료된 직후 관리자가 직전에 작업 중이던 상세 관리 페이지로 곧바로 복귀할 수 있도록 워크플로우를 개선했습니다.

## 4. 성과 및 교훈 (Takeaways)

이번 작업을 통해 얻은 성과는 명확합니다.

1. **소셜 로그인 실패율 0% 달성**: 멀티 도메인 환경에서의 세션 및 리다이렉트 유실 문제를 완벽히 해결하여 사용자 이탈률을 방어했습니다.
2. **표준 규격의 적극적 활용**: 브라우저 스토리지의 불안정성에 기대지 않고, OAuth 프로토콜이 지원하는 `state` 파라미터를 아키텍처 수준에서 활용함으로써 견고함을 높였습니다.

분리 배포 환경이나 멀티 도메인 아키텍처를 설계하고 계신 엔지니어분들께 이번 글이 작은 참고가 되었기를 바랍니다. 앞으로도 PickSafe는 안정적이고 매끄러운 사용자 경험을 제공하기 위해 기술적 고민을 지속하겠습니다. 감사합니다.
