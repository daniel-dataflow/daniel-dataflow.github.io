안녕하세요, PickSafe 팀의 시니어 백엔드 에디터입니다. 

현대적인 웹 서비스 아키텍처에서는 프론트엔드와 백엔드가 서로 다른 도메인으로 분리 배포(예: Vercel과 Render/AWS 조합)되는 경우가 많습니다. 저희 PickSafe 서비스 역시 이러한 멀티 도메인 환경을 채택하고 있는데요. 최근 소셜 로그인(Google, Facebook, Kakao, Naver 등) 도입 과정에서 **"인증은 성공했는데 사용자가 엉뚱한 페이지로 튕기거나 세션이 유실되는 현상"**이라는 치명적인 사용자 경험(UX) 저하 문제를 마주했습니다.

이번 포스팅에서는 멀티 도메인 환경에서 OAuth 흐름이 깨지는 원인을 분석하고, `State Relay 패턴`을 통해 이를 안전하고 우아하게 해결한 아키텍처적 의사결정 과정을 공유합니다.

---

## 1. 문제 정의 (Context & Problem)

멀티 도메인 환경에서 소셜 로그인을 구현할 때, 프론트엔드와 백엔드는 서로 다른 오리진(Origin)을 가집니다. 이로 인해 다음과 같은 세 가지 구조적 문제를 겪었습니다.

1. **콜백 Origin 유실**: 
   사용자가 `https://picksafe.app` (프론트엔드)에서 소셜 로그인을 시도하면, OAuth 인증 서버를 거쳐 백엔드 콜백 API(`https://api.picksafe.app/auth/callback/...`)로 리다이렉트됩니다. 백엔드 처리가 끝난 뒤 사용자를 다시 프론트엔드로 돌려보내야 하는데, 이때 **"사용자가 원래 어느 도메인/경로에서 왔는지"**에 대한 정보를 잃어버려 404 에러나 잘못된 호스트로 낙오되는 현상이 발생했습니다.
2. **소셜 플랫폼별 응답 포맷 및 예외 케이스**: 
   페이스북 등의 플랫폼은 특정 권한(예: 이메일 동의)을 사용자가 거부하거나 제공하지 않을 경우, 백엔드 콜백 처리부에서 500 에러를 유발하며 전체 인증 흐름을 깨뜨렸습니다.
3. **어드민 페이지 Deep-Link 복귀 누락**: 
   관리자가 특정 관리 페이지(예: `/admin/...`)를 이용하다 세션이 만료되어 로그인 화면으로 이동된 경우, 로그인을 마치고 나면 원래 보던 페이지가 아닌 무조건 대시보드 홈으로 강제 이동되어 업무 생산성이 떨어지는 불편함이 있었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Design)

이 문제를 해결하기 위해 두 가지 방안을 검토했습니다.

- **대안 A: 프론트엔드 로컬 스토리지(LocalStorage) 또는 쿠키 활용**
  - 로그인 요청 직전, 브라우저의 로컬 스토리지에 `origin`과 `return_to` 경로를 저장해 둔 뒤 콜백 시점에 읽어오는 방식.
  - *단점*: OAuth 인증 과정에서 서드파티 도메인 리다이렉트가 발생하므로, 브라우저 정책(특히 Safari 등 ITP 환경)이나 크로스 사이트 제약으로 인해 쿠키나 스토리지 값이 유실될 확률이 높았습니다.
- **대안 B: OAuth 표준 `state` 파라미터를 활용한 State Relay 패턴 (선택)**
  - OAuth 2.0 스펙에서 지원하는 `state` 파라미터는 인증 서버가 상태를 유지하고 콜백 시 그대로 돌려주는 특성이 있습니다. 이 `state` 내부에 프론트엔드 오리진과 복귀 경로를 인코딩하여 태워 보내는 방식.
  - *장점*: 브라우저 스토리지 의존성을 제거할 수 있으며, OAuth 서버가 상태를 안전하게 에코(Echo)해주므로 분리 배포 환경에서도 완벽한 컨텍스트 유지가 가능합니다.

## 3. 최종 해결: OAuth State Relay 및 방어적 설계 구현

최종적으로 **OAuth State Relay 패턴**을 도입하고, 보안과 예외 처리를 강화했습니다.

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드에서 [소셜 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(next)을 인코딩하여 state 파라미터에 탑재
     state = encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  Provider(Google/Facebook 등)가 state 값을 그대로 유지하여 백엔드 콜백으로 전달

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 302 Redirect
  - 허용된 화이트리스트 도메인 검증(Open Redirect 취약점 방어)
```

### 핵심 엔지니어링 포인트

1. **상태 릴레이(State Relay) 메커니즘**
   * 로그인 시작 시점의 `origin`과 `next_url` 정보를 구조화하여 `state` 토큰에 포함시켰습니다. 콜백 완료 후 백엔드는 이 토큰을 파싱하여 정확한 프론트엔드 도메인으로 안전하게 302 리다이렉트를 수행합니다.
   * 이때, 악의적인 사용자가 `state`를 조작하여 다른 피싱 사이트로 리다이렉트 시키는 **Open Redirect 취약점**을 방어하기 위해, 백엔드 레벨에서 사전 정의된 프론트엔드 도메인 화이트리스트 검증 로직을 필수로 거치도록 구현했습니다.

2. **소셜 프로필 정규화 및 방어 코드**
   * 페이스북, 카카오 등에서 이메일 필수 동의를 해제한 사용자가 유입되더라도 예외로 빠지지 않도록, 고유 식별자 패턴(`social_id@social.picksafe.app`)을 활용한 가상 이메일 생성 및 방어 로직을 적용하여 가입/로그인 성공률을 100%로 끌어올렸습니다.

3. **어드민 `Return-To` 연속성 확보**
   * 관리자 로그인 프로세스에서도 쿼리스트링 기반의 `next` 파라미터를 유지하도록 확장하여, 세션 만료 후 재로그인하더라도 직전에 작업하던 관리자 서브 페이지로 즉각 복귀할 수 있는 매끄러운 UX를 완성했습니다.

---

## 4. 성과 및 맺음말 (Takeaways)

이번 아키텍처 개선을 통해 분리 배포(Vercel + Render) 환경에서 발생하던 **소셜 로그인 실패율을 0%**로 낮추었으며, 일반 사용자뿐만 아니라 관리자의 작업 연속성까지 완벽하게 확보할 수 있었습니다.

분산 시스템이나 멀티 도메인 환경에서는 상태(State)가 어디서 유실될 수 있는지 그 라이프사이클을 정확히 이해하는 것이 중요합니다. OAuth 표준 스펙이 제공하는 `state` 파라미터의 본래 목적을 적극 활용함으로써, 클라이언트 스토리지 의존성 없이 안전하고 확장 가능한 인증 파이프라인을 구축할 수 있었습니다.

PickSafe 팀은 앞으로도 견고하고 안정적인 아키텍처를 바탕으로 최상의 사용자 경험을 만들어 가겠습니다. 감사합니다!
