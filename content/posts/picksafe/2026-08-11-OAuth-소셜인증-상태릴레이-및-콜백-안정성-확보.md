안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

현대적인 웹 서비스 아키텍처에서 프론트엔드(Vercel 등)와 백엔드 API(Render, AWS 등)를 서로 다른 도메인으로 분리하여 배포하는 것은 이제 흔한 일입니다. 하지만 이러한 **멀티 도메인(Multi-domain) 환경**은 쿠키 정책, CORS, 그리고 **OAuth 2.0 소셜 인증 흐름**에서 미묘하지만 치명적인 엔지니어링 난제를 발생시키곤 합니다.

이번 포스팅에서는 PickSafe 서비스에서 마주한 **OAuth 리다이렉트 및 세션 유실 문제**를 어떻게 해결했는지, 그리고 Open Redirect 취약점을 방어하면서 어떻게 사용자 경험(UX)을 극대화했는지 그 기술적 의사결정 과정을 공유합니다.

---

## 1. 마주한 문제 (Problem)

PickSafe는 프론트엔드와 백엔드 서버가 분리된 환경에서 운영되고 있습니다. 소셜 로그인(구글, 페이스북, 카카오, 네이버 등)을 도입하는 과정에서 다음과 같은 3가지 치명적인 문제가 발생했습니다.

1. **콜백 Origin 유실 문제**
   * 사용자가 프로덕션 도메인(`picksafe.app`), 프리뷰 도메인(`picksafe.vercel.app`), 혹은 로컬 개발 환경(`localhost:3000`) 중 어디서 접속했든, OAuth 인증 후 백엔드 콜백 엔드포인트(`https://api.picksafe.app/auth/callback`)로 돌아올 때 **"사용자가 원래 어디서 왔는지"**에 대한 컨텍스트가 유실되는 현상이 발생했습니다. 이로 인해 인증은 성공했으나 잘못된 도메인으로 튕기거나 404 에러를 맞닥뜨리게 되었습니다.
2. **소셜 플랫폼별 응답 포맷 및 정책 차이**
   * 특히 페이스북 등의 플랫폼은 사용자가 이메일 제공을 거부하거나 특정 권한을 허용하지 않을 경우, 콜백 서버에서 예외가 발생하며 500 Internal Server Error로 이어지는 견고하지 못한 에러 핸들링 구조를 가지고 있었습니다.
3. **어드민 로그인 후 세션 컨텍스트 유실**
   * 관리자가 특정 관리자 페이지(예: `/admin/translations`)를 보던 중 세션이 만료되어 로그인 페이지로 튕겼을 때, 로그인 후 원래 보던 페이지가 아닌 무조건 대시보드 홈으로 이동하여 작업 흐름이 끊기는 불편함이 있었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

콜백 시점의 도메인 컨텍스트를 유지하기 위해 몇 가지 대안을 검토했습니다.

* **Alternative A: 브라우저 `localStorage` 또는 `sessionStorage` 활용**
  * *장점*: 구현이 단순함.
  * *단점*: OAuth 인증 과정은 외부 프로바이더(Google, Facebook 등)의 서버로 리다이렉트되었다가 돌아오는 **Cross-Origin 이동**이기 때문에, 리다이렉트 과정에서 브라우저 보안 정책이나 모바일 앱 내 브라우저 환경에 따라 스토리지 데이터가 유실될 위험이 컸습니다.
* **Alternative B: 백엔드 세션/DB에 임시 토큰 매핑**
  * *장점*: 안전함.
  * *단점*: 로그인 시도마다 DB에 불필요한 임시 레코드를 생성하고 소거해야 하는 I/O 오버헤드가 발생하며, 분산 환경에서 세션 스토리지 동기화 이슈가 발생할 수 있음.
* **Selected Alternative: OAuth `state` 파라미터를 활용한 '상태 릴레이(State Relay) 패턴'**
  * *이유*: OAuth 2.0 스펙에서 지원하는 `state` 파라미터는 인증 서버가 그대로 우리 백엔드 콜백으로 돌려주기 때문에 무상태(Stateless)로 안전하게 컨텍스트를 전달할 수 있습니다. 여기에 보안을 위해 인코딩 및 화이트리스트 검증을 결합하기로 결정했습니다.

## 3. 해결 및 아키텍처 설계 (Solution & Architecture)

### 3.1. OAuth State Relay 패턴 구현

OAuth 인증 요청 시 프론트엔드의 현재 `origin` 정보와 로그인 성공 후 돌아갈 `next` 경로를 JSON으로 묶어 Base64 인코딩한 뒤, `state` 파라미터에 담아 전송하도록 설계했습니다.

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드(picksafe.app)에서 [구글/페이스북 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(return_to)을 인코딩하여 state 파라미터에 탑재
     state = base64_encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  Provider(Google/Facebook) 인증 후 state 값을 그대로 유지하여 백엔드 콜백으로 전송

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 안전하게 302 Redirect
```

* **보안 강화 (Open Redirect 방어)**: `state`를 디코딩하여 리다이렉트를 수행할 때, 허용된 도메인 화이트리스트(Whitelist)에 포함된 도메인인지 엄격하게 검증하여 악의적인 사용자가 외부 피싱 사이트로 리다이렉트시키는 **Open Redirect 취약점**을 원천 차단했습니다.

### 3.2. 플랫폼별 프로필 정규화 및 방어 코드

페이스북, 카카오 등에서 이메일 동의를 필수로 받지 않거나 누락된 유저 케이스를 방어하기 위해, 백엔드 인증 계층에 **프로필 정규화(Normalization) 레이어**를 도입했습니다. 이메일 정보가 없는 경우에도 안전한 가상 고유 식별자(예: `provider_id@social.picksafe.app`)를 생성·할당하여 계정 생성 및 로그인 프로세스가 중단 없이 100% 성공하도록 예외 처리를 강화했습니다.

### 3.3. 어드민 Return-To 흐름 완성

관리자 로그인 폼 제출 시 쿼리스트링의 `next` 파라미터를 세션 및 리다이렉트 로직과 연동하여, 인증 완료 후 사용자가 직전까지 작업하던 어드민 서브 페이지로 매끄럽게 복귀할 수 있도록 개선했습니다.

## 4. 성과 및 교훈 (Takeaways)

* **결과**: Vercel(프론트엔드)과 Render(백엔드)로 분리된 멀티 도메인 환경에서 소셜 로그인 실패율 **0%를 달성**했습니다.
* **엔지니어링 교훈**: 
  1. 외부 서비스(OAuth Provider)와 연동할 때는 **"내가 보낸 데이터가 그대로 돌아온다"는 보장(State 파라미터)**을 최대한 활용하는 것이 무상태(Stateless) 아키텍처 유지에 가장 유리합니다.
  2. 멀티 클라이언트(프로덕션, 프리뷰, 로컬) 환경을 지원해야 하는 모던 웹 서비스에서는 하드코딩된 Redirect URI 대신 **동적 Origin 릴레이 메커니즘**이 필수적이라는 점을 다시 한번 확인했습니다.

앞으로도 PickSafe 팀은 견고하고 확장 가능한 인증/인가 시스템을 바탕으로 사용자에게 안정적인 서비스를 제공하겠습니다. 감사합니다.
