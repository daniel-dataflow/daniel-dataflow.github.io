안녕하세요. PickSafe 기술 블로그입니다. 

현대 웹 아키텍처에서 프론트엔드와 백엔드를 분리(Decoupled)하여 배포하는 것은 이제 표준적인 방식이 되었습니다. 저희 PickSafe 역시 프론트엔드는 Vercel, 백엔드 API는 Render로 분리된 멀티 도메인 환경에서 서비스를 운영하고 있습니다. 

하지만 서로 다른 도메인 간의 인증 흐름을 다룰 때, 흔히 간과하기 쉬운 **‘상태 유실(State Loss) 문제’**가 발생하기 마련입니다. 이번 포스팅에서는 OAuth 2.0 소셜 로그인 과정에서 마주했던 문제들과, 이를 **State Relay 패턴**을 통해 어떻게 우아하게 해결했는지 공유해 드리고자 합니다.

---

## 1. 문제 정의 (Context & Problem)

Vercel과 Render가 분리된 환경에서 소셜 로그인(구글, 페이스북, 카카오, 네이버 등)을 구현했을 때, 다음과 같은 세 가지 치명적인 문제가 발생했습니다.

### ① 콜백 Origin 유실 문제
사용자가 프론트엔드 도메인(`picksafe.app` 또는 테스트용 `vercel.app`)에서 로그인을 시도한 뒤, 외부 OAuth Provider를 거쳐 백엔드 콜백 엔드포인트(`/auth/callback/...`)로 돌아올 때 **‘사용자가 원래 어느 도메인에서 요청을 보냈는지’**에 대한 컨텍스트가 사라지는 현상이 발생했습니다. 이로 인해 인증은 성공했음에도 프론트엔드로 안전하게 리다이렉트하지 못하고 404 에러나 잘못된 호스트로 튕기는 문제가 발생했습니다.

### ② 소셜 플랫폼별 응답 포맷 및 제약 차이 (예: 페이스북)
표준을 따르지 않거나 예외적인 케이스를 던지는 소셜 플랫폼이 존재했습니다. 특히 페이스북의 경우, 사용자가 특정 권한(이메일 등)을 거부하거나 프로필에 이메일 정보가 없는 상태로 가입을 시도할 때 백엔드 콜백 단계에서 500 에러를 유발했습니다.

### ③ 어드민 페이지 탐색 중 세션 만료 및 복귀 누락
관리자가 복잡한 어드민 페이지(`/admin/translations` 등)를 작업하다 세션이 만료되어 로그인 페이지로 튕긴 후, 다시 로그인을 마치면 원래 보던 페이지가 아닌 엉뚱한 대시보드 홈으로 강제 이동되는 UX 결함이 있었습니다.

## 2. 기술적 고민과 아키텍처 대안 비교

이 문제를 해결하기 위해 두 가지 대안을 고민했습니다.

* **대안 A: 프론트엔드 세션 스토리지(SessionStorage) 활용**
  * *접근법*: 로그인 요청 직전 `sessionStorage`에 원래 도메인과 `next` URL을 저장하고, 콜백 시 이를 읽어옴.
  * *한계*: OAuth 인증 과정에서 브라우저가 외부 인증 서버로 완전히 리다이렉트(Cross-site)되었다가 돌아오기 때문에, 일부 모바일 브라우저나 엄격한 쿠키 정책(SameSite) 환경에서 스토리지 데이터가 유실될 위험이 큼.
* **대안 B: OAuth `state` 파라미터를 활용한 State Relay 패턴 (선택)**
  * *접근법*: OAuth 2.0 스펙에서 지원하는 `state` 파라미터에 프론트엔드 Origin 정보와 복귀 URL을 안전하게 인코딩하여 태워 보냄.
  * *장점*: 인증 서버가 `state` 값을 그대로 백엔드 콜백으로 돌려주므로, 별도의 브라우저 스토리지 의존성 없이 상태를 100% 신뢰성 있게 유지할 수 있음.

## 3. 최종 해결 및 구현 (State Relay Architecture)

최종적으로 **OAuth State Relay 패턴**을 도입하여 아키텍처를 재설계했습니다.

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드(picksafe.app)에서 [소셜 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(next)을 JSON으로 묶어 Base64 인코딩 후 state에 탑재
     state = base64_encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  Provider(Google/Facebook 등) 인증 후 state 값을 그대로 유지하여 백엔드 콜백으로 전달

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 안전하게 302 Redirect
  - ※ Open Redirect 취약점 방어를 위해 화이트리스트 기반 도메인 검증 로직 필수 적용
```

### 핵심 구현 포인트

1. **상태 릴레이 메커니즘 (`auth.py`)**
   * 로그인 시작 시점의 `origin`과 `next_url` 정보를 직렬화하여 `state` 파라미터에 담아 전송하고, 콜백 핸들러에서 이를 파싱하여 정확한 출발지로 리다이렉트하도록 구현했습니다. 단, 악의적인 사용자가 임의의 외부 사이트로 리다이렉트시키는 **Open Redirect 취약점**을 막기 위해, 허용된 도메인 화이트리스트 검증 로직을 반드시 거치도록 방어 장치를 마련했습니다.

2. **소셜 프로필 정규화 (Normalization) 방어 코드**
   * 페이스북 및 카카오 등에서 이메일 정보 제공을 필수로 잡지 않은 사용자의 경우에도 로그인이 실패하지 않도록, 가상의 고유 식별자 패턴(`social_id@social.picksafe.app`)을 동적으로 생성하여 내부 계정 생성 및 로그인 파이프라인이 100% 중단 없이 동작하도록 예외 처리를 강화했습니다.

3. **Admin Return-To URL 지원**
   * 어드민 로그인 폼 제출 시 `next` 쿼리스트링 파라미터를 세션과 리다이렉트 흐름 전체에 걸쳐 유지하여, 관리자가 인증 갱신 후에도 끊김 없이 원래 작업 중이던 하위 페이지로 즉각 복귀할 수 있도록 사용자 경험을 개선했습니다.

---

## 4. 맺음말 (Takeaways)

이번 작업을 통해 분리 배포 환경(멀티 도메인)에서의 인증 흐름이 얼마나 섬세한 상태 관리를 필요로 하는지 다시 한번 깊이 체감할 수 있었습니다. 

* **스펙의 적극적 활용**: OAuth 2.0이 기본 제공하는 `state` 파라미터의 본래 목적(CSRF 방어)을 확장하여, 멀티 도메인 환경에서의 **컨텍스트 릴레이(Context Relay)** 용도로 활용한 점이 주효했습니다.
* **예외 없는 방어적 프로그래밍**: 서드파티 API(소셜 로그인)는 언제든 예상치 못한 페이로드(이메일 누락 등)를 보낼 수 있으므로, 백엔드 단에서의 견고한 정규화 및 예외 처리가 서비스 신뢰성을 결정한다는 것을 배웠습니다.

이번 개선을 통해 멀티 도메인 환경에서의 소셜 로그인 실패율 **0%**를 달성하였으며, 사용자에게 끊김 없는(Seamless) 인증 경험을 제공할 수 있게 되었습니다. 앞으로도 PickSafe는 안정적이고 견고한 엔지니어링을 바탕으로 서비스를 고도화해 나가겠습니다. 

감사합니다.
