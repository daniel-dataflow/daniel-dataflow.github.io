안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

최근 우리는 프론트엔드(Vercel)와 백엔드 API(Render)가 서로 다른 도메인으로 분리 배포된 **멀티 도메인 아키텍처** 환경에서, 소셜 로그인(구글, 페이스북, 카카오, 네이버 등) 연동 시 발생하던 복잡한 인증 유실 및 리다이렉트 실패 문제를 해결했습니다. 

이번 글에서는 분리 배포 환경에서 흔히 겪을 수 있는 OAuth 콜백 이슈를 어떻게 구조적으로 해결했는지, 그리고 그 과정에서 고려한 기술적 트레이드오프와 보안 설계에 대해 공유해 드립니다.

---

## 1. 배경 및 마주한 문제 상황 (Context & Problem)

PickSafe 서비스는 프론트엔드와 백엔드가 분리된 구조로 운영되고 있습니다. 이로 인해 OAuth 2.0 소셜 로그인 흐름에서 다음과 같은 세 가지 치명적인 문제가 발생했습니다.

### ① 콜백 Origin 유실 문제
사용자가 프론트엔드(`https://picksafe.app`)에서 소셜 로그인을 시도하면, OAuth 인증 서버를 거쳐 백엔드 콜백 엔드포인트(`https://api.picksafe.app/auth/callback/...`)로 리다이렉트됩니다. 
이때, 백엔드 입장에서 **"이 사용자가 원래 어느 프론트엔드 도메인에서 왔는지"**에 대한 정보를 잃어버리는 문제가 발생했습니다. 브라우저의 리다이렉트 과정에서 세션이나 컨텍스트가 유실되면서 사용자가 404 에러를 마주하거나 잘못된 호스트로 튕기는 현상이 빈번했습니다.

### ② 소셜 플랫폼별 응답 포맷 및 정책 차이
특히 페이스북의 경우, 사용자가 특정 권한 동의를 거부하거나 이메일 정보를 제공하지 않는 경우 콜백 단계에서 500 에러를 유발하며 전체 인증 프로세스가 중단되는 취약점이 있었습니다.

### ③ 어드민 UX 단절 문제
관리자가 백오피스 특정 페이지(예: 번역 관리 등)를 이용하다 세션이 만료되어 로그인 페이지로 튕긴 경우, 로그인을 완료하더라도 원래 보던 페이지가 아닌 대시보드 메인으로 강제 이동되어 작업 흐름이 끊기는 불편함이 있었습니다.

## 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 두 가지 대안을 검토했습니다.

- **대안 A: 프론트엔드 LocalStorage/SessionStorage 활용**
  - *접근 방식*: 로그인 요청 전, 브라우저 스토리지에 `origin`과 `return_to`를 저장해 두고 콜백 시점에 읽어오기.
  - *단점*: OAuth 인증 서버로 리다이렉트되는 과정에서 도메인이 완전히 바뀌거나(Cross-site), 모바일 웹브라우저의 인앱 브라우저 정책 등에 따라 스토리지 데이터가 유실될 위험이 매우 컸습니다.
- **대안 B: OAuth `state` 파라미터를 활용한 '상태 릴레이(State Relay)' 패턴**
  - *접근 방식*: OAuth 표준 규격인 `state` 파라미터에 프론트엔드의 메타데이터를 담아 인증 서버로 넘기고, 백엔드 콜백 시 이를 그대로 돌려받는 방식.
  - *장점*: 추가적인 세션 스토리지 의존성 없이 OAuth 프로토콜 자체의 무상태(Stateless) 성격을 활용해 안전하게 컨텍스트를 전달할 수 있습니다.

우리는 **안정성과 표준 준수 측면에서 압도적으로 유리한 '대안 B (OAuth State Relay 패턴)'를 최종 아키텍처로 선택**했습니다.

## 3. 최종 해결 및 아키텍처 설계

```
[1. 소셜 로그인 시도]
  사용자가 프론트엔드(picksafe.app)에서 [구글/페이스북 로그인] 클릭
  ➔ 프론트엔드 Origin + 복귀 대상 URL(return_to)을 인코딩하여 state 파라미터에 탑재
     state = encode({ "origin": "https://picksafe.app", "next": "/mypage" })

[2. OAuth Provider 승인]
  Provider(Google/Facebook) 인증 후 state 값을 그대로 유지하여 백엔드 콜백으로 전송

[3. 백엔드 콜백 및 안전한 복귀]
  - 백엔드가 state 디코딩 ➔ 세션 쿠키(HttpOnly) 발급 ➔ 원래 origin/next로 안전하게 302 Redirect
  - 올바른 화이트리스트 도메인 검증으로 Open Redirect 취약점 완벽 방어
```

### 3.1. OAuth State Relay 구현
로그인 초기화 단계(`auth.py`)에서 프론트엔드의 현재 `origin`과 사용자가 이동하려던 `next_url` 정보를 JSON으로 직렬화한 뒤, 안전하게 서명/인코딩하여 `state` 파라미터에 담아 전송했습니다. 백엔드는 콜백 시 이 `state`를 파싱하여 정확한 원본 도메인과 복귀 주소를 알아내어 302 리다이렉트를 수행합니다.

> 🔒 **Security Note (Open Redirect 방어)**:
> `state`에 포함된 리다이렉트 URL을 무조건 신뢰하면 Open Redirect 공격에 노출될 수 있습니다. 이를 방어하기 위해 백엔드 레벨에서 사전에 정의된 **신뢰할 수 있는 프론트엔드 도메인 화이트리스트(Whitelist)** 검증 로직을 반드시 거치도록 구현했습니다.

### 3.2. 소셜 프로필 정규화 및 방어 코드
페이스북이나 카카오 등 이메일 제공이 필수가 아닌 플랫폼의 정책 변화에 대응하기 위해, 이메일 정보가 누락된 경우에도 시스템 내부에서 고유하게 식별 가능한 가상 고유 식별자(`{provider}_{id}@social.picksafe.app`)를 생성하도록 예외 처리를 추가하여 가입/로그인 성공률을 100%로 끌어올렸습니다.

### 3.3. 어드민 Return-To 메커니즘 연동
관리자 인증 흐름에서도 `next` 쿼리스트링 파라미터를 세션 전반에 걸쳐 유지하도록 설계하여, 인증 완료 후 사용자가 정확히 직전에 머물렀던 어드민 하위 페이지로 즉시 복귀할 수 있도록 사용자 경험을 개선했습니다.

---

## 4. Takeaway (엔지니어링 교훈)

1. **표준 스펙의 적극적 활용**: 문제를 해결하려 복잡한 외부 스토리지나 세션 DB를 파기보다, OAuth 프로토콜이 기본으로 제공하는 `state` 파라미터를 확장하여 활용하는 것이 분리 배포 환경에서 가장 우아하고 안전한 해법임을 재확인했습니다.
2. **멀티 도메인 환경의 보안 경계 인식**: 프론트엔드와 백엔드가 분리된 환경에서는 CORS뿐만 아니라 리다이렉트 시점의 컨텍스트 유실 문제가 빈번합니다. 이를 설계 단계부터 상태 릴레이 패턴으로 방어하는 것이 견고한 인증 시스템의 핵심입니다.

이번 개선을 통해 멀티 도메인 환경에서의 소셜 로그인 실패율 **0%**를 달성하였으며, 사용자 및 관리자 경험의 연속성을 완벽하게 확보할 수 있었습니다.
