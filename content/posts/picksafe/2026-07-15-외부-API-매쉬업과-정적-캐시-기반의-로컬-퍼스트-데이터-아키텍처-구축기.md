화장품 성분 분석 서비스 **PickSafe**를 개발하며 서비스의 핵심인 '성분 데이터의 정확도'와 '인프라 운영 효율성' 사이에서 적절한 균형점을 찾는 작업을 진행했습니다.

초기 구현 단계에서는 외부 공공 데이터 API를 실시간 호출하거나 원격 데이터베이스에 모든 쿼리를 의존하는 단순한 방식을 취했습니다. 하지만 이 구조는 외부 API의 응답 지연, 원격 DB의 대역폭 한계, 그리고 단순 명칭 외에 배합 제한 및 규제 정보가 누락되는 현실적인 문제에 직면했습니다.

이 글에서는 공공 API 매쉬업을 통해 성분 안전 데이터의 깊이를 확보하는 과정과, 제한된 인프라 환경에서 DB 부하를 차단하기 위해 **정적 JSON 기반 로컬 퍼스트(Local-First) 캐싱 아키텍처**를 수립한 기술적 과정 및 회고를 정리합니다.

---

## 🎯 마주한 고민과 문제 배경

### 1. 단일 API 데이터의 정보 부족
초기에는 식약처의 기본 원료 성분 정보 API 1개만을 활용해 데이터를 수집했습니다. 하지만 이 데이터는 성분의 국문/영문 표준명만 제공할 뿐, 사용자의 피부 안전에 직결되는 **'배합 한도(예: 특정 성분 0.5% 이하 restriction)'**나 **'국가별 규제 정보'**를 제공하지 못했습니다. 서비스 목적상 단순 성분 존재 여부 파악을 넘어 상세 안전 경고를 제공해야 했기에 정보의 깊이를 확장할 필요가 있었습니다.

### 2. 원격 Serverless DB의 네트워크 및 리소스 제약
PickSafe 백엔드는 클라우드 Serverless PostgreSQL(Neon DB)을 사용하고 있습니다. 
무료/저비용 티어 특성상 월간 네트워크 전송량(Network Transfer)과 컴퓨팅 시간에 명확한 상한선이 존재합니다.

성분 분석 요청이 들어올 때마다 수십~수백 개의 성분을 원격 DB에서 `SELECT` 하거나, 대량의 공공데이터를 원격 DB에 직접 반복 시딩(Bulk Seeding)할 경우 아래와 같은 문제가 발생했습니다.
* **네트워크 레이턴시 증가**: 단순 성분 매칭조차 원격 DB RTT(Round Trip Time) 영향으로 처리 시간이 늘어남
* **대역폭 고갈 위험**: 이미지 OCR 결과나 텍스트에서 추출된 다수의 성분을 조회하면서 쿼리 횟수와 전송량이 급증
* **DB 커넥션 병목**: 서버리스 인스턴스가 스케일링되는 과정에서 DB 커넥션 수 제한에 도달할 가능성

추가적인 메모리 캐시 인프라(예: Managed Redis)를 별도로 구축하지 않고, 애플리케이션 레이어에서 이를 효율적으로 방어할 수 있는 구조가 필요했습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

문제 해결을 위해 크게 세 가지 아키텍처 대안을 검토했습니다.

| 항목 | 대안 A: 매 요청마다 원격 DB / 외부 API 실시간 조회 | 대안 B: 별도 Redis 인메모리 캐시 서버 구축 | 대안 C (최종 선택): 사전 컴파일 정적 JSON + 메모리 맵 캐시 (로컬 퍼스트) |
| :--- | :--- | :--- | :--- |
| **장점** | 데이터 최신성 보장, 구현 단순함 | 빠른 응답 속도, 동적 캐시 갱신 용이 | 추가 인프라 비용 없음, DB 장애 시에도 조회 가능, 1ms 미만의 빠른 매칭 |
| **단점** | 원격 DB 대역폭/컴퓨팅 소모 큼, API 장애 시 서비스 마비 | 별도 인프라 관리 및 비용 발생 | 데이터 업데이트 시 컴파일/배포 프로세스 필요 |
| **Trade-off** | 인프라 한계로 운영 안정성 낮음 | 시스템 복잡도 및 비용 증가 | 빌드/시딩 파이프라인 구축 비용 발생 |

### 최종 선택: 정적 JSON 백업 파일 (`ingredients_master.json`)을 통한 로컬 퍼스트 전략
인프라 추가 도입 없이 애플리케이션 메모리와 디스크를 활용하는 **대안 C**를 선택했습니다.

1. **식약처 3대 API 매쉬업 사전 처리**:
   - `원료성분정보`, `사용제한원료정보`, `규제정보` API를 수집 단계에서 사전에 조인(Join)하여 종합 사전 데이터셋을 구성합니다.
2. **정적 아티팩트 컴파일**:
   - 수집 및 병합된 데이터를 애플리케이션 내부 정적 경로(`app/resources/ingredients_master.json`)에 단일 아티팩트로 저장합니다.
3. **메모리 로딩 및 로컬 최우선 매칭**:
   - 백엔드 애플리케이션이 구동될 때 이 JSON을 메모리 Hash Map
