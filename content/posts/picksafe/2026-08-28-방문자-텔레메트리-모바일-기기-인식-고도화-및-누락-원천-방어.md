안녕하세요. 프로덕트의 백엔드와 데이터 신뢰성을 담당하고 있는 시니어 엔지니어입니다.

최근 관리자 대시보드의 방문자 텔레메트리 데이터를 분석하는 과정에서, 실제 모바일 트래픽이 제대로 집계되지 않거나 기기 환경이 `Unknown`으로 대거 누락되는 치명적인 데이터 왜곡 현상을 발견했습니다. 

비즈니스의 의사결정을 돕는 텔레메트리 데이터의 신뢰성은 프로덕트의 성패를 가르는 핵심 요소입니다. 이번 포스팅에서는 모바일 인앱 브라우저의 특수성과 사내 네트워크 환경(동일 IP, Wi-Fi/LTE 전환 등)에서 발생한 문제를 어떻게 아키텍처 관점에서 분석하고 해결했는지 공유하고자 합니다.

---

## 1. 마주한 문제 (Problem)

대시보드 운영 중 보고된 텔레메트리 왜곡 현상은 크게 두 가지 카테고리로 나뉘었습니다.

### ① 모바일 인앱 브라우저 및 축소형 UA로 인한 'Unknown' 대량 발생
* 온보딩 완료 및 전환 이벤트 발생 시, 요청(`request`) 객체로부터 User-Agent(UA)와 IP 정보를 제대로 전달하지 못하고 `None`으로 적재되고 있었습니다.
* 특히 카카오톡, 네이버, 인스타그램 등 국내 사용자 비중이 높은 **인앱 브라우저**들과 최신 모바일 브라우저의 축소형 UA 문자열을 기존 파서가 식별하지 못해, 대다수의 모바일 트래픽이 `Unknown / Other`로 분류되는 문제가 발생했습니다.

### ② 외부 모바일 접속 시 세션 누락 및 오탐지
* **동일 IP 다중 기기 과도 차단**: 기존 텔레메트리 로깅 로직은 '당일 동일 IP의 2번째 세션'을 무조건 중복으로 간주하고 버렸습니다. 이로 인해 동일한 Wi-Fi 환경에서 PC로 테스트 후 모바일로 접속한 경우, 모바일 세션이 강제로 유실되었습니다.
* **관리자 IP 오판정**: 사용자가 단순히 `/admin` 경로에 진입 시도한 것만으로도, 해당 모바일의 LTE/5G 통신사 IP가 관리자 IP 목록에 자동 등록되어 일반 사용자의 세션까지 차단(`is_active = true`)되는 보안 오탐이 발생했습니다.
* **봇 오인**: 웹뷰나 PWA 환경의 15자 미만 짧은 UA 문자열이 무차별적으로 봇 차단 로직에 걸려 드롭되었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 백엔드 미들웨어부터 프론트엔드 핑(Ping) 구조까지 전면적인 리팩터링을 계획했습니다.

### 대안 1: 서드파티 애널리틱스 솔루션 도입
* **장점**: 개발 공수가 적고 즉시 도입 가능.
* **단점**: 비즈니스 도메인(온보딩, 커스텀 세션 등)과 완벽하게 결합된 실시간 대시보드 구축에 한계가 있으며, 내부 데이터 주권 확보가 어려움.
* **결론**: **자체 텔레메트리 파이프라인 고도화**를 선택. 데이터의 정확도를 직접 통제하고 비즈니스 맞춤형 메타데이터를 적재하는 방향으로 결정했습니다.

### 대안 2: 복합 키 기반 세션 분리 및 클라이언트 컨텍스트 표준화
* **장점**: 동일 IP 환경에서도 기기 및 브라우저별로 완벽한 세션 분리 가능.
* **단점**: 기존 단일 IP 기반의 단순한 중복 체크 로직 대비 DB 쿼리 및 유효성 검증 로직이 복잡해짐.
* **결론**: 채택. IP 주소 단일 의존성을 제거하고, `(session_id, ip_address, device_type)` 복합 기준으로 세션 중복 검사 로직을 고도화하기로 했습니다.

---

## 3. 최종 해결 및 엔지니어링 적용 (Solution)

### ① 인앱 브라우저 및 모바일 정밀 파서 전면 고도화
국내외 주요 인앱 브라우저(카카오톡, 네이버, 인스타그램, 페이스북, 라인, 삼성 브라우저 등) 15종 이상의 패턴을 분석하여 UA 파서 함수(`parse_user_agent`)를 고도화했습니다. 불완전한 UA 문자열이 들어오더라도 모바일 서비스 특성을 반영한 지능형 폴백(Fallback)을 적용해 `Mobile`, `iOS`, `Android`를 100% 탐지하도록 개선했습니다.

### ② 클라이언트 컨텍스트 추출 표준화 (`extract_client_context`)
인증, 온보딩, 스캔 등 주요 라우터에서 흩어져 있던 메타데이터 수집 로직을 중앙집중화했습니다. 단 한 줄의 함수 호출로 `session_id`, `ip_address`, `device_type`, `os_name`, `locale` 등을 완벽히 캡처하여 이벤트 로깅 시 온전한 데이터가 DB에 적재되도록 보장했습니다.

### ③ 세션 및 관리자 IP 판정 로직 정교화
* **다중 기기 허용**: 동일 IP라 할지라도 `session_id` 또는 `device_type`이 다르면 별개의 정상 세션으로 인정하도록 복합 기준을 도입했습니다.
* **엄격한 관리자 IP 등록**: URL 패스만 보고 IP를 등록하던 방식을 개선하여, **유효한 관리자 인증 토큰 쿠키가 실제로 존재하는 경우에만** 관리자 IP로 등록되도록 보안 조건을 강화했습니다.

### ④ 프론트엔드 텔레메트리 2중 안전망 구축
모바일 PWA 환경이나 브라우저 뒤로가기 캐시(BFcache) 등으로 인해 백엔드 미들웨어가 누락될 가능성에 대비했습니다. 프론트엔드 단에서 화면 로드 시 비동기로 백엔드 핑(`/api/telemetry/ping`)을 발송하는 안전망을 구축하여 모바일 실사용자 방문이 누락되지 않도록 설계했습니다.

---

## 4. 검증 결과 및 배운 점 (Takeaway)

리팩터링 이후 기존 적재된 이벤트 데이터를 전수 클린업(`visitors_events` 테이블 대상)한 결과, 다음과 같은 유의미한 지표를 확인했습니다.

* **`Unknown / Other` 환경: 18건 전수 소멸 (0건 달성)**
* 실시간 집계 API 테스트 결과 모바일/데스크톱 및 OS/로케일별 브레이크다운이 정확하게 분기됨을 확인.

### 💡 Takeaway
1. **모바일 환경의 특수성 이해**: 데스크톱 중심의 사고에서 벗어나, 인앱 브라우저와 다양한 네트워크(Wi-Fi ↔ LTE 전환) 환경에서 발생할 수 있는 엣지 케이스를 설계 단계부터 고려해야 합니다.
2. **데이터 파이프라인의 가시성**: 텔레메트리 데이터는 단순한 로그가 아니라 제품의 비즈니스 지표를 지탱하는 뼈대입니다. 데이터 수집부(Collector)의 파서와 컨텍스트 표준화는 프로덕트 초기부터 견고하게 다져야 기술 부채를 예방할 수 있습니다.
