서비스를 운영하면서 가장 진땀을 빼는 순간 중 하나는 **"사용자는 분명 들어왔다는데, 대시보드 지표가 텅 비어있을 때"**입니다. 

최근 관리자 대시보드의 방문자 텔레메트리 시스템을 모니터링하던 중, 모바일 환경에서의 이벤트가 대거 `Unknown / Other`로 누락되거나 심지어 정상적인 사용자의 세션이 중복으로 오인되어 차단되는 치명적인 현상을 발견했습니다. 

이번 글에서는 모바일 인앱 브라우저의 특성에서 기인한 텔레메트리 왜곡 문제를 어떻게 분석하고, 백엔드 아키텍처와 프론트엔드 안전망(2중 구조)을 통해 원천적으로 해결했는지 공유하고자 합니다.

---

## 1. 문제 정의: 왜 모바일 방문자 데이터는 이토록 유실되기 쉬울까?

보고된 문제는 크게 두 가지 영역으로 나뉘었습니다.

### ① 기기 환경의 `Unknown / Other` 대량 발생
* `onboarding_completed`, `guest_converted` 등의 핵심 전환 이벤트 발생 시, 요청(`request`) 객체로부터 User-Agent, IP, Device Type 등의 메타데이터를 누락한 채 `None`으로 적재하고 있었습니다.
* 설상가상으로, 카카오톡, 네이버, 인스타그램 등 **국내 유저들이 주로 사용하는 모바일 인앱 브라우저의 축소형 UA(User-Agent) 문자열**을 기존 파서가 식별하지 못해 전부 `Unknown`으로 처리되고 있었습니다.

### ② 외부 모바일 접속 시 세션 기록 유실 및 오차단
* **동일 IP 다중 기기 과도 차단:** 백엔드 분석 로직이 당일 동일 IP의 2번째 세션을 무조건 중복(Duplicate)으로 판단하여 폐기하고 있었습니다. 동일한 Wi-Fi 환경에서 PC로 테스트 후 모바일로 접속한 경우, 모바일 세션이 통째로 버려지는 참사가 발생했습니다.
* **관리자 IP 오판정:** `/admin` 경로에 단순히 진입만 시도해도, 해당 모바일의 LTE/5G 통신사 IP가 관리자 IP 목록에 자동 등록되어 `is_active = true` 상태로 시스템 접근이 차단되는 버그가 있었습니다.
* **짧은 UA 봇 오인:** 일부 웹뷰나 PWA 환경의 15자 미만 짧은 UA 문자열이 백엔드의 봇(Bot) 방어 로직에 걸려 차단되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 크게 3가지 아키텍처적 개선 방향을 도출하고 트레이드오프를 검토했습니다.

### 대안 A: 서드파티 애널리틱스(Google Analytics, Mixpanel 등) 도입
* **장점:** 개발 공수가 적고, 고도화된 UA 파싱 기능을 기본 제공받음.
* **단점:** 내부 비즈니스 로직(온보딩, 관리자 권한, 자체 DB 기반 실시간 대시보드)과 실시간 연동하는 데 제약이 따르며, 데이터 주권 및 커스텀 IP 필터링 로직을 유연하게 구현하기 어려움.
* **결정:** **기각.** 자체 DB 기반의 정밀한 방문자 관리 시스템(PickSafe)의 특성상 내부 백엔드 파이프라인을 직접 고도화하는 것이 장기적으로 유리하다고 판단.

### 대안 B: 백엔드 단일 파이프라인 고도화 + 프론트엔드 핑(Ping) 2중 안전망 구축 (채택)
* **장점:** 
  1. 인앱 브라우저 및 커스텀 UA 패턴을 우리 서비스 요구사항에 맞춰 100% 커버 가능.
  2. 미들웨어 계층의 유실을 방어하기 위해 프론트엔드에서 한 번 더 세션 초기화를 보장.
  3. 동일 IP 내 복합 기기(PC + Mobile) 세션을 안전하게 분리.
* **단점:** 파서 및 컨텍스트 추출 로직을 직접 관리해야 하므로 초기 구현 및 테스트 공수가 듦.

## 3. 최종 해결 및 엔지니어링 구현

### 3.1 인앱 브라우저 및 모바일 정밀 파서(`parse_user_agent`) 고도화
국내 모바일 환경의 특수성을 고려하여, 카카오톡, 네이버, 인스타그램, 페이스북, 라인, 삼성 브라우저 등 15종 이상의 인앱 브라우저와 웹뷰(`wv`) 패턴을 정확히 감지하도록 파서를 전면 재작성했습니다. 불완전한 UA가 들어오더라도 모바일 서비스 특성을 반영해 안전한 폴백(Fallback) 값을 반환하도록 방어 코드를 추가했습니다.

### 3.2 클라이언트 컨텍스트 추출 표준화 (`extract_client_context`)
인증, 온보딩, 스캔 등 주요 라우터에서 파편화되어 있던 메타데이터 수집 로직을 단일 함수(`extract_client_context`)로 표준화했습니다. 이를 통해 `session_id`, `ip_address`, `device_type`, `os_name`, `locale` 등이 이벤트 로깅 시 누락 없이 100% DB에 보존되도록 개선했습니다.

### 3.3 세션 및 관리자 IP 판정 로직 정교화
* **복합 키 기준 중복 검사:** 동일 IP라 할지라도 `(session_id, ip_address, device_type)`을 복합 기준으로 삼아, 동일 Wi-Fi 내의 PC와 모바일이 서로를 간섭하지 않고 공존할 수 있도록 완화했습니다.
* **엄격한 관리자 IP 등록:** 단순 URL 접근이 아닌, **유효한 관리자 인증 토큰 쿠키가 존재하는 실제 세션**일 때만 관리자 IP로 등록되도록 조건을 엄격히 강화했습니다.

### 3.4 프론트엔드 텔레메트리 핑 2중 안전망 (`base.js`)
모바일 PWA 환경이나 브라우저 캐시 등으로 인해 특정 HTTP 미들웨어가 우회되는 상황을 대비했습니다. 프론트엔드 기본 스크립트(`base.js`)에서 화면 로드 시 백엔드로 비동기 핑(`initSessionTelemetry`)을 발송하여, 모바일 실사용자의 방문이 어떤 환경에서도 100조각 중 단 1조각도 누락되지 않도록 이중 장치를 마련했습니다.

## 4. 검증 결과 및 Takeaway

개선 사항을 프로덕션 환경에 배포한 후, 기존 적재된 데이터 클린업 및 실시간 집계 API를 검증했습니다.

1. **DB 이벤트 전수 클린업 결과:**
   - `Mobile / Android`: 다수 정상 적재
   - `Desktop / Linux`: 다수 정상 적재
   - **`Unknown / Other`: 0건 (완전 소멸)**
2. **실시간 당일 집계 API (`get_realtime_today_summary`):**
   - 디바이스, OS, 로케일 브레이크다운이 왜곡 없이 정확하게 집계되는 것을 확인했습니다.

### 엔지니어링 교훈 (Takeaway)
> **"프레임워크와 미들웨어를 맹신하지 말고, 클라이언트의 다양한 네트워크/브라우저 환경(특히 모바일 인앱 브라우저)을 가정하여 방어적으로 설계하라."**

이번 트러블슈팅을 통해 단순히 API를 호출하는 것을 넘어, 사용자가 마주하는 다양한 모바일 브라우저 생태계와 네트워크 환경(Wi-Fi 공유기 환경 등)까지 고려한 엔지니어링의 중요성을 다시 한번 깊이 깨달았습니다. 견고한 데이터 파이프라인은 신뢰할 수 있는 대시보드의 기초가 됩니다.
