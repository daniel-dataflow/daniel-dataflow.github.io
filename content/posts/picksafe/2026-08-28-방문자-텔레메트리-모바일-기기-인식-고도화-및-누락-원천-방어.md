대규모 트래픽을 다루는 서비스에서 '방문자 분석(Telemetry)'은 비즈니스 의사결정의 핵심 데이터입니다. 하지만 모바일 환경, 특히 다양한 인앱 브라우저(카카오톡, 네이버, 인스타그램 등)와 복잡한 네트워크 환경(동일 Wi-Fi, 공용 공유기)이 얽히면 백엔드 개발자가 마주하는 데이터는 종종 '누락'과 '왜곡'으로 얼룩지기 쉽습니다.

최근 관리자 대시보드 모니터링 과정에서 사용자 환경(UA)이 `Unknown`으로 대거 누락되고, 특정 모바일 유저의 세션이 무차별적으로 차단되는 현상을 발견했습니다. 이번 포스팅에서는 이 문제를 어떻게 정의하고, 어떤 아키텍처적 트레이드오프를 거쳐 해결했는지 공유합니다.

---

## 1. 마주한 문제 (Problem Definition)

서비스 고도화 과정에서 수집된 텔레메트리 데이터를 분석하던 중 두 가지 치명적인 문제가 보고되었습니다.

### ① 기기 환경 `Unknown / Other` 대량 발생
* **원인**: 온보딩 완료 및 전환 이벤트 발생 시, 내부 서비스 레이어로 `request` 객체의 메타데이터(User-Agent, IP, Device Type 등)를 누락한 채 `None`으로 적재하고 있었습니다.
* **추가 난제**: 카카오톡, 네이버, 인스타그램 등 국내 트래픽의 상당 부분을 차지하는 **인앱 브라우저** 및 최신 모바일 브라우저의 축소형·특수 User-Agent(UA) 패턴을 기존 파서가 식별하지 못해 대거 `Unknown` 처리되었습니다.

### ② 외부 모바일 접속 시 세션 데이터 누락 및 과도한 차단
* **동일 IP 다중 기기 오차단**: 기존 이벤트 로깅 로직은 '당일 동일 IP의 2번째 세션'을 무조건 중복(Duplicate)으로 판단하여 폐기했습니다. 이로 인해 같은 Wi-Fi 환경에서 PC로 접속 후 모바일로 접속한 사용자의 세션이 통째로 유실되었습니다.
* **관리자 IP 오판정**: `/admin` 경로에 접근한 시점만으로 모바일 LTE/5G 통신사의 동적 IP가 관리자 IP 목록에 자동 등록되어, 일반 유저의 정상적인 세션마저 `is_active = false`로 차단되는 치명적인 버그가 발생했습니다.
* **봇(Bot) 오인**: 웹뷰(WebView)나 PWA 환경의 15자 미만 짧은 UA 문자열이 무분별하게 봇 차단 로직에 걸려 드롭되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs & Architecture)

문제를 해결하기 위해 단순히 임시 예외 처리를 추가하는 대신, **데이터 수집 파이프라인의 전면적인 표준화와 방어 로직 설계**를 진행했습니다.

### 대안 1: 서드파티 애널리틱스 솔루션 도입 vs 자체 텔레메트리 고도화
* **서드파티 도입**: 개발 공수가 적으나, 내부 비즈니스 로직(온보딩 단계, 관리자 권한 연동 등)과의 실시간 결합이 어렵고 비용 발생.
* **자체 텔레메트리 고도화 (채택)**: FastAPI 백엔드와 프론트엔드 간의 컨텍스트 전달 체계를 직접 통제하여, 비즈니스 이벤트와 텔레메트리를 정밀하게 동기화하고 커스텀 파서를 최적화할 수 있음.

### 주요 설계 포인트

#### 1) 인앱 브라우저 대응 정밀 UA 파서 (`parse_user_agent`) 구현
국내 모바일 환경의 특수성을 고려해 카카오톡, 네이버, 인스타그램, 페이스북, 라인, 삼성 브라우저 등 15종 이상의 인앱 브라우저 시그니처를 명시적으로 매핑하고, 불완전한 UA에 대해서도 모바일 중심의 지능형 폴백(Fallback) 로직을 적용했습니다.

#### 2) 클라이언트 컨텍스트 표준화 (`extract_client_context`)
인증, 온보딩, 스캔 등 핵심 라우터 전반에서 분산되어 있던 메타데이터 추출 로직을 공통 유틸리티로 추상화했습니다. 이를 통해 단 한 줄의 코드로 `session_id`, `ip_address`, `device_type`, `os_name` 등을 완벽히 캡처하도록 보장했습니다.

#### 3) 복합 키 기반 세션 중복 검사로 전환
동일 IP 차단 문제를 해결하기 위해, 중복 판단 기준을 단순 IP 일치에서 **`(session_id, ip_address, device_type)` 복합 기준**으로 완화했습니다. 또한, 관리자 IP 자동 등록 조건 역시 단순 URL 접근이 아닌 **유효한 관리자 인증 토큰 쿠키가 검증된 경우**로 엄격하게 제한했습니다.

#### 4) 프론트엔드 2중 안전망 구축 (`initSessionTelemetry`)
모바일 PWA 환경이나 브라우저 캐시 정책 등으로 인해 백엔드 미들웨어가 간헐적으로 우회되는 상황을 방어하기 위해, 프론트엔드 진입 시점에 백엔드로 비동기 핑(Ping)을 발송하여 방문 기록이 100% 수집되도록 이중 안전망을 구축했습니다.

## 3. 검증 결과 및 배운 점 (Takeaways)

개선 사항을 프로덕션 환경에 배포하고 기존 적재 데이터를 대상으로 클린업을 수행한 결과, 다음과 같은 극적인 변화를 확인했습니다.

* **데이터 정합성 확보**: 기존 `visitors_events` 테이블의 `Unknown / Other` 비율이 **0%로 완전 소멸**하며, 모바일 OS 및 브라우저 환경이 100% 정확하게 분류되었습니다.
* **세션 유실 방지**: 동일 네트워크 내 다중 기기 사용자 및 모바일 접속 유저의 데이터가 누락 없이 정상 집계됨을 실시간 대시보드를 통해 검증했습니다.

### 💡 Engineering Takeaway
> *"텔레메트리 데이터는 비즈니스의 눈과 귀입니다. 백엔드 개발에서 클라이언트의 User-Agent나 IP를 다룰 때는 항상 '비정상적인 네트워크 환경'과 '국내 특화된 인앱 브라우저의 변칙성'을 염두에 두어야 합니다. 방어적인 세션 검증 로직과 표준화된 컨텍스트 추출 파이프라인이야말로 신뢰할 수 있는 대시보드를 만드는 뼈대입니다."*
