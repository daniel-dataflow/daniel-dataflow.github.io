제품의 성장을 가르는 가장 중요한 자산 중 하나는 **정확한 데이터**입니다. 특히 서비스 초기 단계에서는 사용자가 어떤 환경으로 유입되는지, 어디서 이탈하는지 파악하는 텔레메트리(Telemetry) 데이터가 프로덕트의 방향성을 결정합니다.

하지만 최근, 서비스 내 관리자 대시보드 분석 과정에서 **텔레메트리 왜곡 및 데이터 누락 현상**이 도마 위에 올랐습니다. 카카오톡, 네이버 등 국내 모바일 환경에서 유입된 사용자의 기기 정보가 `Unknown`으로 대거 누락되고, 동일 네트워크 환경(Wi-Fi)을 사용하는 모바일 유저들이 통째로 차단당하는 치명적인 버그였습니다.

이번 글에서는 해당 문제를 어떻게 진단했고, 백엔드와 프론트엔드 전반에 걸쳐 어떤 아키텍처적 개선과 트레이드오프(Trade-off)를 거쳐 해결했는지 공유하고자 합니다.

---

## 1. 마주한 문제 (Problem)

운영 중인 서비스의 방문자 분석 시스템에서 크게 두 가지 문제가 확인되었습니다.

### ① 기기 환경 `Unknown / Other` 대량 발생
온보딩(`onboarding_completed`, `onboarding_skipped`)이나 주요 전환 이벤트 발생 시, 백엔드 `request` 객체로부터 User-Agent(UA)와 IP, Device Type을 제대로 추출하지 못하고 `None`으로 적재하고 있었습니다. 
설상가상으로, 국내 사용자 유입의 대다수를 차지하는 **인앱 브라우저(카카오톡, 네이버, 인스타그램, 페이스북 등)** 및 최신 크롬 모바일의 축소형 UA에 대한 파서 식별력이 부족하여, 수집된 데이터의 상당수가 `Unknown`으로 버려지고 있었습니다.

### ② 외부 모바일 접속 시 기록 누락 및 과도한 차단
모바일 사용자 경험을 심각하게 해치는 로직상의 결함도 발견되었습니다.
* **동일 IP 다중 기기 과도 차단:** 기존 `log_analytics_event` 로직은 당일 동일 IP의 2번째 세션을 무조건 중복으로 판단하여 드랍했습니다. (예: 같은 Wi-Fi 환경에서 PC로 접속해 테스트한 뒤 모바일로 접속하면, 모바일 세션이 무조건 누락됨)
* **관리자 IP 오판정:** `/admin` 경로에 단순히 진입하기만 해도, 해당 모바일의 LTE/5G 통신사 IP가 관리자 IP 목록으로 자동 등록되어 `is_active = true`로 차단되는 버그가 발생했습니다.
* **짧은 UA 봇 오인:** 일부 웹뷰나 PWA 환경의 15자 미만 짧은 UA 문자열이 백엔드의 봇(Bot) 방어 로직에 걸려 차단되었습니다.

## 2. 기술적 고민과 아키텍처 대안 (Trade-offs)

문제를 해결하기 위해 단순히 파서 라이브러리를 교체하는 것을 넘어, **데이터 수집 파이프라인 전반의 신뢰성**을 높이는 방향으로 설계를 수정했습니다.

### 대안 1: 인앱 브라우저 및 모바일 정밀 파서 전면 고도화 (`parse_user_agent`)
* **고민:** 서드파티 UA 파서 라이브러리만으로는 국내 특유의 인앱 브라우저(`kakaotalk`, `naver`, `instagram`, `line` 등)를 세밀하게 잡아내기 어렵습니다.
* **선택:** 핵심 인앱 브라우저 15종 이상을 정밀 탐지하는 커스텀 정규식 기반의 폴백(Fallback) 로직을 파서 계층에 결합했습니다. 불완전한 UA가 들어오더라도 모바일 서비스 특성을 반영해 `Mobile`, `iOS`, `Android`로 안전하게 분류되도록 보장했습니다.

### 대안 2: 클라이언트 컨텍스트 추출 표준화 (`extract_client_context`)
* **고민:** 각 라우터(`auth.py`, `onboarding.py`, `scan.py` 등)마다 개별적으로 request를 파싱하다 보니 필드 누락이 빈번했습니다.
* **선택:** 공통 유틸리티 함수인 `extract_client_context`를 구현하여, 단 한 줄의 코드로 `session_id`, `ip_address`, `device_type`, `os_name`, `locale` 등을 일관되게 캡처하도록 표준화했습니다.

### 대안 3: 중복 세션 기준 완화 및 관리자 IP 등록 조건 강화
* **고민:** 보안을 강화하려다 정상적인 실사용자의 유입을 막는 부작용(False Positive)이 발생했습니다.
* **선택:** 
  * 중복 검사 기준을 기존 `IP 단일 기준`에서 **`(session_id, ip_address, device_type)` 복합 기준**으로 완화하여, 동일 공유기를 쓰는 다중 기기 환경을 보호했습니다.
  * 관리자 IP 자동 등록 조건에 **‘유효한 관리자 인증 토큰(`admin_token`) 쿠키 존재 여부’**를 필수로 추가하여 오인 차단을 원천 차단했습니다.

### 대안 4: 프론트엔드 텔레메트리 핑 2중 안전망 구축 (`/api/telemetry/ping` & `base.js`)
* **고민:** 모바일 PWA 환경이나 브라우저 뒤로가기 캐시(BFCache) 등으로 인해 백엔드 미들웨어가 텔레메트리 로직을 건너뛰는 예외 케이스가 존재했습니다.
* **선택:** 백엔드 수집에만 의존하지 않고, 프론트엔드(`base.js`)에서 화면 로드 시 당일 1회 백엔드로 비동기 핑(`initSessionTelemetry`)을 발송하는 **2중 안전망(Dual-layer safety net)**을 구축했습니다.

## 3. 검증 결과 및 Takeaway

개선 사항을 프로덕트에 반영한 직후, 기존 적재된 이벤트 데이터를 대상으로 클린업을 수행했습니다.

* **결과 1 (데이터 정밀도):** 기존 DB의 `visitors_events` 샘플 18건 전수 클린업 결과, `Unknown / Other` 비중이 **0건(완전 소멸)**으로 수렴했으며, 실사용자의 모바일 OS 및 브라우저 환경이 100% 정확하게 집계되는 것을 확인했습니다.
* **결과 2 (실시간 집계 안정성):** 실시간 당일 집계 API (`get_realtime_today_summary`)에서 디바이스 및 OS 브레이크다운이 누락 없이 정상 출력되었습니다.

### 💡 엔지니어링 교훈 (Takeaways)

1. **보안과 비즈니스 로직의 균형 (False Positive 경계):** 보안을 강화하는 과정(`is_active` 차단, 봇 필터링)에서 정상적인 사용자 유입 데이터가 손실되고 있지 않은지 항상 모니터링해야 합니다. 
2. **단일 진입점(Single Point of Entry)의 중요성:** 클라이언트 컨텍스트(UA, IP 등)를 수집하는 로직이 여러 라우터에 흩어져 있으면 휴먼 에러가 발생하기 쉽습니다. 공통화된 헬퍼 함수와 미들웨어 패턴을 통해 파이프라인의 일관성을 유지해야 합니다.
3. **프론트-백엔드 2중 안전망:** 네트워크 환경이 불안정한 모바일 웹/PWA 환경에서는 백엔드 로그 수집에만 의존하기보다, 프론트엔드 레벨의 핑(Ping) 메커니즘을 함께 설계하는 것이 데이터 유실을 막는 가장 확실한 방법입니다.
