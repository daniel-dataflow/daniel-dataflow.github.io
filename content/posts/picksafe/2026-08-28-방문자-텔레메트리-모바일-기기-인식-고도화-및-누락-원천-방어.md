안녕하세요, PickSafe 백엔드 에디터입니다. 

서비스가 성장함에 따라 가장 먼저 마주하는 난관 중 하나는 **"데이터의 신뢰성"**입니다. 대시보드에 찍히는 숫자가 실제 사용자의 행동과 다를 때, 비즈니스 의사결정은 흔들릴 수밖에 없습니다.

최근 우리 팀은 관리자 대시보드의 방문자 텔레메트리(Telemetry) 데이터에서 **모바일 기기 환경이 `Unknown / Other`로 대거 누락되거나, 동일 Wi-Fi/통신사 환경에서 실제 유저의 세션이 과도하게 차단되는 현상**을 발견했습니다. 

이번 포스팅에서는 이 문제를 어떻게 정의하고, 어떤 아키텍처적 Trade-off를 거쳐 해결했는지 공유해 드립니다.

---

## 1. Problem: 무엇이 문제였는가?

대시보드 모니터링 중 다음 두 가지 치명적인 텔레메트리 왜곡 현상이 보고되었습니다.

### ① 기기 환경의 블랙박스화 (`Unknown / Other` 대량 발생)
온보딩 완료(`onboarding_completed`), 전환(`guest_converted`) 등의 주요 비즈니스 이벤트 발생 시, 백엔드 로깅 레이어에서 `request` 객체로부터 User-Agent, IP, Device Type을 누락하고 `None`으로 적재하고 있었습니다. 
설상가상으로, 국내 모바일 환경의 특성인 **다양한 인앱 브라우저(카카오톡, 네이버, 인스타그램, 페이스북 등)**와 최신 모바일 크롬의 축소형 User-Agent(UA)를 기존 단순 파서로는 식별하지 못해 데이터가 `Unknown`으로 공중분해되고 있었습니다.

### ② 외부 모바일 접속자의 '억울한' 세션 누락
* **동일 IP 다중 기기 과도 차단:** 백엔드 분석 로직이 '당일 동일 IP의 2번째 세션'을 무조건 중복(Duplicate)으로 판단하여 드롭하고 있었습니다. (예: 같은 Wi-Fi 환경에서 PC로 접속해 테스트를 하다가 모바일로 접속하면, 모바일 세션이 무참히 버려짐)
* **관리자 IP 오판정:** 사용자가 단순히 `/admin` 경로를 브라우저에 입력해 진입 시도만 해도, 해당 모바일의 LTE/5G 통신사 IP가 관리자 IP 목록에 자동 등록되어 일반 방문자 집계에서 차단되는 치명적인 버그가 있었습니다.
* **짧은 UA 봇 오인:** 웹뷰나 PWA 환경의 15자 미만 짧은 UA 문자열이 백엔드의 봇(Bot) 방어 로직에 걸려 차단되었습니다.

---

## 2. Solution: 기술적 고민과 아키텍처 대안

문제를 해결하기 위해 백엔드와 프론트엔드 전반에 걸친 파이프라인 개편을 단행했습니다.

### 2.1 인앱 브라우저 및 모바일 정밀 파서 (`parse_user_agent`) 고도화
단순 문자열 매칭을 넘어, 국내 서비스 환경에 특화된 파싱 로직을 도입했습니다.
* 카카오톡, 네이버, 인스타그램, 페이스북, 라인, 삼성 브라우저 등 **15종 이상의 모바일 인앱 브라우저 패턴**을 정밀하게 탐지하여 `Mobile`, `iOS`, `Android`로 정확히 분류하도록 개선했습니다.
* 비어 있거나 불완전한 UA에 대해서도 모바일 서비스의 특성을 반영한 **지능형 폴백(Fall-back) 전략**을 적용하여 데이터 유실률을 0%에 가깝게 낮췄습니다.

### 2.2 클라이언트 컨텍스트 추출 표준화 (`extract_client_context`)
각 라우터마다 제각각이던 메타데이터 수집 방식을 중앙화했습니다.
* 인증(`auth`), 온보딩(`onboarding`), 스캔(`scan`) 등 주요 라우터에서 단 한 줄의 함수 호출로 `session_id`, `ip_address`, `device_type`, `os_name`, `locale` 등을 완벽히 캡처하도록 표준화 하였습니다.

### 2.3 비즈니스 로직 및 세션 검증 기준 완화 (Trade-off)
보안성과 가용성 사이의 균형(Trade-off)을 맞추었습니다.
* **복합 키 기반 세션 허용:** 동일 IP라 할지라도 `session_id` 또는 `device_type`이 다르면 명백히 다른 디바이스로 간주하도록 중복 검사 기준을 `(session_id, ip_address, device_type)` 복합 키로 확장했습니다.
* **엄격한 관리자 인증 조건:** 단순히 `/admin` URL을 호출했다고 IP를 등록하는 것이 아니라, **유효한 관리자 인증 토큰(`admin_token`) 쿠키가 실제로 존재하는 경우에만** 관리자 IP로 등록되도록 보안 방어를 강화했습니다.

### 2.4 프론트엔드 텔레메트리 핑 2중 안전망 구축
모바일 PWA 환경이나 브라우저 뒤로가기 캐시(BFcache) 등으로 인해 백엔드 미들웨어가 간혹 이벤트를 놓치는 상황을 방어하기 위해, 프론트엔드 단에 안전망을 구축했습니다.
* 화면 로드 시 백엔드로 비동기 핑(`/api/telemetry/ping`)을 발송하는 `initSessionTelemetry()`를 구현하여, 실사용자 방문이 네트워크 환경과 관계없이 100% 집계되도록 보장했습니다.

## 3. Takeaway: 무엇을 배웠는가?

개선 작업 직후 기존 적재된 이벤트 데이터를 전수 클린업(Cleanup)하고 실시간 집계 API를 검증한 결과, **`Unknown / Other` 비율이 정확히 0%**로 수렴하는 것을 확인했습니다.

이번 작업을 통해 얻은 엔지니어링 교훈은 명확합니다.
1. **데이터의 신뢰성은 수집 단의 엄격함에서 시작된다:** 로깅을 비즈니스 로직의 '부수적인 부산물'이 아니라, '핵심 퍼스트 클래스 데이터'로 다루어야 합니다.
2. **모바일 환경은 데스크톱의 표준을 따르지 않는다:** 인앱 브라우저, 웹뷰, PWA 등 모바일 특유의 파편화된 환경을 고려하지 않은 보안/분석 로직은 결국 선량한 유저의 데이터를 버리게 됩니다.

앞으로도 PickSafe 팀은 작은 데이터 조각 하나 놓치지 않는 견고한 아키텍처를 만들어 나가겠습니다.
