안녕하세요. 백엔드 및 아키텍처를 담당하고 있는 시니어 엔지니어입니다.

최근 프로덕션 환경의 관리자 대시보드를 모니터링하던 중, 방문자 텔레메트리 데이터에서 **'기기 환경 Unknown 대량 발생'**과 **'외부 모바일 접속 시 세션 누락'**이라는 두 가지 치명적인 지표 왜곡 현상을 발견했습니다. 

비즈니스의 성장을 트래킹하고 사용자 경험을 분석하는 핵심 데이터에 구멍이 생긴 것입니다. 본 포스팅에서는 이 문제를 어떻게 정의하고, 어떤 아키텍처적 트레이드오프를 거쳐 해결했는지 공유해 드리고자 합니다.

---

## 1. 마주한 문제 (Problem)

운영 중인 서비스의 방문자 분석 시스템에서 다음과 같은 두 가지 뚜렷한 병목이자 오류가 발생하고 있었습니다.

### ① 모바일 환경 및 인앱 브라우저의 'Unknown' 처리
온보딩 완료, 전환 이벤트 등의 세부 텔레메트리 적재 시, `request` 객체로부터 User-Agent나 IP 등의 컨텍스트를 누락한 채 `None`으로 처리하는 경우가 있었습니다. 
더불어, 카카오톡, 네이버, 인스타그램 등 국내 사용자들이 빈번하게 사용하는 **인앱 브라우저(In-App Browser)**와 축소형 UA(User-Agent) 문자열을 기존 파서가 식별하지 못해 대다수의 모바일 유입이 `Unknown / Other`로 버려지고 있었습니다.

### ② 외부 모바일 접속 시 세션 누락 및 과도한 차단
* **동일 IP 다중 기기 과도 차단:** 기존 로직은 '당일 동일 IP의 2번째 세션'을 무조건 중복(Duplicate)으로 판단하여 버렸습니다. 이로 인해 동일 Wi-Fi 환경에서 PC로 테스트 후 모바일로 접속한 경우, 모바일 세션이 통째로 유실되었습니다.
* **관리자 IP 오판정:** `/admin` 경로에 단순히 접근을 시도한 것만으로도, 모바일 LTE/5G 통신사의 동적 IP가 관리자 IP 목록에 자동 등록되어 일반 사용자 세션까지 차단되는 보안 역설이 발생했습니다.
* **짧은 UA 봇 오인:** 일부 PWA 및 웹뷰 환경의 15자 미만 짧은 UA 스트링이 안티봇 로직에 걸려 차단되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 아키텍처 전반에 걸쳐 아래와 같은 기술적 의사결정을 내렸습니다.

### 대안 A: 서드파티 상용 텔레메트리 솔루션 도입 (예: Google Analytics, Amplitude 등)
* **장점:** 개발 공수가 매우 적고, 정교한 디바이스 파싱 기능을 기본 제공함.
* **단점:** 내부 비즈니스 로직(관리자 IP 판정, 온보딩 퍼널 추적 등)과 실시간 연동 시 커스텀 제약이 크고, 데이터 주권 및 비용 문제 발생.
* **결론:** ** 자체 텔레메트리 파이프라인 고도화** 선택. 당사의 온프레미스/클라우드 하이브리드 인프라에서 완벽한 데이터 제어권을 가지는 것이 중요하다고 판단했습니다.

### 대안 B: 백엔드 미들웨어 중심의 컨텍스트 추출 표준화 및 파서 리팩토링
* **장점:** 모든 라우터(`auth`, `onboarding`, `telemetry` 등)에서 일관된 메타데이터를 보장할 수 있음.
* **단점:** 기존 레거시 이벤트 로깅 코드를 전면 수정해야 하므로 일시적인 휴먼 에러 리스크 존재.
* **결론:** 공통 유틸리티 함수(`extract_client_context`)를 구현하여 각 라우터에 일관되게 주입하는 방식을 채택했습니다.

## 3. 최종 해결 및 구현 (Solution)

### 3.1 인앱 브라우저 및 모바일 정밀 파서 (`parse_user_agent`) 고도화
국내 모바일 환경의 특수성을 반영하여, 카카오톡, 네이버, 인스타그램, 페이스북, 라인, 삼성 브라우저 등 15종 이상의 인앱 브라우저그니처를 정밀 탐지하도록 파서를 전면 재작성했습니다. 불완전한 UA에 대해서도 지능형 폴백(Fallback)을 적용하여 `Unknown` 발생 확률을 원천 차단했습니다.

### 3.2 복합 기준 세션 중복 검사 도입
기존의 `IP 단일 기준`에서 벗어나, 아래와 같이 중복 검사 기준을 세분화했습니다.
* **변경 전:** `IP` 기준 단일 체크 (동일 IP = 중복)
* **변경 후:** `(session_id, ip_address, device_type)` 복합 기준 적용. 동일 IP라도 세션 ID나 디바이스 타입이 다르면 독립된 실사용자로 정상 집계합니다.

### 3.3 엄격한 관리자 IP 인증 로직 분리
단순 URL 라우팅 체크(`path.startswith('/admin')`)를 제거하고, **유효한 관리자 인증 토큰 쿠키가 실제로 존재하는 경우에만** 관리자 IP로 등록되도록 보안 로직을 강화했습니다. 이를 통해 일반 모바일 사용자가 관리자 IP로 오인되어 차단되는 문제를 해결했습니다.

### 3.4 프론트엔드 2중 안전망 구축 (`initSessionTelemetry`)
네트워크 미들웨어가 캐시나 PWA 특성상 간헐적으로 누락될 수 있는 지점을 보완하기 위해, 프론트엔드(`base.js`)에서 화면 로드 시 백엔드로 가벼운 핑을 보내는 2중 안전망을 구축했습니다.

## 4. 검증 결과 및 배운 점 (Takeaway)

개선 사항을 프로덕션에 배포한 후 기존 DB의 이벤트 데이터를 전수 클린업한 결과는 매우 고무적이었다.

1. **데이터 정합성 확보:** 기존 `visitors_events` 테이블의 `Unknown / Other` 비율이 **0%**로 완전히 수렴했습니다.
2. **실시간 집계 정확도 향상:** 모바일과 데스크톱의 디바이스, OS, 로케일별 트래픽이 유실 없이 정확하게 대시보드에 렌더링되기 시작했습니다.

> **💡 엔지니어링 교훈:**
> "텔레메트리(Telemetry) 데이터는 비즈니스의 눈과 귀입니다. 인프라나 백엔드 로직이 완벽하더라도, 클라이언트의 다양성(인앱 브라우저, 동적 IP, 모바일 네트워크 환경)을 고려하지 않은 수집 로직은 결국 허황된 지표를 낳습니다. 시스템을 설계할 때는 항상 '가장 거칠고 예외적인 클라이언트 환경'을 기준으로 예외 처리를 견고하게 다져야 한다는 것을 다시 한번 깨달았습니다."
