안녕하세요, PickSafe 팀의 백엔드 엔지니어입니다.

PickSafe 서비스의 핵심 가치는 사용자에게 '정확하고 안전한 화장품 성분 정보'를 신속하게 전달하는 데 있습니다. 이를 위해 우리 팀은 정기적으로 식약처 공공데이터 포털 OpenAPI로부터 수만 건에 달하는 국내외 화장품 전성분 데이터를 수집하고 동기화하는 배치 파이프라인을 운영하고 있습니다.

하지만 데이터의 규모가 커지고 외부 API와의 연동이 빈번해지면서, 초기 아키텍처에서는 예상치 못한 **인프라 병목과 안정성 이슈**가 발생하기 시작했습니다. 

이번 포스팅에서는 대용량 데이터를 동기화하는 과정에서 마주했던 **세 가지 기술적 난제(디스크 초과, 커넥션 누수, CPU 스파이크)**를 정의하고, 한정된 자원 속에서 이를 어떻게 우아하게 해결했는지(Trade-off), 그리고 이 과정에서 얻은 엔지니어링적 교훈을 공유하고자 합니다.

---

## 1. 문제 상황: 안정적인 데이터 수집을 가로막는 세 가지 벽

수만 건의 성분 데이터를 배치 시스템으로 마이그레이션하는 과정에서 서비스 전체의 생존을 위협하는 세 가지 징후가 감지되었습니다.

### ① 디스크 용량의 급격한 잠식 (Disk Full Alert)
대용량 데이터를 루프를 돌며 수집하다 보니, 디버깅과 이력 추적을 위해 남겨둔 로그 파일의 크기가 며칠 사이에 수십 GB 단위로 치솟았습니다. 별도의 로그 제한 정책이 없다 보니 단일 파일에 계속해서 로그가 누적되었고, 결국 서버 디스크 사용량 초과 경고가 발생했습니다.

### ② 간헐적 네트워크 지연으로 인한 DB 커넥션 고갈 (Connection Leak)
공공데이터 포털 API는 간헐적으로 응답이 지연되거나 네트워크 타임아웃을 발생시킵니다. 이때 수집 프로세스가 대기 상태에 빠지면서, 이미 선점한 데이터베이스 세션이 정상적으로 반환되지 않고 `idle in transaction` 상태로 묶이는 현상이 발생했습니다. 이는 배치가 실행되는 동안 실시간 서비스용 DB 커넥션까지 말라버리는 심각한 장애로 이어졌습니다.

### ③ 실시간 로그 조회 시 발생하는 서버 CPU 스파이크 (OOM 및 CPU 과부하)
어드민 페이지에서는 관리자가 수집 작업이 잘 진행되고 있는지 실시간으로 모니터링할 수 있는 로그 뷰어 기능을 제공하고 있었습니다. 하지만 웹 클라이언트가 "실시간 로그 조회 API"를 지속적으로 폴링(Polling)할 때마다, 서버는 이미 수백 MB를 넘어선 대용량 로그 파일 전체를 매번 메모리에 로드하여 읽어 들였습니다. 이로 인해 서버 CPU 점유율이 100%에 달하는 스파이크 현상이 주기적으로 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 단순히 서버의 스펙을 올리는(Scale-up) 임시방편 대신, **지속 가능하고 비용 효율적인 아키텍처적 해결책**을 찾기로 했습니다.

### 고민 1. 로그 관리: ELK 스택 도입 vs. 경량 로그 로테이션
* **대안 A (ELK/Loki 도입):** Elasticsearch나 Grafana Loki 같은 중앙 집중형 로그 시스템을 구축하는 방안. 검색과 시각화는 훌륭하지만, 배치용 로그 조회를 위해 추가적인 인프라 비용과 관리 공수가 너무 컸습니다.
* **대안 B (RotatingHandler + Stream Tail):** 애플리케이션 레벨에서 로그 크기를 제한하고, 파일의 가장 최근 버퍼(Tail)만 읽어 응답하는 방식. 추가 비용이 전혀 없고 구현이 매우 단순합니다.
* **결정:** **대안 B 선택.** 서비스 규모와 비용 대비 효과를 고려해, 무거운 인프라 도입 대신 로컬의 `RotatingFileHandler`를 설정하고 어드민 조회 시 꼬리 부분(Tail 500줄)만 스트리밍으로 읽어 응답하는 구조를 선택했습니다.

### 고민 2. 커넥션 누수 방어: DB 세션 풀 확장 vs. 안전한 회수 가드(Safe Teardown)
* **대안 A (DB 세션 풀 늘리기):** 커넥션 개수 자체를 늘려 대기 시간을 벌어주는 방식. 그러나 이는 근본적인 누수 원인을 해결하지 못하며, 언젠가 임계치를 넘으면 DB 자체가 다운되는 문제를 안고 있습니다.
* **대안 B (Safe Teardown & Timeout 가드):** 코드 레벨에서 명시적으로 트랜잭션 수명을 보장하고, 외부 HTTP 요청에 명확한 타임아웃과 백off 재시도 메커니즘을 두어 안전하게 커넥션을 회수하는 방식.
* **결정:** **대안 B 선택.** 견고한 예외 처리(`try ... except ... finally`)를 통해 어떤 예외 상황에서도 DB 커넥션이 무조건 풀(Pool)로 반환되도록 강제하는 안전장치를 마련했습니다.

### 고민 3. DB 쓰기 부하: 단일 DB 처리 vs. 메인/DW 이중화 격리
* **대안 A (단일 메인 테이블 쓰기):** 수집된 원본 raw 데이터와 분석 로그를 서비스 운영 데이터베이스에 직접 인서트하는 방식. 구조는 단순하지만, 대량의 쓰기 작업이 일어나는 동안 사용자 조회 쿼리 성능이 극도로 저하됩니다.
* **대안 B (데이터웨어하우스(DW) 성격의 테이블 분리):** 원본 적재 및 작업 이력 로그는 메인 서비스 테이블과 물리적/논리적으로 격리된 보조 테이블(DW성 테이블)에 먼저 적재하고, 가공된 최종 데이터만 메인 테이블에 반영하는 방식.
* **결정:** **대안 B 선택.** 대용량 수집 쓰기 부하가 사용자 서비스(OLTP) 성능에 영향을 미치지 않도록 이중화 격리 구조를 택했습니다.

## 3. 최종 아키텍처 및 구현 설계

이 세 가지 결정을 바탕으로 완성한 안정화 수집 파이프라인의 구조는 다음과 같습니다.

```
+─────────────────────────────────────────────────────────────+
│ [1. 로그 가드 및 스트리밍]                                   │
│  - RotatingFileHandler (Max 5MB, Backup 3개 제한)            │
│  - 어드민 폴링 요청 시 Tail 500줄만 읽어 메모리 절약         │
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
│ [2. 세션 수명 제어 (Safe Teardown)]                          │
│  - 외부 OpenAPI 호출 시 Strict Timeout (10초) 설정          │
│  - try ... except ... finally 구문으로 세션 명시적 close    │
+─────────────────────────────────────────────────────────────+
                               │
                               ▼
+─────────────────────────────────────────────────────────────+
│ [3. 데이터 적재 이중화 및 격리]                             │
│  - 실시간 서비스용 테이블 (Main DB) 영향도 제로             │
│  - 대용량 원본 데이터 및 수집 로그는 별도 보조 DB/테이블 적재  │
+─────────────────────────────────────────────────────────────+
```

### 주요 구현 포인트

1. **로그 로테이션 적용**:
   로그 파일 크기가 최대 5MB를 초과하지 않도록 설정하고, 최대 3개의 백업 파일만 유지하여 디스크 공간 점유율을 상한선 내로 제어했습니다. 동시에 실시간 로그 뷰어 API는 파일 전체가 아닌 최근 500줄만 추출하는 스트리밍 로직을 적용했습니다.

2. **철저한 예외 회수 처리 (Safe Teardown)**:
   데이터 수집 함수의 생명 주기를 확실히 제어했습니다. 외부 통신 장애가 발생해도 커넥션이 영원히 물려있지 않도록 10초의 제한 시간을 부여하고, 백오프(Backoff) 알고리즘을 통한 재시도를 수행한 뒤 최종 실패 시에도 `finally` 블록을 통해 커넥션을 확실하게 닫았습니다.

3. **이력 관리 고도화**:
   수집 작업의 실행 주기마다 실제 소요 시간(Duration)을 측정하고 상태(Success/Fail)를 가벼운 메타 데이터로 보조 테이블에 기록하도록 하여, 향후 성능 튜닝 및 장애 복구를 위한 가시성을 확보했습니다.

## 4. 결과 및 엔지니어링 교훈 (Takeaways)

### 눈으로 확인한 성과
* **중단 없는 배치 수집 성공**: 식약처 30,000+건의 대용량 성분 데이터를 수집·가공하는 과정에서 단 한 번의 커넥션 누수나 서버 중단 없이 **100% 안정적으로 수집을 완주**했습니다.
* **서버 자원 소모 극적 절감**: 실시간 로그 모니터링 시 발생하던 메모리 점유율과 CPU 스파이크를 **90% 이상 절감**했습니다. 무분별한 파일 전체 읽기(Full Read)를 막음으로써 얻은 쾌거입니다.
* **디스크 오버플로우 원천 차단**: 아무리 많은 수집 배치가 돌아도 로컬 디스크 내 수집 로그 점유 공간은 항상 안전 범위 내로 제한되었습니다.

### 이 프로젝트를 통해 배운 교훈

1. **해제(Teardown)는 작성(Write)만큼 중요하다**
   기능 개발 단계에서는 '어떻게 데이터를 가져올 것인가'에만 집중하기 쉽습니다. 하지만 프로덕션 환경에서의 안정성은 '에러가 발생했을 때 어떻게 안전하게 자원을 반환할 것인가'에서 결정된다는 것을 뼈저리게 배웠습니다.

2. **적정 기술(Pragmatic Architecture)의 가치**
   만약 우리가 처음에 문제를 해결하기 위해 거대한 ELK 스택이나 별도의 분산 메시지 큐를 무조건 도입했다면, 배보다 배꼽이 더 큰 인프라 비용과 유지 보수 비용을 치렀을 것입니다. 우리 서비스의 현재 규모에 맞는 적절한 가성비 기술(Log Rotation + Tail stream)을 선택하여 빠르고 안정적인 비즈니스 가치를 창출할 수 있었습니다.

앞으로도 PickSafe 팀은 사용자에게 안정적인 서비스를 제공하기 위해 백엔드 시스템의 보이지 않는 곳까지 꼼꼼하게 다듬고 발전시켜 나갈 것입니다. 긴 글 읽어주셔서 감사합니다.
