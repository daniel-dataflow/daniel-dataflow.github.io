외부 공공데이터 API를 연동하여 대량의 데이터를 수집하는 작업은 보기보다 까다롭습니다. 네트워크 상태는 언제나 가변적이고, 외부 서버의 응답 지연은 우리 시스템의 앙상블로 전이되기 쉽습니다.

최근 **PickSafe** 팀에서는 식약처 공공데이터 포털로부터 30,000건 이상의 화장품 전성분 데이터를 안정적으로 동기화하는 엔지니어링 과제를 수행했습니다. 이 과정에서 발생했던 **디스크 낭비, DB 커넥션 고갈, CPU 스파이크**라는 세 가지 인프라 병목을 어떻게 정의하고 해결했는지 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

초기 데이터 수집 배치(Batch) 파이프라인 구축 후, 대규모 동기화를 테스트하는 과정에서 3가지 심각한 장애 징후가 포착되었습니다.

```
[외부 API] ──(타임아웃 발생)──> [수집 서버]
                                  │
                                  ├─ 1. DB 세션 미반환 (idle in transaction) ➔ 커넥션 풀 고갈
                                  ├─ 2. 디스크에 무제한 로그 누적 ➔ 서버 디스크 초과 위험
                                  └─ 3. 어드민 로그 폴링시 전체 로딩 ➔ CPU/RAM 스파이크
```

1. **로그 파일 폭증으로 인한 디스크 초과 위험**: 상세 디버깅을 위해 남겨둔 수집 로그가 단일 파일에 무제한으로 쌓여, 수집 횟수가 늘어남에 따라 디스크 가용 용량이 급격히 줄어들었습니다.
2. **외부 API 지연 시 DB 커넥션 누수**: 외부 API 호출 시 간헐적으로 네트워크 타임아웃이 발생했는데, 이때 DB 세션이 정상 닫히지 않고 `idle in transaction` 상태로 유실되어 커넥션 풀(Connection Pool)이 순식간에 고갈되었습니다.
3. **실시간 모니터링 시 CPU 스파이크**: 관리자 페이지에서 현재 수집 상태를 확인하기 위해 수집 로그 파일 전체를 메모리로 읽어와 읽어주는 구조여서, 모니터링 요청 시마다 서버 CPU/메모리가 급증했습니다.

## 2. 기술적 고민과 대안 비교 (Engineering Trade-offs)

### 고민 1. 로그 로테이션 및 실시간 스트리밍 읽기

대용량 로그 관리에는 보통 **ELK 스택(Elasticsearch + Logstash + Kibana)**이나 **Loki** 같은 Centralized Logging 시스템이 권장됩니다. 

* **대안 A: ELK / Loki 등 중앙 집중형 로그 시스템 도입**
  * *장점*: 로그 분석 및 대시보드 구축 용이.
  * *단점*: 현재 단일 수집 파이프라인의 로그 문제를 해결하기에는 과도한 인프라 공수(Over-engineering) 및 운영 비용 발생.
* **대안 B: Standard Library 로그 로테이션 + Tail 방식의 파일 뷰어 (선택)**
  * *장점*: 별도 인프라 추가 없이 Python의 `RotatingFileHandler`만으로 디스크 점유율을 제어 가능. 어드민 모니터링 시 파일 전체가 아닌 **최신 N줄(Tail)**만 `seek()`로 읽어 메모리 효율 극대화.
  * *단점*: 복잡한 로그 분석 검색에는 한계가 있으나, 현재 서비스 요구사항에 완벽히 부합.

#### [적용 예시: 메모리 효율적인 Tail 방식 읽기 구현]
```python
# 보안을 위해 비즈니스 로직 및 세부 경로는 추상화되었습니다.
import os

def read_log_tail(file_path: str, lines_to_read: int = 500, buffer_size: int = 1024):
    """
    대용량 파일 전체를 메모리에 올리지 않고,
    파일의 끝(Tail)부터 역방향으로 읽어 지정된 줄 수만 반환합니다.
    """
    if not os.path.exists(file_path):
        return []
    
    with open(file_path, "rb") as f:
        f.seek(0, os.SEEK_END)
        file_size = f.tell()
        buffer = bytearray()
        pointer = file_size
        lines_found = 0

        while pointer > 0 and lines_found <= lines_to_read:
            read_size = min(buffer_size, pointer)
            pointer -= read_size
            f.seek(pointer)
            chunk = f.read(read_size)
            buffer[0:0] = chunk
            lines_found = buffer.count(b'\n')

        lines = buffer.decode('utf-8', errors='ignore').splitlines()
        return lines[-lines_to_read:]
```

### 고민 2. 외부 네트워크 타임아웃 대응 및 DB Connection Safe Teardown

외부 API 요청과 DB 트랜잭션이 한 함수 내에 강하게 결합되어 있을 때, 네트워크 타임아웃은 커넥션 누수의 주범이 됩니다.

```python
# ❌ [개선 전] 외부 API 타임아웃 발생 시 db.close()에 도달하지 못해 커넥션 누수 발생
def collect_data(db: Session):
    data = fetch_external_api() # 여기서 Timeout 예외 발생 시 세션 반환 안 됨!
    db.add(data)
    db.commit()
    db.close()
```

* **해결 방안: Context Manager 패턴과 Safe Teardown 보장**
  1. 외부 API 호출에는 반드시 **명시적 타임아웃(예: 10초)**과 지수 백오프(Exponential Backoff) 재시도 로직을 적용.
  2. DB 세션 관리는 `try ... except ... finally` 또는 Python의 Context Manager로 감싸, 어떤 예외(Network Exception, Parsing Error)가 발생해도 `finally` 블록에서 **Rollback 및 Session Close가 100% 보장**되도록 구조 변경.

```python
# ✅ [개선 후] Safe Teardown을 보장하는 Context Manager 패턴
from contextlib import contextmanager

@contextmanager
def safe_db_session():
    session = SessionLocal()
    try:
        yield session
        session.commit()
    except Exception as e:
        session.rollback()
        logger.error(f"Collection failed, transaction rolled back: {e}")
        raise
    finally:
        session.close()  # 커넥션 풀로 안전하게 반환
```

### 고민 3. 운영 DB(Main OLTP)와 수집/DW 테이블의 격리

수집 과정에서 발생하는 대량의 Raw Data 조작 및 작업 로그(Job Log)가 운영 중인 메인 사용자 DB 성능에 영향을 주지 않도록, 데이터 적재 레이어를 물리적/논리적으로 격리했습니다.

* 수집 실행 이력 및 원본 Raw 데이터를 저장하는 테이블을 **DW(Data Warehouse) 영역으로 분리**하여 적재.
* 각 수집 작업의 시작 시간, 종료 시간, **실제 소요 시간(Duration)**을 측정하여 추후 API 성능 저하 추이를 추적할 수 있는 메트릭 기반 제공.

## 3. 해결 및 성과 (Impact & Results)

이번 아키텍처 개선을 통해 얻은 정량적·정성적 성과는 다음과 같습니다.

* **30,000+건 대용량 데이터 수집 안정성 확보**: 수집 중 발생하던 간헐적 외부 네트워크 단절 상황에서도 DB 세션 누수 없이 **100% 무중단 완주**를 달성했습니다.
* **메모리 점유율 90% 이상 절감**: 관리자 페이지의 실시간 로그 폴링 시 전체 로그 파일(수십 MB 이상)을 읽는 대신 Tail 방식(최신 500줄) 스트리밍 기법을 도입하여 어드민 API 메모리 사용량을 절반 이하로 감소시켰습니다.
* **디스크 관리 자동화**: `RotatingFileHandler`(최대 5MB, 백업 파일 3개 유지) 적용으로 로그 파일 폭증으로 인한 서버 다운 가능성을 근본적으로 제거했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

1. **외부 서비스는 언제든 실패할 수 있다 (Zero Trust Network)**: 외부 API 연동 시 타임아웃과 방어적 예외 처리(Safe Teardown)는 선택이 아닌 필수입니다. DB 트랜잭션과 외부 HTTP 요청의 수명을 엄격히 분리해야 합니다.
2. **모니터링 유틸리티의 부하를 간과하지 말 것**: 시스템을 관찰하기 위해 만든 모니터링 기능(로그 조회 등)이 정작 시스템 본체의 성능을 갉아먹는 주범이 될 수 있습니다. 
3. **적절한 기술 스택의 선택**: 당장 무거운 중앙 집중형 로그 서버를 구축하기보다, 현재 상황에서 가장 간단하고 직관적인 `Standard Rotator + Stream Tail` 조합을 선택함으로써 빠르게 문제를 해결하고 제품 가치를 전달할 수 있었습니다.
