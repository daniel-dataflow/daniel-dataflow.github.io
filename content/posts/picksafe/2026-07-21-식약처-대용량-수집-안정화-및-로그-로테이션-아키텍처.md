안녕하세요, PickSafe 개발 팀입니다. 

PickSafe 서비스의 핵심 경쟁력 중 하나는 사용자가 신뢰할 수 있는 정확하고 방대한 화장품 성분 데이터를 실시간에 가깝게 제공하는 것입니다. 이를 위해 저희 팀은 식약처 공공데이터 포털 등 다양한 외부 OpenAPI로부터 수만 건에 달하는 전성분 데이터를 주기적으로 수집하고 동기화하는 파이프라인을 운영하고 있습니다.

하지만 배치(Batch) 단위의 대용량 데이터 수집 과정은 네트워크 지연, 인프라 리소스 한계 등 다양한 변수를 동반합니다. 최근 수집 프로세스 운영 중 **디스크 용량 급증, 데이터베이스 커넥션 고갈, 실시간 모니터링 시 CPU 과부하**라는 삼중고를 겪었습니다. 

본 포스팅에서는 저희가 이 세 가지 문제를 어떻게 기술적으로 정의하고, 어떤 트레이드오프를 거쳐 아키텍처를 개선했는지 그 여정을 공유하고자 합니다.

## 1. 문제 정의 (Problem)

수집 데몬이 작동하면서 발생한 병목과 장애 징후는 크게 세 가지 영역에서 나타났습니다.

```
[외부 API 서버] ──(간헐적 타임아웃)──> [수집 서버 (FastAPI)] ──(로그 누적)──> [서버 디스크 풀]
                                              │
                                       (커넥션 미반환)
                                              ▼
                                      [운영 DB (PostgreSQL)] -> idle in transaction 발생
```

### ① 디스크 용량 급증 (Log Explosion)
수집 프로세스는 상세한 추적을 위해 다량의 디버그(Debug) 로그를 남깁니다. 수만 건의 데이터를 처리하다 보니 단 한 번의 수집 주기(Run)만으로도 수십 기가바이트(GB)에 달하는 단일 대용량 로그 파일이 생성되었고, 이로 인해 서버 디스크 사용량이 임계치를 초과하는 경보(Alert)가 수시로 발생했습니다.

### ② 네트워크 단절로 인한 DB 커넥션 고갈 (Connection Leak)
외부 OpenAPI 호출 시 간헐적인 네트워크 타임아웃이나 세션 끊김 현상이 발생했습니다. 이때 예외 처리(Exception Handling)가 미흡하여, 트랜잭션이 열린 상태로 데이터베이스 세션이 반환되지 않고 `idle in transaction` 상태로 커넥션 풀을 점유하는 현상이 발생했습니다. 결과적으로 다음 수집 주기나 실시간 사용자 요청을 처리할 DB 커넥션이 고갈되었습니다.

### ③ 실시간 로그 모니터링 시 CPU 스파이크 (I/O Bottleneck)
관리자 페이지에서 "현재 수집이 잘 되고 있는가?"를 모니터링하기 위해 수집 로그 파일을 실시간 웹 소켓이나 폴링(Polling) 방식으로 조회하는 기능이 있었습니다. 하지만 수집 서버가 단일 대용량 로그 파일의 처음부터 끝까지 전체를 매번 메모리에 로드해 읽어 들이면서, 관리자가 어드민 페이지에 접속할 때마다 서버 CPU가 100%에 달하는 스파이크 현상이 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 근본적으로 해결하기 위해 몇 가지 설계 대안을 검토했습니다.

### 고민 1. 로그 관리 방식: ELK / CloudWatch 도입 vs 로컬 로테이션 & 스트리밍
* **대안 A (중앙 집중형 로깅 소루션 도입):** ELK 스택이나 AWS CloudWatch, Datadog 등으로 모든 로그를 전송합니다.
  * *장점:* 로컬 디스크 용량 문제를 완벽히 해결하고 세련된 대시보드를 구축할 수 있습니다.
  * *단점:* 전송 및 보관 비용이 크게 상승하며, 단순 수집 이력 확인용으로는 오버엔지니어링일 수 있습니다.
* **대안 B (RotatingFileHandler + Tail 조회 API 구현):** 로컬 인프라 환경에서 처리하되, 로그 용량을 제한하고 필요한 부분만 스트리밍합니다.
  * *장점:* 추가 인프라 비용이 들지 않으며, 네트워크 레이턴시 없이 빠른 모니터링이 가능합니다.
  * *결정:* 수집 데이터 로그는 보존 기간이 길 필요가 없으므로 **대안 B**를 선택했습니다. 단일 파일 크기를 제한하고, 모니터링 시 파일의 마지막 부분만 읽는 구조로 가기로 결정했습니다.

### 고민 2. 커넥션 관리: 글로벌 세션 생명주기 관리 vs 명시적 Safe Teardown
* **대안 A (프레임워크 수준의 의존성 주입에 의존):** 프레임워크가 제공하는 미들웨어나 DI(Dependency Injection)가 알아서 세션을 닫아주길 기대합니다.
  * *문제점:* 외부 API 호출처럼 장시간 소요되는 I/O 작업 도중 예외가 발생하면 예외 전파 경로에 따라 세션 클로즈가 누락될 위험이 큽니다.
* **대안 B (Try-Except-Finally 기반의 명시적 Guard):** 수집 라이프사이클에 맞춰 물리적으로 엄격한 트랜잭션 가드를 직접 구현합니다.
  * *결정:* 데이터 정합성과 인프라 안정성을 위해 수집 전용 커넥션 풀을 별도로 격리하고, 예기치 못한 실패 상황에서도 무조건 커넥션을 회수하는 **안전 회수(Safe Teardown)** 패턴을 명시적으로 작성하기로 결정했습니다.

## 3. 최종 해결 및 구현 (Engineering Solution)

우리는 위 결정을 바탕으로 세 가지 핵심 레이어에서 아키텍처를 개선했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 로그 로테이션 & 크기 제한 (Log Rotation)                 │
│    - RotatingFileHandler 기반 최대 5MB, 백업 파일 3개 제한   │
│    - 어드민 조회 시 파일의 끝부분(Tail 500줄)만 읽어 응답     │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. Safe Teardown 커넥션 풀 보호 (Connection Guard)          │
│    - try ... except ... finally 구조를 통한 DB 세션 강제 반환│
│    - 외부 API 타임아웃(Timeout: 10s) 설정 및 재시도 로직      │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 데이터웨어하우스(DW) 테이블 이중화 격리                  │
│    - 수집 원본 raw 데이터와 로그성 데이터를 운영 DB에서 분리  │
│    - 수집 로그 분석 및 이력 관리를 보조 테이블로 이중화 이관   │
└─────────────────────────────────────────────────────────────┘
```

### ① RotatingFileHandler 도입 및 Tail 스트리밍 읽기
무제한 로그 누적을 방지하기 위해 파이썬 내장 로깅 라이브러리의 `RotatingFileHandler`를 설정했습니다. 파일 크기가 5MB에 도달하면 자동으로 새 파일로 롤링(Rolling)되고 최대 3개의 백업 파일만 유지되도록 제한했습니다.

또한, 관리자 웹에서 모니터링 시 파일 전체를 읽지 않고 최신 로그 500줄만 역순으로 읽어 응답하는 스트리밍 구조를 도입해 I/O 부하를 완전히 차단했습니다.

```python
# [보안 처리 가이드라인에 따라 마스킹 및 간소화된 예시 코드입니다]
import logging
from logging.handlers import RotatingFileHandler

def setup_collector_logger():
    logger = logging.getLogger("DataCollector")
    logger.setLevel(logging.DEBUG)
    
    # 최대 5MB 크기 제한, 백업본은 3개만 유지
    handler = RotatingFileHandler(
        "logs/ingestion.log", 
        maxBytes=5 * 1024 * 1024, 
        backupCount=3,
        encoding="utf-8"
    )
    logger.addHandler(handler)
    return logger
```

### ② Safe Teardown과 네트워크 타임아웃 적용
외부 시스템 장애가 내부 서비스 장애로 전파되지 않도록 하는 **'서킷 브레이커'** 정신을 적용했습니다. 외부 API 호출부에는 최대 10초의 타임아웃 제한과 지수 백오프(Exponential Backoff)를 적용하고, DB 연결은 아래와 같이 어떤 상황에서도 안전하게 소멸(Teardown)되도록 설계했습니다.

```python
# DB 세션 안전 관리 컨텍스트 매니저 예시
from contextlib import contextmanager

@contextmanager
def safe_session_scope(session_factory):
    session = session_factory()
    try:
        yield session
        session.commit()
    except Exception as e:
        session.rollback()
        raise e
    finally:
        # 어떤 예외가 발생하든, 네트워크가 끊기든 커넥션은 무조건 풀로 반환
        session.close()
```

### ③ DW 테이블 격리 및 이력 적재
동기화 중 대량으로 적재되는 원본 데이터(Raw Data)와 임시 수집 로그가 운영계(OLTP) 메인 테이블에 직접 쌓여 인덱스 성능을 저하시키는 것을 방지하기 위해, 수집 전용 보조 테이블(Data Warehouse 성격)로 이중화 분리했습니다. 덕분에 메인 테이블은 사용자 쿼리 성능 저하 없이 고유의 속도를 유지할 수 있게 되었습니다.

## 4. 성과 및 엔지니어링 교훈 (Takeaways)

이 개선 작업을 통해 서비스는 다음과 같은 정량적/정성적 성과를 거두었습니다.

* **무중단·무누수 100% 완주**: 30,000건 이상의 식약처 성분 데이터를 주기적으로 수집할 때 발생하던 `Connection Pool Timeout` 장애가 완전히 사라졌습니다. 
* **모니터링 리소스 90% 절감**: 관리자 페이지에서 실시간 모니터링 시 CPU 스파이크 현상이 완전히 제거되었으며, 어드민 로딩 메모리 점유율이 기존 대비 90% 이상 절감되었습니다.
* **디스크 관리 자동화**: 용량 오버플로우 위험이 사전에 차단되어 데브옵스(DevOps) 팀의 운영 피로도가 대폭 줄어들었습니다.

### 💡 이번 프로젝트를 통해 배운 교훈:
1. **외부 인프라는 절대 신뢰하지 마라**: 외부 API 호출 시 타임아웃과 명시적인 커넥션 종료(Safe Teardown)를 구현하는 것은 대규모 배치의 기본 격률입니다.
2. **관찰 가능성(Observability)이 시스템을 망치게 두지 마라**: 로그 수집과 모니터링은 반드시 시스템에 부하를 주지 않는 범위 내에서 이루어져야 합니다. 성능을 고려하지 않은 모니터링 쿼리는 그 자체로 장애 유발 요인이 될 수 있습니다.

앞으로도 PickSafe는 끊임없이 밀려오는 대용량 데이터를 안전하고 빠르게 처리하며, 사용자들에게 신뢰할 수 있는 가치를 제공하기 위해 엔지니어링 역량을 다해나갈 것입니다.
