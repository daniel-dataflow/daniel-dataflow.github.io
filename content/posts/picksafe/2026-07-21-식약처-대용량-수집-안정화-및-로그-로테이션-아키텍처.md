안녕하세요, PickSafe 개발 팀입니다.

최근 저희 팀은 서비스의 핵심 엔진 중 하나인 **'식약처 공공데이터 포털 기반, 3만 건 이상의 국내 화장품 전성분 데이터 수집 및 동기화 파이프라인'**을 개선하는 작업을 진행했습니다. 

처음 단순하게 구현되었던 수집 배치(Batch) 프로그램은 데이터양이 늘어나고 네트워크가 불안정해짐에 따라 **서버 디스크 고갈, DB 커넥션 누수, CPU 급증**이라는 삼중고를 겪게 되었습니다. 

이 글에서는 저희가 마주했던 구체적인 기술적 문제들과 이를 해결하기 위해 취했던 아키텍처 레벨의 의사결정, 그리고 트레이드오프 과정을 공유하고자 합니다.

## 1. 우리가 마주한 세 가지 무서운 경고등 (Problem)

수집 데몬이 백그라운드에서 동작한 지 며칠 지나지 않아, 인프라 모니터링 시스템에서 경고 알림이 울리기 시작했습니다. 원인을 분석해 보니 크게 세 가지의 병목과 장애 포인트가 존재했습니다.

### ① 디스크 용량의 선형적 급증 (Disk Exhaustion)
수집 과정에서 발생하는 대량의 데이터 정제 및 매핑 과정 로그가 단일 텍스트 파일에 무제한으로 기록되고 있었습니다. 단기적으로는 디버깅에 유리했지만, 수집 주기마다 수십 기가바이트(GB) 단위로 로그가 쌓여 운영 서버 전체의 디스크가 가득 차기 일보 직전이었습니다.

### ② 간헐적 네트워크 지연으로 인한 DB 커넥션 고갈 (Connection Pool Starvation)
외부 공공데이터 API는 가끔 호출 지연(Latency)이 발생하거나 일시적으로 응답을 주지 못했습니다. 이때 API 호출부에서 타임아웃 처리가 미흡해 커넥션이 대기 상태로 묶였고, 이로 인해 데이터베이스 세션이 정상 반환되지 않는 `idle in transaction` 상태로 잔류하는 현상이 발생했습니다. 결과적으로 커넥션 풀이 마르고 대기 중인 다른 API 서비스까지 마비되는 연쇄 장애로 이어졌습니다.

### ③ 로그 모니터링 시 발생하는 CPU 스파이크 (Memory & CPU Spike)
관리자 페이지에서는 관리자가 수집 상태를 실시간으로 모니터링할 수 있도록 로그 조회 기능을 제공했습니다. 그러나 로그를 조회할 때마다 백엔드 서버가 **기가바이트 단위의 로그 파일 전체를 메모리로 읽어와(Full Read)** 클라이언트에 전송하고 있었습니다. 여러 명의 관리자가 새로고침을 누를 때마다 서버 CPU 사용량이 100% 근처까지 치솟았습니다.

## 2. 지속 가능한 시스템을 위한 아키텍처 개선 (Trade-off & Solution)

저희는 문제를 임시방편으로 때우기보다, 시스템 구조를 근본적으로 개선하여 운영 공수를 최소화할 수 있는 방향으로 설계 방향을 잡았습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 로그 로테이션 & 크기 제한 (Log Rotation)                 │
│    - 최대 5MB 크기 제한, 백업 파일 3개 유지 (RotatingHandler)│
│    - 어드민 조회 시 꼬리 부분(Tail 500줄)만 스트리밍 읽기   │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. Safe Teardown 커넥션 풀 보호 (Connection Guard)          │
│    - try ... except ... finally 구조로 DB 세션 명시적 close │
│    - 외부 API 타임아웃(Timeout: 10s) 및 자동 재시도(Backoff)│
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 데이터웨어하우스(DW) 테이블 이중화 격리                  │
│    - 운영 DB(Main) 부하 방지를 위해 수집 로그 및 원본 raw    │
│      데이터를 DW 보조 테이블로 이중화 분리 적재             │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. 로그 로테이션 도입 및 조회 아키텍처 최적화

* **AS-IS**: 단일 로그 파일 무제한 쓰기 + 전체 파일 API 리드
* **TO-BE**: `RotatingFileHandler` 적용 + Tail 기반 스트리밍 조회

먼저 파이썬 표준 로깅 라이브러리의 `RotatingFileHandler`를 활용해 로그 파일 크기를 최대 `5MB`로 제한하고, 백업 파일을 최대 `3개`만 유지하도록 롤링 정책을 적용했습니다. 이로써 로그 파일이 차지하는 최대 디스크 공간을 약 `20MB` 선으로 제어(Bounded)할 수 있게 되었습니다.

또한, 실시간 모니터링 API의 성능 문제를 해결하기 위해 **파일 포인터를 역순으로 탐색(Tail)하는 로직**을 적용했습니다. 전체 파일을 메모리에 올릴 필요 없이, 가장 마지막에 기록된 로그 500줄만 스트리밍 형태로 읽어 응답함으로써 서버의 부하를 극적으로 낮췄습니다.

### 2.2. 외부 장애 전파를 막는 '안전한 연결 회수(Safe Teardown)' 및 클라이언트 보호

외부 API의 장애가 우리 데이터베이스의 장애로 이어지는 고리를 끊어내야 했습니다.

```python
# 시스템 안정성을 확보한 수집 트랜잭션 의사 코드
async def safe_ingredient_ingestion_task(session_factory, api_client):
    session = session_factory()
    try:
        # 1. 외부 API 타임아웃(10초)을 명시적으로 지정하고 지수 백오프 적용
        raw_data = await api_client.fetch_data_with_retry(timeout=10, retries=3)
        
        # 2. 비즈니스 로직 처리 및 적재
        process_and_save_data(session, raw_data)
        session.commit()
    except Exception as e:
        session.rollback()
        logger.error(f"Ingestion failed: {str(e)}")
        raise
    finally:
        # 3. 어떤 예외 상황에서도 세션을 안전하게 커넥션 풀로 반환 (Safe Teardown)
        session.close()
```

* **네트워크 타임아웃 & 백오프**: 외부 API 호출 시 최대 타임아웃(10s)을 명시하고, 일시적인 네트워크 장애에는 지수 백오프(Exponential Backoff) 기반의 재시도 정책을 적용해 불필요한 실패율을 줄였습니다.
* **명시적 자원 반환 (Safe Teardown)**: `try ... except ... finally` 구조를 엄격히 적용하여, 비즈니스 로직 중 어떤 예외나 타임아웃이 발생하더라도 `finally` 블록에서 데이터베이스 커넥션을 반드시 풀(Pool)로 회수하도록 강제했습니다. 이로 인해 `idle in transaction` 누수가 완전히 사라졌습니다.

### 2.3. 읽기/쓰기 관심사 분리를 위한 데이터 적재 이중화 격리

서비스를 이용 중인 일반 사용자들의 조회 성능을 보장하기 위해, 대용량 수집 프로세스가 메인 운영 테이블에 직접 대규모 락(Lock)을 거는 행위를 지양해야 했습니다.

따라서, 수집되는 중간 상태 로그 및 정제되지 않은 대용량 원본 데이터(Raw Data)는 **메인 테이블과 격리된 별도의 보조/DW(Data Warehouse) 성격의 테이블에 분리 적재**하도록 구성했습니다. 데이터의 최종 정제본만 메인 서비스 테이블에 배치 형태로 이관(Upsert) 함으로써, 백그라운드 수집 시에도 웹 서비스의 메인 트랜잭션 성능을 안정적으로 보존할 수 있게 되었습니다.

## 3. 어떤 결과를 얻었을까요? (Results & Takeaway)

이러한 아키텍처 개선을 통해 당장 눈에 보이는 지표의 변화를 체감할 수 있었습니다.

* **대용량 수집 완주**: 외부 API 상태가 불안정한 상황에서도 30,000건 이상의 화장품 전성분 데이터를 **중단 없이, 누수 없이 100% 안정적으로 완주**해 냈습니다.
* **메모리 절감 90%**: 관리자 페이지의 실시간 로그 모니터링 기능 작동 시, 파일 전체를 읽지 않고 꼬리(Tail) 부분만 조회하게 되면서 **메모리 점유율을 90% 이상 대폭 절감**했습니다. 더 이상 로그 모니터링 시 CPU 스파이크가 발생하지 않습니다.
* **인프라 비용 보존**: 무분별한 디스크 증설 예산을 아낄 수 있게 되었으며, 인프라의 전체적인 CPU/Memory 예측 가능성(Predictability)이 크게 향상되었습니다.

### 이번 작업을 통해 배운 교훈

1. **외부 자원은 결코 믿을 수 없다**: 외부 네트워크와 연동되는 모든 구간에는 반드시 엄격한 타임아웃과 자원 회수(Teardown) 코드가 동반되어야 시스템 전체의 가용성을 지킬 수 있습니다.
2. **로그 역시 유한한 리소스다**: 개발 단계에서 유용한 로그가 실서비스 환경에서는 파일 디스크를 삼키는 괴물이 될 수 있습니다. 로테이션과 보관 주기 설정은 서비스 오픈 전 반드시 챙겨야 하는 필수 점검 요소입니다.

앞으로도 PickSafe 팀은 보이지 않는 백엔드의 비효율을 찾아 개선하고, 고가용성의 인프라를 바탕으로 고객 중심적인 가치를 더 빠르게 제공하기 위해 최선을 다할 것입니다. 긴 글 읽어주셔서 감사합니다.
