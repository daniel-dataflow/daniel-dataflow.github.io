안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

서비스를 운영하면서 외부 공공데이터 연동은 피할 수 없는 과제 중 하나입니다. 저희 PickSafe에서는 국내 화장품 전성분 데이터를 제공하기 위해 식약처 공공데이터 포털의 OpenAPI를 활용하고 있습니다. 

수만 건에 달하는 데이터를 주기적으로 동기화하는 파이프라인을 구축하는 과정에서, **디스크 용량 초과, 데이터베이스 커넥션 고갈, 어드민 모니터링 부하**라는 삼중고를 마주했습니다. 

이번 글에서는 이 문제를 어떻게 정의하고, 어떤 아키텍처적 트레이드오프를 거쳐 해결했는지 공유해 드리고자 합니다.

---

## 1. 마주한 문제 (Problem)

수만 건의 화장품 데이터를 한 번에 수집·동기화하는 배치 작업을 테스트하던 중, 인프라 전반에서 치명적인 시그널이 감지되었습니다.

1. **디스크 용량 급증 (Disk Exhaustion)**
   * 상세 디버그 로그가 단일 파일에 무제한으로 누적되면서 서버 디스크 사용량이 수 시간 만에 임계치를 초과하는 위험이 발생했습니다.
2. **네트워크 타임아웃으로 인한 커넥션 고갈 (Connection Leak)**
   * 외부 API 호출 중 간헐적인 네트워크 지연이나 단절이 발생했을 때, DB 세션이 정상적으로 반환되지 않고 `idle in transaction` 상태로 잔류하여 결국 커넥션 풀이 말라버리는 현상이 발생했습니다.
3. **실시간 로그 모니터링 시 CPU/Memory 스파이크**
   * 운영팀이 관리자 페이지에서 수집 로그를 실시간으로 확인할 때, 수십 MB에 달하는 전체 로그 파일을 매번 통째로 읽어 들여 서버 CPU와 메모리에 불필요한 부하를 유발했습니다.

---

## 2. 기술적 해결 방안 및 아키텍처 (Trade-offs & Solutions)

이 문제들을 해결하기 위해 로그 관리, DB 커넥션 보호, 그리고 데이터 격리라는 세 가지 측면에서 아키텍처를 재설계했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 로그 로테이션 & 크기 제한 (Log Rotation)                 │
│    - 최대 5MB 크기 제한, 백업 파일 3개 유지 (RotatingHandler)│
│    - 어드민 조회 시 꼬리 부분(Tail 500줄)만 스트리밍 읽기   │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. Safe Teardown 커넥션 풀 보호 (Connection Guard)          │
│    - try ... except ... finally 구조로 DB 세션 명시적 close │
│    - 외부 API 타임아웃 설정 및 예외 안전 장치 마련          │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 데이터웨어하우스(DW) 테이블 이중화 격리                  │
│    - 운영 DB(Main) 부하 방지를 위해 수집 로그 및 원본 raw    │
│      데이터를 DW 보조 테이블로 이중화 분리 적재             │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. `RotatingFileHandler` 도입과 Tail 스트리밍 읽기
무제한으로 쌓이는 로그를 방지하기 위해 파이썬 표준 로깅 모듈의 `RotatingFileHandler`를 적용했습니다.
* **정책**: 로그 파일 당 최대 5MB로 제한하고, 최대 3개의 백업 파일(`*.log.1`, `*.log.2`, `*.log.3`)만 유지하도록 자동 순환(Rotation) 구조를 도입했습니다.
* **어드민 API 최적화**: 관리자 페이지에서 전체 파일을 읽지 않고, 파일의 끝부분(Tail, 최근 500줄)만 효율적으로 읽어오는 스트리밍 방식을 적용해 메모리 점유율을 극적으로 낮췄습니다.

### 2.2. Safe Teardown 패턴을 통한 커넥션 누수 방어
외부 네트워크 I/O 작업은 언제나 실패할 가능성을 내포하고 있습니다. 예외 발생 시에도 DB 커넥션이 누수되지 않도록 방어 로직을 강화했습니다.
* 모든 수집 및 트랜잭션 블록에 엄격한 `try ... except ... finally` 구조를 적용하여, 에러 발생 여부와 무관하게 세션이 안전하게 롤백되고 커넥션 풀(`Connection Pool`)로 즉시 반환되도록 보장했습니다.
* 또한, 수집 실행 히스토리에 실제 소요 시간(Duration)을 측정하는 필드를 추가하여 병목 구간을 모니터링할 수 있게 개선했습니다.

### 2.3. 운영 DB와 수집 로그의 물리적 격리
대량의 원본 데이터(Raw Data)와 상세 수집 로그가 핵심 트랜잭션을 처리하는 메인 운영 DB에 직접 쓰여질 경우, 락(Lock) 경합이나 성능 저하를 유발할 수 있습니다. 이를 방지하기 위해 보조 데이터웨어하우스(DW) 테이블을 두어 수집 관련 로그와 원본 데이터를 이중화하여 분리 적재하도록 구조를 변경했습니다.

## 3. 결과 및 성과 (Takeaways)

위 아키텍처 개선을 적용한 결과, 다음과 같은 안정성을 확보할 수 있었습니다.

* **100% 안정적 완주**: 식약처 30,000건 이상의 대용량 성분 데이터를 중단 없이, 커넥션 누수 없이 안정적으로 동기화 완료했습니다.
* **리소스 효율화**: 관리자 페이지의 실시간 로그 모니터링 시 발생하는 메모리 점유율을 **90% 이상 절감**하여 서버 인프라의 안정성을 높였습니다.

외부 연동 시스템을 개발할 때는 '정상적인 응답'을 처리하는 것만큼이나, **'네트워크가 끊기거나 예외가 발생했을 때 시스템이 얼마나 안전하게 자원을 회수하는가(Graceful Degradation & Teardown)'**가 백엔드 아키텍처의 완성도를 결정한다는 것을 깊이 깨달은 프로젝트였습니다.
