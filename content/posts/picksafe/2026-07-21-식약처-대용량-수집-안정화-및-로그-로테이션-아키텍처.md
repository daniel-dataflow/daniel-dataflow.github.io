안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

서비스를 운영하면서 외부 공공데이터 연동은 피할 수 없는 과제 중 하나입니다. 저희 PickSafe에서는 국내 화장품 전성분 데이터를 제공하기 위해 식약처 공공데이터 포털 OpenAPI를 주기적으로 동기화하고 있습니다. 

데이터의 양이 수만 건에 달하다 보니, 초기 구현 당시에는 가볍게 여겼던 부분들이 실제 프로덕션 환경에서 치명적인 인프라 이슈로 돌아왔습니다. 이번 포스팅에서는 **대용량 수집 과정에서 직면한 3가지 핵심 문제와 이를 해결하기 위해 적용한 아키텍처 및 트레이드오프(Trade-off)**를 공유해 드립니다.

---

## 1. 마주한 문제 (Problem)

수만 건의 데이터를 배치로 수집하는 과정에서 다음과 같은 인프라스트럭처 레벨의 장애 징후가 포착되었습니다.

1. **디스크 용량 급증 (Disk Exhaustion)**: 수집 프로세스의 상세 디버그 로그가 단일 파일에 무제한으로 누적되면서, 단일 배치 작업만으로도 서버 디스크 사용량이 임계치를 초과하는 위험이 발생했습니다.
2. **네트워크 단절과 커넥션 고갈 (Connection Leak)**: 외부 API를 호출하는 도중 간헐적인 네트워크 타임아웃이나 예외가 발생할 때, DB 세션이 정상적으로 반환되지 않고 `idle in transaction` 상태로 잔류하여 커넥션 풀이 고갈되는 현상이 나타났습니다.
3. **실시간 모니터링 부하 (CPU Spike)**: 운영 관리자 페이지에서 수집 로그를 모니터링하기 위해 주기적으로 폴링(Polling)을 수행할 때, 서버가 전체 대용량 로그 파일을 통째로 읽어 들여 CPU 스파이크를 유발했습니다.

---

## 2. 기술적 고민과 아키텍처 선택 (Trade-off & Solution)

문제 해결을 위해 인프라와 애플리케이션 레벨에서 동시에 방어 로직을 구축했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 로그 로테이션 & 크기 제한 (Log Rotation)                 │
│    - 최대 5MB 크기 제한, 백업 파일 3개 유지 (RotatingHandler)│
│    - 어드민 조회 시 꼬리 부분(Tail 500줄)만 스트리밍 읽기   │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. Safe Teardown 커넥션 풀 보호 (Connection Guard)          │
│    - try ... except ... finally 구조로 DB 세션 명시적 close │
│    - 외부 API 타임아웃(Timeout: 10s) 및 자동 재시도(Backoff)│
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 데이터웨어하우스(DW) 테이블 이중화 격리                  │
│    - 운영 DB(Main) 부하 방지를 위해 수집 로그 및 원본 raw    │
│      데이터를 DW 보조 테이블로 이중화 분리 적재             │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. 로그 로테이션과 Tail 스트리밍 도입
* **대안 비교**: 모든 로그를 외부 로깅 시스템(예: ELK 등)으로 즉시 이관하는 방안도 검토했으나, 현재 인프라 규모 대비 과도한(Over-engineering) 비용이 발생한다고 판단했습니다.
* **최종 선택**: 파이썬 표준 라이브러리의 `RotatingFileHandler`를 도입하여 로그 파일당 최대 5MB, 백업 3개까지만 유지하도록 강제했습니다. 또한, 관리자 페이지의 실시간 로그 조회 API는 파일 전체를 로드하는 대신 파일의 끝부분(Tail 500줄)만 효율적으로 읽어오도록 최적화했습니다.

### 2.2. Safe Teardown을 통한 커넥션 누수 방어
* **문제 분석**: 외부 API 호출부는 I/O 바운드 작업 특성상 네트워크 지연이나 응답 지연이 잦습니다. 이때 예외 처리가 누락되면 트랜잭션이 열린 채로 세션이 반환되지 않는 문제가 있었습니다.
* **최종 선택**: 모든 수집 트랜잭션 로직에 `try ... except ... finally` 패턴을 엄격히 적용하여, 예외 발생 여부와 상관없이 트랜잭션이 안전하게 롤백되거나 커밋된 후 DB 세션이 커넥션 풀로 확실히 반환(`close`)되도록 보장했습니다. 추가로 외부 API 호출 시 명시적 타임아웃(10s)과 백오프 재시도 정책을 결합했습니다.

### 2.3. 운영 DB와 수집 데이터의 격리 (DW 이중화)
* 수만 건의 대량 Upsert/Insert 작업이 메인 운영 DB에 직접적인 부하를 주는 것을 막기 위해, 수집 로그 및 원본 Raw 데이터를 별도의 DW(Data Warehouse) 보조 테이블에 분리 적재하여 트랜잭션 격리를 달성했습니다.

## 3. 결과 및 엔지니어링 교훈 (Takeaway)

이번 아키텍처 개선을 통해 다음과 같은 유의미한 성과를 거둘 수 있었습니다.

* **100% 안정성 확보**: 식약처 30,000건 이상의 대용량 전성분 데이터를 처리하는 동안 디스크 초과나 커넥션 고갈 없이 **무중단·무누수**로 배치를 완주할 수 있게 되었습니다.
* **모니터링 성능 극대화**: 로그 파싱 방식을 Tail 스트리밍으로 전환한 결과, 실시간 로그 모니터링 시 **서버 메모리 점유율을 90% 이상 절감**했습니다.

### 💡 Takeaway
> "아무리 사소해 보이는 배치 수집 로직이라도, 외부 네트워크 환경의 불안정성과 대용량 I/O가 만나는 지점에서는 반드시 **리소스 제한(Limit)**과 **안전한 자원 반환(Teardown)** 장치가 설계 단계부터 고려되어야 합니다."
