수만 건에 달하는 외부 API 연동 작업은 단순해 보이지만, **"네트워크 불확실성"**과 **"시스템 자원 관리"** 측면에서 많은 엔지니어링 도전 과제를 던져줍니다. 최근 데이터 수집 파이프라인을 고도화하면서 겪었던 인프라 병목 현상과, 이를 해결하기 위해 고민했던 기술적 의사결정 과정을 공유합니다.

## 1. 문제 정의 (Problem Definition)

식약처 대용량 수집 배치(Batch) 작업 수행 중 시스템 안정성을 위협하는 3가지 핵심 문제가 발생했습니다.

### ① 디스크 용량의 폭발적 증가 (Disk Bloat)
수만 건의 데이터를 동기화하는 과정에서 상세한 추적을 위해 디버그 로그를 남겼으나, 로그 파일이 단일 파일 형태로 무제한 커지면서 서버 디스크 사용량이 임계치에 도달했습니다.

### ② 외부 네트워크 타임아웃 시 DB 커넥션 고갈 (Connection Leak)
공공 데이터 API는 간헐적으로 응답 지연이나 타임아웃을 일으켰습니다. 이때 애플리케이션 영역에서 트랜잭션 수거가 제대로 이루어지지 않아, 데이터베이스에 `idle in transaction` 상태의 커넥션이 누적되었고 최종적으로 DB 커넥션 풀이 고갈되는 현상이 발생했습니다.

### ③ 실시간 로그 모니터링 시 CPU 스파이크
어드민 Dashboard에서 수집 진행 상황을 실시간 폴링(Polling)할 때마다 전체 대용량 로그 파일(수십~수백 MB)을 통째로 읽어 들여 서버의 CPU 및 메모리 사용량이 급증했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs)

이 문제들을 해결하기 위해 다양한 아키텍처 대안을 검토했습니다.

### 💡 고민 1. 대용량 로그와 실시간 모니터링을 어떻게 처리할 것인가?
* **대안 A: ELK(Elasticsearch, Logstash, Kibana) 또는 외부 APM 도입**
  * *장점*: 강력한 검색 및 모니터링 기능 제공.
  * *단점*: 현재 단일 수집 로그 동기화 목적에 비해 외부 인프라 구축 및 유지 관리 비용(Overhead)이 큼.
* **대안 B: 파일 기반 Rotating Handler + Tail Streaming 방식 채택 (최종 선택)**
  * *장점*: 별도의 중앙집중형 로그 서버 없이도 표준 라이브러리를 통해 디스크 용량을 상한선(Max Byte Limit) 내부로 제어 가능. 어드민 읽기 요청 시 파일의 끝부분(Tail)만 파싱하여 메모리 점유 최소화.

### 💡 고민 2. 외부 API 장애 시 DB 트랜잭션을 어떻게 보호할 것인가?
* **대안 A: DB 커넥션 타임아웃(Client-side timeout) 설정에 의존**
  * *장점*: 코드 수정량이 적음.
  * *단점*: 애플리케이션의 세션 해제 시점과 DB 세션 타임아웃 간 격차가 발생하여 짧은 시간 내 대량의 타임아웃 발생 시 대응 불가.
* **대안 B: Safe Teardown 패턴 및 엑스포넨셜 백오프(Exponential Backoff) 적용 (최종 선택)**
  * *장점*: HTTP 클라이언트 수준에서 10초 타임아웃을 강제하고, 재시도 실패 시 `try ... except ... finally` 구문을 통해 DB 세션을 명시적으로 `rollback` 및 `close`하여 커넥션을 안전하게 회수.

## 3. 최종 아키텍처 및 구현 (Architecture & Solutions)

검토한 대안을 바탕으로 설계한 수집 파이프라인 아키텍처는 다음과 같습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 로그 로테이션 & Tail 스트리밍 읽기                      │
│    - RotatingFileHandler (Max 5MB, Backup 3개 제한)         │
│    - Admin Log Viewer: 파일 하단 500줄만 Streaming 파싱      │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 2. Connection Guard (Safe Teardown)                         │
│    - HTTP Client: Timeout 10s + Auto Backoff Retry          │
│    - DB Session: Explicit Rollback & Close via Context      │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ 3. 데이터웨어하우스(DW) 격리 적재                           │
│    - 메인 서비스 OLTP 테이블 부하 방지                      │
│    - 수집 원본(Raw Data) 및 실시간 로그는 Staging DW에 분리 │
└─────────────────────────────────────────────────────────────┘
```

### 핵심 구현 포인트

#### 1) Safe Teardown & Connection Guard
데이터 수집 컨텍스트에서 예외가 발생하더라도 커넥션이 즉시 반환되도록 방어적 세션 관리를 적용했습니다. 

```python
# [핵심 개념 구현 예시 - 보안을 위해 비즈니스 로직은 추상화되었습니다]
async def safe_data_ingest_pipeline(batch_items):
    session = DBManager.get_session()
    start_time = time.time()
    try:
        async with ExternalAPIClient(timeout=10.0, max_retries=3) as client:
            raw_data = await client.fetch_bulk_data(batch_items)
            await save_to_dw_staging(session, raw_data)
            session.commit()
    except ExternalAPIException as e:
        logger.error(f"External Network Error: {e}")
        session.rollback() # 타임아웃 시 트랜잭션 롤백
    except Exception as e:
        logger.critical(f"Unexpected Pipeline Error: {e}")
        session.rollback()
    finally:
        # 소요 시간 측정 및 DB 커넥션 명시적 반환 (Connection Leak 방지)
        duration = time.time() - start_time
        logger.info(f"Batch completed in {duration:.2f}s")
        session.close() 
```

#### 2) Bounded Logging & Tail File Streaming
로그 파일의 폭증을 막기 위해 `RotatingFileHandler`를 적용하고, 어드민 모니터링 시 전체 파일을 읽는 대신 파일 꼬리(Tail) 영역의 500줄만 메모리에 올리는 스트리밍 읽기 로직을 구성했습니다.

* **로그 롤링 정책**: 파일당 5MB 제한, 최대 3개의 파일만 백업 유지 (총 20MB 이하로 상한 제어)
* **어드민 IO 최적화**: 파일의 끝 지점(`SEEK_END`)부터 역방향 바이트 블록을 읽어 효율적으로 최신 500줄 추출

## 5. 엔지니어링 교훈 (Takeaways)

이번 개선 작업을 진행하며 팀 내부적으로 얻은 핵심 교훈은 다음과 같습니다.

1. **외부 시스템의 불확실성을 내부 시스템으로 전파하지 마라**
   외부 API 타임아웃이나 네트워크 분절은 언제든 일어날 수 있는 '일상적인 이벤트'입니다. 이를 대비한 명시적인 Teardown 처리와 재시도(Backoff) 전략이 없으면 외부 시스템의 장애가 내부 DB 고갈로 이어지게 됩니다.
2. **관찰 가능성(Observability) 구축 시 자원 소비를 고려하라**
   시스템 상황을 파악하기 위한 로그나 모니터링 기능이 정작 시스템 본연의 자원(CPU, Memory, Disk)을 고갈시키는 주범이 되어서는 안 됩니다.
3. **격리(Isolation)의 중요성**
   대용량 배치 수집 작업의 Raw 데이터 및 시스템 로그는 메인 서비스 OLTP DB와 분리된 Staging/DW 영역에 격리 적재함으로써 실시간 사용자 서비스의 성능 저하를 방지할 수 있었습니다.

PickSafe 팀은 앞으로도 대규모 데이터 처리 파이프라인의 견고함을 유지하며, 사용자에게 가장 빠르고 정확한 성분 안전 정보를 제공하기 위해 아키텍처를 continuamente 개선해 나갈 것입니다.
