안녕하세요, PickSafe 백엔드 에디터입니다. 글로벌 서비스로 도약하는 과정에서 마주한 **'다국어 확장성의 한계'**를 어떻게 극복했는지, 그 아키텍처 의사결정 과정을 공유하고자 합니다.

---

## 1. Problem: 글로벌 서비스의 발목을 잡는 '하드코딩'과 '휴먼 에러'

초기 PickSafe는 한국어, 영어, 일본어, 중국어(간/번체), 포르투갈어 등 6개 언어를 하드코딩 기반으로 지원하고 있었습니다. 하지만 비즈니스가 성장함에 따라 다음과 같은 구조적 병목 현상이 명확해졌습니다.

1. **높은 유지보수 비용 (O(N)의 복잡도)**: 새로운 언어(스페인어, 프랑스어 등)를 추가할 때마다 프론트엔드 렌더링 코드, 백엔드 API 검증 로직, DB 테이블 컬럼까지 전 영역을 수동으로 수정해야 했습니다.
2. **콘텐츠 번역 리소스 부족**: 언어 코드를 추가하더라도, 방대한 양의 `ui_string` 데이터를 사람이 일일이 수 번역해야 했습니다. 단건 번역이나 클라이언트 사이드 도구에만 의존해 대규모 누락 데이터를 한 번에 채울 자동화 수단이 부재했습니다.

코드 수정 없이 어드민에서 유연하게 언어를 추가하고, 누락된 번역을 원클릭으로 채울 수 있는 **동적 다국어 시스템**이 절실했습니다.

---

## 2. Decision: 동적 로케일 시스템과 서버 사이드 AI 파이프라인

이 문제를 해결하기 위해 시스템을 **완전한 동적(Dynamic) 구조**로 개편하고, 백엔드 주도의 일괄 번역 파이프라인을 도입하기로 결정했습니다.

### ① 데이터베이스 기반의 다국어(로케일) 동적 렌더링
* **메타데이터 분리**: 서버 설정 파일에 글로벌 17개국 이상의 언어 리스트(`GLOBAL_LOCALES`)를 상수로 정의했습니다.
* **시스템 활성화 언어 DB화 (`system_locales`)**: 관리자가 어드민 UI에서 언어를 추가하면 동적으로 DB에 적재되도록 설계했습니다.
* **프론트엔드 동적화**: 프론트엔드의 하드코딩된 배열을 전면 제거하고, API를 통해 받은 시스템 설정 언어 목록을 기반으로 UI(테이블 컬럼, 모달, 셀렉트박스 등)가 동적으로 렌더링되도록 재구조화했습니다.

### ② 클라이언트 번역 vs 서버 사이드 AI 번역 (Trade-off)
번역 자동화 기능을 구현할 때, 프론트엔드에서 기존 외부 번역 API를 호출하는 방식과 백엔드(FastAPI)에서 LLM을 호출하는 방식을 저울질했습니다.

* **선택: 백엔드(FastAPI) 기반 Gemini API 연동 (`A방식`)**
  * **보안 및 안정성**: 어드민 권한의 환경 변수 키를 서버 단에서만 안전하게 관리할 수 있습니다.
  * **스마트 빈칸 전용 번역 전략**: 전체 DB를 일괄 덮어쓰는 방식은 기존에 사람이 공들여 검수한 번역 품질을 해칠 수 있습니다. 따라서 **'타겟 언어의 텍스트가 빈 문자열인 경우에만'** 영어 원문을 기반으로 Gemini 1.5 Flash에 프롬프트를 구성해 질의하도록 구현했습니다.

## 3. Takeaway: 엔지니어링 교훈과 향후 과제

이번 아키텍처 개편을 통해 얻은 성과와 한계점은 명확합니다.

* **확장성 극대화**: 개발자의 소스 코드 배포 없이, 어드민 UI 클릭만으로 새로운 글로벌 언어를 실시간에 가깝게 추가할 수 있는 기반을 마련했습니다.
* **운영 생산성 향상**: `[✨ 빈칸 자동 번역]` 버튼 하나로 수백 개의 UI 텍스트가 안전하게 채워지며, 기존에 검수된 데이터는 완벽히 보호되는(Data Integrity) 안정성을 확보했습니다.

### ⚠️ 고려해야 할 Trade-off (한계와 대응)
현재 동기(Sync) 방식으로 구현된 일괄 번역 엔드포인트는 데이터가 수천 건 이상으로 방대해질 경우 서버 타임아웃을 유발할 수 있습니다. 

이를 해결하기 위해, 향후 텍스트 볼륨이 폭증할 시점에 대비하여 **비동기 워커(Celery / BackgroundTasks) 도입**과 어드민 내 **프로그레스 바(Progress Bar) 연동**을 다음 고도화 스프린트로 계획하고 있습니다.
