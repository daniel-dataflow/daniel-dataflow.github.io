안녕하세요, PickSafe 팀의 백엔드 엔지니어입니다. 

글로벌 서비스를 운영하다 보면 필연적으로 직면하는 문제 중 하나가 바로 **'다국어 지원(Localization)'**입니다. 서비스 초기에는 한국어, 영어, 일본어 등 소수의 핵심 언어로 빠르게 시작하지만, 비즈니스가 성장함에 따라 스페인어, 프랑스어 등 새로운 언어 추가 요구가 빗발치게 됩니다.

이번 포스팅에서는 PickSafe가 기존의 하드코딩된 다국어 구조에서 벗어나, **개발자 투입 없이 어드민 UI 클릭 한 번으로 언어를 추가하고, LLM을 통해 누락된 번역을 안전하게 일괄 처리**하도록 아키텍처를 개편한 과정과 기술적 의사결정(Trade-off)을 공유하려 합니다.

---

## 1. 기존 시스템의 문제점 (Problem)

초기 PickSafe 시스템은 6개 언어셋이 프론트엔드 코드와 백엔드 API, 그리고 DB 스키마에 단단히 결합된 **하드코딩 구조**였습니다.

* **높은 유지보수 비용**: 새로운 언어 하나를 추가하기 위해 프론트엔드 렌더링 코드, API 검증 로직, DB 테이블 컬럼을 일일이 수정해야 했습니다.
* **번역 자원 부족**: 언어 코드를 추가하더라도 수백 개에 달하는 기존 `ui_string` 데이터를 사람이 일일이 수동 번역해야 하는 막대한 리소스 문제가 발생했습니다.
* **데이터 관리의 한계**: 클라이언트 사이드 번역이나 단건 번역에 의존하다 보니, 특정 언어의 누락된 빈칸(Missing translation)을 효율적으로 식별하고 일괄 채워 넣을 수 있는 어드민 기능이 부재했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 **1) 시스템의 완전한 동적(Dynamic) 구조 개편**과 **2) 백엔드 주도 일괄 번역 파이프라인 구축**이라는 투 트랙 전략을 세웠습니다. 특히 번역 자동화 과정에서 몇 가지 중요한 아키텍처적 고민이 있었습니다.

### 대안 1: 프론트엔드(Client-side) 번역 API 활용 vs 백엔드(Server-side) LLM 활용
* **프론트엔드 번역 위임 방식**: 구현이 단순하고 서버 부하가 적지만, API 키 노출 위험 및 브라우저 환경에서의 대량 데이터 제어 한계가 있었습니다.
* **백엔드 주도 LLM 활용 방식 (`Selected`)**: FastAPI 서버 단에서 API를 호출하여 보안(Secret Key 안전 보관)과 데이터 정합성을 동시에 챙길 수 있습니다. 당사는 **Gemini 1.5 Flash** 모델을 백엔드에 연동하여, 고속이면서도 비용 효율적인 일괄 번역 파이프라인을 구축하기로 결정했습니다.

### 데이터 덮어쓰기 방지 전략 (Smart Filtering)
대량 번역 시 가장 우려되었던 점은 **"기존에 사람이 직접 공들여 검수한 번역 데이터를 AI가 엉뚱하게 덮어쓰는 리스크"**였습니다. 
이를 해결하기 위해 전체 DB를 무조건 갱신하는 방식이 아니라, **"타겟 언어의 텍스트가 빈 문자열(Missing)인 경우에만, 영어(English) 원문을 기반으로 프롬프트를 구성해 요청하는 조건부 번역 알고리즘"**을 적용했습니다.

## 3. 최종 아키텍처 및 구현 (Solution)

### 3.1 동적 로케일(Locale) 메타데이터 아키텍처
* **메타데이터 사전 정의**: 백엔드 설정 파일에 글로벌 지원 가능한 언어 리스트(`GLOBAL_LOCALES`)를 상수로 정의해 둡니다.
* **DB 기반 활성화**: 관리자가 어드민에서 `[+ 언어 추가]`를 누르면, `system_locales` 테이블에 동적으로 등록됩니다.
* **프론트엔드 동적 렌더링**: 프론트엔드는 더 이상 언어 배열을 하드코딩하지 않고, `/admin/locales` API를 통해 활성화된 언어 목록을 받아 UI(테이블 컬럼, 입력 폼 등)를 동적으로 그려냅니다.

### 3.2 백엔드 빈칸 자동 일괄 번역 파이프라인
1. 어드민에서 `[✨ 빈칸 자동 번역]` 버튼 클릭 시 FastAPI 엔드포인트로 요청이 전달됩니다.
2. 서버는 DB에서 누락된(빈칸인) `ui_string`들을 필터링합니다.
3. 보안이 유지된 서버 환경에서 Gemini API를 호출하여 영문 원본을 타겟 언어로 번역합니다.
4. 번역된 데이터만 안전하게 DB에 개별 적재하고, API 호출량은 모니터링 쿼터 시스템(`Admin_Quotas`)에 반영합니다.

## 4. 기대 효과 및 향후 과제 (Takeaway)

### 🚀 도입 효과
* **확장성 극대화**: 소스 코드 배포 없이, 어드민 UI 조작만으로 전 세계 새로운 언어를 시스템에 1초 만에 추가할 수 있게 되었습니다.
* **생산성 혁신**: 언어 추가 후 버튼 클릭 한 번으로 수백 개의 UI 텍스트가 100% 자동 번역되어 즉시 글로벌 배포가 가능해졌습니다.
* **안정성 확보**: 기존 수동 검수 데이터의 무결성을 완벽하게 보존하면서 누락분만 정확히 채워 넣는 안전한 파이프라인을 완성했습니다.

### 📈 향후 고려사항 (Scale-up)
현재는 동기(Sync) 방식으로 일괄 번역을 처리하고 있으나, 향후 지원 언어와 텍스트량이 폭증할 경우 서버 타임아웃(Timeout) 발생 우려가 있습니다. 
이를 대비해 추후 `auto_translate` 엔드포인트를 **비동기 워커(Celery 또는 BackgroundTasks) 기반으로 전환**하고, 어드민 화면에 실시간 진행률을 보여주는 **Progress Bar**를 도입하여 더욱 견고한 시스템으로 고도화할 예정입니다.
