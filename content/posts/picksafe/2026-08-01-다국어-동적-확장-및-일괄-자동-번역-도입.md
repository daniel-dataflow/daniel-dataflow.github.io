안녕하세요, PickSafe 백엔드 에디터입니다. 
글로벌 서비스를 운영하면서 가장 마주치기 쉬운 기술적 난제 중 하나는 바로 **'다국어 확장성'**입니다. 

초기 PickSafe는 6개의 주요 언어를 기준으로 하드코딩된 구조를 가지고 있었습니다. 하지만 비즈니스가 성장하고 글로벌 고객의 요구가 다양해짐에 따라, 기존의 아키텍처는 심각한 병목현상을 일으켰습니다. 

이번 포스팅에서는 **새로운 언어 추가 시 발생하는 높은 유지보수 비용과 수동 번역의 리소스 부족 문제**를 어떻게 백엔드 주도의 동적 아키텍처와 LLM(Gemini API)을 활용해 해결했는지, 그 의사결정 과정과 아키텍처 트레이드오프(Trade-off)를 공유하고자 합니다.

---

## 1. Problem: 하드코딩된 다국어 시스템의 한계

초기 PickSafe 시스템은 다음과 같은 구조적 부채를 안고 있었습니다.

1. **높은 유지보수 비용 (High Maintenance Cost)**
   * 스페인어, 프랑스어 등 새로운 언어를 추가할 때마다 프론트엔드 UI 렌더링 코드, 백엔드 API 검증 로직, DB 테이블 컬럼 구성을 일일이 수정해야 했습니다.
2. **번역 리소스 부족 (Lack of Resources)**
   * 언어를 추가하더라도 수백 개에 달하는 기존 `ui_string` 데이터를 사람이 직접 번역하고 입력해야 하는 공수가 발생했습니다.
3. **어드민 자동화 부재**
   * 누락된 번역(빈칸)을 타겟팅하여 일괄적으로 채워 넣을 수 있는 서버 사이드 자동화 수단이 없어 운영 효율성이 크게 떨어졌습니다.

---

## 2. Decision: 기술적 고민과 대안 비교

이 문제를 해결하기 위해 **1) 시스템의 완전한 동적(Dynamic) 구조 개편**과 **2) 백엔드 주도 일괄 번역 파이프라인 구축**을 목표로 잡았습니다.

### 2.1 다국어(로케일) 동적 렌더링 시스템 설계
* **메타데이터 사전 정의 및 DB화**: 백엔드 코드 내 상수로 글로벌 로케일 풀(`GLOBAL_LOCALES`)을 정의하고, 실제 시스템에서 활성화된 언어 목록은 `system_locales` 테이블에서 관리하도록 분리했습니다.
* **프론트엔드 동적 렌더링**: 프론트엔드에 하드코딩되어 있던 언어 배열을 전면 제거하고, `/admin/locales` API를 통해 동적으로 UI(테이블 컬럼, 입력 폼 등)를 구성하도록 재설계했습니다. 이제 개발자의 코드 수정 없이 어드민 클릭 한 번으로 시스템에 새 언어를 등록할 수 있습니다.

### 2.2 번역 자동화: 프론트엔드 vs 백엔드 (LLM 활용)
번역 기능을 어디서 수행할 것인가에 대한 고민이 있었습니다. 
* **대안 A (채택): 백엔드(FastAPI)와 Gemini API 연동**
  * *장점*: 서버 단에서 안전한 API Key 관리(`PROD_OFFI_GEMINI_API_KEY`)가 가능하며, 대량의 데이터베이스 레코드를 순차적/제어적으로 처리할 수 있습니다.
  * *단점*: 대용량 처리 시 HTTP 요청 타임아웃 위험 존재.
* **대안 B (기각): 프론트엔드(Client-side) 번역 API 호출**
  * *장점*: 서버 부하 분산.
  * *단점*: 프론트엔드 환경에서 API Key 노출 보안 위험 및 브라우저 네트워크 제약으로 인한 일괄 처리 불안정.

결과적으로 보안과 일괄 처리의 안정성을 위해 **백엔드(FastAPI)에서 Gemini 1.5 Flash를 호출하는 방식(대안 A)**을 선택했습니다.

#### 💡 스마트 번역 전략: "누락(빈칸) 전용 덮어쓰기 방지"
모든 데이터를 무작정 번역하면 사람이 공들여 검수한 기존 번역 데이터가 유실될 위험이 있습니다. 이를 방지하기 위해 다음과 같은 알고리즘을 적용했습니다.
1. 전체 DB 데이터를 로드한 뒤, 타겟 언어의 필드가 **빈 문자열("")인 경우에만** 필터링합니다.
2. 영어(English) 원문을 기반으로 한 최적화된 프롬프트를 구성하여 Gemini 1.5 Flash에 질의합니다.
3. 번역 결과가 반환되면 해당 빈칸에만 안전하게 개별 적재하고, API 쿼터 모니터링 시스템(`Admin_Quotas`)과 연동하여 사용량을 추적합니다.

## 3. Takeaway: 기대 효과 및 향후 과제

이번 아키텍처 개편을 통해 얻은 성과와 앞으로의 개선점은 다음과 같습니다.

### 👍 Pros (기대 효과)
* **확장성 극대화**: 소스 코드 배포 없이 어드민 UI 조작만으로 전 세계 언어를 시스템에 1초 만에 추가할 수 있는 기반을 마련했습니다.
* **생산성 폭발적 향상**: `[✨ 빈칸 자동 번역]` 버튼 클릭 한 번으로 수백 개의 UI 텍스트가 수초 내에 번역되어 글로벌 서비스 런칭 타임투마켓(Time-to-Market)을 단축했습니다.
* **데이터 무결성 확보**: 기존에 사람이 검수한 고품질 번역 데이터는 절대 덮어쓰지 않고, 누락된 데이터만 정확히 타겟팅하여 품질 저하 리스크를 원천 차단했습니다.

### ⚠️ Cons & Mitigations (고려사항 및 한계)
* **서버 타임아웃 이슈**: 향후 지원 국가와 UI 스트링이 수천 개 이상으로 폭증할 경우, 동기(Sync) 방식의 API 요청은 웹 서버 타임아웃을 유발할 수 있습니다.
* **Mitigation (고도화 계획)**: 텍스트 볼륨이 임계치를 넘어서는 시점에 맞춰, 해당 엔드포인트를 **비동기 워커(Celery 또는 FastAPI BackgroundTasks)** 기반으로 전환하고, 어드민 UI에 실시간 프로그레스 바(Progress Bar)를 연동하여 UX를 보완할 예정입니다.

---

초기에는 단순해 보이는 다국어 지원 기능이라도, 비즈니스 확장에 대비하지 않으면 거대한 기술적 부채가 됩니다. 이번 Refactoring은 **"동적 메타데이터 관리 + LLM 서버사이드 파이프라인"**이라는 명확한 Trade-off 분석을 통해, 유지보수성과 확장성이라는 두 토키를 모두 잡은 좋은 사례가 되었습니다.
