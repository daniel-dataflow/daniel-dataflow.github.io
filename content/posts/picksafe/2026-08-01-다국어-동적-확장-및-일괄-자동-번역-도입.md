안녕하세요, PickSafe 백엔드 에디터입니다. 
글로벌 서비스를 지향하는 프로덕트라면 피할 수 없는 관문이 있습니다. 바로 **'다국어 지원(Localization)'**입니다. 

초기 PickSafe는 6개의 주요 언어(한국어, 영어, 일본어, 중국어 간/번체, 포르투갈어)를 소스 코드 내에 하드코딩하는 방식으로 시작했습니다. 하지만 비즈니스가 빠르게 성장하고 글로벌 고객층이 다변화되면서, 이 방식은 곧 개발 병목 현상과 운영 리소스를 갉아먹는 주범이 되었습니다.

이번 포스팅에서는 **새로운 언어 추가 시 소스 코드 수정 비용을 0으로 만들고, AI(LLM) 기반의 안전한 누락 데이터 일괄 번역 파이프라인을 구축한 아키텍처 의사결정 과정(Trade-off)**을 공유하려 합니다.

---

## 1. Problem: 하드코딩된 다국어 시스템의 한계

초기 구조에서는 다음과 같은 세 가지 치명적인 문제가 반복되었습니다.

1. **높은 유지보수 비용 (Dev-Dependency)**: 새로운 언어(예: 스페인어, 프랑스어 등)를 추가할 때마다 프론트엔드 UI 렌더링 코드, 백엔드 API 검증 로직, DB 테이블 컬럼 구성을 모두 수동으로 수정해야 했습니다.
2. **콘텐츠 수급의 병목**: 언어를 추가하더라도 방대한 양의 기존 `ui_string` 데이터를 사람이 일일이 번역해야 하는 막대한 리소스 부족 문제가 발생했습니다.
3. **운영 도구의 부재**: 단건 번역이나 클라이언트 사이드 임시 처리에 의존하다 보니, 특정 언어의 누락된 빈칸을 어드민에서 한 번에 채울 수 있는 자동화된 수단이 없었습니다.

> **"언어 추가는 개발자의 손을 거치지 않고, 번역은 자동화할 수 있는 구조가 필요하다."**

---

## 2. Decision: 동적 렌더링과 백엔드 주도 AI 일괄 번역 파이프라인

이 문제를 해결하기 위해 시스템을 완전한 동적(Dynamic) 구조로 개편하고, 서버 사이드에서 LLM을 활용한 일괄 번역 파이프라인을 구축했습니다.

### ① 다국어(로케일) 동적 렌더링 시스템 설계
* **메타데이터 분리**: 전역으로 지원 가능한 언어 리스트를 백엔드 설정 파일에 상수로 정의(`GLOBAL_LOCALES`)하고, 실제 서비스에서 활성화된 언어 목록은 DB(`system_locales`)에서 관리하도록 변경했습니다.
* **프론트엔드 동적화**: 프론트엔드 코드 내에 하드코딩되어 있던 언어 배열을 전면 제거했습니다. 대신 초기 로드 시 API를 통해 활성화된 언어 목록을 동적으로 받아와 UI(테이블 컬럼, 모달 폼 등)를 그리도록 리팩토링했습니다.
* **결과**: 관리자가 어드민 UI에서 `[+ 언어 추가]` 버튼을 누르는 순간, 소스 코드 배포 없이 즉시 새로운 언어셋이 시스템에 반영됩니다.

### ② 안전한 '빈칸 전용' LLM 일괄 번역 도입 (FastAPI + Gemini API)
번역 자동화를 구현할 때 가장 우려했던 점은 **"이미 사람이 검수한 고품질의 번역 데이터를 AI가 덮어씌워 망가뜨리는 리스크"**였습니다. 이를 방지하기 위해 다음과 같은 아키텍처를 채택했습니다.

* **Client vs Server Trade-off**: 클라이언트(브라우저) 사이드에서 외부 번역 API를 호출하는 방식은 CORS 문제 및 프론트엔드에 API 키가 노출되는 보안 취약점이 있었습니다. 따라서 **안전한 서버 사이드(FastAPI)에서 어드민 전용 시크릿 키를 활용해 API를 호출하는 방식(A방식)**을 선택했습니다.
* **Smart Filtering (누락분 타겟팅)**: 전체 DB를 순회하되, **'타겟 언어의 문자열이 빈칸(Empty string)인 경우'에만** 영어(English) 원문을 기반으로 프롬프트를 구성해 `Gemini 1.5 Flash`에 질의하도록 구현했습니다.
* **안전장치(Data Integrity)**: 이미 채워져 있는 기존 번역 데이터는 절대 건드리지 않고, 오직 누락된 빈칸만 채우기 때문에 기존 데이터의 품질 저하 리스크를 원천 차단했습니다.

---

## 3. Takeaway & Future Work

이번 아키텍처 개편을 통해 얻은 엔지니어링 교훈은 명확합니다.

* **확장성(Scalability) 확보**: 비즈니스 확장 시 개발 파이프라인이 발목을 잡지 않도록, 설정 데이터를 코드가 아닌 DB와 메타데이터 기반으로 격리하는 것의 중요성을 다시 한번 실감했습니다.
* **명확한 Trade-off 관리**: AI 번역을 도입할 때 전체를 일괄 덮어쓰는 무식한 방식 대신, 비즈니스 안전성을 고려해 **"누락분(빈칸)만 타겟팅하는 필터링 로직"**을 넣은 것이 서비스 안정성 유지에 결정적인 역할을 했습니다.

### 💡 향후 개선 과제 (Cons & Mitigations)
현재 구현된 동기(Sync) 방식의 일괄 번역은 데이터가 수천 건 이상으로 폭증할 경우 HTTP 타임아웃을 유발할 수 있습니다. 
이를 해결하기 위해 향후에는 `BackgroundTasks` 혹은 `Celery` 기반의 **비동기 워커 파이프라인**으로 전환하고, 어드민 UI에 실시간 진행률을 보여주는 프로그레스 바(Progress Bar)를 연동하여 사용자 경험을 한 단계 더 고도화할 계획입니다.
