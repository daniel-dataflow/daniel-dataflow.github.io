안녕하세요, PickSafe 개발팀입니다. 
글로벌 서비스를 운영하다 보면 피할 수 없는 과제가 바로 '다국어 지원(Localization)'입니다. 서비스 초기, 우리는 속도와 단순함을 위해 주요 6개국 언어를 하드코딩하는 방식을 선택했습니다. 하지만 비즈니스가 성장하고 지원 국가가 늘어나면서, 이 하드코딩 구조는 개발 생산성을 갉아먹는 거대한 기술 부채로 돌아왔습니다.

이번 포스팅에서는 **하드코딩된 다국어 시스템을 완전한 동적 구조로 전환**하고, **LLM(Gemini API)을 활용해 백엔드 주도의 일괄 자동 번역 파이프라인을 구축**한 아키텍처 의사결정 과정과 트러블슈팅 경험을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 하드코딩이 낳은 3가지 병목 현상

초기 PickSafe는 한국어, 영어, 일본어 등 6개국 언어를 정적 배열과 고정된 DB 컬럼으로 관리하고 있었습니다. 글로벌 고객의 요구가 다양해지면서 다음과 같은 한계에 부딪혔습니다.

1. **높은 유지보수 비용 (High Maintenance Cost)**
   - 새로운 언어(예: 스페인어, 프랑스어)를 추가할 때마다 프론트엔드 렌더링 코드, 백엔드 API 검증 로직, DB 테이블 컬럼 구성을 모두 수동으로 수정해야 했습니다.
2. **번역 리소스 부족**
   - 언어를 추가하더라도 방대한 `ui_string` 데이터를 사람이 일일이 번역하기에는 리소스가 턱없이 부족했습니다.
3. **어드민 자동화 수단의 부재**
   - 기존에는 클라이언트 사이드 번역이나 단건 번역에 의존하여, 관리자(어드민) 페이지에서 특정 언어의 누락된 빈칸을 한 번에 채울 수 있는 자동화된 파이프라인이 없었습니다.

> **"개발자의 코드 수정 없이 어드민에서 언어를 추가하고, 누락된 번역을 원클릭으로 채울 수 있는 구조를 만들자."** 이것이 이번 개편의 핵심 목표였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Decision)

이 문제를 해결하기 위해 시스템을 **동적(Dynamic) 구조**로 개편하고, 번역 자동화 파이프라인을 설계했습니다.

### 2.1 다국어(로케일) 동적 렌더링 시스템 구축
* **메타데이터 사전 정의 및 DB화**: 
  - 백엔드 설정 파일에 글로벌 주요 17개국 이상의 언어 리스트를 상수로 정의(`GLOBAL_LOCALES`)했습니다.
  - 관리자가 어드민 UI에서 `[+ 언어 추가]`를 누르면, 이 중 선택된 언어가 `system_locales` 테이블에 동적으로 적재되도록 설계했습니다.
* **프론트엔드 동적 렌더링**: 
  - 프론트엔드(HTML/JS)에 하드코딩되어 있던 언어 배열을 전면 제거했습니다.
  - 대신 `/admin/locales` API를 통해 활성화된 시스템 설정 언어 목록을 받아와 UI(테이블 칼럼, 모달 입력 폼, 셀렉트박스 등)를 동적으로 그리도록 리팩토링했습니다.

### 2.2 빈칸 자동 일괄 번역 기능 (서버 사이드 A방식 선택)
번역 자동화를 구현할 때 프론트엔드에서 직접 번역 API를 호출하는 방식과 백엔드에서 처리하는 방식을 두고 고민했습니다.

* **고민한 대안**: 
  - 프론트엔드 사이드에서 Google 번역 등 외부 API 호출
  - 백엔드(FastAPI) 서버를 통한 LLM(Gemini API) 일괄 번역
* **최종 선택**: **백엔드(FastAPI) 기반 Gemini API 일괄 번역 파이프라인**
  - **이유**: API Key의 보안 유지, 사용자 편의성(버튼 1회 클릭으로 백그라운드 처리), 그리고 세밀한 데이터 정합성 제어가 필요했기 때문입니다. 어드민 권한의 환경 변수(`PROD_OFFI_GEMINI_API_KEY`)를 백엔드에 안전하게 격리했습니다.
* **누락(빈칸) 전용 번역 전략**:
  - 전체 DB 데이터를 순회하되, **이미 사람이 검수한 기존 번역 데이터는 절대 덮어쓰지 않고**, 타겟 언어의 텍스트가 빈 문자열(`""`)인 경우에만 영어(English) 원문을 기반으로 프롬프트를 구성해 `Gemini 1.5 Flash` 모델에 질의하도록 구현했습니다.

## 3. 기대 효과 및 향후 과제 (Takeaways)

이번 아키텍처 개편을 통해 얻은 성장은 명확했습니다.

* **확장성 극대화**: 개발자의 소스 코드 수정 및 재배포 없이, 어드민 UI 클릭만으로 새로운 글로벌 언어를 시스템에 즉시 추가할 수 있게 되었습니다.
* **생산성 향상**: 새로운 언어를 추가한 직후 `[✨ 빈칸 자동 번역]` 버튼을 누르면 수백 개의 UI 텍스트가 해당 언어로 자동 번역 및 적재되어 즉시 글로벌 서비스 전개가 가능해졌습니다.
* **데이터 안정성 보장**: 기존에 사람이 꼼꼼하게 검수한 번역 데이터는 안전하게 보호하고, 오직 '누락된 빈칸'만 채우는 방식을 통해 품질 저하 리스크를 원천 차단했습니다.

### ⚠️ 남겨진 과제와 Mitigation (서버 타임아웃 대응)
현재는 동기(Sync) 방식으로 일괄 번역을 처리하고 있으나, 향후 지원 국가와 텍스트량이 수천 개 이상으로 폭증할 경우 API 요청 지연에 따른 서버 타임아웃 발생 우려가 있습니다. 
이를 해결하기 위해 향후 텍스트량이 폭증하는 시점에 맞춰 `auto_translate` 엔드포인트를 **비동기 워커(Celery 또는 FastAPI BackgroundTasks)** 방식으로 전환하고, 어드민 UI에 실시간 진행률(Progress Bar)을 제공하는 형태로 고도화할 계획입니다.
