안녕하세요, **PickSafe** 백엔드/아키텍처 에디터입니다. 
서비스가 글로벌로 확장되고 유저 접점이 넓어질수록, 비즈니스 로직의 견고함뿐만 아니라 **보안 컴플라이언스(Compliance)**와 **사용자 경험(UX)**의 아귀를 맞추는 작업이 중요해집니다.

이번 포스팅에서는 최근 도입한 **‘가입 동의 절차 보안 가드(Consent Guard)’**와 **‘알레르기 성분 및 약관 전문 6개 국어 전면 다국어화’** 아키텍처 의사결정 과정을 공유합니다. 어떤 보안 결함이 있었고, 이를 어떻게 아키텍처 레벨에서 깔끔하게 해결했는지 정리했습니다.

---

## 1. Problem: 무엇을 마주했는가?

### ① 보안 결함: 동의 전 서비스 접근 허용 (Broken Authentication Flow)
기존 소셜 로그인(Google/Facebook) 구현에서는 `finalize_login` 시점에 사용자의 필수 약관 동의 여부와 무관하게 즉시 HttpOnly 세션 쿠키가 발급되었습니다. 
이로 인해 사용자가 `/consent` 화면에서 동의를 거부하거나, URL 직접 입력을 시도할 경우 **이미 로그인 상태로 판정되어 메인 서비스와 개인정보 페이지를 자유롭게 이용할 수 있는 심각한 보안 취약점**이 존재했습니다. 개인정보보호법 및 글로벌 프라이버시 규정 관점에서 반드시 해결해야 하는 이슈였습니다.

### ② UX 파편화와 인지 부하
- **중복 노출:** `/consent`와 온보딩(`/onboarding`) 화면 양쪽에 건강 정보 동의 블록이 중복 배치되어 유저에게 혼란을 줬습니다.
- **시각 피드백 부족:** 동의 항목 누락 시 하단 텍스트 경고만 표시될 뿐, 어떤 체크박스가 누락되었는지 시각적 강조(Red Border)나 자동 스크롤 인터랙션이 없어 이탈률을 높이고 있었습니다.

### ③ 글로벌 현지화의 한계
일본어(`JA`), 중국어(`ZH-CN`, `ZH-TW`) 등 비한국어권 유저가 접속했을 때, 복잡한 알레르기 유발 성분명(예: 하이드록시메틸펜틸사이클로헥센카복스알데하이드 등)이 한국어 및 영문 INCI명으로만 고정 노출되었습니다. 약관 문서 역시 주요 로케일 파일이 누락되어 글로벌 서비스로서의 완성도가 떨어졌습니다.

## 2. Trade-off & Architecture: 기술적 고민과 대안 비교

이 문제를 해결하기 위해 백엔드와 프론트엔드 전반에 걸친 아키텍처 개편을 단행했습니다.

### 2.1 3대 필수 약관 Consent Guard 강제화
단순히 프론트엔드 라우터에서만 막는 것은 보안상 무의미합니다. 백엔드와 전역 템플릿 레이어의 다중 방어선(Defense-in-Depth)을 구축했습니다.

1. **OAuth 로그인 리다이렉트 분기 (`auth.py`):**
   - `finalize_login` 단계에서 신규 사용자이거나 필수 3대 약관(`terms_of_service`, `privacy_policy`, `sensitive_health_data`) 동의 이력이 없는 경우, 세션은 발급하되 목적지를 메인이 아닌 `/consent?next=/onboarding`으로 강제 고정했습니다.
2. **전역 템플릿 가드 (`shared.py`, `base.html`):**
   - 로그인 상태이나 필수 동의가 미완료된 유저에게 `needs_consent = True` 플래그를 주입합니다.
   - 클라이언트 사이드 스크립트 및 서버 라우터 레벨에서 `/consent`, `/terms` 등 예외 경로를 제외한 모든 내부 접근을 차단하고 동의 페이지로 리다이렉트시킵니다.

### 2.2 온보딩 흐름 단순화 (Single Source of Truth)
동의 절차는 오직 `/consent` 화면에서만 일괄 처리하도록 책임을 명확히 분리했습니다. `/onboarding` 페이지 내 중복 체크박스를 완전히 제거하여, 유저는 오직 '기피 성분 선택'이라는 본질적인 온보딩 경험에만 집중할 수 있게 아키텍처를 단순화했습니다.

### 2.3 다국어 아키텍처 고도화 (I18n)
- **성분명 로케일 매핑:** 공식 알레르기 성분 26종에 대해 6개 국어(KO, EN, JA, ZH-CN, ZH-TW, PT-BR) 사전을 DB 시드(`bin/seed_multilingual_db.py`)로 구축했습니다. 백엔드 엔드포인트(`/allergens/standard-list` 등)에서 클라이언트의 로케일을 인지하여 `localized_name`을 동적으로 서빙합니다.
- **로케일 폴백 지원:** `docs/consent/` 디렉토리에 지역화 마크다운 파일을 체계적으로 배치하고, `find_consent_file` 헬퍼 함수를 통해 `pt-BR -> pt`, `zh-CN`, `zh-TW` 등 세부 로케일 폴백(Fallback)을 완벽히 지원하도록 설계했습니다.

## 3. Implementation: 주요 구현 내용

변경 사항은 백엔드 라우터, 서비스 레이어, 프론트엔드 템플릿/JS 전반에 걸쳐 유기적으로 반영되었습니다.

| 구분 | 주요 파일 | 핵심 변경 요약 |
| :--- | :--- | :--- |
| **Backend** | `routers/auth.py` | `finalize_login` 시 3대 동의 미완료 유저 `/consent` 강제 분기 |
| **Backend** | `routers/shared.py` | `needs_consent` 전역 가드 및 다국어 마크다운 탐색기(`find_consent_file`) 도입 |
| **Backend** | `services/translation.py` | 성분 번역 헬퍼(`get_ingredient_translation`) 추가 |
| **Frontend** | `templates/base.html` | 전역 리다이렉트 스크립트 주입 |
| **Frontend** | `static/js/consent.js` | 미체크 항목 실시간 빨간 테두리(`border: 2px solid #ef4444`) 및 `smooth scroll` 적용 |
| **Docs** | `docs/consent/*.md` | JA, ZH-CN, ZH-TW 등 9개 다국어 약관 파일 신규 완비 |

## 4. Takeaway: 무엇을 배웠는가?

1. **보안은 프론트가 아니라 백엔드와 전역 레이어에서 완성된다:** 
   사용자가 URL을 직접 조작하거나 뒤로가기를 시도할 수 있는 웹 애플리케이션 환경에서, 인증과 동의 상태 검증은 반드시 서버 진입점(`auth.py` 및 전역 가드)에서 원천 차단해야 안전하다는 점을 다시 한번 확인했습니다.
2. **UX 미세 조정(Micro-interaction)이 프로덕트의 신뢰도를 만든다:** 
   단순한 텍스트 경고를 넘어, 누락된 폼 요소에 `smooth scroll`과 `Red Border`를 적용하고 체크 즉시 인터랙션이 해제되도록 만든 작은 디테일이 서비스의 완성도를 극적으로 끌어올렸습니다.
3. **확장 가능한 글로벌 아키텍처의 기초 공사:** 
   처음부터 다국어 사전을 DB 레벨에서 시드 데이터로 관리하고 폴백 로직을 설계해 둔 덕분에, 향후 새로운 국가 진입 시 비즈니스 로직 수정 없이 콘텐츠 파일과 사전 데이터만 추가하면 되는 확장성(Scalability)을 확보했습니다.
