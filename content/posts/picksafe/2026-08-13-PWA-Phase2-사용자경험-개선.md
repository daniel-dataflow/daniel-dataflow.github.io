안녕하세요, PickSafe 백엔드/프론트엔드 개발팀입니다. 

웹의 도달성과 네이티브 앱의 사용성을 동시에 잡기 위해 PWA(Progressive Web App)를 도입하는 팀이 많습니다. 저희 PickSafe 역시 PWA 기반의 서비스를 구축하며 Phase 1을 성공적으로 마무리했습니다. 

하지만 실제 프로덕션 환경에 배포하고 사용자의 피드백을 수집하면서, **"브라우저가 제공하는 기본 설치 프롬프트(beforeinstallprompt)만으로는 완벽한 네이티브 경험을 주기에 한계가 있다"**는 점을 마주하게 되었습니다. 

이번 글에서는 PWA Phase 2 고도화 과정에서 마주한 UX 단절 문제를 해결하기 위해 **커스텀 설치 모달을 도입하고, 앱 삭제 상태를 동기화하며, 환경별 매니페스트를 동적 분리**한 아키텍처 의사결정(ADR) 과정을 공유합니다.

---

## 1. Problem: 마주한 기술적 난관들

PWA Phase 1 직후, 다음과 같은 사용자 경험(UX) 및 엔지니어링 병목 현상이 발생했습니다.

1. **맥락 없는 기본 프롬프트**: 브라우저가 제공하는 기본 설치 유도 UI는 디자인 일관성이 떨어지고, 사용자가 무심코 닫았을 때 다시 띄우기 어려워 설치 전환율이 정체되었습니다.
2. **앱 삭제 후 상태 불일치 (Ghost State)**: 사용자가 홈 화면에서 PWA를 삭제했음에도 불구하고, 브라우저 스토리지에 남아있는 플래그 때문에 시스템은 "이미 설치된 사용자"로 오인하여 설치 모달을 다시 띄우지 않는 버그가 발견되었습니다.
3. **DEV / PROD 환경 혼선**: 개발(DEV) 환경과 운영(PROD) 환경을 오가며 테스트할 때, 홈 화면에 추가된 PWA 아이콘의 이름과 생김새가 동일하여 QA 과정에서 치명적인 휴먼 에러가 발생했습니다.

---

## 2. Trade-off & Decision: 대안 비교와 기술적 선택

이 문제를 해결하기 위해 팀 내에서 다양한 대안을 검토하고 다음과 같이 아키텍처를 결정했습니다.

### [Decision 1] 브라우저 기본 프롬프트 포기, '커스텀 설치 모달' 구축
* **대안 A**: 브라우저 기본 `prompt()` 이벤트에 전적으로 의존
  * *Pros*: 구현 비용이 거의 없음.
  * *Cons*: 브라우저마다 UI가 상이하고, 사용자가 거절했을 때 재노출 제어가 불가능함.
* **대안 B (선택)**: 브라우저 이벤트를 가로채어(`beforeinstallprompt` 이벤트 방지), 서비스 디자인 시스템이 적용된 **커스텀 모달(`pwaInstallModal`)**을 `base.html`/`base.js`에 구현
  * *Pros*: 서비스 브랜딩 유지, '다음에 하기(Skip)' 버튼을 통한 유연한 제어 가능.
  * *Cons*: 프롬프트 호출 시점과 UI 상태를 직접 관리해야 하는 복잡성 증가.
  * *UX 최적화*: 사용자가 '다음에 하기'를 누를 경우, `localStorage('pwa_skip_until')`에 타임스탬프를 기록하여 **24시간 동안 모달 노출을 제한**함으로써 사용자 피로도를 최소화했습니다.

### [Decision 2] 앱 삭제 감지 및 상태 동기화 로직 (`syncPwaInstallState`)
* 사용자가 홈 화면에서 앱을 삭제하더라도 브라우저의 `localStorage`는 이를 즉시 알 수 없습니다. 
* 이를 해결하기 위해 앱 로드시 현재 실행 환경이 `isStandalone()`(독립 앱 모드)인지 체크하는 로직을 추가했습니다.
* 만약 내부적으로는 "설치됨(`installed`)"으로 마킹되어 있으나, 실제 브라우저 접속 환경이 독립 앱 모드가 아니라면 **"사용자가 앱을 삭제했다"**고 판단하고 상태를 강제로 리셋(Reset)하여 유저가 재설치 유도 모달을 다시 볼 수 있도록 보정했습니다.

### [Decision 3] 정적 파일 대신 백엔드 라우팅을 통한 '동적 매니페스트(Manifest)' 서빙
* **대안 A**: 환경별로 별도의 `manifest.dev.json`, `manifest.prod.json` 파일을 두고 빌드 시점에 교체
  * *Pros*: 백엔드 로직이 단순함.
  * *Cons*: 배포 파이프라인이 복잡해지고 실수로 잘못된 파일이 서빙될 위험이 있음.
* **대안 B (선택)**: `main.py`에 `@app.get("/manifest.json")` 엔드포인트를 두어 백엔드에서 동적으로 JSON을 서빙
  * *Pros*: 서버의 환경 변수(`settings.ENV`)를 참조하여 DEV 환경일 경우 앱 이름을 `"dev.picksafe"`로 동적으로 오버라이딩 가능. QA 및 개발 시각적 안정성 극대화.

---

## 3. Takeaway: 엔지니어링 교훈

이번 PWA 고도화 작업을 통해 얻은 핵심 인사이트는 다음과 같습니다.

1. **웹과 네이티브의 경계에서 오는 UX 예외 처리는 철저해야 한다**: PWA는 웹의 유연함과 앱의 편의성을 동시에 제공하지만, 반대로 두 영역의 상태(브라우저 스토리지 vs 홈 화면 앱 존재 여부)가 어긋날 때 발생하는 엣지 케이스를 개발자가 직접 메워야 합니다.
2. **개발자건축(Developer Experience)도 프로덕트 품질에 직결된다**: DEV/PROD 매니페스트 동적 분리는 단순한 편의 기능처럼 보이지만, QA 단계에서의 오인실수를 원천 차단하여 결과적으로 프로덕션 안정성을 높이는 중요한 아키텍처적 결정이었습니다.

PickSafe 팀은 앞으로도 단순한 기능 구현을 넘어, 사용자와 개발자 모두가 만족하는 견고한 프로덕트 환경을 만들어 가겠습니다. 

감사합니다.
