혼자서 서비스를 기획, 개발, 운영하는 '솔로 파운더(Solo Founder)'에게 가장 두려운 순간은 언제일까요? 아마도 **"잠든 사이에 서버가 죽거나, 무료 AI API 쿼터가 순식간에 고갈되거나, 악의적인 사용자의 공격으로 알림 폭탄이 쏟아지는 상황"**일 것입니다.

24시간 교대 근무나 상주 모니터링이 불가능한 1인 개발 환경에서, 저는 서비스 정식 오픈을 앞두고 **"시스템이 스스로 1차 방어를 하고, 꼭 필요한 상황에만 모바일 슬랙으로 조기 경보를 보내는 구조"**를 목표로 종합 가드레일을 설계하고 구현했습니다. 

이번 글에서는 무료 인프라(Render, Neon DB)의 제약 속에서 마주한 기술적 문제들과, 이를 해결하기 위해 채택한 아키텍처적 트레이드오프(Trade-off), 그리고 1인 운영을 지탱하는 5대 가드레일 구축 경험을유별하게 공유합니다.

---

## 1. 1인 개발 환경의 현실적 제약과 해결해야 할 문제(Problem)

PickSafe는 성분 분석 및 스캔 서비스를 제공하는 웹 애플리케이션으로, 다음과 같은 인프라 환경 위에서 동작합니다.

* **Backend**: Render Web Service (RAM 512MB 제약)
* **Database**: Neon PostgreSQL (서버리스 환경, 인위적 Keep-Alive 지양 원칙)
* **AI Engine**: Google Gemini API (분당 15회 RPM, 일일 1,500회 RPD 무료 티어)

이러한 제약 속에서 서비스가 오픈되었을 때 발생할 수 있는 시나리오는 1인 개발자에게 치명적입니다.
1. **AI 쿼터 조기 고갈**: 동일한 이미지나 반복적인 요청으로 인해 소중한 무료 AI 쿼터가 몇 시간 만에 바닥나는 현상.
2. **서버 메모리(OOM) 크래시**: 유저가 업로드한 수십 MB짜리 고해상도 이미지가 512MB RAM 서버를 다운시키는 현상.
3. **Alert Fatigue (알림 피로)**: 장애나 CS 유입 시 슬랙 알림이 초당 수십 개씩 와서 개발자의 멘탈을 흔드는 현상.
4. **보안 사각지대**: 무차별 대입(Brute-Force) 공격과 크롤러의 무분별한 서버 자원 낭비.

## 2. 기술적 고민과 아키텍처 대안 비교 (Trade-offs)

### ① AI 쿼터 방어와 오인식 방지의 딜레마
* **고민**: API 호출을 줄이기 위해 이미지 해시(SHA-256) 기반 캐싱을 도입하려 했으나, OCR(광학 문자 인식)이 간헐적으로 오인식할 경우 **잘못된 분석 결과가 캐시되어 다른 사용자에게 영구적으로 전파되는 위험**이 있었습니다.
* **해결 (4중 가드레일)**:
  1. 공식 DB와 매칭된 성분이 3개 미만인 불량 스캔은 캐시에 등록하지 않습니다 (`matched_count >= 3`).
  2. 사용자가 강제 재분석을 원할 경우 캐시를 무시하는 파라미터(`force_reanalysis=true`)를 제공합니다.
  3. 60일 TTL을 두어 오래된 캐시는 자연 만료시킵니다.
  4. OCR 원문만 캐싱하고, 사용자별 맞춤형 기피 성분 판정은 매번 실시간으로 연산합니다.

### ② 슬랙 알림 폭탄(Alert Fatigue) 방어: 즉시성과 취합의 조율
* **고민**: 고객 문의나 에러가 급증할 때 모든 건을 실시간으로 슬랙에 보내면 알림 폭탄으로 인해 진짜 중요한 장애 징후를 놓치게 됩니다. 그렇다고 무조건 묶어서 보내면 긴급 CS 대응이 느려집니다.
* **해결 (스마트 윈도우 다이제스트 아키텍처)**:
  * **첫 번째 이벤트**: 1초 만에 슬랙으로 **즉시 발송**하여 1인 운영자가 초고속으로 인지하게 합니다. 동시에 3분(180초) 동안의 인메모리 버퍼 취합 윈도우를 가동합니다.
  * **3분 윈도우 내 추가 이벤트**: 개별 알림을 차단하고 버퍼에 조용히 적재합니다.
  * **3분 만료 시**: 모인 이벤트들을 단 1장의 요약 리포트로 묶어서 **1회만 발송**합니다.
  * 이 방식을 통해 동시 문의 50건이 들어와도 "최초 1회 즉시 알림"과 "3분 뒤 취합 보고"로 개발자의 집중력을 지켜냅니다.

## 3. 핵심 엔지니어링 구현 내용

### 🛡️ 메모리 OOM 방어: 클라이언트 & 서버 2중 압축
* **클라이언트 1차 방어**: 브라우저 레벨에서 10MB를 초과하는 대용량 파일은 서버 전송 전에 즉시 차단합니다.
* **백엔드 2차 방어**: 서버로 유입된 이미지가 가로/세로 1800px를 초과할 경우, Python Pillow 라이브러리를 통해 `thumbnail((1800, 1800))` 처리를 거쳐 JPEG 85% 품질로 압축합니다. 수십 MB의 원본이 300KB 수준으로 줄어들어 Render 무료 티어(RAM 512MB) 환경에서도 OOM 크래시가 발생하지 않습니다.

### 🛡️ 엔터프라이즈 급 보안: Rate Limiting과 Tarpit
* **문의 엔드포인트 보호**: 마이페이지 1:1 고객 문의(`POST /mypage/inquiries`)에 Rate Limiting을 적용하여 분당 최대 5회로 제한, 스크립트 매크로를 통한 슬랙 알림 도배를 차단합니다.
* **관리자 로그인 보호**: 관리자 로그인(`POST /admin/login`) 실패 시 의도적인 **1초 지연(Tarpit, `asyncio.sleep(1.0)`)**을 주입하고 분당 10회로 제한하여 무차별 대입(Brute-Force) 공격을 원천 무력화했습니다.

## 4. 무엇을 배웠는가 (Takeaways)

1. **1인 운영 시스템의 핵심은 '방어력'이다**: 화려한 기능보다도, 서버가 예상치 못한 자원 고갈이나 공격으로부터 스스로 살아남을 수 있는 안전장치(Rate Limit, OOM 방어, 캐싱)를 먼저 구축하는 것이 서비스 지속 가능성을 결정합니다.
2. **알림도 UX다 (Alert Fatigue 고려)**: 개발자를 위한 모니터링 알림 역시 사용자 경험처럼 다뤄야 합니다. 디바운싱(Debouncing)과 버퍼링 취합 전략을 통해 '꼭 필요한 때에만 정확한 정보'를 전달받는 구조를 만든 것은 최고의 선택이었습니다.
3. **완벽한 제약 속의 창의성**: 무료 인프라와 512MB RAM이라는 한계는 오히려 불필요한 비용을 줄이고, 아키텍처를 치밀하게 다듬게 만드는 훌륭한 촉진제가 되었습니다.

서비스 오픈을 준비하며 구축한 이 5대 가드레일 덕분에, 이제 저는 안심하고 깊은 잠을 잘 수 있게 되었습니다. 1인 개발 및 소규모 팀에서 안정적인 서비스를 고민하시는 분들에게 이 글이 작은 인사이트가 되었기를 바랍니다.
