안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스가 성장함에 따라 사용자 유입 경로를 파악하고 시스템 안정성을 모니터링하기 위한 어드민 기능의 필요성이 대두되었습니다. 

일반적으로는 Google Analytics(GA) 같은 외부 솔루션을 도입하는 것이 정석이지만, 이번 프로젝트에서는 **프라이버시 존중, 오프라인 PWA 환경 최적화, 그리고 불필요한 외부 네트워크 의존성 제거**를 목표로 **자체 방문자 분석 및 로그 모니터링 시스템**을 직접 구축하기로 결정했습니다.

이번 글에서는 가벼우면서도 강력한 FastAPI 기반의 아키텍처를 설계하면서 마주한 기술적 고민과 트레이드오프, 그리고 구현 과정의 인사이트를 공유하고자 합니다.

---

## 1. Problem: 왜 외부 솔루션 대신 '자체 구축'을 선택했는가?

서비스 초기, 트래픽 분석과 에러 추적을 위해 상용 서드파티 툴을 검토했습니다. 하지만 우리 서비스가 가진 고유한 제약 사항들이 있었습니다.

1. **프라이버시 및 보안:** 사용자 IP나 민감한 트래픽 데이터가 제3자 서비스로 전송되는 것을 최소화해야 했습니다.
2. **오프라인 PWA 성격 유지:** 네트워크가 불안정한 환경이나 특정 프라이버시 브라우저 환경에서도 내부 로깅이 안정적으로 동작해야 했습니다.
3. **통합 대시보드 필요:** 어드민 페이지 내에서 방문자 통계(PV/UV)와 실시간 서버 에러 로그(500 에러, API 실패 등)를 한눈에 모니터링할 수 있는 일원화된 인터페이스가 필요했습니다.

결론적으로, 무거운 외부 SDK를 붙이기보다는 **FastAPI 미들웨어와 관계형 데이터베이스를 활용한 자체 로깅 파이프라인**을 구축하는 것이 유지보수와 커스텀 측면에서 훨씬 유리하다고 판단했습니다.

---

## 2. Architecture & Trade-off: 어떻게 설계할 것인가?

### 2.1 미들웨어 기반 트래킹 (Visitor Analytics)
모든 HTTP 요청을 가로채서 로깅하기 위해 **FastAPI Middleware**를 도입했습니다. 

* **대상 필터링:** 불필요한 I/O 발생을 막고 성능을 최적화하기 위해, 정적 파일(`CSS`, `JS`, `/static/` 등) 요청은 미들웨어 단계에서 조기에 필터링(Early Return)합니다.
* **개인정보 보호 (IP 해싱):** 개인정보 보호법 및 보안을 고려하여 원본 IP 주소는 DB에 그대로 저장하지 않고, **단방향 해시(예: SHA-256 등)** 처리하여 `ip_hash`로 저장합니다. 이를 통해 개인정보를 보호하면서도 고유 방문자(UV)를 정확하게 집계할 수 있습니다.
* **UA 파싱 및 컨텍스트 수집:** `User-Agent` 원문을 바탕으로 브라우저와 OS 정보를 파싱하고, 접속 언어(`Locale`), 유입 경로(`Referer`) 등을 함께 수집하여 마케팅 및 기술 환경 분석 지표로 활용합니다.

### 2.2 데이터베이스 설계 (`visitor_logs` 테이블)
고속 인서트와 대용량 집계 쿼리를 모두 고려한 스키마를 설계했습니다.

```sql
CREATE TABLE visitor_logs (
    id VARCHAR(36) PRIMARY KEY,
    ip_hash VARCHAR(64) NOT NULL,       -- IP 단방향 해시 (개인정보 보호 및 UV 측정)
    session_id VARCHAR(100) NOT NULL,   -- 브라우저 세션 식별자
    user_id VARCHAR(36) REFERENCES users(id) ON DELETE SET NULL, -- 로그인 유저 매핑
    path VARCHAR(255) NOT NULL,         -- 요청 경로
    method VARCHAR(10) NOT NULL,        -- HTTP Method (GET, POST 등)
    user_agent TEXT,                    -- User-Agent 원문
    browser VARCHAR(50),                -- 파싱된 브라우저명
    os VARCHAR(50),                     -- 파싱된 OS명
    locale VARCHAR(10),                 -- 접속 언어
    referer TEXT,                       -- 유입 경로
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 시계열 집계 쿼리 성능을 위한 인덱스
CREATE INDEX idx_visitor_logs_created_at ON visitor_logs(created_at);
```

**Trade-off 고민:** 
모든 HTTP 요청마다 DB에 `INSERT`를 수행하면 트래픽이 몰릴 때 DB I/O 부하가 발생할 수 있습니다. 
* *대안:* Redis 같은 인메모리 저장소에 버퍼링 후 배치(Batch) 인서트하는 방식.
* *선택:* 현재 단계에서는 시스템의 단순성과 인프라 복잡도를 낮추기 위해 직접 DB에 적재하되, `created_at` 인덱스를 통해 대시보드 집계 쿼리의 성능 저하를 방어하는 방식을 택했습니다. 향후 트래픽이 급증할 경우 비동기 큐(Celery 등)나 Redis 버퍼링 레이어로 확장할 예정입니다.

## 3. Implementation: 어드민 모니터링 기능 구현

구축된 데이터를 기반으로 어드민 대시보드에 다음과 같은 실용적인 기능들을 구현했습니다.

1. **개요 (Summary Metrics):** 
   * 지정 기간 내 전체 페이지 뷰(PV)와 `ip_hash`/`session_id` 기준의 고유 방문자(UV) 산출
   * 최근 30분 이내 활동 기록을 기반으로 한 '활성 세션 수' 트래킹
   * User-Agent 파싱 데이터를 활용한 브라우저/OS 점유율 도넛 차트 렌더링
2. **시스템 및 에러 로그 모니터링:**
   * 시스템 내부 크래시(500 에러), 외부 API 연동 실패 로그 등을 심각도(`INFO`, `WARNING`, `ERROR`)별로 필터링하여 조회
   * 관리자가 긴급 상황 시 백엔드 로그 파일(`.log`)을 즉시 다운로드할 수 있는 기능 제공

## 4. Takeaway: 엔지니어링 교훈

* **오버엔지니어링 경계:** 처음부터 거대한 모니터링 인프라(ELK 스택 등)를 구축하기보다, 현재 비즈니스 규모에 맞는 FastAPI 미들웨어와 DB 인덱스 조합만으로도 충분히 빠르고 실용적인 분석 시스템을 만들 수 있었습니다.
* **보안과 데이터 활용의 균형:** IP를 그대로 저장하는 대신 **해싱(Hashing)** 기법을 적용하여 프라이버시 이슈를 원천 차단하면서도, 서비스 지표(UV) 측정이라는 비즈니스 요구사항을 모두 만족시킬 수 있었습니다.

자체 구축한 모니터링 시스템 덕분에 외부 유출 없는 안전한 데이터 파이프라인을 확보했으며, 서비스 운영의 투명성이 한층 높아졌습니다. 앞으로는 수집된 데이터를 바탕으로 유저 세션 코호트 분석까지 확장해 나갈 계획입니다.
