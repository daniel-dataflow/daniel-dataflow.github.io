안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스를 고도화하면서 마주하는 수많은 기술적 고민 중 하나는 **"어떻게 사용자 분석과 시스템 모니터링을 가져갈 것인가"**입니다. 

일반적으로는 Google Analytics(GA)나 Datadog, Sentry 같은 강력한 외부 SaaS 솔루션을 도입하는 것이 정석으로 여겨집니다. 하지만 우리 서비스는 **오프라인 PWA 성격**을 띠고 있으며, **사용자의 프라이버시를 최우선**으로 보호해야 하는 도메인적 특성이 있었습니다. 

이번 글에서는 외부 무거운 솔루션 의존성을 배제하고, **FastAPI 미들웨어와 커스텀 로깅을 활용해 자체 방문자 분석 및 실시간 로그 모니터링 시스템을 구축한 아키텍처적 의사결정과 트레이드오프**를 공유하려 합니다.

---

## 1. Problem: 왜 외부 분석 툴 대신 '자체 구축'을 선택했는가?

초기 서비스 기획 단계에서 표준적인 사용자 분석 도구 도입을 검토했으나, 다음과 같은 뚜렷한 한계점(Pain Points)에 부딪혔습니다.

1. **프라이버시 이슈와 규정 준수:** 외부 서드파티 스크립트를 주입하는 방식은 사용자 IP나 행동 패턴이 외부 서버로 직접 전송되는 문제를 야기합니다. PWA 환경에서 유저의 데이터 주권과 프라이버시를 엄격히 지키고 싶었습니다.
2. **도메인 맞춤형 지표 부족:** 단순 페이지 뷰(PV) 외에도 우리 서비스만의 특화된 인터랙션 로그를 실시간으로 결합하여 어드민 대시보드에 즉시 렌더링해야 했습니다.
3. **비용 및 오버헤드:** 초기 단계에서 무거운 외부 솔루션의 유료 티어로 전환되는 비용을 방지하고, 단일 서버 환경 내에서 가볍고 완결성 있는 모니터링 구조를 지향했습니다.

결론적으로, **"FastAPI의 미들웨어(Middleware)를 활용해 HTTP 요청을 가로채고, 최소한의 정보만 안전하게 가공하여 자체 DB에 적재하자"**는 방향성으로 가닥을 잡았습니다.

---

## 2. Architecture & Trade-off: 어떻게 설계하고 구현할 것인가?

### 2.1 미들웨어 기반 트래킹 & 개인정보 보호 (Privacy-First)
FastAPI의 HTTP 미들웨어를 활용해 정적 파일(`.css`, `.js`, `/static/` 등)을 제외한 모든 유효한 페이지 뷰 요청(`GET`, `POST` 등)을 감지합니다. 

여기서 가장 중요한 기술적 고민은 **개인정보 보호**였습니다. IP 주소는 개인식별정보(PII)에 해당하므로, 원본을 그대로 저장하지 않고 **단방향 해시(Hashing)** 처리하여 `ip_hash` 컬럼에 저장합니다. 이를 통해 개인정보 침해 우려를 원천 차단하면서도, 고유 방문자 수(UV)와 중복 방문 여부는 정확히 집계할 수 있도록 설계했습니다.

```sql
-- 방문자 로그 저장을 위한 핵심 스키마 구조 (보안 마스킹 적용)
CREATE TABLE visitor_logs (
    id VARCHAR(36) PRIMARY KEY,
    ip_hash VARCHAR(64) NOT NULL,       -- IP 주소 단방향 해시
    session_id VARCHAR(100) NOT NULL,   -- 브라우저 세션 식별자
    user_id VARCHAR(36) REFERENCES users(id) ON DELETE SET NULL, 
    path VARCHAR(255) NOT NULL,         -- 방문 경로
    method VARCHAR(10) NOT NULL,        -- HTTP Method
    browser VARCHAR(50),                -- 파싱된 브라우저명 (User-Agent 기반)
    os VARCHAR(50),                     -- 파싱된 운영체제명
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_visitor_logs_created_at ON visitor_logs(created_at);
```

### 2.2 어드민 실시간 로그 및 통계 대시보드
수집된 데이터는 어드민 페이지에서 다각도로 활용됩니다.
* **Summary Metrics:** 총 PV, UV, 최근 30분 내 활성 세션 수, 접속 브라우저/OS 분포(User-Agent 파싱 데이터 기반 도넛 차트 렌더링).
* **Log Monitoring:** 시스템 내부 크래시나 API 장애 로그를 심각도별(INFO, WARNING, ERROR)로 필터링하고, 어드민 화면에서 최근 로그 라인을 스트리밍 형태로 조회할 수 있도록 구성했습니다.

### ⚠️ Trade-off 분석
* **Pros (장점):** 외부 네트워크 호출 없이 자체 DB 내에서 모든 통계와 로그를 처리하므로 데이터 소유권이 온전히 우리에게 있으며, 프라이버시 규슈로부터 자유롭습니다. 또한 어드민 화면과의 밀접한 실시간 연동이 가능합니다.
* **Cons (단점):** 트래픽이 폭증할 경우 `visitor_logs` 테이블에 쓰기(Write) 부하가 집중될 수 있습니다. 
* **Mitigation (완화 전략):** `created_at` 컬럼에 인덱스를 걸어 집계 쿼리 성능을 최적화하고, 추후 트래픽이 커질 경우 로그 수집 전용 가벼운 NoSQL이나 로컬 버퍼(Queue)를 두는 방식으로 확장할 수 있도록 아키텍처의 결합도를 낮추어 설계했습니다.

## 3. Takeaway: 엔지니어링 교훈

이번 자체 모니터링 시스템 구현을 통해 얻은 핵심 배움은 다음과 같습니다.

1. **"필요한 만큼만" 만드는 기술적 용기:** 모든 기능을 거대한 서드파티 솔루션에 의존할 필요는 없습니다. 비즈니스의 규모와 보안 요구사항(프라이버시)에 맞춰 직접 코어 로직을 구현하는 것이 오히려 아키텍처의 복잡도를 낮추고 제어권을 높이는 길이 될 수 있습니다.
2. **개인정보 보호는 설계 단계부터:** 데이터를 저장하는 순간부터 보안 이슈가 발생합니다. IP 해시화 같은 안전장치를 초기 DB 설계 단계부터 반영함으로써 법적 리스크와 보안 부채를 사전에 차단할 수 있었습니다.
3. **FastAPI 미들웨어의 강력함:** 비즈니스 로직을 오염시키지 않고, 횡단 관심사(Cross-Cutting Concern)인 로깅과 트래킹을 미들웨어 레벨에서 우아하게 처리할 수 있음을 재확인했습니다.

PickSafe는 앞으로도 불필요한 의존성을 경계하고, 서비스의 본질과 보안에 집중하는 탄탄한 아키텍처를 만들어 나갈 것입니다.
