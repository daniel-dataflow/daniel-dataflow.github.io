안녕하세요, PickSafe 백엔드 개발팀입니다. 

서비스를 운영하면서 유저의 행동 패턴을 파악하고 시스템 에러를 모니터링하는 것은 필수적입니다. 보통 이 요구사항을 해결하기 위해 Google Analytics(GA) 같은 외부 솔루션을 도입하거나 무거운 APM(Application Performance Monitoring) 툴을 연동하곤 합니다.

하지만 이번 프로젝트에서는 **프라이버시를 존중하고, 오프라인 PWA(Progressive Web App) 환경의 가벼움을 유지**한다는 핵심 가치를 지키기 위해, **FastAPI 미들웨어와 자체 DB를 활용한 인하우스 방문자 분석 및 로그 모니터링 시스템**을 직접 구축하기로 결정했습니다. 

이번 글에서는 외부 솔루션 대신 자체 로깅 시스템을 설계하면서 마주한 기술적 고민과 트레이드오프, 그리고 이를 해결한 아키텍처를 공유합니다.

---

## 1. Problem: 왜 외부 솔루션 대신 자체 로깅 시스템을 선택했는가?

초기 서비스 기획 단계에서 아래와 같은 제약 사항과 요구가 있었습니다.

1. **개인정보 보호 및 규정 준수:** 민감할 수 있는 유저의 IP 주소와 식별자를 외부 서드파티 서버에 그대로 전송하는 것은 보안상 리스크가 컸습니다.
2. **PWA 환경 및 가벼운 아키텍처:** 무거운 외부 스크립트 로딩을 최소화하여 서비스 로딩 속도와 오프라인 가동성을 해치지 않아야 했습니다.
3. **통합 대시보드 필요:** 방문자 통계(PV/UV)뿐만 아니라 시스템 내부 에러 로그, API 실패 로그를 하나의 어드민 화면에서 실시간으로 확인하고 관리할 수 있어야 했습니다.

결과적으로, **"우리가 직접 트래픽을 인터셉트하여 필요한 메트릭만 안전하게 가공하고 저장하자"**는 결론에 이르렀습니다.

---

## 2. Technical Decisions & Trade-offs (기술적 고민과 대안)

### A. 데이터 수집: 서드파티 스크립트 vs FastAPI 미들웨어
* **대안 1 (프론트엔드 스크립트):** 클라이언트 측에서 뷰(View)벤트를 수집하여 전송하는 방식. Ad-blocker에 의해 트래픽이 유실될 수 있고, PWA 환경에서 네트워크 제약이 존재합니다.
* **대안 2 (백엔드 미들웨어 - 선택):** FastAPI의 HTTP 미들웨어를 활용해 서버로 들어오는 모든 요청을 가로채어 처리하는 방식.
  * **Trade-off:** 모든 HTTP 요청마다 미들웨어 로직이 실행되므로 오버헤드가 발생할 수 있습니다. 이를 해결하기 위해 정적 파일(`static`, `.css`, `.js` 등) 요청은 필터링하여 제외하고, 핵심 페이지 뷰(`GET /`, `GET /result`, `POST /scan` 등)만 비동기적으로 처리하도록 설계했습니다.

### B. 개인정보 보호: IP 원문 저장 vs 단방향 해시
* **문제:** 고유 방문자(UV)를 측정하기 위해 IP와 세션 정보가 필요하지만, 원본 IP를 DB에 저장하는 것은 보안 및 프라이버시 측면에서 위험합니다.
* **해결:** IP 주소는 수집 즉시 단방향 해시(`ip_hash`) 처리를 거쳐 저장하도록 구현했습니다. 이를 통해 개인정보 유출 위험을 원천 차단하면서도, 동일 방문자의 중복 방문 여부나 고유 방문자 수(UV)는 정확하게 집계할 수 있게 되었습니다.

## 3. Architecture & Implementation (아키텍처 및 구현)

### 3.1 데이터베이스 설계 (`visitor_logs`)
방문자의 유입 경로와 환경을 정밀하게 분석하기 위해 최소한의 필수 메트릭만 담은 스키마를 설계했습니다.

* 주요 필드:
  * `id`: 식별용 UUID
  * `ip_hash`: 개인정보 보호를 위한 IP 단방향 해시값
  * `session_id` & `user_id`: 세션 브라우저 식별 및 로그인 유저 매핑
  * `path` & `method`: 요청 경로 및 HTTP 메서드
  * `user_agent`, `browser`, `os`: 접속 환경 파싱 데이터
  * `created_at`: 타임스탬프 (인덱스 생성으로 기간별 조회 성능 최적화)

### 3.2 어드민 모니터링 시스템 구성
구축된 로그 데이터를 바탕으로 어드민 대시보드에 다음과 같은 기능을 구현했습니다.

1. **개요 (Summary Metrics):** 전체 PV, 고유 방문자(UV), 최근 30분 활성 세션 수 집계 및 User-Agent 기반 브라우저/OS 분포 시각화.
2. **세션 분석 (Session Cohort):** 유저 세션별 평균 체류 시간 및 페이지 이동 흐름 트래킹.
3. **실시간 로그 모니터링:** 시스템 내부 크래시(500 에러), API 실패 로그 등을 심각도(INFO, WARNING, ERROR)별로 필터링하고 실시간으로 스트리밍 조회.

## 4. Takeaways (엔지니어링 교훈)

1. **목적에 맞는 최소한의 도구 선택:** 무조건 유명한 서드파티 솔루션을 붙이기보다, 서비스의 성격(프라이버시 강조, PWA 환경)에 맞춰 자체 시스템을 구축하는 것이 장기적으로 데이터 주권과 커스텀 유연성 측면에서 큰 이점이 있었습니다.
2. **보안과 데이터 분석의 균형:** IP를 그대로 저장하지 않고 단방향 해시 처리를 거침으로써, 개인정보 규제 이슈를 피하면서도 정확한 비즈니스 지표(UV)를 산출할 수 있는 아키텍처적 타협점을 찾았습니다.
3. **확장성 고려:** 초기 설계 단계부터 인덱스 전략(`created_at` 등)과 정적 자원 필터링 로직을 미들웨어에 반영하여, 트래픽이 증가하더라도 DB 부하와 응답 지연을 최소화할 수 있도록 대비했습니다.

이번에 구축한 인하우스 로깅 및 분석 시스템은 앞으로 서비스가 성장함에 따라 알림 연동, 이상 탐지(Anomaly Detection) 등 다양한 기능으로 확장할 수 있는 튼튼한 기반이 될 것입니다.
