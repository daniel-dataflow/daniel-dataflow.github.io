안녕하세요, PickSafe 백엔드 에디터입니다. 
이번 글에서는 서비스 초기 단계에서 **외부 분석 솔루션(Google Analytics 등)의 무거움과 프라이버시 이슈를 해결하기 위해, FastAPI 미들웨어와 자체 DB를 활용해 경량 방문자 분석 및 실시간 로그 모니터링 시스템을 구축한 아키텍처 의사결정 과정**을 공유합니다.

---

## 1. Problem: 왜 외부 분석 툴 대신 '자체 로깅 시스템'을 만들었는가?

서비스가 성장함에 따라 사용자 유입 경로, 브라우저/OS 분포, 그리고 실시간 에러 모니터링은 필수적인 요구사항이 되었습니다. 초기에는 Google Analytics(GA)나 서드파티 로그 수집 솔루션을 고려했으나, 다음과 같은 뚜렷한 한계에 부딪혔습니다.

1. **프라이버시 및 PWA 성격 유지:** 우리 서비스는 오프라인 PWA 성격을 지향하며, 유저의 민감한 데이터가 외부 서드파티 서버로 전송되는 것을 최소화하고 싶었습니다.
2. **비즈니스 도메인과의 밀접한 결합:** 단순 페이지 뷰(PV)뿐만 아니라, 내부 회원(`users` 테이블)과 세션, 그리고 특정 API 요청(`.scan` 등)과의 연계 분석이 필요했습니다.
3. **무거운 스크립트 로딩 지연:** 프론트엔드에 무거운 서드파티 스크립트를 심는 것은 초기 로딩 성능(Lighthouse 점수)에 악영향을 줍니다.

결론적으로, **"백엔드 레벨에서 가볍게 트래픽을 가로채고(Interception), 개인정보를 안전하게 익명화하여 자체 DB에 쌓자"**는 방향으로 결론을 내렸습니다.

## 2. Trade-off & Architecture: 기술적 고민과 대안 비교

### 2.1 데이터 수집 방식: 미들웨어(Middleware) vs 데코레이터(Decorator)
* **대안 A (Route Decorator):** 분석이 필요한 각 엔드포인트마다 데코레이터를 붙이는 방식.
  * *단점:* 휴먼 에러로 인해 로깅을 누락할 위험이 크고, 비즈니스 로직 코드와 관심사가 강하게 결합됨.
* **대안 B (FastAPI HTTP Middleware) — [선택]:** 전역 미들웨어에서 정적 파일(`.css`, `.js`, `/static/`)을 필터링하고, 모든 핵심 라우트(`GET /`, `POST /scan` 등)의 요청을 일괄 가로채는 방식.
  * *장점:* 비즈니스 코드 수정 없이 전역에서 일관된 로깅 보장.

### 2.2 개인정보 보호와 식별의 트레이드오프 (IP 해싱)
방문자 분석을 위해서는 고유 방문자(UV)를 측정해야 하지만, 원본 IP를 그대로 저장하는 것은 개인정보 보호법 및 보안 관점에서 위험합니다.
* **해결책:** IP 주소를 그대로 저장하는 대신, 단방향 해시 함수(`ip_hash VARCHAR(64)`)를 적용하여 **"개인 식별은 불가능하지만, 동일 사용자의 중복 방문 여부는 판별할 수 있는 상태"**를 구현했습니다. 또한, 로그인한 유저는 `user_id`를 외래 키로 매핑하여 세션과 유저 행동을 입체적으로 추적할 수 있게 설계했습니다.

## 3. Implementation: 핵심 설계 및 구현

### 3.1 데이터베이스 스키마 설계 (`visitor_logs`)
고성능 집계 쿼리와 유연한 분석을 위해 정규화된 로그 테이블을 설계했습니다.

```sql
CREATE TABLE visitor_logs (
    id VARCHAR(36) PRIMARY KEY,
    ip_hash VARCHAR(64) NOT NULL,       -- IP 단방향 해시 (개인정보 보호 및 UV 측정용)
    session_id VARCHAR(100) NOT NULL,   -- 세션 브라우저 식별자
    user_id VARCHAR(36) REFERENCES users(id) ON DELETE SET NULL, -- 로그인 유저 매핑
    path VARCHAR(255) NOT NULL,         -- 방문 경로 (예: '/', '/scan')
    method VARCHAR(10) NOT NULL,        -- HTTP Method (GET, POST)
    user_agent TEXT,                    -- User-Agent 원문
    browser VARCHAR(50),                -- 파싱된 브라우저명 (Chrome, Safari 등)
    os VARCHAR(50),                     -- 파싱된 OS명 (iOS, Android 등)
    locale VARCHAR(10),                 -- 유저 접속 언어
    referer TEXT,                       -- 유입 경로
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 시계열 집계 쿼리 최적화를 위한 인덱스
CREATE INDEX idx_visitor_logs_created_at ON visitor_logs(created_at);
```

### 3.2 어드민 대시보드 및 실시간 로그 모니터링
수집된 데이터를 바탕으로 어드민 전용 분석 기능을 구현했습니다.
* **개요(Summary):** 지정 기간 내 PV, UV, 최근 30분 활성 세션 수 집계 및 User-Agent 기반 브라우저/OS 분포 시각화.
* **에러 로그 모니터링:** 시스템 내부 크래시(500 에러) 및 외부 API 연동 실패 로그를 심각도별(INFO, WARNING, ERROR)로 파싱하여 관리자가 즉시 필터링하고 원문 `.log` 파일을 다운로드할 수 있는 기능 제공.

## 4. Takeaway: 이번 아키텍처를 통해 배운 것들

1. **"오버엔지니어링 경계하기":** 처음부터 복잡한 빅데이터 처리 파이프라인(Kafka, ElasticSearch 등)을 구축하는 대신, 관계형 DB와 적절한 인덱싱(`created_at`)만으로도 중소규모 서비스의 트래픽 분석과 로그 모니터링은 충분히 감당할 수 있음을 확인했습니다.
2. **프라이버시-by-Design:** 초기 설계 단계부터 IP 해싱 처리를 도입함으로써, 추후 발생할 수 있는 보안 및 프라이버시 이슈를 원천 차단했습니다.
3. **관심사의 분리(SoC):** FastAPI 미들웨어를 활용해 비즈니스 로직과 트래킹 로직을 철저히 분리함으로써 코드의 유지보수성을 크게 높였습니다.

PickSafe는 앞으로도 불필요한 서드파티 의존성을 줄이고, 가볍고 독립적인 아키텍처를 만들어 나가는 과정을 공유하겠습니다. 감사합니다!
