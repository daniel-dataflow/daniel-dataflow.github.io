안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스가 성장함에 따라 유저의 유입 경로를 파악하고 시스템 안정성을 모니터링하기 위한 대시보드의 필요성이 대두되었습니다. 

일반적으로는 Google Analytics(GA)나 Datadog 같은 외부 SaaS 솔루션을 도입하는 것이 정석이지만, 이번 프로젝트에서는 **프라이버시 보호, 오프라인 PWA 성격 유지, 그리고 불필요한 외부 네트워크 레이턴시 제거**를 위해 **FastAPI 미들웨어와 자체 데이터베이스를 활용한 경량화된 자체 로깅·모니터링 시스템**을 직접 구축하기로 결정했습니다.

이번 포스팅에서는 이 시스템을 설계하면서 마주한 기술적 고민(Trade-off)과 해결 과정을 공유합니다.

---

## 1. Problem: 왜 무거운 외부 솔루션 대신 '자체 로깅 시스템'을 선택했는가?

초기 서비스 아키텍처를 구상할 때 마주한 제약 조건은 명확했습니다.
1. **개인정보 보호 (Privacy-First):** 유저의 원본 IP 주소나 민감한 세션 정보를 서드파티 서버로 전송하는 것을 원치 않았습니다.
2. **PWA 및 오프라인 환경:** 외부 스크립트 로딩으로 인한 성능 저하를 방지하고, 독립적인 서비스 운영이 가능해야 했습니다.
3. **통합 관리:** 비즈니스 로직 에러와 사용자 트래픽 통계를 어드민 페이지 하나에서 심리스하게 모니터링하고 싶었습니다.

결과적으로, **"서버사이드 미들웨어를 통해 직접 트래픽을 가로채고, 최소한의 정보만 안전하게 가공하여 DB에 적재하자"**는 결론에 이르렀습니다.

---

## 2. Architecture & Trade-off: 어떻게 설계할 것인가?

### ① FastAPI 미들웨어를 활용한 트래킹
정적 파일(`.css`, `.js`, `/static/` 등) 요청을 제외한 모든 핵심 페이지 뷰 요청(`GET /`, `POST /scan` 등)을 미들웨어단에서 감지하도록 구현했습니다.

*   **Trade-off (성능 vs 정확도):** 모든 요청을 DB에 직접 `INSERT`하면 트래픽이 몰릴 때 DB I/O 병목이 발생할 수 있습니다. 
*   **해결책:** 핵심 지표인 PV(Page View)와 UV(Unique Visitor) 집계를 위해 불필요한 필드는 배제하고, 인덱스를 최적화한 전용 로그 테이블(`visitor_logs`)을 설계했습니다.

### ② 개인정보 보호를 위한 IP 단방향 해싱
규제와 보안 이슈를 피하기 위해 **IP 주소 원본을 절대 DB에 저장하지 않는다**는 원칙을 세웠습니다.

```sql
-- 보안이 적용된 visitor_logs 테이블 스키마 예시
CREATE TABLE visitor_logs (
    id VARCHAR(36) PRIMARY KEY,
    ip_hash VARCHAR(64) NOT NULL,       -- IP 주소 단방향 해시 (개인정보 보호 및 중복 방문자 확인)
    session_id VARCHAR(100) NOT NULL,   -- 세션 브라우저 식별자
    user_id VARCHAR(36) REFERENCES users(id) ON DELETE SET NULL,
    path VARCHAR(255) NOT NULL,         
    method VARCHAR(10) NOT NULL,        
    user_agent TEXT,                    
    browser VARCHAR(50),                -- 파싱된 브라우저명 (Chrome, Safari 등)
    os VARCHAR(50),                     -- 파싱된 운영체제명 (iOS, Android 등)
    locale VARCHAR(10),                 
    referer TEXT,                       
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_visitor_logs_created_at ON visitor_logs(created_at);
```
*   `ip_hash`: 원본 IP를 솔트(Salt)와 함께 단방향 해싱하여 저장함으로써, 개인정보를 보호하면서도 **고유 방문자(UV) 산출**이 가능하도록 설계했습니다.
*   User-Agent 파싱을 통해 클라이언트의 브라우저와 OS 환경을 추출하여 어드민 대시보드에서 통계 차트로 렌더링할 수 있도록 가공했습니다.

### ③ 통합 어드민 모니터링 (방문자 분석 + 실시간 에러 로그)
별도의 로그 수집 파이프라인(ELK 스택 등)을 구축하는 것은 현재 서비스 규모에 비해 오버엔지니어링(Over-engineering)이라고 판단했습니다. 

*   **방문자 분석 탭:** 지정 기간 내 PV, UV, 활성 세션 수, 브라우저/OS 분포, 인기 유입 경로를 SQL 집계(`COUNT(DISTINCT)`)를 통해 빠르게 제공합니다.
*   **로그 모니터링 탭:** 시스템 내부 크래시(500 에러), 외부 API 연동 실패 로그 등을 심각도별(INFO, WARNING, ERROR)로 필터링하고, 최근 로그를 실시간 스트리밍 형태로 조회할 수 있도록 구현했습니다.

---

## 3. Takeaway: 엔지니어링 교훈

1. **상황에 맞는 기술 선택 (Right Tool for the Job):**
   대규모 트래픽 분석에는 GA나 Kafka + ELK 같은 거대한 파이프라인이 필수적이지만, 초기~중기 단계의 서비스나 프라이버시가 중요한 프로덕트에서는 **서버 미들웨어 + RDB 조합**만으로도 충분히 강력하고 유연한 모니터링 시스템을 구축할 수 있습니다.
2. **보안은 설계 단계부터:**
   개인정보(IP 주소 등)는 처음부터 원본을 저장하지 않고 해싱(`ip_hash`) 처리하는 방식을 채택함으로써, 향후 발생할 수 있는 컴플라이언스 리스크를 원천 차단할 수 있었습니다.
3. **운영 편의성의 극대화:**
   비즈니스 로직 지표와 시스템 에러 로그를 하나의 어드민 대시보드에서 통합 관리할 수 있게 되면서, 장애 대응 속도가 획기적으로 향상되었습니다.
