외부 공공기관이나 제3자의 API를 연동해 본 엔지니어라면 누구나 공감할 것입니다. **"외부 데이터는 우리가 기대하는 규격대로 들어오지 않는다"**는 명제입니다.

PickSafe 팀은 최근 식약처 성분 공공 데이터를 수집·매쉬업하는 과정에서 데이터 품질 오류와 백그라운드 스레드 제어 불능이라는 이중고를 겪었습니다. 비표준 데이터 포맷으로 인해 에러 로그가 폭증했고, 백그라운드 수집 작업은 제어가 불가능해 시스템 부하를 유발했습니다.

이 글에서는 이러한 문제를 극복하기 위해 **1) 파이썬 백그라운드 스레드의 상호 상태 동기화**, **2) 도메인 지식 기반의 자율 데이터 품질 교정**, **3) 관측 가능성(Observability) 확보**를 이끌어낸 아키텍처적 고민과 해결법을 공유합니다.

---

## 1. 문제 정의 (Problem)

기존 수집 파이프라인은 백그라운드 스레드 형태로 구동되고 있었으나, 대규모 데이터를 처리하는 과정에서 3가지 핵심적 문제가 발생했습니다.

### ① 데이터 불확실성에 따른 '무의미한 에러'의 폭증
식약처 데이터에는 원천 데이터 자체의 오류(CAS 번호 누락, 포맷 오기, 단일 필드 내 복수 번호 기입 등)가 다수 존재했습니다. 
특히 성분명에 슬래시(`/`)가 포함된 **복합 성분(예: 추출물, 코폴리머 등)**은 화장품 성분 표준상 식별 번호(CAS)가 존재하지 않는 것이 정상입니다. 그러나 기존 검증 로직은 이를 단순 '데이터 누락 에러'로 판별하여, 사람이 일일이 수동 검토해야 하는 에러 큐에 불필요하게 많은 데이터가 누적되었습니다.

### ② 백그라운드 스레드 제어 불능 및 상태 추적 부재
수집 작업이 백그라운드 스레드에서 전개되면서 작업의 진행률, 성공/실패율 통계를 실시간으로 추적할 수 없었습니다. 더욱 치명적인 것은 API 오작동이나 서버 부하 발생 시 **진행 중인 스레드를 즉시 강제 종료하거나 안전하게 일시 정지할 수 있는 제어 메커니즘이 부재**했다는 점입니다.

### ③ 비효율적인 운영/검토 프로세스
에러 큐에 담긴 데이터를 수정하기 위해 운영자는 성분명을 일일이 복사하여 국내외 공인 성분 사전에 검색하고, 하나씩 재적재해야 했습니다. 이는 심각한 운영 리소스 낭비로 이어졌습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs & Architecture)

우리는 시스템의 회복탄력성(Resilience)과 운영 효율성을 동시에 확보하기 위해 다음과 같은 아키텍처 결정을 내렸습니다.

### 2.1 스레드 섀도잉 방지를 위한 글로벌 상태 객체화 (`SeedingState`)

파이썬 환경에서 백그라운드 스레드를 안전하게 중단하려면 스레드 간 상태 공유가 필수적입니다. 그러나 단순 글로벌 변수를 사용할 경우 모듈 캐싱 및 섀도잉(Shadowing)으로 인해 백그라운드 스레드가 변경된 상태를 즉시 참조하지 못하는 현상이 발생할 수 있습니다.

* **대안 A: Celery / Redis 기반의 분산 큐 도입**
  * *장점*: 완벽한 작업 분리, 유연한 스케일아웃, 상태 관리의 용이성.
  * *단점*: 현재 단일 애플리케이션 구조 대비 인프라 복잡도 및 운영 비용 불필요한 증가.
* **대안 B: 싱글톤 상태 객체 및 모듈 레벨 `__getattr__` 활용 (최종 선택)**
  * *장점*: 인프라 추가 없이 인메모리 상에서 실시간 스레드 간 참조 유효성 보장.
  * *결정 이유*: 작업 취소 반응성을 1초 이내로 확보하면서도 현 시스템 구조를 단순하게 유지할 수 있음.

```
[ Admin Dashboard ] --(POST /stop)--> [ SeedingState (Global State) ]
                                                │ (Reference Check)
                                                ▼
                                   [ Background Worker Loop ] 
                                   ──> 1초 이내 중단 감지 및 Exit
```

우리는 `SeedingState`라는 전용 상태 관리 클래스를 선언하고, 수집 작업의 내부 루프가 성분 단위 단위로 상태를 참조하도록 설계했습니다. 이를 통해 중지 요청 발생 시 **1초 이내에 안전하게 스레드가 중단**되도록 구현했습니다.

### 2.2 도메인 지식 기반의 자율 품질 교정 (Smart Filtering)

모든 불완전 데이터를 에러로 처리하는 대신, 도메인 규칙을 정밀화하여 정제 단계를 자동화했습니다.

1. **복합 성분 예외 통과**: 성분명 내 `/`가 포함된 복합 원료는 CAS 번호가 없더라도 정상 데이터(NULL 저장)로 판단하여 에러 큐에 수집하지 않고 자율 통과시킵니다.
2. **단일 성분 엄격 검증**: 슬래시가 없는 단일 성분임에도 CAS 번호가 누락되거나 `0`으로 들어온 경우에만 human-in-the-loop 검토를 위해 에러 큐(`IngredientSeedError`)로 격리합니다.

이로써 운영자가 실제 확인해야 하는 '진짜 오류'의 범위만 정확히 타겟팅했습니다.

### 2.3 관측 가능성(Observability) 및 일괄 재처리 지원

수집 작업의 전체 생애주기를 관리하는 `SeedingHistory` 엔티티를 신설했습니다.
작업 실행자(`trigger_by`), 작업 범위, 실시간 성공/실패 수치를 상태 전이 연쇄(`running` ➔ `completed` / `stopped` / `failed`)에 따라 트래킹합니다. 어드민 대시보드는 이를 5초 주기로 폴링하여 실시간 작업 피드백을 제공합니다.

또한 operational friction을 줄이기 위해 다음과 같은 사용자 경험 향상을 도입했습니다:
* 외부 공인 사전(국내 대한화장품협회, EU CosIng)으로 즉시 연결되는 딥링크 단축 버튼 제공.
* 수정된 에러 항목을 한 번에 처리하는 일괄 재적재 API (`POST /admin/seeding/retry-batch`) 구현.

## 3. 최종 결과 및 성과 (Impact)

이번 고도화 작업을 통해 PickSafe의 데이터 파이프라인은 정량적·정성적으로 큰 개선을 이루었습니다.

* **운영 공수 90% 이상 절감**: 불필요한 복합 원료 에러 격리 차단 및 일괄 재처리, 사전 딥링크 연동을 통해 데이터 검토에 소요되던 시간을 획기적으로 줄였습니다.
* **예측 가능하고 안전한 스레드 제어**: 대시보드에서 [수집 중지] 버튼 클릭 시 **1초 이내 안전하게 백그라운드 작업이 중단**되며, 스레드 교착 상태(Deadlock)나 메모리 누수 위험을 완벽히 해소했습니다.
* **실시간 작업 가시성 확보**: 수집 세션별 통계가 모니터링 대시보드에 실시간으로 집계되어 데이터 파이프라인의 상태를 한눈에 파악할 수 있게 되었습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **외부 데이터를 절대 신뢰하지 마라 (Zero Trust Data Pipeline)**
   공공 API나 제3자 데이터 공급자의 스펙은 언제든 깨질 수 있습니다. 데이터 입입 단계에서 도메인 규칙에 기반한 방어적 필터링 체계를 갖추는 것이 전체 시스템의 안정성을 좌우합니다.
2. **운영 자동화는 코드 작성보다 '흐름 제거'에 있다**
   진정한 엔지니어링 생산성은 단순히 코드를 작성하는 것이 아니라, 운영자가 반복적으로 수행하던 검색, 복사, 개별 클릭과 같은 불필요한 공정 흐름(Friction)을 제거하는 데서 나옵니다.
3. **인프라 확장 전, 언어 수준의 동시성 제어를 먼저 고민할 것**
   무작정 메시지 큐(Message Queue)나 외부 인프라를 도입하기 전에, 현재 언어 생태계(Python Threading/State Management) 내에서 비용 효율적으로 문제를 해결할 수 있는지 타당성을 검토하는 것이 좋은 아키텍처적 태도입니다.
