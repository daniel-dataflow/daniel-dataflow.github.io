안녕하세요, PickSafe 백엔드 팀입니다. 

저희 팀은 화장품 및 식품 성분의 안전성을 분석하고 사용자에게 신뢰할 수 있는 정보를 제공하는 서비스를 개발하고 있습니다. 서비스의 핵심 가치인 '정확성'을 유지하기 위해, 식약처를 비롯한 여러 공공기관 및 대외 API로부터 성분 데이터를 주기적으로 수집하고 매쉬업(Mashup)하는 파이프라인을 운영하고 있습니다.

하지만 **대외 공공기관 API의 데이터는 우리가 통제할 수 없는 수많은 불확실성**을 안고 있습니다. 포맷의 불일치, 필수 값 누락, 표준을 벗어난 예외 데이터 등은 고스란히 시스템의 에러 로그 폭증과 운영 공수로 이어집니다. 

이번 글에서는 무분별한 백그라운드 스레드로 인해 제어 불능 상태에 빠졌던 기존 성분 수집 시스템을 개편하여, **실시간 제어가 가능한 스레드 아키텍처를 도입하고 운영 공수를 90% 이상 절감한 데이터 정제 시스템 구축기**를 공유합니다.

## 1. 문제 정의: 통제력을 잃은 백그라운드 작업과 데이터 품질 오류

기존 성분 수집 시스템은 대량의 성분 데이터를 백그라운드 스레드에서 단순 배치(Batch) 형태로 가져오도록 설계되어 있었습니다. 단순한 구조였지만, 데이터 스케일이 커지면서 세 가지 치명적인 병목을 마주하게 되었습니다.

```
[기존 파이프라인의 한계]
대외 API 요청 ➔ 비표준 데이터 유입 ➔ 적재 에러 발생 ➔ 백그라운드 스레드 제어 불능 (좀비 스레드화) ➔ 시스템 리소스 고갈
```

### ① 백그라운드 스레드의 '블랙박스화' 및 제어 수단 부재
기존 수집 작업은 백그라운드 스레드에서 구동되었으나, 메인 프로세스에서 이들의 실행 상태를 추적하거나 강제로 중단할 수 있는 안전장치가 없었습니다. 수집 도중 네트워크 지연이나 대외 API 장애가 발생하면, 스레드가 좀비 상태로 메모리를 점유하거나 DB 커넥션을 붙잡고 있어 시스템 전체의 불안정성을 초래했습니다.

### ② 비표준 데이터로 인한 가짜 에러(False Positive)의 범람
공공 데이터 특성상 표준 규격을 준수하지 않는 경우가 많습니다. 예를 들어, 화학 물질의 주민등록번호라 할 수 있는 **CAS(Chemical Abstracts Service) 번호**가 누락되거나 포맷이 깨진 채 들어오는 경우가 빈번했습니다. 
특히 두 개 이상의 성분이 슬래시(`/`)로 묶인 복합 성분(예: 복합 원료, 추출물 등)은 학술적으로 단일 CAS 번호가 존재하지 않는 것이 정상임에도, 기존 검증 로직은 이를 단순 'CAS 누락 에러'로 취급하여 수많은 무의미한 에러 내역을 누적시켰습니다.

### ③ 운영 어드민의 생산성 저하
데이터 수집 에러가 발생하면, 운영자는 에러 로그에서 성분명을 복사한 뒤, 대한화장품협회나 EU CosIng 같은 신뢰할 수 있는 공인 성분사전에 일일이 수동 검색하여 데이터를 보정해야 했습니다. 또한, 수정 후 한 번에 재적재할 수 있는 벌크(Bulk) 처리 기능이 없어 단순 반복 작업에 지나치게 많은 리소스가 소모되고 있었습니다.

## 2. 기술적 고민과 대안 비교: 안정성과 복잡도의 트레이드 오프

이를 해결하기 위해 저희는 **"스레드를 어떻게 안전하게 제어할 것인가?"**와 **"데이터 필터링을 어떻게 자동화할 것인가?"**라는 두 가지 관점에서 기술적 대안을 검토했습니다.

### 2.1 스레드 제어 방식의 비교

| 비교 군 | 대안 A: Celery + Redis 분산 태스크 큐 | 대안 B: 메모리 공유형 글로벌 상태 객체 (`SeedingState`) |
| :--- | :--- | :--- |
| **작동 방식** | 별도 워커 프로세스를 띄우고 Redis를 통해 메시징 및 취소 시그널 전송 | 모듈 캐싱 레벨에서 동적 참조를 보장하는 스레드 안전(Thread-safe) 상태 객체 구현 |
| **장점** | 멀티 서버 환경에서 수평 확장(Scale-out)이 매우 용이함. 태스크 취소 및 모니터링 기능이 기본 탑재됨. | 인프라 추가 비용 없음. 복잡한 직렬화/역직렬화 비용이 없고 가볍게 적용 가능. |
| **단점** | Redis 인프라 유지보수 비용 발생, Celery 워커 관리 공수 추가. | 멀티 인스턴스 환경으로 확장 시 인스턴스 간 상태 동기화를 위한 추가 레이어 필요. |
| **최종 선택** | **미선택** (현재 배치 트래픽 대비 인프라 복잡도가 과해 오버엔지니어링으로 판단) | **최종 선택** (단일 대용량 배치 프로세스에 적합하며 즉각적인 제어가 가능함) |

> **선택의 이유:** PickSafe의 성분 수집 작업은 높은 수평 확장이 필요한 실시간 트래픽이 아닙니다. 인프라 복잡도를 최소화하면서도, 백그라운드 스레드가 메인 스레드의 취소 시그널에 즉각 반응(1초 이내)하도록 만들기 위해 **글로벌 상태 객체(Thread-safe State) 패턴**을 직접 구현하기로 결정했습니다.

## 3. 최종 해결 방식: 자율 교정 파이프라인과 상태 제어 아키텍처

저희가 설계하고 구현한 핵심 기술적 해결책은 크게 세 가지 축으로 나뉩니다.

```
[개선된 시스템 아키텍처]
어드민 UI ➔ [SeedingState] 상태 변경 ➔ 스레드 루프 내 검출 (1초 내 반응)
                                    ↳ [자율 필터링] 복합 성분(슬래시/) 자동 통과
                                    ↳ [에러 최소화] 실 에러만 검출 ➔ 원클릭 공인 사전 조회 및 일괄 재적재
```

### ① 스레드 섀도잉 방지를 위한 글로벌 상태 객체 (`SeedingState`)
Python은 모듈을 로드할 때 캐싱을 수행하므로, 스레드 간 메모리 공유를 잘못 설계하면 '스레드 섀도잉(Thread Shadowing)'이나 원하지 않는 시점의 속성 복제가 일어날 수 있습니다. 

이를 해결하기 위해 동적 어트리뷰트 조회가 가능한 `SeedingState` 클래스를 정의하고, Python 3.7+의 모듈 레벨 `__getattr__`을 활용하여 모듈 정체성 불일치 문제를 극복했습니다.

```python
# 보안을 위해 비즈니스 로직은 마스킹 및 단순화된 예시 코드로 대체합니다.
class SeedingState:
    def __init__(self):
        self._is_running = False
        self._stop_requested = False

    @property
    def is_running(self):
        return self._is_running

    def request_stop(self):
        self._stop_requested = True

    def should_stop(self):
        return self._stop_requested

    def reset(self):
        self._is_running = True
        self._stop_requested = False

# 백그라운드 워커 루프 내에서 상태를 감지하여 즉시 탈출
def background_seeding_task(state: SeedingState):
    state.reset()
    try:
        for item in ingredient_stream:
            # 매 이터레이션마다 상태를 체크하여 1초 내외로 빠른 취소 반응성 확보
            if state.should_stop():
                logger.info("수집 작업이 사용자에 의해 수동 중단되었습니다.")
                break
            
            # 성분 수집 및 가공 로직 수행...
    finally:
        state._is_running = False
```

### ② 이력 모니터링 (`SeedingHistory`) 설계
진행 상황을 투명하게 공개하기 위해, 수집 세션의 생명주기를 관리하는 `SeedingHistory` 상태 전이 모델을 설계했습니다.

*   **State Transition:** `running` ➔ `completed` / `stopped` / `failed`
*   어드민 대시보드에서는 **5초 주기의 롱 폴링(Long Polling)**을 통해 작업 개시자(`trigger_by`), 시작/종료 페이지, 성공 및 실패 성분 개수를 실시간으로 갱신하여 인지 비용을 최소화했습니다.

### ③ 도메인 규칙을 활용한 자율 데이터 정제 (Composite Pre-filter)
비표준 데이터로 인한 노이즈를 줄이기 위해 성분 도메인 규칙을 정교화했습니다. 대한화장품협회 사전을 참조하여 **슬래시(`/`)가 포함된 복합 원료는 CAS 번호가 없는 것이 정상(Null 허용)**이라는 예외 필터를 구현했습니다.

*   **정상 통과(Null 허용):** 성분명에 `/`가 포함된 경우 (예: "병풀추출물/정제수")
*   **에러 큐 적재:** 단일 성분인데 CAS 번호가 `0`이거나 `Null`인 경우 ➔ `IngredientSeedError` 테이블로 우회하여 운영진의 검토 영역을 명확히 압축했습니다.

### ④ 원클릭 공인 사전 연동 및 Batch Retry API
에러가 발생한 성분을 교정할 때, 운영자의 이동 동선을 최소화하기 위해 공인 성분사전으로 바로 이동하는 딥링크(Deep Link)를 검색 인터페이스에 도입했습니다.

*   **국내 성분:** 화장품협회 성분 사전 새 탭 검색 연동
*   **해외 성분:** EU CosIng 규격 검색 연동

더불어, 정제가 완료된 데이터들을 다중 선택하여 한 번에 안전하게 트랜잭션을 묶어 재적재할 수 있는 벌크 재처리 엔드포인트(`POST /admin/seeding/retry-batch`)를 설계하여 운영 효율성을 극대화했습니다.

## 4. 결과 및 엔지니어링 교훈 (Takeaways)

### 📈 도입 결과
1. **완벽한 작업 제어력 확보:** UI 대시보드 상에서 수동 중단 명령을 내렸을 때, 백그라운드 스레드가 **1초 내외로 즉시 감지하고 중단**되어 시스템 안정성이 크게 개선되었습니다.
2. **운영 리소스 90% 이상 절감:** 자율 예외 필터링을 통해 실제 검토가 필요한 에러 데이터만 골라내어 에러 로그 노출 수가 크게 줄었고, 딥링크와 배치 재적재 덕분에 수동 보정 시간이 기존 대비 10분의 1 수준으로 단축되었습니다.
3. **모바일 웹 지원 및 UX 향상:** 반응형 레이아웃 및 동적 버튼 피드백을 통해 운영진이 긴급 상황 시 모바일 디바이스에서도 안전하게 작업을 제어할 수 있게 되었습니다.

### 💡 엔지니어링 교훈: "소프트웨어 엔지니어링은 운영자의 눈물을 닦아주는 것"
이번 개편을 진행하며 깨달은 가장 큰 교훈은 **아무리 훌륭한 알고리즘과 아키텍처라도 시스템을 사용하는 운영자와의 공감이 없다면 반쪽짜리 시스템에 불과하다**는 점입니다. 

백엔드 개발자로서 단순히 "데이터를 긁어온다"라는 기능적 완성에만 집중했을 때는 보이지 않던 문제들이, 운영의 관점에서 "데이터가 깨졌을 때 운영자는 어떤 고통을 받는가?"를 고민하기 시작하자 해결책이 보이기 시작했습니다.

*   **통제 불가능한 데이터 소스를 다룰 때는 반드시 격리 레이어와 예외 처리 자동화 규칙을 선제적으로 설계해야 합니다.**
*   **장시간 실행되는 백그라운드 프로세스는 반드시 모니터링 가능하고 제어 가능한 형태(Cancelable)로 설계해야 시스템이 영속성을 가질 수 있습니다.**

PickSafe 팀은 앞으로도 이처럼 비즈니스의 성장과 운영의 안정성을 모두 챙길 수 있는 견고한 아키텍처를 치열하게 고민해 나가겠습니다. 긴 글 읽어주셔서 감사합니다!
