외부 공공데이터나 레거시 API를 연동해 대규모 데이터를 수집·가공하는 파이프라인을 구축하다 보면, 언제나 **데이터 품질의 불확실성**과 **백그라운드 작업 제어의 한계**라는 두 가지 큰 벽에 부딪히게 됩니다.

단순히 "데이터를 긁어와서 저장한다"는 수준을 넘어, 불완전한 외부 데이터 속에서 시스템의 안정성을 유지하고 운영 비용을 최소화하기 위해 고민했던 아키텍처 개선 과정을 공유합니다.

---

### 1. 문제 정의: 외부 데이터의 불확실성과 블랙박스 배치 작업

공공 API 기반의 성분 데이터를 대량으로 수집·적재하는 과정에서 크게 세 가지 엔지니어링 이슈가 발생했습니다.

1. **데이터 규격의 비표준화와 무의미한 에러 적재**
   공공데이터 특성상 CAS(Chemical Abstracts Service) 번호 누락, 포맷 오기, 다중 식별자 혼기입 등 정형화되지 않은 원천 데이터가 빈번했습니다. 특히 복합 원료(예: 슬래시 `/`가 포함된 혼합 추출물)는 구조상 단일 CAS 번호가 존재하지 않는 것이 정상임에도 불구하고, 단순 유효성 검증 실패로 처리되어 수천 건의 무의미한 에러 로그가 큐에 쌓였습니다.
2. **백그라운드 스레드 제어 불능 (Lack of Controllability)**
   비동기 백그라운드 스레드로 실행되는 대용량 수집 작업은 실행 도중 DB 부하가 발생하거나 외부 API 응답이 지연될 때 **작업을 안전하게 중단(Graceful Stop)하거나 재개할 수 있는 인터럽트 메커니즘**이 없었습니다.
3. **가시성(Observability) 부족 및 운영 비용 급증**
   작업이 현재 몇 퍼센트 진행되었는지, 어떤 지점에서 병목이나 실패가 발생했는지 실시간으로 파악하기 어려웠고, 실패한 데이터를 교정하기 위해 운영자가 일일이 외부 사전을 검색해 수동 입력해야 하는 높은 운영 리소스가 소모되었습니다.

---

### 2. 기술적 고민과 대안 비교

이 문제를 해결하기 위해 시스템의 신뢰성과 운영 효율성을 기준으로 다음의 설계 옵션들을 검토했습니다.

| 항목 | 대안 A (기존 유지 및 단순 패치) | 대안 B (완전 분산 큐 시스템 도입 - Celery/Kafka) | 대안 C (글로벌 상태 기반 경량 제어 + 도메인 자율 필터) |
| :--- | :--- | :--- | :--- |
| **작업 제어** | 스레드 강제 종료 (불완전 트랜잭션 위험) | 분산 워커 제어 및 모니터링 우수 | **세분화된 루프 레벨 플래그 체크로 1초 내 안전 중단** |
| **인프라 복잡도** | 낮음 | 매우 높음 (Broker, Worker 클러스터 유지보수 필요) | **낮음 (단일 애플리케이션 내 경량 아키텍처 유지)** |
| **데이터 정제** | 사람이 에러 큐를 보고 전수 수동 교정 | 수집 후 별도 배치 파이프라인에서 정제 | **도메인 지식 기반 In-flight 자율 필터링** |

**선택 및 이유:**
현재 트래픽과 서비스 단계에서는 Celery와 같은 무거운 분산 메시지 브로커를 도입하는 것은 오버엔지니어링(Over-engineering)이라 판단했습니다. 따라서 **단일 애플리케이션 내에서 스레드 안전성(Thread-safety)을 보장하는 글로벌 상태 머신을 구축**하고, **수집 파이프라인 내부에서 도메인 규칙에 따라 데이터를 자율 교정하는 경량화된 고효율 아키텍처(대안 C)**를 채택했습니다.

### 3. 아키텍처 구현 및 해결 전략

#### ① 스레드 섀도잉 방지를 위한 글로벌 상태 제어 (`SeedingState`)
Python의 멀티스레딩 환경에서는 모듈 캐싱이나 인스턴스 참조 불일치로 인해 워커 스레드가 메인 스레드의 플래그 변경을 즉각 인지하지 못하는 '스레드 섀도잉' 문제가 발생할 수 있습니다.

- **실시간 레퍼런스 참조:** 중앙 집중형 상태 관리 객체를 선언하고, 백그라운드 스레드가 항상 단일 인스턴스의 Attribute 레퍼런스를 실시간으로 폴링하도록 구성했습니다.
- **Graceful Cancellation:** 수집 루프의 각 성분 처리 단위마다 취소 시그널을 감지하도록 설계하여, 관리자가 작업을 중단했을 때 트랜잭션 오염 없이 **1초 이내에 안전하게 루프를 탈출(Graceful Stop)**하도록 구현했습니다.

#### ② 상태 전이(State Machine) 기반의 관측 가능성 확보
수집 작업의 라이프사이클을 `running` ➔ `completed` / `stopped` / `failed`의 명확한 상태 전이 모델로 정의했습니다.
- 작업 시작자, 대상 범위(페이지), 성공/실패 카운트를 실시간으로 데이터베이스에 갱신하여 운영 대시보드에서 5초 단위로 수집 현황을 파악할 수 있도록 관측 가능성(Observability)을 확보했습니다.

#### ③ 도메인 지식 기반 In-flight 자율 정제 엔진
단순한 유효성 검사에서 벗어나, **도메인 규칙(화장품 성분 명명 표준)을 반영한 예외 필터링 로직**을 적용했습니다.

```
[원천 데이터 수집]
       │
       ▼
[성분명 내 '/' 포함 여부 검사 (복합 원료 판별)]
       ├─ (YES) ─► CAS 번호 미기재 정상 통과 (정상 데이터 적재)
       │
       └─ (NO)  ─► 단일 성분 규칙 적용
                     ├─ CAS 번호 유효 ──► 정상 데이터 적재
                     └─ CAS 번호 누락 ──► 에러 큐 격리 (사람 검토 대상)
```

- 슬래시(`/`)가 포함된 복합 원료는 CAS 번호가 없는 것이 도메인 표준에 부합하므로, 이를 에러로 격리하지 않고 정상 적재되도록 처리했습니다.
- 단일 성분임에도 식별자가 누락되거나 비표준 포맷인 경우에만 정밀 검토 큐에 격리하여, **사람이 검토해야 하는 에러 모수를 대폭 축소**했습니다.

#### ④ 운영자 경험(DX)을 극대화한 보정 파이프라인
불가피하게 에러 큐로 유입된 데이터의 복구 비용을 낮추기 위해 다음 인터페이스를 구축했습니다:
- **공인 사전 원클릭 연동:** 검토 화면에서 국내외 공인 성분 사전(KCIA, EU CosIng 등)으로 다이렉트 딥링크 검색을 지원하여 탐색 비용을 제거했습니다.
- **일괄 재적재(Batch Retry):** 보정 완료된 다수의 레코드를 한 번의 트랜잭션으로 일괄 처리할 수 있는 재처리 파이프라인을 제공했습니다.

### 4. 성과 및 엔지니어링 교훈 (Takeaways)

```
[도입 성과]
- 수동 검토 소요 리소스: 기존 대비 90% 이상 절감
- 작업 중단 반응 속도: 클릭 즉시(1초 이내) 안전한 인터럽트 달성
- 시스템 안정성: 불완전 트랜잭션 및 좀비 스레드 생성 원천 차단
```

#### 핵심 배운 점
1. **외부 시스템 연동 시 무결성을 전제하지 말 것**
   외부 API는 언제든 깨진 데이터와 스키마 불일치를 보낼 수 있습니다. 파이프라인은 단순히 데이터를 통과시키는 파이프가 아니라, **도메인 룰에 기반한 '자율 정제 및 복원력(Self-healing)'을 갖춘 관문**이어야 합니다.
2. **백그라운드 프로세스는 반드시 제어 가능해야 한다**
   비동기 작업은 시작하는 것보다 **안전하게 멈추고 복구하는 것(Controllability)**이 훨씬 어렵고 중요합니다. 루프 레벨에서의 세밀한 인터럽트 설계가 시스템 전체의 회복 탄력성을 결정합니다.
3. **엔지니어링의 완성은 운영 비용 절감이다**
   아무리 정교한 수집 엔진도 에러 처리가 운영자에게 전가된다면 기술적 부채가 됩니다. 에러 필터링 자동화와 원클릭 보정 환경 구축을 통해 운영 병목을 선제적으로 해소하는 것이 진정한 백엔드 엔지니어링의 가치임을 확인했습니다.
