제품 서비스의 가치를 높이기 위해 공공데이터(Public API)를 활용해본 엔지니어라면 누구나 한 번쯤 경험해 보았을 것입니다. **"외부 API의 데이터는 결코 정제되어 있지 않다"**는 사실을요. 

PickSafe 팀은 식약처 3대 공공 API 데이터를 수집·매쉬업하여 사용자에게 안전한 성분 정보를 제공하고 있습니다. 하지만 수집 과정에서 **비표준 CAS 번호, 복수 번호 기입, 필수값 누락** 등 원천 데이터의 품질 오염으로 인해 수집 파이프라인이 빈번히 실패하고 무의미한 에러 로그가 쌓이는 문제가 발생했습니다.

설상가상으로 기존의 백그라운드 수집 프로세스는 스레드 제어 수단이 미비하여, 문제가 발생해도 즉시 중단할 수 없고 모니터링조차 불가능한 '블랙박스' 형태였습니다.

본 포스팅에서는 이 문제를 해결하기 위해 **1) 스레드 세이프한 글로벌 상태 제어**, **2) 도메인 규칙 기반의 자율 데이터 교정 파이프라인**, **3) 운영진(Ops)을 위한 DX 개선**을 도출하고 적용한 엔지니어링 여정을 소개합니다.

---

## 1. 문제 정의 (Problem Statement)

우리가 해결해야 했던 핵심 과제는 크게 세 가지였습니다.

### ① 통제할 수 없는 백그라운드 프로세스 (Thread Control)
기존 데이터 수집 작업은 Python 백그라운드 스레드에서 단순 구동되었습니다. 수집 중 서버 부하가 급증하거나 식약처 API 응답 이상이 감지되어도 **작업을 중간에 안전하게 취소(Cancel)할 수 있는 인터럽트 구조가 부재**했습니다. 또한 모듈 캐싱 및 메모리 격리로 인해 외부 요청이 스레드 내부 상태에 즉시 반영되지 않는 현상이 있었습니다.

### ② 무의미한 에러 폭풍과 데이터 오염 (Data Quality)
공공데이터 특성상 하나의 성분에 여러 개의 CAS 번호가 슬래시(`/`)로 묶여 있거나, 화장품 복합 원료(추출물, 코폴리머 등)처럼 **도메인 특성상 CAS 번호가 존재하지 않는 성분**들이 다수 존재했습니다. 
기존 파이프라인은 이를 모두 일반적인 데이터 오류(Error)로 취급하여 에러 큐에 적재했고, 운영진은 매일 수천 건의 '가짜 에러(False-Positive)'를 일일이 수동으로 확인해야 했습니다.

### ③ 운영 효율성(Ops DX) 저하
에러가 발생했을 때 운영진은 성분명을 복사하여 대한화장품협회나 해외 성분 사전에 일일이 검색한 뒤 교정해야 했습니다. 또한 수정 후 개별 건마다 재적재를 시도해야 해 심각한 병목이 발생했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-Off & Alternatives)

우리는 이 문제를 해결하기 위해 세 가지 영역에서 아키텍처적 결정을 내렸습니다.

### 2.1 스레드 제어: Message Queue vs Global State Object

작업 취소 및 실시간 제어를 구현하기 위해 두 가지 대안을 검토했습니다.

- **대안 A: Celery + Redis (메시지 큐 기반 작업 관리)**
  - *장점*: 완전한 분산 처리, 태스크 중단(Revoke) 및 상태 추적이 매우 용이함.
  - *단점*: 현재 단일/소규모 인프라 구조 대비 인프라 복잡도(Broker, Worker)와 유지보수 비용이 과도하게 증가함.
- **대안 B: 메모리 기반 레퍼런스 공유 (`SeedingState` 패턴)**
  - *장점*: 별도 인프라 추가 없이 애플리케이션 내에서 스레드 간 상태 레퍼런스를 참조 가능. 메모리 동기화 및 즉시 중단 인터럽트 구현 가능.
  - *단점*: 멀티 프로세스(Multi-process) 환경 확장에 제약이 있으므로 상태 격리 유의 필요.

> **최종 선택 (Option B):** 
> 당장의 과도한 엔지니어링(Over-engineering)을 지양하고, Python 3.7+의 모듈 레벨 `__getattr__` 및 명시적 메모리 참조를 활용한 **`SeedingState` 상태 관리 객체**를 도입하기로 했습니다.

```python
# [개념 코드] 백그라운드 루프 내 인터럽트 감지 구조
class SeedingState:
    def __init__(self):
        self._is_stopped = False

    def stop(self):
        self._is_stopped = True

    @property
    def is_stopped(self):
        return self._is_stopped

# 수집 이터레이션 내부에서 1초 내외로 취소 요청 감지
for item in ingredient_stream:
    if seeding_state.is_stopped:
        logger.info("수집 중지 요청을 감지하여 스레드를 안전하게 종료합니다.")
        break
    process_ingredient(item)
```

## 3. 핵심 해결책 및 아키텍처 (Architecture & Implementation)

### 3.1 자율 교정 체계 및 데이터 필터링 Engine

데이터 품질 문제를 해결하기 위해 도메인 지식을 파이프라인 전처리 단계에 이식했습니다.

```
[식약처 원천 API] 
       │
       ▼
[복합 성분 및 CAS 포맷 검증]
       ├─ (1) 슬래시(/) 포함 복합 원료 ───► CAS Null 저장 (정상 통과)
       ├─ (2) 비표준 CAS 포맷      ───► 자율 정규화 (Auto-Correction)
       └─ (3) 단일 성분인데 CAS 누락  ───► [IngredientSeedError DB Queue] ──► 사람 검토
```

1. **복합 성분(Composite) 분류 예외 처리**:
   대한화장품협회 기준에 따라 성분명에 `/`가 포함된 추출물/복합 원료는 CAS 번호가 없는 것이 정상입니다. 이를 에러 큐로 보내지 않고 `NULL` 상태의 정상 데이터로 판단하여 파이프라인을 통과시킵니다.
2. **진짜 오류의 최소화**:
   단일 성분임에도 CAS 번호가 `0`이거나 `Null`인 극소수의 경우만 human-in-the-loop 검토를 위해 에러 테이블(`IngredientSeedError`)에 수집하도록 변경했습니다.

### 3.2 수집 생명주기 트래킹 (`SeedingHistory`)

수집 세션의 시작부터 끝까지 상태 변화를 이력 테이블로 기록하도록 설계했습니다.

- **상태 전이(State Transition)**: `running` ➔ `completed` / `stopped` / `failed`
- **실시간 텔레메트리**: 작업 개시자(`trigger_by`), 진행 페이지, 성공/실패 수량을 5초 주기 어드민 대시보드 폴링(Polling) API와 연동하여 직관적인 피드백을 제공합니다.

### 3.3 운영 DX 고도화 (사전 연동 & 일괄 재적재)

운영진의 번거로운 작업 동선을 단축했습니다.

```
[에러 검토 대시보드]
   ├── [대한화장품협회 검색] ──► (새 탭) 외부 공인 사전 자동 키워드 쿼리
   ├── [EU CosIng 검색]     ──► (새 탭) INCI 영문명 자동 쿼리
   └── [체크박스 다중 선택]  ──► POST /admin/seeding/retry-batch (일괄 재적재)
```

- **외부 공인 사전 자동 매핑**: 클릭 한 번으로 국문명/영문 INCI명을 조건에 맞춰 외부에 즉시 검색할 수 있는 단축 링크를 렌더링했습니다.
- **다중 선택 일괄 재적재 API**: 정제 완료된 에러 데이터를 체크박스로 다중 선택하여 배치 처리하는 엔드포인트를 제공하여 데이터 재수집 소요 시간을 극적으로 줄였습니다.

## 4. 성과 및 엔지니어링 교훈 (Results & Takeaways)

### 📈 결과 및 기대 효과

1. **수동 검토 소요 시간 90% 이상 절감**:
   복합 원료의 자율 통과 처리 및 외부 사전 1-Click 연동을 통해, 기존에 매일 수시간씩 소요되던 에러 검토 작업이 몇 분 이내로 단축되었습니다.
2. **안정적인 프로세스 제어 (안전 중지 보장)**:
   대시보드의 [중지] 버튼 클릭 시 **1초 이내에 백그라운드 스레드가 안전하게 세션을 정지**하고 `stopped` 상태로 깔끔하게 전이됨을 검증했습니다.
3. **운영 화면 최적화**:
   어드민 UI 모바일/모니터 대시보드 최적화로 긴급 시 모바일 환경에서도 제어 및 모니터링이 가능해졌습니다.

### 💡 Engineering Takeaways (배운 점)

1. **"외부 데이터(External API)는 입력(Input) 단계에서 방어적으로 검증하라"**
   원천 데이터 제공처의 규격을 무조건 신뢰해서는 안 됩니다. 데이터 파이프라인 전면에 도메인 특성을 반영한 검증 및 자율 교정 레이어를 두는 것이 시스템 전체의 회복 탄력성(Resilience)을 높입니다.
2. **"제어할 수 없는 백그라운드 작업은 엔지니어링 부채다"**
   실행 상태를 볼 수 없고, 중간에 멈출 수 없는 작업은 언젠가 시스템 장애의 원인이 됩니다. 상태 객체와 명시적인 인터럽트 메커니즘을 설계하는 것이 단순 기능 구현보다 중요합니다.
3. **"Human-in-the-loop 시스템의 핵심은 DX(Developer/Ops Experience)다"**
   모든 예외 상황을 100% 자동화할 수는 없습니다. 결국 사람이 개입해야 하는 영역이 존재한다면, 그 사람이 최단 동선으로 판단하고 일괄 처리할 수 있는 도구를 제공하는 것까지가 완결된 엔지니어링입니다.
