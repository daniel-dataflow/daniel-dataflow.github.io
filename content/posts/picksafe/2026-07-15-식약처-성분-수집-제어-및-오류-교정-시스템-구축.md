안녕하세요, PickSafe 기술 블로그 구독자 여러분. 

서비스의 핵심 가치를 유지하기 위해서는 외부의 수많은 데이터를 정제하고 내재화하는 과정이 필수적입니다. PickSafe팀은 최근 식약처의 3대 API를 매쉬업하여 성분 사전을 구축하는 프로젝트를 진행했습니다. 

하지만 늘 그렇듯 **"외부 공공 API 데이터는 우리가 원하는 만큼 깨끗하지 않다"**는 냉혹한 현실에 마주하게 되었습니다. 포맷 오류, 빈 값, 복수 표기 등 예측 불가능한 정형화 오류들이 쏟아졌고, 백그라운드에서 돌던 배치 프로세스는 제어가 불가능한 상태로 서버 자원을 갉아먹고 있었습니다.

이번 포스팅에서는 우리가 이 문제를 어떻게 정의했고, 시스템 안정성을 지키면서 데이터 정제 효율을 **90% 이상 개선**하기 위해 어떤 아키텍처적 선택(Trade-off)을 내렸는지 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 제어권 없는 스레드와 더러운 데이터의 협공

초기 수집 시스템은 단순한 백그라운드 스레드 기반의 일괄 처리 방식으로 구현되어 있었습니다. 이 구조는 서비스 규모가 작을 때는 잘 작동했지만, 데이터 양이 늘어나면서 두 가지 치명적인 병목을 유발했습니다.

### 병목 1: "블랙박스"가 된 백그라운드 스레드
수집 배치가 구동되면 시스템 내부에서 어떤 성분을 처리하고 있는지, 성공률은 얼마인지 알 길이 없었습니다. 가장 큰 문제는 **작업을 중단할 수 있는 제어 수단이 없었다는 점**입니다. 외부 API 통신 장애나 시스템 부하가 감지되어도 배치를 강제 종료할 방법이 없어, 결국 프로세스를 통째로 킬(Kill)해야 하는 무식한(?) 운영을 반복해야 했습니다.

### 병목 2: 공공 데이터 본연의 정형화 오류와 가짜 에러(False Positive)의 범람
식약처 원본 데이터에는 CAS 번호(Chemical Abstracts Service Registry Number)가 누락되거나, 비표준 포맷으로 기입된 경우가 많았습니다. 
또한, 복합 성분(예: 슬래시 `/`가 포함된 추출물이나 복합 원료)의 경우 표준 사전 기준 CAS 번호가 존재하지 않는 것이 정상임에도 불구하고, 기존 시스템은 이를 모두 '성분 등록 실패' 에러로 처리하여 관리자 화면에 불필요한 에러 내역을 수만 건씩 누적시켰습니다. 진짜 해결해야 할 에러들이 가짜 에러들에 묻혀버리는 상황이었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 아키텍처 레이어에서 몇 가지 중요한 의사결정을 내려야 했습니다.

### 고민 1. 스레드 상태 제어 및 동기화: Celery vs. 인메모리 글로벌 상태 관리
배치를 안전하게 멈추고 재개하려면, 메인 스레드와 작업 스레드 간의 안전한 상태 공유가 필요했습니다.

*   **대안 A: Celery + Redis 조합의 분산 태스크 큐 도입**
    *   *장점:* 태스크의 취소, 재개, 모니터링을 프레임워크 수준에서 강력하게 지원합니다.
    *   *단점:* 현재 가벼운 백그라운드 스레드로도 충분한 태스크 규모에 비해, Redis 인프라를 신설하고 Celery 의존성을 추가하는 것은 과도한 엔지니어링(Over-engineering)이자 리소스 낭비였습니다.
*   **대안 B: 글로벌 상태 객체(`SeedingState`) 및 DB 이력 트래킹 (선택)**
    *   *이유:* 모듈 캐싱과 스레드 섀도잉 문제를 회복력 있게 극복하기 위해, 전역 상태 관리 싱글톤 클래스를 설계했습니다. Python 3.7+에서 지원하는 모듈 레벨 `__getattr__`을 활용해 안전한 레퍼런스 참조를 보장했습니다. DB 기반의 `SeedingHistory` 상태 전이(State Transition) 모델을 추가하여 실시간 대시보드 통계와 작업 제어를 연동했습니다. 

```python
# [개념 예시] Python 모듈 레벨 상태 관리 클래스
class SeedingState:
    def __init__(self):
        self._is_running = False
        self._should_stop = False

    @property
    def should_stop(self) -> bool:
        return self._should_stop

    def stop(self):
        self._should_stop = True

# 데이터 수집 루프 내에서 즉각 피드백 (1초 내외 반응)
for ingredient in batch_items:
    if state.should_stop:
        history.update_status("stopped")
        break
    process(ingredient)
```

### 고민 2. 에러 필터링 자동화: 무조건적인 엄격한 검증 vs. 도메인 지식 기반의 자율 교정
데이터 무결성을 위해 무조건 엄격한 CAS 번호 정형 규칙을 적용하는 것이 맞는지 고민했습니다.

*   **대안 A: 엄격한 스키마 검증 및 전체 에러 적재**
    *   데이터 오염은 막을 수 있지만, 화장품 협회 등의 도메인 특성상 복합 원료(`/` 기입 성분)는 CAS가 없는 것이 정상입니다. 이를 다 에러로 던지면 운영 공수가 무한대로 늘어납니다.
*   **대안 B: 도메인 지식 기반 자율 교정 파이프라인 (선택)**
    *   *이유:* 성분명에 슬래시(`/`)가 포함된 복합 성분은 에러 큐에 넣지 않고 정상(NULL)으로 처리하도록 비즈니스 룰을 세분화했습니다. 반면, 슬래시가 없는 단일 성분인데 CAS 번호가 `0`이거나 Null인 진짜 문제들만 필터링하여 `IngredientSeedError` 큐로 분류했습니다.

## 3. 최종 해결 및 구현 성과

이러한 의사결정을 바탕으로 우리는 다음과 같은 "자율 교정 및 정밀 제어 파이프라인"을 성공적으로 안착시켰습니다.

```
[식약처 API] ──> [복합 성분 필터] ──(슬래시 포함?)──> [Yes] ──> 정상 데이터 적재 (CAS: NULL)
                         │
                        [No]
                         ▼
             [CAS 규격 자동 검증] ──(정상 규격?)───> [Yes] ──> 정상 데이터 적재
                         │
                        [No (0, Null, 오기)]
                         ▼
             [IngredientSeedError 큐] ──> [어드민 UI (공인 사전 링크 연동 & 일괄 재적재)]
```

### 1) 1초 내외의 즉각적인 작업 제어
어드민 페이지의 대시보드를 통해 수집 시작, 일시정지, 강제 중단 명령을 내릴 수 있습니다. 루프 레벨에서 `should_stop` 플래그를 실시간 체크하기 때문에, **[수집 중지]** 클릭 시 최대 1초 내로 스레드가 안전하게 작업을 중단하고 상태를 보존합니다.

### 2) 실시간 이력 모니터링 (`SeedingHistory`)
수집 세션의 라이프사이클을 `running` ➔ `completed` / `stopped` / `failed` 상태 머신으로 관리합니다. 작업 트리거 주체, 시작/종료 페이지, 성공 및 예외율 통계가 실시간으로 기록되며, 어드민 화면에서 5초 주기 폴링을 통해 모니터링됩니다.

### 3) 클릭 한 번으로 끝나는 에러 교정 UX (Human-in-the-loop)
자율 교정 체계를 거쳐 분류된 진짜 에러들에 대해, 담당자가 빠르게 수동 검토를 수행할 수 있도록 어드민 화면에 공인 성분 사전(대한화장품협회 및 EU CosIng) 새 탭 검색 링크를 자동 생성하여 바인딩했습니다. 검토가 끝난 데이터는 체크박스로 다중 선택하여 `POST /admin/seeding/retry-batch` API를 통해 한 번에 재적재할 수 있습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 고도화 작업을 통해 PickSafe 엔지니어링 팀은 세 가지 값진 교훈을 얻었습니다.

1.  **데이터 품질 검증은 "도메인 지식"의 영역이다:** 단순 정규식 검증만 고집했다면 여전히 가짜 에러 메일 더미 속에서 고통받았을 것입니다. 비즈니스 도메인(복합 원료의 특성)을 아키텍처에 반영할 때 비로소 노이즈 없는 깨끗한 데이터 파이프라인이 완성됩니다.
2.  **적정 기술(Appropriate Technology)의 가치:** 분산 큐 프레임워크(Celery) 도입이라는 화려한 선택지 대신, 현재 팀의 인프라 규모와 요구사항에 딱 맞는 싱글톤 기반의 인메모리 제어 및 DB 트래킹을 선택함으로써 개발 리소스를 아끼고 오버헤드를 최소화했습니다.
3.  **운영 효율(Admin UX)도 시스템 설계의 일부다:** 아무리 훌륭한 백엔드 아키텍처도 운영자의 사용성이 나쁘면 빛을 바랩니다. 검색 연동 단축키와 일괄 재적재 기능을 통합함으로써, 기존 대비 **수동 검토 소요 시간을 90% 이상 대폭 절감**하는 쾌거를 이루었습니다.

앞으로도 PickSafe팀은 사용자에게 가장 안전하고 정확한 성분 정보를 제공하기 위해 데이터 파이프라인의 안정성을 끊임없이 한계까지 끌어올릴 것입니다. 우리의 여정에 흥미가 생기셨다면, 언제든 문을 두드려주세요!
