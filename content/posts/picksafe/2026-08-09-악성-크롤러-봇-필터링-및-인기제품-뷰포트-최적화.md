안녕하세요, **PickSafe** 백엔드/프론트엔드 엔지니어링 팀입니다. 

서비스를 런칭하고 초기 운영을 궤도에 올리면서, 개발자로서 마주하는 가장 흥미로운 순간 중 하나는 **‘데이터의 진실성(Data Integrity)’**과 **‘사용자 경험(UX)의 사각지대’**를 동시에 해결해 나가는 과정입니다.

이번 포스팅에서는 최근 프로덕션 환경에서 마주한 두 가지 주요 이슈—**검색엔진 및 악성 봇으로 인한 통계 왜곡 문제**와 **다양한 모바일 기기에서의 뷰포트 레이아웃 깨짐 현상**—를 어떻게 아키텍처 관점에서 정의하고 해결했는지 그 기술적 의사결정 과정을 공유합니다.

---

## 1. 문제 정의 (Context & Problem)

서비스 오픈 후, 비즈니스 지표를 모니터링하기 위해 구축한 방문자 분석(Analytics) 대시보드를 검토하던 중 몇 가지 치명적인 모순을 발견했습니다.

### (1) 봇 트래픽(Phantom Traffic)으로 인한 통계 왜곡
Googlebot, Bingbot, Yandex, AhrefsBot과 같은 공인된 검색엔진 봇뿐만 아니라, 데이터 수집용 스파이더와 정체불명의 악성 자동화 크롤러(`python-requests`, `headlesschrome`, `curl`, `wget` 등)의 트래픽이 실시간 방문자(UV) 통계에 무차별적으로 합산되고 있었습니다. 이로 인해 마케팅 지표와 실제 활성 사용자(DAU/MAU) 간의 괴리가 발생하여, 데이터 기반의 의사결정이 불가능한 상태였습니다.

### (2) 모바일 뷰포트 환경에서의 UI 레이아웃 결함
홈 화면의 핵심 컨텐츠인 '인기 화장품 랭킹' 섹션에서 특정 모바일 기기 해상도(특히 소형 화면 뷰포트)에 진입할 때 제품 썸네일 이미지 공간이 비정상적으로 축소되거나, 상품명이 영역을 벗어나 텍스트가 겹치는 현상(Layout Shift)이 확인되었습니다.

## 2. 기술적 고민과 아키텍처 대안 (Trade-off)

문제를 해결하기 위해 백엔드와 프론트엔드 양쪽에서 각각 어떤 아키텍처적 대안을 검토했는지 살펴보겠습니다.

### [Backend] 봇 필터링: API Gateway vs Application Middleware
* **대안 A (API Gateway 레벨 차단):** Nginx나 Cloudflare 같은 프록시 계층에서 User-Agent를 검사하여 403 Forbidden을 리턴하는 방식.
  * *Pros:* 애플리케이션 서버로 유입되는 트래픽 부하 자체를 원천 차단 가능.
  * *Cons:* SEO를 위한 공식 검색엔진 크롤러(Googlebot 등)는 허용하면서 순수 방문자 통계 집계만 제외해야 하는 비즈니스 요구사항을 세밀하게 제어하기 번거로움.
* **대안 B (Application Middleware 기반 필터링):** FastAPI 미들웨어 계층에서 `User-Agent` 헤더를 파싱하여 통계 집계 대상(Analytics Service) 여부를 동적으로 제어하는 방식.
  * *Pros:* 비즈니스 로직과 밀접하게 결합되어 유연한 예외 처리 및 로깅 가능. SEO 크롤러의 접근은 허용하되, 통계 DB 적재 파이프라인에서만 스마트하게 필터링 가능.
  * *Cons:* 봇 요청도 애플리케이션 프로세스 내부로 진입하므로 소폭의 컴퓨팅 리소스 소모 발생.

> **결정 (Alternative B 선택):** PickSafe는 서비스의 검색엔진 노출(SEO)을 유지하면서 정밀한 유저 메트릭을 확보하는 것이 우선이므로, **애플리케이션 미들웨어 계층에서 봇 시그니처를 판별하고 통계 적재를 우회하는 방식**을 채택했습니다.

### [Frontend] 모바일 뷰포트: 하드코딩된 미디어쿼리 vs 모던 CSS 레이아웃 시스템
* **대안 A (Break-point 기반 미디어쿼리 하드코딩):** 기기별 폭(`@media (max-width: 375px)` 등)을 일일이 정의하여 폰트 크기와 이미지 사이즈를 조절하는 방식.
  * *Pros:* 구형 브라우저 호환성 확보.
  * *Cons:* 파편화된 안드로이드 기기와 끊임없이 늘어나는 신규 아이폰 폼팩터 대응에 막대한 유지보수 공수 발생.
* **대안 B (CSS `aspect-ratio` 및 `flex/grid` 유연성 극대화):** 고정 픽셀 의존도를 낮추고, 브라우저 엔진의 네이티브 레이아웃 계산 능력(`aspect-ratio: 1 / 1`, `object-fit: contain`, `min-width: 0`, `truncate`)을 활용하는 방식.
  * *Pros:* 기기 스펙에 상관없이 일관된 비율과 유연한 텍스트 오버플로우 제어 가능. CSS 코드베이스 대폭 슬림화.
  * *Cons:* 극단적으로 오래된 레거시 브라우저에서의 폴리필 검토 필요 (현재 타겟 유저 군에서는 이슈 없음).

> **결정 (Alternative B 선택):** 모바일 퍼스트 프로덕트로서 다양한 뷰포트의 변화에 유연하게 대응하기 위해, **모던 CSS 속성을 활용한 유체 레이아웃(Fluid Layout)**을 구축했습니다.

## 3. 최종 구현 및 엔지니어링 성과 (Implementation & Results)

### 1) 텔레메트리 봇 필터링 미들웨어 도입
FastAPI 애플리케이션의 핵심 미들웨어 레벨에서 `request.headers.get("user-agent")`를 정규식 기반 패턴(`bot`, `spider`, `crawler`, `python-requests`, `headlesschrome`, `curl`, `wget` 등 50여 종의 시그니처)으로 실시간 스캔합니다. 

감지된 요청은 핵심 비즈니스 로직이나 정적 리소스 응답에는 정상적으로 협조하되, 비동기 통계 집계 파이프라인(Telemetry/Analytics DB) 적재 단계에서는 원천 제외되도록 설계했습니다.

### 2) 반응형 뷰포트 카드 스타일 최적화
인기 제품 랭킹 그리드 컴포넌트에 아래의 핵심 CSS 규칙을 적용하여 시각적 안정성을 확보했습니다.
* `aspect-ratio: 1 / 1`과 `object-fit: contain` 조합을 통해 어떤 모바일 화면에서도 썸네일 비율이 왜곡되거나 찌그러지지 않도록 고정.
* Flexbox 컨테이너 내부에 `min-width: 0`을 명시하여 텍스트 노드가 부모 영역을 강제로 밀어내는 현상을 방지하고, `truncate` 처리로 깔끔한 말줄임 UX 제공.

## 4. Takeaway (교훈 및 향후 계획)

이번 작업을 통해 얻은 가장 큰 엔지니어링 교훈은 **"좋은 제품 지표는 신뢰할 수 있는 데이터 파이프라인에서 시작되며, 훌륭한 UI는 복잡한 하드코딩이 아니라 브라우저의 네이티브 기능을 얼마나 잘 활용하느냐에 달려 있다"**는 점입니다.

* **데이터 무결성:** 프론트엔드/백엔드 경계면에서 발생하는 노이즈(봇 트래픽 등)를 조기에 차단함으로써, 향후 도입할 머신러닝 기반 추천 시스템이나 사용자 행동 분석의 정확도를 높일 수 있는 발판을 마련했습니다.
* **UX 안정성:** 모바일 디바이스 파편화 문제에 대응할 때, 무분별한 미디어쿼리 확장보다는 모던 CSS 표준을 적극 채택하는 것이 장기적인 코드 유지보수성과 성능 면에서 압도적으로 유리함을 재확인했습니다.
