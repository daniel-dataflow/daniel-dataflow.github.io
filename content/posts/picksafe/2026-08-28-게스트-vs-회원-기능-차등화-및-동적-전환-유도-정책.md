서비스를 만드는 엔지니어라면 누구나 한 번쯤 이런 고민을 합니다. 

> **"회원가입 장벽을 낮춰 대규모 트래픽을 유치하고 싶지만, 동시에 비회원(Guest)이 자연스럽게 가입하도록 유도하는 방법은 없을까?"**

대부분의 서비스는 가입 프로세스를 맨 앞에 두어 사용자 진입 장벽을 높이거나(Hard Wall), 반대로 로그인 없이 모든 기능을 다 열어두어 가입 유도 타이밍을 놓치곤 합니다. 

화장품 라벨 스캔 및 성분 분석 서비스인 **픽세이프(PickSafe)** 팀은 이 문제를 해결하기 위해 **"핵심 기능(Core Value)은 무제한 제공하되, 개인화 및 데이터 저장 영역에서 손실 회피 심리를 자극하는 동적 전환 퍼널"**을 설계하기로 결정했습니다. 

이 글에서는 비회원과 회원 간의 기능 차등화 정책을 정의하고, 이를 코드 배포 없이 실시간으로 제어하기 위해 구축한 **'실시간 동적 정책 엔진 아키텍처'**와 그 과정에서의 기술적 고민을 공유합니다.

---

## 1. 문제 정의: "가입 유도"와 "콜드 스타트 방지" 사이의 트레이드오프

픽세이프는 사용자가 화장품 라벨을 촬영하면 기피 성분을 매칭해 주는 직관적인 유틸리티로 시작했습니다. 초기 사용자의 리텐션을 확보하기 위해서는 가입 절차 없이 앱을 켜자마자 바로 스캔을 경험하게 하는 **'게스트 모드'**가 필수적이었습니다.

그러나 게스트가 앱의 가치를 충분히 느낀 시점에서도 정식 회원으로 유치할 정교한 'Nudge(넛지)' 장치가 부족했습니다. 

우리는 다음과 같은 가설을 세웠습니다.
> **"핵심 기능인 '스캔'과 '성분 확인'은 완전히 무료로 열어두어 신뢰를 주되, '내가 찜한 상품 목록'과 '스캔 기록 보관'처럼 개인의 데이터 축적(Investment)이 일어나는 시점에 부드러운 가입 유도 모달을 띄운다면 가입 전환율이 극대화될 것이다."**

이를 위해 다음과 같은 기능 차등화 매트릭스를 정의했습니다.

| 기능 항목 | 게스트 (비로그인) | 회원 (로그인) | UX 전략 및 심리학적 근거 |
| :--- | :--- | :--- | :--- |
| **스캔 & 성분 대조** | **무제한** | **무제한** | 서비스 핵심 가치 경험 (무마찰 온보딩) |
| **저장한 상품 (찜)** | **최대 N개 (동적 제한)** | **무제한 (클라우드 동기화)** | 손실 회피 심리 자극 (5개 초과 시 가입 제안) |
| **스캔 기록 보관** | **최근 M건 (로컬 스토리지)** | **전체 이력 서버 보관** | 기기 유실 시 데이터 삭제 리스크 고지 |
| **검색 기록** | **당일 세션 한정** | **영구 보관 & 자동완성** | 검색 편의성 차등 |

## 2. 아키텍처 설계: 코드 배포 없는 실시간 정책 제어 (Dynamic Tuning)

"게스트가 몇 개의 상품을 저장했을 때 가입 팝업을 띄우는 것이 가장 효과적일까?"
이 질문에 대한 정답은 고정되어 있지 않습니다. 어떤 유저군에게는 `5개`가 적절할 수 있고, 이벤트 기간에는 `10개`로 늘려야 할 수도 있습니다. 

이를 하드코딩하여 클라이언트(App/Web)에 심어둔다면, 수치를 변경할 때마다 배포 및 스토어 심사를 거쳐야 하는 병목이 발생합니다. 따라서 우리는 **클라이언트 비즈니스 로직과 비회원 정책 설정을 완전히 분리하는 실시간 엔진**을 설계했습니다.

### 동적 정책 제어 아키텍처 흐름

비회원 제약 조건 데이터(예: 찜 한도, 스캔 보관 한도)는 DB의 공통 설정 테이블에서 관리되며, 관리자가 이를 실시간으로 변경하면 클라이언트에 즉시 반영되는 구조입니다.

```
┌─────────────────────────────────────────────────────────────┐
│ [관리자 대시보드] (Admin Console)                            │
│ ⚙️ 실시간 게스트 정책 변경 (예: 찜 한도 5 -> 8개로 수정)          │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼ (공통 설정 DB 업데이트)
┌─────────────────────────────────────────────────────────────┐
│ [설정 조회 API] (GET /api/v1/app-config)                     │
│ { "max_saved_products": 5, "max_scan_history": 3 }          │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼ (클라이언트 동적 렌더링 및 로직 판단)
┌─────────────────────────────────────────────────────────────┐
│ [사용자 UI - 결과 화면 및 마이페이지]                             │
│                                                             │
│ 1. 실시간 UX 노출: "🏷️ 게스트 모드 · 3/5개 저장됨"             │
│ 2. 임계값 도달 시 스마트 바텀 시트 노출:                        │
│    - [기존 저장 품목 교체 후 저장 (FIFO)]                    │
│    - [회원가입하고 무제한 보관 및 연동]                       │
└─────────────────────────────────────────────────────────────┘
```

## 3. 핵심 기술적 고민과 트레이드오프 (Trade-off)

### 고민 1. 게스트 데이터를 어디에 저장할 것인가? (Local vs Server DB)
로그인하지 않은 사용자의 찜 목록과 스캔 기록을 관리하는 방식에 대해 두 가지 대안을 두고 토론했습니다.

*   **대안 A: 임시 세션 ID를 발급하여 서버 DB에 저장**
    *   *장점*: 가입 시점에 서버에서 1:1 매핑만 해주면 되므로 전환 데이터 유실이 적음.
    *   *단점*: 가입하지 않고 이탈하는 대량의 게스트 정크 데이터가 DB 용량을 무한정 차지함. DB 비용 급증.
*   **대안 B: 브라우저 LocalStorage / 기기 로컬 DB 활용**
    *   *장점*: 서버 스토리지 비용 Zero. 네트워크 요청 최소화로 빠른 UX 구현 가능.
    *   *단점*: 사용자가 쿠키를 지우거나 기기를 바꾸면 데이터 유실. 가입 시 로컬 데이터를 서버로 마이그레이션하는 동기화 로직 필요.

**[선택]** 
우리는 비즈니스 효율과 인프라 비용을 고려하여 **대안 B(로컬 스토리지 기반)**를 채택했습니다. 기기 변경 시 데이터 유실 위험이 있다는 점 자체가 오히려 사용자로 하여금 **"내 데이터를 영구 보관하기 위해 가입해야겠다"**는 동기를 부여하는 훌륭한 넛지 포인트가 될 수 있다고 판단했기 때문입니다.

### 고민 2. 가입 시점의 데이터 이관 (Data Migration & Synchronize)
로컬에 5개의 상품을 찜해 둔 게스트가 가입 전환 모달을 클릭해 회원가입을 완료했습니다. 이때 기존 기기에 저장된 5개의 데이터를 로그인한 계정의 서버 DB로 안전하게 합쳐주어야(Merge) 합니다.

이때 발생할 수 있는 코너 케이스를 다음과 같이 제어했습니다.
*   **중복 제거 (Deduplication)**: 로컬 스토리지의 찜 리스트와 이미 서버 DB에 존재할 수 있는 기존 회원 찜 리스트 간 고유 ID(UUID) 기준 중복 체크 및 병합 처리.
*   **한도 초과 시 처리 (FIFO)**: 만약 어드민 정책이 실시간으로 5개에서 3개로 줄어든 시점에 사용자가 로컬에 5개를 들고 가입하려고 시도한다면? FIFO(First-In-First-Out) 기반으로 오래된 순서대로 트리밍하여 최신 3개만 이관하는 정밀한 정합성 검증 로직을 클라이언트/서버 단 양쪽에 모두 구현했습니다.

## 4. 데이터 기반 의사결정: 전환 성과 추적 체계 (Telemetry)

새로운 게스트 정책이 가입률에 미치는 영향을 데이터로 입증하지 못한다면 훌륭한 아키텍처라 볼 수 없습니다. 우리는 비회원의 이탈과 전환 경로를 정량적으로 파악하기 위해 3가지 핵심 지표를 추적하는 이벤트를 설계했습니다.

1.  **Nudge Drop-off Rate (넛지 직후 전환 실패율)**:
    *   한도 제한(N/5) 모달을 마주한 게스트 중 `[회원가입]` 버튼을 누르지 않고 닫은 비율을 추적합니다. 이탈률이 과도하게 높다면 한도가 너무 빡빡하다는 신호이므로, 관리자 페이지에서 즉시 한도를 상향 조정(e.g., 5개 $\rightarrow$ 8개)하여 테스트합니다.
2.  **Simple Bounce Rate (단순 바운스율)**:
    *   접속 후 핵심 가치 기능(스캔)을 단 한 번도 실행하지 않고 이탈한 유저 비율을 모니터링하여, 초기 온보딩 UI의 직관성을 점검합니다.
3.  **Long-term Churn (게스트 소멸율)**:
    *   가입하지 않은 상태로 특정 기간 내 재방문하지 않는 기기 토큰을 추적하여 마케팅 채널 재인입 시나리오에 활용합니다.

## 5. Engineering Takeaways: 프로젝트를 통해 배운 점

1.  **성급한 인프라 확장을 피하는 설계**: 모든 비회원 상태 정보를 서버 DB에 쓰려 했다면 매달 대규모 트래픽 비용을 감당해야 했을 것입니다. 로컬 자원과 서버 자원의 역할을 명확히 분리함으로써, 최소한의 클라우드 비용으로 최대의 서비스 목적을 달성했습니다.
2.  **유연성(Flexibility) 확보의 중요성**: 비즈니스 정책 수치는 기획팀과 마케팅팀의 가설 검증 결과에 따라 수시로 변합니다. 이를 실시간 JSON 설정 API 구조로 이원화해 둔 덕분에 개발팀의 리소스 낭비(수정 배포)를 완전히 방지했습니다.
3.  **기능 제한(Blocking)보다 가치 제안(Seduction)이 강하다**: 시스템 설계 단계부터 사용자를 '막는 것'이 아니라 '보여주는 것'에 초점을 맞추었습니다. 기술이 비즈니스 목표와 사용자의 심리학적 경험을 어떻게 지원할 수 있는지 깊이 체득하는 계기가 되었습니다.
