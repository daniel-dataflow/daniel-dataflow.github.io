안녕하세요. 화장품 성분 분석 서비스 **PickSafe** 백엔드/프로덕트 에디터입니다.

서비스를 운영하면서 가장 풀기 까다로운 숙제 중 하나는 **"어떻게 하면 사용자에게 거부감을 주지 않고 자연스럽게 회원가입(Conversion)을 유도할 것인가?"**입니다. 특히 우리 서비스처럼 라벨 스캔과 기피 성분 확인이 핵심 가치인 경우, 앱을 켜자마자 "로그인하세요"라는 로그인 벽(Login Wall)을 세우는 순간 사용자 이탈률(Bounce Rate)은 수직 상승합니다.

이번 포스팅에서는 **핵심 기능의 장벽은 없애되, 저장과 이력 관리의 편리성 영역에서 손실 회피 심리를 자극하여 자연스러운 회원 전환을 유도한 아키텍처와 정책 설계 과정**을 공유하고자 합니다.

---

## 1. Problem: 콜드스타트 해소와 비즈니스 성장의 딜레마

초기 PickSafe는 회원가입 없이도 누구나 즉시 화장품 라벨을 스캔할 수 있는 **게스트 모드(Guest Mode)**를 지원했습니다. 이 방식은 첫 유입 장벽(콜드스타트)을 낮추는 데는 탁월했지만, 치명적인 문제가 있었습니다.

* **낮은 회원 전환율**: 사용자가 익명 상태로 편리하게 기능을 이용만 할 뿐, 서비스에 계정을 만들고 정착할 동기(Trigger)가 부족했습니다.
* **무분별한 기능 차단의 위험**: 회원 전환을 유도하겠다고 스캔 기능 자체를 막아버리면, 서비스의 본질적인 가치가 훼손되어 바이럴과 유입 자체가 끊기는 역효과가 발생합니다.

> **핵심 과제**: *"핵심 가치 경험은 100% 보장하되, 서비스와 깊이 상호작용하는 시점에 자연스럽게 회원가입을 유도하는 구조를 어떻게 설계할 것인가?"*

---

## 2. Trade-off & Architecture: "막는다"가 아니라 "보여준다"

우리는 기능을 일방적으로 차단하는 방식 대신, **사용자의 손실 회피 심리(Loss Aversion)**를 자극하는 전략을 선택했습니다. 

### ① 기능의 전략적 분리 (Core vs Persistence)
* **핵심 가치 활동 (`스캔`, `기피 성분 등록`, `공유`)**: 게스트에게도 무제한으로 제공하여 첫 경험의 마찰을 제거했습니다.
* **저장 및 이력 영역 (`찜한 상품`, `스캔 기록`, `검색 기록`)**: 게스트에게는 일정한 한도(예: 찜 5개, 기록 3건)를 두되, 한계에 도달했을 때 스마트한 선택지를 제공합니다.

### ② 하드코딩 탈피: 관리자 주도형 동적 정책(Dynamic Policy) 엔진
기능 제한 횟수(5개, 3건 등)를 프론트엔드나 백엔드 코드에 하드코딩하면, 지표를 보며 빠르게 실험(A/B Test or Tuning)하기 어렵습니다. 
이를 해결하기 위해 인프라 설정(Infra Settings) DB와 연동된 **동적 설정 API**를 구축했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ [관리자 대시보드] 게스트 전환 정책 설정                     │
└─────────────────────────────────────────────────────────────┘
                             │ (DB 저장)
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ [공개 API: GET /api/config/guest-policy]                    │
│ { "max_saved_products": 5, "max_scan_history": 3 }          │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼ (실시간 동적 연동)
┌─────────────────────────────────────────────────────────────┐
│ [사용자 프론트엔드]                                         │
│ - 상시 상태 노출: "🏷️ 게스트 모드 · 3/5개 저장됨"         │
│ - 6번째 저장 시 스마트 모달(FIFO 교체 vs 회원가입 후 무제한)│
└─────────────────────────────────────────────────────────────┘
```

1. **중앙 집중식 설정 관리**: 관리자 어드민 페이지에서 찜 한도나 스캔 기록 보관 개수를 변경하면, DB에 즉시 반영됩니다.
2. **클라이언트 실시간 동기화**: 프론트엔드는 API를 통해 최신 정책을 읽어와 사용자에게 현재 상태(`3/5개 저장됨`)를 투명하게 노출하고, 꽉 찼을 때의 인터랙션을 동적으로 처리합니다.

---

## 3. UX & Engineering Strategy: 스마트 모달과 손실 회피

사용자가 게스트 상태로 5개의 상품을 찜한 뒤, 6번째 상품을 저장하려고 시도하는 순간이 바로 전환 퍼널의 핵심(Conversion Moment)입니다.

이때 단순히 "로그인이 필요합니다"라는 차가운 에러 팝업을 띄우지 않고, 다음과 같은 **스마트 모달(Smart Modal / Bottom Sheet)**을 노출합니다.

* **선택지 A**: `[가장 오래된 상품 교체 후 저장 (FIFO)]` -> 게스트 경험을 유지해주되, 관리가 번거로워짐을 체감하게 함.
* **선택지 B**: `[회원가입하고 무제한 보관하기]` -> 지금까지 모은 소중한 찜 목록과 스캔 기록을 원클릭으로 서버에 안전하게 이관.

또한, 마이페이지와 결과 화면 상단에 현재 상태를 항상 노출(`🏷️ 게스트 모드 · 3/5개 저장됨 · 기기 변경 시 삭제 위험`)하여 자연스러운 각인 효과를 주었습니다.

---

## 4. 닫으며: 데이터 기반의 지속 가능한 최적화

이번 아키텍처 개편은 단순히 UI를 바꾼 것이 아니라, **비즈니스 지표를 엔지니어링 관점에서 컨트롤할 수 있는 기반**을 다진 작업이었습니다.

우리는 관리자가 실전에서 정책을 튜닝할 수 있도록 3가지 핵심 이탈 지표(Drop-off, Bounce Rate, Long-term Churn)를 함께 모니터링하고 있습니다. 예를 들어, 5개 제한 모달에서 이탈하는 비율이 너무 높다면 관리자 페이지에서 한도를 7개나 10개로 즉시 상향 조정하며 최적의 균형점을 찾아갈 수 있습니다.

"좋은 기술은 비즈니스의 성장을 방해하지 않고 오히려 가속화한다"는 점을 다시 한번 느낀 프로젝트였습니다. 앞으로도 PickSafe는 유저에게는 매끄러운 경험을, 비즈니스에는 확실한 성장을 가져다주는 견고한 아키텍처를 만들어 나갈 것입니다.

감사합니다.
