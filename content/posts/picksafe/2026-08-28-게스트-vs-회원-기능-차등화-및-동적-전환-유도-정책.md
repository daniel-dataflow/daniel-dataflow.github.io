안녕하세요, **PickSafe** 팀의 백엔드 엔지니어 Daniel & Antigravity입니다. 

화장품 라벨 스캔 및 기피 성분 대조 서비스인 PickSafe는 서비스 초기 유입 장벽을 낮추기 위해 **'비회원(게스트) 모드'**를 기본 지원하고 있습니다. 하지만 서비스가 성장함에 따라 **"어떻게 하면 유저의 첫 진입을 방해하지 않으면서, 자연스럽게 정식 회원으로 안착시킬 것인가?"**라는 고질적인 프로덕트 엔지니어링 과제에 직면했습니다.

이번 포스팅에서는 무조건적인 회원가입 유도가 아닌, **핵심 가치는 온전히 제공하되 저장과 이력 영역에서 손실 회피 심리를 자극하고, 관리자(Admin)가 실시간으로 정책을 튜닝할 수 있도록 구현한 동적 전환 아키텍처**의 기술적 고민과 해결 과정을 공유합니다.

---

## 1. Problem: 콜드스타트 해소와 비즈니스 성장 사이의 딜레마

서비스 초기, 개발팀과 프로덕트 오너가 마주한 가장 큰 문제(Problem)는 **높은 이탈률(Drop-off)**이었습니다.

- **진입장벽의 문제**: 앱을 켜자마자 회원가입을 요구하면, 사용자들은 성분 분석을 해보기도 전에 이탈(Bounce)해 버립니다.
- **성장(Conversion)의 문제**: 반대로 모든 기능을 완전히 무료로, 익명으로 열어주면 사용자는 편리하지만, 서비스 내에 데이터가 쌓이지 않아 장기적인 락인(Lock-in) 효과와 재방문율(Retention)을 확보할 수 없습니다.

> **핵심 질문**: *"사용자의 첫 경험(Zero-friction Onboarding)을 해치지 않으면서, 서비스에 애착을 가진 시점에 어떻게 자연스러운 회원가입 전환(Funnel)을 유도할 것인가?"*

---

## 2. Trade-off & Architecture: "막는다"가 아니라 "보여준다"

우리는 기능을 일방적으로 차단하는 방식 대신, **UX 심리학(손실 회피 심리)**과 **유연한 시스템 설계**를 결합하기로 결정했습니다.

### ① 핵심 기능은 100% 무제한 개방
`스캔 및 성분 대조`, `기피 성분 등록`, `결과 공유`와 같은 서비스의 본질적인 가치는 게스트에게도 제한 없이 열어두어 콜드스타트 장벽을 완전히 제거했습니다.

### ② 저장/이력 영역의 전략적 차등화 및 동적 튜닝
사용자가 서비스를 쓰면서 자연스럽게 쌓이는 데이터(찜한 상품, 스캔 기록, 검색 기록)에 대해서는 제한을 두되, 이를 하드코딩하지 않고 **관리자 페이지에서 실시간으로 튜닝할 수 있는 동적 설정(Dynamic Configuration) 구조**로 설계했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ [관리자 대시보드] 관리자가 게스트 정책 실시간 설정           │
│ (예: 찜 한도: 5개 / 스캔 기록 한도: 3건)                    │
└─────────────────────────────────────────────────────────────┘
                             │ (DB 세팅 저장)
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ [공개 API 엔드포인트] 실시간 정책 데이터 제공                 │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ [사용자 프론트엔드]                                          │
│ - 상시 상태 노출: "🏷️ 게스트 모드 · 3/5개 저장됨"            │
│ - 6번째 저장 시 스마트 모달(Modal) 노출:                    │
│   1) [가장 오래된 상품 교체 후 저장 (FIFO)]                 │
│   2) [회원가입하고 무제한 보관하기 (전체 자동 이관)]        │
└─────────────────────────────────────────────────────────────┘
```

## 3. Implementation: 어떻게 구현했는가?

### 실시간 동적 정책 API 구조
백엔드에서는 정책 수치를 코드에 박아두는 대신, 설정 테이블(`infra_settings`)을 두고 API를 통해 프론트엔드로 전달합니다.

```python
# [Conceptual Code] FastAPI를 활용한 게스트 정책 조회 엔지니어링 예시
@router.get("/api/config/guest-policy")
async def get_guest_policy(db: Session = Depends(get_db)):
    # 관리자 어드민에서 실시간으로 튜닝된 정책 값을 조회
    policy = settings_repository.get_active_guest_policy(db)
    return {
        "max_saved_products": policy.max_saved_products, # 기본값 5
        "max_scan_history": policy.max_scan_history,     # 기본값 3
        "session_search_only": True
    }
```

### 사용자 경험(UX)과 심리적 넛지(Nudge)
프론트엔드에서는 마이페이지와 결과 화면에 현재 게스트 상태와 한도 카운터를 상시 노출합니다.
- *"🏷️ 게스트 모드 · 3/5개 저장됨 (기기 변경 시 삭제 위험)"*

사용자가 5개를 모두 채우고 6번째 상품을 저장하려는 순간, 시스템은 단순 에러를 뿜는 대신 **스마트 모달(Bottom Sheet)**을 띄워 두 가지 선택지를 제시합니다.
1. **FIFO(First-In, First-Out) 방식으로 가장 오래된 찜 교체하기**
2. **회원가입하고 지금까지의 기록을 서버로 안전하게 이관하기**

이를 통해 사용자는 강요받는다는 느낌 대신, 본인의 데이터를 지키기 위한 자발적인 동기로 회원가입 버튼을 누르게 됩니다.

## 4. Monitoring & Data-Driven Tuning

좋은 아키텍처는 배포로 끝나지 않고 측정 가능해야 합니다. 우리 팀은 게스트 전환 정책이 실제로 효과가 있는지 검증하기 위해 3가지 핵심 이탈 지표(Drop-off Metrics)를 대시보드에 연동했습니다.

1. **Nudge 직후 전환 실패율**: 5개 제한 모달을 만난 게스트 중 가입을 누르지 않고 이탈한 비율 (이탈률이 너무 높다면 관리자 페이지에서 한도를 7개~10개로 즉시 상향 조정 가능)
2. **단순 세션 이탈률(Bounce Rate)**: 첫 접속 후 스캔 0회 상태로 나간 비율
3. **게스트 장기 이탈률**: 30일 이내 미접속 세션 수

## 5. Takeaways (엔지니어링 교훈)

이번 게스트 정책 개편을 통해 얻은 교훈은 명확합니다.

- **제한은 억압이 아니라 맥락이어야 한다**: 서비스를 막는 대신, 사용자가 진정으로 가치를 느끼는 순간(저장 및 보관)에 맞춰 자연스러운 전환 퍼널을 설계할 수 있었습니다.
- **운영 유연성(Configurability)의 가치**: 비즈니스 정책은 언제든지 바뀔 수 있습니다. 하드코딩을 배제하고 관리자 어드민을 통한 동적 제어 구조를 채택함으로써, 개발자 배포 없이도 프로덕트 매니저가 실시간으로 실험(A/B Test 유사 효과)을 진행할 수 있는 기반을 마련했습니다.

PickSafe는 앞으로도 사용자에게는 최고의 무마찰 경험을, 비즈니스에게는 견고한 성장 지표를 안겨주는 기술적 고민을 이어가겠습니다.
