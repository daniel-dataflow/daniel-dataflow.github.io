안녕하세요, **PickSafe** 팀의 백엔드/프로덕트 엔지니어입니다.

서비스 초기 성장을 이끌어내는 데 있어 가장 중요한 지표 중 하나는 **‘첫 사용자 경험(First-time User Experience)의 마찰력(Friction)을 얼마나 줄이느냐’**입니다. 화장품 라벨 스캔 및 성분 분석 서비스인 PickSafe 역시 사용자가 앱을 켜자마자 회원가입을 강요받는다면, 콜드스타트(Cold Start) 구간을 넘지 못하고 이탈할 것입니다.

하지만 반대로, **모든 기능을 로그인 없이 무제한으로 제공한다면 굳이 회원가입을 할 이유가 사라집니다.** 

이번 포스팅에서는 **‘핵심 가치는 100% 열어주되, 저장과 이력 관리 영역에서 손실 회피 심리를 자극하여 자연스러운 회원 전환을 유도하는 동적 정책 아키텍처’**를 어떻게 설계하고 구현했는지 공유하고자 합니다.

---

## 1. Problem: 무제한의 편안함 뒤에 숨은 전환율 정체

PickSafe는 게스트 모드(Guest Mode)를 통해 회원가입 없이도 누구나 즉시 화장품을 스캔하고 기피 성분을 대조할 수 있도록 지원하고 있습니다. 

초기에는 이 방식이 신규 유입(Traffic)을 늘리는 데 큰 도움이 되었지만, 비즈니스 지표를 분석한 결과 치명적인 병목(Bottleneck)이 발견되었습니다.
- **높은 게스트 체류 시간 대비 낮은 회원 전환율**: 사용자들이 서비스를 잘 쓰지만, 로그인 계정으로 데이터가 쌓이지 않고 세션이 종료되면 그대로 이탈했습니다.
- **‘막는’ 방식의 한계**: 만약 특정 기능(예: 스캔)을 로그인 사용자에게만 제한했다면, 사용자는 첫 화면에서 바로 앱을 삭제했을 것입니다.

> **Core Question**: *"어떻게 하면 사용자의 초기 진입 장벽을 완전히 없애면서도, 서비스에 애착을 가지는 시점에 자연스럽게 회원가입으로 유도할 수 있을까?"*

---

## 2. Trade-off & Architecture: "막는다"가 아니라 "보여준다"

우리는 강제적인 팝업으로 유저를 차단하는 대신, **사용자의 ‘손실 회피 심리(Loss Aversion)’를 자극하는 UX 전략**과 이를 **서버 하드코딩 없이 유연하게 제어할 수 있는 동적 설정 아키텍처**를 선택했습니다.

### ① 기능의 전략적 차등화
- **절대 차단 불가 영역**: `스캔 & 성분 대조`, `기피 성분 등록`은 서비스의 본질이므로 게스트에게도 100% 무제한으로 제공합니다.
- **전략적 차등 영역 (저장 및 이력)**: 
  - 찜한 상품(저장): 게스트 최대 5개 제한 (6번째 저장 시 교체 또는 회원가입 유도)
  - 스캔 기록: 게스트 최근 3건 보관

### ② 하드코딩을 피하고 비즈니스 민첩성을 높인 동적 설정 구조
이러한 제한치(예: 찜 5개, 스캔 3건)는 서비스 운영 과정에서 A/B 테스트나 지표에 따라 수시로 바뀔 수 있습니다. 따라서 이를 코드에 상수로 박아두는(Hard-coding) 대신, 관리자 페이지를 통해 실시간으로 튜닝할 수 있는 **동적 정책 연동 아키텍처**로 설계했습니다.

```
┌─────────────────────────────────────────────────────────────┐
│ [관리자 대시보드]                                           │
│ ⚙️ 게스트 전환 정책 설정 (찜 한도: N개 / 스캔 한도: M개)       │
└─────────────────────────────────────────────────────────────┘
                             │ (DB 설정 저장)
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ [공개 API 엔드포인트]                                       │
│ 실시간 게스트 정책 스펙 제공                                  │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼ (프론트엔드 연동)
┌─────────────────────────────────────────────────────────────┐
│ [클라이언트 (Web/App)]                                      │
│ 1. 상시 상태 노출: "🏷️ 게스트 모드 · 3/5개 저장됨"         │
│ 2. 한도 도달 시 스마트 모달 (FIFO 교체 vs 회원가입 및 이관)   │
└─────────────────────────────────────────────────────────────┘
```

## 3. Implementation Details: 스마트 Nudge와 데이터 이관

사용자가 한도(예: 5개)에 도달했을 때 단순 에러를 띄우는 것은 최악의 UX입니다. 우리는 사용자가 자연스럽게 선택지를 마주하도록 설계했습니다.

1. **상시 상태 노출 (Always-on Nudge)**:
   - 마이페이지 및 결과 화면에 현재 상태를 투명하게 노출합니다.
   - *예시: "🏷️ 게스트 모드 · 3/5개 저장됨 (기기 변경 시 삭제 위험)"*
2. **6번째 저장 시도 시 스마트 모달(Modal / Bottom Sheet)**:
   - 사용자가 열심히 고른 상품들을 잃어버리지 않도록 두 가지 선택지를 제공합니다.
   - 옵션 A: **[가장 오래된 상품을 교체하고 저장 (FIFO)]** -> 게스트 경험 유지
   - 옵션 B: **[회원가입하고 무제한 보관하기]** -> 지금까지 쌓은 로컬 데이터를 서버 DB로 안전하게 자동 이관(Migration)

---

## 4. Churn & Drop-off 측정 체계

엔지니어링의 완성은 모니터링입니다. 우리는 이 정책이 실제로 효과가 있는지 검증하기 위해 세 가지 핵심 지표(Metrics)를 로깅하고 분석 체계를 구축했습니다.

1. **Nudge 직후 전환 실패율 (Drop-off)**: 제한 모달을 만난 게스트 중 가입을 누르지 않고 이탈한 비율 (이 수치가 너무 높으면 한도를 5개에서 7~10개로 상향 조정)
2. **단순 세션 이탈 (Bounce Rate)**: 스캔 0회 상태로 앱을 나간 비율
3. **게스트 재방문 소멸 (Long-term Churn)**: 30일 이내 미복귀 세션 추적

---

## 5. Takeaway & Lessons Learned

이번 아키텍처 설계와 구현을 통해 다음과 같은 엔지니어링 및 프로덕트적 교훈을 얻었습니다.

- **좋은 비즈니스 로직은 기술적 제약을 최소화한다**: 시스템을 경직되게 만들지 않고, 관리자 설정을 통해 동적으로 정책을 제어할 수 있게 분리함으로써 운영 효율성을 극대화했습니다.
- **UX와 데이터 수집의 공존**: 사용자의 편의를 뺏지 않으면서도, 손실 회피라는 인간의 심리를 공학적으로 녹여내어 강제성 없는 자발적 회원 전환 퍼널을 완성했습니다.

제품의 성장을 고민하는 백엔드/프로덕트 엔지니어분들께 "막지 말고 보여주며, 유연하게 제어하라"는 이번 설계 방식이 작은 영감이 되었기를 바랍니다. 감사합니다!
