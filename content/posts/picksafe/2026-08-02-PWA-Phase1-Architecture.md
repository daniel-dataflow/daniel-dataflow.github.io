안녕하세요. **PickSafe** 백엔드/아키텍처 에디터입니다. 
최근 PickSafe 팀은 모바일 웹 환경의 사용성 한계를 극복하고, 네이티브 앱과 같은 사용자 경험을 제공하기 위해 **PWA(Progressive Web App) Phase 1** 도입을 성공적으로 마쳤습니다. 

이번 글에서는 단순한 기능 구현을 넘어, 한정된 리소스 속에서 프로덕션 안정성을 확보하기 위해 어떤 기술적 고민을 했고 왜 지금의 아키텍처를 선택했는지 공유해 드립니다.

---

## 1. 문제 정의 (Problem): 모바일 웹의 한계와 접근성 마찰

PickSafe 서비스 특성상 모바일 환경에서의 접속 빈도가 매우 높습니다. 하지만 기존 모바일 웹 방식은 다음과 같은 치명적인 UX 마찰(Friction)을 발생시키고 있었습니다.

* **반복적인 접근의 불편함**: 사용자가 브라우저(Safari, Chrome 등)를 실행할 때마다 URL을 입력하거나 북마크를 찾아 들어가야 함.
* **브라우저 UI로 인한 몰입감 저하**: 브라우저 주소창과 툴바가 화면 공간을 차지하여 네이티브 앱에 비해 UX가 떨어진다는 피드백 접수.

우리의 목표는 명확했습니다. **"별도의 앱스토어 심사 과정을 거치지 않고, 사용자가 웹에서 즉시 네이티브 앱처럼 홈 화면에 설치하여 진입할 수 있게 만들자."**

---

## 2. 기술적 고민과 대안 비교 (Trade-offs & Decisions)

PWA 도입을 기획하며 마주한 핵심 기술적 딜레마와 그에 대한 의사결정 과정입니다.

### 2.1 서비스 워커(Service Worker) 전략: "오프라인 캐싱인가, 설치 안정성인가?"
PWA를 검색하면 대다수가 강력한 '오프라인 캐싱(Offline Caching)'과 '백그라운드 동기화'를 강조합니다. 하지만 프로덕션 환경에서 무분별한 캐싱 전략은 **프론트엔드 배포 후 리소스가 갱신되지 않는 치명적인 캐시 오염(Stale Cache) 장애**로 이어질 위험이 큽니다.

* **대안 A (Full PWA)**: 설치와 오프라인 캐싱, 푸시 알림을 한번에 도입.
  * *Pros*: 완벽한 오프라인 경험 제공.
  * *Cons*: 캐시 무효화(Cache Invalidation) 전략 부재 시 디버깅 지옥 및 사용자 브라우저 강제 새로고침 유도 필요.
* **대안 B (Phase 1: 설치 우선 전략) - [SELECTED]**: 서비스 워커는 등록하되, 캐싱 로직은 완전히 비워둠.
  * *Pros*: 캐시 관련 장애 원인 원천 차단. PWA의 핵심 목적인 '홈 화면 설치(Add to Home Screen)' 기능과 네이티브 감성(스플래시 화면, 테마 컬러)만 빠르게 검증 가능.
  * *Cons*: 오프라인 상태에서는 동작하지 않음 (Phase 2로 연기).

> **Decision**: 1차 배포의 목적은 오프라인 지원이 아닌 **'앱 진입 장벽 낮추기'**입니다. 따라서 복잡한 캐싱 로직은 과감히 배제하고 설치 기능 검증에만 집중하기로 결정했습니다.

### 2.2 어드민 영역의 PWA 배제 (Scope Control)
모든 페이지에 무조건적인 PWA를 적용하는 것은 오버엔지니어링입니다. 관리자(Admin) 페이지의 경우, 보안과 기능 특성상 데스크톱 환경에서 브라우저를 통해 직접 접속하는 것이 훨씬 효율적이며, 모바일 홈 화면 설치 대상이 아닙니다.
* 따라서 `base.html`을 사용하는 일반 사용자 화면에만 PWA 메타 태그와 스크립트를 격리하고, 어드민 템플릿 영역은 완전히 배제하여 불필요한 프롬프트 노출을 막았습니다.

### 2.3 백엔드 라우팅: 서비스 워커 Scope 이슈 해결 (FastAPI)
서비스 워커는 기본적으로 **자신이 위치한 디렉토리 이하**의 경로만 통제(Scope)할 수 있는 보안 정책을 가집니다. 
우리의 정적 자원은 `/static/` 디렉토리 하위에서 서빙되고 있었기 때문에, 이 상태 그대로 등록하면 최상위 도메인(`https://example.com/`) 전체를 제어할 수 없는 문제가 발생합니다.

이를 해결하기 위해 프론트엔드 파일 위치만 수정하는 대신, **FastAPI 백엔드 라우터에서 명시적인 엔드포인트**를 열어주기로 했습니다.

```python
# FastAPI 라우팅 예시 (개념 코드)
@app.get("/manifest.json")
async def get_manifest():
    return FileResponse("static/images/pwa/manifest.json")

@app.get("/service-worker.js")
async def get_service_worker():
    return FileResponse("static/js/service-worker.js", media_type="application/javascript")
```
이를 통해 최상위 루트 경로에서도 브라우저가 원활하게 Manifest와 Service Worker를 인식할 수 있도록 아키텍처를 설계했습니다.

## 3. 최종 구현 및 검증 (Validation)

도입 후, 크로스 브라우징 환경에서 다음과 같은 검증 시나리오를 수행하여 안정성을 확보했습니다.

1. **iOS Safari 검증**: 아이폰 사파리에서 '홈 화면에 추가' 진행 시, 지정한 아이보리 파스텔 톤(`#FFF8F0`) 테마 컬러와 리사이징된 아이콘(192x192, 512x512)이 스플래시 화면에 정상 노출되는지 확인.
2. **어드민 격리 검증**: 관리자 페이지 진입 시 서비스 워커가 등록되지 않으며, 불필요한 앱 설치 프롬프트가 뜨지 않는지 확인.
3. **Android Chrome 검증**: 안드로이드 환경에서 하단에 자연스러운 '앱 설치' 네이티브 팝업이 트리거되는지 확인.

## 4. 엔지니어링 교훈 (Takeaways)

* **완벽함보다 점진적인 Delivery**: 한 번에 모든 PWA 기능을 넣으려 했다면 캐싱 이슈로 고생했을 것입니다. "설치 우선(Phase 1)"이라는 명확한 제약(Constraint)을 두어 리스크를 최소화하고 가치를 빠르게 전달할 수 있었습니다.
* **백엔드와 프롬프트의 협력**: 프론트엔드 기술처럼 보이는 PWA도 브라우저 보안 정책(Scope)을 준수하기 위해서는 백엔드(FastAPI)의 라우팅단에서의 세심한 설계가 뒷받침되어야 한다는 점을 다시 한번 확인했습니다.

PickSafe는 앞으로도 사용자에게 매끄럽고 빠른 경험을 제공하기 위해 기술적 타협점과 최적의 아키텍처를 치열하게 고민하겠습니다. 감사합니다.
