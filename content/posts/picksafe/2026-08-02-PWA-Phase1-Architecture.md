모바일 환경에서의 접근성은 서비스의 성패를 가르는 중요한 지표 중 하나입니다. PickSafe 역시 모바일 브라우저를 통해 접속하는 유저 비중이 압도적으로 높았습니다. 하지만 브라우저를 켤 때마다 URL을 입력하거나 북마크를 뒤져야 하는 마찰(Friction)은 사용자 경험을 떨어뜨리는 명확한 병목이었습니다.

이를 해결하기 위해 **PWA(Progressive Web App)** 도입을 검토하게 되었습니다. 네이티브 앱 개발이라는 거대한 리소스를 들이지 않고도, 웹을 기반으로 홈 화면 설치와 네이티브 앱 같은 사용자 경험을 제공할 수 있기 때문입니다.

이번 글에서는 PickSafe가 PWA Phase 1을 도입하며 마주한 기술적 고민, 리스크를 최소화하기 위한 아키텍처적 트레이드오프, 그리고 백엔드(FastAPI)단에서의 라우팅 최적화 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): 웹의 한계와 유저 경험의 마찰

PickSafe는 사용자가 빠르게 접속해 핵심 기능을 이용해야 하는 서비스입니다. 그러나 모바일 브라우저 환경은 다음과 같은 구조적 한계가 있었습니다.
* **접근의 번거로움**: 매번 브라우저를 실행하고 주소를 입력하거나 북마크를 찾아야 함.
* **몰입도 저하**: 브라우저 주소창과 탭 UI로 인해 네이티브 앱 특유의 몰입감 있는 화면 제공 불가.

이 문제를 해결하기 위해 PWA의 핵심 기능인 **"홈 화면에 추가(Add to Home Screen)"**를 지원하기로 결정했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 2.1 서비스 워커(Service Worker) 전략: "오프라인 캐싱" vs "안정적인 설치"
PWA를 도입한다고 하면 흔히 강력한 오프라인 캐싱(`Fetch` 이벤트 가로채기, Cache API 등)을 먼저 떠올립니다. 하지만 시니어 관점에서 Phase 1의 비즈니스 목표와 리스크를 저울질했을 때, 오프라인 캐싱은 당장 불필요한 위험 요소였습니다.

* **대안 A (Full PWA)**: 오프라인 모드 지원 및 리소스 캐싱 적극 도입
  * *Pros*: 네트워크가 불안정한 환경에서도 동작, 속도 극대화.
  * *Cons*: 캐싱 정책 설계 오류 시, 배포 후에도 유저 브라우저에 구버전 리소스가 남아 수정이 반영되지 않는 **치명적인 캐시 꼬임 장애** 발생 가능성 높음.
* **대안 B (Phase 1: 설치 우선 전략)** (★ 선택)
  * *Pros*: 캐시 관련 장애 원천 차단. 오직 홈 화면 설치 및 네이티브 앱 스킨(테마, 아이콘) 경험에만 집중하여 빠른 검증 가능.
  * *Cons*: 완벽한 오프라인 동작은 미지원 (추후 Phase 2에서 점진적 도입).

우리는 **"안정성이 검증되지 않은 복잡한 캐싱보다, 확실한 앱 설치 경험을 먼저 주는 것이 우선"**이라고 판단하여 대안 B를 채택했습니다. 서비스 워커 파일은 브라우저 등록을 위해 생성하되, 내부 캐싱 로직은 완전히 비워두는 방식을 택했습니다.

### 2.2 어드민 영역의 격리 (Scope Control)
모든 페이지에 PWA를 적용하는 것은 오버엔지니어링이자 보안/운영상 리스크였습니다. 관리자 페이지(Admin)는 데스크톱 환경에서의 정밀한 제어가 주를 이루며, 모바일 홈 화면에 추가될 이유가 전혀 없습니다.

* **결정**: 공통 레이아웃인 `base.html`을 사용하는 일반 사용자 화면(홈, 스캔, 결과, 마이페이지 등)에만 PWA 스크립트와 메타 태그를 주입하고, 어드민 영역의 템플릿에는 일절 포함시키지 않기로 했습니다.

## 3. 구현 및 아키텍처 해결 과제: FastAPI에서의 PWA Scope 문제

PWA를 구현하며 가장 까다로웠던 점은 **서비스 워커의 Scope(통제 범위)** 제약이었습니다. 
서비스 워커는 기본적으로 **자신이 위치한 디렉토리 하위** 페이지만 제어할 수 있습니다. 

PickSafe는 정적 자원을 `/static/` 경로에서 서빙하고 있었기 때문에, 이 구조를 그대로 두면 서비스 워커가 최상위 도메인 전체를 컨트롤하지 못해 앱 설치 프롬프트가 정상 동작하지 않는 문제가 발생했습니다.

### 해결책: 백엔드 루트 라우팅 위임 (FastAPI)
이를 해결하기 위해 프론트엔드 파일 배포 방식을 바꾸는 대신, 백엔드인 **FastAPI 라우터**를 활용해 루트 경로(`/`)에서 매니페스트와 서비스 워커를 서빙하도록 엔드포인트를 강제로 열어주었습니다.

```python
# FastAPI 라우팅 예시 (개념 코드)
@app.get("/manifest.json")
async def get_manifest():
    # PWA 매니페스트 파일 반환 (테마 컬러 #FFF8F0, 아이콘 매핑 등)
    ...

@app.get("/service-worker.js")
async def get_service_worker():
    # 빈 Shell 형태의 서비스 워커 파일 반환 (Phase 1 전략)
    ...
```

이를 통해 서비스 워커가 최상단 도메인(`https://domain.com/`)을 완벽히 스코프에 담을 수 있게 되었고, 브라우저가 PWA로 인식하는 데 성공했습니다.

---

## 4. 검증 및 결과 (Validation)

배포 전, 파편화된 모바일 환경에서의 오작동을 막기 위해 철저한 검증 시나리오를 거쳤습니다.

1. **iOS Safari 검증**: 아이폰에서 '홈 화면에 추가' 시, 설정한 아이파크 파스텔 톤(`#FFF8F0`) 스플래시 화면과 지정한 해상도(`192x192`, `512x512`)의 아이콘이 정상 렌더링되는지 확인.
2. **Android Chrome 검증**: 안드로이드 환경에서 하단 네이티브 앱 설치 프롬프트가 자연스럽게 트리거되는지 확인.
3. **어드민 격리 검증**: 관리자 페이지 접근 시 불필요한 앱 설치 팝업이 뜨지 않으며, 서비스 워커가 등록되지 않음을 콘솔에서 최종 확인.

---

## 5. 엔지니어링 교훈 (Takeaways)

* **"완벽함"보다 "단계적 배포(Phase-based)"의 가치**: 오프라인 캐싱이라는 욕심을 버리고 '설치'라는 단 하나의 목적에 집중함으로써, 복잡한 캐시 릴리즈 이슈 없이 안전하게 PWA를 안착시킬 수 있었습니다.
* **프론트엔드 기술의 백엔드 이해**: PWA의 Scope 제약이라는 프론트엔드 이슈를 FastAPI의 라우팅 구조 조정을 통해 우아하게 해결하며, 시스템 전체를 조망하는 시야의 중요성을 다시 한번 느꼈습니다.

PickSafe의 PWA Phase 1 도입은 단순한 기능 추가를 넘어, 웹과 앱의 경계를 허물고 사용자에게 한 걸음 더 가까이 다가간 의미 있는 아키텍처적 진전이었습니다. 앞으로 Phase 2에서는 안정화된 기반 위에서 점진적인 리소스 캐싱 전략을 얹어갈 예정입니다.
