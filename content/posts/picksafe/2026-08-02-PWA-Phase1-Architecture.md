안녕하세요, PickSafe 백엔드/아키텍처 팀입니다. 

모바일 환경에서의 접근성은 웹 서비스의 성패를 가르는 중요한 요소 중 하나입니다. 이번 포스팅에서는 PickSafe가 사용자 경험(UX)을 극대화하기 위해 **PWA(Progressive Web App)**를 도입한 과정, 그리고 초기 리스크를 최소화하기 위해 수립한 **Phase 1 전략과 트레이드오프(Trade-off)**에 대해 공유하고자 합니다.

---

## 1. Problem: 사용자는 브라우저 켜는 것도 귀찮다

PickSafe는 모바일 환경에서 스캔 및 결과 조회를 위해 접속하는 사용자의 비중이 압도적으로 높습니다. 하지만 기존 웹 서비스 구조에서는 사용자가 서비스를 이용하기 위해 매번 브라우저(Safari, Chrome 등)를 실행하고, 주소창에 URL을 입력하거나 북마크를 찾아 들어가야 하는 마찰(Friction)이 존재했습니다.

> *"네이티브 앱처럼 홈 화면에 아이콘을 두고, 터치 한 번으로 바로 실행할 수 있게 만들 수 없을까?"*

이 문제를 해결하기 위해 웹 표준 기술을 활용해 네이티브 앱과 유사한 사용자 경험을 제공하는 **PWA 도입**을 결정했습니다.

---

## 2. Trade-off & Decision: 모든 것을 한 번에 하려 하지 않기

PWA를 검색해 보면 보통 '오프라인 모드 지원(Offline-first)', '강력한 캐싱 전략(Service Worker Cache)' 등이 세트로 따라옵니다. 하지만 시니어 관점에서 **첫 번째 배포의 핵심 목적**을 명확히 정의할 필요가 있었습니다.

### 2.1 Service Worker 전략: 캐싱은 과감히 보류, '설치'에만 집중 (Phase 1)
* **고민**: 서비스 워커를 도입하면서 네트워크 요청을 가로채 캐싱하는 로직까지 한 번에 구현할 경우, 프론트엔드 리소스가 갱신되지 않는 치명적인 캐시 갱신 장애(Stale Cache Issue)가 발생할 위험이 큽니다.
* **결정**: Phase 1의 최우선 목적은 **"홈 화면에 앱 설치(Add to Home Screen) 지원"**으로 못 박았습니다. 
* 서비스 워커 파일(`service-worker.js`)을 등록하되, 내부 네트워크 캐싱 로직(Fetch / Install 이벤트 핸들러)은 완전히 비워두어 캐싱 관련 리스크를 원천 차단하고 PWA 설치 기능의 안정성부터 검증하기로 했습니다.

### 2.2 적용 범위의 분리: 사용자 영역 vs 어드민 영역
* **고민**: 모든 페이지에 서비스 워커를 등록하는 것이 맞을까?
* **결정**: PWA 설치 프롬프트와 웹앱 속성은 일반 사용자 화면(`base.html`을 사용하는 홈, 스캔, 결과, 마이페이지 등)에만 적용하고, 내부 관리자 페이지(어드민)에는 일체 배제했습니다. 관리자 페이지는 네이티브 앱처럼 홈 화면에 설치할 유인이 낮고, 오히려 내부 관리용 배포 시 캐시 오염 등의 사이드 에피소드를 만들지 않는 것이 이득이기 때문입니다.

### 2.3 백엔드 라우팅 구조 개선 (FastAPI단 대응)
PWA 스펙상 서비스 워커는 기본적으로 자신의 위치한 디렉토리 이하만 통제(Scope)할 수 있는 제약이 있습니다. 

현재 정적 자원들이 `/static/` 경로에서 서빙되고 있기 때문에, 최상위 도메인 전체를 서비스 워커가 제어할 수 있도록 **FastAPI 라우터 레벨에서 루트 경로 매핑**을 처리했습니다.

```python
# FastAPI 라우팅 예시 (개념 코드)
@app.get("/manifest.json")
async def serve_manifest():
    # 매니페스트 파일 반환
    pass

@app.get("/service-worker.js")
async def serve_service_worker():
    # 서비스 워커 파일 반환 (Scope 확장을 위해 루트에서 서빙)
    pass
```

이를 통해 서비스 워커가 앱의 루트(`/`) 권한을 획득하여 정상적으로 PWA 라이프사이클을 관리할 수 있도록 설계했습니다.

## 3. Validation: 꼼꼼한 검증 플랜

배포 전, 아래 시나리오를 바탕으로 디바이스별 검증을 완료했습니다.

1. **iOS Safari 검증**: 아이폰 Safari에서 '홈 화면에 추가' 진행 시, 지정한 아이보리 파스텔 톤(`#FFF8F0`)의 테마 컬러와 아이콘(192x192, 512x512)이 스플래시 화면과 홈 화면에 정상 노출되는지 확인.
2. **어드민 격리 검증**: 관리자 페이지 진입 시, 서비스 워커가 등록되지 않으며 앱 설치 프롬프트가 트리거되지 않는지 확인.
3. **Android Chrome 검증**: 안드로이드 환경에서 접속 시, 하단에 자연스러운 '앱 설치' 팝업(BeforeInstallPromptEvent)이 노출되는지 확인.

---

## 4. Takeaway: 점진적 엔지니어링의 미학

이번 PWA Phase 1 도입을 통해 얻은 가장 큰 교훈은 **"욕심을 버리면 안정성이 보인다"**는 점입니다. 

처음부터 오프라인 캐싱, 백그라운드 싱크 등 PWA의 모든 기능을 구현하려 했다면 캐시 버스팅(Cache Busting) 문제나 브라우저 호환성 디버깅으로 인해 배포 일정이 크게 지연되었을 것입니다. 

하지만 **"이번 단계의 목적은 오직 홈 화면 설치"**라는 명확한 가이드라인을 세우고, 아키텍처를 단순화한 덕분에 리스크 없이 빠르게 프로덕션 환경에 PWA 기반을 다질 수 있었습니다. 

앞으로 PickSafe는 Phase 1의 안정성 데이터를 바탕으로, 제한적인 오프라인 캐싱 전략(Phase 2)을 점진적으로 도입해 나갈 예정입니다.
