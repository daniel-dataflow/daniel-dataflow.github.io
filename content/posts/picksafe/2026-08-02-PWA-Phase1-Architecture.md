안녕하세요, PickSafe 백엔드/인프라스트럭처 엔지니어입니다. 

모바일 환경에서의 접근성은 서비스의 성패를 가르는 중요한 지표 중 하나입니다. PickSafe 역시 모바일 웹 접속 비율이 압도적으로 높지만, 사용자가 브라우저를 켤 때마다 URL을 입력하거나 북마크를 찾아야 하는 UX 마찰(Friction)이 존재했습니다. 

이를 해결하기 위해 **PWA(Progressive Web App)** 도입을 결정했습니다. 이번 포스팅에서는 네이티브 앱 같은 사용자 경험을 제공하기 위해 어떤 기술적 고민을 거쳤고, 특히 **초기 도입 단계(Phase 1)에서 왜 복잡한 캐싱 전략을 과감히 포기했는지**에 대한 아키텍처 의사결정 과정(ADR)을 공유합니다.

---

## 1. 문제 정의 (Problem Definition)

PickSafe는 사용자가 빠르게 진입하여 기능을 활용해야 하는 모바일 중심의 유틸리티 성격이 강합니다. 하지만 모바일 웹의 특성상 브라우저 UI(주소창, 탭 버튼 등)가 화면의 일정 부분을 차지하고, 재방문 시 주소를 직접 입력해야 하는 번거로움이 있었습니다.

단기간에 네이티브 앱을 개발·배포(App Store / Google Play 심사 등)하는 것은 오버헤드가 컸기에, **웹 기술을 활용하되 홈 화면에 아이콘을 두고 앱처럼 실행할 수 있는 PWA를 도입**하기로 했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Decisions)

PWA를 도입하면서 마주한 기술적 과제는 크게 세 가지였습니다. 

### ① 서비스 워커(Service Worker) 전략: "오프라인 캐싱 vs 설치 기능 확보"
* **고민**: PWA를 검색하면 흔히 등장하는 것이 강력한 리소스 캐싱을 통한 '오프라인 지원'입니다. 하지만 백엔드 API와 프론트엔드 정적 자원이 빈번하게 업데이트되는 초기 서비스에서 무리하게 캐싱 전략을 도입했다가 **"배포 후에도 사용자의 브라우저에 구버전 리소스가 남아버리는 캐시 갱신 장애"**가 발생할 위험이 컸습니다.
* **결정 (Phase 1 전략)**: 1차 배포의 최우선 목적은 오프라인 동작이 아닌 **"홈 화면에 앱 설치(Add to Home Screen) 지원"**입니다. 따라서 서비스 워커 파일은 등록하되 내부의 `Fetch / Install` 이벤트 가로채기 로직은 완전히 비워두었습니다. 
* **효과**: 캐싱 관련 사이드이펙트를 원천 차단하면서, PWA의 핵심인 '홈 화면 설치'와 '테마 컬러/스플래시 화면' 연동이 안정적으로 작동하는지 먼저 검증할 수 있었습니다.

### ② 적용 범위(Scope): 사용자 영역과 어드민(Admin)의 분리
* **고민**: 모든 페이지에 서비스 워커를 등록하는 것이 기술적으로는 간단하지만, 시스템 관리용 어드민 페이지에까지 PWA 프롬프트가 뜨거나 불필요한 캐싱 레이어가 얹어지는 것은 보안 및 관리 측면에서 바람직하지 않습니다.
* **결정**: 공통 템플릿 구조를 활용해 일반 사용자 화면(홈, 스캔, 결과, 마이페이지 등)을 서빙하는 `base.html`에만 PWA 메타 태그와 스크립트를 포함하고, 어드민 영역은 서비스 워커 및 설치 프롬프트 대상에서 완전히 배제했습니다.

### ③ 백엔드 라우팅(FastAPI Scope Issue)
* **고민**: PWA의 서비스 워커는 기본적으로 자신의 위치한 디렉토리 이하만 통제(Scope)할 수 있는 보안 정책을 가집니다. 프로젝트 구조상 정적 자원이 `/static/` 경로 하위에 서빙되고 있어, 루트 도메인 전체를 컨트롤하기에는 제약이 있었습니다.
* **결정**: FastAPI 서버(`main.py`)단에서 별도의 엔드포인트(`@app.get("/manifest.json")` 및 `/service-worker.js`)를 명시적으로 구성하여, 루트 경로(`/`) 요청 시에도 정적 자원이 정상적으로 매핑되도록 라우팅 아키텍처를 조정했습니다.

```python
# FastAPI 라우팅 예시 (개념 코드)
@app.get("/manifest.json")
async def get_manifest():
    return FileResponse("static/manifest.json")

@app.get("/service-worker.js")
async def get_service_worker():
    return FileResponse("static/service-worker.js", media_type="application/javascript")
```

## 3. 검증 및 테스트 (Validation)

아키텍처 변경 후, 주요 모바일 환경에서 의도대로 동작하는지 철저한 검증을 거쳤습니다.

1. **iOS Safari 검증**: 아이폰 사파리에서 '홈 화면에 추가' 진행 시, 지정한 아이보리 파스텔 톤(`#FFF8F0`)의 스플래시 화면과 고해상도 아이콘(192x192, 512x512)이 정상 렌더링되는지 확인.
2. **Android Chrome 검증**: 안드로이드 환경에서 접속 시 하단에 자연스러운 '앱 설치' 프롬프트가 트리거되는지 확인.
3. **어드민 격리 검증**: 관리자 페이지 진입 시 서비스 워커가 등록되지 않으며, 설치 유도 팝업이 일체 노출되지 않는지 보안 및 UX 측면 검증 완료.

## 4. 엔지니어링 교훈 (Takeaways)

> **"모든 기능을 한 번에 구현하려 하지 말고, 프로덕션 안정성을 최우선으로 한 단계씩(Phase) 쪼개어 배포하라."**

이번 PWA Phase 1 도입을 통해 얻은 가장 큰 교훈입니다. 개발자로서 화려한 기술(오프라인 퍼스트 캐싱, 백그라운드 싱크 등)을 한 번에 적용하고 싶은 유혹이 있었지만, 서비스의 현재 단계에서 가장 필요한 가치(홈 화면 진입성)에 집중하고 복잡성을 과감히 덜어냈습니다. 

그 결과, 장애 없는 매끄러운 배포를 완료할 수 있었습니다. 앞으로 사용자 피드백을 바탕으로 Phase 2 캐싱 전략을 점진적으로 고도화해 나갈 예정입니다.

PickSafe의 더 나은 사용자 경험을 위한 기술적 여정은 계속됩니다. 읽어주셔서 감사합니다.
