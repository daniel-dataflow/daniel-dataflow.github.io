안녕하세요, PickSafe 백엔드 및 웹 엔지니어링을 담당하고 있는 시니어 에디터입니다. 

모바일 환경에서의 사용자 경험(UX)은 서비스의 성패를 가르는 핵심 요소입니다. 이번 포스팅에서는 PickSafe가 모바일 웹의 한계를 극복하고 네이티브 앱과 같은 사용성을 제공하기 위해 **PWA(Progressive Web App) Phase 1을 어떻게 설계하고 도입했는지**, 그 기술적 의사결정 과정(ADR)을 공유해 드립니다.

---

## 1. Problem: 모바일 웹의 태생적 한계와 사용자 이탈

PickSafe는 모바일 환경에서 접속하는 사용자의 비율이 압도적으로 높습니다. 하지만 기존 모바일 웹 환경에는 명확한 UX적 페인 포인트가 존재했습니다.
* 사용자가 서비스를 이용하려면 매번 브라우저(Safari, Chrome 등)를 켜고 URL을 입력하거나 북마크를 찾아야 했습니다.
* 네이티브 앱 대비 접근성이 떨어지며, 재방문율을 높이는 데 걸림돌이 되었습니다.

이 문제를 해결하기 위해 **"사용자가 스마트폰 홈 화면에 PickSafe 아이콘을 추가하고, 네이티브 앱처럼 원터치로 진입하게 만들자"**는 목표를 세웠습니다. 이를 위한 가장 가볍고 표준적인 방법이 바로 PWA 도입이었습니다.

---

## 2. Trade-off & Decision: 오프라인 캐싱의 과감한 포기와 '단계적 도입(Phase 1)'

PWA를 검색해 보면 대부분 대규모 오프라인 캐싱 전략(Service Worker를 이용한 Cache First, Network First 등)부터 다룹니다. 하지만 우리는 **Phase 1에서 오프라인 캐싱 로직을 완전히 배제**하는 과감한 트레이드오프를 선택했습니다.

### ① 왜 캐싱 로직을 보류했을까? (Risk Management)
* **장애 예방**: 초기 단계부터 공격적인 캐싱 정책을 도입하면, 배포 후 리소스가 갱신되지 않아 사용자가 구버전 UI를 보게 되는 치명적인 캐시 정합성 이슈가 발생할 수 있습니다.
* **목표의 집중**: 1차 목표는 오프라인 동작이 아닌 **"홈 화면에 앱 설치(Add to Home Screen) 유도"**입니다. 복잡한 캐싱은 변수를 늘릴 뿐이므로, 설치 기능의 안정성 확보를 최우선으로 두었습니다.

### ② 서비스 워커(Service Worker) 전략
* 서비스 워커 파일자체는 등록하되, 내부의 `fetch` 및 `install` 이벤트 가로채기 로직은 비워두어 네트워크 요청에 개입하지 않도록 했습니다. 
* 이를 통해 캐시 오염으로 인한 리스크를 원천 차단하면서도, 브라우저가 PWA로 인식하여 홈 화면에 설치 프롬프트를 띄우는 조건은 완벽히 충족시켰습니다.

### ③ 적용 범위(Scope)의 명확한 분리
* **사용자 화면 전용**: 일반 사용자 대상 페이지(`base.html`을 공유하는 홈, 스캔, 결과, 마이페이지 등)에만 PWA 속성과 스크립트를 적용했습니다.
* **어드민 영역 배제**: 운영 및 관리를 위한 어드민 페이지에는 서비스 워커와 설치 프롬프트를 완전히 배제하여, 불필요한 캐싱이나 오작동 가능성을 차단했습니다.

## 3. Engineering: FastAPI 환경에서의 PWA 스코프(Scope) 이슈 해결

PWA 서비스 워커는 보안상의 이유로 **자신이 위치한 디렉토리 이하의 경로만 통제(Scope)**할 수 있는 특성이 있습니다. 

PickSafe는 정적 자원을 `/static/` 경로 하위에서 서빙하고 있었기 때문에, 자칫하면 서비스 워커의 제어 범위가 제한되어 최상단 도메인 전체를 아우르는 PWA 기능을 수행하기 어려워질 수 있었습니다.

이를 해결하기 위해 백엔드 프레임워크인 **FastAPI의 라우팅 기능을 활용**했습니다.

```python
# 개념적 구현 예시 (FastAPI)
@app.get("/manifest.json")
async def get_manifest():
    # 웹앱 매니페스트 반환 (테마 컬러 #FFF8F0, 아이콘 규격 192x192, 512x512 등 설정)
    ...

@app.get("/service-worker.js")
async def get_service_worker():
    # 루트 경로에서 서비스 워커 스크립트 서빙
    ...
```

정적 파일 디렉토리에 종속시키지 않고, FastAPI의 엔드포인트를 직접 열어 최상위 루트(` /manifest.json`, `/service-worker.js`)에서 리소스를 서빙하도록 구조를 변경했습니다. 덕분에 서비스 워커가 도메인 전체를 안정적으로 스코프할 수 있게 되었습니다.

---

## 4. Takeaway: 엔지니어링 교훈

1. **"완벽함"보다 "목표 집중"이 우선이다**: PWA의 모든 기능을 한 번에 구현하려 하기보다, Phase 1에서는 '앱 설치'라는 핵심 가치에만 집중하여 복잡도를 낮추고 안정성을 챙겼습니다.
2. **백엔드 라우팅을 통한 프론트엔드 제약 극복**: PWA 스코프 문제처럼 프론트엔드 표준 기술이 가진 물리적 한계를 백엔드(FastAPI) 라우팅을 통해 우아하게 해결할 수 있음을 확인했습니다.

PickSafe는 이번 PWA Phase 1 도입을 통해 모바일 웹 사용자들에게 한 걸음 더 네이티브 앱에 가까운 경험을 제공할 수 있게 되었습니다. 앞으로도 사용자 경험과 시스템 안정성의 균형을 찾는 기술적 여정을 공유해 드리겠습니다. 감사합니다.
