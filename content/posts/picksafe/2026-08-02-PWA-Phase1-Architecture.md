안녕하세요, PickSafe 백엔드 및 웹 엔지니어링을 담당하고 있는 시니어 개발자입니다. 

모바일 환경에서의 접근성이 비즈니스의 성패를 가르는 핵심 지표가 되면서, 우리 팀은 최근 **PWA(Progressive Web App)** 도입을 결정했습니다. 사용자가 브라우저를 켤 때마다 URL을 입력하거나 북마크를 찾아야 하는 마찰(Friction)을 줄이고, 네이티브 앱처럼 홈 화면에서 원터치로 진입할 수 있는 경험을 제공하기 위함입니다.

이번 포스팅에서는 PWA를 도입하는 과정에서 마주한 기술적 고민, 오프라인 캐싱 대신 '설치 경험'에 집중한 Trade-off, 그리고 FastAPI 환경에서 서비스 워커 Scope 문제를 해결한 아키텍처 의사결정 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): 모바일 웹의 한계와 진입 장벽

PickSafe는 모바일 환경에서 실시간으로 스캔하고 결과를 확인하는 유저들이 많습니다. 하지만 기존 모바일 웹 구조에서는 다음과 같은 사용자 경험(UX)적 한계가 존재했습니다.
* 매번 브라우저 앱 실행 -> 북마크 또는 URL 입력이라는 반복적인 진입 단계
* 브라우저 상단 주소창 등으로 인해 몰입도가 떨어지는 화면 영역
* 네이티브 앱과 유사한 아이콘 및 스플래시 화면 부재로 인한 브랜드 신뢰도 저하

이를 해결하기 위해 PWA 표준 스펙을 도입하기로 했으나, 막상 구현에 착수하자 **"서비스 워커를 어디까지, 어떻게 붙여야 하는가?"**에 대한 기술적 딜레마에 부딪혔습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 2.1 서비스 워커(Service Worker) 전략: "오프라인 캐싱 vs 설치(A2HS)"
대다수의 개발자들이 PWA를 도입할 때 가장 먼저 욕심을 내는 부분이 바로 **오프라인 캐싱(Offline Caching)**입니다. 네트워크가 끊긴 상태에서도 앱이 동작하도록 Fetch 이벤트를 가로채 정적/동적 리소스를 Cache Storage에 적재하는 방식입니다.

그러나 우리는 1차 페이즈(Phase 1)에서 **오프라인 캐싱 로직을 과감히 배포 범위에서 제외**하기로 결정했습니다.

* **대안 A (All-in-one: 설치 + 공격적 캐싱)**: 
  * *장점*: 완벽한 PWA 경험 제공.
  * *단점*: 초기 배포 시 캐싱 전략(Stale-While-Revalidate 등) 설계 오류나 정적 자원 버전 관리 미숙으로 인해, 유저 브라우저에 구버전 UI가 고착화되는 치명적인 장애(Cache Poisoning) 위험 급증.
* **대안 B (Phase 1: 설치 우선 전략 - 선택)**:
  * *장점*: 서비스 워커와 매니페스트를 등록하되, 캐싱 로직을 비워둠으로써 **"홈 화면에 앱 설치(Add to Home Screen)"** 기능만 안정적으로 검증. 캐시 갱신 실패로 인한 프론트엔드 장애 리스크 원천 차단.
  * *단점*: 완전한 오프라인 환경 지원은 다음 페이즈로 연기됨.

> **Eng. Decision**: 비즈니스 관점에서 현재 가장 시급한 것은 "유저가 홈 화면에 PickSafe 아이콘을 두고 빠르게 진입하는 것"이었습니다. 복잡한 캐싱 레이어를 한 번에 올리기보다, **설치 기능의 안정성을 먼저 확보하는 것**이 엔지니어링 리스크를 줄이는 합리적인 선택이었습니다.

### 2.2 어드민 영역의 철저한 분리 (Scope Control)
모든 페이지에 PWA 스크립트와 서비스 워커를 일괄 주입하는 것은 쉬운 방법입니다. 하지만 관리자 페이지(어드민)는 보안과 실시간성(항상 최신 서버 상태 반영)이 최우선입니다. 어드민 페이지에 서비스 워커나 앱 설치 프롬프트가 노출되는 것은 불필요할 뿐더러 잠재적인 보안 홀이나 캐시 오염을 유발할 수 있습니다.
* **결과**: 공통 레이아웃인 `base.html`을 사용하는 일반 사용자 화면(홈, 스캔, 결과, 마이페이지 등)에만 PWA 관련 메타 태그와 스크립트를 포함하고, 어드민 템플릿 영역은 완전히 배제했습니다.

### 2.3 FastAPI 환경에서의 백엔드 라우팅 (Scope Issue 해결)
PWA 서비스 워커의 스펙상, **서비스 워커 파일이 위치한 디렉토리 이하의 경로만 통제(Scope)**할 수 있다는 제약이 있습니다. 정적 자원을 전통적으로 `/static/` 경로에서 서빙하고 있었기 때문에, 루트 도메인 전체(`https://domain.com/`)를 서비스 워커의 통제하에 두려면 라우팅 구조에 대한 고민이 필요했습니다.

* **해결책**: FastAPI 백엔드 서버(`main.py`)에 별도의 엔드포인트를 명시적으로 선언하여, 루트 경로로 들어오는 요청을 서빙하도록 처리했습니다.
  ```python
  @app.get("/manifest.json")
  async def serve_manifest():
      # 매니페스트 파일 반환 로직
      pass

  @app.get("/service-worker.js")
  async def serve_service_worker():
      # 서비스 워커 파일 반환 로직 (MIME 타입 주의)
      pass
  ```
* 이를 통해 정적 파일 디렉토리 구조의 한계를 우회하고, 루트 도메인 전반에 걸쳐 완벽한 PWA 스코프를 확보할 수 있었습니다.

## 3. 검증 및 테스팅 (Validation)

안정적인 배포를 위해 다음과 같은 세 가지 시나리오를 엄격히 검증했습니다.

1. **iOS Safari 검증**: 아이폰 사파리에서 '홈 화면에 추가' 시, 정의된 아이콘과 파스텔 톤(`#FFF8F0`)의 스플래시 테마가 네이티브 앱처럼 매끄럽게 연동되는지 확인.
2. **어드민 영역 격리 확인**: 관리자 전용 경로(예: `/admin/...`) 접근 시, 서비스 워커가 등록되지 않고 설치 프롬프트가 트리거되지 않음을 보장.
3. **Android Chrome 검증**: 안드로이드 크롬 환경에서 하단 네이티브 설치 배너(A2HS Prompt)가 정상 노출되는지 확인.

## 4. Takeaway (엔지니어링 교훈)

> **"욕심을 버리고 페이즈를 쪼개는 것이 가장 빠른 배포다."**

새로운 기술(PWA)을 도입할 때, 해당 기술이 가진 모든 기능을 한 번에 구현하려고 하면 복잡도만 높아지고 장애 위험성만 가중됩니다. 
이번 PickSafe PWA Phase 1 프로젝트는 **"우리가 이번에 해결하고자 하는 핵심 문제가 무엇인가?"**에만 집중하여 캐싱을 과감히 들어내고 '설치 기능' 자체의 안정성을 빠르게 확보했습니다. 

견고한 기반(Foundation)이 다져졌으니, 이제 안심하고 다음 페이즈에서 오프라인 캐싱과 백그라운드 동기화 전략을 고도화해 나갈 수 있게 되었습니다. 

읽어주셔서 감사합니다. 서비스 아키텍처나 구현 방식에 대해 궁금한 점이 있으시다면 언제든 피드백 남겨주세요!
