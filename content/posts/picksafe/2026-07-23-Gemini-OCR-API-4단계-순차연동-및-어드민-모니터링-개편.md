화장품 성분 분석 서비스 'PickSafe'에서 성분표 OCR(광학 문자 인식) 기능은 사용자 경험의 핵심입니다. 하지만 외부 LLM 기반 Vision API나 전문 OCR 엔진에 의존하는 서비스 파이프라인은 언제나 **"Rate Limit(HTTP 429)", "호출 비용", "API 응답 지연"**이라는 삼중고에 직면하게 됩니다.

이번 포스팅에서는 PickSafe 팀이 어떻게 **4단계 순차 연동(Fallback Chain)** 구조를 도입하여 API 가용성을 극대화하고, **`asyncio.gather` 기반의 비동기 병렬 벤치마킹 시스템**을 통해 성능과 비용의 최적 밸런스를 찾았는지 공유하고자 합니다.

---

## 1. 문제 정의: "무료 쿼터의 한계와 단일 API 의존의 위험성"

성분표 이미지를 텍스트로 변환하고 분석할 때, 고성능 Vision LLM 모델은 높은 정확도를 제공합니다. 그러나 서비스 운영 과정에서 다음과 같은 문제에 직면했습니다.

1. **429 Too Many Requests (Rate Limit Issue)**  
   무료/저비용 티어 API는 분당 요청 수(RPM)와 일일 요청 수(RPD) 제한이 빡빡합니다. 서비스 이용자가 갑자기 몰릴 경우 단일 모델에 의존하는 파이프라인은 즉시 에러를 반환하며 사용자 경험을 훼손합니다.
2. **비용 대 효율의 트레이드오프**  
   모든 요청을 최상위 고성능 모델로 처리하는 것은 예산상 불가능합니다. 쿼터 한도가 넉넉한 Lite 모델을 주력으로 쓰되, 필요할 때 상위 모델로 유연하게 넘어가야 하는 구조가 필요했습니다.
3. **LLM 모델별 성능 가시성 부재**  
   각 모델(Lite vs Flash)과 상용 OCR 엔진(예: Naver Clova) 간의 실시간 추출 정확도 및 지연시간(Latency)을 객관적으로 비교할 수 있는 인프라가 부족했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 시스템 아키텍처 관점에서 세 가지 대안을 검토했습니다.

| 구분 | 대안 A: 단일 상용 API + 재시도(Retry) | 대안 B: 유료 플랜 전면 도입 | 대안 C: 4단계 Fallback Chain + 실시간 모니터링 (선택) |
| :--- | :--- | :--- | :--- |
| **비용** | 낮음 | 매우 높음 | **최적화 (무료 쿼터 최대 활용)** |
| **가용성** | 낮음 (Quota 초과 시 서비스 중단) | 높음 | **매우 높음 (단계별 자동 전환)** |
| **복잡도** | 매우 낮음 | 낮음 | 중간 (쿼터 추적 및 폴백 로직 필요) |
| **결론** | **기계적 재시도는 429 해결 불가** | **초기 스타트업 예산 한계** | **최적의 시스템 회복탄력성(Resilience) 확보** |

저희는 시스템의 복잡도를 소폭 늘리더라도 **"비용 효율성"**과 **"고가용성"**을 동시에 챙길 수 있는 **대안 C(Fallback Chain + 병렬 모니터링)**를 선택했습니다.

---

## 3. 최종 해결책: 아키텍처 개편

### (1) 4단계 순차 연동 (Fallback Chain) 설계

요청이 들어왔을 때 쿼터가 넉넉한 Lite 모델을 우선적으로 소모하고, 장애 발생이나 쿼터 소진 시 하위 모델로 자동 릴레이 호출되는 'Graceful Degradation' 전략을 채택했습니다.

```
[사용자 OCR 스캔 요청]
       │
       ▼
┌───────────────────────────────┐
│ 1순위: Gemini 3.1 Flash-Lite  │ ── (성공) ──> [결과 반환]
└──────────────┬────────────────┘
               │ (429 Rate Limit / Fail)
               ▼
┌───────────────────────────────┐
│ 2순위: Gemini 3.5 Flash-Lite  │ ── (성공) ──> [결과 반환]
└──────────────┬────────────────┘
               │ (429 Rate Limit / Fail)
               ▼
┌───────────────────────────────┐
│ 3순위: Gemini 3.5 Flash       │ ── (성공) ──> [결과 반환]
└──────────────┬────────────────┘
               │ (429 Rate Limit / Fail)
               ▼
┌───────────────────────────────┐
│ 4순위: Gemini 3.6 Flash       │ ── (성공) ──> [결과 반환]
└───────────────────────────────┘
```

- **1~2순위 (Lite 모델군)**: 일일 쿼터(RPD 500)가 넉넉하므로 대부분의 일반 요청을 처리합니다.
- **3~4순위 (Flash 모델군)**: 쿼터(RPD 20)는 적지만 높은 성능을 보장하므로, Lite 모델 쿼터가 만료되었을 때의 보루(Safety Net) 역할을 수행합니다.

### (2) `asyncio.gather` 기반 비동기 병렬 벤치마킹 Engine

어드민 영역에서는 어떤 OCR 엔진이 현재 서비스에 가장 적합한지 정밀 측정하기 위해 **총 5개 엔진(Gemini 4종 + Naver Clova OCR)**을 동기 블로킹 없이 동시 대조할 수 있는 시스템을 구축했습니다.

Python의 `asyncio` 라이브러리를 활용하여, 5개 외부 API에 대한 Network I/O 요청을 병렬로 처리함으로써 전체 벤치마킹 테스트 소요 시간을 **단일 최고 지연시간(Max Latency) 수준**으로 단축시켰습니다.

```python
# 개념적 비동기 병렬 처리 구조 (보안을 위해 래핑된 코드)
async def run_ocr_benchmark(image_payload: bytes):
    tasks = [
        call_gemini_engine("3.1-flash-lite", image_payload),
        call_gemini_engine("3.5-flash-lite", image_payload),
        call_gemini_engine("3.5-flash", image_payload),
        call_gemini_engine("3.6-flash", image_payload),
        call_clova_ocr_engine(image_payload),
    ]
    
    # 5개 API를 동시 병렬 요청하여 Non-blocking으로 응답 수집
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return process_benchmark_metrics(results)
```

### (3) 실시간 관측 가능성(Observability) 및 쿼터 추적 Dashboard

백엔드 내에 각 모델별 **[남은 쿼터, 실시간 RPM, 평균 지연시간(Latency)]**을 상태값으로 관리하는 쿼터 카운터 메커니즘을 구현했습니다. 이를 어드민 모니터링 시스템과 실시간 바인딩하여, 엔지니어가 인프라 상태를 한눈에 파악하고 이상 징후를 조기에 감지할 수 있도록 개선했습니다.

## 4. 성과 및 엔지니어링 교훈 (Takeaways)

### 📈 도입 성과
1. **서비스 가용성 99.9% 달성**: 특정 모델의 429 Rate Limit 발생 시에도 사용자 단에서의 스캔 실패율을 0%에 가깝게 방어했습니다.
2. **운영 비용 절감**: Lite 모델의 무료 쿼터를 우선 소모하도록 제어하여 외부 API 호출 비용을 획기적으로 절약했습니다.
3. **데이터 기반 의사결정**: 어드민 병렬 벤치마킹을 통해 모델별 정확도 대비 Latency 데이터를 확보, 파이프라인의 순서를 과학적으로 검증할 수 있게 되었습니다.

### 💡 Engineering Takeaway

> **"외부 API는 언제든 실패할 수 있다. 중요한 것은 '어떻게 우아하게 대처(Graceful Fallback)할 것인가'이다."**

LLM과 외부 API를 프로덕션 환경에 도입할 때, 단일 Vender/Model에 시스템 생명선을 내어주는 것은 매우 위험합니다. 

이번 작업을 통해 **회복탄력성(Resilience) 있는 다중 연동 설계**의 중요성을 재확인하였으며, 비동기 파이프라인과 관측 가능성(Observability)이 결합될 때 최상의 시스템 안정성을 확보할 수 있음을 배웠습니다. PickSafe 팀은 앞으로도 예측 불가능한 외부 환경 속에서 흔들리지 않는 견고한 백엔드 아키텍처를 만들어 나갈 것입니다.
