안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스를 운영하면서 가장 마주하기 싫은 에러 중 하나는 바로 외부 API의 **`429 Too Many Requests` (Rate Limit Exceeded)**입니다. 특히 초기 스타트업이나 개인 프로젝트 단계에서 LLM 및 Vision API의 무료 티어(Free Tier)를 활용할 때, 단일 모델 의존성은 서비스 전체의 장애로 직결되는 치명적인 병목이 됩니다.

이번 포스팅에서는 화장품 성분표 OCR 인식 파이프라인의 가용성을 극대화하기 위해 **Gemini OCR API 4단계 순차 연동(Fallback Chain)**과 **어드민 실시간 벤치마크 시스템**을 구축하며 고민했던 아키텍처적 의사결정과 교훈을 공유합니다.

---

## 1. Problem: 단일 모델 OCR 의존성의 함정과 Rate Limit

PickSafe는 화장품 성분표 이미지를 분석하기 위해 고성능 비전 AI 모델을 활용하고 있습니다. 초기에는 특정 Gemini 모델 하나를 주력으로 연동하여 사용했으나, 서비스 사용량이 늘어남에 따라 다음과 같은 한계에 부딪혔습니다.

1. **엄격한 Rate Limit (RPM / RPD 한계)**: 무료 티어의 특성상 분당 요청 수(RPM)와 일일 요청 수(RPD)가 제한되어 있어, 트래픽이 몰릴 때 어김없이 `429 에러`가 발생하며 유저 스캔 요청이 실패했습니다.
2. **비효율적인 쿼터 분배**: 쿼터가 넉넉한 모델과 성능은 뛰어나지만 쿼터가 매우 적은(예: 일일 20회) 모델이 혼재되어 있었으나, 이를 지능적으로 분배하지 못하고 무작위로 소모하고 있었습니다.
3. **정량적 비교의 부재**: 여러 모델과 서드파티 OCR(Naver Clova 등) 간의 실제 Latency와 정확도를 직관적으로 비교할 수 없어, 어떤 모델이 프로덕션 환경에 가장 적합한지 데이터 기반으로 판단하기 어려웠습니다.

---

## 2. Trade-off & Architecture: 어떻게 해결할 것인가?

이 문제를 해결하기 위해 두 가지 핵심 아키텍처를 설계하고 도입했습니다.

### ① Gemini OCR API 4단계 순차 연동 (Fallback Chain)
단일 실패 지점(Single Point of Failure)을 없애고 무료 쿼터의 효율을 극대화하기 위해, 4개의 Gemini 모델을 우선순위에 따라 체인 형태로 묶었습니다.

* **1순위 (주력)**: `Gemini 3.1 Flash-Lite` (일일 500회 / 15 RPM)
* **2순위**: `Gemini 3.5 Flash-Lite` (일일 500회 / 15 RPM)
* **3순위**: `Gemini 3.5 Flash` (일일 20회 / 5 RPM)
* **4순위**: `Gemini 3.6 Flash` (일일 20회 / 5 RPM)

**[의사결정 포인트 및 Trade-off]**
* **장점**: 쿼터가 넉넉한 Flash-Lite 모델들을 우선 소모(`500회 + 500회`)하여 대부분의 트래픽을 방어하고, 일시적인 부하로 한계에 도달하면 상위 Flash 모델로 자연스럽게 폴백(Fallback)되어 서비스 연속성을 보장합니다.
* **단점 및 고려사항**: 순차 호출로 인해 최악의 경우(1~3순위 모두 실패 후 4순위 도달) 총 지연 시간(Latency)이 길어질 수 있습니다. 이를 방어하기 위해 각 단계별 타임아웃 설정을 엄격하게 가져가고, 어드민을 통해 실시간 Latency를 모니터링하도록 보완했습니다.

### ② `asyncio.gather` 기반의 비동기 병렬 벤치마크 파이프라인
모델별 성능을 실시간으로 비교하기 위해, 어드민 대시보드에서 4개의 Gemini 모델과 Naver Clova OCR을 포함한 **총 5개 엔진**을 동시에 테스트할 수 있는 기능을 구현했습니다.

* 블로킹 I/O로 순차 요청을 보내면 전체 테스트 시간이 수 초 이상 소요되는 문제를 해결하기 위해, Python의 `asyncio.gather`를 도입했습니다.
* 외부 API 호출을 논블로킹(Non-blocking)으로 동시에 병렬 처리함으로써, 5개 엔진의 결과를 단 몇 백 밀리초 만에 수집하여 대조할 수 있게 되었습니다.

## 3. Takeaway: 엔지니어링 교훈

1. **Resilience(회복탄력성)는 아키텍처 설계의 기본이다**: 
   외부 API를 사용하는 시스템에서 서드파티의 장애나 쿼터 제한은 '언젠가 일어날 일'입니다. Fallback Chain 패턴을 도입함으로써 비즈니스 로직의 중단 없이 안정적인 서비스를 제공할 수 있음을 체감했습니다.
2. **데이터 기반의 가시성 확보 (Observability)**: 
   단순히 코드를 구현하는 것에서 끝나지 않고, 어드민 모니터링을 통해 각 모델별 RPM, 남은 쿼터, Latency를 실시간으로 추적할 수 있어야 시스템을 지속 가능하게 개선할 수 있습니다.
3. **비동기 프로그래밍의 실무적 가치**: 
   `asyncio`를 활용한 병렬 벤치마크 처리는 어드민 사용자의 답답함을 해소했을 뿐만 아니라, 향후 대규모 멀티 모델 앙상블 구조로 확장할 수 있는 기반 기술이 되었습니다.
