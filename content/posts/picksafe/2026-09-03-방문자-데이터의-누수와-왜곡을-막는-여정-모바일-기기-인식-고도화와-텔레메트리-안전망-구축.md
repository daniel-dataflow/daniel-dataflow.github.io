화장품 성분 분석 서비스인 **PickSafe**를 개발하고 운영하면서, 사용자 행동을 정확히 이해하는 것은 서비스 개선의 나침반과 같습니다. 이를 위해 자체적인 방문자 텔레메트리(Telemetry) 시스템을 구축하여 운영해 왔습니다. 

하지만 최근 관리자 대시보드의 방문자 통계 데이터에서 심각한 데이터 왜곡과 누락 현상이 발견되었습니다. 모바일 접속 비중이 절대적으로 높은 서비스임에도 불구하고, 많은 이벤트가 `Unknown` 기기로 분류되거나 아예 기록조차 되지 않는 문제가 발생한 것입니다. 

이 글에서는 모바일 환경의 특수성으로 인해 발생했던 텔레메트리 누수 문제를 진단하고, 이를 해결하기 위해 아키텍처와 로직을 고도화한 과정을 담담히 기록해 보고자 합니다.

## 🎯 마주한 고민과 문제 배경

기존 시스템에서 발견된 문제는 크게 두 가지 영역으로 나뉘었습니다. **기기 식별의 한계**와 **과도한 차단 정책으로 인한 세션 유실**이었습니다.

### 1. 기기 환경 `Unknown / Other` 대량 발생
* **컨텍스트 유실**: `onboarding_completed`, `onboarding_skipped` 등 유저의 핵심 전환 이벤트가 발생할 때, API 라우터 단에서 `request` 객체로부터 클라이언트 컨텍스트(User-Agent, IP 등)를 온전히 추출하지 못하고 `None`으로 적재하는 설계 결함이 있었습니다.
* **인앱 브라우저 식별 실패**: 국내 모바일 유저의 상당수는 카카오톡, 네이버, 인스타그램 등의 인앱 브라우저(WebView)를 통해 유입됩니다. 기존의 단순한 User-Agent(UA) 파서로는 이러한 하이브리드 환경 및 최신 크롬 모바일의 축소형(Reduced) UA를 제대로 파싱하지 못해 전부 `Unknown`으로 분류해 버렸습니다.

### 2. 외부 모바일 접속 시 기록 누락
* **동일 IP 다중 기기 오판정**: 기존 텔레메트리 필터는 어뷰징 방지를 위해 당일 동일 IP에서 들어오는 두 번째 세션을 중복으로 판단해 드롭했습니다. 이로 인해 같은 Wi-Fi 환경에서 PC로 먼저 테스트한 뒤 모바일로 접속하면, 모바일 기기의 정상적인 활동이 통째로 버려졌습니다.
* **관리자 IP 오판정으로 인한 영구 차단**: 관리자가 모바일(LTE/5G) 환경에서 단순히 `/admin` 경로를 호출하거나 진입을 시도하기만 해도, 해당 통신사 IP가 관리자 IP 목록(`visitors_admin_ips`)에 자동 등록되었습니다. 그 결과, 동일한 기지국 IP 대역을 공유하는 다른 일반 모바일 사용자들의 트래픽까지 대거 차단되는 치명적인 부작용이 발생했습니다.
* **봇(Bot) 오인으로 인한 차단**: 일부 모바일 웹뷰나 PWA 환경에서 전달되는 15자 미만의 짧은 UA 문자열이 기존의 단순 봇 필터링 룰에 걸려 차단되었습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

문제를 해결하기 위해 User-Agent 파싱 및 클라이언트 식별 방식을 재설계해야 했습니다. 두 가지 방향성을 두고 고민했습니다.

### 대안 1: 외부 무거운 UA 파싱 라이브러리(예: `user-agents` 등) 도입
* **장점**: 수많은 기기 및 브라우저 데이터베이스가 이미 구축되어 있어 범용성이 높음.
* **단점**: 패키지 의존성이 늘어나고, 매 요청마다 무거운 정규식 딕셔너리를 탐색하므로 미들웨어 단에서 CPU 병목이 발생할 수 있음. 특히 카카오톡, 네이버 등 국내 특화 인앱 브라우저의 미세한 UA 패턴을 커스텀하게 튜닝하기 까다로움.

### 대안 2: 성능 최적화된 경량 커스텀 파서 구현 + 컨텍스트 추출 표준화
* **장점**: 외부 의존성이 없고 메모리 오버헤드가 극히 적음. 서비스 타겟에 집중하여 카카오톡(`kakaotalk`), 네이버(`naver`), 인스타그램(`instagram`), 페이스북(`fban`/`fbav`), 라인(`line`) 등 국내외 주요 인앱 브라우저 15종을 100% 정확하게 타겟팅 가능.
* **단점**: 새로운 기기나 특이 브라우저가 등장할 경우 정규식 패턴을 직접 유지보수해야 함.

### 선택과 이유
PickSafe는 실시간 성분 분석 요청이 몰릴 때 API 레이어의 지연 시간(Latency)을 최소화해야 합니다. 따라서 무거운 외부 라이브러리를 도입하는 대신, **가볍고 명확한 정규식 기반의 커스텀 파서(대안 2)**를 작성하기로 결정했습니다. 

동시에 중복 세션 판정 기준을 단순 IP에서 `(session_id, ip_address, device_type)` 복합 키로 완화하고, 관리자 IP 등록 조건을 엄격하게 제한하는 아키텍처 개선을 병행했습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 인앱 브라우저 대응형 정밀 UA 파서 구현

가장 먼저 해결해야 했던 것은 누락 없는 기기 파싱이었습니다. 아래와 같이 국내 주요 인앱 브라우저와 모바일 환경을 정확히 캡처할 수 있는 `parse_user_agent` 함수를 재설계했습니다.

```python
import re
from typing import Dict, Any

def parse_user_agent(ua_string: str) -> Dict[str, str]:
    if not ua_string:
        return {"device_type": "Mobile", "os_name": "Android", "browser_name": "Unknown"}

    ua_lower = ua_string.lower()
    
    # 1. OS 판별
    os_name = "Other"
    if "android" in ua_lower:
        os_name = "Android"
    elif any(x in ua_lower for x in ["iphone", "ipad", "ipod"]):
        os_name = "iOS"
    elif "windows" in ua_lower:
        os_name = "Windows"
    elif "macintosh" in ua_lower:
        os_name = "macOS"
    elif "linux" in ua_lower:
        os_name = "Linux"

    # 2. 기기 타입 판별
    device_type = "Desktop"
    if any(x in ua_lower for x in ["mobi", "android", "iphone", "ipad", "ipod", "telephony"]):
        device_type = "Mobile"

    # 3. 브라우저 및 인앱 환경 정밀 분석 (우선순위 고려)
    browser_name = "Other"
    if "kakaotalk" in ua_lower:
        browser_name = "KakaoTalk"
        device_type = "Mobile"
    elif "naver" in ua_lower:
        browser_name = "Naver"
        device_type = "Mobile"
    elif "instagram" in ua_lower:
        browser_name = "Instagram"
        device_type = "Mobile"
    elif any(x in ua_lower for x in ["fban", "fbav"]):
        browser_name = "Facebook"
        device_type = "Mobile"
    elif "line" in ua_lower:
        browser_name = "Line"
        device_type = "Mobile"
    elif "samsungbrowser" in ua_lower:
        browser_name = "Samsung Browser"
        device_type = "Mobile"
    elif "chrome" in ua_lower or "criof" in ua_lower:
        browser_name = "Chrome"
    elif "safari" in ua_lower and "chrome" not in ua_lower:
        browser_name = "Safari"
    elif "firefox" in ua_lower:
        browser_name = "Firefox"
        
    return {
        "device_type": device_type,
        "os_name": os_name,
        "browser_name": browser_name
    }
```

### 2. 표준화된 클라이언트 컨텍스트 추출기 (`extract_client_context`)

라우터마다 제각각이던 클라이언트 정보 수집 코드를 단 한 줄로 표준화했습니다. `extract_client_context`는 요청의 헤더, IP, 쿠키를 파싱하여 신뢰할 수 있는 메타데이터 세트를 반환합니다.

```python
from fastapi import Request

def extract_client_context(request: Request) -> Dict[str, Any]:
    # Cloudflare 또는 리버스 프록시 헤더 고려한 IP 추출
    ip_address = (
        request.headers.get("cf-connecting-ip")
        or request.headers.get("x-forwarded-for")
        or (request.client.host if request.client else "127.0.0.1")
    )
    if "," in ip_address:
        ip_address = ip_address.split(",")[0].strip()

    ua_string = request.headers.get("user-agent", "")
    ua_info = parse_user_agent(ua_string)
    
    # 로케일 추출
    accept_language = request.headers.get("accept-language", "ko-KR")
    locale = accept_language.split(",")[0].split(";")[0].strip()

    return {
        "ip_address": ip_address,
        "device_type": ua_info["device_type"],
        "os_name": ua_info["os_name"],
        "browser_name": ua_info["browser_name"],
        "locale": locale,
        "user_agent": ua_string
    }
```

### 3. 트러블슈팅: 동일 IP 다중 기기 세션 차단 완화와 관리자 IP 오판 방지

가장 까다로웠던 버그는 **동일 IP 차단 로직**과 **관리자 IP 오등록**이 결합되어 대규모 모바일 트래픽이 유실되던 현상이었습니다.

* **기존 문제 코드**:
  ```python
  # 단순히 /admin 경로에 접근을 시도하면 해당 IP를 관리자 IP로 등록하여 차단함
  if "admin" in request.url.path:
      register_admin_ip(client_ip)  # 심각한 오판의 원인
  ```
* **개선된 코드**:
  실제 유효한 관리자 세션 쿠키(`admin_session_token`)를 보유한 정상적인 관리자 요청일 때만 IP를 등록하도록 엄격하게 수정했습니다. 또한 복합 키를 도입하여 동일 IP 내 다중 기기 접속을 허용했습니다.

```python
# web/backend/app/services/analytics_service.py

async def log_analytics_event(db, session_id: str, ip_address: str, device_type: str, event_name: str, ...):
    # 1. 관리자 토큰 검증을 통한 IP 필터링 엄격화
    # 단순 경로 접근이 아닌, 유효한 쿠키가 있는 경우에만 관리자 IP로 판정
    is_admin_request = request.cookies.get(SETTINGS.ADMIN_COOKIE_NAME) is not None
    
    if is_admin_request:
        await register_admin_ip(db, ip_address)
        return  # 관리자 이벤트는 로깅에서 제외
        
    # 2. 동일 IP 다중 기기 세션 인정 (복합 키 검사)
    # 기존: 당일 동일 IP가 존재하면 중복 처리하여 무시
    # 변경: (session_id, ip_address, device_type) 조합이 모두 일치할 때만 중복으로 처리
    is_duplicate = await check_duplicate_session(
        db, 
        session_id=session_id, 
        ip_address=ip_address, 
        device_type=device_type
    )
    
    if is_duplicate and event_name == "session_start":
        return  # 중복 세션 시작 이벤트만 무시하고 진행
```

### 4. 프론트엔드 텔레메트리 2중 안전망 (`base.js`)

모바일 브라우저의 뒤로가기 캐시(BFCache)나 PWA 오프라인 상태 등으로 인해 백엔드 미들웨어가 최초 1회 실행된 후 스킵되는 현상이 있었습니다. 이를 보완하기 위해 화면이 로드될 때 프론트엔드 단에서 세션 상태를 검증하고 백엔드로 핑(`ping`)을 날려 세션을 동기화하는 로직을 추가했습니다.

```javascript
// web/frontend/static/js/base.js

async function initSessionTelemetry() {
    const today = new Date().toISOString().slice(0, 10);
    const lastPingDate = localStorage.getItem('last_telemetry_ping_date');
    
    // 당일 이미 핑을 보냈다면 추가 요청 방지 (불필요한 트래픽 최소화)
    if (lastPingDate === today) {
        return;
    }

    try {
        const response = await fetch('/api/telemetry/ping', {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
            },
            body: JSON.stringify({
                referrer: document.referrer,
                screen_resolution: `${window.screen.width}x${window.screen.height}`
            })
        });
        
        if (response.ok) {
            localStorage.setItem('last_telemetry_ping_date', today);
        }
    } catch (error) {
        console.error('Telemetry ping failed:', error);
    }
}

document.addEventListener('DOMContentLoaded', initSessionTelemetry);
```

## 💡 돌아보며 배운 점

텔레메트리 고도화 작업을 완료한 후, 데이터베이스의 `visitors_events` 테이블을 전수 조사했습니다. 

기존에 수십 퍼센트에 달하던 `Unknown / Other` 기기 유형이 **0건으로 완전히 소멸**했으며, 수집된 모바일 기기 데이터가 정상적으로 `Mobile / Android`, `Mobile / iOS`로 분류되어 집계되는 것을 확인했습니다. 실시간 대시보드 API에서도 디바이스 및 로케일 분포가 왜곡 없이 깨끗하게 출력되었습니다.

이번 개선 과정을 거치며 깊게 느낀 점은 다음과 같습니다.

1. **"Unknown"은 시스템의 게으름이다**: 로그에 찍히는 `Unknown`이나 `Other`는 대부분의 경우 시스템이 복잡한 예외 상황 처리를 회피했을 때 발생합니다. 귀찮더라도 모바일 웹뷰의 특수한 헤더 패턴과 환경적 특성을 끝까지 파고들어 파싱 규칙을 정의했을 때, 비로소 데이터의 신뢰성이 확보된다는 것을 배웠습니다.
2. **보안과 데이터 수집의 균형**: 어뷰징 방지나 관리자 트래픽 제외를 위한 필터링 정책은 정교하게 설계되지 않으면 정상적인 사용자 데이터까지 함께 도려내는 양날의 검이 됩니다. IP 단일 값에 의존하는 거친 필터링 대신, 세션 쿠키와 디바이스 타입 등 다차원적인 컨텍스트를 조합해 판단하는 정밀함이 시스템 안정성에 얼마나 기여하는지 몸소 체험할 수 있었습니다.

앞으로 서비스의 규모가 더 커지더라도, 이렇게 정제되고 신뢰할 수 있는 지표를 바탕으로 PickSafe의 사용자 경험을 한 단계씩 더 정교하게 개선해 나갈 수 있으리라 확신합니다.
