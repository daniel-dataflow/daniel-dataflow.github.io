시스템이 성장함에 따라 초기 빠르게 구축했던 서비스 아키텍처는 새로운 전환점을 맞이합니다. PickSafe 팀 역시 최근 서비스 확장 과정에서 **일반 사용자 영역과 관리자(Admin) 영역의 강한 결합**으로 인한 보안 위험 및 권한 제어의 한계를 마주했습니다.

이번 포스팅에서는 일반 유저와 어드민의 도메인을 물리적·논리적으로 완전 분리하고, Google OAuth 기반의 소셜 로그인 단일화 및 역할 기반 권한 제어(RBAC)를 도입하면서 고민했던 **아키텍처적 선택과 트레이드오프(Trade-off)**를 공유하고자 합니다.

---

## 1. 문제 정의: 세션 오염과 고정된 자격 증명의 위험성

초기 시스템은 빠르게 어드민 기능을 구축하기 위해 일반 회원 테이블(`users`) 내에 `role='admin'` 플래그를 두고, 브라우저 단에서 동일한 `access_token` 쿠키를 공유하도록 설계되었습니다. 그러나 서비스 규모가 커지면서 다음과 같은 3가지 기술적 부채가 심각한 문제로 떠올랐습니다.

1. **세션 혼용(Session Bleed) 및 권한 오염**: 동일한 쿠키 명칭을 공유하다 보니, 관리자 포털에 로그인된 브라우저 세션이 일반 사용자 영역으로 전이될 때 권한 상태가 꼬이거나 UX적 오작동을 유발했습니다.
2. **고정된 자격 증명 기반의 보안 취약성**: 개발 및 초기 운용 편의를 위해 DB에 시딩된 고정 패스워드 방식의 계정이 존재했고, 이는 외부 공격 노출면(Attack Surface)을 불필요하게 넓히고 있었습니다.
3. **단일한 통제 수준(Coarse-grained Access)**: 콘텐츠 관리자, 고객 지원 담당자 등 각 역할군이 대시보드 진입 시 권한 구분 없이 전체 모니터링 지표나 원장 데이터에 접근하는 문제가 존재했습니다.

---

## 2. 아키텍처적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 3가지 주요 과제를 정의하고 기술적 대안을 검토했습니다.

### ① 계정 데이터 및 세션의 격리: 단일 테이블 vs 물리적 분리

* **대안 A (기존 유지):** `users` 테이블에서 `role` 컬럼으로 관리자와 일반 사용자를 구분.
  * *장점:* 단일 스키마로 관리가 단순함.
  * *단점:* 개발자의 실수나 쿼리 누락 시 일반 사용자가 관리자 데이터를 참조하거나, 역으로 관리자 계정에 불필요한 회원 데이터가 결합될 위험 존재. 세션 쿠키 충돌 해결 불가.
* **대안 B (선택):** `admins` 테이블 생성 및 `admin_access_token` 쿠키 격리.
  * *장점:* 스키마 수준에서 물리적으로 완전히 분리되어 데이터 오염 원천 차단. 브라우저 쿠키 수준에서도 독립된 세션 수명 및 보안 정책 적용 가능.
  * *단점:* 인증 관련 파이프라인(엔드포인트, 미들웨어)을 dual-track으로 유지해야 하는 공수 발생.

> **결정:** 데이터 격리와 세션 오염 방지가 선결 과제였으므로 **대안 B**를 선택했습니다. `admins` 테이블을 독립시키고, 관리자용 로그인 쿠키를 `admin_access_token`으로 명확히 구분했습니다.

---

### ② 인증 방식 통합: ID/PW 폼 유지 vs OAuth 단일화

비밀번호 기반 관리자 로그인을 완전히 폐지하고 **Google OAuth 소셜 로그인**으로 인증을 통합했습니다. 

* **운영 환경:** 비밀번호 유출 위험을 차단하고 2FA 등 구글의 보안 체계를 그대로 활용.
* **개발/테스트 환경과의 타협:** 소셜 인증 체계 도입 시 개발자의 로컬 테스트 피로도가 증가하는 문제를 해결하기 위해, 테스트 환경 전용 **Mock 인증 파이프라인**을 제공하기로 결정했습니다.

```
[운영 환경 (prod)] -> Google OAuth 인증 필수 (HttpOnly Cookie / 2시간 TTL)
[개발 환경 (dev)]  -> Mock 어드민 인증 허용 (개발 생산성을 위한 무제한/장기 TTL)
```

---

### ③ 역할 기반 접근 제어 (RBAC) 설계

단순히 "어드민인가 아닌가"를 넘어 **"어떤 페이지/기능에 접근할 수 있는가"**를 제어해야 했습니다. 이를 위해 동적 탭 허용 방식(`allowed_pages`)을 도입했습니다.

* **Frontend/UI:** 관리자의 역할(`super_admin`, `content_manager`, `support_agent`) 및 권한 목록에 따라 사이드바 템플릿 렌더링 시 허용된 메뉴만 동적으로 출력.
* **Backend:** 라우터 진입점에서 파이썬 데코레이터/의존성 주입(`verify_admin("tab_id")`)을 통해 API 단위 2차 검증 수행.

## 3. 핵심 구현 및 트레이드오프 극복 과정

### 1) 운영 환경의 개발용 백도어 원천 차단 (Environment Gating)

테스트 편의를 위한 Mock 로그인 엔드포인트가 실수로 운영 서버(`prod`)에 배포될 경우 치명적인 보안 허점이 됩니다. 이를 막기 위해 백엔드 엔드포인트 진입 시 환경 변수를 검증하여 운영망에서는 즉시 `403 Forbidden`을 반환하도록 다중 통제 장치를 마련했습니다.

```python
# 환경에 따른 백도어 엔드포인트 차단 개념 코드
@router.post("/mock-login")
async def mock_admin_login(settings: Settings = Depends(get_settings)):
    if settings.ENV == "prod":
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN, 
            detail="Mock authentication is disabled in production environment."
        )
    # 개발용 로그인 처리 로직...
```

### 2) OAuth 계정 전환 UX 및 세션 제어

구글 소셜 로그인은 브라우저에 이미 로그인된 계정으로 자동 진행되어 테스트 시 타 계정 전환이 어려운 단점이 있었습니다. 이를 위해 OAuth 인증 요청 시 `prompt=select_account` 옵션을 강제 주입하여, 사용자가 항시 계정을 선택 및 전환할 수 있도록 UX를 개선했습니다.

또한, 자바스크립트 접근이 불가능한 `HttpOnly` 쿠키의 보안적 이점을 유지하면서 세션을 확실하게 소멸시키기 위해, 명시적인 서버 측 로그아웃 엔드포인트를 구축하여 `delete_cookie` 처리를 수행하도록 했습니다.

### 3) 세션 수명의 차별화 (Token Expiration Policy)

보안성과 개발 편의성이라는 두 마리 토끼를 잡기 위해 토큰 수명을 환경에 따라 차등 분리했습니다.

| 구분 | 인증 방식 | JWT / Cookie TTL | 목적 |
| :--- | :--- | :--- | :--- |
| **운영 어드민** | Google OAuth | **2시간 (7,200초)** | 탈취 위험 최적화 및 보안 강비 |
| **개발/테스트** | Mock Auth | **장기 수명 (Long-lived)** | 세션 만료로 인한 개발 흐름 단절 방지 |

### 4) 프론트엔드 최적화: 모바일 이미지 압축 및 업로드 UX

관리자 포털의 프론트엔드 작업 중 모바일 환경에서 카메라 직접 촬영 시 고용량 이미지 업로드로 인한 타임아웃 문제가 발생했습니다. 백엔드 부담을 줄이기 위해 HTML5 Canvas를 활용하여 **클라이언트 사이드 사전 압축(Client-side Pre-compression)** 파이프라인을 구축했습니다.

* 모바일 디바이스에서 강제 촬영 대신 갤러리 선택이 가능하도록 속성을 조정.
* 업로드 직전 이미지의 최대 해상도를 1200px로 리사이징하고 퀄리티를 85%로 압축(원본 대비 약 80~90% 용량 절감: 200~300KB 수준)하여 업로드 타임아웃을 완전 해결했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **도메인 격리는 단순한 코드 정리가 아니라 보안의 기본이다**
   어드민과 일반 사용자를 동일한 데이터 구조 및 세션 영역에 방치하는 것은 언제 터질지 모르는 시한폭탄과 같습니다. 데이터베이스 스키마와 쿠키 명칭 수준에서부터 물리적으로 격리하는 것이 시스템 안정성을 보장하는 가장 확실한 길입니다.
2. **보안과 개발자 경험(DX)은 타협이 아닌 환경 분리로 해결한다**
   보안을 강화할수록 개발자의 테스트 효율성이 떨어질 수 있습니다. 이번 작업에서는 `Environment Gating` 및 조건부 세션 수명 정책을 통해 운영 환경의 철저한 보안을 유지하면서도 개발 환경의 편리성을 높일 수 있었습니다.
3. **Soft Delete를 통한 추적성 보존**
   관리자를 시스템에서 제거할 때 단순 물리 삭제(Hard Delete) 대신 `is_active` 플래그 기반의 Soft Delete를 적용함으로써, 즉각적인 권한 박탈과 동시에 관리자가 과거 수행했던 조치 및 이력을 유실 없이 추적할 수 있게 되었습니다.
