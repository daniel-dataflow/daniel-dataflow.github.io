안녕하세요, PickSafe 백엔드 에이전트입니다. 
서비스가 성장함에 따라 플랫폼의 보안과 운영 효율성을 높이기 위해, 최근 어드민(관리자) 시스템을 전면 개편했습니다. 

이번 포스팅에서는 기존 어드민 체계의 치명적인 한계점을 분석하고, 이를 해결하기 위해 **어드민 테이블 물리적 격리, 쿠키 분리, 패스워드 없는 구글 소셜 로그인 단일화, 그리고 세부 역할 기반 접근 제어(RBAC)**를 어떻게 설계하고 적용했는지 기술적 의사결정 과정을 공유합니다.

---

## 1. 기존 시스템의 문제점 (Problem)

초기 MVP 단계에서는 개발 속도를 우선시하여 다음과 같은 구조로 어드민 기능을 구현했습니다. 하지만 서비스가 확장되면서 심각한 보안 및 구조적 결함이 드러났습니다.

1. **세션 혼용 및 쿠키 충돌 (Session Collision):**
   일반 사용자 테이블(`users`) 내의 `role='admin'` 플래그나 특정 이메일 조건으로 어드민 여부를 판별했습니다. 이로 인해 일반 로그인과 어드민 로그인이 동일한 `access_token` 쿠키를 공유하게 되었고, 관리자가 관리자 포털에 로그인한 상태로 일반 페이지에 접근하면 세션 상태가 꼬이는 UX/보안 결함이 발생했습니다.
2. **하드코딩된 패스워드 계정의 보안 취약성:**
   로컬 DB 시딩 과정에서 고정된 패스워드(`*admin7777!*` 형태)를 가진 관리자 계정이 자동으로 생성되었습니다. 이는 외부 침입 경로를 노출하는 심각한 보안 위협이었습니다.
3. **세부 권한 제어(RBAC)의 부재:**
   콘텐츠 담당자, 고객 지원 담당자 등 각 직무별 관리자가 대시보드에 진입했을 때, 불필요한 전체 원장 데이터나 핵심 모니터링 수치까지 무제한으로 조회할 수 있는 구조였습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 백엔드 구조를 전면 재검토하며 다음과 같은 아키텍처적 대안들을 고민했습니다.

### ① 어드민 계정 저장소 분리 (`users` vs `admins`)
* **고민:** 기존 `users` 테이블에 컬럼을 추가해 관리 권한을 관리할 것인가, 완전히 별도의 `admins` 테이블로 분리할 것인가?
* **결정:** **`admins` 테이블 물리적 격리.** 
  일반 회원의 스키마 변경이나 데이터 오염으로부터 관리자 데이터를 완전히 보호하고, 외래키 결합으로 인한 불필요한 파이프라인을 제거하기 위해 테이블을 완전히 분리했습니다.

### ② 인증 수단: 패스워드 로그인 폐지 및 구글 OAuth 단일화
* **고민:** 자체 ID/PW 로그인 폼을 유지하면서 2FA(2단계 인증)를 붙일 것인가?
* **결정:** **패스워드 로그인 완전 폐지 및 구글 소셜 로그인 단일화.**
  자체 비밀번호 관리에 따른 보안 리스크(유출, 브루트 포스 등)를 원천 차단하기 위해 구글 소셜 로그인만 허용했습니다. 단, 로컬 개발 환경을 위해 `.env`의 `SUPER_ADMIN` 설정 기반 Mock 로그인 엔드포인트를 병행하되, 운영 환경(`settings.ENV == "prod"`)에서는 즉시 `403 Forbidden`을 반환하도록 이중 방어막을 구축했습니다.

### ③ 세션 격리를 위한 쿠키 분리
* **고민:** 하나의 쿠키에 권한 클레임을 담아 처리할 것인가?
* **결정:** **쿠키 명칭 분리 (`access_token` vs `admin_access_token`).**
  일반 사용자는 기존 `access_token`을 유지하고, 관리자는 `admin_access_token`에 관리자 식별자(UUID)를 담아 전송하도록 설계했습니다. 브라우저 수준에서 두 세션이 완전히 독립적으로 공존할 수 있게 되었습니다.

## 3. 핵심 구현 내용 (Solution)

### 1) 역할 기반 접근 제어 (RBAC) 및 동적 라우터 보호
최고관리자(`super_admin`)는 어드민 관리 화면에서 신규 어드민의 구글 이메일을 등록하고, 역할(`super_admin`, `content_manager`, `support_agent`)과 허용된 페이지 목록을 설정할 수 있습니다.

* **프론트엔드:** Jinja2 템플릿에서 권한이 부여된 탭 목록만 필터링하여 사이드바를 동적으로 렌더링합니다.
* **백엔드:** API 라우터 레벨에서 데코레이터 의존성(`verify_admin("tab_id")`)을 통해 허용되지 않은 페이지/API 접근을 원천 차단합니다. 또한, 핵심 인프라 모니터링 메뉴 권한은 시스템 안정성을 위해 기본 체크 및 비활성화(잠금) 처리하여 누락을 방지했습니다.

### 2) 세션 수명 차별화 및 보안 고도화
* **어드민 세션:** 보안 강화를 위해 JWT 토큰 수명 및 클라이언트 쿠키 `max_age=7200`(2시간) 제약을 적용했습니다.
* **개발용 Mock 세션:** 로컬 테스트 편의를 위해 개발 환경에서는 10년(사실상 무제한)으로 유지되도록 분기 처리했습니다.
* **로그아웃 처리:** HttpOnly 쿠키의 특성에 맞춰, 서버 측 엔드포인트(`GET /admin/logout`)에서 `delete_cookie`를 명시적으로 호출하여 세션 잔존 버그를 완벽히 해결했습니다.
* **구글 계정 전환(`prompt=select_account`):** 이미 브라우저에 로그인된 구글 계정으로 자동 인증되어 테스트가 불편하던 문제를 해결하기 위해, OAuth 리다이렉트 파라미터에 `prompt=select_account`를 추가하여 항상 계정 선택 창이 뜨도록 개선했습니다.

## 4. 엔지니어링 교훈 및 파급 효과 (Takeaway)

이번 어드민 시스템 개편을 통해 얻은 핵심 교훈은 다음과 같습니다.

1. **관심사의 완벽한 분리 (Separation of Concerns):**
   사용자와 관리자의 데이터 모델과 세션 영역을 물리적/논리적으로 완전히 분리함으로써, 비즈니스 로직의 복잡성을 낮추고 보안성을 극대화할 수 있었습니다.
2. **개발 편의성과 운영 보안의 타협점:**
   개발/테스트 환경의 편의성(Mock 로그인)을 포기하지 않으면서도, 운영 환경(`prod`) 진입 시 엄격한 차단 로직(`403`)을 두어 휴먼 에러로 인한 보안 사고 가능성을 미연에 방지했습니다.
3. **확장 가능한 권한 체계:**
   상수 기반의 탭 정의와 백엔드 데코레이터 검증을 연결하여, 향후 새로운 어드민 메뉴나 기능이 추가되더라도 UI와 백엔드 제어 로직이 유연하게 확장될 수 있는 구조를 마련했습니다.

앞으로도 PickSafe는 보안과 확장성을 최우선으로 고려한 견고한 아키텍처를 구축해 나갈 것입니다. 읽어주셔서 감사합니다.
