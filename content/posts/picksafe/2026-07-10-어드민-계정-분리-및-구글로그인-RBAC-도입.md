안녕하세요. PickSafe 기술 블로그 편집장입니다.

스타트업이나 성장하는 서비스에서 흔히 발생하는 기술 부채 중 하나는 바로 **"어드민(관리자) 시스템의 느슨한 격리"**입니다. 서비스 초기에는 빠른 딜리버리를 위해 일반 사용자 테이블에 `is_admin` 혹은 `role` 컬럼 하나만 추가하여 어드민 권한을 관리하곤 합니다.

하지만 서비스 규모가 커지고 다루는 데이터의 민감도가 높아질수록, 이러한 방식은 치명적인 보안 위협과 UX 엉킴 현상을 초래합니다. 

최근 PickSafe 개발 팀은 기존의 느슨했던 어드민 시스템을 전면 개편하여, **물리적 데이터 격리, 브라우저 세션 독립, 구글 OAuth 단일화, 그리고 세밀한 역할 기반 접근 제어(RBAC)**를 성공적으로 구축했습니다. 이 과정에서 마주한 문제들과 아키텍처적 고민, 그리고 엔지니어링적 교훈을 공유하고자 합니다.

---

## 1. 마주한 기술적 문제 (Problem)

개편 전 PickSafe의 어드민 시스템은 크게 세 가지 구조적 문제를 안고 있었습니다.

### ① 세션 혼용으로 인한 권한 꼬임 및 UX 결함
기존 시스템은 일반 사용자와 어드민이 동일한 `access_token`이라는 쿠키 명칭을 공유했습니다. 이로 인해 한 브라우저에서 관리자 포털에 로그인한 상태로 일반 사용자 페이지로 이동하면 권한 상태가 충돌하거나 세션이 꼬여 비정상적인 에러를 뿜는 UX 결함이 지속적으로 발생했습니다.

### ② 고정 패스워드 시딩으로 인한 보안 취약성
로컬 개발 및 편리한 테스트를 위해 데이터베이스에 고정된 비밀번호(예: `admin7777!`)를 가진 계정이 자동 시딩되고 있었습니다. 이는 개발 편의성을 대가로 외부 침입 및 인증 경로 유출이라는 거대한 보안 리스크를 안고 가는 시한폭탄과 같았습니다.

### ③ 세부 권한 제어(RBAC)의 부재
콘텐츠 담당자, 고객 지원 담당자, 인프라 담당자 등 각 조직의 역할에 맞게 접근할 수 있는 페이지가 제한되어야 했습니다. 하지만 기존에는 어드민 권한이 '전무(None)' 아니면 '전부(All)'인 이분법적 구조였기에, 특정 대시보드 진입 시 민감한 원장 정보나 시스템 핵심 지표가 불필요하게 노출되는 문제가 있었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 위 문제를 해결하기 위해 크게 세 가지 아키텍처적 의사결정을 내려야 했습니다.

### 고민 1: 단일 사용자 테이블 확장 vs 물리적 테이블 격리
*   **대안 A (단일 테이블 유지):** 기존 `users` 테이블에 이메일 조건이나 `role='admin'` 컬럼을 고도화하여 필터링하는 방식.
    *   *장점:* 데이터 모델이 단순하게 유지되며 회원 관련 공통 유틸리티 코드를 재사용할 수 있음.
    *   *단점:* 데이터가 물리적으로 섞여 있어 쿼리 실수 한 번으로 어드민 권한이 일반 사용자에게 부여될 위험(Accidental Privilege Escalation)이 상존함.
*   **대안 B (물리적 격리 - 선택):** 일반 사용자가 가입하는 `users` 테이블과 어드민 권한만을 다루는 `admins` 테이블을 완벽히 분리.
    *   *선택 이유:* 보안적 안전성(Security Boundary) 확보가 최우선이었습니다. 일반 회원 스키마의 잦은 변경이나 데이터 오염이 어드민 권한 체계에 전혀 영향을 주지 않도록 완벽히 격리하는 대안 B를 채택했습니다.

### 고민 2: ID/PW 로그인 유지 vs 구글 소셜 로그인(OAuth) 단일화
*   **대안 A (ID/PW 로그인 유지):** 강력한 패스워드 복잡도 규칙을 적용하고 DB에 단방향 해시로 저장하여 로그인 폼 제공.
    *   *단점:* 비밀번호 유출 위험, 주기적 변경 강제 정책 수립 필요, 개발 환경용 하드코딩 패스워드 방치 위험 지속.
*   **대안 B (소셜 로그인 단일화 - 선택):** 자체 패스워드 로그인을 전면 폐지하고, 사내 구글 워크스페이스 계정을 통한 구글 OAuth 로그인만 지원.
    *   *선택 이유:* 비밀번호 자체를 관리하지 않음으로써 자격 증명 유출 위험을 0%에 수렴시켰습니다. 또한 퇴사자 발생 시 구글 워크스페이스 계정만 차단하면 어드민 접근 권한이 즉시 회수되므로 운영 공수가 획기적으로 줄어듭니다.

## 3. 최종 해결책 및 아키텍처 구현 (Solution)

우리는 위의 고민을 바탕으로 다음과 같은 견고한 어드민 권한 및 세션 분리 아키텍처를 구현했습니다.

```
[Client Browser]
   │
   ├─── (User Session)  ───> Cookie: access_token ──────> [User Portal (FastAPI)]
   │
   └─── (Admin Session) ───> Cookie: admin_access_token ──> [Admin Portal (FastAPI)]
                                                                │ (verify_admin("tab_id"))
                                                                └──> RBAC Engine (admins table)
```

### ① 쿠키 격리를 통한 세션 공존 보장
일반 사용자는 기존의 `access_token` 쿠키를 사용하고, 관리자는 로그인 시 **`admin_access_token`**이라는 별도의 쿠키를 사용하도록 물리적으로 분리했습니다. 
이 덕분에 관리자는 한 브라우저 내에서 일반 서비스 화면과 관리자 화면을 넘나들어도 세션 간섭 없이 완벽하게 독립된 동작을 보장받게 되었습니다.

### ② 보안이 강화된 환경별 로그인 정책 (Production vs Dev)
패스워드를 완전히 제거하고 구글 소셜 로그인만 채택하면서 발생할 수 있는 로컬 개발 환경의 불편함을 해소하기 위해 **이중 세션 정책**을 도입했습니다.

*   **운영 환경(Prod):** 보안 강화를 위해 오직 구글 소셜 로그인만 허용하며, 세션 만료 시간을 **2시간**(`max_age=7200`)으로 타이트하게 제한했습니다. 만약 개발용 Mock 로그인 엔드포인트에 접근을 시도하면, 인프라 환경 변수(`ENV == "prod"`)를 감지하여 즉시 `403 Forbidden`을 반환하도록 통제 장치를 마련했습니다.
*   **개발 환경(Dev/Local):** 빠른 디버깅과 로컬 테스트를 위해 `.env`에 정의된 `SUPER_ADMIN` 정보와 연동되는 Mock 로그인 백엔드 엔드포인트를 병행 지원하며, 이 환경에서는 세션 수명을 **10년(사실상 무제한)**으로 설정하여 개발자 경험(DX)을 극대화했습니다.

### ③ 유연한 RBAC(역할 기반 접근 제어)와 의존성 주입
최고관리자(`super_admin`)는 다른 어드민 계정의 허용 페이지 목록(`allowed_pages`)을 제어할 수 있습니다. 이를 효율적으로 검증하기 위해 FastAPI의 의존성 주입(Dependency Injection)을 적극 활용했습니다.

```python
# [보안 필터링 적용 예시 - 콘셉트 코드]
def verify_admin(required_tab: str):
    def dependency(admin_user: Admin = Depends(get_current_admin)):
        # 슈퍼어드민은 모든 권한을 우회 통과
        if admin_user.role == "super_admin" or admin_user.allowed_pages == "*":
            return admin_user
            
        # 세부 탭 권한 검증
        allowed_tabs = admin_user.allowed_pages.split(",")
        if required_tab not in allowed_tabs:
            raise HTTPException(status_code=403, detail="해당 메뉴에 대한 접근 권한이 없습니다.")
            
        return admin_user
    return dependency
```

이 검증 로직은 Jinja2 템플릿과도 연동되어, 백엔드 라우터 API 레벨의 차단뿐만 아니라 프론트엔드 사이드바 메뉴 렌더링 시에도 해당 어드민이 접근할 수 있는 탭 목록만 걸러서 그리도록 통합 설계되었습니다.

### ④ 실무 UX 고도화와 디테일의 완성

아키텍처 개편에 맞춰, 실무자들의 업무 능률을 비약적으로 상승시킨 디테일한 개선들도 함께 진행되었습니다.

1.  **구글 계정 전환 편의성 개선 (`prompt=select_account`):** 기존에는 구글 로그인 시 브라우저에 이미 로그인된 계정으로 강제 자동 로그인되어 다른 부계정으로 테스트하기 어려웠습니다. 리다이렉트 파라미터에 `prompt=select_account` 옵션을 탑재하여 소셜 로그인 진입 시 항상 계정 선택 창이 활성화되도록 개선했습니다.
2.  **안전한 HttpOnly 쿠키 로그아웃:** 자바스크립트로 탈취가 불가능한 HttpOnly 쿠키 정책을 고수하면서, 어드민 로그아웃 시에는 반드시 서버 측 엔드포인트(`GET /admin/logout`)를 통과하게 하여 쿠키를 서버 단에서 확실하게 파괴(`delete_cookie`)하도록 함으로써 세션 잔존 버그를 해결했습니다.
3.  **모바일 카메라 업로드 이미지 압축 최적화:** 현장에서 모바일로 즉석 촬영한 원본 고용량 이미지를 업로드할 때 발생하는 타임아웃과 대역폭 낭비를 막기 위해, 클라이언트(HTML5 Canvas) 단에서 업로드 전 이미지를 최대 1200px, 퀄리티 85% 수준(200~300KB 내외)으로 압축하여 전송하는 최적화 파이프라인을 구축했습니다.
4.  **다중 소셜 계정 연동 시각화:** 어드민이 회원 목록을 조회할 때, 사용자가 어떤 소셜 채널(Google, Facebook 등)들을 연동하고 있는지 한눈에 알 수 있도록 1:N 구조의 소셜 연동 정보를 파이프라인으로 병합하여 프론트엔드에 가로 정렬 배지 리스트로 직관적으로 노출했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 어드민 시스템 개편을 진행하며 PickSafe 팀이 얻은 가장 큰 배움은 다음과 같습니다.

### 첫째, "보안은 격리에서 시작된다"
테이블 하나를 같이 쓰면서 조건문 몇 개로 권한을 분증하는 것은 당장 구현하긴 편하지만, 시스템이 복잡해질수록 휴먼 에러의 가능성을 기하급수적으로 높입니다. 데이터를 물리적으로 격리하고, 브라우저 쿠키의 이름을 다르게 가져가는 단순한 아키텍처적 격리 조치만으로도 수많은 권한 충돌 버그와 보안 허점을 원천 차단할 수 있었습니다.

### 둘째, "보안과 UX는 트레이드오프 관계가 아니다"
보안을 강화한다고 해서 사용성과 개발자 경험이 나빠질 필요는 없습니다. `prompt=select_account`를 통한 계정 전환의 유연성 확보, 그리고 운영계와 개발계의 세션 만료 정책 차별화(2시간 vs 10년)는 강력한 보안을 유지하면서도 개발 속도와 운영 생산성을 모두 챙길 수 있는 영리한 절충안이었습니다.

### 셋째, "코드 수준의 강제 장치 마련의 중요성"
운영 서버의 실수를 방지하기 위해 환경 변수(`ENV == "prod"`)를 코드 단에서 엄격히 검증하여 Mock 로그인을 원천 차단한 것처럼, 시스템 안정성은 인간의 주의력에 의존하기보다 **코드가 스스로 검증하도록 설계(Self-validating Architecture)**해야 한다는 것을 다시 한번 절감했습니다.

PickSafe 팀은 단순한 기능 구현을 넘어, 서비스의 안전성과 지속 가능성을 담보할 수 있는 견고한 아키텍처를 지향합니다. 앞으로도 안전하고 신뢰할 수 있는 서비스를 만들기 위한 저희의 여정을 기대해 주세요!
