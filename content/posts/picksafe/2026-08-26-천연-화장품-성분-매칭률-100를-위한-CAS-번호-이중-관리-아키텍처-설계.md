화장품 성분 분석 서비스인 **PickSafe**를 개발하면서 가장 까다로웠던 영역 중 하나는 국내외 성분 데이터의 표준화였습니다. 특히 한국 식품의약품안전처(식약처)의 공인 성분 데이터 약 2만 건을 마스터 DB에 구축하는 과정에서 예기치 못한 병목을 마주했습니다. 

"가공소금", "누룩추출물", "온천수"와 같은 천연/식품 기반 원료들이 수집 과정에서 대거 오류 검토 큐(`ingredients_seeding_errors`)로 빠지는 현상이 발생한 것입니다. 이 문제를 해결하기 위해 고민했던 기술적 배경과 이중 관리 아키텍처로의 전환 과정을 차분히 기록해 봅니다.

## 🎯 마주한 고민과 문제 배경

기존의 수집 엔진은 데이터 정합성을 위해 매우 엄격한 기준을 적용하고 있었습니다. 모든 성분은 식별자로서 화학 물질 고유 번호인 **CAS 번호(Chemical Abstracts Service Registry Number)**를 필수로 가져야 했고, 수집 시 `숫자-숫자-숫자` 포맷 검증을 거치도록 설계했습니다.

그러나 실제 도메인은 이론과 달랐습니다.
1. **천연물 및 복합물의 특수성**: 단일 화학 분자가 아닌 천연 추출물이나 식품 원료는 국제적으로 CAS 번호가 존재하지 않거나(N/A), 여러 개의 CAS 번호가 혼재되어 있었습니다.
2. **검증 실패와 유실**: 엄격한 규칙 때문에 약 1,000여 건의 천연 성분이 수집 단계에서 누락되었습니다.
3. **UX 저하**: 이로 인해 사용자가 천연 소금 스크럽이나 발효 화장품을 스캔했을 때, 식약처 공인 성분임에도 서비스 화면에는 `❓ 미확인 성분`으로 분류되어 신뢰도를 떨어뜨리는 심각한 문제가 발생했습니다.

데이터의 정합성을 지키면서도 사용자에게 즉각적인 매칭 서비스를 제공해야 하는 상충된 상황에서, 아키텍처의 근본적인 체질 개선이 필요했습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

문제를 해결하기 위해 세 가지 접근 방식을 두고 저울질했습니다.

| 비교 항목 | 대안 1: CAS 번호 수동 전수조사 후 반영 | 대안 2: CAS 유효성 검증 전면 폐기 | 대안 3: 이중 관리 체계 (Dual Management) |
| :--- | :--- | :--- | :--- |
| **반영 속도** | 매우 느림 (1,000여 건 수동 분석 필요) | 매우 빠름 (즉시 반영) | **빠름 (즉시 마스터 편입 및 순차 보강)** |
| **데이터 정합성**| 높음 | 매우 낮음 (가짜 CAS 번호 난입 가능) | **높음 (검증 완료된 데이터만 마스터 업데이트)** |
| **운영 공수** | 극심함 | 없음 (방치) | **적절함 (자동화 큐 및 어드민 도구 활용)** |
| **선택 여부** | 탈락 | 탈락 | **최종 선택 (Alternative 3)** |

### 선택 이유 (Trade-off)
대안 3의 **이중 관리 체계**를 선택했습니다. 
사용자 서비스 관점에서는 한글 성분명만 매칭되면 즉시 정보를 보여주는 것이 중요하므로, CAS 번호가 없더라도 우선 마스터 DB(`IngredientMaster`)에 편입시킵니다. 대신 데이터 품질 관리를 위해 이들을 `pending` 상태로 분류하고, 관리자 영역에서 백그라운드로 자동/수동 보강할 수 있는 전용 파이프라인을 분리하기로 결정했습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 이중 관리를 위한 DB 스키마 및 수집 서비스 구현
먼저 마스터 테이블에 보강 상태를 추적할 수 있는 `cas_enrichment_status` 컬럼을 추가하고 인덱스를 생성했습니다. 수집 서비스 단계에서 CAS 번호가 없거나 형식이 맞지 않으면 `pending` 상태로 마킹하여 저장합니다.

```python
# models.py (SqlAlchemy 예시)
class IngredientMaster(Base):
    __tablename__ = "ingredients_master"

    id = Column(Integer, primary_key=True)
    korean_name = Column(String(255), nullable=False, index=True)
    english_name = Column(String(255), nullable=True)
    cas_no = Column(String(50), nullable=True, index=True)
    # 'none' (기본값/보강불필요), 'pending' (보강대상), 'completed' (보강완료)
    cas_enrichment_status = Column(String(20), default="none", nullable=False, index=True) 
```

```python
# seeding_service.py
def ingest_ingredient(db: Session, raw_data: dict):
    korean_name = raw_data.get("korean_name")
    raw_cas = raw_data.get("cas_no")
    
    # CAS 번호 유효성 검증 규칙 (간단한 정규식 검증)
    is_valid_cas = False
    if raw_cas and re.match(r"^\d+-\d+-\d+$", raw_cas.strip()):
        is_valid_cas = True
        
    if is_valid_cas:
        cas_no = raw_cas.strip()
        status = "none"
    else:
        cas_no = None
        status = "pending"  # 추후 보강을 위한 마킹
        
    # INCI(국제성분명)가 없을 경우 식별을 위한 가상 식별자 부여
    inci_name = raw_data.get("english_name") or f"N/A-{korean_name}"

    ingredient = IngredientMaster(
        korean_name=korean_name,
        english_name=inci_name,
        cas_no=cas_no,
        cas_enrichment_status=status
    )
    db.add(ingredient)
    db.commit()
```

### 2. PubChem API를 활용한 자동 보강 파이프라인
보강 큐에 들어온 성분들은 미국 국립보건원(NIH)에서 제공하는 **PubChem PUG-REST API**를 통해 영문명 또는 한글명으로 자동 조회하여 CAS 번호를 추천받도록 구현했습니다.

```python
# seeding_cas_service.py
import requests
import urllib.parse

class PubChemEnricher:
    def __init__(self):
        # 내부 설정 파일에서 API 기본 주소 로드
        self.api_url = SETTINGS.PUBCHEM_API_URL # "https://pubchem.ncbi.nlm.nih.gov/rest/pug"

    def find_cas_by_name(self, name: str) -> str | None:
        if not name:
            return None
        
        encoded_name = urllib.parse.quote(name)
        # PubChem PUG-REST API를 통해 Synonyms 정보 조회
        url = f"{self.api_url}/compound/name/{encoded_name}/synonyms/JSON"
        
        try:
            response = requests.get(url, timeout=5)
            if response.status_code != 200:
                return None
                
            data = response.json()
            synonyms = data.get("InformationList", {}).get("Information", [{}])[0].get("Synonym", [])
            
            # Synonym 목록 중 CAS 번호 패턴(정규식) 매칭 탐색
            for synonym in synonyms:
                match = re.match(r"^(\d{2,7}-\d{2}-\d)$", synonym.strip())
                if match:
                    return match.group(1)
        except Exception as e:
            # 실 운영 환경에서는 별도 로깅 라이브러리로 처리
            print(f"PubChem API Error for {name}: {str(e)}")
            
        return None
```

### 3. 트러블슈팅: 배치 작업 시의 DB 부하와 캐시 정합성 문제
자동 보강 배치를 구현한 후 테스트하는 과정에서 예상치 못한 부하 문제가 있었습니다.
성분 테이블을 업데이트할 때마다 실시간으로 캐시를 무효화(Invalidation)하거나 DB 조회를 반복하게 만들었더니, Serverless DB(Neon DB)의 CPU 사용량이 순간적으로 치솟았습니다.

**해결책**:
- **벌크 처리 및 캐시 리빌드 분리**: 배치가 실행되는 동안에는 DB의 `cas_enrichment_status`만 조용히 업데이트하도록 제한했습니다.
- **정적 캐시 단일 리빌드**: 모든 보강 작업이 끝난 시점에 단 한 번만 전체 마스터 데이터를 JSON 파일(`ingredients_master.json`)로 다시 빌드하여 S3에 업로드하도록 프로세스를 분리했습니다. 
- 결과적으로 사용자 스캔 API는 DB를 전혀 건드리지 않고 메모리 및 정적 캐시 파일만 조회하므로, DB 부하를 **0%**에 가깝게 유지할 수 있었습니다.

## 💡 돌아보며 배운 점 (회고)

이번 개편을 진행하며 엔지니어로서 데이터 정합성과 비즈니스 가치(사용자 경험) 사이의 균형을 잡는 법을 배웠습니다.

1. **도메인에 대한 이해가 우선이다**: 모든 데이터가 관계형 데이터베이스의 제약 조건처럼 깔끔하게 떨어지지 않는다는 점을 인정해야 했습니다. 천연물이라는 도메인 특성을 고려하지 않고 엄격한 CAS 룰만 고집했다면, 서비스 사용성은 계속 나빠졌을 것입니다.
2. **비동기적 해결의 유용성**: 완벽한 데이터를 수집 시점에 강제하기보다, "우선 서비스 가능한 형태로 유연하게 받고, 백그라운드에서 정제한다"는 아키텍처가 실제 운영 공수를 얼마나 획기적으로 줄여주는지 체감했습니다. PubChem API 자동 보강과 3대 사전(KCIA, CosIng, K-REACH) 원클릭 링크 덕분에, 관리자 화면에서 단 몇 번의 클릭만으로 1,000여 개의 예외 성분을 빠르게 정제할 수 있었습니다.

추후에는 이 보강 배치를 주기적인 스케줄러(Cron Job)로 등록하여, 식약처 신규 고시 성분이 추가될 때마다 자동으로 보강 큐가 작동하도록 고도화할 계획입니다. 실용적인 타협과 영리한 파이프라인 설계가 서비스의 완성도를 만든다는 것을 다시금 깨달은 유의미한 작업이었습니다.
