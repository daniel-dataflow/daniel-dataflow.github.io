안녕하세요. PickSafe 백엔드 엔지니어입니다. 

서비스가 성장함에 따라 운영 지표를 모니터링하는 방문자 분석 시스템의 중요성도 커지고 있습니다. 하지만 최근 운영 환경에서 **"오늘 방문자 수가 0으로 보인다"**, **"네트워크를 바꿔도 새 방문으로 집계되지 않는다"**, **"관리자 테스트가 자꾸 지표를 오염시킨다"** 등 4가지 치명적인 피드백이 접수되었습니다.

이번 포스팅에서는 이 문제들을 해결하기 위해 **어떤 아키텍처적 고민을 했고, 왜 그러한 트레이드오프를 선택했는지** 엔지니어링 관점에서 공유하고자 합니다.

---

## 1. 문제 정의 (Problem Statement)

운영 중 발견된 문제는 크게 데이터의 실시간성, 세션 정책의 허점, 그리고 인프라 제약(DB 전환) 상황에서의 데이터 연속성 단절이었습니다.

1. **실시간 집계의 부재**: 관리자 페이지가 전일 마감된 요약 테이블(`daily_analytics_summary`)만 조회하고 있어, 당일 발생한 실시간 이벤트가 자정 배치 전까지는 완전히 누락(`0명`)되는 현상.
2. **비정상적으로 긴 세션 수명**: 세션 쿠키의 만료 기한이 `1년`으로 설정되어 있어, Wi-Fi나 LTE 등 네트워크 환경이 바뀌어도 기존 쿠키가 유지되어 신규 세션(`is_new_session = False`)으로 잡히지 않는 문제.
3. **프록시 환경에서의 IP 유실**: CDN 및 프록시 환경(`Cloudflare` 등)을 거치며 `request.client.host`만 바라보다 보니 국가/도시 정보가 `null`로 기록되는 현상.
4. **인프라 제약(Compute 한도)에 따른 데이터 단절**: 무료 티어 컴퓨팅 한도로 인해 월말/월초에 DW1 ↔ DW2 간 스위칭(Failover/Failback)이 발생할 때, 기존 분석 데이터가 단절되는 구조적 한계.

## 2. 기술적 고민과 아키텍처 대안 비교

### 2.1. 오늘 데이터 실시간 조회: 실시간 스트리밍 vs 하이브리드 집계
* **대안 A (실시간 스트리밍 - Redis/Kafka 도입)**: 모든 이벤트를 인메모리 스토어에 적재하고 실시간으로 카운팅.
  * *Pros*: 가장 완벽한 실시간성.
  * *Cons*: 현재 서비스 규모 대비 과도한 인프라 복잡도와 비용 발생 (Over-engineering).
* **대안 B (하이브리드 집계 - 선택)**: 
  * 과거 데이터: 기존대로 고속 마감 테이블(`daily_analytics_summary`) 조회.
  * 오늘 데이터: `analytics_events` 테이블을 직접 `GROUP BY`하여 실시간 연산 후 합산.
  * *Pros*: 인프라 추가 없이 구현 가능하며, 조회 시점에만 연산하므로 부하가 적음.
  * *Cons*: 트래픽이 폭증할 경우 오늘 날짜 조회 시점에 약간의 DB 부하 가능 (캐싱 및 인덱싱으로 완충).

### 2.2. DW 스위칭 환경에서의 데이터 연속성: 외부 DW에만 의존 vs 중앙 허브(Bridge) 패턴
* **대안 A (외부 DW 단독 운영)**: DW1에서 DW2로 전환될 때마다 데이터 스냅샷을 수동 마이그레이션.
  * *Pros*: 구조가 단순함.
  * *Cons*: 인프라 전환 시점에 수동 작업이 개입되어 휴먼 에러 발생 위험 및 시계열 데이터 단절.
* **대안 B (Main DB 중앙 허브 앵커링 - 선택)**: 
  * 용량이 매우 작고 핵심 메타데이터인 일별 요약 정보(~1KB/일)와 관리자 예외 설정(`admin_ips`)을 **Main DB에 상시 앵커링**.
  * 새로운 DW가 활성화되거나 기동될 때(`Pull Sync`), Main DB로부터 과거 전체 요약 데이터를 자동으로 복제.
  * *Pros*: DW1과 DW2가 언제 스위칭되든 1일~31일 전체 시계열 그래프가 1초의 단절도 없이 완벽히 유지됨.
  * *Cons*: Main DB가 약간의 부하를 분담하지만, 하루 1회 1KB 수준의 트래픽이므로 영향도는 0.0001% 미만.

## 3. 핵심 해결 전략 및 구현

### ① 프록시 환경을 고려한 IP 추출 우선순위 정립
로드밸런서나 CDN 환경에서 원본 클라이언트 IP가 유실되지 않도록, 백엔드 미들웨어 단계에서 명확한 헤더 파싱 체계를 구축했습니다.

> **우선순위 순서**: `cf-connecting-ip` (Cloudflare) $\rightarrow$ `x-real-ip` $\rightarrow$ `x-forwarded-for` (첫 번째 IP) $\rightarrow$ `request.client.host`

### ② 스마트 세션 쿠키 정책
DAU(일간 활성 방문자) 지표의 정확도를 높이기 위해, 세션 쿠키의 `max-age`를 고정 1년에서 **"당일 KST 자정까지 남은 초(Seconds)"**로 동적 계산하도록 변경했습니다. 이를 통해 사용자가 매일 첫 접속 시 새로운 세션으로 자연스럽게 판정되도록 개선했습니다.

### ③ Main DB 브릿지를 통한 DW 무중단 Failover 보장
아래와 같이 매일 자정 집계 시 Main DB에 요약 데이터를 동시 UPSERT하고, DW 전환 시 자동으로 Pull Sync하는 구조를 완성했습니다.

```
[ Active DW ] ──(매일 자정 1회 UPSERT: ~1KB)──> [ Main DB (Bridge) ]
                                                       │
                                           (DW2 전환 시 자동 Pull Sync)
                                                       ▼
                                                [ New DW (DW2) ]
```

- **효과**: DW 서버가 완전히 교체되어도 어드민 설정(`admin_ips`)과 방문자 시계열 통계가 유실되지 않으며, 100% 데이터 연속성을 보장합니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **오버엔지니어링 경계하기**: 실시간성을 확보하기 위해 Redis나 Kafka 같은 무거운 인프라를 바로 도입하기보다, 현재 RDBMS 구조 안에서 `GROUP BY`를 활용한 하이브리드 조회가 훨씬 빠르고 실용적인 해답이 될 수 있음을 배웠습니다.
2. **아키텍처의 제약을 비즈니스 로직으로 극복하기**: 무료 티어 클라우드 환경의 Compute 한도라는 인프라 제약을, 가장 가벼운 저장소인 Main DB를 '중앙 브릿지'로 활용하는 패턴으로 우아하게 해결했습니다. 제약 조건은 때로는 더 단순하고 견고한 아키텍처를 낳습니다.
3. **운영자 관점의 예외 처리**: 개발자 중심의 기능 구현을 넘어, 관리자 자신의 테스트 트래픽이 지표를 왜곡하지 않도록 IP 자동 등록 및 토글 기능을 제공함으로써 "관측 가능한 시스템"의 신뢰도를 높였습니다.

앞으로도 PickSafe는 안정적이고 확장 가능한 아키텍처를 바탕으로 고도화된 분석 환경을 제공해 나가겠습니다. 읽어주셔서 감사합니다.
