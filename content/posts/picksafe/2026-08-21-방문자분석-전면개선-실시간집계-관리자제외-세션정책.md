안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스가 성장함에 따라 사용자 트래픽을 정확하게 분석하는 것은 제품 고도화의 핵심 과제입니다. 이번 포스팅에서는 최근 진행한 **방문자 분석 시스템 전면 개편** 과정에서 마주한 4가지 기술적 난제와, 이를 해결하기 위해 선택한 아키텍처적 트레이드오프(Trade-off)를 공유하고자 합니다.

특히 서버 비용을 최적화하기 위해 **무료 티어 Compute 환경을 사용하면서 발생한 인프라 제약을 메인 데이터베이스(Main DB) 중심의 브릿지 전략으로 극복한 과정**에 초점을 맞추어 설명하겠습니다.

---

## 1. 배경 및 문제 정의 (Problem)

기존 방문자 분석 시스템은 비용 절감을 위해 배치(Batch) 기반으로 전날 데이터를 집계하는 구조를 취하고 있었습니다. 하지만 이로 인해 프로덕션 환경에서 다음과 같은 치명적인 한계들이 드러났습니다.

1. **오늘 방문 데이터가 차트에 보이지 않는 문제**: `GET /admin/analytics` API가 전날 마감된 요약 데이터(`daily_analytics_summary`)만 바라보고 있어, 자정 배치(Batch)가 돌기 전까지는 오늘 발생한 모든 실시간 트래픽이 `0`으로 표시되었습니다.
2. **세션 만료 정책의 허점 (1년 쿠키)**: 재방문율(DAU)의 정확도를 높여야 했으나, 세션 쿠키 만료 기한이 1년으로 설정되어 있어 네트워크(Wi-Fi/LTE)를 변경하거나 브라우저를 재시작해도 동일 세션으로 인식, 신규 방문 이벤트가 누락되었습니다.
3. **프록시 환경에서의 IP 누락**: CDN 및 리버스 프록시 환경에서 `X-Forwarded-For` 등 표준 헤더의 우선순위가 정교하게 처리되지 않아 국가/도시 지도 통계에 `null`이 빈번하게 기록되었습니다.
4. **관리자 트래픽의 오염**: 어드민 경로(`/admin/*`) 외의 일반 페이지(예: 메인 화면 등)를 탐색할 때 관리자의 테스트용 방문이 순수 유저 트래픽에 섞여 분석 지표를 왜곡했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

### ① 실시간 '오늘' 데이터 조회: 집계 테이블 vs 하이브리드 실시간 쿼리
* **고민**: 오늘 발생한 수많은 이벤트 데이터를 매번 `GROUP BY`로 실시간 집계하면 DB 부하가 커지지 않을까?
* **대안 비교**:
  - **대안 A (전면 실시간 집계)**: 모든 조회 시점에 `analytics_events`를 풀 집계. (과거 데이터까지 조회 시 성능 저하 우려)
  - **대안 B (하이브리드 전략)**: 과거 날짜는 기존 마감 테이블(`daily_analytics_summary`)을 조회하고, **오늘 날짜가 포함된 경우에만** `analytics_events` 테이블에서 직접 `GROUP BY` 연산을 수행.
* **선택 (대안 B)**: 과거 데이터의 조회 속도는 보장하면서, 오늘 데이터만 실시간으로 정확히 보여주기 위해 응답 값에 `today_live: true` 플래그를 포함하는 하이브리드 방식을 채택했습니다. (※ 여기서 '실시간'은 웹소켓 폴링이 아닌, 대시보드 조회 버튼을 누르는 시점의 최신 데이터를 의미합니다.)

### ② 인프라 스위칭(Failover/Failback) 시 데이터 단절 문제 해결
* **고민**: 무료 티어 Compute 인스턴스의 자원 한계로 인해 월말에 DW1에서 DW2로 전환(Failover)하고, 월초에 다시 복귀(Failback)하는 주기적 스위칭 구조를 가지고 있습니다. DW1이 완전히 잠길 경우 과거 시계열 데이터가 유실될 위험이 있었습니다.
* **선택 (Main DB 중앙 허브 앵커링)**: 
  - 데이터 크기가 상대적으로 매우 작은 일별 요약(`daily_analytics_summary`, 약 1KB) 데이터를 매일 자정 배치 시 **Main DB에도 동시 UPSERT**하도록 설계했습니다.
  - 신규 DW가 활성화되거나 서버가 기동 될 때(`Pull Sync`), Main DB에 축적된 과거 전체 요약 데이터를 자동으로 복제하여 **1일~31일 전체 방문자 통계가 단 1일의 단절도 없이 완벽한 시계열로 이어지도록 보장**했습니다.

## 3. 핵심 구현 내용 (Solution)

### 세션 및 프록시/관리자 예외 처리 (FastAPI Middleware & Services)
* **세션 쿠키 정책 정비**: 쿠키 만료 시간을 1년에서 `당일 KST 자정까지 남은 초(0~86400초)`로 동적 설정하여, 일 단위로 명확한 DAU 집계가 가능하도록 변경했습니다.
* **프록시 IP 추출 우선순위 적용**: 
  ```python
  # IP 추출 우선순위 체인
  ip = request.headers.get("cf-connecting-ip") or \
       request.headers.get("x-real-ip") or \
       request.headers.get("x-forwarded-for", "").split(",")[0].strip() or \
       request.client.host
  ```
* **관리자 자동 예외 처리 (`admin_ips`)**: 메인 DB에 관리자 IP 테이블을 두고, 어드민 세션 활성화 상태로 일반 페이지에 접근 시 자동으로 IP를 감지·등록하여 방문자 집계에서 영구 제외시켰습니다.

## 4. 엔지니어링 교훈 (Takeaway)

1. **"완벽한 실시간"과 "비용 효율성"의 타협점 찾기**: 
   모든 데이터를 실시간 스트리밍 인프라로 구축하는 것은 과도한 엔지니어링(Over-engineering)일 수 있습니다. 과거 데이터는 정적 마감 테이블로, 오늘 데이터는 온디맨드 쿼리로 처리하는 **하이브리드 아키텍처**만으로도 비즈니스 요구사항을 충분히 만족시킬 수 있었습니다.
2. **제한된 인프라 환경에서의 회복탄력성(Resiliency)**: 
   클라우드 무료 티어의 제약(Compute 한도 소진 등)은 아키텍처 설계를 더 견고하게 만드는 촉매가 됩니다. 핵심 메타데이터를 안정적인 Main DB를 중앙 허브(Bridge)로 삼아 싱크하는 패턴은, 인프라 교체 주기 속에서도 **데이터의 연속성을 100% 보장**하는 강력한 무기가 되었습니다.
