## 1. 배경 및 문제 정의 (Problem)

기존 방문자 분석 시스템은 자정마다 실행되는 배치 작업(Cron)을 통해 `daily_analytics_summary` 테이블에 전일 데이터를 요약 저장하고, 어드민 조회 시 이 요약본을 불러오는 구조였습니다. 

하지만 실제 운영 과정에서 사용자 경험을 해치는 4가지 문제가 수면 위로 떠올랐습니다.

1. **"오늘 방문자가 차트에 안 보여요" (실시간성 부재)**
   * `GET /admin/analytics` API가 오직 어제 이전의 마감 데이터(`daily_analytics_summary`)만 조회하고 있었습니다. 자정 배치 전까지는 오늘 발생한 모든 트래픽이 0으로 표시되는 치명적인 UX 결함이 있었습니다.
2. **영구 세션 쿠키로 인한 DAU 왜곡**
   * 세션 쿠키 만료 기한이 `1년`으로 설정되어 있어, 네트워크(Wi-Fi ↔ LTE)를 변경하거나 브라우저를 재접속해도 동일 세션으로 인식되었습니다. 이로 인해 일간 활성 사용자(DAU) 지표가 제대로 집계되지 않았습니다.
3. **프록시 환경에서의 IP 유실**
   * CDN 및 리버스 프록시 환경에서 `X-Forwarded-For` 등의 헤더 우선순위 처리가 미흡하여, 국가/도시 기반 통계에 `null`이 빈번하게 찍혔습니다.
4. **어드민 사용자의 오염된 트래픽**
   * `/admin/*` 경로만 방문자 집계에서 제외하고 있어, 관리자가 일반 페이지(`/`, `/scan`)를 탐색할 경우 자신의 테스트 트래픽이 그대로 방문자로 집계되었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

### ① 오늘 데이터 실시간 조회: 실시간 스트리밍 vs 하이브리드 조회
* **고민**: 모든 실시간벤트를 Redis에 캐싱하거나 매번 무거운 `analytics_events` 테이블을 Full Scan할 것인가?
* **선택 (하이브리드 아키텍처)**: 
  * 과거 데이터는 성능이 검증된 `daily_analytics_summary`를 그대로 조회합니다.
  * **오늘 날짜**가 포함된 조회 요청에 한해서만 `analytics_events` 테이블에서 직접 `GROUP BY` 연산을 수행하도록 동적 분기 처리를 구현했습니다.
  * *Trade-off*: 약간의 DB 쿼리 부하가 발생하지만, 별도의 Redis 인프라를 구축·운영하는 비용을 아끼면서도 "조회 시점의 정확한 실시간 데이터"라는 비즈니스 요구사항을 완벽히 만족시켰습니다.

### ② 클라우드 무료 티어 제약 극복: DW ↔ Main DB 브릿지 전략
* **고민**: 프로젝트 인프라의 무료 티어 Compute 한도로 인해, 월말마다 데이터웨어하우스(DW1) 한도가 소진되어 DW2로 스위칭(Failover)하고 월초에 복귀(Failback)해야 하는 구조적 한계가 있었습니다. DW 교체 시 기존 분석 데이터의 시계열 단절이 우려되었습니다.
* **선택 (Main DB 중앙 허브 앵커링)**:
  * 트래픽이 적고 영구 보존이 필요한 Main DB를 브릿지(Bridge)로 활용하기로 했습니다.
  * 매일 자정 집계 시, 활성 DW에 생성된 1KB 미만의 일별 요약 데이터를 Main DB에도 동시 UPSERT(`상시 앵커링`)합니다.
  * DW 스위칭이나 서버 기동 시, DW에 부족한 과거 데이터를 Main DB로부터 즉시 복제(Pull Sync)하여 **시계열 단절 없는 100% 데이터 연속성**을 확보했습니다.

## 3. 핵심 구현 내용 (Solution)

### 세션 쿠키 정책 정비
세션 만료 시점을 고정된 1년이 아닌, **'당일 KST 자정'**으로 동적 계산되도록 변경했습니다.
```python
# 당일 자정까지 남은 초(Seconds) 계산
expires_at = get_seconds_until_midnight_kst()
response.set_cookie(key="session_id", value=new_session_id, max_age=expires_at)
```
이를 통해 사용자가 하루에 한 번 앱을 재방문하거나 네트워크를 전환할 경우, 자연스럽게 새로운 세션(`session_started`)으로 기록되어 정확한 DAU 측정이 가능해졌습니다.

### 프록시 환경 IP 추출 우선순위 정립
클라이언트의 진짜 IP를 누락 없이 캡처하기 위해 프록시 헤더 검증 체계를 표준화했습니다.
> **우선순위**: `cf-connecting-ip` (Cloudflare) → `x-real-ip` → `x-forwarded-for` (첫 번째 값) → `request.client.host`

### 관리자 IP 자동 등록 및 트래픽 격리
관리자가 어드민 영역 외의 일반 페이지를 방문하더라도 집계에서 제외되도록 `admin_ips` 테이블을 Main DB에 구축했습니다.
* **자동 등록**: 관리자 토큰(`admin_token`)을 가진 사용자가 접속하면, 현재 접속 IP가 Main DB에 자동  kayıt(등록)되어 별도의 수동 설정 없이도 즉시 집계 대상에서 제외됩니다.
* **DB 파편화 방지**: DW가 교체되더라도 관리자 예외 처리 설정은 Main DB에 안전하게 보존됩니다.

```sql
CREATE TABLE admin_ips (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ip_address VARCHAR(45) NOT NULL UNIQUE,
    label VARCHAR(100),               -- "Daniel 집 맥북", "사무실 공유기" 등
    device_type VARCHAR(30),
    os_name VARCHAR(30),
    registered_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
    last_seen_at TIMESTAMP WITH TIME ZONE,
    is_active BOOLEAN NOT NULL DEFAULT true
);
```

## 4. 엔지니어링 교훈 (Takeaway)

1. **완벽한 아키텍처보다 제약 조건 속의 최적화**: 
   유료 인프라로 즉시 마이그레이션하는 대신, Main DB를 가벼운 브릿지로 활용하는 아이디어(Bridge Pattern)를 통해 비용을 0으로 유지하면서도 인프라 Failover 안정성을 확보했습니다.
2. **비즈니스 지표의 정의는 기술적 제약과 맞닿아 있다**: 
   단순한 "세션 쿠키 만료 시간 변경"이라는 작은 설정 수정이, 프로덕트의 핵심 지표인 DAU의 신뢰도를 결정한다는 것을 다시 한번 깨달았습니다.
3. **UX와 데이터의 타협점 (하이브리드 쿼리)**:
   모든 데이터를 실시간 스트리밍 처리할 필요는 없습니다. "사용자가 조회 버튼을 눌렀을 때만 오늘 데이터를 동적으로 합산한다"는 실용적인 타협(Pragmatic Approach)이 시스템 복잡도를 낮추면서도 훌륭한 사용자 경험을 만들어냈습니다.
