안녕하세요. `PickSafe` 팀의 시니어 에디터입니다. 

서비스를 운영하면서 흔히 마주하는 고민 중 하나는 **"비용을 최적화하면서도 사용자에게 실시간성과 정확성을 제공하는 것"**입니다. 이번 포스팅에서는 최근 방문자 분석 시스템을 전면 개편하면서 마주했던 4가지 치명적인 기술적 문제와, 이를 해결하기 위해 선택한 아키텍처 의사결정 과정을 공유하고자 합니다.

---

## 1. 배경 및 문제 정의 (Problem)

초기 구현된 방문자 분석 시스템은 비용 절감을 위해 배치(Batch) 위주로 설계되었습니다. 하지만 운영 단계에서 다음과 같은 4가지 구조적 한계(Bug & Limitation)가 드러났습니다.

1. **실시간성의 부재**: 어드민에서 오늘 방문자 차트를 보면 항상 0으로 노출되었습니다. `GET /admin/analytics` API가 어제 이전의 마감 데이터(`daily_analytics_summary`)만 바라보고 있었기 때문입니다. 자정 배치가 돌기 전까지는 오늘 데이터를 볼 수 없는 구조였습니다.
2. **무한 세션 문제**: DAU(일간 활성 사용자)를 집계하기 위한 세션 쿠키의 `max_age`가 1년으로 설정되어 있었습니다. 네트워크(Wi-Fi ↔ LTE)를 변경해도 세션이 유지되어 새로운 방문으로 집계되지 않는 치명타가 발생했습니다.
3. **부 정확한 IP 추출**: 프록시/CDN 환경(예: Cloudflare 등)을 거치면서 실제 사용자 IP가 유실되어 국가/도시 지도 통계에 `null`이 빈번하게 찍혔습니다.
4. **관리자 트래픽 오염**: 관리자가 `/admin/*` 경로가 아닌 일반 페이지(`/`, `/scan`)를 탐색할 때도 방문자로 집계되어 정확한 비즈니스 지표를 왜곡했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

### ① 오늘 데이터 처리를 위한 '실시간 하이브리드 집계'
* **대안 A (실시간 스트리밍 도입)**: Kafka나 Redis 등을 도입하여 실시간 이벤트 스트리밍 구성.
  * *Trade-off*: 현재 인프라 규모에 비해 오버엔지니어링이며, 유지보수 비용과 인프라 비용 급증.
* **대안 B (하이브리드 쿼리 라우팅)**: 과거 데이터는 기존처럼 요약 테이블을 조회하고, **오늘 날짜가 포함된 경우에만 원본 이벤트 테이블(`analytics_events`)에서 직접 `GROUP BY` 연산** 수행.
  * *Trade-off*: 원본 테이블 조회로 인한 DB 부하가 발생할 수 있으나, 조회 시점에만 집계하고 인덱스를 최적화하면 충분히 감내 가능한 수준. **(선택)**

### ② 무료 티어 인프라(Compute 한도) 전환 시 데이터 연속성 보장
* **문제**: 클라우드 무료 티어 Compute 한도로 인해 월말에 DW1 소진 시 DW2로 Failover하고, 월초에 Failback하는 구조입니다. DW가 완전히 잠기면 직접 데이터를 마이그레이션할 수 없습니다.
* **해결책 (Main DB를 중앙 브릿지로 활용)**:
  * 1일 1회 자정 배치 시, 활성 DW의 당일 요약 데이터(~1KB)를 **Main DB의 요약 테이블에도 동시 UPSERT(상시 앵커링)**.
  * DW 스위칭 시, Main DB에 축적된 과거 요약 데이터를 새로운 DW로 자동 복제(Pull Sync).
  * *Trade-off*: Main DB에 미미한 쓰기 부하가 추가되지만(0.0001% 미만), DW 인프라가 교체되거나 다운되더라도 **시계열 데이터의 단절이 0%인 완벽한 연속성을 보장**합니다.

## 3. 핵심 해결 방안 (Solution)

### ① 세션 및 IP 추출 정비
* **세션 만료 정책 변경**: 쿠키 유효기간을 1년에서 **'당일 KST 자정까지 남은 초(Seconds)'**로 변경하여 매일 자정을 기준으로 자연스럽게 새로운 세션이 발급되도록 유도했습니다.
* **프록시 IP 우선순위 파싱**: 
  우선순위를 명확히 정의하여 CDN 환경에서도 정확한 클라이언트 IP를 확보하도록 수정했습니다.
  `cf-connecting-ip` → `x-real-ip` → `x-forwarded-for (첫 번째 IP)` → `request.client.host`

### ② 관리자 IP 자동 등록 및 예외 처리 (`admin_ips`)
* 관리자가 어드민 영역에 접근하거나 로그인 세션을 유지한 상태로 일반 페이지를 탐색할 경우, 접속 IP가 Main DB의 `admin_ips` 테이블에 **자동 등록(Auto-Registration)**되도록 구현했습니다.
* 이를 통해 수동으로 설정하는 번거로움을 없애고, 일반 페이지 방문 시 집계 대상에서 원천 배제시켰습니다. 또한 DW가 교체되더라도 관리자 예외 설정이 유실되지 않도록 Main DB에 영구 보관합니다.

```sql
CREATE TABLE admin_ips (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ip_address VARCHAR(45) NOT NULL UNIQUE,
    label VARCHAR(100),               -- "Daniel 집 맥북", "사무실 공유기" 등
    device_type VARCHAR(30),
    os_name VARCHAR(30),
    registered_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
    last_seen_at TIMESTAMP WITH TIME ZONE,
    is_active BOOLEAN NOT NULL DEFAULT true
);
```

## 4. 엔지니어링 교훈 (Takeaway)

1. **상황에 맞는 타협 (Pragmatic Architecture)**: 모든 데이터를 실시간 스트리밍 파이프라인으로 처리할 필요는 없습니다. "조회 버튼을 누를 때만 오늘 데이터를 동적으로 묶어준다"는 하이브리드 접근법만으로도 비용을 아끼면서 사용자 경험(실시간성)을 완벽히 챙길 수 있었습니다.
2. **인프라 제약 속 데이터 연속성 확보**: 서버나 DB 인스턴스가 주기적으로 교체되는 변동성 높은 환경(무료 티어 등)에서는, 휘발성이 적은 **중앙 허브(Main DB)를 활용한 앵커링 전략**이 시스템의 강건성(Resilience)을 크게 높여준다는 것을 다시 한번 체감했습니다.
3. **운영자 관점의 예외 처리 자동화**: 관리자 트래픽 분리 같은 내부 운영 편의 기능은 수동 설정보다 '자동 감지 및 등록' 형태로 설계해야 휴먼 에러를 방지하고 데이터의 신뢰도를 지킬 수 있습니다.

이번 개선을 통해 PickSafe의 방문자 분석 시스템은 인프라 비용을 제로에 가깝게 유지하면서도, 데이터 정확도와 실시간 조회 성능이라는 두 마리 토끼를 모두 잡을 수 있었습니다.
