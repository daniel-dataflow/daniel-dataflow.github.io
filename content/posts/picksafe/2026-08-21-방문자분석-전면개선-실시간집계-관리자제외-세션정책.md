안녕하세요. PickSafe 백엔드 엔지니어입니다.

서비스가 성장함에 따라 프로덕션 환경의 데이터 분석 시스템을 전면 개선할 필요성이 대두되었습니다. 이번 포스팅에서는 운영 중 마주한 4가지 핵심 문제(실시간성 부재, 세션 쿠키 수명 이슈, 프록시 환경의 IP 유실, 어드민 트래픽 오염)를 해결하고, 인프라 비용 절감을 위한 **멀티 DW(Data Warehouse) 환경에서의 데이터 연속성을 보장한 아키텍처 설계 경험**을 공유하려 합니다.

---

## 1. Problem: 운영 환경에서 발견된 4가지 한계

방문자 분석 시스템을 운영하면서 다음과 같은 치명적/중요 버그들이 사용자 경험과 지표의 정확성을 떨어뜨리고 있었습니다.

1. **오늘 방문 데이터가 차트에 보이지 않는 현상 (치명)**
   - 기존 API는 전날 마감된 요약 테이블(`daily_analytics_summary`)만 조회하도록 설계되어 있었습니다. 자정 배치(Cron)가 돌기 전까지는 당일 방문 데이터가 항상 `0`으로 표시되는 문제가 있었습니다.
2. **네트워크 변경(Wi-Fi ↔ LTE) 시 새 방문 미집계 (치명)**
   - 세션 쿠키의 `max_age`가 1년으로 설정되어 있어, 한 번 쿠키를 발급받은 사용자는 사실상 영구 세션으로 인식되었습니다. 이로 인해 DAU(일간 활성 사용자) 집계의 핵심인 `is_new_session` 플래그가 동작하지 않았습니다.
3. **국가/도시 지도 데이터의 `null` 빈발 (중요)**
   - 프록시 및 CDN 환경(Cloudflare 등)에서 원본 클라이언트 IP를 추출할 때 헤더 우선순위(`cf-connecting-ip`, `x-real-ip`) 처리가 누락되어 있었습니다.
4. **관리자 트래픽의 모호한 제외 기준 (중요)**
   - `/admin/*` 경로만 집계에서 제외하고 있어, 관리자가 일반 페이지(`/`, `/scan` 등)를 탐색할 때 운영 데이터가 왜곡되는 현상이 발생했습니다.

## 2. Technical Decisions & Trade-offs

### ① 오늘 데이터 처리를 위한 '하이브리드 조회 전략'
* **대안 A**: 모든 이벤트를 실시간으로 `GROUP BY` 연산
  * *Trade-off*: 데이터가 쌓일수록 관리자 대시보드 조회 속도가 급격히 저하됨.
* **대안 B**: 1분마다 전체 집계 배치 실행
  * *Trade-off*: 불필요한 DB 부하 유발 및 실시간성 확보 실패.
* **선택 (하이브리드)**: 
  * **과거 날짜**: 기존대로 미리 집계된 요약 테이블을 조회하여 응답 속도 최적화.
  * **오늘 날짜**: 원본 이벤트 테이블(`analytics_events`)에서 직접 `GROUP BY` 집계 수행. 응답에 `today_live: true` 플래그를 내려주어 프론트엔드에서 실시간 집계 중임을 명시.

### ② 세션 쿠키 정책 수정 (1년 $\rightarrow$ 당일 자정까지)
DAU 지표의 정확성을 확보하기 위해 쿠키 만료 기한을 **"당일 KST 자정까지 남은 초(Seconds)"**로 동적 계산하도록 변경했습니다. 하루에 한 번은 새로운 세션 쿠키가 발급되도록 유도하여 일별 방문 빈도 추적의 정밀도를 높였습니다.

### ③ 프록시 환경 IP 추출 파이프라인 표준화
CDN 및 로드밸런서 환경을 고려하여 백엔드 미들웨어에서 IP를 추출하는 표준 우선순위를 정립했습니다.
> `cf-connecting-ip` $\rightarrow$ `x-real-ip` $\rightarrow$ `x-forwarded-for` (첫 번째 값) $\rightarrow$ `request.client.host`

### ④ 인프라 제약을 극복하기 위한 'Main DB 중앙 허브(Bridge)' 패턴
PickSafe는 무료 티어 Compute 한도로 인해 월말에 DW1 한도 소진 시 DW2로 전환(Failover)하고, 월초에 DW1로 복귀(Failback)하는 주기적 스위칭 구조를 가집니다. DW가 교체될 때 시계열 데이터가 끊기는 문제를 해결해야 했습니다.

* **결정**: 메인 데이터베이스(`Main DB`)를 중앙 브릿지로 활용하기로 했습니다.
  * **상시 앵커링**: 매일 자정 집계 시, 활성 DW에 적재된 당일 요약 데이터(약 1KB)를 Main DB에도 동시 `UPSERT` 합니다. (Main DB 부하 0.0001% 미만)
  * **Pull Sync (Failover/Failback 자동 복원)**: 새로운 DW가 기동될 때, Main DB에 축적된 전체 요약 데이터를 읽어와 누락된 구간을 즉시 복제합니다.
  * 결과적으로 DW 인프라가 언제 스위칭되더라도 **단 1일의 단절도 없는 완벽한 시계열 통계**를 보장합니다.

## 3. Implementation (FastAPI & SQL)

### 1) 관리자 IP 자동 등록 및 메타데이터 관리 (`Main DB 영구 보관`)
DW가 교체되더라도 관리자 예외 처리가 유실되지 않도록 Main DB에 `admin_ips` 테이블을 두고 단일 관리합니다. 관리자가 어드민 경로에 접근하면 현재 IP가 자동으로 인식 및 등록됩니다.

```sql
CREATE TABLE admin_ips (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ip_address VARCHAR(45) NOT NULL UNIQUE,
    label VARCHAR(100),               -- "개발자 맥북", "사무실 공유기" 등
    device_type VARCHAR(30),
    os_name VARCHAR(30),
    registered_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
    last_seen_at TIMESTAMP WITH TIME ZONE,
    is_active BOOLEAN NOT NULL DEFAULT true
);
```

### 2) 실시간 하이브리드 집계 로직 (Service Layer)
FastAPI 백엔드 서비스 계층에서는 요청된 날짜가 '오늘'인지 판단하여 쿼리 경로를 분기합니다.

```python
async def get_analytics_summary(db: Session, target_date: date):
    if target_date == date.today():
        # 오늘 날짜는 events 테이블에서 실시간 집계
        return query_live_events_from_analytics(db, target_date)
    else:
        # 과거 날짜는 빠른 조회를 위해 미리 마감된 summary 테이블 조회
        return query_daily_summary(db, target_date)
```

## 4. Takeaways & Lessons Learned

1. **비즈니스 지표의 정의는 기술 구현 방식을 결정한다**: 
   - 단순한 '방문자 수' 측정이라도 DAU의 정의(일일 고유 방문자)에 따라 세션 쿠키 만료 정책을 비즈니스 로직에 맞게 재정의해야 함을 배웠습니다.
2. **비용 효율적인 아키텍처와 데이터 연속성의 트레이드오프 극복**: 
   - 클라우드 인프라의 무료 티어 한계(DW 교체 주기)라는 제약 속에서도, 가벼운 메타데이터(1KB 수준의 요약본)를 Main DB에 브릿징하는 패턴을 통해 비용을 아끼면서도 데이터 정합성을 완벽하게 지켜낼 수 있었습니다.
3. **운영자 경험(OX)의 중요성**: 
   - 개발자 본인의 테스트 트래픽이 분석 데이터를 오염시키지 않도록 '관리자 IP 자동 등록 및 제외 시스템'을 구축함으로써, 운영 데이터의 신뢰성을 한층 더 높일 수 있었습니다.
