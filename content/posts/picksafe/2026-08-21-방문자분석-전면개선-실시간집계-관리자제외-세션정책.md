안녕하세요, PickSafe 백엔드 에디터입니다. 
서비스를 운영하면서 마주하는 기술적 난제 중 상당수는 비즈니스 로직 자체의 복잡함보다는 **"인프라의 제약"과 "현실적인 사용자 환경의 변수"** 사이의 괴리에서 발생합니다.

최근 PickSafe의 방문자 분석 시스템을 전면 개선하는 작업을 진행했습니다. 이 과정에서 4가지 핵심적인 버그를 해결하고, **무료 티어 Compute 인프라 환경에서 DB 스위칭(Failover/Failback)을 무중단으로 버텨내는 중앙 허브 아키텍처**를 설계했습니다. 

어떤 문제를 마주했고, 왜 그런 트레이드오프를 선택했는지 공유해 드립니다.

---

## 1. Problem: 운영 중 마주한 4가지 현실적 한계

서비스가 성장하면서 운영 대시보드와 데이터 수집 파이프라인에서 다음과 같은 모순들이 발견되었습니다.

1. **"오늘 방문자가 왜 0명이지?" (실시간 집계의 부재)**
   * 기존 대시보드는 전날 마감된 요약 테이블(`daily_analytics_summary`)만 조회하고 있었습니다. 자정 배치 집계가 돌기 전까지는 오늘 발생한 데이터가 대시보드에 전혀 반영되지 않는 치명적인 UX 결함이 있었습니다.
2. **영구 세션 쿠키로 인한 DAU 왜곡**
   * 세션 쿠키의 만료 기한이 1년으로 설정되어 있어, 한 번 방문한 사용자의 네트워크(Wi-Fi ↔ LTE)가 바뀌어도 새로운 세션으로 인식되지 않았습니다. 일간 활성 사용자(DAU) 지표가 왜곡되는 원인이었습니다.
3. **프록시 환경에서의 IP 유실**
   * CDN이나 리버스 프록시 환경을 거치면서 원본 클라이언트 IP 대신 프록시 서버의 IP가 찍히거나 `null`이 기록되는 현상이 빈번했습니다.
4. **관리자의 '내돈내산' 테스트 트래픽 유입**
   * `/admin/*` 경로 외에 일반 페이지(`/`, `/scan`)를 탐색할 때 관리자의 테스트 트래픽이 그대로 방문자로 집계되어 데이터 신뢰도를 떨어뜨리고 있었습니다.

## 2. Technical Choices & Trade-offs: 아키텍처 의사결정

### ① 실시간 하이브리드 집계 (Hybrid Aggregation)
* **대안 비교**: 
  * *A안: 매 요청마다 전체 이벤트 테이블을 `GROUP BY`* -> 데이터가 쌓일수록 대시보드 조회 속도 저하 (비효율)
  * *B안: 실시간 스트리밍 파이프라인(Kafka, Redis 등) 구축* -> 현재 규모 대비 오버엔지니어링
* **선택 (Hybrid)**: 과거 데이터는 기존대로 빠른 요약 테이블을 조회하고, **'오늘' 날짜가 포함된 조회 요청에 한해서만 이벤트 테이블에서 직접 `GROUP BY` 집계**하여 합산하기로 했습니다. "자동 실시간 폴링"이 아닌 "조회 버튼을 누를 때 최신 데이터를 보장"하는 방식으로 서버 부하와 데이터 정확성의 균형을 맞췄습니다.

### ② Main DB를 활용한 '중앙 허브 앵커링' (DW Failover 대응)
* **문제 상황**: 무료 티어 Compute 한도로 인해 월말에 DW1 한도 소진 시 DW2로 전환(Failover)하고, 월초에 복귀(Failback)하는 주기적 스위칭이 발생합니다. DW1이 잠기면 직접 데이터를 가져올 수 없습니다.
* **아키텍처 결정**: 
  * 데이터 크기가 작고 핵심 메타데이터인 관리자 IP 목록(`admin_ips`)과 일별 요약 데이터는 **Main DB를 중앙 허브(Bridge)로 활용해 영구 보관**합니다.
  * **상시 앵커링**: 매일 자정 집계 시, 활성 DW DB의 1KB짜리 일별 요약 데이터를 Main DB에도 동시 `UPSERT` 합니다. (부하 0.0001% 미만)
  * **Pull Sync**: DW 스위칭이 발생할 때 신규 DW는 Main DB로부터 누락된 과거 데이터를 0.1초 만에 복제(Pull)해 옵니다.

```
[Client] ---> (요청) ---> [FastAPI Backend]
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
     [Main DB (Central Bridge)]       [DW DB (DW1 <-> DW2 Switching)]
     - 관리자 IP 목록 영구 보관           - 상세 이벤트 수집 (`analytics_events`)
     - 일별 요약 상시 앵커링 (1KB)        - 대용량 트래픽 처리
```

## 3. Implementation Highlights

### 프록시 IP 추출 우선순위 파이프라인
CDN 및 프록시 환경에서 클라이언트의 진짜 IP를 안정적으로 잡아내기 위해 명확한 Fallback 체인을 구성했습니다.
* 우선순위: `cf-connecting-ip` (Cloudflare) → `x-real-ip` → `x-forwarded-for` (첫 번째 IP) → `request.client.host`

### 관리자 IP 자동 등록 (Auto-Registration)
관리자가 어드민 세션을 유지한 채 일반 페이지를 탐색할 때, 현재 접속 IP가 Main DB의 `admin_ips`에 자동으로 등록되도록 구현했습니다. 이를 통해 수동으로 설정하는 번거로움을 없애고, 테스트 트래픽을 원천적으로 차단했습니다.

```sql
CREATE TABLE admin_ips (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ip_address VARCHAR(45) NOT NULL UNIQUE,
    label VARCHAR(100),               -- "Daniel 집 맥북" 등
    device_type VARCHAR(30),
    os_name VARCHAR(30),
    registered_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
    last_seen_at TIMESTAMP WITH TIME ZONE,
    is_active BOOLEAN NOT NULL DEFAULT true
);
```

## 4. Takeaways & Lessons Learned

1. **완벽한 자동화보다 '실용적인 타협점'이 중요하다**
   * 실시간 데이터를 보여주기 위해 웹소켓이나 복잡한 스트리밍 인프라를 구축하는 대신, "오늘 데이터만 동적 집계"하는 하이브리드 방식을 택함으로써 적은 리소스로 비즈니스 요구사항을 완벽히 해결했습니다.
2. **인프라 제약은 아키텍처의 제약이 될 수 없다 (중앙 허브 패턴)**
   * 무료 티어의 한계라는 물리적 제약을 Main DB 브랜칭(중앙 허브 앵커링) 패턴으로 우회하여, DW가 언제든 교체되더라도 시계열 데이터가 단 1일의 끊김도 없이 이어지도록 강건한 구조를 완성했습니다.

작은 기능 개선처럼 보이지만, 인프라의 한계를 이해하고 이를 소프트웨어 아키텍처로 극복해낸 훌륭한 엔지니어링 사례였습니다. 앞으로도 PickSafe는 견고하고 효율적인 시스템을 만들기 위해 치열하게 고민하겠습니다.
