안녕하세요, PickSafe 백엔드 개발자입니다. 
서비스를 운영하면서 마주치는 문제 중 가장 까다로운 것 중 하나는 **"비즈니스 지표의 정확성"**과 **"제한된 인프라 리소스"** 사이의 줄다리기입니다.

최근 당사 방문자 분석 시스템에서 실시간 데이터 누락, 세션 만료 정책의 허점, 그리고 인프라 비용 절감을 위해 도입한 다중 데이터웨어하우스(DW) 환경에서 발생하는 데이터 단절 문제를 동시에 해결했습니다. 

이번 포스팅에서는 이 문제를 해결하기 위해 어떤 기술적 고민을 했고, 어떤 아키텍처를 선택했는지 공유해 드립니다.

---

## 1. 문제 정의 (Problem): 무엇이 잘못되었는가?

기존 방문자 분석 시스템은 비용 절감을 위해 일일 배치(Batch) 집계 위주로 설계되어 있었습니다. 하지만 이로 인해 프로덕션 환경에서 다음과 같은 치명적인 한계가 드러났습니다.

1. **오늘 방문 데이터의 증발 (실시간성 부재):** 
   대시보드가 전날 마감된 요약 테이블(`daily_analytics_summary`)만 조회하도록 구현되어 있어, 자정 배치 전까지는 오늘 발생한 방문 데이터가 통계에 전혀 반영되지 않는 문제가 있었습니다.
2. **영구 세션으로 인한 DAU 왜곡:** 
   세션 쿠키 만료 기한이 1년으로 설정되어 있어, 네트워크(Wi-Fi/LTE)를 변경하거나 브라우저를 재접속해도 기존 세션이 유지되었습니다. 이로 인해 신규 세션 이벤트(`is_new_session`)가 발생하지 않아 일간 활성 사용자(DAU) 지표가 왜곡되었습니다.
3. **관리자 트래픽의 오염:** 
   `/admin/*` 경로만 집계에서 제외하고 있었기 때문에, 관리자가 서비스 메인 화면이나 일반 페이지를 탐색할 경우 운영 테스트 트래픽이 그대로 방문자로 집계되었습니다.
4. **인프라 Failover 시 데이터 단절 (DW1 ↔ DW2 스위칭):** 
   클라우드 무료 티어의 Compute 한도 이슈로 인해 월말에는 DW1에서 DW2로 전환하고, 월초에 다시 복귀하는 구조였습니다. 이 과정에서 DW 간 데이터 동기화가 원활하지 않으면 시계열 그래프가 끊기는 현상이 발생했습니다.

## 2. 기술적 고민과 아키텍처 대안 비교 (Trade-off)

### 고민 1: 실시간 집계 vs 배치 성능
* **대안 A (전면 실시간화):** 모든 조회 요청마다 `analytics_events` 테이블을 실시간으로 `GROUP BY` 연산.
  * *Pros:* 언제나 완벽한 실시간 데이터 보장.
  * *Cons:* 트래픽이 몰릴 경우 DB 부하 급증 및 응답 속도 저하.
* **대안 B (하이브리드 캐싱 및 조건부 실시간 집계 - 선택):** 과거 데이터는 기존처럼 배치 요약본을 사용하고, **'오늘' 날짜가 포함된 조회에만** 동적으로 이벤트를 실시간 집계.
  * *Pros:* 과거 대용량 데이터 조회 성능은 유지하면서, 운영자가 가장 궁금해하는 '오늘의 지표'를 즉시 확인 가능.

### 고민 2: 관리자 IP 예외 처리의 저장소 위치
* **대안 C (임시 캐시/Redis 저장):** 관리자 IP 목록을 캐시에 저장.
  * *Pros:* 빠른 조회 속도.
  * *Cons:* 인프라 스위칭이나 캐시 유실 시 설정이 날아갈 위험 존재.
* **대안 D (Main DB 영구 보관 및 자동 앵커링 - 선택):** 관리자 메타데이터 성격이므로 데이터 크기가 매우 작음(`admin_ips`). DW가 교체되더라도 유실되지 않도록 **Main DB(`SessionLocal`)에 영구 보관**.
  * *Pros:* 인프라 Failover와 무관하게 예외 설정의 영속성 보장. 미들웨어와 CRUD API 모두에서 단일 소스로 일관되게 관리 가능.

### 고민 3: 멀티 DW 환경에서의 데이터 연속성 보장 (Bridge 패턴)
* 무료 티어 한도로 인한 주기적인 DW 스위칭 환경에서, **Main DB를 '중앙 허브(브릿지)'**로 활용하기로 결정했습니다.
  - **상시 앵커링:** 매일 자정 배치 시, 활성 DW에 적재된 1KB 미만의 일별 요약 데이터를 Main DB에도 동시 UPSERT (부하 0.0001% 미만).
  - **Pull Sync:** DW2로 전환되거나 서버가 기동될 때, Main DB에 축적된 과거 요약 데이터를 새로운 DW로 즉시 복제하여 시계열 데이터의 단절을 원천 차단.

## 3. 핵심 해결 및 구현 (Solution)

### ① 하이브리드 실시간 조회 (FastAPI)
`GET /admin/analytics` 엔프포인트에서 조회 기간에 '오늘'이 포함되어 있는지 검사하고, 오늘 날짜에 한해서만 `analytics_events` 테이블을 직접 집계하여 기존 요약 데이터와 병합(`today_live: true` 플래그 포함)하도록 구현했습니다.

### ② 세션 쿠키 만료 정책 개선
DAU의 정확한 측정을 위해 쿠키 만료 기한을 1년에서 **'당일 KST 자정까지 남은 초(Seconds)'**로 변경했습니다. 하루에 한 번은 세션이 새롭게 갱신되도록 유도하여 일별 활성 방문자 추적이 가능해졌습니다.

### ③ 자동 등록을 지원하는 관리자 IP 예외 처리
관리자가 어드민 영역에 접속하거나 세션을 유지한 채 일반 페이지를 탐색할 경우, 미들웨어에서 접속 IP를 감지하여 Main DB `admin_ips` 테이블에 자동으로 등록(`Auto-Registration`)되도록 처리했습니다. 이를 통해 수동으로 설정하는 번거로움을 없애고 일반 방문자 집계 오염을 원천 차단했습니다.

## 4. 엔지니어링 교훈 (Takeaway)

1. **완벽한 실시간보다 '비즈니스 목적에 맞는' 타협점이 중요하다:**
   모든 데이터를 실시간으로 처리하는 것은 비용과 성능 낭비일 수 있습니다. "과거는 통계 마감, 오늘은 실시간"이라는 하이브리드 접근법은 리소스를 아끼면서도 UX를 만족시키는 좋은 대안이 됩니다.
2. **제한된 인프라 환경에서의 설계 패턴:**
   무료 티어나 리소스 제약이 있는 환경(멀티 DW 전환 등)에서는 단일 장애점이나 스위칭 공백을 메워줄 수 있는 **중앙 허브(Bridge) 성격의 영구 저장소**를 두는 것이 시스템 안정성에 큰 도움이 됩니다.
3. **운영자 관점의 UX (Dogfooding):**
   개발자 편의를 위한 예외 처리(시크릿 모드 강제 등)보다, 시스템이 스스로 관리자 IP를 인식하고 예외 처리하게 만드는 자동화가 운영 페인포인트를 극적으로 줄여준다는 것을 배웠습니다.
