안녕하세요, PickSafe 백엔드/인프라 에디터입니다. 
최근 우리는 AI 모델(Gemini 등)의 멀티 키 로드밸런싱을 운영하는 과정에서 마주한 **프론트엔드-백엔드 간 데이터 불일치**, **쿼터 정합성 유실**, 그리고 **UI 파편화** 문제를 해결하기 위해 대대적인 아키텍처 개선 작업을 진행했습니다.

이번 포스팅에서는 다수의 AI 모델을 유연하게 관리하면서도, 쿼터 추적의 정확도를 높이고 UI 일관성을 확보하기 위해 어떤 기술적 고민과 대안을 거쳤는지 공유해 드립니다.

---

## 1. Problem: 마주했던 기술적 난제들

서비스 내에서 OCR 성능 테스트, 대시보드, 번역 관리, 인프라 모니터링 등 다양한 도메인에서 Gemini API를 호출하고 모니터링하고 있습니다. 하지만 서비스가 확장됨에 따라 다음과 같은 구조적 한계(Technical Debt)가 드러났습니다.

### ① 설정의 파편화와 하드코딩 (Single Source of Truth 부재)
모델 목록, RPD(일일 한도), RPM(분당 한도), 그리고 UI에서 사용되는 고유 색상이 프론트엔드 스크립트 파일 여러 곳에 하드코딩되어 있었습니다. 새로운 모델이 추가되거나 기존 모델의 스펙이 변경될 때마다 프론트엔드와 백엔드의 코드를 동시에 수정해야 하는 유지보수 병목이 발생했습니다.

### ② 쿼터 차감의 정합성 문제 (False Deduction)
외부 API 호출 과정에서 네트워크 타임아웃이나 서버 에러가 발생했음에도 불구하고, 요청 시작 단계에서 무조건 로컬 쿼터(RPD/RPM)를 선차감(Pre-deduction)해 버리는 구조였습니다. 이로 인해 **실제 사용량과 시스템이 추적하는 남은 쿼터량 간의 오차**가 발생했습니다.

### ③ 비동기 레이스 콘디션(Race Condition)과 UI 통일성 저하
- `translations.js` 등 일부 페이지에서 언어 설정(`loadLocaleSettings`)이 비동기로 로드되는 도중 렌더링이 먼저 트리거되어 빈 화면이 노출되는 간헐적 버그가 있었습니다.
- 페이지마다 모델 렌더링 순서와 색상이 제각각이었고, 인프라 쿼터 카드 레이아웃이 반응형에 따라 3개-1개 등으로 무작위 배치되어 시각적 안정감을 해치고 있었습니다.

## 2. Trade-offs & Decisions: 어떻게 해결할 것인가?

### A. 백엔드 중심의 단일 진실 소스(SSOT) 구축과 동적 환경 설정
설정의 파편화 문제를 해결하기 위해 **"설정의 소유권을 어디에 둘 것인가?"**에 대한 논의가 있었습니다.

* **대안 1: 프론트엔드 전역 설정 파일(.json / .js) 도입**
  * *장점*: 프론트엔드 단독 수정 및 배포 용이
  * *단점*: 백엔드의 실제 API 로드밸런싱 로직(`quota_service.py`)과 동기화가 깨질 위험 상존
* **대안 2: 백엔드 `quota_service.py`를 단일 진실 소스로 지정하고 메타데이터 API화** (선택)
  * *장점*: 백엔드가 관리하는 실제 사용 가능한 모델 및 쿼터 정책과 프론트엔드 UI가 100% 동기화됨. 소스 코드 수정 없이 `.env` 및 환경 변수(`GEMINI_MODELS_CONFIG`)만으로 동적 제어 가능.

우리는 **대안 2**를 선택했습니다. 백엔드가 `models_meta` 형태로 모델 스펙과 시그니처 색상을 내려주면, 프론트엔드는 이를 기반으로 동적 렌더링(Dynamic Rendering)하도록 구조를 변경했습니다.

> **🎨 디자인 시스템 적용 (Gemini 그라데이션 그레이디언트 차용)**
> - Gemini 3.5 Flash-Lite (메인): `#2563eb` (딥 블루)
> - Gemini 3.5 Flash: `#9333ea` (퍼플)
> - Gemini 3.6 Flash: `#ec4899` (핑크)
> - Gemini 3.1 Flash-Lite (백업): `#f59e0b` (오렌지)
> - *Note*: 타사 모델(예: 네이버 클로바)과의 시각적 구분을 위해 네이버 그린(`#059669`)을 할당하여 인지 부하를 줄였습니다.

### B. 트랜잭션 개념을 차용한 '쿼터 롤백(Rollback) 로직' 도입
실제 API 통신 실패 시 쿼터가 차감되는 문제를 해결하기 위해, 예외 처리(Exception Handling) 블록을 확장했습니다. 
API 호출 실패 응답이나 타임아웃 감지 시, 이미 메모리/DB상에 차감되었던 RPD와 RPM 수치를 원상 복구하는 롤백 함수를 호출하도록 방어로직(Defensive Logic)을 추가하여 실사용량 계산의 정확도를 극대화했습니다.

### C. 비동기 처리 및 레이아웃 그리드 고정
- **Async/Await 보장**: `DOMContentLoaded` 이벤트 리스너 내부에서 언어 설정 의존성을 완전히 해결할 때까지(`await loadLocaleSettings()`) 렌더링 프로세스를 블로킹하도록 비동기 흐름을 정돈했습니다.
- **CSS Grid 표준화**: 유연성만 강조하다 깨지던 인프라 쿼터 컨테이너를 `grid-template-columns: repeat(2, 1fr)`로 고정하여, 모든 뷰포트에서 안정적인 2x2 카드 레이아웃을 유지하도록 개선했습니다.

## 3. Takeaways & Results

이번 개선을 통해 얻은 엔지니어링 교훈은 명확합니다.

1. **중앙집권적 설정 관리의 힘**: 설정 데이터를 백엔드 단일 소스로 모으고 동적 환경 변수와 결합하자, 향후 새로운 AI 모델(예: Gemini 3.7 등)이 출시되더라도 백엔드 설정 배열 단 1줄만 수정하면 전체 시스템과 UI가 자동으로 동기화되는 확장성을 확보했습니다.
2. **분산 환경 및 외부 API 연동 시 '보상 트랜잭션'의 중요성**: 외부 의존성이 있는 작업(API 호출)에서는 실패 시의 상태 복구(Rollback) 메커니즘이 데이터 정합성 유지의 핵심임을 다시 한번 확인했습니다.
3. **사용자 경험(UX)과 일관성**: 철저한 비동기 처리 제어와 디자인 시스템(색상/그리드)의 통일은 제품의 완성도를 높이는 가장 기본적이면서도 강력한 방법입니다.

앞으로도 PickSafe 팀은 견고하고 확장 가능한 아키텍처를 바탕으로 안정적인 AI 인프라 서비스를 만들어 나가겠습니다. 읽어주셔서 감사합니다!
