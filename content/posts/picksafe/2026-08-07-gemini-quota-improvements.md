## 1. 들어가며 (Problem Statement)

LLM(대형 언어 모델)을 프로덕션 서비스에 연동할 때 직면하는 가장 큰 과제 중 하나는 **API 호출 쿼터(Quota)의 효율적 관리**와 **급변하는 모델 생태계에 대한 유연한 대응**입니다.

PickSafe 서비스는 여러 버전의 LLM 모델을 동시에 운용하며, 멀티 API 키 로드밸런싱을 통해 트래픽을 분산 처리하고 있습니다. 그러나 서비스 규모가 확장됨에 따라 다음과 같은 기술적 부채가 누적되었습니다:

1. **메타데이터 파편화로 인한 동기화 문제**:
   OCR 벤치마크, 인프라 모니터링, 번역 관리 등 여러 클라이언트 화면에 모델 식별자, UI 시각화 테마(Color/Order), 쿼터 임계치(RPD/RPM)가 하드코딩되어 있었습니다. 새로운 모델이 추가될 때마다 백엔드뿐만 아니라 다수의 프론트엔드 스크립트를 일일이 수정 및 배포해야 하는 높은 결합도(High Coupling) 문제가 발생했습니다.
2. **네트워크 장애 시 쿼터 데이터 정합성 왜곡**:
   상위 API 제공자의 일시적 타임아웃이나 5xx 오류 발생 시에도 사전 차감된 쿼터가 복구되지 않아, 실제 잔여 쿼터와 시스템이 인지하는 쿼터 간의 오차가 누적되는 문제가 존재했습니다.
3. **비동기 렌더링 시점의 Race Condition**:
   국제화(i18n) 설정 및 메타데이터 로드 시점과 데이터 렌더링 시점의 불일치로 인해 간헐적으로 대시보드 컴포넌트가 빈 화면으로 출력되는 렌더링 병목이 있었습니다.

본 포스팅에서는 **단일 진실 공급원(Single Source of Truth, SSOT)** 패턴을 통한 메타데이터 중앙화, **보상 트랜잭션 기반의 쿼터 롤백 메커니즘**, 그리고 **비동기 렌더링 파이프라인 최적화**를 통해 이 문제들을 어떻게 해결했는지 공유합니다.

## 2. 기술적 고민과 아키텍처 트레이드오프

### 메타데이터 관리: 코드 기반 vs 동적 설정 주입

| 비교 항목 | 클라이언트/서버 코드 하드코딩 (기존) | DB 기반 동적 관리 | 환경 변수 및 설정 기반 SSOT (채택) |
| :--- | :--- | :--- | :--- |
| **유연성** | 매우 낮음 (수정 시 재빌드/배포 필수) | 높음 (실시간 변경 가능) | 높음 (무중단 핫리로드 또는 재기동으로 반영) |
| **운영 복잡도** | 낮음 (단순 구현) | 높음 (DB 스키마 관리 및 캐싱 전략 필요) | 낮음 (인프라 설정 레벨에서 단일 제어) |
| **정합성 보장** | 다중 컴포넌트 간 파편화 발생 | 쿼리 지연 및 동기화 오버헤드 | **백엔드가 메타데이터를 클라이언트에 단방향 공급** |

- **결정**: DB 모델을 별도로 설계하는 것은 모델 메타데이터의 변경 빈도 대비 인프라 복잡도를 과도하게 증가시킵니다. 따라서 백엔드 환경 설정(`Config`)을 **단일 진실 공급원(SSOT)**으로 삼고, 백엔드 서비스 계층에서 유효성 검증을 거친 `ModelMeta` 객체를 프론트엔드에 단방향 주입(Hydration)하는 방식을 채택했습니다.

## 3. 핵심 해결 전략 및 구현

### 3.1. SSOT 기반 동적 메타데이터 공급 파이프라인 구축

모델의 식별자, 시각화 색상 코드, 속도 제한(RPM/RPD), 우선순위 메타데이터를 백엔드 쿼터 관리 레이어에서 일원화했습니다.

```
[인프라 환경 변수 (Config)]
           │
           ▼
[Quota Service (SSOT)] ──── (Model Metadata 단방향 주입) ────► [다중 클라이언트 UI]
  - Gemini 3.5 Flash-Lite (#2563eb)                              - OCR Dashboard
  - Gemini 3.5 Flash      (#9333ea)                              - Infra Monitoring
  - Gemini 3.6 Flash      (#ec4899)                              - Translation Manager
  - Gemini 3.1 Flash-Lite (#f59e0b)
```

이제 새로운 LLM 버전이 릴리즈되더라도 프론트엔드 소스 코드 수정 없이, 백엔드 환경 설정 수정만으로 모든 모니터링 뷰 및 기능 셀렉터에 즉시 반영됩니다.

### 3.2. 쿼터 롤백(Rollback)을 통한 정합성 보장

API 호출 흐름에서 사전 차감(Optimistic Deduction) 방식을 유지하되, 업스트림 서버 오류나 네트워크 타임아웃 시 **보상 트랜잭션(Compensating Action)**이 동작하도록 쿼터 매니저를 개선했습니다.

```python
# 개념적 의사 코드 (Conceptual Implementation)
class QuotaManager:
    async def execute_with_quota(self, model_key: str, request_fn):
        # 1. 분당/일일 쿼터 사전 차감 (Optimistic Deduction)
        await self.deduct_quota(model_key)
        
        try:
            response = await request_fn()
            return response
        except (UpstreamTimeoutException, UpstreamServerErrorException) as ex:
            # 2. 업스트림 장애 발생 시 즉시 쿼터 롤백 (Compensating Rollback)
            await self.rollback_quota(model_key)
            logger.warn(f"Quota rolled back for {model_key} due to upstream failure.")
            raise ex
```

이 메커니즘을 통해 멀티 키 로드밸런싱 풀에서 유효 쿼터가 과소평가되어 사용 가능한 리소스가 조기에 차단되는 문제를 원천 차단했습니다.

### 3.3. 비동기 렌더링 Race Condition 및 UI Grid 안정화

클라이언트 사이드에서 비동기 데이터 의존성이 꼬여 화면이 깨지거나 빈 테이블이 노출되는 현상을 해결하기 위해 렌더링 라이프사이클을 동기화했습니다.

1. **Promise 의존성 체이닝**: 메타데이터 및 i18n 리소스 수신이 완료된 이후에만 종속 뷰 컴포넌트가 마운트되도록 `await` 기반 동기화 파이프라인을 확립했습니다.
2. **레이아웃 반응형 Grid 고정**: 모니터링 카드가 뷰포트에 따라 불규칙하게 배치되던 문제를 `repeat(2, 1fr)` 기반의 2x2 고정 그리드 시스템으로 재설계하여 정보 밀도와 시각적 안정성을 높였습니다.

## 4. 엔지니어링 성과 및 배운 점 (Key Takeaways)

1. **운영 비용(Toil)의 획기적 절감**:
   모델 추가 및 메타데이터 변경 시 소요되던 작업 단위가 `프론트/백엔드 동시 수정 및 배포(수십 분)`에서 `설정값 갱신(수 초)`으로 단축되었습니다.
2. **분산 리소스 추적의 신뢰도 향상**:
   API 장애 상황에서도 쿼터 실사용량과 로컬 트래커의 오차가 발생하지 않도록 방어 로직을 완성함으로써, 외부 API 비용을 정확히 통제할 수 있게 되었습니다.
3. **UI 일관성과 개발 생산성의 결합**:
   단순히 화면을 통일하는 것을 넘어, 백엔드의 데이터 모델이 프론트엔드의 렌더링 스키마를 주도하는 구조를 설계하여 다중 화면 유지보수에 따르는 인지 부하를 크게 낮췄습니다.

앞으로도 PickSafe 팀은 시스템의 확장성과 데이터 정합성을 타협하지 않는 견고한 엔지니어링 표준을 만들어 나갈 것입니다.
