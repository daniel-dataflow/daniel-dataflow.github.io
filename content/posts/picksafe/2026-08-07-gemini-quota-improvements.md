안녕하세요. PickSafe 팀의 백엔드 엔지니어입니다.

최근 우리 서비스에서 사용하는 LLM API(Gemini) 호출량이 급증하면서, 운영 효율성과 데이터 정합성 측면에서 몇 가지 기술적 부채를 마주하게 되었습니다. 이번 글에서는 파편화된 프론트엔드 환경 설정을 백엔드 주도로 통합하고, API 오류 상황에서의 쿼터 신뢰성을 높이기 위해 고민했던 과정을 공유합니다.

---

### 1. 문제 정의: 파편화된 설정과 데이터 불일치
우리 서비스는 OCR, 번역, 인프라 모니터링 등 다양한 기능에서 제미나이 API를 사용 중입니다. 그러나 다음과 같은 문제들이 시스템의 발목을 잡고 있었습니다.

1.  **하드코딩된 설정**: 모델 목록과 색상 정보가 여러 프론트엔드 파일(`ocr.js`, `translations.js` 등)에 파편화되어 있어, 모델 업데이트 시마다 전체 코드를 수정해야 했습니다.
2.  **쿼터 신뢰성 부족**: API 호출 실패(타임아웃, 서버 오류) 시에도 쿼터가 차감되어, 실제 가용 리소스와 기록된 사용량 간의 간극이 벌어졌습니다.
3.  **UI 레이아웃 및 렌더링 결함**: 비동기 로딩 타이밍(Race Condition)으로 인한 번역 화면의 빈 공간 노출, 그리고 페이지별로 제각각인 카드 배치 방식이 사용자 경험을 저해하고 있었습니다.

---

### 2. 기술적 고민과 대안 비교

#### A. 단일 진실 소스(Single Source of Truth) 확보
**고민**: 설정을 백엔드에서 내려줄 것인가, 아니면 공유 환경 설정 파일(JSON)을 별도로 둘 것인가?
*   **선택**: **백엔드 주도 관리(환경 변수 + API 응답)**
*   **이유**: `quota_service.py`를 중앙 제어 센터로 설정했습니다. `.env` 파일을 통해 시스템 관리자가 소스 코드 수정 없이 모델명, 한도(RPD/RPM), 브랜드 컬러를 동적으로 배포할 수 있도록 구성했습니다. 프론트엔드는 런타임에 이 `models_meta`를 수신하여 렌더링합니다. 이 방식은 모델 추가 시 배포 사이클을 최소화할 수 있는 강력한 장점이 있습니다.

#### B. 쿼터 롤백(Rollback) 로직
**고민**: 단순 호출 시 차감하는 방식은 정합성을 깨뜨립니다. 어떻게 보장할 것인가?
*   **선택**: **예외 처리 기반 롤백 메커니즘**
*   **해결**: API 응답이 성공(200 OK)하지 못한 경우, 호출 전 로컬 로직에서 수행했던 RPD/RPM 차감 연산을 `except` 블록 내에서 즉각 원상 복구하도록 트랜잭션 개념의 로직을 적용했습니다. 이를 통해 API의 불안정성이 데이터 통계에 미치는 영향을 차단했습니다.

#### C. 비동기 데이터 렌더링 최적화
**고민**: `DOMContentLoaded`와 데이터 비동기 로딩 사이의 Race Condition 해결.
*   **선택**: `async/await` 동기화 및 `grid-template-columns` 기반의 고정 레이아웃
*   **해결**: 언어 설정이 완전히 로드된 후 화면을 그리는 명시적 `await` 처리를 통해 빈 화면 문제를 해결하고, 레이아웃의 유동성 대신 `grid` 기반의 일관된 2x2 컨테이너 레이아웃을 도입하여 시각적 통일성을 극대화했습니다.

### 3. 엔지니어링 교훈 (Takeaway)

이번 개선 작업을 통해 두 가지 중요한 교훈을 얻었습니다.

1.  **설정의 중앙화는 유지보수 비용을 기하급수적으로 줄인다**: '설정값'을 코드에서 분리하여 서버 관리자가 변경할 수 있게 만드는 것만으로도, 개발자는 비즈니스 로직 구현에 더 집중할 수 있는 환경이 조성되었습니다.
2.  **방어적 프로그래밍의 중요성**: 특히 외부 API를 연동할 때는 "성공할 것"이라는 가정보다는 "실패했을 때 어떻게 상태를 원복할 것인가"라는 질문이 데이터 정합성을 결정짓는 핵심임을 다시금 확인했습니다.

앞으로도 사용자에게는 통일된 경험을, 개발자에게는 효율적인 유지보수 환경을 제공하는 아키텍처를 고민해 나가겠습니다. 관련해서 궁금한 점은 댓글로 남겨주세요!
