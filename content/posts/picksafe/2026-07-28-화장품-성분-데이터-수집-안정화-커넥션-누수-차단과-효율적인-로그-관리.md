화장품 성분 분석 서비스 PickSafe를 개발하며 가장 먼저 해결해야 했던 과제 중 하나는 식약처 공공데이터 포털로부터 수만 건의 국내 화장품 전성분 데이터를 안정적으로 동기화하는 작업이었습니다.

초기 구현에서는 단순히 외부 API를 호출하여 DB에 적재하는 단순 반복문으로 시작했습니다. 하지만 데이터 수집량이 3만 건을 넘어가면서, 제한된 서버 인프라 환경에서 예상치 못한 운영 이슈들이 하나둘 드러나기 시작했습니다. 수집 과정에서 마주쳤던 병목과 이를 다듬어 나간 기록을 정리했습니다.

---

## 1. 🎯 마주한 고민과 문제 배경

배치(Batch) 동기화 작업을 수행하면서 발견된 문제는 크게 세 가지였습니다.

### 1) 무제한 로그 누적으로 인한 디스크 용량 위협
데이터 수집 중 발생하는 상세 디버그 로그가 단일 로그 파일에 무제한으로 누적되었습니다. 수만 건의 API 요청과 응답, 파싱 과정을 기록하다 보니 단 한 번의 전체 수집만으로도 로그 파일 크기가 수백 MB 단위로 불어났습니다. 디스크 사용량이 점진적으로 증가하여 서버 안정성을 위협하는 구조였습니다.

### 2) 간헐적 네트워크 타임아웃과 DB 커넥션 누수
외부 API 통신 중 간헐적인 네트워크 지연이나 타임아웃(Timeout)이 발생할 때, 예외 처리가 매끄럽지 못해 DB 세션이 정상적으로 반환되지 않는 문제가 있었습니다. 결과적으로 DB 커넥션이 `idle in transaction` 상태로 계속 남아 커넥션 풀(Connection Pool)이 고갈되는 현상이 발생했습니다.

### 3) 실시간 로그 모니터링 시 CPU/메모리 스파이크
관리자 화면에서 수집 진행 상황을 확인하기 위해 로그 파일에 대한 실시간 폴링(Polling) 요청을 보낼 때, 백엔드에서 전체 대용량 로그 파일을 매번 메모리에 통째로 올려 읽어오는 방식으로 구현되어 있었습니다. 이로 인해 어드민 조회 시점에 서버 메모리 점유율과 CPU 사용량이 급격히 치솟았습니다.

## 2. ⚖️ 기술적 대안 비교 및 선택 이유

문제를 해결하기 위해 인프라를 확장하기보다는, 현재 주어진 리소스 안에서 애플리케이션 구조를 정돈하는 방식을 우선 검토했습니다.

### 로그 관리 방식: 외부 로그 솔루션(ELK/Loki) vs RotatingFileHandler + Tail 읽기
- **외부 로그 스택 도입**: 중앙 집중식 로그 관리가 가능하지만, 현재 단일 서비스 인프라 규모 대비 운영 오버헤드가 크고 별도의 메모리 리소스를 상시 점유한다는 단점이 있었습니다.
- **Python 표준 `RotatingFileHandler` + Tail 읽기**: 추가적인 외부 시스템 없이 파일 단위의 크기 제한(5MB)과 백업 개수(3개)를 강제할 수 있습니다. 또한 어드민 조회 시 파일 전체가 아닌 마지막 N 줄(Tail)만 읽어오도록 개선하면 인메모리 부하를 완전히 없앨 수 있다고 판단했습니다.

### 커넥션 누수 방어: DB 설정 단순 조정 vs Safe Teardown 컨텍스트 패턴
- **DB 서버의 Timeout 설정 단축**: DB 차원에서 고사시킨 연결을 강제 끊기 방식은 애플리케이션 측에서 예측하지 못한 트랜잭션 유실을 야기할 수 있었습니다.
- **애플리케이션 내 Safe Teardown 명시**: 수집 단위마다 `try ... except ... finally` 구조를 보장하고, 외부 API 요청 시 10초 타임아웃과 지수 백오프(Exponential Backoff) 재시도를 적용하여 예외 상황에서도 세션이 확실히 반환되도록 코드를 재구성했습니다.

### 데이터 적재 방식: 운영 테이블 직접 적재 vs DW/수집 전용 보조 테이블 분리
- 수집 및 로그 기록용 데이터를 메인 서비스 운영 테이블(`staging_raw_ingredients`)과 이중화 분리하여, 배치 작업 수행 시 메인 비즈니스 쿼리의 락(Lock) 대기 현상을 차단하기로 결정했습니다.

## 4. 💻 핵심 구현 및 트러블슈팅

### 1) 롤링 로그 파일 설정 및 Tail 방식의 스트리밍 읽기

로그 파일이 일정 크기를 넘어서면 자동으로 분할되도록 설정하고, API 조회 시에는 파일의 끝부분만 효율적으로 읽어오는 로직을 작성했습니다.

```python
import logging
from logging.handlers import RotatingFileHandler
import os

# 1. RotatingFileHandler 설정 (파일당 최대 5MB, 백업 파일 3개 유지)
log_formatter = logging.Formatter('[%(asctime)s] %(levelname)s: %(message)s')
log_file_path = "logs/data_sync.log"

os.makedirs(os.path.dirname(log_file_path), exist_ok=True)

file_handler = RotatingFileHandler(
    log_file_path,
    maxBytes=5 * 1024 * 1024, # 5MB
    backupCount=3,
    encoding='utf-8'
)
file_handler.setFormatter(log_formatter)

logger = logging.getLogger("CollectorLogger")
logger.setLevel(logging.INFO)
logger.addHandler(file_handler)


# 2. 어드민 조회용 Tail 읽기 함수 (전체 파일 로드 방지)
def read_log_tail(file_path: str, lines_to_read: int = 500) -> list[str]:
    if not os.path.exists(file_path):
        return []

    buffer_size = 1024
    lines = []
    
    with open(file_path, 'rb') as f:
        f.seek(0, os.SEEK_END)
        file_size = f.tell()
        pointer = file_size
        remainder = b""

        while pointer > 0 and len(lines) < lines_to_read:
            read_size = min(buffer_size, pointer)
            pointer -= read_size
            f.seek(pointer)
            chunk = f.read(read_size) + remainder
            
            split_lines = chunk.split(b'\n')
            remainder = split_lines[0]
            
            for line in reversed(split_lines[1:]):
                if line.strip():
                    lines.append(line.decode('utf-8', errors='ignore'))
                if len(lines) >= lines_to_read:
                    break

        if remainder.strip() and len(lines) < lines_to_read:
            lines.append(remainder.decode('utf-8', errors='ignore'))

    return list(reversed(lines))
```

### 2) Safe Teardown 커넥션 풀 보호 구문

네트워크 예외나 파싱 오류가 발생하더라도 트랜잭션을 정돈하고 DB 세션을 반환하도록 세션 생명주기를 엄격하게 통제했습니다.

```python
import httpx
from contextlib import contextmanager
import time

@contextmanager
def safe_db_session(session_factory):
    """DB 세션의 명시적 생명주기 관리를 위한 컨텍스트 매니저"""
    session = session_factory()
    try:
        yield session
        session.commit()
    except Exception as e:
        session.rollback()
        logger.error(f"Transaction failed and rolled back: {str(e)}")
        raise
    finally:
        session.close()  # 커넥션 풀로 확실한 반환

def fetch_and_store_ingredient_batch(session_factory, api_url: str, params: dict):
    start_time = time.time()
    
    # HTTP 클라이언트 타임아웃을 10초로 제한
    with httpx.Client(timeout=10.0) as client:
        try:
            response = client.get(api_url, params=params)
            response.raise_for_status()
            raw_data = response.json()
        except httpx.RequestError as exc:
            logger.error(f"External API Request Exception: {exc}")
            return

    # 안전한 DB 트랜잭션 수행
    with safe_db_session(session_factory) as db:
        # 보조/원시 데이터 테이블에 이중화 분리 적재
        staging_record = RawIngredientStaging(
            payload=raw_data,
            processed=False
        )
        db.add(staging_record)

    duration = time.time() - start_time
    logger.info(f"Batch Sync Completed - Duration: {duration:.2f}s")
```

개선 작업 후 식약처 30,000건 이상의 성분 데이터 수집을 다시 진행해 보았습니다.

* **운영 안정성**: 수집 작업이 완주할 때까지 DB 커넥션 수치가 일정 범위 내로 안정적으로 유지되었으며, `idle in transaction`으로 인한 누수 현상이 완전히 사라졌습니다.
* **리소스 절감**: 어드민 페이지에서 실시간 로그 수집 현황을 모니터링할 때 백엔드 메모리 점유율이 이전 대비 **90% 이상 감소**했습니다. 5MB 단위로 롤링되는 로그 파일 덕분에 서버 디스크 용량 고민도 해결되었습니다.

대규모 시스템 구축이나 거대한 분산 프레임워크를 도입하지 않더라도, **파일 I/O 단위 제한**, **자원 해제(Teardown) 구문 명시**, **타임아웃 설정** 같은 기본적인 프로그래밍 원칙을 지키는 것만으로도 서비스 안정성을 크게 끌어올릴 수 있음을 재확인할 수 있었습니다.
