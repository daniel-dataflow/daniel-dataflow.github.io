고성능 AI/OCR 시스템을 구축할 때 처리량(Throughput)을 극대화하고 쿼터 제약을 회피하기 위해 **'다중 API 키 라운드 로빈(Ping-Pong) 분산 처리'** 아키텍처를 자주 도입합니다. PickSafe 팀 역시 멀티 키 로드밸런싱을 통해 파이프라인의 병목을 해소해 왔습니다.

하지만 시스템 규모가 커지고 다양한 커스텀 AI 모델(Gemini 3.5 Flash-Lite 등)을 유연하게 검증하는 과정에서 **"잘못된 폴백(Fallback) 방침이 시스템 전체의 신뢰도를 어떻게 무너뜨리는가"**에 대한 중요한 엔지니어링 과제에 직면했습니다.

본 포스팅에서는 백엔드 예외 처리의 투명성 확보 과정과 프론트엔드 비동기 UI 상태 동기화 버그를 해결한 과정을 공유합니다.

---

## 1. 문제 정의: "작동하는 것처럼 보이는 거짓말"의 위험성

시스템은 다중 API 키 쿼터를 실시간으로 추적하며 최적의 키를 배정(`get_optimal_api_key`)하도록 설계되었습니다. 그러나 로컬 환경(`.env`) 설정 미비나 하위 호환되지 않는 최신 모델 호출 시 구글 API 단에서 `404 Not Found` 또는 네트워크 에러가 발생하는 예외 상황이 관측되었습니다.

당시 백엔드는 장애 대응(Graceful Degradation) 관점에서 **"API 호출 실패 시 쿼터를 롤백하고, 가짜(Mock) 성분 데이터를 리턴"**하도록 구현되어 있었습니다. 표면적으로는 서비스가 멈추지 않는 것처럼 보였으나, 실제로는 심각한 사이드 이펙트를 유발했습니다.

```
[기존 파이프라인의 맹점]
API 호출 시도 ──> 404 Error 발생 ──> 쿼터 롤백(Rollback) ──> Mock 데이터 반환 ──> (시스템은 성공으로 인식)
```

### 핵심 문제점 3가지
1. **벤치마크 신뢰성 붕괴 (Silent Failure)**  
   실제 API 제약이나 모델 미지원으로 실패했음에도 불구하고 시스템이 가짜 데이터를 반환하면서, 사용자와 엔지니어 모두 "정상 작동 중"이라고 착각하게 되었습니다. 이는 모델 성능 평가(Benchmark) 데이터의 왜곡으로 이어졌습니다.
2. **방어적 UI 수정으로 인한 레이아웃 파괴**  
   Mock 데이터임을 사용자에게 알리기 위해 타이틀 뱃지 공간에 `[API 실패 / Mock 폴백]` 같은 장문의 텍스트를 강제로 주입하면서 좁은 뱃지 영역의 CSS 레이아웃이 상시 깨지는 문제가 생겼습니다.
3. **프론트엔드 실시간 메트릭 동기화 버그 (UI State Leakage)**  
   핑퐁 로드밸런싱으로 `Key_1`만 실제로 API를 호출했음에도, 렌더링 후 화면의 모든 키 패널(`Key_1`, `Key_2`)에 동일한 처리 속도(초)가 동시에 갱신되는 UI 렌더링 버그가 발견되었습니다.

## 2. 기술적 고민과 의사결정 (Trade-offs)

### 백엔드: "우아한 실패(Graceful Fallback)" vs "투명한 예외(Explicit Failure)"

시스템 모니터링 및 벤치마크 환경에서는 **'어설픈 성공'보다 '명확한 실패'가 훨씬 가치 있습니다.**

*   **대안 A: 기존 Mock 폴백 유지** (User-facing 서비스에는 유리할 수 있으나, 시스템 진단/벤치마크 신뢰성을 크게 해침)
*   **대안 B: 예외(Exception) 전파 및 투명한 에러 리포팅** (시스템 상태 파악이 즉각적이고, 데이터 벤치마크의 오염을 완벽히 방지함)

 PickSafe 팀은 **대안 B**를 선택했습니다. API 실패 시 차감된 쿼터를 정상 복구(`rollback_quota`)한 뒤, 하드코딩된 Mock 데이터를 반환하던 암묵적 로직을 전면 삭제했습니다. 대신 발생한 에러 원인(`last_api_error`)을 포함한 `Exception`을 명시적으로 터뜨려 프론트엔드에 `[분석 실패]` 상태를 정직하게 노출하도록 변경했습니다.

## 3. 해결 및 구현 내용

### 3.1. 백엔드: 예외 투명성 확보 및 쿼터 롤백 격리 (`ocr_service.py`)

Mock 반환 코드를 제거하고, 다중 키 재시도 루프가 종료될 때 마지막 에러 상태를 보존하여 라우터(`ocr.py`)로 명시적 예외를 던지도록 개편했습니다.

```python
# [개선된 서비스 로직의 개념적 구조]
async def process_ocr_with_retry(payload):
    last_api_error = None
    
    for attempt in range(MAX_RETRIES):
        key_info = await quota_manager.get_optimal_api_key()
        try:
            # External API Call
            result = await call_ocr_provider(key_info, payload)
            return result
        except Exception as e:
            # 1. 쿼터 상태 복원 (Rollback)
            await quota_manager.rollback_quota(key_info.key_id)
            last_api_error = e
            
    # 2. Mock 데이터 반환 삭제 -> 명시적 예외 발생
    raise OCRProcessingException(f"API 호출 실패: {str(last_api_error)}")
```

### 3.2. 프론트엔드: DOM 셀렉터 타게팅 수정 및 UI 클린업 (`ocr.js`)

#### 1) UI 레이아웃 오버플로우 방지
기존의 비대했던 뱃지 텍스트(`[사용 Key: Key_1]`) 및 에러 폴백 강제 메시지 로직을 삭제하고, **`[Key_1]`** 형태의 콤팩트한 컴포넌트로 간소화하여 UI 격자를 보호했습니다.

#### 2) `data-key` 속성을 통한 정확한 UI 상태 동기화
기존 버그의 원인은 DOM을 탐색할 때 단일 조건(`data-model`)으로만 조회했기 때문이었습니다.

```javascript
// ❌ 기존 코드: 모델명으로만 셀렉팅하여 모든 Key 패널의 UI가 동시에 갱신됨
document.querySelectorAll(`.model-time[data-model="${modelName}"]`);
```

이를 해결하기 위해 쿼터 카드를 렌더링하는 시점에 `<div class="model-time" data-model="..." data-key="Key_1">` 형태로 복합 식별자를 주입하고, **`data-model`과 `data-key` 두 조건이 모두 일치하는 단일 엘리먼트만 타게팅**하도록 개선했습니다.

```javascript
// ✅ 개선된 UI 갱신 헬퍼 함수
function updateQuotaTimeUI(modelName, keyUsed, executionTime) {
  // data-model과 data-key가 모두 일치하는 정확한 패널만 렌더링
  const targetEl = document.querySelector(
    `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`
  );
  
  if (targetEl) {
    targetEl.textContent = `${executionTime}s`;
    targetEl.classList.add('highlight-update');
  }
}
```

## 4. 엔지니어링 성과 및 레슨 런 (Takeaways)

### 📈 결론 및 결과
1. **시스템 벤치마크 신뢰도 100% 확보**: 할당량 부족(429), 미지원 모델(404) 등 외부 요인 발생 시 시스템이 은폐하지 않고 즉시 가시적인 에러를 리포팅하여 테스트 데이터 수집의 불확실성을 완전히 제거했습니다.
2. **로드밸런싱 시각화(Telemetry) 완벽 동기화**: 프론트엔드의 멀티 패널에 실제 요청을 처리한 키의 메트릭만 정확히 사핑(Targeting)되어 렌더링되므로, 관제 타워(Dashboard)로서의 기능이 명확해졌습니다.

```
[최종 시스템 동작 파이프라인]
[요청] ──> [키 배정 (Key_1)] ──> [OCR 수행]
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼ (성공)                                ▼ (실패: 404/429)
     [Key_1 UI 패널에만 속도 표출]              [쿼터 롤백] -> [명시적 Exception 전파]
                                            [대시보드에 [분석 실패] 정직하게 표출]
```

### 💡 Senior Developer's Takeaway

* **"잘못된 Graceful Degradation은 안티패턴이 될 수 있다."**  
  사용자 접점의 서비스 layer가 아닌 내부 평가/모니터링 레벨에서의 무분별한 Mock 폴백은 시스템의 문제를 숨기는 독이 됩니다. 실패는 일찍, 그리고 명확하게 드러내야(Fail-Fast) 시스템이 건강해집니다.
* **비동기 UI 동기화 시 복합 식별자의 중요성**  
  다중 인스턴스/다중 키 상태를 시각화할 때는 단순 식별자(`data-model`)만으로 DOM을 조작하면 State Leakage가 발생하기 쉽습니다. UI 데이터 바인딩 시 백엔드의 도메인 키 식별 구조(`Model + Key`)를 프론트엔드 DOM 구조에도 1:1로 사핑시켜야 레이아웃 사이드 이펙트를 예방할 수 있습니다.
