안녕하세요. PickSafe 백엔드/아키텍처팀입니다. 

AI 기반 OCR 시스템을 운영하면서 대규모 트래픽 분산을 위해 **다중 API 키 기반의 로드 밸런싱(핑퐁) 시스템**을 도입했습니다. 시스템 자체는 유연하게 동작했으나, 최근 최신 커스텀 모델(Gemini 계열 등)을 연동하는 과정에서 예기치 못한 에러 핸들링과 UI 동기화 이슈를 마주했습니다.

이번 글에서는 **"시스템이 실패했을 때, 과연 어디까지 감싸 안아야 하는가?"**에 대한 기술적 고민과, 멀티 키 환경에서 프론트엔드 상태를 정확히 동기화하기 위해 적용한 트러블슈팅 과정을 공유합니다.

---

## 1. 배경 및 문제 상황

시스템은 여러 개의 외부 LLM/OCR API 키를 라운드 로빈 방식으로 분산 사용하여 할당량(Quota) 제한을 우회하고 처리 속도를 극대화하도록 설계되었습니다. 하지만 이 과정에서 다음과 같은 3가지 치명적인 엔지니어링 부채가 드러났습니다.

### 1.1. "실패를 숨기는" 가짜(Mock) 데이터 폴백의 함정
최신 모델 호출 시 외부 API에서 `404 Not Found`나 네트워크 에러가 발생했을 때, 기존 시스템은 쿼터를 롤백한 뒤 **하드코딩된 임의의 Mock 성분 데이터("리모넨, 리날룰...")를 강제로 반환**하고 있었습니다. 
* **문제점**: 사용자는 시스템이 정상 동작한 것으로 오인하며, 벤치마크 테스트의 신뢰도가 완전히 무너지는 결과를 초래했습니다.

### 1.2. 에러 처리에 종속된 UI 레이아웃 파괴
Mock 데이터임을 억지로 알리기 위해 프론트엔드 타이틀 뱃지 영역에 `[API 실패 / Mock 폴백]`과 같은 장문의 텍스트를 주입했습니다. 이로 인해 제한된 공간의 UI 레이아웃이 깨지고 사용자 경험(UX)이 심각하게 저해되었습니다.

### 1.3. 멀티 키 로드밸런싱 UI 표출 버그 (상태 오염)
특정 모델이 `Key_1`을 통해 정상 호출되었음에도 불구하고, 화면 상에서는 사용되지도 않은 `Key_2` 패널의 인식 속도(초)까지 동시에 갱신되는 렌더링 버그가 발생했습니다. DOM 셀렉터의 타게팅 정밀도가 떨어졌기 때문입니다.

## 2. 기술적 고민과 대안 비교

문제를 해결하기 위해 두 가지 아키텍처 및 구현 방향을 두고 고민했습니다.

* **Alternative A (기존 유지 및 완화)**: Mock 데이터를 유지하되 예외 메시지를 좀 더 부드럽게 다듬고, DOM 셀렉터만 우회하여 수정한다.
  * *Pros*: 사용자가 에러 화면을 마주하지 않아 서비스가 '항상 성공하는 것처럼' 보임.
  * *Cons*: **벤치마크 시스템 본연의 목적(정확한 성능 및 제약 측정) 상실.** 기술적 부채가 누적됨.
* **Alternative B (Fail-Fast 및 투명성 확보 - 선택)**: Mock 폴백을 과감히 제거하고, 외부 API 실패 시 즉시 예외(`Exception`)를 발생시켜 시스템의 한계를 투명하게 노출한다. UI 또한 정확한 타게팅 방식으로 전면 개편한다.
  * *Pros*: 시스템의 신뢰성 확보, 디버깅 용이성, 정확한 트래픽 분산 상태 모니터링 가능.
  * *Cons*: 일시적인 API 실패 시 사용자가 에러 마크를 직접 보게 됨 (단, 벤치마크/관리자 도구 특성상 오히려 올바른 동작임).

우리는 **'정직한 실패와 명확한 관측 가능성(Observability)'**이 엔지니어링 관점에서 훨씬 가치 있다고 판단하여 **Alternative B**를 채택했습니다.

## 3. 최종 해결 및 구현

### 3.1. Mock 폴백 제거 및 Fail-Fast 원칙 적용 (`Backend`)
백엔드 서비스 레이어(`ocr_service.py`)에서 하드코딩된 Mock 데이터 반환 로직을 완전히 도려냈습니다.

```python
# 수정 전 (Anti-Pattern)
if not success:
    rollback_quota(api_key)
    return get_mock_fallback_data() # 실패를 은폐함

# 수정 후 (Fail-Fast)
if not success:
    rollback_quota(api_key)
    raise HTTPException(
        status_code=502, 
        detail=f"OCR 모델 분석 실패: {last_api_error}"
    )
```
API 호출 실패 시 쿼터는 안전하게 롤백하되, 마지막 에러(`last_api_error`)를 담은 예외를 상위 라우터로 즉시 전파하여 클라이언트가 실패 원인을 투명하게 인지할 수 있도록 개선했습니다.

### 3.2. 정밀 DOM 타게팅을 통한 로드밸런싱 상태 동기화 (`Frontend`)
기존에 `document.querySelectorAll('.model-time')`로 모든 패널의 속도를 일괄 갱신하던 무지성 DOM 조작 방식을 폐기했습니다.

* **개선안**: 쿼터 카드를 렌더링할 때 `data-model`과 `data-key` 속성을 조합하여 식별자를 명시하고, 정확히 일치하는 엘리먼트만 타게팅하도록 수정했습니다.

```javascript
// 정확한 키와 모델 매칭을 통한 상태 업데이터
function updateQuotaTimeUI(modelName, keyUsed, elapsedTime) {
    const targetElement = document.querySelector(
        `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`
    );
    if (targetElement) {
        targetElement.textContent = `${elapsedTime}s`;
    }
}
```
이를 통해 멀티 키 핑퐁 로드 밸런싱이 동작할 때, 실제 트래픽을 처리한 특정 키 패널에만 정확히 속도가 기재되도록 시각화 버그를 해결했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **"은폐된 성공"보다 "투명한 실패"가 낫다**: 
   벤치마크 및 검증 시스템에서 가짜 데이터(Mock)로 에러를 덮는 것은 개발 단계에서는 편할지 몰라도, 장기적으로는 시스템에 대한 신뢰를 무너뜨립니다. 예외는 숨기지 말고 드러내어 원인을 빠르게 파악할 수 있어야 합니다.
2. **상태 관리와 UI 렌더링의 정밀성**: 
   멀티 인스턴스나 멀티 키와 같은 분산 환경을 다룰 때는, 프론트엔드 UI 렌더링 역시 전역적인 조작보다는 명시적인 식별자(`data- attribute` 등)를 활용한 타게팅 방식으로 설계해야 상태 오염을 방지할 수 있습니다.

이번 트러블슈팅을 통해 PickSafe의 OCR 벤치마크 파이프라인은 더욱 견고해졌으며, 관리자는 실시간 트래픽 분산 현황을 한 눈에 신뢰할 수 있게 되었습니다. 앞으로도 안정성과 투명성을 최우선으로하는 아키텍처를 만들어 나가겠습니다.
