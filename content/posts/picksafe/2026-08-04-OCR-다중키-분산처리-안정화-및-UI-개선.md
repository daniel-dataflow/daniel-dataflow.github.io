고성능 AI/OCR 서비스를 운용할 때 트래픽 분산과 API 쿼터 관리(Load Balancing)는 필수적입니다. 그러나 시스템이 장애 상황을 대처하는 방식에서 **'잘못된 우아한 퇴보(Graceful Degradation)'** 전략을 취하면, 오히려 시스템의 신뢰성을 근본적으로 훼손할 수 있습니다.

이번 글에서는 Gemini OCR 다중 키 핑퐁(분산) 시스템을 운용하며 발생했던 **1) '가짜 데이터(Mock) 폴백'으로 인한 벤치마크 신뢰성 저하 문제**와 **2) 프론트엔드 DOM 타게팅 오류로 인한 로드밸런싱 시각화 버그**를 어떻게 구조적으로 해결했는지 공유합니다.

---

## 1. 문제 상황 (Problem Definition)

우리는 외부 AI API의 쿼터 제한을 극복하기 위해 Multi-API Key 기반의 핑퐁(Round-robin/Least-used) 로드밸런서를 구축해 사용 중이었습니다. 하지만 특정 커스텀 모델 호출 시 또는 네트워크 단선/404/429 에러 발생 시 세 가지 치명적인 문제가 드러났습니다.

### ① '가짜 데이터(Mock)' 폴백이 불러온 신뢰성 위기
기존 백엔드는 API 호출이 실패할 경우, 사용한 쿼터를 롤백한 뒤 **미리 정의된 하드코딩 Mock 성분 데이터**를 강제로 반환하도록 설계되어 있었습니다. 
* 시스템이 정상 동작하는 것처럼 보였지만, 실제로 성능 벤치마크를 수행하는 평가자 입장에서는 **API가 실패했음에도 성공으로 오인**하는 상황이 발생했습니다.
* 장애를 은폐하는 폴백 로직이 도리어 서비스 벤치마크 결과 전체의 불신으로 이어졌습니다.

### ② 예외 문자열 주입으로 인한 UI 레이아웃 파괴
Mock 폴백 발생 사실을 어떻게든 관리자 UI에 알리기 위해, 프론트엔드의 좁은 타이틀 뱃지 영역에 `[API 실패 / Mock 폴백]`이라는 긴 텍스트를 강제로 삽입했습니다. 이로 인해 뱃지가 컨테이너를 뚫고 나가는 **UI 레이아웃 오버플로우 현상**이 빈번하게 일어났습니다.

### ③ 로드밸런싱 실시간 메트릭의 동기화 버그
다중 키 중 어떤 키가 실제로 요청을 처리했는지 실시간 응답 속도(초)를 관리자 패널에 시각화해 주는 기능이 있었습니다. 그러나 특정 모델(예: `Flash`) 요청이 `Key_1`에 할당되어 완료되었음에도, **사용되지 않은 `Key_2` 패널의 응답 속도까지 동시에 동일하게 갱신**되는 프론트엔드 렌더링 버그가 발견되었습니다.

## 2. 엔지니어링 의사결정 (Trade-offs & Architecture)

### [Backend] Fail-Fast vs. Graceful Degradation
* **고민**: 시스템의 Uptime 수치를 유지하기 위해 가짜 응답이라도 돌려주는 것이 맞을까, 아니면 명확한 에러를 발생시키는 것이 맞을까?
* **결정**: **투명한 실패(Explicit Fail-Fast) 채택.**
  * 관리자 및 벤치마크 타겟 시스템에서는 '잘못된 성공'보다 '명확한 실패 원인'을 아는 것이 시스템 개선에 훨씬 유용합니다.
  * 따라서 Mock 데이터 생성 로직을 완전히 격리/삭제하고, 쿼터 롤백 후 발생한 **실제 API 예외(Exception)를 라우터 상단까지 투명하게 전파(Raise)** 하기로 결정했습니다.

### [Frontend] 데이터 속성 기반 단일 타게팅 바인딩
* **고민**: 모델 단위(`data-model`)로만 묶여 있던 DOM 구조에서 특정 키(`Key_X`)의 메트릭만 정확히 업데이트하려면 어떻게 해야 하는가?
* **결정**: DOM 셀렉터 스코프의 명확화.
  * 기존 `querySelectorAll('.model-time[data-model="..."]')` 방식은 동일 모델명을 가진 모든 Key 패널을 제어해 버리는 부작용을 낳았습니다.
  * DOM 생성 시점에 `data-key` 복합 식별자를 주입하여, $O(1)$에 가까운 정확성으로 해당 키의 패널만 지목해 UI를 업데이트하도록 개선했습니다.

## 3. 핵심 구현 내용 (Implementation)

### 3.1. 백엔드: 예외 투명성 확보 및 쿼터 안전 롤백
기존의 하드코딩 폴백을 제거하고, 실패 원인을 명확히 래핑하여 에러를 상위 라우터로 전달하도록 흐름을 단순화했습니다.

```python
# web/backend/app/services/ocr_service.py (개념적 구조)

async def process_ocr_with_pingpong(model_name: str, payload: dict):
    key_info = await get_optimal_api_key()
    last_api_error = None

    try:
        # API 호출 시도
        response = await call_external_ocr_api(key_info, model_name, payload)
        return response
    except Exception as e:
        # 쿼터 원상복구 및 에러 기록
        await rollback_quota(key_info)
        last_api_error = f"API 오류 ({type(e).__name__}): {str(e)}"
        
        # [핵심] 가짜 Mock 데이터를 반환하던 이전 코드를 완전히 제거하고 예외를 명확히 던짐
        raise RuntimeError(f"OCR 분석 실패: {last_api_error}") from e
```

라우터 단에서는 이 예외를 Catch하여 사용자 UI에 `[분석 실패] {에러 메시지}` 형태로 적나라하게 표출함으로써, 벤치마크 본연의 모니터링 목적을 회복했습니다.

### 3.2. 프론트엔드: 복합 Data-Attribute 타게팅 렌더링
렌더링 엔진에서 쿼터 카드를 그릴 때 `data-key` 속성을 동적으로 바인딩하고, UI 업데이트 함수가 이를 정교하게 지목하도록 수정했습니다.

```javascript
// web/frontend/static/js/admin/ocr.js

// 1. 쿼터 카드 동적 생성 시 data-key 명시
function renderQuotaCard(modelName, keyName) {
    return `
      <div class="quota-card">
        <span class="badge">[${keyName}]</span>
        <div class="model-time" data-model="${modelName}" data-key="${keyName}">
          -
        </div>
      </div>
    `;
}

// 2. 타겟 패널만 정밀 업데이트하는 헬퍼 함수
function updateQuotaTimeUI(modelName, keyUsed, durationSec) {
    // data-model과 data-key가 동시에 일치하는 단 하나의 엘리먼트만 타게팅
    const targetEl = document.querySelector(
        `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`
    );
    
    if (targetEl) {
        targetEl.textContent = `${durationSec}s`;
    }
}
```
또한, 기존 `[사용 Key: Key_1]`과 같은 불필요하게 긴 텍스트 뱃지를 **`[Key_1]`** 형태로 축약하여 CSS 레이아웃 파괴 문제를 근본적으로 방지했습니다.

## 4. 결과 및 성과 (Impact & Takeaways)

### 📊 측정 가능한 성과
1. **벤치마크 측정 데이터 신뢰도 100% 확보**: 네트워크 문제나 404/429 오류 발생 시 시스템이 이를 은폐하지 않고 정확한 에러 로그를 남기게 되어, 커스텀 모델 파이프라인의 하자가 즉시 감지 가능해졌습니다.
2. **트래픽 분산 시각화 정상화**: 멀티키 핑퐁 로드밸런싱 동작이 우측 메트릭 패널에 정확히 일대일 매핑되어, 어떤 API Key가 병목 상태인지 한눈에 모니터링할 수 있게 되었습니다.
3. **UI 깨짐 현상 완전히 해결**: 예외 문구 크기 초과로 인한 DOM 찌그러짐 현상이 제거되었습니다.

## 💡 엔지니어링 교훈 (Key Takeaways)

1. **"Graceful Degradation"은 문맥에 맞게 써야 한다.**
   최종 사용자 서비스에서의 Fallback은 사용자 경험을 지키는 좋은 전략일 수 있지만, **시스템 상태를 측정하고 개발자/관리자가 판단해야 하는 관리자 및 벤치마크 환경에서는 '잘못된 성공'보다 '명확한 실패'가 훨씬 가치 있습니다.**
2. **상태(State)와 뷰(View)의 바인딩은 구체적이어야 한다.**
   DOM을 조작할 때 애매한 단일 셀렉터(`data-model`)를 사용하면 로드밸런싱과 같은 다중 인스턴스 환경에서 시각적 동기화 버그를 유발합니다. 식별자는 항상 유일(Unique)하거나 조합 가능(Compound)해야 합니다.
3. **에러 메시지도 UI/UX 규격의 일부다.**
   디버깅용 예외 문구를 UI 요소에 직접 주입할 때는 텍스트 길이에 따른 레이아웃 깨짐을 고려해야 합니다. UI 시스템은 텍스트 유연성을 가지거나, 백엔드에서 규격화된 에러 코드로 응답하는 것이 안전합니다.
