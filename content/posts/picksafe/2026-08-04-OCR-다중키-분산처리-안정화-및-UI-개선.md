외부 API 트래픽을 효율적으로 관리하기 위해 **다중 API 키 기반 분산처리(Load Balancing) 시스템**을 구축하는 것은 대규모 LLM/OCR 서비스에서 흔히 사용하는 전략입니다. PickSafe 서비스 역시 구글 Gemini API의 할당량(Quota) 한계를 극복하고 최신 커스텀 모델(Gemini 3.5 Flash-Lite 등)의 성능을 실험하기 위해 멀티 키 핑퐁 방식의 로드밸런서를 운용하고 있었습니다.

하지만 시스템 구축 후, 예기치 않은 곳에서 **데이터 신뢰성 저하**와 **UI 레이아웃 파괴**, 그리고 **상태 동기화 버그**라는 세 가지 문제에 직면했습니다. 

본 포스팅에서는 **시스템의 '가짜 성공' 폴백 로직을 제거하여 투명성을 확보한 과정**과 **프론트엔드 DOM 상태 동기화 이슈를 해결한 엔지니어링 경험**을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

### 1) '가짜 성공(Mock Fallback)'이 초래한 벤치마크 신뢰성 붕괴
기존 백엔드 엔진은 외부 API 호출 중 오류(404 Not Found, 429 Rate Limit 등)가 발생하면 할당량을 롤백한 후, 서비스 중단을 막기 위해 사전 정의된 가짜 성분 데이터(Mock Data)를 반환하도록 하드코딩되어 있었습니다.

유저 대상의 상용 서비스라면 이러한 'Graceful Degradation'이 유효할 수 있으나, **내부 성능 측정 및 모델 벤치마크 시스템에서는 치명적인 독**이 되었습니다.
* 개발자와 테스터는 시스템이 정상 작동하여 결과를 낸 것으로 오인함.
* 실제 API 오류 원인을 파악하기 어려워 벤치마크 결과 전체의 신뢰성이 하락함.
* Mock 데이터 표시를 위해 UI 뱃지에 `[API 실패 / Mock 폴백]`이라는 긴 텍스트를 억지로 집어넣으면서 레이아웃 오버플로우 발생.

### 2) 멀티 키 핑퐁 UI의 상태 업데이트 버그
멀티 키 로드밸런싱 현황을 관찰하는 관리자 패널에서 **Key_1만 사용되어 처리가 완료되었음에도, 사용되지 않은 Key_2 패널의 인식 속도 타이머까지 동시에 갱신되는 렌더링 버그**가 발생했습니다. 이로 인해 어떤 키가 실제 트래픽을 처리했는지 시각적으로 추적하기 불가능해졌습니다.

## 2. 기술적 고민과 대안 비교 (Trade-offs & Decisions)

이 문제를 해결하기 위해 백엔드 예외 처리 방식과 프론트엔드 상태 반영 방식을 재설계했습니다.

### 백엔드: Silent Fallback vs. Fail-Fast (투명한 예외 전파)

| 비교 항목 | 옵션 A: 기존 Mock 데이터 폴백 (Silent Fallback) | 옵션 B: Fail-Fast 및 투명한 Exception 전파 (선택) |
| :--- | :--- | :--- |
| **시스템 가용성** | 높음 (실패해도 가짜 결과 반환) | 에러 발생 시 즉시 실패 처리 |
| **데이터 신뢰성** | **매우 낮음** (오류 원인 은폐) | **매우 높음** (원인 및 에러 코드 즉시 파악) |
| **용도 적합성** | B2C 최종 서비스 fallback 처리 | **벤치마크 및 관리자 시스템** |

> **선택 이과**: 벤치마크 도구의 본질은 **'정확한 측정과 관찰'**입니다. 에러를 은폐하는 것은 시스템 진단을 방해하므로, API 쿼터는 정상 롤백하되 실패 원인은 명확한 `Exception`으로 전파하여 시스템에 투명하게 기록하는 **Fail-Fast** 전략을 채택했습니다.

### 프론트엔드: 포괄적 Selector vs. 속성 기반 데이터 바인딩 (Data Attribute Targeting)

UI 업데이트 버그의 원인은 단순 `querySelectorAll('.model-time[data-model="..."]')` 방식의 조회가 호출에 사용된 API Key 정보까지 구분하지 못했기 때문이었습니다.
* **대안 1**: 키 조합별 독자적인 ID 부여 (`#model-key1-time`) $\rightarrow$ DOM 구조 변경 시 유연성 저하.
* **대안 2**: `data-key`와 `data-model` 복합 속성을 활용한 Target Query Selector $\rightarrow$ **선택**

## 3. 해결 방안 및 구현 (Implementation)

### 3.1. 백엔드 예외 투명성 확보 및 Clean Architecture 적용

하드코딩된 Mock 반환 로직을 제거하고, 마지막으로 발생한 실제 API 에러 메시지를 명확히 래핑하여 명시적 예외를 발생시키도록 `OCRService`를 수정했습니다.

```python
# web/backend/app/services/ocr_service.py (개념적 구조)

async def process_ocr_with_retry(payload):
    last_api_error = None
    
    for key_info in available_keys:
        try:
            # 1. 쿼터 차감 및 API 호출
            return await call_google_ocr_api(key_info, payload)
        except Exception as e:
            # 2. 실패 시 차감된 쿼터 롤백
            await quota_manager.rollback_quota(key_info)
            last_api_error = e
            continue
            
    # [기존] 하드코딩된 Mock 데이터 리턴 (삭제됨)
    # return MOCK_INGREDIENT_DATA 
    
    # [개선] 실패 원인을 투명하게 전파
    raise OCRProcessingException(
        status_code=500,
        detail=f"[분석 실패] API 호출 실패: {str(last_api_error)}"
    )
```

이를 통해 라우터 레이어에서는 에러 인터셉트 후 클라이언트에 명확한 실패 사유를 반환할 수 있게 되었으며, 벤치마크 신뢰도가 즉시 회복되었습니다.

### 3.2. Precise Target Rendering으로 UI 상태 동기화

프론트엔드 렌더링 로직에 `data-key` 데이터 속성을 바인딩하여 선택된 키 패널만 타겟팅해 속도를 업데이트하도록 조치했습니다.

```javascript
// web/frontend/static/js/admin/ocr.js

// 1. 쿼터 카드 동적 생성 시 data-key 속성 명시
function renderQuotaCard(modelName, keyId) {
    return `
        <div class="model-card">
            <span class="badge">[${keyId}]</span>
            <div class="model-time" data-model="${modelName}" data-key="${keyId}">
                -- 초
            </div>
        </div>
    `;
}

// 2. 사용된 key와 model이 정확히 일치하는 엘리먼트만 핀포인트 렌더링
function updateQuotaTimeUI(modelName, keyUsed, elapsedTime) {
    // data-model과 data-key 복합 선택자 사용
    const targetEl = document.querySelector(
        `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`
    );
    
    if (targetEl) {
        targetEl.textContent = `${elapsedTime}초`;
    }
}
```

추가로 UI 뱃지 텍스트를 `[사용 Key: Key_1]` $\rightarrow$ **`[Key_1]`** 로 간소화하여 좁은 컨테이너 내에서 발생하던 레이아웃 오버플로우 문제도 함께 깨끗하게 해결했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **도구의 목적에 맞는 에러 핸들링 전략 수립**
   모든 시스템에 'Graceful Fallback'이 정답은 아닙니다. 관리자 도구나 성능 측정 벤치마크 시스템에서는 **오류를 빠르게 명시하고 원인을 투명하게 드러내는 것(Fail-Fast & Transparent Exception)**이 시스템 전반의 신뢰도를 향상시킵니다.

2. **분산 상태 시각화 시 명확한 식별자 설계 필수**
   다중 API 키, 멀티 노드 등 로드밸런싱이 적용된 아키텍처의 상태를 클라이언트에 시각화할 때는 단순 모델명뿐만 아니라 **실행 주체(Key ID, Node ID)를 엮은 콤포짓 식별자(Composite Key)** 기반으로 DOM 및 상태 관리 로직을 설계해야 사이드 이펙트를 막을 수 있습니다.
