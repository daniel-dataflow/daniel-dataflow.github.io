안녕하세요, PickSafe 백엔드/아키텍처 팀입니다. 

최근 서비스 내에서 다중 API 키를 활용한 Gemini OCR 분산 핑퐁 시스템(Load Balancing)을 도입한 이후, 외부 API 스펙 변경 및 커스텀 모델 호출 실패 시 발생하는 예외 상황을 다루는 과정에서 몇 가지 기술적 부채를 마주했습니다. 

이번 포스팅에서는 **"시스템이 친절하게 에러를 숨겨주는 것(Mock Fallback)이 왜 독이 되는지"**, 그리고 **"멀티 키 환경에서 정확한 실시간 메트릭을 렌더링하기 위해 어떤 아키텍처적 결정을 내렸는지"**에 대한 트러블슈팅 과정을 공유합니다.

---

## 1. 문제 정의 (Problem): "실패를 숨기는 친절함"이 낳은 부작용

멀티 API 키 기반의 OCR 로드밸런싱 시스템을 운영하면서, 최신 커스텀 모델 호출 시 간헐적으로 `404 Not Found`나 네트워크 예외가 발생하는 상황이 포착되었습니다. 

당시 기존 시스템은 이러한 장애 상황에서 다음과 같은 방식으로 동작하고 있었습니다.

1. **Mock 데이터 폴백(Fallback)으로 인한 신뢰성 하락**
   - API 호출 실패 시 쿼터를 롤백한 뒤, 시스템이 임의의 하드코딩된 성분 데이터("리모넨, 리날룰...")를 강제로 리턴하도록 설계되어 있었습니다.
   - 개발 의도는 '사용자 경험(UX) 방어'였으나, 실제로는 **사용자가 시스템 장애를 인지하지 못한 채 가짜 데이터로 벤치마크 결과를 신뢰하게 되는 치명적인 문제**가 발생했습니다.
2. **UI 레이아웃 파괴**
   - Mock 데이터임을 억지로 알리기 위해 좁은 타이틀 뱃지 공간에 `[API 실패 / Mock 폴백]`과 같은 장문의 텍스트를 주입하면서 프론트엔드 UI가 깨졌습니다.
3. **멀티 키 상태 표출 렌더링 버그**
   - 특정 키(`Key_1`)를 통해 모델이 호출되었음에도, 화면 상의 모든 키 패널(`Key_1`, `Key_2` 등)에 동시에 처리 시간(초)이 갱신되는 프론트엔드 동기화 버그가 발생했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 대안 A: 사용자 경험(UX)을 위한 스마트 폴백 유지 (기존 방식)
- **장점**: 에러 화면을 마주하지 않아 일시적인 시각적 안정감을 줌.
- **단점**: 벤치마크 및 테스트 시스템으로서 **가장 중요한 '투명성'과 '정확성'을 상실**함. 디버깅이 어려워지고 시스템 신뢰도가 급격히 하락함.

### 대안 B: 에러 투명성 확보 및 UI 타게팅 정밀화 (선택한 방식)
- **장점**: 시스템의 현재 상태(성공/실패)를 가감 없이 노출하여 디버깅 용이성 확보 및 벤치마크 신뢰도 사수. 정확한 DOM 타게팅으로 렌더링 오작동 원인 원천 차단.
- **단점**: 일시적인 API 에러 시 사용자가 에러 메시지를 직접 마주하게 됨 (단, 내부 어드민 및 벤치마크 목적의 시스템이므로 투명성이 우선시되어야 함).

## 3. 최종 해결 및 구현 (Solution)

### 3.1. Mock 폴백 제거 및 예외(Exception) 전파
`web/backend/app/services/ocr_service.py` 내부에서 API 호출 실패 시 하드코딩된 데이터를 반환하던 로직을 전면 제거했습니다.

* **변경 전**: API 실패 시 쿼터 롤백 후 Mock 텍스트 반환
* **변경 후**: 쿼터 롤백은 정상 수행하되, 마지막 에러(`last_api_error`)를 담아 과감히 `Exception`을 `raise`하도록 수정

```python
# ocr_service.py (개념 코드)
if not success:
    rollback_quota(api_key)
    raise HTTPException(
        status_code=500, 
        detail=f"OCR 분석 실패: {last_api_error}"
    )
```
이를 통해 라우터 레이어에서 에러를 그대로 캐치하여 사용자에게 명확한 실패 사유를 전달하도록 구조를 변경했습니다.

### 3.2. DOM 셀렉터 정밀화를 통한 렌더링 버그 픽스
프론트엔드(`web/frontend/static/js/admin/ocr.js`)에서 기존에는 클래스명(`document.querySelectorAll('.model-time')`)만으로 DOM을 탐색하여 모든 패널의 속도가 동기화되는 문제가 있었습니다.

이를 해결하기 위해 쿼터 카드를 동적으로 렌더링할 때 `data-key` 속성을 추가하고, 헬퍼 함수에서 **모델명과 키가 모두 일치하는 경우에만** 메트릭을 업데이트하도록 타게팅을 고도화했습니다.

```javascript
// 수정된 렌더링 타게팅 로직 (개념 코드)
function updateQuotaTimeUI(modelName, keyUsed, elapsedTime) {
    // data-model과 data-key가 정확히 일치하는 엘리먼트만 타겟팅
    const targetElement = document.querySelector(
        `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`
    );
    if (targetElement) {
        targetElement.textContent = `${elapsedTime}s`;
    }
}
```

## 4. 엔지니어링 교훈 (Takeaways)

1. **"장애를 감추는 친절함"보다 "문제를 드러내는 투명함"이 낫다**
   - 특히 벤치마크나 데이터 분석 시스템에서 Mock 데이터를 통한 방어 코드는 오히려 엔지니어의 디버깅을 방해하고 제품 신뢰도를 갉아먹습니다. 장애는 감추는 것이 아니라 정확히 드러내고 모니터링할 수 있어야 합니다.
2. **프론트엔드 상태 렌더링 시 식별자(Identifier)의 중요성**
   - 멀티 인스턴스나 멀티 키를 다루는 대시보드 UI에서는 클래스 기반의 광범위한 DOM 조작을 지양하고, 고유 식별자(`data-*` 속성 등)를 활용한 정밀한 바인딩이 필수적임을 다시 한번 확인했습니다.

이번 개선을 통해 PickSafe의 OCR 벤치마크 파이프라인은 더 높은 신뢰성을 갖추게 되었으며, 관리자는 로드밸런싱의 트래픽 분산 현황을 실시간으로 정확하게 파악할 수 있게 되었습니다.
