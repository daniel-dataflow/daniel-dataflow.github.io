안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다.

최근 저희 팀은 LLM 및 OCR 모델의 처리 효율을 극대화하기 위해 **다중 API 키 기반의 분산 처리(Load Balancing) 시스템**을 도입했습니다. 트래픽을 여러 키로 분산시켜 쿼터(Quota) 제한을 극복하는 데는 성공했지만, 시스템 운영 중 예기치 못한 예외 상황과 프론트엔드 동기화 과정에서 흥미로운 기술적 과제들을 마주하게 되었습니다.

이번 포스팅에서는 잘못 설계된 폴백(Fallback) 메커니즘이 어떻게 시스템의 신뢰성을 떨어뜨릴 수 있는지, 그리고 이를 해결하기 위해 백엔드의 예외 처리 아키텍처와 프론트엔드의 렌더링 파이프라인을 어떻게 개선했는지 공유하고자 합니다.

## 1. 문제 정의: "침묵하는 실패"가 가져온 부작용

초기 시스템은 API 호출 실패 시 서비스가 완전히 중단되는 것을 막기 위해, 시스템 내부적으로 가짜(Mock) 데이터를 반환하는 '우아한 성능 저하(Graceful Degradation)' 전략을 취하고 있었습니다. 구글 Gemini API 호출 중 `404 Not Found`나 네트워크 에러가 발생하면, 쿼터를 롤백한 뒤 가상의 성분 데이터(예: "리모넨, 리날룰...")를 강제로 리턴하는 방식이었습니다.

하지만 이 방식은 다음과 같은 치명적인 부작용을 낳았습니다.

### 1.1. 벤치마크 시스템의 신뢰성 붕괴 (Silent Failure)
저희 플랫폼은 다양한 OCR 모델의 성능을 정량적으로 비교 분석하는 벤치마크 도구의 역할도 겸하고 있습니다. 특정 모델(예: 최신 커스텀 모델)이 환경 설정 문제로 호출에 실패했음에도 불구하고, 시스템이 가짜 데이터를 정상 결과처럼 보여주면서 사용자들은 벤치마크 결과 자체를 불신하기 시작했습니다. **"실패를 숨기는 시스템은 신뢰할 수 없다"**는 뼈아픈 교훈을 얻은 순간이었습니다.

### 1.2. 과도한 예외 정보 주입으로 인한 UI 레이아웃 파괴
실패 상황임을 화면에 어떻게든 표현하려다 보니, 좁은 타이틀 뱃지 영역에 `[API 실패 / Mock 폴백]`이라는 긴 텍스트를 강제로 주입하게 되었습니다. 이는 고정된 UI 그리드를 무너뜨려 시각적 완성도를 크게 해쳤습니다.

### 1.3. 실시간 분산 처리 UI의 상태 동기화 버그
다중 API 키(예: `Key_1`, `Key_2`)가 번갈아가며 요청을 처리하는 핑퐁(Ping-Pong) 시스템이 동작할 때, 특정 키(`Key_1`)만 사용되어 처리가 완료되었음에도 화면 상에서는 사용되지 않은 다른 키(`Key_2`)의 응답 속도 지표까지 동시에 갱신되는 UI 버그가 발견되었습니다. 이는 분산 처리 현황을 투명하게 모니터링해야 하는 관리자 화면에서 치명적인 혼선을 주었습니다.

## 2. 기술적 고민과 대안 비교

문제를 해결하기 위해 저희 팀은 두 가지 핵심 아키텍처적 의사결정을 내려야 했습니다.

### 고민 1: 하드코딩된 폴백 데이터를 유지할 것인가, 예외를 전파할 것인가?

*   **대안 A: 기존 유지 및 폴백 UI 개선**
    *   *장점:* 사용자에게 에러 화면을 보여주지 않고 항상 결과물을 제공할 수 있음.
    *   *단점:* 데이터의 정밀함이 생명인 분석 플랫폼에서 거짓 정보를 제공하는 꼴이 됨. 근본적인 API 설정 오류를 디버깅하기 어려움.
*   **대안 B: Fail-Fast 및 투명한 에러 전파 (선택)**
    *   *장점:* API 실패 원인(쿼터 부족, 미지원 모델 등)을 명확히 인지할 수 있어 벤치마크 도구로서의 신뢰성 확보. 빠른 디버깅 가능.
    *   *단점:* 사용자가 에러 메시지를 마주하게 됨.

> **결정 이유:** 서비스의 도메인 특성상 **"잘못된 정보를 보여주는 것보다, 실패했음을 명확히 알리고 대안을 찾게 유도하는 것"**이 장기적인 신뢰 관점에서 훨씬 우월한 전략이라고 판단했습니다.

### 고민 2: 실시간 쿼터 UI의 갱신 버그를 어떻게 해결할 것인가?

*   **대안 A: 모델명 기반의 상태 브로드캐스팅**
    *   기존처럼 `model` 클래스명을 가진 모든 DOM 요소를 찾아 한 번에 업데이트하는 방식. 빠르지만 다중 키 분산 환경에서는 개별 키의 상태를 추적할 수 없음.
*   **대안 B: 복합 식별자(Composite Identifier) 도입 (선택)**
    *   DOM 요소에 `data-model`과 `data-key`를 동시에 부여하여, 실제 이벤트를 발생시킨 특정 모델과 특정 API 키의 쌍(Pair)만 타게팅하여 업데이트하는 방식.

## 3. 최종 해결 및 구현

### 3.1. 백엔드: 투명한 예외 처리 파이프라인 구축 (`ocr_service.py`)

기존의 은폐식 롤백 코드를 제거하고, 마지막에 발생한 실제 하부 시스템의 에러를 상위 레이어로 명확히 전파(Raise)하도록 리팩토링했습니다.

```python
# web/backend/app/services/ocr_service.py (구조화된 예시)

def process_ocr_with_balancing(image_data, model_name):
    # ... 중략 (API 키 로드밸런싱 및 쿼터 차감 로직) ...
    last_api_error = None
    
    for trial in range(MAX_RETRIES):
        api_key_node = get_optimal_api_key()
        try:
            # 실제 모델 호출 API (예시)
            result = call_external_ocr_api(image_data, model_name, api_key_node.key)
            return result
        except Exception as e:
            # 실패 시 해당 키의 쿼터는 안전하게 복구
            rollback_quota(api_key_node)
            last_api_error = e
            logger.warning(f"Key {api_key_node.name} failed: {str(e)}")
            
    # [핵심 개선] 가짜(Mock) 데이터를 반환하던 과거 루프 제거
    # 발생한 실제 에러를 상위 라우터로 전파하여 투명성 확보
    raise OCRProcessingException(
        message=f"모든 API 키가 요청에 실패했습니다. 최종 에러: {str(last_api_error)}"
    )
```

이제 라우터(`ocr.py`)는 이 예외를 잡아 프론트엔드에 `500 Internal Server Error`와 함께 구체적인 에러 메시지를 반환합니다. 화면에는 `[분석 실패] API 호출 오류 (404)...`와 같이 실패의 원인이 정직하게 표시됩니다.

### 3.2. 프론트엔드: UI 레이아웃 클린업 및 복합 Selector 최적화 (`ocr.js`)

#### ① 텍스트 오버플로우 방지 및 UI 간소화
기존의 복잡하고 장황한 에러 뱃지 텍스트를 제거하고, 사용된 API 키를 표현하는 방식을 `[Key_1]`과 같이 최소한의 정보만 깔끔하게 노출하도록 간소화했습니다.

#### ② 복합 식별자를 통한 정밀 렌더링 타게팅
DOM 요소가 어떤 모델과 어떤 API 키에 매핑되는지 식별할 수 있도록 `data-key` 속성을 템플릿 마크업에 동적으로 추가했습니다.

```javascript
// web/frontend/static/js/admin/ocr.js

// 1. 쿼터 카드 동적 생성 시 식별자 부여
function loadQuotaMetrics(metrics) {
    const cardHtml = `
        <div class="quota-card">
            <span class="model-name">${metrics.modelName}</span>
            <!-- 모델과 API 키를 조합하여 고유한 타겟 지정 가능하도록 구현 -->
            <div class="model-time" data-model="${metrics.modelName}" data-key="${metrics.keyId}">
                대기 중...
            </div>
        </div>
    `;
    // ... 렌더링 로직 ...
}

// 2. 특정 API 키 사용 결과만 타게팅하여 업데이트
function updateQuotaTimeUI(modelName, keyUsed, duration) {
    // [개선] data-model과 data-key가 동시에 일치하는 단 하나의 DOM만 셀렉팅
    const targetSelector = `.model-time[data-model="${modelName}"][data-key="${keyUsed}"]`;
    const targetElement = document.querySelector(targetSelector);
    
    if (targetElement) {
        targetElement.textContent = `${duration}s`;
        targetElement.classList.add('highlight-update'); // 실시간 시각 효과
    }
}
```

## 4. 엔지니어링 교훈 (Takeaways)

1.  **'우아한 실패(Graceful Failure)'가 항상 정답은 아니다**  
    사용자 경험(UX) 측면에서 시스템 에러를 숨기는 것이 대개 권장되지만, 정확성과 데이터 정밀도가 핵심 가치인 벤치마크 및 관리 시스템에서는 **투명하게 에러를 드러내는 것(Fail-Fast)**이 시스템의 신뢰도를 지키는 가장 좋은 방법입니다.
2.  **느슨한 DOM 선택자는 상태 버그의 주범이다**  
    마이크로서비스나 비동기 분산 시스템의 상태를 프론트엔드에 실시간으로 반영할 때는, DOM 선택자의 범위를 엄격하게 제한해야 합니다. 엔티티를 유일하게 식별할 수 있는 복합 Key(`data-*` 속성 활용) 설계는 렌더링 오버헤드를 줄이고 데이터 일관성을 지켜줍니다.
3.  **UI 설계 시 정보의 밀도를 제어해야 한다**  
    디자인 레이아웃을 깰 정도로 많은 정보를 좁은 UI에 구겨 넣기보다는, 핵심 식별 정보만 깔끔하게 시각화하고 상세한 예외 정보는 툴팁이나 로그 디테일 영역으로 분리하는 것이 바람직합니다.

저희 PickSafe 팀은 앞으로도 분산 환경에서 발생할 수 있는 사소한 싱크 오차와 예외 케이스들을 집요하게 추적하여, 가장 신뢰할 수 있는 플랫폼을 만들어 나가겠습니다. 감사합니다.
