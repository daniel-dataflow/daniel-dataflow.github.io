## 들어가는 말: 다중 키 분산 시스템의 역설

LLM 및 Vision OCR 서비스를 대규모로 운영할 때 필연적으로 마주치는 병목은 **API 쿼터(Quota)와 처리 속도 제약(Rate Limit)**입니다. 

PickSafe 팀은 이러한 한계를 극복하기 위해 다중 API 키를 지능적으로 순환·배분하는 **분산 핑퐁(Ping-Pong) 로드 밸런싱 아키텍처**를 설계했습니다. 특정 키에 트래픽이 몰리지 않도록 가용 쿼터를 추적하고 최적의 키로 라우팅하는 구조입니다.

하지만 신규 모델 실험 및 벤치마크 단계에서 예상치 못한 문제가 발생했습니다. **"시스템이 실패를 숨기려다 신뢰성을 잃는 현상"**과 **"분산 상태가 UI에 부정확하게 반영되는 동기화 버그"**였습니다. 

이번 포스팅에서는 잘못 설계된 폴백(Fallback) 메커니즘을 걷어내고, 시스템의 신뢰성과 투명한 관측 가능성(Observability)을 확보한 엔지니어링 과정을 공유합니다.

---

## 1. 문제 정의 (Problem Statement)

### 1.1. '친절한' Mock 데이터가 초래한 벤치마크 신뢰성 붕괴
초기 시스템은 API 호출 실패(존재하지 않는 최신 커스텀 모델 호출로 인한 `404 Not Found`, 네트워크 타임아웃 등) 발생 시, 서비스 중단을 막기 위해 사전 정의된 Mock 성분 데이터를 반환하도록 구현되어 있었습니다.

```text
[요청 실패] -> [쿼터 롤백] -> [하드코딩된 Mock 데이터 반환] -> [사용자는 정상 응답으로 오인]
```

- **문제점**: 관리자 및 엔지니어링 벤치마크 도구 관점에서, 실패 원인(모델 미지원, 엔드포인트 설정 오류 등)이 Mock 데이터 뒤로 숨겨졌습니다. 실제 모델의 성능과 응답을 객관적으로 측정해야 하는 시스템의 존재 목적을 훼손한 것입니다.

### 1.2. 땜질식 UI 대응으로 인한 레이아웃 파괴
Mock 데이터 반환 여부를 프론트엔드에 알리기 위해 좁은 타이틀 뱃지 영역에 `[API 실패 / Mock 폴백]`이라는 긴 스트링을 강제로 주입했습니다. 이로 인해 반응형 UI 그리드가 깨지고 텍스트가 오버플로우되는 시각적 결함이 발생했습니다.

### 1.3. 프론트엔드 렌더링 타게팅 오류로 인한 분산 관측 불가
멀티키 로드 밸런서가 `Key_1`을 선택해 작업을 성공적으로 마쳤음에도, UI 상에서는 대기 중이던 `Key_2` 패널의 응답 속도까지 동일하게 갱신되는 현상이 발견되었습니다. 프론트엔드 셀렉터가 모델 식별자(`data-model`)만으로 DOM을 탐색하여 발생한 버그였습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off & Decisions)

### Q1. "Graceful Degradation(우아한 성능 저하)" vs "Fail-Fast(실패 즉시 노출)"
일반적인 엔드유저 대면 서비스라면 캐싱된 데이터나 Mock 데이터를 내려주는 Graceful Degradation이 합리적일 수 있습니다. 

* **대안 A: Mock 폴백 유지 및 상세 로그 분리**
  * *장점*: 프론트엔드에서 일관된 포맷의 데이터를 수신하므로 예외 처리 부담이 적음.
  * *단점*: 벤치마크/관리 시스템 특성상 '정상 동작'으로 오인하여 잘못된 비즈니스 의사결정 유발.
* **대안 B (선택): 쿼터 원자적 롤백 후 투명한 Exception 전파 (Fail-Fast)**
  * *이유*: 벤치마크 도구의 핵심 가치는 **'정확한 측정과 결함의 즉각적 발견'**에 있습니다. 사용된 쿼터는 원자적으로 롤백(Rollback)하되, 발생한 예외(404, 429 등)는 상위 계층으로 명확히 전달하여 화면에 가감 없이 노출하는 방식이 시스템 신뢰도에 부합합니다.

### Q2. 렌더링 상태 동기화 방식
* **대안 A: 전역 상태 관리 도입 후 전체 패널 리렌더링**
  * *단점*: 단순 지표 갱신을 위해 과도한 리렌더링 오버헤드 발생.
* **대안 B (선택): 복합 속성(Composite Data Attributes) 기반 정밀 타게팅**
  * *이유*: `data-model`과 `data-key`를 조합한 정확한 DOM 타게팅으로 최소한의 비용으로 정확한 상태를 갱신.

## 3. 해결 및 구현 (Implementation)

### 3.1. 백엔드: 투명한 예외 전파 및 쿼터 정합성 보장
API 호출 실패 시 차감되었던 쿼터를 즉시 안전하게 롤백한 후, 하단에 존재하던 Mock 반환 로직을 제거했습니다. 실제 서드파티 API에서 발생한 상세 에러를 캡슐화하여 상위 라우터로 전달했습니다.

```python
# 서비스 계층 의사코드 (Sanitized)
try:
    api_key = quota_manager.get_optimal_key()
    response = call_vision_ocr_api(model=target_model, key=api_key)
    return parse_response(response)
except ExternalApiException as e:
    # 1. 쿼터 정합성 유지 (차감 취소)
    quota_manager.rollback_quota(api_key)
    
    # 2. Mock 반환 대신 실제 에러 컨텍스트를 명확히 전파
    logger.error(f"OCR Pipeline Failed for key {api_key.id}: {str(e)}")
    raise BenchmarkExecutionException(f"[분석 실패] {e.status_code}: {e.message}")
```

### 3.2. 프론트엔드: 정밀 타게팅 렌더링 및 UI 경량화
DOM 엘리먼트 생성 시 `data-key` 메타데이터를 바인딩하고, 갱신 헬퍼 함수에서 두 속성을 모두 만족하는 노드만 선별적으로 업데이트하도록 개선했습니다.

```javascript
// 프론트엔드 렌더링 타게팅 개선 (Sanitized)
function updateQuotaMetricUI(modelName, keyUsed, responseTimeSec) {
  // data-model과 data-key가 모두 일치하는 단일 엘리먼트 정밀 타게팅
  const targetElement = document.querySelector(
    `.model-time[data-model="${CSS.escape(modelName)}"][data-key="${CSS.escape(keyUsed)}"]`
  );

  if (targetElement) {
    targetElement.textContent = `${responseTimeSec}s`;
  }
}
```

또한, 뱃지 텍스트를 `[Key_1]` 형태로 간결화하여 UI 컨테이너의 가독성과 레이아웃 안정성을 확보했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

1. **컨텍스트에 맞는 실패 전략(Failure Strategy)의 중요성**
   고객 대면 서비스에서의 '장애 격리용 폴백'이 벤치마크 및 관리 도구에서는 오히려 시스템의 '침묵하는 독'이 될 수 있습니다. 시스템의 성격(Product vs. Benchmarking Tool)에 맞춰 Fail-Fast와 Graceful Degradation 중 올바른 전략을 선택해야 합니다.

2. **분산 시스템의 관측 가능성(Observability)은 UI 정합성에서 완성된다**
   백엔드에서 아무리 완벽하게 로드 밸런싱(핑퐁)을 처리하더라도, 이를 표현하는 대시보드가 잘못된 엘리먼트를 가리키면 운영자는 시스템 결함으로 인지합니다. 분산 상태를 추적할 때는 식별자(Identifier)를 프론트엔드 컴포넌트 단위까지 일관되게 전파해야 합니다.

3. **신뢰할 수 있는 데이터 파이프라인 구축**
   에러를 숨기지 않고 투명하게 노출함으로써 지원되지 않는 모델 식별, 네트워크 이슈 등 외부 의존성 문제를 즉각 파악하고 수정할 수 있는 견고한 개발 루프를 완성했습니다.
