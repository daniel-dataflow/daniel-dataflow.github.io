안녕하세요. PickSafe 백엔드 엔지니어링 팀입니다.

최근 클라우드 기반 관리형 데이터베이스(DB)를 운영하던 중, 예기치 못한 Compute 및 Network 쿼터 초과로 인해 데이터웨어하우스(DW) 접근이 차단되는 장애를 마주했습니다. 

이번 글에서는 해당 장애를 해결하기 위해 **자동 Failover(예비 DB 우회) 시스템**을 구축하는 과정에서 직면했던 아키텍처의 허점을 분석하고, **"데이터의 성격에 따른 DB 역할 분리"**를 통해 시스템의 안정성과 정합성을 높인 의사결정 과정을 공유하고자 합니다.

---

## 1. 배경: 클라우드 DB 쿼터 초과 장애와 Failover의 필요성

우리 시스템은 대규모 로그와 외부 연동 데이터 처리를 위해 메인 DW DB를 운용하고 있습니다. 그러던 중 리소스 사용량이 쿼터 한계에 도달하면서 DW 접근이 전면 차단되는 서비스 중단 위기를 겪었습니다.

근본적인 인프라 확장 외에도, **"만약 DW DB에 장애가 발생하더라도 서비스가 멈추지 않도록 만들 수 없을까?"**라는 고민에서 출발해 예비 DW(Secondary DW)를 두어 자동 전환하는 **DW Failover 시스템** 설계에 착수했습니다.

### 💡 초기 설계한 Failover 및 자동 복구 메커니즘
1. **자동 우회(Failover):** 메인 DW 접속 실패 감지 시, 즉시 예비 DW(`DATABASE_DW_URL_2`)로 커넥션을 우회.
2. **자동 원상 복구(Recovery Check):** 백그라운드 스레드(`check_primary_db_recovery`)를 통해 주기적으로 메인 DW의 연결 가능 여부를 확인. 매월 1일 쿼터가 갱신되는 점을 고려해, 메인 DB 복구가 확인되면 서버 재시작을 유도하여 정상화.
3. **운영자 가시성 확보:** 현재 예비 DB로 우회 접속 중인 경우, 어드민 인프라 모니터링 화면에 명시적인 태그(예: `"개발 DW2 (DEV)"`, `"운영 DW2 (PROD)"`)를 노출하여 운영 인지가 즉시 가능하도록 조치.

하지만, 이 자동 전환 시스템을 구현하고 테스트하던 도중 **아키텍처 상의 치명적인 모순**을 발견하게 됩니다.

---

## 2. 마주한 문제점: DW에 '상태(State)'가 존재한다

Failover 시스템은 "모든 DW DB의 데이터는 동일하다"는 가정하에 움직입니다. 그러나 우리 시스템의 실제 구조를 뜯어보니 위험 요소가 있었습니다.

1. **상태 데이터의 혼재 (`seeding_schedule_settings`):**
   * 식약처 자동 수집 크론잡의 '예약 설정'을 관리하는 테이블이 메인 운영 DB가 아닌 DW DB에 저장되고 있었습니다.
   * 만약 메인 DW 쿼터 초과로 예비 DW로 우회하게 될 경우, **예비 DW에는 해당 설정 데이터가 비어있기 때문에 크론잡이 오작동하거나 예약이 초기화**되는 심각한 비즈니스 로직 장애가 발생할 상황이었습니다.
2. **성분 마스터 데이터의 불필요한 이중화 (`ingredients_master`):**
   * 핵심 도메인 데이터인 성분 마스터 테이블이 메인 DB와 DW DB 양쪽에 이중화되어 기록되고 있었습니다.
   * Failover 발생 시 양쪽 DB 간 데이터 싱크가 틀어지면서 **데이터 정합성이 심각하게 훼손**될 우려가 있었습니다.

즉, **"분석 및 적재용"**으로 써야 할 DW DB에 **"서비스 상태(State)와 핵심 마스터 데이터"**가 혼재되어 있었던 것이 근본 원인이었습니다.

## 3. 기술적 고민과 최종 결정: DW의 역할을 순수화하다

이 문제를 해결하기 위해 두 가지 대안을 놓고 고민했습니다.
* **대안 A:** 예비 DW로 넘어갈 때 마스터 데이터와 설정 테이블을 실시간으로 싱크맞추는 동기화 레이어 구축.
  * *Trade-off:* 복잡도가 급격히 상승하며, 네트워크 장애 시 싱크 실패로 인한 사이드펙 발생 우려 큼.
* **대안 B:** DW DB의 역할을 재정의하고, 상태 데이터를 메인 운영 DB로 전면 이관.
  * *Trade-off:* 초기 코드 리팩토링 및 데이터 migration 공수가 발생하나, 장기적으로 아키텍처가 매우 견고해짐.

우리는 **대안 B**를 선택했습니다. 데이터 아키텍처의 원칙으로 돌아가기로 한 것입니다.

### 🛠️ 최종 아키텍처 결정 사항
1. **DW DB 역할의 엄격한 재정의:**
   * DW DB는 철저히 **"휘발되어도 무방한 로그, 모니터링 데이터, 외부 연동 Staging 데이터"** 전용으로만 격리합니다.
2. **핵심 상태 데이터 메인 DB 이관:**
   * `seeding_schedule_settings` (예약 설정) 및 `ingredients_master` (성분 마스터 이중화본) 등 상태 유지가 필수인 데이터는 DW에서 즉각 Drop 및 제거했습니다.
   * 해당 데이터들을 **메인 운영 DB로 완전 이관 및 통합 관리**하여, 향후 어떤 DB 인프라 이슈로 우회가 일어나더라도 비즈니스 로직과 데이터 정합성이 100% 유지되도록 설계했습니다.

## 4. 기대 효과 및 엔지니어링 Takeaway

이번 아키텍처 개선을 통해 얻은 성과는 다음과 같습니다.

* **견고한 고가용성(HA) 확보:** 클라우드 DB의 리소스 쿼터 초과 등 인프라 장애 발생 시에도, 비즈니스 로직의 유실 없이 안전하게 데이터 파이프라인을 우회 가동할 수 있게 되었습니다.
* **데이터 무결성(Integrity) 보장:** 분산 환경 및 Failover 상황에서도 핵심 마스터 데이터와 스케줄 설정값이 흔들리지 않도록 보장합니다.
* **관심사 분리(Separation of Concerns):** DW DB가 순수한 분석/적재 용도의 가벼운 구조로 변경됨에 따라, 향후 DB 유지보수성과 확장성이 극대화되었습니다.

### 💡 오늘의 교훈 (Takeaway)
> **"인프라 레벨의 Failover(우회 시스템)를 구축하기 전에, 먼저 데이터의 성격(State vs Stateles/Log)부터 철저히 분리해야 한다."**

아무리 훌륭한 자동 복구 시스템을 구축하더라도, 시스템의 '상태(State)'가 잘못된 곳에 저장되어 있다면 반쪽짜리 복구에 불과합니다. 이번 경험을 통해 데이터 아키텍처의 기본 원칙인 '관심사의 분리'가 인프라 안정성 확보의 전제 조건임을 다시 한번 깨달았습니다.
