시스템이 성장하면서 직면하는 가장 흔하지만 뼈아픈 고통 중 하나는 **‘데이터베이스의 한계’**에 부딪히는 순간입니다. 

최근 저희 PickSafe 팀은 데이터 웨어하우스(DW)로 사용 중이던 Cloud DB(Neon DB)의 컴퓨팅 및 네트워크 쿼터 초과로 인해 DW 접근이 일시적으로 차단되는 장애를 겪었습니다. 단순히 "사양을 높이거나 예비 DB를 붙이면 되겠지"라는 안일한 생각으로 접근했다가, 시스템 내부에 숨겨져 있던 **심각한 아키텍처적 부채(Technical Debt)**를 발견하게 되었습니다.

이번 포스팅에서는 일시적인 장애를 극복하기 위해 **자동 페일오버(Failover) 및 복구 시스템을 구축한 과정**과, 그 과정에서 발견한 **데이터 정합성 문제를 근본적으로 해결하기 위해 데이터 아키텍처를 어떻게 재구조화했는지**에 대한 엔지니어링 여정을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 단순한 쿼터 초과가 가져온 아키텍처의 민낯

처음 장애가 발생했을 때의 해결책은 심플해 보였습니다. 메인 DW(Primary DW)가 쿼터 초과로 죽을 때를 대비해, 예비 DW(Secondary DW)를 준비하고 장애 발생 시 접속 경로를 우회(Failover)시키는 것이었습니다.

하지만 이 자동 전환 시스템을 설계하던 중, 시스템의 안정성을 통째로 흔들 수 있는 **두 가지 치명적인 설계 결함**이 수면 위로 드러났습니다.

### 문제 1. 상태(State) 데이터의 부적절한 위치
자동 수집 스케줄러의 예약 설정을 관리하는 `seeding_schedule_settings` 테이블이 메인 운영 DB가 아닌 **DW DB에 저장**되고 있었습니다. 
만약 메인 DW가 다운되어 예비 DW로 페일오버되면, 예비 DW에는 해당 설정 데이터가 없기 때문에 **배치 크론잡이 오작동하거나 기존 예약이 모두 초기화되는 대형 장애**로 이어지는 구조였습니다.

### 문제 2. 핵심 마스터 데이터의 불필요한 이중 기록 (Split-Brain 위험)
성분 데이터의 기준이 되는 `ingredients_master` 테이블이 메인 DB와 DW DB 양쪽 모두에 이중화되어 기록되고 있었습니다. 
이 상태에서 예비 DW로 커넥션이 넘어가면 양쪽 DW 간의 데이터 불일치가 발생하고, 종국에는 **어떤 데이터가 진짜 신뢰할 수 있는 데이터인지 알 수 없는 정합성 파괴 상태**에 직면하게 되는 위험이 있었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 두 가지 방향성을 두고 치열하게 토론했습니다.

| 비교군 | 안 1. 예비 DW까지 완벽히 복제하기 (Replication) | 안 2. 데이터 역할 정의 및 아키텍처 재구조화 (Refactoring) |
| :--- | :--- | :--- |
| **방법** | 예비 DW에도 실시간으로 상태 데이터와 마스터 데이터를 동기화하는 파이프라인 구축 | DW의 역할을 재정의하고, 상태 및 마스터 데이터를 메인 DB로 이관/통합 |
| **장점** | 기존 코드의 쿼리나 스키마 수정 없이 인프라 레이어에서 해결 가능 | **Single Source of Truth(단일 진실 공급원)** 확보, DW 비용 절감, 궁극적인 아키텍처 정화 |
| **단점** | 동기화 지연(Lag) 가능성, 인프라 복잡도 급증, 추가적인 동기화 비용 발생 | 일시적인 데이터 이관 공수 필요, 관련 비즈니스 로직 수정 필요 |

### 우리의 선택: 안 2. "데이터 아키텍처의 근본적 리팩토링"
인프라의 복잡도를 높여 문제를 덮는 것보다는, **"데이터의 성격에 맞게 제 자리를 찾아주는 것"**이 장기적으로 시스템의 생존에 유리하다고 판단했습니다. 

* **OLTP(메인 DB):** 상태 유지(Stateful), 비즈니스 핵심 트랜잭션, 마스터 데이터 관리 담당.
* **OLAP(DW DB):** 무상태(Stateless), 휘발되어도 무방한 로그, 모니터링 데이터, 외부 연동 임시(Staging) 데이터만 담당.

## 3. 최종 해결 및 아키텍처 구현 (Implementation)

이 결정을 바탕으로 우리는 단기적 생존을 위한 **페일오버 시스템 구축**과 장기적 안정을 위한 **데이터 이관 작업**을 동시에 진행했습니다.

### ① 회복 탄력성을 지닌 자동 페일오버 및 복구(Failback) 시스템

FastAPI 백엔드 애플리케이션에 메인 DW 접속 실패 시 예비 DW로 즉시 우회하는 로직을 적용했습니다. 또한, 쿼터가 갱신되는 시점에 자동으로 원상 복구(Failback)되도록 백그라운드 스레드를 설계했습니다.

```python
# 이해를 돕기 위해 간소화한 아키텍처 개념 코드입니다.
import threading
import time

class DatabaseConnectionManager:
    def __init__(self):
        self.current_dw_url = DATABASE_DW_URL_1
        self.is_fallback = False

    def handle_failover(self):
        print("Primary DW Connection Failed. Switching to Secondary DW...")
        self.current_dw_url = DATABASE_DW_URL_2
        self.is_fallback = True

    def check_primary_db_recovery(self):
        """6시간마다 Primary DW의 상태를 체크하고, 복구 시 안정적인 서버 재시작을 유도합니다."""
        while True:
            time.sleep(21600)  # 6 hours
            if self.is_fallback and is_primary_dw_healthy():
                print("Primary DW is recovered. Initiating safe restart for rollback...")
                trigger_graceful_restart()
```

* **자가 치유(Self-Healing):** 백그라운드 데몬 스레드(`check_primary_db_recovery`)가 6시간 주기로 메인 DW의 헬스 체크를 수행합니다.
* **가시성 확보(Visibility):** 어드민 페이지 내 인프라 모니터링 대시보드를 추가하여, 현재 시스템이 예비 DB로 작동 중일 경우 운영자에게 **"개발 DW2 (DEV)"**, **"운영 DW2 (PROD)"**와 같은 경고 메시지를 명시적으로 노출하도록 했습니다.

### ② 데이터 다이어트 및 메인 DB 이관

* **Drop & Migrate:** DW DB에 존재하던 `seeding_schedule_settings` 테이블과 이중화되어 있던 `ingredients_master` 테이블을 DW에서 완전히 Drop했습니다.
* **Single Source of Truth 구축:** 해당 테이블들을 메인 운영 DB(DB A)로 완전 이관하여 단일 뷰로 관리하게 했습니다. 이로써 어떤 DW로 페일오버가 일어나더라도 핵심 서비스 동작과 데이터 정합성에는 아무런 영향이 없게 되었습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 장애 대응과 아키텍처 개선 작업을 통해 우리 팀은 값진 교훈을 얻었습니다.

1. **장애는 아키텍처의 악취(Smell)를 맡을 수 있는 가장 좋은 기회다:**
   만약 단순히 DB 쿼터만 늘리고 넘어갔다면, 추후 더 큰 스케일에서 원인 모를 데이터 정합성 깨짐 현상으로 고통받았을 것입니다. 장애가 발생했을 때 임시방편(Hardening)에 그치지 않고 근본 원인을 파고드는 태도의 중요성을 다시금 깨달았습니다.

2. **데이터의 "Life Cycle"과 "역할"을 엄격히 구분하라:**
   모든 DB가 동일한 신뢰 수준을 가질 필요는 없습니다. 분석용 데이터웨어하우스는 언제든 날아가고 새로 구축할 수 있는 'Stateless'한 성격을 유지해야만, 인프라의 유연성(Flexibility)을 극대화할 수 있습니다.

3. **가시성(Visibility)이 곧 안정성이다:**
   자동 페일오버만큼 중요한 것은 "현재 시스템이 비정상 경로(예비 DB)로 돌고 있음"을 인간 운영자에게 명확히 인지시키는 것입니다. 모니터링 화면에 이를 명시함으로써 운영 리스크를 크게 줄였습니다.

결과적으로 PickSafe는 **"인프라 리스크에 무중단으로 대응하면서도 데이터 무결성을 100% 보장하는"** 한 단계 더 성숙한 시스템으로 진화했습니다. 앞으로도 저희 팀은 타협 없는 엔지니어링으로 고객에게 가장 안전한 서비스를 제공하기 위해 노력하겠습니다.
