안녕하세요. PickSafe 백엔드 엔지니어링 팀입니다. 

최근 시스템을 운영하던 중, 클라우드 기반 데이터웨어하우스(DW) DB의 Compute 및 Network 쿼터 초과로 인해 DW 접근이 차단되는 예기치 못한 인프라 장애를 마주했습니다. 단순한 서비스 중단을 넘어, 데이터 파이프라인의 안정성과 아키텍처의 근본적인 결함을 돌아보게 된 계기였습니다.

이번 글에서는 해당 장애를 해결하기 위해 **자동 Failover 및 복구 시스템**을 도입하고, 이 과정에서 발견된 아키텍처의 구조적 모순을 해결하기 위해 **데이터를 재배치한 아키텍처 의사결정 과정(ADR)**을 공유하고자 합니다.

---

## 1. Problem: 쿼터 초과 장애와 숨겨진 아키텍처의 함정

장애 원인은 명확했습니다. 외부 관리형 DW DB의 컴퓨팅 및 네트워크 리소스 쿼터가 한계에 도달하면서 커넥션이 거부되었고, 이는 데이터 수집 및 분석 파이프라인 전반의 마비로 이어졌습니다.

이에 대응하기 위해 즉각적으로 **예비 DW(Secondary DW)**를 준비하고, 메인 DW 장애 시 자동으로 우회 접속하는 Failover 시스템 설계에 착수했습니다. 하지만 구현 과정에서 아키텍처 상의 치명적인 위험 요소 두 가지를 추가로 발견했습니다.

1. **상태(State) 데이터의 DW 혼재 문제**
   - 외부 수집 자동화 스케줄을 관리하는 설정 테이블이 메인 DW DB 내부에 저장되고 있었습니다.
   - 만약 메인 DW 쿼터 초과로 예비 DW로 우회할 경우, 예비 DW에는 해당 설정 데이터가 비어있기 때문에 스케줄링 크론잡이 오작동하거나 예약 설정이 초기화되는 문제가 발생할 예정이었습니다.
2. **성분 마스터 데이터의 불필요한 이중화와 정합성 위험**
   - 핵심 도메인 데이터인 '성분 마스터' 데이터가 메인 운영 DB와 DW DB 양쪽에 이중화되어 기록되고 있었습니다.
   - 이 상태로 DW 우회가 일어날 경우, 메인 DB와 예비 DW 간의 데이터 불일치가 발생해 서비스 정합성이 심각하게 훼손될 우려가 있었습니다.

즉, **"분석 및 적재 전용이어야 할 DW에 핵심 상태(State) 데이터가 섞여 있어, DB Failover 시 서비스 정합성이 깨지는 구조"**가 근본적인 문제였습니다.

---

## 2. Trade-off & Decision: 아키텍처 재구조화와 자동 Failover 전략

이 문제를 해결하기 위해 두 가지 축(인프라적 가용성 확보 + 데이터 구조의 도메인 분리)에서 의사결정을 내렸습니다.

### ① 자동 Failover 및 스마트 복구(Self-Healing) 시스템 도입
* **우회 접속:** 메인 DW 커넥션 실패 시, 예비 DW 커넥션 URL로 즉시 트래픽을 우회하도록 구현했습니다.
* **자동 원상 복구 (`check_primary_db_recovery`):** 백그라운드 스레드를 통해 6시간 주기로 쿼터가 갱신된 메인 DW에 헬스체크를 수행합니다. 매월 1일 등 쿼터가 리셋되어 메인 DB 정상 접속이 확인되면, 시스템을 안전하게 원상 복구(`check_primary_db_recovery`)하도록 설계했습니다.
* **운영 가시성 확보:** 인프라 모니터링 대시보드에서 현재 시스템이 예비 DW를 바라보고 있을 경우, 운영자가 즉시 인지할 수 있도록 명시적인 레이블링(`개발 DW2 (DEV)`, `운영 DW2 (PROD)`)을 적용했습니다.

### ② DW DB의 역할 재정의 및 핵심 데이터 마이그레이션
가장 중요한 결정은 **DW DB의 역할을 순수 분석/적재 용도로 엄격히 제한**하는 것이었습니다.

* **상태 데이터 제거:** DW DB에 저장되던 예약 설정 테이블과 성분 마스터 이중화본을 DW에서 즉각 Drop 및 제거했습니다.
* **메인 DB로의 통합:** 해당 데이터들을 모두 **메인 운영 DB로 완전 이관 및 통합 관리**하도록 구조를 변경했습니다. 

> **Trade-off 고찰:** 
> 데이터를 메인 DB로 일원화할 경우 DW의 분산 처리가 일부 제한될 수 있으나, **'데이터 정합성 보장'**과 **'장애 시 무중단 페일오버'**라는 비즈니스 연속성 가치가 시스템 아키텍처 상 훨씬 우선순위에 있다고 판단했습니다. 결과적으로 DW는 일시적으로 유실되어도 무방한 **"로그, 모니터링, 외부 연동 Staging 데이터"**만을 다루는 가벼운 저장소로 거듭나게 되었습니다.

## 3. Takeaway: 엔지니어링 교훈

이번 작업을 통해 얻은 기술적 교훈은 명확합니다.

1. **DB의 역할(Role)을 명확히 분리하라:** 분석용 DB(DW)와 트랜잭션/상태 관리용 DB(Operational DB)의 경계가 흐려지면, 인프라 장애 대응(Failover) 시 데이터 정합성이라는 거대한 부채로 돌아옵니다.
2. **장애 대응은 인프라와 데이터 모델링의 결합으로 완성된다:** 단순히 커넥션을 우회하는 인프라스트럭처 레벨의 대응만으로는 부족하며, 그 커넥션이 바라보는 '데이터의 상태(State)'까지 고려해야 진정한 High Availability(고가용성)를 달성할 수 있습니다.

이번 아키텍처 개선 덕분에, 향후 유사한 인프라 쿼터 초과 장애가 발생하더라도 서비스 무중단(또는 최소화된 중단)으로 데이터 파이프라인 우회 가동이 가능해졌습니다. 또한, 어떠한 DB 분산 환경에서도 핵심 데이터의 무결성이 100% 보장되는 단단한 기반을 다지게 되었습니다.

앞으로도 PickSafe는 안정적이고 확장 가능한 백엔드 아키텍처를 만들어 나가겠습니다. 감사합니다.
