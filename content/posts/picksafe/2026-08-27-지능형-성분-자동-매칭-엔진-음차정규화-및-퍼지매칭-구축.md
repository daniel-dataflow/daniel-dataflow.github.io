안녕하세요, PickSafe 백엔드 엔지니어링 팀입니다. 

서비스를 운영하다 보면 **"데이터의 미묘한 차이"** 때문에 비즈니스 가치가 훼손되는 순간을 마주하곤 합니다. PickSafe의 핵심 기능 중 하나는 화장품 패키지 라벨을 카메라로 스캔하여 성분을 분석하고 알레르기 유발 성분을 안내하는 것입니다. 

하지만 사용자가 제품을 스캔했을 때, 식약처 공인 DB에 분명히 존재하는 성분임에도 불구하고 **"확인 불가 성분"**으로 분류되어 사용자 경험(UX)을 해치는 사례가 종종 발생했습니다. 

오늘은 저희 팀이 이 문제를 해결하기 위해 **단순 DB 조회 방식에서 벗어나, 언어학적 음차 규칙과 수학적 알고리즘을 결합한 '지능형 성분 자동 매칭 엔진'을 설계하고 성능을 극대화한 여정**을 공유하고자 합니다.

---

## 1. 문제 정의: "같은 성분, 다른 이름"의 늪

사용자가 화장품 라벨을 스캔하면 OCR(광학 문자 인식) 엔진을 통해 성분명 텍스트를 추출합니다. 그러나 원본 성분 사전 DB와 OCR 추출 결과 사이에는 다음과 같은 괴리가 있었습니다.

1. **외래어 표기법의 다양성 (음차 변형)**
   * 라벨의 `시카라이드아이소머레이트` vs 식약처 DB의 `사카라이드아이소머레이트` (`시` vs `사`)
   * 라벨의 `알파-아이소메틸아이오논` vs 식약처 DB의 `알파-아이소메틸이오논` (`아이오논` vs `이오논`)
2. **단순 포맷 차이**
   * 불필요한 띄어쓰기, 하이픈(`-`), 언더바(`_`), 특수문자 삽입 등
3. **OCR 자체의 오인식**
   * 인쇄 번짐, 굴곡진 용기 표면 등으로 인한 자모음 누락 또는 오타

전체 성분 수가 20,000개가 넘는 상황에서, 이 모든 변형 케이스를 일일이 하드코딩(Synonym Table 작성)하는 것은 지속 불가능한 유지보수의 지옥을 의미했습니다. 우리는 **규칙 기반(Rule-based) 정규화와 수학적 유사도 측정 알고리즘을 결합한 자동 매칭 파이프라인**이 필요했습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 백엔드 팀은 세 가지 아키텍처 대안을 두고 치열하게 고민했습니다.

### 대안 A: 데이터베이스(RDB) 유사도 쿼리 (LIKE 및 Full-Text Search)
* **장점**: 구현이 단순하며 별도의 메모리 관리가 필요 없음.
* **단점**: 사용자 트래픽이 몰릴 때 DB CPU 부하가 급증함. 특히 한글 형태소 분석이나 유사도 계산을 SQL 레벨에서 처리하는 것은 쿼리 지연 시간(Latency)을 유발함.

### 대안 B: 대형 언어 모델(LLM) 또는 임베딩 기반 의미론적 매칭
* **장점**: 오타나 문맥적 의미를 가장 유연하게 파악함.
* **단점**: API 호출 비용이 발생하며, 무엇보다 실시간 스캔 결과 반환에 필요한 **ms(밀리초) 단위의 응답 속도**를 보장할 수 없음. 

### 대안 C: O(1) 인메모리 이중 색인 + 4단계 매칭 파이프라인 (선택)
* **장점**: 20,000여 개의 성분 데이터는 인메모리(RAM)에 캐싱하기에 매우 적은 용량임. 이를 해시맵(HashMap) 구조로 이중 색인화하여 DB 부하를 0으로 줄이고, 단 1ms 내외로 매칭을 완료할 수 있음. 
* **결정**: 서비스의 실시간성과 고성능 처리를 위해 **대안 C**를 선택하고 가벼우면서도 강력한 파이프라인을 구축하기로 했습니다.

## 3. 지능형 매칭 4단계 파이프라인 설계

저희가 설계한 최종 매칭 파이프라인의 아키텍처는 다음과 같습니다. 낭비되는 연산을 최소화하기 위해 '가장 비용이 저렴한 단계'부터 순차적으로 통과하도록 구성했습니다.

```
[📷 OCR 성분명 추출]
         │
         ▼
[1단계: 정규화 키(Canonical Key) 변환] ── (정확 일치 시 즉시 반환) ──> [🎉 매칭 완료]
         │ (미매칭 시)
         ▼
[2단계: 화장품 음차 형태소 정규화] ──── (정형화 규칙 일치 시) ─────> [🎉 매칭 완료]
         │ (미매칭 시)
         ▼
[3단계: N-gram / SequenceMatcher] ─── (유사도 88% 이상 탐색 시) ──> [🎉 매칭 완료]
         │ (미매칭 시)
         ▼
[4단계: 공공 API 실시간 조회 & 캐싱]
```

### ① 1단계: Canonical Key (정규화 키) 생성
가장 먼저 텍스트의 잡음(Noise)을 제거합니다. 대소문자 통일, 공백 제거, 하이픈/괄호/특수기호를 제거하여 비교 표준형을 만듭니다.
* 예: `알파-아이소메틸아이오논` ➔ `알파아이소메틸아이오논`

### ② 2단계: 화장품 음차 형태소 정규화 (Phonetic Normalization)
화장품 성분 사전의 명명 규약(INCI 명칭 전환 규약)을 분석하여, 자주 발생하는 **15대 음차 변형 패턴**을 정규 표현식 기반의 양방향 규칙으로 정의했습니다. 

이 규칙을 통해 입력된 텍스트를 대표형(Canonical Form)으로 치환합니다.
* `아이소` ↔ `이소` (Iso)
* `시카라이드` ↔ `사카라이드` (Saccharide)
* `아이오논` ↔ `이오논` (Ionone)
* `하이드록시` ↔ `히드록시` (Hydroxy)
* `글라이콜` ↔ `글리콜` (Glycol)

이 단계 덕분에 `시카라이드아이소머레이트`가 입력되어도 `사카라이드이소머레이트`라는 표준 성분명을 완벽하게 찾아낼 수 있게 되었습니다.

### ③ 3단계: 초고속 O(1) 인메모리 이중 색인 (Dual Indexing)
성분 검색 속도를 극대화하기 위해, 애플리케이션(FastAPI) 기동 시점에 메인 DB의 성분 마스터 테이블을 스캔하여 메모리에 이중 해시맵을 빌드합니다.

* `_canonical_index`: 정규화 키를 Key로, 성분 메타데이터를 Value로 매핑.
* `_phonetic_index`: 음차 정규화가 적용된 키를 Key로 매핑.

이를 통해 1, 2단계의 매칭 작업은 데이터베이스를 거치지 않고 메모리 상에서 **O(1)의 시간 복잡도(0.001초 미만)**로 즉시 해결됩니다.

### ④ 4단계: 퍼지 매칭 (Fuzzy Fallback Matching) 및 외부 연동
정규화 규칙마저 빗나간 심각한 오타(예: `알파아이소메틸아이오논`이 `알파이소메칠아오논`으로 잘못 인식된 경우)는 수학적 유사도를 측정하는 `difflib.SequenceMatcher`를 활용합니다. 

임계값(Threshold)을 **88%**로 설정하여 최적의 유사 성분을 찾아내며, 이마저도 실패할 경우 최종 보루로서 식약처 공공 API를 실시간 조회한 뒤 Neon DB에 캐싱하여 다음 요청에 대비합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 지능형 성분 자동 매칭 엔진 구축 작업을 통해 우리 팀은 몇 가지 값진 교훈을 얻을 수 있었습니다.

1. **도메인 지식(Domain Knowledge)의 힘**
   만약 단순히 머신러닝 모델이나 무거운 알고리즘에 의존했다면 자원 낭비가 심했을 것입니다. 화장품 성분명이 가지는 언어학적/명명법적 규칙을 파악하고 이를 코드(15대 음차 규칙)로 녹여냈기에 가볍고 명확한 해결책을 도출할 수 있었습니다.
2. **적절한 인메모리 활용의 극적인 성능 개선**
   모든 데이터를 데이터베이스에서 해결하려 하지 않고, 데이터의 크기(20,000여 건)와 변경 주기(낮음)를 고려해 **인메모리 인덱싱 전략**을 세운 덕분에 DB 부하를 원천 차단하고 초고속 응답 속도를 달성했습니다.
3. **단계적 방어벽(Fallback) 설계의 중요성**
   '정확 매칭 -> 규칙 매칭 -> 유사도 매칭 -> 외부 API'로 이어지는 단계적 아키텍처는 시스템의 성능과 정확도라는 두 마리 토끼를 모두 잡는 데 핵심적인 역할을 했습니다.

성분 매칭 실패율은 이 엔진 도입 이후 **0%에 수렴**하게 되었고, 스캔 API의 평균 응답 시간은 크게 단축되었습니다. 앞으로도 PickSafe 팀은 기술적 타협 없이, 우아하고 견고한 아키텍처로 사용자 경험을 혁신해 나가겠습니다.
