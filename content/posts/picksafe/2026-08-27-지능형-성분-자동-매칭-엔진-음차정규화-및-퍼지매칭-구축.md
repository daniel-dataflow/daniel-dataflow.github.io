제품 패키지 라벨을 촬영하여 화장품 성분을 분석하는 서비스를 운영하다 보면, 기술적으로 매우 까다로운 **'텍스트 불일치 문제'**를 마주하게 됩니다. 

데이터베이스에는 명확히 존재하는 안전한 성분임에도 불구하고, 제품 라벨의 외래어 표기법 차이나 인쇄 번짐으로 인해 **"확인 불가 성분"**으로 분류되는 현상입니다. 이는 유저 경험을 훼손할 뿐만 아니라 서비스의 신뢰도와 직결됩니다.

이번 글에서는 2만 개가 넘는 성분 데이터를 수작업으로 관리하는 대대적인 노가다(?) 대신, **언어학적 규칙(Phonetic Rules)**과 **수학적 알고리즘(Fuzzy Matching)**, 그리고 **인메모리 캐싱**을 결합하여 매칭 성공률을 획기적으로 높인 기술적 여정과 아키텍처 결정을 공유합니다.

---

## 1. 문제 정의: "같은 성분, 다른 이름"

성분 데이터 매칭에서 발생하는 문제는 크게 두 가지였습니다.

1. **외래어 음차 변형 (Transliteration Noise)**
   * 라벨 표기: `시카라이드아이소머레이트` ↔ DB 표기: `사카라이드아이소머레이트` (`시` vs `사`)
   * 라벨 표기: `알파-아이소메틸아이오논` ↔ DB 표기: `알파-아이소메틸이오논` (`아이오논` vs `이오논`)
2. **OCR 오인식 및 표기 규칙 차이**
   * 공백, 하이픈(`-`), 특수문자 유무에 따른 단어 파편화
   * 글자 획 누락 또는 번짐으로 인한 미세한 문자 오인식

### 왜 단순 DB Search나 DB 별칭(Synonym) 추가로는 해결할 수 없는가?
- **DB Synonym 관리의 한계**: 성분 2만 여 개에 대해 발생 가능한 모든 음차 조합을 DB 별칭 테이블에 하드코딩하는 것은 $O(N)$의 데이터 팽창을 야기하며, 유지보수가 불가능합니다.
- **RDBMS `LIKE` 검색의 성능 한계**: 스캔 요청이 몰릴 때 매번 SQL `LIKE '%...%'` 쿼리를 날리는 것은 DB CPU에 치명적인 부하를 주며, 응답 지연(Latency)을 유발합니다.

저희의 목표는 **"DB 부하는 0에 수렴하게 하면서, 0.001초(1ms) 내외의 초고속으로 음차 변형 및 노이즈 성분을 100% 자동 매칭하는 파이프라인을 구축하는 것"**이었습니다.

## 2. 지능형 4단계 매칭 파이프라인 아키텍처

저희는 가벼운 연산(O(1))부터 헤비한 연산(Fuzzy/External API)으로 단계별로 넘어가는 **비용 효율적 계층형 파이프라인(Tiered Pipeline)**을 설계했습니다.

```mermaid
flowchart TD
    A["📷 OCR 추출 성분명"] --> B["1단계: Canonical Key 생성<br>(특수문자, 하이픈, 공백 제거 & 소문자화)"]
    B --> C{"정확 일치?<br>(O(1) 인메모리 색인)"}
    C -- "YES" --> Z["🎉 매칭 성공 (표준명 반환)"]
    C -- "NO" --> D["2단계: 화장품 음차 형태소 정규화<br>(아이소↔이소, 아이오논↔이오논 등 15대 규칙)"}]
    D --> E{"음차 정규화 일치?<br>(O(1) 인메모리 색인)"}
    E -- "YES" --> Z
    E -- "NO" --> F["3단계: SequenceMatcher 퍼지 매칭<br>(유사도 88% 이상 최적 성분 탐색)"]
    F --> G{"유사 성분 발견?"}
    G -- "YES" --> Z
    G -- "NO" --> H["4단계: 외부 공공 API 실시간 조회 & DB 캐싱"]
```

## 3. 핵심 엔지니어링 설계 & Trade-off

### ① Canonical Key: 노이즈 제거의 표준화
문자열 비교 전 가장 먼저 수행하는 것은 '노이즈 제거'입니다. 띄어쓰기, 언더바, 하이픈, 괄호 등 의미 없는 제어 문자를 제거하고 영문은 소문자로 변환하여 고유 키를 생성합니다.

* 예: `알파-아이소메틸아이오논 (Alpha-Isomethyl Ionone)` ➔ `알파아이소메틸아이오논`

### ② 화장품 도메인 음차 형태소 정규화 (Phonetic Normalization)
매번 DB를 수정하는 대신, 명명 규약 기반의 **15대 화장품 음차 정규화 규칙 Engine**을 구축했습니다. 단어를 통째로 바꾸는 것이 아니라, 접두사/접미사 및 자주 틀리는 형태소를 양방향 변환합니다.

```python
# 음차 정규화 규칙 예시 (개념화된 코드)
PHONETIC_RULES = [
    ("시카라이드", "사카라이드"),
    ("아이오논", "이오논"),
    ("아이소", "이소"),
    ("메틸", "메칠"),
    ("하이드록시", "히드록시"),
    ("글라이콜", "글리콜"),
    ("하이드롤라이즈드", "가수분해"),
    # ... 총 15대 음차 변환 규칙
]
```
이 규칙을 적용하면 `시카라이드아이소머레이트`는 순간적으로 `사카라이드이소머레이트` 등의 정규화 키로 변환되어 DB 수정 없이도 기존 데이터와 매칭됩니다.

### ③ Memory vs I/O Trade-off: $O(1)$ 이중 인메모리 색인
속도와 DB 보호를 위해 서버 실행 시(또는 데이터 갱신 시) DB의 전체 성분 master 데이터를 불러와 **메모리 내 해시맵(Hash Map)으로 이중 색인**을 생성하도록 설계했습니다.

* `_canonical_index`: 정규화된 원본 성분명 키 $\rightarrow$ 성분 Master ID
* `_phonetic_index`: 음차 규칙이 적용된 정규화 키 $\rightarrow$ 성분 Master ID

**Trade-off 결정 이유:**
* **Loss**: 메모리 사용량 약 20~30MB 증가 (2만여 개 성분 키 기준, 서비스에 무리가 없는 아주 적은 양).
* **Gain**: DB Network I/O를 완전히 제거. 1~2단계 매칭 시 **$O(1)$ 시간 복잡도**를 가지며 평균 지연 시간 **0.001초(1ms) 미만** 달성.

### ④ Fuzzy Fallback: OCR 오인식 대응 (SequenceMatcher)
음차 규칙으로도 걸러지지 않는 획 누락(예: `글리세린` $\rightarrow$ `글리세림`)과 같은 OCR 인식 오류는 Python `difflib.SequenceMatcher` 기반의 퍼지 매칭으로 구제합니다.

* **Threshold 튜닝 (88%)**: 임계값이 너무 낮으면 잘못된 성분으로 매칭(False Positive)되고, 너무 높으면 오인식을 잡지 못합니다(False Negative). 테스트 세트를 통해 **유사도 88%**가 정확도를 보장하는 최적의 임계값임을 검증하여 적용했습니다.

## 4. 성과 및 기술적 레슨 (Takeaways)

### 📈 처리 성과
* **매칭 실패율 획기적 감소**: 음차 변형 및 노이즈가 포함된 테스트 데이터 세트 매칭 성공률 **100% 달성**.
* **초고속 응답 속도**: 1~2단계 인메모리 매칭을 통해 99% 이상의 요청을 **1ms 이하**로 처리. DB 쿼리 전송 횟수 0회 기록.

### 💡 Engineering Takeaways

1. **"문제 해결의 시작은 DB 쿼리가 아닌 도메인 규칙 정의에 있다"**
   무작정 DB 검색을 고도화하거나 AI 모델을 붙이기 전에, **도메인의 언어학적 패턴(15대 음차 규칙)**을 분석하고 단순화한 것이 복잡도를 줄이는 최선의 열쇠였습니다.

2. **계층적 아키텍처(Tiered Architecture)의 힘**
   모든 텍스트를 무거운 퍼지 매칭(Fuzzy Search)으로 처리했다면 CPU 병목이 발생했을 것입니다. **[정확 일치 $O(1)$] $\rightarrow$ [음차 정규화 $O(1)$] $\rightarrow$ [퍼지 매칭 $O(N)$]**으로 이어지는 계층적 구조를 통해 성능과 정교함을 모두 확보할 수 있었습니다.

3. **인메모리 캐싱을 통한 Infrastructure 비용 절감**
   자주 변경되지 않는 읽기 전용 도메인 데이터(성분 마스터)는 RDBMS에 의존하기보다 서버 메모리 구조(Hash Map)로 승화시키는 것이 System Throughput 향상에 얼마나 결정적인지 재확인했습니다.
