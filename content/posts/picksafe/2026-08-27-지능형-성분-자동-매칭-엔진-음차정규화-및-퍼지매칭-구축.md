화장품 패키지에 적힌 성분을 라벨 스캔(OCR) 기술로 추출할 때, 가장 흔하게 마주치는 걸림돌은 무엇일까요? 바로 **"DB에는 명백히 존재하지만, 표기법이 달라 찾아내지 못하는 문제"**입니다. 

식약처 표준 DB에 등록된 성분명과 실제 제품 패키지에 인쇄된 외래어 표기 사이에는 생각보다 큰 간극이 존재합니다. 이번 글에서는 20,000개 이상의 성분 데이터를 매번 DB 쿼리로 검색하거나 일일이 하드코딩하지 않고, **언어학적 규칙과 $O(1)$ 인메모리 파이프라인을 구축하여 1ms 미만의 지연 시간으로 성분 매칭 성공률을 극대화한 경험**을 공유합니다.

---

## 1. 문제 정의: 텍스트 일치율 99%의 함정

OCR 시스템이 이미지에서 텍스트를 정확하게 추출했더라도, 도메인 특유의 **외래어 음차 변형** 때문에 단순 문자열 비교(`StringEquals`)나 단순 DB 검색은 실패합니다.

### 실제 실패 케이스
1. **음차 표기 차이**: 라벨 표기 `시카라이드아이소머레이트` vs 식약처 DB `사카라이드아이소머레이트` (`시` ↔ `사`)
2. **외래어 자모음 변형**: 라벨 표기 `알파-아이소메틸아이오논` vs 식약처 DB `알파-아이소메틸이오논` (`아이오논` ↔ `이오논`)
3. **특수문자 및 공백**: 하이픈(`-`), 언더바(`_`), 괄호 및 띄어쓰기 오차

이러한 미매칭 문제는 서비스의 핵심 기능인 '성분 안전성 분석' 및 '알레르기 유발 성분 경고'를 무력화하여 사용자 경험을 심각하게 저하시킵니다.

---

## 2. 아키텍처 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 시스템 설계 단계에서 3가지 대안을 검토했습니다.

| 항목 | 대안 A: DB 퍼지 검색 (`pg_trgm` / `LIKE`) | 대안 B: ML 기반 임베딩 검색 (Vector Search) | **대안 C: 다단계 인메모리 파이프라인 (선택)** |
| :--- | :--- | :--- | :--- |
| **처리 속도** | 동시 요청 증가 시 DB CPU 급증 (10~50ms) | 모델 추론 지연 및 비용 발생 (100ms 이상) | **$O(1)$ 해시맵 접근으로 1ms 미만** |
| **정확도** | 유사도 기반 임계값 조절의 어려움 | 도메인 특화 단어의 오탐 가능성 | **규칙 기반 + 퍼지 보완으로 제어 가능** |
| **운영 비용** | DB 인스턴스 스케일업 필요 | GPU/외부 API 비용 발생 | **추가 비용 0원 (기존 서버 메모리 활용)** |

### 왜 대안 C(다단계 파이프라인)를 선택했는가?
성분 탐색은 100% 완벽한 정답률이 최우선이면서도 실시간 이미지 처리 서비스 특성상 **극도의 저지연(Low Latency)**이 요구됩니다. 
따라서 무거운 ML 모델이나 DB 쿼리를 매 스캔마다 호출하는 대신, **[정규화 ➔ 음차 치환 ➔ 퍼지 매칭 ➔ 외부 API Fallback]**의 4단계 샌드위치 아키텍처를 설계했습니다.

## 3. 지능형 매칭 4단계 파이프라인 아키텍처

저희가 구현한 4단계 파이프라인의 전체 흐름은 다음과 같습니다.

```mermaid
flowchart TD
    A["📷 OCR 추출 성분명"] --> B["1단계: 정규화 키 생성<br>(특수문자, 하이픈, 공백 제거)"]
    B --> C{"정확 일치 (O(1) 인메모리)?"}
    C -- "YES" --> Z["🎉 매칭 성공 (표준명/알레르기 매핑)"]
    C -- "NO" --> D["2단계: 화장품 음차 형태소 정규화<br>(아이소↔이소, 아이오논↔이오논 등)"]
    D --> E{"음차 정규화 일치?"}
    E -- "YES" --> Z
    E -- "NO" --> F["3단계: N-gram / SequenceMatcher 퍼지 매칭<br>(유사도 88% 이상 최적 성분 탐색)"]
    F --> G{"유사 성분 발견?"}
    G -- "YES" --> Z
    G -- "NO" --> H["4단계: 식약처 공공 API 실시간 조회 & DB 캐싱"]
```

## 4. 핵심 엔지니어링 전략

### ① Canonical Key (정규화 키) 생성
가장 먼저 입력 텍스트의 노이즈를 제거합니다. 공백, 하이픈(`-`), 언더바(`_`), 괄호, 특수기호를 제거하고 영문은 소문자화하여 결정론적인 키(Deterministic Key)를 만듭니다.
- 예: `알파-아이소메틸아이오논 (Alpha-Isomethyl Ionone)` ➔ `알파아이소메틸아이오논`

### ② 화장품 원료 명명 규약 기반 음차 정규화 (Phonetic Normalization)
20,000개가 넘는 성분의 변형을 일일이 수동 등록하는 방식은 불가능에 가깝습니다. 대안으로 **대한화장품협회 및 식약처 명명 규약 패턴 15종을 추출하여 양방향 자동 치환 규칙**을 정립했습니다.

```python
# 음차 정규화 핵심 규칙 패밀리 예시
PHONETIC_RULES = {
    "시카라이드": "사카라이드",
    "아이오논": "이오논",
    "아이소": "이소",
    "하이드록시": "히드록시",
    "하이드롤라이즈드": "가수분해",
    "글라이콜": "글리콜",
    "다이올": "디올",
    "트라이": "트리",
    # ... 총 15대 음차 변형 패턴 자동 적용
}
```

### ③ $O(1)$ 초고속 이중 인메모리 색인 (`_canonical_index`, `_phonetic_index`)
성분 데이터베이스 전체(국문명, INCI 영문명, 이명/별칭)를 애플리케이션 기동 시점에 **해시맵 형태의 이중 색인 구조**로 메모리에 로드합니다.

1. `_canonical_index`: 정규화 키 ➔ 표준 성분 객체
2. `_phonetic_index`: 음차 정규화 적용 키 ➔ 표준 성분 객체

이 구조 덕분에 실시간 매칭 요청 시 **DB I/O 발생 횟수는 0회**가 되며, 연산 시간은 평균 **0.0003초(0.3ms)**로 극단적인 최적화를 이뤄냈습니다.

### ④ Fuzzy Fallback (유사도 매칭)
인쇄 번짐이나 OCR의 획 누락(예: `아` ➔ `아ㅣ`) 같은 음차 규칙으로 커버할 수 없는 노이즈에 한해 `difflib.SequenceMatcher` 알고리즘을 사용해 유사도 88% 이상의 최적 후보 성분을 탐색합니다.

## 5. 구현 결과 및 매칭 검증

단위 테스트 환경에서 기존 스캔 실패 사례들을 대상으로 테스트를 진행한 결과, 다음과 같이 **100% 매칭에 성공**했습니다.

```python
# 서비스 테스트 검증 예시
def test_phonetic_matching():
    # 1. '시' -> '사' 변형 케이스
    result_1 = matcher_service.match("시카라이드아이소머레이트")
    assert result_1.standard_name == "사카라이드아이소머레이트"

    # 2. '아이오논' -> '이오논' & 하이픈 포함 케이스
    result_2 = matcher_service.match("알파-아이소메틸아이오논")
    assert result_2.standard_name == "알파-아이소메틸이오논"
```

- **처리 속도**: 평균 매칭 지연시간 **< 0.5ms** (퍼지 매칭 진입 시에도 5ms 이내)
- **DB 부하**: 스캔 요청에 따른 DB 읽기 부하 **100% 제거** (인메모리 타겟팅)

## 6. 엔지니어링 교훈 (Takeaways)

1. **복잡한 ML보다 단순한 도메인 지식이 강력할 수 있다**  
   모든 문제를 딥러닝이나 LLM 기반 검색으로 해결하려고 하면 과도한 오버헤드가 발생합니다. 도메인의 언어학적 패턴(화장품 음차 규칙)을 정교하게 다듬는 것만으로도 연산 비용을 획기적으로 줄이면서 높은 정확도를 확보할 수 있었습니다.

2. **계층적 방어(Layered Defense) 아키텍처의 중요성**  
   `완벽 일치(O(1))` ➔ `음차 정규화(O(1))` ➔ `퍼지 매칭(Soft Fallback)` ➔ `외부 API(Hard Fallback)`로 이어지는 계층 구조를 설계함으로써, 시스템 전체의 평균 응답 속도를 최상으로 유지하면서도 예외 케이스에 대한 유연한 대응력을 확보했습니다.

3. **데이터의 Canonicalization은 빠를수록 좋다**  
   비교 연산을 수행하기 전 텍스트의 표준 형태(Canonical Form)를 정의하고 인덱싱해 두는 패턴은 향후 검색 성능 및 데이터 정제 작업에 지속적으로 긍정적인 영향을 준다는 점을 재확인했습니다.
