화장품 성분 분석 서비스 PickSafe를 개발하면서 가장 핵심적인 기능은 사용자가 촬영한 화장품 성분표 이미지를 분석하여 유해 성분이나 알레르기 유발 성분을 판별해 주는 것입니다. 

하지만 실제 사용자가 스마트폰 카메라로 촬영한 이미지는 개발 환경처럼 이상적이지 않았습니다. 조명의 반사, 용기의 곡면 왜곡, 초점 흔들림, 그리고 저해상도 폰트 등 다양한 실환경 노이즈가 존재했습니다. 이로 인해 초기 프로토타입 단계에서 여러 기술적 병목과 인식 실패 현상을 마주하게 되었습니다.

이 글에서는 제한된 인프라 리소스 속에서 이미지 전처리 및 OCR 파이프라인을 최적화하고, 성분명 매칭 정확도를 올리기 위해 고민하고 해결한 과정을 담백하게 기록해 보고자 합니다.

## 🎯 마주한 고민과 문제 배경

초기 단순 텍스트 추출 방식에서는 크게 세 가지의 명확한 한계가 드러났습니다.

1. **구분자 누락으로 인한 인식 실패**
   성분표 이미지에서 쉼표(`,`)나 점(`.`)이 흐릿하게 인쇄되어 있거나 빛 반사로 인해 누락되는 경우, `정제수, 글리세린`이 `정제수글리세린`과 같이 하나의 텍스트로 합쳐져 데이터베이스 내의 성분 마스터 테이블과 매칭되지 않는 문제가 발생했습니다.

2. **성분명 오타 및 유사 표기법 대응 부재**
   OCR 엔진이 텍스트를 일부 오인식하거나(예: `디메치콘`을 `다이메티콘`으로 오타 인식), 화장품 제조사마다 다르게 사용하는 한글 음차 표기법 때문에 표준 성분명 매칭 시스템이 오작동했습니다.

3. **네트워크 대역폭 낭비와 타임아웃**
   최신 스마트폰으로 촬영한 원본 이미지 파일은 대개 5MB에서 10MB에 육박합니다. 이를 모바일 네트워크 환경에서 그대로 백엔드 서버에 업로드할 경우, 심각한 대역폭 낭비와 네트워크 지연이 발생했습니다. 이는 외부 OCR API의 처리 시간 증가 및 타임아웃 에러로 이어졌고, 제한된 인프라 리소스 하에서 서버 메모리 병목을 유발했습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

문제를 해결하기 위해 두 가지 방향성을 두고 고민했습니다.

### 대안 1: 서버 중심의 이미지 전처리 (OpenCV 활용)
서버에서 원본 이미지를 업로드받아 OpenCV 등의 라이브러리로 그레이스케일 변환, 이진화(Binarization), 왜곡 보정을 거친 후 OCR 엔진에 전달하는 방식입니다.
* **장점**: 정교한 이미지 처리가 가능하며, 클라이언트 기기 성능에 의존하지 않습니다.
* **단점**: 고용량 이미지가 서버로 업로드되는 네트워크 병목을 해결할 수 없으며, 이미지 처리 작업이 CPU 집약적이기 때문에 제한된 서버 리소스에서 동시 요청이 발생할 경우 메모리 고갈 및 서빙 지연이 발생할 위험이 큽니다.

### 대안 2: 클라이언트 사전 압축 + 백엔드 LLM OCR & 정규화 파이프라인 (최종 선택)
클라이언트 브라우저 단에서 Canvas API를 활용해 이미지를 1차 압축하여 업로드 크기를 줄이고, 백엔드에서는 Vision API의 구조화된 프롬프트(JSON Output)를 활용해 1차 텍스트 정제를 수행한 뒤, 최종적으로 정규식 엔진을 통해 매칭 신뢰도를 높이는 방식입니다.
* **장점**: 이미지 업로드 크기를 90% 이상 줄여 네트워크 지연을 극적으로 단축할 수 있습니다. 무거운 이미지 연산을 클라이언트에 분산시키고, 백엔드는 정형 데이터 정제 및 매칭에만 집중하므로 인프라 비용과 서버 부하를 최소화할 수 있습니다.
* **단점**: 클라이언트 브라우저 환경에 따라 Canvas API의 동작 성능에 미세한 차이가 있을 수 있으나, 현대 모바일 환경에서는 무리 없이 구동 가능한 수준입니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 클라이언트 이미지 사전 압축 (Canvas API)
사용자 기기에서 이미지를 선택하거나 촬영했을 때, 서버로 전송하기 전 브라우저 내 메모리에서 이미지를 축소하는 프론트엔드 코드입니다. 최대 해상도를 1200px로 제한하고 JPEG 화질을 85%로 설정하여, 평균 5MB의 이미지를 300KB 내외로 압축했습니다.

```javascript
// 클라이언트 이미지 전처리 유틸리티
export async function compressImage(file) {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.readAsDataURL(file);
    reader.onload = (event) => {
      const img = new Image();
      img.src = event.target.result;
      img.onload = () => {
        const canvas = document.createElement('canvas');
        let width = img.width;
        let height = img.height;
        const maxDimension = 1200;

        // 비율을 유지하며 최대 해상도 제한
        if (width > height) {
          if (width > maxDimension) {
            height = Math.round((height * maxDimension) / width);
            width = maxDimension;
          }
        } else {
          if (height > maxDimension) {
            width = Math.round((width * maxDimension) / height);
            height = maxDimension;
          }
        }

        canvas.width = width;
        canvas.height = height;
        const ctx = canvas.getContext('2d');
        ctx.drawImage(img, 0, 0, width, height);

        // JPEG 85% 압축률 적용하여 Blob 반환
        canvas.toBlob(
          (blob) => {
            if (blob) {
              resolve(new File([blob], file.name, { type: 'image/jpeg' }));
            } else {
              reject(new Error('이미지 압축 실패'));
            }
          },
          'image/jpeg',
          0.85
        );
      };
    };
    reader.onerror = (error) => reject(error);
  });
}
```

### 2. 백엔드 성분 정규화 및 괄호 제거 로직
OCR 결과로 들어오는 로 데이터(Raw Data)에는 성분명 외에 부가 정보가 괄호 형태로 포함되어 있는 경우가 많습니다. 예를 들어 `글리세린(식물성 추출)`이나 `향료(리모넨 함유)` 같은 형태입니다. 

이를 데이터베이스 내 표준 성분명인 `글리세린` 혹은 `향료`와 매칭시키기 위해, 정규식을 이용하여 불필요한 부가 설명을 제거하고 텍스트를 정규화하는 파이프라인을 구축했습니다.

```python
import re

class IngredientNormalizer:
    def __init__(self):
        # 괄호 및 내부 텍스트 제거를 위한 정규식 패턴
        self.bracket_pattern = re.compile(r'\([^)]*\)|\[[^\]]*\]')
        # 불필요한 공백 및 특수문자 제거 패턴
        self.clean_pattern = re.compile(r'[^a-zA-Z0-9가-힣\s,]')

    def normalize(self, raw_ingredient_string: str) -> list[str]:
        """
        원시 성분 문자열을 정제하여 개별 성분 배열로 반환합니다.
        예: "정제수, 글리세린(식물성 유래), 디메치콘 [실리콘]" -> ["정제수", "글리세린", "디메치콘"]
        """
        if not raw_ingredient_string:
            return []

        # 1. 괄호와 괄호 안 내용 제거
        cleaned = self.bracket_pattern.sub('', raw_ingredient_string)
        
        # 2. 허용되지 않은 특수문자 제거
        cleaned = self.clean_pattern.sub('', cleaned)

        # 3. 쉼표 기준 분할 및 양끝 공백 제거
        ingredients = [
            item.strip() 
            for item in cleaned.split(',') 
            if item.strip()
        ]
        
        return ingredients

# 동작 예시
# normalizer = IngredientNormalizer()
# print(normalizer.normalize("정제수, 글리세린(식물성), 향료(리모넨 함유)"))
# 결과: ['정제수', '글리세린', '향료']
```

### 3. 트러블슈팅: 복합 성분 분리 실패 대응
초기에는 단순히 쉼표(`,`)로만 분할을 시도했으나, OCR 인식 오류로 인해 `정제수글리세린`처럼 구분자가 생략되는 케이스가 발견되었습니다. 

이를 해결하기 위해 Gemini Vision API의 프롬프트에 성분 목록을 강제적으로 구조화된 JSON 배열 형식(`["정제수", "글리세린"]`)으로 반환하도록 규정했습니다. 

```json
// LLM에 요청하는 시스템 지시문(System Instruction)의 일부
{
  "instruction": "이미지에서 화장품 성분표 부분을 찾아 각 성분명을 분리하여 JSON string array 형식으로만 반환해 주세요. 임의의 텍스트나 서술형 답변은 제외하고 오직 ['성분1', '성분2'] 형태의 유효한 JSON 배열이어야 합니다."
}
```

이와 같이 Vision API가 1차적으로 문맥을 파악해 성분을 분리하고, 백엔드의 정규화 엔진이 2차적으로 노이즈를 제거하는 상호 보완적 파이프라인을 구축함으로써 예외 상황을 대폭 줄일 수 있었습니다.

## 💡 돌아보며 배운 점 (회고)

이번 스캔 엔진 파이프라인 구축 작업을 진행하며 얻은 가장 큰 교훈은 **"모든 연산과 처리를 백엔드 서버에서만 해결하려 하지 말자"**는 것입니다.

* **자원 절약과 사용자 경험의 양립**: 클라이언트 단에서 구동되는 가벼운 Canvas API 전처리를 통해 서버의 업로드 대역폭 부담을 90% 가까이 덜어냈고, 결과적으로 서버 인프라 리소스를 극적으로 아낄 수 있었습니다. 평균 응답 속도 역시 기존 대비 대폭 단축되어 **1.5초 이내**에 분석 결과를 사용자에게 보여줄 수 있게 되었습니다.
* **정밀한 데이터 정제의 필요성**: 아무리 훌륭한 OCR 엔진을 사용하더라도 실환경 이미지의 노이즈를 100% 완벽하게 파악해 표준 데이터베이스와 매칭하기는 어렵습니다. 정규식을 통한 괄호 제거, 오타 정제 등의 정규화 레이어를 촘촘하게 설계하는 것이 전체 시스템의 신뢰도(정확도 **35% 향상**)를 결정짓는 핵심 요소임을 다시 한번 깨달았습니다.

추후에는 잦은 요청에 대비하여 자주 매칭되는 표준 성분 딕셔너리를 메모리 캐시 레이어에 적재하고, 모바일 오프라인 환경에서도 기본적인 성분 분석이 가능하도록 클라이언트 로컬 캐시 구조를 고도화해 볼 계획입니다.
