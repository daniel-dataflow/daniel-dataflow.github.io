안녕하세요, PickSafe 개발 팀입니다. 

서비스를 개발하다 보면 기술적 도전만큼이나 **'비즈니스 요구사항(법률 규제)'과 '사용자 경험(UX)' 사이의 아슬아슬한 줄타기**를 마주할 때가 많습니다. 특히 사용자의 건강 정보를 다루는 헬스케어/푸드테크 서비스라면 '개인정보보호법'은 피해 갈 수 없는 거대한 장벽이자, 제품의 신뢰도를 결정짓는 핵심 기준이 됩니다.

최근 저희 팀은 사용자의 기피 성분 및 알레르기 정보를 다루기 위해 **"개인정보 약관 및 건강 민감정보 수집 동의 체계"**를 밑바닥부터 새롭게 설계했습니다. 규제를 완벽하게 준수하면서도 전환율(Conversion)을 해치지 않기 위해 고민했던 아키텍처 관점의 고민과 트레이드오프, 그리고 해결 과정을 공유합니다.

---

## 1. 마주한 문제 (Problem)

### "건강 기피 성분은 '민감 정보'입니다"
대한민국 개인정보보호법 및 글로벌 규제(GDPR 등)에 따르면, 알레르기나 특정 질환용 기피 성분 같은 정보는 **사상·신념 외에 '건강에 관한 정보'로서 민감정보(Sensitive Personal Information)**로 분류됩니다. 

이를 수집하기 위해서는 다음 두 가지 엄격한 기준을 충족해야 했습니다.
1. **별도 동의(Separate Consent):** 일반 서비스 이용 약관과 민감정보 수집 동의를 하나의 체크박스로 뭉뚱그려 받을 수 없고, **각각 독립된 동의 항목(체크박스)으로 분리**하여 명시적 동의를 받아야 합니다.
2. **이력 추적성(Auditable Audit Trail):** 사용자가 '몇 년도, 몇 월, 몇 일에', '어떤 버전의 약관'에 동의했는지 데이터베이스에 유실 없이 이력(Log)으로 남겨야 합니다.

### 개발팀의 핵심 당면 과제: "규제는 지키되, 허들은 낮춰라"
* **UX 허들 최소화:** 앱을 켜자마자 거대한 약관 동의 팝업이 전면을 가로막는다면, 신규 유저의 이탈률은 치솟을 것입니다.
* **비회원(게스트) 지원:** 가입 없이 가볍게 서비스를 둘러보는 게스트 사용자는 어떻게 처리해야 할까요? 게스트 상태에서도 동의를 강제해야 할까요?
* **다국어 및 버전 관리:** 글로벌 유저를 위해 각 국가 언어(Locale)별로 다른 약관을 서빙해야 하고, 법이 개정되어 약관 버전이 올라갔을 때 기존 유저에게 재동의를 매끄럽게 받아야 합니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 저희 팀은 크게 세 가지 아키텍처적 선택지를 두고 고민했습니다.

### 고민 1. 동의 여부 검증을 어디서 할 것인가? (미들웨어 vs 어플리케이션 레이어)

*   **대안 A: 전역 API 미들웨어(Middleware)에서 일괄 차단**
    *   *설명:* 모든 API 요청 도입부에서 유저의 동의 여부를 검사하여, 미동의 시 즉시 `/consent` 페이지로 리다이렉트하거나 에러(403)를 반환하는 방식.
    *   *장점:* 비즈니스 로직에 동의 검증 코드가 섞이지 않아 안전하고 일관됨.
    *   *단점:* 게스트 유저의 자유로운 탐색이나, 동의가 필요 없는 공용 API(예: 단순 상품 검색)까지 불필요하게 가로막아 UX 유연성이 극도로 떨어짐.
*   **대안 B: 온보딩/특정 API 진입 시점에만 컨텍스트 검증 (선택)**
    *   *설명:* 핵심 민감 데이터가 서버로 업로드되는 '성분 설정 및 온보딩' 진입점과 실제 데이터를 저장하는 엔드포인트(`POST /users/me/allergens`) 직전에만 동의 여부를 확인하는 방식.
    *   *이유:* 법률상 규제 대상은 '서버에 개인정보가 수집/저장되는 시점'입니다. 따라서 서버 통신이 필요 없는 게스트 상태에서는 규제 대상이 아니므로 UX 마찰을 Zero로 만들고, **회원 전환 및 프로필 저장 시점에만 검증을 트리거**하는 것이 최선이라고 판단했습니다.

### 고민 2. 게스트(비회원) 데이터는 어떻게 처리할 것인가?

로그인을 하지 않은 게스트 유저는 기기 내부의 로컬 스토리지(Local Storage)만을 사용하도록 설계했습니다. 즉, **서버 DB에 데이터를 전송하지 않으므로 어떠한 개인정보 동의 유도 팝업도 띄우지 않습니다.** 

이후 사용자가 소셜 로그인을 통해 정식 회원으로 전환하는 순간(`POST /auth/guest-convert`), 로컬에 임시 저장되어 있던 성분 정보와 함께 일반 약관 및 민감 정보 동의 이력을 단 한 번의 API 콜(Atomic Operation)로 묶어서 서버 DB에 일괄 이관하도록 파이프라인을 구축했습니다.

## 3. 최종 해결 방식 및 아키텍처

우리는 위의 고민을 바탕으로 다음과 같이 세련되고 안전한 동의 체계를 구축했습니다.

```
[사용자 흐름 (User Flow)]
- 게스트 사용: 동의 불필요 (로컬 저장소 활용)
- 로그인/가입: 필수 동의 여부 검사 ──(미동의 유저)──> /consent 화면 리다이렉트
                                    ├── ① 일반 정보 수집 동의 (필수 체크)
                                    └── ② 민감 건강 정보 동의 (필수 체크)
```

### 1) 정교한 데이터 모델링 (`user_consents`)
동의 여부를 단순 `Boolean` 필드 하나로 유저 테이블에 두면, 추후 약관이 개정되었을 때 대참사가 일어납니다. 어떤 버전에 동의했는지 알 수 없기 때문입니다. 이를 해결하기 위해 이력 추적용 다대일(N:1) 릴레이션 테이블을 설계했습니다.

```python
# [보안 처리를 위해 실제 코드의 일부를 개념적으로 추상화했습니다]
class UserConsent(Base):
    __tablename__ = "user_consents"

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False)
    consent_type = Column(String(50), nullable=False)  # 'privacy_policy', 'sensitive_health_data' 등
    version = Column(String(20), nullable=False)       # 예: '2026-07-08'
    is_agreed = Column(Boolean, default=True, nullable=False)
    created_at = Column(DateTime, default=datetime.utcnow)
```
이렇게 설계하면 특정 유저가 과거에 어떤 버전의 약관에 동의했는지 히스토리를 완벽하게 역추적(Auditing)할 수 있습니다.

### 2) UI/UX 구현: 2채널 개별 동의 화면과 Collapsible 아코디언
법률 준수를 위해 `/consent` 화면에서 일반 약관 동의와 건강 정보 동의 체크박스를 완전히 독립시켰습니다. 또한 사용자가 귀찮게 화면을 벗어나지 않고도 내용을 즉시 확인할 수 있도록 **다국어 마크다운 약관 자동 변환 기능**을 구현했습니다.

*   서버 내 `docs/consent/` 폴더에 언어별 마크다운 파일(`privacy_policy_ko.md`, `sensitive_health_en.md` 등)을 관리합니다.
*   사용자 브라우저의 Locale 설정을 파악하여 적절한 마크다운을 실시간으로 HTML 변환 후, 프론트엔드의 Collapsible(아코디언) 컴포넌트에 바인딩합니다.
*   두 개의 개별 체크박스가 모두 활성화되어 전송되어야만 데이터베이스에 순차적으로 트랜잭션 처리가 완료됩니다.

## 4. 이번 작업을 통해 얻은 엔지니어링 교훈 (Takeaways)

1. **"규제 준수와 훌륭한 UX는 배타적이지 않다"**
   개발 초기에는 "약관 동의 화면이 생기면 가입률이 무조건 떨어질 텐데..."라는 걱정이 앞섰습니다. 하지만 비회원 단계에서는 철저히 로컬 스토리지를 활용해 '마찰 제로(Zero Friction)' 환경을 제공하고, 실제 서버 통신이 일어나는 온보딩과 소셜 가입 시점에 자연스럽게 동의 흐름을 엮음으로써 법률적 방어권과 사용자 경험 둘 다를 챙길 수 있었습니다.

2. **"히스토리 관리는 데이터베이스 설계의 기본이다"**
   현재 시점의 단발성 상태(`is_agreed = True`)만 기록하는 방식은 비즈니스가 성장함에 따라 반드시 부메랑이 되어 돌아옵니다. 규제 기관의 감사나 유저 피드백에 유연하게 대응하기 위해서는 처음부터 '버전 기반의 이력성 데이터 모델'을 설계해야 함을 재확인했습니다.

3. **"도메인 지식을 갖춘 엔지니어의 가치"**
   단순히 기획서에 "체크박스 두 개 만들어주세요"라고 적힌 요구사항을 그대로 구현하는 것을 넘어, "개인정보보호법상 민감정보 처리가 왜 필요한지", "이를 아키텍처적으로 우아하게 푸는 방법은 무엇인지" 고민하는 엔지니어링이 실제 고품질의 프로덕트를 만듭니다.
