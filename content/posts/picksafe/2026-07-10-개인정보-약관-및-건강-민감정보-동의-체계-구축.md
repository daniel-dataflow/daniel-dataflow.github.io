안녕하세요. PickSafe 팀의 백엔드 아키텍트입니다. 

스타트업이 헬스케어, 푸드테크 등 사용자의 신체 정보를 다루는 비즈니스로 확장할 때 반드시 마주치는 거대한 장벽이 있습니다. 바로 **'개인정보보호법'**과 **'민감 정보 수집 규제'**입니다. 특히 사용자의 알레르기나 기피 성분과 같은 건강 관련 정보는 법적으로 '민감 정보'에 분류되어, 일반 개인정보와는 별도의 명시적 동의(Separated Explicit Consent)를 받아야 합니다.

하지만 규제만을 준수하기 위해 앱을 켜자마자 수많은 동의 팝업과 체크박스를 들이밀면 어떻게 될까요? 신규 유저의 이탈률(Drop-off)은 걷잡을 수 없이 치솟을 것입니다. 

오늘 포스팅에서는 저희 PickSafe 팀이 **'철저한 법적 증적 확보'**라는 규제적 요구사항과 **'가입 마찰 제로화'**라는 서비스적 요구사항을 아키텍처 관점에서 어떻게 동시에 해결했는지 공유하고자 합니다.

---

## 1. 마주한 문제 (Problem)

기존 PickSafe 서비스는 사용자의 편의를 위해 '비회원 게스트 모드'를 지원하고 있었습니다. 그러나 맞춤형 기피 성분 필터링 기능을 고도화하면서 두 가지 기술적/법적 과제에 직면했습니다.

1. **민감 정보(건강 데이터)의 별도 동의 규제:** 일반 개인정보 약관 동의와 건강 정보 수집 동의를 하나의 체크박스로 뭉뚱그려 받을 수 없습니다. 법적으로 두 항목은 **개별적인 체크박스로 완전히 분리**되어야 하며, 사용자가 이를 명확히 인지할 수 있는 법적 고지(약관 뷰어)가 제공되어야 합니다.
2. **비회원 경험과 데이터 일관성의 충돌:** 게스트 유저는 서버에 개인정보를 남기지 않고 디바이스 로컬 저장소만 이용합니다. 이들에게까지 귀찮은 동의 팝업을 띄우는 것은 최악의 UX입니다. 반면, 이 게스트가 정식 회원으로 전환(Social Login)될 때는 로컬에 저장되어 있던 성분 데이터가 서버로 이관되므로, **그 즉시 법적으로 유효한 동의 이력을 서버 DB에 생성**해야 합니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제를 해결하기 위해 크게 두 가지 아키텍처 방향성을 두고 고민했습니다.

### 대안 A: 전역 미들웨어(Global Middleware) 기반의 강제 차단
모든 API 요청 길목에 미들웨어를 두고, 동의 이력이 없는 사용자의 접근을 원천 차단한 뒤 `/consent` 페이지로 리다이렉트하는 방식입니다.

*   **장점:** 구현이 단순하며, 동의하지 않은 유저가 실수로 서비스를 이용하는 것을 원천 차단할 수 있어 법적 안전성이 높습니다.
*   **단점:** 유연성이 극도로 떨어집니다. 비회원 게스트 유저 역시 미들웨어 체크 대상에 포함되므로, 게스트 예외 처리를 위한 복잡한 화이트리스트(Whitelist) 관리가 필요해집니다. 결과적으로 초기 진입 장벽이 매우 높아집니다.

### 대안 B: 상태 기반의 지연 동의(Lazy Consent) 및 적재적소 인터셉트
기본적으로 전역 차단을 하지 않고, **실제 서버에 민감 데이터가 전송되는 시점(온보딩 저장 및 회원 가입 단계)**에만 동의 여부를 확인하고 수집하는 방식입니다.

*   **장점:** 비회원 게스트는 어떠한 방해 요소도 없이 서비스를 탐색할 수 있습니다. 동의 프로세스는 오직 데이터가 디바이스를 떠나 서버로 업로드되는 순간에만 트리거되므로 매끄러운 UX를 유지할 수 있습니다.
*   **단점:** 비동기 상태 관리 및 회원 전환 시점의 트랜잭션 처리가 정교해야 합니다.

### 우리의 선택: 대안 B (지연 동의 아키텍처)
우리는 서비스 성장을 위해 UX 마찰을 최소화하는 **대안 B**를 선택했습니다. 단, 법적 리스크를 완벽히 제거하기 위해 데이터베이스 수준에서 강력한 제약 조건을 갖춘 동의 이력 관리 체계를 설계하기로 했습니다.

## 3. 최종 해결 방식 및 엔지니어링 구현

### ① 이력 추적성을 보장하는 동의 데이터 모델 (`UserConsent`)
약관은 수시로 개정됩니다. 법적 증적을 완벽히 남기기 위해서는 "이 유저가 '몇 년 몇 월 몇 일'에 '어떤 버전'의 약관에 동의했는가"를 단방향(Append-only)으로 기록해야 합니다. 

이를 위해 기존 유저 테이블에 단순히 `is_consented = True` 필드를 추가하는 대신, 1:N 관계의 `UserConsent` 테이블을 신설했습니다.

```python
# [보안을 위해 단순화된 예시 개념 모델 구조입니다]
class UserConsent(Base):
    __tablename__ = "user_consents"

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    consent_type = Column(String, nullable=False)  # 'privacy_policy', 'sensitive_health_data' 등
    version = Column(String, nullable=False)       # 동의한 약관의 고유 버전 (예: '2026-07-08')
    agreed_at = Column(DateTime, default=datetime.utcnow, nullable=False)
```

이 모델을 통해 특정 유저가 과거에 동의했던 모든 약관 버전의 타임스탬프를 보관하며, 데이터 보존 의무를 충족합니다.

### ② 다국어 약관의 Dynamic Rendering & Collapsible 컴포넌트 화
약관 텍스트를 데이터베이스나 HTML 내부에 하드코딩하면 유지보수가 지옥이 됩니다. 저희는 일반 약관(`privacy_policy_{locale}.md`)과 민감정보 약관(`sensitive_health_{locale}.md`)을 마크다운 파일로 분리하고 싱글 소스(Single Source of Truth)로 관리했습니다.

사용자가 온보딩이나 동의 페이지에 진입하면, FastAPI 백엔드는 유저의 로케일(Locale) 설정을 감지하여 알맞은 마크다운 파일을 로드합니다. 이후 이를 Jinja2 템플릿 엔진과 연동하여 실시간으로 HTML로 파싱하고, 프론트엔드에서는 레이아웃을 해치지 않도록 깔끔한 아코디언(Collapsible) 컴포넌트로 렌더링합니다.

```
📁 docs/consent/
  ├── privacy_policy_ko.md
  ├── privacy_policy_en.md
  ├── sensitive_health_ko.md
  └── sensitive_health_en.md
```

### ③ 게스트에서 회원으로의 무마찰 전환 (Seamless Guest Migration)
이 아키텍처의 핵심 하이라이트입니다. 게스트 유저가 로그인 버튼을 누르는 순간 수행되는 비즈니스 로직의 흐름은 다음과 같습니다.

```
[ 게스트 기기 ] --(로컬 성분 설정 + 소셜 가입 요청)--> [ FastAPI 서버 ]
                                                            │
                     ┌──────────────────────────────────────┴──────────────────────────────────────┐
                     ▼ (Transaction Start)                                                         ▼
         [ 1. 정식 회원(User) 생성 ]                                                 [ 2. 성분 데이터 서버 DB 이관 ]
                     │                                                                             │
                     └──────────────────────────────────────┬──────────────────────────────────────┘
                                                            ▼
                                   [ 3. 필수 동의 이력 2종(일반/민감) 일괄 적재 ]
                                                            │
                                                            ▼ (Transaction Commit)
```

이 모든 과정이 단 하나의 원자적 트랜잭션(Atomic Transaction)으로 묶여 처리되므로, 데이터 유실이나 동의 이력이 유실된 채 회원 가입만 완료되는 모순적인 상황을 원천 방지합니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 규제 대응 및 동의 체계 구축 작업을 통해 배운 핵심 레슨은 다음과 같습니다.

1. **규제(Compliance)는 극복해야 할 엔지니어링 스펙이다:** 기획팀과 법무팀이 가져오는 법적 규제 사항을 단순히 "안 되니까 다 막아야 한다"로 해석해서는 안 됩니다. 아키텍트의 역할은 기술적 레이어(Client-Side Storage vs Server-Side DB)를 분리하여 법과 UX를 둘 다 만족시키는 최적의 타협점(Trade-off)을 찾는 것입니다.
2. **동의 이력은 절대 가변(Mutable) 상태로 관리하지 않는다:** "현재 동의 상태"만을 관리하는 플래그 필드는 소송이나 감사가 발생했을 때 소급 증명력이 떨어집니다. 이력(Log) 형태의 Append-only 구조로 동의 테이블을 분리하는 것이 장기적으로 가장 안전한 선택입니다.
3. **사용자 경험의 일관성 유지:** 가입 전 게스트 유저에게 과도한 허들을 주지 않고, 실제 가치가 발생하는 시점(Value Delivery Point)까지 권한 획득과 동의 유도를 미루는 **'지연 동의(Lazy Consent)'** 전략은 비즈니스 지표 개선에 거대한 영향을 미칩니다.

앞으로도 PickSafe는 철저한 보안과 규제 준수 하에, 전 세계 사용자들이 가장 매끄럽고 안전하게 서비스를 이용할 수 있는 환경을 구축해 나갈 것입니다.
