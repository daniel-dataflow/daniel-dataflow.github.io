안녕하세요. PickSafe 팀의 백엔드 엔지니어입니다.

최근 개인정보보호법이 강화됨에 따라, 사용자의 데이터를 다루는 서비스들은 기술적 기능뿐만 아니라 **'법적 규제 준수(Compliance)'**에 대해서도 깊은 고민을 해야 합니다. 특히 사용자의 기피 성분이나 알레르기 유발 정보와 같은 '건강 관련 데이터'는 법적으로 **민감 정보**에 해당하여, 일반 개인정보와는 완전히 분리된 **명시적인 별도 동의**를 받아야 합니다.

이번 포스팅에서는 서비스의 핵심 가치인 **'게스트 사용의 무마찰(Zero-Friction) 경험'**을 훼손하지 않으면서, 까다로운 **'민감 정보 수집 동의 규제'**를 완벽하게 충족하기 위해 우리 팀이 마주했던 기술적 고민과 아키텍처 해결 과정을 공유하고자 합니다.

---

## 1. 문제 정의 (The Problem)

기존 PickSafe의 온보딩 과정은 단순했습니다. 하지만 기피 성분 설정 기능이 고도화되면서 법적 규제라는 큰 벽에 마주하게 되었습니다.

### 핵심 과제
1. **민감 정보의 개별 동의 강제**: 
   개인정보보호법에 의거, '일반 개인정보 수집 동의'와 '건강 민감정보 수집 동의'는 하나의 체크박스로 묶어 처리할 수 없습니다. 각각 독립된 항목으로 노출하고 사용자가 개별적으로 인지 및 체크해야만 했습니다.
2. **동의 이력(Audit Trail)의 추적성 확보**: 
   단순히 "동의함" 여부만 저장하는 것이 아니라, **'어떤 버전의 약관'**에 **'언제'** 동의했는지 추적할 수 있는 증적이 필요했습니다. 약관이 개정될 경우 미동의자를 식별해 재동의를 받아야 하기 때문입니다.
3. **게스트(비회원) UX의 마찰 최소화**: 
   우리 서비스는 비회원 상태에서도 자유롭게 상품 성분을 탐색할 수 있는 무마찰 경험을 지향합니다. 가입도 하지 않은 게스트에게 앱 진입부터 팝업을 띄우고 약관 동의를 강제하는 것은 심각한 이탈 요인이었습니다.

---

## 2. 기술적 고민과 아키텍처 선택 (Trade-offs)

### 고민 1. 동의 상태를 어디에, 어떻게 저장할 것인가?
* **대안 A: User 테이블에 Boolean 필드 추가 (`is_privacy_agreed`, `is_health_agreed`)**
  * *장점:* 구현이 매우 단순하고 조회가 빠름.
  * *단점:* 약관이 개정되었을 때 버전 관리가 불가능함. 과거에 어떤 버전의 약관에 동의했는지 증적을 남길 수 없어 법적 리스크 존재.
* **대안 B (선택): 이력 관리 테이블 분리 (`user_consents`)**
  * *장점:* 사용자와 N:M에 준하는 1:N 관계의 독립된 테이블을 신설하여, 약관 코드, 동의 버전, 동의 시점을 타임스탬프로 기록. 규제 기관의 감사(Audit)에 완벽히 대응 가능하며 약관 개정 시 유연한 대처 가능.
  * *단점:* 관계형 데이터베이스 조인이 추가로 필요하나, 인덱싱 설계로 성능 저하 극복 가능.

### 고민 2. 법적 고지(약관 내용)를 어디서 관리하고 렌더링할 것인가?
* **대안 A: 프론트엔드 코드 내에 하드코딩**
  * *장점:* 프론트엔드 독립적으로 빠른 구현 가능.
  * *단점:* 기획팀에서 약관 자구 하나만 수정해도 앱 배포가 필요함. 다국어(Locale) 처리가 까다로움.
* **대안 B (선택): 백엔드 마크다운(Markdown) 관리 및 런타임 렌더링**
  * *장점:* 약관 본문을 Git에서 마크다운 문서(`docs/consent/*.md`)로 관리. FastAPI 서버 가동 시 사용자 언어설정(Locale)에 맞게 실시간 렌더링하여 프론트엔드에 전달. 내용 수정 시 배포 파이프라인을 통한 정적 파일 업데이트만으로 대응 가능.

### 고민 3. 비회원 게스트에서 회원으로 전환될 때 데이터 유실 방지
게스트 상태에서는 서버가 아닌 디바이스 내부 로컬 스토리지에 기피 성분 정보를 저장합니다. 이 사용자가 회원 가입(`POST /auth/guest-convert`)을 진행할 때, **'로컬 데이터 업로드'**와 **'서버 DB의 개인정보 동의 기록'**이 원자적(Atomic)으로 처리되어야 했습니다. 

동의는 하지 않았는데 데이터만 서버에 적재되거나, 반대로 동의만 처리되고 설정했던 기피 성분이 사라지는 불일치 현상을 막아야 했습니다.

## 3. 최종 구현 및 해결책 (Implementation)

우리 팀은 규제와 UX라는 두 마리 토끼를 모두 잡기 위해 다음과 같은 단계별 파이프라인을 구축했습니다.

### 구조도: 무마찰 게스트 탐색부터 정식 회원 전환까지의 데이터 흐름

```text
[게스트 모드] 
  - 서버 통신 없음 (동의 요구 X)
  - 기피 성분 설정을 로컬 스토리지에만 임시 보존
       │
       ▼ (소셜 로그인 / 회원 가입 시도)
[가입 전환 API 호출: POST /auth/guest-convert]
  - 요청 바디: 로컬 성분 데이터 + 약관 동의 플래그 2종
       │
  ┌────┴────────────────────────┐
  │ 단일 데이터베이스 트랜잭션 시작  │
  ├─────────────────────────────┤
  │ 1. 신규 회원 계정 생성        │
  │ 2. user_consents 테이블에    │
  │    필수 동의 2종 개별 적재    │
  │ 3. 기피 성분 데이터 서버 저장 │
  └────┬────────────────────────┘
       │ (트랜잭션 커밋 완료)
       ▼
[온보딩 완료 및 서비스 진입]
```

### Key Implementation 1: 동의 이력 엔티티 설계
SQLAlchemy를 활용하여 동의 이력을 관리하는 테이블을 아래와 같이 설계했습니다. 각 동의 항목은 고유한 `consent_type`(예: 일반 약관, 민감 정보)과 `version`을 가집니다.

```python
# 실제 코드 스키마를 추상화한 예시입니다.
class UserConsent(Base):
    __tablename__ = "user_consents"

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False)
    consent_type = Column(String(50), nullable=False)  # 'privacy_policy', 'sensitive_health_data'
    version = Column(String(20), nullable=False)       # '2026-07-08'
    agreed_at = Column(DateTime, default=datetime.utcnow, nullable=False)

    user = relationship("User", back_populates="consents")
```

### Key Implementation 2: 다국어 지원 및 Dynamic Markdown Collapsible 렌더링
사용자의 설정에 맞는 최신 약관 파일(`docs/consent/sensitive_health_{locale}.md`)을 읽어와 Jinja2 템플릿 엔진을 통해 HTML로 동적 변환합니다. 프론트엔드에서는 이를 아코디언(Collapsible) 컴포넌트로 바인딩하여 사용자가 화면을 벗어나지 않고도 전체 약관을 명확히 확인할 수 있도록 구현했습니다.

```python
# FastAPI 엔드포인트 예시 (추상화됨)
@router.get("/consent")
async def get_consent_page(request: Request, locale: str = "ko"):
    privacy_html = load_and_convert_markdown(f"docs/consent/privacy_policy_{locale}.md")
    sensitive_html = load_and_convert_markdown(f"docs/consent/sensitive_health_{locale}.md")
    
    return templates.TemplateResponse(
        "consent.html", 
        {
            "request": request, 
            "privacy_content": privacy_html, 
            "sensitive_content": sensitive_html
        }
    )
```

## 4. 엔지니어링 교훈 (Takeaway)

이번 태스크를 진행하며 배운 점은 다음과 같습니다.

1. **규제 준수(Compliance)도 엔지니어링의 일부이다**: 
   처음에는 기획과 법률 검토 단계에서 추가된 '2단계 분리 동의' 요구사항이 개발 스케줄을 지연시키는 장애물처럼 느껴졌습니다. 하지만 이를 유연한 데이터베이스 스키마(이력 관리)와 파일 기반 다국어 템플릿 아키텍처로 풀어내면서, 미래의 규제 변화에도 즉각 대응할 수 있는 단단한 기초 체력을 다지게 되었습니다.
2. **UX 마찰은 미룰 수 있을 때까지 미뤄라**: 
   모든 사용자에게 무조건적인 동의를 먼저 강요하는 방식 대신, '데이터가 서버로 전송되는 시점'에 맞추어 동의를 요청하고 비회원 단계에서는 온전히 서비스를 경험하게 한 UX 설계는 신규 유저의 이탈률을 방어하는 데 큰 기여를 했습니다.
3. **결합도 낮추기**: 
   약관 텍스트와 앱 소스 코드를 분리함으로써, 문구 수정이 필요할 때마다 전체 서비스를 빌드하고 배포할 필요가 없어졌습니다. 비즈니스 영역(법률 약관)과 기술 영역(렌더링 및 저장 메커니즘)의 결합도를 낮추는 아키텍처의 중요성을 다시 한번 절감했습니다.

기술적 규제 속에서도 사용자 경험을 타협하지 않는 제품을 만드는 것, 그것이 시니어 엔지니어가 비즈니스에 기여할 수 있는 가장 가치 있는 일 중 하나가 아닐까 생각합니다.
