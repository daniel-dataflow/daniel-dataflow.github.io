서비스를 성장시키다 보면 기술적 도전만큼이나 **비즈니스 환경과 법적 규제(Compliance)** 대응이라는 큰 벽을 마주하게 됩니다. 특히 사용자의 건강, 기피 성분, 알레르기 정보 등을 다루는 서비스라면 더욱 그렇습니다. 현행 개인정보보호법상 이러한 '건강 관련 정보'는 **민감 정보**로 분류되어, 일반 개인정보와 반드시 분리하여 명시적인 별도 동의를 받아야 하고, 이에 대한 명확한 증적(Audit Trail)을 남겨야 합니다.

하지만 법적 규제를 핑계로 무작위 팝업을 띄우거나 긴 약관을 강제로 읽게 만든다면 사용자 경험(UX)은 망가지고 신규 유저 전환율은 급락할 것입니다.

이번 포스팅에서는 **PickSafe** 팀이 어떻게 **1) 엄격한 법적 규제를 준수하면서도, 2) 비회원(게스트) 사용자의 경험을 해치지 않고, 3) 확장성 있는 다국어 약관 동의 시스템을 구축했는지** 아키텍처 고민과 해결 과정을 공유합니다.

---

## 1. 마주한 문제 (Problem)

기존 시스템은 일반적인 약관 동의 체계로 운영되어, 민감 정보인 '기피 성분 설정' 시 명확한 법적 고지와 분리 동의를 지원하지 못하는 한계가 있었습니다. 법적 준수와 비즈니스 성장을 모두 잡기 위해 해결해야 할 과제는 다음과 같았습니다.

1.  **동의 이력의 이력화(Versioning) 부재**: 어떤 사용자가 몇 년 몇 월 몇 일에 '어떤 버전'의 약관에 동의했는지 추적할 수 없어 법적 증적 능력이 부족했습니다.
2.  **일괄 동의(All-in-One)의 법적 리스크**: 일반 개인정보 수집 동의와 민감 정보(건강 데이터) 수집 동의를 한 번에 묶어서 받으면 규제 위반 소지가 있었습니다. 두 항목은 반드시 **각각 독립된 체크박스로 분리**하여 동의를 받아야 했습니다.
3.  **게스트 사용자의 UX 마찰**: 비회원으로 서비스를 가볍게 둘러보고 싶은 유저에게 가입 즉시 개인정보 동의를 강제하는 것은 이탈율을 높이는 주범이었습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 아키텍처 관점에서 몇 가지 대안을 비교해 보았습니다.

### 고민 1: 동의 체크 여부를 검사하는 시점 (전역 미들웨어 vs 타겟 페이지 가드)

*   **안 A) 전역 미들웨어(Global Middleware)에서 세션 검사 후 리다이렉트**
    *   *장점*: 모든 API와 페이지 진입 전에 동의 여부를 강력하게 통제할 수 있어 안전함.
    *   *단점*: 정적 자원(Static Assets)이나 비회원용 메인 페이지 진입 시에도 매번 세션을 검사하여 데이터베이스에 불필요한 부하를 주며, 게스트 유저의 마찰을 제거하기 어려움.
*   **안 B) 온보딩 및 핵심 API 진입 지점에서의 타겟 가딩 (선택)**
    *   *장점*: 게스트 상태에서는 로컬 저장소만 활용하므로 동의 프로세스를 완벽히 생략 가능. 사용자가 실제 개인 맞춤형 기능(기피 성분 설정 등)을 사용하기 위해 온보딩에 진입하거나, 소셜 로그인을 통해 서버에 데이터를 저장하는 시점에만 선택적으로 동의를 요구함.
    *   *단점*: 라우터 단위에서 동의 여부를 확인하는 로직이 꼼꼼하게 관리되어야 함.

**[결정]** 저희는 사용자 경험을 최우선으로 고려하여 **안 B**를 선택했습니다. 무분별한 전역 미들웨어 대신, 데이터가 실제 서버로 전송되는 **온보딩(`/onboarding`) 및 가입/이관 API**단에서 동의 이력을 검증하는 방식으로 설계했습니다.

## 3. 최종 해결 방식 (Implementation)

PickSafe 팀은 아래와 같이 세 가지 핵심 레이어에서 문제를 해결했습니다.

```
[비회원 (Local Storage 활용)] ──(회원가입/로그인)──> [온보딩 / 동의 게이트] ──> [DB 적재 (user_consents)]
- 동의 팝업 없음                                    - 다국어 마크다운 동의서         - 약관 버전별 이력 관리
- 서버 데이터 전송 없음                              - 개별 체크박스 강제            - 트랜잭션 보장 일괄 이관
```

### ① 데이터 모델링: 동의 이력 테이블 (`user_consents`) 신설
단순히 `User` 테이블에 `is_agreed` 형태의 Boolean 플래그만 두는 기존 방식에서 탈피하여, 다대다(M:N) 관계를 지원하는 이력 테이블을 설계했습니다.

```python
# 이해를 돕기 위해 간소화된 관계형 모델 코드입니다.
class UserConsent(Base):
    __tablename__ = "user_consents"

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False)
    consent_type = Column(String(50), nullable=False)  # 'privacy_policy', 'sensitive_health_data' 등
    version = Column(String(20), nullable=False)       # 예: '2026-07-08'
    agreed_at = Column(DateTime(timezone=True), server_default=func.now())
```
이를 통해 향후 약관이 개정되더라도 기존 동의 이력을 유지하면서 새 버전에 대한 동의만 추가로 요구할 수 있는 유연성을 확보했습니다.

### ② 인터스텔 화면 (`/consent`) 구축 및 다국어 렌더링
약관을 관리하는 폴더 구조를 기존에 흩어져 있던 구조에서 `docs/consent`로 일원화했습니다.

*   `docs/consent/privacy_policy_{locale}.md`
*   `docs/consent/sensitive_health_{locale}.md`

Jinja2 템플릿 엔진을 활용해 사용자의 Locale(다국어 설정)에 대응하는 마크다운 문서를 실시간으로 HTML로 변환하여 아코디언(Collapsible) 컴포넌트에 바인딩했습니다. 

또한 화면 UI에서 **"개인정보 수집 및 이용 동의"**와 **"건강 관련 정보 수집 및 이용 동의"** 체크박스를 완벽히 독립시켜 법률 리스크를 원천 차단했습니다.

```javascript
// 프론트엔드 제어 예시: 두 체크박스가 모두 활성화되어야 진행 가능
const generalAgreed = document.getElementById('general-check').checked;
const sensitiveAgreed = document.getElementById('sensitive-check').checked;
const submitBtn = document.getElementById('submit-btn');

submitBtn.disabled = !(generalAgreed && sensitiveAgreed);
```

### ③ 게스트 유저의 '마찰 제로(Zero-Friction)' 온보딩 및 데이터 일괄 이관
가장 공을 들인 부분은 바로 **비회원 경험**이었습니다. 비회원이 서비스를 구경할 때는 동의서가 필요하지 않습니다. 데이터가 서버로 저장되지 않고 오직 단말기의 Local Storage에서만 맴돌기 때문입니다.

이후 게스트 유저가 소셜 로그인을 통해 정식 회원으로 전환되는 시점에, **[기존 로컬 저장 정보 전송 + 약관 동의 이력 생성]**을 한 번의 트랜잭션으로 묶어 서버 DB에 이관하는 `/auth/guest-convert` API를 개발했습니다. 이 덕분에 유저는 어떠한 데이터 유실도 없이 자연스러운 업그레이드 경험을 체감하게 됩니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 프로젝트를 진행하며 팀 전체가 얻은 소중한 인사이트는 다음과 같습니다.

1.  **법적 규제(Compliance)는 기술적 제약 사항이자 아키텍처의 설계 기준이다.**
    개발 초기부터 규제 준수를 고려하지 않으면 나중에 비즈니스 로직 전체를 뜯어고쳐야 하는 재앙이 발생합니다. 법률적 요구 사항을 정형화된 데이터 모델(Versioning, Granularity)로 세련되게 치환하는 능력이 시니어 엔지니어의 핵심 역량임을 다시 한번 깨달았습니다.
2.  **보안/규제와 사용자 경험(UX)은 타협 불가능한 대립 관계가 아니다.**
    '점진적 동의(Progressive Consent)' 기법과 Local Storage를 활용한 오프라인 우선(Offline-First) 설계를 도입함으로써, 규제를 100% 만족하면서도 게스트의 진입 장벽을 완전히 허물 수 있었습니다.
3.  **다국어(i18n) 마크다운 파이프라인의 효율성.**
    약관을 코드로 관리하는 대신 마크다운 문서로 파편화되지 않게 중앙 집중식으로 관리함으로써, 기획/법무 부서와의 소통 비용을 대폭 줄일 수 있었습니다.

안전한 서비스, 그리고 유저가 안심하고 쓸 수 있는 서비스를 만들기 위한 PickSafe 팀의 여정은 계속됩니다. 혹시 이와 유사한 민감 정보 처리 아키텍처를 고민하고 계신다면 이 글이 작은 힌트가 되기를 바랍니다.
