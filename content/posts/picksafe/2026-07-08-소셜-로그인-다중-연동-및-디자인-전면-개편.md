안녕하세요, PickSafe 개발 팀입니다. 

스타트업이나 신규 서비스를 빌딩할 때, 우리는 종종 '빠른 MVP 출시'와 '지속 가능한 아키텍처' 사이에서 타협을 해야 하는 상황에 놓입니다. 초기 PickSafe 역시 빠르게 시장 검증을 하기 위해, 사용자가 하나의 소셜 계정(Google, Facebook 등)만 연동할 수 있는 단순한 1:1 구조로 로그인 기능을 구현했었습니다.

하지만 서비스가 성장하고 유저가 늘어나면서, **"동일한 이메일인데 다른 소셜로 로그인했더니 기존 데이터가 유실되었어요"**, **"브랜드 로고는 아기자기한데 웹사이트 톤앤매너는 너무 어두워 이질감이 느껴져요"** 같은 실제 유저들의 페인 포인트(Pain Point)가 접수되기 시작했습니다.

이번 포스팅에서는 이러한 문제를 해결하기 위해 백엔드 DB 스키마 설계부터 보안 필터링, 그리고 프론트엔드 UI 디자인 시스템 전면 개편까지, **PickSafe 팀이 마주한 기술적 도전과 의사결정 과정**을 공유합니다.

---

## 1. 문제 정의 (Problem)

저희가 당면한 과제는 크게 세 가지 영역으로 나뉘었습니다.

### ① 1:1 관계 소셜 계정의 한계와 데이터 유실 위험
기존 설계에서는 `users` 테이블 내에 소셜 로그인 정보가 종속되어 있었습니다. 이 구조에서는 유저가 구글로 가입한 후 나중에 동일한 이메일을 사용하는 페이스북으로 로그인을 시도할 때, 기존 연동 정보가 덮어씌워지거나 계정이 이중으로 생성되어 데이터 정합성이 깨지는 치명적인 문제가 있었습니다.

### ② 보안 무임승차(Account Hijacking) 공격 위험
다중 소셜 연동을 허용할 때 가장 주의해야 할 점은 **이메일 소유권 검증**입니다. 이메일 검증 기능이 없는 서드파티 제공자(IdP)를 통해 타인의 이메일을 사칭해 로그인할 경우, 기존에 존재하는 정상 유저의 계정에 무단으로 연결되는 보안 사고가 발생할 수 있습니다.

### ③ 개발 생산성(DX) 저하
회원가입 및 비밀번호 찾기 시 이메일 인증 기능이 작동해야 하는데, 로컬 개발 환경에서는 외부 이메일 API의 샌드박스 제한(등록된 테스트 메일 주소 외 수신 불가) 때문에 전체 회원가입 시나리오를 매끄럽게 디버깅하기 어려웠습니다.

### ④ 브랜드 정체성과 UI의 불일치
친근하고 귀여운 파스텔 톤 로고 컨셉과 다르게, 기존 웹사이트 UI는 어두운 다크 네이비 테마를 유지하고 있어 첫인상에서 브랜드 아이덴티티가 제대로 전달되지 않았습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 고민 1. 다중 소셜 계정을 어떻게 모델링할 것인가?
* **대안 A: 기존 `users` 테이블에 컬럼 추가 (`google_id`, `facebook_id` 등)**
  * *장점:* 조인(Join)이 필요 없어 조회가 빠르고 구현이 직관적임.
  * *단점:* 새로운 소셜 로그인 수단이 추가될 때마다 DB 스키마를 변경(DDL)해야 함. 확장성이 극히 낮음.
* **대안 B (선택): 외래키 매핑 테이블(`UserSocialAccount`)로 분리 (1:N 관계)**
  * *장점:* `users` 테이블을 건드리지 않고도 무한히 새로운 소셜 로그인 프로바이더를 추가할 수 있음.
  * *단점:* 사용자 정보 조회 시 조인 연산이 추가됨. 
  * *결정:* 인덱싱을 적절히 적용하면 조인 비용은 미미하므로, **유연성과 확장성**을 위해 대안 B를 선택했습니다.

```
[기존 구조]
[users] (social_id, provider 직접 소유) 

[개선된 1:N 구조]
[users] 1  ───  N [user_social_accounts] (provider, provider_user_id, email_verified...)
```

### 고민 2. 이메일 기반 자동 매핑, 어디까지 허용할 것인가?
동일한 이메일 주소를 가진 서로 다른 소셜 계정 요청이 들어왔을 때의 보안 정책을 수립해야 했습니다.
* **보안 필터링 도입:** OAuth 프로바이더로부터 전달받은 `email_verified` 플래그가 `True`인 신뢰할 수 있는 요청에 한해서만 기존 계정과 자동 연동을 수행하도록 결정했습니다. 만약 해당 이메일이 검증되지 않은 소셜 계정이라면 연동을 거부하여 타인의 무단 계정 점유를 원천 차단했습니다.

### 고민 3. 로컬 개발 환경에서의 이메일 테스트 병목 해결
* **대안 A: 로컬 환경용 가짜 이메일 서버(Mailhog 등) 구축**
  * *장점:* 완벽한 격리 테스트 가능.
  * *단점:* 도커 환경 등 인프라 설정 공수가 듦.
* **대안 B (선택): 개발용 폴백(Fallback) 모드 구현**
  * *장점:* 환경 변수(`ENV=dev`)가 감지되면 API 전송 에러를 우회(Skip)하고 터미널 콘솔 로그에 인증 링크를 직접 출력하도록 함.
  * *결정:* 리소스를 최소화하면서 즉각적인 디버깅 흐름을 확보하기 위해 대안 B를 도입했습니다.

## 3. 최종 해결 및 엔지니어링 교훈 (Takeaway)

### 실질적인 해결책 적용

1. **DB 스키마 마이그레이션 안전장치 마련**
   * 테이블 구조를 변경하며 `users` 테이블에 관리자 권한 여부를 구분할 수 있는 `role` 컬럼을 추가했습니다. 
   * 이때, 배포 초기 구동 시 컬럼 부재로 인한 SQL 에러 발생 가능성을 예방하기 위해, **자가 진단 DDL 마이그레이션 로직**을 가동 단계에 추가했습니다. 데이터베이스 커넥션 풀이 잡히는 시점에 컬럼의 존재 여부를 체크하고 안전하게 신설하도록 보장했습니다.

2. **유연한 디자인 시스템 구축**
   * 서비스의 로고(`picksafe_log.png`) 분석을 바탕으로 브랜드 메인 컬러인 **민트 그린(#5ABFAD), 파스텔 핑크(#F4A5B0), 크림색(#FFF8F0)**을 도출했습니다.
   * 이를 CSS 커스텀 변수(Variables)로 정의하고 하드코딩되어 있던 스타일을 변수 기반으로 전면 리팩토링하여, 차후 다크모드 지원이나 테마 변경 요구사항에도 손쉽게 대응할 수 있는 아키텍처를 프론트엔드에 적용했습니다.
   * 또한 사용자 인터랙션 강화를 위해 로고 호버 시 윙크하는 이미지(`picksafe_log_on.png`)로 전환되는 세심한 마이크로 인터랙션을 반영했습니다.

### 엔지니어링 교훈 (Takeaways)

* **보안과 사용자 편의성은 트레이드 오프 관계이지만, 타협 불가능한 기준선이 존재한다.**
  * 이메일 자동 연동은 유저 입장에서 매우 편리하지만, `email_verified`를 검증하지 않았다면 보안 홀(Vulnerability)이 될 수 있었습니다. 보안과 UX를 설계할 때는 항상 최악의 시나리오를 먼저 산정해야 합니다.
* **개발자 경험(DX) 투자는 즉각적인 비즈니스 가치로 이어진다.**
  * 개발용 이메일 폴백 모드를 도입한 덕분에 로컬 환경 가입 테스트에 낭비되던 엔지니어링 시간이 하루 평균 수십 분 이상 단축되었고, 가입 프로세스 개선 작업에 집중할 수 있었습니다.
* **브랜드 언어와 UI 언어는 통일되어야 한다.**
  * 아름다운 기술을 만들어도 사용자가 느끼는 첫인상이 일관되지 못하면 가치가 떨어집니다. 로고 이미지 기반의 리뉴얼 작업을 거쳐 비로소 프로덕트의 완성도가 한 단계 올라갔음을 느꼈습니다.

우리는 이번 아키텍처 개편을 통해 더 안전하고, 더 유연하며, 더욱 친근한 서비스를 완성할 수 있었습니다. 앞으로도 PickSafe 팀은 기술적 부채를 적시에 해결하며, 단단한 프로덕트를 만들어 나가겠습니다.
