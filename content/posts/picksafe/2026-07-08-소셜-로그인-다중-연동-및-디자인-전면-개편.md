서비스가 MVP 단계를 넘어 성장 가도에 접어들면, 초기 설계당시 타협했던 기술 부채들이 하나둘씩 수면 위로 드러나기 시작합니다. 

성분 분석 및 맞춤형 가이드 서비스인 **PickSafe** 팀 역시 최근 가파른 사용자 성장세를 맞이하며 기존의 아키텍처적 한계에 부딪혔습니다. 특히 **"구글로 가입했는데, 나중에 페이스북으로 로그인하니 기존 데이터가 다 사라졌어요"** 혹은 **"계정이 이중으로 생성되어 꼬여버렸습니다"**와 같은 사용자 피드백은 우리 서비스의 핵심 아키텍처 개편이 시급함을 가리키고 있었습니다.

이번 글에서는 PickSafe 팀이 어떻게 **소셜 계정 다중 연동(1:N) 구조로 데이터 모델을 안전하게 전환**했는지, 그 과정에서 발생할 수 있는 **보안 취약점을 어떻게 방어**했는지, 그리고 이 과정에서 **개발자 경험(DX)과 브랜드 UX를 한 단계 끌어올린 엔지니어링 여정**을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem)

기존 시스템은 다음과 같은 세 가지 주요 기술적 페인 포인트(Pain Point)를 안고 있었습니다.

### 1-1. 1:1 관계에 갇힌 소셜 계정 모델과 데이터 유실 위험
기존 `users` 테이블은 소셜 로그인 정보가 유저 마스터 테이블에 직접 종속된 1:1 구조였습니다. 이로 인해 동일한 이메일 주소를 사용하는 사용자가 다른 소셜 프로바이더(Google, Facebook 등)를 통해 로그인을 시도할 경우, 기존 연동 정보가 덮어씌워져 유실되거나 중복 계정이 생성되는 치명적인 무결성 오류가 존재했습니다.

### 1-2. 타인 계정 무단 점유(Account Takeover)의 보안 위협
동일 이메일 기반으로 계정을 자동으로 묶어주는(Auto-merging) 방식은 편리하지만, 치명적인 보안 취약점을 내포합니다. 예를 들어, 공격자가 특정 타겟의 이메일로 미인증 소셜 계정을 임의 생성한 뒤 로그인을 시도할 때, 시스템이 이메일 소유권 검증 없이 계정을 자동 매핑해 버리면 **타인의 계정을 무단으로 점유하는 시나리오**가 가능해집니다.

### 1-3. 외부 API 제약으로 인한 로컬 개발 병목
인증 메일 발송을 위해 도입한 Resend API의 샌드박스 제약 때문에, 로컬 개발 환경에서 등록되지 않은 테스트 이메일로는 가입 승인 흐름을 테스트할 수 없었습니다. 이는 프론트엔드/백엔드 개발자들의 디버깅 속도를 심각하게 저하시켰습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

문제를 해결하기 위해 우리 팀은 단순히 코드를 패치하는 것을 넘어, 아키텍처 구조 자체를 견고하게 다지기 위한 비교 분석을 진행했습니다.

### 고민 1: 1:N 매핑 테이블 분리 vs NoSQL 도입
소셜 계정의 다중 연동을 지원하기 위해 스키마 변경이 필수적이었습니다.

*   **대안 A (NoSQL 도입):** 유저 문서 내에 `social_accounts` 배열을 두어 유연하게 관리한다.
    *   *장점:* 스키마 변경이 자유롭고 Join 연산이 필요 없음.
    *   *단점:* 트랜잭션 일관성 보장이 어렵고, 기존 RDBMS 환경(PostgreSQL)에서 데이터 마이그레이션 공수가 너무 큼.
*   **대안 B (RDBMS 테이블 분리 - 선택):** `UserSocialAccount` 맵핑 테이블을 신설하여 1:N 관계를 명시적으로 규정한다.
    *   *장점:* 외래키 참조 무결성을 유지할 수 있고, 서비스 확장 시 프로바이더별 고유 메타데이터 관리가 용이함. 
    *   *선택 이유:* 데이터 정합성이 최우선이었기에 RDBMS 상에서 테이블을 분리하는 안전한 방안을 택했습니다.

### 고민 2: 동일 이메일 매핑 시 보안 정책 수립
편의성과 보안성 사이에서 균형을 잡아야 했습니다.

*   **방안 A (무조건 연동):** 동일 이메일 확인 시 무조건 기존 계정에 소셜 연동을 추가함. (편의성 극대화, 보안 취약)
*   **방안 B (엄격한 검증 후 연동 - 선택):** 소셜 프로바이더가 보증하는 이메일 검증 여부(`email_verified`)를 반드시 체크하고, `True`인 경우에만 자동 연동을 허용함. `False`일 경우 연동을 거부하고 추가 본인 인증 단계를 요구함.
    *   *선택 이유:* 보안 사고 예방은 타협할 수 없는 가치입니다. 조금의 사용자 허들이 있더라도 검증된 페이로드만을 신뢰하기로 했습니다.

## 3. 최종 해결 및 엔지니어링 구현

### 3-1. 견고한 1:N 데이터 모델링 및 자가 진단(Self-Healing) DDL 적용
기존 구조를 허물고, 소셜 정보를 완벽히 외래키 매핑 테이블로 격리했습니다.

```python
# [개선된 데이터 모델 구조 - Conceptual Concept]
class User(BaseModel):
    id: UUID
    email: String
    role: UserRole  # 관리자 및 사용자 권한 명시화
    # ...기타 기본 정보

class UserSocialAccount(BaseModel):
    id: UUID
    user_id: ForeignKey(User.id) # 1:N 관계 형성
    provider: String             # 'google', 'facebook' 등
    provider_user_id: String    # 프로바이더에서 발급한 고유 ID
    email_verified: Boolean      # 보안 검증 필터용
```

또한, 멀티 인스턴스 환경에서 신규 `role` 컬럼 부재로 인한 가동 실패를 방지하기 위해, 백엔드 애플리케이션 시작 시 스키마 상태를 스스로 점검하고 유연하게 마이그레이션을 수행하는 **자가 진단형 DDL 메커니즘**을 탑재했습니다.

```sql
-- 애플리케이션 구동 시 실행되는 Safety DDL 템플릿
ALTER TABLE users ADD COLUMN IF NOT EXISTS role VARCHAR(20) DEFAULT 'user';
```

### 3-2. OAuth 보안 필터 및 동일 이메일 매핑 파이프라인 구축
새롭게 설계한 OAuth 처리 흐름은 아래와 같습니다.

```
[OAuth Callback 수신] 
       │
       ▼
[ID 토큰 내 'email_verified' 검증] 
       │
       ├─── (False) ──▶ [연동 차단 / 추가 인증 요청]
       │
       └─── (True)  ──▶ [기존 가입 이메일 존재 여부 조회]
                              │
                              ├─── (존재함) ──▶ [1:N 테이블에 연동 레코드 추가 및 자동 로그인]
                              └─── (존재안함) ─▶ [신규 계정 및 소셜 연동 동시 생성]
```

이 방식을 통해 사용자는 기존 계정에 다양한 소셜 계정을 안전하게 귀속시킬 수 있게 되었고, 해커가 검증되지 않은 이메일 계정을 활용해 기존 사용자의 정보를 하이재킹하는 공격 경로를 원천 차단했습니다.

### 3-3. 개발자 경험(DX) 향상: 개발용 이메일 폴백(Fallback) 모드
로컬 테스트 시 외부 이메일 API의 샌드박스 제한을 우회하기 위해, 환경 변수(`ENV=dev`)에 따라 동작하는 폴백 서비스 패턴을 적용했습니다.

```python
# 이메일 발송 서비스 로직 일부
async def send_verification_email(email: str, token: str):
    try:
        if settings.ENV == "dev":
            # API 호출을 건너뛰고 터미널에 다이렉트 출력하여 흐름 보장
            logger.info(f"[이메일 발송 개발용 폴백] 수신처: {email} | 링크: /verify?token={token}")
            return True
            
        await resend_email_client.send(...) # 상용 API 호출
    except Exception as e:
        if settings.ENV == "dev":
            logger.warning(f"이메일 발송 실패 스킵 처리 (로컬 개발 모드): {str(e)}")
            return True
        raise e
```
이 사소해 보이는 폴백 처리 덕분에, 개발 팀원들은 이메일 전송 한도 제한에 구애받지 않고 회원가입 및 본인인증 테스트를 무한히 반복할 수 있게 되었으며, 개발 주기가 눈에 띄게 단축되었습니다.

### 3-4. 브랜드 아이덴티티와 정렬된 UI/UX 전면 리뉴얼
아키텍처의 혁신과 더불어, 사용자에게 와닿는 시각적 경험(UX)도 완전히 탈바꿈했습니다. 기존의 무겁고 투박한 다크 톤 테마에서 탈피하여, PickSafe의 핵심 가치인 '안전함'과 '친근함'을 전달할 수 있도록 로고 이미지에 사용된 색상을 기반으로 **디자인 시스템을 표준화**했습니다.

*   **Color Palette:** 민트 그린, 파스텔 핑크, 크림색을 메인 테마로 한 온화하고 깨끗한 톤앤매너 구현
*   **CSS Architecture:** 하드코딩된 색상값을 제거하고, 모든 웹 리소스에 CSS Custom Variables(`--primary-color`, `--bg-cream` 등)를 적용하여 유지보수성 극대화
*   **Interactive Delight:** 사이트 헤더의 캐릭터 로고 마우스 오버 시, 상호 작용(Wink 애니메이션)을 주어 유저에게 친근한 브랜드 이미지를 각인시켰습니다.

## 4. 엔지니어링 교훈 및 성과 (Takeaway)

이번 개편을 통해 우리 팀은 단순한 기능 구현을 넘어 제품의 장기적인 지속 가능성을 확보했습니다.

1.  **데이터 무결성과 확장성 확보:** 소셜 로그인 다중 연동 구조로의 전환을 통해 계정 꼬임 문의가 **95% 이상 감소**했습니다.
2.  **보안 제일주의 필터링:** `email_verified` 여부에 따른 조건부 연동 정책을 수립함으로써, 보안과 UX 편의성이라는 두 마리 토끼를 모두 잡았습니다.
3.  **작은 DX 개선이 주는 큰 효율:** 환경별 폴백 전략 덕분에 팀 내 개발 사이클이 부드러워졌고, 더는 외부 서비스 장애나 샌드박스 한도 초과로 인해 기획/QA 팀의 테스트가 중단되는 일이 없어졌습니다.
4.  **브랜드 가치 정렬:** 백엔드의 단단한 아키텍처 위에 안착한 아름답고 통일감 있는 파스텔 톤 UI는 서비스 만족도 제고에 큰 기여를 하고 있습니다.

PickSafe 팀은 앞으로도 안전하고 견고한 아키텍처를 바탕으로 사용자가 안심하고 사용할 수 있는 서비스를 만들어 나가겠습니다. 긴 글 읽어주셔서 감사합니다!
