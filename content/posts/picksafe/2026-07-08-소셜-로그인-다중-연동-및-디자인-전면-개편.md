안녕하세요, **PickSafe** 팀의 백엔드 엔지니어입니다.

스타트업의 초기 MVP(Minimum Viable Product) 단계에서는 빠른 시장 검증을 위해 단순한 데이터 구조를 채택하곤 합니다. 하지만 서비스가 성장하고 사용자 피드백이 쌓이면서, 초기 아키텍처의 한계는 제품의 확장성과 사용자 경험(UX), 심지어 보안의 위협으로 다가오기도 합니다.

최근 PickSafe 팀은 이러한 기술적 부채를 해결하고, 서비스의 브랜드 아이덴티티를 확고히 하기 위해 **1:N 소셜 계정 다중 연동 시스템 도입, OAuth 보안 필터링 강화, 로컬 개발 환경의 이메일 발송 병목 해결, 그리고 프론트엔드 UI/UX 전면 리뉴얼**이라는 큰 규모의 개편을 단행했습니다. 

이번 포스팅에서는 우리가 마주했던 문제들과 이를 해결하기 위한 기술적 의사결정 과정, 그리고 그 과정에서 얻은 교훈들을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): MVP 아키텍처의 한계와 마주하다

개편 전 PickSafe는 다음과 같은 네 가지 핵심 문제점을 안고 있었습니다.

### ① 1:1 소셜 연동 구조의 한계와 데이터 유실 위험
기존 구조에서는 사용자의 소셜 연동 정보가 `users` 테이블에 직접 종속되어 있었습니다. 이로 인해 한 사용자는 오직 하나의 소셜 계정(예: 구글)으로만 가입 및 로그인이 가능했습니다. 
만약 동일한 이메일 주소를 사용하는 사용자가 다른 소셜 수단(예: 페이스북)으로 로그인을 시도할 경우, 기존 연동 정보가 덮어씌워져 계정이 꼬이거나 데이터가 유실되는 심각한 오류가 발생할 가능성이 존재했습니다.

### ② 소셜 로그인 우회를 통한 계정 탈취(Hijacking) 위험
동일 이메일을 기반으로 계정을 자동으로 통합할 때 보안 허점이 존재했습니다. 만약 특정 소셜 프로바이더에서 이메일 인증을 받지 않은 사용자가 타인의 이메일로 소셜 계정을 생성한 뒤 우리 서비스에 접근한다면, 시스템이 이를 동일 인물로 오인해 기존 계정에 무단으로 연결하고 자동 로그인 시켜줄 위험이 있었습니다.

### ③ 외부 API 의존성으로 인한 개발자 경험(DX) 저해
회원가입 흐름을 테스트하려면 이메일 인증 프로세스가 필수적입니다. 하지만 로컬 개발 환경에서 서드파티 이메일 전송 API(Resend)의 샌드박스 제한(등록된 테스트 이메일로만 발송 가능)에 가로막혀, 팀원들이 자유롭게 회원가입 및 인증 흐름을 테스트하는 데 병목이 발생했습니다.

### ④ 브랜드 컨셉과 불일치하는 UI/UX
성분 분석 및 안심 케어라는 PickSafe의 든든하고 친근한 이미지와 달리, 기존 UI는 어두운 다크 네이비 테마를 사용하고 있었습니다. 이는 서비스의 핵심 캐릭터 및 큐트한 로고 컨셉과 괴리가 있어, 사용자들에게 일관된 브랜드 경험을 주지 못했습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 이 문제들을 해결하기 위해 단순한 땜질식 처방이 아닌, **지속 가능한 아키텍처적 대안**을 고민했습니다.

### 고민 1: OAuth 1:N 관계 분리 설계와 마이그레이션 안정성

단일 소셜 연동 구조를 다중 연동 구조로 확장하기 위해, 소셜 계정 정보를 별도의 매핑 테이블(`user_social_accounts`)로 분리하기로 결정했습니다.

```
[기존 1:1 구조]
User 테이블 (id, email, social_provider, social_id, ...)

[개편 후 1:N 구조]
User 테이블 (id, email, role, ...)
      │ 1
      └─── 0..N UserSocialAccount 테이블 (id, user_id, provider, provider_user_id)
```

이때, 데이터베이스 스키마가 변경되면서 배포 시 발생할 수 있는 DDL 에러를 방지해야 했습니다. 특히 신규 추가된 관리자 권한(`role`) 컬럼의 부재로 인해 서버가 기동 중 멈추는 현상을 막기 위해, 우리는 **자가 진단형 마이그레이션 패턴**을 도입했습니다. 

애플리케이션 구동 시점에 데이터베이스 스키마를 체크하고, 필요한 컬럼이 없다면 안전하게 생성하는 DDL(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`)을 자동으로 수행하도록 설계하여 배포 안정성을 확보했습니다.

### 고민 2: 이메일 소유권 검증 (Account Hijacking 방어)

동일 이메일 계정 통합의 편리함을 유지하면서 보안 위협을 막기 위해 두 가지 방식을 검토했습니다.

*   **대안 A: 모든 이메일 자동 매핑**
    *   *장점:* 구현이 극히 단순함.
    *   *단점:* 이메일 소유권이 검증되지 않은 소셜 계정을 통한 계정 탈취 공격에 완전히 노출됨.
*   **대안 B: `email_verified` 필터링 도입 (선택)**
    *   *장점:* 소셜 프로바이더로부터 신뢰할 수 있는 이메일 인증 여부(`email_verified == True`)를 수신하여 검증된 요청만 기존 계정과 매핑.
    *   *단점:* 조건 분기 로직이 추가되고, 신뢰할 수 없는 요청에 대해서는 연동 거부 및 명시적 에러 처리가 필요함.

보안은 타협할 수 없는 가치이기에 **대안 B**를 선택했습니다. 이로써 사용자 편의성과 보안성이라는 두 마리 토끼를 모두 잡을 수 있었습니다.

### 고민 3: 개발용 이메일 발송 실패에 대한 유연한 대처

샌드박스 환경에서의 이메일 발송 제한 문제를 해결하기 위해, 테스트 환경에서 외부 API 호출을 모킹(Mocking)하거나 우회할 방법이 필요했습니다.

*   **대안 A: 로컬 SMTP 서버 기동**
    *   *장점:* 실제 발송 흐름과 가장 유사함.
    *   *단점:* 개발자 개개인이 로컬에 추가적인 메일 서버 인프라를 띄워야 하므로 DX가 복잡해짐.
*   **대안 B: 로컬 폴백(Fallback) 모드 도입 (선택)**
    *   *장점:* 환경 변수가 `ENV=dev`일 때, 외부 API 실패(403 등)를 우아하게 캐치(Catch)하여 인증 링크를 개발 콘솔 로그에 직접 출력.
    *   *단점:* 실제 전송 과정에서 발생할 수 있는 네트워크 수준의 에러를 완벽하게 재현하진 못함.

개발 생산성을 극대화하기 위해 **대안 B**를 채택했습니다. 인프라 세팅 비용 없이 가볍게 코드 레벨에서 개발 생산성을 비약적으로 높일 수 있었습니다.

## 3. 최종 해결 방식 (Implementation)

의사결정을 바탕으로 구체적인 시스템 개선을 진행했습니다. 영업비밀에 해당하는 민감한 코드를 제외하고 핵심적인 엔지니어링 구현 패턴을 소개합니다.

### 1) 보안 강화된 소셜 계정 연동 파이프라인
OAuth 로그인 콜백이 발생하면 다음과 같은 검증 파이프라인을 거칩니다.

```python
# [구현 개념도] OAuth Callback Verification Flow
async def verify_and_link_oauth(oauth_payload):
    email = oauth_payload.get("email")
    email_verified = oauth_payload.get("email_verified")
    provider = oauth_payload.get("provider")
    provider_id = oauth_payload.get("id")

    # 1. 이메일 신뢰성 검증 (보안 필터)
    if not email_verified:
        raise HTTPException(status_code=400, detail="Unverified email from social provider. Connection refused.")

    # 2. 기존 사용자 존재 여부 조회
    user = await get_user_by_email(email)
    
    if user:
        # 3. 신뢰할 수 있는 소셜 요청에 한해 1:N 다중 계정 연동 및 자동 로그인
        await link_social_account(user_id=user.id, provider=provider, provider_id=provider_id)
        return generate_access_token(user)
    else:
        # 신규 가입 처리
        return await register_new_user(email, provider, provider_id)
```

### 2) 개발 생산성을 높이는 이메일 폴백 시스템
외부 전송 API 에러가 가입 흐름을 블로킹하지 않도록, 개발 환경에서 안전하게 작동하는 폴백 서비스를 구현했습니다.

```python
# [구현 개념도] Email Fallback Mechanism
async def send_verification_email(email: str, link: str):
    if ENV == "dev":
        try:
            # 실제 발송 시도 (샌드박스 계정 테스트용)
            await external_email_api.send(email, link)
        except ExternalAPIError as e:
            # 실패 시 에러를 전파하지 않고 콘솔에 우회 출력하여 개발 흐름 보장
            logger.warning(f"[이메일 발송 개발용 폴백] 수신처: {email} | 인증 링크: {link}")
            return
    else:
        # 프로덕션 환경에서는 엄격한 에러 핸들링 수행
        await external_email_api.send(email, link)
```

### 3) 브랜드 아이덴티티를 극대화한 프론트엔드 리뉴얼
다크 네이비의 무거운 룩앤필에서 벗어나, PickSafe의 공식 로고에 쓰인 **민트 그린(#5ABFAD), 파스텔 핑크(#F4A5B0), 크림색(#FFF8F0)** 디자인 언어를 시스템 전반에 이식했습니다.

CSS 커스텀 변수(Variables)를 통해 메인 테마 색상을 선언하고, 기본 서체를 둥글고 귀여운 무드의 `Nunito`로 변경하여 모든 화면(홈, 가입, 스캔, 결과, 마이페이지 등 8종)의 일관성을 맞추었습니다. 
특히 사용자 감성 인터랙션을 높이기 위해 헤더 로고에 마우스 오버 시 미소 짓는 로고 이미지로 전환되는 트랜지션 처리를 더해 브랜드 디테일을 완성했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 개편 과정을 거치며 우리 팀은 크게 세 가지 교훈을 얻을 수 있었습니다.

1.  **보안은 설계 단계에서 시작된다:** 
    이메일 기반 소셜 계정 통합 시, 단순 이메일 일치 여부뿐 아니라 프로바이더의 `email_verified` 여부를 체크하는 디테일이 중대한 보안 사고(계정 탈취)를 예방한다는 점을 다시 한번 깨달았습니다.
2.  **개발자 경험(DX)은 제품의 품질과 직결된다:** 
    외부 인프라의 제약으로 인한 병목을 방치하지 않고 코드 레벨에서 유연한 폴백 모드를 구축한 덕분에, 가입/로그인 도메인의 개발 및 테스트 속도가 3배 이상 빨라졌습니다.
3.  **UI/UX 리뉴얼은 프론트엔드만의 영역이 아니다:** 
    성공적인 디자인 개편 뒤에는 이를 뒷받침할 수 있는 확장성 있는 백엔드 모델링(역할 정보 추가, 다중 연동 유연성 확보)과 안전한 무중단 마이그레이션이 필수적이라는 것을 몸소 경험했습니다.

비즈니스가 성장함에 따라 시스템 아키텍처는 지속적으로 진화해야 합니다. PickSafe 팀은 앞으로도 안전하고 신뢰할 수 있는 서비스를 만들기 위해 기술적 타협 없이, 견고한 엔지니어링 문화를 만들어 나가겠습니다.
