서비스가 성장하고 사용자 유입 경로가 다양해짐에 따라, **인증(Authentication) 시스템의 유연성과 보안성**은 백엔드 아키텍처에서 가장 먼저 직면하는 과제 중 하나입니다.

이번 글에서는 **PickSafe** 백엔드 팀이 기존 단일 소셜 계정 연동(1:1) 구조의 한계를 극복하기 위해 **1:N 다중 소셜 계정 모델로 스키마를 재설계한 과정**, **계정 무단 점유(Account Takeover)를 막기 위한 OAuth 보안 필터링 적용**, 그리고 **개발자 경험(DX) 향상을 위한 폴백(Fallback) 구조 구축 경험**을 공유합니다.

---

## 1. Problem: 1:1 관계의 한계와 계정 덮어쓰기 문제

### 문제 상황
기존 PickSafe의 회원 모델은 `User` 테이블 내부에 OAuth Provider 정보(e.g., `provider`, `provider_user_id`)를 직접 소유하는 **1:1 종속 구조**였습니다. 

이 방식은 초기에 빠르게 인증을 구현할 수 있다는 장점이 있지만, 다음과 같은 치명적인 문제가 발생했습니다.
1. **계정 정보 유실/덮어쓰기:** 사용자가 동일한 이메일 주소로 구글 로그인 후 페이스북 로그인을 시도할 때, 기존 인증 정보가 덮어씌워지거나 데이터 무결성이 깨지는 현상 발생.
2. **확장성 부재:** 추후 자사 이메일 로그인(Local ID/PW)과 다중 소셜 계정을 병합(Merge)하거나 유연하게 연동/해제할 수 있는 비즈니스 요구사항을 수용할 수 없음.

### 해결책: 1:N 다중 계정 모델로의 정규화 (Decoupling)
사용자 Entity(`User`)와 소셜 인증 Entity(`UserSocialAccount`)를 분리하여 **1:N 관계**로 재설계했습니다.

```
[ 기존 1:1 구조 ]
User (id, email, oauth_provider, oauth_provider_id) -> 확장 불가능

[ 개편된 1:N 구조 ]
User (id, email, role, ...)
  └── 1:N ── UserSocialAccount (id, user_id, provider, provider_user_id, ...)
```

#### Engineering Trade-off
* **Trade-off:** 인증 시 `User`와 `UserSocialAccount` 간의 `JOIN` 쿼리 비용이 추가로 발생합니다.
* **의사결정:** 인덱싱(`user_id`, `provider + provider_user_id` 복합 인덱스)을 통해 Query Overhead를 최소화했으며, 계정 확장성과 데이터 안정성 확보라는 이점이 성능 손실보다 훨씬 크다고 판단했습니다.

또한, 서비스 운영 중 스키마 변경으로 인한 서버 런타임 에러를 방지하기 위해 서버 구동 시점에 미반영된 컬럼이나 테이블을 자가 진단(Self-healing)하고 안전하게 보완하는 롤백 패치 로직을 백엔드 진입점에 배치하여 **배포 안정성**을 확보했습니다.

## 2. Security: 계정 무단 점유(Account Takeover) 방지

소셜 로그인을 통한 다중 계정 자동 통합(Auto-linking)을 구현할 때, **가장 위험한 보안 허점은 "이메일 신뢰성"에 대한 맹신**입니다.

### 공격 시나리오
1. 공격자가 타인의 이메일 주소(`target@email.com`)로 검증(Verification) 절차가 허술한 제3의 OAuth Provider 계정을 생성합니다.
2. 공격자가 해당 소셜 계정으로 PickSafe에 로그인을 시도합니다.
3. 시스템이 "동일한 이메일이 존재하니까 기존 계정에 연동해줘야지" 하고 무조건 병합할 경우, **공격자는 타인의 PickSafe 계정에 무단 접근**할 수 있게 됩니다.

### 방어 아키텍처: Strict `email_verified` 검증
이를 차단하기 위해 **OAuth Provider가 제공하는 `email_verified` 플래그를 필수 보안 필터로 적용**했습니다.

```python
# [보안 로직 개념 예시]
async def process_oauth_login(provider_payload: dict):
    email = provider_payload.get("email")
    is_email_verified = provider_payload.get("email_verified", False)
    
    existing_user = await find_user_by_email(email)
    
    if existing_user:
        # 이메일 검증이 완료된 신뢰할 수 있는 소셜 요청인 경우에만 다중 연동 허용
        if is_email_verified:
            return await link_social_account(existing_user, provider_payload)
        else:
            # 검증되지 않은 이메일의 접근은 거부하여 Account Takeover 차단
            raise SecurityException("Unverified OAuth email cannot be linked.")
            
    return await create_new_user(provider_payload)
```

이 규칙을 통해 **"검증된 소셜 계정만 기존 사용자 데이터에 병합"**되는 엄격한 보안 바운더리를 구축했습니다.

## 3. Developer Experience (DX): 로컬 개발용 API Fallback 모드

### 문제 상황
회원가입 및 인증 흐름에서 메일 발송 서비스(Resend API)를 활용하고 있습니다. 그러나 로컬 개발 및 QA 환경(`ENV=dev`)에서는 외부 메일 API의 샌드박스 제약(등록된 테스터 이메일 외 수신 불가, API Rate Limit 등)으로 인해 회원가입 및 이메일 인증 디버깅이 자주 블로킹되는 문제가 있었습니다.

### 해결책: Graceful Degradation 패턴 적용
개발 환경에 한해, 외부 메일 API 호출 실패(HTTP 403 등)가 발생해도 파이프라인이 중단되지 않도록 **자동 폴백(Fallback) 모드**를 구축했습니다.

* 외부 메일 발송 실패 시 예외를 스로우하여 프로세스를 멈추는 대신, 에러를 수용(Catch)합니다.
* 개발 콘솔 인터널 로그에 인증 토큰 및 링크를 안전하게 인쇄(`[이메일 발송 개발용 폴백]`)합니다.
* 결과적으로 외부 의존성(External API) 장애나 제약에 영향받지 않고 **로컬 환경에서 끊김 없이(Seamless) 가입/인증 흐름을 완주**할 수 있게 되었습니다.

## 4. Brand & UI Modernization: 디자인 시스템 전면 개편

기술 백엔드의 레이어 개편과 함께, 프론트엔드 역시 브랜딩 일관성을 높이기 위한 시스템 개편을 병행했습니다.

* **CSS Custom Variables 기반 테마 시스템:** 브랜드 로고의 키 컬러(Mint Green `#5ABFAD`, Pastel Pink `#F4A5B0`, Cream `#FFF8F0`)를 토큰화하여, 기존 다크 네이비 톤에서 밝고 친근한 파스텔 톤 UI로 전면 개편했습니다.
* **Micro-interaction 도입:** 헤더 로고 Hover 시 윙크 이미지로 교체되는 인터랙션을 추가하여 브랜드 아이덴티티를 유저에게 보다 입체적으로 전달하도록 개선했습니다.

## Takeaways: 이번 개편을 통해 배운 것

1. **아키텍처의 유연성은 초기 도메인 모델링에서 나온다.**
   1:1 구조는 당장 빠를지 몰라도 확장성을 저해합니다. Entity 간의 관계(1:N)를 올바르게 정규화하는 것이 비즈니스 요구사항 변화에 유연하게 대응하는 열쇠임을 재확인했습니다.
2. **편의성과 보안의 균형 (Security Trade-off)**
   소셜 로그인 자동 연동은 유저에게 매우 편리하지만, `email_verified`와 같은 명시적 검증 장치가 없다면 치명적인 보안 허점이 됩니다. 편의 기능을 추가할 때는 항상 **위협 모델(Threat Model)**을 함께 검토해야 합니다.
3. **DX는 생산성과 직결된다.**
   외부 API 제약으로 인해 개발 흐름이 끊기는 것을 방지하는 작은 폴백 장치 하나가 전체 팀의 디버깅 속도와 테스트 생산성을 크게 향상시킵니다.

---

 PickSafe 백엔드 팀은 앞으로도 **안정적인 아키텍처**와 **높은 보안 수준**, 그리고 **뛰어난 사용자 및 개발자 경험**을 제공하기 위해 계속해서 시스템을 개선해 나갈 것입니다.
