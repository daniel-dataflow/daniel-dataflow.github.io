우리 팀이 개발 중인 성분 분석 및 추천 서비스 **PickSafe** 역시 유저 유입이 늘어남에 따라 크게 세 가지 병목에 직면했습니다. **첫째, 소셜 로그인 연동의 구조적 한계**, **둘째, 타사 API 제한으로 인한 로컬 개발 생산성 저하**, **셋째, 브랜드 아이덴티티와 서비스 UI의 불일치**였습니다.

시니어 개발자로서 이 문제들을 어떻게 정의하고, 어떤 기술적 트레이드오프를 거쳐 우아하게 해결했는지 그 과정과 교훈을 공유합니다.

## 1. 무엇이 문제였는가? (Problem Definition)

### 문제 1: 1:1 관계에 갇힌 소셜 로그인과 데이터 유실 위험
기존 데이터베이스 구조는 `users` 테이블이 소셜 로그인 정보를 직접 들고 있는 1:1 구조였습니다. 이 구조에서는 구글로 가입한 사용자가 나중에 페이스북으로 동일한 이메일을 통해 로그인을 시도할 때 기존 가입 정보가 덮어씌워지거나, 계정 정보가 꼬여 연동 데이터가 유실되는 치명적인 오류가 발생할 수 있었습니다. 

### 문제 2: 계정 탈취(Account Hijacking)의 보안 취약점
단순히 이메일 주소만 일치한다고 해서 자동으로 계정을 연동해 주면 심각한 보안 사고로 이어집니다. 일부 소셜 프로바이더는 이메일 소유권 검증 없이 계정을 생성해 주기도 합니다. 만약 공격자가 피해자의 이메일로 가짜 소셜 계정을 만든 후 우리 서비스에 로그인했을 때 자동으로 계정이 연동된다면, 타인의 계정을 무단 점유할 위험이 있었습니다.

### 문제 3: Sandbox 제한에 막힌 로컬 개발 환경 (Developer Experience, DX)
회원가입 흐름을 테스트하려면 이메일 인증이 필수적입니다. 하지만 운영 단계에서 사용하는 외부 이메일 발송 API(Resend)의 무료 샌드박스 환경은 '인증된 발송처/수신처' 외에는 메일을 보낼 수 없도록 제한되어 있었습니다. 이로 인해 로컬 개발 환경에서 가입 및 인증 흐름을 자유롭게 디버깅하기가 매우 까다로웠습니다.

### 문제 4: 브랜드 언어와 따로 노는 UI/UX
우리의 마스코트이자 로고 디자인은 친근하고 아기자기한 톤앤매너를 지향하고 있었습니다. 하지만 기존 웹 페이지는 다크 네이비 테마의 다소 무겁고 투박한 스타일을 고수하고 있어, 사용자가 랜딩 페이지와 로고를 보았을 때 느끼는 브랜드 경험의 인지적 불일치가 컸습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off & Alternatives)

### 고민 1: OAuth 구조 개선 - 컬럼 추가 vs 매핑 테이블 분리

사용자가 여러 소셜 계정(구글, 카카오, 애플 등)을 하나의 통합 계정에 연동할 수 있도록 데이터 모델을 재설계해야 했습니다.

*   **대안 A: `users` 테이블에 소셜 연동 컬럼 계속 추가하기**
    *   *장점:* 마이그레이션 공수가 적고 단순함.
    *   *단점:* 새로운 소셜 로그인 프로바이더가 추가될 때마다 DDL(Data Definition Language)을 실행해 컬럼을 늘려야 함. 확장성과 정규화 관점에서 최악의 선택.
*   **대안 B: 외래키(FK) 기반의 1:N 매핑 테이블 분리 (선택)**
    *   *장점:* `user_social_accounts` 테이블을 신설하여 1명의 유저(`users`)가 여러 개의 소셜 연동 정보(`UserSocialAccount`)를 가질 수 있도록 차단벽을 세움. 새로운 로그인 수단이 추가되어도 스키마 변경 없이 데이터 로우(Row)만 추가하면 됨.
    *   *단점:* 조인(Join) 연산이 추가되어 아주 미세한 성능 저하가 있을 수 있으나, 인덱싱을 통해 충분히 극복 가능한 수준.

**[보너스 구현 - 자가 진단(Self-healing) DDL]**
스키마 마이그레이션 시, 배포 파이프라인에서 발생할 수 있는 데이터베이스 정렬 예외를 방지하고자 했습니다. 서비스 기동 시 관리자 권한 여부를 판단하는 `role` 컬럼의 존재 여부를 쿼리로 자가 진단하고, 없을 경우 안전하게 `ALTER TABLE`을 수행하는 방어적 로직을 추가했습니다.

### 고민 2: 안전한 이메일 매핑 기준 수립

동일한 이메일을 가진 소셜 요청이 올 때 자동 연동을 허용할 것인가에 대한 기준이 필요했습니다.

```python
# 보안 필터링 비즈니스 로직 예시 (Concept)
if current_provider_email == existing_user_email:
    # 핵심 보안 필터: 해당 프로바이더가 이메일의 실소유주를 검증했는가?
    if oauth_payload.get("email_verified") is True:
        # 안전한 상태: 자동으로 1:N 매핑 테이블에 연동 추가 및 세션 발급
        link_social_account(user_id=existing_user.id, provider=provider, provider_user_id=provider_user_id)
    else:
        # 위험 상태: 연동을 차단하고 본인 인증 추가 요구
        raise SecurityException("Unverified email cannot be linked automatically.")
```
이메일 신뢰성 여부(`email_verified`)가 `True`인 신뢰할 수 있는 소셜 요청에 한해서만 계정을 연동하도록 제한함으로써, 잠재적인 계정 탈취 위협을 원천 차단했습니다.

### 고민 3: 로컬 개발망 메일 전송 문제 해결 - Mocking vs Fallback Log

*   **대안 A: 개발 환경용 Mock Object 생성**
    *   *단점:* 실제 회원가입 과정에서 발생하는 이메일 발송 비동기 이벤트 흐름을 완벽히 테스트하기 어려움.
*   **대안 B: 환경 변수 기반의 폴백 모드(Fallback Mode) 구현 (선택)**
    *   개발 모드(`ENV=dev`)일 때, 외부 API 호출 실패(예: 403 Sandbox Limit)가 발생하면 이를 에러로 터트리지 않고 예외 포착(Catch) 후 **터미널 콘솔 로그에 인증 링크를 직접 출력**하도록 구성했습니다.
    *   이로 인해 개발자는 외부 이메일 인박스를 열어볼 필요 없이, 터미널 로그에 찍힌 주소를 클릭하는 것만으로 즉시 가입 프로세스를 완벽하게 테스트할 수 있게 되었습니다.

## 3. 최종 해결 및 엔지니어링 교훈 (Takeaways)

### 주요 구현 결과
1.  **스키마 리팩토링:** `user_social_accounts` 구조로 전환하여 사용자가 구글, 페이스북, 애플 계정을 자유롭게 연동/해제할 수 있는 유연한 멀티 소셜 아키텍처를 완성했습니다.
2.  **보안 강화:** 소셜 프로바이더의 `email_verified` 여부를 검증하는 방어적 필터를 구축하여, 도메인 악용을 통한 타인 계정 무단 점유 위협을 완전히 방지했습니다.
3.  **DX 극대화:** 로컬 가입 테스트 도중 Resend API의 발송 제한 한계에 부딪혀 흐름이 끊기던 현상을 **'개발용 폴백 모드'**로 우아하게 해결했습니다. 덕분에 회원가입 관련 피처 개발 속도가 2배 이상 빨라졌습니다.
4.  **디자인 시스템 개편:** 로고 이미지의 컬러 스펙트럼인 **민트 그린(#5ABFAD), 파스텔 핑크(#F4A5B0), 크림색(#FFF8F0)**을 CSS 커스텀 변수(`--primary`, `--accent` 등)로 명세화하고, 화면 8종에 일괄 적용했습니다. 사용자가 체감하는 서비스의 톤앤매너를 일관되게 정렬했고, 인터랙티브 로고(Wink Hover Effect)를 더해 디테일한 재미를 부여했습니다.

### 시니어 개발자로서 얻은 교훈

*   **데이터 모델은 언제나 '확장'을 대비해야 합니다.** "지금은 소셜 연동 하나만 쓰니까 괜찮겠지"라는 안일한 생각이 큰 기술 부채로 돌아옴을 다시 한번 느꼈습니다. 1:N 매핑 테이블 구조는 초기 구축 비용 대비 서비스 확장 시 가져다주는 이점이 압도적으로 큽니다.
*   **개발자 경험(DX) 투자는 공짜가 아닙니다.** 로컬 개발망에서의 사소한 장애물이 쌓이면 전체 팀의 배포 주기가 늘어납니다. 환경별 세밀한 폴백 처리는 개발 생산성을 올리는 훌륭한 레버리지입니다.
*   **UI/UX는 브랜드 메시지의 확장입니다.** 기술적으로 훌륭한 백엔드를 갖추었더라도 사용자가 마주하는 첫인상이 어색하다면 제품의 신뢰도는 떨어집니다. 브랜딩 요소를 개발 단계에서 CSS 변수로 규격화하는 작업이 디자인 생산성에 얼마나 큰 도움을 주는지 실감할 수 있었던 프로젝트였습니다.
