안녕하세요. **PickSafe** 백엔드/풀스택 엔지니어링 팀입니다.

최근 서비스 내 게스트 전환 유도 정책(한도 제한 및 Nudge)을 도입하는 과정에서, 실제 사용자 경험을 저해하는 몇 가지 치명적인 정합성 결함과 성능 병목 현상을 마주했습니다. 

보안 강화를 위해 도입한 `HttpOnly` 쿠키가 프론트엔드의 로그인 상태 판별을 방해했고, ORM의 무분별한 지연 로딩(Lazy Loading)이 마이페이지 로딩 시간을 최대 10초까지 지연시키고 있었습니다.

이번 글에서는 **보안과 클라이언트 상태 관리의 괴리 문제를 해결한 아키텍처 개선 과정**, **게스트 데이터 승격(Migration) 파이프라인 설계**, 그리고 **단일 집계 SQL을 통한 마이페이지 극한의 성능 최적화(N+1 제거)** 경험을 공유하고자 합니다.

---

## 1. 마주한 문제 (Problem)

### ① `HttpOnly` 쿠키 환경과 프론트엔드의 인증 상태 오인식
보안을 위해 액세스 토큰을 `HttpOnly=True` 쿠키로 발행하기 시작했습니다. 그러나 이로 인해 클라이언트 자바스크립트(`document.cookie`)에서 토큰을 직접 읽을 수 없게 되었습니다. 
그 결과, 프론트엔드는 실제로 로그인된 사용자를 "게스트"로 오인하여, 서버가 아닌 로컬스토리지에 스캔 기록과 찜 목록을 임의 적재하는 데이터 파편화 현상이 발생했습니다.

### ② 마이페이지 로딩 지연 (최대 10초) 및 N+1 병목
마이페이지 진입 시, 사용자의 저장 상품과 스캔 이력을 렌더링하는 과정에서 심각한 병목이 발생했습니다. 
수십 개의 상품과 스캔 이력마다 연관된 성분(Ingredients) 정보를 ORM 객체로 각각 개별 조회(`SELECT N+1`)하면서, 백엔드에서 수백 번의 쿼리가 발생했고 렌더링에 최대 10초가 소요되는 최악의 사용자 경험을 낳았습니다.

---

## 2. 기술적 고민과 대안 비교 (Trade-off)

### 2.1. 인증 상태 판별: 클라이언트 파싱 vs 서버 주입(SSR Global Injection)
* **대안 A (기존 방식 유지 - 클라이언트 쿠키 파싱)**: 자바스크립트가 접근 가능한 쿠키 설정(`HttpOnly=False`)으로 회귀. 
  * *Trade-off*: XSS(Cross-Site Scripting) 공격에 토큰이 탈취될 위험이 급증하므로 보안 원칙에 위배되어 기각.
* **대안 B (API를 통한 비동기 세션 검증)**: 페이지 진입 시마다 `/auth/me` 등을 호출해 로그인 여부를 비동기로 판별.
  * *Trade-off*: 네트워크 라운드 트립이 추가 발생하여 초기 렌더링 속도에 악영향.
* **최종 선택 (대안 C - 서버 세션 기반 전역 변수 주입)**: 
  템플릿 렌더링 시점에 서버 세션 정보를 바탕으로 `window.IS_LOGGED_IN = true/false;` 및 `window.isGuestUser()` 헬퍼 함수를 전역으로 주입하기로 결정했습니다. 보안(`HttpOnly`)을 유지하면서도 프론트엔드 로직에서 추가 네트워크 요청 없이 즉시 인증 상태를 동기화할 수 있는 가장 우수한 선택이었습니다.

### 2.2. 마이페이지 성능 최적화: ORM Eager Loading vs 직접 집계 SQL
* **대안 A (SQLAlchemy `joinedload` / `subqueryload`)**: ORM의 관계 로딩 옵션을 활용.
  * *Trade-off*: 복잡한 다대다 관계와 집계 연산(예: 주의 성분 개수 카운트)을 ORM으로 처리하려니 쿼리가 지나치게 복잡해지고, 여전히 파이썬 객체 인스턴스화 오헤드가 남음.
* **최종 선택 (대안 B - 네이티브 SQL 직접 집계 및 `LEFT JOIN`, `STRING_AGG`)**:
  화면에 필요한 데이터(`caution_count`, `total_ingredients`, 상위 대표 성분 이름 등)를 데이터베이스 레벨에서 `COUNT`와 `STRING_AGG`로 한 번에 집계하도록 직접 쿼리를 작성했습니다. 
  * *Trade-off*: ORM의 추상화 이점을 일부 포기해야 하지만, 데이터베이스가 가장 잘하는 연산(Aggregation)을 활용함으로써 네트워크 I/O와 메모리 사용량을 극적으로 줄일 수 있었습니다.

## 3. 최종 해결 및 아키텍처 설계 (Solution)

### 3.1. 게스트 데이터 승격(Migration) 및 수명주기 파이프라인
게스트 상태에서 쌓인 데이터가 로그인 시 유실되지 않도록 파이프라인을 정립했습니다.
* **동기화 트리거**: `guest_saved_products`, `guest_scan_history` 등 게스트 관련 로컬 데이터가 단 하나라도 존재할 경우, 로그인 직후 즉시 임시 식별자를 생성하여 서버의 `/auth/guest-convert` API를 100% 호출하도록 강제했습니다.
* **데이터 수명주기(Life-Cycle) 원칙 수립**:
  * **로그인 시**: 로컬 게스트 데이터를 회원 DB로 이전(Migration) 후 로컬스토리지 클린업.
  * **로그아웃 시**: 공용 기기에서의 민감 정보 유출 방지를 위해 해당 기기의 로컬 저장소를 완전히 백지 상태로 만드는 **Clean Slate 원칙** 적용.
  * **회원 탈퇴 시**: GDPR 및 PIPA '잊힐 권리' 준수를 위해 관련 DB 레코드를 **Hard Delete** 처리.

### 3.2. 마이페이지 쿼리 최적화 결과
`mypage.py`의 데이터 조회 로직을 직접 집계 SQL로 전면 개편하고, 프론트엔드에서 `Promise.all`을 이용한 병렬 로딩을 적용한 결과는 다음과 같습니다.

* **저장 상품 조회 (`get_saved_products`)**: 400ms ➔ **79ms** (약 5배 단축)
* **스캔 이력 조회 (`get_my_scan_history`)**: 240ms ➔ **73ms** (약 3.5배 단축)
* **마이페이지 전체 체감 렌더링 속도**: 최대 10초 ➔ **0.1~0.2초 (초고속 반응 달성)**

## 4. 엔지니어링 교훈 (Takeaway)

1. **보안과 프론트엔드 DX의 조화**: `HttpOnly` 쿠키와 같은 강력한 보안 정책을 도입할 때는, 프론트엔드가 상태를 인지하는 방식(SSR을 통한 전역 컨텍스트 주입 등)을 함께 설계해야 디버깅하기 어려운 사이드 에러를 예방할 수 있습니다.
2. **N+1 문제의 근본적인 해결은 DB 집계에서**: 객체 매핑에만 의존하기보다, 화면 표시에 필요한 최소한의 데이터 형태를 정의하고 데이터베이스의 집계 함수를 활용하는 것이 대규모 데이터 조회 성능 개선에 훨씬 효과적입니다.
3. **사용자 데이터의 수명주기(Life-Cycle) 관리**: 단순히 데이터를 잘 저장하는 것뿐만 아니라, 로그인, 로그아웃, 탈퇴 등 상태 변화에 따른 데이터의 흐름(Migration & Cleanup)을 명확히 정의하는 것이 서비스 신뢰도를 높이는 핵심입니다.
