웹 서비스가 성장함에 따라 보안을 강화하기 위해 인증 토큰을 `HttpOnly` 쿠키로 전환하는 것은 필수적인 단계입니다. 하지만 이 과정에서 프론트엔드와 백엔드 간의 인증 상태 인지 괴리, 게스트 데이터 유실, 그리고 ORM의 고질적인 N+1 문제라는 복합적인 병목 현상과 마주했습니다.

이번 포스팅에서는 **PickSafe** 서비스에서 마주한 **[보안 쿠키 도입에 따른 로그인 오인식 버그]**, **[게스트-회원 간 데이터 승격 파이프라인 정립]**, 그리고 **[직접 집계 SQL을 통한 마이페이지 5배 가속화]** 과정을 공유합니다.

---

## 1. Problem: 무엇이 문제였는가?

게스트 전환 유도 정책(한도 제한 및 Nudge)을 도입한 직후, 사용자 경험을 심각하게 해치는 몇 가지 치명적인 문제가 보고되었습니다.

1. **HttpOnly 쿠키와 프론트엔드의 인증 괴리 (`document.cookie` 한계)**
   - 보안 강화를 위해 `access_token`을 `HttpOnly=True` 쿠키로 발급하자, 프론트엔드 자바스크립트(`document.cookie`)에서 토큰을 읽을 수 없게 되었습니다.
   - 이로 인해 **로그인한 유저임에도 프론트엔드는 "게스트"로 판별**하여, 회원 서버가 아닌 로컬스토리지에 데이터를 오인 적재하는 버그가 발생했습니다.
2. **게스트 데이터 승격(Migration) 누락**
   - 온보딩을 거치지 않은 게스트가 로그인했을 때 동기화 API가 조기 반환(`Early Return`)되어, 이전에 스캔한 기록이나 찜 목록이 계정으로 이전되지 않고 유실되는 문제가 발생했습니다.
3. **마이페이지 로딩 지연 (최대 10초)**
   - 마이페이지 진입 시, 수백 개의 상품 및 스캔 이력과 연관된 성분 ORM 객체들을 루프 안에서 개별 조회(N+1 문제)하느라 응답 시간이 최대 10초까지 치솟았습니다.

## 2. Trade-off & Architecture: 기술적 고민과 해결 방안

### ① 인증 판별 표준화: `HttpOnly` 환경에서의 전역 주입 패턴
* **고민**: 자바스크립트에서 직접 쿠키를 읽을 수 없는 상황에서, 프론트엔드가 로그인 상태를 안전하고 정확하게 인지하는 방법은 무엇일까?
* **대안 비교**:
  * *대안 A*: 클라이언트가 별도의 `/auth/me` API를 매번 호출하여 상태 확인 (네트워크 요청 낭비 및 초기 렌더링 지연 발생)
  * *대안 B*: SSR(Server-Side Rendering) 시점에 서버 세션 기반의 전역 변수 주입 (**선택**)
* **결정**: `base.html` 렌더링 시 서버 단에서 `window.IS_LOGGED_IN = true/false;` 및 `window.isGuestUser()` 헬퍼 함수를 전역으로 주입했습니다. 프론트엔드 전반의 쿠키 파싱 로직을 제거하고 이를 일원화하여, 보안성과 개발 생산성을 모두 잡았습니다.

### ② 데이터 수명주기(Life-Cycle) 및 승격 파이프라인 정립
* **고민**: 게스트 상태에서 쌓인 데이터와 회원 계정의 데이터를 어떻게 무결하게 동기화할 것인가? 또한 보안 사고를 어떻게 예방할 것인가?
* **결정**:
  - **동기화 트리거 개선**: 로컬에 저장된 게스트 데이터(`guest_saved_products` 등)가 단 하나라도 존재하면, `guest_device_id` 유무와 관계없이 즉시 임시 식별자를 생성하여 변환 API(`/auth/guest-convert`)를 호출하도록 보장했습니다.
  - **Clean Slate 및 잊힐 권리 원칙 적용**: 
    - 로그인 시: 로컬 데이터를 회원 DB로 이전 후 로컬스토리지를 클린업합니다.
    - 로그아웃 시: 공용 기기에서의 민감 정보(알레르기, 스캔 이력 등) 유출을 막기 위해 기기를 백지 상태로 리셋합니다.
    - 회원 탈퇴 시: 개인정보 보호법 및 GDPR을 준수하여 DB의 관련 데이터를 영구 파기(`Hard Delete`)합니다.

### ③ ORM N+1 지옥 탈출: 직접 집계 SQL 도입
* **고민**: 복잡한 관계를 가진 데이터를 다룰 때 ORM의 편의성에만 의존하면 성능 대참사가 발생합니다. 마이페이지의 수백 개 객체 조회를 어떻게 최적화할 것인가?
* **대안 비교**:
  * *대안 A*: SQLAlchemy `joinedload` / `subqueryload` 활용 (여전히 방대한 객체 인스턴스화 오버헤드 존재)
  * *대안 B*: 화면 표시에 필요한 데이터만 연산하는 **단일 직접 집계 SQL(`COUNT`, `STRING_AGG`, `LEFT JOIN`) 작성** (**선택**)
* **결정**: 화면 표시에 불필요한 파이썬 객체 생성 과정을 과감히 들어내고, DB 레벨에서 필요한 지표(`caution_count`, `total_ingredients`, `top_names`)를 한 번에 계산해 가져오는 최적화 쿼리를 적용했습니다.

## 3. Takeaway: 무엇을 배웠는가?

1. **보안과 사용자 경험(UX)은 트레이드오프가 아니다**
   - `HttpOnly` 쿠키 도입으로 보안을 강화했음에도, 서버 사이드 전역 변수 주입이라는 영리한 패턴을 통해 프론트엔드의 상태 인지 오류를 깔끔하게 해결할 수 있었습니다.
2. **성능 병목의 주범은 언제나 N+1과 불필요한 객체화**
   - 마이페이지 조회 API에 직접 집계 SQL을 도입한 결과, 백엔드 응답 속도가 **400ms에서 79ms로 5배 이상 단축**되었으며, 체감 렌더링 속도 역시 10초에서 0.1초대로 혁신적으로 개선되었습니다.
3. **데이터 수명주기(Life-Cycle) 설계의 중요성**
   - 비즈니스 로직 구현뿐만 아니라, "로그아웃 시 기기 초기화", "탈퇴 시 하드 딜리트" 같은 데이터의 생명주기를 명확히 정의하는 것이 서비스의 신뢰성과 보안성을 결정짓는 핵심 요소임을 다시 한번 깨달았습니다.
