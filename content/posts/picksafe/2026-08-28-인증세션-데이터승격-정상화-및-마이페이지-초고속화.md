안녕하세요, PickSafe 개발팀입니다. 

서비스가 성장하고 사용자 유입이 늘어나면서 개발팀은 "게스트 사용자들을 어떻게 자연스럽게 회원으로 전환(Convert)시킬 것인가?"라는 비즈니스 요구사항을 마주하게 되었습니다. 이 과정에서 게스트의 스캔 기록과 찜 목록을 로그인 시 계정으로 안전하게 이전하는 **'데이터 승격(Migration) 파이프라인'**을 구축해야 했죠.

그러나 이 아름다운 기획 뒤에는 보안 쿠키 환경에서의 상태 동기화 결함, 분산 데이터 유실, 그리고 **마이페이지 진입 시 최대 10초가 소요되는 치명적인 성능 병목**이 숨어 있었습니다.

오늘은 PickSafe 개발팀이 이 복합적인 문제를 어떻게 정의하고, 어떤 아키텍처적 트레이드오프를 거쳐 해결했는지, 그리고 이 과정에서 얻은 엔지니어링 교훈을 공유하고자 합니다.

---

## 1. 문제 정의: 무엇이 사용자 경험을 가로막았는가?

우리가 해결해야 할 문제는 크게 세 가지 레이어(보안, 데이터 정합성, 성능)에 걸쳐 있었습니다.

### ① 보안 쿠키(HttpOnly) 도입으로 인한 프론트엔드의 로그인 상태 오인식
보안을 강화하기 위해 인증 토큰(`access_token`)을 `HttpOnly=True` 쿠키로 발급하도록 변경했습니다. XSS 공격으로부터 토큰을 보호하기 위한 올바른 선택이었지만, 사이드 이펙트가 발생했습니다. 클라이언트 사이드 JavaScript(`document.cookie`)에서 토큰의 존재 여부를 확인할 수 없게 되자, 프론트엔드가 로그인한 사용자를 "게스트"로 오인하여 유저의 저장 데이터를 로컬 스토리지에 잘못 적재하는 버그가 발생했습니다.

### ② 불안정한 게스트 데이터 승격 및 무결성 깨짐
온보딩 과정을 건너뛰고 바로 서비스를 이용하던 게스트(`guest_device_id` 미발급 사용자)가 로그인을 수행할 때, 동기화 트리거가 누락되는 현상이 발견되었습니다. 게다가 백엔드 승격 API 가동 시, 복합 유니크 제약 조건 위반으로 인해 DB 에러(500 Internal Server Error)가 발생하며 데이터가 공중 분해되는 정합성 이슈가 있었습니다.

### ③ 마이페이지 렌더링 지연 (최대 10초)
가장 심각한 병목은 마이페이지였습니다. 사용자가 마이페이지에 진입하면 저장된 상품 정보와 최근 스캔 이력을 렌더링해야 합니다. 
이때 ORM 객체 관계 매핑의 한계로 인해 **수백 번의 N+1 쿼리가 발생**하고 있었고, 파이썬 런타임에서 수많은 객체를 인스턴스화하는 오버헤드까지 더해져 화면이 표시되기까지 최대 10초 동안 빈 화면이 유지되는 최악의 경험을 제공하고 있었습니다.

## 2. 기술적 고민과 대안 비교 (Trade-off)

우리는 각 문제를 임시방편이 아닌 구조적으로 해결하기 위해 다음과 같은 아키텍처 대안들을 비교했습니다.

### 고민 1. 보안 쿠키 환경에서 어떻게 프론트엔드에 로그인 상태를 알릴 것인가?
* **대안 A: API 추가 호출 (`/auth/status`)**
  * *장점:* 명확하고 표준적인 방법.
  * *단점:* 페이지 로드 시마다 추가적인 왕복 지연 시간(RTT)이 발생하여 초기 렌더링이 느려짐.
* **대안 B: SSR을 통한 상태 전역 주입 (선택)**
  * *장점:* 서버 사이드 렌더링(SSR) 템플릿 엔진 단계에서 세션 상태를 판단하여 `window.IS_LOGGED_IN = true/false;` 형태의 전역 변수와 헬퍼 함수를 주입. RTT가 0이며, 보안 쿠키의 이점을 그대로 유지.

### 고민 2. ORM N+1 쿼리와 렌더링 지연을 어떻게 해결할 것인가?
* **대안 A: SQL Alchemy의 이지 로딩(Eager Loading) 설정 (`joinedload`, `selectinload`)**
  * *장점:* 코드 레벨에서 간단히 적용 가능.
  * *단점:* 복잡한 다대다 관계와 메타 데이터 구조상 여전히 수많은 파이썬 객체가 생성되어 메모리 적재 오버헤드가 컸음. 백엔드 처리 시간을 수백 밀리초 이하로 낮추기 어려움.
* **대안 B: Redis 캐시 도입**
  * *장점:* 두 번째 조회부터 초고속 응답 가능.
  * *단점:* 실시간 데이터 정합성(스캔 즉시 반영 등)을 맞추기 위한 캐시 무효화(Cache Invalidation) 로직의 복잡성 증가.
* **대안 C: 직접 집계 SQL (Direct Aggregation SQL) 도입 (선택)**
  * *장점:* 화면 렌더링에 필요한 핵심 정보(주의 성분 개수, 총 성분 수, 상위 대표 성분 등)를 **단일 DB 집계 쿼리(`COUNT`, `STRING_AGG`, `LEFT JOIN`)**로 직접 산출하여 반환. 파이썬 객체 생성 오버헤드를 극적으로 줄임.

## 3. 최종 해결 방식 및 구현 디테일

### ① 프론트엔드 로그인 상태 판별 표준화
서버 사이드 템플릿 렌더링 시점에 세션 기반의 전역 헬퍼를 주입하여, 프론트엔드 전반의 상태 판별 기준을 통일했습니다.

```javascript
// base.html (SSR 시점에 서버에서 주입)
window.IS_LOGGED_IN = {{ 'true' if user.is_authenticated else 'false' }};
window.isGuestUser = function() {
    return !window.IS_LOGGED_IN;
};
```
이후 `result.js`, `scan.js` 등에서는 쿠키 직접 접근 대신 `window.isGuestUser()`를 바라보도록 일원화하여 보안과 성능을 모두 잡았습니다.

### ② 데이터 수명주기(Life-Cycle) 및 무결성이 보장된 승격 파이프라인
임시 디바이스 식별자 유무와 관계없이, 로컬 스토리지에 게스트 데이터가 하나라도 감지되면 즉시 이관 API(`/auth/guest-convert`)를 호출하도록 트리거를 개편했습니다.

또한, 백엔드 이관 로직에서 발생하던 중복 제약 조건 위반을 방지하기 위해 중복 성분을 메모리 상에서 1차 필터링(`seen_ingredients` 셋 활용) 후 벌크 인서트를 수행하도록 보완했습니다.

나아가 개인정보 보호와 보안을 위해 데이터 수명 주기를 다음과 같이 명확히 정의했습니다:
* **로그인 시**: 로컬 게스트 데이터 ➔ 회원 DB로 이전 후 로컬 스토리지 정리(`removeItem`).
* **로그아웃 시**: 공용 기기에서의 건강 정보 유출을 막기 위해 **로컬 상태를 완전히 리셋 (Clean Slate 원칙)**.
* **회원 탈퇴 시**: 관련 규정(GDPR/PIPA) 준수를 위해 **DB 내 모든 개인 데이터 영구 파기(Hard Delete)**.

### ③ 직접 집계 SQL을 통한 마이페이지 초고속화
ORM의 마법 뒤에 숨겨진 비효율을 걷어내기 위해 직접 짠 고성능 Raw Query 구조를 도입했습니다. 

```sql
-- 마이페이지 조회를 위한 직접 집계 쿼리 예시
SELECT 
    sp.id,
    sp.product_name,
    COUNT(pi.id) AS total_ingredients,
    COUNT(CASE WHEN pi.is_caution = TRUE THEN 1 END) AS caution_count,
    STRING_AGG(pi.name, ', ' ORDER BY pi.severity DESC) AS top_names
FROM saved_products sp
LEFT JOIN product_ingredients pi ON sp.product_id = pi.product_id
WHERE sp.user_id = :user_id
GROUP BY sp.id
ORDER BY sp.created_at DESC;
```

기존에는 상품 리스트를 가져온 후, 각 상품마다 성분 테이블을 루프 돌며 쿼리하던 N+1 구조였습니다. 이를 단 한 번의 조인과 집계(`COUNT`, `STRING_AGG`)로 데이터베이스 엔진 내부에서 처리하도록 변경하여 네트워크 왕복과 파이썬 객체 매핑 시간을 소멸시켰습니다.

여기에 더해 프론트엔드에서는 `Promise.all`을 이용해 저장 상품 목록, 최근 스캔 기록, 문의 내역을 병렬로 요청하여 블로킹 없는 화면 진입을 구현했습니다.

## 4. 도입 결과 및 정량적 성과

구조 개선 후 성능 측정을 진행한 결과, 눈부신 개선 지표를 얻을 수 있었습니다.

* **`get_saved_products` API 속도**: `400ms` ➔ **`79ms` (약 5배 개선)**
* **`get_my_scan_history` API 속도**: `240ms` ➔ **`73ms` (약 3.3배 개선)**
* **마이페이지 전체 렌더링 체감 속도**: 기존 최대 `10초` ➔ 개선 후 **`0.1 ~ 0.2초` 내 완료 (최대 50배 이상 단축)**

또한, 방금 승격되거나 추가된 상품이 최신순(`DESC`) 정렬 누락으로 인해 2페이지로 밀려 "데이터가 사라졌다"고 오해하던 CS 인입 건수가 **0건**으로 감소했습니다.

| 성능 지표 비교 | 개선 전 | 개선 후 | 개선율 |
| :--- | :--- | :--- | :--- |
| **저장 상품 조회** | 400ms | **79ms** | **80.2% 감소** |
| **스캔 기록 조회** | 240ms | **73ms** | **69.5% 감소** |
| **화면 초기 진입 시간** | 3.0 ~ 10.0s | **0.1 ~ 0.2s** | **98% 이상 단축** |

## 5. 엔지니어링 교훈 (Takeaway)

이번 개선 작업을 진행하며 우리 팀은 세 가지 소중한 교훈을 얻었습니다.

1. **보안과 기능은 Trade-off가 아니다**: `HttpOnly` 쿠키와 같은 보안 정책이 프론트엔드 상태 관리를 방해할 때, 보안 수준을 낮추는 타협 대신 **아키텍처(SSR 전역 상태 주입 등)를 우회 설계**하여 둘 다 충족할 수 있음을 배웠습니다.
2. **ORM은 만능 도구가 아니다**: 생산성을 높여주는 ORM이지만, 복잡한 통계 및 집계 화면에서는 **직접 작성한 집계 쿼리가 수십 배의 성능 향상과 메모리 절약**을 가져다줍니다. 병목 구간에서는 주저 없이 Low-level SQL을 고려해야 합니다.
3. **데이터 수명 주기는 기획 초기부터 설계되어야 한다**: 로그인/로그아웃/회원 탈퇴 시의 로컬 스토리지 및 DB 데이터 삭제 정책은 단순한 기능 구현을 넘어, 사용자 프라이버시 보호와 컴플라이언스 준수의 핵심 요소입니다.

앞으로도 PickSafe는 성능과 보안, 정합성 세 마리 토끼를 모두 잡는 단단한 서비스를 만들어 가겠습니다. 긴 글 읽어주셔서 감사합니다!
