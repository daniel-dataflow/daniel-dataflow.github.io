웹 서비스 규모가 커지고 게스트 전환 유도 정책(Nudge)을 도입하는 과정에서, 우리는 **보안 강화와 사용자 경험(UX) 사이의 미묘한 마찰**을 마주했습니다. 보안을 위해 도입한 `HttpOnly` 쿠키가 프론트엔드의 상태 판별을 교란했고, 이는 데이터 유실 오인과 심각한 성능 병목(N+1 쿼리)으로 이어졌습니다.

본 포스팅에서는 PickSafe 서비스에서 마주한 **인증 세션 정규화, 게스트 데이터 승격(Migration) 파이프라인 구축, 그리고 마이페이지 쿼리 최적화 과정(5배 속도 개선)**에서의 기술적 고민과 해결 과정을 공유합니다.

---

## 1. Problem: 마주한 기술적 난제들

### ① `HttpOnly` 쿠키와 프론트엔드 상태 오인식
보안을 강화하기 위해 인증 토큰(`access_token`)을 `HttpOnly=True` 쿠키로 전환했습니다. 문제는 프론트엔드 자바스크립트가 `document.cookie`를 통해 로그인 여부를 직접 확인하고 있었다는 점입니다. 
결과적으로, **서버 측에서는 유저가 로그인 상태임에도 프론트엔드는 "게스트"로 판별**하여, 사용자가 생성한 스캔 기록과 찜 목록을 서버가 아닌 로컬스토리지에 게스트 데이터로 오인 적재하는 버그가 발생했습니다.

### ② 마이페이지 렌더링 지연 (최대 10초)
마이페이지 진입 시, 저장된 상품 및 스캔 이력과 연관된 수십 개의 성분 정보(Ingredient)를 ORM 관계를 통해 개별 조회하고 파이썬 객체로 변환(Instantiation)하는 과정에서 **전형적인 N+1 쿼리 병목**이 발생했습니다. 이로 인해 화면 렌더링에 최대 10초가 소요되는 치명적인 UX 저하가 발생했습니다.

### ③ 게스트 데이터 승격(Migration) 누락 및 수명주기(Life-Cycle) 부재
온보딩을 거치지 않은 게스트가 로그인했을 때 동기화 API가 조기 반환(`Early Return`)되어 기존 데이터가 계정으로 이전되지 않았습니다. 또한 로그아웃 시 공용 기기에 민감한 건강/알레르기 정보가 남는 보안 결함도 존재했습니다.

## 2. Trade-off & Architecture: 기술적 고민과 대안 선택

### 2.1. 인증 판별 표준화: 프론트엔드 vs 백엔드 소스 오브 트루스(Source of Truth)
* **대안 A (토큰 노출)**: 쿠키의 `HttpOnly`를 해제하여 JS에서 토큰을 읽을 수 있게 함. 
  * *Trade-off*: XSS(Cross-Site Scripting) 공격에 취약해지므로 보안 요구사항에 위배되어 기각.
* **대안 B (서버 렌더링 시점 전역 주입)**: `base.html` 렌더링 시 서버 세션 기반의 `window.IS_LOGGED_IN = true/false;` 플래그를 전역 주입하고, 헬퍼 함수(`window.isGuestUser()`)로 프론트엔드 판별 로직을 일원화.
  * *Trade-off*: 서버 템플릿 의존성이 약간 높아지나, 보안(`HttpOnly`)을 완벽히 유지하면서 프론트엔드 상태 불일치를 원천 차단할 수 있어 채택.

### 2.2. 마이페이지 성능 개선: ORM 최적화 vs 직접 집계 SQL (Raw/Builder Query)
* **대안 A (ORM Eager Loading `joinedload` / `selectinload`)**: SQLAlchemy의 로딩 옵션 조정.
  * *Trade-off*: 복잡한 1:N:M 관계와 집계(Count, String Aggregation) 연산에는 여전히 객체 변환 오버헤드가 남고 쿼리가 비대해짐.
* **대안 B (직접 집계 SQL 도입)**: 화면 표시에 필요한 데이터(`caution_count`, `total_ingredients`, 대표 성분 이름 등)를 단일 DB 집계 쿼리(`COUNT`, `STRING_AGG`, `LEFT JOIN`)로 직접 산출.
  * *Trade-off*: ORM 객체 모델링의 이점을 일부 포기해야 하지만, 데이터베이스의 연산 능력을 최대한 활용하여 네트워크 라운드트립과 메모리 객체 생성 비용을 극적으로 줄일 수 있어 채택.

## 3. Solution: 핵심 해결 및 구현

### ① 게스트 데이터 승격 및 Clean Slate 원칙
* **데이터 승격 파이프라인 개편**: 게스트 식별자 유무와 무관하게, 로컬에 저장된 데이터(`guest_saved_products`, `guest_scan_history` 등)가 하나라도 감지되면 즉시 임시 식별자를 생성하여 동기화 엔드포인트(`*auth/guest-convert`)를 호출하도록 보장했습니다.
* **수명주기 정의**:
  * **로그인 시**: 로컬 데이터 회원 DB로 마이그레이션 후 로컬스토리지 정리(`removeItem`).
  * **로그아웃 시**: 공용 기기 보안을 위해 기기를 백지 게스트 상태로 리셋하는 **Clean Slate 원칙** 적용.
  * **회원 탈퇴 시**: PIPA 및 GDPR 준수를 위해 관련 데이터를 영구 파기(`Hard Delete`).

### ② 초고속 집계 SQL을 통한 마이페이지 가속화
`mypage.py` 라우터에 집계 쿼리를 도입하여, 루프를 돌며 개별 조회하던 구조를 단일 쿼리로 재작성했습니다.

```python
# 예시: 단일 집계 쿼리를 통한 N+1 제거 (개념적 구조)
# 수백 번 발생하던 ORM 개별 조회를 단 1회의 JOIN 및 집계 쿼리로 통합
stmt = (
    select(
        SavedProduct,
        func.count(ProductIngredient.id).label("total_ingredients"),
        func.string_agg(ProductIngredient.name, ", ").label("top_names"),
    )
    .join(ProductIngredient, ...)
    .group_by(SavedProduct.id)
    .order_by(SavedProduct.created_at.desc())
)
```
추가로 프론트엔드에서는 `Promise.all`을 이용해 저장 상품, 스캔 기록, 문의 내역을 **병렬 로드**하고, 무거운 데이터 동기화 작업은 백그라운드 비동기로 격리하여 화면 첫 진입 딜레이를 제거했습니다.

## 4. Takeaway: 엔지니어링 교훈

1. **보안과 UX는 트레이드오프가 아닐 수 있다**: `HttpOnly` 쿠키 도입으로 발생한 프론트엔드 상태 오인식 문제를 서버 사이드 전역 변수 주입(`window.IS_LOGGED_IN`)이라는 우아한 방식으로 해결하며, 보안성과 매끄러운 UX를 동시에 챙길 수 있었습니다.
2. **ORM에만 의존하지 않는 용기**: 객체 지향적인 설계는 유지보수에 좋지만, 대시보드나 마이페이지와 같은 집계 중심의 화면에서는 **적절한 Raw SQL 및 집계 함수 활용**이 시스템 성능을 수 배 이상 끌어올리는 치트키가 됩니다.
3. **사용자의 데이터는 신성하다**: 게스트 상태에서 쌓은 데이터가 로그인 전환 과정이나 로그아웃 시 유실되거나 섞이지 않도록 **데이터 수명주기(Life-Cycle) 정책**을 명확히 정의하는 것이 서비스 신뢰도의 핵심임을 다시 한번 깨달았습니다.

### 📊 최종 성과
* **`get_saved_products` 조회 속도**: 400ms ➔ **79ms** (약 5배 개선)
* **`get_my_scan_history` 조회 속도**: 240ms ➔ **73ms** (약 3.5배 개선)
* **마이페이지 체감 렌더링 속도**: 최대 10초 ➔ **0.1~0.2초 (초고속 반응)**
