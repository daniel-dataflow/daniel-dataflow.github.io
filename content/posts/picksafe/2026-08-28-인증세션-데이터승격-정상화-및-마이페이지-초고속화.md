안녕하세요. PickSafe 개발팀입니다. 

서비스의 규모가 커지고 게스트 전환 유도 정책(Nudge)을 고도화하는 과정에서, 우리는 **"사용자가 로그인 상태인데 왜 게스트로 인식되지?", "마이페이지를 열었는데 왜 10초나 걸리지?"**라는 치명적인 유저 Experience(UX) 병목과 마주했습니다.

이번 포스팅에서는 보안을 강화하는 과정에서 발생한 프론트엔드-백엔드 간 인증 상태 괴리 문제를 해결하고, ORM의 N+1 지옥에서 벗어나 마이페이지 렌더링 속도를 **최대 5배 이상 단축**시킨 아키텍처 의사결정 과정을 공유합니다.

---

## 1. Problem: 마주한 기술적 난제들

서비스를 운영하며 사용자 피드백과 모니터링을 통해 다음과 같은 3가지 핵심 문제를 발견했습니다.

### ① `HttpOnly` 보안 쿠키와 프론트엔드 로그인 오인식
보안성 강화를 위해 `access_token`을 `HttpOnly=True` 쿠키로 발행하기 시작했습니다. XSS 공격으로부터 토큰을 보호하는 데는 성공했지만, 클라이언트 JavaScript(`document.cookie`)에서 토큰을 직접 읽을 수 없게 되었습니다.
이로 인해 프론트엔드는 **로그인 상태의 유저를 무조건 "게스트"로 판별**하였고, 사용자가 로그인을 했음에도 스캔 결과가 브라우저 로컬 스토리지에만 갇히는 데이터 정합성 결함이 발생했습니다.

### ② 게스트 데이터 승격(Migration) 누락 및 데이터 유실 오인
온보딩을 거치지 않은 순수 익명 게스트가 로그인했을 때, 기존 데이터 동기화 API가 조기 반환(`early return`)되어 사용자가 열심히 모아둔 스캔 기록과 찜 목록이 계정으로 이전되지 않았습니다. 설상가상으로 최신순 정렬 로직이 누락되어, 겨우 이관된 데이터가 페이지 하단으로 밀려 사용자들은 "데이터가 다 날아갔다"고 오인하게 되었습니다.

### ③ 마이페이지 로딩 지연 (최대 10초)
마이페이지 진입 시, 백엔드는 수십 개의 상품 및 스캔 이력과 연관된 성분 데이터들을 ORM을 통해 개별적으로 탐색(Lazy Loading)하고 있었습니다. 이로 인해 **수백 번의 N+1 쿼리와 파이썬 객체 생성 오버헤드**가 발생하여 API 응답 속도가 400ms에서 최대 10초까지 치솟는 심각한 성능 병목을 겪었습니다.

## 2. Trade-off & Solution: 아키텍처 개선 및 대안 비교

각 문제를 해결하기 위해 우리가 선택한 기술적 접근 방식과 트레이드오프는 다음과 같습니다.

### [인증] 클라이언트 쿠키 파싱 포기 및 서버 주입형 전역 헬퍼 도입
* **고민**: 자바스크립트에서 `HttpOnly` 쿠키를 읽을 방법은 존재하지 않습니다. (보안 설계상 당연한 제약입니다.)
* **대안 비교**: 
  1. *토큰을 일반 쿠키로 전환*: XSS 취약점에 다시 노출되므로 기각.
  2. *서버 렌더링 시점에 상태 주입*: HTML 렌더링 단계에서 서버 세션을 확인해 전역 변수로 주입.
* **최종 선택**: 
  `base.html` 렌더링 시 서버 세션 기반의 `window.IS_LOGGED_IN = true/false;` 및 `window.isGuestUser()` 헬퍼 함수를 전역에 주입하기로 했습니다. 프론트엔드 전반의 쿠키 파싱 로직을 제거하고 이 헬퍼를 바라보도록 통일하여, 보안을 유지하면서도 정확한 로그인 상태 감지를 달성했습니다.

### [데이터 수명주기] Clean Slate 원칙과 무조건적 승격 파이프라인
* **데이터 승격**: `guest_device_id`의 유무와 관계없이, 로컬 스토리지에 `guest_saved_products` 등 **단 하나의 게스트 데이터라도 존재한다면 즉시 임시 식별자를 생성해 서버의 변환 엔드포인트로 전송**하도록 트리거를 강화했습니다.
* **수명주기(Life-Cycle) 정책 확립**:
  * **로그인 시**: 로컬 게스트 데이터를 회원 DB로 안전하게 이전(`Migration`) 후 로컬 스토리지 클리어.
  * **로그아웃 시**: 공용 기기에서의 민감한 건강/알레르기 정보 유출을 원천 차단하기 위해 **해당 기기를 완전한 백지 상태(0개)로 리셋하는 'Clean Slate' 원칙** 적용.
  * **회원 탈퇴 시**: PIPA 및 GDPR의 '잊힐 권리'를 준수하기 위해 관련 데이터 **Hard Delete(영구 파기)** 처리.

### [성능] ORM N+1 지옥 탈출과 직접 집계 SQL (Direct Aggregation SQL)
* **고민**: Django/SQLAlchemy 등의 ORM을 통한 편리한 객체 조작은 개발 생산성을 높여주지만, 연관관계가 복잡한 대시보드 화면에서는 치명적인 성능 저하를 유발합니다.
* **대안 비교**:
  1. *Eager Loading (`joinedload`, `subqueryload`)*: 쿼리 수는 줄어들지만, 거대한 JOIN으로 인해 데이터 중복 전송 및 메모리 사용량이 급증.
  2. *직접 집계 SQL (`COUNT`, `STRING_AGG`, `LEFT JOIN`)*: 화면에 필요한 데이터만 DB 레벨에서 미리 계산하여 가벼운 DTO 형태로 반환.
* **최종 선택**: 
  마이페이지의 특성상 복잡한 도메인 로직 수정보다는 **단일 DB 집계 쿼리를 통한 직접 조회**가 압도적으로 유리하다고 판단했습니다. 화면 표시에 필요한 '주의 성분 개수', '총 성분 수', '대표 성분명'을 SQL 레벨에서 한 번에 연산하도록 리팩토링했습니다.
  또한, 프론트엔드에서는 `Promise.all`을 이용해 저장 상품, 스캔 기록, 문의 내역을 **병렬 비동기 로드**하고, 데이터 동기화 작업은 백그라운드로 격리하여 초기 렌더링 블로킹을 없애버렸습니다.

## 3. Takeaway: 엔지니어링 교훈

이번 개선 작업을 통해 얻은 핵심 교훈은 다음과 같습니다.

1. **보안과 UX는 트레이드오프가 아니다**: `HttpOnly` 쿠키라는 보안 제약으로 인해 발생한 UX 결함을 서버 사이드 렌더링을 활용한 전역 상태 주입 패턴으로 우아하게 해결했습니다. 보안을 타협하지 않으면서도 정확한 사용자 상태를 추적할 수 있음을 증명했습니다.
2. **ORM은 은총알이 아니다**: 편리함 뒤에 숨겨진 N+1 문제를 방치하면 대규모 트래픽에서 서비스 마비로 이어질 수 있습니다. 대시보드나 마이페이지와 같이 집계 성격이 강한 조회 로직은 **DB의 연산 능력을 적극 활용하는 직접 집계 쿼리**가 정답일 수 있음을 체감했습니다.
3. **데이터 수명주기(Lifecycle)의 명확한 정의**: 게스트에서 회원으로 넘어가는 파이프라인, 로그아웃 시의 데이터 클렌징 등 데이터의 탄생부터 소멸까지의 흐름을 정의하는 것이 서비스 신뢰도(정합성)의 핵심입니다.

## 4. 검증 결과 (Performance Metrics)

성능 개선 작업 전후의 지표는 명확한 성과를 보여주었습니다.

* **`get_saved_products` (저장 상품 조회)**: 400ms ➔ **79ms** (**약 5배 개선**)
* **`get_my_scan_history` (스캔 이력 조회)**: 240ms ➔ **73ms** (**약 3.5배 개선**)
* **마이페이지 전체 렌더링 체감 속도**: 3초 ~ 10초 ➔ **0.1초 ~ 0.2초 (초고속 반응)**

앞으로도 PickSafe는 보안, 성능, 그리고 사용자 경험(UX) 어느 하나도 놓치지 않는 견고한 아키텍처를 만들어 나갈 것입니다. 

감사합니다.
