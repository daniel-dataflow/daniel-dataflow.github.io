안녕하세요, PickSafe 개발팀입니다. 
최근 우리는 사용자 경험(UX)을 크게 저해하던 몇 가지 치명적인 정합성 결함과 성능 병목을 마주했습니다. 보안을 강화하기 위해 도입했던 `HttpOnly` 쿠키가 프론트엔드의 로그인 상태 오인식을 유발했고, 백엔드에서는 ORM의 N+1 문제로 마이페이지 로딩이 최대 10초까지 지연되는 상황이었습니다.

이번 글에서는 이 문제를 어떻게 정의하고, 어떤 아키텍처적 트레이드오프를 거쳐 해결했는지, 그리고 무엇을 배웠는지 공유하고자 합니다.

---

## 1. Problem: 무엇이 문제였는가?

서비스 고도화 과정(게스트 한도 제한 및 Nudge 도입)에서 유저들은 다음과 같은 답답한 상황을 겪고 있었습니다.

1. **"로그인했는데 왜 게스트로 처리되죠?" (`HttpOnly` 쿠키 파싱의 한계)**
   보안 강화를 위해 `access_token`을 `HttpOnly=True` 쿠키로 발행하기 시작했습니다. 문제는 클라이언트 JavaScript(`document.cookie`)에서 이 토큰을 읽을 수 없다는 점이었습니다. 프론트엔드 코드는 토큰이 없다는 이유로 로그인된 유저를 무조건 "게스트"로 판별했고, 소중한 스캔/저장 데이터를 로컬 스토리지에 오인 적재하고 있었습니다.
2. **게스트 데이터 승격(Migration) 누락**
   온보딩을 거치지 않은 게스트가 로그인했을 때 동기화 API가 조기 반환(`Early Return`)되어, 기존에 스캔하고 찜해둔 기록들이 계정으로 이전되지 않는 데이터 유실 정합성 결함이 발생했습니다.
3. **마이페이지 로딩 지연 (최대 10초의 병목)**
   마이페이지 진입 시, 수십 개의 상품과 수백 개의 스캔 이력에 엮인 성분(Ingredient)들을 ORM 루프 안에서 개별 쿼리로 조회하고 파이썬 객체로 인스턴스화하느라 400ms에서 최대 10초까지 렌더링이 지연되었습니다.

---

## 2. Trade-off & Solution: 어떻게 해결할 것인가?

### ① 프론트엔드 로그인 감지 표준화: 보안과 개발 편의성의 타협
* **고민**: `HttpOnly` 쿠키의 보안 이점(XSS 방어)을 포기하고 다시 클라이언트가 접근 가능한 쿠키로 돌아갈 것인가? 아니면 서버 측 렌더링(SSR) 이점을 활용할 것인가?
* **해결**: 보안은 포기할 수 없으므로, **서버 세션 기반의 전역 플래그 주입 방식**을 선택했습니다.
  - `base.html` 렌더링 시 서버가 인증 상태를 평가하여 `window.IS_LOGGED_IN = true/false;` 및 `window.isGuestUser()` 헬퍼 함수를 전역에 주입했습니다.
  - 프론트엔드 전반의 쿠키 파싱 로직을 제거하고, 단일 진실 공급원(Single Source of Truth)인 `window.isGuestUser()`를 바라보도록 통일하여 인증 판별의 신뢰성을 높였습니다.

### ② 데이터 수명주기(Life-Cycle) 및 무결성 보장 파이프라인 구축
* **게스트 데이터 승격**: `guest_device_id`의 유무와 관계없이, 로컬에 `guest_saved_products` 등 **단 하나의 데이터라도 존재한다면 즉시 임시 식별자를 생성하여 승격 API를 강제 호출**하도록 트리거를 개편했습니다.
* **Clean Slate & Hard Delete 원칙 수립**:
  - **로그인 시**: 로컬 게스트 데이터를 회원 DB로 이전 후 로컬 스토리지를 깔끔하게 비웁니다(`removeItem`).
  - **로그아웃 시**: 공용 기기에서의 민감한 건강/알레르기 정보 유출을 막기 위해 해당 기기의 상태를 완벽한 백지 상태(0개)로 리셋하는 **Clean Slate 원칙**을 적용했습니다.
  - **회원 탈퇴 시**: PIPA 및 GDPR의 '잊힐 권리' 준수를 위해 DB 내 계정 데이터를 영구 파기(`Hard Delete`)하도록 설계했습니다.

### ③ ORM N+1 지옥탈출: 직접 집계 SQL(Direct Aggregation SQL) 도입
* **고민**: 복잡한 관계형 데이터를 다룰 때 ORM의 편리함을 유지할 것인가, 아니면 성능을 위해 Raw SQL/집계 쿼리를 타협할 것인가?
* **해결**: 마이페이지와 같이 읽기(Read) 연산이 많고 대량의 연관 데이터를 다루는 화면에서는 **성능이 최우선**입니다. SQLAlchemy의 ORM 루프 조회를 과감히 버리고, **단일 DB 집계 쿼리(`COUNT`, `STRING_AGG`, `LEFT JOIN`)**를 직접 작성했습니다.
  - 화면에 필요한 `주의 성분 개수`, `총 성분 수`, `상위 대표 성분 2개`를 DB 서버가 한 번에 계산해서 오도록 변경했습니다.
  - 추가로 `Promise.all`을 이용해 저장 상품, 스캔 기록, 문의 내역을 병렬 로드하고, 게스트 데이터 동기화는 백그라운드로 격리(`Non-blocking`)했습니다.

## 3. Takeaway: 무엇을 배웠는가?

1. **보안과 아키텍처는 초기 설계부터 맞물려야 한다**: `HttpOnly` 쿠키 도입 시, 프론트엔드가 인증 상태를 인지해야 하는 프론트엔드-백엔드 간 인터페이스 시나리오를 미리 검토했어야 합니다. 보안 강화는 항상 클라이언트 측의 상태 관리 방식을 재정의하게 만든다는 점을 배웠습니다.
2. **측정하고, 쿼리를 뜯어라 (ORM의 함정)**: 객체지향적 모델링은 개발을 편하게 해주지만, 대규모 리스트 조회 화면에서는 치명적인 성능 저하를 낳습니다. 
   - 결과적으로 마이페이지 백엔드 조회 속도는 **400ms에서 79ms로 5배 이상 단축**되었고, 체감 렌더링 속도 역시 **최대 10초에서 0.1~0.2초**로 비약적으로 향상되었습니다.
3. **데이터 수명주기(Life-Cycle)의 명확한 정의**: 게스트에서 회원으로 전환될 때, 로그아웃할 때, 탈퇴할 때 데이터가 어떻게 흐르고 사라져야 하는지 명세(Spec)를 명확히 하는 것이 서비스 신뢰도(정합성)의 핵심입니다.

엔지니어링은 결국 트레이드오프의 연속입니다. 보안을 지키면서도, 사용자가 체감하는 속도를 0.1초로 줄여낸 이번 경험은 서비스의 완성도를 한 단계 끌어올린 소중한 기점이었습니다.
