성장하는 웹 서비스에서 **'게스트(비회원) 경험'**은 양날의 검과 같습니다. 가입 장벽을 낮춰 사용자 유입을 극대화할 수 있지만, 게스트가 축적한 데이터를 회원 가입 시점에 유실 없이 안전하게 승격(Migration)시키는 작업과 보안 체계를 동시에 유지하기란 기술적으로 매우 까다롭기 때문입니다.

성분 분석 및 개인 맞춤형 헬스케어 서비스 **PickSafe** 개발 팀은 최근 게스트 전환율을 높이기 위한 기능 도입 중, **보안 쿠키 도입에 따른 프론트엔드 상태 오인식, 데이터 이관 누락, 그리고 마이페이지의 치명적인 렌더링 지연(최대 10초)**이라는 복합적인 병목 현상에 직면했습니다. 

이 글은 저희 팀이 보안과 성능이라는 트레이드오프 관계 속에서 어떻게 정합성 문제를 해결하고, **마이페이지 렌더링 속도를 50배 이상(10초에서 0.2초로) 개선**했는지에 대한 엔지니어링 기록입니다.

---

## 1. Problem: 우리가 마주한 세 가지 기술적 장벽

### ① 보안 쿠키(HttpOnly) 도입과 프론트엔드의 세션 판별 실패
보안 강화를 위해 세션 토큰(`access_token`)을 클라이언트가 읽을 수 없는 `HttpOnly=True` 쿠키로 발급하도록 전환했습니다. XSS 공격을 원천 차단하는 데는 성공했으나, 새로운 문제가 발생했습니다. 

기존의 프론트엔드 코드(`result.js`, `scan.js`)가 `document.cookie`에서 토큰 존재 여부를 확인해 로그인 상태를 판별하고 있었기 때문입니다. 프론트엔드는 사용자가 로그인했음에도 '비회원'으로 오인하여 회원 전용 데이터를 로컬 스토리지에 쌓기 시작했고, 이는 심각한 데이터 정합성 왜곡으로 이어졌습니다.

### ② 임시 게스트 데이터의 승격(Migration) 누락 및 동기화 무결성 위반
온보딩 과정을 건너뛰어 임시 식별자(`guest_device_id`)가 발급되지 않은 게스트가 로그인을 시도할 경우, 기존 동기화 API가 조기 반환(Early Return)되어 그동안 쌓인 스캔 기록과 찜 목록이 계정으로 이전되지 않고 소실되는 버그가 있었습니다. 

또한, 백엔드 이관 과정에서 성분 데이터(`ProductIngredient`) 임포트 누락으로 인한 500 에러와 복합 유니크 제약 조건 위반으로 데이터가 유실되는 위험을 안고 있었습니다.

### ③ ORM N+1 쿼리가 만든 지옥: 마이페이지 10초 로딩
사용자가 마이페이지에 진입하면 저장한 상품(평균 6개)과 최근 스캔 기록(평균 50개)을 보여주어야 합니다. 하지만 ORM의 Lazy Loading 속성으로 인해, 루프를 돌며 각 상품과 연관된 수십 개의 성분 객체를 매번 개별 쿼리로 조회하고 있었습니다. 

```
마이페이지 요청 ➔ 상품 조회 (1회) ➔ 각 상품의 성분 상세 조회 (N회) ➔ 스캔 이력 조회 (1회) ➔ 이력별 성분/주의성분 상세 조회 (M회)...
```
이로 인해 단 한 번의 페이지 로드에 **수백 번의 DB 왕복(Round-trip) 및 파이썬 객체 생성 오버헤드**가 발생하여, 진입 시 최대 10초까지 화면이 얼어붙는 최악의 UX를 유발했습니다.

## 2. Trade-off & Decision: 아키텍처적 고민과 대안 비교

문제를 정의한 후, 저희 팀은 단순한 '땜질식 패치'가 아닌 구조적 해결책을 찾기 위해 치열하게 토론했습니다.

### 고민 1: 쿠키 보안을 유지하면서 프론트엔드에 로그인 상태를 어떻게 전달할 것인가?
*   **대안 A: API 추가 호출** -> 페이지 로드 시마다 `/api/auth/status`를 호출하여 로그인 여부를 확인한다.
    *   *단점*: 추가 네트워크 레이턴시가 발생하고 화면 깜빡임이 생겨 UX가 저하됩니다.
*   **대안 B: SSR 기반 전역 상태 주입 (선택)** -> 서버에서 HTML 템플릿(`base.html`)을 렌더링하여 내려줄 때, 서버 세션 상태를 JS 전역 변수에 동적으로 마킹합니다.
    *   *선택 이유*: 추가 API 호출 없이 첫 렌더링 시점에 100% 정확한 로그인 세션 상태를 보장할 수 있으며, 기존 클라이언트 측 세션 판별 로직을 완전히 일원화할 수 있습니다.

### 고민 2: ORM의 편리함을 포기하고 직접 SQL을 작성할 것인가?
*   **대안 A: SQLAlchemy `joinedload` (Eager Loading) 적용** -> ORM 레벨에서 조인을 맺어 데이터를 한 번에 가져옵니다.
    *   *단점*: 성분 데이터처럼 1:N, N:M 관계가 얽혀 있는 경우, 메모리 상에 거대한 데카르트 곱(Cartesian Product) 데이터셋이 로드되어 여전히 CPU 및 메모리 부하가 컸습니다.
*   **대안 B: Raw SQL 기반 단일 집계 쿼리 작성 (선택)** -> 필요한 통계값(`주의 성분 개수`, `총 성분 수`, `상위 대표 성분 2개`)을 DB 레이어에서 직접 `COUNT`, `STRING_AGG` 함수로 연산해 단 한 번의 쿼리로 가공해 가져옵니다.
    *   *선택 이유*: 파이썬 메모리 가상 객체 생성 오버헤드를 극적으로 줄이고, DB가 가장 잘하는 '대량 데이터 필터링 및 집계' 능력을 200% 활용하기 위함입니다.

## 3. Solution: 최종 해결책 구현

### ① HttpOnly 장벽 극복 및 로그인 상태 판별 표준화
서버 측 템플릿 엔진을 활용해 `base.html` 렌더링 시점에 로그인 컨텍스트를 주입하는 헬퍼 함수를 구축했습니다.

```html
<!-- base.html (서버 사이드 템플릿 엔진 환경) -->
<script>
  window.IS_LOGGED_IN = {{ 'true' if current_user.is_authenticated else 'false' }};
  window.isGuestUser = function() {
    return !window.IS_LOGGED_IN;
  };
</script>
```
이후 `result.js`, `scan.js` 등 프론트엔드 전반의 레거시 쿠키 파싱 로직을 `window.isGuestUser()` 호출로 일체화하여 세션 판별 오류를 완벽히 종식시켰습니다.

### ② 완벽한 데이터 승격(Migration) 및 생애주기 파이프라인 설계
게스트 식별값 존재 여부와 상관없이, 로컬 스토리지 내에 임시 데이터(`guest_saved_products`, `guest_scan_history` 등)가 감지되면 즉시 백그라운드에서 임시 토큰을 발행하여 승격 API `/auth/guest-convert`를 호출하도록 프론트엔드 흐름을 개편했습니다.

```javascript
// auth.js
async function syncGuestData() {
  const localDataExists = checkLocalGuestData(); // 스캔, 알레르기, 찜 데이터 감지
  if (localDataExists) {
    const tempId = generateTemporaryIdentifier();
    await api.post('/auth/guest-convert', { temp_id: tempId, data: getLocalData() });
    clearLocalStorage(); // 동기화 완료 후 로컬 정리
  }
}
```

#### 데이터 라이프사이클 3대 원칙 확립:
1.  **로그인**: 로컬 게스트 데이터 수집 ➔ 회원 계정 DB로 이전 ➔ 기기 로컬 스토리지 정리(`removeItem`).
2.  **로그아웃**: 공용 기기에서의 민감 정보(개인 건강, 알레르기 데이터) 노출을 방지하기 위해 **해당 기기를 깨끗한 백지 상태로 초기화 (Clean Slate 원칙)**.
3.  **회원 탈퇴**: 개인정보 보호법(PIPA) 및 GDPR '잊힐 권리' 준수를 위해 백엔드 DB의 모든 연관 계정 데이터를 영구 파기(Hard Delete).

또한, 이관 중 복합 유니크 제약조건 위반으로 발생하는 DB 에러를 막기 위해 백엔드 파이프라인 내부에서 `seen_ingredients` 메모리 캐싱 및 필터링 레이어를 추가했습니다.

### ③ SQL 직접 집계 & 병렬 처리를 통한 마이페이지 초고속화
마이페이지 조회에 소요되던 병목을 해결하기 위해 백엔드(`mypage.py`) 코드를 개편했습니다. ORM 루프를 거치지 않고, 화면에 필요한 정보를 한 번에 집계하는 SQL을 작성했습니다. *(아래는 개념적으로 재구성한 최적화 쿼리 예시입니다.)*

```sql
-- 마이페이지에 표현할 저장 상품 리스트 및 요약 정보를 단 1회의 쿼리로 집계
SELECT 
    sp.id,
    sp.product_name,
    sp.created_at,
    COUNT(pi.ingredient_id) AS total_ingredients,
    COUNT(CASE WHEN pi.is_caution = TRUE THEN 1 END) AS caution_count,
    STRING_AGG(pi.ingredient_name, ', ' ORDER BY pi.importance DESC) FILTER (WHERE pi.rank <= 2) AS top_names
FROM saved_products sp
LEFT JOIN product_ingredients pi ON sp.product_id = pi.product_id
WHERE sp.user_id = :user_id
GROUP BY sp.id, sp.product_name, sp.created_at
ORDER BY sp.created_at DESC; -- 최신순 정렬 보장
```

프론트엔드(`mypage.html`)에서도 순차적으로 API를 호출하던 비동기 흐름을 `Promise.all` 기반 병렬 로딩 아키텍처로 전면 개편했습니다.

```javascript
// mypage.js - 화면 첫 진입 속도 향상을 위한 병렬 로딩 설계
async function initMypage() {
  try {
    // 3가지 핵심 영역 데이터를 동시에 비동기 요청
    const [savedProducts, scanHistory, inquiries] = await Promise.all([
      fetchSavedProducts(),
      fetchScanHistory(),
      fetchMyInquiries()
    ]);
    
    renderSavedProducts(savedProducts);
    renderScanHistory(scanHistory);
    
    // 게스트 데이터가 있다면 화면 로딩에 방해를 주지 않도록 백그라운드에서 동기화 진행
    setTimeout(syncGuestData, 0); 
  } catch (error) {
    console.error("MyPage data loading failed", error);
  }
}
```

## 4. Result: 수치로 증명된 개선 효과

이번 개편을 통해 사용자 편의성 향상과 백엔드 자원 절약 부문에서 압도적인 성과 지표를 기록했습니다.

*   **API 성능 개선**:
    *   `get_saved_products`: 400ms ➔ **79ms (약 5배 개선)**
    *   `get_my_scan_history`: 240ms ➔ **73ms (약 3.3배 개선)**
*   **체감 UI 렌더링 시간**: 최악의 케이스 기준 **10초 ➔ 0.1 ~ 0.2초 내외로 단축 (최대 50배 이상 체감 속도 향상)**.
*   **정합성 지표**: 데이터 유실 문의율 **0% 달성**, 로그인 세션 오작동 보고 **0건**.

## 5. Takeaway: 이 과정에서 우리가 배운 것들

1.  **보안과 편의성은 트레이드오프 관계지만, 기술적 절충안은 존재한다.**
    `HttpOnly` 쿠키는 웹 보안의 표준이지만 프론트엔드 상태 관리를 까다롭게 만듭니다. 이번에 적용한 *'서버 주입형 상태 헬퍼(SSR State Hydration)'*는 보안을 1%도 타협하지 않으면서 클라이언트의 세션 판별 복잡성을 제거하는 훌륭한 해법이 되었습니다.
2.  **ORM의 추상화 뒤에 숨겨진 비용을 잊지 말자.**
    ORM은 빠른 생산성을 제공하지만 대량의 복합 조인과 집계 연산에서는 심각한 N+1 병목을 만들어냅니다. 병목이 발생하는 병목 포인트(Hotspot)에서는 과감히 직접 작성한 고성능 SQL을 사용하는 것이 대규모 트래픽 환경에서 인프라 비용을 줄이고 UX를 살리는 지름길입니다.
3.  **데이터의 수명 주기를 명확히 하는 것이 좋은 아키텍처의 시작이다.**
    사용자의 온보딩(게스트), 가입(회원), 로그아웃, 회원 탈퇴에 이르는 전체 라이프사이클 전반에 걸쳐 데이터를 어떻게 다룰지 명확한 원칙(`Clean Slate`, `GDPR 준수`)을 확립함으로써, 법적 안전성을 확보하고 장기적인 정합성 문제를 예방할 수 있었습니다.
