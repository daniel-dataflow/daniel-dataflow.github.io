안녕하세요, PickSafe 백엔드/풀스택 엔지니어입니다. 
서비스의 고도화를 진행하다 보면 새로운 인프라 환경 도입이나 기능 확장(멀티 키 시스템 등)으로 인해 예상치 못한 런타임 에러를 마주하곤 합니다. 

이번 포스팅에서는 최근 Vercel Proxy 환경 도입 과정에서 발생한 소셜 로그인 콜백 에러, 멀티 API 키 도입에 따른 언패킹 미스 매치 에러를 해결한 트러블슈팅 과정과 글로벌 서비스를 위한 다국어(i18n) 시스템 완성 과정을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem)

프로덕션 환경을 고도화하는 과정에서 사용자 경험을 해치는 크고 작은 세 가지 기술적 이슈가 발생했습니다.

1. **소셜 로그인 무한 루프 (500 에러)**: Vercel Proxy 환경에서 구글/소셜 로그인 콜백 직후 `finalize_login` 라우터로 진입할 때 `ModuleNotFoundError` 발생.
2. **이미지 스캔(Scan) 기능의 불투명한 500 에러**: 이미지 스캔 요청 시 포괄적인 에러 메시지만 노출될 뿐, 백엔드의 정확한 예외 원인을 알 수 없어 디버깅이 지연됨.
3. **글로벌 확장 저해 요소**: UI 템플릿 곳곳에 잔존하던 하드코딩된 한글 텍스트로 인해 완전한 다국어(i18n) 지원에 공백 발생.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Solution)

### Issue 1. Vercel Proxy 환경에서의 JWT 복호화 에러
* **원인 분석**: 서버리스 및 리버스 프록시 환경(Vercel)으로 라우팅이 전환되는 과정에서, 특정 토큰 검증 모듈(`python-jose`)의 의존성 누락으로 인해 500 에러가 발생하고 인증 흐름이 깨졌습니다.
* **해결 방안**: 
  - 단순 모듈을 무작정 추가하여 배포 번들 사이즈를 키우는 것보다, 이미 프로젝트 내부에 안전하게 구현된 커스텀 보안 모듈의 `decode_access_token` 함수를 활용하는 방향으로 리팩토링을 결정했습니다.
  - 이를 통해 환경(로컬 vs Vercel Proxy)에 구애받지 않는 일관된 JWT 토큰 검증 파이프라인을 구축했습니다.

### Issue 2. 멀티 API 키 시스템 도입에 따른 언패킹(Unpacking) 에러
* **추적 과정**: 
  1. 먼저 사용자 UI에 포괄적인 에러 대신 구체적인 Python Exception String이 노출되도록 `scan.py`의 에러 핸들링을 일시적으로 패치했습니다. (`detail=f"성분 분석 오류 원인: {str(e)}"`)
  2. 첫 번째 원인으로 `elapsed_ms` 측정 시 `start_time` 변수 미초기화(`NameError`)를 확인하여 즉시 수정했습니다.
  3. 두 번째 원인으로 `too many values to unpack (expected 2)` 에러가 식별되었습니다. 최근 OCR 서비스의 **멀티 API 키 시스템** 도입으로 인해 `perform_ocr_on_image` 함수의 리턴값이 `(text, model, key_id)` 3개로 확장되었으나, 라우터 레벨에서는 여전히 과거의 2개 튜플 형태로 받고 있었던 것이 화근이었습니다.
* **해결 방안**: 
  - 라우터단에서 언패킹 변수를 `raw_ocr_text, used_model, used_key_id` 3개로 명확히 수신하도록 수정했습니다.
  - 또한, 테스트용 Mock 응답 분기(`lang == "en"`)를 포함한 서비스 계층 전반의 Type Hint와 리턴 타입을 3튜플로 동기화하여 구조적 안정성을 높였습니다.

### Issue 3. 글로벌 서비스를 위한 i18n 아키텍처 완성
* **접근 방식**: `result.html`, `base.html` 등 주요 뷰 템플릿에 정밀 정규식 탐색(`grep_search`)을 수행하여 잔존하던 하드코딩 텍스트를 전수 조사했습니다.
* **구현**: 
  - 배합한도, 규제정보, 성분 안내 등 5개의 새로운 고유 번역 키를 정의하고 `seed_multilingual_db.py`에 등록했습니다.
  - 이를 6개 국어 데이터베이스와 병합하여, 프로젝트 전반의 고유 다국어 키를 **총 150개**, 번역 데이터 **약 900개** 규모로 확장하여 완전한 다국어(i18n) 시스템을 마감했습니다.

## 3. 엔지니어링 교훈 (Takeaway)

1. **에러 메시지의 가독성은 디버깅 속도를 좌우한다**: 프로덕션 환경에서 발생한 500 에러를 추상적으로 숨기기보다, 시큐어한 범위 내에서 구체적인 예외 스택/메시지를 추적할 수 있는 로깅 및 에러 반환 체계가 선행되어야 원인 파악 시간을 극적으로 단축할 수 있습니다.
2. **시그니처 변경 시 영향도 분석(Impact Analysis)의 중요성**: 멀티 API 키 도입과 같은 기능 확장 시, 내부 서비스 로직의 리턴 값 변경이 상위 라우터나 의존성에 미치는 영향을 타입 시스템(Type Hint)과 함께 엄격하게 관리해야 런타임 언패킹 에러를 방지할 수 있습니다.
3. **아키텍처의 일관성**: 환경(Vercel Proxy 등)이 변하더라도 인증 및 핵심 로직이 파편화되지 않도록 내부 공통 모듈을 적극 활용하는 것이 유지보수성을 높이는 지름길입니다.
