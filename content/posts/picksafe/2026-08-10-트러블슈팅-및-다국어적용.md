안녕하세요. PickSafe 서비스 개발 과정에서 마주한 기술적 난관들과, 이를 해결하며 얻은 아키텍처적 인사이트를 공유하고자 합니다.

실서비스 환경(Production)에서 발생하는 에러는 언제나 예상치 못한 지점에서 발생합니다. 이번 포스팅에서는 **Vercel Proxy 환경에서의 의존성 충돌**, **멀티 API 구조 전환에 따른 튜플 언패킹(Unpacking) 미스**, 그리고 **글로벌 서비스를 위한 i18n 아키텍처 완성기**를 다룹니다.

## 1. 소셜 로그인 콜백과 Vercel Proxy 환경: 의존성 복잡도 줄이기

### Problem (문제 정의)
Vercel Proxy 등의 리버스 프록시 환경을 통해 구글 등 소셜 로그인 콜백을 거친 후, 인증 처리 라우터(`finalize_login`)로 진입하는 시점에 `ModuleNotFoundError`와 함께 500 에러가 발생했습니다. 이로 인해 유저가 로그인 시도 시 무한 루프에 빠지는 치명적인 온보딩 이탈 현상이 발생했습니다.

### Trade-off & Decision (기술적 고민과 대안)
- **대안 A: 외부 모듈(`python-jose`) 추가 설치**
  - *장점*: 표준적인 JWT 검증 방식을 그대로 가져갈 수 있음.
  - *단점*: Vercel 서버리스 함수의 번들 사이즈가 불필요하게 커지고, 환경별로 모듈 패키징 누락 위험이 잔존함.
- **대안 B: 내부 보안 모듈의 커스텀 토큰 함수 활용**
  - *장점*: 프로젝트 내부에 이미 안정적으로 구현된 `decode_access_token` 함수가 존재함. 외부 의존성을 추가하지 않아 배포 안정성이 높아짐.
  - *단점*: 내부 구현체에 대한 의존성이 생기나, 이미 검증된 로직이므로 리스크가 낮음.

**결정:** 의존성을 과도하게 늘리기보다는, 이미 검증된 내부 커스텀 함수(`decode_access_token`)를 활용하도록 아키텍처를 단순화하기로 결정했습니다.

### Result
Vercel 프록시 및 로컬 개발 환경 어디서나 예외 없이 유효한 JWT 토큰 검증이 수행되도록 리팩토링을 완료했습니다. 결과적으로 소셜 로그인 및 세션 쿠키 발급이 에러 없이 통과되며 마이페이지로 매끄럽게 진입하는 사용자 경험을 확보했습니다.

## 2. 이미지 성분 스캔(Scan) 500 에러 추적: 점진적 에러 가시화의 중요성

### Problem (문제 정의)
이미지 스캔 요청 시 클라이언트에는 `성분 인식 및 분석 중 오류가 발생했습니다`라는 포괄적인 메시지만 뜰 뿐, 구체적인 원인을 파악하기 힘든 500 서버 에러가 발생했습니다. 블랙박스 형태의 에러 처리가 디버깅을 가로막고 있었습니다.

### Troubleshooting (추적 및 해결 과정)

**1단계: 예외(Exception) 투명성 확보**
먼저 에러 핸들링부를 패치하여 서버 내부의 실제 Python Exception String이 프론트엔드 응답에 직관적으로 노출되도록 변경했습니다(`detail=f"성분 분석 오류 원인: {str(e)}"`).

**2단계: 연쇄적 버그 식별 및 수정**
투명해진 에러 로그를 통해 두 가지 핵심 문제를 실시간으로 파악할 수 있었습니다.
1. **`NameError`**: 타이밍 측정 로직에서 `start_time` 변수가 초기화되지 않은 채 사용됨 -> 즉각적인 초기화 구문 추가.
2. **`ValueError: too many values to unpack (expected 2)`**: 최근 도입된 **멀티 API 키 시스템**으로 인해 OCR 수행 함수(`perform_ocr_on_image`)의 리턴값이 2개에서 3개(`text, model, key_id`)로 확장되었으나, 호출부인 라우터는 여전히 2개의 변수만 받으려다 발생한 시그니처 불일치 문제.

**해결 방안:**
- 라우터 단에서 언패킹 변수를 3개(`raw_ocr_text, used_model, used_key_id`)로 정확히 수신하도록 수정했습니다.
- 테스트용 Mock 응답 분기(`ocr_service.py`)에서도 동일하게 3개의 튜플을 반환하도록 Type Hint를 통일하고 구조를 정비했습니다.

## 3. 글로벌 서비스를 향한 마지막 조각: 하드코딩 철폐와 i18n 아키텍처 완성

### Problem (문제 정의)
백엔드 로직과 컴포넌트 구조가 고도화되는 동안, 프론트엔드 뷰 템플릿 일부에 한국어 텍스트("배합한도", "규제정보", "성분 안내" 등)가 하드코딩되어 있었습니다. 이는 향후 글로벌 확장 시 레이아웃 붕괴 및 번역 누락을 유발할 수 있는 기술 부채였습니다.

### Implementation (구현 내용)
- 정규식 기반 검색(`grep_search`)을 통해 사용자 뷰 전역에 잔존한 하드코딩 텍스트 5곳을 완벽히 색출했습니다.
- 데이터베이스 시딩 스크립트(`seed_multilingual_db.py`)에 고유 번역 키를 추가하고 6개 국어 데이터를 병합했습니다.
  - 예: `result.restriction_label`, `result.regulation_label`, `base.alert_default` 등
- 이로써 프로젝트 내 총 고유 다국어 키는 **150개**, 총 번역 데이터 세트는 **900개(150 * 6개 국어)**에 도달하여 견고한 i18n(국제화) 파이프라인을 완성했습니다.

## Takeaway (엔지니어링 교훈)

1. **에러 메시지의 투명성은 디버깅 비용을 획기적으로 줄인다**: 포괄적인 에러 메시지는 사용자 경험뿐만 아니라 개발자 경험(DX)도 해칩니다. 예외 상황의 원인을 명확히 노출하는 것이 문제 해결의 지름길입니다.
2. **인터페이스(시그니처) 변경 시 전파 범위를 철저히 관리하자**: 멀티 API 도입과 같은 기능 확장 시, 함수 리턴 타입의 변경이 호출부(Consumer)에 미치는 영향을 타입 시스템이나 철저한 코드 리뷰로 사전에 차단해야 합니다.
3. **글로벌 스케일은 사소한 하드코딩 제거에서 시작된다**: i18n은 나중에 몰아서 하려면 엄청난 리팩토링 비용이 듭니다. 아키텍처 초기 단계부터 텍스트를 데이터로 분리하는 습관이 중요합니다.
