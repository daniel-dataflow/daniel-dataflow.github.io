안녕하세요, PickSafe 개발 팀입니다. 

서비스의 규모가 확장되고 Vercel과 같은 리버스 프록시 환경 도입, 멀티 API 키 시스템 통합, 그리고 글로벌 유저를 위한 다국어(i18n) 고도화 작업을 진행하는 과정에서 마주했던 기술적 도전과 해결 과정을 공유합니다. 

이번 포스팅에서는 실제 프로덕션 환경에서 발생한 3가지 핵심 이슈와 이를 해결하며 얻은 엔지니어링 인사이트를 다룹니다.

## 1. 소셜 로그인 콜백(JWT) 에러: 리버스 프록시 환경에서의 의존성 최적화

### **Problem (문제 정의)**
Vercel Proxy 환경으로 전환하는 과정에서 구글 등 소셜 로그인 콜백 이후 `finalize_login` 라우터로 진입할 때 무한 루프가 발생하며 500 에러가 떨어지는 현상이 발생했습니다. 원인은 특정 인증 모듈에서 요구하는 외부 패키지(`python-jose`)의 누락이었습니다.

### **Trade-off & Architecture (기술적 고민과 대안)**
* **대안 A: 누락된 패키지 외부 설치**
  * *장점:* 기존 코드를 수정하지 않고 빠르게 배포 가능.
  * *단점:* 불필요한 서드파티 의존성이 늘어나며, 서버less 환경(Vercel)의 콜드 스타트 시간 및 번들 크기에 미세한 악영향을 줌.
* **대안 B: 내부 보안 모듈 재활용 (채택)**
  * *장점:* 이미 프로젝트 내부에 안정적으로 구현되어 있는 커스텀 토큰 검증 함수(`decode_access_token`)를 활용하므로 추가 의존성을 걷어낼 수 있음. 아키텍처가 더 단순해짐.
  * *단점:* 내부 모듈의 규격에 맞게 호출부를 약간 수정해야 함.

### **Resolution (최종 해결)**
외부 패키지 추가 대신 프로젝트 내 이미 검증된 `decode_access_token` 보안 모듈을 활용하도록 인증 플로우를 리팩토링했습니다. 이를 통해 Vercel 프록시 및 로컬 환경 양측에서 일관된 JWT 검증이 가능해졌으며, 소셜 로그인 및 세션 쿠키 발급 프로세스가 안정적으로 정상화되었습니다.

## 2. 이미지 성분 스캔(OCR) 라우터 500 에러 추적기: 방어적 에러 핸들링의 중요성

### **Problem (문제 정의)**
이미지 스캔 요청 시 클라이언트에는 `성분 인식 및 분석 중 오류가 발생했습니다`라는 포괄적인 500 에러 메시지만 노출되고, 정확한 서버 내부 원인을 파악하기 어려운 상황이었습니다. 

### **Troubleshooting Process (추적 과정)**
1. **가시성 확보 (Observability 패치):**
   먼저 `scan.py`의 에러 반환부를 수정하여, 뭉뚱그려진 메시지 대신 실제 Python Exception String이 UI에 노출되도록 패치했습니다 (`detail=f"성분 분석 오류 원인: {str(e)}"`).
2. **1차 원인 식별 (`NameError`):**
   에러를 가시화하자 `start_time` 변수가 초기화되지 않은 채 사용된 `NameError`가 발견되었습니다. 즉각적인 변수 초기화 구문을 추가했습니다.
3. **2차 원인 식별 (튜플 언패킹 충돌):**
   이후 테스트에서 `too many values to unpack (expected 2)` 에러가 식별되었습니다. 최근 도입된 멀티 API 키 시스템으로 인해 OCR 수행 함수(`perform_ocr_on_image`)의 리턴값이 3개(`text`, `model`, `key_id`)로 확장되었으나, 라우터 레벨에서는 여전히 예전 규격인 2개만 받으려다 발생한 충돌이었습니다.

### **Resolution (최종 해결)**
* `scan.py`의 언패킹 변수를 3개(`raw_ocr_text, used_model, used_key_id`)로 올바르게 수정했습니다.
* `ocr_service.py` 내부의 테스트용 Mock 응답 분기에서도 동일하게 3개 값을 리턴하도록 타입 힌트와 인터페이스를 일괄 정비했습니다. 
* **Takeaway:** 예외 메시지를 감추는 것은 사용자 경험에 좋을 수 있으나, 개발 및 운영 단계에서는 명확한 디버깅 정보를 제공하는 방어적 에러 핸들링과 인터페이스 변경 시의 전파 관리(Type Safety)가 얼마나 중요한지 다시금 깨달았습니다.

## 3. 글로벌 서비스를 위한 다국어(i18n) 시스템 완성

### **Problem (문제 정의)**
UI 뷰 템플릿(`result.html`, `base.html` 등) 곳곳에 "성분 안내:", "배합한도:", "확인" 같은 한국어 텍스트가 하드코딩되어 있어, 글로벌 환경(다국어 서비스)으로 확장할 때 레이아웃 붕괴나 번들 누락 위험이 존재했습니다.

### **Resolution (최종 해결)**
1. **정밀 정규식 탐색(`grep_search`):** 사용자 뷰 전반을 스캔하여 잔존하는 하드코딩 텍스트 5곳을 색출했습니다.
2. **DB 기반 i18n 고도화:** 데이터베이스 시딩 스크립트(`seed_multilingual_db.py`)에 고유 번역 키 5종을 추가하고 6개 국어 데이터를 병합했습니다.
   * 예: `result.restriction_label`, `result.regulation_label`, `base.alert_default` 등
3. **결과:** 이로써 PickSafe 프로젝트는 **총 150개의 고유 다국어 키**와 **약 900개의 번역 데이터**를 확보하며 완전한 i18n 아키텍처를 구축했습니다.

## 💡 Takeaway (엔지니어링 교훈)

이번 트러블슈팅과 기능 고도화를 통해 다음의 교훈을 얻었습니다.

1. **서버less/프록시 환경에서의 의존성 최소화:** 배포 환경(Vercel 등)의 특성을 고려하여 불필요한 외부 패키지 의존성을 줄이고, 내부 코어 모듈을 재활용하는 것이 인프라 안정성에 유리합니다.
2. **예외 처리의 투명성:** 프로덕션 환경일수록 에러 로그와 응답을 명확히 설계해야 문제의 근원(Root Cause)을 빠르게 파괴할 수 있습니다.
3. **확장 가능한 아키텍처 설계:** 기능이 확장될 때(예: OCR 리턴 값 변경 등) 인터페이스 계약(Interface Contract)이 누락되지 않도록 타입 시스템과 서비스 레이어를 견고하게 유지해야 합니다.
