안녕하세요. PickSafe 백엔드 및 풀스택 아키텍처를 담당하고 있는 시니어 에디터입니다. 

서비스를 고도화하고 글로벌 타겟을 위한 다국어(i18n) 시스템을 확장하는 과정에서는 사소해 보이는 코드 변경이 연쇄적인 이슈를 낳기도 합니다. 이번 포스팅에서는 **Vercel Proxy 환경에서의 의존성 누락 문제**, **멀티 API 키 도입에 따른 언패킹(Unpacking) 에러**, 그리고 **글로벌 서비스 완성도를 높인 i18n 아키텍처 정비 과정**에서 얻은 실무적 교훈을 공유하고자 합니다.

---

## 1. 문제 정의 (Problem): 배포 환경과 코드 파편화가 부른 500 에러들

서비스 릴리스 주기가 빨라지고 여러 컴포넌트(인증, OCR 분석 파이프라인, 글로벌 i18n)가 동시에 확장될 때, 시스템은 다음과 같은 형태의 복합적인 예외 상황을 마주하게 됩니다.

1. **리버스 프록시(Vercel Proxy) 환경에서의 모듈 의존성 누락**
   - 소셜 로그인 콜백 직후 `finalize_login` 라우터 진입 시, 특정 인증 모듈의 의존성 누락(`ModuleNotFoundError`)으로 인해 500 에러와 무한 리디렉션 루프 발생.
2. **멀티 API 키 시스템 도입 후 누락된 언패킹(Unpacking) 정합성**
   - 이미지 성분 스캔(Scan) 로직 수정 과정에서 OCR 서비스 함수의 리턴 시그니처가 변경되었으나, 이를 호출하는 라우터 레코드의 변수 할당 개수가 동기화되지 않아 `too many values to unpack` 에러 발생.
   - 에러 핸들링 부재로 인해 프론트엔드에는 모호한 500 에러 메시지만 노출되어 디버깅에 난항.
3. **하드코딩된 문자열로 인한 글로벌(i18n) UX 일관성 저하**
   - UI 템플릿 내부에 남아있던 잔존 하드코딩 텍스트로 인해 글로벌 사용자가 다국어 환경을 이용할 때 레이아웃 붕괴 및 UX 단절 발생.

---

## 2. 기술적 고민과 대안 비교 (Trade-off & Solution)

### ① 인증 모듈 의존성 문제: 외부 패키지 추가 vs 내부 유틸리티 재사용
- **고민**: Vercel Proxy 환경에서 `python-jose` 관련 예외가 발생했을 때, 단순하게 패키지를 추가하여 대응할 것인가?
- **대안 비교**:
  - *대안 A (외부 패키지 추가)*: 당장의 에러는 해결되겠지만, 패키지 간 버전 충돌 및 불필요한 의존성 비대화(Bloat) 우려.
  - *대안 B (내부 유틸리티 재사용)*: 이미 보안 모듈 내에 안전하게 구현되어 검증된 커스텀 토큰 검증 함수(`decode_access_token`)를 활용.
- **선택 및 결과**: **대안 B**를 선택. 불필요한 서드파티 의존성을 제거하고, 프록시 환경과 로컬 환경 전반에서 일관된 JWT 검증 파이프라인을 구축하여 소셜 로그인 세션 발급 안정성을 확보했습니다.

### ② OCR 서비스 시그니처 변경과 Fail-Fast 에러 가시화
- **고민**: 500 에러 발생 시 포괄적인 메시지만 노출되어 원인 파악이 지연되는 문제.
- **해결 방안**:
  1. **디버깅 가시성 확보**: 예외 응답부(`detail`)에 실제 Python Exception String을 임시로 노출하도록 패치하여 `NameError(`start_time` 미초기화)` 및 `ValueError`를 즉각 식별.
  2. **시그니처 동기화**: 멀티 API 키 시스템 도입으로 인해 튜플 형태로 확장된 리턴값(`text, model, key_id`)을 호출부(Router) 및 Mock 테스트 분기점까지 엄격하게 타입 힌트와 언패킹 구조로 통일.

### ③ 다국어(i18n) 확장: 하드코딩 철폐와 정규식 탐색
- **문제**: UI 템플릿 곳곳에 남아있는 하드코딩된 한국어 텍스트.
- **해결 방안**: 
  - 정밀 정규식 탐색(`grep_search`)을 통해 사용자 뷰 내 잔존 텍스트를 전수 조사.
  - 데이터베이스 기반 다국어 시드 스크립트에 고유 키를 추가하고, 6개 국어 데이터베이스 병합 작업을 수행.
  - 결과적으로 총 150개의 고유 키와 약 900개의 번역 데이터를 확보하여 완전한 글로벌 i18n 아키텍처를 완성.

## 3. 엔지니어링 교훈 (Takeaways)

1. **에러 핸들링은 '구체적'이어야 한다**
   - 사용자 친화적인 에러 메시지도 중요하지만, 개발 및 스테이징 단계에서는 시스템 내부의 예외 스택과 상세 원인이 명확히 드러나야 트러블슈팅 타임(MTTR)을 단축할 수 있습니다.
2. **시그니처 변경 시 전파 범위(Blast Radius) 파악의 중요성**
   - 백엔드 서비스의 내부 함수 리턴값이 변경될 때(예: 2튜플 -> 3튜플), 이를 소비하는 라우터와 Mock 테스트 환경까지 일괄적으로 수정되었는지 검증하는 정적 분석(Type Hinting)이나 테스트 케이스가 필수적입니다.
3. **글로벌 서비스의 UX는 아키텍처 단계에서 설계되어야 한다**
   - 다국어(i18n) 시스템은 나중에 덧붙이는 기능이 아니라, 초기 개발 단계부터 하드코딩을 배제하고 데이터베이스 기반의 키-값 매핑 구조로 일관성 있게 관리되어야 확장성 리스크를 줄일 수 있습니다.
