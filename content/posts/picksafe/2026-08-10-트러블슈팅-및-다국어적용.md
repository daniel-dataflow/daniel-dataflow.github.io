서비스를 고도화하고 글로벌 유저를 위한 다국어(i18n) 시스템을 확장하는 과정에서 마주했던 기술적 도전 과제들과, 이를 아키텍처 관점에서 어떻게 해결하고 정교화했는지 그 과정을 공유하고자 합니다.

## 1. Problem: 프로덕션 환경의 의존성 누락과 예외 가시성 문제

서비스 운영 중 프로덕션 환경(Vercel Proxy 기반 리버스 프록시)과 이미지 분석(OCR) 파이프라인에서 예기치 않은 500 에러를 마주했습니다.

### 1) 소셜 로그인 콜백 무한 루프 (ModuleNotFoundError)
* **문제 현상:** Vercel Proxy 환경에서 구글 및 소셜 로그인 콜백 후 인증 라우터로 진입할 때 `ModuleNotFoundError`가 발생하며 500 에러를 리턴, 로그인이 무한 루프에 빠지는 현상 발생.
* **원인 분석:** 특정 환경에서 외부 인증 관련 모듈 의존성 누락이 발생하였고, 이는 인증 토큰 검증 단계의 불안정성으로 직결되었습니다.

### 2) 블랙박스화된 이미지 스캔(Scan) API 500 에러
* **문제 현상:** 이미지 스캔 요청 시 구체적인 원인 없이 `성분 인식 및 분석 중 오류가 발생했습니다`라는 포괄적인 메시지만 노출되어 디버깅이 난항을 겪음.
* **원인 분석:** 
  - **1차:** 타이틀 로직 내 `start_time` 변수 미초기화로 인한 `NameError`.
  - **2차:** 최근 멀티 API 키 시스템 도입 과정에서 OCR 서비스 함수의 리턴 시그니처가 변경(2개 튜플 $\rightarrow$ 3개 튜플)되었으나, 라우터 레벨에서 여전히 기존 언패킹 방식을 고수하여 발생한 `too many values to unpack` 예외.

## 2. Trade-off & Architecture Decision: 안정성과 확장성을 고려한 해결책

### ① 의존성 단순화 vs 외부 패키지 추가 (소셜 로그인 이슈)
* **고민:** 부족한 모듈을 무조건 외부 패키지로 추가할 것인가, 아니면 이미 검증된 내부 인프라를 활용할 것인가?
* **결정:** 불필요한 외부 패키지 의존성을 추가하는 것은 번들 크기 증가 및 잠재적 보안 취약점으로 이어진다고 판단했습니다. 대신, 프로젝트 내에 이미 안정적으로 구현되어 있는 커스텀 토큰 검증 함수(`decode_access_token`)로 로직을 교체했습니다.
* **결과:** Vercel Proxy와 로컬 환경 간의 환경 편차를 없애고, 인증 모듈의 응집도를 높여 404/500 에러 없이 세션 쿠키 발급이 매끄럽게 이루어지도록 개선했습니다.

### ② 예외 투명성 확보 및 타입 안전성 강화 (스캔 라우터 이슈)
* **조치:** 
  - 프로덕션 에러 핸들링 부에 실제 Python Exception String을 노출하도록 일시적으로 패치하여 빠른 원인 식별을 도모했습니다.
  - `ocr_service.py`와 `scan.py` 간의 리턴 타입 계약(Type Contract)을 명확히 정의하고, Mock 응답을 포함한 모든 분기에서 3개의 튜플(`raw_ocr_text`, `used_model`, `used_key_id`)을 엄격하게 반환하도록 Type Hint와 구조를 통일했습니다.

## 3. Engineering Detail: 글로벌 스케일을 위한 i18n 아키텍처 완성

백엔드 트러블슈팅과 더불어, 프론트엔드 UI/UX 전반에 남아있던 하드코딩된 한국어 텍스트를 제거하고 완벽한 글로벌 다국어(i18n) 체계를 구축했습니다.

* **하드코딩 제거:** 정밀 정규식 탐색(`grep_search`)을 통해 사용자 뷰 템플릿 내에 잔존하던 하드코딩 텍스트를 전수 조사 및 색출.
* **DB 기반 다국어 확장:** 데이터베이스 시드 스크립트에 고유 번역 키들을 추가하고, 6개 국어 데이터베이스를 병합 처리.
* **성과:** 본 작업을 통해 프로젝트의 총 고유 다국어 키는 **150개**, 총 번역 데이터 **약 900개(150 * 6개 국어)**를 확보하여 어떤 언어 환경에서도 레이아웃 붕괴 없는 견고한 i18n 시스템을 완성했습니다. 또한 PWA 모달 UX에 직관적인 닫기 버튼을 추가하여 모바일 사용자 경험(UX)을 한층 끌어올렸습니다.

## 4. Takeaway

1. **환경 격차(Environment Parity)의 중요성:** 로컬과 리버스 프록시(Vercel 등) 환경 간의 의존성 차이는 사전에 철저히 검증되어야 합니다. 가급적 외부 의존성을 낮추고 자체 검증된 모듈을 사용하는 것이 아키텍처의 복잡도를 낮추는 길입니다.
2. **함수 시그니처 변경 관리:** 멀티 API 키 시스템 도입과 같은 대규모 리팩토링 시, 서비스 레이어와 라우터 레이어 간의 인터페이스 계약(Interface Contract)이 누락되지 않도록 타입 체커나 엄격한 코드 리뷰 프로세스가 필수적입니다.
3. **글로벌 스탠다드 준수:** 초기 단계부터 i18n을 아키텍처 설계에 포함하여 하드코딩을 원천 차단하는 것이, 추후 글로벌 확장 시 발생할 기술 부채를 예방하는 가장 확실한 방법입니다.
