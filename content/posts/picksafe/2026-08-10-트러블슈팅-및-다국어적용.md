안녕하세요. `PickSafe` 서비스의 백엔드와 인프라 아키텍처를 담당하고 있는 시니어 엔지니어입니다. 

서비스를 고도화하고 글로벌 사용자(i18n)를 위한 다국어 시스템을 확장하는 과정에서, 사소해 보이지만 프로덕션 환경의 안정성을 흔들 수 있는 몇 가지 기술적 난제들을 마주했습니다. 이번 포스팅에서는 **Vercel 리버스 프록시 환경에서의 인증 모듈 의존성 문제**, **OCR 멀티 API 도입에 따른 튜플 언패킹 충돌**, 그리고 **글로벌 서비스를 위한 하드코딩 철폐 과정**에서 얻은 트러블슈팅 경험과 엔지니어링 인사이트를 공유하고자 합니다.

---

## 1. 소셜 로그인 콜백 (JWT 복호화) 에러 해결: 번거로운 의존성보다 중요한 것

### Problem (문제 정의)
Vercel 등의 서버less 리버스 프록시 환경에 애플리케이션을 배포한 직후, 구글 등 소셜 로그인 콜백이 특정 라우터로 진입하는 시점에 `ModuleNotFoundError`와 함께 500 에러가 발생하는 현상이 발생했습니다. 이로 인해 사용자가 로그인 시도가 무한 루프에 빠지는 치명적인 온보딩 드롭(Drop) 현상이 관측되었습니다.

### Trade-off & Decision (기술적 고민과 대안)
* **대안 A: 누락된 서드파티 모듈(`python-jose`)을 패키지 매니저에 추가하기**
  * *장점*: 기존 레거시 코드를 수정할 필요가 없음.
  * *단점*: 배포 환경(Vercel 서버less 런타임)의 번들 사이즈가 불필요하게 커지고, 보안 토큰 검증 로직이 외부 라이브러리에 과도하게 결합됨.
* **대안 B: 이미 검증된 사내 시큐리티 유틸리티 함수로 대체하기**
  * *장점*: 프로젝트 내부에 이미 강력하고 안정적으로 구현된 커스텀 JWT 검증 함수(`decode_access_token`)가 존재함. 의존성을 줄이고 런타임 안정성을 확보할 수 있음.
  * *단점*: 약간의 코드 리팩토링 공수 소요.

**결정:** 우리는 장기적인 유지보수성과 서버less 환경 최적화를 위해 **대안 B**를 선택했습니다. 불필요한 외부 의존성을 제거하고, 내부 보안 모듈을 통해 토큰 검증 로직을 단순화했습니다.

### Takeaway (배운 점)
서버less 및 프록시 환경에서는 **"최소한의 의존성(Minimal Dependency)"** 원칙이 배포 안정성을 좌우합니다. 외부 라이브러리에 의존하기 전, 내부 아키텍처 내에 재사용 가능한 자원이 있는지 먼저 점검하는 습관이 프로덕션 장애를 예방하는 지름길입니다.

## 2. 이미지 성분 스캔(Scan) 라우터 500 에러 추적기: 연쇄적 예외(Cascading Exceptions) 대응

### Problem (문제 정의)
이미지 성분 스캔 요청 시, 클라이언트단에는 `성분 인식 및 분석 중 오류가 발생했습니다`라는 포괄적인 메시지만 노출된 채 500 에러가 반환되었습니다. 블랙박스 상태의 에러는 디버깅을 지연시켰습니다.

### Troubleshooting Process (추적 및 해결 과정)
1. **가시성 확보 (Observability First)**: 
   먼저 예외 처리부를 패치하여 스택 트레이스 대신 구체적인 Python Exception String이 UI에 노출되도록 일시적으로 변경했습니다 (`detail=f"성분 분석 오류 원인: {str(e)}"`).
2. **1차 원인 (`NameError`)**: 
   연산 시간 측정 로직(`elapsed_ms = round((time.time() - start_time) * 1000, 1)`)에서 `start_time` 변수가 초기화되지 않은 채 참조되는 버그를 발견하여 즉각 초기화 구문을 추가했습니다.
3. **2차 원인 (`ValueError: too many values to unpack`)**: 
   1차 버그를 잡자마자 새로운 에러가 수면 위로 드러났습니다. 최근 멀티 API 키 시스템을 도입하면서 OCR 서비스 함수의 리턴 시그니처가 변경(2개 반환 -> 3개 반환: 텍스트, 모델, 키 ID)되었으나, 라우터 레이어에서는 여전히 예전 방식대로 2개의 변수만 언패킹하려다 충돌이 발생한 것입니다.

### Solution (최종 해결)
* `scan.py` 라우터의 수신부를 3개의 변수(`raw_ocr_text, used_model, used_key_id`)로 정확히 매핑하도록 수정했습니다.
* 동시에 `ocr_service.py` 내 테스트용 Mock 응답 분기에서도 동일하게 3튜플을 리턴하도록 타입 힌트(Type Hint)와 반환 구조를 엄격히 통일했습니다.

### Takeaway (배운 점)
* **에러 메시지의 구체화**: 프로덕션 환경이 아니라면, 초기 디버깅 단계에서 상세한 에러 컨텍스트를 클라이언트에 전달하는 것이 문제 해결 시간을 극적으로 단축시킵니다.
* **인터페이스 변경의 파급 효과 관리**: 비즈니스 로직 확장으로 내부 서비스 함수 시그니처가 바뀔 때는, 이를 호출하는 라우터 및 테스트 Mock 환경까지 전수 검사(Impact Analysis)하는 프로세스가 필수적입니다.

## 3. 사용자 뷰 하드코딩 완전 철폐와 견고한 i18n(다국어) 아키텍처 완성

### Problem (문제 정의)
글로벌 타겟 서비스를 지향하고 있음에도 불구하고, `result.html`과 `base.html` 등의 주요 템플릿 곳곳에 "성분 안내:", "배합한도:" 같은 한국어 텍스트가 하드코딩되어 있었습니다. 이는 글로벌 사용자에게 레이아웃 붕괴나 UX 저하를 유발할 수 있는 요인이었습니다.

### Implementation (구현 내용)
* **정밀 탐색**: 정규식 기반의 검색(`grep_search`)을 통해 뷰 템플릿에 숨겨진 하드코딩 텍스트 5곳을 모두 색출했습니다.
* **DB 드리븐 다국어 확장**: 데이터베이스 시드 스크립트(`seed_multilingual_db.py`)에 고유 번역 키 5종을 추가하고 6개 국어 데이터를 병합했습니다.
  * `result.restriction_label` (배합한도)
  * `result.regulation_label` (규제정보)
  * `result.unverified_prefix` / `result.unverified_reason` 등
* 이를 통해 `PickSafe` 프로젝트의 총 고유 다국어 키는 **150개**, 총 번역 데이터는 **900개(150 * 6개 국어)**에 도달하여 빈틈없는 글로벌 i18n 시스템을 완성했습니다.

## 마무리하며

이번 업데이트는 단순한 버그 픽스를 넘어, **서버less 환경에서의 의존성 최소화**, **인터페이스 변경에 따른 철저한 영향도 분석**, 그리고 **글로벌 확장성을 고려한 코드 클린업(i18n)**이라는 엔지니어링의 기본기를 다시 한번 다지는 계기가 되었습니다. 

앞으로도 `PickSafe`는 사용자에게 매끄럽고 안정적인 경험을 제공하기 위해, 견고하고 확장 가능한 아키텍처를 구축해 나갈 것입니다.
