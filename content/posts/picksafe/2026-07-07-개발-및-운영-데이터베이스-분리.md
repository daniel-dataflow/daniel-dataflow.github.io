안녕하세요. `PickSafe` 개발팀입니다. 

서비스를 개발하고 운영하다 보면 마주하게 되는 수많은 기술적 분기점들이 있습니다. 그중에서도 초기 스타트업이나 소규모 팀에서 가장 흔히 겪는 실수 중 하나는 **'개발(Development) 환경과 운영(Production) 환경의 데이터베이스 미분리'**로 인한 데이터 오염 사고입니다.

이번 포스팅에서는 단일 데이터베이스 설정으로 인해 발생할 수 있는 리스크를 사전에 차단하고, 서버리스 DB 환경의 제약을 극복하기 위해 어떻게 데이터베이스 연결 구조를 개선했는지 그 아키텍처 의사결정 과정을 공유하고자 합니다.

---

### 1. 문제 정의 (Problem): 단일 `DATABASE_URL`의 함정

초기 개발 단계에서는 속도와 단순함이 중요하기 때문에, 대다수의 프로젝트가 하나의 환경 변수(`DATABASE_URL`)를 바라보도록 설정합니다. 로컬에서 테스트할 때나 상용 서버에 배포할 때나 동일한 변수명에 값만 바꿔 끼우는 방식이죠.

하지만 서비스가 고도화되고 실사용자가 늘어나는 시점에서 이 방식은 다음과 같은 치명적인 위험을 안고 있습니다.

1. **데이터 오염 리스크**: 로컬 환경에서 테스트 코드를 실행하거나 마이그레이션을 테스트할 때, 실수로 상용(PROD) 데이터베이스에 접속해 실제 유저 데이터를 삭제하거나 변조할 위험(휴먼 에러)이 상존합니다.
2. **비즈니스 격리 부재**: 개발 중 발생하는 더미 데이터와 운영 데이터가 섞이면서 데이터 분석의 정확도가 떨어지고, 장애 발생 시 원인 파악이 어려워집니다.
3. **인프라 제약 (Neon Postgres 등 서버리스 DB 특성)**: 무료 티어 혹은 제한된 리소스를 제공하는 서버리스 DB를 사용할 경우, 개발 트래픽과 운영 트래픽이 한 곳으로 몰리면 리소스 고갈(Connection Pool 부족, Storage 한도 초과 등)로 인해 서비스 장애로 직결될 수 있습니다.

### 2. 기술적 고민과 대안 비교 (Trade-off)

이 문제를 해결하기 위해 두 가지 대안을 놓고 고민했습니다.

* **대안 A: 배포 파이프라인에서 `.env` 파일을 동적으로 교체하는 방식**
  * *장점:* 애플리케이션 코드는 기존의 단일 `DATABASE_URL` 인터페이스를 그대로 유지할 수 있습니다.
  * *단점:* CI/CD 파이프라인 설정이 복잡해지고, 개발자가 로컬에서 실수로 `.env`를 잘못 설정하여 상용 DB로 커넥션을 맺을 휴먼 에러 원인을 원천 차단하기 어렵습니다.

* **대안 B: 애플리케이션 레벨에서 환경(`ENV`)에 따른 명시적 변수 분기 처리**
  * *장점:* 코드 레벨에서 명확하게 `DEV`와 `PROD` 환경을 나누어 관리하므로 의도가 직관적입니다. 또한 단 하나의 설정(`ENV=prod`)만으로 안전하게 상용 DB로 스위칭이 가능합니다.
  * *단점:* 설정 파일(`config.py`)에 약간의 로직이 추가됩니다.

**최종 선택:** 팀은 **안전성(Safety)**과 **휴먼 에러 방지**를 최우선 가치로 두고, **[대안 B]** 방식을 선택했습니다. 기존 비즈니스 로직의 변경을 최소화하면서도 설정 계층에서 환경을 강제 분리하는 구조입니다.

### 3. 아키텍처 적용 및 구현 (Solution)

FastAPI 기반의 설정(Configuration) 관리 모듈을 수정하여, 환경 변수에 따라 동적으로 올바른 데이터베이스 URL을 바인딩하도록 구현했습니다.

#### ① 환경 변수 분리 (`.env`)
기존의 단일 변수 대신, 개발용과 운영용 URL을 명시적으로 분리합니다.

```env
ENV=dev  # 혹은 prod
DEV_DATABASE_URL=postgresql://user:password@dev-db-host/picksafe_dev
PROD_DATABASE_URL=postgresql://user:password@prod-db-host/picksafe_prod
```

#### ② Config 모듈 내 프로퍼티 분기 처리 (`app/config.py`)
Pydantic 등의 설정 관리 도구를 활용해, `ENV` 값에 따라 `DATABASE_URL` 프로퍼티가 동적으로 올바른 DB를 가리키도록 설정합니다.

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    ENV: str = "dev"
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

    class Config:
        env_file = ".env"

settings = Settings()
```

#### ③ 영향 범위 최소화 (Zero-impact on Business Logic)
이 아키텍처의 가장 큰 장점은 **비즈니스 로직이나 데이터베이스 커넥션을 맺는 `database.py` 등의 코드를 전혀 수정할 필요가 없다**는 점입니다. 타 모듈에서는 기존과 동일하게 `settings.DATABASE_URL`을 호출하기만 하면, 현재 실행 중인 환경에 맞춰 안전하게 커넥션이 맺어집니다.

### 4. 엔지니어링 교훈 (Takeaways)

1. **환경 분리는 '귀찮은 일'이 아니라 '기본 안전장치'다:** 프로젝트 초기일수록 환경 분리를 미루기 쉽지만, 데이터 유실 사고나 장애는 항상 방심한 순간에 찾아옵니다. 초기 구조 설계 단계에서부터 환경을 분리해 두는 것이 장기적인 생산성을 높이는 길입니다.
2. **휴먼 에러를 구조적으로 차단하라:** "실수하지 말자"는 다짐보다, "실수할 수 없는 구조를 만드는 것"이 시니어 엔지니어가 해야 할 일입니다. `ENV=prod` 설정 하나만으로 상용 DB가 안전하게 바뀔 수 있도록 설계하여 배포 단계에서의 휴먼 에러 요소를 제거했습니다.
3. **비즈니스 로직과 인프라 설정의 관심사 분리:** 설정 계층(`config.py`)에서 환경 분기 책임을 도맡아 처리함으로써, 실제 데이터를 다루는 레포지토리나 서비스 레이어는 인프라 변경으로부터 안전하게 보호받을 수 있었습니다.

작은 설정 변경이지만, 서비스의 안정성과 신뢰도를 높이는 데는 이처럼 견고한 아키텍처적 고민이 필수적입니다. 앞으로도 `PickSafe`는 안정적이고 확장 가능한 시스템을 만들기 위한 고민들을 기술 블로그를 통해 공유해 나가겠습니다.
