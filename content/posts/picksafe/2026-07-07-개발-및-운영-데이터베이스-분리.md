안녕하세요, **PickSafe** 백엔드 팀입니다. 

서비스를 개발하고 운영하다 보면 가장 아찔한 순간 중 하나는 바로 **"개발(Test) 중인 쿼리가 실수로 운영(Production) 데이터베이스를 건드렸을 때"**입니다. 특히 소규모 팀이나 애자일 환경에서는 단일 데이터베이스 설정을 사용하다가 발생하는 데이터 오염 리스크가 항상 존재합니다.

이번 포스팅에서는 PickSafe 백엔드(FastAPI)가 이러한 휴먼 에러를 원천 차단하고, 클라우드 DB(Neon Postgres 등)의 리소스 제약을 효율적으로 관리하기 위해 **개발/운영 데이터베이스 연결을 어떻게 분리하고 설계했는지** 그 아키텍처 의사결정 과정을 공유합니다.

---

## 1. Problem: 단일 데이터베이스 환경의 치명적인 리스크

초기 프로젝트 셋업 단계에서는 속도와 단순함을 위해 단일 `DATABASE_URL` 환경 변수를 두고 개발과 운영을 처리하기 쉽습니다. 하지만 서비스가 고도화되면서 다음과 같은 문제점에 직면했습니다.

1. **데이터 오염 리스크**: 로컬 환경에서 테스트 코드를 실행하거나 마이그레이션을 테스트할 때, 실수로 운영 DB에 접속해 테스트 데이터를 생성하거나 기존 데이터를 변조할 위험이 상존합니다.
2. **클라우드 DB 무료 티어(Free Tier)의 제약**: 현대적인 서버리스/클라우드 DB(예: Neon Postgres 등)는 개발 및 PoC 단계에서 유용한 무료 티어를 제공하지만, 트래픽과 스토리지 용량에 명확한 한계가 있습니다. 개발 트래픽과 실사용자 트래픽이 하나의 DB로 몰리면 리소스 경합이 발생합니다.
3. **배포 단계의 휴먼 에러**: 수동으로 환경 변수를 바꿔 끼우며 배포하는 방식은 사람의 실수로 이어지기 쉽습니다.

---

## 2. Trade-off & Architecture: 어떻게 분리할 것인가?

이 문제를 해결하기 위해 두 가지 대안을 검토했습니다.

* **대안 A: 빌드/배포 파이프라인에서 `.env` 파일을 동적으로 교체하는 방식**
  * *장점:* 애플리케이션 코드는 단일 `DATABASE_URL`을 유지해도 됩니다.
  * *단점:* 로컬 개발 환경과 CI/CD 파이프라인 간의 설정 파일 동기화 과정에서 휴먼 에러가 발생할 확률이 높고, 설정 추적이 복잡해집니다.
* **대안 B: 애플리케이션 레벨에서 `ENV` 값에 따른 동적 분기(Property) 패턴 적용**
  * *장점:* 애플리케이션 설정(`config.py`)에서 명시적으로 환경(`dev`/`prod`)을 분기하므로 코드가 직관적입니다. 또한, 비즈니스 로직이나 데이터 Access Layer 코드는 수정할 필요가 없습니다.
  * *단점:* 환경 변수 관리 항목이 늘어납니다 (`DEV_DATABASE_URL`, `PROD_DATABASE_URL`).

### 최종 선택: 대안 B (동적 분기 프로퍼티 패턴)

우리는 **안전성과 개발 생산성**에 더 높은 점수를 주어 **대안 B**를 채택했습니다. 

핵심 아이디어는 **"하위 레이어(데이터베이스 커넥션 설정 등)는 단일 인터페이스를 바라보게 하고, 상위 설정 계층에서 환경에 맞게 주입해 준다"**는 것입니다.

## 3. Implementation: FastAPI에서의 우아한 설정 분리

FastAPI의 환경 설정 관리 표준인 `pydantic-settings` (또는 유사한 설정 클래스)를 활용하여 다음과 같이 구조를 설계했습니다.

### (1) 환경 변수 정의 (`.env`)
개발 환경과 운영 환경의 커넥션 스트링을 명시적으로 분리하여 정의합니다.
```env
ENV=dev
DEV_DATABASE_URL=postgresql://user:password@dev-db-host/picksafe_dev
PROD_DATABASE_URL=postgresql://user:password@prod-db-host/picksafe_prod
```

### (2) 설정 클래스 구현 (`app/config.py`)
`ENV` 값에 따라 `DATABASE_URL` 프로퍼티가 동적으로 올바른 데이터베이스를 가리키도록 구현합니다.

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    ENV: str = "dev"
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        """ENV 설정에 따라 실시간으로 적절한 DB URL을 반환"""
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

    class Config:
        env_file = ".env"

settings = Settings()
```

### (3) 영향 범위 최소화
기존에 데이터베이스 커넥션을 맺던 `database.py` 등의 코드는 아래와 같이 기존 인터페이스(`settings.DATABASE_URL`)를 그대로 유지합니다.

```python
# app/database.py
from app.config import settings
from sqlalchemy import create_engine

# 타 코드는 변경할 필요 없이 안전하게 분리된 DB에 연결됩니다.
engine = create_engine(settings.DATABASE_URL)
```

이 구조 덕분에 비즈니스 로직이나 레포지토리 레이어의 코드를 단 한 줄도 수정하지 않고도, 안전하게 데이터베이스 격리를 달성할 수 있었습니다.

## 4. Takeaway: 시니어 에디터의 한 줄 평

이번 아키텍처 개선은 **"휴먼 에러를 방지하는 가장 좋은 방법은 프로세스가 아니라 시스템 구조로 막는 것"**임을 다시 한번 증명한 사례입니다.

* **관심사 분리(Separation of Concerns):** 비즈니스 로직과 인프라 설정 계층을 철저히 분리하여 코드의 안정성을 높였습니다.
* **낮은 결합도(Low Coupling):** `config.py` 내부에서 분기 처리를 캡슐화함으로써, 애플리케이션 전반의 코드 수정 비용을 `0`으로 만들었습니다.
* **운영 안정성:** `ENV=prod` 선언 하나만으로 상용 DB 스위칭이 가능해져 배포 과정의 리스크를 극적으로 낮추었습니다.

PickSafe 팀은 앞으로도 개발자 경험(DX)을 해치지 않으면서, 프로덕션의 안정성을 극대화하는 아키텍처 고민을 지속해 나갈 것입니다.
