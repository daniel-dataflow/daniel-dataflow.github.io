스타트업이나 신규 프로젝트의 초기 개발 단계에서는 속도가 생명입니다. 그러나 속도를 내는 과정에서 간과하기 쉬운 가작 치명적인 위험 중 하나는 바로 **"개발 환경과 운영 환경의 혼선"**입니다. 

로컬에서 테스트 코드를 돌리다 실수로 상용(Production) 데이터베이스를 날려버리거나, 반대로 상용 배포본이 개발용 데이터베이스를 바라보아 실제 고객 데이터가 유실되는 사고는 생각보다 빈번하게 발생합니다.

저희 PickSafe 팀은 최근 서비스의 안정성을 강화하고 리소스를 효율적으로 관리하기 위해, 데이터베이스 환경 분리 작업을 진행했습니다. 이 과정에서 마주한 기술적 고민과 이를 우아하게 해결한 설계 방식을 공유합니다.

---

## 1. 문제 정의: "단 하나의 `DATABASE_URL`이 가진 위험성"

기존 아키텍처에서는 단일 `DATABASE_URL` 환경 변수만을 활용해 데이터베이스에 연결했습니다. 이 방식은 초기 구축 속도를 높여주었지만, 서비스가 고도화됨에 따라 다음과 같은 세 가지 심각한 리스크를 초래했습니다.

### ① 휴먼 에러(Human Error)의 상존
로컬 개발 환경과 staging, production 환경이 명확히 분리되지 않으면, 개발자의 설정 실수 한 번으로 상용 데이터베이스에 마이그레이션이 실행되거나 테스트 데이터가 삽입될 위험이 있었습니다.

### ② 클라우드 DB(Neon Postgres)의 자원 제약 효율화
저희는 서버리스 Postgres인 **Neon**을 활용하고 있습니다. Neon의 프리 티어(Free Tier)는 빠른 프로토타이핑에 매우 유용하지만, 트래픽 및 스토리지 사용량에 제한이 있습니다. 무거운 통합 테스트나 대량의 더미 데이터 적재 작업을 상용 DB 인스턴스와 공유하는 것은 인프라 안정성 면에서 지속 불가능했습니다.

### ③ 유연하지 못한 인프라 확장성
추후 트래픽 증가로 인해 상용 데이터베이스만 리드 복제본(Read Replica)을 붙이거나 클러스터를 다르게 가져가야 할 때, 단일 환경 변수 구조는 발목을 잡을 것이 자명했습니다.

## 2. 기술적 고민과 대안 (Trade-off)

문제를 해결하기 위해 두 가지 방향성을 두고 고민했습니다.

### 안 1) 환경별로 별도의 환경 설정 파일(.env.dev, .env.prod)을 로드하기
가장 전통적인 방식입니다. 실행 환경(OS 환경 변수)에 따라 어플리케이션 시작 시 로드하는 `.env` 파일 자체를 다르게 가져가는 구조입니다.
* **장점**: 직관적이며 프레임워크에 구애받지 않습니다.
* **단점**: CI/CD 파이프라인이 복잡해지고, 배포 스크립트에서 설정 파일이 누락되었을 때의 대처가 까다롭습니다. 자칫 배포 패키지에 기밀 정보가 포함된 다른 환경 파일이 함께 빌드될 리스크가 있습니다.

### 안 2) 어플리케이션 내부에서 환경 변수(ENV)에 따라 동적으로 분기하기 (선택)
설정 클래스 내부에 환경(ENV)을 식별하는 상태값을 두고, 이에 따라 내부 프로퍼티가 적절한 커넥션 스트링을 동적으로 반환하도록 설계하는 방식입니다.
* **장점**: 설정의 단일 진입점(Single Point of Entry)을 유지할 수 있으며, 어플리케이션 코드 외부(CI/CD 도구 등)에서는 단지 `ENV=prod`라는 직관적인 값 하나만 제어하면 되므로 실수의 여지가 줄어듭니다.
* **단점**: 설정(Config) 클래스 내부의 복잡도가 다소 증가합니다.

**우리의 선택:** PickSafe 팀은 **안 2**를 선택했습니다. 개발자 경험(DX)을 해치지 않으면서 배포 파이프라인을 가장 단순하게 유지할 수 있고, 코드 수준에서 안전장치(Fail-Safe)를 마련할 수 있기 때문입니다.

## 3. 최종 해결 및 구현: "안전하고 확장성 있는 동적 환경 분리"

우리는 Python의 `pydantic-settings`와 FastAPI 환경을 활용하여 설정을 안전하게 추상화했습니다. 

핵심 아이디어는 **기존에 데이터베이스 연결을 담당하던 다른 모듈들(예: `database.py`)의 코드를 단 한 줄도 수정하지 않는 것**이었습니다. 이를 위해 파이썬의 `@property` 데코레이터를 활용해 다형성(Polymorphism)과 유사한 효과를 냈습니다.

*(보안을 위해 실제 접속 정보 및 비즈니스 로직은 마스킹 처리된 예시 코드로 대체합니다.)*

```python
# app/config.py
from pydantic import Field
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    # 실행 환경 구분 (기본값은 안전하게 'dev'로 설정)
    ENV: str = Field(default="dev", validation_alias="ENV")
    
    # 개발 및 운영 환경의 DB 주소를 개별적으로 주입받음
    DEV_DATABASE_URL: str = Field(..., validation_alias="DEV_DATABASE_URL")
    PROD_DATABASE_URL: str = Field(..., validation_alias="PROD_DATABASE_URL")

    class Config:
        env_file = ".env"
        extra = "ignore"

    # 타 모듈에서는 이 프로퍼티만 호출하면 내부 분기 로직을 신경 쓸 필요가 없음
    @property
    def DATABASE_URL(self) -> str:
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

settings = Settings()
```

### 이 설계가 주는 엔지니어링적 이점

1. **하위 호환성 및 OCP(Open-Closed Principle) 준수**: 
   `database.py` 등 실제 세션을 맺는 코드에서는 기존과 동일하게 `settings.DATABASE_URL`을 호출합니다. 호출하는 쪽에서는 자신이 개발 DB에 붙는지 상용 DB에 붙는지 알 필요가 없습니다. 설정 파일 변경으로 인한 사이드 이펙트가 완벽히 차단되었습니다.
2. **Fail-Safe 기본값 설계**: 
   `ENV` 변수가 명시적으로 `"prod"`로 설정되지 않은 모든 경우(실수 빈값이거나 잘못된 입력일 때)에는 가장 안전한 `DEV_DATABASE_URL`을 바라보도록 롤백 처리를 했습니다. 즉, 최악의 순간에도 운영 데이터가 훼손되는 일은 없습니다.

## 4. 이번 작업을 통한 엔지니어링 교훈 (Takeaway)

이번 작업은 단순히 '환경 변수 몇 개를 분리한 것' 이상의 중요한 소프트웨어 공학적 교훈을 주었습니다.

* **기술적 제약(Neon Postgres 프리티어 한계)은 더 나은 아키텍처의 기폭제가 된다**: 클라우드 자원의 한계를 인지하고 대비하는 과정에서 시스템은 한 단계 더 견고해집니다.
* **추상화의 힘**: 데이터베이스 연결 문자열을 구체적인 변수에서 프로퍼티(Property)로 한 단계 추상화함으로써, 비즈니스 로직의 변경 없이 시스템 인프라 구조를 변경할 수 있었습니다.
* **지속 가능한 안전 장치**: 시스템의 안정성은 개발자의 주의력에 의존해서는 안 되며, **'실수하기 힘든 구조(Make Errors Difficult)'**를 코드 레벨에서 강제하는 것이 시니어 개발자의 역할임을 다시 한번 실감했습니다.

앞으로도 PickSafe 팀은 견고한 아키텍처를 바탕으로 사용자가 신뢰할 수 있는 서비스를 만들어 나가겠습니다.
