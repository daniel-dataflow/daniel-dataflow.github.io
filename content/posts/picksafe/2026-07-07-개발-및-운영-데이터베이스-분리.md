안녕하세요. PickSafe 백엔드 팀입니다. 

서비스를 개발하고 운영하다 보면 가장 아찔한 순간 중 하나는 **"개발(테스트) 데이터가 실수로 운영(Production) 데이터베이스에 들어갔을 때"** 혹은 그 반대의 상황일 것입니다. 

초기 스타트업이나 소규모 프로젝트에서는 비용 절감과 빠른 구현을 위해 단일 데이터베이스 연결(`DATABASE_URL`)을 공유하기 쉽습니다. 하지만 서비스가 성장하고 프로덕션 환경의 안정성이 중요해짐에 따라, 이러한 관행은 잠재적인 장애 요인이 됩니다.

이번 포스팅에서는 PickSafe 백엔드(FastAPI) 환경에서 **개발 데이터베이스와 운영 데이터베이스를 어떻게 안전하게 분리했는지**, 그리고 비즈니스 로직의 변경 없이 **설정 계층(Configuration Layer)에서 이를 우아하게 해결한 아키텍처 의사결정 과정**을 공유합니다.

---

## 1. Problem: 단일 DB 연결 방식이 가진 위험성

프로젝트 초기, 우리는 단일 환경 변수(`DATABASE_URL`)를 사용하여 로컬 개발 환경과 클라우드 상용 환경의 연결을 관리했습니다. 하지만 이 구조는 다음과 같은 명확한 한계와 위험을 내포하고 있었습니다.

* **데이터 오염 위험:** 로컬 환경에서 테스트 코드를 실행하거나 마이그레이션을 테스트할 때, 실수로 환경 변수 설정을 누락하면 운영 데이터베이스에 직접 스키마가 변경되거나 더미 데이터가 적재될 위험이 존재했습니다.
* **클라우드 DB(Neon Postgres) 무료 티어의 제약:** 현재 활용 중인 클라우드 기반 서버리스 Postgres 환경은 리소스(트래픽, 스토리지)에 한계가 있습니다. 개발 단계의 무거운 쿼리나 대량 테스트가 상용 리소스에 영향을 주지 않도록 물리적/논리적 분리가 필수적이었습니다.
* **휴먼 에러(Human Error)의 가능성:** 배포 파이프라인이나 수동 배포 과정에서 환경 변수 교체가 누락될 경우, 운영 서버가 개발 DB를 바라보거나 반대의 상황이 발생할 수 있었습니다.

---

## 2. Trade-off & Architecture: 어떻게 분리할 것인가?

이 문제를 해결하기 위해 두 가지 대안을 검토했습니다.

* **대안 A: 배포 파이프라인에서 `.env` 파일을 동적으로 교체하기**
  * *장점:* 애플리케이션 코드는 기존의 단일 `DATABASE_URL` 인터페이스를 그대로 유지할 수 있음.
  * *단점:* CI/CD 파이프라인의 복잡도가 증가하며, 로컬에서 상용 DB로 접속해야 하는 긴급 상황 등의 예외 처리가 까다로움. 휴먼 에러의 여지가 여전히 남아 있음.
* **대안 B: 애플리케이션 설정 계층(`config.py`)에서 환경별 변수 분기 처리하기**
  * *장점:* 명시적인 `ENV` 플래그(`dev` / `prod`)를 통해 연결 대상을 코드가 아닌 설정으로 제어. 비즈니스 로직이나 DB 커넥션 코드를 수정할 필요가 없음.
  * *단점:* 설정 파일의 코드가 약간 길어짐.

우리는 **안전성과 유지보수성의 균형**을 위해 **[대안 B]**를 선택했습니다. 애플리케이션이 실행될 때 `ENV` 환경 변수를 기준으로 적절한 데이터베이스 URL을 동적으로 바인딩하도록 설계했습니다.

---

## 3. Solution: FastAPI Pydantic Settings를 활용한 동적 DB 라우팅

우선 `.env` 파일을 분리하여 개발용과 운영용 URL을 개별 등록했습니다.

```env
# .env 예시
ENV=dev
DEV_DATABASE_URL=postgresql://user:password@host-dev/picksafe_dev
PROD_DATABASE_URL=postgresql://user:password@host-prod/picksafe_prod
```

이후, FastAPI의 설정 관리 계층(`app/config.py`)에서 `ENV` 값에 따라 `DATABASE_URL` 프로퍼티가 동적으로 반환되도록 구현했습니다.

```python
import os
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    ENV: str = "dev"
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        """ENV 설정에 따라 연결할 데이터베이스 URL을 동적으로 결정합니다."""
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

    class Config:
        env_file = ".env"

settings = Settings()
```

### 💡 엔지니어링 포인트: 영향 범위 최소화 (Open-Closed Principle)
이 설계를 통해 얻은 가장 큰 장점은 **타 영역의 코드를 전혀 수정할 필요가 없었다는 점**입니다. 
데이터베이스 세션을 생성하는 `database.py` 등의 파일은 기존과 동일하게 `settings.DATABASE_URL`을 호출합니다. 호출하는 쪽에서는 내부적으로 어떤 DB(Dev/Prod)를 바라보는지 알 필요 없이, 설정 계층에서 알아서 라우팅해주는 구조를 완성했습니다.

## 4. Takeaway: 무엇을 배웠는가?

1. **설정의 명시성이 곧 안정성이다:** 
   "실수로 운영 DB를 건드리면 어쩌지?"라는 불안감은 감정에 의존할 것이 아니라, 아키텍처와 설정 레벨에서 원천 차단해야 합니다. `ENV=prod`라는 단 하나의 명시적 플래그로 환경이 분리되도록 강제함으로써 휴먼 에러의 확률을 극적으로 낮췄습니다.
2. **코드 변경 없는 리팩토링의 가치:**
   DB 연결 방식을 변경했음에도 불구하고 비즈니스 로직이나 세션 매니저 코드를 한 줄도 수정하지 않았습니다. 잘 설계된 설정 계층(Configuration Layer) 하나가 시스템 전체의 확장성과 유지보수성에 얼마나 큰 기여를 하는지 다시 한번 체감할 수 있었습니다.

PickSafe 팀은 앞으로도 안정적이고 확장 가능한 백엔드 아키텍처를 구축하기 위해 작은 디테일도 놓치지 않고 개선해 나가겠습니다. 감사합니다!
