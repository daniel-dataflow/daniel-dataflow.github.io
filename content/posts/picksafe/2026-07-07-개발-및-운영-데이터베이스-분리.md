안녕하세요, PickSafe 백엔드 아키텍처를 담당하고 있는 시니어 엔지니어입니다. 

초기 스타트업 및 사이드 프로젝트 단계에서는 속도 측면을 고려해 단일 데이터베이스(Single Database) 인스턴스를 개발과 운영에 함께 사용하는 경우가 많습니다. 하지만 서비스의 고도화와 데이터 무결성의 중요성이 대두되면서, **"개발 데이터와 운영 데이터의 물리적 분리"**는 더 이상 미룰 수 없는 과제가 됩니다.

이번 포스팅에서는 FastAPI 기반의 백엔드 환경에서 비즈니스 로직의 변경 없이 안전하게 데이터베이스 연결을 분리하고, 클라우드 DB(Neon Postgres 등)의 제약 사항을 극복한 아키텍처 의사결정 과정을 공유합니다.

---

### 1. Problem: 단일 DB 사용의 치명적인 위험과 마주하다

서비스 초기, 개발과 운영 환경에서 하나의 데이터베이스 인스턴스를 공유하거나 단순한 `.env` 교체 방식을 사용하고 있었습니다. 하지만 이 구조는 다음과 같은 치명적인 문제를 내포하고 있었습니다.

* **데이터 오염 위험:** 개발 환경에서의 부하 테스트나 로컬 디버깅 중 생성된 더미 데이터가 운영 데이터와 섞일 위험이 상존했습니다.
* **휴먼 에러(Human Error) 가능성:** 배포 과정이나 로컬 환경 설정 변경 시 실수로 프로덕션 환경 변수가 누락되거나 잘못 설정될 경우, 장애로 직결될 수 있는 구조였습니다.
* **클라우드 리소스 제약:** 현재 활용 중인 Serverless PostgreSQL(예: Neon Postgres 무료 티어)은 트래픽과 스토리지에 명확한 한계가 존재합니다. 개발 테스트 쿼리가 운영 DB의 리소스를 점유하는 것은 아키텍처 관점에서 비효율적이었습니다.

따라서 우리는 **"코드의 수정 없이, 환경 변수(`ENV`) 값 하나만으로 개발용 DB와 운영용 DB를 완벽하게 격리"**하는 구조를 설계해야 했습니다.

---

### 2. Trade-off & Architecture: 어떻게 안전하게 분리할 것인가?

데이터베이스 분리를 위한 대안으로 몇 가지 방식을 검토했습니다.

#### 대안 A: 배포 파이프라인에서 `.env` 파일을 동적으로 교체
* **방식:** CI/CD 파이프라인 빌드 시점에 환경에 맞는 `.env` 파일을 주입.
* **단점:** 로컬 개발 환경과 배포 환경의 설정 파일 관리가 이원화되며, 로컬 테스트 시 실수로 프로덕션 DB에 접속할 위험이 여전히 존재합니다.

#### 대안 B: 애플리케이션 레벨에서의 동적 라우팅 (`config.py` 분기 처리)
* **방식:** 하나의 설정 클래스 내에서 `ENV` 변수를 감지하여 동적으로 `DATABASE_URL` 프로퍼티를 스위칭.
* **장점:** 
  1. 외부 의존성 없이 설정 파일(`config.py`) 단 한 곳에서 정책을 강제할 수 있습니다.
  2. 기존 비즈니스 로직이나 데이터베이스 커넥션 코드(`database.py` 등)의 수정이 **전혀 필요 없습니다**.

우리는 **유지보수성의 극대화와 휴먼 에러 방지**를 위해 **대안 B**를 채택했습니다.

### 3. Implementation: FastAPI 설정(Config) 패턴 적용

실제 구현은 Pydantic 기반의 `BaseSettings`를 활용하여 견고하게 작성했습니다. 보안 정보를 배제한 핵심 설계 구조는 다음과 같습니다.

```python
import os
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    ENV: str = "dev"  # 기본값은 안전한 개발 환경
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        """ENV 값에 따라 동적으로 올바른 데이터베이스 URL을 반환"""
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

    class Config:
        env_file = ".env"

settings = Settings()
```

#### 💡 엔지니어링 포인트 (Impact Scope)
1. **타 코드와의 결합도 제거:** 애플리케이션의 다른 모듈들은 오직 `settings.DATABASE_URL`만 바라봅니다. 내부 구현이 어떻게 바뀌든 커넥션 레이어의 코드를 수정할 필요가 없습니다.
2. **Fail-Safe 디폴트 전략:** 명시적으로 `ENV=prod`를 선언하지 않는 한, 시스템은 무조건 `DEV_DATABASE_URL`을 바라보도록 설계하여 로컬 개발 시 실수를 원천 차단했습니다.

### 4. Takeaway: 무엇을 얻었는가?

이번 아키텍처 개선을 통해 얻은 교훈은 명확합니다.

* **안전성은 단순함에서 온다:** 복잡한 인프라스트럭처 변경 없이, 애플리케이션 레벨의 작은 설계 변경만으로도 운영 안정성을 크게 높일 수 있었습니다.
* **제약 사항을 성장의 기회로:** 클라우드 DB의 리소스 제약(Neon Postgres Free Tier 등)을 회피하기 위해 데이터 환경을 분리한 결과, 결과적으로 로컬-운영 간의 데이터 격리성이라는 모범 사례(Best Practice)를 정립하게 되었습니다.

PickSafe 팀은 앞으로도 확장 가능하고 안정적인 백엔드 아키텍처를 구축하기 위해 지속적인 기술 부채를 해결해 나갈 것입니다. 다음 포스팅에서는 이러한 아키텍처 기반 위에서 수행한 성능 최적화 사례를 다뤄보겠습니다. 많은 기대 바랍니다.
