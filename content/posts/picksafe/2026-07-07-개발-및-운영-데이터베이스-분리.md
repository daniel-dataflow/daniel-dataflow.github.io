안녕하세요. PickSafe 기술 블로그입니다. 
서비스를 개발하고 운영하다 보면 가장 아찔한 순간 중 하나는 **"개발 중인 테스트 데이터가 실수로 운영(Production) 데이터베이스에 들어갔을 때"** 혹은 반대의 상황일 것입니다. 

초기 스타트업이나 소규모 프로젝트에서는 비용 절감과 빠른 개발을 위해 단일 데이터베이스(Single DB) 환경에서 커넥션만 바꾸어가며 개발을 진행하기 쉽습니다. 하지만 서비스 규모가 커지고 데이터의 무결성이 중요해지면서, 이러한 관행은 잠재적인 대형 장애의 불씨가 됩니다.

이번 포스팅에서는 PickSafe 팀이 어떻게 데이터베이스 연결 설정을 안전하게 분리하고, 코드의 수정 비용을 최소화하면서도 휴먼 에러를 원천 차단할 수 있는 아키텍처를 구축했는지 공유해 드립니다.

---

## 1. Problem: 단일 `DATABASE_URL`이 가진 치명적인 위험

프로젝트 초기, 우리는 하나의 환경 변수(`DATABASE_URL`)를 공유하여 사용하고 있었습니다. 로컬 개발 환경(`.env`)에서도, 상용 배포 환경에서도 이 변수만 덮어씌우는 방식으로 동작했죠.

하지만 이 방식은 다음과 같은 치명적인 문제점(Problem)을 내포하고 있었습니다.

1. **데이터 오염 리스크**: 로컬에서 ORM을 이용해 마이그레이션 테스트나 더미 데이터 생성을 수행할 때, 실수로 .env 파일을 잘못 설정하면 상용 DB에 직접 타격을 줄 수 있습니다.
2. **비용 및 리소스 제약 (Neon Postgres 환경)**: 현재 활용 중인 서버리스 Postgres 환경(예: Neon Postgres 무료 티어 등)은 트래픽과 스토리지에 명확한 한계가 존재합니다. 개발용 대량 테스트 트래픽과 상용 트래픽이 한 공간에 섞이는 것은 인프라 효율 측면에서도 바람직하지 않습니다.
3. **휴먼 에러 유발**: 배포 파이프라인이나 수동 배포 과정에서 환경 변수 주입을 누락하거나 잘못 입력했을 때 이를 방어할 안전장치가 부족했습니다.

---

## 2. Trade-off & Architecture: 어떻게 안전하고 유연하게 분리할 것인가?

이 문제를 해결하기 위해 팀 내에서 몇 가지 대안을 논의했습니다.

* **대안 A: 배포 파이프라인에서 스크립트로 `.env` 파일을 동적으로 생성하기**
  * *장점*: 애플리케이션 코드를 수정할 필요가 없음.
  * *단점*: CI/CD 파이프라인이 복잡해지고, 로컬 개발 환경과 배포 환경의 설정 이원화로 인한 디버깅 난이도 상승.
* **대안 B: 설정 레이어(Config Layer)에서 동적 분기 로직 구현하기 (채택)**
  * *장점*: 코드 한 곳(`config.py`)에서 환경 변수를 중앙 집중적으로 제어할 수 있으며, 타 비즈니스 로직이나 DB 커넥션 코드는 변경할 필요가 없음. `ENV=prod` 선언만으로 직관적인 전환 가능.
  * *단점*: 설정 파일의 코드가 약간 길어짐 (단, 감수할 만한 트레이드오프).

우리는 **유지보수성과 휴먼 에러 방지**에 가장 높은 가치를 두고 **대안 B**를 선택했습니다.

## 3. Solution: FastAPI Pydantic Settings를 활용한 동적 DB 라우팅

FastAPI 환경에서 설정 관리로 널리 쓰이는 `pydantic-settings` 기반의 구성을 활용해, 애플리케이션 레벨에서 개발/운영 DB를 안전하게 분기하도록 설계했습니다.

### 설정 구조 개선 (`app/config.py`)

기존의 단일 변수 구조에서 벗어나, `DEV_DATABASE_URL`과 `PROD_DATABASE_URL`을 각각 선언하고 `ENV` 값에 따라 동적으로 바인딩되도록 프로퍼티를 구성했습니다.

```python
# 개념적 구현 예시 (app/config.py)
import os
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    ENV: str = "dev"  # 기본값은 안전한 dev 설정
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        """ENV 값에 따라 자동으로 적절한 DB URL을 반환"""
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL

    class Config:
        env_file = ".env"

settings = Settings()
```

### 이 설계가 가져온 엔지니어링적 장점

1. **Zero Impact on Business Logic**: 
   데이터베이스 커넥션을 맺는 `database.py`나 여타 Repository/Service 레이어에서는 여전히 `settings.DATABASE_URL`을 호출합니다. 설정 내부의 프로퍼티가 알아서 라우팅을 해주기 때문에, **타 코드를 단 한 줄도 수정할 필요가 없습니다.**
2. **명시적인 환경 분리 (`ENV=prod`)**: 
   상용 서버에서는 오직 `ENV=prod` 환경 변수 하나만 정확히 주입되면, 애플리케이션이 알아서 `PROD_DATABASE_URL`을 바라보게 됩니다. 개발자가 실수로 테스트 코드를 상용에 배포하더라도 DB 레벨에서의 격리가 보장됩니다.
3. **로컬 개발 편의성**: 
   로컬 개발 환경에서는 `.env`에 정의된 `DEV_DATABASE_URL`과 매핑되므로, 마음껏 데이터를 지우고 삽입하며 테스트를 진행해도 상용 데이터에 전혀 영향을 주지 않습니다.

## 4. Takeaway: 시니어 에디터의 회고

작은 설정 변경처럼 보이지만, 이번 아키텍처 개선을 통해 우리는 **"장애를 사전에 차단하는 방어적 설계"**의 중요성을 다시 한번 느꼈습니다.

* **휴먼 에러는 시스템으로 막아야 한다:** 개발자에게 "조심해서 배포해라"라고 교육하는 것보다, 시스템 구조 자체가 실수를 받아주지 않도록(Fail-safe) 설계하는 것이 훨씬 강력합니다.
* **추상화의 힘:** 설정 계층(Config Layer)에서 책임을 분리해 둔 덕분에 비즈니스 로직의 오염 없이 안전하게 인프라 환경을 격리할 수 있었습니다.

PickSafe 팀은 앞으로도 안정적이고 확장 가능한 아키텍처를 구축하기 위해 작은 디테일도 놓치지 않고 고민하겠습니다. 다음 기술 블로그도 기대해 주세요!
