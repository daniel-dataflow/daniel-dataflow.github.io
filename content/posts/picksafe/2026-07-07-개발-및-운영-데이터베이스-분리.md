안녕하세요, **PickSafe** 백엔드 팀입니다. 

서비스를 개발하고 운영하다 보면 가장 아찔한 순간 중 하나는 **"개발(테스트) 중인 데이터가 실수로 운영(Production) 데이터베이스에 반영되었을 때"** 혹은 그 반대의 상황일 것입니다. 

초기 프로젝트 단계에서는 빠른 구현을 위해 단일 데이터베이스 연결 설정을 사용하기 쉽지만, 서비스가 고도화되고 클라우드 기반의 DB 티어 제약을 관리해야 하는 시점이 오면 이는 심각한 아키텍처 부채로 다가옵니다.

이번 글에서는 FastAPI 기반 백엔드 환경에서 비즈니스 로직의 수정 없이 안전하게 개발/운영 DB를 분리하고, 휴먼 에러를 원천 차단하기 위해 적용한 아키텍처 의사결정 과정을유지보수 관점에서 공유해 드립니다.

---

## 1. Problem: 단일 DB 연결 방식이 가진 위험성

프로젝트 초기에는 환경 변수 하나(`DATABASE_URL`)로 로컬 개발부터 테스트, 운영까지 대응하도록 구성하는 경우가 많습니다. 하지만 이 구조는 다음과 같은 치명적인 문제점을 내포하고 있습니다.

1. **데이터 오염 리스크**: 로컬 환경에서 테스트 데이터를 밀어 넣거나 마이그레이션 스크립트를 잘못 실행했을 때, 상용(Production) DB가 오염될 위험이 상존합니다.
2. **클라우드 인프라 제약 (Serverless/Managed DB)**: 특히 서버리스 DB나 클라우드 제공자의 Free-tier(예: Neon Postgres 등)를 활용할 때, 개발 트래픽과 운영 트래픽이 한 곳으로 몰리면 리소스 관리 효율이 급격히 떨어집니다.
3. **배포 단계의 수동 개입 한계**: 배포 파이프라인이나 `.env` 파일을 수동으로 스위칭하는 방식은 언제나 휴먼 에러(Human Error)의 가능성을 열어둡니다.

---

## 2. Trade-off & Architecture: 어떻게 안전하게 분리할 것인가?

이 문제를 해결하기 위해 두 가지 대안을 놓고 고민했습니다.

* **대안 A: 배포 시점마다 `.env` 파일을 동적으로 교체/주입하는 방식**
  * *장점*: 코드 레벨의 변경이 최소화됨.
  * *단점*: CI/CD 파이프라인이나 로컬 설정 과정에서 실수가 발생할 경우 여전히 운영 DB를 바라보게 될 위험이 큼.
* **대안 B: 설정 레이어(Config Layer)에서 환경 변수 기반의 동적 프로퍼티 분기 처리**
  * *장점*: 코드가 실행되는 환경(`ENV=prod` 등)에 따라 애플리케이션 레벨에서 연결할 DB URL을 강제하므로 휴먼 에러를 원천 차단할 수 있음. 비즈니스 로직이나 DB 커넥션 코드를 수정할 필요가 없음.
  * *단점*: 초기 설정 관리 포인트가 살짝 늘어남.

우리는 **안전성(Safety)과 개발자 경험(DX)**을 최우선으로 고려하여 **대안 B**를 채택했습니다. 

### 💡 구현 방식 요약

1. **환경 변수 세분화**: 단일 변수 대신 `DEV_DATABASE_URL`과 `PROD_DATABASE_URL`을 개별 등록하도록 `.env` 스펙을 정의했습니다.
2. **동적 프로퍼티 구성 (`app/config.py`)**: 
   현재 시스템의 환경을 나타내는 `ENV` 변수를 참조하여, 값이 `'prod'`일 경우에만 엄격하게 `PROD_DATABASE_URL`을 반환하고, 그 외의 경우(기본값 `'dev'`)에는 개발용 DB를 바라보도록 프로퍼티를 설계했습니다.

```python
# 개념적 구현 예시 (app/config.py)
class Settings(BaseSettings):
    ENV: str = "dev"
    DEV_DATABASE_URL: str
    PROD_DATABASE_URL: str

    @property
    def DATABASE_URL(self) -> str:
        if self.ENV.lower() == "prod":
            return self.PROD_DATABASE_URL
        return self.DEV_DATABASE_URL
```

3. **관심사의 분리 (Separation of Concerns)**: 
   실제 데이터베이스 커넥션을 맺는 `database.py`나 여타 비즈니스 로직 레이어에서는 기존과 동일하게 `settings.DATABASE_URL`을 호출합니다. 설정 레이어 하위의 코드는 상위 환경이 무엇인지 신경 쓸 필요가 없도록 설계했습니다.

## 3. Takeaway: 무엇을 얻었는가?

이번 아키텍처 개선을 통해 얻은 핵심 엔지니어링 교훈은 다음과 같습니다.

* **휴먼 에러의 시스템적 방어**: "실수로 운영 DB에 연결했다"는 휴먼 에러는 개발자의 주의력에만 의존해서는 해결되지 않습니다. `ENV=prod`라는 명확한 선언적 설정을 통해서만 상용 DB에 접근하도록 구조를 강제함으로써 불안 요소를 제거했습니다.
* **확장 가능한 인프라 운영**: 개발용 DB와 운영용 DB의 물리적 분리를 통해, 무료 티어 기반의 클라우드 DB 제약 사항에 유연하게 대응하면서도 트래픽과 테스트 데이터를 깔끔하게 격리할 수 있게 되었습니다.
* **코드 수정 없는 투명한 전환**: 설정(`Config`) 객체 내부의 `@property` 활용만으로 하위 레이어의 코드 변경 없이 안전한 환경 전환 구조를 구축했습니다.

작은 설정 변경이지만, 견고한 서비스를 만들기 위해서는 이처럼 '실수할 수 없는 구조'를 만드는 것이 시니어 엔지니어가 고민해야 할 핵심 가치임을 다시 한번 확인한 작업이었습니다. 

PickSafe는 앞으로도 안정적이고 확장 가능한 아키텍처를 바탕으로 완성도 높은 서비스를 만들어 나가겠습니다. 감사합니다.
