제품을 개발하다 보면 **"기술적으로 자동화가 가능한가?"** 와 **"이 자동화가 서비스의 핵심 가치를 훼손하지 않는가?"** 사이에서 신중한 선택을 내려야 하는 순간이 찾아옵니다. 

화장품 규제 데이터 분석 플랫폼 **PickSafe** 서비스를 개발하며, 데이터 파이프라인의 자동 보강(Enrichment) 엔진을 설계했던 경험을 공유합니다. 100% 자동화를 목표로 구축하려 했던 외부 데이터셋 연동 건을 **왜 전면 백지화**했고, 대신 **어떻게 Human-in-the-Loop(HITL) 체계를 통해 엔지니어링 효율성과 데이터 무결성을 동시에 잡았는지**에 대한 이야기입니다.

---

## 1. 문제 정의: 식약처 데이터의 식별자 누락 현상

PickSafe의 핵심 엔진은 공공 데이터(식약처 성분 DB)를 정기적으로 수집하고 구조화하는 데이터 파이프라인입니다. 그러나 수집 과정에서 다음과 같은 품질 문제가 발생했습니다.

- **글로벌 표준 식별자 누락:** 복합 성분, 식물 추출물 등 일부 성분 데이터에 글로벌 화학 물질 식별자인 **CAS 번호**와 표준 성분명인 **INCI(International Nomenclature Cosmetic Ingredient)명**이 누락되어 수집됨.
- **분석 한계:** 표준 식별자가 없으면 해외 규제 DB(EU, US 등)와의 교차 검증 및 안전성 분석이 불가능해집니다.

이를 해결하기 위해 당초 팀에서는 **"외부 공공/글로벌 성분 사전을 연동하여 파이프라인 내부에서 자동 매칭 및 캐싱"**하는 구조를 설계했습니다.

---

## 2. 초기 가설과 기술적 한계 (The Trade-off & Friction)

### 당초 아키텍처 가설
1. **EU CosIng 데이터셋의 로컬 캐싱:** EU의 공식 성분 인벤토리를 일괄 다운로드하여 내부 참조 DB(`cosing_reference`)로 구축.
2. **파이프라인 내 즉시 매칭:** 식약처 데이터 수집 직후 영문 INCI명 기준 **완전 일치(Exact Match)** 조회 및 CAS 번호 자동 보강.
3. **네트워크 병목 최소화:** 외부 API 실시간 호출 대신 로컬 캐시 쿼리를 수행하여 파이프라인 지연 최소화.

```
[식약처 API] ──(수집)──> [파이프라인] ──(Exact Match)──> [CosIng 로컬 캐시]
                                                             │
                                                    (자동 매칭 & 보강)
                                                             ▼
                                                [ingredients_master DB]
```

### 마주한 기술적 결함과 위험 요소

그러나 실제 구현 전 0단계 데이터 검증 과정에서 심각한 데이터 아키텍처적 위험 요소를 발견했습니다.

1. **공식 일괄 다운로드 API의 부재:** EU CosIng 공식 포털은 단일 파일(CSV/JSON) 형태의 전체 데이터셋 Bulk Download 기능을 공식 제공하지 않았습니다.
2. **서드파티 데이터셋의 신뢰성 문제:** 대안으로 Kaggle, GitHub 등의 서드파티 오픈소스 스크래핑 데이터셋 활용을 검토했으나, **갱신 주기의 불확실성**과 **출처의 무결성 미보장** 문제가 존재했습니다.
3. **도메인 특이적 리스크:** PickSafe는 **'규제 및 안전성 데이터'**를 다루는 서비스입니다. 검증되지 않은 외부 데이터로 인해 잘못된 CAS 번호가 단 0.1%라도 자동 매핑될 경우, 서비스 전체 데이터의 신뢰도가 치명상을 입게 됩니다.

> **"신뢰할 수 없는 자동화는 데이터 오염을 대량 생산하는 파이프라인에 불과하다."**

우리는 엔지니어링 리소스를 투입해 비공식 스크래퍼를 유지보수하는 대신, **CosIng 로컬 캐시 연동 계획을 전면 백지화(Pivot)**하기로 결정했습니다.

---

## 3. 피봇 및 새로운 해결책: Human-in-the-Loop (HITL) 어드민 설계

100% 자동화를 포기하는 대신, **"사람(도메인 전문가/관리자)의 판단을 가장 쉽고 정확하게 돕는 인터페이스"**를 구축하는 방향으로 전환했습니다. 

자동 매칭의 위험성을 제거하되, 관리자의 교정 공수를 90% 이상 절감할 수 있는 **Human-in-the-Loop(HITL)** 아키텍처를 어드민 UI/백엔드에 도입했습니다.

```
[식약처 누락 데이터] ──> [어드민 검토 대기열]
                               │
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
         [KCIA 딥링크]   [CosIng 딥링크]  [K-REACH 딥링크]
               └───────────────┬───────────────┘
                               │ (관리자 수동 검증)
                               ▼
                   [Dual Inline-Editing]
                   (INCI + CAS 즉시 반영)
```

### 1) 멀티 소스 컨텍스트 딥링크 (Deep-Linking)
자동으로 데이터를 긁어와 합성하는 대신, 관리자가 단 한 번의 클릭으로 외부 검증 기관의 정확한 페이지에 도달할 수 있도록 조치했습니다.
- **분기 로직:** 영문 INCI명이 존재할 경우 영문 키워드로, 부재 시 국문 성분명으로 외부 사전(KCIA, EU CosIng, 환경부 K-REACH)의 검색 결과 페이지를 즉시 새 탭으로 생성.

### 2) Atomic Dual Inline-Editing & 재적재 파이프라인
기존에는 CAS 번호만 수정 가능했으나, 성분 데이터의 정체성인 **"INCI명"과 "CAS 번호"를 동시에 교정할 수 있는 원자적 입력 폼**을 구축했습니다.
- 외부 사전 링크를 확인한 관리자가 UI 상에서 INCI와 CAS를 즉시 수정하고 저장하면, 백엔드의 데이터 검증 게이트를 거쳐 안전하게 마스터 DB로 승인/재적재됩니다.

### 3) 프론트엔드 방어적 레이아웃 설계 (Defensive Data Grid Design)
화학 성분명 및 식물 추출물명은 문자열의 길이가 매우 길어, 좁은 어드민 창에서 UI 레이아웃이 깨지는 문제가 자주 발생합니다.
- **Grid Ratio 우선할당:** `오류 사유 > 국문 성분명 > 영문 INCI명` 순으로 텍스트 공간을 유연하게 할당.
- **Text Wrapping & Defensive CSS:** 긴 성분명으로 인해 컬럼이 찌그러지거나 글자가 세로로 잘리는 현상을 방지하도록 CSS Flex/Grid 파이프라인을 재설계하고 액션 버튼군은 Flex-Wrap을 적용해 자연스럽게 배치되도록 처리했습니다.

## 4. 엔지니어링 교훈 (Takeaways)

이번 아키텍처 결정과 데이터 파이프라인 재설계를 통해 얻은 핵심 배움은 다음과 같습니다.

### 1. 자동화는 수단일 뿐, 목적은 데이터 품질(Integrity)이다
개발자로서 "모든 것을 자동화하겠다"는 욕심은 자연스러운 본능입니다.하지만 도메인의 특성에 따라 **100% 미완성된 자동화보다 99%의 정확도를 보장하는 수동 제어 시스템(HITL)이 훨씬 더 뛰어난 아키텍처**가 될 수 있습니다.

### 2. 무조건적인 원자성보다 Trade-off를 인정하는 용기
외부 데이터 연동 시 출처의 무결성(Data Provenance)이 확인되지 않는다면, 파이프라인 전단에서 연결 고리를 단호하게 끊어낼 수 있어야 합니다. 비공식 스크래핑 데이터셋을 로컬 캐싱하는 땜빵식 기술 부채를 지지 않음으로써 시스템 고도화 시 발생할 대형 장애를 미연에 방지했습니다.

### 3. UX 최적화도 훌륭한 엔지니어링 해결책이다
백엔드 자동화 로직을 포기한 대신, 관리자 UI의 딥링크 연동과 인라인 에디팅, 방어적 글자 레이아웃을 다듬음으로써 관리자의 성분 교정 시간을 건당 1분 이상에서 **단 5초 내외로 단축**시켰습니다.

## 마치며

기술적 우아함은 복잡한 자동화 로직을 작성하는 데서만 나오지 않습니다. **비즈니스 리스크를 파악하고, 불확실한 외부 의존성을 제거하며, 사용자의 작업 효율을 정교하게 다듬는 것** 또한 시니어 개발자가 가져야 할 중요한 아키텍처적 관점임을 다시 한번 체감할 수 있었습니다.
