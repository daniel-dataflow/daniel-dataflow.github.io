성분 분석 및 규제 준수 서비스인 **PickSafe**에서 가장 중요한 자산은 바로 **'데이터의 신뢰성'**입니다. 화장품 성분을 식별하는 표준 코드인 CAS 번호와 영문 INCI(국제화장품성분명) 데이터는 서비스의 핵심 정합성을 결정짓는 척도입니다. 

그러나 식약처 원본 데이터셋에는 일부 복합 성분이나 식물 추출물의 CAS/INCI 정보가 누락되어 있는 고질적인 문제가 있었습니다. 이를 해결하기 위해 추진했던 **'EU CosIng(유럽 화장품 성분 데이터베이스) 자동 연동 파이프라인 구축'** 과정에서 마주한 기술적 한계, 그리고 데이터 무결성을 위해 **자동화를 과감히 백지화하고 수동 검증 UX를 극대화하는 방향으로 피벗(Pivot)**한 여정을 공유합니다.

---

## 1. 문제 정의: 1%의 부정확성이 초래하는 치명적인 리스크

기존 PickSafe는 식약처 데이터 수집 과정에서 누락된 CAS/INCI 정보를 보강하기 위해 대한화장품협회(KCIA) 스크래핑 소스만을 사용하고 있었습니다. 하지만 스크래핑 방식은 태생적으로 몇 가지 한계를 지닙니다.

1. **실시간 검색 스크래핑의 지연(Latency):** 외부 사이트에 건건이 HTTP 요청을 보내고 파싱하는 과정에서 수집 파이프라인의 전체 속도가 크게 저하되었습니다.
2. **검색 결과 매칭의 부정확성:** 검색 결과 리스트의 첫 번째 항목을 기계적으로 매핑하면서, 동음이의어 성분이나 유사 성분의 올바르지 않은 CAS 번호가 DB에 오염되는 이슈가 발생했습니다.

특히, 규제 및 안전성 정보를 제공하는 RegTech 서비스 특성상 **잘못된 CAS 번호 매핑은 서비스 신뢰도에 치명적인 타격**을 줍니다. 우리는 이를 해결하기 위해 신뢰성 높은 글로벌 오픈데이터 소스인 **EU CosIng** 데이터를 자동 연동 파이프라인에 추가하기로 결정했습니다.

## 2. 기술적 고민과 설계: '로컬 캐시(Local Cache)' 기반의 자동 매칭

기존 실시간 스크래핑의 단점을 극복하기 위해 설계한 아키텍처 핵심은 **"대량 다운로드 후 로컬 캐싱(Local Caching)"**이었습니다.

```
[EU CosIng 오픈데이터 포털] 
       │ (월 1회 배치 다운로드)
       ▼
[로컬 Reference DB 테이블] ── (Exact Match) ──┐
                                             ▼
[식약처 수집 파이프라인] ───────────────► [검증 승인 대기 단계]
```

### 선택한 아키텍처의 트레이드오프

* **매 요청마다 외부 API 호출 배제 (성능 이점):** 
  CosIng 전체 인벤토리를 미리 로컬 DB(`cosing_reference`)에 적재해 두고, 파이프라인 안에서는 단순 `SELECT ... WHERE inci_name = :inci` 쿼리만 실행하므로 외부 네트워크 오버헤드가 '0'에 수렴합니다.
* **유사도 기반 매칭 금지 (정합성 최우선):** 
  과거의 매칭 사고를 예방하기 위해, 오직 INCI명이 100% 일치(`Exact Match`)하는 경우에만 자동으로 매핑 필드를 채워주도록 제한했습니다.
* **승인 게이트(Approval Gate) 제도 도입:** 
  EU 정부의 공식 데이터라 할지라도 시스템 정착 초기에는 관리자가 눈으로 직접 확인하고 승인해야만 실제 프로덕션 DB(`ingredients_master`)에 병합되도록 이중 잠금장치를 두었습니다.

## 3. 반전: 자동화 계획의 전면 백지화 (Rollback & Pivot)

설계를 마치고 구현 단계에 진입했을 때, 예상치 못한 큰 장애물에 부딪혔습니다. 

### "신뢰할 수 없는 데이터 소스로 자동화를 돌릴 것인가?"
EU 공식 오픈데이터 포털 확인 결과, CosIng의 전체 인벤토리를 단일 파일(CSV/JSON 등)로 제공하는 공식 API 및 다운로드 경로가 지원되지 않았습니다. 

대안으로 Kaggle이나 GitHub 등 서드파티 개발자들이 크롤링해 둔 비공식 오픈소스 데이터셋을 파이프라인에 이식하는 방안을 검토했습니다. 그러나 시니어 엔지니어 그룹의 치열한 논의 끝에 **이 계획을 전면 백지화**하기로 결정했습니다.

* **이유:** 비공식 데이터셋은 갱신 주기를 보장할 수 없고, 원본 데이터가 왜곡되었을 가능성(Data Integrity)이 존재합니다. 규제/안전 서비스인 PickSafe에서 **출처가 불명확한 데이터를 기반으로 자동 매칭 배치를 돌리는 것은 시한폭탄을 안고 가는 것**과 같았기 때문입니다.

## 4. 최종 해결책: '인간 루프(Human-in-the-Loop)'와 UX 최적화

우리는 무리한 자동화 대신, **관리자가 수동으로 검증하고 교정할 수 있는 도구의 완성도를 극대화**하는 방향으로 선회했습니다. 기계의 불완전한 자동화보다 **"사람이 가장 쉽고 정확하게 판단할 수 있는 환경"**을 만들어주는 것이 더 가치 있는 엔지니어링이기 때문입니다.

이를 위해 프론트엔드와 어드민 시스템 영역에서 세 가지 핵심 개선을 진행했습니다.

### ① 다중 소스 수동 검색 연동 및 자동 분기 (Fallback)
자동 매칭은 포기하되, 관리자가 클릭 한 번으로 신뢰할 수 있는 외부 소스들을 교차 검증할 수 있도록 지원했습니다. 기존 KCIA, CosIng 조회 버튼에 더해 화학물질 정보의 보고인 **K-REACH(환경부 화학물질정보시스템) 검색 링크**를 추가했습니다.

```javascript
// 관리자 화면에서 외부 사전 조회를 쉽게 할 수 있도록 돕는 분기 로직 예시
function handleKReachSearch(ingredient) {
  const query = ingredient.inciName ? ingredient.inciName : ingredient.koName;
  const baseUrl = "https://kreach.mcee.go.kr/.../search?q="; 
  window.open(`${baseUrl}${encodeURIComponent(query)}`, '_blank');
}
```
영문 INCI명이 존재하면 영문명으로 검색을 시작하고, 없을 경우 국문명으로 검색하도록 자동 분기하여 관리자의 불필요한 타이핑과 마우스 이동 동선을 최소화했습니다.

### ② 데이터 일관성 유지를 위한 입력창 통합 확장
기존에는 CAS 번호만 수정할 수 있었기 때문에 INCI명이 비어 있는 경우 수동 보강이 번거로웠습니다. 이를 개선하여 CAS 번호와 INCI명을 상하로 나란히 편집할 수 있는 입력 폼을 구축하고, 백엔드 원자적(Atomic) 트랜잭션으로 두 값이 동시에 갱신되도록 개선했습니다.

### ③ 공간 집약적 반응형 테이블 레이아웃 구현 (CSS Grid / Flex Wrap)
관리자 화면은 수많은 정보(실패 사유, 국문명, 영문명, CAS 번호, 제어 버튼 등)가 한눈에 들어와야 합니다. 브라우저 크기가 작아지더라도 정보가 뭉개지거나 글자가 깨지지 않도록 CSS 레이아웃 구조를 전면 개편했습니다.

* `실패/경고 사유 > 국문 성분명 > INCI명` 순서로 반응형 너비 비율을 다르게 적용했습니다.
* 가로 해상도가 부족해질 경우, 우측의 다중 사전 검색 버튼 그룹(`KCIA` | `CosIng` | `K-REACH`)이 부드럽게 줄바꿈(`flex-wrap: wrap`)되도록 처리하여 테이블 셀 찌그러짐 현상을 방지했습니다.

## 5. 엔지니어링 교훈 (Takeaway)

이번 태스크를 진행하며 시니어 개발자로서 다시금 새긴 교훈은 다음과 같습니다.

1. **때로는 멈추는 것이 더 용기 있는 결정이다:** 
   트렌디하고 멋진 자동화 파이프라인 아키텍처를 그렸더라도, 그 기반이 되는 데이터의 신뢰성이 보장되지 않는다면 과감하게 설계를 버리고 대안을 찾아야 합니다.
2. **기술의 부재는 훌륭한 UX로 보완할 수 있다:** 
   완벽한 100% 자동화란 현실적으로 존재하기 어렵습니다. 자동화율이 90%에서 멈출 수밖에 없다면, 남은 10%를 메워줄 관리자(Human)가 피로를 느끼지 않도록 **도구와 UI를 정교하게 깎아내는 것 또한 엔지니어의 핵심 역량**입니다.
3. **도메인의 성격을 이해하는 아키텍처 설계:** 
   일반 커머스 서비스와 달리, 컴플라이언스(RegTech) 영역에서는 성능이나 코드의 세련됨보다 **'무결성'이 최우선 가치**여야 함을 원칙 레벨에서 다시 한번 검증할 수 있었습니다.
