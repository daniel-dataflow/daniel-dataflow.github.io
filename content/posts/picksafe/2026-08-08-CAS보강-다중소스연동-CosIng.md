## 들어가며: 규제 기술(RegTech)에서 '99%'의 정확도는 실패다

화장품 성분의 규제 및 안전 정보를 다루는 **PickSafe** 서비스에서 가장 중요한 가치는 **데이터의 신뢰성**입니다. 규제 정보를 다루는 플랫폼에서는 단 1%의 잘못 매핑된 데이터가 서비스 전체의 신뢰도를 무너뜨리고, 최종 사용자에게는 규제 위반이나 안전사고라는 실질적인 리스크로 이어질 수 있기 때문입니다.

최근 저희 개발팀은 식약처 수집 파이프라인에서 누락된 성분 정보(CAS 번호 및 INCI명)를 보강하기 위해 **EU CosIng(유럽 화장품 성분 데이터베이스)** 전체를 로컬에 캐싱하여 100% 자동 매칭하는 야심 찬 아키텍처를 설계했습니다. 

그러나 개발 최종 단계에서 이 계획을 **전면 백지화(Pivot)**했습니다. 

수많은 엔지니어가 '자동화'라는 기술적 성취에 매몰되기 쉽지만, 저희 팀이 왜 자동화 파이프라인을 포기하고 **'Human-in-the-Loop(인간 참여형)' 검증 모델**로 선회했는지, 그 트레이드오프와 엔지니어링적 교훈을 공유합니다.

---

## 1. 문제 정의: 수집 파이프라인의 빈틈, CAS/INCI 누락

식약처 데이터를 수집하다 보면, 복합 성분이나 식물 추출물 등 약 10건 내외(전체 수집량 대비 극소수)의 성분에서 필수 식별자인 **CAS 번호**나 영문 **INCI명**이 누락되는 현상이 발생합니다.

기존에는 대한화장품협회(KCIA) 스크래핑 데이터에만 의존해 이를 보강하고 있었으나, 커버리지 한계가 존재했습니다. 이를 해결하기 위해 신뢰성 높은 글로벌 오픈 데이터셋인 **EU CosIng**을 파이프라인에 추가 연동하여 빈틈을 메우고자 했습니다.

---

## 2. 초기 설계와 기술적 고민 (트레이드오프)

처음 구상했던 아키텍처는 **"대량 다운로드 후 로컬 캐싱(Local Caching)"** 방식이었습니다. 

```
[식약처 수집 파이프라인] 
      │
      ▼ CAS/INCI 누락 발생
[CosIng 로컬 캐시 (DB)] ── (영문명 완전 일치 조회) ──> 자동 보강 완료
```

### 왜 실시간 검색 API가 아닌 로컬 캐시였는가?
1. **네트워크 신뢰성과 성능:** 외부 API를 수집 파이프라인 중간에 실시간으로 호출하면 네트워크 지연(Latency)이 발생하고 실패율이 올라갑니다. 반면, 전체 데이터를 로컬 DB에 올려두고 조회하면 일반 `SELECT` 쿼리 수준의 비용만 발생하므로 파이프라인에 영향이 거의 없습니다.
2. **잘못된 첫 페이지 신뢰 리스크 방지:** 검색 결과를 파싱하여 첫 번째 항목을 무조건 매칭하는 방식은 오매칭 리스크가 큽니다. 로컬 캐시를 이용하면 데이터 전체를 확보한 상태에서 **'완전 일치(Exact Match)'** 조건으로만 매칭을 엄격하게 통제할 수 있다고 판단했습니다.

---

## 3. 브레이크: 자동화 계획의 맹점과 과감한 백지화

구현을 구체화하던 중 결정적인 장애물에 부딪혔습니다. **EU CosIng 공식 포털에서 제공하는 전체 인벤토리 다운로드 데이터셋의 부재**였습니다.

Kaggle이나 GitHub 등 서드파티가 크롤링해 둔 비공식 데이터셋을 활용하는 대안을 검토했으나, 이는 서비스의 핵심 원칙을 위배하는 일이었습니다.
* **출처의 무결성 미달:** 비공식 데이터는 필드의 정합성을 보장할 수 없습니다.
* **갱신 주기 신뢰 불가:** 규제 데이터는 실시간성 혹은 명확한 배치 주기를 가져야 하는데, 서드파티 데이터셋은 언제 업데이트가 중단될지 알 수 없습니다.

**"부정확한 데이터가 자동 매칭을 통해 DB에 유입되어 대량 오염될 리스크"**가 **"자동화로 얻는 운영상의 편의성"**보다 훨씬 크다고 결론을 내렸습니다. 결국, 저희는 CosIng 로컬 캐시 연동 계획을 전면 백지화했습니다.

## 4. 최종 해결책: Human-in-the-Loop 검증 도구 고도화

우리는 시스템이 100% 알아서 처리하게 만드는 대신, **"관리자가 가장 쉽고 정확하게 판단하고 교정할 수 있도록 도구를 극대화하자"**는 방향으로 피벗했습니다.

### ① 다중 소스 수동 검색 라우팅 인프라 구축
자동 스크래핑 대신 관리자가 클릭 한 번으로 신뢰할 수 있는 외부 소스의 검색 결과를 즉시 확인할 수 있도록 딥링크(Deep Link) 검색 버튼들을 추가했습니다.
* **K-REACH(환경부 화학물질정보시스템) 대응:** 영문 INCI명이 존재하면 영문명으로 검색하고, 없으면 국문명으로 검색하도록 스마트 분기 처리 로직을 적용했습니다.

### ② 양방향 데이터 교정 인터페이스 (CAS & INCI 수정 폼)
기존에는 CAS 번호만 교정할 수 있었으나, 실제 관리 워크플로우를 분석한 결과 CAS와 INCI명은 서로 긴밀하게 연관되어 있었습니다. 이에 CAS 입력창과 상하로 나란히 **"INCI 수정 입력창"**을 추가하여, 수동으로 확인한 검증 데이터를 백엔드에 원스톱으로 즉시 반영할 수 있게 개선했습니다.

```
[ 기존 ]  CAS 수정 폼만 제공 (INCI 수정 불가로 데이터 정합성 불일치 유발)
  ▼
[ 개선 ]  CAS / INCI 동시 편집 폼 탑재 ──> 트랜잭션 단위로 정합성 보장 업데이트
```

### ③ 프론트엔드 공간 최적화 및 뷰포트 방어 (CSS 레지리언스)
어드민 UI 특성상 수많은 데이터 컬럼이 좁은 화면에 배치됩니다. 창이 좁아져도 데이터가 뭉개지거나 식별이 불가능해지는 현상을 막기 위해 다음과 같은 레이아웃 규칙을 적용했습니다.
* **우선순위 기반 공간 배분:** 핵심 필드인 `실패 사유 > 성분명(국문) > INCI명(영문)` 순으로 비율을 고정 할당했습니다.
* **유연한 줄바꿈(Flex-Wrap) 제어:** 검색 버튼들이 많아져 레이아웃이 깨지는 것을 막기 위해, 공간 부족 시 버튼들이 2줄로 자연스럽게 Wrap되도록 스타일을 견고히 설계했습니다.

## 5. 엔지니어링 교훈 (Takeaway)

이번 태스크를 진행하며 시니어 개발자로서 얻은 소중한 깨달음은 다음과 같습니다.

1. **자동화가 늘 정답은 아니다:** 
   엔지니어는 모든 문제를 코드로 자동화하고 싶어 하는 본능이 있습니다. 하지만 원천 데이터의 출처가 불확실할 때 억지로 구현한 자동화는 오히려 시스템에 '침묵하는 재앙(Silent Failure)'을 가져옵니다. 때로는 똑똑한 수동 검증 인터페이스를 제공하는 것이 정답일 수 있습니다.
2. **에러를 마주하는 아키텍처의 유연성:** 
   개발 단계에서 예상치 못한 제약 사항(CosIng 다운로드 불가)을 마주했을 때, 일정을 핑계로 타협하지 않고 과감히 이전 아키텍처를 폐기(Deprecate)할 수 있는 결단력이 좋은 소프트웨어를 만듭니다.
3. **도메인에 대한 깊은 이해가 우선이다:** 
   만약 우리가 규제/안전 서비스라는 도메인 특성을 간과하고 일반적인 e-커머스 상품 매칭 시스템처럼 생각했다면 리스크가 큰 서드파티 데이터를 사용했을지도 모릅니다. 기술적 결정은 언제나 비즈니스의 핵심 가치 위에서 이루어져야 합니다.

앞으로도 PickSafe 개발팀은 타협하지 않는 데이터 신뢰성을 바탕으로, 엔지니어링적 실용주의를 실현해 나갈 것입니다.
