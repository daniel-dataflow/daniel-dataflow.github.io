화장품 성분 분석 서비스 PickSafe를 개발하고 운영하면서 식약처(KFDA) 데이터 수집·보강 파이프라인과 관리자(어드민) 대시보드 기능이 점차 확장되었습니다. 도메인 로직이 늘어남에 따라 백엔드 레이어 간 파일명이 파편화되고, 어드민 프론트엔드 코드의 복잡도가 급격히 증가하는 기술 부채를 마주하게 되었습니다.

이번 작업에서는 시스템의 안정성을 해치지 않으면서 코드 구조 정합성을 높이고, 과거 손상 이력이 있던 어드민 대시보드를 독립적인 화면 단위로 분리하는 구조 정비 작업을 진행했습니다.

---

## 🎯 마주한 고민과 문제 배경

프로젝트를 진행하며 크게 세 가지 문제점이 드러났습니다.

### 1. 식약처(KFDA) 관련 파일명의 파편화
식약처 성분 데이터를 수집, 보강, 병합, 스케줄링하는 도메인 로직이 시스템 전반에 걸쳐 퍼져 있었습니다. 그러나 각 레이어별 파일명이 제각각으로 작성되어 있었습니다.
- 모델 레이어: `models/staging.py`
- 라우터 레이어: `routers/seeding.py`
- 서비스 레이어: `services/kfda_service.py`, `services/seed_kfda_ingredients.py`

동일한 도메인 맥락을 다루고 있음에도 파일명만으로는 관계를 파악하기 어려웠고, 신규 기능을 추가하거나 디버깅할 때 관련 파일을 찾는 데 쓸데없는 탐색 비용이 발생했습니다.

### 2. 거대해진 단일 어드민 템플릿 (`dashboard.html`)
PickSafe의 어드민 영역은 서버사이드 렌더링(SSR)과 최소한의 JavaScript 활용을 기본 원칙으로 삼고 있습니다. 그러나 `dashboard.html` 파일 하나 안에 인프라 모니터링, 로그, 문의 관리, 방문자 분석, 인기 제품 관리, 번역 관리 등 6개 이상의 기능 섹션이 인라인 JavaScript 탭 전환 방식으로 몰려 있었습니다.

이로 인해 단일 파일의 줄 수가 과도하게 늘어났고, 과거 기능 수정 과정에서 커밋 충돌과 로직 꼬임으로 인해 파일이 두 차례나 손상되는 사고가 있었습니다.

### 3. 기능 문서(`docs/features/`)와 실제 코드 간의 불일치
개발 속도를 내는 과정에서 기능 설계 문서에 기재된 파일 경로와 실제 코드베이스의 파일 경로가 어긋나는 현상(Documentation Drift)이 발생했습니다. 일례로 어드민 방문자 분석 문서가 실제 파일명(`11_어드민_방문자분석.md`)과 다른 번호로 참조되는 등 문서의 신뢰도가 떨어진 상태였습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

### 💡 어드민 대시보드 구조 개선 대안

| 비교 항목 | 대안 A: 기존 구조 유지 + 인라인 JS 분리 | 대안 B: 라우트 및 SSR 템플릿 단위 완벽 분리 (최종 선택) |
| :--- | :--- | :--- |
| **구조** | single URL (`/admin/dashboard`) 내 JS 탭 상태 관리 | 독립된 라우트 (`/admin/inquiries`, `/admin/analytics` 등) |
| **템플릿** | 단일 `dashboard.html` | 공통 `base_admin.html` + 섹션별 독립 `.html` |
| **안정성** | 한 섹션의 스크립트 에러가 전체 탭 동작에 영향을 줌 | 화면 간 격리(Isolation)로 개별 오류 영향 차단 |
| **유지보수성** | 파일 손상 위험 지속 존재 | 개별 파일 크기가 작아지고 변경 범위가 명확해짐 |
| **원칙 부합성**| SSR 원칙에 위배 (클라이언트 JS 비중 높음) | SSR + 최소 JS 원칙 완벽 충족 |

**선택 이유:**
관리자 기능의 특성상 SPA(Single Page Application) 수준의 매끄러운 탭 전환보다는 **화면별 독립성과 운영 안정성**이 훨씬 중요합니다. 공통 템플릿 상속(`{% extends %}`) 구조를 도입하여 네비게이션을 한 곳에서 관리하고, 각 섹션을 독립된 라우트와 템플릿으로 분리하는 대안 B를 선택했습니다.

### 💡 파일 리네이밍 및 모듈화 접근 전략

한 번에 모든 파일명을 변경하고 임포트를 일괄 수정할 경우, 순환 참조나 누락된 임포트로 인해 서버 기동 자체가 불가능해질 위험이 컸습니다. 따라서 **'파일 1개 변경 → 임포트 구문 수정 → `py_compile` 및 서버 기동 검증'**을 반복하는 점진적(Incremental) 리네이밍 전략을 채택했습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 점진적 파일 리네이밍과 의존성 검증

리네이밍 전 `grep` 전수 조사를 통해 영향 범위를 파악한 후 작업을 진행했습니다.

```bash
# 식약처 관련 참조 모듈 전수 조사
grep -rn "import.*seed_kfda\|import.*kfda_service\|from.*staging" web/backend/app/
```

리네이밍 후에는 단순히 코드를 눈으로 확인하는 것에 그치지 않고, Python의 `py_compile` 모듈을 활용해 구문 오류와 참조 실패를 기동 전에 검증했습니다.

```python
# scripts/verify_imports.py (검증 스크립트 예시)
import py_compile
import sys
from pathlib import Path

def check_compilation(root_dir: str):
    has_error = False
    for path in Path(root_dir).rglob("*.py"):
        try:
            py_compile.compile(str(path), doraise=True)
        except py_compile.PyCompileError as e:
            print(f"[ERROR] Compilation failed: {path}\n{e}")
            has_error = True
    if has_error:
        sys.exit(1)
    print("[SUCCESS] All files compiled successfully.")

if __name__ == "__main__":
    check_compilation("web/backend/app")
```

### 2. 어드민 대시보드 모듈화 (Jinja2 Template Inheritance)

공통 레이아웃을 `base_admin.html`로 추상화하여 네비게이션 메뉴 수정 시 단 한 곳만 변경되도록 개선했습니다.

```html
<!-- web/frontend/templates/admin/base_admin.html -->
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <title>{% block title %}PickSafe Admin{% endblock %}</title>
    <link rel="stylesheet" href="/static/css/admin.css">
</head>
<body>
    <aside class="sidebar">
        <nav>
            <a href="/admin/analytics" class="{% if active_page == 'analytics' %}active{% endif %}">방문자 분석</a>
            <a href="/admin/inquiries" class="{% if active_page == 'inquiries' %}active{% endif %}">문의 관리</a>
            <a href="/admin/products" class="{% if active_page == 'products' %}active{% endif %}">인기 제품 관리</a>
            <a href="/admin/infra" class="{% if active_page == 'infra' %}active{% endif %}">인프라 모니터링</a>
        </nav>
    </aside>
    <main class="content">
        {% block content %}{% endblock %}
    </main>
    {% block extra_scripts %}{% endblock %}
</body>
</html>
```

개별 기능 화면은 상속을 받아 본문 로직 및 해당 화면 전용 JavaScript 파일만 깔끔하게 포함합니다.

```html
<!-- web/frontend/templates/admin/inquiries.html -->
{% extends "admin/base_admin.html" %}

{% block title %}문의 관리 - PickSafe Admin{% endblock %}

{% block content %}
<section class="inquiry-container">
    <h2>1:1 문의 내역</h2>
    <!-- 문의 목록 테이블 및 승인 폼 -->
</section>
{% endblock %}

{% block extra_scripts %}
<script src="/static/js/admin/inquiries.js"></script>
{% endblock %}
```

### 3. 트러블슈팅: 스케줄러(`scheduler.py`) 모듈의 책임 분리 문제

리네이밍 과정에서 `services/scheduler.py`를 `kfda_scheduler.py`로 변경할지 고민이 있었습니다. 

코드 내부를 확인해보니 현재는 식약처 수집 작업만 등록되어 있었지만, 향후 '주간 인기 제품 분석 배치'나 '로그 정기 압축' 등 범용 배치 작업이 추가될 여지가 있었습니다.

- **문제:** 식약처 전용으로 파일명을 바꾸면 추후 타 도메인 배치 추가 시 재수정이 필요해짐.
- **해결:** `scheduler.py`라는 파일명은 그대로 유지하되, 내부 작업 등록 함수를 `register_kfda_jobs()` 형태로 식약처 로직임을 명확히 명시하는 방식으로 책임을 정리했습니다.

## 💡 돌아보며 배운 점 (회고)

이번 리팩토링 작업을 마치며 얻은 실질적인 개선 효과와 엔지니어링 시사점은 다음과 같습니다.

### 1. 얻은 성과
- **운영 안정성 향상:** 단일 대시보드 파일(`dashboard.html`)의 코드 분량 감소. 화면 단위 파일 분리로 과거 발생했던 커밋 충돌 및 파일 손상 위험성 차단.
- **가독성 및 도메인 명확성:** `models/kfda_staging.py`, `routers/kfda_seeding.py` 등 파일명만으로도 도메인 역할과 레이어를 즉시 파악 가능.
- **문서 정합성 100% 달성:** `docs/features/` 문서 전체 경로와 실제 코드베이스의 일치성을 검증하여 프로젝트 온보딩 및 유지보수 효율성 향상.

### 2. 깨달은 엔지니어링 교훈
- **점진적 리팩토링의 가치:** 아무리 작은 파일명 변경이라도 임포트 관계가 얽혀 있다면 시스템 전체를 멈추게 할 수 있습니다. 하나씩 변경하고 검증하는 솔직하고 단단한 접근 방식이 결과적으로 가장 빠른 길임을 재확인했습니다.
- **적절한 상속과 분리의 중요성:** 프론트엔드 프레임워크를 도입하지 않는 SSR 환경에서도 SSR의 강점인 템플릿 상속을 적극 활용하면 SPA 못지않은 우수한 구조적 격리를 이룰 수 있었습니다.

### 추후 보완할 점
어드민 대시보드의 URL 분리는 완료되었으나, 각 대시보드 API의 응답 규격이 일부 상이한 부분이 남아있습니다. 다음 작업에서는 어드민 전용 API들의 에러 응답 포맷과 페이징 규격을 공통 DTO 형태로 통일하는 작업을 이어서 진행할 계획입니다.
