화장품 성분 분석 서비스 PickSafe를 개발하면서, 서비스 초기 단계에 빠르게 기능을 구현하는 과정에서 작성되었던 루트 디렉토리 중심의 코드 구조가 점차 유지보수의 병목으로 작용하기 시작했습니다. 

단순히 엔드포인트를 추가하고 템플릿을 연결하는 수준을 넘어, OCR 스캔 비즈니스 로직과 성분 데이터 매칭 알고리즘이 복잡해짐에 따라 프로젝트 전반의 디렉토리 구조를 재정의해야 할 필요성을 느꼈습니다. 본 글에서는 디렉토리 격리 및 계층화 마이그레이션을 진행하며 했던 기술적 고민과 트러블슈팅 경험을 담백하게 기록합니다.

---

## 🎯 마주한 고민과 문제 배경

프로젝트 초기에는 FastAPI의 빠른 생산성을 활용하기 위해 루트 디렉토리에 백엔드 로직, Jinja2 HTML 템플릿, 정적 리소스(CSS, JS)를 함께 두고 개발을 진행했습니다. 하지만 스캔 기능, 회원 관리, 성분 DB 매칭 등 기능이 확장되면서 세 가지 주요 문제에 부딪혔습니다.

1. **프론트엔드와 백엔드 자원의 모호한 경계**
   - Jinja2 기반의 Server-Side Rendering(SSR)을 사용하고 있었지만, HTML 템플릿과 CSS/JS 정적 파일이 백엔드 코드와 동일한 층위에 섞여 있어 파일 탐색과 관리가 비효율적이었습니다.
   - 추후 프론트엔드를 React나 Next.js와 같은 SPA/SSR 프레임워크로 전면 교체할 경우를 대비한 물리적 격리가 불가능한 구조였습니다.

2. **비즈니스 로직과 HTTP 엔드포인트의 결합**
   - 라우터 함수 내부에서 스캔 이미지의 OCR을 처리하고, 알레르기 유발 성분 매칭을 수행하며, 데이터베이스 쿼리까지 직접 호출하는 형태가 늘어났습니다.
   - 이로 인해 단위 테스트 작성이 어려워졌고, 코드 재사용성이 현저히 떨어졌습니다.

3. **실행 및 모듈 참조 경로의 불확실성**
   - 앱이 커짐에 따라 상대 경로 참조(`from ..services import ...`)가 복잡해졌고, 실행 위치에 따라 Python의 `sys.path` 인식이 달라져 임포트 에러가 종종 발생했습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

프로젝트의 구조 개선을 위해 세 가지 대안을 놓고 고민했습니다.

| 구분 | 대안 A: 루트 기반 디렉토리 유지 | 대안 B: 완전 독립 모노레포 구축 | 대안 C: 계층적 디렉토리 격리 및 레이어드 패턴 (최종 선택) |
| :--- | :--- | :--- | :--- |
| **구조** | 루트에 `/routers`, `/models`, `/templates` 배치 | Turborepo/Nx 등을 활용한 별도 패키지 분리 | `/web/backend`와 `/web/frontend` 디렉토리 완전 분리 |
| **장점** | 마이그레이션 비용 없음 | 완전한 서비스 분리 가능, CI/CD 독립화 | 현재 Jinja2 템플릿 구조 유지 가능, 향후 FE 전면 교체 용이 |
| **단점** | 코드 결합도 누증, 프론트엔드 분리 어려움 | 현재 프로젝트 규모 대비 빌드/배포 오버헤드 과다 | 일부 모듈 실행 경로 변경에 따른 스크립트 수정 필요 |

### 대안 C를 선택한 이유
현재 PickSafe는 Jinja2 템플릿 엔진을 활용해 빠르게 화면을 제공하고 있으므로, 과도한 모노레포 도구를 도입하는 대안 B는 오버헤드가 크다고 판단했습니다. 

대신 **대안 C**를 선택하여 `/web/backend` 하위에 백엔드 애플리케이션 코드를 집약하고, `/web/frontend` 하위에 HTML과 정적 리소스를 격리했습니다. 백엔드 내부 역시 `models`, `routers`, `services`로 책임을 명확히 나눔으로써 비즈니스 로직(OCR, 매칭 알고리즘)의 독립성을 확보했습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 갱신된 재정의 디렉토리 구조

`web/backend`와 `web/frontend`로 역할을 격리하고, 비즈니스 로직을 `services` 레이어로 승격시킨 최종 구조입니다.

```text
/picksafe

      /app
        /models       (ORM 테이블 정의)
        /routers      (엔드포인트 및 Jinja2 렌더링)
        /services     (OCR, 성분 매칭 등 핵심 비즈니스 로직)
```

### 2. 마이그레이션 중 마주친 문제: 모듈 실행 경로 및 static 경로 이슈

디렉토리 이동 후 발생한 첫 번째 문제는 Uvicorn 실행 시 Python 패키지 경로 탐색 오류였습니다. 

#### [문제 1] Python Path 인지 문제
기존 `uvicorn app.main:app` 명령어를 루트에서 실행할 때 `app` 모듈을 찾지 못하는 현상이 발생했습니다.

*해결 과정:*
`web/backend` 내부로 이동하여 구동하거나, 실행 스크립트에서 실행 맥락을 명시적으로 변경하여 해결했습니다. 임포트 구문은 기존의 clean한 형태(`from app.models.user import User`)를 그대로 유지하도록 보존했습니다.

#### [문제 2] 프론트엔드 정적 파일/템플릿 경로 유실
`main.py` 위치가 깊어짐에 따라 `StaticFiles` 및 `Jinja2Templates`의 상대 경로 인식이 깨졌습니다.

*해결 코드 스니펫:*
경로 하드코딩을 방지하기 위해 `pathlib.Path`를 활용하여 절대 경로 기준으로 정적 파일과 템플릿 디렉토리를 바인딩하도록 수정했습니다.

```python
# web/backend/app/main.py (일부)

from pathlib import Path
from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

# 현재 파일 기준 상위 디렉토리 추적
BASE_DIR = Path(__file__).resolve().parent.parent.parent  # /picksafe/web 디렉토리 지점

app = FastAPI(title="PickSafe API")

# 프론트엔드 정적 파일 및 템플릿 경로 재설정
FRONTEND_DIR = BASE_DIR / "frontend"
STATIC_DIR = FRONTEND_DIR / "static"
TEMPLATES_DIR = FRONTEND_DIR / "templates"

app.mount("/static", StaticFiles(directory=str(STATIC_DIR)), name="static")
templates = Jinja2Templates(directory=str(TEMPLATES_DIR))

# 환경 설정 검증 (보안 시크릿 키 등)
# SETTINGS = get_settings()
```

### 3. 서비스 레이어 분리를 통한 엔드포인트 단순화

기존에 라우터 함수 내부에 작성되어 있던 성분 분석 알고리즘을 `app/services/ingredient_matcher.py`로 분리하여 라우터의 책임을 단순화했습니다.

```python
# web/backend/app/services/ingredient_matcher.py

from typing import List, Dict

class IngredientMatcher:
    """
    OCR 추출 텍스트와 전성분 DB 데이터를 비교 분석하는 비즈니스 로직 서비스
    """
    def __init__(self, standard_allergens: List[str]):
        self.allergens = standard_allergens

    def match_ingredients(self, raw_ocr_text: str) -> Dict[str, List[str]]:
        # 성분 정제 및 알레르기 유발 성분 필터링 비즈니스 로직
        extracted_tokens = [t.strip() for t in raw_ocr_text.split(",") if t.strip()]
        detected_allergens = [token for token in extracted_tokens if token in self.allergens]
        
        return {
            "all_ingredients": extracted_tokens,
            "detected_allergens": detected_allergens
        }
```

## 💡 돌아보며 배운 점 (회고)

프로젝트 규모가 작을 때는 단일 디렉토리에 코드를 몰아두는 것이 빠른 속도를 가져다주는 것처럼 보입니다. 그러나 기능이 추가될수록 모호한 boundary는 디버깅과 기능 추가의 속도를 오히려 저하시킨다는 점을 이번 마이그레이션을 통해 다시금 확인했습니다.

### 실질적 개선 효과
1. **유지보수 가독성 향상**: 라우터 코드가 단순해지고 비즈니스 로직이 `services/` 하위로 분리되면서, 성분 분석 알고리즘을 수정할 때 HTTP 레이어 코드를 건드리지 않아도 되게 되었습니다.
2. **프론트엔드 교체 용이성 확보**: 백엔드는 `web/backend` 내부로 완전히 격리되었으며, `web/frontend` 영역은 독립된 자원으로 존재하므로 향후 프론트엔드 스택 전환 시 백엔드 영향도를 최소화할 수 있는 토대를 마련했습니다.
3. **테스트 용이성**: `ingredient_matcher.py`와 같은 핵심 서비스 로직을 DB 연동이나 HTTP 요청 없이 독립적으로 단위 테스트(Unit Test)할 수 있게 되었습니다.

### 향후 보완할 점
현재는 Jinja2 템플릿 경로를 백엔드에서 직접 참조하여 렌더링하고 있지만, API 엔드포인트와 HTML 렌더링 라우트가 `app/routers` 내에 혼재되어 있습니다. 서비스가 확장된다면 순수 RESTful API 라우트(`/api/v1/...`)와 뷰 렌더링 라우트를 명확하게 분리하거나, 프론트엔드를 완전한 API 기반의 독립 애플리케이션으로 분리하는 단계를 고려해 볼 수 있을 것입니다. 

초기에 구조를 다듬는 과정은 다소 번거롭게 느껴지지만, 완성도 높은 애플리케이션으로 나아가기 위해 반드시 거쳐야 하는 단단한 인프라 작업임을 배웠습니다.
