> "사용자가 서비스의 가치를 경험하기도 전에 회원가입 폼을 내밀지 마라."

서비스 초기 온보딩 경험에서 가장 큰 이탈 원인 중 하나는 **'강제적인 회원가입'**입니다. 화장품 성분 분석 플랫폼 **PickSafe** 역시 서비스 초기에 "카메라로 성분을 스캔하거나 진단을 받기 전, 회원가입 절차에서 유저의 40% 이상이 이탈하는 문제"에 직면했습니다.

저희 엔지니어링 팀은 이 문제를 해결하기 위해 **로그인 없이 즉시 핵심 기능을 체험할 수 있는 '게스트 모드(Guest Mode)'**를 도입하고, 추후 회원 전환 시 비회원 데이터를 손실 없이 서버로 병합하는 **데이터 전이 파이프라인(Data Migration Pipeline)**을 구축했습니다. 

이번 포스팅에서는 왜 이 아키텍처를 선택했는지, 서버 리소스를 극단적으로 아끼면서도 매끄러운 UX를 구현한 과정과 기술적 Trade-off를 깊이 있게 다뤄보겠습니다.

## 🎯 문제 정의: 가입 허들과 DB 리소스 관리의 딜레마

게스트 모드를 구현하는 방식은 크게 두 가지로 나뉩니다.

1. **서버 세션/임시 회원 방식**: 비회원 방문 시 서버 DB에 Anonymous User 레코드를 생성하고 세션 쿠키 발급.
2. **클라이언트 사이드 방식**: 브라우저 로컬 저장소(`localStorage`)에 데이터를 유지하다가 회원가입 시점에 서버로 전송.

처음에는 implementation이 단순한 1번 방식을 고려했으나, 다음과 같은 심각한 엔지니어링 병목이 예견되었습니다.

- **유령 데이터(Zombie Data)로 인한 DB 오염**: 일회성으로 들어와 카메라만 한 번 켜보고 떠나는 불특정 다수 방문객의 데이터가 DB 레코드로 쌓이면서 Storage 및 Connection 비용이 급증합니다.
- **불필요한 DB Write I/O**: 게스트의 알레르기 설정, 찜한 화장품 목록이 업데이트될 때마다 서버 DB에 트랜잭션이 발생합니다.
- **가입 전환 시 데이터 손실 UX**: 게스트 상태에서 저장한 성분 및 상품 데이터가 회원가입 후 사라진다면 유저는 심각한 피로감을 느끼고 탈퇴하게 됩니다.

따라서 저희는 **"비회원 상태의 모든 인메모리/저장소 부담을 클라이언트(브라우저)로 위임하고, 회원가입이라는 '확정 이벤트'가 발생했을 때만 서버 트랜잭션을 실행한다"**는 원칙을 세웠습니다.

## 🏗️ 핵심 아키텍처 및 데이터 흐름

전체 아키텍처는 클라이언트의 `localStorage` 이벤트 모니터링과 백엔드의 `Guest-Convert API` 파이프라인으로 구성됩니다.

```mermaid
flowgraph TD
    subgraph Client ["Browser (Frontend)"]
        A["Guest User Interaction"] -->|1. Store Preferences| B["localStorage\n('guest_allergens', 'guest_saved_products')"]
        B -->|2. Trigger Signup/Login| C["Auth Form Submission"]
        C -->|3. Extract Payload| D["Payload Construction\n(Auth Data + Guest JSON)"]
    end

    subgraph Backend ["Server & DB Layer"]
        D -->|4. POST /auth/guest-convert| E["API Controller"]
        E -->|5. Validate & Sanitize| F["Service Layer"]
        F -->|6. Atomic Transaction| G[("Main Database")]
    end

    subgraph PostProcess ["Client Cleanup"]
        G -->|7. 200 OK Response| H["Clear localStorage"]
        H -->|8. Set Auth Token| I["Active Authenticated Session"]
    end
```

### 아키텍처 핵심 포인트
1. **격리성(Isolation)**: 게스트 상태에서는 백엔드 DB와 어떠한 세션/I/O 커넥션도 맺지 않습니다.
2. **원자성(Atomicity)**: 데이터 이관 API(`/auth/guest-convert`) 호출 시, 회원 계정 생성 및 게스트 데이터 병합 작업이 **단일 DB 트랜잭션** 내에서 처리됩니다.
3. **복구 가능성(Resiliency)**: 서버 측 이관 처리가 완전히 성공(HTTP 200 OK)한 것을 확인한 뒤에만 클라이언트의 `localStorage`를 비웁니다.

## ⚖️ 대안 비교 및 Trade-off 분석

클라이언트 저장소를 선택함에 있어 여러 스토리지 매체와 방식을 비교 검토했습니다.

| 항목 | Session Storage | IndexedDB | **localStorage (선택)** | 서버 측 Anonymous DB |
| :--- | :--- | :--- | :--- | :--- |
| **데이터 영속성** | 탭 닫을 시 삭제 (X) | 영구 보관 (O) | **영구 보관 (O)** | 영구 보관 (O) |
| **API 복잡도** | 매우 낮음 | 높음 (비동기, DB 객체) | **매우 낮음 (동기형)** | 보통 (REST/GraphQL) |
| **서버 I/O 비용** | 없음 | 없음 | **없음** | 매우 높음 (DB 쓰기 발생) |
| **용량 한계** | ~5MB | ~250MB+ | **~5MB (텍스트)** | 제한 없음 |
| **보안 (XSS 위험)** | 스크립트 접근 가능 | 스크립트 접근 가능 | **스크립트 접근 가능** | Session Cookie로 방어 가능 |

### 🔍 Trade-off 관점에서의 의사결정
- **용량 한계 (~5MB) 극복**: PickSafe 게스트 모드에서 저장하는 데이터는 `성분 ID 배열(Array<int>)` 및 `상품 ID 배열(Array<int>)`입니다. 아무리 많이 저장해도 수십 KB를 넘지 않으므로 `localStorage` 용량 한계는 전혀 문제가 되지 않았습니다.
- **XSS 보안 위험 방어**: `localStorage`는 XSS 공격에 취약할 수 있습니다. 따라서 **JWT 토큰이나 민감한 개인정보는 절대로 `localStorage`에 저장하지 않으며**, 오직 성분 PK 및 상품 PK 등 공개된 식별자 값만 JSON Array 형태로 인코딩하여 보관하도록 규칙을 수립했습니다.

## 🚀 구현 핵심 코드 및 트러블슈팅 경험

### 1. Frontend: 게스트 데이터 관리 및 안전한 백엔드 전송 (`auth.js`)

클라이언트에서는 localstorage 데이터를 읽어와 유효성을 검증하고 API 요청 구조로 변환합니다.

```javascript
// static/js/auth.js

const GUEST_KEYS = {
  ALLERGENS: 'guest_allergens',
  SAVED_PRODUCTS: 'guest_saved_products'
};

class GuestDataManager {
  // 로컬 스토리지 데이터 안전 조회 및 파싱
  static getGuestData() {
    try {
      const allergens = JSON.parse(localStorage.getItem(GUEST_KEYS.ALLERGENS) || '[]');
      const savedProducts = JSON.parse(localStorage.getItem(GUEST_KEYS.SAVED_PRODUCTS) || '[]');
      
      return {
        guest_allergens: Array.isArray(allergens) ? allergens : [],
        guest_saved_products: Array.isArray(savedProducts) ? savedProducts : []
      };
    } catch (e) {
      console.error("Localstorage parsing error, falling back to empty arrays", e);
      return { guest_allergens: [], guest_saved_products: [] };
    }
  }

  // 데이터 동기화 완료 후 정교한 삭제
  static clearGuestData() {
    localStorage.removeItem(GUEST_KEYS.ALLERGENS);
    localStorage.removeItem(GUEST_KEYS.SAVED_PRODUCTS);
  }
}

// 회원가입 및 게스트 전환 API 호출 함수
async function registerAndConvertGuest(signupFormData) {
  const guestPayload = GuestDataManager.getGuestData();
  
  const requestBody = {
    ...signupFormData,
    guest_data: guestPayload
  };

  try {
    const response = await fetch('/api/v1/auth/guest-convert', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(requestBody)
    });

    if (!response.ok) {
      throw new Error(`Server returned status ${response.status}`);
    }

    const result = await response.json();
    
    // 🔥 중요: 서버 동기화 성공 확인 후 클라이언트 데이터 삭제
    GuestDataManager.clearGuestData();
    
    return result;
  } catch (error) {
    // 네트워크 실패 시 localStorage 데이터를 유지하여 차후 재시도 가능하도록 보장
    console.error("Failed to migrate guest data:", error);
    throw error;
  }
}
```

### 2. Backend: 원자적 데이터 병합 및 중복 제거 (`auth_service.py`)

백엔드에서는 클라이언트가 보낸 데이터와 기존 DB 레코드 간의 **중복(Conflict)**을 방지하고 트랜잭션 내에서 안전하게 이관합니다.

```python
# app/services/auth_service.py

from typing import Dict, List
from sqlalchemy.orm import Session
from app.models import User, UserAllergen, UserSavedProduct
from app.core.config import SETTINGS

    """
    guest_allergens = set(guest_data.get("guest_allergens", []))
    guest_products = set(guest_data.get("guest_saved_products", []))

    try:

        existing_allergens = set(
            row.allergen_id for row in db.query(UserAllergen.allergen_id).filter_by(user_id=user_id).all()
        )
        new_allergens = guest_allergens - existing_allergens

        new_allergen_records =
