화장품 성분 분석 서비스인 PickSafe를 개발하면서, 초기 모놀리식 구조에서 서비스 기능이 확장됨에 따라 프로젝트 폴더 구조의 복잡도가 급격히 증가하는 문제를 마주했습니다. 

스캔 OCR 로직, 성분 매칭 알고리즘, 사용자 마이페이지 및 어드민 관리 기능 등이 추가되면서 루트 디렉토리에 백엔드 파이썬 코드와 프론트엔드 정적 파일이 엉키기 시작했습니다. 향후 프론트엔드 아키텍처를 React/Next.js 기반으로 이관할 가능성까지 염두에 두고, 레이어 간 책임 분리와 유지보수성 향상을 위해 프로젝트 디렉토리 구조를 대대적으로 재설계하고 마이그레이션을 진행했습니다.

이 글에서는 해당 구조 개선을 고민했던 배경과 기술적 대안 비교, 그리고 실행 과정에서 발생했던 이슈들을 담담하게 정리해보려 합니다.

---

## 🎯 마주한 고민과 문제 배경

초기 MVP 단계에서는 빠른 검증을 위해 단일 루트 디렉토리 근처에 `app.py`, `database.py`, `templates/`, `static/` 등을 모아두고 개발을 진행했습니다. 그러나 서비스가 구체화되면서 다음과 같은 문제점이 명확해졌습니다.

1. **책임 경계의 모호함**
   - Jinja2 템플릿 파일과 정적 자원(CSS/JS), 그리고 데이터베이스 모델 및 스캔 비즈니스 로직이 동일 레이어 수준에 흩어져 있어 코드 탐색 비용이 높아졌습니다.
2. **비즈니스 로직과 라우팅의 결합**
   - OCR 엔진 연동(`ocr_service.py`)과 성분 데이터 매칭(`ingredient_matcher.py`) 알고리즘이 엔드포인트 내부에 섞이면서, 동일한 비즈니스 로직을 API 엔드포인트와 HTML 렌더링 라우터 양쪽에서 중복 호출하거나 깔끔하게 재사용하기 어려웠습니다.
3. **향후 프론트엔드 이관의 걸림돌**
   - 현재는 Jinja2 템플릿 기반 렌더링을 사용하고 있지만, 향후 모바일 앱 대응이나 클라이언트 사이드 렌더링(CSR) 프레임워크 도입 시 백엔드 코드와 정적 리소스가 결합되어 있다면 분리 작업에 큰 공수가 들 것으로 예상되었습니다.

## ⚖️ 기술적 대안 비교 및 선택 이유

디렉토리 구조 변경을 결정한 후, 프로젝트 구조를 어떤 수준으로 격리할지 세 가지 대안을 두고 비교했습니다.

| 구분 | 대안 1: 기존 층위 유지 (단일 루트) | 대안 2: 모놀리식 내 모듈 격리 (`web/backend`, `web/frontend`) | 대안 3: 멀티 레포지토리 완전 분리 (Git Repo 분리) |
| :--- | :--- | :--- | :--- |
| **구조** | 루트에 `app/`, `templates/` 혼재 | `web/` 하위에 `backend/`, `frontend/` 독립 구성 | 백엔드/프론트엔드 Git 레포지토리 별도 생성 |
| **장점** | 초기 설정 불필요, 이동 공수 없음 | **단일 레포 관리 용이성 유지 + 책임 경계 명확화** | 완전한 독립 배포 및 기술 스택 자유도 제공 |
| **단점** | 파일 증가 시 스파게티화, 유지보수 한계 | Uvicorn 및 템플릿 참조 경로 재설정 필요 | CI/CD 파이프라인 개별 구축 필요, 현 단계에서 오버헤드 큼 |
| **결정** | ❌ 탈락 | **✅ 최종 선택** | ❌ 탈락 (향후 서비스 확장 시 검토) |

**선택 이유:**
현 단계에서 멀티 레포지토리로 분리하는 것은 배포 파이프라인 및 개발 오버헤드가 과도하다고 판단했습니다. 따라서 **단일 레포지토리 내에서 물리적 계층을 `web/backend`와 `web/frontend`로 명확히 분리하는 대안 2**를 선택했습니다. 

이를 통해 백엔드는 FastAPI 아키텍처 규칙(Model-Service-Router)에 집중하고, 프론트엔드는 정적 자원과 템플릿을 독립적으로 관리할 수 있게 되었습니다.

## 💻 핵심 구현 및 트러블슈팅

### 1. 물리적 경로 변경에 따른 FastAPI 애플리케이션 진입점 및 경로 설정

폴더 구조 이동 후 `main.py`에서 정적 파일과 Jinja2 템플릿 디렉토리를 바인딩할 때 경로 탐색 오류가 발생했습니다. 기존 상대 경로 방식은 서버를 실행하는 위치(CWD)에 따라 경로가 깨지는 문제가 있었습니다.

이를 해결하기 위해 `pathlib.Path`를 사용하여 `main.py` 위치 기준으로 정적 파일 및 템플릿 절대 경로를 계산하도록 정제했습니다.

```python
# web/backend/app/main.py
from pathlib import Path
from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

# web/backend/app/main.py 파일의 위치 기준으로 프로젝트 루트 계산
BASE_DIR = Path(__file__).resolve().parent.parent.parent  # web/ 디렉토리 지점

app = FastAPI(title="PickSafe API")

# 프론트엔드 정적 자원 및 템플릿 경로 바인딩
FRONTEND_DIR = BASE_DIR / "frontend"
STATIC_DIR = FRONTEND_DIR / "static"
TEMPLATES_DIR = FRONTEND_DIR / "templates"

app.mount("/static", StaticFiles(directory=str(STATIC_DIR)), name="static")
templates = Jinja2Templates(directory=str(TEMPLATES_DIR))
```

### 2. 파이썬 패키지 경로(PYTHONPATH) 및 Uvicorn 구동 트러블슈팅

구조 마이그레이션 직후 `uvicorn app.main:app --reload` 명령을 루트 디렉토리에서 실행할 때 `ModuleNotFoundError: No module named 'app'` 에러가 마주쳤습니다.

* **원인:** 파이썬 인터프리터가 `app` 패키지를 찾기 위한 검색 경로에 `web/backend` 디렉토리가 포함되지 않았기 때문입니다.
* **해결 방안:**
  프로젝트 루트에서 실행할 경우 `PYTHONPATH` 환경변수를 명시하거나, `web/backend` 디렉토리 내부로 이동하여 Uvicorn을 실행하도록 실행 가이드를 표준화했습니다.

```bash
# 해결 방법 A: 백엔드 디렉토리 내부로 이동하여 실행
cd web/backend
uvicorn app.main:app --reload

# 해결 방법 B: 루트 디렉토리에서 PYTHONPATH 지정 후 실행
PYTHONPATH=web/backend uvicorn app.main:app --reload
```

## 💡 돌아보며 배운 점 (회고)

디렉토리 구조 마이그레이션 작업을 마치며 얻은 주요 교훈은 다음과 같습니다.

1. **레이어드 아키텍처(Layered Architecture)의 이점 체감**
   - 비즈니스 로직(`services`)과 데이터 모델(`models`), 뷰 라우팅(`routers`)을 명확히 분리함으로써 코드의 응집도가 높아졌습니다. 예를 들어, 성분 위험도 분석 알고리즘(`ingredient_matcher.py`)을 수정할 때 더 이상 라우터 코드를 훑어볼 필요 없이 서비스 레이어에만 집중할 수 있게 되었습니다.

2. **초기 아키텍처 정의의 중요성**
   - 개발 초기 빠른 기능 작성을 우선하더라도, 디렉토리 경계 설정은 가급적 일찍 다듬는 것이 비용을 줄이는 길임을 배웠습니다. 라우터 파일 내 수십 개의 임포트 경로를 일일이 재조정하는 과정에서 정적 타입 체크 및 단위 테스트의 필요성을 다시 한번 확인했습니다.

3. **향후 과제**
   - 현재는 `web/frontend` 내부의 Jinja2 템플릿을 FastAPI 애플리케이션이 직접 렌더링하고 있습니다. 백엔드가 순수한 Restful API 전용으로 동작하도록 엔드포인트를 완전히 분리하고, 프론트엔드를 독립적인 SPA/SSR 환경으로 마이그레이션하기 위한 기초 작업을 차근차근 진행할 예정입니다.
