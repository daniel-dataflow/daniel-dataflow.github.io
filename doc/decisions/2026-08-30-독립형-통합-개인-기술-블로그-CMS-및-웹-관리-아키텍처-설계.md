# [ADR-001] 독립형 통합 개인 기술 블로그 CMS 및 웹 관리 아키텍처 설계

- **상태 (Status)**: 채택됨 (Accepted)
- **일자 (Date)**: 2026-08-30
- **작성자 (Author)**: Daniel (Backend & Systems Architect)
- **대상 시스템**: `daniel-dataflow.github.io` (GitHub Pages Hugo Blog) & PickSafe Admin Blog Studio CMS

## 1. 배경 및 문제 정의 (Context & Problem Statement)

기존 기술 블로그 운영 및 배포 환경은 특정 프로젝트(PickSafe)의 개발일지(ADR) 자동 배포에 초점이 맞추어져 있어 다음과 같은 구조적 한계와 비일관성이 존재했습니다:

1. **단일 프로젝트 종속성**:
   - 블로그 상단 스킨 배너 뱃지 및 메타데이터가 `PickSafe Engineering Archive`로 하드코딩되어 있어, Daniel 개인의 다양한 엔지니어링 프로젝트(`Lookalike`, 데이터 파이프라인, 아키텍처, 알고리즘 등)를 통합 수용하지 못함.
2. **코드 및 로컬 터미널 의존성**:
   - 사이트 소개글, 작성자 프로필, 상단 뱃지, 카테고리 추가, 글 삭제 등을 수행할 때마다 로컬 환경에서 코드를 수정하고 깃 명령어를 입력해야 하는 유지보수 병목 발생.
3. **100% 웹 관리(CMS) 요구**:
   - 웹 브라우저(Admin GUI) 상에서 **글 작성/수정/삭제, 카테고리 동적 추가, 배너 및 프로필 아바타 교체, 사이트 전역 브랜딩 설정**을 자유롭게 수행할 수 있는 독립형 통합 CMS가 필수적임.

---

## 2. 핵심 의사결정 요인 (Decision Drivers)

- **범용성 (Decoupling)**: PickSafe 외 다수의 프로젝트 및 기술 아카이브를 카테고리별로 무한 확장 가능한 통합 포털 구조.
- **100% 웹 관리성 (Zero-Code Web CMS)**: 브라우저에서 사이트 문구(헤더/소개/SNS), 카테고리, 포스트 CRUD, 이미지를 원클릭으로 관리.
- **인프라 비용 0원 및 유지보수 제로**: 별도 유료 서버나 DB 인스턴스 없이 GitHub의 글로벌 Fastly CDN과 저장소를 단일 진실 공급원(Single Source of Truth)으로 활용.
- **데이터 영속성 및 링크 유실 방지**: 외부 이미지 서버 정책 변경이나 무료 티어 만료로 인한 링크 깨짐을 방지하고, 마크다운과 이미지를 깃 저장소 내에서 영구 보존.

## 3. 검토된 아키텍처 대안 및 비교 분석 (Considered Options)

```mermaid
flowchart LR
    subgraph OptionA [Option A: Git-based Headless CMS (선택됨)]
        A1[어드민 웹 CMS] -->|GitHub REST API| A2[(GitHub Repository<br>Single Source of Truth)]
        A2 -->|GitHub Actions| A3[GitHub Pages 글로벌 CDN]
    end

    subgraph OptionB [Option B: External DB & Image Server]
        B1[어드민 웹 CMS] -->|SQL| B2[(NeonDB / Postgres)]
        B1 -->|Upload| B3[(AWS S3 / Cloudinary)]
        B2 -->|Sync Batch| B4[GitHub Pages]
    end
```

### ① 데이터 저장소: Git 기반 Headless CMS vs NeonDB (PostgreSQL)

| 비교 항목 | Option A: Git 기반 Headless CMS (채택) | Option B: NeonDB(Postgres) 하이브리드 |
| :--- | :--- | :--- |
| **데이터 진실 공급원** | GitHub 저장소 (`hugo.yaml`, `_index.md`, `posts/*.md`) | NeonDB 데이터베이스 |
| **동기화 및 정합성** | 100% 일치 (저장소와 배포 환경이 직접 연결) | DB ↔ Git 간 데이터 불일치(Split-brain) 위험 존재 |
| **운영 비용 & 복잡도** | **0원 / 서버리스 / 무중단** | DB 커넥션 풀 관리, 마이그레이션 관리 필요 |
| **백업 & 롤백** | **Git 커밋 히스토리가 곧 무결점 감사 로그 및 롤백 체계** | DB 스냅샷 백업 별도 설정 필요 |
| **결론** | **정적 사이트 제네레이터(Hugo)와 완벽히 호환되는 최적의 아키텍처로 채택** |

### ② 미디어 저장소: GitHub Pages CDN 저장소 vs 외부 이미지 서버 (S3 / Cloudinary)

- **외부 이미지 서버의 문제점**: 무료 티어 용량/트래픽 한계, 계정 만료 시 블로그 이미지 일괄 깨짐 현상, 별도 인증 키 관리 부담.
- **Git 내부 저장소(`static/blog_images/`) 채택 이유**:
  1. GitHub Pages가 Fastly 글로벌 엣지 CDN을 통해 전 세계에 무료/초고속 서빙.
  2. 마크다운 문서와 해당 이미지가 같은 레포지토리에 커밋되어 평생 유실되지 않음.
  3. 에디터 드래그앤드롭 시 GitHub REST API를 통해 자동 커밋되도록 연동 완료.

## 5. 세부 기능 구현 현황 (Implementation Details)

### 1) 사이트 브랜딩 및 메타데이터 전역 설정 (`/api/blog/settings`)
- 상단 배너 초록 뱃지(`banner_badge`), 블로그 타이틀, 서브타이틀, SEO 요약문, 사이드바 프로필(닉네임, 역할, 자기소개), 문의 이메일, 깃허브 URL을 웹 폼에서 수정 후 GitHub에 즉시 배포.

### 2) 포스트 전체 라이프사이클 관리 (Full CRUD)
- **생성 (Create)**: `✨ 새 글 작성` 버튼으로 빈 에디터에서 마크다운 작성 또는 타 블로그 글 복사/붙여넣기 발행.
- **조회 (Read)**: `[📑 기발행 글]` 탭을 통해 발행된 전체 글 실시간 탐색.
- **수정 (Update)**: 기발행 글 클릭 시 에디터로 즉시 원문 로드되어 내용 수정 후 재발행.
- **삭제 (Delete)**: 기발행 글 목록의 `🗑️` 삭제 버튼을 통해 로컬 및 GitHub 원격 저장소에서 완전 삭제 (`DELETE /api/blog/posts`).

### 3) 카테고리 및 미디어 웹 관리
- **카테고리**: 신규 카테고리 생성 시 GitHub에 `content/posts/<slug>/_index.md` 자동 커밋.
- **스킨 배너 & 아바타**: 상단 배너(`banner.jpg`) 및 프로필 아바타(`profile.jpg`) 웹 업로드 지원.
- **본문 이미지**: 에디터 내 드래그앤드롭 및 `Ctrl+V` 붙여넣기 시 `static/blog_images/` 자동 업로드 및 마크다운 태그 자동 삽입.

## 6. 도입 성과 및 기대 효과 (Consequences)

1. **독립성과 확장성 확보**:
   - PickSafe 프로젝트 종속에서 완전히 벗어나, `PickSafe`, `Lookalike`, `DataPipeline`, `Architecture` 등 무제한 카테고리를 총괄하는 Daniel의 대표 기술 블로그로 자리매김.
2. **개발 생산성 극대화**:
   - VS Code를 열거나 Git 커맨드를 칠 필요 없이 웹 브라우저에서 글 작성, 수정, 삭제, 배너 변경을 1초 만에 수행.
3. **비용 0원 & 완벽한 데이터 보존**:
   - 별도 유료 서버/DB 없이 GitHub 생태계(Actions, Pages, REST API, CDN)를 극대화하여 비용 0원에 평생 유지 가능한 견고한 아키텍처 완성.
